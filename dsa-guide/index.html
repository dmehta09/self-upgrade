How to think about any coding problem

Strong candidates don't memorise 500 problems. They learn to recognise which of a dozen patterns a question is really asking for. Almost everything in this guide is one step of this picture — keep it in mind.

Steps 2 and 3 are the whole game. Learn the patterns and the right data structure, and the code almost writes itself.
Think of a toolbox analogy

Imagine a carpenter with a small toolbox. They don't own a different tool for every job — they own a saw, a hammer, a drill, and they know which one a job needs. A pattern is a tool. There are only about a dozen. Once you can look at a problem and think "that's a job for the two-pointers tool," you've done the hard part.

What you'll learn

Read Big-O on sight

What O(1), O(log n), O(n) and O(n²) actually feel like — and how to say the cost of your solution out loud, the thing interviewers always ask.

Know your structures

Arrays, hash maps, linked lists, stacks, queues, trees, heaps and graphs — what each is great at, and what it's slow at.

Recognise the pattern

The dozen patterns that cover most interviews — two pointers, sliding window, BFS/DFS, dynamic programming — and the tells that point to each.

Solve ~30 key problems

A curated, high-signal set — not 500. Each one teaches a reusable idea, with hints you reveal only when you're stuck.

See it move

Step-through animations show exactly how pointers slide, how a tree is walked, how a search halves the haystack — built for visual learners.

Keep a cheat-sheet

One page of Big-O cost tables per structure plus a plain-words glossary — for the night before the interview.
