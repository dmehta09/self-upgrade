Big-O & complexity

Big-O sounds like maths homework, but it answers one plain question: as the input gets bigger, how fast does the work pile up? That's it. By the end of this page you'll read it on sight, picture each class with an everyday story, and say the cost of your own code out loud — the thing interviewers always ask.

01  What Big-O means

Big-O describes how the amount of work grows as the input grows. It deliberately ignores the small stuff: we drop constant factors and keep only the biggest term, because for a large input that term dwarfs everything else.

A recipe for 2 people vs 200 analogy

You can cook dinner for two. Now cook for two hundred. Some steps barely change — you preheat the oven once no matter how many guests. Other steps scale with the headcount — you peel a potato per person. And some explode — if every guest must clink glasses with every other guest, the toasts grow far faster than the crowd. Big-O is just naming which kind of step dominates as the party grows. The fixed steps (the oven) are the "constants" we ignore; the per-person and per-pair steps are what we keep.

So we don't say "about 3n + 7 steps." We say O(n) — "if the list doubles, the work roughly doubles." The + 7 and the 3 wash out at scale. Big-O is about the shape of the growth, not an exact stopwatch.

02  The complexity zoo

You'll meet the same handful of growth curves over and over. Here's each one in a single plain sentence, with a picture to make it stick:

O(1)
Constant — the work doesn't grow at all. Like flipping a light switch: same effort whether the room is tiny or huge.
O(log n)
Logarithmic — each step throws away half of what's left. Like finding a name in the phone book: each guess discards half the pages.
O(n)
Linear — look at every item once. Like reading every page of a book to count how many say "the".
O(n log n)
Linearithmic — do a little log-n work for each of the n items. The speed of a good sort.
O(n²)
Quadratic — every item meets every other item. Like a party where everyone shakes hands with everyone else.
O(2ⁿ)
Exponential — each extra item doubles the work. Like trying every on/off combination of n switches. Only fine for tiny n.

03  Time vs space

Big-O measures two different things, and interviewers ask about both. Time complexity is how the number of steps grows. Space complexity is how much extra memory you use as the input grows — beyond the input itself.

The classic split is in-place versus making a copy. Reversing a list by swapping its ends needs only two index variables, so it's O(1) extra space. Building a brand-new reversed list needs room for every element, so it's O(n) extra space — even though both take O(n) time.

Count only the EXTRA memory

The input list is already there — it doesn't count toward space. Only count what your algorithm adds: a couple of variables is O(1); a whole second list or a hash map holding every item is O(n). When two solutions tie on time, the one with smaller space usually wins the interview.

04  How to say it out loud

Interview skill Easy ~8 min O(n) vs O(1) lookup

Knowing the cost isn't enough — you have to state it. The formula is simple: name the time, give the one-line reason, then name the space and its reason.

Reading a contents page vs a phone's contacts analogy

To check if a friend is in a paper guest-list, you read down the whole page, name by name — the longer the list, the longer it takes. To check if they're in your phone, you just type the name and it jumps straight there, no matter how many contacts you have. A plain list is the paper page (scan everything, O(n)); a set is the phone (jump straight to it, O(1) on average), because it remembers where each item lives by hashing it.

Say it like this: "This is O(n) time because we pass over the list once, and O(1) space because we only keep a couple of variables." Short, specific, done. Here's the list-vs-set difference you can run yourself:

Way to check "is X present"CostWhy
x in a_listO(n)Python walks the list item by item until it finds x or runs out.
x in a_setO(1)A set hashes x and jumps straight to its bucket — no scanning.

You'll check "is this value present?" thousands of times on a big unsorted list. What's faster: scanning the list each time, or putting the items in a set first and checking that?

Right. Scanning costs O(n) every time. A set hashes the value and jumps to it in O(1) on average, so for many lookups it wins easily. You pay O(n) once to build the set, then every check is effectively free.
