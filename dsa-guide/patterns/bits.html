Bit Manipulation

Every number is secretly a row of on/off switches, and three tiny tricks on that row solve a surprising family of interview problems in O(1) space. Learn the switch-board view once, and operators that looked like alien runes — ^, &, << — turn into plain sentences.

00  The idea

Inside the computer, the number 13 isn't a "13" at all — it's the binary row 1101. Read it like a switch panel labelled 8, 4, 2, 1: the 8-switch, the 4-switch and the 1-switch are on, and 8 + 4 + 1 = 13. Every bit operator is just a rule for combining or sliding two rows of switches.

A row of light switches analogy

Picture a wall of light switches labelled ... 16, 8, 4, 2, 1. The number 13 is just the switches 8, 4 and 1 turned on (1101). Once you see numbers this way, every "weird" bit operator becomes a plain sentence about switches: "on where both are on", "flip them all", "slide the whole row one step".

The operators, as sentences about switches

OperatorIn plain wordsTiny example
& (AND)On only where both rows are on — a stencil/mask.0b0110 & 0b0011 = 0b0010
| (OR)On where either row is on.0b0110 | 0b0011 = 0b0111
^ (XOR)On where the rows differ — the difference detector.0b0110 ^ 0b0011 = 0b0101
~ (NOT)Flip every switch.~0b0110 = -7 (Python's signed view)
<< (left shift)Slide the row left — ×2 per step.0b0011 << 1 = 0b0110
>> (right shift)Slide right — ÷2 per step, dropping the last switch.0b0110 >> 1 = 0b0011

The two house tricks

x ^ x == 0 and x ^ 0 == x — XOR cancels pairs, and order never matters. Two identical rows differ nowhere (all off), and XOR-ing with the all-off row changes nothing — so in a long XOR chain, every pair quietly annihilates and only the unpaired value survives.

n & (n - 1) turns OFF the lowest on-switch. Subtracting 1 flips the trailing zeros and that lowest 1; AND-ing with the original keeps everything above it untouched and kills exactly that one switch.

When to reach for bits

These tells in a problem statement should make your hand twitch toward the switch panel:

"appears exactly twice except one"
Pairs that should cancel — that's XOR's whole personality.
"without extra memory"
An O(1)-space demand where a counting dict feels natural is a strong bits hint.
"count the 1s / power of two"
Hamming weight, n & (n - 1), and friends.
Parity, toggling, sets of flags
Odd/even via the last bit, on/off toggles via XOR, or a mask of seen-letters packed into one integer.

What is 0b1010 ^ 0b1010?

Right. XOR lights up only where the two rows differ — and identical rows differ nowhere, so every switch goes off: 0. That cancellation is the engine of Single Number, our first problem below.

01  Single Number

Bits Easy ~10 min O(n) time · O(1) space

Every number in the list appears exactly twice, except one loner — find it in O(n) time and O(1) space. The space bound is the whole puzzle: a counting dict finds it easily, but that's O(n) extra memory.

Glow-sticks at a party analogy

Everyone at a party wears a glow-stick pattern, and pairs cancel each other's light when they hug. Let everybody hug their twin — every paired glow goes dark. After all the hugging, the only glow left in the room is the loner's. XOR is the hug.

How to solve it

Fold XOR over the whole list: start an accumulator at 0 and XOR every number into it. Because XOR is order-blind and pairs cancel, the accumulator ends up holding exactly the unpaired number. The one-liner version is functools.reduce(operator.xor, nums, 0) — but write the loop in an interview and say the cancellation argument out loud.

Compare the two baselines you should reject by name: a counting dict is O(n) space (it might store every distinct number), and sorting first to find the odd one out costs O(n log n) time. The XOR fold beats both at once.

MeasureCostWhy
TimeO(n)One pass, one XOR per number.
SpaceO(1)A single integer accumulator — no dict, no sorting.

New to this notation? See the Big-O cheat-sheet.

The famous follow-up: "every number appears THREE times"

Triples don't cancel under XOR (x ^ x ^ x == x, not 0), so this trick breaks. The known approach counts each bit position across all numbers mod 3 — the loner's bits are whatever doesn't divide evenly. Name-drop it if asked; you don't need to derive it here.

The two 1s in [4, 1, 2, 1, 2] aren't next to each other. Why doesn't the ORDER of the XORs matter?

Exactly. You can mentally reshuffle the chain into (1 ^ 1) ^ (2 ^ 2) ^ 4 — commutativity and associativity make that legal — and the pairs collapse to 0 wherever they started. No sorting, no adjacency needed.
Stuck? Reveal a hint hint

You need a "container" where adding a number twice is the same as never adding it. XOR is exactly that: x ^ x == 0 and x ^ 0 == x. Start at 0, XOR everything in, and see what's left.

One variable, one pass. Every paired number hugs its twin somewhere along the chain and goes dark; acc ends as the loner. The one-liner functools.reduce(operator.xor, nums, 0) does the same fold.

02  Number of 1 Bits

Bits Easy ~10 min O(k) time (k = on-bits)

Count the on-switches in a number — its Hamming weight. 13 is 1101, so the answer is 3. The clever loop runs once per ON bit, not once per bit.

Slam off the lowest switch analogy

Instead of walking the wall and checking all 32 switches one by one, you have a magic move that always slams OFF the lowest on-switch — that move is n & (n - 1). Count how many slams it takes until the room is dark. Three switches on? Three slams. Done.

How to solve it

Loop while n is non-zero: slam with n &= n - 1 and add one to a counter. When n hits 0 the counter is the Hamming weight. The pragmatic Python one-liner is bin(n).count("1") — interviewers accept it happily, but only after you've shown you know the slam trick and why it loops only k times.

MeasureCostWhy
TimeO(k)k = number of 1-bits. Each slam removes exactly one, so the loop runs k times — not once per bit.
SpaceO(1)Just n and a counter.

What does n & (n - 1) == 0 (for n > 0) test?

Right. The slam removes exactly one on-switch. If a single slam leaves the room completely dark, there was only one switch on to begin with — and one-switch numbers (1, 2, 4, 8, ...) are exactly the powers of two. A classic one-line interview check.
Stuck? Reveal a hint hint

You don't need to inspect every bit. Each round, do n &= n - 1 — it always switches off exactly the lowest 1 — and count the rounds until n becomes 0.

The loop body is the magic move; the loop count is the answer. For 16 (a power of two) one slam darkens the whole room — which is exactly why the power-of-two check from the quiz works.

03  Counting Bits

Bits Medium ~20 min O(n) time

For every i from 0 to n, output how many 1-bits i has — in O(n) total, not O(n log n). The trick is realizing the answers reuse each other: this is bits meeting Dynamic Programming.

Every row is a shorter row plus maybe one switch analogy

i's switch row is just i shifted right once, with possibly one extra switch — the last one. So i's count = count of i // 2, plus 1 if i is odd. And here's the gift: you've already computed i // 2's answer, because it's a smaller number. Just read it off the table.

How to solve it

Build the table bottom-up: dp = [0] * (n + 1), then for each i from 1 to n set dp[i] = dp[i >> 1] + (i & 1). The shift drops the last switch (giving a smaller, already-solved number) and i & 1 asks whether that dropped switch was on. Each entry costs O(1), so the whole table costs O(n) — beating the "call Hamming weight n times" plan, which is O(n log n).

MeasureCostWhy
TimeO(n)One O(1) table lookup + add per number.
SpaceO(n)The dp table — but the output IS the space, so you can't do better.

Why is dp[i >> 1] already correct when we need it?

Exactly. Halving a positive number always makes it smaller, so the entry we read sits to the left of the one we're writing. Filling left-to-right guarantees it's finished. That "dependencies point backwards" check is the heart of every bottom-up DP.
Stuck? Reveal a hint hint

Don't count each number's bits from scratch. Relate i to i >> 1: dropping the last bit gives a smaller number whose answer is already in your table; the dropped bit itself is i & 1. Add the two.

Show the solution & run it solution
counting_bits.py
[0, 1, 1, 2, 1, 2, 2, 3, 1]

One line of recurrence does all the work: shift right to find the smaller, already-solved cousin; AND with 1 to see if the dropped switch was on. Bits supplied the relationship, DP supplied the table — a tidy little crossover episode.
