Patterns · graphs

Graphs

A graph is just dots joined by lines: the dots are nodes (things) and the lines are edges (connections). Once you can explore one, a whole shelf of problems opens up — including many "grid" puzzles that are secretly graphs in disguise. Let's learn the two ways to walk a graph, then solve three classics.

00  The idea

Picture a map of towns joined by roads. Each town is a node; each road is an edge. Almost every graph question is really one question: "starting here, how do I visit everywhere I can reach?" You have two ways to wander.

BFS
Breadth-first search uses a queue (a waiting line). It explores in rings: all towns one road away, then two roads away, then three. Because it grows outward evenly, the first time it reaches a town it used the fewest hops — so BFS finds shortest paths (in hops).
DFS
Depth-first search follows one road as far as it goes, then backtracks and tries the next. It's natural to write with recursion (a function that calls itself). Great for "visit everything" and "is there a path".

Both share one golden rule: keep a seen set so you never visit a node twice. Without it, a loop of roads traps you forever.

A map of towns and roads analogy

Think of a road map. Towns are the dots, roads are the lines. To explore from your home town you can ripple outward street by street (BFS — the queue), or pick one road and drive until it dead-ends, then back up and try another (DFS — recursion). Either way, you cross off each town as you arrive so you don't drive in circles.

When you're really looking at a graph

The tells are easy once you know them:

Things + connections
People and friendships, cities and flights, tasks and "must-come-before" rules — anything pairs up.
A grid of cells
Each cell is a node; its up/down/left/right neighbours are edges. "Islands", "rotting oranges", "maze" — all grid-graphs.
"Reach / connected / shortest hops"
Questions about what you can get to, how groups clump, or the fewest steps between two points.
"No cycles allowed"
Dependency or ordering puzzles ask whether the connections form a loop.
Trees are graphs too

A tree is just a graph with no loops and one clear top. So the BFS/DFS you learn here is the same machinery — graphs simply add the seen set to cope with loops.

01  Number of Islands

Graphs · Flood Fill Medium ~20 min O(rows·cols) time · O(rows·cols) space

You're given a grid of "1"s (land) and "0"s (water). Count the islands — groups of land cells joined up/down/left/right. Diagonals don't connect.

Spot land, then flood it analogy

Walk the grid like reading a page. The moment you step on a fresh piece of land, you've found a new island — so add one to the count. Then flood it: walk to every land cell connected to it and sink each one (turn it to water) so you can't count it again. When the flood finishes, keep scanning for the next dry patch.

How to solve it

Sweep every cell. When you hit a "1" you haven't sunk yet, that's a brand-new island, so bump the count and start a flood-fill (a DFS) from there:

  1. If you've walked off the grid, or this cell is water, stop — there's nothing to flood.
  2. Otherwise sink this cell (set it to "0") so it's never counted again.
  3. Recurse into all four neighbours: down, up, right, left.

Closing the loop with the picture: each count += 1 is "I found a new island", and the flood-fill is "I walked the whole island so I won't re-count any of it".

Easy trap: forgetting to sink the cell

If you don't mark a land cell visited before recursing, the flood bounces back and forth between two neighbours forever (a stack overflow). Sink first, then recurse.

MeasureCostWhy
TimeO(rows·cols)Each cell is looked at a constant number of times — once by the scan, once by a flood.
SpaceO(rows·cols)Worst case the recursion stack holds one big all-land island.

New to this notation? See the Big-O cheat-sheet.

Why do we set each visited land cell to "0" as we flood it?

Right. Sinking a cell is our seen marker. It stops one island from being counted twice and stops the recursion from revisiting neighbours endlessly. (If you can't modify the grid, keep a separate visited set instead.)
Stuck? Reveal a hint hint

Loop over every cell. When you meet a "1", add 1 to the count and call a helper sink(r, c) that turns this cell to "0" and then calls itself on the four neighbours. The helper's first line should bail out if the cell is off-grid or already water.

Line-by-line walkthrough + flow walkthrough

Scan the grid; each fresh "1" is a new island — flood-fill (DFS/BFS) to sink the whole component so it is counted once. A separate visited matrix works too; mutating to water is the common interview shortcut.

flowchart TD
  start[Scan every cell] --> land{Cell is 1?}
  land -->|yes| bump[count += 1]
  bump --> sink[DFS sink four dirs]
  sink --> mark[Mark cell as 0]
  mark --> neigh[Recurse neighbors]
  land -->|no| next[Next cell]
  neigh --> next
  next --> more{More cells?}
  more -->|yes| land
  more -->|no| ret[Return count]
  1. def num_islands(grid):Count connected components of land in the grid.
  2. if not grid:Empty input → zero islands.
  3. return 0Bail out early.
  4. rows, cols = len(grid), len(grid[0])Cache dimensions for bounds checks.
  5. count = 0Running island total.
  6. def sink(r, c):Flood-fill helper: drown this land cell and its connected land.
  7. if r < 0 or c < 0 or r >= rows or c >= cols or grid[r][c] != "1":Off-grid or already water — stop.
  8. returnNothing to sink here.
  9. grid[r][c] = "0"Mark visited by turning land into water.
  10. sink(r + 1, c); sink(r - 1, c); sink(r, c + 1); sink(r, c - 1)Recurse on the four orthogonal neighbors.
  11. for r in range(rows):Walk every row.
  12. for c in range(cols):Walk every column.
  13. if grid[r][c] == "1":Unvisited land starts a new island.
  14. count += 1Tally it.
  15. sink(r, c)Drown the whole island so we never recount it.
  16. return countFinal number of islands.

Time O(rows · cols) — each cell visited a constant number of times; space O(rows · cols) worst-case recursion depth.

02  Clone Graph

Graphs · DFS Medium ~20 min O(V+E) time · O(V) space

Given one node of a connected graph, build a deep copy: brand-new nodes with the same values, wired up the same way. The copy must share no nodes with the original.

Photocopy a friendship network analogy

Imagine copying a circle of friends. You visit each person, make a fresh copy of them, then copy their friendships. The catch: friendships go both ways, so you'd loop forever. The fix is a notebook (a map of old → new): before copying anyone, check the notebook. If they're already in it, just point to the copy you made earlier. That single rule turns the loop into a tidy visit-everyone-once.

How to solve it

Run a DFS from the start node, carrying a dictionary clones that maps each original node to its fresh copy:

  1. If this node is already a key in clones, return its copy — we've been here before.
  2. Otherwise make a new node with the same value and record it in clones before recursing.
  3. For each neighbour, recurse to get (or build) its copy and append it to this copy's neighbour list.

Back to the analogy: the dictionary is the notebook, and "record it before recursing" is what stops two-way friendships from spinning you in circles.

The map IS the visited-set

Here one dictionary does double duty: it remembers what we've already copied (so no loops) and stores the copies we'll need to link everything up. Two jobs, one structure.

MeasureCostWhy
TimeO(V+E)Each node (V) is copied once; each edge (E) is walked once to wire neighbours.
SpaceO(V)The map holds one copy per node, plus the recursion stack.

What goes wrong if we forget the clones map?

Exactly. Edges point both ways, so without a record of who's been copied, node 1 copies 2, which copies 1, which copies 2… forever. The map both stops the loop and lets neighbours link to the same copy.
Stuck? Reveal a hint hint

Write a recursive dfs(node) that returns the clone. First line: if node in clones: return clones[node]. Then create the copy, store it in clones right away, and only then loop over node.neighbors appending dfs(neighbor).

Line-by-line walkthrough + flow walkthrough

DFS/BFS with a map old→new: create each node once, store it before wiring neighbors, and reuse the map on cycles. Cloning without the map infinite-loops on undirected edges.

03  Course Schedule

Graphs · Topological Sort Medium ~25 min O(V+E) time · O(V+E) space

You have num_courses courses and a list of prerequisite pairs [a, b] meaning "take b before a". Can you finish them all? In graph terms: is the dependency graph free of cycles?

Only take a course once its prereqs are done analogy

Picture each course as a box, with arrows from a prereq to the course that needs it. You can only sign up for a course whose prereqs are all finished — a box with no incoming arrows left. So: take every such free course, then erase its outgoing arrows (its dependents now owe one less). Repeat. If you manage to take all of them, great. If you ever get stuck with courses remaining but none free, there's a loop — A needs B which needs A — and nobody can start.

How to solve it

This is Kahn's algorithm — a topological sort that counts how many courses you manage to take:

  1. Build the graph (prereq → course) and an indegree array: how many prereqs each course still has.
  2. Put every course with indegree 0 (no prereqs) into a queue.
  3. Pop a course, mark it done. For each course that depended on it, drop that course's indegree by one; if it hits 0, it's now free — enqueue it.
  4. If the number you managed to finish equals num_courses, you did them all. Otherwise a cycle blocked you.

Closing the loop: the queue holds exactly the "free" boxes, and finishing fewer than all of them means some boxes were stuck pointing at each other.

Mind the arrow direction

The pair [a, b] means "b before a", so the edge runs b → a and it's a's indegree that goes up. Flip this and a valid schedule looks like a cycle. Read the direction carefully.

MeasureCostWhy
TimeO(V+E)Each course (V) is enqueued once; each prerequisite edge (E) is processed once.
SpaceO(V+E)The graph stores every edge, plus an indegree array and the queue.

After Kahn's algorithm runs, how do you know a cycle existed?

Right. Courses tangled in a loop never reach indegree 0, so they're never enqueued or finished. If done < num_courses, those left-over courses form a cycle and the schedule is impossible.
Stuck? Reveal a hint hint

Count indegree[course] for every prereq pair. Start a deque with all courses whose indegree is 0. Pop, increment a done counter, and for each dependent course decrement its indegree, enqueueing it when it reaches 0. At the end return done == num_courses.

Line-by-line walkthrough + flow walkthrough

Kahn's algorithm: process indegree-0 courses, peel edges, repeat. If you finish fewer than num_courses, a cycle remains. DFS coloring also works; Kahn is the clearest interview story for "can finish?"

flowchart TD
  start[Build graph and indegrees] --> seed[Enqueue indegree 0]
  seed --> loop{Queue empty?}
  loop -->|no| pop[Pop course]
  pop --> done[done += 1]
  done --> dec[Decrement neighbors]
  dec --> zero{Indegree hit 0?}
  zero -->|yes| enq[Enqueue neighbor]
  zero -->|no| loop
  enq --> loop
  loop -->|yes| cmp{done == num_courses?}
  cmp -->|yes| ok[Return True]
  cmp -->|no| bad[Return False]
  1. from collections import defaultdict, dequeGraph as defaultdict; BFS queue as deque.
  2. def can_finish(num_courses, prerequisites):Return whether all courses can be completed.
  3. graph = defaultdict(list)Adjacency: prereq → list of courses that need it.
  4. indegree = [0] * num_coursesHow many prereqs each course still owes.
  5. for course, prereq in prerequisites:Each pair is [course, prereq] = take prereq first.
  6. graph[prereq].append(course)Edge prereq → course.
  7. indegree[course] += 1Course gains one outstanding prereq.
  8. q = deque([c for c in range(num_courses) if indegree[c] == 0])Seed with courses that need nothing.

  11. node = q.popleft()Take the next available course.
  12. done += 1Count it finished.
  13. for nxt in graph[node]:Unlock dependents.
  14. indegree[nxt] -= 1One fewer prereq remaining.
  15. if indegree[nxt] == 0:Now free to take.

04  Network Delay Time

Dijkstra Medium ~30 min O((V+E) log V) time · O(V+E) space
Say it out loud

“Weighted shortest paths from one source → Dijkstra with a min-heap of (dist, node). Answer is the max distance among reachable nodes, or −1 if someone never hears the signal.”

You have n network nodes and directed edges [u, v, w] (signal from u to v takes time w). A signal starts at node k. Return how long until every node receives it — or -1 if impossible. Example: times = [[2,1,1],[2,3,1],[3,4,1]], n = 4, k = 2 → 2.

Ripples on weighted roads analogy

BFS ripples evenly when every road costs 1. When roads have different travel times, always expand next from the town you've reached soonest — that's Dijkstra. The last town to hear the signal sets the network delay.

How to solve it (Dijkstra sketch)

  1. Build an adjacency list: u → [(v, w), …].
  2. Set dist[k] = 0, others to infinity. Push (0, k) into a min-heap.
  3. While the heap isn't empty: pop (d, u). Skip if d > dist[u] (stale). For each edge u→v, if d + w < dist[v], update and push.
  4. If any node is still infinity, return -1; else return max(dist).
MeasureCostWhy
TimeO((V+E) log V)Each node/edge processed with heap ops (binary heap).
SpaceO(V+E)Graph, distance array, and the heap.

Requires non-negative weights. Negative edges → Bellman-Ford. Unweighted → plain BFS.

Why can't plain BFS replace Dijkstra when edge weights differ?

Exactly. With unequal weights, “fewest edges” ≠ “smallest total time.” The min-heap always expands the currently closest unsettled node by distance.
Stuck? Reveal a hint hint

Use heapq with (dist, node). Skip stale pops. After the loop, if max(dist.values()) is still infinity return -1.

Line-by-line walkthrough + flow walkthrough

Weighted single-source shortest paths with non-negative edges → Dijkstra via a min-heap of (dist, node). The network delay is max(dist), or −1 if any node stays unreachable. Plain BFS is wrong when weights differ.

  loop -->|no| pop[Pop d u]
  pop --> stale{d greater than dist u?}
  stale -->|yes| loop
  stale -->|no| edges[For each neighbor v w]

  fin -->|no| ret[Return ans]

  2. from collections import defaultdictAdjacency list builder.
  3. def network_delay_time(times, n, k):Time for signal from k to reach all n nodes.
  4. graph = defaultdict(list)u → list of (v, weight).
  5. for u, v, w in times:Ingest each directed edge.
  6. graph[u].append((v, w))Store neighbor and travel time.
  7. dist = {i: float("inf") for i in range(1, n + 1)}All nodes start unreachable.
  8. dist[k] = 0Source is distance 0.
  9. heap = [(0, k)]Min-heap of (distance, node).
  10. while heap:Expand closest unsettled distances first.
  11. d, u = heapq.heappop(heap)Pop the currently nearest candidate.
  12. if d > dist[u]:Stale heap entry — we already found a better path.
  13. continueSkip it.
  14. for v, w in graph[u]:Relax outgoing edges.
  15. nd = d + wCandidate distance through u.
  16. if nd < dist[v]:Improvement found.
  17. dist[v] = ndRecord the better distance.
  18. heapq.heappush(heap, (nd, v))Push lazy entry (duplicates OK).
  19. ans = max(dist.values())Last node to hear the signal.
  20. return -1 if ans == float("inf") else ansUnreachable node → −1; else the delay.
