Binary Search

When a list is already sorted, you never have to check every item. Look at the middle, decide which half the answer lives in, and throw the other half away. Each peek halves what's left — so even a million items take only about twenty looks. Let's watch it work, then solve three classic problems with it — and learn the senior trick of binary-searching the answer itself.

00  The idea

Binary search works on a sorted list. You keep two markers — lo (the lowest spot the answer could be) and hi (the highest). Look at the middle item between them. If it's your target, you're done. If the middle is too small, the answer must be to the right, so drop the whole left half; if it's too big, drop the right half. Repeat on the half that's left. Because each step cuts the list in two, you close in fast.

Finding a word in a dictionary analogy

To find "kangaroo" in a paper dictionary, you don't start at page 1 and flip one page at a time. You flop it open near the middle, see you've landed on "M", and realise "kangaroo" is earlier — so you ignore the whole second half and open the middle of what's left. A few flips and you're there. That's binary search: each open throws away half the book.

When to reach for binary search

It's the right tool when you spot any of these tells:

Sorted input
The list is already in order (or the answer space is "monotonic" — once true, always true).
"Find the position"
You're locating a target, a first/last occurrence, or an insert spot.
O(log n) wanted
A linear scan (O(n)) is too slow and the input could be huge.
Halving feels possible
At any midpoint you can tell which side the answer is on — so half can be discarded.
O(log n) in plain words

log n just counts how many times you can halve n before reaching 1. A list of 1,000,000 halves to ~1 in only 20 steps; double the list to 2,000,000 and you pay just one extra step. That gentle growth is why binary search scales so well.

01  Binary Search

Binary Search Easy ~10 min O(log n) time · O(1) space

Given a sorted list of numbers and a target, return the index where the target sits, or -1 if it isn't there. For [-1, 0, 3, 5, 9, 12] and target 9, the answer is 4.

A "higher or lower?" guessing game analogy

A friend picks a number from 1 to 100 and you must guess it. The clever opening guess is 50: they say "higher", so you instantly know it's 51–100 and guess 75. Each answer halves the range. Binary search plays exactly this game against a sorted list, and the index of the middle is your guess.

How to solve it

Keep two indices, lo at the start and hi at the end. While lo <= hi (there's still a range to look at):

  1. Compute the middle index mid = (lo + hi) // 2.
  2. If nums[mid] equals the target, return mid — found it.
  3. If nums[mid] is smaller than the target, the answer is to the right: set lo = mid + 1.
  4. If it's bigger, the answer is to the left: set hi = mid - 1.

If the loop ends without a match, the target isn't there — return -1. Each turn throws away half of what remains, so you finish in about log n steps.

MeasureCostWhy
TimeO(log n)Each step halves the remaining range, so the count of steps is log n.
SpaceO(1)Just two indices and a middle — no extra list.

New to this notation? See the Big-O cheat-sheet.

The classic bug: infinite loops

Two details keep binary search safe. Loop while lo <= hi (with <=, not <), so a single remaining item still gets checked. And always step past the middle — lo = mid + 1 or hi = mid - 1, never lo = mid. If you leave lo or hi sitting on mid, the range stops shrinking and the loop spins forever.

A sorted list has 1,000,000 items. Roughly how many checks does binary search need in the worst case?

Right. Halving 1,000,000 reaches 1 in about 20 steps (2²⁰ ≈ 1,000,000). That's O(log n). A plain scan would be O(n) — up to a million checks. Halving is the whole win.
Stuck? Reveal a hint hint

Use a while lo <= hi loop. Compute mid = (lo + hi) // 2, compare nums[mid] with the target, and move lo or hi past mid each time. Return mid on a match, or -1 after the loop.

Line-by-line walkthrough + flow walkthrough

Classic binary search is the interview default on a sorted array: each comparison halves the window, so you get O(log n) instead of a linear scan. The only trick is the loop condition lo <= hi and moving past mid — miss either and you loop forever or skip the answer.

02  Search in Rotated Sorted Array

Binary Search Medium ~25 min O(log n) time · O(1) space

A sorted list was rotated at some unknown spot — for example [0,1,2,4,5,6,7] becomes [4,5,6,7,0,1,2]. Given the rotated list and a target, return its index, or -1. Still aim for O(log n).

A deck of cards, cut once analogy

Imagine a sorted stack of cards that someone cut once — lifted off the top chunk and dropped it on the bottom. The deck looks scrambled, but here's the trick: no matter where you split it in the middle, one of the two halves is still perfectly in order. So check which half is sorted, see whether your target's value falls inside that tidy range, and binary-search the right side. You still throw away half each step.

4 5 6 7 | cut | 0 1 2

Left run 4 5 6 7 is sorted; right run 0 1 2 is sorted. The "cut" is the only break — and any midpoint lands inside one tidy run.

How to solve it

It's still binary search, with one extra question at each step. Take mid. First, is nums[mid] the target? If so, done. Otherwise figure out which side is the sorted one:

  1. If nums[lo] <= nums[mid], the left half is in order. Check whether the target's value sits between nums[lo] and nums[mid]: if yes, search left (hi = mid - 1); if no, search right (lo = mid + 1).
  2. Otherwise the right half is in order. Check whether the target sits between nums[mid] and nums[hi]: if yes, search right; if no, search left.

Each step still discards one half, so the cost stays O(log n) — we just spend a couple of comparisons deciding which half is the trustworthy, sorted one.

MeasureCostWhy
TimeO(log n)One half is dropped each step, exactly like plain binary search.
SpaceO(1)Only the lo, hi, and mid indices.
Always trust the sorted half

The rotated half is confusing, so don't reason about it. Identify the sorted half, ask "does the target fall inside it?", and let that one yes/no pick your direction. Decisions about sorted ranges are easy and exact.

In a rotated sorted array, what's always true at any midpoint?

Exactly. A single rotation leaves only one "break" in the list. Wherever you split it, the break falls on one side — so the other side is a clean sorted run. Spotting that sorted half is what keeps the search O(log n).
Stuck? Reveal a hint hint

Standard binary search skeleton, plus: compare nums[lo] with nums[mid] to learn which half is sorted. Then test if the target lies within that sorted half's value range (e.g. nums[lo] <= target < nums[mid]) to choose which way to shrink.

Line-by-line walkthrough + flow walkthrough

A rotated sorted array still has one fully sorted half at every mid — find that half, then ask whether the target sits inside its value range. That keeps the O(log n) binary-search skeleton instead of a linear scan or an explicit "find pivot then search" two-pass.

  14. return -1Window empty — target absent.

03  Binary search on the answer

Here's the senior move: the haystack doesn't have to be an array at all. If you can ask a yes/no question whose answers form NNN…YYY as some number grows — "can speed k finish in time?" (if yes for k, it's yes for every faster k too) — then you can binary-search the number itself. Interviewers call this "binary search on the answer", and naming it out loud is worth points.

The tells

"Minimize the maximum"
Or "maximize the minimum" — that wording is practically a flashing sign for this technique.
The answer is a number with obvious bounds
You can immediately name a smallest possible value (lo) and a largest possible value (hi) it must sit between.
Checking one candidate is cheap, trying all is huge
A single "does candidate x work?" check costs O(n), but the candidate range is enormous — so you binary-search it instead of scanning it.

The template

The skeleton barely changes — only what lo and hi mean. They are candidate answers now, not indices:

  1. Start with lo, hi = smallest possible answer, largest possible answer.
  2. While lo < hi: compute mid = (lo + hi) // 2.
  3. If works(mid) is true, the answer is mid or something smaller — keep it: hi = mid.
  4. If works(mid) is false, mid can't be the answer — exclude it: lo = mid + 1.
  5. When the loop ends, lo == hi is the first Y in NNN…YYY: return lo.

The rule worth memorising: a feasible mid stays in the range (hi = mid, because it might be the optimum), while an infeasible one is excluded (lo = mid + 1). The window shrinks every turn until it pins the boundary.

04  Koko Eating Bananas

Binary Search Medium ~20 min O(n log m) time · O(1) space

Koko has piles of bananas and h hours. Each hour she picks one pile and eats up to k bananas from it — if the pile runs out early, the rest of that hour is wasted. Find the minimum integer speed k that finishes everything within h hours. For piles [3, 6, 7, 11] and h = 8, the answer is 4.

Picking a reading speed analogy

You have a stack of books and one evening per book. Read too slowly and you run out of evenings before the stack is done. But any speed that works keeps working if you read faster — finishing earlier never hurts. So across the speeds, the verdicts line up as NO NO NO YES YES, and your job is to hunt the boundary: the slowest speed that still gets a YES.

How to solve it

Two pieces: a cheap feasibility check, and the on-the-answer template wrapped around it.

  1. Write a helper hours(k): at speed k, each pile p takes ceil(p / k) hours, so total hours is the sum of those ceilings. The integer idiom (p + k - 1) // k computes a ceiling without floats.
  2. Binary-search the speed: lo = 1 (slowest imaginable) and hi = max(piles) (any faster is pointless — one pile per hour is the floor).
  3. If hours(mid) <= h, speed mid is feasible — it might be the answer, so keep it: hi = mid. Otherwise it's too slow: lo = mid + 1.
  4. When lo == hi, that's the minimum feasible speed.
MeasureCostWhy
TimeO(n log max(piles))The log is over the answer range (speeds 1..max), not the array length — each of the ~log m candidate speeds costs one O(n) pass through the piles.
SpaceO(1)Just lo, hi, mid, and a running sum.
Don't evict the feasible mid

Writing hi = mid - 1 on a feasible mid throws away a possibly-optimal answer — that speed might be exactly the minimum you're hunting. Feasible candidates must stay in the range (hi = mid); only infeasible ones get excluded (lo = mid + 1). That's the one place this template differs from the classic find-a-target loop.

Which property makes binary search legal here?

Exactly. The piles are never sorted and never need to be — we don't search them. We search the speeds, and that only works because the yes/no verdicts line up as NNN…YYY: one clean boundary to hunt, so halving is safe.
Stuck? Reveal a hint hint

Write hours(k) first — both brute force and binary search need it. It's just the sum of (p + k - 1) // k over the piles. Once that works, wrap the on-the-answer template around it: lo, hi = 1, max(piles), and hours(mid) <= h is your works(mid).

Line-by-line walkthrough + flow walkthrough

Binary search on the answer: speeds form a NO→YES frontier ("can speed k finish in h hours?"), so you search the speed range instead of the piles. Trying every k from 1 to max(pile) is O(m·n); binary search cuts that to O(n log m).
