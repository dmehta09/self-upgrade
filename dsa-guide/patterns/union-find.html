Patterns · union-find

Union-Find

Some problems keep asking one little question over and over: "are these two in the same group?" — while the groups themselves keep merging. Friend circles grow, islands get bridged, wires get connected. Union-Find (also called Disjoint Set Union) answers that question in what is basically constant time, no matter how big the groups get. Let's meet the clubs and their presidents.

00  The idea

Clubs with presidents analogy

Every kid in school belongs to exactly one club, and every club has exactly one president. To check whether two kids are in the same club, each kid walks up the chain — "who do you report to?" — until they reach someone who reports to themselves. That self-reporting person is the president. Same president → same club. To merge two clubs, you don't move all the members — one president simply agrees to work for the other. That's the entire data structure: a parent array (or dict) saying who each kid reports to.

In plain words: find(x) follows parents upward until it reaches someone who is their own parent — that's the president (the "root"), and it's the group's name. union(a, b) calls find on both, and if the two presidents differ, points one at the other. Two clubs just became one, in a single pointer write.

Done naively, the chains can grow long and find gets slow. Two famous one-line upgrades fix that:

  • Path compression — while walking up, make every kid you pass report directly to the president ("once you've met the president, skip the middle managers forever"): parent[x] = find(parent[x]).
  • Union by size / rank — the smaller club always joins the bigger one, keeping chains short: parent[small] = big.
Go deeper: "basically O(1)" has a real name deeper

The honest cost of find/union with both upgrades is O(α(n)) amortized, where α is the inverse Ackermann function — a function that grows so absurdly slowly that α(n) ≤ 4 for any n that fits in the observable universe. In an interview, say "amortized inverse-Ackermann, effectively constant" and move on; nobody expects the proof.

When to reach for union-find

These are the tells:

Groups that merge over time
Connections arrive one by one and groups only ever fuse together — never split.
Repeated "same group?" questions
You're asked "are a and b connected?" again and again, interleaved with new connections.
Cycle detection on undirected edges
While adding edges, the first edge whose two ends are already in the same group closes a cycle.
Counting components
Track how many groups remain without re-walking the whole graph after each new edge — start at n and decrement on every real merge.

Which of these questions is union-find the WRONG tool for?

Right. Union-find only remembers which group each node is in — it deliberately forgets the actual paths, so it can't measure distance. Shortest path is BFS territory (see Graphs). Connectivity questions and group counts, though, are exactly its home turf.

01  Number of Provinces

Union-Find Medium ~20 min O(n² α) time · O(n) space

There are n cities and an adjacency matrix isConnected, where isConnected[i][j] = 1 means cities i and j are directly connected. A province is a group of cities connected directly or indirectly. Count the provinces. Example: [[1,1,0],[1,1,0],[0,0,1]] → 2.

Every handshake merges two clubs analogy

Start with every city as its own one-kid club — n cities, n clubs. Every "1" in the matrix is a handshake that merges the two clubs involved (if they weren't already one). When all the handshakes are done, count the presidents left standing. That count is the number of provinces.

How to solve it

  1. Make a parent list where every city starts as its own parent: parent = list(range(n)).
  2. Write find with path compression (re-point as you climb).
  3. Write union(a, b) so it returns True only when it actually merged two different clubs.
  4. Start count = n. Scan the upper triangle of the matrix (j > i — the matrix is symmetric, no need to read each handshake twice); for every 1, call union and decrement count on each successful merge.

At the end, count is the number of provinces — no second pass, no graph walk.

MeasureCostWhy
TimeO(n² · α(n))Reading the n×n matrix dominates; each union/find is effectively constant.
SpaceO(n)One parent entry per city.

New to this notation? See the Big-O cheat-sheet.

DFS flood-fill also works here

You could equally DFS from each unvisited city and count the launches — see the Graphs page. Union-find earns its keep when connections arrive over time and you must answer "how many groups now?" between arrivals — DFS would have to re-walk everything each time; union-find just keeps a counter.

Why do we decrement count only when find(a) != find(b)?

Exactly. If both cities already report to the same president, the "merge" is a no-op — there were 3 clubs before and 3 after. Only a union of two different presidents fuses two clubs into one, so only then does the count drop.
Stuck? Reveal a hint hint

You need three small pieces: parent = list(range(n)); a find(x) that loops while parent[x] != x, re-pointing with parent[x] = parent[parent[x]] as it goes; and a union(a, b) that returns whether it merged. Then it's just a double loop over the matrix with a counter starting at n.

02  Redundant Connection

Union-Find Medium ~20 min O(n α) time · O(n) space

You're given a graph that started as a tree and then got exactly one extra edge. The edges arrive in order. Return the edge that closes the cycle — the last edge that connects two already-connected nodes. Example: [[1,2],[1,3],[2,3]] → [2,3].

The bridge nobody needed analogy

Kids keep building bridges between islands, one at a time. Each new bridge between two separate island-groups is useful — it joins them. But the moment someone proposes a bridge between two islands that are already connected (maybe through a chain of other bridges), that bridge is the redundant one. You can already walk between them; the new bridge only creates a loop.

How to solve it

  1. Process the edges in the given order.
  2. For each edge (a, b), try union(a, b).
  3. The first time union returns False (both ends already share a president), that edge is the answer — return it immediately.

No DFS, no cycle-walking — the parent array is the memory of everything connected so far, and one find per endpoint consults it in effectively constant time.

MeasureCostWhy
TimeO(n · α(n))One union per edge, each effectively constant.
SpaceO(n)The parent map.
"Return the LAST such edge" — already handled

The problem says that if several edges could be removed to restore a tree, return the one that appears last in the input. Processing edges in input order with union-find finds exactly that one for free: every earlier edge got unioned while it was still useful, so the edge that trips "already connected" is necessarily the latest possible one.

What does it mean when find(a) == find(b) BEFORE you union a new edge (a, b)?

Right. Same president means a and b are already in one connected club — there's some path of earlier edges between them. Adding a direct edge on top of an existing path is precisely what a cycle is. (Note: it doesn't mean the exact edge (a, b) appeared before — only that some route exists.)
Stuck? Reveal a hint hint

You don't need to detect the cycle after building the graph — detect it while building. Walk the edge list once; for each edge compare find(a) and find(b). Equal presidents → return that edge. Otherwise union and keep going.

Process edges in order with Union-Find — the first edge whose ends already share a president closes the cycle. That edge is also the "last" removable one the problem asks for, for free.

03  Accounts Merge

Union-Find Hard ~30 min O(E α + E log E)

Each account is a list [name, email1, email2, …]. Two accounts belong to the same person if they share any email — transitively! Names repeat across different people, so they prove nothing. Merge the accounts and output each person as [name, sorted unique emails]. This one is a senior favorite — it also lives in the timed coding drills.

Email chains prove "same human" analogy

People keep signing up with new email addresses, but any shared address proves "same human". And the proof chains: if accounts A and B share one address, and B and C share a different one, then A, B and C are all the same human — even though A and C share nothing directly. That "groups keep fusing through chains" shape is the union-find bat-signal.

How to solve it: three passes

1

Union

For each account, union every email with the account's first email (so all of one account's emails land in one club), and record email → name along the way.

2

Regroup

Bucket every email under find(email). Each bucket is one human — every address that's transitively linked ends up under the same president email.

3

Format

For each bucket, output [name] + sorted(emails), taking the name from any email in the bucket (they all belong to the same person, so any recorded name works).

Names lie

Two Johns with disjoint emails are two different people; one person might even appear under a name typo. Only emails identify. That's exactly why we union emails (not account indices): the structure then groups by identity automatically, and the name is just a label we pin on at the end.

MeasureCostWhy
TimeO(E · α + E log E)E = total emails. Unions are effectively constant each; sorting each bucket's emails is what dominates.
SpaceO(E)Parent map, name map, and the buckets.

Accounts [["John","a@x"],["John","b@x"]] — one person or two?

Two people. The only evidence of identity is a shared email, and a@x and b@x never touch. The matching name "John" is a red herring — the problem plants it on purpose. Your union structure never even looks at names until output time.
Stuck? Reveal a hint hint

Use a dict as the parent map so emails (strings) can be keys — parent.setdefault(x, x) auto-registers new emails inside find. In pass 1, you only need union(email, emails[0]) for each email in an account: linking everyone to the first email chains the whole account together. Pass 2 uses groups.setdefault(root, []).append(email) on a plain dict.
