Linked List

A linked list is a chain of little boxes, each holding a value and an arrow (next) pointing to the box behind it. You can't jump to "item 5" — you can only follow arrows. So these problems are pointer surgery: carefully re-hook the arrows, often with a spare dummy box at the front, or with two markers moving at different speeds. Let's see the arrows move, then solve three classics.

00  The idea

Each box is a node: it stores a value and a single arrow, next, to the following node. The last node's arrow points at None (nothing). Because there's no index, almost every trick comes down to one of three moves: relink arrows one at a time (always saving the next box before you overwrite an arrow), park a throwaway dummy head in front so the "first node" is never a special case, or run two pointers — often one fast, one slow — to find the middle or a loop.

Re-hooking train carriages analogy

Think of train carriages coupled in a line: each one is hooked to the carriage behind it. To rearrange the train you don't teleport carriages around — you walk along unhooking and re-hooking couplings, one joint at a time. And before you unhook a carriage, you'd better remember which one was attached, or it rolls off and is lost. That "remember the next one first" habit is the heart of linked-list code.

When you're on a linked-list problem

These tells point you at the pattern's tools:

Relinking, not indexing
You need to reverse, splice, or reorder nodes — work the next arrows, since there's no random access.
Messy "first node" case
Inserting or deleting at the head feels fiddly — add a dummy head so the front is no longer special.
Find a middle or a loop
Run a fast pointer (2 steps) and a slow pointer (1 step) together.
O(1) space wanted
Rearrange in place by moving arrows, never copying the list into an array.
Save next before you overwrite it

The instant you do cur.next = prev, the old onward arrow is gone — and with it the rest of the list. Always stash nxt = cur.next first, like remembering which carriage you're about to unhook. Lose that reference and the chain rolls away.

Why a dummy head helps

A dummy is a throwaway node you place before the real first one. Now "the node before me" always exists, so inserting or deleting the head needs no special if. At the end you just return dummy.next — the real head. You'll see this trick shine in Merge Two Sorted Lists.

01  Reverse Linked List

Linked List Easy ~10 min O(n) time · O(1) space

Given the head of a linked list like 1 → 2 → 3 → 4 → 5, flip all the arrows so it becomes 5 → 4 → 3 → 2 → 1, and return the new head. Do it in place.

Walk the chain, flipping each arrow analogy

Walk along the chain and turn each arrow around to point at the box you just came from. You hold three things: prev (the box behind you, where this arrow should now point), cur (the box you're flipping), and — crucially — next, the box ahead, which you must memorise before you flip, or you'll lose the way forward.

How to solve it

Keep two markers: prev (starts at None) and cur (starts at the head). Loop while cur exists:

  1. Remember the next box: nxt = cur.next. (Save it before you destroy the arrow!)
  2. Flip cur's arrow backwards: cur.next = prev.
  3. Shuffle both markers one step forward: prev = cur, then cur = nxt.

When cur runs off the end, prev is sitting on the old last node — which is now the new head. Return prev. One walk down the chain reverses it.

MeasureCostWhy
TimeO(n)Each of the n nodes is visited once to flip its arrow.
SpaceO(1)Three small references (prev, cur, nxt) — no new list.

New to this notation? See the Big-O cheat-sheet.

Order matters in the swap

Do the three lines in the right order: save nxt, then point cur.next = prev, then advance. Flip the arrow before saving nxt and the rest of the chain vanishes — exactly like unhooking a carriage without holding on to it.

Why must we store nxt = cur.next before doing cur.next = prev?

Right. The arrow cur.next is the only way to reach the remaining nodes. Overwrite it without a saved copy and everything ahead is unreachable — the carriages roll off. Stash nxt first, then flip.
Stuck? Reveal a hint hint

Start prev = None, cur = head. Each loop: nxt = cur.next; cur.next = prev; prev = cur; cur = nxt. Return prev at the end.

Iterative reverse with three pointers is the interview default: O(n) time, O(1) space. Recursion also works but uses O(n) stack frames — interviewers usually want the in-place flip.

02  Linked List Cycle

Fast & Slow Pointers Easy ~15 min O(n) time · O(1) space

Given the head of a linked list, decide whether it has a cycle — does some node's arrow point back into the chain, forming a loop, instead of eventually reaching None? Return True or False, using only O(1) extra space.

Tortoise and hare on a track analogy

Two runners start together: a slow tortoise that takes one step at a time and a fast hare that takes two. If the track is a straight line, the hare simply reaches the finish (runs off the end) first. But if the track secretly loops back on itself, the hare keeps lapping and must eventually catch up to the tortoise from behind — they land on the same spot. Meeting means there's a loop.

1 → 2 → 3 → 4 ⤺ back to 2

Node 4's arrow loops back to node 2, so following arrows never reaches None. A fast pointer will lap the slow one inside the 2 → 3 → 4 ring.

How to solve it

The naive idea is to remember every node you've seen in a set and watch for a repeat — but that costs O(n) extra space. The two-pointer trick needs none:

  1. Start slow and fast both at the head.
  2. Each loop, move slow one step (slow = slow.next) and fast two (fast = fast.next.next).
  3. If fast (or fast.next) ever hits None, the chain ended — no loop, return False.
  4. If slow is fast (same node), the fast runner lapped the slow one — there's a loop, return True.

Inside a loop, the gap between hare and tortoise shrinks by one each step, so they're guaranteed to collide. That's why one pass settles it.

MeasureCostWhy
TimeO(n)The slow pointer walks at most n steps before they meet or fast exits.
SpaceO(1)Two pointers only — no "seen" set to store every node.
Check fast and fast.next first

The hare reads two arrows ahead, so guard the loop with while fast and fast.next:. That stops you from calling .next on None when the chain ends on an even or odd length.

Why does the fast/slow approach use O(1) space, while a "remember every node" approach uses O(n)?

Right. Both run in O(n) time, but a "seen" set grows with the list — O(n) memory. The two runners hold just two references no matter how long the chain is, so they catch a loop with O(1) extra space.
Stuck? Reveal a hint hint

Set slow = fast = head. Loop while fast and fast.next: moving slow by one and fast by two. If slow is fast, return True. If the loop exits, return False.

Line-by-line walkthrough + flow walkthrough

Floyd's tortoise and hare is the interview default for cycle detection: O(n) time and O(1) space. A hash set of seen nodes also works but costs O(n) memory — call that out if they ask for trade-offs.

03  Merge Two Sorted Lists

Linked List + Dummy Head Easy ~15 min O(n+m) time · O(1) space

Given two sorted linked lists, weave them into one sorted list and return its head. For 1 → 2 → 4 and 1 → 3 → 4, the result is 1 → 1 → 2 → 3 → 4 → 4.

Merging two sorted piles of cards analogy

You have two face-up piles of cards, each already sorted with the smallest on top. To build one sorted pile, you just keep comparing the two top cards and taking the smaller one. Because both piles stay sorted, the smaller top card is always the next smallest overall. To make the code tidy, lay down a blank "dummy" card first — then there's always a card to attach the next one to.

How to solve it

Make a dummy node and a tail pointer that starts on it. While both lists still have nodes:

  1. Compare the two front values. Attach the smaller node to tail.next, and step that list's pointer forward.
  2. Move tail onto the node you just attached.

When one list runs out, attach whatever's left of the other in one go (tail.next = l1 or l2) — it's already sorted. Return dummy.next, the real head. The dummy means we never write a special case for the very first node.

MeasureCostWhy
TimeO(n + m)Each node from both lists is attached exactly once.
SpaceO(1)We relink existing nodes — only a dummy and a tail pointer.
Use <=, and let the leftover attach itself

Comparing with <= (not <) keeps equal values in a stable order. And tail.next = l1 or l2 grabs whichever list is non-empty, so you never write a second loop to drain the remainder.

What's the main job of the dummy head node here?

Exactly. Without a dummy you'd need an if to pick the very first head, then more code to keep extending it. The dummy is a blank starter card: tail always has somewhere to hook the next node, and the real answer is dummy.next.

A dummy head plus a tail pointer is the clean merge pattern: always attach the smaller front node, then splice on whatever list remains. Recursion works too but uses O(n) stack; the iterative dummy version is O(1) extra space and easier to narrate.

04  Remove Nth Node From End of List

Linked List · Two Pointers Medium ~20 min O(n) time · O(1) space

Given the head of a linked list, remove the nth node from the end and return the new head. For 1 → 2 → 3 → 4 → 5 and n = 2, drop the 4 to get 1 → 2 → 3 → 5. Do it in one pass if you can.

Two hikers with a fixed gap analogy

Send a fast hiker n steps ahead first. Then walk both together — fast at the front, slow lagging by exactly n nodes. When fast falls off the end, slow is sitting on the node just before the one you want to delete. Relink past it. A blank dummy box at the front means deleting the original head is the same surgery as deleting any other node.

How to solve it

One pass with a dummy head and a fixed gap:

  1. Create dummy = ListNode(0, head) so deleting the first real node is uniform.
  2. Set fast = slow = dummy. Advance fast exactly n + 1 steps (or advance n times from dummy then one more — either way fast ends n nodes ahead of slow when both move).
  3. While fast is not None, step both fast and slow forward together.
  4. When fast is None, slow.next is the nth-from-end node. Skip it: slow.next = slow.next.next.
  5. Return dummy.next.
MeasureCostWhy
TimeO(n)One pass: fast walks the list once; slow trails behind.
SpaceO(1)Dummy plus two pointers — no second list.
Why n + 1 from the dummy?

You need slow on the node before the victim so you can rewire slow.next. Starting both on the dummy and giving fast an n + 1 lead places that gap correctly — including when the victim is the original head.

Why use a dummy head for this problem?

Exactly. Without a dummy you'd special-case n == length (delete head). With a dummy, slow can sit before the head and dummy.next is always the answer.
Stuck? Reveal a hint hint

dummy = ListNode(0, head); fast = slow = dummy. Move fast ahead n + 1 times. Then while fast: advance both. Finally slow.next = slow.next.next and return dummy.next.

Two pointers with gap n plus a dummy head is the interview default: one pass, O(1) space, and head deletion needs no special case. Counting length then walking again also works but costs a second pass.

05  Reorder List

Linked List Medium ~25 min O(n) time · O(1) space

Reorder L0 → L1 → … → Ln-1 → Ln into L0 → Ln → L1 → Ln-1 → … in place (do not return a new list). Classic: 1→2→3→4 becomes 1→4→2→3; 1→2→3→4→5 becomes 1→5→2→4→3.

Cut the deck, flip the bottom half, riffle analogy

Find the middle, reverse the second half so the old tail becomes the next card to deal, then weave first-half and reversed-second one node at a time. Three familiar list tricks glued together — mid, reverse, merge alternate.

How to solve it

Three phases, all O(1) extra space:

  1. Find mid — slow/fast from head; when fast finishes, slow is the end of the first half. Detach: second = slow.next; slow.next = None.
  2. Reverse second half — classic three-pointer reverse (same idea as Reverse Linked List on this page).
  3. Merge alternate — while the second half remains: save both nexts, point first.next = second, second.next = first_next, advance both.

Mutate in place; return nothing (or the same head). Demo helpers build/to_list match the other problems on this page so you can print the result.

MeasureCostWhy
TimeO(n)One mid pass, one reverse, one merge — each linear.
SpaceO(1)Only a handful of pointers; no array of nodes.

Why reverse the second half before merging?

Exactly. After reverse, walking the second half yields Ln, Ln-1, … — precisely the order you need to interleave with L0, L1, …
Stuck? Reveal a hint hint

Slow/fast to mid → cut → reverse second → while second: stash nexts, a.next = b, b.next = a_next, advance. Print with to_list after mutating.
