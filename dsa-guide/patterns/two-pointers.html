Patterns · two pointers

Two Pointers

Some problems become easy the moment you stop using one finger to scan a list and start using two — usually one at each end, walking toward the middle. This single trick turns a slow "check every pair" into a fast single pass. Let's see it move, then solve three classic problems with it.

00  The idea

Picture a row of cards on a table. The slow way to compare or rearrange them is to scan with one finger, again and again. The two-pointer way: put one finger (left) on the first card and another (right) on the last, then move them toward each other. Each step does useful work and the fingers meet in the middle — so you touch each card once.

Two friends closing a curtain analogy

Two friends stand at opposite ends of a long curtain rail and walk toward each other, tidying as they go. Because they start far apart and meet in the middle, the whole rail gets covered in half the trips — and they never re-check the same spot twice.

When to reach for two pointers

It's the right tool when you see any of these tells:

Sorted input
The data is sorted (or you can sort it) and you're hunting for a pair/triple with some target.
From both ends
The answer depends on the outermost items — palindromes, "most water", reversing.
O(1) space wanted
You must do it in place, without building a second list.
"Every pair" feels slow
A brute-force solution would check all pairs — O(n²) — and you sense there's a single-pass shortcut.
A cousin: fast & slow pointers

Sometimes the two pointers move in the same direction at different speeds (one fast, one slow) instead of toward each other. We use that variant on the Linked List page to detect loops. Same idea, two markers — different choreography.

01  Valid Palindrome

Two Pointers Easy ~10 min O(n) time · O(1) space

A palindrome reads the same forwards and backwards. Given a string, return True if it's a palindrome when you ignore punctuation, spaces, and capital-vs-small letters. Example: "A man, a plan, a canal: Panama" → True.

Two readers meeting in the middle analogy

One friend reads the word left-to-right, another reads it right-to-left, and they call out one letter at a time. If their letters ever disagree, it's not a palindrome. If they make it to the middle always agreeing, it is. (They politely skip over commas and spaces.)

How to solve it

Keep two indices, left at the start and right at the end. In a loop while left < right:

  1. If left points at something that isn't a letter or digit, nudge it right (skip it). Do the same for right, nudging it left.
  2. Compare the two characters in lower-case. If they differ, it's not a palindrome — return False immediately.
  3. Otherwise move both inward and continue.

Survive until the pointers cross and it's a palindrome. Because each pointer only ever moves toward the other, we look at each character at most once.

MeasureCostWhy
TimeO(n)Each of the n characters is visited at most once.
SpaceO(1)Just two index variables — we don't build a cleaned copy.

New to this notation? See the Big-O cheat-sheet.

Easy trap: forgetting to skip non-letters

"Race a car" has spaces. If you compare raw characters without skipping spaces and punctuation, you'll get the wrong answer. Always advance past anything that isn't a letter or digit first.

Trace it on "a,b;a"

1

left=0 ('a'), right=4 ('a')

Both are letters and match. Move inward.

2

left=1 (','), right=3 (';')

Both are punctuation — skip them: left→2, right→2.

3

left=2 ('b'), right=2

Pointers met — loop ends. It's a palindrome → True.

Why is the two-pointer check O(1) space, while "reverse the cleaned string and compare" is O(n) space?

Right. Both are O(n) time, but reversing makes a copy (O(n) extra memory). Two pointers walks the original in place, holding just left and right — O(1) extra space. Interviewers love that distinction.
Stuck? Reveal a hint hint

You don't need to clean the string into a new one. Use left and right indices, and the string method .isalnum() to decide whether to skip a character. Compare with .lower() so case doesn't matter.

Line-by-line walkthrough + flow walkthrough

Two pointers from the ends is the interview default: O(n) time, O(1) space, no extra cleaned string. Building a filtered lowercase copy then checking it is fine but uses O(n) space — interviewers usually prefer in-place skipping with .isalnum().

flowchart TD
  start[Start: left and right at ends] --> loop{left < right?}
  loop -->|no| ok[Return True]
  loop -->|yes| skipL[Skip non-alnum from left]
  skipL --> skipR[Skip non-alnum from right]
  skipR --> cmp{Chars match ignoring case?}
  cmp -->|no| fail[Return False]
  cmp -->|yes| move[Move left in and right in]
  move --> loop
  ok --> done[Done]
  fail --> done
  1. def is_palindrome(s: str) -> bool:Define a function that returns whether s reads the same forward and back (letters/digits only, case-insensitive).
  2. left, right = 0, len(s) - 1Plant one finger at each end of the string.
  3. while left < right:Keep going while the fingers haven't crossed.
  4. while left < right and not s[left].isalnum():If the left finger sits on punctuation or space, keep sliding it right.
  5. left += 1Advance left past that non-alphanumeric character.
  6. while left < right and not s[right].isalnum():Same idea from the right end — skip junk.
  7. right -= 1Pull right inward past that non-alphanumeric character.
  8. if s[left].lower() != s[right].lower():Compare the next real characters, ignoring case.
  9. return FalseMismatch — not a palindrome.
  10. left += 1They matched — step left inward for the next pair.
  11. right -= 1Step right inward too.
  12. return TrueFingers met with no mismatches — it is a palindrome.

Time O(n) — each index is visited at most a constant number of times; space O(1) beyond the input string.

02  3Sum

Two Pointers + Sort Medium ~20 min O(n²) time · O(1) space

Given a list of numbers, find every unique triple that adds up to 0. For [-1, 0, 1, 2, -1, -4] the answer is [[-1, -1, 2], [-1, 0, 1]].

Lay the cards out in order first analogy

Sort the numbers into a neat row, smallest to largest. Now hold one card down with your thumb (the "fixed" number). You need two other cards that cancel it out. Put a finger just past your thumb and another at the far end, and slide them: if their sum is too small, the left finger moves right to grab a bigger number; too big, the right finger moves left. Sorting is what makes "too big / too small" mean "move this way".

How to solve it

The brute force is three nested loops — O(n³). Sorting unlocks something much better:

  1. Sort the numbers.
  2. Walk a "fixed" index i across the list. For each i, the target for the other two is 0 - nums[i].
  3. Run two pointers (left = i+1, right = end) over the rest. If the three sum to 0, record it; if the sum is too small move left right; too big, move right left.
  4. Skip duplicates for both the fixed number and the found pairs, so triples aren't repeated.
MeasureCostWhy
TimeO(n²)For each fixed number (n of them) the two pointers sweep the rest (n). Sorting is only O(n log n).
SpaceO(1)Beyond the output list, just a few indices (sorting in place).
The pattern generalises

"Fix one, two-pointer the rest" is how 3Sum, 4Sum, and "closest sum" problems all work. Learn it once here and you've learned a small family.

Why do we sort the array before using two pointers?

Exactly. On a sorted row, moving left right always increases the sum and moving right left always decreases it — that's what makes the two-pointer sweep correct. Sorting also lines up duplicates so we can skip them.
Stuck? Reveal a hint hint

After sorting, loop i from the start. Inside, set left = i + 1 and right = len - 1 and move them based on whether nums[i] + nums[left] + nums[right] is below, above, or equal to 0. To avoid repeats: if i > 0 and nums[i] == nums[i-1]: continue, and after finding a triple, skip equal neighbours.

The outer loop picks the fixed number; the inner two-pointer loop finds matching pairs in one sweep. The two duplicate-skips are what make the triples unique — without them you'd print [-1, 0, 1] twice.

Line-by-line walkthrough + flow walkthrough

Sort, then fix one index and two-pointer the rest: interview default at O(n²). Triple nested loops are O(n³). A hash-set of pairs also works but duplicate handling and memory get messier — sorting makes "too small / too big" and duplicate skips natural.

flowchart TD
  start[Sort nums] --> fix[For each fixed index i]
  fix --> skipI{Duplicate of nums i-1?}
  skipI -->|yes| fix
  skipI -->|no| ptrs[left = i+1, right = end]
  ptrs --> sum{total vs 0}
  sum -->|"< 0"| L[left += 1]
  sum -->|"> 0"| R[right -= 1]
  sum -->|"= 0"| hit[Record triple, move both, skip dups]
  L --> more{left < right?}
  R --> more
  hit --> more
  more -->|yes| sum
  more -->|no| nextI{More i?}
  nextI -->|yes| fix
  nextI -->|no| out[Return res]
  out --> done[Done]
  1. def three_sum(nums):Define a function that returns every unique triple summing to 0.
  2. nums.sort()Sort in place so two-pointer moves have a clear direction and duplicates sit together.
  3. res = []Collector for the unique triples we find.
  4. n = len(nums)Cache length for the loops.
  5. for i in range(n - 2):Fix one number; leave at least two slots for the pair.
  6. if i > 0 and nums[i] == nums[i - 1]:Same fixed value as last time — skip to avoid duplicate triples.
  7. continueJump to the next i.
  8. left, right = i + 1, n - 1Two pointers on the remaining sorted slice.
  9. while left < right:Search for a pair that cancels nums[i].
  10. total = nums[i] + nums[left] + nums[right]Current three-sum.
  11. if total < 0:Too small — need a larger middle value.
  12. left += 1Move left rightward to grow the sum.
  13. elif total > 0:Too big — need a smaller right value.
  14. right -= 1Move right leftward to shrink the sum.
  15. else:Exactly zero — a valid triple.
  16. res.append([nums[i], nums[left], nums[right]])Record it.
  17. left += 1Advance left to hunt for more pairs with this fixed i.
  18. right -= 1Pull right in as well.
  19. while left < right and nums[left] == nums[left - 1]:Skip duplicate left values so we don't re-record the same triple.
  20. left += 1Keep skipping while the left value repeats.
  21. return resHand back all unique triples.

Time O(n²) after O(n log n) sort; extra space O(1) beyond the output (in-place sort).

03  Container With Most Water

Two Pointers Medium ~15 min O(n) time · O(1) space

Each number is the height of a vertical wall. Pick two walls so the water trapped between them is as much as possible. Water held = min(left, right) × (distance between them). For [1,8,6,2,5,4,8,3,7] the most is 49.

Water spills over the shorter wall analogy

Two walls hold a pool of water between them. The water can only rise as high as the shorter wall — raise the level higher and it spills over the short side. Start with the two widest-apart walls, then always move the shorter wall inward: keeping the short wall could never help (you'd only lose width), but swapping it for a taller one just might.

How to solve it

Two pointers at the ends. Each step, compute the area; keep the biggest you've seen. Then move whichever wall is shorter one step inward. Repeat until the pointers meet.

Why is "move the shorter wall" safe? The area is capped by the shorter wall. If you moved the taller wall in, the width shrinks and the height is still capped by the same short wall — you can only do worse or equal. Moving the short wall is the only move that has a chance to help.

MeasureCostWhy
TimeO(n)The two pointers only ever move toward each other — one pass.
SpaceO(1)Two indices and a "best so far" number.

We're at walls of height 8 (left) and 7 (right). Which pointer should move?

Right. Move the shorter wall (7). Keeping it can't ever beat the current area — the water is capped at 7 and any further pair using it is narrower. Moving it gives a shot at a taller wall.
Stuck? Reveal a hint hint

Don't try all pairs (that's O(n²)). Start with left = 0, right = len - 1. Track best = max(best, min(h[left], h[right]) * (right - left)), then move whichever side is shorter inward.

One pass, two indices, one running maximum. The whole cleverness is the single line that decides which pointer to move — and the analogy (water spills over the short wall) is exactly why that line is correct.

Line-by-line walkthrough + flow walkthrough

Start wide and always move the shorter wall: O(n) interview default. Checking every pair is O(n²). Moving the taller wall can never improve the area while the short wall still caps height — so the greedy move is safe and optimal.

flowchart TD
  start[left and right at ends, best = 0] --> loop{left < right?}
  loop -->|no| out[Return best]
  loop -->|yes| area[Update best with min height times width]
  area --> which{Which wall is shorter?}
  which -->|left| moveL[left += 1]
  which -->|right or tie| moveR[right -= 1]
  moveL --> loop
  moveR --> loop
  out --> done[Done]
  1. def max_area(height):Define a function that returns the maximum water area between two walls.
  2. left, right = 0, len(height) - 1Start at the widest possible pair of walls.
  3. best = 0Track the largest area seen so far.
  4. while left < right:Shrink until the pointers meet.
  5. width = right - leftHorizontal distance between the two walls.
  6. best = max(best, min(height[left], height[right]) * width)Area is capped by the shorter wall; keep the max.
  7. if height[left] < height[right]:Left wall is the short one — only moving it can help.
  8. left += 1Step the short wall inward hoping for a taller one.
  9. else:Right is shorter or they tie — move right (either side is fine on a tie).
  10. right -= 1Step the right wall inward.
  11. return bestHand back the maximum area found.

Time O(n) for one inward pass; space O(1) for two indices and a running best.
