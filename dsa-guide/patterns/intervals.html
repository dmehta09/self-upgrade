Patterns · intervals

Intervals

Lots of problems are really about ranges that might overlap — meetings on a calendar, time slots, booked rooms. The secret that unlocks almost all of them is the same: sort by start time first. Once the ranges are lined up, a single left-to-right pass is enough to merge them, count clashes, or spot a free gap. Let's watch the merge happen step by step.

00  The idea

An interval is just a range with a start and an end, like a meeting from 1 to 3. When you have a pile of them, two ranges overlap if one begins before the other ends. Checking every pair is slow. The trick: sort the intervals by their start time. Now they march left to right in order, so you only ever need to compare each one with the block you're currently building — never with everything behind you.

Appointments lined up by start time analogy

Picture appointment cards spread on a desk. First you line them up by when they start, earliest on the left. Now walking through them in order, you can instantly see which ones bump into each other — a card that starts before the one before it has finished is a clash. Lining them up first is what turns a messy pile into one tidy sweep.

When to reach for the intervals pattern

It's the right tool when you spot any of these tells:

Ranges with start & end
The input is pairs like [start, end] — meetings, bookings, time slots, number ranges.
"Overlap" or "merge"
The task mentions overlapping, merging, free gaps, or how many things happen at once.
Order isn't given
The ranges arrive jumbled, and sorting them by start (sometimes by end) makes the structure appear.
One block at a time
After sorting, you can decide everything by comparing the next range to a single "current" block.
Sort by start, almost always

For merging and most clash problems, sorting by start time is the move. A few problems (like "fit the most meetings in a room") instead sort by end time. When you're unsure, start with start time — it's right far more often than not.

01  Merge Intervals

Intervals + Sort Medium ~20 min O(n log n) time · O(n) space

Given a list of intervals, merge any that overlap and return the tidy list. For [[1,3], [2,6], [8,10], [15,18]] the first two overlap, so the answer is [[1,6], [8,10], [15,18]].

Gluing overlapping strips of tape analogy

Sort the strips of tape by where they start, then lay them down left to right. Keep one "current" strip in hand. If the next strip starts before your current one ends, they touch — so stretch the current strip's end to cover both. If it starts after a clean gap, the current strip is finished: set it down and pick up the new one. By the end you've got the fewest, longest strips that cover the same ground.

How to solve it

Sort the intervals by start time, then sweep once with a result list called merged:

  1. For each interval [start, end] in sorted order, look at the last block in merged.
  2. If merged isn't empty and this start is at or before that block's end — they overlap — stretch the block's end to max(old end, end).
  3. Otherwise there's a clean gap: append [start, end] as a new block.

Because the list is sorted by start, you only ever compare against the most recent block — anything earlier is already safely closed. That's why one pass suffices. Connecting to the tape: you stretch the current strip or set it down and grab the next.

Touching counts as overlapping — and stretch with max

Use start <= end (not <) so ranges that just touch, like [1,4] and [4,5], still merge into [1,5]. And always set the end to max(old, new): a short interval like [2,3] sitting inside [1,9] must not shrink the block to 3.

MeasureCostWhy
TimeO(n log n)The sort dominates; the single sweep afterward is only O(n).
SpaceO(n)The merged output list can hold up to n blocks when nothing overlaps.

New to this notation? See the Big-O cheat-sheet. O(n log n) is the cost of a good sort — a bit more than one pass, far less than checking every pair.

Why does sorting by start time let us merge in a single left-to-right pass?

Right. After sorting by start, each new interval starts at or after every one before it. So if it overlaps anything still open, it must overlap the latest block — earlier blocks ended even sooner. That's why comparing to just the last block in merged is enough.
Stuck? Reveal a hint hint

First intervals.sort(key=lambda x: x[0]). Keep a merged list. For each [start, end]: if merged and start <= merged[-1][1], set merged[-1][1] = max(merged[-1][1], end); else merged.append([start, end]).

02  Meeting Rooms II

Intervals + Heap Medium ~25 min O(n log n) time · O(n) space
Say it out loud

“Sort by start, keep a min-heap of end times for rooms in use. When the next meeting starts after the earliest end, reuse that room; else open a new one. Answer = peak heap size.”

Given meeting time intervals, return the minimum number of rooms required so no two overlapping meetings share a room. For [[0,30],[5,10],[15,20]] you need 2 rooms.

Front desk with sticky notes of end times analogy

Meetings arrive sorted by start. The sticky notes on the desk are the rooms currently occupied — each note shows when that room frees up. Always check the earliest free time: if the next guest arrives after that, peel the note and reuse the room; otherwise grab a fresh room. The most notes you ever had out is how many rooms you needed.

How to solve it

  1. Sort intervals by start.
  2. Keep a min-heap of end times for rooms currently occupied.
  3. For each meeting: if the heap is non-empty and start >= heap[0], pop (reuse). Then push this meeting's end.
  4. After each push, update best = max(best, len(heap)) — that's peak concurrency.
MeasureCostWhy
TimeO(n log n)Sort plus up to n heap push/pop operations.
SpaceO(n)The heap holds at most one end per meeting.
Touching meetings can share a room

Use start >= end (not >) so a meeting ending at 10 and one starting at 10 reuse the same room. Also: this is not Merge Intervals — overlapping meetings stay separate; you count concurrency.

Why is a min-heap of end times the right structure here?

Right. You only need to know whether any room is free by this start time — and the earliest end answers that in O(1) peek / O(log n) pop.
Stuck? Reveal a hint hint

intervals.sort(key=lambda x: x[0]). heap = []. For each s, e: if heap and s >= heap[0], heappop; then heappush(heap, e); track max(len(heap)).
