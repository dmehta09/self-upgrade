Sliding Window

When a problem asks for the best, longest, or shortest contiguous run inside a list or string, you don't have to re-check every possible window from scratch. Instead you slide a window along the data — add the new item on the right, drop the old one on the left — and reuse everything in between. That turns a slow "try every window" into a fast single pass.

00  The idea

A sliding window is just two markers — a left edge and a right edge — that frame a stretch of the data. You grow the window by moving right forward, and you shrink it by moving left forward. The trick is that when the window moves, you only update for the one item that entered and the one that left — you never re-scan the middle. That's why the whole sweep is one pass.

A window on a moving train analogy

You're on a train, looking out a window. As the train rolls forward, new scenery enters on the right edge of the window and old scenery slips away on the left. You never re-look at the trees in the middle — they're already framed. Sliding the window forward shows you the next view almost for free.

When to reach for a sliding window

It's the right tool when you spot these tells:

Contiguous run
You want a subarray or substring — items next to each other, not scattered picks.
Best / longest / shortest
You're maximising or minimising over all such runs (longest unique stretch, smallest sum ≥ k, max average…).
"Recompute each window" feels slow
Brute force re-adds every window from scratch — O(n²) or worse — and you sense neighbouring windows share almost everything.
Cheap to update at the edges
Adding the new item and removing the old one is O(1) (a running sum, a count, a set).
Fixed vs. variable windows

Some windows are a fixed width (always 3 items). Others grow and shrink on the fly — expand right until a rule breaks, then pull left in until it holds again. Both problems below are the growing-and-shrinking kind, which is the more common interview flavour.

A close cousin of two pointers

A sliding window is two pointers (left and right) moving the same direction, with a running "summary" of what's between them. If you've read Two Pointers, this is the next step in the same family.

01  Best Time to Buy and Sell Stock

Sliding Window Easy ~10 min O(n) time · O(1) space

You're given the daily price of a stock. You may buy once and then sell once on a later day. Return the biggest profit you can make — or 0 if no profitable trade exists. For [7, 1, 5, 3, 6, 4] the best is 5 (buy at 1, sell at 6).

Remember the cheapest day behind you analogy

Walk forward through the days, one at a time. As you go, remember the lowest price you've seen so far — that's the best day you could have bought. At every new day ask one question: "If I sold today, having bought on that cheapest earlier day, how much would I make?" Keep the best answer. Your window stretches from the cheapest day so far up to today.

How to solve it

Keep two simple values as you scan left to right:

  1. min_price — the cheapest price seen so far (the best day to have bought).
  2. best — the biggest profit found so far.

At each day's price p: first update min_price = min(min_price, p), then ask "what if I sold today?" with best = max(best, p - min_price). One pass, two numbers, done. The brute force — try every buy-day paired with every later sell-day — is O(n²); remembering the cheapest-so-far collapses it to O(n).

MeasureCostWhy
TimeO(n)One left-to-right pass; each day does a tiny constant amount of work.
SpaceO(1)Just two numbers — the cheapest price and the best profit.

New to this notation? See the Big-O cheat-sheet.

Easy trap: selling before you buy

You must buy first and sell later. Because we update min_price from the days we've already passed, today's sell price is always compared against an earlier buy. If prices only fall, no trade beats 0 — that's why best starts at 0.

Why is it safe to compare today's price only against the single cheapest price so far, instead of every earlier day?

Right. Selling on a fixed day, the most profit comes from the lowest possible buy price before it. So the single cheapest-so-far is all you need to remember — that's what turns O(n²) into O(n).
Stuck? Reveal a hint hint

Don't pair every buy-day with every sell-day. Make one pass. Keep min_price (start it at infinity) and best (start it at 0). For each price, update the cheapest, then check the profit if you sold right now.

02  Longest Substring Without Repeating Characters

Sliding Window Medium ~20 min O(n) time · O(min(n, alphabet)) space

Given a string, find the length of the longest run of characters with no repeats. For "abcabcbb" the answer is 3 (the stretch "abc"). For "bbbbb" it's 1.

A window of all-different letters analogy

Hold a window over a stretch of letters where every letter is different. Keep stretching the right edge to swallow the next letter. The moment a duplicate tries to enter — a letter already inside the window — pull the left edge in, dropping letters one by one, until that old copy of the duplicate has slid out. Now the window is all-different again, and you keep going.

How to solve it

Use a window [left, right] and a small map seen that remembers the last index where each character appeared. Walk right across the string:

  1. If the current character was seen inside the current window (its last index is >= left), jump left to just past that old copy — the duplicate has now slid out.
  2. Record this character's position: seen[ch] = right.
  3. The window is now repeat-free, so its length is right - left + 1. Update best with the larger value.

Each character is added once (by right) and the left edge only ever moves forward, so the total work is one pass.

MeasureCostWhy
TimeO(n)Both edges only move forward, so each character is handled a constant number of times.
SpaceO(min(n, alphabet))The seen map holds at most one entry per distinct character.
Off-by-one trap: stale duplicates

A character can sit in seen from before the window. That's why we check seen[ch] >= left, not just "is it in the map". Without that guard, left could jump backwards past a letter that already left the window, breaking the count.

When a repeated character appears, why do we move left to seen[ch] + 1 instead of just left + 1?

Exactly. Nudging left by one at a time would still contain the duplicate. Jumping straight to seen[ch] + 1 drops every letter up to and including the old copy in a single step, keeping the whole thing one pass.
Stuck? Reveal a hint hint

Keep a dictionary mapping each character to the last index you saw it. As right moves, if the character is already in the window (seen[ch] >= left), set left = seen[ch] + 1. Then update seen[ch] and track best = max(best, right - left + 1).
