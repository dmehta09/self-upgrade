Tries

Type two letters into a search box and autocomplete answers instantly — whether the dictionary behind it holds a hundred words or a hundred million. The trick is a trie (prefix tree): a tree where words physically share their common beginnings, so answering "what starts with ca?" costs only as much as the letters you typed. Let's build one, then put it to work on three classic problems.

00  The idea

A trie stores words the way a hotel stores guests: not in one big bag, but along hallways of letters. To find a word you walk its letters, one hallway per letter, starting from the lobby (the root). Words that begin the same way walk the very same hallways — they only split where their spellings differ.

A hotel where words share hallways analogy

"card", "care" and "cat" all check into the same hotel. They walk the same C hallway, then the same A hallway — and only split at the last doors. That sharing is the whole superpower: to ask "does any word start with CA?" you just check whether the CA hallway exists. You never open a single room, and you never care how many thousands of guests are upstairs.

In plain code-words: each node is a tiny dict of children (letter → next node) plus an end flag that marks "a word stops here". The end flag is the whole trick — it's how "app" being a prefix of "apple" differs from "app" being an inserted word. The path a→p→p exists either way; the flag on the second p is what says someone actually checked in there.

OperationTrieHash setWhy it matters
insert(word)O(L)O(1)L = word length. Both are fast.
search(word) (exact)O(L)O(1)The hash set wins narrowly on exact lookups.
startsWith(prefix)O(L)O(N·L)The set must scan every one of its N words; the trie just walks L hallways — independent of how many words are stored.

The prefix row is the entire reason tries exist. For plain exact-membership work, a set from Arrays & Hashing is simpler — reach for a trie the moment prefixes enter the story.

When to reach for a trie

"Starts with…" / autocomplete
Any question about prefixes — suggestions, completions, "is this a prefix of a stored word?".
Many words sharing prefixes
A big dictionary where words overlap heavily — the trie stores each shared beginning once.
Wildcard letters in queries
Searches like ".ad" where a dot can be any letter — the tree shape lets you branch at the wildcard.
Search a board for MANY words at once
Instead of one scan per word, carry all the words as a single trie and scan once (Word Search II below).

You run insert("apple") on a fresh trie. What does search("app") return?

Exactly. The hallway a→p→p exists because "apple" walks through it — but nobody flagged the second p as a word-end, so search("app") is False (while startsWith("app") would be True). Telling those two apart is exactly what the end flag is for.

01  Implement Trie (Prefix Tree)

Tries Medium ~20 min O(L) per op

Build the hotel yourself: a class with insert(word), search(word) (exact words only — the end flag matters!) and startsWith(prefix). All input is lowercase letters.

How to solve it

A TrieNode is almost embarrassingly small: {children: {}, end: False}. Everything else is walking.

  1. insert: start at the root and walk the word letter by letter, using setdefault to create any hallway that doesn't exist yet. Flag the final node with end = True.
  2. Factor a _walk(s) helper that follows the letters of s and returns the final node — or None the moment a hallway is missing.
  3. search = walk + check the end flag. startsWith = walk only — if you arrived anywhere at all, the prefix exists.
MeasureCostWhy
Time (each op)O(L)Every operation walks at most L letters — one dict hop per letter, regardless of how many words are stored.
SpaceO(total characters inserted)Worst case one node per character — but shared prefixes are stored only once, so real dictionaries use far less.

Why factor out the _walk helper instead of writing the loop inside both methods?

Right. Both methods follow letters until the path runs out; the only difference is whether you look at the end flag when you arrive. Copy-pasting the loop twice is how bugs sneak in — one copy gets fixed, the other doesn't.
Stuck? Reveal a hint hint

A node is just a dict plus a boolean. node.children.setdefault(ch, TrieNode()) does "follow this hallway, building it if needed" in one line. For lookups, write one helper that walks a string and returns the node it lands on (or None) — then search and starts_with are each one line on top of it.

Line-by-line walkthrough + flow walkthrough

A trie is dict-of-dicts plus an end flag — insert/search/prefix are all "walk one letter at a time". Factoring _walk keeps search vs starts_with a one-liner difference; the end flag is the whole word/prefix distinction.

  2. self.children = {}Map letter → child TrieNode.
  3. self.end = FalseTrue only if a full word checks in at this room.
  4. class Trie:Public API wrapping a root node.

Time O(L) per op for word length L; space O(total characters inserted) across shared prefixes.

02  Design Add & Search Words

Tries Medium ~20 min O(L) add · O(26^d) worst search

Build add_word(word) and search(word) — but the search word may contain ".", which matches any letter. After adding "bad", "dad", "mad": search("pad") → False, search(".ad") → True, search("b..") → True.

A skeleton key for one hallway analogy

It's the hallway hotel again — but now a "." in your query is a skeleton key. A normal letter opens exactly one door. At a dot, you must peek through every door on that hallway and continue the search from each one. If any of those branches reaches the end of the query on a flagged room, the answer is True.

How to solve it

add_word is exactly the insert from problem 01. The search becomes a small recursive DFS, dfs(node, i):

  1. If i == len(word): we've consumed the whole query — return node.end.
  2. If word[i] is a real letter: descend into that one child (or return False if the hallway doesn't exist).
  3. If word[i] is ".": try every child and OR the results — any(dfs(child, i + 1) for child in node.children.values()).
MeasureCostWhy
add_wordO(L)Plain trie insert — one hop per letter.
search (worst)O(26^dots · L)Each dot can fan out to up to 26 children. Honestly: a query that's all dots is the worst case — and in practice queries have few dots, so most searches stay near O(L).
SpaceO(total chars)The trie itself, plus O(L) recursion depth.
Easy trap: checking the end flag too early

Return node.end only at the end of the query word — when i == len(word) — not whenever you happen to pass a flagged node mid-walk. With "bad" stored, search("ba.") must walk all three letters and check the flag on the last node; stopping at a ✓ you stumble past would make search("b") wrongly True.

search("..") returns True only if…

Right. Both dots must land exactly on a path of length 2 that ends in a flag. "bad" alone gives False — the path b→a exists but a carries no ✓. Dots loosen which doors you may open, never how many you must walk through.
Stuck? Reveal a hint hint

Write search as a recursive helper carrying two things: the current trie node and the index i into the query. A letter is a single recursive call; a dot is a loop over node.children.values() where finding one success is enough — Python's any(...) says it perfectly.

03  Word Search II

Tries Hard ~30 min stretch goal

Given a grid of letters and a list of words, find every word you can trace through adjacent cells (up/down/left/right), without reusing a cell within one word. The senior twist: don't search the board once per word — search it once for all words simultaneously, guided by a trie. This is a stretch problem: read it, understand the idea, and come back to code it from scratch once the rest of the pattern feels easy.

Carry the whole list as a word-tree analogy

The naive plan runs through the maze once per word on your list — exhausting. Instead, carry the whole list as one trie. At each fork in the maze you ask the trie: "does some word on my list go this way?" If no hallway matches, you stop on the spot. Dead hallways prune themselves, and one walk through the maze checks every word at once.

How to solve it

It's Backtracking on the grid, with a trie as the map of what's worth exploring:

  1. Build a trie of all the words first. Store the full word at its end node (instead of a bare flag) so you can collect it without rebuilding the path.
  2. DFS from every cell, carrying the current trie node alongside your position.
  3. Kill the branch the moment the cell's letter isn't a child of the current node — no word on the list continues this way.
  4. Collect when you hit an end node — then clear its stored word so the same word isn't reported twice via a different path.
  5. Mark cells visited in place (overwrite with "#") and restore on backtrack — the classic choose/explore/undo dance.
MeasureCostWhy
TimeO(cells · 3^(L-1))Worst case: from each cell, a DFS that branches up to 3 ways per step (you can't go back where you came from) for the longest word L. In practice the trie prunes most branches at the first letter.
SpaceO(total trie chars)The trie of all words, plus O(L) recursion depth.

Why does the trie version beat running a plain DFS once per word?

That's it. With 1000 words, plain DFS walks the board 1000 times — and re-discovers the same dead-end prefixes 1000 times. The trie merges all the words into one map, so a single sweep checks everything, and a hopeless start like "aa" is rejected once, instantly, for every word at the same time.
Stuck? Reveal a hint hint

Your DFS signature is dfs(r, c, node) — position plus trie node. First thing inside: nxt = node.children.get(board[r][c]); if it's None, return (that's the pruning). If nxt carries a stored word, append it and set it to None. Then mark the cell "#", recurse into the 4 neighbours that aren't "#", and restore the letter before returning.

Line-by-line walkthrough + flow walkthrough

Build one trie of all words, then DFS the board once carrying the current trie node. Missing children prune instantly; store the full word at end nodes and clear it after collecting so duplicates don't report twice.
