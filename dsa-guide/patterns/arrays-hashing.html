Arrays & Hashing

The most common tool in the whole guide. A hash map is instant memory of what you've already seen — ask "have I met this before?" and it answers immediately. That one superpower turns many slow "compare everything to everything" scans into a single fast pass. Let's build the intuition, then solve three classics with it.

00  The idea

A hash map (Python calls it a dict) is a box of labelled drawers. You file a value under a key, and later you can fetch it back — or just check "is anything filed under this key?" — in O(1), meaning the time doesn't grow as the map gets bigger. Compare that to a plain list, where "is this in here?" means scanning every item.

So the move is: as you walk the data once, remember what you've seen in a map. The next time you need to know "did I already see the thing that completes this answer?", you ask the map instead of looping again. You trade a little extra space (O(n) to store what you've seen) for much faster lookups — and a brute-force O(n²) double scan collapses into one O(n) pass.

A coat-check at a theatre analogy

You hand over your coat and get a numbered ticket. Later you show the ticket and the attendant grabs your exact coat instantly — they never rummage through every coat on the rack. The ticket is the key; your coat is the value. A hash map is that coat-check: file things under a label, fetch them back in one step.

When to reach for a hash map

It's the right tool when you see any of these tells:

"Have I seen this?"
You need to check membership or look something up while scanning — and a plain list scan would be too slow.
Counting
You're tallying how many times each thing appears (a frequency count).
Grouping by a key
You want to bucket items that share some property (same sorted letters, same remainder…).
"Every pair" feels slow
A brute force checks all pairs — O(n²) — and you sense one value remembered could skip the inner loop.
A set is a map with keys only

When you only care "have I seen this?" and not a stored value, use a set instead of a dict. Same O(1) lookup, less clutter. A dict is for when you also want to remember something about each key — like the index it lived at.

01  Two Sum

Arrays & Hashing Easy ~10 min O(n) time · O(n) space

Given a list of numbers and a target, return the indices of the two numbers that add up to it. For nums = [2, 7, 11, 15] and target = 9, the answer is [0, 1] because 2 + 7 = 9.

Sticky notes of "what I still need" analogy

As you meet each number, jot a sticky note: "I still need target − me." Then before writing each new note, glance at the notes you've already stuck up. The answer is the first time a number you're holding is already written on a note — that note's number plus this one hits the target.

How to solve it

The brute force checks every pair — two nested loops, O(n²). The hash-map trick keeps a map called seen that maps a number to the index where it lived. Walk the list once:

  1. For the current number n, compute what would complete it: need = target - n.
  2. If need is already a key in seen, you've found the pair — return [seen[need], i].
  3. Otherwise file the current number: seen[n] = i, and move on.

Each number is checked against the map (O(1)) and then stored (O(1)), so the whole thing is one O(n) pass. Closing the loop with the picture: the map is the wall of sticky notes, and step 2 is the glance that finds a match.

MeasureCostWhy
TimeO(n)One pass; each lookup and insert into the map is O(1) on average.
SpaceO(n)In the worst case we store nearly every number in the map before we match.

New to this notation? See the Big-O cheat-sheet.

Check the map before you add the current number

If you store n first and then look for need, a number could match itself (e.g. target 6 with a single 3). Look up need first, then file n — that guarantees the two indices are different.

Why is the hash-map version O(n) time while checking every pair is O(n²)?

Right. The inner loop of the brute force existed only to search for the complement. A hash map does that search in one step, so a single pass suffices — O(n) time, at the cost of O(n) space for the map.
Stuck? Reveal a hint hint

Keep a dict seen mapping number → index. As you loop with enumerate, compute need = target - n and check if need in seen before storing n. Return [seen[need], i] the moment you find it.

Line-by-line walkthrough + flow walkthrough

A hash map of value → index is the interview default: one pass, O(n) time. Nested loops are O(n²) and sorting then two-pointers only works if the problem allows returning values (not indices) or you track indices carefully — the map is simpler and optimal.

  1. def two_sum(nums, target):Define a function that takes the list of numbers and the target sum we want.
  2. seen = {}Start an empty dictionary — our sticky-note wall mapping each number we've seen to its index.
  3. for i, n in enumerate(nums):Walk the list once; i is the position and n is the value at that position.
  4. need = target - nCompute the partner number that would make n + need equal the target.
  5. if need in seen:Ask: did we already pass that partner earlier? A dict lookup is O(1).
  6. return [seen[need], i]Yes — return the earlier index and the current index. We're done.

Time O(n) for one pass; space O(n) for the dictionary in the worst case.

02  Group Anagrams

Arrays & Hashing Medium ~15 min O(n·k log k) time · O(n·k) space

Given a list of words, group together the ones that are rearrangements of each other (anagrams). For ["eat","tea","tan","ate","nat","bat"], one grouping is [["eat","tea","ate"], ["tan","nat"], ["bat"]].

File each word by its fingerprint analogy

Two words are anagrams exactly when their letters, sorted, come out the same: "eat" and "tea" both sort to "aet". So sorted-letters is a fingerprint. Take a filing cabinet of drawers, label each drawer with a fingerprint, and drop every word into the drawer that matches its fingerprint. Words in the same drawer are anagrams.

How to solve it

Use a dict whose key is the fingerprint (the word's letters sorted into a string) and whose value is the list of words that share it. A defaultdict(list) makes the "first word for a new key" case painless — it auto-creates an empty list. For each word:

  1. Build the key: "".join(sorted(word)) — sort the letters, glue them back into a string.
  2. Append the word to groups[key].

At the end, the dict's values are exactly the groups. Closing the loop: the dict is the filing cabinet, and the sorted-letters key is the label on each drawer.

MeasureCostWhy
TimeO(n·k log k)For each of the n words we sort its k letters, and sorting k things costs k log k.
SpaceO(n·k)The map holds every word (total length n·k) plus its fingerprint keys.
A faster fingerprint when letters are limited

If the words are all lowercase a–z, you can use a 26-slot count of letters as the key instead of sorting. That drops each key to O(k) and avoids the log k — a classic interview follow-up.

What makes a good dictionary key for grouping anagrams?

Exactly. First letter or length would lump together non-anagrams ("bat" and "big" share a length). Sorted letters are the same for all anagrams and differ for everything else — a perfect fingerprint.
Stuck? Reveal a hint hint

Reach for collections.defaultdict(list). Loop over the words; for each, compute key = "".join(sorted(s)) and do groups[key].append(s). Finally return list(groups.values()).

Line-by-line walkthrough + flow walkthrough

Sort-letters-as-key is the interview default: one map, one pass over the words. Pairwise comparing every word is O(n²·k). A 26-count fingerprint is a common follow-up for lowercase a–z (O(n·k) time); sorted keys are simpler to write under pressure and still optimal enough.

03  Product of Array Except Self

Arrays & Hashing Medium ~20 min O(n) time · O(1) extra space

Return a new array where out[i] is the product of all the numbers except nums[i] — and do it without division. For [1, 2, 3, 4] the answer is [24, 12, 8, 6].

Everything on my left × everything on my right analogy

Stand on any number in the row. The product of "everything except me" is just everything to my left multiplied by everything to my right. So make two sweeps: one left-to-right gathering the running product of what came before, one right-to-left gathering what comes after. Multiply the two and you've left yourself out — no division needed.

How to solve it

Division would be easy (total product ÷ each number) but breaks on a zero and is banned here. The two-sweep trick avoids it and uses only the output array for storage:

  1. Left sweep. Walk left-to-right keeping a running prefix (start at 1). Before multiplying it in, store it: out[i] = prefix, then prefix *= nums[i]. Now out[i] holds the product of everything before i.
  2. Right sweep. Walk right-to-left keeping a running suffix (start at 1). Multiply it into what's already there: out[i] *= suffix, then suffix *= nums[i].

After both passes, each out[i] is left-product × right-product — exactly "everything except me". The output array doesn't count as extra space, so this is O(1) extra. Closing the loop: sweep one builds every "left of me", sweep two folds in every "right of me".

MeasureCostWhy
TimeO(n)Two straight passes over the list — n + n steps.
SpaceO(1)Only two running numbers; the output array isn't counted as extra space.
Store the prefix before multiplying yourself in

The order matters: write out[i] = prefix first, then do prefix *= nums[i]. If you multiply first, you'd include your own number — and the whole point is to leave yourself out.

Why does this approach avoid the division trick (total product ÷ nums[i])?

Right. A single zero makes the total product zero and dividing by it blows up. The prefix/suffix sweeps sidestep division entirely and still run in one O(n) pass with O(1) extra space.
Stuck? Reveal a hint hint

Make res = [1] * n. First loop forward with a prefix: set res[i] = prefix, then prefix *= nums[i]. Then loop backward with a suffix: res[i] *= suffix, then suffix *= nums[i].

Line-by-line walkthrough + flow walkthrough

Prefix × suffix in the output array is the interview default: O(n) time, O(1) extra space, no division. Building full prefix/suffix arrays also works but uses O(n) extra space. Division by the total product fails on zeros and is usually banned.

  pref --> writeL["res i = prefix, then prefix *= nums i"]
  writeL --> moreL{More left?}
  moreL -->|yes| writeL
  moreL -->|no| suf[Backward pass: multiply right products]
  suf --> writeR["res i *= suffix, then suffix *= nums i"]
  writeR --> moreR{More right?}
  moreR -->|yes| writeR
  moreR -->|no| out[Return res]
  out --> done[Done]
  1. def product_except_self(nums):Define a function that returns, for each index, the product of every other element.
  2. n = len(nums)Cache the length so both loops know how far to go.
  3. res = [1] * nOutput array — starts as all ones so multiplying into it is safe.
  4. prefix = 1Running product of everything strictly to the left of the current index.
  5. for i in range(n):Left-to-right sweep.
  6. res[i] = prefixWrite the left-product before including nums[i] — that's how we leave ourselves out.
  7. prefix *= nums[i]Fold this value into the running left product for the next index.
  8. suffix = 1Running product of everything strictly to the right.
  9. for i in range(n - 1, -1, -1):Right-to-left sweep.
  10. res[i] *= suffixMultiply in the right-product so res[i] becomes left × right.
  11. suffix *= nums[i]Fold this value into the running right product for the previous index.
  12. return resHand back the filled product array.

Time O(n) for two linear passes; extra space O(1) beyond the output array (two running scalars).
