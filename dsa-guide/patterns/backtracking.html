Backtracking

Some problems ask for every combination, subset, or arrangement — and the only honest way is to try them all. Backtracking does this without getting lost: make one choice, dig deeper, then undo that choice and try the next. You explore a whole tree of decisions and leave no mess behind on the way back up. Let's watch it grow, then solve two classics.

00  The idea

Imagine you're exploring a maze while unrolling a ball of string behind you. At every fork you pick a path and keep going. If it dead-ends, you don't panic — you rewind the string back to the last fork and try a different path. Backtracking is exactly that, in code: at each step you make a choice (take this number), recurse — call the same function on the smaller leftover problem — then undo the choice and try the next one. Every path you finish is one answer; every rewind frees you to find another.

A maze and a ball of string analogy

You walk a maze unrolling a string behind you. At each fork you try a path; if it dead-ends, you rewind the string to the last fork and try another. You never lose your way, and you eventually walk every path. The string is your stack of choices — and rewinding it is the undo that makes backtracking work.

When to reach for backtracking

It's the right tool when you spot any of these tells:

"Find ALL …"
The task wants every subset, combination, permutation, or arrangement — not just one or a count.
Build-a-choice-at-a-time
An answer is built step by step, and at each step there are a few options to try.
Constraints to respect
You must prune branches that break a rule (a queen attacks, a sum overshoots) before going deeper.
Small n, exponential answers
There can be up to 2ⁿ or n! results, so n is usually small — and exploring them all is expected.
The three-line skeleton

Almost every backtracking solution is: choose (append to the path) → recurse (call yourself on what's left) → un-choose (pop it back off). Memorise that rhythm — choose, recurse, undo — and most of these problems become fill-in-the-blanks.

Save a copy, not the live path

The path list keeps changing as you choose and undo. When you record an answer, store path[:] (a snapshot copy), never path itself — otherwise every saved answer ends up pointing at the same list, which is empty by the end.

01  Subsets

Backtracking Medium ~15 min O(n·2ⁿ) time · O(n) space

Given a list of distinct numbers, return every possible subset (the "power set") — including the empty set and the full set. For [1, 2, 3] there are 8 subsets, from [] up to [1, 2, 3].

Pack a bag, one item at a time analogy

As in the picture above: walk along the list of items. At each index you stand at a fork — add this item to your bag, explore everything that follows, then take it back out and explore again without it. Every snapshot of the bag along the way is one valid subset. You never repeat a packing because each item is only ever offered once, in order.

How to solve it

Write a helper backtrack(start, path). The start index says "only numbers from here on are still on offer", and path is the bag we've built so far.

  1. Record a copy of the current path — every path we reach is itself a valid subset.
  2. Loop i from start to the end. For each: choose by appending nums[i], recurse with start = i + 1 (so we never reuse or reorder), then undo with path.pop().

Passing i + 1 (not 0) is what keeps subsets like [1, 2] and [2, 1] from both appearing — we only ever go forward. Connecting to the maze: each pop() is rewinding the string one fork.

The picture above showed the subsets; this one shows the machine — the actual call tree. Watch each call record its bag on arrival, and each return pop in exact reverse order. The pop is what people forget on a whiteboard; once you've watched it, you won't.

MeasureCostWhy
TimeO(n·2ⁿ)There are 2ⁿ subsets, and copying each one into the result costs up to O(n).
SpaceO(n)Recursion depth and the working path are at most n deep (the output itself aside).

New to this notation? See the Big-O cheat-sheet. O(2ⁿ) means each extra item doubles the work — fine for small n, hopeless for large.

Why do we append path[:] to the results instead of path itself?

Right. path is one shared list that grows and shrinks as we recurse and pop. Storing path would save a reference to that same list — by the end it's empty, so every saved answer would look empty. path[:] freezes a copy at that moment.
Stuck? Reveal a hint hint

Use a recursive helper backtrack(start, path). First line: record path[:]. Then loop i from start: path.append(nums[i]), call backtrack(i + 1, path), then path.pop(). Kick it off with backtrack(0, []).

Show the solution & run it solution
subsets.py
[[], [1], [1, 2], [1, 2, 3], [1, 3], [2], [2, 3], [3]]

Each call records the bag as it stands, then tries adding every later number in turn — undoing after each. The append/pop() pair is the choose/undo of the maze, and i + 1 stops us from revisiting an earlier fork.

02  Combination Sum

Backtracking Medium ~25 min exponential time · O(target) space

Given a list of distinct positive numbers and a target, find every combination that sums to the target. The catch: each number may be reused as many times as you like. For candidates [2, 3, 6, 7] and target 7, the answers are [2, 2, 3] and [7].

Making exact change with a coin tray analogy

You have coins of a few values and want to make an exact amount. Keep dropping coins into a pile — and you're allowed to pick the same coin value again and again. If the pile hits the target exactly, write that combination down. If it ever overshoots, that path is hopeless, so rewind one coin and try the next. To avoid writing the same pile in a different order, you only ever pick the current coin or a later one — never an earlier one.

How to solve it

Write backtrack(start, path, remain), where remain is how much of the target is still unpaid.

  1. If remain == 0, the pile is exact — record path[:] and return.
  2. If remain < 0, we overshot — this path is dead, return.
  3. Otherwise loop i from start: choose candidates[i], recurse with i (not i + 1!) so the same coin can be reused, subtracting it from remain, then undo with pop().
One tiny index controls reuse

Recursing with i lets a coin repeat; recursing with i + 1 (like Subsets) forbids reuse. That single character is the whole difference between this problem and "each number used once". The start index also stops [2,3] and [3,2] from both appearing.

Don't recurse from 0 every time

If you pass start = 0 on every call, you'll let a later coin sit before an earlier one — and the same combination shows up in many orders. Always recurse from i (current coin onward), so each pile is built in non-decreasing order exactly once.

MeasureCostWhy
TimeexponentialThe tree of coin choices can branch deeply; its size depends on the candidates and target.
SpaceO(target)Recursion goes at most as deep as the smallest coin divides into target.

In the recursive call, why do we pass i rather than i + 1?

Correct. Passing i keeps the current coin in play for the next level, which is exactly what "numbers may be reused" demands. We still don't go backward below i, so each combination is generated in one fixed order — no duplicates.
Stuck? Reveal a hint hint

Track a remain (target minus what you've taken). Base cases first: remain == 0 records path[:]; remain < 0 returns. Then loop i from start, append candidates[i], recurse with backtrack(i, path, remain - candidates[i]), then pop.

Show the solution & run it solution
combination_sum.py
[[2, 2, 3], [7]]

The two base cases prune: an exact pile is saved, an overshoot is abandoned. Recursing from i keeps each coin reusable while the start index fixes the order — so the coin-tray rule "same value again, but never reorder" holds, and each combination is found once.
