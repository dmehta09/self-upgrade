OOP fundamentals · the four pillars

The four pillars of OOP.

Encapsulation, abstraction, inheritance, polymorphism. Four words that sound academic but each solve a very concrete problem. We take them one at a time — analogy first, then Python.

01  Encapsulation: protect your own data

Encapsulation means an object guards its own state. Instead of letting any code reach in and set fields to nonsense, you expose methods that enforce the rules. The object can never be put into an invalid state.

Like an ATM, not an open cash drawer analogy

An open drawer lets anyone take any amount, including more than is there. An ATM forces every change through rules: you can't withdraw more than your balance, can't deposit negative money. The balance is locked away; the buttons enforce the invariants.

Python has no private keyword. Instead there's a convention: a leading underscore (_balance) means "internal — don't touch from outside." It's a polite "keep out," not a locked door. Then you expose safe access through methods or a @property.

account.py
class BankAccount:
    def __init__(self, balance: float = 0):
        self._balance = balance        # "_" = internal, hands off

    @property
    def balance(self) -> float:        # read-only window onto _balance
        return self._balance

    def deposit(self, amount: float) -> None:
        if amount <= 0:
            raise ValueError("deposit must be positive")
        self._balance += amount

    def withdraw(self, amount: float) -> None:
        if amount > self._balance:
            raise ValueError("insufficient funds")
        self._balance -= amount

acct = BankAccount(100)
acct.deposit(50)
print(acct.balance)        # 150
acct.withdraw(999)         # ValueError: insufficient funds
Output150 ValueError: insufficient funds
Single vs double underscore

_x is a convention. __x (two leading underscores) triggers name mangling: Python renames it to _ClassName__x to avoid clashes in subclasses. Use _x by default; reach for __x only when you truly need to prevent a subclass from colliding with the name.

02  Abstraction: show what, hide how

Where encapsulation hides data, abstraction hides complexity. You define a simple, stable surface — "every payment method has a pay()" — and let each concrete type fill in the messy details. Callers depend on the idea, not the implementation.

Driving a car analogy

You steer, accelerate, brake. You don't think about fuel injection or torque vectoring. The pedals are the abstraction; the engine is the hidden implementation. Swap a petrol engine for electric and you still just press the pedal.

In Python you express an abstraction two ways. An abstract base class (ABC) says "you must implement these methods to be a subclass." A Protocol says "anything with these methods counts" — no inheritance required (structural typing).

from abc import ABC, abstractmethod

class PaymentMethod(ABC):
    @abstractmethod
    def pay(self, amount: float) -> str:
        ...                              # no body — subclasses must supply one

class CreditCard(PaymentMethod):
    def pay(self, amount: float) -> str:
        return f"Charged ${amount} to card"

class PayPal(PaymentMethod):
    def pay(self, amount: float) -> str:
        return f"Sent ${amount} via PayPal"

def checkout(method: PaymentMethod, amount: float) -> None:
    print(method.pay(amount))            # doesn't care which kind it is

checkout(CreditCard(), 30)               # Charged $30 to card
checkout(PayPal(), 12)                   # Sent $12 via PayPal
PaymentMethod()                          # TypeError: can't instantiate abstract class
from typing import Protocol

class Payable(Protocol):
    def pay(self, amount: float) -> str: ...

# No inheritance! Any class with a matching pay() satisfies Payable.
class Cash:
    def pay(self, amount: float) -> str:
        return f"Took ${amount} in cash"

def checkout(method: Payable, amount: float) -> None:
    print(method.pay(amount))

checkout(Cash(), 5)                      # Took $5 in cash  — Cash never imported Payable
ABC or Protocol?

Use an ABC when you own the hierarchy and want to share code + force a contract. Use a Protocol when you want to accept anything "shaped right," including classes you don't control. Protocols are Python's take on Go-style interfaces.

03  Inheritance: build on what exists

Inheritance lets a class reuse and extend another. The child is a kind of the parent — a Dog is an Animal — so it gets the parent's attributes and methods for free, and can add or override behavior.

Specialized job roles analogy

An Employee has a name and can clock in. A Manager is an Employee who can also approve budgets. You don't re-describe "has a name" — you say "a Manager is an Employee, plus this extra."

animals.py
class Animal:
    def __init__(self, name: str):
        self.name = name

    def speak(self) -> str:
        return "..."

class Dog(Animal):
    def speak(self) -> str:              # override the parent's version
        return "Woof!"

class Puppy(Dog):
    def __init__(self, name: str, weeks: int):
        super().__init__(name)           # call Animal.__init__ to set name
        self.weeks = weeks

    def speak(self) -> str:
        return super().speak() + " (tiny)"   # extend, don't replace

print(Dog("Rex").speak())                # Woof!
print(Puppy("Milo", 6).speak())          # Woof! (tiny)
OutputWoof! Woof! (tiny)
What does super() actually do? go deeper

super() calls the next class up the method resolution order (MRO) — the linear list Python builds of where to look for methods. For single inheritance it's just "the parent." With multiple inheritance it follows the C3 linearization (see Dog.__mro__). Using super() instead of naming the parent directly keeps things working when the hierarchy changes.

Don't reach for inheritance first

Inheritance is a tight, permanent coupling — the child depends on the parent's internals. If the relationship is really "has-a" not "is-a" (a Car has an Engine, it isn't one), prefer composition. More on this in Relationships and the inheritance & composition deep dive.

04  Polymorphism: one call, many shapes

"Poly-morph" = many forms. The same method call does the right thing for whatever object it lands on. Write a function once against the general idea, and it works for every type that fits — including types invented later.

A universal "play" button analogy

Press play and a song plays, a video plays, a podcast plays. One verb, the right behavior per medium. Your remote doesn't need a different button per file type.

shapes.py
from abc import ABC, abstractmethod
from math import pi

class Shape(ABC):
    @abstractmethod
    def area(self) -> float: ...

class Circle(Shape):
    def __init__(self, r: float): self.r = r
    def area(self) -> float: return pi * self.r ** 2

class Rectangle(Shape):
    def __init__(self, w: float, h: float): self.w, self.h = w, h
    def area(self) -> float: return self.w * self.h

def total_area(shapes: list[Shape]) -> float:
    return sum(s.area() for s in shapes)     # calls the right area() for each

print(round(total_area([Circle(1), Rectangle(2, 3)]), 2))   # 9.14
Output9.14

The magic: total_area never checks types. Add a Triangle tomorrow and it just works — no edits to existing code. (That's the Open/Closed Principle in action.)

Python's superpower: duck typing

"If it walks like a duck and quacks like a duck, it's a duck." Python doesn't require a shared base class — if an object has an .area() method, total_area is happy. The Shape ABC here is for clarity and type-checking, not a runtime requirement.

A class exposes balance as a read-only @property backed by _balance. Which pillar is this?

Right: hiding the raw field and controlling access through a property is encapsulation — the object protects its own state.

Why can total_area(shapes) handle a Triangle you add next week without changing the function?

Right: the function depends only on the shared area() behavior. Any object that provides it slots in — that's polymorphism (and the Open/Closed Principle).

06  Practice

Exercise 1 · encapsulation

Build a Temperature class that stores Celsius internally but lets callers read/write Fahrenheit too — without ever storing an impossible temperature (below absolute zero, -273.15°C).

Use a @property for fahrenheit with a getter and setter, and validate in the setter.

Show a solution solution
temperature.py
class Temperature:
    def __init__(self, celsius: float = 0):
        self.celsius = celsius           # goes through the setter below

    @property
    def celsius(self) -> float:
        return self._celsius

    @celsius.setter
    def celsius(self, value: float) -> None:
        if value < -273.15:
            raise ValueError("below absolute zero")
        self._celsius = value

    @property
    def fahrenheit(self) -> float:
        return self._celsius * 9 / 5 + 32

    @fahrenheit.setter
    def fahrenheit(self, value: float) -> None:
        self.celsius = (value - 32) * 5 / 9   # reuse validation

t = Temperature(25)
print(t.fahrenheit)      # 77.0
t.fahrenheit = 212
print(t.celsius)         # 100.0
t.celsius = -300         # ValueError: below absolute zero
Exercise 2 · polymorphism

Add a Triangle(base, height) to the shapes example. How many lines of the existing total_area function do you need to change?

Show a solution solution

Zero. That's the whole point. You only add a new class:

triangle.py
class Triangle(Shape):
    def __init__(self, base: float, height: float):
        self.base, self.height = base, height
    def area(self) -> float:
        return 0.5 * self.base * self.height

# total_area([...]) is untouched and now handles Triangle too.
