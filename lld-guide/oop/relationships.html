OOP fundamentals · relationships

How classes relate — and the UML to draw it.

Real systems are many classes wired together. The single most useful design question is "is-a or has-a?" Get the relationships right and the diagram almost writes itself.

01  The big question: is-a or has-a?

When one class involves another, it's almost always one of two relationships:

🧬

is-a → inheritance

A Manager is an Employee. The subclass is a kind of the base. Use class Manager(Employee).

🧩

has-a → composition

A Car has an Engine. One object contains/uses another. Store it as an attribute.

Say it out loud analogy

Read the sentence: "A dog is an animal" — sounds right, so inherit. "A car is an engine" — sounds absurd, so don't; a car has an engine. The English "is-a / has-a" test catches most modelling mistakes for free.

02  The five relationships, and their UML arrows

UML (Unified Modeling Language) is just a shared notation for these. You don't need all of UML — five line styles cover almost everything you'll draw in an interview or design doc:

Inheritance (is-a)hollow triangle → points to the parent
Composition (owns)filled diamond at the whole; part dies with it
Aggregation (has)hollow diamond; part can outlive the whole
Association (uses)solid arrow; a lasting link between peers
Dependency (needs)dashed arrow; a passing use (a method argument)
Composition vs aggregation — the lifetime test

Both are "has-a." The difference is ownership of lifetime: with composition the part can't exist without the whole (a House and its Rooms). With aggregation the part lives independently (a Team and its Players — players exist before and after the team). In code they look similar; the distinction is about meaning.

03  How to read a UML class box

A class is drawn as a box with up to three compartments: the name on top, attributes in the middle, methods at the bottom. A + means public, - means private/internal.

Name · attributes · methods. - private, + public. Abstract classes & interfaces are drawn in italics (often with a «interface» stereotype).

04  Composition in Python

Composition is wonderfully simple in code: the whole just holds the part as an attribute. No special syntax — that's a feature.

class Engine:
    def __init__(self, hp: int):
        self.hp = hp
    def start(self) -> str:
        return f"Engine ({self.hp}hp) roars to life"

class Car:
    def __init__(self, hp: int):
        self.engine = Engine(hp)         # the Car OWNS its Engine (composition)
    def start(self) -> str:
        return self.engine.start()       # delegate to the part

print(Car(300).start())                  # Engine (300hp) roars to life

05  "Favour composition over inheritance"

You'll hear this constantly. The reason: inheritance locks a child to its parent's implementation forever, and deep hierarchies get rigid fast. Composition keeps parts swappable and relationships explicit. The full treatment — kinds of inheritance, the diamond problem, mixins, delegation and dependency injection — is in the inheritance & composition deep dive.

The classic trap

"A Stack is just a list with fewer methods, so class Stack(list)!" Now your Stack accidentally inherits insert, __setitem__, slicing… and someone can poke the middle of your stack. It has-a list; it isn't one.

class Stack(list):              # "is-a list" — too much leaks in
    def push(self, x): self.append(x)
    def pop_top(self): return self.pop()

s = Stack()
s.push(1); s.push(2)
s.insert(0, 99)                 # oops: list.insert still works, breaks LIFO
print(s)                        # [99, 1, 2]  — not a real stack anymore
class Stack:                    # "has-a list" — only the stack API is exposed
    def __init__(self):
        self._items: list = []
    def push(self, x) -> None:
        self._items.append(x)
    def pop(self):
        return self._items.pop()
    def __len__(self) -> int:
        return len(self._items)

s = Stack()
s.push(1); s.push(2)
print(s.pop(), len(s))          # 2 1  — only push/pop/len are possible

A Playlist contains Songs, but songs exist on their own and can be in many playlists. Which relationship?

Right: the songs outlive any one playlist and are shared — that independent lifetime makes it aggregation, not composition.

You're tempted to write class Email(dict) so an email "is a dict of headers." Better?

Right: an Email has headers, it isn't a dictionary. Inheriting dict exposes clear(), popitem(), iteration… none of which belong on an Email. Compose.
