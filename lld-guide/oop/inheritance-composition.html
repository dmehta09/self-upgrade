Inheritance vs composition — and when to use each.

Two ways to reuse code: a class can be a kind of another (inheritance) or have another inside it (composition). Both look tempting; only one is right for a given relationship. This page goes deep on each, then hands you a rule for choosing.

01  Two ways to reuse: be one, or have one

You already met the headline in Relationships: is-a → inheritance, has-a → composition. That sentence is the whole game — but each tool has depth worth knowing before an interview or a real design. Here's the framing for the rest of the page:

🧬

Inheritance — reuse by being

A subclass is a kind of its parent and inherits its behavior. Powerful, but it's the tightest coupling in OOP: the child is welded to the parent's internals.

🧩

Composition — reuse by having

An object holds other objects and delegates to them. Looser, swappable, and explicit — which is why the old advice is "favour composition over inheritance."

Inherit a family trait, carry a toolbox analogy

Inheritance is like a trait you're born with — you can't easily hand it back. Composition is like a toolbox you carry: you can swap a hammer for a nail-gun any time, and lend the box to someone else. Born-with is fine when it's truly permanent; for everything else, carry the toolbox.

02  The kinds of inheritance

Interviewers love to ask you to name these. They're just shapes of the family tree:

①

Single

One child, one parent. class Dog(Animal).

⛓️

Multilevel

A chain: grandparent → parent → child. class Puppy(Dog) where Dog(Animal).

🌿

Hierarchical

Many children share one parent. Dog(Animal) and Cat(Animal).

🔱

Multiple

One child, several parents at once. class Duck(Walks, Swims). Python allows it; Java doesn't.

kinds.py
class Animal:
    def __init__(self, name):
        self.name = name

class Dog(Animal):   pass          # single:       Dog   -> Animal
class Puppy(Dog):    pass          # multilevel:   Puppy -> Dog -> Animal
class Cat(Animal):   pass          # hierarchical: Dog and Cat both -> Animal

class Walks:
    def move(self): return "walks"
class Swims:
    def move(self): return "swims"
class Duck(Walks, Swims): pass     # multiple:     Duck  -> Walks, Swims

print(Puppy("Milo").name)          # Milo  — name came two levels up
print(Duck().move())               # walks — the LEFT parent wins (the MRO)
OutputMilo walks

That last line is the interesting one. Duck has two parents that both define move() — so which runs? Python has a precise rule for that, and it's the key to multiple inheritance: the MRO.

03  super(), the MRO, and the diamond problem

Every class has a method resolution order (MRO): a single, flat list of where Python looks for a method, parents included. super() doesn't mean "my parent" — it means "the next class in the MRO." For single inheritance that's the same thing; with multiple inheritance it's the superpower that makes everything line up.

The famous puzzle is the diamond: two classes A and B both inherit one Base, and D inherits both. If D triggers Base's work, does Base run twice?

The diamond: D(A, B), A(Base), B(Base)
Every line points up to a parent (is-a). The MRO flattens this diamond into one line so Base is visited exactly once.
diamond.py
class Base:
    def __init__(self):
        print("Base.__init__")

class A(Base):
    def __init__(self):
        print("A.__init__")
        super().__init__()          # "next in the MRO", not literally Base

class B(Base):
    def __init__(self):
        print("B.__init__")
        super().__init__()

class D(A, B):
    def __init__(self):
        print("D.__init__")
        super().__init__()

D()
print([cls.__name__ for cls in D.__mro__])
OutputD.__init__ A.__init__ B.__init__ Base.__init__ ['D', 'A', 'B', 'Base', 'object']

Base ran once, not twice. Follow the MRO D → A → B → Base → object: inside A, super() is not Base — it's B, the next link in that flat list. Each class is visited exactly once, in order. That's the diamond problem, solved.

Don't hardcode the parent

If A.__init__ had called Base.__init__(self) directly instead of super().__init__(), it would jump straight to Base and skip B entirely. In any multiple-inheritance tree, always use super() so the MRO stays intact.

Cooperative super(): passing arguments along the MRO go deeper

When several classes in the chain need constructor arguments, each takes what it needs and forwards the rest with **kwargs. The base "swallows" the leftovers. This is cooperative multiple inheritance:

cooperative.py
class Base:
    def __init__(self, **kw):
        pass                        # end of the line — absorb the rest

class Named(Base):
    def __init__(self, name, **kw):
        self.name = name
        super().__init__(**kw)      # forward what isn't ours

class Aged(Base):
    def __init__(self, age, **kw):
        self.age = age
        super().__init__(**kw)

class Person(Named, Aged):
    pass

p = Person(name="Ada", age=36)
print(p.name, p.age)                # Ada 36
OutputAda 36

The MRO is Person → Named → Aged → Base. Each __init__ peels off its own keyword and hands the remainder onward, so every class is initialised exactly once. How Python builds that order is the C3 linearization — the gist is simply: children before parents, left-to-right, and never list a class before something that depends on it.

For class D(A, B) with A(Base) and B(Base), what is D.__mro__ (names only)?

Right: children before parents, and left parent (A) before right (B) — but Base waits until after both A and B, so it's visited just once. Every class ultimately ends at object.

04  Mixins: bolt-on capabilities

A mixin is a small class that adds one capability and isn't meant to stand on its own. You "mix it in" to unrelated classes via multiple inheritance. Convention: name it …Mixin. It's horizontal reuse — sprinkle a feature across a fleet of classes — versus the vertical reuse of a deep parent chain.

Toppings, not a new species analogy

A mixin is a topping you add to many dishes — sprinkle "can be serialised to JSON" onto a User, an Invoice, a Sensor reading. You're not saying a User is a kind of JSON-thing; you're adding a side capability. Keep each topping small and self-contained.

mixins.py
import json

class AsDictMixin:
    def as_dict(self) -> dict:
        # turn public attributes into a plain dict
        return {k: v for k, v in vars(self).items() if not k.startswith("_")}

class AsJSONMixin:
    def as_json(self) -> str:
        return json.dumps(self.as_dict())     # relies on the host's as_dict()

class User(AsDictMixin, AsJSONMixin):
    def __init__(self, name, email):
        self.name = name
        self.email = email

print(User("Ada", "ada@calc.io").as_json())
Output{"name": "Ada", "email": "ada@calc.io"}
A mixin has a contract too

AsJSONMixin assumes its host provides as_dict(). That's fine — but document it. Keep mixins tiny and few in number; a class that inherits from six mixins is usually trying to hide that it does too much.

You need a .to_csv() method on three unrelated classes — User, Invoice, and Sensor. Best tool?

Right: the three classes aren't a family — forcing a common base just to share one method is a fake is-a. A mixin adds the capability horizontally without claiming they're related.

05  When inheritance bites: the fragile base class

Here's inheritance's dark side. A subclass doesn't just use the parent's public API — it can depend on the parent's internal wiring. So a harmless-looking change inside the base can silently break children. This is the fragile base class problem.

class Greeter:
    def greet(self, name):
        return "Hello, " + self._format(name)   # greet() leans on _format()
    def _format(self, name):
        return name.title()

class LoudGreeter(Greeter):
    def _format(self, name):                     # override the internal hook
        return super()._format(name).upper()

print(LoudGreeter().greet("ada"))                # Hello, ADA
class Greeter:                                   # v2: same public greet()...
    def greet(self, name):
        return "Hello, " + name.title()          # ...but _format() is gone

class LoudGreeter(Greeter):
    def _format(self, name):                     # now dead code — never called
        return super()._format(name).upper()

print(LoudGreeter().greet("ada"))                # Hello, Ada  — silently not loud!
Output (v2)Hello, Ada

Nothing errored. The base's public method greet() still works — but LoudGreeter had quietly hooked into the private _format(), and when the base author inlined it, the subclass stopped doing its job. No exception, just wrong behavior. The subclass was coupled to an implementation detail the base never promised to keep.

This is also a Liskov question

Inheritance only stays safe when a subclass can stand in for its parent everywhere, honoring every promise — the Liskov Substitution Principle. Override behavior, not the parent's private plumbing. We dig into LSP in the SOLID five. When the coupling feels this risky, that's your cue to compose instead.

06  Composition & delegation, in depth

Composition is "has-a": store the other object as an attribute and delegate — forward calls to it. The power move is that you choose exactly which parts of the inner object to expose. Two ways to wire it:

class Engine:
    def start(self): return "vroom"
    def stop(self):  return "silence"
    def serial_no(self): return "X-900"

class Car:
    def __init__(self):
        self._engine = Engine()
    def start(self):                     # you pick what leaks out
        return self._engine.start()
    def stop(self):
        return self._engine.stop()

print(Car().start())                     # vroom  (serial_no stays hidden)
class Car:
    def __init__(self):
        self._engine = Engine()
    def __getattr__(self, name):
        # called ONLY when normal lookup on Car fails
        return getattr(self._engine, name)   # forward everything else

c = Car()
print(c.start(), c.stop(), c.serial_no())    # vroom silence X-900
Output (explicit version)vroom
__getattr__ forwards everything

The auto-forward version re-exposes the engine's whole surface — including serial_no() and any future method, plus typos like c.staart sail through to the engine. That's the same leakage inheritance causes. Reach for __getattr__ only for thin proxies/wrappers; use explicit forwarding when you want a deliberate, minimal API.

07  Dependency injection: hand the parts in

Dependency injection (DI) is just composition with one rule: don't build your collaborators inside — receive them from outside (usually via __init__). It sounds fancy; it's a one-line change with a big payoff: you can swap a real dependency for a fake one, which makes the class testable and flexible.

class OrderService:
    def __init__(self):
        self._notifier = EmailNotifier()     # built inside — a test can't replace it
    def place(self, order):
        return self._notifier.send(f"Order {order} placed")

# To test this, you'd send real emails. Ugh.
class EmailNotifier:
    def send(self, msg): return "email: " + msg

class FakeNotifier:                          # a test double: records, doesn't send
    def __init__(self): self.sent = []
    def send(self, msg):
        self.sent.append(msg)
        return msg

class OrderService:
    def __init__(self, notifier):            # collaborator handed in from outside
        self._notifier = notifier
    def place(self, order):
        return self._notifier.send(f"Order {order} placed")

print(OrderService(EmailNotifier()).place("#42"))   # real path

spy = FakeNotifier()                         # in a test, inject the fake
OrderService(spy).place("#7")
print(spy.sent)                              # ['Order #7 placed']
Output (injected version)email: Order #42 placed ['Order #7 placed']
DI is the engine behind testable design

The same trick frees you to inject a frozen Clock, an in-memory database, or a different payment gateway. It's the practical face of the Dependency Inversion Principle — depend on what a thing does (an interface), not on a specific concrete class.

08  Choosing: a framework you can say out loud

Default to composition. Reach for inheritance only when the relationship passes both of these gates:

The choosing rule of thumb
gate 1
Truly "is-a"?
a real kind-of, not just "shares some code"
gate 2
Substitutable? (LSP)
child works anywhere the parent does
both yes
Inherit
any "no" → compose
Two yeses → inheritance is safe. A single "no" anywhere → reach for composition (has-a / uses-a).
Inheritance (is-a)Composition (has-a)
CouplingTight — child sees the parent's internalsLoose — only the part's public API
Reuse styleVertical — inherit a whole family of behaviorHorizontal — assemble from chosen parts
FlexibilityFixed at class-definition timeSwap parts at runtime (inject them)
Exposed surfaceEverything the parent hasExactly what you choose to forward
Reach for it whenA true, stable is-a that passes LSPAlmost everything else

And the move that ends most "which one?" debates — use both: inherit a tiny interface (an ABC or Protocol) to declare a contract, then compose the concrete behavior in so you can swap it. That's the Strategy pattern:

strategy.py
from typing import Protocol

class Discount(Protocol):                 # the contract (an interface to honor)
    def apply(self, total: float) -> float: ...

class NoDiscount:
    def apply(self, total): return total
class TenPercent:
    def apply(self, total): return round(total * 0.9, 2)

class Cart:
    def __init__(self, discount: Discount):   # COMPOSE the behavior in...
        self._discount = discount
    def total(self, subtotal):
        return self._discount.apply(subtotal)

print(Cart(TenPercent()).total(100))      # 90.0  — swap the part, change the policy
print(Cart(NoDiscount()).total(100))      # 100
Output90.0 100

The interface is inherited (a stable contract); the behavior is composed (swappable at runtime). Inheritance and composition aren't rivals here — they're a team.

09  Practice & interview check

A PremiumUser needs everything a User has, plus perks, and must work anywhere a User is accepted. Inheritance or composition?

Right: a PremiumUser genuinely is a User and can stand in for one everywhere (LSP holds), so inheritance fits. Both gates pass.

A Report needs the current time, and your tests must freeze it. How should Report get the clock?

Right: inject it. Then production passes a real clock and tests pass a frozen one — no global state, no patching. Calling datetime.now() inside welds time in; subclassing datetime is a fake is-a.

class WeatherWidget:
    def __init__(self, city, client):   # inject the collaborator
        self.city = city
        self._client = client
    def temperature(self):
        return self._client.get(f"/weather/{self.city}")

Exercise 2 · is-a vs has-a

Model a GUI Window that contains a TitleBar and a CloseButton, and a DialogWindow that is a specialized window with a message. Which relationship is which?

Show a solution solution

A window has a title bar and a close button (composition); a dialog is a kind of window (inheritance).

windows.py
class TitleBar: ...
class CloseButton: ...

class Window:                       # HAS-A parts -> composition
    def __init__(self, title):
        self.title = title
        self.title_bar = TitleBar()
        self.close_btn = CloseButton()

class DialogWindow(Window):         # IS-A Window -> inheritance
    def __init__(self, title, message):
        super().__init__(title)     # reuse the window setup
        self.message = message

DialogWindow can be used anywhere a Window is expected (LSP holds), so inheritance is safe; the parts are owned, so they're composed.
