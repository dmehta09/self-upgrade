Design patterns · creational

Creational patterns.

Creational patterns are about flexible, decoupled object creation — separating what to make from how and when it's made. The payoff: your code can ask for an object without hard-wiring a specific class, so new kinds slot in without edits.

01  Factory Method

Intent: defer the decision of which class to instantiate to a dedicated method, so callers ask for an object by intent — not by constructor.

A restaurant kitchen analogy

You order "a dessert" from the waiter. You don't tell the kitchen to new TiramisuFromFridge3() — you state intent, and the kitchen decides which dish, made how. Add a new dessert to the menu and you, the customer, change nothing.

The problem: when calling code uses EmailNotifier() directly, it's welded to that concrete class. Want SMS too? Now there are if-checks scattered everywhere a notifier is built. The Factory Method centralises the choice in one place behind a common interface.

notifiers.py
from typing import Protocol

class Notifier(Protocol):
    def send(self, msg: str) -> str: ...

class EmailNotifier:
    def send(self, msg: str) -> str:
        return f"Email: {msg}"

class SMSNotifier:
    def send(self, msg: str) -> str:
        return f"SMS: {msg}"

def notifier_factory(kind: str) -> Notifier:
    if kind == "email":
        return EmailNotifier()
    if kind == "sms":
        return SMSNotifier()
    raise ValueError(f"unknown notifier: {kind}")

# Callers state intent; they never name a concrete class:
n = notifier_factory("sms")
print(n.send("Build passed"))
OutputSMS: Build passed
Use it when… / skip it when…

Use when the concrete type depends on a runtime value (config, user input) and you want one place to change it. Skip when there's only one type, or when callers genuinely need the specific class — a factory then just hides what's going on.

The Pythonic way

You rarely need a subclass hierarchy of factories. A plain function is a factory. Even better, replace the if-ladder with a dict dispatch mapping keys to classes — then registering a new type is one line:

dispatch.py
_NOTIFIERS = {"email": EmailNotifier, "sms": SMSNotifier}

def notifier_factory(kind: str) -> Notifier:
    try:
        return _NOTIFIERS[kind]()       # look up the class, then call it
    except KeyError:
        raise ValueError(f"unknown notifier: {kind}") from None

print(notifier_factory("email").send("Hi"))
OutputEmail: Hi

02  Abstract Factory

Intent: create whole families of related objects through one interface, without naming their concrete classes — and guarantee the family members match.

A furniture set analogy

You pick a style — "Modern" or "Victorian" — and the showroom hands you a chair, a sofa, and a table that all match that style. You never mix a Victorian chair with a Modern sofa. The factory guarantees the whole set is consistent.

The problem: a Factory Method makes one product. But sometimes products come in coordinated families — a GUI toolkit needs a button and a checkbox that share a look. Abstract Factory bundles those creators so you switch the whole family at once (Windows ↔ Mac) and can never accidentally mix them.

gui_factory.py
from abc import ABC, abstractmethod

class Button(ABC):
    @abstractmethod
    def render(self) -> str: ...

class Checkbox(ABC):
    @abstractmethod
    def render(self) -> str: ...

class WinButton(Button):
    def render(self) -> str: return "[ Win button ]"
class WinCheckbox(Checkbox):
    def render(self) -> str: return "[x] Win checkbox"
class MacButton(Button):
    def render(self) -> str: return "( Mac button )"
class MacCheckbox(Checkbox):
    def render(self) -> str: return "(/) Mac checkbox"

class GUIFactory(ABC):
    @abstractmethod
    def button(self) -> Button: ...
    @abstractmethod
    def checkbox(self) -> Checkbox: ...

class WinFactory(GUIFactory):
    def button(self) -> Button: return WinButton()
    def checkbox(self) -> Checkbox: return WinCheckbox()

class MacFactory(GUIFactory):
    def button(self) -> Button: return MacButton()
    def checkbox(self) -> Checkbox: return MacCheckbox()

def build_form(factory: GUIFactory) -> None:
    print(factory.button().render())
    print(factory.checkbox().render())

build_form(MacFactory())
Output( Mac button ) (/) Mac checkbox
Use it when… / skip it when…

Use when you have several products that must vary together as a set, and the set is chosen at runtime. Skip when there's only one product type (a plain Factory Method is enough) — Abstract Factory adds a lot of classes and is the family most prone to over-engineering.

The Pythonic way

A "factory object with several creator methods" is often just a module with several functions, or a NamedTuple of callables. Pick the module (import win_widgets as ui) and you've selected the whole family — ui.button(), ui.checkbox() — with no class hierarchy at all.

03  Builder

Intent: construct a complex object step by step, so the same construction process can produce different representations — and you avoid a constructor with a dozen parameters.

Build-your-own burger analogy

At the counter you add a patty, then cheese, then skip the pickles, then say "done." You assemble the burger one choice at a time instead of memorising one giant order like Burger(True, False, 2, True, None, ...). The order isn't built until you say "done."

The problem: a constructor with many optional parameters becomes unreadable — Burger(True, False, 2, None, True) — and you can't tell which boolean is which. A Builder gives each step a name, chains them fluently, and only produces the object on build().

Director-free fluent builder

Each step returns self, so calls chain; build() hands back the finished product.
burger_builder.py
from dataclasses import dataclass, field

@dataclass
class Burger:
    patty: str = "beef"
    cheese: bool = False
    toppings: list[str] = field(default_factory=list)

class BurgerBuilder:
    def __init__(self) -> None:
        self._burger = Burger()
    def patty(self, kind: str) -> "BurgerBuilder":
        self._burger.patty = kind
        return self                       # return self → chainable
    def cheese(self) -> "BurgerBuilder":
        self._burger.cheese = True
        return self
    def add(self, topping: str) -> "BurgerBuilder":
        self._burger.toppings.append(topping)
        return self
    def build(self) -> Burger:
        return self._burger

order = (BurgerBuilder()
         .patty("chicken")
         .cheese()
         .add("lettuce")
         .add("tomato")
         .build())
print(order)
OutputBurger(patty='chicken', cheese=True, toppings=['lettuce', 'tomato'])
Use it when… / skip it when…

Use when an object has many optional parts, needs step-by-step assembly, or you want a fluent API (think a QueryBuilder: .select(...).where(...).order_by(...)). Skip when the object has a handful of fields — keyword arguments do the job with far less code.

The Pythonic way

Python has keyword arguments with defaults, so the classic Builder is usually unnecessary. A @dataclass gives you named, optional, self-documenting construction for free — Burger(patty="chicken", cheese=True, toppings=["lettuce"]). Reach for a real Builder only when assembly is genuinely staged or you want a fluent chain for ergonomics.

04  Prototype

Intent: create new objects by cloning an existing, already-configured one — instead of building each from scratch.

A document "template" analogy

You don't reformat your invoice every month. You open last month's, Save As, and tweak the numbers. The template is a configured prototype; "Save As" is the clone. Far less work than starting from a blank page.

The problem: some objects are expensive or fiddly to set up — a game enemy with dozens of tuned stats, a config object with many defaults. If you already have one configured exactly right, cloning it and adjusting a field beats re-running all the setup.

The clone gets its own independent loot list — a deep copy, not a shared reference.
prototype.py
import copy
from dataclasses import dataclass, field

@dataclass
class Enemy:
    name: str
    hp: int
    loot: list[str] = field(default_factory=list)

    def clone(self) -> "Enemy":
        return copy.deepcopy(self)        # independent copy, nested list included

# Configure one "template" once...
goblin = Enemy("Goblin", hp=30, loot=["coin"])

# ...then stamp out variants by cloning + tweaking:
elite = goblin.clone()
elite.name = "Goblin Chief"
elite.hp = 80
elite.loot.append("crown")

print(goblin)
print(elite)
print(goblin.loot is elite.loot)          # False — deep copy gave separate lists
OutputEnemy(name='Goblin', hp=30, loot=['coin']) Enemy(name='Goblin Chief', hp=80, loot=['coin', 'crown']) False
Use it when… / skip it when…

Use when constructing from scratch is costly or you want copies of a tuned instance (templates, presets, game entities). Skip — and mind the shallow-vs-deep trap: copy.copy shares nested mutable objects, so two "clones" can stomp on each other's lists. Use copy.deepcopy when parts are mutable.

The Pythonic way

Python ships Prototype in the standard library: copy.copy(obj) for a shallow clone and copy.deepcopy(obj) for a fully independent one. You rarely write a clone() method — just call copy. (For dataclasses, dataclasses.replace(obj, hp=80) clones and overrides fields in one step.)

05  Singleton (handle with care)

Intent: guarantee a class has exactly one instance and provide a single global point of access to it.

A country's president analogy

There's exactly one sitting president at a time, and "the President" refers to that single office no matter who asks. You don't accidentally end up with two. That single, shared point of reference is the Singleton idea.

The problem it claims to solve: things you want exactly one of — a config registry, a connection pool, a logger. Below are two textbook ways to enforce one instance: overriding __new__, or a metaclass.

class Config:
    _instance = None

    def __new__(cls) -> "Config":
        if cls._instance is None:
            cls._instance = super().__new__(cls)   # build only the first time
            cls._instance.settings = {}
        return cls._instance

a = Config()
b = Config()
a.settings["theme"] = "dark"
print(a is b)              # True — same object
print(b.settings)         # {'theme': 'dark'} — b sees a's change
class Singleton(type):
    _instances: dict = {}
    def __call__(cls, *args, **kwargs):
        if cls not in cls._instances:
            cls._instances[cls] = super().__call__(*args, **kwargs)
        return cls._instances[cls]

class Config(metaclass=Singleton):
    def __init__(self) -> None:
        self.settings: dict = {}

a = Config()
b = Config()
print(a is b)             # True — the metaclass intercepts construction
Output (__new__ version)True {'theme': 'dark'}
Singleton is often an anti-pattern

A Singleton is hidden global state wearing a class costume. It makes code hard to test (tests share one mutable instance and leak state into each other), hard to reason about (any code anywhere can mutate it), and hard to parallelise. Most "I need a Singleton" cases are better solved by creating one instance and passing it in (dependency injection). Reach for it rarely, and only for truly process-wide, read-mostly resources.

The Pythonic way

Python modules are already singletons — imported once and cached. So the idiomatic "one instance" is simply a module-level object: define config = Config() in a module and import it. For a lazily-built, cached singleton, decorate a factory with @functools.cache (or @lru_cache):

pythonic_singleton.py
import functools

class Config:
    def __init__(self) -> None:
        self.settings: dict = {}

@functools.cache                  # builds once, returns the same object after
def get_config() -> Config:
    return Config()

print(get_config() is get_config())   # True
OutputTrue

You need to build an object that has many optional parameters and reads best assembled step by step. Which pattern fits?

Right: Builder assembles a complex object step by step and avoids a giant constructor. (In Python, keyword arguments on a dataclass often replace it for the simple cases.)

What's the strongest reason Singleton is often called an anti-pattern?

Right: a Singleton is global mutable state in disguise. Tests share and leak it, and any code can mutate it. Prefer creating one instance and passing it in (dependency injection).

You want a new object identical to one you've already tuned, with its own independent nested list. The Pythonic move?

Right: copy.deepcopy clones the object and its nested mutables, so the copies don't share lists. copy.copy would leave the nested list shared.
