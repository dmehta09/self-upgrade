Design patterns · overview

Patterns: the field's shared vocabulary.

A design pattern is a named, reusable shape for solving a problem that keeps coming back. Learn the names and you can describe a whole chunk of design in two words — "use a Strategy here" — and everyone nods.

01  What is a design pattern?

A design pattern is a named, reusable solution to a recurring design problem. It isn't a library you import or code you copy-paste — it's a shape, an approach you adapt to your own classes. Patterns were popularised by the 1994 book Design Patterns by the "Gang of Four" (Gamma, Helm, Johnson, Vlissides), which catalogued 23 of them.

Recipes and architectural blueprints analogy

A recipe for risotto tells you the technique — toast the rice, add stock slowly, stir — not the exact grams in your kitchen. You adapt it to what you have. Patterns are the same: an architect knows an arch spans a gap and a buttress holds a wall against outward thrust. They don't reinvent those each time — they reach for the named solution and size it to the building.

The biggest payoff isn't even the code — it's the shared vocabulary. Saying "this is an Observer" instantly conveys intent, structure, and trade-offs to anyone who knows the catalog. Patterns turn a paragraph of explanation into a single word.

A pattern is an approach, not a snippet

There's no canonical "Strategy.py" to download. The pattern lives in how your classes are arranged and how they collaborate. Two correct implementations can look quite different — and in Python, the idiomatic version is often shorter than the textbook one.

02  The three families

The Gang of Four sorted patterns into three families by the kind of problem they tackle. Almost every pattern you'll meet lives in one of these buckets:

What each family is about
creational
Make
how objects are made
structural
Compose
how objects fit together
behavioral
Collaborate
how objects talk & share work
Creational = construction, Structural = arrangement, Behavioral = communication.
🏗️

Creational

How objects are made. Decouple "what to build" from "how and when it's built": Factory Method, Abstract Factory, Builder, Prototype, Singleton.

 🧩

Structural

How objects are composed into larger structures while keeping them flexible: Adapter, Decorator, Facade, Proxy, Composite, Bridge, Flyweight.

 💬

Behavioral

How objects collaborate & communicate and divide responsibility: Strategy, Observer, Command, State, Template Method, Iterator, Chain of Responsibility.

03  How to choose — and not over-engineer

Patterns are answers to real pressures, not decorations. The two pressures that justify almost every pattern are: something that varies (different payment methods, different export formats) and something that changes (requirements you expect to shift). When you feel that pressure, reach for the pattern that isolates it. When you don't, write the plain code.

Something varies?
Encapsulate the varying part behind an interface (Strategy, Factory, Adapter…).
Something changes often?
Put a seam there so change is local, not scattered (Observer, Command…).
Neither?
Don't add the pattern. A function or a plain class is the right answer.
Beware "pattern-itis"

The most common beginner mistake after learning patterns is using all of them. A three-line script does not need an Abstract Factory and a Singleton registry. That's over-abstraction — layers of indirection that hide what the code actually does. Follow YAGNI ("You Aren't Gonna Need It"): add the flexibility when the second case actually arrives, not in anticipation. A pattern you don't need is just complexity you do.

04  Pattern vs anti-pattern

If a pattern is a named good solution, an anti-pattern is a named bad one — a tempting shape that looks like it solves the problem but quietly makes things worse. Knowing their names helps you call them out in review.

👑

God Object

One class that knows and does everything. Impossible to test or change; violates Single Responsibility. Split it.

🍝

Spaghetti Code

No clear structure — control flow tangled across modules. Every change risks breaking something far away.

🔨

Golden Hammer

"When all you have is a hammer, everything looks like a nail." Forcing one favourite pattern onto every problem.

Patterns and anti-patterns are two sides of one coin

Overusing a real pattern creates an anti-pattern: a Singleton everywhere is hidden global state; a Factory for a class you'll only ever make one way is just ceremony. The skill is matching force to pressure.

06  Check yourself

Which best describes what a design pattern is?

Right: a pattern is an adaptable approach plus a shared name — not a package and not copy-paste code. You shape it to your own classes.

A pattern that handles how objects are created, decoupling "what to build" from "how it's built," belongs to which family?

Right: creational patterns are all about construction. Structural is about composing objects; behavioral is about how they collaborate.

You add a Singleton, an Abstract Factory, and a Command queue to a 30-line script "to be safe." What's the name for that mistake?

Right: patterns answer real pressures. With no varying or changing part to isolate, the layers are pure overhead. YAGNI: add it when you actually need it.
