Design patterns · structural

Structural patterns: composing the pieces.

Structural patterns are about composing objects into bigger structures while keeping every piece flexible. They answer "how do I wire these classes together so the whole stays simple and the parts stay swappable?" Seven classics, each analogy-first.

01  Adapter: make an incompatible interface fit

Intent: wrap an object with the wrong interface so it satisfies the one your code expects — without touching either side.

A travel power-plug adapter analogy

Your laptop charger has a two-pin plug; the wall socket abroad takes three. You don't rewire the laptop or the wall — you slot in a little adapter that exposes the shape the wall wants and forwards the power. The adapter translates one interface into another.

The problem: a third-party LegacyLogger exposes write_log(), but all your code calls .log() against a Logger Protocol. You can't edit the library. So you wrap it.

adapter.py
from typing import Protocol

class Logger(Protocol):                  # what our app expects
    def log(self, message: str) -> None: ...

class LegacyLogger:                      # 3rd-party, can't change it
    def write_log(self, text: str) -> None:
        print(f"[LEGACY] {text}")

class LoggerAdapter:                     # speaks Logger, delegates to legacy
    def __init__(self, legacy: LegacyLogger):
        self._legacy = legacy
    def log(self, message: str) -> None:
        self._legacy.write_log(message)  # translate the call

def run(logger: Logger) -> None:
    logger.log("user signed in")

run(LoggerAdapter(LegacyLogger()))       # [LEGACY] user signed in
Output[LEGACY] user signed in
Use when
you must integrate code you can't modify (a library, an old API) behind a clean interface.
Avoid when
you control both sides — just change the interface directly instead of adding a layer.
The Pythonic way

Thanks to duck typing you rarely need a formal Adapter class. A thin wrapper class — or even a one-line function log = legacy.write_log — is often enough. The Protocol gives type-checkers the contract; no inheritance required.

02  Decorator: add behavior by wrapping

Intent: attach new responsibilities to an object by wrapping it in another object of the same interface — stacking behaviors without subclassing.

Coffee add-ons (or gift-wrapping) analogy

Start with a plain coffee. Add milk — still coffee, costs a bit more. Add caramel — still coffee, costs more again. Each add-on wraps the drink, keeps the same "is a drink" surface, and tweaks the result. You can stack them in any order.

The problem: a DataSource can read() bytes. You want optional compression and encryption — in any combination — without a class explosion (CompressedEncryptedFileSource…). So each feature is a wrapper that shares the interface.

data_source.py
from abc import ABC, abstractmethod

class DataSource(ABC):
    @abstractmethod
    def read(self) -> str: ...

class FileSource(DataSource):
    def read(self) -> str:
        return "payload"

class SourceDecorator(DataSource):       # wraps another DataSource
    def __init__(self, wrapped: DataSource):
        self._wrapped = wrapped

class Compressed(SourceDecorator):
    def read(self) -> str:
        return f"zip({self._wrapped.read()})"

class Encrypted(SourceDecorator):
    def read(self) -> str:
        return f"enc({self._wrapped.read()})"

src = Encrypted(Compressed(FileSource()))   # stack in any order
print(src.read())                           # enc(zip(payload))
Outputenc(zip(payload))
Use when
you need to mix-and-match optional behaviors at runtime, or avoid a subclass for every combination.
Avoid when
there's only ever one fixed extra behavior — just put it in the class.
The Pythonic way: function decorators

For wrapping functions (not objects), Python bakes the pattern into the language with @ syntax. Use functools.wraps so the wrapper keeps the original's name and docstring:

timed.py
import functools, time

def timed(fn):
    @functools.wraps(fn)                 # keep fn's __name__/__doc__
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = fn(*args, **kwargs)
        elapsed = time.perf_counter() - start
        print(f"{fn.__name__} took {elapsed:.4f}s")
        return result
    return wrapper

@timed
def work(n: int) -> int:
    return sum(range(n))

print(work(1_000_000))
print(work.__name__)                     # still "work", thanks to wraps
Outputwork took 0.0123s 499999500000 work

03  Facade: one simple front over a complex subsystem

Intent: provide a single, friendly entry point that hides a tangle of subsystems behind one method.

A restaurant waiter analogy

You don't walk into the kitchen and coordinate the grill, the fryer, and the dishwasher. You tell the waiter "the steak, please." The waiter is the facade: one simple request, a whole choreography hidden behind it.

The problem: watching a movie at home means turning on the amp, lowering the projector, dimming the lights and starting the player — in the right order. A HomeTheaterFacade.watch_movie() bundles that into one call.

home_theater.py
class Amplifier:
    def on(self) -> str: return "amp on"

class Projector:
    def lower(self) -> str: return "projector down"

class Lights:
    def dim(self) -> str: return "lights dimmed"

class HomeTheaterFacade:
    def __init__(self):
        self._amp = Amplifier()
        self._projector = Projector()
        self._lights = Lights()
    def watch_movie(self) -> None:        # the one simple front door
        for step in (self._lights.dim(),
                     self._projector.lower(),
                     self._amp.on()):
            print(step)
        print("Enjoy the movie!")

HomeTheaterFacade().watch_movie()
Outputlights dimmed projector down amp on Enjoy the movie!
Use when
callers shouldn't need to know the subsystem's wiring or call order.
Avoid when
the subsystem is already simple, or callers genuinely need fine-grained control.
The Pythonic way

A facade doesn't have to be a class. A module with a single convenience function (think requests.get() hiding sessions, adapters and pools) is the most Pythonic facade there is.

04  Proxy: a stand-in that controls access

Intent: put a placeholder in front of a real object to control access to it — for lazy loading, caching, or permission checks — while keeping the same interface.

A debit card analogy

A debit card stands in for the cash in your account. It looks like a way to pay, but really it controls access — checking your balance, applying limits — before the real money moves. You hold the proxy, not the vault.

The problem: a high-resolution image is expensive to load. A LazyImage proxy holds only the filename and loads the real bytes on the first display() — never if you never show it.

lazy_image.py
class RealImage:
    def __init__(self, filename: str):
        self._filename = filename
        print(f"loading {filename} from disk")   # the expensive bit
    def display(self) -> None:
        print(f"showing {self._filename}")

class LazyImage:                          # same display() interface
    def __init__(self, filename: str):
        self._filename = filename
        self._real: RealImage | None = None
    def display(self) -> None:
        if self._real is None:            # load only on first use
            self._real = RealImage(self._filename)
        self._real.display()

img = LazyImage("cat.png")                # nothing loaded yet
print("created, not loaded")
img.display()                             # loads now
img.display()                             # cached, no reload
Outputcreated, not loaded loading cat.png from disk showing cat.png showing cat.png
Use when
you need lazy init, caching, logging, or access control around an existing object.
Avoid when
the indirection buys nothing — don't proxy something that's already cheap and open.
The Pythonic way

For a transparent proxy, implement __getattr__ to forward any unknown attribute to the wrapped object — so you don't hand-write every method. For pure lazy loading, a @property (or functools.cached_property) often does the job with far less code.

05  Composite: treat parts and wholes alike

Intent: arrange objects into a tree and let client code treat a single object and a whole group through the same interface.

Folders inside folders analogy

"How big is this?" works the same whether you ask a single file or a folder full of folders. A folder just adds up its children — which might themselves be folders. One question, any depth.

The problem: a filesystem has Files and Folders. Both should answer .size(); a folder sums its children recursively, and a child can be either kind.

filesystem.py
from abc import ABC, abstractmethod

class Node(ABC):                          # common interface for leaf + group
    @abstractmethod
    def size(self) -> int: ...

class File(Node):                         # leaf
    def __init__(self, name: str, size: int):
        self.name, self._size = name, size
    def size(self) -> int:
        return self._size

class Folder(Node):                       # composite
    def __init__(self, name: str):
        self.name, self._children: list[Node] = name, []
    def add(self, node: Node) -> "Folder":
        self._children.append(node)
        return self
    def size(self) -> int:
        return sum(child.size() for child in self._children)  # recurse

root = Folder("root").add(File("a.txt", 100)).add(
    Folder("sub").add(File("b.txt", 200)))
print(root.size())                        # 300 — files and folders alike
Output300
Use when
your data is naturally a tree (files, UI widgets, org charts) and clients shouldn't special-case leaf vs branch.
Avoid when
the structure is flat — a plain list is simpler than a tree.
The Pythonic way

The shared interface can be a Protocol instead of an ABC — anything with a size() method drops into the tree. Recursion plus a generator expression (sum(c.size() for c in ...)) keeps the composite tiny.

06  Bridge: split abstraction from implementation

Intent: separate what a thing does (the abstraction) from how it's done (the implementation) so the two can vary independently — no combinatorial subclass blow-up.

A universal remote analogy

One remote (the abstraction) can drive a TV or a radio (the implementations). You add a new gadget without designing a new remote, and a fancier remote without rewiring every gadget. The remote and the device meet over a thin "device" contract — the bridge.

The problem: a RemoteControl needs to work with many Device types. Subclassing (BasicTVRemote, AdvancedRadioRemote…) multiplies fast. Instead the remote holds a device.

bridge.py
from typing import Protocol

class Device(Protocol):                   # the implementation side
    def enable(self) -> str: ...

class TV:
    def enable(self) -> str: return "TV on"

class Radio:
    def enable(self) -> str: return "Radio on"

class RemoteControl:                      # the abstraction side
    def __init__(self, device: Device):   # bridge: holds an implementation
        self._device = device
    def power(self) -> None:
        print(self._device.enable())

RemoteControl(TV()).power()               # TV on
RemoteControl(Radio()).power()            # Radio on
OutputTV on Radio on
Use when
two dimensions vary independently (remote × device, shape × renderer) and you'd otherwise get a class per combination.
Avoid when
there's only one implementation — the extra layer is pure ceremony.
The Pythonic way

Bridge is just composition over a Protocol: pass the implementation into the abstraction's constructor (dependency injection). No deep hierarchy, no abstract base required.

07  Flyweight: share immutable state to save memory

Intent: when you'd otherwise create millions of near-identical objects, share the common immutable part (the "intrinsic state") instead of copying it.

A rubber stamp analogy

A forest game has a million trees. You don't store a full texture per tree — you keep one "oak" stamp and reuse it everywhere, recording only each tree's position. The shared stamp is the flyweight; the position is the bit that actually differs.

The problem: rendering thousands of trees, each with a heavy TreeType (name, mesh, texture). Cache one TreeType per kind and share it across every tree at a different (x, y).

flyweight.py
import functools
from dataclasses import dataclass

@dataclass(frozen=True)                   # frozen = immutable, hashable
class TreeType:
    name: str
    texture: str

@functools.lru_cache(maxsize=None)        # cache: one object per kind
def tree_type(name: str, texture: str) -> TreeType:
    print(f"building {name} flyweight")   # only runs on a cache miss
    return TreeType(name, texture)

# 3 trees, but only 2 distinct TreeType objects are ever built:
a = tree_type("oak", "oak.png")
b = tree_type("oak", "oak.png")
c = tree_type("pine", "pine.png")
print(a is b)                             # True — shared instance
print(a is c)                             # False
Outputbuilding oak flyweight building pine flyweight True False
Use when
huge numbers of objects share a big immutable core and memory is the bottleneck.
Avoid when
the objects are few, or their state is mostly unique — sharing buys nothing and adds complexity.
The Pythonic way

functools.lru_cache on a factory is the flyweight pool — it hands back the same instance for the same arguments. Python already interns small ints and short strings for exactly this reason. Pair it with a frozen=True dataclass so the shared object can't be mutated out from under everyone.

08  The seven, side by side

PatternIntentPythonic shortcut
AdapterMake an incompatible interface fitThin wrapper class or function · duck typing
DecoratorAdd behavior by wrapping, same interface@decorator + functools.wraps
FacadeOne simple front over a subsystemA module or one convenience function
ProxyStand-in controlling access__getattr__ · cached_property
CompositeTreat parts & wholes uniformly (tree)Recursion + a shared Protocol
BridgeSplit abstraction from implementationComposition / inject a Protocol
FlyweightShare immutable state to save memorylru_cache · interning

You wrap an object in another object of the same interface, but the wrapper's goal is lazy-loading and caching — not adding visible behavior. Which pattern?

Right: both Decorator and Proxy wrap an object with the same interface — the intent separates them. Decorator adds behavior the caller wants; Proxy controls access (lazy load, cache, permissions) while staying invisible.

You need to add up the size of a directory tree where any item may be a single file or a nested folder, treated uniformly. Which pattern fits?

Right: a uniform tree of parts and wholes — leaves and groups sharing one interface — is the Composite pattern. The folder recursively sums its children.

A game spawns 50,000 bullets that all share the same sprite and damage value. To stop wasting memory you cache one shared, immutable descriptor per bullet kind. Which pattern?

Right: sharing an immutable intrinsic core across many objects to save memory is Flyweight — in Python, a frozen dataclass behind functools.lru_cache.
