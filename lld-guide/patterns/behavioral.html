Design patterns · behavioral

Behavioral patterns: who talks to whom.

Behavioral patterns are about how objects communicate and divide responsibility — which object decides, which one acts, and how a request flows between them. Eleven classics, and in Python many collapse to "just pass a function."

01  Strategy: swap an algorithm at runtime

Intent: define a family of interchangeable algorithms, encapsulate each one, and let the caller pick which to use — without the surrounding code changing.

Picking a route in a maps app analogy

"Fastest," "no tolls," "scenic" — same trip, same start and end, different algorithm to compute the route. You swap the strategy with one tap; the map doesn't care which one you chose.

The problem: a PaymentProcessor must support card, PayPal, crypto… You don't want a giant if/elif. Inject a payment strategy instead.

from typing import Protocol

class PayStrategy(Protocol):
    def pay(self, amount: float) -> str: ...

class CardStrategy:
    def pay(self, amount: float) -> str:
        return f"${amount} via card"

class PayPalStrategy:
    def pay(self, amount: float) -> str:
        return f"${amount} via PayPal"

class PaymentProcessor:
    def __init__(self, strategy: PayStrategy):
        self._strategy = strategy        # plug in any algorithm
    def checkout(self, amount: float) -> None:
        print(self._strategy.pay(amount))

PaymentProcessor(CardStrategy()).checkout(30)     # $30 via card
PaymentProcessor(PayPalStrategy()).checkout(12)   # $12 via PayPal
# In Python a "strategy" is usually just a function — first-class.
def by_card(amount: float) -> str:
    return f"${amount} via card"

def by_paypal(amount: float) -> str:
    return f"${amount} via PayPal"

def checkout(amount: float, strategy) -> None:
    print(strategy(amount))              # call the passed-in function

checkout(30, by_card)                    # $30 via card
checkout(12, by_paypal)                  # $12 via PayPal

# Same idea powers sorted(key=...): the key IS a strategy.
words = ["pear", "fig", "apple"]
print(sorted(words, key=len))            # ['fig', 'pear', 'apple']
Output (function version)$30 via card $12 via PayPal ['fig', 'pear', 'apple']

Watch the dispatch happen. The processor's checkout() never changes — only the object behind the interface does:

Use when
one step has several interchangeable implementations chosen at runtime.
Avoid when
there's only one algorithm, or the choice never changes — a plain function call is enough.
The Pythonic way

Functions are first-class objects, so a one-method strategy class is overkill — pass the plain function. You've used this forever: sorted(key=...), max(key=...), and callbacks are all Strategy in disguise.

02  Observer: tell the subscribers when something changes

Intent: let one object (the subject) keep a list of dependents and notify them automatically whenever its state changes — without knowing who they are.

A newsletter subscription analogy

You subscribe once. When a new issue ships, every subscriber gets it automatically — the publisher doesn't email you each personally, it just "notifies the list." Unsubscribe and the updates stop.

The problem: a NewsAgency publishes headlines; several displays should refresh when a story breaks. The agency shouldn't hard-code its readers.

observer.py
from typing import Protocol

class Observer(Protocol):
    def update(self, headline: str) -> None: ...

class NewsAgency:                         # the subject
    def __init__(self):
        self._subscribers: list[Observer] = []
    def subscribe(self, obs: Observer) -> None:
        self._subscribers.append(obs)
    def publish(self, headline: str) -> None:
        for obs in self._subscribers:     # notify everyone
            obs.update(headline)

class Phone:
    def update(self, headline: str) -> None:
        print(f"Phone buzzes: {headline}")

class Email:
    def update(self, headline: str) -> None:
        print(f"Email sent: {headline}")

agency = NewsAgency()
agency.subscribe(Phone())
agency.subscribe(Email())
agency.publish("Market up 2%")
OutputPhone buzzes: Market up 2% Email sent: Market up 2%

Here's that exact code running — step through and watch the fan-out happen one call at a time, with the executing line highlighted:

Use when
a change in one object must fan out to many others that can come and go.
Avoid when
there's exactly one dependent forever — just call it directly.
The Pythonic way

Observers don't need a class or an update() method — keep a list of plain callables (callbacks) and call each on change. That's exactly how event handlers and signal/slot libraries work.

03  Command: wrap a request as an object

Intent: turn a request into a standalone object holding everything needed to perform (and undo) it — so you can queue, log, or reverse actions.

A restaurant order ticket analogy

The waiter writes your order on a ticket. The ticket is a thing — it can be queued behind others, re-fired if the kitchen drops it, or voided. The request to cook lives independently of who placed it and who cooks it.

The problem: a remote should turn a Light on/off and support undo. Wrap each action as a Command with execute() / undo(); the invoker keeps a history.

command.py
from abc import ABC, abstractmethod

class Light:
    def on(self) -> None:  print("light ON")
    def off(self) -> None: print("light OFF")

class Command(ABC):
    @abstractmethod
    def execute(self) -> None: ...
    @abstractmethod
    def undo(self) -> None: ...

class OnCommand(Command):
    def __init__(self, light: Light): self._light = light
    def execute(self) -> None: self._light.on()
    def undo(self) -> None:    self._light.off()

class Invoker:
    def __init__(self): self._history: list[Command] = []
    def run(self, cmd: Command) -> None:
        cmd.execute(); self._history.append(cmd)
    def undo_last(self) -> None:
        self._history.pop().undo()        # reverse the most recent

inv = Invoker()
inv.run(OnCommand(Light()))               # light ON
inv.undo_last()                           # light OFF
Outputlight ON light OFF
Use when
you need undo/redo, action queues, macros, or to log requests for replay.
Avoid when
actions never need to be stored or reversed — call the method directly.
The Pythonic way

If you don't need undo, a command is just a callable. Bundle the target and arguments with functools.partial(light.on) and store those in your queue — no Command subclass per action.

04  State: behavior changes with internal state

Intent: let an object alter its behavior when its internal state changes — it appears to change class. Each state is its own object with its own rules.

A traffic light analogy

Green, yellow, red — same light, but "what happens next" depends entirely on the current color. Each state knows only its own transition. The light doesn't run a giant checklist; it just is green, then becomes yellow.

The problem: a Document behaves differently in Draft, Moderation, and Published. Calling publish() means different things in each. Model each state as a class and delegate.

from abc import ABC, abstractmethod

class State(ABC):
    @abstractmethod
    def publish(self, doc: "Document") -> None: ...

class Draft(State):
    def publish(self, doc):
        print("Draft -> sent to moderation")
        doc.state = Moderation()

class Moderation(State):
    def publish(self, doc):
        print("Moderation -> now published")
        doc.state = Published()

class Published(State):
    def publish(self, doc):
        print("Already published; nothing to do")

class Document:
    def __init__(self): self.state: State = Draft()
    def publish(self) -> None:
        self.state.publish(self)          # behavior depends on state

doc = Document()
doc.publish()                             # Draft -> moderation
doc.publish()                             # Moderation -> published
doc.publish()                             # already published
from enum import Enum, auto

class Stage(Enum):
    DRAFT = auto(); MODERATION = auto(); PUBLISHED = auto()

class Document:
    def __init__(self): self.stage = Stage.DRAFT
    def publish(self) -> None:
        match self.stage:                 # one place, all transitions
            case Stage.DRAFT:
                print("Draft -> sent to moderation")
                self.stage = Stage.MODERATION
            case Stage.MODERATION:
                print("Moderation -> now published")
                self.stage = Stage.PUBLISHED
            case Stage.PUBLISHED:
                print("Already published; nothing to do")

doc = Document()
doc.publish(); doc.publish(); doc.publish()
OutputDraft -> sent to moderation Moderation -> now published Already published; nothing to do

This same machine drives the vending-machine case study — Idle → HasMoney → Dispensing — where each state accepts different inputs.

Use when
an object has a handful of modes with genuinely different behavior and clear transitions.
Avoid when
there are only two trivial states — a boolean flag and an if is clearer.
The Pythonic way

For a few states, an Enum plus a match/case (Python 3.10+) keeps every transition in one readable place. Reach for full state classes only when each state carries its own data and behavior worth isolating.

05  Template Method: fix the skeleton, fill the steps

Intent: a base class defines the overall algorithm as a fixed sequence of steps, and subclasses override individual steps without changing the order.

A recipe template analogy

Every soup recipe is "prep, cook, season, serve" in that order. The steps differ per soup, but the sequence is fixed. The template owns the order; each recipe fills in the steps.

The problem: a DataMiner always does extract → parse → analyze, but CSV and PDF sources extract and parse differently. Fix the flow in the base; defer the variable steps.

data_miner.py
from abc import ABC, abstractmethod

class DataMiner(ABC):
    def mine(self) -> None:               # the template method: fixed order
        raw = self.extract()
        data = self.parse(raw)
        print(f"analyzed: {data}")
    @abstractmethod
    def extract(self) -> str: ...         # subclasses fill these in
    @abstractmethod
    def parse(self, raw: str) -> str: ...

class CSVMiner(DataMiner):
    def extract(self) -> str:    return "a,b,c"
    def parse(self, raw: str) -> str: return raw.replace(",", " | ")

class PDFMiner(DataMiner):
    def extract(self) -> str:    return "PDF bytes"
    def parse(self, raw: str) -> str: return raw.upper()

CSVMiner().mine()                         # analyzed: a | b | c
PDFMiner().mine()                         # analyzed: PDF BYTES
Outputanalyzed: a | b | c analyzed: PDF BYTES
Use when
several variants share one fixed workflow but differ in a few steps.
Avoid when
the steps vary independently of any flow — prefer Strategy (compose) over inheritance.
The Pythonic way

This is the one classic that does lean on inheritance: an ABC with abstract hook methods. Keep the public mine() concrete and the hooks @abstractmethod so a subclass can't forget a step.

06  Iterator: walk a collection without exposing its guts

Intent: provide a way to access elements of a collection one at a time, in order, without revealing how the collection is stored.

A TV remote's channel button analogy

Press "next" and you get the next channel — you never need to know whether channels live in an array, a linked list, or a database. The remote gives you "next" and "are we done?", nothing more.

The problem: you want for x in countdown to work on your own type. Python's iterator protocol is __iter__ (give me an iterator) + __next__ (give me the next item, or raise StopIteration).

class Countdown:
    def __init__(self, start: int):
        self._start = start
    def __iter__(self):
        self._n = self._start            # reset, return the iterator
        return self
    def __next__(self) -> int:
        if self._n <= 0:
            raise StopIteration          # signals "done"
        self._n -= 1
        return self._n + 1

print(list(Countdown(3)))                # [3, 2, 1]
for n in Countdown(2):
    print(n)                             # 2 then 1
# A generator builds the iterator for you — no __next__ boilerplate.
def countdown(start: int):
    n = start
    while n > 0:
        yield n                          # pause here, resume on next()
        n -= 1

print(list(countdown(3)))                # [3, 2, 1]
for n in countdown(2):
    print(n)                             # 2 then 1
Output (generator version)[3, 2, 1] 2 1
Use when
you want your object to work in for loops, comprehensions, and list() uniformly.
Avoid when
you can just expose a built-in list — don't hand-roll iteration you don't need.
The Pythonic way: generators

A function with yield is an iterator — Python writes __iter__, __next__, and StopIteration for you. Generators are lazy (one item at a time) so they work on infinite or huge sequences without blowing memory.

07  Chain of Responsibility: pass it down the line

Intent: give several handlers a chance to process a request by linking them in a chain — each either handles it or passes it to the next.

Tiered customer support analogy

Your ticket starts with the front-line agent. Can't fix it? Escalate to a specialist. Still stuck? Up to engineering. Each tier handles what it can and forwards the rest. You don't address one person — you address the chain.

The problem: a support ticket has a severity. Low severity goes to the bot, medium to a human, high to a manager. Each handler decides "mine?" or "pass on."

chain.py
from abc import ABC, abstractmethod

class Handler(ABC):
    def __init__(self):
        self._next: "Handler | None" = None
    def set_next(self, nxt: "Handler") -> "Handler":
        self._next = nxt
        return nxt                        # return next to allow chaining
    @abstractmethod
    def handle(self, level: int) -> None: ...
    def pass_on(self, level: int) -> None:
        if self._next:
            self._next.handle(level)
        else:
            print(f"level {level}: unhandled")

class Bot(Handler):
    def handle(self, level: int) -> None:
        print("Bot handled it") if level <= 1 else self.pass_on(level)

class Human(Handler):
    def handle(self, level: int) -> None:
        print("Human handled it") if level <= 2 else self.pass_on(level)

bot = Bot()
bot.set_next(Human())                     # bot -> human
bot.handle(1)                             # Bot handled it
bot.handle(2)                             # Human handled it
bot.handle(9)                             # level 9: unhandled
OutputBot handled it Human handled it level 9: unhandled

Step through two tickets walking the chain — one that a handler claims, one that falls off the end:

Use when
more than one object might handle a request and the handler isn't known in advance (logging levels, event pipelines, middleware).
Avoid when
exactly one object always handles it — the chain is needless indirection.
The Pythonic way

Skip the linked-list plumbing: keep a plain list of handler callables and loop until one returns a result. This is how WSGI/ASGI middleware and logging handlers are wired.

08  Mediator: talk through a hub, not each other

Intent: define an object that encapsulates how a set of objects interact — colleagues never call each other directly; they go through the mediator.

An air-traffic controller analogy

Planes don't negotiate landing slots with each other over the radio. They talk to the tower; the tower sequences everyone. Swap the tower's rules and every plane follows — without rewriting the fleet.

The problem: a chat room's users must broadcast messages. Wiring every User to every other user is an N² mess. Put a ChatRoom in the middle.

mediator.py
from typing import Protocol

class Mediator(Protocol):
    def broadcast(self, sender: "User", text: str) -> None: ...

class ChatRoom:                              # the mediator
    def __init__(self):
        self._users: list[User] = []
    def join(self, user: "User") -> None:
        self._users.append(user)
        user.room = self
    def broadcast(self, sender: "User", text: str) -> None:
        for u in self._users:
            if u is not sender:
                u.receive(sender.name, text)

class User:                                  # a colleague — knows only the room
    def __init__(self, name: str):
        self.name = name
        self.room: ChatRoom | None = None
    def send(self, text: str) -> None:
        self.room.broadcast(self, text)
    def receive(self, who: str, text: str) -> None:
        print(f"{self.name} heard {who}: {text}")

room = ChatRoom()
alice, bob = User("Alice"), User("Bob")
room.join(alice); room.join(bob)
alice.send("hi")                             # Bob heard Alice: hi
OutputBob heard Alice: hi
Use when
many objects need coordinated interaction and direct links would explode into a spaghetti graph (UI widgets, chat, game pieces).
Avoid when
two objects have a simple one-way relationship — a direct call is clearer than a hub.
Don't build a god object

A mediator that knows every detail of every colleague becomes the new coupling bottleneck. Keep it thin: route events, don't own all business logic. If it grows forever, split domains or prefer Observer for one-to-many fire-and-forget.

09  Memento: snapshot state for later undo

Intent: capture an object's internal state so you can restore it later — without exposing that state to the rest of the world.

A save-game slot analogy

You don't hand the console your brain dumps mid-level. You hit Save; the cartridge stores an opaque blob. Load restores you — the UI never peeks inside the blob, and the game's private fields stay private.

The problem: a text editor needs undo. Exposing _text to the history stack breaks encapsulation. Hand the caretaker an opaque memento instead.

memento.py
from dataclasses import dataclass

@dataclass(frozen=True)
class Memento:                               # opaque snapshot
    text: str

class Editor:                                # originator
    def __init__(self): self._text = ""
    def type(self, chunk: str) -> None:
        self._text += chunk
    def save(self) -> Memento:
        return Memento(self._text)
    def restore(self, m: Memento) -> None:
        self._text = m.text
    def show(self) -> str: return self._text

class History:                               # caretaker — never opens the memento
    def __init__(self): self._stack: list[Memento] = []
    def push(self, m: Memento) -> None: self._stack.append(m)
    def pop(self) -> Memento: return self._stack.pop()

ed, hist = Editor(), History()
ed.type("Hello"); hist.push(ed.save())
ed.type(" world")
print(ed.show())                             # Hello world
ed.restore(hist.pop())
print(ed.show())                             # Hello
OutputHello world Hello
Use when
you need undo/rollback and the originator alone should know how to read its own snapshot (editors, transactions, games).
Avoid when
a Command already carries enough info to reverse itself — Command undo is often simpler than full snapshots.
Snapshots cost memory

Every save clones state. For large documents, prefer incremental Command history or store diffs. Also: if the caretaker peeks inside the memento, you've broken the pattern — keep fields private or frozen and only the originator restores.

10  Visitor: add an operation without changing the classes

Intent: represent an operation to be performed on elements of an object structure — new operations land in new visitor classes, not by editing every element type.

A museum docent analogy

The paintings don't learn new talks. A docent (visitor) walks the gallery and knows how to describe a portrait vs a landscape. Hire a new docent for a new tour — the art stays on the wall unchanged.

The problem: a shape tree needs area() today and export_svg() tomorrow. Editing every shape class for each new op violates OCP. Double-dispatch via accept(visitor).

visitor.py
from typing import Protocol

class Visitor(Protocol):
    def visit_circle(self, c: "Circle") -> None: ...
    def visit_rect(self, r: "Rect") -> None: ...

class Shape(Protocol):
    def accept(self, v: Visitor) -> None: ...

class Circle:
    def __init__(self, r: float): self.r = r
    def accept(self, v: Visitor) -> None: v.visit_circle(self)

class Rect:
    def __init__(self, w: float, h: float): self.w, self.h = w, h
    def accept(self, v: Visitor) -> None: v.visit_rect(self)

class AreaVisitor:                           # a new operation — no shape edits
    def __init__(self): self.total = 0.0
    def visit_circle(self, c: Circle) -> None:
        self.total += 3.14159 * c.r * c.r
    def visit_rect(self, r: Rect) -> None:
        self.total += r.w * r.h

shapes = [Circle(1), Rect(2, 3)]
v = AreaVisitor()
for s in shapes: s.accept(v)
print(round(v.total, 2))                     # 9.14
Output9.14
Use when
the element hierarchy is stable but you keep inventing new operations over it (compilers, AST tools, document exporters).
Avoid when
you add element types often — every new leaf forces every visitor to grow a method.
Visitor trades the wrong axis of change

It makes operations easy and new element types hard. In Python, functools.singledispatch or a plain match on type often replaces textbook Visitor with less ceremony — reach for the classic form when you need a family of related ops that travel together.

11  Interpreter: a grammar as objects

Intent: given a language, define a representation for its grammar along with an interpreter that uses the representation to evaluate sentences.

A pocket calculator tree analogy

"3 + (4 × 5)" isn't one blob — it's a tree: a Plus node holding a Number and a Times, which holds two Numbers. Evaluating means each node asks its children what they mean. The grammar is the object graph.

The problem: a tiny expression language for rules or filters. Model each grammar rule as a class with interpret(context).

interpreter.py
from typing import Protocol

class Expr(Protocol):
    def interpret(self, ctx: dict[str, int]) -> int: ...

class Number:
    def __init__(self, n: int): self.n = n
    def interpret(self, ctx: dict[str, int]) -> int: return self.n

class Var:
    def __init__(self, name: str): self.name = name
    def interpret(self, ctx: dict[str, int]) -> int: return ctx[self.name]

class Add:
    def __init__(self, left: Expr, right: Expr):
        self.left, self.right = left, right
    def interpret(self, ctx: dict[str, int]) -> int:
        return self.left.interpret(ctx) + self.right.interpret(ctx)

# tree for: a + 3
expr: Expr = Add(Var("a"), Number(3))
print(expr.interpret({"a": 10}))             # 13
Output13
Use when
you have a small, stable grammar worth modelling as objects (config DSL, simple rules, query filters).
Avoid when
the language is large — a real parser generator / AST library beats hand-rolled Interpreter classes.
It's Composite with evaluate()

Interpreter is often just Composite applied to a grammar tree. Don't oversell it in interviews — say when you'd stop and reach for ast, Lark, or a PEG parser instead of growing expression classes forever.

You want a sorting routine where the caller decides the comparison key — by length, by date, by price — chosen fresh each call. Which pattern?

Right: swapping the algorithm (here, the sort key) at runtime is Strategy. In Python you just pass a function — sorted(items, key=...) is Strategy built into the language.

Strategy and State look almost identical — both delegate to a swappable object. What's the real difference?

Right: the structure is similar, the intent differs. A Strategy is picked by the client and doesn't change the object's mode; State objects represent modes that transition — each state typically decides what the next state is.

You need undo/redo plus the ability to queue actions for later replay. Wrapping each action — with its target and arguments — as a reversible object points to which pattern?

Right: turning a request into a first-class object with execute()/undo() so it can be stored, queued, and reversed is the Command pattern.
