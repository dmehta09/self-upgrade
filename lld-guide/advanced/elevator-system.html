Advanced case · State + Strategy

Case study: an elevator system.

A bank of elevators is two design problems in one. Each car's behaviour depends on which way it's going — that's the State pattern, with direction as the state. And the question of which car should answer a call is a rule that changes from building to building — so we make it a pluggable Strategy. Build the single car first, then the controller that dispatches between many.

01  Step 1 — Requirements & assumptions

There are several elevators serving a tall building. A person presses a hall button on some floor; the system picks a car and sends it. Once a car has work, it serves requests along a SCAN sweep — it keeps moving one direction, stopping at floors on the way, until nothing's left ahead, then it reverses. That one rule (don't thrash back and forth — finish the sweep) is the heart of how real elevators feel efficient.

Clarifying questions I'd ask: How many cars? Do we model in-car (destination) buttons separately from hall buttons? Is a hall call directional (up vs down) or just "a floor"? What rule chooses the car — nearest, same-direction, least-busy? Single-threaded simulation or many cars stepping concurrently?

My stated assumptions

Floors are plain integers, so the math stays exact and deterministic. The demo is single-threaded — one car steps at a time so the output is reproducible. The SCAN is simplified: a call is just a target floor (we don't track its up/down intent), and a car serves every target in its set as it passes, reversing when nothing remains in the current direction.

✅

Functional (in scope)

Several elevators · accept a hall call for a floor and dispatch a car · a car serves its targets along a SCAN sweep · reverse direction when nothing remains ahead · return to idle when there's no work · a swappable rule for choosing the car.

📐

Out of scope (noted extensions)

Directional hall calls (separate up/down buttons), in-car destination buttons, weight/capacity limits, door timing, real concurrency across cars, and emergency/maintenance modes. Each is a clean add-on rather than a rewrite.

02  Step 2 — Direction as State

A single car is a little state machine, and the state is its direction of travel. There are exactly three:

StateMeaningHow it leaves
IDLENo targets, parked, going nowhereA target arrives → start UP or DOWN, whichever points at the work
MOVING UPClimbing, serving stops as it passesNothing left above → flip to DOWN; nothing left at all → IDLE
MOVING DOWNDescending, serving stops as it passesNothing left below → flip to UP; nothing left at all → IDLE

The transitions are the whole behaviour: idle → up or down when a target arrives (pick the direction that has work); up → down when nothing remains above the car; down → up by symmetry; and → idle whenever the target set empties. Notice the car never asks "what should I do?" with a tangle of flags — it simply is a direction, and each direction knows when to flip. That is the same insight behind the vending machine's State pattern: behaviour that "depends on the current state" becomes a named state plus its transitions.

A waiter clearing tables analogy

A good waiter doesn't zig-zag across the room. They sweep down one side of the restaurant clearing every table that's ready, reach the end, then sweep back up the other side — never doubling back mid-row. That single "finish the direction you're going before you reverse" rule is exactly the SCAN sweep, and "which way am I currently sweeping" is the elevator's direction state.

03  The state machine + the dispatch

First, a single car's direction state machine. Each arrow is a transition the car makes on its own as it steps along the sweep:

A target arriving moves IDLE → UP (or DOWN). When nothing remains above, UP flips to DOWN to serve the lower stops; when the target set empties, the car settles back to IDLE. Each flip is decided inside the car's step(), not by an external scheduler.

Second, the dispatch seam. The controller never hard-codes which car answers — it asks a SelectionStrategy, which is interchangeable:

ElevatorController
Owns the list of cars. On a hall call it delegates the choice, then hands the chosen car the new target. It contains no selection logic itself.
SelectionStrategy «interface»
One job: pick(elevators, floor) → the chosen Elevator. The varying part of the design lives here.
NearestStrategy
The default rule — pick the car with the smallest abs(car.floor - call_floor). Swap it for same-direction or least-busy without touching the controller.

The "no flip!" self-loops are the interview point: a naive elevator chases every new call (starving riders mid-route); SCAN finishes the current direction first. The flip decisions live inside the car's step logic — the controller never micromanages direction.

04  Step 4 — The implementation

The car owns its own movement. Direction is an enum whose value (+1 / -1 / 0) doubles as the floor delta per step, so step() just adds it. add_target wakes an idle car; step advances one floor and decides whether to keep going, reverse the sweep, or stop.

elevator.py
from enum import Enum

class Direction(Enum):
    UP = 1
    DOWN = -1
    IDLE = 0

class Elevator:
    def __init__(self, id, floor=0):
        self.id = id
        self.floor = floor
        self.direction = Direction.IDLE
        self.targets = set()             # floors this car still must visit

    def add_target(self, floor):
        if floor != self.floor:
            self.targets.add(floor)
        if self.direction is Direction.IDLE and self.targets:
            self.direction = (Direction.UP if max(self.targets) > self.floor
                              else Direction.DOWN)

    def step(self):                      # advance one floor along the SCAN sweep
        if not self.targets:
            self.direction = Direction.IDLE
            return
        self.floor += self.direction.value
        self.targets.discard(self.floor)            # doors open if it was a stop
        above = any(t > self.floor for t in self.targets)
        below = any(t < self.floor for t in self.targets)
        if not self.targets:
            self.direction = Direction.IDLE
        elif self.direction is Direction.UP and not above:
            self.direction = Direction.DOWN         # reverse the sweep
        elif self.direction is Direction.DOWN and not below:
            self.direction = Direction.UP

Now the dispatch half. SelectionStrategy is a Protocol — a structural interface — so a strategy class just needs a pick method, no inheritance required. ElevatorController takes the cars and a strategy in its constructor and forwards every call.

dispatch.py
from typing import Protocol

class SelectionStrategy(Protocol):
    def pick(self, elevators, floor): ...      # return the chosen Elevator

class NearestStrategy:
    def pick(self, elevators, floor):
        return min(elevators, key=lambda e: abs(e.floor - floor))

class ElevatorController:
    def __init__(self, elevators, strategy):
        self.elevators = elevators
        self.strategy = strategy               # injected — swappable dispatch rule
    def request(self, floor):
        car = self.strategy.pick(self.elevators, floor)
        car.add_target(floor)
        return car
Why the enum value is the step delta

Direction.UP.value is +1, DOWN is -1, IDLE is 0. So self.floor += self.direction.value moves the car one floor the right way with no if branch — and an idle car that somehow stepped wouldn't move at all. Small touch, but it keeps step() almost branch-free except for the sweep-reversal logic.

05  Walk a scenario

Two cars: car 1 parked at floor 0, car 2 at floor 8. A call comes from floor 3. Under NearestStrategy, car 1 (distance 3) beats car 2 (distance 5), so car 1 is dispatched and climbs to floor 3, settling to IDLE the moment it arrives and the target set empties:

demo.py
ctrl = ElevatorController(
    [Elevator(1, floor=0), Elevator(2, floor=8)],
    NearestStrategy(),
)
car = ctrl.request(3)                      # nearest to 3 is car 1
print(f"Car {car.id} dispatched to floor 3")
for _ in range(3):
    car.step()
    print(f"Car {car.id} at floor {car.floor}, dir {car.direction.name}")
OutputCar 1 dispatched to floor 3 Car 1 at floor 1, dir UP Car 1 at floor 2, dir UP Car 1 at floor 3, dir IDLE

Car 1 climbs floor by floor while it still has a target above, then drops to IDLE exactly when it reaches floor 3 and the set empties — the state machine doing its job with no external scheduler.

Two cars at floors 0 and 8; a call comes from floor 3 under NearestStrategy. Which car is dispatched?

Right: NearestStrategy.pick takes the min by abs(car.floor - floor). Car 1 is 3 floors away, car 2 is 5 — so car 1 wins. Distance, not current height, is what the rule compares.

Why model the dispatch rule as a Strategy object instead of an if inside the controller?

Right: the choosing rule is the part that varies between buildings. Isolating it behind pick(elevators, floor) means a new rule is a new class — the controller stays closed to modification, open to extension. See the parking lot's pricing Strategy for the same move.

06  Extensions — your turn

The payoff of splitting State (the car) from Strategy (the dispatch) is that each grows on its own. Try these before peeking.

Exercise 1 · a SameDirectionStrategy

Add a SameDirectionStrategy that prefers a car already heading toward the caller — a car moving up below the call, or moving down above it — and only falls back to nearest when no car is conveniently aligned. Where does it plug in, and what stays untouched?

Hint: it's a new class with the same pick(elevators, floor) shape. Filter the cars to those whose direction points at floor; if any qualify, pick the nearest of those; otherwise pick the nearest overall. The controller and the Elevator never change.

Show a solution solution

One new class implementing the same protocol. A car "matches" if it's moving up and sits at or below the call, or moving down and sits at or above it; among matches we take the nearest, and if there are none we fall back to nearest overall.

same_direction.py
from elevator import Direction

def _heading_toward(car, floor):
    if car.direction is Direction.UP:
        return car.floor <= floor          # caller is ahead, going up
    if car.direction is Direction.DOWN:
        return car.floor >= floor          # caller is ahead, going down
    return True                            # idle cars are always available

class SameDirectionStrategy:
    def pick(self, elevators, floor):
        aligned = [e for e in elevators if _heading_toward(e, floor)]
        pool = aligned or elevators        # fall back to nearest overall
        return min(pool, key=lambda e: abs(e.floor - floor))

Because it satisfies the same SelectionStrategy protocol, you hand it to the controller exactly like NearestStrategy() — ElevatorController(cars, SameDirectionStrategy()) — and nothing else in the system moves.

Exercise 2 · capacity, or internal vs external calls

Pick one: (a) give each car a weight / occupancy limit so a full car is skipped by the dispatcher, or (b) split internal (in-car destination) requests from external (hall) calls. What does each need, and which class owns the new data?

Hint for (a): the car gains a load and capacity, and a LeastBusyStrategy (or any strategy) filters out cars where load >= capacity before ranking. For (b): both kinds still become entries in targets — the difference is only in who creates them (a passenger inside vs the controller outside), so the SCAN logic is reused verbatim.

Show a solution solution

For the capacity variant, the new state lives on the Elevator (it owns its own occupancy), and the skipping rule lives in a strategy (selection is the controller's concern). The two responsibilities stay cleanly separated.

capacity.py
# Elevator gains: self.load = 0  and  self.capacity = 8
class CapacityAwareStrategy:
    def pick(self, elevators, floor):
        free = [e for e in elevators if e.load < e.capacity]
        pool = free or elevators           # if every car is full, accept anyway
        return min(pool, key=lambda e: abs(e.floor - floor))

# Internal vs external: both just call the same entry point —
#   car.add_target(dest)     # passenger pressed a button inside
#   ctrl.request(hall_floor) # someone pressed a hall button outside
# so the SCAN sweep in step() serves them identically.

Whichever you chose, the shape is the same: car-owned state (load) stays on the Elevator; the choosing rule stays a swappable SelectionStrategy. Adding capacity-awareness never touched step() or the controller.

What this design used — the toolkit recap

State pattern — a car's direction (IDLE / UP / DOWN) is its state, and each step() decides its own transition (keep going, reverse the sweep, or stop). Strategy pattern — the dispatch rule lives behind pick(elevators, floor), so NearestStrategy, SameDirectionStrategy, and CapacityAwareStrategy are interchangeable with the controller untouched (Open/Closed). Enums for the direction vocabulary, with the value doubling as the step delta. Single Responsibility — the Elevator owns its movement and occupancy; the ElevatorController owns selection. Two jobs, two classes.

One thing we kept out: real concurrency. In production many cars step in parallel and a hall call mutates a car's shared targets set, so each car would need its own lock around add_target and step to avoid corrupting that set — the same discipline as the concurrency primer.
