Case study: an in-memory KV store.

The machine-coding question of the moment. It starts insultingly simple — get/put/delete on a dict — then escalates twice: per-key TTL (now you have a time problem) and nested transactions (now you have a layering problem). Both escalations have beautiful small answers; both have tar pits.

01  Clarify the requirements

  • get(k) / put(k, v, ttl=None) / delete(k) — string keys, arbitrary values.
  • TTL: a key with ttl=30 stops existing 30 seconds after the put. Expired = absent, atomically — never serve a stale value.
  • Transactions: begin() / commit() / rollback(), and they nest: an inner rollback discards only the inner changes.
  • Thread-safe; everything in memory.

Two clarifying questions that mark seniority: "reads inside a transaction see its own uncommitted writes, right?" (yes — read-your-writes) and "does TTL count from the original put if a transaction rewrites the key?" (pin an answer; we'll say the rewrite resets it). And one invariant: after rollback, the store is byte-identical to before begin.

02  TTL: lazy expiry + a heap sweeper, and an injected Clock

Store each entry as (value, expires_at) where expires_at = clock.now() + ttl. Then expiry is two cooperating mechanisms:

Lazy (correctness)
get() checks expires_at before returning — an expired key is deleted on touch and reported absent. This alone makes the store correct; no timer can race a read.
Sweeper (memory)
Lazy expiry never frees keys nobody reads again. Keep a min-heap of (expires_at, key); a background pass pops everything due. One subtlety: a re-put with a new TTL leaves a stale heap entry — on pop, re-check against the dict and skip if the entry no longer matches (the standard "lazy deletion from a heap" trick).
Injected Clock (testability)
Clock is a Protocol with now(). Production uses time.monotonic; tests use a FakeClock you advance by hand. TTL tests with sleep() are flaky and slow — injecting the clock is the difference between "knows DI" and "uses DI."

Why time.monotonic() rather than time.time() for expiry math?

Right: durations belong to the monotonic clock; timestamps for humans belong to the wall clock. Mixing them is a real production bug class, and naming it earns instant credibility.

03  Transactions: a stack of delta maps

The tar pit is copying the whole store on begin() — correct, O(n) per transaction, and the interviewer will ask about a million keys. The senior answer inverts it: record only the changes. Each begin() pushes an empty delta map; writes go to the top delta; reads walk the stack top-down, falling through to the base store. A special TOMBSTONE marker makes deletes overlay correctly:

kv_store.py
import threading

TOMBSTONE = object()        # sentinel: "deleted in this layer"

class KVStore:
    def __init__(self, clock: Clock | None = None):
        self._base: dict[str, tuple] = {}     # key -> (value, expires_at)
        self._stack: list[dict] = []          # delta maps, innermost last
        self._clock = clock or MonotonicClock()
        self._lock = threading.RLock()

    # ---- reads walk the overlay stack, then the base ----
    def get(self, key: str):
        with self._lock:
            for delta in reversed(self._stack):
                if key in delta:
                    v = delta[key]
                    return None if v is TOMBSTONE else self._fresh(key, v)
            if key in self._base:
                return self._fresh(key, self._base[key])
            return None

    def _fresh(self, key, entry):
        value, expires_at = entry
        if expires_at is not None and self._clock.now() >= expires_at:
            self.delete(key)                  # lazy expiry on touch
            return None
        return value

    # ---- writes always land in the innermost layer ----
    def put(self, key: str, value, ttl: float | None = None) -> None:
        with self._lock:
            exp = self._clock.now() + ttl if ttl else None
            target = self._stack[-1] if self._stack else self._base
            target[key] = (value, exp)

    def delete(self, key: str) -> None:
        with self._lock:
            if self._stack:
                self._stack[-1][key] = TOMBSTONE   # overlay the delete
            else:
                self._base.pop(key, None)

    # ---- transactions: push / merge-down / discard ----
    def begin(self) -> None:
        with self._lock:
            self._stack.append({})

    def commit(self) -> None:
        with self._lock:
            if not self._stack:
                raise RuntimeError("no transaction")
            delta = self._stack.pop()
            target = self._stack[-1] if self._stack else self._base
            for k, v in delta.items():
                if v is TOMBSTONE and not self._stack:
                    target.pop(k, None)       # tombstone reaches the base
                else:
                    target[k] = v             # else: stays an overlay entry

    def rollback(self) -> None:
        with self._lock:
            if not self._stack:
                raise RuntimeError("no transaction")
            self._stack.pop()                 # discard — that's the whole undo

Look at rollback(): one pop. The invariant ("byte-identical to before begin") holds by construction because nothing inside the transaction ever touched the layers below. Nesting falls out for free — the stack is the nesting. Pattern-wise this is Memento by layering rather than by snapshot, and each delta is effectively a batched Command.

Why is the TOMBSTONE needed — why not just remove the key from the delta on delete?

Right: the delta map has three meanings per key: present (new value), TOMBSTONE (deleted here), absent (no opinion — ask below). Without the sentinel, "deleted" and "untouched" collapse into one and deletes silently un-happen on read.

04  Why every method takes the lock

A KV store's counter = get + 1; put(counter) is the primer's lost update wearing an API. But even a single put() is multi-step here (read stack state, compute expiry, write the right layer). Scrub two bare puts colliding, then the same schedule under the RLock:

Two design notes to narrate: it's an RLock because methods call each other (get → delete on lazy expiry) and a plain Lock would self-deadlock; and the lock protects each call, not the get-then-put pair — for that, real stores expose an atomic incr()/compare-and-set, which is exactly the extension to pitch.

05  Extensions

Atomic primitives
incr(key), cas(key, expected, new) — one lock acquisition wrapping read+write. This is how Redis sidesteps client-side races.
Metrics / logging wrapper
A Decorator implementing the same store interface: counts hits/misses, times calls, then delegates. Zero edits to the store.
LRU eviction at capacity
Bolt the LRU machinery under the same API — dict + linked list, evict on insert past max size.
Persistence (AOF)
Append every committed mutation to a log; replay on boot. Commands again — the same shape as chess's move history.
Exercise · read-your-writes proof

Trace by hand: put(x,1) · begin · put(x,2) · begin · delete(x) · get(x) · rollback · get(x) · commit · get(x). Write the three get results and the stack state at each step.

Hint: None (tombstone in the inner layer) · 2 (inner layer discarded, outer's put visible) · 2 (outer delta merged into base). If you got all three, you understand the design.
