Advanced cases · overview

The cases that separate seniors.

The six-step method doesn't change here — but the design decisions get harder. These nine studies layer in custom data structures, two patterns you haven't met yet (Chain of Responsibility, Composite), and the dimension the classic cases skipped: concurrency. Start with the primer below, then take them in order.

01  What makes a case "advanced"

The classic cases (parking lot, vending machine, notification service) are about modelling — finding the right classes and wiring them cleanly. These advanced ones keep all of that and add one or more of:

🧮

Custom data structures

An LRU cache isn't a pattern — it's a HashMap + a doubly linked list designed together for O(1) operations. You build the structure, not just arrange classes.

🧵

Concurrency

Booking the same seat from two threads, refilling a token bucket, fanning a message out to subscribers — many of these break unless you reason about shared mutable state.

🧩

More patterns, combined

Chain of Responsibility, Composite, Strategy, Observer and State show up — often two or three in one design, each doing one job.

⚖️

Real trade-offs

Optimistic vs pessimistic locking, batch vs real-time matching, token bucket vs sliding window. The interviewer wants the why, not just code.

Same recipe, tougher ingredients analogy

You still cook with the same method — scope it, find the entities, draw it, build it. But now some ingredients are slippery: shared state that two cooks grab at once. Most of the new skill is learning to put a lock on the one drawer they both reach into.

02  The concurrency primer

Several cases below share one new hazard, so we cover it once, here. A race condition happens when two threads touch the same data at the same time and the result depends on who got there first. The classic culprit is read–modify–write: x += 1 looks like one step but is really three — read x, add one, write it back — and a thread can be paused mid-way.

Two people, one shared notebook analogy

You both read "balance: 100", each add 50 in your head, and each write "150". Two deposits happened; the notebook says 150, not 200. One update was lost. A lock is the rule "hold the pen before you read, put it down after you write" — now the second person sees 150 and writes 200.

Watch it happen. Five threads each increment a counter 100,000 times; the total should be 500,000:

import threading

class Counter:
    def __init__(self):
        self.value = 0
    def increment(self):
        self.value += 1            # read, +1, write — three steps, not one

c = Counter()
def work():
    for _ in range(100_000):
        c.increment()

threads = [threading.Thread(target=work) for _ in range(5)]
for t in threads: t.start()
for t in threads: t.join()

print(c.value)                     # NOT 500000 — updates were lost
import threading

class Counter:
    def __init__(self):
        self.value = 0
        self._lock = threading.Lock()
    def increment(self):
        with self._lock:           # only ONE thread inside at a time
            self.value += 1        # now the 3 steps can't be interleaved

c = Counter()
def work():
    for _ in range(100_000):
        c.increment()

threads = [threading.Thread(target=work) for _ in range(5)]
for t in threads: t.start()
for t in threads: t.join()

print(c.value)                     # 500000 — always
OutputRacy: 482137 (a different wrong number each run) Fixed: 500000

500,000 increments are too fast to see — so here is one lost update in slow motion. Scrub through the exact interleaving where Thread B's write lands on top of Thread A's, then replay the same schedule with the lock:

That red verdict is the notebook analogy made literal: B read the same 0 A did, so B's 1 erased A's 1. Multiply by 100,000 iterations and you get the "different wrong number each run" above. Notice in the locked replay how B's first move is blocked — that brief wait is the entire price of correctness.

The fix is a threading.Lock guarding the critical section — the few lines that read-then-write shared state. with self._lock: acquires the lock on entry and releases it on exit (even if an exception fires). Keep critical sections small: lock, touch the shared data, unlock.

"Doesn't the GIL make Python thread-safe?" — no

CPython's Global Interpreter Lock means one thread runs bytecode at a time, but a thread can still be switched out between bytecodes — right in the middle of read → add → write. So compound operations like x += 1, "check then act", and "find a free seat then book it" are not atomic. You still need your own lock. (A single list.append happens to be atomic in CPython, but never rely on that for your own multi-step logic.)

The toolbox you'll reuse

Lock — one holder at a time (mutual exclusion). RLock — re-entrant; the same thread can acquire it twice (handy when a locked method calls another locked method). Queue (from queue) — a thread-safe FIFO, so producers and consumers hand off work without their own locks. Optimistic locking — don't lock; attach a version number and retry if it changed. We use each of these in the cases below.

Why is self.value += 1 unsafe across threads even with CPython's GIL?

Right: the GIL serialises individual bytecodes, not your logical operation. The read–modify–write can be interrupted mid-way, so two threads can both read the same value and one update is lost. A lock makes the three steps indivisible.

What's the rule of thumb for the size of a critical section (the code under a lock)?

Right: a lock serialises everything inside it, so a big critical section throttles throughput and risks deadlock. Lock the minimum — read/modify/write the shared data, then release.
