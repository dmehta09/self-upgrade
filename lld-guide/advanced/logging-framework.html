Case study: a logging framework.

A log message is born somewhere deep in your code and needs to reach the right places — the console for everything, a file for warnings, an on-call inbox for genuine fires. The clean way is a chain: hand the message to the first handler, which decides whether to act and then passes it on to the next. Each link does its own small job, and you grow the system by adding links — never by editing them.

01  Step 1 — Requirements & assumptions

A logger must support several severity levels — DEBUG<INFO<WARN<ERROR — and several destinations: the console, a log file, and an on-call email. The catch that makes this interesting: each destination has its own minimum level. The console prints everything; the file only cares from WARN up; email fires only on ERROR.

Clarifying questions I'd ask: Which severity levels do we need, and are they strictly ordered? Should a single message be able to reach multiple destinations at once, or just one? Does each destination set its own threshold? Do we need this thread-safe? Is the set of destinations fixed, or will new ones (Slack, metrics, …) be added later?

My stated assumptions

Four ordered levels (DEBUG<INFO<WARN<ERROR). A message may reach several destinations — every destination whose threshold it clears logs it, not just the first. Each handler owns its own minimum level. Single-threaded for the demo (a Lock is a noted extension). The set of destinations must be open to extension — adding one shouldn't touch existing code.

✅

Functional (in scope)

Emit a message at a chosen level · route it through console, file, and on-call email · each destination logs only at or above its own threshold · one message can land in several destinations · adding a destination is additive.

📐

Non-functional notes

New destinations and new levels must not force edits to existing handlers — design for extension. Each handler does one thing (write to its sink). The ordering of levels should be expressed once, in code, not duplicated as scattered magic numbers.

02  Step 2 — Why a chain

The naive version is one function with a cascade of if/elif:

naive_log.py
def log(level, message):
    if level >= DEBUG:
        print_to_console(message)
    if level >= WARN:
        write_to_file(message)
    if level >= ERROR:
        send_email(message)
    # want Slack too? edit THIS function. Again. And again.

It works — but every new destination means cracking open this one function and adding another branch. That violates the Open/Closed Principle: the function is supposed to be closed to modification, yet you keep modifying it. The thresholds, the sinks, and the routing are all tangled into a single growing blob.

The Chain of Responsibility pattern untangles it. Make each destination its own small handler object that knows two things: its threshold, and the next handler in line. When a message arrives, a handler asks "is this at or above my level?" — if so it logs — and then, regardless, passes the message along to its successor. Routing logic disappears into a uniform link-to-link handoff.

Handler (base)
The chain link. Holds its own minimum level and a reference to the _next handler. Its handle() decides whether to act, then forwards.
Concrete handlers
ConsoleHandler, FileHandler, EmailHandler — each overrides one method, write(), to talk to its own sink. They share all the routing logic from the base.
The chain
Handlers wired head-to-tail. You build it once; emitting is just chain.handle(level, msg).
An escalation chain at a help desk analogy

A complaint walks down the line: the front desk handles the small stuff, the manager the bigger stuff, the director the worst. Each person looks at the issue and acts if it's in their remit. The twist that makes logging special: here it's not "first one who can, stops" — every capable handler logs and the message keeps travelling down the whole chain. An ERROR doesn't get caught by the console and disappear; it hits console and file and email.

The message is handed to Console, then passed on to File, then to Email — always travelling the full chain. At each link the handler logs only if the message clears its own threshold. An INFO stops being logged after Console (File and Email skip it but still pass it on); an ERROR is logged by all three.

04  Step 4 — The implementation

The base LogHandler carries all the routing: the "do I act?" check and the "pass it on" handoff. Each concrete handler fills in just one method — write() — so the destinations stay tiny and the chain logic lives in exactly one place. Levels are an IntEnum so >= compares them in severity order.

logging_chain.py
from enum import IntEnum

class Level(IntEnum):
    DEBUG = 10
    INFO = 20
    WARN = 30
    ERROR = 40

class LogHandler:                          # the chain link (handler base)
    def __init__(self, level, nxt=None):
        self.level = level                 # this destination's minimum level
        self._next = nxt                   # the next handler in the chain

    def handle(self, level, message):
        if level >= self.level:            # high enough? this destination logs it
            self.write(level, message)
        if self._next is not None:         # pass it on regardless
            self._next.handle(level, message)

    def write(self, level, message):
        raise NotImplementedError          # each concrete handler fills this in

class ConsoleHandler(LogHandler):
    def write(self, level, message):
        print(f"[{level.name}] console: {message}")

class FileHandler(LogHandler):
    def __init__(self, level, path, nxt=None):
        super().__init__(level, nxt)
        self.path = path
    def write(self, level, message):
        print(f"[{level.name}] file({self.path}): {message}")   # pretend disk write

class EmailHandler(LogHandler):
    def write(self, level, message):
        print(f"[{level.name}] EMAIL on-call: {message}")
Why IntEnum instead of bare ints or strings

IntEnum gives us both readability and ordering for free. level.name prints "WARN" in the log line, while level >= self.level still compares by the numeric value (10/20/30/40). The numeric gaps (10 apart) leave room to slot a TRACE = 5 or FATAL = 50 in later without renumbering anything.

05  Walk a scenario

We wire console → file → email once, with the thresholds from the brief, then emit two messages: a quiet INFO and a real ERROR. Watch the INFO reach only the console while the ERROR lights up all three destinations.

demo.py
# console logs everything; file only WARN+; email only ERROR+
chain = ConsoleHandler(Level.DEBUG,
            FileHandler(Level.WARN, "/var/log/app.log",
                EmailHandler(Level.ERROR)))

chain.handle(Level.INFO, "user logged in")
print("---")
chain.handle(Level.ERROR, "payment gateway down")
Output[INFO] console: user logged in --- [ERROR] console: payment gateway down [ERROR] file(/var/log/app.log): payment gateway down [ERROR] EMAIL on-call: payment gateway down

The INFO cleared only the console's threshold; it still travelled to File and Email, but those skipped it. The ERROR cleared all three. Notice the message never had to know who its destinations were — the chain did the routing.

An INFO message goes through console(≥DEBUG)→file(≥WARN)→email(≥ERROR). Which handlers log it?

Right: INFO (20) clears only the console's DEBUG (10) threshold. It's still passed to file and email, but their handle() sees 20 < 30 and 20 < 40, so neither writes. Passing on a message is not the same as logging it.

Why prefer the chain over one big if/elif in a log() function?

Right: a new destination is a new handler class plus one wiring line — the base LogHandler and every existing handler stay exactly as they are. The if/elif version forces an edit to one shared function for every change, which is the Open/Closed violation the pattern removes.

06  Extensions — your turn

A strong answer ends by showing where the design grows. With Chain of Responsibility, growth means new links — never surgery on old ones. Try these before peeking.

Exercise 1 · a new destination

Add a SlackHandler that posts to a channel for WARN and above — without editing any existing handler. Where does it go, and how much of the old code changes?

Hint: subclass LogHandler, override only write(), and splice it into the chain wherever you want it to sit. The base class already does all the routing.

Show a solution solution

One new class, one new wiring line. Every existing handler is untouched — that "barely anything changes" feeling is Open/Closed paying off:

slack_handler.py
class SlackHandler(LogHandler):
    def __init__(self, level, channel, nxt=None):
        super().__init__(level, nxt)
        self.channel = channel
    def write(self, level, message):
        print(f"[{level.name}] slack #{self.channel}: {message}")

# splice it in anywhere — here, between file and email:
chain = ConsoleHandler(Level.DEBUG,
            FileHandler(Level.WARN, "/var/log/app.log",
                SlackHandler(Level.WARN, "alerts",
                    EmailHandler(Level.ERROR))))

The base LogHandler, ConsoleHandler, FileHandler, and EmailHandler are all unchanged. The same shape works for an AsyncHandler that hands write() off to a background queue so logging never blocks the caller — again, a new link, no edits.

Exercise 2 · two flavours of the pattern

Our chain has every capable handler act and always passes the message on. But the classic textbook Chain of Responsibility usually stops at the first capable handler. When would you want each behaviour?

Show a solution solution

"Logging-style" CoR (ours): every handler whose threshold the message clears acts, and the message always continues down the chain. Use it when more than one party legitimately wants the same event — a log line belongs in the console and the file and the alert inbox at once.

"Pure" CoR: the first handler that can deal with the request handles it and stops — the message never reaches the rest. Use it when the request should be consumed exactly once, like an approval chain (a manager who can approve a $500 expense does so and the request goes no higher) or a support ticket escalating until someone resolves it. The only code change is to stop forwarding once handled:

pure_cor.py
def handle(self, request):
    if self.can_handle(request):
        self.act(request)
        return                     # consumed — STOP, don't pass on
    if self._next is not None:
        self._next.handle(request) # only forward when WE couldn't handle it

Same skeleton — a base link holding a _next — two routing policies. Knowing which one a problem wants ("fan-out to all" vs. "first responder consumes") is the senior insight.

One more production-ready touch: shared across threads, several callers could interleave their write() calls and scramble a file or console line. Guard the writes with a single threading.Lock (or push messages onto a queue drained by one writer thread) — see the concurrency primer for the pattern.

What this design used — the toolkit recap

Chain of Responsibility — each handler decides whether to act, then forwards, so routing is a uniform link-to-link handoff. Open/Closed Principle — a new destination is a new handler, never an edit to existing ones. Polymorphism via a base handler — the shared LogHandler.handle() does the routing while each subclass overrides only write(). IntEnum for ordered, self-naming severity levels. And the production extensions: a Lock or queue for thread-safe writes, and knowing "fan-out" vs. "first-responder" CoR. That's the pattern, applied end to end.
