Advanced case · concurrency

Case study: movie ticket booking.

The whole design hinges on one hazard: two people click "buy seat A1" at the same instant, and a naive system happily sells it twice. The fix isn't more code — it's a hold-then-pay flow guarded by a lock, so checking that seats are free and marking them held is one atomic step. Hold the seats, take the (slow) payment, then confirm — or release the hold if it fails.

01  Step 1 — Requirements & assumptions

A customer picks one or more seats for a particular show and pays for them. The system must never double-book a seat, even when two requests for the same seat arrive at the same moment. Because payment is slow, we hold the chosen seats while it runs, and release them if the payment fails or times out — so a half-finished booking never strands a seat forever.

Clarifying questions I'd ask: Can a customer book several seats in one go, all-or-nothing? What happens if one of the requested seats is already taken — fail the whole request, or book the rest? How long do we hold seats before the payment must complete? Is payment synchronous, or a callback we wait on? Do we need this thread-safe across many concurrent requests (yes — that's the point)?

Assumptions, so the code stays focused

Everything is in-memory and in one process (a real system would use a database row-lock or a distributed lock — same idea, bigger blast radius). Payment is a boolean we pass in (pay_succeeds) standing in for a real gateway. The timeout is shown as an explicit release call rather than a background timer, so the seat state machine stays the star.

In scope

Seat state machine (free / held / booked) · atomic all-or-nothing hold of several seats · confirm on payment success · release on payment failure or timeout · a single Lock per show.

Out of scope

Pricing, discounts and tax · seat maps and UI · users and auth · persistence and a real payment gateway · cross-process / distributed locking · a live background expiry timer (sketched as an extension).

02  Step 2 — The race condition

This is the whole case in one paragraph, so read it slowly. Two requests arrive for seat A1 at the same instant. Each one does the obvious thing: check that A1 is FREE, see that it is, then book it. But if both threads run the check before either runs the book, they both see FREE and they both book — two customers, one seat. The seat was double-sold, and worse, both got a "success." This is a classic read–modify–write race (see the concurrency primer).

The fix is to make "check that all requested seats are free, THEN mark them held" a single, indivisible critical section under a lock. While one thread holds the lock, no other thread can even peek at the seats — so the second request sees A1 as HELD and fails cleanly, exactly as it should.

"Check-then-act" is not atomic

Any code shaped like "if the seat is free, then take it" is two operations with a gap in between — and a thread can be switched out right in that gap. CPython's GIL does not save you: it serialises single bytecodes, not your multi-step logic. The only fix is to put the check and the act inside the same with self._lock: block so nothing can run between them.

03  Step 3 — Seat states

Every seat is always in exactly one of three states, and only certain transitions are legal. A free seat can be held; a held seat can be confirmed (booked) or released back to free; a booked seat is terminal. That little state machine is what makes the rules easy to reason about.

hold moves FREE → HELD · confirm moves HELD → BOOKED on payment success · release moves HELD → FREE when payment fails or times out. A booked seat never goes back.

Two small classes carry the design — one owns the state, the other owns the flow (single responsibility):

Show
Owns the seats and their states, plus the one threading.Lock. Exposes the three atomic transitions — hold, confirm, release — each guarded by that lock. It is the only thing that ever touches seat state.
BookingService
Orchestrates the flow: hold the seats → take payment → confirm on success or release on failure. It holds no locks and no seat state of its own; it just calls the Show in the right order.

04  Step 4 — The implementation

Notice how every state change in show.py lives inside a with self._lock: block — the check and the set are never separated. And note hold is all-or-nothing: if any one seat is taken, the whole request fails and nothing is changed.

show.py
import threading
from enum import Enum

class SeatState(Enum):
    FREE = "free"
    HELD = "held"
    BOOKED = "booked"

class Show:
    def __init__(self, show_id, seat_ids):
        self.show_id = show_id
        self.seats = {s: SeatState.FREE for s in seat_ids}
        self._lock = threading.Lock()

    def hold(self, seat_ids):
        with self._lock:                    # check-and-set is ONE atomic step
            if any(self.seats[s] is not SeatState.FREE for s in seat_ids):
                return False                # at least one is taken -> fail as a whole
            for s in seat_ids:
                self.seats[s] = SeatState.HELD
            return True

    def confirm(self, seat_ids):
        with self._lock:
            if any(self.seats[s] is not SeatState.HELD for s in seat_ids):
                return False
            for s in seat_ids:
                self.seats[s] = SeatState.BOOKED
            return True

    def release(self, seat_ids):            # called on payment failure / timeout
        with self._lock:
            for s in seat_ids:
                if self.seats[s] is SeatState.HELD:
                    self.seats[s] = SeatState.FREE

The service is deliberately dumb — it knows the order of steps, nothing about locks:

booking.py
class BookingService:
    def __init__(self, show):
        self.show = show

    def book(self, seat_ids, pay_succeeds):
        if not self.show.hold(seat_ids):        # atomically reserve, or bail
            return "seats unavailable"
        # seats are HELD; take payment (this part can be slow)
        if pay_succeeds:
            self.show.confirm(seat_ids)
            return "booked"
        self.show.release(seat_ids)             # payment failed -> free the holds
        return "payment failed, seats released"
Why payment happens outside the lock

The lock is held only for the microseconds it takes to flip a few seats to HELD — then it's released. Payment, which can take seconds, runs while the lock is free, so other customers can keep booking other seats. The held seats are reserved for this buyer, but the whole show isn't frozen waiting on one slow card. Keep the critical section tiny; do the slow work outside it.

05  Walk a scenario

Three seats. The first booking takes A1 and A2; the second asks for A2 and A3 and is rejected as a whole because A2 is gone; the third holds A3, fails payment, and the seat returns to free.

demo.py
show = Show("INTERSTELLAR-9pm", ["A1", "A2", "A3"])
svc = BookingService(show)

print(svc.book(["A1", "A2"], pay_succeeds=True))   # books A1, A2
print(svc.book(["A2", "A3"], pay_succeeds=True))   # A2 already taken
print(svc.book(["A3"], pay_succeeds=False))        # held, then payment fails
print(show.seats["A3"].value)                       # back to free
Outputbooked seats unavailable payment failed, seats released free

Why must "check the seats are free" and "mark them held" happen inside ONE lock?

Right: separate the check from the set and a second thread can slip into the gap, see the seat still FREE, and book it too. Wrapping both in one critical section makes the check-and-set indivisible, so the second request reliably sees HELD and fails.

Why hold seats and take payment after, instead of booking immediately?

Right: if you "booked" before payment you'd sell unpaid seats; if you took payment before reserving, two buyers could pay for the same seat. The HELD state is the middle ground — it reserves the seats during the slow payment and hands them back to FREE if it doesn't go through.

06  Extensions — your turn

Exercise 1 · optimistic concurrency

Our lock is pessimistic — it assumes a clash and blocks everyone. The alternative is optimistic: don't lock, give each seat a version number, and on confirm only succeed if the version is unchanged, else retry. Sketch that compare-and-set, and say when each approach wins.

Hint: read the seat's version when you start, do your work, then on commit check the version is still what you read; bump it on success, retry on a mismatch.

Show a solution solution
optimistic.py
# each seat carries (state, version). No lock held during the slow work.
def try_book(self, seat_id):
    state, version = self.seats[seat_id]      # snapshot what we saw
    if state is not SeatState.FREE:
        return False
    # ...slow work (e.g. payment) happens here, holding NO lock...
    return self._compare_and_set(seat_id, expected_version=version)

def _compare_and_set(self, seat_id, expected_version):
    with self._lock:                          # tiny atomic commit window
        state, version = self.seats[seat_id]
        if version != expected_version:       # someone changed it first
            return False                      # caller re-reads and retries
        self.seats[seat_id] = (SeatState.BOOKED, version + 1)
        return True

Pessimistic (a lock) wins when contention is high — many people fight over the same hot seats — because retries would thrash. Optimistic (versioning) wins when contention is low — clashes are rare, so you avoid the cost of locking on the common path and only pay on the occasional retry. Databases expose this as a version column; the compare-and-set becomes UPDATE ... WHERE version = :v, succeeding only if rows_affected == 1.

Exercise 2 · a real hold timeout

Right now a hold only ends when the service calls release. What if the customer walks away mid-payment? Add a real timeout that auto-releases a held seat after T seconds, so abandoned holds don't strand seats forever.

Hint: two common designs — a background sweeper thread that periodically frees expired holds, or a hold-expiry timestamp on each seat that's checked lazily on access.

Show a solution solution
expiry.py
# on hold(): also stamp self.hold_expiry[s] = now + T

def _expire_stale_holds(self, now):
    with self._lock:                          # same lock guards the sweep
        for s, state in self.seats.items():
            if state is SeatState.HELD and now >= self.hold_expiry[s]:
                self.seats[s] = SeatState.FREE   # abandoned -> back to free

# Option A: a daemon thread calls this every second.
# Option B: call it lazily at the top of hold()/confirm() so an
#           expired hold is reclaimed the moment someone else asks for it.

Either way the sweep runs under the same lock as the booking logic, so an expiring hold can't race a confirm. The lazy option needs no extra thread but only reclaims seats when traffic touches them; the sweeper reclaims promptly but costs a background thread. A real ticketing site usually does both: a sweeper for promptness, lazy checks as a safety net.

What this design used — the toolkit recap

Atomic critical sections — a threading.Lock wraps each check-and-set so "free? then hold" is indivisible and double-booking can't happen. A held / booked state machine (FREE → HELD → BOOKED, with HELD → FREE) models the slow payment cleanly and makes release trivial. Optimistic vs pessimistic locking — versioning-with-retry as the low-contention alternative to a blocking lock. And SRP: the Show owns seat state and locking, the BookingService owns the flow — neither reaches into the other's job.
