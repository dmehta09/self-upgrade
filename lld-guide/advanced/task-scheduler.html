Case study: a task scheduler.

Build cron in a process: one-shot and recurring jobs, priorities, cancel, retry. It composes half the guide — a heap (data structure), Command/Strategy/Observer (patterns), and the hardest concurrency primitive so far: the Condition wait-with-timeout loop that lets workers sleep exactly until there's something to do.

01  Clarify the requirements

  • submit(fn, run_at) — one-shot; submit_recurring(fn, every=60) — repeats.
  • N worker threads execute due tasks; a task that raises is retried per a retry policy (e.g. 3 tries, exponential backoff).
  • cancel(task_id) — a cancelled task never runs (again).
  • Ties at the same due time break by priority.

Invariants: a task runs at most once per due-time (two workers must never both grab it); no worker burns CPU while idle (no sleep(0.1) polling loops — say this unprompted); shutdown drains or abandons cleanly, never hangs.

02  The shape: heap + pool + one Condition

ScheduledTask (Command)
Wraps the callable with id, run_at, priority, cancelled flag, its SchedulePolicy and RetryPolicy. Orders by (run_at, priority) for the heap.
Min-heap (heapq)
The earliest-due task is always the root. Push O(log n), peek O(1) — exactly the access pattern a scheduler needs.
Worker pool
N identical threads running the same loop: wait until the root is due → pop → execute → maybe reschedule.
threading.Condition
One lock + a waiting room. Workers wait(timeout=until_next_due); submit() calls notify() — which is how a newly-submitted earlier task wakes a worker that was sleeping toward a later one. That wake-up is the whole question.
Policies (Strategy) & hooks (Observer)
SchedulePolicy.next_run(now) (once / interval / cron later) and RetryPolicy.next_delay(attempt) are injected; on_success/on_failure listeners hang off the lifecycle.

Why is queue.Queue — so perfect for producer–consumer — the wrong container here?

Right: a scheduler is ordered by time, not arrival — that's the min-heap's job. (Even PriorityQueue falls short: you can't peek at the root and sleep until it's due; you can only block-pop.)

03  The core: the worker loop

This loop is the interview. Every line answers a follow-up question:

scheduler.py
import heapq, threading, time

class Scheduler:
    def __init__(self, workers: int = 4):
        self._heap: list[ScheduledTask] = []
        self._cond = threading.Condition()        # one lock + waiting room
        self._shutdown = False
        self._threads = [threading.Thread(target=self._worker, daemon=True)
                         for _ in range(workers)]
        for t in self._threads: t.start()

    def submit(self, task: ScheduledTask) -> None:
        with self._cond:                           # Condition IS the lock
            heapq.heappush(self._heap, task)
            self._cond.notify()                    # maybe an EARLIER task:
                                                   # wake a sleeper to re-look
    def cancel(self, task: ScheduledTask) -> None:
        with self._cond:
            task.cancelled = True                  # lazy: skip it on pop
                                                   # (no O(n) heap surgery)
    def _worker(self) -> None:
        while True:
            with self._cond:
                while True:                        # the wait loop
                    if self._shutdown:
                        return
                    if not self._heap:
                        self._cond.wait()          # sleep: nothing scheduled
                        continue
                    delay = self._heap[0].run_at - time.monotonic()
                    if delay > 0:
                        self._cond.wait(timeout=delay)   # sleep until root
                        continue                   # is due OR notify() — then
                                                   # RE-CHECK (root may differ!)
                    task = heapq.heappop(self._heap)
                    break                          # we own it; leave the lock
            if task.cancelled:
                continue
            self._run(task)                        # execute OUTSIDE the lock

    def _run(self, task: ScheduledTask) -> None:
        try:
            task.fn()
        except Exception:
            delay = task.retry.next_delay(task.attempt)
            if delay is not None:                  # retry with backoff
                task.attempt += 1
                task.run_at = time.monotonic() + delay
                self.submit(task)
            return
        nxt = task.schedule.next_run(time.monotonic())
        if nxt is not None:                        # recurring: go again
            task.run_at, task.attempt = nxt, 0
            self.submit(task)

The three follow-ups it answers: "why re-check after wait?" — because wait() returning means maybe (a new root, a spurious wake-up, shutdown), so the condition is always re-evaluated in a loop; "why execute outside the lock?" — a 5-second task inside it would serialize the whole pool; "why lazy cancel?" — removing from a heap's middle is O(n) and re-heapifies; a flag checked after pop is O(1) and good enough.

04  The race the Condition kills: peek-then-pop

Suppose workers used a bare heap with no lock: both peek the root, both see it's due, both pop — one gets the real task, the other gets the wrong task (or an empty-heap crash), and a payment job runs twice. In the racy run the two claims collapse into one recorded claim — both workers believed they owned task #7. Under the lock, Worker 2 blocks at acquire and the claims serialize. In the real scheduler the entire peek → check due → pop sits inside with self._cond:, which is this fix generalized — and it's why the at-most-once invariant survives any interleaving.

05  Trace one submit, and the asyncio comparison

Trace to say out loud: submit(backup, run_at=now+300) → heap push, notify → an idle worker wakes, sees root due in 300s, sleeps wait(300) → at +120 someone submits an alert due now → push + notify → the sleeper wakes early, re-checks, sees the alert at the root, pops and runs it → loops back, resumes sleeping ~180s toward the backup. No polling, no missed work, no thundering herd (one notify(), not notify_all()).

The asyncio version, in one breath

Replace workers with coroutines, the Condition with asyncio.Condition (or just loop.call_at for the timing), and blocking task bodies with awaits — see the async deep-dive. Same design, cheaper waiting; the heap and the policies don't change at all. Saying "the structure survives the concurrency-model swap" is a senior closer.

06  Extensions

Cron expressions
Just another SchedulePolicy — parse once, next_run() computes the next matching instant. The Strategy seam absorbs it with zero scheduler edits.
Persistence
Journal submits/completions (Command log, like the KV store's AOF); on boot, reload pending tasks. Now a crash doesn't lose the backup job.
Distributed scheduling
Many machines, one logical scheduler → leader election or per-task leases — the boundary where this LLD question becomes a system-design question; name it and stop.
Exercise · graceful shutdown

Implement shutdown(drain: bool): drain=True runs everything already due, then stops; drain=False stops as soon as running tasks finish. Which line of the worker loop changes, and why must shutdown use notify_all() when submit only needed notify()?

Hint: submit creates one unit of work — one waker is enough. Shutdown changes the world for every sleeper; any worker left in wait() would sleep forever.
