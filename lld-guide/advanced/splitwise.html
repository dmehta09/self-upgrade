Case study: Splitwise.

A group goes to dinner, shares a cab, books an Airbnb — and now nobody can remember who owes whom. We'll build the engine: expenses that can be split equally, by exact amounts, or by percentages behind one pluggable rule, plus a settlement step that nets everyone out and produces the fewest cash transfers. Strategy for the split, a greedy graph algorithm for the payback.

01  Step 1 — Requirements & assumptions

A user adds an expense: who paid, how much, who shares it, and crucially how it's split — equally, by exact amounts, or by percentages. The system tracks each person's net balance (up or down), and can produce a minimal list of "X pays Y $Z" settlements that zeroes everyone out.

Clarifying questions I'd ask: What split modes do we support — just equal, or exact and percentage too? Do exact/percent splits have to add up to the total (and what do we do if they don't)? One currency or many? Do we need groups, or one shared ledger? Is this concurrent — many people adding expenses at once?

My stated assumptions

Amounts are plain floats rounded to cents (a real system would use integer cents or Decimal to avoid float drift — I'll note that). Everything is in-memory, single currency, and single-threaded for the demo. The split rule is the part that varies, so it goes behind one interface; settlement is a separate, pure computation over the net balances.

✅

Functional (in scope)

Add an expense with a payer, amount, participants and a split rule · split equally, by exact amounts, or by percentage · track each person's running net balance · produce a minimal "who pays whom" settlement list.

📐

Non-functional notes

Adding a new split rule must not touch the ledger — design for extension. Settlement is a pure function of the balances, easy to test. Money math stays at cent precision; thread-safety is a noted extension.

02  Step 2 — Entities

The noun–verb pass: "a person pays an expense, which a split rule divides into shares, and the ledger tracks each person's net so it can produce settlements." Each varying piece becomes its own object.

SplitStrategy
interface. One job: shares(amount, participants, **kw) -> dict — turn an amount into a {person: share} mapping. The **kw lets each rule accept its own extras (exact amounts, percentages).
EqualSplit / ExactSplit / PercentSplit
The concrete rules. EqualSplit divides evenly; ExactSplit takes the caller's per-person amounts verbatim; PercentSplit applies percentages. Interchangeable — each just implements shares().
Ledger
The coordinator. Holds each person's net balance; add_expense(...) applies a split and updates balances; settlements() computes the minimal repayment list. It depends on the interface, never a concrete rule.
Splitting the dinner bill analogy

Three of you finish dinner. Equal split: "just divide it three ways." Exact split: "I only had the salad — I owe $8, you two split the rest." Percent split: "I'll cover 50% since it was my idea." Same bill, three different rules for carving it up — which is exactly why the rule belongs behind one swappable interface rather than baked into the ledger.

03  Step 3 — The split Strategy

The way an expense is divided is the part of the brief that varies: equal today, exact amounts tomorrow, percentages next week, maybe shares-by-weight after that. Baking those into the ledger with a chain of if mode == "equal" … elif mode == "exact" … means editing the ledger every single time a new rule appears. Instead we make the split a pluggable Strategy: one interface, shares(amount, participants, **kw), and a family of interchangeable implementations. The ledger is then closed to modification but open to extension (Open/Closed).

splits.py
from typing import Protocol

class SplitStrategy(Protocol):
    def shares(self, amount, participants, **kw) -> dict: ...

class EqualSplit:
    def shares(self, amount, participants, **kw):
        each = round(amount / len(participants), 2)
        return {p: each for p in participants}

class ExactSplit:
    def shares(self, amount, participants, *, amounts):
        return dict(zip(participants, amounts))          # caller gives each share

class PercentSplit:
    def shares(self, amount, participants, *, percents):
        return {p: round(amount * pct / 100, 2)
                for p, pct in zip(participants, percents)}

Each rule has the same shape — take an amount and participants, hand back a {person: share} dict — so the ledger can call any of them without knowing which it holds. Using a Protocol (structural typing) means a new rule doesn't even need to inherit anything: define a class with a shares() method and it already is a SplitStrategy. See Behavioral patterns for Strategy in depth.

04  Step 4 — Net balances & debt simplification

The naive model stores every pairwise IOU: "Alice owes Bob $30, Bob owes Carol $20, Carol owes Alice $15…" That explodes — n people can have up to n² edges, and it's full of cancellable cycles. The insight: don't store who-owes-whom at all — store each person's single NET balance (everything they paid minus everything they owe). A positive net means the group owes them; a negative net means they owe the group. Those two pools are all settlement needs.

To settle, run a greedy min-cash-flow: repeatedly match the biggest creditor with the biggest debtor, transfer the smaller of the two amounts, and drop whoever hits zero. Each transfer zeroes out at least one person, so you never make more transfers than there are non-zero people — a small, practical list. (The true minimum number of transfers is NP-hard in general; greedy is the standard, expected interview answer and is excellent in practice.)

ledger.py
from collections import defaultdict

class Ledger:
    def __init__(self):
        self.net = defaultdict(float)        # person -> net (owed if +, owes if -)

    def add_expense(self, paid_by, amount, participants, strategy, **kw):
        owed = strategy.shares(amount, participants, **kw)
        for person, share in owed.items():
            self.net[person] -= share        # each participant owes their share
        self.net[paid_by] += amount          # the payer fronted the whole bill

    def settlements(self):
        # greedy min-cash-flow: biggest debtor pays biggest creditor
        debtors = [[p, -v] for p, v in self.net.items() if v < 0]
        creditors = [[p, v] for p, v in self.net.items() if v > 0]
        debtors.sort(key=lambda x: -x[1])
        creditors.sort(key=lambda x: -x[1])
        result, i, j = [], 0, 0
        while i < len(debtors) and j < len(creditors):
            pay = round(min(debtors[i][1], creditors[j][1]), 2)
            result.append((debtors[i][0], creditors[j][0], pay))
            debtors[i][1] -= pay
            creditors[j][1] -= pay
            if debtors[i][1] <= 1e-9:
                i += 1
            if creditors[j][1] <= 1e-9:
                j += 1
        return result
The netting insight

add_expense never records "A owes B." It only nudges two running totals: every participant's net drops by their share, and the payer's net rises by the whole bill. After any number of expenses, a person's net is the only number that matters — the sum of all their debts is exactly equal and opposite to the sum of all credits, so settlement just drains one pool into the other. The 1e-9 comparison is a float-epsilon guard so a balance that's effectively zero (but reads as 0.0000001) is treated as settled.

05  Walk a scenario

Three friends, two expenses, both split three ways. Alice fronts a $90 dinner; Bob fronts a $60 cab. Each owes $30 of the dinner and $20 of the cab — $50 each — while Alice paid $90 and Bob paid $60. Net it out: Alice is up $40, Bob is up $10, Carol (who paid nothing) is down $50.

demo.py
ledger = Ledger()
# Alice pays $90 dinner, split equally 3 ways
ledger.add_expense("Alice", 90, ["Alice", "Bob", "Carol"], EqualSplit())
# Bob pays $60 cab, split equally 3 ways
ledger.add_expense("Bob", 60, ["Alice", "Bob", "Carol"], EqualSplit())

for debtor, creditor, amt in ledger.settlements():
    print(f"{debtor} pays {creditor} ${amt:.2f}")
OutputCarol pays Alice $40.00 Carol pays Bob $10.00

Carol — the only debtor — clears her $50 in two transfers: $40 to the biggest creditor (Alice) first, then the remaining $10 to Bob. Two transfers, everyone at zero. The greedy match is exactly what you'd do by hand: pay the person you owe most, first.

Why store each person's single NET balance instead of every pairwise debt?

Right: pairwise IOUs blow up to O(n²) edges full of cancellable cycles. One net number per person collapses all of that — settlement just drains the debtor pool into the creditor pool, and that's what makes a minimal "who pays whom" list possible.

What pattern lets equal, exact, and percentage splits coexist without an if ladder?

Right: each rule is its own object behind a common shares() interface, so the ledger calls whichever it's handed without branching. Adding WeightedSplit is a new class, never an edit to the ledger — Open/Closed via Strategy.

06  Extensions — your turn

A strong answer ends by showing where the design grows. Each of these is a small, additive change — the payoff of keeping the split rule and the settlement maths cleanly separated. Try them before peeking.

Exercise 1 · groups & validated percentages

Add Groups, each owning its own Ledger (a household ledger, a trip ledger), so balances don't leak across unrelated circles. Or: make PercentSplit reject input where the percentages don't sum to 100. Where does each change live — and what stays untouched?

Hint: a group is just a named owner of a Ledger — the ledger and the strategies don't change at all. Validation belongs inside PercentSplit.shares, before it builds the dict — the ledger never needs to know.

Show a solution solution

A Group wraps a ledger; PercentSplit guards its own input. Both are additive — the existing ledger and other strategies are untouched:

groups.py
from dataclasses import dataclass, field

@dataclass
class Group:
    name: str
    members: list
    ledger: Ledger = field(default_factory=Ledger)   # one ledger per group

# validated percentages — guard inside the strategy
class PercentSplit:
    def shares(self, amount, participants, *, percents):
        if round(sum(percents), 2) != 100:
            raise ValueError(f"percents must sum to 100, got {sum(percents)}")
        return {p: round(amount * pct / 100, 2)
                for p, pct in zip(participants, percents)}

Per-group ledgers keep a trip's balances apart from a flatshare's. And because validation lives in the strategy, every ledger that uses PercentSplit gets the check for free — Single Responsibility paying off.

Exercise 2 · fair rounding

Split $10 three ways and round(10/3, 2) gives $3.33 each — but 3 × $3.33 = $9.99, a penny short. Where does the leftover cent go, and how do you hand it out fairly instead of silently losing it?

Hint: compute the rounded shares, sum them, and the difference from the total is the remainder. Give that leftover cent to one participant (commonly the payer) so the shares add back to exactly the bill.

Show a solution solution

Round everyone down to cents, then drop the residual cent on one payer so the shares reconcile to the total exactly:

rounding.py
class EqualSplit:
    def shares(self, amount, participants, *, remainder_to=None, **kw):
        each = round(amount / len(participants), 2)
        owed = {p: each for p in participants}
        residual = round(amount - each * len(participants), 2)  # the lost cent(s)
        if residual:
            taker = remainder_to or participants[0]   # one payer absorbs it
            owed[taker] = round(owed[taker] + residual, 2)
        return owed

Now the shares always sum to the exact bill — no quietly vanishing pennies. (In a money-serious system you'd skip floats entirely and work in integer cents or Decimal, which sidesteps the drift at the source.)

What this design used — the toolkit recap

Strategy pattern for the split rule — equal, exact, percent (and any future rule) behind one shares() interface, giving us the Open/Closed Principle: new rules are new classes, never edits to the ledger. A greedy graph / settlement algorithm (min-cash-flow) over the balances, with the honest caveat that the true minimum is NP-hard. Net-balance modelling — one number per person collapses O(n²) IOUs into two pools. And Single Responsibility: strategies divide, the ledger tracks and settles, nobody does both. If many people add expenses at once, add_expense mutates shared balances, so you'd guard it with a single threading.Lock (see the concurrency primer) — coarse and correct first, shard only if profiling demands it.
