Case study: an LRU cache in O(1).

One of the most-asked design questions there is. The twist: it's not a pattern, it's a structure — a HashMap and a doubly linked list, designed together so every get and put is constant time. Build that, then meet its trickier sibling (LFU) and make it thread-safe.

01  Step 1 — Requirements & assumptions

A cache holds a bounded number of key→value entries. When it's full and a new key arrives, something must be thrown out. LRU — Least Recently Used — evicts whatever hasn't been touched for the longest.

Clarifying questions I'd ask: What capacity? What counts as a "use" — both reads and writes? What should get return on a miss? Do we need it thread-safe? Is LRU the right policy, or LFU (least frequently used)?

The hard requirement: O(1)

Both get(key) and put(key, value) must run in constant time, capacity included. That single line rules out the obvious designs and forces the HashMap-plus-linked-list combo. A miss returns None; every get and put counts as a use.

02  Step 2 — Why two structures, not one

Try the naive designs and watch them fail the O(1) bar:

Ideagetfind & evict LRU
A plain dictO(1) ✓O(n) — must scan for the oldest ✗
A list ordered by recencyO(n) — must search ✗O(1) at the end ✓
HashMap + doubly linked listO(1) ✓O(1) ✓

Neither structure alone wins. So we use both, pointing at the same nodes:

HashMap (dict)
Maps key → Node. Gives O(1) "is this key here, and where's its node?"
Doubly linked list
Holds the nodes in recency order: most-recent at the front, least-recent at the back. Doubly linked so we can unlink any node in O(1) (we have its prev and next).
Node
Stores key, value, and the two list pointers. (It holds the key too, so that on eviction we can delete it from the map.)
A stack of plates with an index analogy

The linked list is a stack of plates — touch a plate and it goes back on top; the bottom plate is the one to toss. The HashMap is a sticky-note index telling you exactly which plate is "B" so you don't dig through the stack. Index to find, stack to order.

04  Step 4 — The implementation

Two tiny list helpers — _remove and _push_front — do all the pointer work; get and put are then just "unlink, move to front, maybe evict."

lru.py
class Node:
    __slots__ = ("key", "value", "prev", "next")
    def __init__(self, key=None, value=None):
        self.key = key
        self.value = value
        self.prev = None
        self.next = None

class LRUCache:
    def __init__(self, capacity: int):
        self.capacity = capacity
        self._map: dict = {}                  # key -> Node  (O(1) lookup)
        self._head = Node()                   # sentinels: head.next = MRU,
        self._tail = Node()                   #            tail.prev = LRU
        self._head.next = self._tail
        self._tail.prev = self._head

    def _remove(self, node: Node) -> None:    # unlink in O(1)
        node.prev.next = node.next
        node.next.prev = node.prev

    def _push_front(self, node: Node) -> None:  # link just after head (MRU)
        node.prev = self._head
        node.next = self._head.next
        self._head.next.prev = node
        self._head.next = node

    def get(self, key):
        node = self._map.get(key)
        if node is None:
            return None
        self._remove(node)                    # touched -> becomes most-recent
        self._push_front(node)
        return node.value

    def put(self, key, value) -> None:
        node = self._map.get(key)
        if node is not None:                  # update + promote
            node.value = value
            self._remove(node)
            self._push_front(node)
            return
        if len(self._map) >= self.capacity:   # full -> evict the LRU (tail.prev)
            lru = self._tail.prev
            self._remove(lru)
            del self._map[lru.key]            # this is why a node stores its key
        node = Node(key, value)
        self._map[key] = node
        self._push_front(node)
Why a node stores its own key

On eviction we have the node (it's tail.prev), but we must also delete it from the map — and the map is keyed by key. Without node.key we'd have no way to find the map entry in O(1). Small detail, classic interview "gotcha."

05  Walk a scenario

Capacity 2. Watch "a" survive because we used it, while "b" — untouched — gets evicted when "c" arrives.

demo.py
cache = LRUCache(capacity=2)
cache.put("a", 1)              # [a]
cache.put("b", 2)              # [b, a]   (b most-recent)
print(cache.get("a"))          # 1   -> [a, b]   (a promoted, b now LRU)
cache.put("c", 3)              # full: evict b -> [c, a]
print(cache.get("b"))          # None  (b was evicted)
print(cache.get("c"))          # 3
Output1 None 3

Why must the list be doubly linked rather than singly linked?

Right: on a get we yank a node out of the middle and move it to the front. To splice it out we must fix the node before it — which a singly linked list can't reach in O(1). The back-pointer is what keeps everything constant time.

In this design, is get a read-only operation?

Right: a successful get moves the node to the front. That's a write to the structure — which is exactly why making this thread-safe (below) means locking get too, not just put.
The 12-line Pythonic version with OrderedDict go deeper

In real code you'd rarely hand-roll the list. collections.OrderedDict already is a hash map with order, plus O(1) move_to_end and popitem. (And for pure function memoisation, functools.lru_cache does the whole thing.) Build it by hand once — for the interview — then reach for these:

lru_ordered.py
from collections import OrderedDict

class LRUCache:
    def __init__(self, capacity: int):
        self.capacity = capacity
        self._d: OrderedDict = OrderedDict()

    def get(self, key):
        if key not in self._d:
            return None
        self._d.move_to_end(key)          # mark most-recent
        return self._d[key]

    def put(self, key, value) -> None:
        if key in self._d:
            self._d.move_to_end(key)
        self._d[key] = value
        if len(self._d) > self.capacity:
            self._d.popitem(last=False)   # pop the least-recent (front)

Same O(1) behaviour, a fraction of the code. The hand-rolled version is still worth knowing — it's what OrderedDict is doing under the hood.

06  The LFU variant — evict by frequency

LFU evicts the least frequently used key; ties are broken by recency (oldest of the least-used goes). The trick for O(1): bucket keys by their use-count, and track the current min count so eviction is "pop the oldest key from the min bucket."

lfu.py
from collections import defaultdict, OrderedDict

class LFUCache:
    def __init__(self, capacity: int):
        self.capacity = capacity
        self._vals: dict = {}                          # key -> value
        self._freq: dict = {}                          # key -> use count
        self._buckets = defaultdict(OrderedDict)       # count -> keys (in LRU order)
        self._min = 0                                  # smallest live count

    def _bump(self, key) -> None:
        f = self._freq[key]
        del self._buckets[f][key]                      # leave the old bucket
        if not self._buckets[f]:                       # bucket emptied?
            del self._buckets[f]
            if self._min == f:
                self._min += 1                         # min moves up
        self._freq[key] = f + 1
        self._buckets[f + 1][key] = None               # join the next bucket

    def get(self, key):
        if key not in self._vals:
            return None
        self._bump(key)
        return self._vals[key]

    def put(self, key, value) -> None:
        if self.capacity == 0:
            return
        if key in self._vals:                          # update + bump
            self._vals[key] = value
            self._bump(key)
            return
        if len(self._vals) >= self.capacity:           # evict least-freq, oldest
            evict_key, _ = self._buckets[self._min].popitem(last=False)
            del self._vals[evict_key]
            del self._freq[evict_key]
        self._vals[key] = value                        # new keys start at freq 1
        self._freq[key] = 1
        self._buckets[1][key] = None
        self._min = 1
The two things people get wrong

① A brand-new key has frequency 1, so after an eviction you must reset self._min = 1. ② Use an ordered bucket (here OrderedDict) so that within the same frequency you can still evict the least-recently-used — LFU's tie-breaker is LRU.

07  Making it thread-safe

Share one cache across threads and both get and put become dangerous — remember, get rewires the list, so it's a writer too. Two threads interleaving those pointer updates can corrupt the list outright. Guard every public operation with a single lock (see the concurrency primer).

Scrub the lost-update shape (read → modify → write on shared structure) that mirrors an unlocked list splice:

safe_lru.py
import threading

class ThreadSafeLRU(LRUCache):
    def __init__(self, capacity: int):
        super().__init__(capacity)
        self._lock = threading.Lock()

    def get(self, key):
        with self._lock:                  # get() mutates the list -> must lock
            return super().get(key)

    def put(self, key, value) -> None:
        with self._lock:
            super().put(key, value)
One coarse lock is the right first answer

Each operation is a handful of pointer swaps — microseconds — so a single lock around the whole cache is simple and plenty fast. Only if profiling shows lock contention would you reach for sharding (many small caches keyed by hash(key) % N, each with its own lock) to spread the traffic. Don't pre-optimise; say that out loud in an interview.

08  Extensions — your turn

Exercise 1 · TTL expiry

Add a per-entry time-to-live: a key older than ttl seconds is treated as a miss (and dropped). What does each node need, and where do you check it?

Hint: store an expires_at on the node (pass the "now" in to stay deterministic). Check it at the top of get — an expired hit becomes a miss, and you unlink + delete it.

Show a solution solution
ttl.py
# node gains: self.expires_at = now + ttl   (set in put)
def get(self, key, now: float):
    node = self._map.get(key)
    if node is None:
        return None
    if now >= node.expires_at:            # expired -> treat as a miss
        self._remove(node)
        del self._map[key]
        return None
    self._remove(node); self._push_front(node)
    return node.value

Recency eviction and TTL expiry are independent policies that compose cleanly: one keeps the cache small, the other keeps it fresh.

Exercise 2 · the trade-off question

An interviewer asks: "When would LFU beat LRU, and when would it lose?" Give a one-sentence answer for each.

Show a solution solution

LFU wins when popularity is stable — a few hot keys hit constantly should never be evicted just because of a recent quiet spell. LFU loses when access patterns shift: an old key with a huge historical count clings on long after it stopped being used (the "cache pollution" problem), while LRU adapts immediately. Many real caches use a hybrid (e.g. LFU with aging, or LRU-K).

What this design used — the toolkit recap

Custom data structure — a HashMap and a doubly linked list co-designed for O(1). Sentinels to erase edge-cases. Encapsulation — _remove/_push_front hide the pointer surgery. Inheritance for the thread-safe wrapper, and a single Lock for the critical sections. And the senior move: knowing the stdlib (OrderedDict, functools.lru_cache) does this for you in production.
