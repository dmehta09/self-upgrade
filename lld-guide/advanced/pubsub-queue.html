Advanced case · async Observer

Case study: a pub/sub message queue.

A publisher should be able to shout "order placed!" without knowing — or waiting for — anyone who's listening. We'll decouple publishers from subscribers and deliver asynchronously, so one slow subscriber can't stall the publisher or its peers. It's the notification service's Observer, grown up: each listener gets its own thread-safe queue and a worker thread to drain it.

01  Step 1 — Requirements & assumptions

Publishers send messages to a named topic. Any number of subscribers can register on that topic, and every one of them receives every message. The catch that makes this advanced: delivery is asynchronous — publishing returns immediately, and a slow subscriber never blocks the publisher or the other subscribers.

Clarifying questions I'd ask: Do messages need to arrive in order per subscriber? Is delivery at-least-once, at-most-once, or best-effort? Do we need persistence (survive a crash) or is in-memory fine? How many subscribers, and how fast do they consume? Should a subscriber that joins late see old messages?

Assumptions I'll lock in

In-process (one Python program, not a network broker like Kafka). In-memory (no persistence — a crash loses undelivered messages). Best-effort delivery (we don't track acks or retries yet). Threads, not processes — we lean on shared memory and a thread-safe queue, which is exactly where the GIL caveats from the concurrency primer matter.

In scope

  • Named topics with many subscribers
  • Async fan-out (publish returns instantly)
  • Per-subscriber ordering (FIFO)
  • One slow subscriber can't stall peers

Out of scope (for now)

  • Persistence / durability across crashes
  • Acks, retries, exactly-once delivery
  • Cross-process / network distribution
  • Replay of history for late joiners

02  Step 2 — From Observer to async pub/sub

The notification service taught the Observer pattern: a subject keeps a list of observers and calls each one when something happens. The simplest version is synchronous — the publisher loops over subscribers and calls each handler directly:

Synchronous Observer
for sub in subscribers: sub.handle(message) — the publisher does the work, in its own thread, one subscriber at a time.
The failure
If one handler is slow (a 2-second HTTP call) or throws, everyone behind it waits — or the loop dies and later subscribers never get the message. The publisher is held hostage by its slowest, flakiest listener.

The fix is to decouple delivery from handling. Give each subscriber its own queue and a dedicated worker thread. Publishing now just drops a copy of the message into each subscriber's queue and returns — fan-out is a few non-blocking put calls. Each worker drains its own queue at its own pace:

Per-subscriber queue
A thread-safe queue.Queue buffers messages for that one subscriber. Publishing is queue.put(message) — it returns immediately and never blocks the publisher.
Per-subscriber worker
A background thread loops on queue.get() (which blocks until a message arrives) and calls the handler. A slow handler only backs up its own queue — the publisher and other subscribers are untouched.
The office mailroom analogy

The publisher is a mail carrier with a stack of identical letters. Instead of waiting at each desk for the person to read their letter, the carrier just drops one copy into each person's pigeonhole and walks off. Each person checks their own pigeonhole and reads at their own pace — the slowpoke who lets letters pile up doesn't hold up the carrier or anyone else. The pigeonhole is the queue; the person reading is the worker thread.

The publisher hands the message to the Topic, which drops a copy into each subscriber's own queue. Every subscriber owns a separate queue.Queue and a separate worker thread, so the emailer and analytics consume independently — a stall in one never reaches the other.

04  Step 4 — The implementation

Two small classes. Subscriber owns the queue + worker and exposes a non-blocking deliver; Topic keeps the subscriber list (guarded by a lock) and fans a message out to each one.

subscriber.py
import threading
import queue

class Subscriber:
    def __init__(self, name, handler):
        self.name = name
        self.handler = handler                  # callable(name, message)
        self.inbox = queue.Queue()              # thread-safe per-subscriber buffer
        self._thread = threading.Thread(target=self._run, daemon=True)
        self._thread.start()

    def deliver(self, message):
        self.inbox.put(message)                 # returns immediately, never blocks

    def _run(self):
        while True:
            message = self.inbox.get()          # blocks until a message arrives
            self.handler(self.name, message)
            self.inbox.task_done()
topic.py
import threading

class Topic:
    def __init__(self, name):
        self.name = name
        self.subscribers = []
        self._lock = threading.Lock()

    def subscribe(self, sub):
        with self._lock:
            self.subscribers.append(sub)

    def publish(self, message):
        with self._lock:
            subs = list(self.subscribers)       # snapshot under the lock
        for sub in subs:                        # fan out OUTSIDE the lock
            sub.deliver(message)
Why snapshot the list, then fan out outside the lock

publish copies the subscriber list under the lock, then releases it before calling deliver. We hold the lock only for the tiny, shared-state read — keeping the critical section small, exactly as the primer urges. We must guard the list because subscribe can append from another thread mid-publish; iterating a list while it mutates is undefined. And since deliver is just a non-blocking put, doing it outside the lock costs nothing and avoids holding the lock during the (potentially many) fan-out calls.

05  Walk a scenario

Two subscribers on the "orders" topic. We publish two messages; each subscriber's worker drains its own inbox and records what it got. Because the workers run on separate threads, the natural arrival order of lines varies run-to-run — so the demo sorts the collected lines before printing, making the output deterministic to read.

demo.py
import time

received = []
def handle(name, msg):
    received.append(f"{name} got: {msg}")       # list.append is atomic in CPython

topic = Topic("orders")
topic.subscribe(Subscriber("emailer", handle))
topic.subscribe(Subscriber("analytics", handle))

topic.publish("order #42 placed")
topic.publish("order #43 placed")

time.sleep(0.1)                                  # let the workers drain their inboxes
for line in sorted(received):                    # sort so the demo is deterministic
    print(line)
Outputanalytics got: order #42 placed analytics got: order #43 placed emailer got: order #42 placed emailer got: order #43 placed

Both subscribers received both messages, in order, and publish returned the instant it had dropped each message into the two inboxes — it never waited for a handler to run.

Why give each subscriber its own queue and worker thread instead of the publisher calling each subscriber directly?

Right: the per-subscriber queue absorbs the message instantly and the worker handles it independently. A subscriber that takes two seconds (or throws) only backs up its own inbox — the publisher returns at once and the other subscribers keep flowing.

How does pub/sub differ from a plain method call to each listener?

Right: with a direct call the publisher holds a reference to each listener and blocks until it returns. With pub/sub the publisher only knows the topic; the topic owns the subscriber list and fan-out, and delivery happens asynchronously through each subscriber's queue. That indirection is what lets you add or remove subscribers without touching the publisher.

06  Extensions — your turn

Exercise 1 · a dead-letter queue

Right now, if a handler raises an exception, the worker's _run loop dies and that subscriber silently stops receiving messages. Add a dead-letter queue (DLQ): if handler(...) throws, route the message to a DLQ instead of crashing the worker. Where do you wrap it?

Hint: wrap the handler(...) call in a try/except inside _run, so the loop keeps running. On failure, push the message (and maybe the error) onto a separate self.dlq queue for later inspection or retry.

Show a solution solution
subscriber_dlq.py
# in __init__:  self.dlq = queue.Queue()

def _run(self):
    while True:
        message = self.inbox.get()
        try:
            self.handler(self.name, message)
        except Exception as exc:              # one bad message can't kill the worker
            self.dlq.put((message, exc))      # park it for inspection / retry
        finally:
            self.inbox.task_done()

The try/except turns a fatal crash into a logged, recoverable event: the worker survives, this subscriber keeps consuming, and the poison message sits in the DLQ where you can inspect it. The finally ensures task_done always fires so a join on the inbox can't hang.

Exercise 2 · backpressure with a bounded queue

An unbounded inbox can grow without limit if a subscriber falls permanently behind — eventually you run out of memory. Bound it with queue.Queue(maxsize=...). What does put do when the queue is full, and how does that change publish?

Show a solution solution

Construct the inbox as queue.Queue(maxsize=1000). Now a plain put(message) blocks when the queue is full — it waits until a worker pulls something off. That's backpressure: a slow subscriber slows the publisher down (for that one deliver) rather than letting memory grow unbounded. That re-couples them, though, so you choose per call:

put(msg)  (block)
Wait for room. Lossless, but a stuck subscriber can now stall the publisher — backpressure all the way up.
put_nowait(msg)
Raise queue.Full immediately. Lets you drop the message (or DLQ it) and keep the publisher fast — choosing availability over completeness.

For at-least-once delivery you'd go the other way: keep the message until the subscriber acks it (calls task_done after a successful handle), and re-deliver on timeout. Bounded queue versus acks is the classic availability-vs-durability trade-off — name it out loud in the interview.

What this design used — the toolkit recap

Observer / pub-sub decoupling — the publisher knows only the topic, never the subscribers, so listeners come and go freely. Async fan-out turns a synchronous Observer into a non-blocking one. Thread-safe queue.Queue hands messages between threads with no locks of your own — one buffer per subscriber. A worker thread per subscriber drains each queue independently, so a slow consumer is isolated. Daemon threads let the program exit without waiting on the workers. And the senior move: snapshot shared state under a tiny lock, then do the slow work outside it.
