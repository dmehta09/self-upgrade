Async Python, properly.

The primer covered threads and locks. Modern interviews increasingly probe the other model: asyncio — one thread, thousands of concurrent I/O waits, no locks for most of it. This lesson is the decision table, the mental model, and the one worked example (producer–consumer) that machine-coding rounds keep asking for.

01  Threads, asyncio, processes — the decision table

The first interview question is never "write a coroutine"; it's "why would you choose async here?" The answer hangs entirely on what your code spends its time doing:

WorkloadReach forWhy
I/O-bound, few concurrent ops (a handful of requests, a DB call)threading / a thread poolSimplest mental model; blocking libraries just work; the GIL releases during I/O anyway.
I/O-bound, many concurrent ops (10K sockets, scrapers, chat servers, LLM-API fan-out)asyncioThreads cost ~MBs of stack each and context-switch via the OS; coroutines cost ~KBs and switch in user space — and only at await.
CPU-bound (hashing, parsing, ML preprocessing)multiprocessing / ProcessPoolExecutorThe GIL serialises Python bytecode in one process — threads and asyncio both stall. Separate processes get separate GILs.
Sequential anywaynothingConcurrency you don't need is bugs you don't need.
asyncio does not make code faster

It makes waiting cheaper. A single CPU-bound loop runs at identical speed under asyncio — worse, it freezes every other coroutine while it runs (see pitfalls). If the profiler says CPU, the answer is processes, never async def.

02  The event-loop mental model

A coroutine (async def) is a function that can pause itself. Every await is a marked pause point: "I'm waiting on something — loop, run somebody else." The event loop keeps a ready-list and a watch-list (timers, sockets); it runs one coroutine until it awaits, then picks the next ready one. That's cooperative scheduling — nothing is ever interrupted mid-statement, which is why most async code needs no locks.

Two consequences worth saying in an interview: between awaits your code is effectively atomic (no other coroutine can run), so the lost-update races of the threads world mostly vanish; and a coroutine that never awaits starves everyone — cooperative means the cooperation is mandatory.

Under asyncio, when can the "current task" change?

Right: that visibility is the superpower. check_then_act with no await in between needs no lock under asyncio — but add one await inside the critical section and the race comes straight back (then you reach for asyncio.Lock).

03  The toolbox: gather, executor, timeout, cancel

toolbox.py
import asyncio

async def main():
    # 1 · fan out and wait for all (order of results = order of args)
    user, orders = await asyncio.gather(fetch_user(), fetch_orders())

    # 2 · a blocking/CPU call inside async code: push it OFF the loop
    loop = asyncio.get_running_loop()
    report = await loop.run_in_executor(None, build_report_cpu, orders)

    # 3 · deadline: cancel anything slower than 2s
    try:
        async with asyncio.timeout(2.0):          # Python 3.11+
            fresh = await fetch_prices()
    except TimeoutError:
        fresh = cached_prices()                   # graceful fallback

    # 4 · explicit cancellation
    task = asyncio.create_task(poll_forever())
    ...
    task.cancel()                                 # raises CancelledError
    try:                                          #   INSIDE the task at
        await task                                #   its next await
    except asyncio.CancelledError:
        pass                                      # cleanup ran in finally

asyncio.run(main())

The interview-grade details: gather with return_exceptions=True keeps one failure from cancelling its siblings; run_in_executor is the official bridge to blocking libraries (and with a ProcessPoolExecutor, to CPU work); and cancellation is cooperative too — CancelledError is raised at the task's next await, so finally: blocks are how async code releases resources on the way out.

04  The worked staple: producer–consumer with backpressure

The single most-asked async machine-coding exercise: N producers feed work, M workers drain it, and the queue must apply backpressure — producers slow down when consumers can't keep up. asyncio.Queue(maxsize=…) gives you all of it:

pipeline.py
import asyncio

async def producer(q: asyncio.Queue, urls: list[str]) -> None:
    for url in urls:
        await q.put(url)        # BLOCKS (yields) when the queue is full
    # signal completion: one sentinel per worker
    for _ in range(NUM_WORKERS):
        await q.put(None)

async def worker(name: str, q: asyncio.Queue, results: list) -> None:
    while True:
        url = await q.get()     # yields until an item is available
        if url is None:         # sentinel -> this worker is done
            q.task_done()
            return
        try:
            results.append(await fetch(url))
        finally:
            q.task_done()       # ALWAYS — even if fetch raised

NUM_WORKERS = 5

async def main(urls: list[str]) -> list:
    q: asyncio.Queue = asyncio.Queue(maxsize=20)   # the backpressure knob
    results: list = []
    workers = [asyncio.create_task(worker(f"w{i}", q, results))
               for i in range(NUM_WORKERS)]
    await producer(q, urls)
    await q.join()              # every put() matched by a task_done()
    await asyncio.gather(*workers)
    return results

The three lines that score points: maxsize=20 (without it the producer happily queues a million items and you discover memory limits in production), the sentinel-per-worker shutdown (cleaner than cancelling mid-item), and task_done() in a finally (or q.join() deadlocks on the first exception). Note what's absent: no locks — asyncio.Queue is the coordination.

What does Queue(maxsize=20) actually buy the design?

Right: unbounded queues turn "consumers are slow" into "the process OOMs an hour later." Bounding the queue moves the slowdown to the source, where it's visible and survivable. Say the word backpressure — interviewers listen for it.

05  The pitfalls that fail interviews

Blocking the loop
time.sleep(), requests.get(), heavy CPU inside a coroutine freezes every task. Fixes: await asyncio.sleep(), an async client (aiohttp/httpx), or run_in_executor.
Fire-and-forget tasks
asyncio.create_task(f()) without keeping the reference: the task can be garbage-collected mid-flight and its exceptions vanish silently. Hold references (or use 3.11+ asyncio.TaskGroup, which also cancels siblings on failure — say it, it's current).
The wrong Lock
threading.Lock in async code blocks the whole loop; asyncio.Lock in threaded code isn't thread-safe. The two worlds have parallel toolkits — never mix them.
Async where nothing awaits
An async def with zero awaits is a plain function with extra ceremony and a misleading signature. Concurrency is a requirement, not a default.

06  Where this shows up in design rounds

Async is rarely the question; it's the sharp answer to a follow-up inside another design:

  • Notification service — "10K subscribers, email takes 800ms each?" → fan out with a bounded worker pool exactly like §4; channels become async def send().
  • Rate limiter — the refill "thread" becomes a single looping task; with switches only at await, the bucket needs no lock at all in the async version.
  • Task scheduler — the worker pool + Condition machinery maps to coroutines + asyncio.Queue; compare the two in that lesson.
  • Ride-hailing — pinging N nearby drivers concurrently with a 2s asyncio.timeout is the textbook gather-with-deadline.

The senior framing to close with: threads when a blocking library forces your hand, asyncio when concurrency is wide and I/O-shaped, processes when the CPU is the bottleneck — and the decision said out loud before any code.
