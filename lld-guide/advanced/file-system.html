Case study: an in-memory file system.

A file system is a tree: directories hold files, and directories hold other directories. The quiet insight is that a directory is itself a "file-like" thing — it has a name, a parent, a size, a path — so one interface can describe both. Build that single interface and the leaves and branches stop needing special cases: that's the Composite pattern.

01  Step 1 — Requirements & assumptions

We're modelling a file system in memory — no disk, no syscalls. It must hold files and directories, let directories nest arbitrarily, list a directory's contents (ls), report a total size (a directory's size is the sum of everything inside it, recursively), and give any entry its absolute path from the root.

Clarifying questions I'd ask: Files and directories, or also symlinks and hard links? Is a file's size just its content length, or do we count metadata? Are names unique within a directory? Should size on a directory recurse all the way down? Single-threaded, or shared across threads?

My stated assumptions

Two kinds of entry — files and directories — forming a single tree under one root named "/". A file's size is len(content); a directory's size is the recursive sum of its children. Names are unique within a directory (so children live in a dict keyed by name). No symlinks, no permissions. Single-threaded for the demo; a lock for sharing is noted as an extension.

✅

In scope

Create files and directories · nest directories arbitrarily · ls a directory's names · total size that recurses through subdirectories · absolute path for any entry from the root.

🚫

Out of scope

Real disk I/O, blocks and inodes, permissions and ownership, symlinks and hard links, timestamps, and concurrent access (a single lock is sketched as an extension, not built in).

02  Step 2 — Entities

The noun pass is short, because the whole trick is that there are really only two concrete things — a file and a directory — sharing one abstract idea of an "entry." Give each entry a name and a parent, and make size() and path() the operations every entry must answer.

Entry
abstract component. The shared idea: every entry has a name and a parent, and must define size() and path(). Client code only ever talks to an Entry — it never asks "are you a file or a directory?"
File
leaf. Holds content and nothing else underneath it. Its size() is simply len(content). A leaf has no children, so the recursion stops here.
Directory
composite. Holds a collection of child entries (a dict name → Entry). Its size() recurses: it sums size() over its children — each of which may itself be a file or another directory.
A cardboard box analogy

A box can hold books, or it can hold more boxes — which themselves hold books or yet more boxes. When you want the total weight, you don't care which: you put the whole thing on the scale and it just works, the nested boxes adding their contents into the total. A File is a book; a Directory is a box; size() is the scale. One way to weigh everything, whether it's a leaf or a branch — that's Composite.

03  Step 3 — The Composite shape

Both concrete classes are an Entry (interface realization — the hollow triangle), and a Directory is built out of more Entry objects (composition — the filled diamond). That second relationship is the recursive one: a directory contains entries, and a directory is an entry, so directories nest without limit. Read the connectors against the UML legend.

Hollow triangle = File and Directory both realize the abstract Entry interface, so callers treat them identically. One uniform interface over a recursive whole: that is the Composite pattern.

04  Step 4 — The implementation

Entry defines the shared shape and a single concrete helper — path() walks parent pointers up to the root and joins the names. File answers size() directly; Directory answers it by recursing over its children. Notice neither class ever type-checks the other.

filesystem.py
from __future__ import annotations

class Entry:                              # the shared component
    def __init__(self, name):
        self.name = name
        self.parent = None               # set when added to a directory

    def size(self):
        raise NotImplementedError

    def path(self):
        parts = []
        node = self
        while node is not None:
            parts.append(node.name)
            node = node.parent
        parts.reverse()                  # root .. self
        inner = "/".join(p for p in parts if p != "/")
        return "/" + inner               # always absolute, from "/"

class File(Entry):                       # leaf
    def __init__(self, name, content=""):
        super().__init__(name)
        self.content = content
    def size(self):
        return len(self.content)

class Directory(Entry):                  # composite
    def __init__(self, name):
        super().__init__(name)
        self.children = {}               # name -> Entry
    def add(self, entry):
        entry.parent = self
        self.children[entry.name] = entry
        return entry                     # return it so calls can chain
    def size(self):                      # recurse: sum of everything inside
        return sum(child.size() for child in self.children.values())
    def ls(self):
        return sorted(self.children)
Why add() returns the entry

Returning the entry it just stored lets you write home = root.add(Directory("home")) and immediately keep building inside home. It's a small ergonomic touch that makes assembling a tree read top-down, the way the tree actually grows — and it's why the walkthrough below can chain so tidily.

05  Walk a scenario

Build a small tree: a notes.txt (11 bytes) under home, and an app.py (8 bytes) under home/projects. Then ask the root for its size — and watch the recursion pull the whole tree's bytes up into one number, 11 + 8 = 19.

demo.py
root = Directory("/")
home = root.add(Directory("home"))
home.add(File("notes.txt", "hello world"))      # 11 bytes
projects = home.add(Directory("projects"))
projects.add(File("app.py", "print(1)"))        # 8 bytes

print(root.size())                               # 19  (whole tree)
print(home.ls())                                 # ['notes.txt', 'projects']
print(projects.children["app.py"].path())        # /home/projects/app.py
Output19 ['notes.txt', 'projects'] /home/projects/app.py

One root.size() call fanned out through home, into projects, and reached both files — no caller ever wrote a loop or a type check. ls lists names alphabetically, and path() reconstructed the absolute path by walking parent pointers back to "/".

What makes this the Composite pattern?

Right: Composite is about the shared interface over a part-whole tree. Because a leaf and a branch both present the same Entry face, the client can treat a single file and an entire directory subtree the same way. Recursion and the dictionary are implementation details that fall out of that uniform interface.

Why does Directory.size() call size() on its children rather than checking their type?

Right: every child is an Entry, so child.size() is valid whatever it is. A File returns its byte count; a Directory recurses into its children. No isinstance ladder, no special cases — the polymorphism does the branching, and the tree unwinds itself.

06  Extensions — your turn

A clean Composite grows by adding one more operation that "just works" over the whole tree. Each of these is a small, additive method on Directory — the leaf and the interface stay untouched. Try them before peeking.

Exercise 1 · recursive find

Add a find(name) to Directory that searches the whole subtree and returns the first entry with that name (or None). It should look inside nested directories, not just the immediate children.

Hint: loop over the children. If a child's name matches, return it. Otherwise, if the child is itself a Directory, recurse into it — exactly the same move size() makes.

Show a solution solution
find.py
def find(self, name):                    # add to Directory
    for child in self.children.values():
        if child.name == name:
            return child
        if isinstance(child, Directory):
            hit = child.find(name)       # recurse into subdirectories
            if hit is not None:
                return hit
    return None

This is the one place the recursion legitimately asks "is this a Directory?" — because only a directory has a subtree to descend into. The leaf File needs no find at all; it simply can't match deeper, so the search skips past it. Same tree-walk skeleton as size(), returning the first hit instead of summing.

Exercise 2 · a tree() pretty-printer (or du)

Add a tree() that prints the whole hierarchy indented by depth — like the Unix tree / du command — showing each directory and the files inside it. Bonus: print each entry's size() beside its name so you get a per-folder disk-usage view.

Hint: recurse with a depth argument. Print " " * depth + entry.name, then if it's a Directory, recurse over its sorted children at depth + 1. A move/rename is the same idea in reverse — re-parent an entry by deleting it from its old directory's children, setting a new parent, and inserting it into the new one.

Show a solution solution

One recursive walk, indented by depth, printing each entry's size() alongside it. Because size() is uniform, a folder line shows its whole recursive total for free:

tree.py
def tree(self, depth=0):                 # add to Directory
    indent = "  " * depth
    print(f"{indent}{self.name}/  ({self.size()} bytes)")
    for name in sorted(self.children):
        child = self.children[name]
        if isinstance(child, Directory):
            child.tree(depth + 1)        # recurse into subdirectories
        else:
            print(f"{indent}  {child.name}  ({child.size()} bytes)")

Move/rename is just re-parenting: del old.children[entry.name], then entry.parent = new and new.children[entry.name] = entry — after which entry.path() and both folders' size() report the new reality automatically, because nothing caches.

What this design used — the toolkit recap

Composite pattern — one Entry interface over a part-whole tree, so a leaf File and a branch Directory are interchangeable to callers. Recursion — size(), find(), and tree() all walk the structure by trusting children to handle themselves. Polymorphism — child.size() branches without an isinstance ladder. Encapsulation of children — a directory owns its children dict and the add() that maintains parent back-pointers. If this tree were shared across threads, wrap a threading.Lock around add() (and any other mutation) so two writers can't corrupt a directory's children — see the concurrency primer.
