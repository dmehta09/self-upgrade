Case study: a rate limiter.

Cap how many requests a client may make per time window, and reject the overflow. The catch: there are two classic algorithms — token bucket and sliding window — and a good design hides both behind one interface so you can swap them freely. Then make the whole thing safe when many threads call it at once.

01  Step 1 — Requirements & assumptions

A rate limiter answers one yes/no question per request: is this client allowed right now? The contract is "allow at most N requests per client per time window; reject the rest." And because requests arrive from many connections at once, it must stay correct under concurrent calls.

Clarifying questions I'd ask: Per-user or global? One limit, or different tiers per client? Is this a single process, or distributed across many servers (which changes everything)? When we reject, do we drop the request or queue it? And which window semantics do they want — fixed, sliding, or smooth-burst?

Assumptions that keep the demo honest

We pass now (in seconds) into allow() explicitly instead of reading the clock, so every run is deterministic — you can read the output and trust it. We assume a single process, and one limiter per client (the caller picks the right limiter by client id). Distribution across servers is discussed at the end, not built.

In scope

A single allow(now) → bool decision; two interchangeable algorithms behind one interface; correct behaviour when many threads share one limiter; controlled bursts.

Out of scope

Per-client routing and tier config; a distributed/shared store (Redis); queuing or back-pressure on rejection; HTTP plumbing (headers like Retry-After). All sketched, none built.

02  Step 2 — The algorithms behind one interface

The naive design is a fixed window: count requests in the current wall-clock window (say each calendar second), reset the count when the window rolls over. It's trivial — and it has one ugly flaw.

The boundary burst. Suppose the limit is N per second. A client sends N requests in the last 10 ms of one window, then N more in the first 10 ms of the next. Both windows are individually under the limit, yet the client just pushed 2N requests in 20 ms. Fixed window counts within rigid boxes, so traffic that straddles a box edge slips through.

Two better algorithms fix this:

Token bucket
A bucket holds up to capacity tokens and refills at refill_rate tokens/second. Each request spends one token; no token, no entry. It smooths the rate while still allowing a controlled burst up to the bucket size — great when occasional spikes are fine.
Sliding-window log
Keep the timestamps of recent allowed requests; on each call, drop the ones older than the window and admit only if fewer than limit remain. It's exact — no boundary burst at all — at the cost of storing one timestamp per recent request (more memory).

Both expose the same shape — allow(now) → bool — so they're interchangeable Strategies. The caller holds a RateLimiter and never knows (or cares) which algorithm is inside; you swap token bucket for sliding window by changing one line at construction.

A bowl of arcade tokens analogy

The token bucket is a bowl of arcade tokens that refills slowly on its own. Play a game, drop a token in the slot. If the bowl's empty, you wait for it to top up — no token, no play. Because the bowl can hold a few, you can play a small burst back-to-back, but you can't run forever: the refill rate is the real ceiling.

03  Step 3 — The implementation

Two small classes, one shared method name. Each owns its state and a lock; each answers allow(now). That shared signature is what makes them drop-in replacements for each other.

token_bucket.py
import threading

class TokenBucket:
    def __init__(self, capacity, refill_rate):
        self.capacity = capacity            # max tokens (burst size)
        self.refill_rate = refill_rate      # tokens added per second
        self.tokens = capacity
        self.last = 0.0                     # time of last refill (seconds)
        self._lock = threading.Lock()

    def allow(self, now):                   # now = current time, in seconds
        with self._lock:                    # check-and-decrement must be atomic
            elapsed = now - self.last
            self.tokens = min(self.capacity, self.tokens + elapsed * self.refill_rate)
            self.last = now
            if self.tokens >= 1:
                self.tokens -= 1
                return True
            return False
sliding_window.py
import threading
from collections import deque

class SlidingWindow:
    def __init__(self, limit, window):
        self.limit = limit                  # max requests per window
        self.window = window                # window length, seconds
        self.hits = deque()                 # timestamps of recent allowed requests
        self._lock = threading.Lock()

    def allow(self, now):
        with self._lock:
            while self.hits and now - self.hits[0] >= self.window:
                self.hits.popleft()         # drop timestamps older than the window
            if len(self.hits) < self.limit:
                self.hits.append(now)
                return True
            return False

Same method, same return type, two completely different internals. Pass either object wherever a limiter is expected — that's the Strategy pattern doing its job.

04  Why the lock matters

Look closely at the token bucket. The core is a read–modify–write on self.tokens: read the count, check it's at least 1, decrement, return. Those are separate steps, and a thread can be paused between any two of them.

Picture two threads when exactly one token remains. Thread A reads tokens == 1, sees 1 >= 1, and is about to decrement. Before it does, Thread B also reads tokens == 1, also sees the check pass. Now both decrement: tokens goes to -1, and both requests were admitted. You just over-admitted — handed out a token that didn't exist.

The fix is with self._lock: wrapping the whole check-and-decrement. The lock makes that sequence atomic: while one thread holds it, no other thread can read tokens, so the second thread arrives only after the first has already decremented to 0 — and is correctly rejected. The sliding window has the same shape (read the deque length, then append) and is guarded the same way. For the underlying mechanics — race conditions, why the GIL doesn't save you, keeping critical sections small — see the concurrency primer.

"Check then act" is never one step

Anytime you test a condition and then mutate based on it — "is there a token? then take one", "is there a free seat? then book it" — that's two operations, and another thread can sneak between them. The whole test-and-act must sit inside one lock. The decision (the if) and the change (the -=) have to be indivisible, or the decision can be stale by the time you act on it.

05  Walk a scenario

A bucket of capacity 3 refilling at 1 token/sec. Three requests fire instantly at t=0 and drain the bucket; the next two are blocked. Two seconds later the bucket has refilled by ~2 tokens, so two more get through.

demo.py
bucket = TokenBucket(capacity=3, refill_rate=1)   # burst 3, then +1/sec
t = 0.0
for i in range(5):
    print(f"t={t:.1f} req{i}: {'OK' if bucket.allow(t) else 'BLOCKED'}")
print("--- 2 seconds later ---")
t = 2.0
for i in range(5, 7):
    print(f"t={t:.1f} req{i}: {'OK' if bucket.allow(t) else 'BLOCKED'}")
Outputt=0.0 req0: OK t=0.0 req1: OK t=0.0 req2: OK t=0.0 req3: BLOCKED t=0.0 req4: BLOCKED --- 2 seconds later --- t=2.0 req5: OK t=2.0 req6: OK

Why can a fixed-window limiter allow ~2N requests in a short span?

Right: each window is judged in isolation, so a client can send N just before a boundary and N just after. Two adjacent windows are each within limit, yet 2N requests landed in a tiny span across the edge. Token bucket and sliding window both close this gap.

Why must allow() hold a lock around the token check-and-decrement?

Right: reading tokens, checking >= 1, and decrementing are separate steps. Two threads can both read the last token, both pass the check, and both decrement to -1 — admitting one request too many. The lock makes the whole check-and-decrement indivisible.

06  Extensions — your turn

Exercise 1 · the fixed-window limiter

Build the simplest algorithm of all: a fixed window. Keep a counter and the start time of the current window; reset the counter when a new window begins. Then explain, in one line, why it has the burst flaw from §02.

Hint: store count and window_start. On each call, if now has crossed into a new window, reset both. Admit while count is under the limit.

Show a solution solution
fixed_window.py
import threading

class FixedWindow:
    def __init__(self, limit, window):
        self.limit = limit
        self.window = window
        self.count = 0
        self.window_start = 0.0
        self._lock = threading.Lock()

    def allow(self, now):
        with self._lock:
            if now - self.window_start >= self.window:
                self.window_start = now     # roll into a fresh window
                self.count = 0
            if self.count < self.limit:
                self.count += 1
                return True
            return False

The burst flaw: the window resets on a rigid clock, so a client can spend its full limit in the last instant of one window and its full limit again in the first instant of the next — up to 2 × limit requests across the boundary, even though each window stayed within its quota. Sliding window stores timestamps precisely to avoid exactly this.

Exercise 2 · distribute it across servers

Our limiter lives in one process. Behind a load balancer you have ten servers, and the limit is per client across all of them. A local in-memory counter on each server lets a client do 10× the limit. How do you make the count shared?

Show a solution solution

Move the shared state out of process memory and into a shared store every server can reach — typically Redis. The lock we used between threads becomes the store's own atomicity between servers:

  • Fixed window, the easy way: a key per (client, window) and Redis INCR — atomic on the server, so no two app servers can lose an update. Set the key to expire at the window's end. One round-trip per request.
  • Sliding window, the precise way: a Redis sorted set per client keyed by timestamp. Each request removes entries older than the window (ZREMRANGEBYSCORE), counts what's left (ZCARD), and adds itself (ZADD) — wrapped in a Lua script or MULTI so the whole sequence is atomic across servers, exactly mirroring our with self._lock:.
  • Token bucket, the cheap way: store tokens and last in Redis and run the same refill-then-decrement logic inside a Lua script, so the read-modify-write happens atomically server-side.

The shape is identical to the single-process design — the only change is where the critical section is enforced: a network store's atomic op instead of a local Lock. That's a clean way to show an interviewer you understand the pattern, not just one implementation.

What this design used — the toolkit recap

Strategy — token bucket and sliding window hide behind one allow(now) interface, swappable at construction. A single threading.Lock per limiter guards the critical section so check-and-decrement stays atomic and we never over-admit. A deque gives the sliding-window log O(1) appends and O(1) pops from the front as old timestamps age out. And the senior move: knowing the same pattern moves to a shared store (Redis INCR / sorted set) when you go distributed.
