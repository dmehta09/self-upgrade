Case study: chess.

Chess is the question interviewers reach for when they want to watch you balance inheritance against composition in real time. Six piece types that move differently (textbook polymorphism), a board that owns everything (composition spine), and an undo requirement that smuggles in the Command pattern. Big surface, but the skeleton is small — if you cut scope correctly.

01  Clarify the requirements — and cut, hard

Scope is the first test. Say in: two human players, legal-move validation, check / checkmate / stalemate, undo. Say out, explicitly: AI, clocks, network play, draw-by-repetition — and park castling/en-passant/promotion as "rule objects in extensions" (interviewers respect the parking more than a doomed attempt). Invariants:

  • Every square holds at most one piece; every piece is on exactly one square (or captured).
  • A move is applied only if fully legal — including "doesn't leave your own king in check."
  • Undo restores the position exactly, captures included.

02  Entities — composition spine, inheritance at the leaves

The skeleton: Game owns a Board and two Players plus the move history; Board owns 64 Squares; a square references a Piece. The only inheritance in the whole design is the Piece hierarchy — six leaves under one abstract class, each differing in exactly one behaviour: how it moves. Everything else is has-a.

That's the sentence to say out loud: "composition for structure, inheritance only where behaviour genuinely varies per type." It's the composition-vs-inheritance lesson in one design.

03  legal_moves(): subclass polymorphism or Strategy?

Two defensible designs, and interviewers love asking you to argue both:

Subclass per piece (chosen)MovementStrategy injected
FitPiece types are fixed by the rules of chess — the hierarchy will never grow at runtimeShines when behaviours mix & match or change at runtime
CostSix small classesSix strategy classes plus the wiring; indirection with no payoff here
When it winsStandard chessFairy-chess variants, a piece-design sandbox — movement becomes data

The deeper cut: Knight-like pieces and Rook-like pieces differ in shape of movement (fixed offsets vs sliding rays). Factor the ray walk into a shared helper and Bishop/Rook/Queen become one-liners that pass different direction sets — reuse via composition inside the inheritance leaves.

Where should "a move may not leave your own king in check" live?

Right: pieces answer the LOCAL question ("how do I move?"); check is a GLOBAL property of the whole position. Putting it in every piece duplicates board-wide logic six times and tangles the layers. The standard structure: pseudo-legal from the piece, legal after the king-safety filter above.

04  The core code — rays, check, undo

The three methods worth writing for real in the 15-minute code phase:

def slide(board, pos, color, directions) -> list["Pos"]:
    """The shared ray walk — Rook, Bishop, Queen differ only in input."""
    out = []
    for dr, dc in directions:
        r, c = pos.r + dr, pos.c + dc
        while 0 <= r < 8 and 0 <= c < 8:
            target = board.piece_at(Pos(r, c))
            if target is None:
                out.append(Pos(r, c))            # empty: keep sliding
            else:
                if target.color != color:
                    out.append(Pos(r, c))        # capture: include, then stop
                break                            # any piece blocks the ray
            r, c = r + dr, c + dc
    return out

class Rook(Piece):
    DIRS = [(1, 0), (-1, 0), (0, 1), (0, -1)]
    def legal_moves(self, board, pos):
        return slide(board, pos, self.color, self.DIRS)

class Queen(Piece):
    DIRS = Rook.DIRS + [(1, 1), (1, -1), (-1, 1), (-1, -1)]
    def legal_moves(self, board, pos):
        return slide(board, pos, self.color, self.DIRS)

class Knight(Piece):
    OFFSETS = [(2, 1), (2, -1), (-2, 1), (-2, -1),
               (1, 2), (1, -2), (-1, 2), (-1, -2)]
    def legal_moves(self, board, pos):
        out = []
        for dr, dc in self.OFFSETS:              # jumps: no ray, no blocking
            r, c = pos.r + dr, pos.c + dc
            if 0 <= r < 8 and 0 <= c < 8:
                t = board.piece_at(Pos(r, c))
                if t is None or t.color != self.color:
                    out.append(Pos(r, c))
        return out
class Game:
    def make_move(self, frm: Pos, to: Pos) -> bool:
        piece = self.board.piece_at(frm)
        if piece is None or piece.color is not self.turn:
            return False
        if to not in piece.legal_moves(self.board, frm):
            return False                          # not even pseudo-legal

        move = Move(frm, to, captured=self.board.piece_at(to))
        self.board.apply(move)                    # try it...
        if self.board.is_check(self.turn):        # ...king exposed?
            self.board.revert(move)               # take it straight back
            return False

        self.history.append(move)                 # Command, recorded
        self.turn = self.turn.opponent
        return True

    def undo(self) -> None:
        if not self.history:
            return
        move = self.history.pop()
        self.board.revert(move)                   # uses move.captured
        self.turn = self.turn.opponent

# is_check: find the king, ask every enemy piece if it can reach him.
# checkmate = in check AND no legal move escapes (try-all with the same
# apply/revert trick). stalemate = NOT in check AND no legal move.

Notice make_move validates king-safety by doing and undoing — the same apply/revert pair that powers the user-facing undo. One mechanism, three features (validation, undo, and later: AI search). That economy is what a great chess answer looks like.

05  Extensions — the parked rules return

Castling / en passant / promotion
Each is a special move generator + special apply/revert. Model them as subclasses of Move (CastleMove carries the rook's hop too; PromotionMove stores the pawn it replaced) — undo keeps working because each Move knows how to reverse itself. Command pattern paying rent again.
Serialization (PGN/FEN)
The history of Moves is the game — replaying commands from the start reconstructs any position. Event-sourcing in miniature; say that phrase.
A move clock / AI
Clock = Observer on turn changes. AI = the apply/revert pair again, now driving minimax — which is why engines obsess over making apply/revert fast.
Exercise · the Pawn

Write Pawn.legal_moves(): forward 1 (2 from the start rank) only onto empty squares, diagonal captures only onto enemy squares, direction depends on color. Which of the lesson's helpers can you reuse, and which assumption breaks?

Hint: none of them cleanly — the pawn moves and captures on different squares, which is exactly why it's the standard probe of whether your Piece abstraction was honest or wishful.
