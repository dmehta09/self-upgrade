LLD case study · table-driven FSM

Designing a traffic light.

The vending machine used a traffic light as its analogy — now we design the real thing. It's the gentlest state machine in the catalog, and it teaches a lesson the vending case can't: sometimes a transition table beats a class per state.

01  Clarify the requirements

One intersection, one light, and a few rules to confirm out loud:

  • The light cycles RED → GREEN → YELLOW → RED on timers (say 30s / 25s / 5s).
  • A pedestrian button requests a crossing — served at the next red, never instantly.
  • An emergency override (ambulance transponder) forces RED from any state.
  • Displays and logs need to know when the light changes — without the light knowing them.

And the one invariant that matters more than all the features: the light is always in exactly one state, and every change goes through one validated path. In the 4-way extension this becomes "never two crossing greens" — the kind of safety property you should name in the first five minutes of an interview.

Scope we'll defer

Multi-intersection coordination, sensors, and real-time guarantees stay out. One controller, software timers, single thread. The extensions section brings the 4-way intersection back.

02  A table, not a class per state

The vending machine earned full State classes because each state carried real behaviour — balance math, stock checks, dispensing. A traffic light's states carry almost none: each one just knows what comes next and after how long. When the per-state behaviour is that thin, a class per state is ceremony. The senior move is a transition table:

CurrentEventNextNotes
REDtimer (30s)GREENserve any queued pedestrian first
GREENtimer (25s)YELLOW—
YELLOWtimer (5s)RED—
anyemergencyREDvia YELLOW if currently GREEN
anyped_requestno changesets a flag; served at next RED

The whole machine becomes data: a dict from (state, event) to the next state. Adding a state edits the table, not a method in five classes. The trade-off to say out loud: tables shine while transitions are uniform; the moment states need rich, divergent behaviour (guards with side effects, per-state data), graduate to State classes — that's exactly the ATM case next door.

Why does the traffic light get a table while the vending machine got State classes?

Right: the deciding question is "how much behaviour does each state carry?" Thin, uniform states → table-driven FSM. Rich, divergent states → State pattern. Both are finite state machines; only the encoding differs.

Two details interviewers probe: the pedestrian press doesn't transition (it sets a flag the RED state consumes), and the emergency path from GREEN still routes through YELLOW — a hard GREEN→RED cut is how you cause the crash you were avoiding.

04  The implementation

Enums for states and events, a dict for the table, and one handle() choke point every change flows through:

traffic_light.py
from enum import Enum, auto

class Light(Enum):
    RED = auto(); GREEN = auto(); YELLOW = auto()

class Event(Enum):
    TICK = auto(); PED_REQUEST = auto(); EMERGENCY = auto()

DURATIONS = {Light.RED: 30, Light.GREEN: 25, Light.YELLOW: 5}

# The whole machine, as data: (state, event) -> next state
TRANSITIONS: dict[tuple[Light, Event], Light] = {
    (Light.RED,    Event.TICK):      Light.GREEN,
    (Light.GREEN,  Event.TICK):      Light.YELLOW,
    (Light.YELLOW, Event.TICK):      Light.RED,
    (Light.GREEN,  Event.EMERGENCY): Light.YELLOW,   # clear safely
    (Light.YELLOW, Event.EMERGENCY): Light.RED,
}

class TrafficLight:
    def __init__(self):
        self.state = Light.RED
        self.ped_waiting = False
        self._subscribers: list = []          # Observer: callables

    def subscribe(self, fn) -> None:
        self._subscribers.append(fn)

    def handle(self, event: Event) -> None:
        """The single choke point — every change validates here."""
        if event is Event.PED_REQUEST:
            self.ped_waiting = True           # a flag, not a transition
            return
        nxt = TRANSITIONS.get((self.state, event))
        if nxt is None:
            return                            # illegal -> ignore (or log)
        if self.state is Light.RED and nxt is Light.GREEN and self.ped_waiting:
            self.ped_waiting = False          # RED consumed the request:
            # hold RED one extra cycle for the crossing, then proceed
        self._set(nxt)

    def _set(self, nxt: Light) -> None:
        old, self.state = self.state, nxt
        for fn in self._subscribers:          # notify displays / logs
            fn(old, nxt)

Three things to narrate while writing it: the table makes illegal moves unrepresentable (a missing key is a no-op, not a bug); PED_REQUEST is deliberately a flag because a mid-green crossing would violate the safety invariant; and the Observer list means a countdown display is one subscribe() away — the light never imports a display.

A new requirement: flashing-yellow night mode between 1am and 5am. What changes?

Right: new behaviour = new state + new rows. The choke point and existing rows stay untouched — the table gives you the Open/Closed Principle for free. The schedule itself is a Strategy (see extensions).

05  Extensions interviewers reach for

Timing plans (Strategy)
Rush-hour vs night vs event-day durations: extract DURATIONS behind a TimingPlan with duration(state) → int, swap plans on a schedule. The FSM never learns which plan is active.
4-way intersection
Four lights + one IntersectionController that owns THE invariant: north–south green ⇒ east–west red. Model the pairs as the controller's states (NS_GREEN, EW_GREEN, ALL_RED interludes) — composing four independent FSMs and hoping is how you get two greens.
Countdown display (Observer)
Already wired: subscribe() a renderer. Worth saying: the subscriber list is exactly the Observer pattern with plain callables.
Exercise · prove the invariant

Write the IntersectionController transition table for a 4-way crossing (states NS_GREEN, NS_YELLOW, ALL_RED_1, EW_GREEN, EW_YELLOW, ALL_RED_2). Then explain in one sentence why "never two crossing greens" holds by construction.

Hint: if no table row ever maps to a state where both directions are green — and every change goes through the table — the bad state is unreachable. That's the argument, and it only works because of the single choke point.
