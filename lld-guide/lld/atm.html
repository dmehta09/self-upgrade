LLD case study · guards on a State machine

Designing an ATM.

Structurally an ATM is the vending machine's sibling — insert something, pick an action, get a thing out. What's new is that nearly every transition carries a guard: three PIN attempts, enough balance, enough cash in the tray. Guards are where state machines earn their keep, and where interviewers separate "knows the pattern" from "can design with it."

01  Clarify the requirements

  • Insert card → enter PIN (max 3 attempts, then the card is captured).
  • Authenticated users can check balance, withdraw, or deposit.
  • A withdrawal must pass two checks: account balance and physical cash inventory.
  • Eject the card at the end of the session — or whenever the user cancels.

Invariants to say out loud: money leaves the tray only in an authenticated session; failed-attempt counting never resets mid-session; and the hardware (card reader, cash dispenser, screen) sits behind interfaces so the brain of the machine is testable without metal.

A guard is a bouncer on a door analogy

The door (transition) exists either way — Authenticating → Transacting is on the map. But the bouncer checks your wristband before letting you through: right PIN, you pass; wrong PIN, you stay; third wrong PIN, you're walked out a different door entirely (card captured). Same event, three outcomes — that's a guard.

Compare this with the traffic light: there, transitions were pure data, so a table won. Here, almost every row needs a decision with state behind it (an attempt counter, a balance lookup, a hardware query) — that's the signal to give each state a class again, vending-machine style, with the guards living inside the state's methods.

Where should the "3 attempts" counter live?

Right: shared session data belongs on the context (like the vending machine's balance). Storing it on the state object is the classic trap — state objects are routinely recreated on re-entry, which would quietly reset the count and hand an attacker infinite guesses.

03  Drive the machine

Try the happy withdrawal — then try getting the PIN wrong three times and watch the third failure take a different door:

The "three wrong PINs" run is the whole lesson: the same event (pin_bad) self-loops twice and then exits to CardCaptured — one event, two destinations, chosen by a guard reading the attempt counter. No diagram without guards can express that.

04  The implementation — guards in the states

The skeleton mirrors the vending machine (rejecting defaults on the ABC, states drive transitions), so here we zoom into the two guard-heavy states only:

atm_states.py
MAX_ATTEMPTS = 3

class AuthenticatingState(AtmState):
    def enter_pin(self, atm: "Atm", pin: str) -> None:
        if atm.bank.verify(atm.card, pin):          # guard 1: PIN
            atm.set_state(SelectingTxnState())
            return
        atm.attempts += 1                           # counter on the CONTEXT
        if atm.attempts >= MAX_ATTEMPTS:            # guard 2: attempts
            atm.reader.capture_card()
            atm.set_state(CardCapturedState())
        else:
            atm.screen.show(f"Wrong PIN ({atm.attempts}/{MAX_ATTEMPTS})")


class SelectingTxnState(AtmState):
    def withdraw(self, atm: "Atm", amount: int) -> None:
        if atm.bank.balance(atm.card) < amount:     # guard: account side
            atm.screen.show("Insufficient funds")
            return
        if not atm.dispenser.can_dispense(amount):  # guard: hardware side
            atm.screen.show("Machine low on cash")
            return
        atm.bank.debit(atm.card, amount)            # debit BEFORE notes move
        atm.set_state(DispensingState(amount))
        atm.dispense()

Note the order in withdraw: debit, then dispense. If the dispenser jams you refund a debit; the other order hands out cash you never collected. Saying that ordering trade-off (and that real ATMs solve it with a two-phase, journaled protocol) is a senior flourish. The bank, reader, dispenser, screen are injected Protocols — the FSM is fully testable with fakes.

And the note tray itself? Paying out 180 from 100/50/20 notes is a textbook Chain of Responsibility: a NoteHandler(100) dispenses what it can and passes the remainder to NoteHandler(50), and so on. If the chain ends with a remainder, the guard above (can_dispense) should have caught it — run the chain "dry" first to answer that.

Why does can_dispense(amount) need to be more than amount <= total_cash?

Right: 150 in the tray ≠ "can pay 80". The dry-run of the note chain (greedy 50+20+… or DP for awkward currencies) is the real guard. This is the detail that makes interviewers sit up.

05  Pick your FSM flavour — the four cases side by side

CaseEncodingWhy
Traffic lightTransition tableUniform, behaviour-free transitions — pure data
Vending machineState classesPer-state behaviour (balance, stock, dispensing)
ATMState classes + guardsSame event, multiple destinations, decided by session data
ElevatorFSM inside a loopStates flip themselves during step(); events merge into a target set

That table is a ready-made interview answer to "when would you not use the State pattern?" — the honest spectrum runs from data table to guarded classes, chosen by how much behaviour the states carry.

06  Extend it yourself

Exercise · deposits with an envelope

Add a deposit() flow: SelectingTxn → AcceptingEnvelope → (validated) → SelectingTxn. The envelope scanner can reject. Which new states, which guards, and what must not change?

Hint: the existing states shouldn't gain a line. New states + a rejecting default on the ABC for deposit() mean the old states reject it for free — the same trick as the vending machine's cancel().

Daily limits
Another guard on withdraw — but the counter lives with the bank, not the machine (you can hop ATMs). Good prompt for "which side of the interface does this state belong on?"
Receipt printer
An Observer on completed transactions — the FSM publishes, the printer subscribes, nothing couples.
Concurrent sessions?
One physical machine = one session, so the FSM itself needs no lock. The account does: two ATMs, one account, simultaneous withdrawals — that's the movie-booking race wearing a different hat.
