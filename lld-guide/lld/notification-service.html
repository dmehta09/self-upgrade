LLD case study · Observer + Strategy + Factory

Designing a notification service.

This one is a favourite interview question precisely because no single pattern solves it. A good design weaves three together — Observer to track who cares, Strategy to swap delivery channels, and Factory to build them — and the payoff is that adding a brand-new channel never touches a line of existing code.

01  Clarify the requirements

The brief: a service that delivers messages to users across several channels. Concretely it should:

  • Send notifications over multiple channels — Email, SMS, Push to begin with.
  • Let users subscribe to topics / events (e.g. "orders", "billing").
  • When an event is published to a topic, notify every subscriber.
  • Crucially: adding a new channel must not require editing existing code. That's the Open/Closed Principle — open for extension, closed for modification.

Three distinct concerns are hiding in there. "Who gets told" is a subscription problem. "How they get told" is a delivery problem with interchangeable options. "How a channel comes into existence" is a construction problem. Each maps cleanly onto a classic pattern.

02  The approach

Let's name the pieces before writing them:

📡

Channel = Strategy

A Channel Protocol with one method, send(user, message). EmailChannel, SMSChannel, PushChannel are interchangeable implementations.

🏭

ChannelFactory = Factory

ChannelFactory.create("email") turns a string into the right channel object, so callers never hard-code constructors.

🔔

NotificationService = Observer

Users subscribe(topic, user); a publish(topic, msg) fans the message out to every subscriber. Subscribers are the "observers."

A magazine subscription analogy

You subscribe to a magazine (Observer): when an issue is published, the publisher mails it to everyone on the list without knowing or caring who they are. How it reaches you — post, email, an app — is the delivery channel (Strategy). And the mailroom that picks the right envelope for your chosen format is the Factory.

04  The implementation

We model a user as a tiny dataclass, define Channel as a Protocol (structural typing — no inheritance needed), then write the three channels, the factory, and the service.

from __future__ import annotations
from dataclasses import dataclass
from typing import Protocol


@dataclass(frozen=True)
class User:
    name: str
    address: str          # email, phone number, or device id — channel decides


class Channel(Protocol):
    """The Strategy contract. Anything with a matching send() is a Channel —
    no inheritance required (structural typing)."""
    def send(self, user: User, message: str) -> None: ...


class EmailChannel:
    def send(self, user: User, message: str) -> None:
        print(f"  [EMAIL] to {user.address}: {message}")


class SMSChannel:
    def send(self, user: User, message: str) -> None:
        print(f"  [SMS]   to {user.address}: {message}")


class PushChannel:
    def send(self, user: User, message: str) -> None:
        print(f"  [PUSH]  to device {user.address}: {message}")
class ChannelFactory:
    """The Factory. Maps a string key to a channel constructor, so callers
    say create('email') instead of importing and newing EmailChannel."""

    _registry: dict[str, type[Channel]] = {
        "email": EmailChannel,
        "sms": SMSChannel,
        "push": PushChannel,
    }

    @classmethod
    def create(cls, kind: str) -> Channel:
        try:
            return cls._registry[kind]()
        except KeyError:
            raise ValueError(f"unknown channel: {kind!r}") from None

    @classmethod
    def register(cls, kind: str, channel: type[Channel]) -> None:
        cls._registry[kind] = channel        # lets new channels plug in
class NotificationService:
    """The Observer subject. Holds subscribers per topic and one delivery
    Channel, and fans a published message out to every subscriber."""

    def __init__(self, channel: Channel):
        self._channel = channel
        self._topics: dict[str, list[User]] = {}

    def subscribe(self, topic: str, user: User) -> None:
        subs = self._topics.setdefault(topic, [])
        if user not in subs:
            subs.append(user)

    def unsubscribe(self, topic: str, user: User) -> None:
        if user in self._topics.get(topic, []):
            self._topics[topic].remove(user)

    def publish(self, topic: str, message: str) -> None:
        subscribers = self._topics.get(topic, [])
        print(f"publish '{topic}' -> {len(subscribers)} subscriber(s)")
        for user in subscribers:              # notify every observer
            self._channel.send(user, message)

Three things to notice. The channels don't inherit from Channel — they just match its shape, which is what a Protocol checks. The factory's create hides which class is built. And NotificationService depends only on the Channel abstraction, never on a concrete channel — so it never needs editing when channels change.

05  Three patterns, one service

Here's the map from requirement to pattern, and how each contributes to the design:

PatternWhat plays the roleJob in this design
ObserverNotificationService + per-topic subscriber listsDecouples publishers from subscribers — publish doesn't know who's listening.
StrategyChannel Protocol + Email/SMS/PushDelivery is an interchangeable algorithm; swap the channel without touching the service.
FactoryChannelFactory.create()Centralises construction; callers pick a channel by name, not by importing classes.
How the Open/Closed Principle is satisfied

Adding a Slack channel means: write a SlackChannel with a send(), then ChannelFactory.register("slack", SlackChannel). You extend the system (new class) without modifying NotificationService, the existing channels, or the factory's source. Because the service depends on the Channel abstraction (Strategy) and never on a concrete type, it simply doesn't care that a new one appeared — that's OCP, made possible by abstraction.

Here are all three patterns firing in one publish() call — Observer fans out to subscribers, and each delivery dispatches through a Strategy channel:

Which pattern is responsible for the service notifying many subscribers when one event is published?

Right: Observer is the one-to-many notification pattern. The NotificationService is the subject; subscribers are observers updated on publish.

Why does adding a SlackChannel not force you to edit NotificationService?

Right: the service talks to the Channel Protocol only. Any object with a matching send() works, so extension lives entirely in new code — the Open/Closed Principle.

06  A runnable walkthrough

Build the service with an email channel from the factory, subscribe two users to "orders", then publish:

run.py
channel = ChannelFactory.create("email")     # Factory builds the strategy
service = NotificationService(channel)

alice = User("Alice", "alice@example.com")
bob   = User("Bob",   "bob@example.com")

service.subscribe("orders", alice)            # Observer: register subscribers
service.subscribe("orders", bob)
service.subscribe("billing", bob)             # Bob also cares about billing

service.publish("orders", "Your order #42 has shipped!")
service.publish("billing", "Invoice #7 is ready.")
service.publish("promos", "50% off!")         # nobody subscribed
Outputpublish 'orders' -> 2 subscriber(s) [EMAIL] to alice@example.com: Your order #42 has shipped! [EMAIL] to bob@example.com: Your order #42 has shipped! publish 'billing' -> 1 subscriber(s) [EMAIL] to bob@example.com: Invoice #7 is ready. publish 'promos' -> 0 subscriber(s)

Both subscribers to "orders" were notified; only Bob got the billing message; and the "promos" topic with no subscribers simply notified nobody. Want SMS instead? Build the service with ChannelFactory.create("sms") — not one other line changes.

07  Extend it yourself

Exercise 1 · add Slack without touching existing code (OCP)

Add a SlackChannel and make ChannelFactory.create("slack") work — without editing NotificationService, the existing channels, or the factory's class body.

Hint: that's exactly what ChannelFactory.register is for.

Show a solution solution

All-new code; nothing existing is modified. The new class just satisfies the Channel shape and registers itself.

slack.py
class SlackChannel:                      # matches the Channel Protocol
    def send(self, user: User, message: str) -> None:
        print(f"  [SLACK] @{user.address}: {message}")

ChannelFactory.register("slack", SlackChannel)   # plug it in

service = NotificationService(ChannelFactory.create("slack"))
service.subscribe("orders", User("Cara", "cara"))
service.publish("orders", "Build passed.")
Outputpublish 'orders' -> 1 subscriber(s) [SLACK] @cara: Build passed.

Not a single existing line changed — pure extension. That is the Open/Closed Principle delivered by the Strategy + Factory combo.

Exercise 2 · wrap a channel with a retry Decorator

Sometimes send fails transiently. Write a RetryChannel that wraps any other channel and retries its send a few times before giving up — without modifying the wrapped channel. This is the Decorator pattern.

Show a solution solution

A decorator is a Channel (same send shape) and has a Channel it delegates to — composition, not inheritance.

retry.py
class FlakyChannel:
    """Pretend channel that fails the first attempt, then succeeds."""
    def __init__(self) -> None:
        self._attempts = 0
    def send(self, user: User, message: str) -> None:
        self._attempts += 1
        if self._attempts < 2:
            raise ConnectionError("network blip")
        print(f"  [FLAKY] to {user.address}: {message}")


class RetryChannel:                       # wraps any Channel, is one too
    def __init__(self, inner: Channel, tries: int = 3) -> None:
        self._inner = inner
        self._tries = tries
    def send(self, user: User, message: str) -> None:
        for attempt in range(1, self._tries + 1):
            try:
                self._inner.send(user, message)
                return
            except ConnectionError as e:
                print(f"  retry {attempt}/{self._tries} after: {e}")
        print("  giving up after retries")


service = NotificationService(RetryChannel(FlakyChannel()))
service.subscribe("orders", User("Dee", "dee@x.io"))
service.publish("orders", "Shipped!")
Outputpublish 'orders' -> 1 subscriber(s) retry 1/3 after: network blip [FLAKY] to dee@x.io: Shipped!

The service still thinks it's talking to a plain Channel; the retry logic was layered on transparently. Decorators stack — you could wrap that again with a logging channel.
