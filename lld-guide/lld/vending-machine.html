LLD case study · the State pattern

Designing a vending machine.

A vending machine is the friendliest possible introduction to the State pattern. It does completely different things depending on what's happening inside it — and that "it depends on the state" is exactly the smell that the pattern was invented for.

01  Clarify the requirements

Before any code, pin down what the machine must do. In an interview you'd say these out loud and confirm scope with the interviewer. Our machine should:

  • Accept coins one at a time, tracking a running balance.
  • Let the user select a product from the inventory.
  • Dispense the product only when there is enough money and stock.
  • Return change if the user paid more than the price.
  • Allow cancel / refund at any point before dispensing.

Notice how every rule is phrased as "if the machine is in this situation, then…". The same button (insert a coin) means different things at different moments: it's fine while idle, but pointless while a product is already being dispensed. That is the tell-tale sign of a finite state machine — a thing that lives in exactly one of a handful of named states, and whose reaction to an event depends on which state it's in.

Scope we'll defer

Real machines worry about exact change, multiple coin denominations, card payments, and concurrency. We'll keep coins as plain integer cents and a single-threaded flow so the design stays in focus. The extensions section adds a couple of the trickier requirements back.

02  Why this is a State machine

The naive version of this code is a swamp of if statements: "if balance is zero do X, unless a product is selected, unless we're mid-dispense…". Every method ends up re-checking the same flags. The State pattern flips that around: instead of one object asking "what state am I in?" everywhere, you give each state its own object that knows how to behave.

A traffic light analogy

A traffic light is always exactly one of red, green, or amber. The "next" event does something different in each: red→green, green→amber, amber→red. The light doesn't keep a tangle of booleans; it simply is a colour, and each colour knows what comes next. Swap "colour" for "machine state" and you have the State pattern.

Concretely, our machine moves between these states:

StateMeaningWhat "select" does here
IdleWaiting, balance is zeroRejects — "insert money first"
HasMoneyCoins inserted, awaiting a choicePicks the product, moves to dispensing
DispensingVending + returning changeRejects — "already dispensing"

Each state is a class. The machine (the context) just holds a reference to "the state I'm currently in" and forwards every event to it. Adding a new state later means adding a class, not editing a giant if ladder — the Open/Closed Principle at work.

04  The implementation

We start with the shared contract. Each state implements the three events; the default ABC version of each rejects the action, so a state only overrides the events it actually allows.

from __future__ import annotations
from abc import ABC, abstractmethod

# Prices in whole cents, keeps the math exact and deterministic.
PRICES: dict[str, int] = {"cola": 125, "water": 100, "chips": 150}


class VendingState(ABC):
    """One object per state. Each method reacts to an event; the
    default is to reject it, so subclasses override only what they allow."""

    @abstractmethod
    def name(self) -> str: ...

    def insert_coin(self, machine: "VendingMachine", amount: int) -> None:
        print(f"  [rejected] can't insert coins while {self.name()}")

    def select(self, machine: "VendingMachine", product: str) -> None:
        print(f"  [rejected] can't select while {self.name()}")

    def dispense(self, machine: "VendingMachine") -> None:
        print(f"  [rejected] nothing to dispense while {self.name()}")


class IdleState(VendingState):
    def name(self) -> str:
        return "idle"

    def insert_coin(self, machine: "VendingMachine", amount: int) -> None:
        machine.balance += amount
        print(f"  inserted {amount}c, balance = {machine.balance}c")
        machine.set_state(HasMoneyState())   # transition Idle -> HasMoney


class HasMoneyState(VendingState):
    def name(self) -> str:
        return "has-money"

    def insert_coin(self, machine: "VendingMachine", amount: int) -> None:
        machine.balance += amount            # stay in HasMoney, just add coins
        print(f"  inserted {amount}c, balance = {machine.balance}c")

    def select(self, machine: "VendingMachine", product: str) -> None:
        if machine.inventory.get(product, 0) <= 0:
            print(f"  [rejected] {product} is out of stock")
            return
        price = PRICES[product]
        if machine.balance < price:
            short = price - machine.balance
            print(f"  [rejected] {product} costs {price}c, insert {short}c more")
            return
        machine.selected = product
        print(f"  selected {product} ({price}c)")
        machine.set_state(DispensingState())  # transition HasMoney -> Dispensing
        machine.dispense()                    # auto-run the dispense step


class DispensingState(VendingState):
    def name(self) -> str:
        return "dispensing"

    def dispense(self, machine: "VendingMachine") -> None:
        product = machine.selected
        price = PRICES[product]
        machine.inventory[product] -= 1
        change = machine.balance - price
        print(f"  dispensed {product}; change returned = {change}c")
        # reset the context and go back to the start
        machine.balance = 0
        machine.selected = None
        machine.set_state(IdleState())        # transition Dispensing -> Idle
class VendingMachine:
    """The CONTEXT. It owns the inventory + balance and delegates every
    event to whatever state object it currently holds."""

    def __init__(self, inventory: dict[str, int]):
        self.inventory = inventory
        self.balance: int = 0
        self.selected: str | None = None
        self.state: VendingState = IdleState()   # always start idle

    def set_state(self, state: VendingState) -> None:
        self.state = state                       # the single transition point

    # --- the public API simply forwards to the current state ---
    def insert_coin(self, amount: int) -> None:
        self.state.insert_coin(self, amount)

    def select(self, product: str) -> None:
        self.state.select(self, product)

    def dispense(self) -> None:
        self.state.dispense(self)

The whole trick is in VendingMachine: its insert_coin / select / dispense methods contain no logic — they hand off to self.state. The states themselves decide what is legal and call machine.set_state(...) to move on.

05  A runnable walkthrough

Let's buy a cola (125c) by inserting a dollar and a quarter, then try a few illegal moves to watch the states reject them:

run.py
vm = VendingMachine(inventory={"cola": 2, "water": 0, "chips": 5})

print("State:", vm.state.name())
vm.dispense()              # illegal while idle

print("State:", vm.state.name())
vm.insert_coin(100)        # Idle -> HasMoney
vm.insert_coin(25)         # stays HasMoney, balance 125

print("State:", vm.state.name())
vm.select("water")         # out of stock -> rejected, still HasMoney
vm.select("cola")          # enough money + in stock -> dispense + reset

print("State:", vm.state.name())
print("Cola left:", vm.inventory["cola"])
OutputState: idle [rejected] nothing to dispense while idle State: idle inserted 100c, balance = 100c inserted 25c, balance = 125c State: has-money [rejected] water is out of stock selected cola (125c) dispensed cola; change returned = 0c State: idle Cola left: 1

The machine ends right back in idle, balance cleared, inventory decremented — ready for the next customer. No flags, no nested conditionals; each state simply did its job and pointed at the next state.

The Pythonic way

For something this small you could replace the state classes with a single method that uses match self._state: and case "idle": branches. That's perfectly Pythonic for two or three states. But every new state then means editing that one growing method (and every event's match). Explicit state classes scale better: each state is isolated, independently testable, and adding one never touches the existing ones — exactly what we'll do in the extensions below.

Strategy and State are nearly identical in structure. What's the real difference?

Right: they share the "interface + interchangeable implementations" shape, but intent differs. With Strategy the caller picks an algorithm and it stays put. With State the objects themselves drive transitions — each state decides what the next state is by calling set_state().

In our design, what actually triggers a transition from one state to the next?

Right: transitions live inside the states. IdleState.insert_coin moves to HasMoneyState; HasMoneyState.select moves to DispensingState. The context's set_state is just the one place the swap happens.

06  Extend it yourself

Exercise 1 · add a SoldOut state

Add a SoldOutState the machine enters when the entire inventory is empty. While sold out, inserting coins should be rejected. Where do you put the check, and what existing code must change?

Hint: the only place that removes stock is DispensingState.dispense — that's the natural spot to ask "is everything gone now?" before choosing the next state.

Show a solution solution

You add one new class and tweak only the dispense transition — the other states are untouched.

sold_out.py
class SoldOutState(VendingState):
    def name(self) -> str:
        return "sold-out"

    def insert_coin(self, machine: "VendingMachine", amount: int) -> None:
        print("  [rejected] machine is sold out")
    # select() and dispense() inherit the ABC's "rejected" defaults.


# inside DispensingState.dispense, replace the final transition with:
class DispensingState(VendingState):
    def name(self) -> str:
        return "dispensing"

    def dispense(self, machine: "VendingMachine") -> None:
        product = machine.selected
        price = PRICES[product]
        machine.inventory[product] -= 1
        change = machine.balance - price
        print(f"  dispensed {product}; change returned = {change}c")
        machine.balance = 0
        machine.selected = None
        if sum(machine.inventory.values()) == 0:        # everything gone?
            machine.set_state(SoldOutState())
        else:
            machine.set_state(IdleState())

Because every state is its own class, "sold out" can't accidentally accept money — it simply doesn't override the methods that would let it.

Exercise 2 · refund on cancel

Add a cancel() event that refunds the full balance and returns the machine to Idle. It should work in HasMoneyState but be rejected while Dispensing (you can't un-vend a snack).

Show a solution solution

Add a default cancel to the interface (rejecting, like the others), forward it from the context, then override it only where a refund makes sense.

cancel.py
# on VendingState (the ABC): a rejecting default
    def cancel(self, machine: "VendingMachine") -> None:
        print(f"  [rejected] can't cancel while {self.name()}")

# on VendingMachine (the context): forward it
    def cancel(self) -> None:
        self.state.cancel(self)

# on HasMoneyState: the real refund
    def cancel(self, machine: "VendingMachine") -> None:
        refund = machine.balance
        machine.balance = 0
        machine.selected = None
        print(f"  cancelled; refunded {refund}c")
        machine.set_state(IdleState())

# usage
vm.insert_coin(100)        # Idle -> HasMoney, balance 100
vm.cancel()                # refunded 100c, back to Idle
Output inserted 100c, balance = 100c cancelled; refunded 100c

DispensingState never overrides cancel, so it falls through to the ABC's rejecting default — exactly the behaviour we want.
