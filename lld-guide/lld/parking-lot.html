LLD case studies · parking lot

Case study: design a parking lot.

The most-asked LLD prompt there is. We run the six-step method end to end — scope it, find the entities, draw the diagram, code it, price it with a Strategy, walk a scenario, then extend it. By the end you'll have a clean, runnable model you could reproduce on a whiteboard.

01  Step 1 — Requirements & assumptions

Before a single class, we scope it. A parking lot can be enormous (reservations, multiple gates, license-plate recognition, monthly passes…). The interviewer doesn't want all of that — they want a clean core. So we ask, then we commit.

Clarifying questions I'd ask: One lot or many floors? Which vehicle types? Do we reserve spots ahead, or just walk-in? How is payment computed — flat or by time? Single-threaded demo or concurrent?

My stated assumptions

I'll model one flat lot (floors are a noted extension), with three spot sizes and three vehicle types. A driver gets a ticket on entry and pays on exit. Single-threaded for the demo. Reservations and real wall-clock time are out of scope — I'll pass entry/exit hours as integers to keep the run deterministic.

✅

Functional (in scope)

Park a vehicle into a free, fitting spot · issue a ticket on entry · unpark and free the spot · compute a fee on exit · support several spot sizes and vehicle types.

📐

Non-functional notes

The fee rule must be easy to swap (flat vs hourly) without touching the lot. Adding a new vehicle or spot type shouldn't force edits to existing classes — design for extension.

02  Step 2 & 3 — Entities & responsibilities

Now the noun–verb pass. "A vehicle parks in a spot in the lot, gets a ticket, and the price is charged on exit." Each noun becomes a class or enum, and we give each exactly one job (Single Responsibility):

VehicleType / SpotType
enums. The fixed vocabulary of sizes and kinds. Enums beat bare strings — typo-proof and self-documenting.
Vehicle
A car/bike/truck identified by a license plate. Just data — a @dataclass.
ParkingSpot
Knows its size and whether it's free; can park() / vacate() a vehicle and report can_fit(). Owns its own occupancy state.
Ticket
The record handed to the driver: which vehicle, which spot, the entry time. Pure data — a @dataclass.
PricingStrategy
interface. The one job is price(hours). Concrete FlatRate / HourlyRate implement it. Pricing is the part that varies.
ParkingLot
The coordinator: holds the spots and a pricing strategy, finds a fitting spot to park(), and on unpark() frees the spot and computes the fee.
ParkingFloor (optional)
A grouping of spots by level. Not needed for one flat lot — noted as the multi-floor extension so the model can grow.
Why split ParkingSpot from ParkingLot?

The spot owns occupancy ("am I free? can this vehicle fit me?"); the lot owns coordination ("which free spot should I hand out?"). Two responsibilities, two classes. If occupancy logic and allocation logic lived in one class, every change to either would risk breaking the other.

04  Step 6 — The implementation

We build it bottom-up: the vocabulary (enums), then the data (Vehicle, Ticket), then the behavior (ParkingSpot, ParkingLot). Time is kept simple — we pass entry/exit hours as integers so the demo is deterministic and runs anywhere.

enums.py
from enum import Enum

class VehicleType(Enum):
    BIKE = "bike"
    CAR = "car"
    TRUCK = "truck"

class SpotType(Enum):
    SMALL = 1            # int values let us compare "big enough"
    MEDIUM = 2
    LARGE = 3

# the smallest spot each vehicle needs
FITS: dict[VehicleType, SpotType] = {
    VehicleType.BIKE:  SpotType.SMALL,
    VehicleType.CAR:   SpotType.MEDIUM,
    VehicleType.TRUCK: SpotType.LARGE,
}

Now the plain-data classes. Vehicle and Ticket are pure records, so @dataclass writes their __init__ and __repr__ for us.

models.py
from __future__ import annotations
from dataclasses import dataclass
from enums import VehicleType, SpotType, FITS

@dataclass
class Vehicle:
    license_plate: str
    type: VehicleType

class ParkingSpot:
    def __init__(self, spot_id: str, type: SpotType) -> None:
        self.spot_id = spot_id
        self.type = type
        self.parked_vehicle: Vehicle | None = None

    @property
    def is_free(self) -> bool:
        return self.parked_vehicle is None

    def can_fit(self, vehicle: Vehicle) -> bool:
        # free, and at least as big as the vehicle needs
        return self.is_free and self.type.value >= FITS[vehicle.type].value

    def park(self, vehicle: Vehicle) -> None:
        if not self.is_free:
            raise ValueError(f"spot {self.spot_id} is occupied")
        self.parked_vehicle = vehicle

    def vacate(self) -> None:
        self.parked_vehicle = None

@dataclass
class Ticket:
    ticket_id: str
    vehicle: Vehicle
    spot: ParkingSpot
    entry_hour: int

Finally the coordinator. ParkingLot receives its spots and a pricing strategy (constructor injection — it never builds them itself). park() returns a Ticket, or None when nothing fits.

parking_lot.py
from __future__ import annotations
from models import Vehicle, ParkingSpot, Ticket
from pricing import PricingStrategy

class ParkingLot:
    def __init__(self, spots: list[ParkingSpot],
                 pricing: PricingStrategy) -> None:
        self.spots = spots                 # the lot OWNS its spots (composition)
        self.pricing = pricing             # injected — the lot depends on the interface
        self._counter = 0

    def park(self, vehicle: Vehicle, entry_hour: int = 0) -> Ticket | None:
        for spot in self.spots:
            if spot.can_fit(vehicle):
                spot.park(vehicle)
                self._counter += 1
                return Ticket(f"T{self._counter}", vehicle, spot, entry_hour)
        return None                        # lot full / no fitting spot

    def unpark(self, ticket: Ticket, exit_hour: int) -> float:
        hours = max(1, exit_hour - ticket.entry_hour)   # bill a 1-hour minimum
        ticket.spot.vacate()               # free the spot
        return self.pricing.price(hours)   # delegate the fee to the strategy

05  Step 5 — Pricing with the Strategy pattern

This is the part of the brief that varies: a lot might bill a flat fee, or per-hour, or weekend rates, or early-bird specials. Baking those into ParkingLot with a chain of if/else means editing the lot every time pricing changes. Instead we make pricing a pluggable Strategy: an interface with one method, price(hours), and a family of interchangeable implementations.

pricing.py
from typing import Protocol

class PricingStrategy(Protocol):
    def price(self, hours: int) -> float: ...   # the one varying job

class FlatRate:
    def __init__(self, amount: float) -> None:
        self.amount = amount
    def price(self, hours: int) -> float:
        return self.amount                      # same fee regardless of time

class HourlyRate:
    def __init__(self, per_hour: float) -> None:
        self.per_hour = per_hour
    def price(self, hours: int) -> float:
        return self.per_hour * hours            # bill by the hour

The lot is handed one of these in its constructor and just calls self.pricing.price(hours). Swapping rates is a one-line change at construction — HourlyRate(2.5) instead of FlatRate(20) — with the lot untouched.

Why Strategy? It buys us the Open/Closed Principle

Adding a new pricing rule (say WeekendRate) means writing a new class — never editing ParkingLot or the existing rates. The lot is closed to modification but open to extension. Using a Protocol (structural typing) means a rate class doesn't even need to inherit anything — it just needs a price(hours) method. See Behavioral patterns for Strategy in depth.

06  Walk a scenario

Now the proof: assemble a lot with three spots and an hourly rate, park a car at hour 9, and unpark it at hour 12. The pieces should line up and the fee should be 3 × $2.50 = $7.50.

demo.py
from enums import VehicleType, SpotType
from models import Vehicle, ParkingSpot
from parking_lot import ParkingLot
from pricing import HourlyRate

lot = ParkingLot(
    spots=[
        ParkingSpot("S1", SpotType.SMALL),
        ParkingSpot("M1", SpotType.MEDIUM),
        ParkingSpot("L1", SpotType.LARGE),
    ],
    pricing=HourlyRate(per_hour=2.5),       # swap for FlatRate(20) and nothing else changes
)

car = Vehicle("KA-01-4321", VehicleType.CAR)
ticket = lot.park(car, entry_hour=9)
print(f"Parked {car.license_plate} at spot {ticket.spot.spot_id}")

fee = lot.unpark(ticket, exit_hour=12)      # 3 hours later
print(f"Fee for 3 hours: ${fee:.2f}")
print(f"Spot {ticket.spot.spot_id} free again: {ticket.spot.is_free}")
OutputParked KA-01-4321 at spot M1 Fee for 3 hours: $7.50 Spot M1 free again: True

The car took the MEDIUM spot (the smallest one it fits — the SMALL spot was too small), parked, and on exit the spot was freed and billed correctly. The whole model is under a hundred lines, and every flow in the brief works.

Why does ParkingLot take a PricingStrategy in its constructor instead of containing the pricing if/else itself?

Right: injecting the strategy isolates the varying part. New pricing = new class; the lot stays closed to modification, open to extension.

A CAR needs a MEDIUM spot. With can_fit using spot.type.value >= FITS[vehicle.type].value, which spots can hold a car?

Right: the >= on the enum's int value means a vehicle fits any spot its own size or bigger — a car takes a MEDIUM or a LARGE, never a SMALL. (Whether to "waste" a LARGE on a car is a policy you could refine.)

07  Extensions — your turn

A strong answer ends by showing where the design grows. Each of these is a small, additive change — that's the payoff of a clean model. Try them before peeking.

Exercise 1 · new spot type

Add an electric spot with charging: a new ELECTRIC SpotType and VehicleType, where an electric vehicle needs an electric spot (and a normal car should not take an electric one). How much of the existing code changes?

Hint: the only behavior that needs a special case is can_fit — everything else (the lot, the ticket, the pricing) is untouched. That "barely anything changes" feeling is the Open/Closed Principle paying off.

Show a solution solution

Extend the two enums and the FITS map, then teach can_fit that electric is a dedicated lane rather than a "bigger size":

electric.py
# enums.py — add members (existing ones untouched)
class VehicleType(Enum):
    BIKE = "bike"; CAR = "car"; TRUCK = "truck"
    ELECTRIC = "electric"

class SpotType(Enum):
    SMALL = 1; MEDIUM = 2; LARGE = 3
    ELECTRIC = 4

FITS[VehicleType.ELECTRIC] = SpotType.ELECTRIC

# models.py — the ONLY method that needs special-casing
def can_fit(self, vehicle: Vehicle) -> bool:
    if vehicle.type is VehicleType.ELECTRIC:
        return self.is_free and self.type is SpotType.ELECTRIC
    # non-electric vehicles never take an electric (charging) spot
    return (self.is_free
            and self.type is not SpotType.ELECTRIC
            and self.type.value >= FITS[vehicle.type].value)

ParkingLot, Ticket, and the pricing strategies are all unchanged. You add an electric spot to the lot's spot list and an EV parks itself there — and a regular car correctly refuses it.

Exercise 2 · find nearest spot across floors

Introduce the ParkingFloor entity (multiple levels) and a "find the nearest free spot" — nearest meaning the lowest floor that has a fitting spot. How would you slot this in without rewriting ParkingSpot?

Hint: a floor is just a labelled group of spots. "Nearest" is a search policy over floors sorted by level — and notice it's exactly the kind of rule you could later make its own Strategy.

Show a solution solution

Add a small ParkingFloor dataclass and a search that scans floors lowest-first. ParkingSpot.can_fit is reused verbatim:

floors.py
from dataclasses import dataclass

@dataclass
class ParkingFloor:
    level: int
    spots: list[ParkingSpot]

def find_nearest(floors: list[ParkingFloor],
                 vehicle: Vehicle) -> tuple[int, ParkingSpot] | None:
    for floor in sorted(floors, key=lambda f: f.level):   # lowest floor first
        for spot in floor.spots:
            if spot.can_fit(vehicle):                     # reuse, don't rewrite
                return floor.level, spot
    return None

floors = [
    ParkingFloor(2, [ParkingSpot("2-M1", SpotType.MEDIUM)]),
    ParkingFloor(1, [ParkingSpot("1-S1", SpotType.SMALL),
                     ParkingSpot("1-M1", SpotType.MEDIUM)]),
]
level, spot = find_nearest(floors, Vehicle("KA-9", VehicleType.CAR))
print(f"Nearest spot for car: floor {level}, spot {spot.spot_id}")
OutputNearest spot for car: floor 1, spot 1-M1

ParkingLot.park would now iterate floors via find_nearest instead of a flat list — and if "nearest" later means "closest to the elevator," that ranking becomes its own injectable Strategy. Same Open/Closed move, one level up.

What this design used — the toolkit recap

Enums for the fixed vocabulary (VehicleType, SpotType). Encapsulation — ParkingSpot guards its own occupancy via is_free. Composition — the lot owns its spots and has a pricing strategy, rather than inheriting. Strategy pattern for pricing, which gives us the Open/Closed Principle: new pricing rules and new spot types are new classes, never edits to existing ones. Single Responsibility — spot owns occupancy, lot owns allocation, ticket is just data. That's the whole syllabus, applied to one prompt.
