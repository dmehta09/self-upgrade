SOLID principles · why principles

Why we need design principles.

Almost any code can be made to work. Design is about what happens next month, when the requirements change and you have to touch it again. Principles are the hard-won habits that keep that next change cheap.

01  Working code vs code you can change

Every program in production is "correct enough" today — it ships, the tests pass, the demo works. That's the easy part. The expensive part is everything after: the bug report, the new feature, the changed rule. Software lives for years and is edited far more than it is written.

A house wired for one lightbulb analogy

Two electricians can both make the bulb turn on. One ran clean labelled circuits to a tidy breaker box; the other twisted every wire together behind the drywall. Today the room looks identical. But the day you want to add an outlet, one job takes an afternoon and the other means tearing open the wall. Good design is the labelled breaker box — invisible until you need to change something.

So the real measure of a design isn't "does it run?" — it's the cost of change. Principles exist to keep that cost low: to make the next edit small, local, and safe instead of sprawling and scary.

02  Coupling & cohesion: the two master ideas

Nearly every design principle is, underneath, a trick to improve one of two things. Get these two right and the rest follows.

High cohesion
A class's parts belong together — it has one clear job, and everything inside it serves that job. The opposite is a grab-bag class that calculates, formats, logs, and saves.
Low coupling
Classes don't depend on each other's guts — they talk through small, stable surfaces. Changing the inside of one doesn't ripple into the others.
Tangled Christmas lights analogy

Tightly-coupled code is one of those old strings of lights wired in series: touch one bulb and the whole string flickers or dies, and you can't tell which bulb did it. Loosely-coupled code is modern lights where each bulb is independent — pull one and the rest stay lit. You want the second kind everywhere.

Tight coupling vs loose coupling
tight
A ⇄ B ⇄ C
each knows the others' internals
change B
💥
A and C break too
loose
A → │ ← C
all talk through B's small surface
change B's guts
✓
A and C don't notice
High cohesion keeps a class focused; low coupling keeps a change from spreading.

03  Code smells that signal bad design

You rarely set out to write bad code — it accumulates. These four "smells" are the warning signs that coupling has crept up or cohesion has slipped. Naming them helps you catch the problem before it spreads.

🧱

Rigidity

Every small change forces a cascade of edits across many files. The code resists being changed at all.

🩹

Fragility

A change in one place breaks something seemingly unrelated somewhere else. You fix a bug and create two.

🔗

Immobility

You can't reuse a nice piece without dragging half the system along with it. Everything is entangled.

🌀

Needless complexity

Layers, abstractions, and "flexibility" no one asked for. Cleverness that makes the simple thing hard to find.

Smells are symptoms, not diagnoses

A smell tells you something is off, not exactly what. Rigidity and fragility usually trace back to high coupling; a class that's hard to name or reuse usually has low cohesion. SOLID is the prescription.

04  Supporting principles you'll lean on

SOLID is the headline act, but it stands on a few simpler, older rules of thumb. You'll meet these constantly, so learn the acronyms now.

DRY
Don't Repeat Yourself. Each piece of knowledge lives in exactly one place. Copy-pasted logic means copy-pasted bugs and edits you'll forget to make in all the copies.
KISS
Keep It Simple, Stupid. Prefer the plainest thing that works. Complexity has to earn its place.
YAGNI
You Aren't Gonna Need It. Don't build for an imagined future. Add the abstraction when the real need shows up, not before.
Favour Composition over Inheritance
Reach for "has-a" (hold an object as a field) before "is-a" (subclassing). Composition keeps parts swappable and coupling loose.
Law of Demeter
"Only talk to your immediate friends." Avoid a.b.c.do_thing() chains that reach deep into other objects' internals — ask your neighbour, don't rummage through its drawers.
They all serve the same goal

DRY, KISS, YAGNI, composition, Demeter — every one of them, in its own way, lowers coupling or raises cohesion. That's the through-line. SOLID just makes the same goal explicit and systematic.

05  Meet SOLID

SOLID is five principles, one per letter, introduced by Robert C. Martin. Each targets a specific way designs go wrong. Here's the map; the next page gives each one a bad→good example.

LetterNameOne-liner
SSingle ResponsibilityA class should have one reason to change.
OOpen/ClosedOpen for extension, closed for modification.
LLiskov SubstitutionSubtypes must be usable anywhere the base is, without surprises.
IInterface SegregationDon't force clients to depend on methods they don't use.
DDependency InversionDepend on abstractions, not concretions — and inject them.

06  Check yourself

"High cohesion" in a class means…

Right: cohesion is about focus — everything inside the class works toward a single responsibility. (Depending on many other classes is high coupling, which you want low.)

You fix a bug in the reporting module and the unrelated login flow suddenly breaks. Which code smell is that?

Right: when a change breaks something seemingly unrelated, that's fragility — a classic symptom of high coupling between parts that shouldn't know about each other.
