SOLID principles · the five

The five SOLID principles.

Five rules, one goal: keep change cheap by lowering coupling and raising cohesion. We take each in turn — a one-line statement, an analogy, then a bad version and the fix in real Python.

01  Single Responsibility (SRP)

"A class should have one reason to change." If a class does several unrelated jobs, every one of those jobs is a reason to come back and edit it — and edits collide.

A one-person company analogy

Imagine one person doing accounting and sales and shipping. When the tax rules change, the sales pitch changes, and the courier changes — all three land on the same overworked desk, and a slip in one spills into the others. Split the roles and each person changes for one reason only.

Here an Invoice calculates totals, formats itself, and saves to a database. Three responsibilities, three reasons to change. Split them.

class Invoice:
    def __init__(self, items: list[tuple[str, float]]):
        self.items = items

    def total(self) -> float:                 # job 1: calculate
        return sum(price for _, price in self.items)

    def to_text(self) -> str:                  # job 2: format
        lines = [f"{name}: ${p}" for name, p in self.items]
        return "\n".join(lines) + f"\nTOTAL: ${self.total()}"

    def save(self) -> None:                    # job 3: persist
        with open("invoice.txt", "w") as f:    # DB/file coupling lives here
            f.write(self.to_text())

# Three unrelated reasons to edit this one class.
inv = Invoice([("Book", 12), ("Pen", 3)])
inv.save()
from dataclasses import dataclass

@dataclass
class Invoice:                                 # only data + calculation
    items: list[tuple[str, float]]
    def total(self) -> float:
        return sum(price for _, price in self.items)

class InvoiceFormatter:                        # only formatting
    def to_text(self, inv: Invoice) -> str:
        lines = [f"{name}: ${p}" for name, p in inv.items]
        return "\n".join(lines) + f"\nTOTAL: ${inv.total()}"

class InvoiceRepository:                        # only persistence
    def save(self, text: str, path: str) -> None:
        with open(path, "w") as f:
            f.write(text)

inv = Invoice([("Book", 12), ("Pen", 3)])
text = InvoiceFormatter().to_text(inv)
print(text)
InvoiceRepository().save(text, "invoice.txt")
Output (Fixed version)Book: $12 Pen: $3 TOTAL: $15
"Responsibility" = a source of change

The test isn't "how many methods?" but "who would ask me to change this?" Accounting changes the calculation; a designer changes the format; an ops engineer changes how it's stored. Three audiences → three classes.

02  Open/Closed (OCP)

"Open for extension, closed for modification." You should be able to add new behavior by adding new code, not by editing code that already works (and that you might break).

Power tools with swappable bits analogy

A good drill doesn't get rebuilt every time you need a new bit — you snap in a different head. The drill is closed (you never open it up), yet open to new attachments. New behaviour plugs in; the proven body stays untouched.

The smell is a growing if/elif ladder over a type field. Every new item type means editing the same function. Make each item compute its own price instead — pure polymorphism.

class Item:
    def __init__(self, kind: str, base: float):
        self.kind, self.base = kind, base

def total_price(items: list[Item]) -> float:
    total = 0.0
    for item in items:
        if item.kind == "book":            # add a type? edit this function
            total += item.base * 0.9       # books: 10% off
        elif item.kind == "food":
            total += item.base * 1.05      # food: +5% tax
        elif item.kind == "electronics":
            total += item.base * 1.18
        # ...one more elif for every future kind
    return total

print(total_price([Item("book", 100), Item("food", 20)]))   # 111.0
from abc import ABC, abstractmethod

class Item(ABC):
    def __init__(self, base: float):
        self.base = base
    @abstractmethod
    def price(self) -> float: ...

class Book(Item):
    def price(self) -> float: return self.base * 0.9

class Food(Item):
    def price(self) -> float: return self.base * 1.05

class Electronics(Item):
    def price(self) -> float: return self.base * 1.18

def total_price(items: list[Item]) -> float:    # never changes again
    return sum(item.price() for item in items)

# A new kind = a new class. total_price is closed for modification.
print(total_price([Book(100), Food(20)]))       # 111.0
Output111.0
This is polymorphism doing the work

OCP is the four-pillars idea of polymorphism turned into a design rule. The same trick powers the Strategy pattern: inject a discount object and you can vary pricing without touching the caller.

03  Liskov Substitution (LSP)

"Subtypes must be usable anywhere the base is, without surprises." If code works with a Bird, handing it any subclass of Bird must not break its expectations.

A toy duck that's labelled "duck" analogy

The recipe says "use a duck." A rubber bath duck is technically a "duck," but try to make it lay an egg or fly and the recipe falls apart. If a subtype can't honour the promises of its base type, it shouldn't claim to be that type. A penguin is a bird — but if Bird promises fly(), a Penguin can't keep that promise.

The classic break: a Penguin subclassing a Bird whose contract includes fly(). The fix is to stop forcing flight into the base — model flight separately so penguins simply don't claim it.

class Bird:
    def fly(self) -> str:
        return "flap flap, airborne!"

class Penguin(Bird):
    def fly(self) -> str:
        raise NotImplementedError("penguins can't fly")  # broken promise

def let_it_fly(bird: Bird) -> None:
    print(bird.fly())            # works for Bird... explodes for Penguin

let_it_fly(Bird())               # flap flap, airborne!
let_it_fly(Penguin())            # NotImplementedError: penguins can't fly
from abc import ABC, abstractmethod

class Bird(ABC):                 # base promises only what ALL birds do
    @abstractmethod
    def eat(self) -> str: ...

class FlyingBird(Bird):          # flight is its own, narrower contract
    @abstractmethod
    def fly(self) -> str: ...

class Sparrow(FlyingBird):
    def eat(self) -> str: return "peck peck"
    def fly(self) -> str: return "flap flap, airborne!"

class Penguin(Bird):             # a Bird, but never claims fly()
    def eat(self) -> str: return "gulp fish"

def let_it_fly(bird: FlyingBird) -> None:
    print(bird.fly())            # only ever handed things that CAN fly

let_it_fly(Sparrow())            # flap flap, airborne!
# let_it_fly(Penguin()) -> a type checker rejects this; no runtime surprise
Output (Fixed version)flap flap, airborne!
Square is not a Rectangle (in code)

The other famous trap: Square(Rectangle). A rectangle lets you set_width and set_height independently; a square must keep them equal, so setting width silently changes height — breaking any code that trusted the rectangle's contract. The "is-a" of geometry isn't an "is-a" of behaviour. Model them separately, or compose, rather than subtyping.

04  Interface Segregation (ISP)

"Don't force clients to depend on methods they don't use." Many small, focused interfaces beat one fat one that makes implementers stub out methods they'll never support.

An all-in-one remote analogy

A universal remote with 80 buttons for a TV you bought to do one thing. You want volume and channel; instead you hunt past "FAX," "DVD eject," and "satellite tuner." A small remote that does exactly your device's job is easier to use — and easier to build.

A fat Machine interface forces a simple printer to implement scan and fax it can't do. Split it into small Protocols and each device implements only what it truly supports.

from abc import ABC, abstractmethod

class Machine(ABC):              # one fat interface
    @abstractmethod
    def print_(self, doc: str) -> str: ...
    @abstractmethod
    def scan(self, doc: str) -> str: ...
    @abstractmethod
    def fax(self, doc: str) -> str: ...

class SimplePrinter(Machine):    # can only print, yet must implement all three
    def print_(self, doc: str) -> str: return f"printing {doc}"
    def scan(self, doc: str) -> str:
        raise NotImplementedError("no scanner")   # forced, useless stub
    def fax(self, doc: str) -> str:
        raise NotImplementedError("no fax")       # forced, useless stub
from typing import Protocol

class Printer(Protocol):
    def print_(self, doc: str) -> str: ...

class Scanner(Protocol):
    def scan(self, doc: str) -> str: ...

class Fax(Protocol):
    def fax(self, doc: str) -> str: ...

class SimplePrinter:             # implements ONLY what it can do
    def print_(self, doc: str) -> str: return f"printing {doc}"

class AllInOne:                  # opts into several small contracts
    def print_(self, doc: str) -> str: return f"printing {doc}"
    def scan(self, doc: str) -> str:  return f"scanning {doc}"
    def fax(self, doc: str) -> str:   return f"faxing {doc}"

def send_to_print(p: Printer, doc: str) -> None:  # asks for the narrow contract
    print(p.print_(doc))

send_to_print(SimplePrinter(), "report.pdf")      # printing report.pdf
send_to_print(AllInOne(), "memo.pdf")             # printing memo.pdf
Output (Fixed version)printing report.pdf printing memo.pdf
Protocols make ISP painless

Because a Protocol is satisfied structurally, a class only "implements" an interface by having the right methods — it never inherits stubs it can't fulfil. A function asks for the smallest contract it needs (Printer), and anything print-shaped fits.

05  Dependency Inversion (DIP)

"Depend on abstractions, not concretions — and inject them." High-level policy (what your app does) shouldn't be welded to low-level details (which email library you use). Both should meet at an abstraction.

A wall socket, not a soldered wire analogy

Your lamp doesn't have its wires soldered directly into the power station. It ends in a plug that fits a standard socket — the abstraction. Swap the lamp for a phone charger; the socket doesn't care. Hard-wiring EmailSender() inside a service is soldering. A Notifier contract is the socket.

An OrderService that constructs its own EmailSender() can never send SMS, and can't be tested without sending real email. Depend on a Notifier Protocol and pass it in.

class EmailSender:
    def send(self, msg: str) -> str:
        return f"EMAIL: {msg}"

class OrderService:
    def __init__(self):
        self.sender = EmailSender()       # hard-wired concretion
    def place(self, item: str) -> None:
        # ...business logic...
        print(self.sender.send(f"Order placed: {item}"))

OrderService().place("Book")              # EMAIL: Order placed: Book
# Want SMS? Edit OrderService. Want a test? You still send real email.
from typing import Protocol

class Notifier(Protocol):                 # the abstraction both sides meet at
    def send(self, msg: str) -> str: ...

class EmailSender:
    def send(self, msg: str) -> str: return f"EMAIL: {msg}"

class SmsSender:
    def send(self, msg: str) -> str: return f"SMS: {msg}"

class FakeSender:                          # for tests — records, sends nothing
    def __init__(self): self.sent: list[str] = []
    def send(self, msg: str) -> str:
        self.sent.append(msg); return f"FAKE: {msg}"

class OrderService:
    def __init__(self, notifier: Notifier):   # injected, not constructed
        self.notifier = notifier
    def place(self, item: str) -> None:
        print(self.notifier.send(f"Order placed: {item}"))

OrderService(EmailSender()).place("Book")  # EMAIL: Order placed: Book
OrderService(SmsSender()).place("Pen")     # SMS: Order placed: Pen
Output (Fixed version)EMAIL: Order placed: Book SMS: Order placed: Pen

Inject at the edge, decide once

"Dependency injection" is just passing collaborators in (here via __init__) rather than newing them up inside. The choice of concrete Notifier moves to one place — the program's entry point — and tests slot in a FakeSender for free.

06  Recap: five smells, five fixes

LetterPrincipleThe smell it fixes
SSingle ResponsibilityA "god class" that changes for many unrelated reasons.
OOpen/ClosedAn if/elif ladder you must edit for every new case.
LLiskov SubstitutionA subclass that breaks the base type's promises (surprise exceptions).
IInterface SegregationFat interfaces forcing empty/raising stub methods.
DDependency InversionHigh-level code hard-wired to a concrete detail; untestable.

Notice the common thread: every fix either lowers coupling (O, L, I, D) or raises cohesion (S). That's the whole point of SOLID — five named moves toward the same goal of managing change.

Penguin(Bird) overrides fly() to raise NotImplementedError. Which principle does this violate?

Right: the penguin can't stand in for a Bird wherever fly() is expected — it breaks the base type's contract with a surprise exception. That's a Liskov violation. The fix: don't model it as a flying bird.

To follow Dependency Inversion, what should OrderService depend on?

Right: depend on the abstraction (Notifier) and have it injected. Now you can pass email, SMS, or a fake in tests — without touching OrderService.

You keep editing total_price() every time a new product category appears. Which principle should you reach for?

Right: the growing if/elif ladder is the Open/Closed smell. Make price() polymorphic so a new category is a new class, and total_price() never changes again.
