Function / tool calling IV

This is the bedrock skill of the whole module — and a near-guaranteed interview topic. You'll describe your functions to the model as schemas, the model will emit a structured request to call one, your code will run it and return the result, and the model will continue. We'll walk the full loop, then cover the things interviewers love to probe: parallel calls, forced vs auto tool choice, multi-step chains, and what happens when a tool errors out.

01  Tools are functions you describe to the model

You don't give the model your actual Python function — you give it a schema: a structured description of what the function is called, what it does, and what arguments it takes (usually as JSON Schema). The model reads that menu and decides whether and how to call each tool.

A restaurant menu, not the kitchen analogy

A schema is a menu item: a name (“Margherita pizza”), a description (“wood-fired, tomato & basil”), and the options you can pick (size, extra toppings). The diner — the model — reads the menu and places an order; it never sees the kitchen. A vague menu (“Item #3”) gets you the wrong dish. The description is how the model decides which tool fits the user's request, so write it like you're explaining the tool to a new teammate, not naming a variable.

A tool schema has three parts that matter:

name
A stable identifier like get_weather. The model emits this verbatim when it wants the tool.
description
Plain-language: what it does and when to use it. This is the single biggest lever on whether the model picks the right tool at the right time.
parameters
A JSON Schema of the arguments — names, types, which are required, allowed enum values. This constrains what the model is allowed to fill in.
tool_schema.py
weather_tool = {
    "name": "get_weather",
    # The description is doing the heavy lifting — be specific.
    "description": "Get the CURRENT weather for a city. "
                   "Use when the user asks about weather right now, "
                   "not forecasts or historical data.",
    "parameters": {
        "type": "object",
        "properties": {
            "city": {"type": "string", "description": "City name, e.g. 'Paris'"},
            "units": {"type": "string", "enum": ["celsius", "fahrenheit"]},
        },
        "required": ["city"],
    },
}
Bad descriptions are the #1 cause of wrong tool calls gotcha

When a model calls the wrong tool, skips a tool it should have used, or invents arguments, the fix is almost never a smarter model — it's a clearer schema. Spell out when to use the tool and when not to, give example argument values, and use enums to lock down choices. Too many overlapping tools also hurts: if two tools sound alike, the model will flip-flop. Treat schema-writing as prompt engineering, because that's exactly what it is.

02  The full loop, message by message

Tool use is a multi-turn exchange even when it looks like one call to the user. Watch the message list grow:

Anatomy of one tool round-trip
1 · you send
messages + tools
user question + the schema menu
2 · model replies
tool_call
name + JSON args, then stops
3 · you run it
execute + append
add a tool-result message
4 · model finishes
natural-language answer
or asks for another tool
The key insight: a tool result is just another message you append to the conversation, then re-send. The model's tool-call message and your tool-result message both become permanent history, so the model "remembers" what it asked and what came back.
loop.py
messages = [{"role": "user", "content": "What's the weather in Paris?"}]

resp = model.generate(messages=messages, tools=[weather_tool])

if resp.stop_reason == "tool_use":            # the model asked for a tool
    call = resp.tool_calls[0]                  # name + parsed arguments
    result = run_tool(call.name, call.args)    # <-- YOUR code executes it

    messages.append(resp.message)              # 1) the model's tool request
    messages.append({                          # 2) the tool's result
        "role": "tool",
        "tool_call_id": call.id,               # must match the request
        "content": str(result),
    })
    resp = model.generate(messages=messages, tools=[weather_tool])  # continue

print(resp.text)   # "It's 18°C and drizzling in Paris."

Exact field names differ by SDK, but every provider follows this same append-the-result-and-resend pattern. The tool_call_id is how the model matches a result to the request it made — essential once there are several calls in flight.

03  Parallel tool calls

Modern models can ask for several tools at once in a single turn when the calls don't depend on each other — "compare the weather in Paris, Tokyo, and Lima" yields three get_weather calls together. You run them (ideally concurrently), append all the results, and resend.

How to say it out loud say it

“When sub-tasks are independent, the model can emit parallel tool calls in one turn. I execute them concurrently to cut latency, then append every result — each tagged with its call id — before resending. If a call depends on another's output, it has to be sequential instead, which means another round-trip.”

The catch: parallel only works for independent calls. If tool B needs tool A's output (look up a user ID, then fetch their orders), the model must do them in separate turns — that's sequential, multi-step tool use, which is the next idea.

04  Forced vs auto tool choice

You control how much freedom the model has to decide on tools, via a tool_choice setting:

SettingBehaviourUse when…
autoModel decides whether to call a tool or just answer in text.The default — a chat assistant that might need a tool.
required / anyModel must call some tool (its choice which), can't answer in plain text.You know the turn needs an action — e.g. a router that must pick a function.
forced (named)Model must call this specific tool.Extracting structured data, or guaranteeing a step happens.
noneTools are visible but the model can't call them this turn.You want a plain answer while keeping tools in context.

Forcing a named tool is a clean trick for structured outputs: define a tool whose parameters are the schema you want, force it, and read the arguments as your typed result.

05  Multi-step tool use is the seed of an agent

Most real tasks need more than one round. The model calls a tool, sees the result, and based on it decides the next tool — looping until it has enough to answer. You implement this by wrapping the loop from §2 in a while: keep going as long as the model keeps asking for tools.

agent_loop.py
messages = [{"role": "user", "content": "How many orders did Acme place last week?"}]

while True:
    resp = model.generate(messages=messages, tools=ALL_TOOLS)
    messages.append(resp.message)

    if resp.stop_reason != "tool_use":
        break                                  # model gave a final answer

    for call in resp.tool_calls:               # e.g. find_customer -> then get_orders
        result = run_tool(call.name, call.args)
        messages.append({"role": "tool",
                         "tool_call_id": call.id,
                         "content": str(result)})

print(resp.text)

That while loop, plus a goal and a stopping rule, is the core of an agent. Everything in the Agents module — memory, planning, multi-agent patterns — is built on top of exactly this. Tool calling is where agents begin.

Frameworks make tools a one-line decorator note

We teach the concept here. In practice you rarely hand-write JSON schemas — frameworks generate them from your function's signature and docstring. See the Lang Stack guide (../../langstack/index.html) for how a @tool decorator and LangChain/LangGraph tool-calling turn a plain Python function into a model-ready tool, loop and all.

06  Errors & formatting tool results

Tools fail — APIs time out, arguments are invalid, a record doesn't exist. The trick that surprises people: don't crash the loop on an error — tell the model about it. Return the error as the tool result and let the model react (retry with different arguments, try another tool, or explain to the user).

tool_errors.py
def run_tool(name, args):
    try:
        return TOOLS[name](**args)
    except Exception as e:
        # Hand the error back AS the result — the model can recover from it.
        return {"error": str(e), "hint": "Check the arguments and retry."}

A few formatting habits that pay off:

Be concise
Tool results are tokens in the context window. Return the fields the model needs, not a 5,000-row dump — trim, summarise, paginate.
Stay structured
JSON or clean key–value text reads far better to the model than a raw HTML blob. Make the signal easy to find.
Errors are data
A clear, short error message lets the model self-correct. A stack trace mostly just burns tokens.
Say it again: the model proposes, your code disposes gotcha

The model emits a request to call a function — it never executes anything itself. That means you own validation, authentication, rate limits, and especially side effects. Never wire a model's raw tool call straight to "delete the database" or "wire the money." Treat every argument the model produces as untrusted input: validate it, scope permissions tightly, and require confirmation for destructive actions. The model is a planner, not a trusted operator.

How to say it out loud say it

“The model emits a tool call — name plus JSON arguments — and stops. My code executes it and appends the result as a new message, then resends so the model can continue. I handle independent calls in parallel, loop for multi-step tasks, and return errors as tool results so the model can recover. Because the model only proposes the call, I validate every argument and gate destructive actions on my side.”

07  Self-check

Your model keeps calling search_orders when the user clearly wants search_products. What's the first thing to fix?
Wrong-tool selection is overwhelmingly a schema problem. The description is how the model disambiguates between tools; vague or overlapping descriptions cause exactly this. Clarify each tool's purpose, add example arguments, and the routing usually fixes itself — no bigger model needed.
“Walk me through what actually happens in a function call.”Core
Model answer

I send the conversation plus a list of tool schemas. If the model wants a tool, it replies with a structured tool-call message — function name and JSON arguments — and stops. My application parses that, runs the real function, and appends the output as a tool-result message tagged with the call id. I resend the whole conversation; now the model has the result in context and either answers or requests another tool. The model never executes anything itself.

How to say it out loud say it

“Send tools, model emits a call and stops, I run it and append the result, resend, model continues. The tool result is just another message in the history.”

“When would you force a specific tool instead of leaving it on auto?”Core
Model answer

When I know the turn requires a particular action and don't want the model to chat instead. Two classic cases: extracting structured data — I force a tool whose parameters are my target schema and read the arguments back as typed output; and guaranteeing a step in a pipeline, like always calling a moderation or classification tool. Auto is right for open-ended assistants; forced is right when the action is non-negotiable.

How to say it out loud say it

“Force a tool when the action is mandatory — structured extraction or a guaranteed pipeline step. Leave it on auto for open-ended chat where a tool is only sometimes needed.”
