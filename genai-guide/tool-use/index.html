Tool use — overview

A plain language model can only do one thing: produce text. It can't check today's weather, query your database, or send an email — it just writes about doing those things. Tool use changes that. You hand the model a menu of functions it's allowed to call, and now it can reach out into the real world: look things up, do exact math, take actions. This module is about how that loop actually works — and how a 2026 standard called MCP turned a thousand bespoke integrations into one universal plug.

01  The brain that can finally press buttons

An LLM on its own is a brilliant brain locked in a sealed room with no hands. It has read the internet and can reason about almost anything, but it can't do anything — no live data, no calculator it can trust, no way to act. Ask it the current Bitcoin price and it will confidently make one up, because guessing plausible text is the only move it has.

A brain in a jar — now with a control panel analogy

Picture a genius floating in a jar. They can answer anything from memory, but they can't open a window or pick up a phone. Tool use bolts a control panel onto the jar — labelled buttons like get_weather, search_db, send_email. The brain still can't push the buttons itself; instead it says out loud which button it wants and with what settings, and an assistant outside the jar (your code) actually presses it and reads the result back in. Suddenly the brain can act on the world — but always through that assistant.

That last sentence is the whole module in miniature: the model decides which tool and with what arguments; your application does the pressing. Everything else is detail on top of that split.

02  The request → execute → return loop

Tool use is not magic and it is not a single API call. It's a small conversation loop that bounces between the model and your code. Here's the shape every framework, SDK, and protocol implements underneath:

One round of tool use
1 · ask
model requests a tool
"call get_weather(city='Paris')"
2 · execute
YOUR app runs it
real API / DB / function
3 · return
result goes back
"18°C, light rain"
4 · continue
model writes the answer
"It's 18°C and drizzling in Paris."
The model never touches the outside world. It asks in step 1, pauses, and your code closes the loop by feeding the result back in step 3 — then the model picks up where it left off. If it needs another tool, the loop simply runs again.
The model does not run the tool gotcha

This trips up almost everyone at first. When the model "calls a function," it doesn't execute anything — it just emits a structured message that says "I'd like to call get_weather with these arguments." It then stops and waits. Your application is responsible for actually running that function and handing the result back. The model is the planner; your code is the hands. Keep that boundary crisp and the rest of this module is easy.

03  Why tool use unlocks everything else

Three capabilities that a bare LLM lacks all arrive the moment you give it tools:

Fresh & private facts
A model's knowledge is frozen at its training cutoff. A search or query_db tool lets it read today's data — prices, tickets, your internal wiki — instead of guessing. (This is exactly how agentic RAG retrieves.)
Exact actions, not vibes
LLMs are shaky at precise arithmetic and can't actually move money. A calculator or create_invoice tool offloads the exact, side-effecting work to real code that's correct by construction.
Agency — doing, not just saying
String several tool calls together in a loop and the model can plan, act, observe, and adjust. That loop is an agent. Tool use is the single feature that turns a chatbot into something that gets work done.
How to say it out loud say it

“A plain LLM can only generate text. Tool use gives it a defined set of functions it can request — the model emits a structured call, my application executes it and returns the result, and the model continues with that result in context. It's what lets a model fetch live data, do exact operations, and take real actions. Chain those calls in a loop and you've got an agent.”

04  A quick vocabulary check

People use several words for the same idea. Don't let the jargon confuse you — in 2026 these all point at the same loop:

TermWhat it really means
Function callingThe original name: the model outputs a function name + arguments. An API-level feature of the model.
Tool use / tool callingThe same thing, broader label. A "tool" is just a function you've described to the model.
MCPA standard protocol for exposing tools (and data) to any model/app. It standardizes function calling — it doesn't replace it.
AgentA program that runs the tool loop repeatedly to pursue a goal. Tools are the agent's hands.

If an interviewer says "function calling" and you say "tool use," you're agreeing. The distinction that does matter is MCP vs the rest — and we'll make that crisp on the MCP page.

06  Self-check

A teammate says “we gave the model a weather tool, so now the model fetches the forecast itself.” What's the precise correction?
The model emits a structured tool-call message and then waits. Running the actual API and returning the result is your application's job. The model is the decision-maker; your code is the executor. Keeping that split clear is the core mental model of the whole module.
“What is tool use, in one breath?”Warm-up
Model answer

It's giving a language model a set of functions it can call. The model can't act on its own, so when it needs live data or an action it emits a structured request for a specific function with arguments; your application runs it and returns the result; the model then continues its answer with that result in context.

How to say it out loud say it

“Tool use lets the model request functions it can't run itself. It asks, my code executes and returns the result, the model continues. That's how it reaches live data and takes real actions.”

“How does tool use relate to agents?”Core
Model answer

Tool use is the primitive; an agent is the loop built on top of it. A single tool call is one request-execute-return cycle. An agent runs that cycle repeatedly — call a tool, read the result, decide the next step — until a goal is met. Without tool use an agent has nothing to act with; it's just chatting.

How to say it out loud say it

“One tool call is a single ask-execute-return cycle. An agent just runs that loop over and over toward a goal. Tools are the hands; the agent loop is the will.”
