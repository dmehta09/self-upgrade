Computer use & code execution NEW

Most tools are narrow — one function, one job. This page covers two general-purpose tools that blew the doors open in 2025–26. Computer use gives a model a screen and a mouse, so it can operate any app a human can. Code execution hands it a sandbox to write and run code, making it its own most flexible tool. Both trade huge power for real questions about safety and speed — exactly the trade-off interviewers want you to reason about.

01  Computer use: a model with eyes and a mouse

A computer-use (or "browser-use") agent doesn't call a tidy API. It works the way you do: it looks at a screenshot of the screen, decides on an action — click here, type that, scroll — and emits it as a tool call. Your runner performs the action, takes a fresh screenshot, and the loop repeats until the task is done.

A remote worker on a screen-share analogy

Picture hiring someone who can only see your screen through a video call and steer it by telling you "click the blue Submit button." They can't peek at the database or the page's code — they read the pixels, like a person would. That's computer use: the model navigates by sight, so it works on apps that have no API at all. Powerful and universal — but, like that remote worker squinting at a screen-share, slower and more error-prone than a clean API call.

It's the same ask→execute→return loop from the rest of the module — the "tool" is just the desktop, and the result is a fresh screenshot. The model is using vision to read the screen each step.

02  Code execution: the model's most general tool

The other power tool is letting the model write code and run it in a sandbox — a "code interpreter." Instead of you predicting every function it might need, you give it one tool: here's a Python environment, write whatever you want and I'll run it and return the output.

This is astonishingly flexible. Need exact math, a CSV parsed, a chart plotted, 10,000 rows filtered? The model doesn't fake it in prose — it writes the code, runs it, reads the real result, and can debug its own errors by looking at the traceback and trying again.

code_tool.py
# ONE tool replaces dozens of hand-written ones:
code_tool = {
    "name": "run_python",
    "description": "Execute Python in a sandbox and return stdout/result. "
                   "Use for math, data wrangling, parsing, or plotting.",
    "parameters": {
        "type": "object",
        "properties": {"code": {"type": "string"}},
        "required": ["code"],
    },
}
# The model might emit:  run_python(code="print(sum(2**i for i in range(20)))")
# Your sandbox runs it and returns "1048575" — exact, not guessed.
How to say it out loud say it

“A code-execution tool turns the model into its own toolmaker — instead of me writing a function per task, it writes and runs code in a sandbox and reads the real output. It's the most general tool there is, which is exactly why it must run isolated: no network, no host filesystem, with CPU and time limits.”

03  The trade-offs: power vs safety vs latency

General tools are powerful precisely because they're unconstrained — and that's also what makes them risky and slow. The interview move is to name all three axes:

Computer useCode execution
PowerOperates any app, even with no APIArbitrary computation & data work
Safety riskCan click destructive buttons; sees whatever's on screenArbitrary code = must sandbox hard (no net, no host FS)
LatencyHigh — many screenshot→action round-trips, each a vision callModerate — run + sometimes debug loops
ReliabilityBrittle — a moved button or popup can derail itSturdier — but bad code can loop or crash
Never run model-authored code or actions unsandboxed gotcha

The model decides; your environment executes — and here it's executing arbitrary code or arbitrary clicks. Run it in an isolated sandbox or virtual machine with no access to your network, secrets, or host filesystem, with CPU/time limits and human confirmation for anything destructive. And because computer-use agents read whatever's on screen, a malicious web page can attempt prompt injection through what the model "sees." Treat both as untrusted by default.

04  When a code tool beats a hand-written tool

So when do you reach for the general tool instead of writing a specific function? A simple rule:

Reach for a code tool when…
the task space is open-ended or unpredictable — ad-hoc data analysis, one-off transformations, exact math, plotting. You can't pre-write a function for every possible request, so let the model compose the solution.
Write a specific tool when…
the task is known, repeated, and has side effects — charge_card, send_email, create_ticket. A narrow tool is safer (tight inputs, clear permissions), faster, and far easier to audit and rate-limit.
Reach for computer use when…
there's simply no API — a legacy desktop app, a site behind a login with no integration. It's the tool of last resort, not first choice, because it's the slowest and most brittle.
How to say it out loud say it

“I match the tool's generality to the task. Known, repeated, side-effecting work gets a narrow, audited function. Open-ended computation gets a sandboxed code tool so the model can write its own solution. Computer use is the last resort — only when there's literally no API — because it's the slowest and most brittle. More generality means more power but more risk, so I don't reach for it unless I need it.”

05  Self-check

A user needs the model to total an arbitrary uploaded spreadsheet and chart the result. Which tool fits best, and why?
The task is open-ended (any spreadsheet, any analysis), so you can't pre-write a function for it — and computer use would be needlessly slow and brittle for pure computation. A code tool lets the model write and run real code for exact math and plotting. Just be sure that sandbox has no network or host-filesystem access.
“How does a computer-use agent actually work?”Core
Model answer

It runs the standard tool loop with the desktop as the tool. The model receives a screenshot, decides on an action — click at coordinates, type text, scroll — and emits it as a tool call. A runner performs that action on a real or virtual machine, captures a fresh screenshot, and feeds it back. It repeats until the task is done. The model navigates by vision, so it can drive apps with no API — at the cost of latency and brittleness.

How to say it out loud say it

“Screenshot in, action out, repeat. It reads the screen with vision and clicks/types like a person, so it works on apps with no API — slower and more fragile, but universal.”

“What's the biggest risk with code execution and computer use, and how do you contain it?”Stretch
Model answer

The model is generating arbitrary code or arbitrary actions, so a mistake or an injection can do real damage — wipe files, exfiltrate secrets, click destructive buttons. Containment: run everything in an isolated sandbox or VM with no network egress, no access to host filesystem or secrets, and CPU/time limits. Require human confirmation for destructive or irreversible actions, and treat anything the agent reads — a web page, a screenshot — as untrusted input that could carry a prompt-injection payload.

How to say it out loud say it

“Arbitrary code or clicks = arbitrary blast radius. Sandbox with no network or host access, set resource limits, gate destructive actions on human approval, and treat everything it reads as a possible injection.”
