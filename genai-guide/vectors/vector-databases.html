Vector databases & ANN IV

Once you have millions of embeddings, the question becomes: how do I find the closest few to a query, fast? Checking every vector is correct but far too slow at scale, so we trade a sliver of accuracy for enormous speed using Approximate Nearest Neighbour (ANN) search. This page demystifies the two indexes you'll be asked about — HNSW and IVF — the distance metrics, the build-vs-query trade-offs, the database landscape, and the metadata-filtering gotcha that bites real systems.

01  What a vector database is for

A vector database stores embeddings and answers one core query incredibly fast: “given this query vector, return the k most similar stored vectors.” That's it. Around that core it adds the things production needs: metadata stored alongside each vector (so you can filter), an index that makes search fast, plus updates, deletes, persistence and scaling.

Asking a city for the nearest coffee shop analogy

You're standing somewhere in a huge city and want the five nearest coffee shops. You could measure the distance to every café in town and sort — guaranteed correct, hopelessly slow. Or you glance at a map, see which district you're in, and check only the cafés nearby — almost always right, a thousand times faster. The first is exact search; the second is approximate search. A vector database is the map that lets you skip straight to the right neighbourhood.

02  Exact vs Approximate Nearest Neighbour

Exact nearest-neighbour search (also called brute-force or “flat”) compares the query to every stored vector. It's 100% accurate and perfectly fine for thousands of vectors — but its cost grows linearly, so at millions or billions it becomes too slow and expensive for live queries.

Approximate nearest-neighbour (ANN) search builds a clever index so the query only visits a tiny fraction of vectors. It might occasionally miss a true neighbour, but it's orders of magnitude faster. We measure that miss rate with recall: the fraction of the true top-k that the approximate search actually returned. Real systems tune for something like 95–99% recall — nearly perfect results, a fraction of the cost.

Exact (flat / brute-force)Approximate (ANN)
Accuracy100% (the true top-k)~95–99% recall (tunable)
Speed at scaleLinear — slow past ~10⁵–10⁶Sub-linear — fast at billions
Use whenSmall / static sets; exactness requiredLarge corpora; live latency budget
“ANN” here is the algorithm, not a neural net gotcha

In this module ANN = Approximate Nearest Neighbour, a search technique — not “artificial neural network.” Same three letters, totally different thing. Interviewers occasionally probe whether you know the difference; say “approximate nearest neighbour” in full the first time and you're safe.

03  The two big indexes: HNSW & IVF

Almost every ANN index is a variation on two ideas: build a navigable graph (HNSW) or group vectors into clusters (IVF). Here's the intuition for each.

Two ways to skip the brute-force scan
HNSW — a navigable graph
Hierarchical Navigable Small World. Picture a road network with a few long motorways and many local streets, stacked in layers. Search starts on the sparse top layer, takes big hops toward the query, then drops to denser layers for fine-grained local steps — like zooming in on a map. Each step greedily moves to whichever connected vector is closer to the query. Fast and high-recall; the default index in most vector DBs (as of June 2026). Downside: it lives in memory and is costlier to build and update.
IVF — clusters (inverted file)
Inverted File index. First, group all vectors into clusters and compute each cluster's centroid (its “district centre”). At query time, find the few centroids nearest the query and search only the vectors in those clusters — ignoring the rest. The knob nprobe sets how many clusters to open: more clusters = higher recall, slower search. Cheaper memory, great for huge static datasets; recall depends on good clustering.
HNSW = “follow the road graph toward the target.” IVF = “only look inside the nearest districts.” Many real indexes combine IVF with compression (e.g. IVF-PQ) to shrink memory further.

You won't implement these by hand in an interview — you need the one-line intuition and the trade-off. Memorise: HNSW = graph, in-memory, top recall, pricier build; IVF = clusters, cheaper memory, tune nprobe.

04  Distance metrics: cosine, dot, Euclidean

“Closest” needs a definition of distance. Three show up constantly — the internals page covered the intuition; here's the practical version:

Cosine similarity
The angle between vectors — same direction = similar, ignores length. The default for text embeddings, because we care about topic, not how long the text was.
Dot product
Like cosine but also rewards magnitude. If vectors are normalised to length 1 (very common), dot product and cosine rank identically — so engines often use the cheaper dot product internally.
Euclidean (L2)
Straight-line distance between the two points. Common for image/other embeddings; for unit-length vectors it gives the same ranking as cosine.
Use the metric the model was trained with gotcha

An embedding model is trained against a specific metric — usually cosine. Index it under a mismatched metric (say Euclidean on un-normalised vectors) and your rankings quietly degrade. Always set the database's distance metric to match the model card, and normalise if the model expects it.

05  Build-time vs query-time trade-offs

Every ANN index dials the same fundamental tension: recall vs speed vs memory vs build cost. You can't max all four; you choose. The headline knobs:

KnobIndexTurn it up →
M (graph connections)HNSWHigher recall + more memory; slower build
ef_constructionHNSW (build)Better-quality graph; slower to build
ef_searchHNSW (query)Higher recall; slower per query
nlist / nprobeIVFMore clusters searched = higher recall, slower query

The useful mental model: build-time knobs (M, ef_construction, nlist) are paid once and shape index quality and memory; query-time knobs (ef_search, nprobe) let you slide recall vs latency live, per request. So you can tune speed without rebuilding — a favourite follow-up question.

06  The database landscape

You don't need to memorise products, but you should be able to sketch the categories and name a few (as of June 2026):

Add-on to an existing DB
pgvector (Postgres extension) — keep vectors next to your relational data; the pragmatic default when you're already on Postgres and not at extreme scale.
Purpose-built vector DBs
Qdrant, Weaviate, Milvus — engineered for vectors first: rich filtering, HNSW, sharding, hybrid search. Self-host or managed.
Fully-managed service
Pinecone — a hosted vector DB; you call an API, they run the infra and scaling.
Library, not a server
FAISS — Meta's ANN library you embed in your own app. No server, persistence or filtering out of the box; the engine many of the above build on.
How to say it out loud say it

“For finding nearest neighbours at scale I use Approximate Nearest Neighbour search — trading a tiny bit of recall for huge speed. HNSW is the common default: a navigable graph you traverse toward the query, high recall, in-memory. IVF clusters vectors and only searches the nearest clusters, cheaper on memory. I match the distance metric to the model — usually cosine — and tune ef_search or nprobe at query time to slide recall against latency. If I'm already on Postgres I'd reach for pgvector before a dedicated DB like Qdrant or Pinecone.”

07  Metadata filtering + vector search

Real queries are rarely pure similarity. You want “the most relevant docs that this user is allowed to see” or “from 2026” or “in the billing category.” So you store metadata (tags, dates, owner, permissions) next to each vector and filter on it. When you apply that filter matters enormously:

Pre-filter
First restrict to vectors matching the metadata, then run ANN over only those. Correct results, but if the filter is very selective the ANN graph/clusters can become sparse and slow — or fall back toward brute force.
Post-filter
First run ANN to get top-k, then drop the ones failing the filter. Fast, but dangerous: if few of the top-k pass, you can end up with far fewer results than k — or none, even though matching docs exist deeper in the index.
Post-filtering can silently return too few results gotcha

The classic bug: you ask for top-10, the DB post-filters, and a highly selective filter (e.g. “owner = this user”) knocks out 9 of them — you return 1 result and assume the data's missing. Modern vector DBs offer filtered ANN that integrates the filter into the graph traversal to dodge both failure modes, but you must opt in. Always know whether your DB pre-filters, post-filters, or does true filtered search — and over-fetch (raise k) when post-filtering.

08  Self-check

Your RAG app filters retrieved chunks by tenant_id so users only see their own data. A small tenant complains they get almost no results even though they have plenty of docs. The DB post-filters after ANN. What's the fix?
With post-filtering, a selective filter can eliminate most of the top-k, leaving too few results. Fixes: enable filtered/pre-filter ANN that applies tenant_id during traversal, or over-fetch (fetch top-200 then filter) so enough matching vectors remain. The metric and dimensions are unrelated.
“Explain HNSW vs IVF in one breath.”Core
Model answer

Both are ANN indexes. HNSW builds a layered navigable graph and greedily hops toward the query — high recall, in-memory, pricier to build and update; it's the common default. IVF clusters vectors and at query time only searches the few clusters nearest the query (knob: nprobe) — cheaper memory, great for huge static sets, recall depends on clustering. HNSW = graph; IVF = clusters.

How to say it out loud say it

“HNSW navigates a graph toward the query — top recall, in-memory, costlier build. IVF only searches the nearest clusters — cheaper memory, tune nprobe. Graph versus clusters.”

“When would you use exact search instead of ANN?”Warm-up
Model answer

When the dataset is small (thousands to low tens of thousands), or when 100% correctness matters more than latency, or for a one-off offline job where speed is irrelevant. Brute-force is simpler, has no index to build or tune, and is exact — ANN only earns its complexity once linear scan gets too slow at scale.

How to say it out loud say it

“Use exact search for small or static sets, or when you can't tolerate any miss. ANN is for when linear scan over millions of vectors blows your latency budget.”
