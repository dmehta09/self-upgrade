Embeddings & vectors · scale

Cheap vector search at scale NEW

A single 1024-dim float32 embedding is 4 KB. Sounds tiny — until you have a hundred million of them and the bill reads 400 GB of RAM. The 2025-era answer is quantization: store each number with far fewer bits. Done right, you shrink memory 4×, 32×, even more, with a small and recoverable accuracy cost. This page covers scalar (int8) and binary (1-bit) quantization, how to stack them with Matryoshka for multiplicative savings, and the production pattern that gets you cheap search and high quality at once.

01  Why full-precision vectors get expensive

By default each dimension is a float32 — 4 bytes. So a 1024-dim vector is 1024 × 4 = 4,096 bytes ≈ 4 KB. The arithmetic is brutal at scale: 100 million vectors × 4 KB ≈ 400 GB, and HNSW wants that in RAM for fast search. Memory is the dominant cost of large vector search, and every comparison also touches all those bytes — so shrinking the vectors makes search both cheaper and faster.

JPEG for vectors analogy

You don't email a 50 MB RAW photo when a 2 MB JPEG looks the same on screen. Quantization is JPEG for embeddings: you throw away precision the task can't perceive, keeping the shape that matters. A coarse thumbnail is enough to find the right photos quickly; you only open the full-resolution file for the handful you actually want. Vector search uses the same move — search on the compressed version, verify on the original.

02  Scalar (int8) quantization

Scalar quantization replaces each 32-bit float with an 8-bit integer (0–255). You find the min and max value per dimension, then map that range onto 256 buckets. The result is 4× smaller (4 bytes → 1 byte) with very little quality loss — the buckets are fine enough that rankings barely move. It's the low-risk default first step into quantization.

03  Binary (1-bit) quantization

Binary quantization is the extreme: keep just one bit per dimension — is this number positive or negative? A 1024-dim vector collapses from 4,096 bytes to 1024 bits = 128 bytes, a 32× saving. And comparing two binary vectors uses Hamming distance (count the differing bits), which CPUs do absurdly fast with bitwise XOR + popcount — so search gets dramatically faster too.

The catch: throwing away everything but the sign loses real information, so raw binary recall drops noticeably — sometimes into the 80s or lower on its own. The trick that makes it viable in production is to not trust binary alone — see §5.

Binary works only with enough dimensions gotcha

One bit per dimension is lossy, so binary quantization only holds up when the vector has many dimensions to vote across (roughly 1000+) and the model was trained to be robust to it. Binary-quantize a 256-dim vector and recall can crater. And never report binary's first-pass results as final — the recovery step (reranking) isn't optional, it's the whole reason it works.

04  Stacking Matryoshka + binary NEW

05  The production pattern: search cheap, rerank precise

Here's how teams get both low cost and high quality — the answer interviewers want. It's a two-stage coarse-to-fine funnel:

Binary-in-memory shortlist → float32 rerank
stage 1 · shortlist
binary search, in RAM
millions → ~top 100–1000, fast & cheap
stage 2 · rerank
float32 (or int8) rescore
just the candidates → final top-k
Stage 1 keeps tiny binary (often binary-MRL) vectors in fast memory and screens the whole corpus cheaply. Stage 2 fetches the full-precision vectors for only the few hundred survivors — from cheaper storage like SSD — and re-scores them exactly. This rescoring / oversampling recovers nearly all the recall the binary stage gave up.

two_stage_search.py
# Stage 1: cheap, fast shortlist over tiny binary vectors (held in RAM).
# Over-fetch far more than you need (oversampling) to protect recall.
candidates = binary_index.search(query_bits, k=400)   # ~32x smaller, Hamming distance

# Stage 2: rescore ONLY those candidates with full-precision floats.
full_q = embed(query)                                 # float32 query
rescored = sorted(
    candidates,
    key=lambda c: cosine(full_q, load_float32(c.id)), # exact score
    reverse=True,
)
top_k = rescored[:10]                                 # precise final results
How to say it out loud say it

“At scale, full-precision vectors are a memory bomb. I quantize — int8 for an easy 4× with almost no loss, or binary for ~32× and blazing Hamming-distance search. Binary alone loses recall, so the production pattern is two stages: keep tiny binary, often binary-MRL, vectors in RAM to shortlist a few hundred candidates, then rescore just those with the full float32 vectors from cheaper storage. You over-fetch in stage one to protect recall and recover almost all the quality.”

06  Sharding & recall tuning

When even quantized vectors outgrow one machine, you shard: split the index across nodes, query them in parallel, and merge the per-shard top-k into a global top-k (a scatter-gather). It scales horizontally but adds a subtlety — recall is per-shard, so you usually fetch a few extra per shard before merging.

Sharding
Partition vectors across nodes; each searches its slice, results are merged. Scales beyond one box's RAM and parallelises latency.
Oversampling
Fetch more candidates than the final k (per shard, and before reranking) so the true neighbours survive merging and rescoring.
Recall tuning
Slide the query-time knobs — ef_search/nprobe, candidate count, rerank depth — to hit your target recall at the lowest latency.
Always measure recall against an exact baseline gotcha

Quantization and ANN both approximate, so you can't eyeball quality — you have to measure it. Build a small exact (brute-force) top-k on a sample as ground truth, then compare your pipeline's results to it. Tuning recall blind is how teams ship a search system that quietly misses the right answer a fifth of the time.

07  Self-check

You switch to binary quantization for a 32× memory saving, but recall drops from 98% to 84%. What's the standard way to get most of that recall back without giving up the memory win?
Binary is a fast, cheap first pass. The fix is the two-stage pattern: shortlist generously with binary (in RAM), then rescore just those candidates with full-precision vectors. That recovers most of the lost recall while keeping the bulk of the data tiny.
“Compare scalar and binary quantization for embeddings.”Core
Model answer

Scalar (int8) maps each float to one of 256 integer buckets — 4× smaller, almost no quality loss; a safe default. Binary keeps one bit per dimension (sign), giving ~32× smaller vectors and very fast Hamming-distance search, but a noticeable recall drop you recover by reranking the shortlist with full-precision vectors. Binary needs many dimensions (~1000+) to work well.

How to say it out loud say it

“Int8 is the safe 4× win with barely any loss. Binary is the aggressive ~32× win with fast bitwise search but real recall loss — viable only because you rerank the shortlist with full-precision vectors.”

“How do Matryoshka and quantization combine?”Stretch
Model answer

They're orthogonal, so the savings multiply. MRL truncates the number of dimensions; quantization shrinks the bits per dimension. A 1024-dim float32 vector (4 KB) truncated to 512 dims (2×) and binarised to 1 bit (32×) is ~64 bytes — roughly 64× smaller. Each adds some quality cost, which the float32 rerank stage buys back, so the net is huge memory savings at near-baseline recall.

How to say it out loud say it

“MRL cuts dimensions, quantization cuts bits — independent levers, so they multiply. Half the dims plus one bit each is ~64× smaller, and the rerank step recovers the quality.”
