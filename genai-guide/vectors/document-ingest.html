Document ingest & loaders IV NEW

Every RAG pipeline starts the same way: turn messy files and URLs into clean, searchable text. That step — document ingest — happens before chunking, embedding, or indexing, and it's where a surprising share of production failures hide. A PDF with no text layer, a web page that's 80% nav chrome, a CSV row missing its column headers — garbage in, garbage indexed. This page is the practical guide: why ingest quality caps everything downstream, how to pick a loader for each format, the full pipeline from load to store, and the gotchas interviewers love.

01  Why ingest matters before chunking

Chunking decides how you cut text; ingest decides whether the text you cut is even worth cutting. If a loader returns empty strings, scrambled table columns, or three pages of cookie-banner boilerplate, no chunk size or embedding model can recover the answer. Ingest is the floor on retrieval quality — everything after it can only preserve or degrade what you loaded.

Washing produce before you chop it analogy

You wouldn't slice vegetables straight from a muddy field and expect a clean salad. Ingest is the wash-and-prep step: strip dirt (HTML boilerplate), peel what isn't edible (headers/footers), and separate varieties (structured vs prose). Chunking is the knife work — useless if what you're cutting is still dirty or empty.

Acme Health built a clinician Q&A bot over 12,000 policy PDFs. Their first pipeline used a generic PDF text extractor and jumped straight to fixed-size chunking. Recall looked fine in demos — until clinicians asked about dosage tables buried in scanned appendices. The “PDFs” were image-only scans: the loader returned blank pages, the chunker had nothing to split, and the index was silently missing half the corpus. Fixing ingest (OCR + table-aware parsing) lifted recall more than any chunk-size tweak.

Ledger Bank crawled its internal wiki for a compliance chatbot. Raw HTML loaders pulled nav menus, “Last edited by…” footers, and sidebar links into every chunk. Users searching “wire transfer limits” got chunks that were mostly site chrome with one sentence of policy buried at the bottom. The fix wasn't a better embedding model — it was cleaning and extracting the main content before chunking.

Once text is clean, chunking strategies decide how to cut it; embedding models turn those cuts into vectors. Ingest is the step neither page can help you with if you skip it.

02  Loader chooser: match format to tool

A loader (or document parser) reads a source — file, URL, database row — and returns one or more documents: a text body plus optional metadata (source path, page number, section title). Pick the wrong loader and you get the wrong shape of text. Here's the chooser interviewers expect:

Source typeWhat to useWatch for
Plain text / MarkdownRead the file directly; preserve headings for structural chunkingEncoding (UTF-8 vs legacy), front-matter YAML in Markdown repos
CSV / JSON (structured)Row- or record-aware loaders: one document per row/object, or templated text per recordColumn names as context; don't flatten a 40-column row into an unreadable blob
PDF (text layer)Text-extraction libraries when the PDF has selectable/copyable textMulti-column layout scrambles reading order; tables become gibberish
PDF (scanned / image-only)OCR (Tesseract, cloud OCR, vision models) — there is no text layer to extractOCR errors on small fonts; cost and latency vs text-layer PDFs
Web / HTMLFetch + extract main content (readability-style parsers, sitemap crawlers)JS-rendered pages, infinite scroll, rate limits, robots.txt, duplicate URLs
Plain text & Markdown
The easy case: read bytes, decode, done. Markdown earns extra credit — headings (##) are natural chunk boundaries, so pair with structural splitting later. Store the file path and heading trail in metadata.
CSV & JSON
Structured data isn't prose — treat each row or JSON object as a unit. Template each record into readable text: “Product SKU-4412, category: electronics, price: $89, in stock: yes.” Keep raw fields in metadata for filtering. Ledger Bank indexed transaction-dispute FAQs from a CSV of Q&A pairs — one row, one document, perfect recall on exact question matches.
PDF: text layer vs OCR
Try text extraction first (fast, cheap). If you get empty or garbage output, the PDF is likely scanned — switch to OCR. Acme Health's scanned dosage appendices needed OCR; their born-digital policy PDFs did not. Never assume all PDFs are the same.
Web loaders & crawl risks
A single URL fetch is not a “crawl.” Production ingest uses sitemaps or bounded crawlers with depth limits, deduplication, and politeness delays. Risks: hammering a site (get blocked), ingesting login walls or error pages, pulling duplicate content from www vs non-www, and storing PII from pages you shouldn't have indexed.
Concepts here; LangChain loaders in langstack note

We teach the decision here — which loader for which format, and why. Framework-specific APIs (PDF loaders, web crawlers, blob storage connectors) live in the Lang Stack guide (langstack · LangChain RAG). This page is about choosing what to load and how to clean it, not the import statement.

03  The ingest pipeline: load → store

In production, ingest is never “read file, chunk, done.” It's a short pipeline where each stage has a job. Skipping parse/clean or metadata is how silent data loss happens.

flowchart LR
  A["Load\n(file, URL, DB)"] --> B["Parse & clean\n(strip boilerplate,\nfix encoding, OCR)"]
  B --> C["Attach metadata\n(source, page, section,\ntimestamp, ACL)"]
  C --> D["Chunk\n(split into units)"]
  D --> E["Embed\n(text → vectors)"]
  E --> F["Store\n(vector DB + metadata)"]
Offline indexing path. Query-time search (embed query → nearest neighbours → feed LLM) is the mirror of the last two boxes — see Naive RAG.
Load
Read the raw source: filesystem, S3/GCS blob, HTTP fetch, database export. Output is bytes or HTML, not yet clean text.
Parse & clean
Extract human-readable text; strip nav/footer boilerplate; fix encoding; run OCR on scans; optionally extract tables into structured form. This is where format-specific loaders earn their keep.
Metadata
Attach provenance before you lose it: source_url, page, section_title, last_modified, access_level. Metadata powers filtering (“only search policies updated in 2026”) and citations in the final answer.
Chunk → embed → store
Hand off to chunking, then embedding, then the vector index. The golden rule from naive RAG still applies: same embedding model at index and query time.

04  Exam gotchas

These four failure modes show up constantly in system-design interviews and real incident post-mortems:

JS-rendered PDF / web pages
A plain HTTP GET returns an empty shell — the real content is built by JavaScript in the browser. Fix: headless browser rendering, official API/export, or pre-rendered static snapshots. Crawling a React SPA with curl indexes nothing useful.
Scanned documents
PDFs that look like text are often images of paper. Text extractors return blank or partial output. Detect early (low character count per page) and route to OCR. Acme Health lost half its corpus until someone checked page-level char counts.
HTML boilerplate
Headers, footers, cookie banners, “Related articles” sidebars pollute every chunk. Use main-content extraction, not raw innerText of the whole page. Ledger Bank's wiki bot improved overnight once nav chrome stopped dominating vectors.
PII & sensitive data
Ingest is the last cheap gate before data lands in an index that may be queried by support staff, logged, or sent to an external embedding API. Redact or mask SSNs, account numbers, and patient identifiers before embed. Check access-control metadata so retrieval respects who may see what.
Silent empty ingest is worse than a loud error gotcha

Many loaders return an empty document instead of failing when a PDF has no text layer or a URL 404s. Your pipeline “succeeds,” the index grows, and retrieval quietly misses entire sources. Always log char counts per document, sample-index a few files, and alert on zero-length outputs.

How to say it out loud say it

“Ingest is upstream of chunking and embedding — if the loader returns garbage, nothing downstream fixes it. I'd match loader to format: direct read for Markdown, row-aware for CSV/JSON, text extraction for born-digital PDFs, OCR for scans, and main-content extraction for web. I'd attach metadata early, redact PII before embed, and monitor for silent empty documents. Framework loaders are in LangChain; the design choice is format-aware parsing and cleaning before I ever chunk.”

05  Self-check

Ledger Bank indexes internal wiki pages for a compliance bot. Users complain answers cite cookie-banner text and sidebar links instead of policy. What's the most likely root cause?
Boilerplate dominating chunks is a classic ingest/clean failure, not an embedding or overlap tuning issue. Fix parse & clean — extract the main article body, strip headers/footers — before chunking. Overlap duplicates text but doesn't invent nav chrome from whole-page HTML dumps.
“Why does ingest matter if you're going to chunk anyway?”Warm-up
Model answer

Because chunking only splits what the loader gives you. Empty PDFs, scrambled tables, HTML nav menus, and OCR garbage get chunked and embedded as-is — retrieval can't find answers that were never loaded cleanly. Ingest sets the floor on quality; chunking and embedding can only work with the text they're handed.

How to say it out loud say it

“Chunking can't fix bad input. If ingest returns empty or noisy text, the index is broken before chunking starts. Wash the data first.”

“When would you use OCR instead of a normal PDF text extractor?”Core
Model answer

When the PDF has no selectable text layer — scanned paper, photographed documents, image-only pages. A text extractor reads embedded text; if there isn't any, output is blank or nonsense and you need OCR (or a vision model) to read pixels. Born-digital PDFs with copyable text should use text extraction first — it's faster and more accurate.

How to say it out loud say it

“Try text extraction first. If pages come back empty or garbled, it's probably scanned — route to OCR. Don't OCR everything by default; it's slower and error-prone on clean PDFs.”

“Walk me through the ingest stages before vectors hit the database.”Core
Model answer

Load the raw source (file, URL, blob), parse and clean into readable text (strip boilerplate, OCR scans, fix encoding), attach metadata (source, page, section, ACL, timestamps), chunk into retrieval units, embed with your chosen model, then store vectors plus metadata in the vector DB. Metadata and cleaning happen before chunking so provenance and quality aren't lost.

How to say it out loud say it

“Load → parse/clean → metadata → chunk → embed → store. Cleaning and metadata come before chunking; embed and store are the handoff to the vector-search stack.”
