Chunking strategies IV

Before you can embed anything, you have to cut your documents into pieces. That cutting — chunking — is the least glamorous and most underrated decision in the whole pipeline. Chunk badly and the right answer gets sliced in half, scattered across fragments, or buried in noise, and no embedding model or reranker can rescue it. This page is the practical guide: why chunking quietly decides RAG quality, the four families of splitter, the size/overlap trade-off, parent-document retrieval, and the newer late-chunking and contextual-retrieval tricks.

01  Why chunking decides RAG quality

Remember the lesson from the RAG module: retrieval is the bottleneck, not generation. Chunking sits upstream of retrieval, so it shapes the ceiling on everything after it. A chunk is the unit of retrieval — it's what gets embedded, what gets searched, and what gets pasted into the prompt. If your chunks don't each contain a coherent, self-contained idea, search has nothing good to find.

Tearing pages out of a book analogy

Imagine prepping a reference book for a quiz by tearing it into snippets you can hand over one at a time. Tear mid-sentence and a snippet ends with “the maximum dose is” — useless without the next page. Tear too coarsely and one snippet covers three unrelated topics, so handing it over drowns the real answer in clutter. The skill is tearing along the natural seams — sections, paragraphs — so each snippet stands on its own. That's chunking.

One embedding has to summarise an entire chunk in a single vector. Cram in multiple topics and the vector becomes a muddy average that's near nothing in particular; split one topic across two chunks and neither vector fully captures it. Coherent chunks → clean vectors → good retrieval.

02  The four families of chunker

Chunking strategies climb a ladder from dumb-but-simple to smart-but-costly. Start at the top and move down only when retrieval quality demands it:

StrategyHow it splitsTrade-off
Fixed-sizeEvery N tokens/characters, blindlyDead simple & fast; happily cuts mid-sentence and mid-idea
RecursiveTry to split on paragraphs → sentences → words, in that order, until pieces fitRespects natural boundaries; the sensible default for prose
SemanticEmbed sentences, start a new chunk when meaning shiftsTopically tight chunks; needs extra embedding calls & tuning
StructuralFollow the document's own structure — Markdown headings, HTML, code functions/classesBest when the format carries meaning; needs format-aware parsing

Recursive is the workhorse: it tries the biggest natural separator first (blank lines between paragraphs), and only if a piece is still too big does it fall back to splitting on sentences, then words — so it keeps as much coherent context together as possible while respecting your size limit. Structural shines for Markdown, HTML and especially code, where splitting on function or class boundaries keeps each unit intact instead of bisecting a function.

Frameworks ship these splitters for you note

We teach the concept here; you rarely hand-roll a splitter in production. Frameworks provide recursive, Markdown, code and semantic splitters out of the box — see the Lang Stack guide (langstack · LangChain concepts) for the text-splitter APIs and code. This page is about choosing which and why, not the import statement.

03  Chunk size & overlap

Two dials govern every chunker, and they pull against each other:

Chunk size
Small chunks (a sentence or two) are precise — their vector is sharp and search pinpoints the exact line — but they lose surrounding context, so a snippet may be relevant yet uninterpretable alone. Large chunks carry context but blur the vector and waste prompt tokens on irrelevant text. The sweet spot for prose is often a few hundred tokens, but it depends on your content.
Overlap
Letting consecutive chunks share a slice of text (say the last ~10–20%) stops an idea sitting on a boundary from being cut in half — the sentence that bridges two chunks survives in both. Costs a little duplication and storage.

A small overlap (≈10–20% of chunk size) is cheap insurance against splitting an idea across a boundary. Note: your embedding model's max sequence length is a hard ceiling — chunks past it get silently truncated.
There's no universal “best” chunk size gotcha

Tweets, legal contracts and Python files want wildly different chunkings — anyone quoting a magic number with no context is guessing. Chunk size is an empirical choice you validate against a retrieval eval set, not a constant. Watch the units too: “512” means something different in characters vs tokens, and your model thinks in tokens.

04  Parent-document / small-to-big retrieval

The size trade-off feels like a forced choice — but you can cheat it. Parent-document retrieval (a.k.a. small-to-big) searches with small chunks but returns big ones. You embed and search over precise little child chunks, then, once you've found the best matches, hand the LLM the larger parent passage (or surrounding window) each child came from.

Best of both worlds: precise matching on tiny chunks, rich context in the generation step. You get the sharp vector and the surrounding paragraph the model needs to actually answer.

05  Late chunking & contextual retrieval NEW

Both classic approaches embed each chunk in isolation, so a chunk loses whatever its document gave it — pronouns dangle (“it raised prices”—what did?), and shared context evaporates. Two 2024–25 techniques fix this from opposite ends:

Late chunking
Run the whole document through a long-context embedding model first, so every token's representation is informed by the full document — then pool those already-contextualised token vectors into chunk vectors. The split happens late, after the model has seen everything, so each chunk vector still “remembers” its surroundings. Needs a long-context embedding model.
Contextual retrieval
Before embedding, prepend a short, LLM-written blurb to each chunk situating it in the document (e.g. “This is from the 2026 refund policy, section on international orders…”). The chunk now carries its own context, so its vector — and any keyword match — is far less ambiguous. Costs an LLM call per chunk at index time (cut with prompt caching).
A chunk embedded alone forgets where it came from gotcha

The single biggest hidden failure in naive chunking: a chunk that reads “It was discontinued in March” is meaningless once detached from the product it referred to three paragraphs up. Search can't recover context the chunk never carried. Late chunking and contextual prepending exist precisely to put that lost context back into the vector before you index it.

06  “How do you choose chunk size?”

A near-guaranteed interview question. The senior answer refuses to name a magic number and instead describes a process:

  1. Start from the content's natural unit. A FAQ chunks per Q&A; code per function; a contract per clause. Let structure lead.
  2. Default to recursive splitting at a few hundred tokens with ~10–20% overlap — a strong baseline for prose.
  3. Respect the embedding model's max sequence length so nothing gets silently truncated.
  4. Measure on a retrieval eval set. Build labelled query→answer pairs and track recall as you vary size; let the numbers, not vibes, decide.
  5. Reach for the advanced tools — parent-document, semantic or structural splitting, late/contextual chunking — only when the eval says the simple baseline isn't enough.
How to say it out loud say it

“There's no universal best size — it depends on the content, so I'd measure it. I start from the document's natural unit, default to recursive splitting at a few hundred tokens with light overlap, and make sure chunks fit the embedding model's max length. Then I tune size against a retrieval eval set. If chunks are losing context I use parent-document retrieval — search small, return big — or contextual prepending and late chunking so each chunk's vector still knows where it came from. Chunking is upstream of retrieval, and retrieval is the RAG bottleneck, so it's worth the effort.”

07  Self-check

Your RAG system retrieves the right chunk, but the LLM still can't answer because the chunk reads “It was recalled in 2025” with no idea what “it” is. Which fix targets this directly?
The retrieval worked — the problem is a context-starved chunk. Returning the larger parent passage (small-to-big) or prepending an LLM-written context blurb (contextual retrieval) restores the “what” the chunk refers to. Distance metric and index knobs don't address missing context.

“What is late chunking and how does it differ from contextual retrieval?”Stretch
Model answer

Both restore lost document context. Late chunking embeds the whole document through a long-context model first, then pools the already-contextualised token vectors into chunks — so the split happens late and each chunk vector remembers its surroundings. Contextual retrieval instead prepends a short LLM-generated context blurb to each chunk before embedding, so the text itself carries the context (helping both vector and keyword match). Late chunking is an embedding-side trick; contextual retrieval is a text-side, LLM-assisted one.

How to say it out loud say it

“Late chunking embeds the whole doc first, then splits — so chunk vectors keep their context. Contextual retrieval prepends an LLM-written context line before embedding. One fixes it on the embedding side, the other on the text side.”
