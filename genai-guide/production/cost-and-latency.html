Productionization · cost & latency

Engineering for cost & latency IV NEW

Two numbers decide whether your LLM feature survives a budget review: how much each request costs and how long users wait. The good news is that both are engineering problems with well-known levers — model choice, token discipline, caching, routing, batching — not mysteries. This page is the toolkit, and the answer to the dreaded “our bill just tripled, what do you do?”

01  Why the bill is a meter, not a subscription

You're billed per token — roughly a word-piece — and the meter runs on both what you send (input) and what the model writes back (output). Crucially, output tokens cost several times more than input tokens, and reasoning models also bill for hidden “thinking” tokens. So a single request's cost is, near enough:

What you pay for, per request
input
prompt + context
cheap, but grows with RAG/history
thinking
reasoning tokens
hidden, billed as output
output
the answer
the expensive part — several× input
Cost ≈ (input tokens × input price) + (thinking + output tokens × output price). The output side dominates — which is why the biggest savings come from generating fewer, shorter answers and not over-thinking easy questions. (Background: Tokens, context & cost.)
A pay-by-the-word phone call analogy

Imagine a phone plan that charges a little for what you say and a lot for what the other person says back — and the “other person” sometimes mutters to themselves for a minute (thinking) before replying, on the clock. To cut the bill you'd talk to a cheaper operator for simple calls, keep your questions tight, and not pay a genius to read out the weather. That's model choice, token discipline, and routing — exactly the levers below.

02  The four cost levers

Whenever cost is the question, reach for these in order — cheapest change first:

LeverWhat you doTypical win
Model choiceUse the smallest model that passes your eval; reserve frontier models for genuinely hard work.Often the biggest single saving — small/open models can be 10–100× cheaper.
Token disciplineTrim the prompt, cap max_tokens, retrieve fewer chunks, summarise long history instead of resending it.Direct, linear savings — every token you don't send or generate is money.
CachingDon't pay twice for the same work — reuse identical or near-identical results and stable prompt prefixes.Huge on repetitive traffic; can cut both cost and latency.
RoutingSend easy requests to a cheap model and only escalate hard ones to a frontier model.Big when traffic is mixed; covered on the next page.
Measure before you optimise gotcha

The classic junior mistake is to jump straight to “switch models” without knowing where the tokens go. Instrument first: log input/output/thinking tokens per request and group by feature. You'll often find one endpoint (a verbose system prompt, an agent that loops, a giant retrieved context) is 80% of the spend — and a five-line fix beats a risky model swap.

03  The latency budget: TTFT, streaming & perceived speed

Generation is sequential — the model emits one token at a time — so a long answer is inherently slow. You manage two distinct numbers:

TTFT — time to first token
How long until the first word appears. This is what makes an app feel responsive or dead. Driven by network, queueing, prompt length (prefill), and any thinking the model does up front.
TPOT / throughput — time per output token
How fast words stream after that. Total time ≈ TTFT + (output tokens × time-per-token), so long answers cost latency just like they cost money.

The single highest-leverage UX trick is streaming: show tokens as they arrive instead of waiting for the whole answer. The total time is unchanged, but perceived latency plummets because the user starts reading immediately.

Plating the first course while the kitchen cooks analogy

A good restaurant brings bread the moment you sit down. The meal isn't ready any faster, but the wait feels short because something's happening. Streaming is that bread basket: the answer takes just as long, but the user is engaged from the first token instead of staring at a spinner. Perceived latency is a real product metric, not a cheat.

Reasoning models complicate this: they can “think” for several seconds before the first visible token, hurting TTFT. Many providers stream a thinking indicator, or you tune the thinking budget down — see §5.

04  Two kinds of caching: prompt vs semantic NEW

“Caching” means two genuinely different things in LLM land, and mixing them up is a common interview slip. Both save money; they work on different principles.

Prompt caching (provider-side)Semantic caching (meaning-match)
Matches onAn exact, reused prompt prefix (token-for-token)The meaning of the request, via embedding similarity
HowThe provider stores the prefill for a shared prefix (system prompt, long doc) and reuses itYou embed the query, look for a near-duplicate past query, and return its stored answer
SavesInput cost on the prefix (often heavily discounted) and TTFTThe entire call — zero tokens on a hit
RiskLow — it's still the model generating; just cheaper prefillReturning a stale or subtly-wrong answer for a “similar but not identical” question
Best forLong, stable system prompts; RAG over a fixed document; few-shot examplesHigh-volume, repetitive FAQ-style traffic where many users ask the same thing

Use them together: prompt caching makes every call cheaper by reusing the stable prefix, while semantic caching skips the call entirely when someone asks a question you've effectively answered before. The trick for prompt caching is ordering — put the stable content (system prompt, retrieved docs, examples) first and the volatile user turn last, so the cacheable prefix is as long as possible.

Semantic caching can serve confidently-wrong answers gotcha

“What's our refund policy?” and “What's our return policy?” embed almost identically — but the right answers may differ. A loose similarity threshold turns your cache into a hallucination amplifier. Set a conservative threshold, scope caches per-tenant/per-user where data is private, and add a TTL so answers don't go stale. When in doubt, cache only clearly idempotent, low-stakes queries.

05  Batch APIs, off-peak & reasoning-effort tuning NEW

Three more levers matter when you control when and how hard the model works:

Batch APIs
For work that isn't time-sensitive — nightly summarisation, bulk classification, back-filling embeddings — submit a batch and accept results within hours. Providers typically discount these heavily (commonly ~50% as of June 2026) because they can schedule the work off-peak.
Off-peak / async scheduling
Even without a formal batch API, deferring non-urgent jobs to quiet periods smooths your rate-limit headroom and can dodge surge contention. Anything a user isn't actively waiting for is a candidate.
Reasoning-effort tuning
Reasoning models expose a knob — “reasoning effort,” a thinking budget, or low/medium/high — that trades thinking tokens for accuracy. Crank it for genuinely hard math/planning; turn it down (or use a non-reasoning model) for routine work, since thinking tokens are billed as expensive output and add latency.
cost_levers.py
# Pseudocode — match each lever to the situation, not one-size-fits-all.

def answer(query):
    # 1) Semantic cache: have we effectively answered this already?
    hit = semantic_cache.lookup(query, threshold=0.95)   # conservative!
    if hit:
        return hit                      # zero tokens, instant

    # 2) Right-size the effort: easy questions don't need a reasoning pass.
    if is_simple(query):
        resp = call(model="small-fast", max_tokens=300, stream=True)
    else:
        resp = call(model="frontier-reasoning",
                    reasoning_effort="high",             # think hard only when needed
                    max_tokens=1200, stream=True)        # cap output + stream for TTFT

    semantic_cache.store(query, resp, ttl="1h")
    return resp

06  Drill: “your LLM bill just tripled — what do you do?”

This is a near-universal interview prompt. A senior answer is a method, calm and ordered — not a panic-swap of models:

Triage the spend, then fix the biggest slice
1 · measure
break down the spend
tokens by feature, model, user
2 · find the cause
volume or per-call?
traffic spike vs bloated prompt/loop
3 · apply levers
cheapest fix first
cache → trim → route → batch
Step 1 almost always localises the problem to one feature. Common culprits: a chatty new system prompt, an agent stuck in a retry loop, retrieved context ballooning, a reasoning model used where a cheap one would do, or simply more users (a good problem — now optimise unit cost).

Then name concrete fixes in order: add semantic + prompt caching, trim tokens (shorter prompts, capped output, fewer chunks), route easy traffic to a cheap model, move non-urgent jobs to a batch API, and dial down reasoning effort where it isn't earning its keep. Set a budget alert so the next spike pages you, not finance.

How to say it out loud say it

“First I'd measure — break the spend down by feature, model and token type to find the 80%. Usually it's one endpoint: a bloated prompt, an agent loop, or a reasoning model doing easy work. Then I apply levers cheapest-first: prompt and semantic caching, trim tokens and cap output, route easy queries to a small model, push non-urgent jobs to the batch API, and lower reasoning effort where it doesn't help. Finally I add a budget alert so we catch the next spike early.”

07  Self-check

A high-traffic support bot answers many near-identical questions. Which caching strategy skips the model call entirely on a repeat?
Prompt caching only discounts the reused prefix — the model still generates the answer. Semantic caching matches on meaning and returns a previously stored answer with no model call at all, which is the big win for repetitive traffic. Watch the similarity threshold so you don't serve a wrong answer to a “similar” question.
“Prompt caching vs semantic caching — what's the difference?”Core
Model answer

Prompt caching is provider-side and matches an exact reused prefix — your system prompt, a long retrieved doc, few-shot examples — so the prefill is reused, cutting input cost and TTFT; the model still generates the answer. Semantic caching is yours and matches on meaning: you embed the query, find a near-duplicate past query, and return its stored answer with zero tokens. Prompt caching makes every call cheaper; semantic caching can skip the call. The catch with semantic is a stale or subtly-wrong answer, so you use a conservative threshold and a TTL.

How to say it out loud say it

“Prompt caching reuses an exact prompt prefix to cut input cost and time-to-first-token — the model still answers. Semantic caching matches the meaning of a query and returns a stored answer for free. I use both, but I keep the semantic threshold conservative so I don't serve a wrong answer to a merely-similar question.”

“Users say the app feels slow. How do you improve latency without a faster model?”Core
Model answer

Separate perceived from actual latency. The fastest win is streaming tokens so the user reads from the first word — same total time, far better feel. Then cut TTFT: shorten the prompt (prefill is part of TTFT), enable prompt caching on the stable prefix, and lower or remove the reasoning budget for easy requests so the model doesn't think for seconds first. Cap max_tokens so answers aren't needlessly long, and serve repeat questions from a semantic cache for instant responses. Only after that would I consider a faster/smaller model.

How to say it out loud say it

“I'd stream first — it transforms perceived speed for free. Then attack TTFT: trim the prompt, cache the stable prefix, and cut the thinking budget on easy queries. Cap output length, and serve repeats from a semantic cache. A faster model is the last lever, not the first.”
