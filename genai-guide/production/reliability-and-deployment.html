Productionization · reliability & deployment

Shipping reliably IV NEW

The model you build on is a flaky, pay-per-token, non-deterministic third party — it can be slow, rate-limit you, go down, or answer differently on a retry. Shipping reliably means wrapping that unreliability so users barely feel it, and changing your prompts and models without breaking anyone. This page is the production discipline: resilient calls, safe rollouts, and the self-host-vs-API decision.

01  The anatomy of a resilient LLM call

A naive call is one line: send prompt, await answer. A production call assumes that line can hang, fail, or get throttled — and wraps it accordingly. The standard toolkit, in layers:

Streaming
Stream tokens so the user sees progress immediately. Beyond UX, it lets you detect a stalled generation early instead of waiting out a long timeout.
Timeouts
Never wait forever. Set a sensible deadline so one slow request doesn't pin a worker and cascade into a pile-up.
Retries with backoff
Transient errors (429s, 5xx, blips) usually pass. Retry a few times, but with exponential backoff + jitter so you don't hammer a struggling provider in lockstep.
Circuit breaker
If a provider is failing hard, stop calling it for a cooldown and fail fast (or fall back). Retrying into a downed service just makes things worse and burns your latency budget.
Fallback
When the primary is exhausted, route to a backup model/provider (see Routing & gateways) — or return a graceful, honest degraded response.
Knock politely, then walk away analogy

If a friend doesn't answer the door, you knock again after a moment, then wait a little longer, then maybe a third time — you don't pound nonstop (backoff). If they're clearly not home, you stop knocking for a while instead of standing there forever (circuit breaker), and you try the neighbour (fallback). That's exactly how a resilient client treats a flaky API: patient, polite, and quick to give up gracefully.

resilient_call.py
import time, random

def resilient_call(messages, max_retries=3, timeout=20):
    if breaker.is_open("provider_a"):       # circuit breaker tripped?
        return call_fallback(messages)      # skip the dead provider entirely

    for attempt in range(max_retries):
        try:
            return call("provider_a", messages, timeout=timeout, stream=True)
        except RateLimited as e:
            wait = (2 ** attempt) + random.random()   # exp. backoff + jitter
            time.sleep(min(wait, e.retry_after or wait))
        except (ServerError, Timeout):
            breaker.record_failure("provider_a")
            wait = (2 ** attempt) + random.random()
            time.sleep(wait)

    breaker.trip("provider_a")              # too many failures: open the breaker
    return call_fallback(messages)          # degrade gracefully, never hang

02  Idempotency & living with non-determinism

Two LLM-specific headaches bite here. First, non-determinism: the same prompt can yield different text, so you can't assert exact-match in tests or assume a retry returns the identical answer. Second, retries plus side-effects: if a call times out after the model already acted (sent an email, charged a card via a tool) and you retry, you can do it twice.

Idempotency keys
Attach a unique key to each logical operation so a retried request is recognised and de-duplicated — the action happens at most once even if the call is repeated. Essential for agents that take real-world actions.
Pin what you can
Set temperature=0 and a seed where supported for the most repeatable behaviour — though identical output still isn't guaranteed across model updates.
Test on properties, not exact strings
Assert the output parses, matches a schema, contains required facts, or passes an LLM-judge — not that it equals a fixed string. (See Eval methods.)
Pin the model version
Providers update models silently; a “same” model can shift behaviour overnight. Pin to a dated/snapshot version so deploys are deliberate, and re-eval before bumping.
A silent model update is a deploy you didn't make gotcha

If you call a floating alias (“latest”), your provider can change the model under you with no code change — and your carefully-tuned prompt may regress. Pin to a specific dated version, treat version bumps like any other change (eval + canary), and keep prompts in version control so you can correlate a quality dip with what actually moved.

03  Prompts in git, versioning & staged rollout NEW

A prompt is code: it changes behaviour, so it belongs in version control, in review, and behind a safe rollout — not pasted into a console and forgotten. The discipline that's standard as of June 2026:

Prompts & configs in git
Every prompt, model choice, temperature and tool definition is versioned and code-reviewed. You can diff a change, see who made it, and roll back instantly when quality dips.
Eval gate
A change must pass your eval set before it ships — the automated check that stands in for “does this answer well?” Eval is a release gate, not an afterthought.
Canary release
Ship the change to a small slice of traffic (say 5%) first, watch quality/cost/latency/errors, then widen only if the signals hold.
A/B test
Run old vs new side by side on real traffic and compare outcome metrics (resolution rate, thumbs-up, conversion) to prove the new version is better, not just different.

Because you can't fully unit-test answer quality, you de-risk with layers: offline eval catches regressions early, a canary limits the blast radius of anything that slips through, and an A/B test proves real improvement before full rollout.

04  Self-host vs API: the trade-off NEW

A recurring decision: call a closed provider's API, or run an open-weight model on your own GPUs? There's no universal answer — it's a trade across cost, privacy and control.

Closed APISelf-hosted open-weight
Time to startMinutes — just a keyDays — GPUs + a serving stack
Cost shapePer-token; cheap to start, can balloon at scaleFixed GPU cost; far cheaper at high, steady volume
Privacy / data controlData leaves your walls (mind the terms)Stays in-house — strong for regulated/sensitive data
ControlVendor picks model updates, limits, availabilityYou pin versions, tune serving, own uptime
Ops burdenLow — provider runs itHigh — you run inference, scaling, on-call
Best forFast start, frontier quality, spiky/low volumeScale, privacy, deep customization, predictable cost

The 2026 reality: open-weight models are close enough to the frontier — and often an order of magnitude cheaper — that “self-host an open model behind a gateway” is mainstream, not fringe. A common hybrid is to use a frontier API for the hardest traffic and a self-hosted open model for the bulk, with the gateway routing between them. (GPU-level serving is covered in Serving engines.)

05  Rate limits, quotas & capacity planning

Whether API or self-hosted, you live within limits — and planning for them is part of reliability:

Rate limits & quotas
Providers cap requests- and tokens-per-minute per key. Hit the ceiling and you get 429s. Handle them with backoff, spread load across keys/providers (a gateway helps), and request higher limits before a launch.
Backpressure & queueing
When demand exceeds capacity, queue rather than drop — and shed load gracefully (a clear “try again” beats a hang). Async/batch the non-urgent work so it doesn't compete with live traffic.
Capacity planning
Estimate peak requests × tokens-per-request against your rate limits (API) or GPU throughput (self-host). Load-test before launch; provision headroom for spikes; for self-hosting, plan autoscaling and the cold-start cost of spinning up GPUs.
How to say it out loud say it

“I'd treat the model as a flaky dependency: stream responses, set timeouts, retry with exponential backoff and jitter, and add a circuit breaker plus a fallback provider so an outage degrades gracefully. I keep prompts, model versions and configs in git, gate changes on an eval set, and roll out via canary then A/B so I never break users. I pin the model version to avoid silent updates, use idempotency keys for any real-world actions, and plan capacity against rate limits with load tests before launch.”

06  Self-check

Your LLM provider starts returning errors for a sustained stretch. Which combination handles this best?
Tight-loop retries hammer a struggling service and burn your latency budget; long timeouts pin workers and cascade. The resilient pattern is bounded retries with backoff and jitter, a circuit breaker that fails fast during a sustained outage, and a fallback so users get a degraded-but-working experience instead of a hang.
“Design a reliable wrapper around a flaky LLM API.”Stretch
Model answer

Wrap every call in layers. On the request path: stream tokens (better UX, early stall detection), a timeout, bounded retries with exponential backoff + jitter for transient 429/5xx, a circuit breaker that fails fast during a sustained outage, and a fallback to a backup model/provider — ideally via a gateway. Make actions idempotent with idempotency keys so a retry can't double-charge or double-send. Pin the model version to avoid silent updates. Keep prompts and configs in git, gate changes on an eval set, and roll out by canary then A/B. Finally, observe everything — cost, latency p50/p95, error and fallback rates, and traces — so you catch regressions fast. The framing: the model is an unreliable, non-deterministic, pay-per-token dependency, and every layer makes that unreliability invisible to the user.

How to say it out loud say it

“Streaming, timeout, retries with backoff + jitter, circuit breaker, fallback provider — usually behind a gateway. Idempotency keys for real-world actions, a pinned model version, prompts in git gated by evals, and canary-then-A/B rollout. Plus full observability on cost, latency and error rates. The goal is to make a flaky, non-deterministic dependency feel solid to the user.”

“How do you safely ship a new prompt to production?”Core
Model answer

Treat the prompt as code. Commit it to git so it's reviewed, versioned and revertible. Run it against an eval set as a release gate to catch regressions offline. Then canary to a small slice of traffic while watching quality, cost, latency and errors; if the signals hold, A/B it against the current version on real outcome metrics to prove it's actually better; only then roll out to 100% — with a fast rollback if anything dips. Because answer quality can't be fully unit-tested, those layers (eval → canary → A/B) are how you de-risk.

How to say it out loud say it

“Prompt-in-git, reviewed and versioned; gate it on an eval set; canary to a small slice while watching metrics; A/B against the old version to prove it's better; then full rollout with instant rollback. Layers, because you can't unit-test quality.”
