Productionization · routing & gateways

Model routing & gateways IV NEW

Not every request deserves your most expensive model — and no single provider stays up forever. Routing sends each request to the right model (cheap for easy, frontier for hard), and an LLM gateway is the smart switchboard in front of it all: one API, automatic fallback, and a single place for rate-limits and spend. Together they're how you cut cost and stop one outage from taking you down.

01  Model routing: right model for the job NEW

Most real traffic is a mix: a flood of easy requests (greetings, simple lookups, short classifications) and a trickle of genuinely hard ones (multi-step reasoning, tricky code, planning). Paying frontier prices for the easy majority is pure waste. Model routing inspects each request and picks the cheapest model likely to get it right, escalating only when needed.

A hospital triage nurse analogy

You don't put every patient in front of a brain surgeon. A triage nurse sees everyone first: a scraped knee gets a quick bandage, chest pain gets escalated to the specialist immediately. A router is that nurse for requests — the cheap model handles the routine, and only the hard cases reach the costly specialist. The whole department runs faster and cheaper because the expert's time is spent where it matters.

Routers decide using one of a few signals, from crude to clever:

Rules / heuristics
Prompt length, detected task type, which feature called, or keywords. Simple, transparent, easy to debug — a great starting point.
A small classifier
A tiny model (or even a cheap LLM) labels difficulty, then you map label → model. More adaptive than rules, still cheap.
Cascade / escalation
Try the cheap model first; if its answer looks weak, escalate to a stronger one. Covered in §3.

02  How routing cuts cost without hurting quality

This is the core interview question, so be crisp. The insight: quality on easy tasks saturates — a small model already nails “classify this ticket” or “is this spam,” so a frontier model adds cost with no measurable benefit. Quality only diverges on hard tasks. Routing exploits that gap: spend big only where the extra capability changes the answer.

Request typeSmall modelFrontier modelRoute to
Greeting / FAQ / classificationAlready correctAlso correct, much pricierSmall — no quality gap to pay for
Summarise a short docUsually fineMarginally betterSmall, with eval to confirm
Multi-step reasoning / planningOften wrongReliableFrontier — the gap is real
Hard code / tricky edge casesMissesSolvesFrontier

The guardrail that makes this safe is your own eval set: you only route a category to the cheap model after measuring that it passes there. Done right, routing is close to free quality-wise because you never downgrade the cases that actually need power.

The router itself costs something gotcha

If your “difficulty classifier” is itself an LLM call, you've added latency and cost to every request — which can wipe out the savings on cheap traffic. Keep the routing decision lightweight (rules or a tiny classifier), and make sure the average saving comfortably exceeds the routing overhead. Also watch for misroutes: a hard question sent to the small model produces a confidently wrong answer, so pair routing with a confidence check or eval monitoring.

03  Cascades & confidence-based escalation

A cascade flips the order: instead of predicting difficulty up front, you try cheap first and escalate on failure. Run the small model, judge whether its answer is good enough, and only call the expensive model if it isn't.

A two-tier cascade
request
try cheap model
small / fast / open-weight
check
good enough?
confidence, schema, self-grade
escalate?
only if it fails

Most requests stop at the cheap tier; only the hard residue pays frontier prices. The art is the “good enough?” check — a self-reported confidence, a schema/validator pass, a cheap LLM-as-judge, or a heuristic. A weak check is the failure mode: too lax and bad answers slip through, too strict and you escalate everything.

Cascades shine when failures are detectable (e.g. the answer must parse as valid JSON, or pass a unit test). When you can't tell good from bad cheaply, up-front routing by category is safer.

04  LLM gateways: one front door for many models NEW

An LLM gateway (a.k.a. AI gateway or LLM proxy) sits between your app and every model provider. Your code calls the gateway in one consistent format; the gateway translates to whichever provider, handles failover, and centralises the cross-cutting concerns. Popular options as of June 2026 include LiteLLM (open-source proxy/SDK), OpenRouter (hosted, many models behind one API), and cloud offerings like Cloudflare AI Gateway and Kong AI Gateway.

A universal power adapter analogy

Travel anywhere with one universal plug adapter and you never care what shape the wall socket is. A gateway is that adapter for models: your app speaks one “shape” of request, and the gateway fits it to OpenAI, Anthropic, Google, or your self-hosted model — and quietly switches sockets if one goes dead. Swap providers without rewiring your app.

What a gateway buys you:

Unified API
One request format for every provider, so swapping or adding models is a config change, not a code rewrite. No vendor lock-in.
Fallback & failover
If provider A errors or times out, retry on provider B automatically — the resilience backbone of multi-provider setups (§5).
Rate-limit & quota management
Enforce per-key/per-team limits and spread load across providers so you stay under each one's ceiling (as of June 2026).
Central spend & logging
One place to track cost, set budgets, log requests, and apply caching — instead of scattering it across services.
Routing hooks
Many gateways implement the routing/cascade logic from §1–3 for you, by config.
Routing ≠ gateway note

Keep the two ideas distinct in an interview. Routing is the decision of which model handles a request. A gateway is the infrastructure that fronts all providers (unified API, fallback, limits, logging) and is a natural place to run routing — but you can route without a gateway, and a gateway can just proxy without routing. The LLM gateway system-design case builds one end to end.

05  Provider failover & multi-provider resilience

Any single provider will have a bad moment — an outage, a regional blip, a rate-limit wall, or a sudden latency spike. If your whole product hangs off one API, their incident is your incident. Multi-provider resilience means you can fail over to an equivalent model elsewhere.

gateway_fallback.py
# Pseudocode for the pattern a gateway implements for you.
# An ordered list of interchangeable models across providers.
fallbacks = [
    ("provider_a", "frontier-model"),    # preferred
    ("provider_b", "comparable-model"),  # different vendor, similar quality
    ("self_hosted", "open-weight-model") # last resort you fully control
]

def call_with_fallback(messages):
    last_error = None
    for provider, model in fallbacks:
        try:
            return call(provider, model, messages, timeout=20)
        except (RateLimited, ProviderDown, Timeout) as e:
            last_error = e
            continue              # try the next provider in the list
    raise AllProvidersFailed(last_error)   # degrade gracefully, don't hang

Two caveats keep this honest. First, fallback models must be genuinely interchangeable for the task — validate the backup on your eval too, or a failover quietly degrades quality. Second, prompts may need small tweaks per provider; a gateway smooths the API shape but not every behavioural quirk. For private data, a self-hosted open-weight model makes an excellent last-resort tier you fully control (more in Shipping reliably).

How to say it out loud say it

“I'd put a gateway like LiteLLM or OpenRouter in front of the models so my app speaks one API. Behind it I route by difficulty — cheap model for easy traffic, frontier for hard — validated on an eval set so quality holds. The gateway also gives me automatic fallback across providers, centralised rate-limits and spend tracking, so one provider's outage degrades gracefully instead of taking us down. I'd keep a self-hosted open model as the last-resort tier.”

06  Self-check

Why does routing easy requests to a small model usually cut cost without hurting quality?
On easy, saturated tasks (classification, FAQs) a small model is already correct, so paying frontier prices buys nothing measurable. The capability gap only opens on hard reasoning/coding. Routing spends big exactly there and saves everywhere else — validated on your own eval so you never downgrade the cases that need power.
“What's an LLM gateway and why use one?”Core
Model answer

A gateway is a proxy between your app and all model providers. Your code calls it in one unified format and it translates to OpenAI, Anthropic, Google, or a self-hosted model. It centralises the cross-cutting concerns: automatic fallback when a provider fails, rate-limit and quota management, spend tracking and logging, caching, and often the routing logic itself. The payoffs are no vendor lock-in (swap models by config) and resilience (one provider's outage doesn't take you down). LiteLLM and OpenRouter are common choices as of June 2026.

How to say it out loud say it

“It's a proxy in front of every provider so my app speaks one API. It gives me fallback, centralised rate-limits and spend tracking, caching, and a place to run routing — so I avoid lock-in and survive a provider outage. LiteLLM or OpenRouter, typically.”

“When would you choose a cascade over up-front routing?”Stretch
Model answer

Use a cascade (try cheap, escalate on failure) when failure is cheaply detectable — the output must parse as valid JSON, pass a validator, run as code, or clear a confidence/judge check. Then most traffic stops at the cheap tier and only the genuinely hard residue pays more. Use up-front routing (classify difficulty, then pick the model) when you can't tell good from bad without expensive checking, since a cascade's “good enough?” gate would be unreliable. They also compose: route by category, and within a category cascade. The risk in both is the quality gate — too lax leaks bad answers, too strict escalates everything and erases the savings.

How to say it out loud say it

“Cascade when I can cheaply detect a bad answer — JSON that must parse, code that must run, a confidence check. Route up-front when I can't verify cheaply. The whole thing hinges on the quality gate: too loose and bad answers slip through, too tight and I escalate everything.”
