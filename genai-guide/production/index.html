Productionization · overview

Productionization & LLMOps

A demo that wows in a meeting and a system that survives Monday-morning traffic are two very different animals. Productionization — often called LLMOps — is everything between “it works on my laptop” and “it works for ten thousand strangers, cheaply, reliably, every day.” This module is about the unglamorous engineering that turns a clever prototype into a service you can actually run.

01  A cool demo is not a system

Almost anyone can wire up an LLM call and get an impressive answer once. The hard part is the second answer — and the ten-thousandth, at 9am on Monday when traffic spikes, the provider has a hiccup, one user pastes a 200-page PDF, and finance asks why the bill quadrupled overnight. A prototype optimises for the happy path. A system assumes everything that can go sideways eventually will.

A food-truck recipe vs feeding a stadium analogy

You can cook one perfect burger at home — that's the prototype. Now serve forty thousand fans during a championship game: you need supply chains, a line that never stalls, a backup grill when one breaks, a price that still turns a profit, and a way to tell instantly when the fries are burning. Same burger, completely different problem. Productionizing an LLM app is that jump from kitchen to stadium.

The skills divide neatly into three questions interviewers love: How much does each request cost and how fast is it? (cost & latency), Which model handles which request, and what happens when a provider fails? (routing & gateways), and How do we ship changes without breaking users? (reliability & deployment).

02  What gets harder when you go live

LLM apps inherit every classic production worry — and add a few of their own that trip up engineers used to ordinary services:

Cost is per-token, not per-server
A single chatty user or a runaway agent loop can cost real money. The bill scales with usage, not just infrastructure — and it can surprise you fast.
Latency is partly unavoidable
The model generates one token at a time, so a long answer is slow by nature. You manage perceived speed (streaming) as much as actual speed.
The output is non-deterministic
The same prompt can return different text twice. Tests, caching and idempotency all have to cope with answers that won't sit still.
You depend on someone else's API
Rate limits, outages and quiet model updates are outside your control. Resilience means planning for the provider having a bad day.
“Better” is fuzzy
There's no green/red unit test for answer quality, so you ship behind evals, canaries and A/B tests rather than gut feel.
“It worked in the demo” is the trap gotcha

The single most common mistake is treating a successful prototype as proof it's production-ready. A demo runs once, with friendly input, ignoring cost, and with you watching. Production runs constantly, with adversarial and weird input, on a budget, while you sleep — and a third-party API that will eventually have a bad day. Don't promise a ship date off a demo; promise it after you've put cost, latency, resilience and a rollout plan around it.

03  The LLMOps lifecycle

LLMOps borrows the shape of classic MLOps but loops faster, because prompts and models change weekly. The discipline is a cycle, not a one-way street — you ship, watch, learn, and improve, over and over:

The LLMOps loop — you never really “finish”
1 · build
prompt & pipeline
model, RAG, tools, agents
2 · eval
measure quality
test set before shipping
3 · deploy
ship safely
canary, A/B, staged rollout
4 · monitor
watch in the wild
cost, latency, errors, traces
5 · iterate
improve & repeat
feed learnings back to build
↻ loop
back to build
real traffic reveals the gaps
Build → eval → deploy → monitor → iterate, then loop. The eval and monitor stages live in their own module (Evaluation & observability); this module focuses on the build, deploy and run-cost side — cost, latency, routing and reliability.

04  Three habits that separate junior from senior

If you remember nothing else, remember these — they're the through-line of every page here and the answers interviewers are fishing for:

Measure before you optimise
Don't guess where the cost or the latency goes — instrument it. “I'd look at the per-request token breakdown first” beats “I'd switch models” every time.
Use the cheapest thing that passes your eval
Start small and escalate only when quality demands it. This single idea drives model choice, routing, and caching alike.
Assume the dependency will fail
Timeouts, retries, fallbacks and circuit breakers aren't paranoia — a third-party API will rate-limit or go down, and your service should degrade gracefully, not fall over.
How to say it out loud say it

“Productionizing an LLM app is mostly about three things: keeping cost and latency under control, routing each request to the right model with a fallback when a provider fails, and shipping changes safely behind evals and canaries. The mindset shift is treating the model as a flaky, pay-per-token dependency you have to measure and wrap, not a magic box.”

05  Your map of this module

Three pages, in the order you'd tackle a real launch — first make each request cheap and fast, then decide who serves it and what happens on failure, then ship it without drama:

Engineering for cost & latency IV NEW
The cost levers (model, tokens, caching, routing) and the latency budget — plus prompt caching vs semantic caching, batch APIs and reasoning-effort tuning. The “your bill tripled” drill.
Model routing & gateways IV NEW
Send easy queries to a cheap model and hard ones to a frontier model; put a gateway (LiteLLM, OpenRouter) in front for one API, fallback and rate-limits. Cascades and multi-provider resilience.
Shipping reliably IV NEW
Streaming, timeouts, retries with backoff, circuit breakers and idempotency; prompts-in-git, versioning, canary and A/B rollout; self-host vs API; capacity planning.

06  Self-check

A teammate says “the prototype works great, let's just point production traffic at it.” What's the most senior pushback?
Working once isn't working at scale. Production adds per-token cost control, latency budgets, resilience to a flaky upstream API, and a way to ship changes without breaking users. None of that shows up in a one-shot demo — which is exactly what this module covers.
“What does LLMOps mean to you?”Warm-up
Model answer

It's the operational discipline of running LLM apps in production: the build-eval-deploy-monitor-iterate loop. Concretely it means controlling cost and latency, routing requests across models with fallbacks, shipping prompt and config changes safely (git, canary, A/B), and monitoring quality, cost and errors in the wild. It's MLOps adapted for systems that are pay-per-token, non-deterministic, and dependent on third-party APIs.

How to say it out loud say it

“LLMOps is MLOps for LLM apps — the loop of building, evaluating, deploying, and monitoring. The twist is that the model is a pay-per-token, non-deterministic, third-party dependency, so cost control, routing with fallbacks, and safe rollout matter as much as the prompt itself.”

“What's actually different about productionizing an LLM app vs a normal web service?”Core
Model answer

Three things. First, cost scales per-token with usage, so a chatty user or an agent loop can blow the budget — you cache and route to control it. Second, latency is partly intrinsic because tokens stream out one at a time, so you optimise perceived speed as well as real speed. Third, outputs are non-deterministic and quality is fuzzy, so you can't lean on simple unit tests — you ship behind evals, canaries and A/B tests, and you monitor in production.

How to say it out loud say it

“Three differences: cost is per-token so usage spikes hurt, latency is partly unavoidable because generation is sequential, and outputs are non-deterministic so quality has to be measured with evals rather than asserted with unit tests.”
