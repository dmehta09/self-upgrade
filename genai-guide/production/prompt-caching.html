Prompt caching & cost engineering IV NEW

The cheapest tokens are the ones you don't recompute. Every request to an agent or chat app re-sends the same system prompt, the same tool definitions, the same examples — and without caching, the provider re-processes every one of those tokens at full price, every time. Prompt caching is the single highest-leverage cost knob most teams underuse: a few layout rules and one cache marker can cut input cost by ~90% and make responses start faster. This page is the deep dive on that one lever (the previous page covers the full toolkit). Current as of June 2026.

01  What providers actually cache

When a provider says “prompt caching,” they mean: the serving stack keeps the KV cache of your prompt's prefix — the already-computed attention state for the tokens at the start of your prompt — and reuses it the next time a request arrives with that exact same beginning. The mechanism underneath is prefix caching in the inference engine, covered in KV cache & attention optimizations; this page is about the product layer you actually bill against.

A hit means the expensive prefill step skips straight past the cached tokens — so it's cheaper and the first token arrives sooner (better TTFT, the metric from the previous page). A miss processes everything at full price and (usually for a small premium) writes the prefix into the cache for next time.

Two provider styles exist, and interviewers like you to know both:

Explicit breakpoints (Anthropic-style)
You place cache_control markers on the last block of the stable content — you decide what's cacheable. Entries are short-lived (TTL on the order of minutes, refreshed every time the entry is read), with longer TTLs (e.g. an hour) available at a higher write premium. Maximum control; you own the layout.
Automatic (OpenAI-style)
Any prompt prefix beyond a minimum length is cached transparently — no markers — and repeated prefixes are billed at a discounted read rate. Zero config, but you still own the one thing that matters: putting stable content first.

Exact prices, minimums, and TTLs churn constantly — learn the shape (cheap reads, small write premium, short TTLs, byte-exact matching), and say “as of June 2026” for any number you quote.

A save point in a video game analogy

Without caching, the model “replays” your entire prompt from the first token on every single request — like restarting a game from the opening cutscene each time. A prompt cache is a save point placed right at the end of the stable part: the next request loads the save and plays only the new bit. But the save is byte-exact — change one word anywhere before the save point (a timestamp, a name) and the save file no longer matches; the game restarts from zero. That single fact drives every rule in the next section.

02  Cache-friendly prompt layout — the core skill

Caching matches the prefix byte-for-byte, left to right. So the entire engineering skill reduces to one ordering rule: stable content first, volatile content last. The canonical layout:

1. System prompt
Frozen. Never interpolate anything per-request into it.
2. Tool definitions
Serialized deterministically (sorted keys, fixed order) so the bytes never wobble.
3. Few-shot examples
A fixed set in a fixed order — not randomly sampled.
4. Reference docs
Shared corpus or per-session documents that many requests reuse.
5. THEN the volatile tail
Per-request user content, retrieved chunks that vary per query, conversation history's newest turn — everything that changes goes after the cacheable prefix.
One volatile byte kills everything after it gotcha

A single timestamp, request-id, or user name interpolated into the system prompt invalidates every byte after it — your 20k-token prompt caches nothing, every request, and nobody notices because nothing errors. Subtler killers: tool definitions re-serialized with non-deterministic key order (json.dumps without sort_keys=True), few-shot examples drawn with random.sample, and conditional sections toggled per user. If your provider reports cached-token counts in the usage object, alert when they sit at zero — that's a silent invalidator at work.

Here's the same prompt assembly, broken and fixed:

assemble_bad.py
# BAD — volatile bytes at the TOP poison the whole prefix.
def build_prompt(user, query):
    system = (
        f"Today is {datetime.now()}. "      # changes every request → 0% hit rate
        f"You are helping {user.name}. "    # changes every user → no sharing
        + COMPANY_PLAYBOOK                  # 20k stable tokens... all wasted
    )
    tools    = json.dumps(TOOL_DEFS)            # dict order can differ run to run
    examples = random.sample(FEW_SHOTS, k=3)    # different bytes every call
    return system, tools, examples, query
assemble_good.py
# GOOD — frozen prefix first, everything volatile after it.
SYSTEM   = COMPANY_PLAYBOOK                        # byte-identical, every request
TOOLS    = json.dumps(TOOL_DEFS, sort_keys=True)   # deterministic serialization
EXAMPLES = FEW_SHOTS[:3]                           # fixed shots, fixed order

def build_prompt(user, query):
    # Cacheable prefix: SYSTEM + TOOLS + EXAMPLES (+ shared docs).
    # On explicit-breakpoint providers, mark the END of the stable part:
    #   {"text": SYSTEM_BLOCK, "cache_control": {"type": "ephemeral"}}
    # Volatile context goes AFTER the breakpoint, never inside the prefix:
    tail = f"User: {user.name} | Date: {date.today()}\n\nQuestion: {query}"
    return SYSTEM, TOOLS, EXAMPLES, tail

Both versions send the model the same information. One pays full price on every call; the other pays ~0.1× for the prefix on every call after the first. That's the whole skill — and it's a layout decision, not an infrastructure project.

03  The math: when caching pays (and when it doesn't)

The pricing shape (as of June 2026, round numbers): cache writes cost a small premium over normal input — roughly 1.25× — and cache reads cost a steep discount, roughly 0.1×. So the cache pays for itself on the second hit. Worked example, flagged illustrative: an agent with a 20k-token stable prompt (system + tools + examples) called 50 times within the TTL, at a pretend input price of $1 per million tokens:

ScenarioToken-equivalents billedCost (illustrative)
50 calls, no caching50 × 20,000 = 1,000,000$1.000
Call 1 — cache write (1.25×)20,000 × 1.25 = 25,000$0.025
Calls 2–50 — cache reads (0.1×)49 × 20,000 × 0.1 = 98,000$0.098
50 calls, cached — total123,000~$0.12 — roughly 88% off, plus faster TTFT on 49 of 50 calls

That “~90% input-cost reduction” headline is real — but only when the prefix is actually reused. Caching does not pay when:

The prompt is below the cacheable minimum
Providers won't cache short prefixes (minimums on the order of 1k–4k tokens, varying by provider and model). Below the bar, nothing caches — silently, with no error.
The traffic is one-shot
A prefix written once and never read again costs you the 1.25× write premium for zero benefit. Diverse, never-repeating prompts gain nothing from prompt caching — trim and route instead.
TTL expires between calls
If requests arrive further apart than the TTL, every call is a fresh write. A longer TTL can fix this, but longer-TTL writes cost more (commonly ~2× instead of 1.25×), so they need more reads to break even.

04  Prompt caching vs the other knobs

Caching is one lever among several from the cost toolkit. Interviewers love asking how it relates to its neighbours:

vs fine-tuning
Fine-tuning bakes stable knowledge into the weights so the prompt can shrink — but it's slow to change (retrain to update), costs training money, and adds ops burden. Caching keeps the same knowledge editable: change the prompt text, pay one new cache write, done. Reach for tuning only when the prompt can't express the behaviour (see RAG vs fine-tune vs long context).
vs shorter prompts / compression
Trimming saves on every call — hits, misses, and output too — so do it first. But aggressive compression can cost quality. The mature combo: trim what's useless, then cache what's left.
vs app-level semantic caching
A different layer entirely. Semantic caching is a whole-response cache keyed on similar queries (embedding match): a hit skips the model call completely, and it works even across users. Prompt caching is a prefix-compute cache: the model still answers, just cheaper and faster. Semantic caching's risk is serving a stale or subtly-wrong answer to a merely-similar question; prompt caching has no such risk. The previous page has the side-by-side table — in production you usually stack both.

How to say it out loud say it

“Prompt caching reuses the KV cache of an exact, byte-identical prompt prefix, so on a hit prefill skips the cached part — input is billed at a steep discount, around 0.1×, and time-to-first-token drops. The skill is layout: order content stable-to-volatile — frozen system prompt, deterministic tool definitions, fixed examples, shared docs, then per-request content — because one volatile byte invalidates everything after it. It shines on agents and multi-turn chat, where every request replays the whole conversation; for repeated identical questions I layer a semantic response cache on top.”

05  Self-check

A teammate adds f"Today is {datetime.now()}" to the first line of your 20k-token system prompt. What happens to your prompt cache?
Prompt caching is a byte-for-byte prefix match, not a semantic one. A timestamp at position zero makes every request's prefix unique, so nothing after it ever matches — and there's no error, just full-price prefill on every call. Fix: freeze the system prompt and inject volatile context (dates, user names, ids) after the stable prefix.
A 20k-token report-generation prompt runs once per day. The provider's cache TTL is ~5 minutes (refreshed on hit). Should you enable caching on it?
Caching pays when reads follow writes within the TTL. One call a day means a fresh write each time — you'd pay more than without caching. (20k tokens is comfortably above typical minimums, so that's not the issue.) A longer TTL could help bursty traffic, but its higher write cost still can't rescue a once-a-day prompt; this workload belongs in a batch API instead.
Why are multi-turn agents the single best customer for prompt caching?
The API is stateless: each agent step replays the system prompt, tool definitions, and all prior turns. Without caching, a 30-step agent run re-bills that growing prefix 30 times at full price; with caching, each step reads everything before the newest turn at ~0.1×. Note the cache doesn't replace resending the conversation — you still send it; the provider just skips recomputing it.
