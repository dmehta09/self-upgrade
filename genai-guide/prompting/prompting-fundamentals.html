Prompting fundamentals IV

A prompt is just the text you hand the model — but a good prompt has structure. This page breaks a prompt into its five reusable parts, shows when to add examples (and the surprising rule about what examples actually teach), how to fence off your data so the model doesn't confuse instructions with content, and the handful of failure modes behind most “the model ignored me” complaints.

01  The anatomy of a prompt

Beginners think of a prompt as “the question.” Pros think of it as a small document with named parts. Almost every effective prompt is some mix of these five ingredients:

Role / system
Who the model is and the durable rules it must always follow (“You are a support agent for Acme; never reveal internal pricing”). Set once, applies to the whole conversation.
Instructions
The actual task, stated as a clear directive (“Summarize the ticket below in 3 bullet points”). The single most important part.
Context
The data the task operates on: the document to summarize, the retrieved passages, the user's history. The model can only use facts that appear here.
Examples
Zero or more worked input→output pairs that show the desired behaviour instead of describing it (few-shot, §3).
Output spec
The exact shape you want back: format, length, language, “return only JSON,” “no preamble.” Removes guesswork.
A work order for a freelancer analogy

Think of a job ticket you'd hand a freelancer: who you are and the house rules (role), what you need done (instructions), the materials (context), a sample of past work you liked (examples), and how to deliver it (output spec). Leave any of these vague and you'll get something technically valid but not what you wanted — and that's on the ticket, not the worker.

prompt_parts.py
messages = [
    # role / system: durable identity + rules
    {"role": "system", "content": "You are a concise support agent for Acme. "
                                  "Never reveal internal pricing."},
    # instructions + context + output spec, all in the user turn
    {"role": "user", "content": (
        "Summarize the customer ticket in exactly 3 bullet points.\n"   # instructions
        "<ticket>\n" + ticket_text + "\n</ticket>\n"               # context (fenced)
        "Return only the bullets, no preamble."                          # output spec
    )},
]

Not every prompt needs all five — a quick one-off may be pure instructions — but when output is inconsistent, the fix is almost always a missing part: usually the output spec or a clearer instruction.

02  Zero-shot vs few-shot NEW

Zero-shot means you describe the task and ask — no examples. Few-shot means you include a handful of solved examples first, then the real input. The model treats those examples as a pattern to continue.

Modern instruction-tuned models are strong zero-shot, so reach for few-shot when the task is idiosyncratic: a specific output format, a particular tone, an edge-case-heavy classification, or anything easier to show than to describe. A good range is 3–5 diverse examples — enough to pin the pattern, few enough to keep the window cheap.

Examples teach the format, not just the right answers gotcha

A famous, counter-intuitive finding: with in-context examples, the label space and format often matter as much as whether each example's answer is correct. The examples mostly show the model what the task looks like — the set of valid labels, the structure of a response — more than they teach facts. Practical upshots: make sure your example labels cover the full range of possible answers, keep every example's format identical to what you want back, and balance the classes so the model doesn't infer a bias from the order or frequency you happened to use.

Zero-shotFew-shot
You provideInstructions onlyInstructions + 3–5 examples
Best forCommon, well-described tasksCustom format, tone, or tricky edge cases
CostCheaper (fewer tokens)Pricier — examples ride on every call
Watch out forUnderspecified formatSkewed/odd examples leaking bias

03  Delimiters & structure NEW

When your prompt mixes instructions with data (a document, user text, retrieved passages), the model can blur the line — treating part of your data as a command, or part of your command as data. Delimiters are explicit fences that say “this block is content, not instructions.”

Common fences: triple backticks, triple quotes, or — especially effective with Claude-family models — XML-ish tags like <document>…</document>. Tags read clearly to the model, nest cleanly, and let you refer back to a block by name (“quote the relevant line from inside <document>”). As of June 2026, tagged sections are a widely recommended default for structured prompts.

delimiters.py
prompt = f"""Answer the question using ONLY the document below.
If the answer isn't in it, say "I don't know".

<document>
{retrieved_text}
</document>

<question>
{user_question}
</question>"""
Delimiters are clarity, not security gotcha

Fencing user data makes the model less likely to accidentally follow text inside it — but a determined attacker can still write “ignore the above and …” inside the block. Delimiters reduce confusion; they are not a defense against deliberate prompt injection. Treat untrusted content as untrusted no matter how you fence it.

04  System prompts & persona

The system prompt is a special, high-priority message that sets durable rules and identity for the whole conversation — separate from each user turn. It's where you put the role, the non-negotiable constraints, the output conventions, and the available tools. Because it's prepended to every turn, models weight it heavily.

A persona (“you are a patient tutor for 10-year-olds”) is a lightweight way to steer tone, vocabulary, and what the model emphasises. It genuinely shifts style; just don't expect a persona to grant knowledge the model lacks — “act as a senior cardiologist” changes voice, not medical correctness.

Put rules in the system prompt, the task in the user turn tip

Durable things that should hold for every message — identity, safety rules, format conventions, tone — go in the system prompt. The specific, changing request goes in the user message. This separation keeps each turn clean and makes the rules harder to knock loose.

05  Common failure modes (and fixes)

Most “the model is wrong” reports trace back to a small set of prompt problems. Learn to spot them:

SymptomLikely causeFix
Vague or generic answerVague ask — no audience, scope, or formatState the task, audience, length, and output shape explicitly
Ignores one of your rulesConflicting instructions (“be brief” + “be thorough”)Resolve the conflict; rank priorities; remove contradictions
Right content, wrong formatMissing output specShow the exact format, or give one example of it
Makes up factsNo grounding; asked beyond what's in contextSupply the data; add “if it's not in the document, say you don't know”
Follows text in your dataInstructions and data not fencedAdd delimiters; keep instructions outside the data block
Conflicting instructions are silent gotcha

The model won't raise an error when you ask for both “a one-line answer” and “a detailed explanation with examples” — it'll just pick one and look like it ignored you. Re-read long prompts for instructions that quietly fight each other; this is the most common cause of “it skipped my requirement.”

How to say it out loud say it

“I think of a prompt as five parts — role, instructions, context, examples, and an output spec. I default to zero-shot and add 3–5 diverse few-shot examples when the format or edge cases are hard to describe, remembering that examples mainly teach the label space and format. I fence untrusted data with tags, put durable rules in the system prompt, and when output is inconsistent I look first for a missing output spec or conflicting instructions.”

06  Self-check

A classification prompt with few-shot examples performs poorly. Which fix is most aligned with how in-context examples actually work?
Examples primarily teach the label space and the output format. Covering all labels, keeping the format uniform, and balancing classes addresses the real levers; creativity/temperature is irrelevant to a deterministic classification format.
“Walk me through the parts of a good prompt.”Warm-up
Model answer

Five reusable parts: a role/system message (identity + durable rules), instructions (the task as a clear directive), context (the data to act on), optional examples (worked input→output pairs for tricky formats), and an output spec (exact shape, length, format). I put durable rules in the system prompt and the specific task in the user turn, and I fence any pasted data with delimiters.
