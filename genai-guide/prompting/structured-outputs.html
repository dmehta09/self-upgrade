Structured outputs IV NEW

Chat is great for humans, but software wants data — a JSON object with the right fields, every time, never a chatty “Sure! Here's your JSON:”. Structured outputs make a model emit machine-readable results reliably. This page covers the spectrum from “please return JSON” to schemas the model cannot violate, how that's enforced at the token level, and when locking things down too hard backfires.

01  Why structure, and the core analogy

If an LLM's reply feeds another program — a database write, an API call, a UI component — you need it in a predictable shape. Free-form prose is unparseable; you can't reliably json.loads() an essay. Structured outputs constrain the model to produce something a machine can consume directly.

A fill-in-the-blank form vs a free essay analogy

Ask someone to “tell me about yourself” and you get a rambling paragraph — lovely, but you can't file it. Hand them a form with labelled boxes — Name, DOB, Email — and you get back exactly the fields you need, in order, ready to enter into a system. Structured outputs turn the model's reply from an essay into a form.

02  JSON mode vs strict JSON-Schema NEW

There are two distinct guarantees, and conflating them is a classic interview slip:

JSON mode
The model is told to return syntactically valid JSON — it'll parse, no markdown fences or prose. But it does not guarantee your shape: fields can be missing, renamed, or the wrong type.
Strict JSON-Schema / structured outputs
You supply a schema, and the output is guaranteed to conform to it — required fields present, correct types, allowed enum values, no extras. This is “structured outputs” proper, and as of June 2026 it's mainstream across major providers.
JSON modeStrict JSON-Schema
GuaranteesValid JSON syntaxValid JSON and matches your schema
Fields/typesNot guaranteedRequired fields, correct types, enums enforced
You provideAn instructionAn explicit schema (JSON Schema)
Use whenLoose, you'll validate yourselfThe shape must be exact (DB/API)
“Valid JSON” ≠ “the JSON I asked for” gotcha

JSON mode can hand you {"answer": "blue"} when your code expected {"color": "blue", "confidence": 0.9} — perfectly valid, completely wrong shape. If your downstream code depends on specific fields, you need a schema, not just JSON mode.

03  How validity is enforced: constrained decoding NEW

How can a probabilistic next-token predictor be guaranteed to produce schema-valid JSON? The trick is constrained decoding (a.k.a. grammar-constrained generation). At each step the model proposes probabilities over the whole vocabulary — but the decoder consults a grammar derived from your schema and masks out every token that would make the output invalid, sampling only from what's still legal.

Bumper bowling for tokens analogy

Picture bumpers in the gutters of a bowling lane: the ball can roll anywhere between them, but it physically can't go into the gutter. Constrained decoding raises bumpers around the grammar — if a { was just opened, only tokens that continue valid JSON are allowed. The model still chooses what to say within the rails; it just can't produce something that breaks the structure.

This is enforced at the token level during generation, which is why the guarantee is hard rather than hopeful — invalid output is made literally unsamplable. (It does add a little decoding overhead, and the grammar has to be compiled from the schema.)

04  Defining schemas: Pydantic / Zod

You rarely hand-write raw JSON Schema. In Python you describe the shape with a Pydantic model (TypeScript uses Zod); the library emits the JSON Schema for you and validates results coming back. One definition does double duty — it constrains generation and parses the reply into a typed object.

structured.py
from pydantic import BaseModel
from enum import Enum

class Sentiment(str, Enum):
    positive = "positive"
    neutral = "neutral"
    negative = "negative"

class Review(BaseModel):
    sentiment: Sentiment          # constrained to the three enum values
    score: float                  # must be a number
    summary: str                  # required string

# Pass the model as the schema; the SDK returns a typed, validated object.
result = client.parse(model="...", schema=Review, messages=[...])
print(result.sentiment, result.score)   # already a Review instance

The enum is doing real work: with strict structured outputs, sentiment can only be one of those three strings — the model can't invent “mixed” or “happy.” That's the schema acting as guardrails.

05  Validation & retries

Even with strict schemas you keep a safety net, because the values can still be wrong even when the shape is right (a number out of range, a date in the future, a field that's valid JSON but nonsense). The standard loop:

Generate → validate → retry

model returns JSON
schema-constrained
validate
parse + check values
Pydantic + business rules
retry
on failure
re-ask with the error message
If validation fails, feed the specific error back (“score must be 0–1; you returned 4.2”) and let the model self-correct. A capped retry count prevents infinite loops.

Returning the precise validation error to the model is the key: a targeted “you violated rule X” fixes far more reliably than a blind “try again.”

06  When over-constraining hurts

Tight schemas feel safe, but locking the model down too hard can degrade the content inside the fields. Two ways it bites:

  • No room to reason. If the schema forces an answer field first and offers nowhere to think, you've effectively banned chain-of-thought. Fix: add a reasoning string field before the answer fields so the model can work before it commits.
  • Brittle, contorted output. An over-specific schema (deep nesting, rigid enums for things that are genuinely open-ended) can force the model to mangle a good answer into a bad-fitting box, or trip the retry loop repeatedly.
Structure can crowd out quality gotcha

Forcing a model straight into a rigid answer field, with no space to reason, often lowers correctness on hard tasks — you traded thinking for tidiness. Constrain the shape you truly need, leave a reasoning field where it helps, and don't over-specify fields that are inherently free-form.

How to say it out loud say it

“JSON mode guarantees valid JSON syntax; strict structured outputs guarantee my schema — required fields, types, enums. That's enforced by constrained decoding, which masks any token that would break the grammar at generation time. I define schemas with Pydantic or Zod, keep a validate-and-retry loop that feeds the exact error back, and I avoid over-constraining — I leave a reasoning field where the model needs to think, because rigid schemas can hurt the answer quality.”

07  Self-check

How does strict structured output guarantee schema-valid JSON from a probabilistic model?
The guarantee is enforced during decoding: a grammar from the schema masks illegal tokens at each step, making invalid output unsamplable. Temperature 0 doesn't constrain structure, and post-hoc fixing isn't a guarantee.
“What's the difference between JSON mode and structured outputs?”Core
Model answer

JSON mode guarantees the output parses as valid JSON but not its shape — fields and types can be off. Structured outputs (strict JSON-Schema) guarantee the output matches a schema you supply: required fields present, correct types, enums respected, no extras. The first is “it's JSON,” the second is “it's my JSON,” and it's enforced via constrained decoding.

How to say it out loud say it

“JSON mode = valid JSON. Structured outputs = valid JSON that matches my schema, enforced by constrained decoding. I use a schema whenever downstream code depends on specific fields.”
