Prompting & context · context engineering

Context engineering IV NEW

Prompting is wording one message; context engineering is the bigger game of deciding what the model sees, when, and in what form — across a whole conversation or agent run. This is the discipline that separates a demo from a product. It's mostly about respecting one hard limit: the context window is finite RAM, and you are its memory manager.

01  What context engineering is

A clean definition to keep in your back pocket: context engineering is deciding what information enters the model's context window, at what moment, and in what representation. Three questions, every turn — what to include, when to include it, and in what form (raw text? a summary? a structured table? a tool result?).

It generalises prompting. A single prompt is a static slice of context; context engineering is the dynamic management of that slice as a conversation grows, documents get retrieved, tools return data, and memories accumulate. As of June 2026 it's the standard framing for building with LLMs, and the lens interviewers expect for anything beyond a one-shot call.

You're the model's working-memory coach analogy

Imagine prepping a brilliant colleague who can only hold a few things in mind at once before something falls out. Your job isn't to make them smarter — it's to put the right few things in front of them at the right moment, summarise the rest, and hand them a reference sheet for the details. That curation is context engineering.

02  The four sources of context

Everything that lands in the window comes from one of four places. Naming them helps you reason about what to keep and what to cut:

Instructions
The system prompt, persona, rules, output spec, tool definitions. Mostly static; the “constitution” of the session.
Retrieval
Documents pulled in on demand — RAG passages, search results, database rows. Fetched per query based on relevance (see the RAG module).
Memory
Carried-over knowledge: chat history, user preferences, facts from earlier sessions. The part that grows and must be managed (see agent memory).
Tool results
Outputs of actions the model took — an API response, a calculation, code output. Often large and noisy; trim before re-inserting.

The art is budgeting a finite window across these four. A long chat history (memory) competing with ten retrieved passages competing with verbose tool output — something has to give, and deciding what gives is the job.

03  Window as RAM, external store as disk NEW

The mental model that ties it all together: the context window is RAM — fast, finite, and the only thing the model can directly compute over. Everything else — vector databases, document stores, files, past-conversation logs — is disk: vast and durable, but invisible to the model until you load a piece of it into RAM.

The memory hierarchy of an LLM app
RAM · window
what the model sees now
instructions + active history + fetched docs
disk · stores
everything else
vector DB · files · full chat log · memory store
“Paging” the right bytes from disk into RAM at the right moment — and evicting what's stale — is the whole job. Retrieval is a page-in; pruning is an eviction.

Once you see it this way, the techniques in §4 are just memory management: you can't keep everything resident, so you compress, evict, and re-fetch on demand.

04  Compaction, summarization, pruning & “lost in the middle” NEW

When the window fills — a long chat, an agent 30 steps deep — you need to shrink what's resident without losing the thread. Three moves:

Summarization
Replace a long stretch of history with a short recap (“earlier: user is migrating a Postgres DB to v16; we ruled out option A”). Keeps the gist, drops the token bulk.
Compaction
Periodically rewrite the whole working context into a tighter form — merge redundant turns, fold tool noise into conclusions. Common in long agent runs to stop context from ballooning.
Pruning
Drop what's no longer relevant outright — stale tool dumps, superseded drafts, off-topic tangents. The “eviction” of the RAM analogy.

Why bother, if windows are huge? Because of a real, measured effect:

“Lost in the middle” gotcha

Models attend most reliably to the start and end of a long context and are likeliest to overlook facts buried in the middle. So a critical instruction or document sitting halfway through a 200k-token prompt can be effectively ignored. Mitigations: keep the window lean, put the most important material near the top or bottom, and don't assume “it's in the context” means “the model used it.”

05  The long-context reality check NEW

It's tempting to think 1M+ token windows (common as of June 2026) make context engineering obsolete — just paste everything. They don't, for three stubborn reasons:

  1. Cost. You pay per token every call. A 500k-token prompt repeated across a conversation is real money, fast.
  2. Latency. More input tokens mean more to process before the first output token — a big window can make responses noticeably slower.
  3. Accuracy. Lost-in-the-middle and general dilution mean a bloated context can lower answer quality, not raise it. Signal-to-noise matters more than raw capacity.
“A bigger window solved context” is a trap answer gotcha

If an interviewer floats this, push back: a larger window raises the ceiling but doesn't remove the cost, latency, and dilution problems. Curating a tight, high-signal context still beats dumping everything — even when everything would fit.

06  Files-as-memory NEW

A powerful 2026 pattern, especially for agents: instead of cramming long-lived state into the window, let the model read and write files (a scratchpad, a notes file, a task list). The window holds only what's needed right now; the durable record lives on “disk,” and the model pages pieces back in as required.

A notebook for a forgetful genius analogy

You don't keep every fact in your head — you jot things in a notebook and flip back when needed. Files-as-memory gives the model that notebook: it writes down decisions and progress, clears its head (the window), and re-reads the relevant page later. The window stays small even on a task that spans hundreds of steps.

This is the bridge to agent memory: programmatic, externalised state that survives beyond what fits in RAM.

How to say it out loud say it

“Context engineering is deciding what the model sees, when, and in what form. Context comes from four sources — instructions, retrieval, memory, and tool results — and they all compete for a finite window, which I treat as RAM with external stores as disk. As it fills I summarise, compact, and prune, and I keep critical material at the start or end because of lost-in-the-middle. A bigger window doesn't solve this — cost, latency, and dilution remain — so I curate. For long-running agents I lean on files-as-memory so the window stays lean.”

07  Self-check

A critical instruction placed in the exact middle of a 200k-token prompt seems to be ignored. What's the most likely explanation?
A 200k-token prompt fits in a large window, so it wasn't truncated. The known lost-in-the-middle effect means buried content gets less reliable attention — move it to the top or bottom and trim the surrounding bulk.
