Design a RAG chatbot IV

The classic opener: “design an internal assistant that answers employees' questions from company docs, with citations.” It's the canonical RAG prompt — Confluence, Google Drive, a wiki, some PDFs, a Slack bot front-end. We'll run the 6-step method top to bottom, narrating each step the way you would at a whiteboard, and land on the trade-offs and failure modes that separate a senior answer from a recited diagram.

01  Step 1 — Requirements & clarifying questions

Resist the urge to draw. The first 90 seconds are for scoping out loud — the interviewer is grading whether you find the constraints that change the design. I'd ask these four before anything else:

Who asks, and about what?

All employees, or a team? Are answers access-controlled (HR docs vs public wiki)? That single answer decides whether retrieval needs per-user permission filtering — a make-or-break detail.

What does “good” mean?

Grounded answers with citations, an honest “I don't know” when the docs are silent, and a tone that matches the company. No citation = not done.

What's the corpus?

How many docs, what formats (Markdown, PDF, HTML, tickets), how often do they change, and how big — 10k pages or 10M? Size and churn drive the index and the freshness story.

Scale & surface?

Daily active users, peak QPS, conversational (multi-turn) or one-shot, web app or Slack bot? Latency budget and whether we stream tokens both fall out of this.

My assumptions (stated, so I can move on): ~5,000 employees, a few thousand daily questions peaking around 5–10 QPS, a corpus of ~500k chunks across a wiki + Drive + a ticketing system, docs that change daily, multi-turn chat in a web widget, and citations as a hard requirement. Some docs are access-restricted, so retrieval must be permission-aware. I'll flag where a different answer flips the design.

02  Step 2 — Constraints, SLAs & NFRs

Now I pin the non-functional spine with rough numbers. Stating these early is the single biggest “sounds senior” signal — every later trade-off references back to them:

Latency
p95 ≤ 3 s to a complete answer, but time-to-first-token < 800 ms because we stream — perceived latency is what users feel. Retrieval + rerank gets a ~300–500 ms budget.
Throughput
~5–10 QPS sustained, design headroom to ~50 QPS for spikes. Embedding and rerank are batchable; the LLM call dominates wall-clock.
Cost / request
Target ~$0.005–0.02 per answered question. Dominated by LLM input tokens (the retrieved context), so context size and caching are the cost levers, not the embedding call.
Freshness
New/edited docs searchable within ~1 hour (scheduled incremental re-indexing); same-day is fine for this use case. Deletes/permission changes should propagate faster — ideally event-driven.
Safety / PII
Prompt-injection defense (a doc can contain “ignore your instructions”), no leaking restricted content, no fabricated citations. Output guardrails + grounding checks before the answer ships.
Privacy
Internal docs can be sensitive → data-residency and “does text leave our walls?” often decide self-host vs API. Assume a vendor with a no-training, zero-retention enterprise tier is acceptable here; note it explicitly.

An open-book exam, not a memory test analogy

RAG turns a closed-book exam (the model guessing from memory) into an open-book one. Ingest is building the textbook and its index; the query path is a smart student who looks up the right pages, reads only those, and answers citing the page numbers. Most failures aren't the student being dumb — they're the index missing the page, or the student grabbing the wrong chapter.

04  Step 4 — Component deep-dives

Now zoom into the boxes that actually move quality, latency and cost. I'd lead with chunking and retrieval, because that's where RAG usually lives or dies:

Chunking
Structure-aware splits (by heading/section), ~400–800 tokens with a small overlap, never mid-sentence. Carry metadata (title, section, URL, last-modified, ACL) on each chunk. Bad chunking quietly caps your ceiling — see Chunking strategies.
Embedding model
A strong general text-embedding model (~1024-dim is plenty); pick by retrieval benchmark on your domain, and pin the version — re-embedding 500k chunks on a silent model swap is a real migration. Same model for ingest and query.
Hybrid retrieval
Dense (semantic) + BM25 (keyword), fused (e.g. reciprocal-rank fusion). Dense catches paraphrase; BM25 nails exact terms, error codes and acronyms employees actually type. This is the June-2026 default — see Hybrid search & rerank.
Reranker
A cross-encoder rescores ~40 candidates down to the 4–8 you'll actually pass in. It's the cheapest big precision win in RAG; budget ~50–150 ms. Skipping it is the most common reason answers feel “off-topic but confident.”
Prompt assembly
System prompt + numbered context blocks + the question. Include a hard citation instruction: <cite> the source id for every claim, and answer only from the provided context — if it's not there, say you don't know.
Caching
Two layers: a prompt/KV cache for the stable system prompt, and a semantic cache keyed on normalized query embedding for repeated FAQs. Big cost + latency win; just scope cache entries by ACL so you never serve restricted content to the wrong user.
Streaming
Stream tokens over SSE/websocket so first token lands <800 ms while the full answer finishes later. Resolve citation markers to real links as you stream, or in a quick post-pass.
How to say it out loud say it

“Retrieval is hybrid — dense plus BM25 — then a cross-encoder reranker trims ~40 candidates to the best handful. I prompt the model to answer only from that context and cite each claim by source id, so a wrong answer is debuggable: I look at the trace and ask whether retrieval missed the doc or generation ignored it.”

The four classic RAG failure modes gotcha

Stale index — a doc changed but the embedding didn't, so you cite the old answer (fix: scheduled + event-driven re-indexing, store last-modified). Hallucinated citations — the model invents a plausible-looking source id (fix: a grounding check that verifies every citation resolves to a retrieved chunk before shipping). Retrieval misses — the right doc never makes top-k, so the model improvises (fix: hybrid + rerank, measure hit-rate, raise k before generation). Cost blow-ups — stuffing 20 chunks × multi-turn history balloons input tokens (fix: rerank to 4–8, cap history, cache). And always handle “the docs don't contain this” → answer “I don't know,” never fabricate.

06  Step 6 — Evaluation, extensions & scaling

Finish on a senior note: how you'd know it works, and how it grows. In June 2026, eval is a production gate, not an afterthought — you don't ship a retrieval or prompt change until it clears the eval set.

Retrieval metrics
Hit-rate@k and MRR on a labelled set (question → gold chunk). This isolates the retriever from the generator — debug retrieval first.
Answer quality
RAGAS-style scores: faithfulness (is every claim grounded in the context?), answer relevance, and context precision/recall. Run them in CI against a golden set as the release gate.
Online signals
Thumbs up/down, “was this cited correctly?”, deflection rate, and traces of low-rated answers fed back into the eval set. Offline catches regressions; online catches reality.
Scaling
Shard/replicate the vector DB, autoscale the stateless query service, lean on semantic + prompt caching for hot questions, and route easy queries to a cheaper model. Re-indexing scales horizontally as a batch job.

Your turn · two extensions

(1) Add per-user access control to retrieval so an employee never sees a chunk they can't open. (2) The corpus grows 100× (to ~50M chunks) — what changes?

Think about where the permission check happens (and the cost of doing it wrong), and which parts of the architecture become the bottleneck at 100× before you peek.

Stuck? Reveal a hint hint

For access control: tag every chunk at ingest with its source ACL, then filter inside the retrieval query (a metadata pre-filter), not after — post-filtering can empty your top-k and is easy to leak. Scope caches by ACL too. For 100×: the vector index, not the LLM, becomes the pressure point — think sharding, quantized vectors (PQ/int8), and whether ANN recall still holds.

Show a solution solution

Access control. Store an allowed_groups / ACL tag on each chunk during ingest, sourced from the original doc's permissions. At query time, resolve the user's groups and pass them as a pre-filter on the vector + BM25 search so only authorised chunks are even candidates — never filter after retrieval (you'd leak existence via timing/counts and risk empty results). Propagate permission changes via events, not just the hourly re-index, so revoked access takes effect fast. Make cache keys include the ACL scope, and add a test that a restricted query returns “I don't know,” not a redacted-but-revealing answer.

100× corpus (~50M chunks). The vector store dominates now. Shard the index (by tenant/space) and replicate for read throughput; quantize vectors (int8 or product quantization) to keep RAM and cost sane — see Quantization & scale; re-tune ANN parameters and re-measure recall, because recall quietly drops as the index grows. Ingest becomes a real distributed batch job (parallel embedding, incremental upserts). Retrieval stays roughly constant-time with good ANN, so the LLM and rerank budgets barely move — the win is keeping recall high at scale, which is exactly why hit-rate@k stays on the dashboard.

Your RAG bot gives a confident, well-written answer that's simply wrong. What do you check first?
Most “wrong answer” bugs are retrieval bugs, not generation bugs — the right chunk never made it into context. Splitting retrieval metrics (hit-rate@k, MRR) from answer metrics (faithfulness) lets you fix the actual layer instead of guessing. A bigger model can't cite a doc it was never shown.
“How do you stop the bot from hallucinating citations?”Core
Model answer

Two layers. In the prompt, force the model to answer only from the numbered context and tag each claim with a source id. Then, before shipping, run a deterministic grounding check: every cited id must resolve to a chunk that was actually retrieved this turn, and ideally the claim should be entailed by that chunk (an NLI or LLM-judge check). If a citation doesn't resolve, drop it or fall back to “I don't know.” Track faithfulness on the eval set so regressions are caught in CI.

How to say it out loud say it

“I never trust the model to cite honestly — I verify. Every citation it emits must map back to a chunk we actually retrieved, checked in a post-pass, and faithfulness is a gated metric in CI.”

“Why not just use a long-context model and skip retrieval?”Core
Model answer

For a small, static doc set, long-context can genuinely replace retrieval. But here the corpus is ~500k chunks — it won't fit in any context window, and even if a slice did, you'd pay for and slow down every token on every request. Retrieval narrows to the relevant handful, which is cheaper, faster, gives natural citation anchors, and lets you enforce per-user access control at query time. Long context still helps inside RAG — bigger chunks, more retrieved context — but it complements retrieval, it doesn't remove the need for it.

How to say it out loud say it

“Long context and RAG aren't rivals — at this corpus size retrieval is what makes it affordable, fast, citable and access-controlled. I'd use long context to widen the chunks I feed in, not to skip retrieval.”
