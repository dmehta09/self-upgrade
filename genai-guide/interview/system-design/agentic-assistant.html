Design an agentic assistant IV NEW

“Design an internal ops & research assistant — it should answer questions, but also take actions: search our wiki, call internal APIs, run a bit of code, and file tickets.” That word take actions changes everything. A RAG chatbot reads and replies; an agent loops — it plans, calls a tool, looks at the result, and decides what to do next, possibly many times. The hard parts move from “is the answer grounded?” to “did it do the right things, in the right order, without breaking anything?” We'll run the same six steps, with an eye on cost, safety and reliability the whole way.

01  Step 1 — Requirements & clarifying questions

Agents fail most often because nobody pinned down what they're allowed to do. Before any architecture, separate read-only tasks from action-taking ones, and surface the autonomy level. The questions below are the ones that visibly mark you as senior — ask them out loud.

Which tasks & scope?

Answer questions, or also do things? “Find the on-call owner for service X” (read) vs “open a Sev-2 incident and page them” (act). Pin the top 5 jobs to be done — the long tail can wait.

Autonomy level?

Is it a copilot (suggests, human runs each step), supervised autonomy (acts, but pauses for approval on risky steps), or fully autonomous (runs end-to-end)? Most internal tools should start as a copilot and earn autonomy.

Which tools / actions are allowed?

Enumerate the toolbox: wiki/search, read-only DB queries, internal REST APIs, a code sandbox, the ticketing system. Each tool is an attack surface and a cost line — fewer, well-scoped tools beat a giant pile.

What must NEVER be auto-done?

The blast-radius list: deleting data, spending money, emailing customers, changing prod config, anything irreversible. These require a human-in-the-loop approval gate — the agent proposes, a person confirms.

Success criteria?

What's “good”? Task completion rate, correct tool calls, low human-correction rate, time saved per task — and a hard ceiling on cost and steps per run. Define this now so Step 6's eval has a target.

Who, where, how often?

Internal engineers only, or support agents too? Volume (runs/day), peak concurrency, and how long a single run may take (seconds for a lookup, minutes for a multi-step investigation). Drives sync vs async in Step 5.

A new hire with a company laptop analogy

Think of the agent as a capable but brand-new intern. You wouldn't hand them prod database credentials on day one. You give them read access, a checklist, and a senior who signs off before anything risky ships. “Which tools, what autonomy, what needs approval” is just the intern's onboarding doc — and the interviewer is checking whether you'd write one.

02  Step 2 — Constraints, SLAs & NFRs

A chatbot's NFRs are about one model call. An agent's NFRs compound over a loop: every extra step multiplies latency and cost, and every action multiplies risk. State these as first-class — numbers, even rough ones.

End-to-end latency
Not one call — a whole run. A 5-step task at ~3 s/step is ~15 s. Stream intermediate steps (“searching… reading… drafting ticket…”) so the user sees progress, and set a p95 per run.
Cost / run
The killer metric: tokens × steps, and the context grows each step as observations pile up. A run can cost 10–50× a single chat turn. Cap steps and prune context to keep it bounded.
Safety of actions
Side effects, not just words. Destructive or irreversible actions need an approval gate; all tools need scoped permissions (least privilege) and per-tool rate limits.
Auditability / traceability
Every run must be replayable: the plan, each tool call with its arguments and result, who approved what. Non-negotiable for incident review and compliance.
Reliability / idempotency
Tools can be retried, so “file ticket” must be idempotent (dedupe key) — a retry shouldn't open three tickets. Plan for partial failure: a step can fail mid-run.
Determinism & recovery
Same input shouldn't wildly diverge. Pin model versions, set stopping conditions, and make a stuck or looping run fail closed (stop & ask a human) rather than burn budget.

03  Step 3 — High-level architecture

The heart of an agent isn't a pipeline — it's a loop. The model plans, picks a tool, the executor runs it, the result (an observation) is fed back, and the model decides whether to continue or finish. Memory rides alongside, and risky actions divert through a human approval gate. Everything sits behind a gateway for auth, rate-limits and routing.

04  Step 4 — Component deep-dives

Zoom into the boxes that make or break an agent. Each is a place interviewers love to push.

The loop: ReAct vs plan-execute

Two dominant shapes. ReAct (reason + act) interleaves a thought, an action, and an observation each step — flexible, great when the path isn't known up front, but it can wander. Plan-and-execute writes a full plan first, then executes the steps (re-planning if something fails) — cheaper and more predictable for known workflows, but brittle if the plan was wrong. Many production agents are a hybrid: plan a little, act, observe, adjust.

Tool schemas & MCP

The model can only use a tool it can describe to itself. Each tool is a typed schema — name, description, JSON-shaped parameters — and the model emits a structured call the executor validates and runs. As of 2026, MCP (Model Context Protocol) standardizes this: instead of bespoke glue per integration, tools/data sources expose an MCP server and any agent speaks the same protocol. Keep descriptions crisp and parameters strongly typed — vague schemas are the #1 cause of wrong tool calls.

Agent memory: working + episodic

Working memory is the current run's scratchpad — the plan and the observations so far, living in the context window. It must be pruned: summarize or drop stale observations or the context (and cost) explodes. Episodic memory persists across runs — past tasks, outcomes, learned preferences — usually in a store the agent can retrieve from. Don't conflate them: working memory is cheap and ephemeral; episodic is durable and needs its own retrieval and privacy rules.

Stopping conditions & iteration ceilings

The single most important reliability control. An agent must have hard limits: a max-steps ceiling, a budget cap (tokens/dollars per run), a wall-clock timeout, and a “no progress” detector (same action repeating). When any trips, the run stops and either returns its best partial result or escalates to a human — it never silently loops forever.

Human-in-the-loop approval

For any action on the “never auto-do” list, the loop pauses: the agent presents the proposed action and its arguments (“DELETE rows where status='stale' — 1,204 rows”), and a human approves, edits, or rejects. Implemented as an interrupt that suspends the run and persists state, so it can resume later — possibly minutes or hours after a human responds.

Sandboxing for code & computer use

If the agent runs code or drives a browser/computer, that executor must be isolated: an ephemeral container with no prod credentials, locked-down network egress, CPU/memory/time limits, and a clean teardown. Treat tool output as untrusted too — a web page or API response can carry a prompt-injection payload aimed at hijacking the loop.

05  Step 5 — Trade-offs & bottlenecks

Name the forks and where you'd land. The big four for agents:

DecisionOption AOption BWhen to pick
Topology Single agent (one loop, all tools) Multi-agent (supervisor + specialists) Start single. Split into a supervisor delegating to specialist sub-agents once one agent juggles too many tools or domains. Supervisor is the production-default multi-agent pattern; free-form swarm hand-offs are more frontier/experimental.
Model routing One frontier model everywhere Frontier supervisor + cheaper workers Use a strong model for planning/decisions; route simple, high-volume sub-steps (extraction, classification) to a cheaper/faster model. Cuts cost without dropping plan quality.
Execution mode Sync (hold the request, stream steps) Async / long-running (job + status) Sync for quick lookups (< ~30 s). Go async with a durable job + webhook/poll for multi-minute investigations or anything that pauses for human approval.
Tool breadth Many fine-grained tools Few coarse, well-scoped tools Fewer, sharper tools usually win — too many choices confuse the planner and inflate the prompt. Group related calls behind one tool with clear parameters.
The four ways an agent loop bites you gotcha

Compounding errors: a small mistake at step 2 feeds step 3, which feeds step 4 — error rates multiply across a long trajectory, so a 95%-per-step agent can be far worse over ten steps. Infinite loops: without a step ceiling and a no-progress detector, an agent can retry the same failing action forever, burning tokens. Tool misuse: wrong tool, wrong arguments, or acting on injected instructions from a tool's output. Cost blow-ups: context grows every step, and a runaway loop turns one task into a four-figure bill. Mitigate all four with stopping conditions, budget caps, idempotent tools, scoped permissions, and treating tool output as untrusted.

How to say it out loud say it

“I'd start with a single ReAct-style agent behind a gateway, with a tightly scoped toolset and hard stopping conditions — max steps, a budget cap, and a no-progress detector. Risky actions route through a human approval gate. As it grows I'd move to a supervisor delegating to specialist sub-agents, route planning to a frontier model and cheap sub-steps to a smaller one, and run anything long or approval-gated asynchronously. My top risks are compounding errors and cost blow-ups, so I'd invest early in tracing and per-run budgets.”

06  Step 6 — Evaluation, extensions & scaling

Evaluating an agent is harder than scoring a single answer, because the agent took a path. Measure both ends:

Outcome eval
Did the final result satisfy the task? (Ticket filed correctly, right answer, side effects as intended.) The bottom line, but it hides how it got there.
Trajectory eval
Was the path sensible — right tools, right order, no wasted or dangerous steps? Catches an agent that got lucky, or one that succeeded via a risky route you'd never allow again.
Tool-call correctness
For each step: right tool chosen? arguments valid and well-formed? This is the most actionable signal for debugging a flaky agent.
Efficiency & cost
Steps per task, tokens per run, human-correction rate, dollars per successful task — track these as regressions, not just quality.
Guardrails
Input/output filters, an allowlist of tools, permission checks at the executor, and injection defenses on tool output. Test that the “never auto-do” gate actually holds.

Build a fixed set of representative tasks with known-good outcomes and acceptable trajectories, run it offline on every change, and gate releases on it — exactly like the RAG and gateway cases, plus the trajectory dimension. Online, sample real runs into traces and use LLM-as-judge for trajectory quality at scale. To scale: shard runs across workers, cache deterministic tool results, route models by step difficulty, and add episodic memory so the agent reuses past solutions.

your turn

Your single-agent ops assistant now juggles eight tools across wiki-search, log-querying, deploys, and ticketing — and it occasionally runs a destructive cleanup script without anyone noticing. Redesign it: (1) split it into a supervisor + specialist sub-agents, and (2) add an approval gate for destructive actions. Sketch the topology and say where the gate sits.

hint

Group the eight tools by domain — that grouping is your sub-agents. Ask which actions are reversible: read-only ones (search, query logs) can run freely; irreversible ones (deploy, run cleanup script, delete) are exactly what the gate guards. The gate belongs between deciding to act and actually executing — i.e. between tool select and the executor in the Step 3 diagram. Think about who holds the “never auto-do” list and least-privilege credentials.

solution

Topology. A supervisor agent owns the task and delegates to three read-mostly specialists — a Research sub-agent (wiki-search + doc retrieval), an Observability sub-agent (log/metric queries), and an Ops sub-agent (deploys, cleanup, ticketing). The supervisor plans, routes each subtask to the right specialist, and assembles the result. This shrinks each agent's toolset (so the planner chooses better) and isolates dangerous capabilities to the Ops sub-agent alone.

Approval gate. Tag every Ops tool as reversible or not. Read-only and easily-undone calls execute directly. Destructive/irreversible ones (deploy to prod, run cleanup, delete) hit a human-in-the-loop interrupt placed between tool-select and execution: the run suspends and persists state, the agent surfaces the exact action and arguments (“run cleanup.sh — will delete 1,204 rows”), and a human approves, edits, or rejects before it resumes. Back it with least-privilege credentials per sub-agent (only Ops can even reach the deploy API), idempotency keys so an approved-then-retried action runs once, and a full trace of who approved what. Optionally route the supervisor's planning to a frontier model and the specialists' routine sub-steps to a cheaper one. The result: smaller blast radius, no silent destructive runs, and an auditable trail.

Your agent succeeds on a task — the right ticket gets filed — but a teammate is uneasy. Why might outcome eval alone be misleading here?
Agents take a path. The right ending can come from a wrong or dangerous route (e.g. it deleted a record on the way, or looped ten times before succeeding). Trajectory and tool-call correctness catch what a final-answer check misses — and flag risks before they bite in production.
“How do you stop an agent from looping forever or blowing the budget?”Core
Model answer

Hard stopping conditions, layered: a max-step ceiling, a per-run token/dollar budget cap, a wall-clock timeout, and a no-progress detector that trips when the same action repeats without new information. When any fires, the run fails closed — returns its best partial result or escalates to a human — rather than looping. Pair that with idempotent tools so retries are safe, and tracing so you can see why it stalled.

How to say it out loud say it

“I give every run hard limits — max steps, a budget cap, a timeout, and a no-progress check — and make it fail closed to a human instead of looping. Tools are idempotent so retries don't double-act, and everything is traced.”

“When do you reach for multi-agent instead of one agent?”Core
Model answer

Start single — it's simpler to build, trace and reason about. Reach for multi-agent when one loop juggles too many tools or distinct domains, hurting tool-selection quality, or when you want to isolate dangerous capabilities. The production-default pattern is a supervisor that delegates to specialist sub-agents (each with a small, scoped toolset); free-form swarm hand-offs are more frontier. Bonus: route the supervisor's planning to a frontier model and cheap sub-steps to a smaller one.

How to say it out loud say it

“One agent until it's juggling too many tools or domains — then a supervisor delegating to scoped specialists. Supervisor is the production default; swarm is more frontier. I'd route planning to a strong model and cheap sub-steps to a smaller one.”
