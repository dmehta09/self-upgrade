Design multimodal search IV

“Build search for a catalogue of millions of images — let users search a catalogue of images with text queries, and vice versa.” It's the canonical cross-modal retrieval prompt: a shopping catalogue, a stock-photo library, a media archive. Type “red running shoes on a trail” and get matching photos; drop in a photo and find visually similar items. We'll run the 6-step method top to bottom, and the whole design hinges on one idea — putting images and text into the same vector space so a query and a result are comparable no matter which modality they arrived in.

01  Step 1 — Requirements & clarifying questions

Don't draw yet. The differentiator here is pinning down which cross-modal directions matter and how big the corpus is — those two answers reshape the whole index. I'd ask these four first:

Which query modalities?

Text→image (“navy linen sofa”), image→image (“more like this photo”), or both? Maybe image+text together (“this dress, but in green”). Each direction must land in the same space to be comparable — this single answer decides whether one joint embedder is enough.

How big is the corpus?

1M images or 100M? Static catalogue or a feed that ingests millions of new images a day? Size drives whether a flat index fits in RAM or you need sharding + quantization, and churn drives the re-embed pipeline.

What's the latency bar?

Interactive search wants sub-200 ms feel. Is a heavier VLM rerank on the top results acceptable for quality, or is every millisecond sacred? That sets whether rerank is in the hot path or optional.

What does “relevant” mean?

Visual similarity, semantic match, or business rules (in-stock, this brand, safe-for-work)? Do we need metadata filters (price, category, region) alongside the vector search? “Relevant” is domain-specific and worth nailing down.

My assumptions (stated, so I can move on): a product catalogue of ~10M images growing by a few hundred thousand a week; both text→image and image→image queries; an interactive UI wanting p95 well under a third of a second; relevance = semantic + visual match, filtered by category / price / in-stock; and an optional quality pass we can afford on the top handful of results. I'll flag where a different answer flips the design — especially corpus size and whether image→image is in scope.

02  Step 2 — Constraints, SLAs & NFRs

Now pin the non-functional spine with rough numbers. For search the headline NFRs are query latency and the memory footprint of the index — state them early and every later trade-off references back:

Query latency
p95 ≤ 150–250 ms end-to-end. Budget: embed the query (~10–30 ms text, ~30–80 ms an image through the encoder) + ANN search (~10–50 ms) + optional VLM rerank on the top ~50 (~50–150 ms if enabled). Text queries are faster than image queries because the image encoder is heavier.
Index size / memory
For 10M images at 768-dim float32 that's 10M × 768 × 4 B ≈ ~30 GB of raw vectors — already past one comfy box. int8 quantization cuts it ~4× to ~7–8 GB; binary (1 bit/dim) to ~1 GB. Memory, not compute, is usually the scaling wall — see Quantization & scale.
Ingest throughput
A few hundred thousand new images/week ≈ a few per second sustained, with backfill bursts. The bottleneck is GPU embedding throughput; batch images through the encoder (hundreds/sec/GPU) and upsert vectors + metadata. Backfilling 10M on a model swap is a real multi-hour-to-day job — plan for it.
Cost
Dominated by (a) GPU hours to embed the corpus once + incrementally, and (b) RAM to hold the index hot. Query-time embedding is cheap per call; the levers are quantization (shrinks RAM) and whether you run a VLM reranker (adds GPU per query). No per-token LLM bill unless you add captioning/rerank.
Freshness
New images searchable within minutes via incremental embed + upsert; price/stock metadata should update near-real-time (event-driven) so you never surface an out-of-stock item.
Quality / safety
NSFW and policy filtering on both ingested images and results, and a relevance floor so a weak top result isn't shown as confident. Cross-modal recall on a labelled set is the gate.

03  Step 3 — High-level architecture

Like RAG, this is two pipelines, and saying so explicitly is the move: a slow offline indexing path that encodes every image into the shared space, and a fast online query path that encodes the query into that same space and searches. The key invariant — one embedding space for images and text — is what makes a text query and an image result directly comparable.

Whatever the query modality, it goes through the same joint encoder so its vector lives in the corpus's space. A cache fronts the encoder for repeated text queries; tracing on every hop tells you whether a bad result was an embedding/recall miss or a rerank miss.
One shared map for two languages analogy

Think of a bilingual library where every book — whether written in “image” or in “text” — is shelved by meaning, not by language. CLIP-style training builds that shared map: a photo of a golden retriever and the words “golden retriever” land on nearly the same spot. Search is then just “go to the spot your query maps to, and grab the nearest neighbours” — and it doesn't matter that the query was words and the neighbours are pictures, because they share one coordinate system.

04  Step 4 — Component deep-dives

Now zoom into the boxes that move quality, latency and cost. I'd lead with the joint embedding space, because that's where multimodal search lives or dies:

Joint contrastive embeddings (CLIP)
The heart of it. A CLIP-style dual-encoder is trained with a contrastive loss on image–caption pairs so matching pairs pull together and mismatches push apart — the result is one shared space where text and images are directly comparable by cosine similarity. Use the same model's text tower for queries and image tower for the corpus; pin the version (re-embedding 10M images on a swap is a migration). Modern open options (e.g. SigLIP-family / EVA-CLIP descendants) push recall well past the original CLIP. See Vision-language models.
VLM captions for hybrid
Run a VLM to caption each image at ingest (“a pair of red trail-running shoes on a rocky path”), index those captions with BM25/keyword, and fuse with the dense cross-modal scores (reciprocal-rank fusion). This rescues exact-term queries — brand names, SKUs, “size 11” — that pure CLIP embeddings blur, and gives you readable alt-text for debugging and accessibility. It's the hybrid-search move applied to pixels.
ANN index + quantization
Flat brute-force is fine to ~1M; past that use an ANN index (HNSW graph, or IVF-PQ for memory). At 10M+, quantize: int8 (~4× smaller, tiny recall loss) or binary (~32× smaller, search by Hamming distance) with a float re-rank of the top candidates to recover precision. This is the single biggest scaling lever — memory is the wall, not FLOPs. See Embeddings & vectors and Quantization & scale.
Metadata filtering
Real catalogue search is vector + structured filters: price range, category, brand, region, in-stock, NSFW flag. Filter inside the ANN query (a pre-filter the index supports) rather than after — post-filtering can empty your top-k. Keep stock/price metadata fresh via events so you never rank a sold-out item.
VLM reranker (optional)
For the top ~50 candidates, a heavier VLM can judge fine-grained match (“is the sofa actually navy linen, not blue leather?”) that a single embedding misses. Big precision win on hard queries; budget ~50–150 ms and run it only when the latency bar allows.
How to say it out loud say it

“A CLIP-style dual encoder puts images and text in one shared space, so a text query and an image result are comparable by cosine similarity — same model's text tower for the query, image tower for the corpus. I search a quantized ANN index with metadata pre-filters, optionally fuse in VLM-caption keyword hits for exact terms, and run a VLM rerank on the top fifty when latency allows.”

05  Step 5 — Trade-offs & bottlenecks

Senior answers name the forks and pick one with a reason. The three that come up every time:

The multimodal-search failure modes gotcha

The modality gap — in CLIP space, image vectors and text vectors cluster in slightly separate cones, so raw cosine scores aren't directly comparable across modalities; fixes include calibrating/normalizing per modality, learning a small alignment, or always comparing query-to-corpus within the trained pairing. Domain shift — web-trained CLIP underperforms on your specialty corpus (medical scans, satellite, niche product photography); fine-tune or pick a domain-matched encoder, and measure recall on your data, not a public benchmark. Cold-start on new images — a freshly added image is invisible until it's embedded and upserted, so an unindexed item can't be found; keep ingest latency low and event-driven, and reconcile so nothing is silently dropped. And quantization quietly erodes recall as the corpus grows — re-measure after every index change.

06  Step 6 — Evaluation, extensions & scaling

Finish on a senior note: how you'd know it works, and how it grows. As with RAG, eval is a production gate — you don't ship an encoder swap or an index change until it clears the retrieval eval set on your own data.

Retrieval metrics
Recall@k and MRR / nDCG on a labelled set (query → known-relevant images), measured per direction — text→image and image→image can differ a lot. This isolates the retriever; debug it before touching rerank.
Cross-modal & human relevance
Track cross-modal retrieval metrics on both directions, plus periodic human relevance judgements (“is this a good match for the query?”) since automated labels miss taste and fine-grained correctness. Slice by query type (exact term vs descriptive vs image-only).
Online signals
Click-through, add-to-cart / dwell, “no good results” rate, and zero-result queries fed back into the eval set. Offline catches regressions; online catches reality and surfaces the queries your embeddings handle badly.
Scaling
Shard the ANN index across nodes and replicate for query throughput; quantize (int8 → binary) to keep RAM sane; cache hot text queries; batch image embedding on GPUs for ingest. ANN keeps search ~constant-time, so the real work at scale is holding recall up as the index quantizes and grows.
Go deeper on the building blocks note

The encoder that creates the shared space is a vision-language model — see Vision-language models for how CLIP-style contrastive training and VLM captioning actually work. The index that makes 10M+ vectors searchable in milliseconds is covered in Embeddings & vectors, with the memory-vs-recall math in Quantization & scale.

Your turn · three extensions

(1) Add video to the catalogue. (2) Improve precision on hard, fine-grained queries. (3) The corpus grows to 100M images — what changes?

Think about how a video differs from a single image, where extra quality comes from without blowing the latency budget, and which part of the architecture becomes the wall at 100× before you peek.

Stuck? Reveal a hint hint

Video: a clip is a sequence of frames — sample keyframes, embed each into the same space, and either index frames individually or pool them into a clip vector. Precision: add a VLM reranker over the top-k. 100M: memory is the wall — think binary quantization + float re-rank, sharding, and re-measuring recall, not bigger GPUs.

Show a solution solution

Add video. Sample keyframes (scene-change or fixed-interval), embed each frame with the same CLIP-style image tower so they share the catalogue's space, and choose a granularity: index frames individually (precise “find this moment,” more vectors) or mean-pool frames into one clip vector (cheaper, coarser). Carry a timestamp on each frame vector so a hit links to the right moment; optionally caption keyframes with a VLM for hybrid recall. The query path is unchanged — text or image still embeds into the same space.

Sharpen fine-grained precision. Add a VLM reranker over the top ~50 ANN candidates: feed the query and each candidate image to a VLM that scores true match on the attributes that matter (colour, material, count, brand). It catches what a single embedding blurs (“navy linen, not blue leather”) for ~50–150 ms on a small candidate set. Pair it with VLM-caption keyword fusion so exact terms (SKU, “size 11”) aren't lost.

100M images. The vector index dominates; raw float32 would be ~300 GB. Switch to binary quantization (~1 bit/dim, ~32× smaller, Hamming-distance search) for a fast first pass, then re-rank the top candidates with int8/float vectors to recover precision — see Quantization & scale. Shard the index across nodes (by category/tenant) and replicate for read throughput; ingest becomes a distributed batch embedding job with incremental upserts. Search stays roughly constant-time with good ANN, so the engineering is keeping recall@k high as you quantize harder — which is exactly why recall stays on the dashboard.

Why can a text query retrieve images in this design, with no captions on the query side?
The whole trick is the shared embedding space: contrastive training aligns matching image–text pairs, so a text query's vector lands near the vectors of images that depict it. Search is then ordinary nearest-neighbour — no per-query captioning, no per-image OCR, no LLM scanning the corpus. (A VLM rerank on the top few is optional precision, not how retrieval works.)
“Why one joint embedding space instead of separate image and text models?”Core
Model answer

A joint space (CLIP-style) is what makes cross-modal search trivial: text→image and image→image both reduce to nearest-neighbour in one index, because matching pairs were trained to land near each other. Separate per-modality encoders put images and text in different coordinate systems, so you'd need a learned bridge to translate between them — that doubles the index, adds a brittle alignment step, and is an extra thing to evaluate and keep in sync. I'd only reach for separate encoders if one modality genuinely needs a specialist model I can't get in a joint form, and even then I'd prefer fine-tuning a joint encoder on my domain first.

How to say it out loud say it

“One joint space means cross-modal search is just nearest-neighbour in a single index. Separate encoders need a bridge to translate between spaces — double the index, extra failure surface — so I default to joint and only split for a true specialist need.”

“Off-the-shelf CLIP gives mediocre results on our catalogue. What do you do?”Stretch
Model answer

That's classic domain shift — web-trained CLIP hasn't seen your specialty imagery, so its space doesn't separate your items well. First I'd confirm it with recall@k on a labelled set from our data, not a public benchmark, and slice by query type to see where it fails. Then, in order of effort: try a stronger or domain-matched open encoder; fine-tune the joint encoder on our image–caption (or image–title) pairs to pull our space into shape; add a VLM-caption hybrid layer so exact terms still hit; and add a VLM reranker for fine-grained attributes. I'd also watch the modality gap — calibrate scores per modality so cross-modal comparisons are fair. Re-measure recall after each change; only ship what clears the gate.

How to say it out loud say it

“Mediocre CLIP results are usually domain shift. I measure recall on our own data, then fine-tune the joint encoder on our pairs, add caption-hybrid for exact terms and a VLM rerank for fine detail — and re-measure after every change.”
