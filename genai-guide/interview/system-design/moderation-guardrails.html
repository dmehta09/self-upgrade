Design a moderation & guardrails pipeline IV

The trust-and-safety prompt: keep an LLM product safe — block bad input, catch bad output, without wrecking latency or annoying good users. It sounds like a single classifier, but a senior answer is a layered system: cheap fast filters in front, a real guard model behind them, output checks on the way back, and a human queue for the calls a machine shouldn't make alone. We'll run the 6-step method top to bottom and land on the trade-off that defines this design — every percentage point of recall you buy costs you false positives that erode user trust.

01  Step 1 — Requirements & clarifying questions

Don't reach for a model yet. The first move is to nail down what we're moderating and how wrong we're allowed to be in each direction — because “block harmful content” means wildly different things for a kids' app versus a security-research tool. I'd ask these four before drawing a box:

What exactly do we block?

Pin the policy categories: PII (emails, cards, SSNs), toxicity/harassment, jailbreaks & prompt injection, off-topic abuse of the product, and self-harm/crisis content. Each category has a different cost of being wrong — self-harm needs recall and a careful response; off-topic just needs a polite redirect.

How costly is a false positive?

Over-blocking a legitimate user is a real harm too. A medical or legal assistant must discuss sensitive words; a consumer chat app can be stricter. This tolerance sets every threshold downstream, so I make the interviewer commit to it.

What's the latency budget?

Moderation sits on the request path, so it's a tax on every call. Is this an interactive chat (single-digit-percent overhead, < ~200 ms) or a batch/async surface where I can afford a heavier check? Streaming changes everything — output can't be fully scanned before the first token leaves.

What must we audit & report?

Regulated contexts (EU AI Act transparency duties, child-safety reporting) demand an immutable log of every decision, the policy version, and who reviewed escalations. “We blocked it” isn't enough — you must be able to show why, months later.

My assumptions (stated, so I can move on): a consumer-facing LLM assistant, ~50 QPS sustained with spikes to ~500, English-first but multilingual on the roadmap, an interactive streaming UI, and a moderate false-positive tolerance — we'd rather occasionally over-redirect than let toxic or self-harm content through. PII redaction and an audit log are hard requirements; a small human-review team exists. I'll flag where a stricter or laxer policy flips the design.

02  Step 2 — Constraints, SLAs & NFRs

Now I pin the non-functional spine with rough numbers. For moderation the spine is unusual — the headline metric isn't latency or cost, it's the precision/recall operating point, because that's the dial that trades user friction against safety risk:

Added latency
Input guardrails get a ~20–50 ms budget (regex + small classifier, run in parallel with prep); a heavier guard-model call ~50–150 ms. Output checks run as the answer streams so they don't block time-to-first-token. Whole pipeline overhead target: < ~200 ms p95 on the critical path.
Precision / recall
Per category, with explicit targets. For high-harm classes (self-harm, CSAM-adjacent) optimize recall ≥ 0.95 and accept lower precision; for low-harm classes (mild off-topic) protect precision ≥ 0.90 so you don't nag good users. State the operating point, not just “accurate.”
Throughput
~50 QPS sustained, headroom to ~500 for spikes. Cheap filters are effectively free; the guard-model tier is the scaling cost, so it must batch and autoscale independently of the main LLM.
Human-review capacity
A finite queue — say a team that can clear ~1–2k items/day. The escalation rate must be tuned to that capacity, or the queue backs up and “human in the loop” becomes “human asleep at the wheel.”
Auditability
Every decision logged immutably: input hash, category scores, threshold & policy version, action taken, and reviewer outcome. Retained per the relevant regime so you can reconstruct any single decision on demand.
Availability / fail-mode
Decide fail-open vs fail-closed up front: if the guard model times out, do we block (safe, frustrating) or allow (risky)? Usually fail-closed for high-harm checks, fail-open with logging for low-harm — and never let moderation latency take down the whole product.

03  Step 3 — High-level architecture

The shape that scores points: moderation is a cascade wrapped around the LLM on both sides. Cheap-and-fast filters first, an expensive guard model only for what survives, then the same layered scan on the output, with a human queue hanging off the ambiguous middle. Airport security, not a single locked door analogy

Good moderation looks like airport security: a cheap boarding-pass scan stops the obviously wrong before they reach the line, the metal detector catches most threats fast, and only the people who beep get the slow, expensive pat-down — and a tiny fraction go to a human supervisor. You'd never put every passenger through the pat-down (that's the latency tax) and you'd never rely on the door lock alone. Layers let you be both fast for the 95% and thorough for the risky few.

04  Step 4 — Component deep-dives

Now zoom into the boxes that decide whether this is safe, fast, and not infuriating. I'd lead with the cascade itself and the guard model, because that's the structural choice everything else hangs off:

Layered defense
Cheap-fast first, expensive-LLM last. L1 is microsecond regex, blocklists and a tiny logistic/embedding classifier that resolves the easy 90%; only the residual reaches the L2 guard model. This keeps average latency and cost low while the slow path handles only the genuinely hard cases — the single most important design move here.
A separate guard classifier
Use a dedicated safety model (e.g. a Llama-Guard-style classifier or a vendor moderation endpoint), not the same LLM that answers. Separation means a jailbreak that fools the chat model still has to beat an independent judge, the guard can be small/cheap/fast, and you can update the policy without retraining the product model. Self-judging is a conflict of interest.
PII detection & redaction
Named-entity + pattern detectors (emails, cards with a Luhn check, phone, SSN) on both input and output. Prefer transform over block: redact or tokenize (<EMAIL>) so the user still gets an answer. Catching PII the model emits matters as much as PII the user sends.
Prompt-injection detection
A classifier for “ignore previous instructions”-style attacks, plus structural defenses: keep system instructions privileged, treat retrieved/tool content as untrusted data, and scan it before it enters context. This is its own arms race — see Injection & jailbreaks.
Output validation & allow-listing
If the model emits structured output or calls tools, validate against a schema and an allow-list — reject actions/URLs/SQL outside the permitted set rather than trying to blocklist every bad one. Allow-listing fails safe; blocklisting always misses something.
Escalation queue
Grey-zone scores (near threshold, or high-harm-but-uncertain) fork to an async human queue prioritized by harm × volume. For the user, the safe action ships immediately; the review happens off-path and its label feeds back. Size the escalation rate to the team's real throughput.
How to say it out loud say it

“It's a cascade: cheap regex and a small classifier resolve the easy 90% in tens of milliseconds, and only the residual hits a separate guard model — never the answering LLM judging itself. The same layers run on the output, I prefer redact-and-transform over hard-block to avoid annoying good users, and grey-zone cases go to an async human queue whose labels retrain the classifier.”

Where moderation pipelines bite gotcha

False positives erode trust — over-block a few times and users learn the product is broken and leave; measure the FP rate as carefully as the catch rate. The latency tax — naively chaining a heavy guard model on every call doubles your p95; the cascade exists precisely to avoid this. Adversarial evasion — attackers will use leetspeak, base64, low-resource languages and obfuscation; static blocklists rot fast, so plan for continuous red-teaming and retraining. And the big one: guardrails are not a silver bullet — they reduce risk, they don't eliminate it, and a determined attacker will eventually find a gap, so layer them with a safety-tuned base model and least-privilege tooling. See Guardrails & defenses for the defense-in-depth picture.

06  Step 6 — Evaluation, extensions & scaling

Finish on a senior note: how you'd know it works, and how it grows. For a safety system, eval is not optional polish — it's the thing that tells you whether you're shipping a sieve or a wall, and it has to track both failure directions at once.

Core metrics
Precision & recall per category on a held-out red-team set (known-bad prompts + adversarial variants) plus a clean set (legitimate prompts that look risky). Recall says how much harm leaks; precision says how much you over-block.
False-positive rate
Tracked as a first-class metric, ideally segmented by user cohort — a spike means you're silently driving away good users. Pair it with the added-latency distribution (p50/p95 overhead) so you see the friction and the tax together.
Online signals
Appeal/overturn rate from the human queue (high overturns = mis-tuned thresholds), user reports of missed content, and reviewer labels fed straight back into the eval set. Offline catches regressions; online catches the adversary you didn't imagine.
Scaling
L1 filters scale trivially (stateless, cacheable). The guard-model tier autoscales and batches independently of the product LLM; cache decisions on identical/near-identical inputs. The human queue is the real bottleneck — tune escalation rate to capacity and prioritize by harm × volume.
This is one layer of a bigger safety story note

A moderation pipeline is the runtime enforcement layer, but it sits inside a wider program — threat modelling, safety-tuned base models, red-teaming, and governance/transparency. For the full landscape (OWASP LLM threats, jailbreak defenses, watermarking and governance) see the Safety & security overview.

Your turn · two extensions

(1) Product wants a new policy category — say “medical advice” — added without re-shipping the whole pipeline. How? (2) Add a human-review feedback loop so the classifier actually improves over time. Where do the labels go, and what could go wrong?

Think about where a new category plugs in (and how you'd test it before it goes live), and how reviewer labels become training data without poisoning the very metric you trust — before you peek.

Stuck? Reveal a hint hint

For the new category: treat policies as configuration, not code — a versioned policy spec + a labelled eval set for that category, run the new check in shadow mode (log, don't act) until precision/recall clear the bar, then turn it on. For the feedback loop: keep a strict train/eval split so reviewer labels that train the model never leak into the held-out eval set, or your numbers lie. Watch for reviewer disagreement (measure inter-annotator agreement) and feedback that just amplifies existing bias.

Show a solution solution

New policy category. Make the policy set a versioned artifact (a category list with definitions, examples, and thresholds) that the guard layer reads at runtime — adding “medical advice” is then a config change plus a labelled eval slice, not a redeploy. Ship it in shadow mode first: run the new classifier on live traffic and log what it would have done, compare against held-out labels, and only flip it to enforcing once precision/recall and the false-positive rate hit target. Bump the policy version on the audit log so every decision records which ruleset judged it. This also lets you A/B a threshold change and roll back instantly.

Human-review feedback loop. Reviewer verdicts on grey-zone cases are gold labels: stream them into a labelled store, then split them — most into the training pool for the next classifier version, a frozen slice into the eval set (never mixed, or you'll grade the model on its own homework). Periodically retrain/fine-tune the guard classifier on the accumulated labels and re-run the full eval before promotion. Guardrails to add: track inter-annotator agreement so a single noisy reviewer can't skew the data, watch for feedback loops that entrench bias (the model over-flags a group, reviewers rubber-stamp, the bias compounds), and keep humans focused on the ambiguous middle — auto-confirming the obvious cases wastes the scarcest resource you have.

Your moderation layer adds a heavy guard-model call on every request and p95 latency has doubled. What's the right fix?
Layered defense is the answer: the expensive check should only run on what the cheap filters can't resolve, which keeps average latency low without lowering the safety bar. Dropping the guard model removes independent judgment, blanket-raising thresholds trades safety for speed blindly, and checking after sending means the harm already reached the user.
“Why not just prompt the main LLM to refuse unsafe requests instead of a separate guard model?”Core
Model answer

Because a model judging itself is a conflict of interest: the same jailbreak that talks the chat model into answering often talks it out of refusing, so a single layer is brittle. A separate guard classifier gives independent judgment an attacker has to defeat twice, and it can be small, cheap and fast — run it on input and output without paying frontier-model latency on every call. It also decouples policy from product: I can update or add safety categories by changing the guard layer's config, with its own eval set, without retraining or risking the main model. The system prompt is still part of defense-in-depth — it's just not the only defense.

How to say it out loud say it

“I never let the model that answers be the only thing that polices it — that's self-judging. An independent guard classifier means a jailbreak has to beat two systems, and I can ship a new policy by updating the guard, not retraining the product model.”

“How do you moderate a streaming response without killing time-to-first-token?”Core
Model answer

You scan as you stream rather than waiting for the whole answer. Run the cheap output filters over a sliding window of buffered tokens in parallel with generation, so the first token still lands fast, and be ready to halt or redact mid-stream the moment a check trips. For high-harm classes I hold the final chunk until the full-answer check clears — a small tail delay is acceptable when the alternative is leaking harmful content. Pure async (send everything, scan later) risks the user already having seen it; pure sync (scan the complete answer before any token) destroys perceived latency. The hybrid — stream-and-scan with a kill switch — is the standard answer.

How to say it out loud say it

“I scan the stream in a sliding window with a kill switch — first token stays fast, but I can halt or redact mid-stream, and I hold the last chunk for high-harm checks. Async-only risks a leak; sync-only kills TTFT.”
