Design a real-time voice assistant IV NEW

“Design a voice assistant you can actually talk to” — you speak, it answers in speech, and the whole loop is fast enough to feel like a conversation rather than a walkie-talkie. Think a phone-support bot, an in-car assistant, or a hands-free helper. We'll run the 6-step method top to bottom, and the whole game here is one number: mouth-to-ear latency — talk to it and it talks back, with low enough latency to feel like a conversation. Everything streams, nothing waits for a full turn, and the user can cut you off mid-sentence.

01  Step 1 — Requirements & clarifying questions

Don't draw the STT→LLM→TTS box yet. Voice has a handful of questions that genuinely flip the architecture, and the interviewer wants to see you find them. I'd ask these five before anything else:

What's the use case?

Open-domain chit-chat, or a narrow task bot (book a table, triage a support call)? A scoped task lets you use a smaller model, tighter prompts, and function calling — and tolerate far less latency slack than open-ended conversation.

Which languages & accents?

One language or many? Code-switching mid-sentence? Phone-quality 8 kHz audio or clean 16 kHz? This decides the STT model and whether one multilingual model covers you or you route per-locale.

Must it interrupt — barge-in?

Can the user talk over the assistant and have it stop and listen? Real conversations need this; a strict push-to-talk demo doesn't. Barge-in support reshapes the whole audio pipeline (echo cancellation, half-duplex vs full-duplex).

On-device or server?

Phone/edge (privacy, works offline, small models) or server (bigger models, more compute, but a network round-trip in the latency budget)? Often a hybrid — VAD on-device, the heavy lifting in the cloud.

What delay feels live?

What's the acceptable response delay before it feels broken? Humans expect a reply within a few hundred ms of finishing; past ~1 s it feels like lag. That target governs every component budget downstream.

How noisy & what surface?

A quiet room, a moving car, a crowded street? Telephony (PSTN/SIP), a mobile app, or a smart speaker? Noise robustness and the transport (WebRTC vs phone line) fall out of this.

My assumptions (stated, so I can move on): a server-side, English-first (multilingual stretch goal) task-oriented assistant — say customer support — reachable over the phone and a web app. Full barge-in is required, it must survive moderate background noise, and the target is conversational: a reply within a few hundred ms of the user finishing. I'll flag where on-device or a strict push-to-talk model would flip the design.

02  Step 2 — Constraints, SLAs & NFRs

Voice lives and dies on latency, so I pin the non-functional spine in milliseconds. Stating these numbers up front is the biggest “sounds senior” signal — every later trade-off references back to them:

Mouth-to-ear latency
The headline NFR: p95 ≤ ~800 ms from the user finishing speaking to the first audio coming back, ideally pushing toward ~300–500 ms to feel truly live. This is the sum of endpointing + STT finalize + LLM time-to-first-token + TTS first-chunk — it compounds, so every stage gets a sub-budget.
Streaming everywhere
Non-negotiable: STT emits partial hypotheses as you speak, the LLM streams tokens, and TTS starts vocalizing the first sentence before the reply is finished. Nothing waits for a complete turn. Perceived latency is what users feel, and streaming is how you hide the rest.
Turn-taking
Endpointing (deciding the user is done) within ~200–500 ms of silence, and barge-in that stops playback within ~100–200 ms of detected speech. Too eager = it interrupts the user; too slow = awkward dead air. This is the hardest UX knob.
Cost / minute
Voice is billed per minute of audio, not per request. Target ~$0.05–0.15 / conversational minute across STT + LLM + TTS. The always-on STT stream and TTS synthesis are real line items here, not rounding error like in a text bot.
Robustness to noise
Hold WER acceptable in cars/cafés, not just a quiet booth. Needs a noise-robust STT model, good VAD, and echo cancellation so the assistant's own voice doesn't get transcribed as user speech.
Availability & concurrency
Each live call holds a stateful, long-lived bidirectional stream (WebRTC/WebSocket) plus GPU time — capacity is “concurrent calls,” not QPS. Graceful degradation (a filler “let me check…”, fall back to a smaller model) beats a dropped call.

03  Step 3 — High-level architecture

The spine is a streaming pipeline, and the senior move is to draw it as a real-time loop, not a request/response chain — audio flows in continuously, partial results flow forward, and a barge-in signal can cut the whole thing short. There are two camps: the modular cascade (STT → LLM → TTS) and a unified speech-to-speech model. I'd draw the cascade first because it's what you can reason about box by box.

A simultaneous interpreter, not a postal exchange analogy

A naive design is two people mailing letters: you finish a whole sentence, post it, wait for a full reply. A real-time voice assistant is a simultaneous interpreter — they start translating while you're still talking, speak the moment they've got the gist, and stop instantly the second you cut in. The cascade is an interpreter with three people in a relay (listener → thinker → speaker), each starting before the previous one finishes; speech-to-speech is one bilingual person doing all three at once. Either way, the magic is the overlap, not any single fast step.

04  Step 4 — Component deep-dives

Now zoom into the boxes that actually move latency and naturalness. The whole theme is overlap — every stage emits partial output so the next stage can start early:

Streaming STT
An ASR model that emits partial hypotheses token-by-token as audio arrives, then a stabilized final at endpoint. The LLM can start reading the partial transcript before the user even stops. Watch for partials that rewrite themselves (“two” → “to” → “too”) — only act on stable prefixes. Noise-robust, optionally streaming punctuation. See Speech (STT/TTS).
Incremental LLM (low TTFT)
Here time-to-first-token matters more than tokens/sec — the user hears the first word as soon as it's generated. Prefer a fast/smaller model or a reasoning-light path, keep the prompt short, and lean on prompt/KV caching for the stable system prompt so prefill is near-instant. A 50 ms TTFT win is audible.
Streaming TTS
Synthesize and play the first sentence (or clause) before the full reply is written. Chunk the LLM stream on sentence boundaries, feed each to a low-latency TTS that returns audio in chunks, and pipeline playback. First-audio-chunk latency is the metric, not total synthesis time. Natural prosody and a consistent voice matter for trust.
VAD + endpointing
A lightweight voice-activity detector (cheap, runs continuously, ideally on-device) gates the expensive STT and flags barge-in. Endpointing — “the user is done” — is the subtle part: pure silence-timeout is laggy and trips on mid-thought pauses; better is a model that fuses silence duration with prosody/semantics. This single decision dominates perceived responsiveness.
Barge-in handling
While TTS plays, keep VAD listening on the (echo-cancelled) mic. On confident user speech: stop playback immediately, cancel the in-flight LLM/TTS generation, discard the unsaid remainder, and feed the new audio to STT. Requires acoustic echo cancellation so the assistant's own voice isn't mistaken for the user, plus a “did they really mean to interrupt vs a back-channel ‘uh-huh’?” threshold.
Context / memory across turns
Keep a running dialog state: prior turns (summarized to stay cheap and low-latency), the current task/slots being filled, and any tool results. Resolve follow-ups (“and the day after?”) against history before the LLM call. Trim aggressively — long history inflates TTFT, which you can hear.
How to say it out loud say it

“Everything streams and overlaps. STT emits partials so the LLM starts before the user stops; I optimize the LLM for time-to-first-token, not throughput; and TTS speaks the first sentence while the rest is still being generated. A VAD runs continuously for endpointing and barge-in — on interruption I kill playback and cancel the in-flight generation. My headline metric is mouth-to-ear p95, and I budget every stage against it because latency compounds.”

05  Step 5 — Trade-offs & bottlenecks

Senior answers name the forks in the road and pick one with a reason. The three that come up every time in voice:

The voice failure modes that bite in production gotcha

Latency compounds across stages — each box can look “fast enough” while the sum feels sluggish; budget end-to-end and overlap stages, don't optimize one in isolation. Endpointing errors — too eager and it cuts the user off mid-sentence; too slow and there's dead air before every reply (fix: prosody/semantic endpointing, not a fixed silence timer). Echo & barge-in — without acoustic echo cancellation the assistant transcribes its own voice as user speech and interrupts itself; barge-in must cancel the in-flight LLM and TTS, or the user talks over a reply that won't stop. Plus: STT errors silently poison the LLM (garbage transcript → confident wrong answer), and network jitter on a live stream causes dropouts a text app would never see.

06  Step 6 — Evaluation, extensions & scaling

Finish on a senior note: how you'd know it works, and how it grows. Voice eval is multi-dimensional — you measure each stage and the felt conversation:

Latency, per stage
The primary dashboard: mouth-to-ear p50/p95, broken down into endpointing, STT-final, LLM-TTFT, and TTS-first-chunk. You can only fix the budget if you can see which stage blew it. Track time-to-first-audio above all.
STT quality
WER (word error rate) on representative audio — your accents, your noise, phone-band audio — not a clean benchmark. A WER regression upstream quietly tanks answer quality, so it's a gated metric.
Naturalness & turn-taking
MOS (mean opinion score) for TTS naturalness, plus interruption / barge-in success rate and false-endpoint rate (how often it cuts the user off). These capture the conversation feel that per-component metrics miss.
Task & online signals
Task-success / completion rate, call-abandon rate, escalation-to-human rate, and thumbs / post-call ratings. Offline catches regressions; live calls catch reality.
Scaling
Capacity is concurrent calls, not QPS — each holds a stateful stream + GPU time. Autoscale STT/LLM/TTS pools independently (they have different profiles), pool/keep-warm GPUs to dodge cold starts (a cold start is dead air), use a region close to users to shave the round-trip, and shed load gracefully (smaller model / “bear with me”) before dropping calls.

Your turn · two extensions

(1) Make the assistant multilingual, including users who code-switch (swap languages mid-sentence). (2) Add function calling mid-conversation — e.g. it must hit a booking API and keep the dialog flowing while the call is in flight.

Think about where language detection happens and what it does to the cascade, and how a tool call that takes 800 ms interacts with a sub-second latency budget, before you peek.

Stuck? Reveal a hint hint

For multilingual: prefer a single multilingual STT/TTS over per-language routing (language ID adds latency and breaks on code-switching), and make sure TTS can voice the detected language. For mid-call tools: you can't freeze the conversation for 800 ms — speak a filler (“let me check that for you…”) via TTS while the tool runs async, then continue when the result lands. Emotion/prosody is another natural extension — detecting user frustration, or expressive TTS.

Show a solution solution

Multilingual + code-switching. Use a multilingual streaming STT model rather than running language detection and routing to per-language ASR — detection adds a serial latency hop and falls apart when a user mixes languages in one sentence, which a single multilingual model handles natively. The LLM is already multilingual; the constraint is TTS: pick a multilingual voice (or a per-language voice map) so the reply is spoken in the matching language, and decide a policy for which language to answer in (mirror the user, or honor a setting). Add per-language WER/MOS to eval, because quality varies a lot by language.

Function calling mid-conversation. The LLM emits a tool call (e.g. book_table(date, party_size)) just like in text. The trick is latency: a real API can take hundreds of ms to seconds, which would be dead air, so the orchestrator immediately speaks a filler/acknowledgement via TTS (“sure, let me check availability…”) while the call runs asynchronously, then resumes generation with the tool result — and barge-in still works during the filler. Stream partial results if the API supports it, set a timeout with a graceful fallback (“that's taking a moment — anything else?”), and design tools to be idempotent since users may interrupt and retry. See Function calling.

Your voice assistant feels sluggish — there's a noticeable pause before it replies, even though STT, the LLM, and TTS each benchmark “fast.” What's the first thing you do?
Latency compounds: each stage can look fine while the sum feels slow, and the pause is frequently endpointing waiting too long on silence before STT even finalizes. Measure per stage first. A bigger model makes TTFT worse, and raising the silence timeout adds more dead air — the opposite of the fix.
“Cascade or a native speech-to-speech model — which would you build?”Core
Model answer

It depends on the product, and I'd say so. The cascade (STT → LLM → TTS) is modular and debuggable: I can log the transcript, swap any stage, reuse a text LLM with my existing tools and RAG, and tune each box against its latency budget — it's the right default for a task bot that needs tool calls and auditability. A native speech-to-speech model collapses the three into one, which gives lower latency and far more natural prosody and barge-in because the audio never round-trips through text — I'd choose it when “feels human” and sub-500 ms latency are the product, accepting that I lose per-stage visibility and some control over tool use. In June 2026 the realtime speech-to-speech APIs are good enough that I'd seriously prototype both.

How to say it out loud say it

“Cascade for control and debuggability, speech-to-speech for latency and naturalness. I'd default to the cascade for a tool-driven task bot, and reach for a native realtime model when human-feel is the product.”

“How do you handle the user interrupting the assistant mid-reply?”Core
Model answer

That's barge-in, and it needs the audio pipeline to stay full-duplex. While TTS is playing, the VAD keeps listening on the mic — but first I run acoustic echo cancellation so the assistant's own playback isn't transcribed as the user, which would make it interrupt itself. On confident user speech (above a threshold so a back-channel “mm-hmm” doesn't trigger it), I stop playback immediately, cancel the in-flight LLM and TTS generation, discard the unspoken remainder, and route the new audio straight into STT as the next turn. The whole stop should happen within ~100–200 ms or it feels unresponsive. Native speech-to-speech models handle a lot of this internally, which is one of their big draws.

How to say it out loud say it

“Echo-cancel first so it doesn't hear itself, keep VAD live during playback, and on real user speech kill playback and cancel the in-flight LLM/TTS within ~150 ms — then the interruption becomes the next turn.”
