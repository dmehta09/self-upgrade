Design an LLM gateway IV NEW

“Every team here calls LLMs their own way — some hit the frontier APIs directly, others stood up a self-hosted model, and nobody can tell me what we're spending or which app caused yesterday's rate-limit storm. Design us one internal API in front of all the models.” That's the LLM gateway: a single proxy — covering both hosted APIs and self-hosted models — that every team calls instead of wiring up each provider themselves. It owns auth, rate-limits, routing, caching, fallback, cost attribution and logging, so each app gets a uniform endpoint and the org gets one control plane. We'll run the 6-step method top to bottom; the recurring theme is that this is infrastructure — its job is to be invisible, fast, and never the reason a launch slips.

01  Step 1 — Requirements & clarifying questions

This isn't an ML problem — it's an API-platform problem that happens to front models. The first move is to figure out who the tenants are and what they actually need from a shared layer, because that decides whether you're building a thin proxy or a full control plane. The six questions below mark you as someone who's run platform infra before:

Which models & providers?

Just the frontier APIs (OpenAI, Anthropic, Google), or also self-hosted open models on our own GPUs (vLLM)? Chat only, or embeddings, rerank, vision, audio too? The set you must support — and how often it churns — sizes the adapter layer.

Who are the tenants?

Internal teams/apps only, or also external customers reselling our capacity? How many — 10 product teams or 500 microservices? Each tenant needs its own keys, quotas and cost line, so “how many, and who owns billing” shapes the whole identity model.

What do teams actually need?

The usual asks: automatic failover when a provider 429s or has an outage, per-team cost caps so one runaway job can't burn the budget, and full request/response logging for debugging and audit. Confirm which are must-haves vs nice-to-haves.

What does “good” mean?

For infra, “good” is negligible added latency, near-100% availability (the gateway must be more reliable than any single backend), correct cost attribution down to the team, and zero app-code changes when we add or swap a model. No new failure mode = done.

One schema, or pass-through?

Do teams want a unified request/response schema (call any model the same way, swap freely), or transparent pass-through to each provider's native API? Unification is the bigger win but means you own a translation layer and must track every provider's quirks.

Data privacy & governance?

Can prompts leave our network? Must some workloads stay on self-hosted models for residency/PII reasons? Who may see the logged prompts? This decides whether routing has hard data-policy constraints, not just cost preferences.

My assumptions (stated, so I can move on): ~30 internal teams, a mix of frontier APIs plus a couple of self-hosted vLLM deployments, chat + embeddings to start. Teams want failover, per-team budgets with alerts, and full logging. We expose a single OpenAI-compatible schema so apps can swap models by changing a string. Some workloads are PII-sensitive and must pin to self-hosted models — so the router has hard policy constraints, not just soft cost preferences. I'll flag where a different answer flips the design.

02  Step 2 — Constraints, SLAs & NFRs

For a gateway the NFRs are the product — it adds no model quality, only operational guarantees, so I pin these hard with numbers. Every later trade-off references back to them:

Added latency
The proxy's own overhead must be tiny: target p50 < 5 ms, p95 < 20 ms excluding the upstream model call. Auth, rate-limit and routing are all in-memory lookups; anything that touches a slow store on the hot path is a bug. And the gateway must stream — it proxies tokens, it doesn't buffer the whole response.
Throughput
Aggregate of every team: design for tens of thousands of req/s and a much larger token/s firehose, since responses stream through. The proxy is I/O-bound (mostly waiting on upstreams), so it's about concurrent connections, not CPU — async, non-blocking, horizontally scaled.
Cost attribution
Per-team, per-model, per-request token + dollar accounting, accurate to ~100% and queryable in near-real-time. This is half the reason the gateway exists; it must never lose a usage record, so metering writes go to a durable async pipeline, not fire-and-forget.
Availability / failover
The gateway's SLA must exceed any single provider's — target 99.95%+. It achieves this precisely by failing over: if provider A is down or rate-limiting, route to provider B or a self-hosted fallback. The proxy is multi-AZ and stateless so an instance dying is a non-event.
Rate-limits & quotas
Per-tenant limits (RPS, tokens/min, $/day) enforced at the edge so one team can't starve others and so we stay under each provider's account-level caps. Distributed rate-limiting (shared counter) since requests hit many instances.
Data privacy
TLS everywhere; secrets (provider API keys) in a vault, never in app code. Logged prompts may contain PII → encryption at rest, redaction options, retention limits, and access controls on who can read the logs. Policy-tagged requests must be guaranteed to only reach approved backends.

03  Step 3 — High-level architecture

The shape is a classic API proxy: a thin, stateless request pipeline on the hot path, multiple model backends behind it, and everything observable off to the side asynchronously. The move is to draw the per-request chain as an ordered pipeline — each stage is cheap and in-memory — and keep logging/metering strictly off the critical path.

After each request the gateway emits a usage event onto a queue/bus — never blocking the response. Downstream consumers fan it into time-series metrics (Prometheus/OTel), distributed traces, and a durable usage store that powers cost dashboards, per-team budgets and anomaly alerts. The hot path stays fast; the analytics stay rich.
A universal power strip with a meter analogy

Every provider is a different wall socket — different shape, different voltage, different billing. The gateway is the universal travel adapter on a metered power strip: your app plugs into one familiar outlet and the strip handles which socket actually carries the current. If one socket dies it transparently switches to another (failover), it caps how much any one device can draw (quotas), and it logs exactly how many watt-hours each device used so you can split the bill (cost attribution). You change the appliance behind the strip without ever rewiring the device.

04  Step 4 — Component deep-dives

Now zoom into the stages that carry the real complexity. I'd lead with routing and caching, because that's where a gateway earns its keep — and where it's easiest to get subtly wrong:

Routing strategies
Three layers, applied in order. Rule/policy-based first — a PII-tagged or residency-bound request must go to a self-hosted model, no exceptions. Then model-based — the caller asked for a specific model, or an alias like fast/smart the gateway maps to a concrete one. Finally cost-based — among equivalent backends, pick the cheapest healthy one (e.g. same model on two providers, or a cheaper model that passes a quality bar). Policy is a hard gate; cost is a soft preference — never let cost override a data-policy rule.
Caching
Two tiers. An exact-match cache keyed on a hash of (model + normalized params + prompt) returns instantly for identical calls. A semantic cache embeds the prompt and returns a stored answer when a near-duplicate query is within a similarity threshold — great for repeated FAQs. Both are huge cost/latency wins; the catch is correctness — see the gotcha. Don't cache non-deterministic high-temperature calls, and always scope cache keys by tenant so you never serve one team's answer to another.
Fallback & retry
On a 429 or 5xx, retry with exponential backoff + jitter, then fail over to the next backend in the model's fallback chain (e.g. provider A → provider B → self-hosted). A circuit breaker per backend stops hammering a dead provider — trip it after N failures, send traffic elsewhere, probe periodically. Retries must respect idempotency and the caller's deadline; failover should be invisible except in the logs.
Unified schema
One request/response contract (OpenAI-compatible is the de-facto lingua franca as of June 2026) that the adapter translates to each provider's native API and back — including streaming chunks, tool-call formats, and token-usage fields, which all differ. This is what lets an app swap models by changing one string. The cost: you own a translation layer and must track every provider's quirks and version bumps.
Per-tenant budgets
Each request is metered (tokens in/out × per-model price) and decremented against the team's running budget. Soft thresholds fire alerts (“80% of monthly spend”); hard caps reject with a clear 4xx once exhausted. Counters live in a fast shared store (e.g. Redis) so enforcement is consistent across instances, with the durable usage DB as the source of truth for billing.
Observability
Structured logs (optionally storing prompt/response, subject to privacy rules), metrics (latency split into gateway overhead vs upstream, error rate, cache hit-rate, tokens/s per backend), and distributed traces that follow a request through routing → adapter → provider. This is how you answer “why is team X slow today?” in minutes — and prove the proxy itself isn't the bottleneck.
How to say it out loud say it

“Routing is layered: policy is a hard gate — PII-tagged traffic only ever reaches self-hosted models — then I honor the requested model or alias, and only among equivalent healthy backends do I optimize for cost. Caching has an exact tier and a semantic tier, both scoped per tenant. Fallback is retry-with-backoff plus a per-provider circuit breaker, all invisible to the caller and fully traced.”

05  Step 5 — Trade-offs & bottlenecks

Senior answers name the forks and pick one with a reason. The three that come up every time for a gateway:

DecisionOption AOption BMy call for this system
Build vs buyBuild a custom gatewayAdopt an existing one — LiteLLM, OpenRouter, Cloudflare AI Gateway, Kong AI Gateway (as of June 2026)Start with an existing layer (LiteLLM proxy if self-hosting, OpenRouter for managed multi-provider, Cloudflare/Kong AI Gateway if you already live there). They already solve adapters, fallback, caching and usage. Build custom only when bespoke routing/policy or scale outgrows them — and even then, often by extending one.
Centralized gateway vs per-app SDKsOne shared gateway serviceEach app imports a provider SDK directlyCentralized. It's the entire point — one place for keys, quotas, cost, failover and audit, and zero app changes to add a model. The cost is a shared dependency on the hot path, so it must be rock-solid and horizontally scaled. A thin client SDK can wrap it for ergonomics.
Sync vs streamingBuffer the full response, return onceStream tokens straight throughStreaming, always. Buffering adds latency, kills the chat UX, and balloons memory under load. The proxy must forward SSE/chunks as they arrive and only meter usage at the end. Sync is fine for short embedding calls, but the chat path streams.
The gateway's own failure modes gotcha

Single point of failure — you've put every team's LLM traffic behind one service, so if it falls over, everything does. It must be more available than any backend: stateless, multi-AZ, autoscaled, with health checks and a tested degraded mode (e.g. bypass cache, shed load) — never a single instance. Added latency — sloppy synchronous logging, a DB read on the hot path, or buffering instead of streaming can add tens of ms; keep metering async and routing in-memory, and alert on gateway-overhead p95 separately from upstream latency. Cache staleness — a cached answer goes out of date (the model improved, the prompt's context changed) and you keep serving the stale reply; bound it with TTLs and per-model cache versioning. Cache poisoning & cross-tenant leakage — an attacker (or a bug) plants a bad/sensitive response that later queries get served, or a missing tenant scope leaks one team's answer to another; defend with per-tenant cache keys, validated entries, and never caching anything policy-restricted. And the quiet one: a too-loose semantic-cache threshold returns a similar but wrong answer — tune it conservatively and exclude high-stakes calls.

06  Step 6 — Evaluation, extensions & scaling

Finish on a senior note: how you'd know the gateway is doing its job, and how it grows. For infra, “eval” is operational — it's the dashboards and SLOs that prove the proxy adds value without adding risk:

Cost saved by routing
Track $/request and total spend before vs after routing + caching. Cache hit-rate and cost-based routing should show a clear, attributable reduction; report it per team so the win is visible to the people who own the budget.
Gateway overhead
The headline SLO: p50/p95 of the proxy's own added latency (total minus upstream), held under target (e.g. p95 < 20 ms). If this creeps, the gateway is becoming the problem it was meant to prevent — page on it.
Failover success
Rate of requests that hit a provider error and were silently rescued by fallback, plus the resulting end-user error rate (should approach zero). Run periodic game-days/chaos tests that kill a provider and confirm traffic reroutes and the circuit breaker trips and recovers.
Scaling
The proxy is stateless → scale horizontally behind a load balancer; it's I/O-bound, so tune for concurrent connections, not CPU. Move rate-limit/budget counters to a sharded shared store, partition the usage pipeline by tenant, and pool/limit upstream connections so a traffic spike to the gateway doesn't translate into an account-level ban from a provider.
Where the gateway sits in the Lang Stack note

Apps built on LangChain/LangGraph point their model client at the gateway's one endpoint instead of a provider SDK — so swapping or failing over models needs zero app changes — while LangSmith traces complement the gateway's own per-hop metrics for end-to-end observability across the proxy and the app. See the Lang Stack guide for how the application layer plugs in.

Your turn · two extensions

(1) A new provider launches a model your teams want — add it so no app changes a single line. (2) Add confidence-based cascade routing: try a cheap model first, escalate to an expensive one only when the cheap answer isn't good enough.

Think about which layer absorbs the new provider, and — for the cascade — how you decide an answer is “good enough” without a human and what that does to your latency/cost math, before you peek.

Stuck? Reveal a hint hint

For the new provider: the whole point of the unified schema is that only the adapter layer + a config entry change — write one adapter that maps the provider's API to your schema, register its models and prices, and apps that asked for an alias like smart can be pointed at it centrally. For the cascade: you need a cheap, automatic “is this good enough?” signal — model-reported confidence/logprobs, a self-check, or a small LLM-judge — and you must account for the worst case where you pay for both calls.

Show a solution solution

Add a provider, zero app changes. Because every model sits behind the unified schema, adding one is a platform change, not an app change: implement a new provider adapter (translate the unified request → its native API, map streaming chunks, tool-calls and token-usage back), add its API key to the vault, and register its models + per-token prices in routing config. Now apps that request a concrete model name reach it immediately; apps using an alias (fast, smart) get it the moment you remap the alias centrally — and you can canary it to one tenant first. The adapter pattern is exactly what makes this a config push instead of a fleet-wide redeploy.

Confidence-based cascade routing. Send the request to a cheap/fast model first, then evaluate the answer with an automatic gate: token logprobs / model-reported confidence, a self-consistency or self-critique check, or a lightweight LLM-judge against the task. If it clears the bar, return it; if not, escalate to the stronger (pricier) model and return that. This slashes average cost when most queries are easy — but watch the failure case: when you escalate you pay for both calls and add the first model's latency, so a poorly-tuned gate can be more expensive and slower than just calling the big model. Tune the threshold on real traffic, cap escalations, and track the realized cost/quality trade-off on the dashboard — it's the same “measure the trade-off, don't assume it” discipline as everywhere else in this guide.

You centralize all teams' LLM traffic behind one gateway. What's the first risk a senior reviewer will raise?
Putting every team behind one service concentrates risk: if the gateway falls over, everything does. The mitigation is exactly what makes it credible infra — stateless instances, multi-AZ, autoscaling, health checks, circuit breakers and a tested degraded mode — so the shared layer is more reliable than any single provider it fronts, not less.
“How does the gateway add almost no latency?”Core
Model answer

By keeping the hot path to in-memory work and never blocking on anything but the model call. Auth, rate-limit, budget and routing are all dictionary/counter lookups in local or fast shared memory; the cache check is a hash lookup. The expensive thing — logging, metering, tracing — is emitted asynchronously onto a queue after the response, so it never sits on the request. And the gateway streams tokens straight through rather than buffering, so it adds no time-to-first-token. I'd hold the proxy's own overhead to a single-digit-ms p50 and alert on gateway-overhead p95 separately from upstream latency, so I can prove the proxy isn't the bottleneck.

How to say it out loud say it

“Everything on the hot path is an in-memory lookup, logging is async off a queue, and I stream instead of buffer — so the proxy adds single-digit milliseconds, and I track gateway overhead as its own SLO separate from the model's latency.”

“Why not just have each app use the provider SDK directly?”Core
Model answer

Because then every cross-cutting concern is reimplemented (badly) in every app. Keys get scattered through codebases, nobody can attribute cost or enforce a per-team budget, there's no central failover when a provider degrades, no shared cache, and swapping a model means a code change and redeploy in every service. A gateway pulls all of that — auth, quotas, routing, caching, failover, logging, cost attribution — into one governed control plane, and gives apps a single endpoint so adding or switching a model is a config change on the platform, not a fleet-wide edit. The price is a shared hot-path dependency, which is why it has to be engineered as serious, highly-available infrastructure.

How to say it out loud say it

“Per-app SDKs scatter keys, lose cost attribution, and reimplement failover everywhere. One gateway centralizes auth, quotas, routing, caching and logging, and lets apps swap models via config — at the cost of a shared dependency I have to make bulletproof.”
