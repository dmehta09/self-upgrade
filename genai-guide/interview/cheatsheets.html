GenAI cheat-sheets IV

The night-before reference. Dense, scannable, no fluff — the one-line truths, the comparison tables, and the answer shape that make you sound senior. Every row is interview-grade; volatile specifics are tagged (as of June 2026). Skim it on the train, then go win.

01  The 20 things you must know

If you remember nothing else, remember these. Each is a one-breath truth an interviewer expects you to state without hesitating.

  1. Token — the unit an LLM reads and writes; ~¾ of a word in English. Models predict the next token, not the next word.
  2. Temperature — scales the logits before softmax: low = sharp/deterministic, high = flat/creative. 0 ≈ greedy.
  3. Embedding — text mapped to a vector so that similar meaning sits nearby. Query and documents must use the same model.
  4. Cosine similarity — angle between two vectors; direction not magnitude. The default relevance metric for embeddings.
  5. RAG vs fine-tune — RAG injects knowledge at inference (fresh, citable); fine-tuning changes behaviour/format. Knowledge → RAG, style → fine-tune.
  6. Attention is O(n²) — cost grows with the square of sequence length; why long context is expensive and why we cache.
  7. KV cache — store past keys/values so each new token is O(n) not O(n²). It's the #1 reason generation is feasible — and it eats memory.
  8. LoRA — train small low-rank adapters, freeze the base weights. ~<1% of params trained; cheap, swappable, mergeable.
  9. DPO vs RLHF — both align to preferences; RLHF trains a reward model + PPO, DPO optimizes preferences directly (no reward model, simpler, stabler).
  10. Hallucination cause — the model optimizes for likely, not true. Ungrounded by default → confident fabrication. Fix with retrieval, tools, eval.
  11. MCP — the Model Context Protocol: an open “USB-C for tools” standard letting any model talk to any tool/data source over a common interface.
  12. ReAct — the agent loop: reason → act (call tool) → observe, repeat until done. The backbone of most single agents.
  13. Supervisor vs swarm — supervisor = one orchestrator routes to workers (controllable); swarm = peers hand off to each other (flexible, harder to debug).
  14. Hybrid + rerank — fuse keyword (BM25) + vector search (RRF), then a cross-encoder reranks the top-k. The default strong retrieval stack.
  15. Quantization formats — GPTQ/AWQ (GPU 4-bit), GGUF (llama.cpp/CPU), FP8 (native on recent GPUs). Trade a little quality for big memory/speed wins.
  16. LLM-as-judge biases — position, verbosity, self-preference. Mitigate by swapping order, rubrics, and validating against human labels.
  17. Prompt injection — the #1 LLM security risk (OWASP LLM01): untrusted input overrides instructions. No clean fix — isolate, least-privilege, guard.
  18. Diffusion — learn to reverse a noising process: start from noise, denoise step by step toward a sample. How most image/video models work.
  19. Context engineering — deciding what goes in the limited context window (and what doesn't). The successor skill to prompt-crafting.
  20. Eval is a gate — without an offline eval set you can't ship or iterate safely. “Vibes” don't survive a regression. Build the eval first.

02  Prompt vs RAG vs fine-tune vs long-context

The most-asked design fork. Pick the cheapest tool that solves the actual problem — and know they compose.

What it changesBest forCostFreshness
PromptingThe instruction only; weights untouchedQuick wins, format, tone, few-shot tasks~free; pay per tokenOnly what you paste in
RAGInjects retrieved knowledge at inferencePrivate / changing facts, citations, large corporaVector DB + retrieval/token costLive — re-index to update
Fine-tuneThe weights → behaviour, style, formatConsistent voice, narrow skill, smaller modelHigh up front (data + train); cheap to serveFrozen at train time
Long-contextStuffs everything into one big windowOne-off over a few docs; no infra to buildPricey per call; O(n²) latencyWhatever you paste, each call

Default heuristic: start with prompting → add RAG for knowledge → fine-tune for behaviour. See the full RAG vs fine-tuning vs long-context module.

03  Decoding parameters

How tokens get picked from the probability distribution. Tune one thing at a time — usually just temperature.

ParamWhat it doesWhen to change
TemperatureScales logits before softmax. ↓ sharper/repetitive, ↑ flatter/diverse. 0 ≈ greedy.Low (0–0.3) for facts/code/extraction; high (0.7–1.0) for brainstorming.
Top-kSample only from the k highest-probability tokens.Hard cap on the candidate pool; rarely tuned directly now.
Top-p (nucleus)Sample from the smallest set whose cumulative prob ≥ p. Adapts to the distribution.Preferred over top-k; leave ~0.9–1.0, lower to tighten.
Repetition / frequency / presence penaltyDown-weights tokens already seen, to curb loops and reuse.Nudge up if output repeats; too high hurts fluency.

Gotcha: temperature and top-p both control randomness — change one, not both. For reproducibility, set temperature 0 and a fixed seed where supported (still not fully deterministic across hardware/batching).

04  Vector index types

How the vector DB finds nearest neighbours. The trade is always recall vs speed vs memory.

IndexHowSpeedRecallMemory
Flat (exact)Brute-force compare to every vectorSlow (O(n))100% (ground truth)Low (just the vectors)
IVFCluster, then search only nearby cells (nprobe)FastTunable, <100%Low–moderate
HNSWNavigable small-world graph; hop to neighboursVery fastHighHigh (graph in RAM)

Defaults: HNSW for most production ANN; Flat for <~10k vectors or to measure “true” recall; IVF(-PQ) when memory is tight at scale. All ANN methods are approximate — recall<100% by design. More in Vector databases and Quantization & scale.

05  Adapting a model: SFT · LoRA · QLoRA · DPO · distillation

Ways to change a model's behaviour, cheapest mental model first.

MethodWhatWhenCost
SFT (full fine-tune)Train all weights on labelled input→output pairsYou have lots of data and need maximum qualityHigh — full GPU memory + a copy of weights
LoRATrain small low-rank adapters; base frozenMost fine-tunes; swappable per-task adaptersLow — ~<1% of params; merge for free serving
QLoRALoRA on a 4-bit quantized base modelFine-tune a big model on a single GPULowest memory; slightly slower training
DPOAlign to preferred vs rejected answers, directlyTune tone/helpfulness/safety after SFTModerate; needs preference pairs, no reward model
DistillationTrain a small “student” on a big “teacher” outputsShrink cost/latency while keeping much qualityTeacher inference + a training run

Typical pipeline: SFT (often via LoRA/QLoRA) → DPO to polish preferences. RLHF/PPO is the heavier classic alternative to DPO.

06  Serving & inference levers

How to make a model fast and cheap to serve. One line each.

LeverOne-liner
KV cacheReuse past keys/values so each token is O(n); the foundational speedup (and the main memory cost).
Continuous batchingAdd/evict requests every step instead of waiting for a whole batch — huge throughput win (vLLM).
Speculative decodingA small draft model proposes several tokens; the big model verifies in one pass → lower latency, same output.
QuantizationStore/compute weights in fewer bits to cut memory + boost speed. GPTQ/AWQ = GPU 4-bit; GGUF = llama.cpp/CPU; FP8 = native on recent GPUs.

Also worth a sentence: PagedAttention (non-contiguous KV blocks → less waste), prefix caching (reuse a shared system prompt across requests), and GQA/MLA (shrink the KV cache itself). See Serving engines.

07  Multi-agent patterns

How to wire more than one agent together. Reach for these only when a single ReAct agent genuinely isn't enough.

PatternOne-liner
Fan-out (parallel)Split a task across agents that run at once, then merge — fast, but costs N× tokens.
Pipeline (sequential)Each agent's output feeds the next (e.g. research → write → edit); simple, but errors compound.
DebateAgents argue/critique to converge on a better answer; higher quality, much higher cost.
Supervisor (orchestrator–worker)One agent routes subtasks to specialist workers; controllable and the common production default.
Swarm (decentralised)Peer agents hand off to each other with no central boss; flexible but hard to debug and bound.

Gotcha: more agents = more tokens, more latency, more failure modes. A single well-prompted agent with good tools beats a fragile swarm most of the time.

08  OWASP LLM Top-10 highlights + mitigations

The security checklist for LLM apps (OWASP LLM Top 10, 2025 list — current as of June 2026). Know the top few cold and the standard defence for each.

LLM01 · Prompt injection
Untrusted input overrides your instructions (direct or via retrieved/3rd-party content). Mitigate: isolate untrusted text, least-privilege tools, human-in-loop for risky actions, input/output guardrails. The #1 risk.
LLM02 · Sensitive info disclosure
Model leaks secrets, PII, or system prompt. Mitigate: output filtering/PII redaction, don't put secrets in prompts, scope data access.
LLM03 · Supply chain
Poisoned models, datasets, or plugins/packages. Mitigate: vet sources, pin & sign artifacts, scan dependencies.
LLM04 · Data & model poisoning
Tampered training/fine-tune data plants backdoors or bias. Mitigate: provenance, data validation, anomaly detection.
LLM05 · Improper output handling
Treating model output as trusted → XSS, SQLi, RCE downstream. Mitigate: encode/validate output, never eval() it, parameterize queries.
LLM06 · Excessive agency
Agent has too much permission/autonomy and acts harmfully. Mitigate: least privilege, scoped tools, approval gates.
LLM07 · System-prompt leakage
Hidden instructions/secrets in the system prompt get extracted. Mitigate: assume the prompt is public; keep secrets out of it.
LLM08 · Vector / embedding weaknesses
RAG-specific: poisoned docs, cross-tenant leakage, injection via retrieved chunks. Mitigate: access-control the index, validate sources, per-tenant isolation.
LLM09 · Misinformation
Confident hallucinations users over-trust. Mitigate: grounding/RAG with citations, eval, show uncertainty.
LLM10 · Unbounded consumption
Cost/DoS from runaway tokens or query floods. Mitigate: rate-limit, token caps, timeouts, budgets.

09  Say it in three beats

define → trade-off → gotcha say it

Whatever they ask, answer in three beats: (1) Define it in one or two plain sentences. (2) Name the trade-off — “you'd use it when… but it costs… so the alternative is…”. (3) Call the gotcha — the failure mode or common mistake. A crisp 30-second answer that names a trade-off beats a two-minute brain-dump; if they want depth, they'll ask the follow-up. Seniority lives in the trade-off; shipped experience shows in the gotcha. Full method on the How to interview page.
