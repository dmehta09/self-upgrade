Safety & security · threat models

The OWASP LLM Top 10 IV NEW

When an interviewer asks “what are the security risks of LLM apps?”, they want a structured answer — not a vibe. The OWASP LLM Top 10 is the industry's shared checklist, and the v2.0 revision is the current reference as of June 2026. Knowing the list (and which entries matter most for agents) instantly signals you've shipped real systems, not just demos.

01  What OWASP is, and why this list exists

OWASP (the Open Worldwide Application Security Project) is a long-running non-profit famous for the OWASP Top 10 for web apps — the canonical list of the most critical risks. As LLM apps exploded, they published a dedicated Top 10 for LLM Applications, because the classic web list didn't capture threats like prompt injection or training-data poisoning. It's the common vocabulary teams use to triage.

The pre-flight checklist for AI analogy

Pilots don't rely on remembering what to check before takeoff — they run a printed checklist, every flight, so nothing critical is skipped. The OWASP LLM Top 10 is that checklist for shipping an AI feature: walk each item, ask “does my system have this hole?”, and you'll catch the failure modes that have actually bitten people. It won't make you creative about novel attacks, but it stops you forgetting the obvious ones.

02  The v2.0 list, walked NEW

You don't need the exact codes memorised, but you should be able to name and explain most of these. Here's the v2.0 set in plain language:

#RiskOne-line meaning
LLM01Prompt injectionUntrusted text overrides your instructions. The headline risk (previous page).
LLM02Sensitive information disclosureThe model leaks PII, secrets, or proprietary data into its output.
LLM03Supply chainA compromised model, dataset, adapter, or library you pulled in is malicious.
LLM04Data & model poisoningTainted training/fine-tune/RAG data plants backdoors or bias.
LLM05Improper output handlingTreating raw LLM output as safe — it flows into SQL, HTML, or a shell.
LLM06Excessive agencyThe model has more tools/permissions/autonomy than the task needs.
LLM07System-prompt leakageThe hidden prompt — and any secrets in it — gets extracted.
LLM08Vector & embedding weaknessesAttacks on the RAG layer: poisoned or leaky vector stores, cross-tenant bleed.
LLM09MisinformationConfident hallucinations users over-trust and act on.
LLM10Unbounded consumptionRunaway tokens/cost/compute — denial-of-wallet and resource exhaustion.

v2.0 notably elevated system-prompt leakage, vector/embedding weaknesses, and broadened the old “denial of service” into unbounded consumption — all reflecting the rise of RAG and agents. Treat the exact ordering as “as of June 2026.”

03  The ones that bite agents hardest NEW

If you're building tool-using agents (and in 2026 you usually are), a few entries dominate the risk. Be able to go deep on these:

Excessive agency (LLM06)
The big one for agents. If a hijacked model can only do small, reversible things, an injection is a nuisance; if it can wire money, delete prod, or email your whole CRM, it's a breach. Fix = least privilege: minimal tools, minimal scopes, human approval on dangerous actions.
Sensitive-information disclosure (LLM02)
Models repeat what they're given. Secrets in the system prompt, PII in retrieved docs, or one tenant's data in another's context all leak out. Fix = don't put secrets in prompts, redact PII, isolate tenants.
System-prompt leakage (LLM07)
Assume the system prompt will be extracted — so it must contain no secrets and no security-by-obscurity. It's instructions, not a vault.
Vector & embedding weaknesses (LLM08)
The RAG attack surface: an attacker plants a doc in your index (poisoning) so it's retrieved and injected; or a shared/leaky vector store lets one user retrieve another's private chunks. Fix = trust your ingestion pipeline, scope retrieval per tenant.
Data & model poisoning (LLM04)
Corrupt the data and you corrupt the model — a backdoor trigger phrase, biased fine-tune data, or a tainted public dataset. Fix = vet data provenance, especially for fine-tuning and RAG ingestion.
Unbounded consumption (LLM10)
An attacker (or a runaway loop) drives huge token/compute usage — “denial of wallet.” Fix = rate limits, per-user budgets, max-iteration caps on agent loops.

04  Improper output handling: the bug devs forget

Everyone watches what goes into the model; far fewer treat what comes out as dangerous. But LLM output is untrusted input to whatever consumes it. Pipe it somewhere powerful without sanitising and you get classic web vulnerabilities wearing an AI hat:

XSS
Model output containing <script> rendered straight into a web page runs in your users' browsers. Escape/sanitise before display.
SQL injection
Letting the model build a query string that hits your database — same disaster as user-supplied SQL. Use parameterised queries; never exec raw model text.
SSRF / command injection
Model output used to construct a URL the server fetches, or a shell command it runs, lets an attacker reach internal services or the host. Validate against an allow-list.
LLM output is user input — to the next system gotcha

The dangerous mental slip is “the output came from our model, so it's trusted.” It isn't — especially once injection enters the picture, an attacker can choose what your model emits. Anything downstream (your DB, your DOM, your shell, a webhook) must treat model output with the same suspicion as a raw form field. This is why improper output handling is its own Top-10 entry rather than a footnote.

05  Threats → mitigations at a glance

The interview-gold version: pair each risk with the control you'd actually reach for.

ThreatPrimary mitigation
Prompt injection (direct & indirect)Untrusted-by-default content, separate detection classifier, least-privilege tools, human approval — defense in depth
Sensitive-info disclosureKeep secrets out of prompts; PII detection & redaction; per-tenant data isolation; output filtering
Improper output handlingTreat output as untrusted; escape/sanitise; parameterised queries; no raw exec; allow-list URLs/commands
Excessive agencyLeast privilege: minimal tools & scopes, sandboxing, human-in-the-loop on irreversible actions
System-prompt leakageAssume it leaks — no secrets in the prompt; enforce policy in code, not by obscurity
Vector/embedding weaknessesVet ingestion provenance; scope retrieval per tenant; access controls on the vector store
Data/model poisoningTrusted data sources, provenance checks, dataset review before fine-tuning
Unbounded consumptionRate limits, per-user/token budgets, max-iteration caps, timeouts
Supply chainVerify model/adapter/library sources & checksums; pin and scan dependencies
MisinformationGrounding (RAG), citations, confidence cues, human review for high-stakes outputs
How to say it out loud say it

“I anchor on the OWASP LLM Top 10 v2.0. Prompt injection is #1, but for agents the ones I worry about most are excessive agency, sensitive-information disclosure, system-prompt leakage, and the RAG-layer risks — vector/embedding weaknesses and data poisoning — plus unbounded consumption as a denial-of-wallet vector. And I never forget improper output handling: model output is untrusted input to my DB, DOM, and shell, so I sanitise it like any user data. Each risk maps to a concrete control, and the unifying theme is least privilege plus defense in depth.”

06  Self-check

Your agent has tools for reading and deleting any record, transferring funds, and emailing externally — even though its job is just answering FAQs. Which OWASP LLM risk is this, first and foremost?
Excessive agency (LLM06) is exactly this: capabilities, permissions, or autonomy beyond what's needed. The danger is multiplicative with prompt injection — if the model is hijacked, those over-broad tools become the attacker's tools. The fix is least privilege: strip the agent down to read-only FAQ access and gate anything sensitive behind human approval.
“Name the top security risks for an LLM application.”Warm-up
Model answer

I'd frame it with the OWASP LLM Top 10 v2.0. Top of mind: prompt injection (direct and indirect), sensitive-information disclosure, improper output handling, excessive agency, system-prompt leakage, vector/embedding weaknesses, data and model poisoning, supply-chain risk, misinformation, and unbounded consumption. For agents specifically, excessive agency and the RAG-layer risks are where I focus, because injection plus broad tool permissions is how a content problem becomes a breach.

How to say it out loud say it

“OWASP LLM Top 10 v2.0 — injection #1, then disclosure, output handling, excessive agency, prompt leakage, vector/poisoning risks, and unbounded consumption.”

“Give a concrete example of improper output handling.”Core
Model answer

A support bot renders its answer as HTML in the browser. An attacker uses indirect injection so the model emits <script>steal-cookies()</script>; because the app trusts its own model's output and injects it into the DOM unescaped, that script runs in every viewer's browser — stored XSS via the LLM. Same shape if model output builds a SQL string (SQLi) or a URL the server fetches (SSRF). The fix is to treat output as untrusted: escape before rendering, parameterise queries, and allow-list any URL or command.

How to say it out loud say it

“Model output rendered as HTML becomes XSS; used as SQL becomes SQLi. Output is untrusted input to the next system — escape, parameterise, allow-list.”
