RAG · advanced retrieval

Late interaction, multi-vector & GraphRAG IV NEW

Hybrid + reranking covers most needs. But some problems push further: you want cross-encoder accuracy at retrieval speed, or you're asking questions that span many documents at once, or your knowledge lives in images and tables. This page tours the frontier — ColBERT / late interaction, multi-vector representations, GraphRAG, and multimodal RAG — and, just as importantly, when each is overkill.

01  ColBERT & late interaction NEW

Recall the tension from the last page: a bi-encoder squashes a whole document into one vector (fast, but lossy), while a cross-encoder reads query and document together (accurate, but can't be pre-indexed). Late interaction, pioneered by ColBERT, is a clever middle ground that keeps most of the cross-encoder's accuracy at close to bi-encoder speed.

The trick: instead of one vector per document, store one vector per token. Both query and document become a bag of token-vectors, computed independently (so documents are still pre-indexed). At query time, for each query token you find its best-matching document token and sum those maxes — the “MaxSim” operator. The token vectors are precomputed; only the cheap matching happens live.

“Late” interaction = the query and document interact late (at scoring time via MaxSim) rather than early (inside one model, like a cross-encoder) or never (a single dot product, like a bi-encoder).
Fingerprints, not a single mugshot analogy

A bi-encoder describes a document with one blurry mugshot. ColBERT keeps a fingerprint per token. To match, each query finger finds the document finger it lines up with best, and you add up the matches. Far more precise — at the cost of storing a lot more fingerprints.

02  Multi-vector & its storage cost

ColBERT is one example of a broader idea: representing a chunk with multiple vectors instead of one. That includes per-token vectors (ColBERT), or storing several summary vectors per document, or embedding both a chunk and a generated summary/question for it. More vectors = more facets captured = better recall. But there's no free lunch:

Per-token vectors explode your index gotcha

One vector per token can mean tens to hundreds of vectors per chunk — an order of magnitude more storage and a heavier index than single-vector dense search. Production ColBERT setups lean hard on quantization and compression to stay affordable. Always weigh the recall gain against the storage and latency bill before reaching for multi-vector.

03  GraphRAG: for multi-hop & theme questions NEW

Plain RAG retrieves a handful of independent chunks. That's fine for “what's our refund window?” but it falls apart on questions that need to connect information across many documents: “How are these three incidents related?” or “What are the main themes across all our customer feedback?” No single chunk holds the answer.

GraphRAG builds a knowledge graph first. During indexing, an LLM extracts entities (people, products, events) and the relationships between them from your documents, forming a graph. It also pre-summarises clusters of related entities into community summaries. At query time you traverse the graph to gather connected facts, or read the community summaries for big-picture questions.

Multi-hop questions
“Who reported the bug that caused the outage that delayed the launch?” needs to chain three facts. Graph edges let you walk from one to the next; flat top-k retrieval can't.
Global / theme questions
“Summarise the top complaints across 10,000 reviews.” No chunk contains the answer; the precomputed community summaries do.
Detective's corkboard vs a pile of clippings analogy

Naive RAG hands the detective a few loose newspaper clippings. GraphRAG gives them the full corkboard — photos pinned up with red string connecting who-knows-whom. To answer “how is A linked to C?” you just follow the string through B. The connections are the answer.

This was the bird's-eye view — the full build-and-query mechanics (indexing pipeline, local vs global search, the cheaper lazy variants) get their own lesson: GraphRAG: graphs meet retrieval.

04  Multimodal RAG over images & tables NEW

Loads of real knowledge isn't clean prose — it's scanned invoices, architecture diagrams, charts, and dense tables. Two approaches let RAG handle them:

Describe, then embed text
Run each image/table through a vision-language model (VLM) to generate a text description or summary, then embed and retrieve that text like normal. Simple, works with your existing text pipeline.
Embed the image directly
Use a multimodal embedding model (CLIP-lineage) so images and text live in the same vector space — a text query can retrieve a relevant image. At generation time you pass the actual image to a VLM that can “see” it.

Either way, the generator is a vision-capable model that can read the retrieved pictures and tables — see Vision-language models for how VLMs work under the hood.

05  When all this is overkill

The single most valuable thing to say about advanced retrieval in an interview is when not to use it. These techniques add real cost, latency, and operational complexity, and they shine only on specific problem shapes.

Don't build GraphRAG for an FAQ bot gotcha

GraphRAG's indexing is expensive — you're running an LLM over your whole corpus to extract entities and summaries, and re-running it as docs change. If your questions are answerable from single chunks (most FAQ / support / doc-search use cases), it's pure overhead. Likewise, reach for ColBERT/multi-vector only when hybrid + reranking has plateaued and you've measured that recall is still the bottleneck. Earn each step up the spectrum with eval numbers.

How to say it out loud say it

“Beyond hybrid + reranking there's late interaction like ColBERT — per-token embeddings scored with MaxSim, near cross-encoder accuracy at retrieval speed, but with a big storage cost. GraphRAG builds an entity-relationship graph so you can answer multi-hop and whole-corpus theme questions a flat top-k can't. And multimodal RAG handles images and tables via VLMs. I'd only adopt these once eval shows hybrid + reranking has plateaued — for most apps they're overkill.”

06  Self-check

A user asks: “Across all our 2025 incident reports, what were the recurring root causes?” Why does naive top-k RAG struggle, and what fits better?
Top-k retrieves a few independent chunks, but “recurring causes across all reports” is a whole-corpus synthesis — the answer isn't in any one chunk. GraphRAG precomputes community summaries for exactly this, or you map-reduce summaries across documents. Just cranking k floods the context without giving the model the cross-document structure.
“Explain late interaction / ColBERT versus a normal bi-encoder.”Stretch
Model answer

A bi-encoder collapses a document into a single vector and scores with one dot product — fast but lossy. ColBERT keeps one vector per token and scores with MaxSim: each query token matches its best document token, and you sum those. Because the token vectors are still computed independently, documents can be pre-indexed, so you get accuracy close to a cross-encoder at roughly bi-encoder speed. The catch is storage — many vectors per chunk — so it leans on compression.

How to say it out loud say it

“Bi-encoder = one vector per doc, one dot product. ColBERT = one vector per token, scored with MaxSim. It interacts late, stays pre-indexable, gets near cross-encoder quality — but the per-token vectors blow up storage.”

“When would you choose GraphRAG over vanilla RAG?”Core
Model answer

When questions require connecting facts across many documents — multi-hop reasoning — or summarising whole-corpus themes, where no single chunk has the answer. GraphRAG extracts an entity-relationship graph and community summaries at index time so you can traverse connections or read precomputed summaries. I wouldn't use it for single-fact lookups; its indexing is LLM-heavy and expensive, so it only pays off for connected or global questions.

How to say it out loud say it

“GraphRAG when the answer spans documents — multi-hop chains or corpus-wide themes. It builds an entity graph plus community summaries at index time. Overkill for single-fact FAQ lookups, though, because indexing is LLM-expensive.”
