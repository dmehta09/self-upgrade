RAG · retrieval as a loop

Agentic RAG IV NEW

Everything so far retrieves once, then answers. Agentic RAG turns retrieval into a loop: the model plans what to look up, retrieves, judges whether the results are good enough, and retrieves again — rephrasing the query, hitting a different source, or falling back to web search — until it can actually answer. It trades latency and cost for the ability to handle hard, vague, or multi-step questions that one-shot RAG simply gets wrong.

01  From one shot to a loop

Naive RAG is a straight line: retrieve → generate. If the first retrieval misses, you're stuck with a bad answer. Agentic RAG closes the loop with an evaluate step and the ability to re-retrieve:

The agentic RAG loop
plan
what do I need?
decompose, pick a source
retrieve
fetch chunks
vector / web / tool
evaluate
good enough?
grade relevance
answer / retry
generate or loop back
re-retrieve if weak
The dashed back-edge — “if the evidence is weak, go again with a better query or a different source” — is the whole point. It's a small agent whose tools are retrievers.
A researcher, not a vending machine analogy

Naive RAG is a vending machine: one query in, one snack out, take what you get. Agentic RAG is a research assistant: they look something up, glance at it, mutter “this isn't quite right,” rephrase the search, check another database, and only come back once they've actually got what you need. The willingness to look again is what makes them useful.

02  Self-RAG & Corrective RAG NEW

Two named patterns make the “evaluate” step concrete. Both add a grader that scores retrieved chunks before the model trusts them:

Self-RAG
The model learns to emit reflection tokens that decide, on the fly, whether to retrieve at all, and to critique whether each retrieved passage is relevant and whether its own draft is supported by it. Retrieval becomes adaptive and self-checked rather than always-on.
Corrective RAG (CRAG)
A lightweight grader labels each retrieval as correct / ambiguous / incorrect. If the local documents are judged poor, it falls back to web search (or another source) instead of answering from weak evidence. The “correction” is switching sources when your index comes up short.
Checking the pantry before ordering takeout analogy

CRAG is like cooking dinner: first you check the fridge (your vector store). If the ingredients are there, great. If they're missing or off, you don't just cook a bad meal — you order in (web search). Grading-then-falling-back keeps a weak local index from poisoning the answer.

03  Adaptive routing: match effort to the question NEW

Not every query deserves the full loop. Adaptive routing (a.k.a. adaptive RAG) puts a cheap classifier up front that sizes the question and sends it down the right path — the key technique for keeping an agentic system's cost under control.

Simple / chit-chat
“Hi” or a fact the model plainly knows → skip retrieval entirely, just answer. Retrieval isn't free; don't pay for it when it adds nothing.
Single-fact lookup
“What's our refund window?” → one round of plain RAG. No loop needed.
Complex / multi-hop
“Compare our Q1 and Q3 incident causes and what changed” → the full agentic loop: decompose, retrieve per sub-question, evaluate, synthesise.
How to say it out loud say it

“Agentic RAG makes retrieval a loop — plan, retrieve, evaluate, re-retrieve — so it can recover from a bad first hit. Self-RAG and Corrective RAG add a grader that judges the chunks and, in CRAG, falls back to web search when the local index is weak. To keep cost sane I'd put adaptive routing in front: a cheap classifier that skips retrieval for trivial queries, does one-shot RAG for simple lookups, and only spends the full loop on genuinely complex questions.”

04  When agentic RAG is overkill

An agentic loop is powerful and expensive: every iteration is extra LLM calls, extra latency, and another place for the model to go off the rails. The senior move is to default to the simplest pipeline that passes your eval and reserve the loop for queries that truly need it.

Loops add latency, cost, and failure surface gotcha

If hybrid + reranking already answers your questions, an agentic loop just makes them slower and pricier — and can loop forever or compound an early mistake across iterations. Always cap the number of iterations, set a per-query budget, and trace each step so you can debug. Reach for the loop only when single-shot retrieval measurably fails on a meaningful slice of your traffic.

Implementing the loop? Use a state graph note

An agentic RAG loop is naturally a graph: nodes for plan / retrieve / grade / generate, and a conditional edge from the grader that either loops back to retrieve or moves on to generate — all over a shared state object. 05  Self-check

In Corrective RAG (CRAG), what happens when the grader labels the retrieved local documents as “incorrect”?
CRAG's “correction” is recognising that the local index came up short and switching sources — usually web search — rather than building an answer on poor evidence. Grading retrieval quality and reacting to it is the core idea.
“What makes RAG ‘agentic,’ and when is it worth it?”Core
Model answer

It's agentic when the model controls retrieval in a loop instead of retrieving once: it plans queries, evaluates whether the results are good enough, and re-retrieves or switches sources if not — patterns like Self-RAG and Corrective RAG. It's worth it for complex, multi-hop, or ambiguous questions where one-shot retrieval reliably misses. It's not worth it for simple lookups, because each loop adds latency and cost — which is why I'd gate it behind adaptive routing.

How to say it out loud say it

“Agentic = retrieval in a loop with a grade-and-retry step, so it recovers from bad first hits. Great for complex/multi-hop questions, overkill for simple lookups — so route by complexity to control cost.”

“How do you stop an agentic RAG loop from running forever or blowing the budget?”Core
Model answer

Hard limits and observability. Cap the iteration count, set a per-query token/cost budget, and have the grader stop once evidence is “good enough” rather than chasing perfection. Add adaptive routing so most queries never enter the loop, and trace every step so you can see where it's spinning. Without these guardrails an agent can loop indefinitely or compound an early bad decision.

How to say it out loud say it

“Cap iterations, set a per-query budget, stop at ‘good enough,’ route simple queries around the loop, and trace every step. Guardrails are non-negotiable or the loop runs away.”
