RAG · the big decision

RAG vs fine-tune vs long context IV NEW

“Should we use RAG or fine-tune the model?” is one of the most common GenAI interview questions — and the trap is treating it as either/or. They solve different problems, a giant context window is now a third option, and the best real systems often combine them. This page gives you the decision framework and the crisp answer.

01  Knowledge vs behaviour vs the desk

The cleanest way to cut through the debate: ask what kind of gap you're closing. RAG adds knowledge. Fine-tuning changes behaviour. A long context window is a bigger desk for one task. Memory persists facts across tasks.

Hiring a new employee analogy

Think of onboarding someone. RAG is giving them access to the company wiki — they can look anything up, and it's always current. Fine-tuning is sending them to training so they internalise how we do things here — our tone, our format, our style. Long context is handing them a fat briefing folder for one specific meeting. You don't send someone to a six-week course just to teach them today's stock price — you give them the wiki.

That analogy resolves most arguments instantly: facts → look them up (RAG); skills and style → train them in (fine-tune); one-off bulk material → put it on the desk (context).

03  The ladder: Prompt → RAG → Fine-tune → Distill NEW

You rarely start at the top. The discipline is to climb only when the rung below stops paying off — each step up costs more effort and money, so earn it with evidence:

Most teams should reach for prompting and RAG long before fine-tuning. Distillation — training a small model to mimic a big one — is a later optimisation for cost/latency at scale, not a first move.

04  Can't I just stuff it all into 1M tokens? NEW

With 1M+ token windows common in 2026, it's tempting to skip retrieval and paste your whole knowledge base into the prompt. Sometimes that genuinely wins — but it has three real costs that keep RAG relevant:

Cost
You pay for every token on every call. Stuffing 500K tokens of context into each request is wildly more expensive than retrieving 5 chunks — and you re-pay it on every single query. (Prompt caching softens repeated prefixes but doesn't make it free.)
Latency
More input tokens means slower responses. A megabyte of context per call adds real wall-clock time versus a tight retrieved prompt.
“Lost in the middle”
Models attend best to the start and end of a long context and reliably miss facts buried in the middle. A huge window doesn't guarantee the model actually uses the relevant part — retrieval + reranking puts the right thing where attention is strongest.

The honest rule: long context wins when the relevant material is modest, fits comfortably, and changes per request (e.g. “answer questions about this one uploaded contract”). It loses when the corpus is large, queried repeatedly, or cost-sensitive — which is most production RAG. The two also compose: retrieve the top ~50 candidates, then let a long-context model read all of them.

A bigger window isn't a free pass gotcha

“We have 1M tokens, so we don't need RAG” ignores cost (you re-pay per call), latency, and lost-in-the-middle. Long context is a powerful complement to retrieval — read more candidates at once — not a wholesale replacement for it in large, repeatedly-queried systems.

05  The best answer is often “both”: RAG + a thin LoRA NEW

Because RAG and fine-tuning fix different gaps, the strongest setups combine them. The classic pairing: RAG for the facts, a small LoRA adapter for the behaviour. A LoRA is a tiny, cheap-to-train add-on that nudges the model's style and format — say, “always answer like our support team, in this JSON shape” — while RAG keeps feeding it current, citable facts.

Trained employee + live wiki analogy

Back to onboarding: the ideal hire has been through your training (the LoRA — they know the house style) and has the wiki open (RAG — current facts). Neither alone is as good. The fine-tune handles “how to say it,” RAG handles “what's true today.”

06  Answering “RAG or fine-tuning?” well

When you get the question, don't pick a side — reframe it. Diagnose the gap, then prescribe:

  1. Name the gap. Is it missing knowledge (facts the model doesn't have) or wrong behaviour (tone, format, a skill)? That one distinction does most of the work.
  2. Knowledge → RAG. Especially if it's fresh, private, or needs citations. Fine-tuning facts is expensive and goes stale.
  3. Behaviour → fine-tune. Consistent style, strict format, a narrow skill the base model fumbles even with good prompts.
  4. Often both, and start cheap: prompt → RAG → fine-tune, climbing the ladder only when eval says the rung below isn't enough.
How to say it out loud say it

“They solve different problems, so it's rarely either/or. RAG adds knowledge — fresh, private, citable facts — by retrieving at query time. Fine-tuning changes behaviour — tone, format, a skill — but bakes facts in expensively and they go stale. I'd diagnose the gap first: knowledge problems get RAG, behaviour problems get a fine-tune, and the best systems often do both — RAG for facts plus a thin LoRA for style. I climb the ladder prompt → RAG → fine-tune → distill only as far as the evals force me. Long context is a fourth lever: great for one-off bulk material, but per-call cost, latency, and lost-in-the-middle keep RAG the default for large, repeatedly-queried corpora.”

07  Self-check

A bank wants a bot that always answers in their exact compliance-approved phrasing and JSON schema, using policy documents that get updated weekly. What's the best approach?
Two different gaps: the behaviour (exact phrasing + schema) is stable → fine-tune/LoRA; the knowledge (weekly-updated policies) changes constantly → RAG, so it's an insert not a retrain, and it's citable. Fine-tuning the documents would go stale in a week; stuffing them all into context every call is needlessly expensive.
“RAG or fine-tuning — how do you decide?”Core
Model answer

I diagnose the gap. Missing knowledge — especially fresh, private, or citation-worthy facts — points to RAG, because it updates with an insert and stays current. Wrong behaviour — tone, format, a narrow skill — points to fine-tuning, because you're changing how the model acts, not what it knows. They're complementary: a common production setup is RAG for facts plus a small LoRA for style. And I'd start cheap, climbing prompt → RAG → fine-tune only as evals demand.

How to say it out loud say it

“Knowledge gap → RAG; behaviour gap → fine-tune; often both. RAG updates instantly and cites; fine-tuning changes style but bakes facts in. I climb the ladder only as far as eval forces.”

“With million-token context windows, is RAG obsolete?”Stretch
Model answer

No. Long context is great when the relevant material is modest and changes per request — “answer about this one document.” But stuffing a large corpus into every call is expensive (you re-pay per query), slower, and hits lost-in-the-middle, where models miss facts buried mid-context. For large, repeatedly-queried knowledge bases, retrieving a few relevant chunks is cheaper, faster, and citable. In practice they compose: retrieve the top candidates, then let a long-context model read all of them.

How to say it out loud say it

“Not obsolete — complementary. Long context suits one-off bulk material; RAG wins on cost, latency, and lost-in-the-middle for big, repeatedly-queried corpora. I often do both: retrieve, then read widely.”
