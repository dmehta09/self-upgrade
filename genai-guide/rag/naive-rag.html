RAG from scratch IV

The best way to understand RAG is to build the smallest possible version with no framework — just a list of text chunks, a similarity score, and a prompt. Once you've seen the whole loop in ~30 lines, every "advanced" technique becomes an obvious upgrade to one specific step. Let's walk the minimal pipeline end to end with a worked example.

01  The minimal loop

Strip RAG down to its bones and there are just three query-time moves: embed the question, find the closest chunks, ask the model with those chunks attached. The indexing (chunk + embed + store) was done earlier. Here's the shape, then the code:

Query time: three moves
question
“What's our refund window?”

top-k chunks

grounded answer

"Retrieve, augment, generate" — the three words hiding in the acronym. Everything fancier is a better version of one of these.
A research assistant with sticky notes analogy

Picture handing an assistant a question. They riffle through a filing cabinet, pull the three most relevant pages, slap them on your desk with the question on top, and say “answer using these.” That's RAG. The cabinet is your vector store, “most relevant” is cosine similarity, and the desk is the prompt.

02  A worked example in Python

Say our knowledge base is a tiny support FAQ. We'll embed each chunk once, then answer a question. (The embedding call is shown generically — any embedding model works; see Embedding models.)

index.py — build the store (once)
import numpy as np

# 1) our knowledge base, already split into chunks
chunks = [
    "Refunds are accepted within 30 days of purchase with a receipt.",
    "Our office is open Monday to Friday, 9am to 5pm.",
    "Premium plans include 24/7 priority support and a dedicated manager.",
]

# 2) embed every chunk ONCE, offline. embed() -> list[float]
store = [(c, np.array(embed(c))) for c in chunks]   # (text, vector) pairs

At query time we embed the question, score every chunk by cosine similarity (angle between vectors — closer meaning = higher score), and keep the top k:

retrieve.py — find the best chunks
def cosine(a, b):
    return float(a @ b / (np.linalg.norm(a) * np.linalg.norm(b)))

def retrieve(question, k=2):
    q = np.array(embed(question))
    scored = [(cosine(q, vec), text) for text, vec in store]
    scored.sort(reverse=True)            # highest similarity first
    return [text for _score, text in scored[:k]]

hits = retrieve("How long do I have to return something?")
# -> ["Refunds are accepted within 30 days of purchase with a receipt.", ...]

Notice the question never used the word “refund,” yet the refund chunk wins — that's the magic of semantic (dense) search: it matches meaning, not keywords. (Its weakness, exact terms and rare IDs, is exactly what hybrid search fixes on the next page.)

03  Prompt assembly: stuffing + a citation rule

Now the part interviewers love: how do the chunks actually get to the model? You build a prompt that (a) gives the model only the retrieved context, (b) tells it to answer from that context, and (c) tells it to cite and to say "I don't know" if the answer isn't there. This last instruction is what keeps RAG honest.

generate.py — assemble & answer
SYSTEM = (
    "Answer ONLY using the numbered context below. "
    "Cite the source number(s) you used like [1]. "
    "If the answer is not in the context, say \"I don't know.\""
)

def build_prompt(question, hits):
    context = "\n".join(f"[{i+1}] {c}" for i, c in enumerate(hits))
    return f"{SYSTEM}\n\nContext:\n{context}\n\nQuestion: {question}"

prompt = build_prompt("How long do I have to return something?", hits)
answer = llm(prompt)
# -> "You have 30 days from purchase to return an item, with a receipt. [1]"

That's a complete RAG system. The three instructions in SYSTEM — use only this, cite it, admit ignorance — are doing enormous work. Drop any one and quality falls off a cliff.

Building this for real? Use a framework note

We teach the concept here so you understand every moving part. In production you'd wire this with a framework rather than hand-rolling it — retrievers, prompt templates, and the LLM chained together with LCEL. See the Lang Stack guide for the LangChain/LangGraph framework code that implements exactly this pipeline.

04  The four ways naive RAG fails

Naive RAG is a great teaching tool and a shaky production system. Knowing its failure modes — and which step each one lives in — is prime interview territory:

FailureWhat happensFix (where we cover it)
Bad retrievalThe right chunk never makes the top-k — wrong or missing context. The #1 cause of bad RAG.Hybrid search + reranking; better chunking
Context overflowToo many / too-long chunks blow the token budget or bury the answer in the middle (“lost in the middle”).Fewer, reranked chunks; compression
Model ignores contextThe chunk is there but the model answers from its own memory anyway, or contradicts it.Stronger “use only context” instruction; eval
Hallucinated citationsThe model invents a [3] that doesn't exist, or cites the wrong source.Validate cites against retrieved IDs; grounding eval

Watch failure #1 happen. The same pipeline, two queries — one that embeddings love, one that they quietly butcher:

A citation is not a guarantee gotcha

Seeing [1] in the output feels reassuring, but the model can cite a source that doesn't actually support the claim — or fabricate one entirely. Always verify citations programmatically: check that every cited number exists in your retrieved set, and ideally that the cited chunk really contains the claim. Trust, but verify.

How to say it out loud say it

“Naive RAG is embed-the-query, take top-k by cosine similarity, stuff the chunks into the prompt with a ‘use only this and cite it’ instruction. It fails in four classic ways: bad retrieval, context overflow, the model ignoring the context, and hallucinated citations. The first one — retrieval misses — is the most common, which is why the next thing I'd add is hybrid search and a reranker.”

05  Self-check

Your naive RAG bot answers a question that is covered in your docs, but gives a generic, slightly-wrong answer with no citation. The retrieved chunk shown in your logs is correct. What's the most likely issue?
If the correct chunk was retrieved (per your logs) but the answer is generic and uncited, retrieval worked — generation didn't follow it. That's the “model ignores context” failure mode, fixed by a stronger grounding instruction and eval, not by touching retrieval.
“Walk me through a minimal RAG pipeline.”Core
Model answer

Offline: split docs into chunks, embed each, store the vectors. At query time: embed the question, find the top-k nearest chunks by cosine similarity, build a prompt that contains those chunks plus an instruction to answer only from them and cite sources, then call the LLM. Optionally validate the citations against the retrieved IDs before returning.

How to say it out loud say it

“Chunk, embed, store — that's indexing. Then embed the query, retrieve top-k by similarity, stuff them into a grounded prompt, generate. Three moves: retrieve, augment, generate.”

“How do you stop a RAG system from making up answers?”Core
Model answer

Three layers. In the prompt: instruct “answer only from the context; if it's not there, say I don't know,” and require citations. In retrieval: make sure the right chunk is actually present (the real fix for most hallucination is better retrieval). In eval: measure faithfulness/groundedness and validate that cited sources exist and support the claim. No single layer is enough alone.

How to say it out loud say it

“Ground it: ‘use only this context, cite it, say I don't know otherwise.’ But the deepest fix is retrieval — if the answer isn't in the chunks, no prompt saves you. Then verify citations and run a faithfulness eval.”
