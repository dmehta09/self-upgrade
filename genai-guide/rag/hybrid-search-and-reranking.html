Hybrid search & reranking IV NEW

If naive RAG disappoints, this is the page that fixes it. Two upgrades do most of the heavy lifting: hybrid search (combine semantic and keyword matching so you never miss the obvious) and a reranker (a second, smarter model that re-scores the candidates). Together they're the strong default for production RAG in 2026 — and the answer interviewers are listening for when they ask "your retrieval is bad, what do you try first?"

01  Two kinds of search, two blind spots

Dense (semantic) search — the embedding-based retrieval from the last page — matches meaning. Sparse (keyword) search like BM25 matches exact terms. Each is brilliant where the other is blind:

Dense / semanticSparse / BM25 (keyword)
Matches onMeaning — paraphrases, synonymsExact words & their frequency
Great at“return policy” → finds “refund window”Error code E-4021, product SKU, names
Blind toRare IDs, acronyms, exact strings it never embedded wellSynonyms it didn't literally see
A librarian and a search box analogy

Dense search is a librarian who knows what you mean — ask for “books about feeling blue” and she brings you titles on depression. Sparse search is the catalog's Ctrl-F — type “ISBN 978-0…” and it finds the exact match instantly, but ask it about “feeling blue” and it shrugs. Hybrid search hires both and merges their picks.

02  Hybrid search: fusing the two with RRF NEW

Run both searches, then merge their ranked lists. The problem: dense scores (cosine, ~0–1) and BM25 scores (unbounded) aren't comparable, so you can't just add them. The robust, parameter-light answer is Reciprocal Rank Fusion (RRF): ignore the raw scores and fuse on rank position instead. Each document gets 1/(k + rank) from each list (with a constant k, commonly 60), summed across lists.

rrf.py — fuse two ranked lists
def rrf(*ranked_lists, k=60):
    scores = {}
    for ranked in ranked_lists:            # each is a list of doc_ids, best first
        for rank, doc_id in enumerate(ranked):
            scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank)
    return sorted(scores, key=scores.get, reverse=True)

dense  = ["d3", "d1", "d7"]                # from embedding search
sparse = ["d1", "d9", "d3"]               # from BM25
fused  = rrf(dense, sparse)               # -> d1, d3, ... (agreed-on docs rise)

Documents that both methods rank highly float to the top; a doc only one method found still gets a fair shot. RRF needs no score normalisation and almost no tuning, which is why it's the default fusion method. Many vector databases now offer hybrid search with RRF as a built-in option (as of June 2026).

03  Reranking: the single biggest quality lever NEW

First-stage retrieval (dense, sparse, or hybrid) is built for speed over millions of docs — so it's approximate. A reranker takes the top ~20–100 candidates it returns and re-scores each one against the query with a much more accurate (but slower) model, then keeps the best few. You retrieve wide and cheap, then rerank narrow and precise.

This two-stage shape — cheap recall then precise reranking — is the workhorse of modern RAG. Teams routinely report it as their biggest single quality jump.

Why does it help so much? Because the reranker sees the query and the document together and can judge true relevance, whereas first-stage embeddings were computed before anyone knew the query. That difference is the bi-encoder vs cross-encoder distinction — next.

04  Bi-encoder vs cross-encoder NEW

This is the conceptual heart of reranking, and a favourite interview probe. The two architectures trade speed for accuracy in opposite directions:

Where the query and document meet
bi-encoder
embed separately
query ▷ vec · doc ▷ vec, then cosine
cross-encoder
read together
[query + doc] ▷ one model ▷ score
Bi-encoder: doc vectors are precomputed and reused — fast, scales to millions, used for first-stage retrieval. Cross-encoder: must run the model fresh on every query–doc pair — slow, can't pre-index, but far more accurate. Used for reranking the shortlist.
Bi-encoder (retriever)
Encodes query and document independently into vectors, compares with cosine. Documents embed once, offline. Cheap at query time → search millions. Less accurate because it never sees the pair together.
Cross-encoder (reranker)
Feeds query + document as one input through the model, outputs a single relevance score. Sees every word interaction → much more accurate. But nothing can be precomputed, so you only run it on a small shortlist.
Never rerank the whole corpus gotcha

A cross-encoder scores one query–doc pair at a time and can't be pre-indexed. Running it over a million documents per query would take minutes and cost a fortune. That's the whole reason for two stages: a fast bi-encoder narrows millions to ~50, then the cross-encoder reranks just those. Use the right tool at each stage.

05  Fixing the query, not just the index NEW

Sometimes retrieval fails because the question is a poor search query — too short, too vague, or phrased unlike the documents. Two cheap, popular techniques rewrite the query before searching:

Query rewriting / expansion
Use an LLM to clean up or expand the query — fix typos, add synonyms, or split a compound question into several focused sub-queries you retrieve for separately. Especially helps conversational follow-ups (“and the second one?” → a standalone query).
HyDE (Hypothetical Document Embeddings)
Ask the LLM to draft a fake answer to the question, then embed that and search with it. The hypothetical answer “looks like” a real document, so it often lands closer to the right chunks than the bare question does — even though the draft itself may be wrong.
HyDE: describe what you're looking for analogy

It's like searching for a song by humming a few bars instead of typing one word. The hum (a hypothetical answer) carries far more of the “shape” of the target than a terse keyword — so even an imperfect hum gets you to the right shelf.

06  The default recommendation & the classic question

Put it together and you get the answer interviewers want for “your RAG retrieval is bad — what do you try first?” Work cheap-to-expensive, and measure after each change:

  1. Check the data & chunking first. Is the answer even in your index? Are chunks a sane size? (Cheapest fix of all.)
  2. Add hybrid search (dense + BM25, fused with RRF). Catches the exact-term misses dense search alone makes.
  3. Add a reranker (cross-encoder over the top ~50). Usually the biggest single jump in answer quality.
  4. Then query-side tricks — rewriting/expansion or HyDE — if specific query types still miss.
How to say it out loud say it

“First I'd confirm the answer is actually in the index and sanity-check chunking — most ‘bad retrieval’ is a data problem. Then the two highest-leverage upgrades: hybrid search, dense plus BM25 fused with RRF so I don't miss exact terms, and a cross-encoder reranker over the top ~50, which is usually the single biggest quality win. If specific queries still miss, I'd add query rewriting or HyDE. My default starting architecture for production RAG is hybrid plus a reranker.”

07  Self-check

Why can't you just use a cross-encoder for the whole retrieval step and skip the bi-encoder?
Cross-encoders are more accurate, but they fuse query and document in one forward pass — nothing can be precomputed. That's fine for reranking ~50 candidates, ruinous for millions. So a fast bi-encoder retrieves wide, then the cross-encoder reranks the shortlist.
“What is hybrid search and why do you need it?”Core
Model answer

Combining dense (embedding) search with sparse keyword search like BM25, then fusing the two ranked lists — usually with Reciprocal Rank Fusion. You need it because dense search misses exact terms (error codes, SKUs, names, acronyms) while BM25 misses paraphrases and synonyms. Together they cover each other's blind spots, and RRF merges them on rank without needing score normalisation.

How to say it out loud say it

“Dense matches meaning, BM25 matches exact terms — each is blind where the other shines. Hybrid runs both and fuses with RRF, which merges on rank so I don't have to normalise incomparable scores.”

“What does a reranker do, and when would you add one?”Core
Model answer

A reranker is a cross-encoder that re-scores the top candidates from first-stage retrieval by reading each query–document pair together, then keeps the best few for the LLM. I'd add one whenever first-stage retrieval returns roughly-relevant but mis-ordered results — it's typically the single biggest quality improvement in a RAG pipeline, at the cost of a bit of latency on the shortlist.

How to say it out loud say it

“Retrieve wide with a fast bi-encoder, then rerank the top ~50 with a cross-encoder that reads query and doc together. It reorders for true relevance and is usually the biggest single win — I just keep it to a shortlist for latency.”
