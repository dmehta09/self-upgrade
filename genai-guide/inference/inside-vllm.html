Inside vLLM: PagedAttention & continuous batching IV NEW

The previous two lessons gave you the ideas — the KV cache that eats memory, and the batching tricks that keep a GPU busy. This page walks through how a real engine composes them, end to end: blocks, block tables, copy-on-write, and the scheduler loop that decides whose token gets made next. We use vLLM as the worked example because it made these mechanics famous, but every serious engine in 2026 plays some variant of this game.

01  The asymmetry everything is built on

Sharpen the two-phase picture before going inside. Prefill processes the whole prompt in one parallel pass — thousands of tokens' worth of matrix math at once — so it saturates the GPU's FLOPs: it is compute-bound. Decode produces one token per step, and to make that single token it must re-read the entire KV cache (plus weights) out of GPU memory — barely any math, mountains of byte traffic: it is memory-bandwidth-bound. Same model, same GPU, opposite bottlenecks.

This one asymmetry explains both neighbours of this page: the serving-engines lesson is about its scheduling consequences (chunked prefill, disaggregation), and the KV-cache lesson is about its memory consequences (the cache decode keeps re-reading). It also assigns an owner to every metric you'll be asked about:

TTFT
Time to first token — how long until the answer starts. Driven by prefill speed (and any queueing before it).
TPOT / ITL
Time per output token / inter-token latency — the pace of the stream once it starts. Driven by decode speed, i.e. memory bandwidth and how much KV must be re-read per step.
Throughput / goodput
Total tokens per second across all users — and goodput, the stricter version: only requests that also met their latency targets count. Driven by how many requests share the GPU at once, which is exactly what KV-memory management decides.

Keep that last line in mind: the rest of this page is one long answer to “how do we fit more concurrent requests into the same VRAM?”

02  Blocks & block tables: PagedAttention, mechanically

The KV lesson gave you the concept — virtual memory for the cache. Here's the machinery. vLLM chops KV memory into fixed-size blocks, each holding the Keys and Values for a small run of tokens (~16 tokens per block by default). Every request owns a block table: a small array mapping its logical blocks (token 0–15 → logical block 0, tokens 16–31 → logical block 1, …) to whatever physical blocks happened to be free — exactly like an OS page table mapping virtual pages to physical frames. The physical blocks of one request can be scattered anywhere in VRAM; the attention kernel follows the table.

Generation becomes a tiny allocation protocol: appending a token means writing its K and V into the last, partially-filled block — and only when that block fills up does the engine grab one new block from the free list. No request ever holds memory for tokens it hasn't produced yet.

The fragmentation math — why this is the whole ballgame
Contiguous pre-reservation
Old engines allocated one contiguous slab per request, sized for the maximum possible length. A request capped at 2,048 tokens that stops at 250 strands ~1,800 tokens of reserved KV, and the leftover gap is the wrong shape for anyone else. Measured waste: 60–80% of KV memory doing nothing.
Paged blocks
The only waste is the unused tail of each request's last block — at most 15 tokens' worth per request. Measured waste: under ~4%.
Same GPU, same model — but now 2–4× more live requests fit in VRAM at once. Those extra requests are what continuous batching feeds on: more occupied slots per token step is the real throughput win. PagedAttention doesn't make any single request faster; it makes the batch bigger.
Hotel rooms, not whole floors analogy

Contiguous pre-reservation is a hotel that books an entire floor for every guest, because they might bring their extended family. Most rooms sit dark, and the hotel turns guests away while standing 70% empty. PagedAttention rents one room at a time as people actually show up, and the front desk's ledger — the block table — tracks which rooms belong to which party. The only vacancy left is the half-used last room of each party.

03  Block sharing & copy-on-write

Once the cache is made of blocks behind a mapping table, a second trick falls out for free: two block tables can point at the same physical block. The engine keeps a reference count per physical block, and a block is only freed when its count hits zero.

Where this pays off first is parallel sampling (asking for n>1 completions of one prompt) and beam search: every branch shares the prompt's blocks instead of duplicating them — one physical copy, n references. Branches only differ once they start generating, and even then vLLM is lazy about it: when a branch is about to write into a block that another branch still shares (ref-count > 1), it copies only that one block, redirects its own table entry to the copy, and writes there. That's copy-on-write, straight from the OS playbook — everything upstream of the divergence point stays shared forever.

Prefix caching is the same machinery wearing a different hat. If a thousand requests start with the same system prompt, their block tables can all map those leading logical blocks to one set of physical blocks already computed — prefill skips straight past them. Nothing new had to be invented: ref-counted shared blocks across branches of one request generalize to shared blocks across different requests (see prefix caching & RadixAttention for the workload-level view).

Sharing is block-granular gotcha

Only complete blocks of identical leading tokens can be shared between requests. If your "shared" system prompt ends mid-block, that last partial block mixes prefix tokens with request-specific ones and can't be reused. It's a small effect (≤15 tokens), but it's why prefix-cache hit accounting is in block multiples — and a nice detail to drop in an interview.

04  One request's life inside the engine

Now compose it. Every iteration of vLLM's core loop, the scheduler rebuilds the running batch in block-level terms:

1 · Arrive
The request lands in the waiting queue. The scheduler computes how many blocks its prompt needs (minus any prefix-cache hits).
2 · Admit
When the free list has enough blocks, the request is admitted and prefilled — possibly chunked so it doesn't stall the streams already running.
3 · Run
It joins the running batch: one decode step per iteration, each appended token written into its last partial block, a fresh block allocated only on overflow.
4 · Finish
On EOS or length cap, its private blocks return to the free list that same step — and continuous batching admits the next waiter immediately.

Under memory pressure the loop has a release valve: preemption. If the free list runs dry mid-decode, the scheduler picks a victim (typically the most recently arrived, so the oldest requests finish first), frees its blocks, and parks it. Getting the victim back has two flavors: swap its KV blocks out to CPU RAM and copy them back later, or just throw them away and recompute the prefill on re-admission. Recompute often wins — prefill is fast, parallel compute, while shuttling gigabytes over PCIe is exactly the kind of byte-moving that decode taught us to fear.

05  Where vLLM sits in 2026

Every modern engine builds on the same block-managed-KV + continuous-batching core; they differ in what they layer on top. The positioning, in one sentence each (as of June 2026):

EnginePositioning
vLLMThe engine that introduced PagedAttention and remains the default open choice — broadest model and hardware support, the mechanics on this page in their original home.
SGLangRadixAttention generalizes prefix reuse from "one cached system prompt" to a whole tree of shared prefixes, matched automatically — strongest when chats branch and agents loop.
TensorRT-LLMNVIDIA's own engine with hand-tuned kernels and aggressive low-precision paths — peak performance on NVIDIA hardware, at the cost of flexibility and build complexity.
TGIHugging Face's server, valued less for raw speed than for tight integration with the HF ecosystem — Hub models, tokenizers, and deployment tooling out of the box.
How to say it out loud say it

“vLLM's throughput comes from two ideas composed. PagedAttention chops the KV cache into fixed-size blocks with a per-request block table — like OS paging — which cuts KV memory waste from 60–80% down to under 4%, so far more concurrent requests fit in the same VRAM. Continuous batching then reschedules after every token step so those extra requests keep every slot busy, while ref-counted block sharing with copy-on-write makes shared prefixes and parallel sampling nearly free.”

06  Self-check

PagedAttention doesn't make any single request decode faster. So where does its big throughput gain actually come from?
Contiguous max-length reservations strand most of their memory (the request usually stops early, and the leftover gap is unusable). Block-granular allocation wastes only the tail of each request's last partial block. The freed memory admits more concurrent requests, and continuous batching keeps them all streaming — bigger batch, same hardware. The kernel itself does the same attention math; per-request speed is unchanged.
A beam-search branch sharing its prompt's KV blocks is about to diverge from its sibling. What does copy-on-write copy?
Sharing is per-block with reference counts. A write into a block whose ref-count is above 1 triggers a copy of just that one block; the writer's block-table entry is redirected to the copy. All earlier blocks — the whole shared prompt — remain one physical copy. Writing into shared blocks directly would corrupt the sibling's cache; copying everything would erase the memory savings.
vLLM preempts a request mid-decode and must restore it later. Why is recompute often preferred over swapping the KV blocks to CPU?
Both produce an identical cache; swap is perfectly possible and engines support it. It's an economics call: prefill saturates the GPU's abundant FLOPs and finishes quickly, whereas a swap spends scarce interconnect bandwidth twice (out and back). When compute is cheap relative to moving bytes — the usual case — throwing the blocks away and recomputing wins.
