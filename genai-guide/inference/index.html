Inference & serving · overview

Inference — overview IV NEW

Training is how a model is made; inference is every time you actually use it — prompt in, tokens out. Training happens once and lives in a research budget; inference happens millions of times a day and lives in your latency graphs and your cloud bill. This module is about the engineering that makes generation fast and cheap: the KV cache, serving engines, speculative decoding, and quantization. Start here for the map and the metrics.

01  Why serving an LLM is its own discipline

You'd think that once a model is trained, running it is the easy part — just multiply some matrices. But inference has a brutal twist: a chat model generates text one token at a time, and each new token needs the model to look back at everything generated so far. So a single reply isn't one forward pass; it's hundreds of them, in a strict sequence, each waiting on the last. Doing that fast, for thousands of users at once, on hardware that costs dollars a minute, is a whole engineering field.

A great chef vs running the whole restaurant analogy

Training gives you a brilliant chef — one who has learned to cook anything. But a hungry dinner rush needs more than talent: you need the chef plating dozens of orders at once, a kitchen that doesn't re-chop the same onion for every dish, tickets batched smartly, and a line that never stalls. Inference and serving is running the restaurant — turning one capable model into fast, cheap answers for a crowd. The rest of this module is the kitchen's tricks.

The recurring theme you'll see on every page: inference is usually memory-bandwidth bound, not compute bound. The GPU isn't struggling to do the math — it's struggling to shuttle the model's weights and the growing KV cache in and out of memory fast enough. Almost every optimization here is, at heart, a way to move less data.

02  Two phases: prefill, then decode NEW

Every LLM request runs in two very different phases, and knowing which is which explains almost all of inference performance.

One request = a big parallel read, then a long one-at-a-time write

Prefill processes the whole prompt in one parallel pass — compute-heavy, but fast because it's parallel. Decode then generates the answer one token per step, each step a separate (smaller) pass that must wait for the previous — memory-bound and inherently sequential.
Prefill (prompt processing)
All your input tokens go through the model together, in parallel. This is compute-bound and it builds the KV cache. Its length sets how long you wait for the first token.
Decode (generation)
The model emits one token, appends it, and runs again — over and over. This is memory-bandwidth-bound and sequential. Its speed sets how fast the rest of the answer streams out.
Why split them?
They stress the hardware differently, so modern engines schedule them differently — even running them on separate GPUs (prefill/decode disaggregation, covered in serving engines).

03  The three latency numbers that matter IV

If an interviewer asks "how do you measure LLM inference performance?", these are the words they want. Two are about your wait; one is about the fleet's efficiency.

MetricWhat it measuresDriven byYou feel it as…
TTFT
time to first token		From request sent to the first token appearingPrefill (prompt length), queueing"How long until it starts answering?"
TPOT / ITL
time per output token / inter-token latency		The gap between each subsequent tokenDecode speed, memory bandwidth, batch sizeHow fast the text streams
ThroughputTotal tokens/sec across all concurrent usersBatching, GPU utilizationCost per token (the fleet's efficiency)

A useful identity: total response time ≈ TTFT + (TPOT × number of output tokens). So a chatty 800-token answer is dominated by TPOT, while a one-line answer to a huge document is dominated by TTFT.

Throughput and latency pull in opposite directions gotcha

The instinct "just make it faster" hides a real trade-off. Packing more requests into one batch raises throughput (cheaper per token) but each user's TPOT gets a little slower, because the GPU is splitting attention more ways. A latency-sensitive voice app and a cost-sensitive batch job want opposite settings on the same engine. Always ask which you're optimizing before quoting a number.

04  Why inference, not training, is the real bill

Training a frontier model is a giant one-time cost. But a popular model is queried billions of times over its life — so summed up, inference usually dwarfs training in total spend. That's why a few percent of inference efficiency is worth enormous engineering effort, and why this whole module exists. Every optimization here maps to one of two goals:

Make each user happier
Lower TTFT and TPOT → snappier, more responsive feel. Tools: KV-cache tricks, speculative decoding, prefix caching.
Make the fleet cheaper
Higher throughput per GPU → lower cost per token. Tools: continuous batching, quantization, smarter scheduling.

The production-side dollars-and-cents view (caching, routing, tiering) lives in the Productionization module; here we stay close to the engine.

How to say it out loud say it

“LLM inference has two phases: a parallel prefill of the prompt that builds the KV cache and sets time-to-first-token, then a sequential decode that emits one token at a time and sets the per-token latency. Decode is memory-bandwidth-bound, so most optimizations — the KV cache, batching, quantization, speculative decoding — are really about moving less data per token or serving more users per GPU. And there's a core tension: bigger batches raise throughput but hurt each user's latency.”

06  Self-check

A user complains your chatbot "takes forever to start replying" on long documents, but once it starts, it's fast. Which metric is the problem?
"Slow to start, then fine" is the signature of high TTFT. A long document means a long prefill phase (processing thousands of input tokens) before the first output token appears. Once decode begins, low TPOT keeps the stream fast. Throughput is a fleet-level cost metric, not what one user perceives as startup lag.
“What's the difference between prefill and decode?”Warm-up
Model answer

Prefill processes the entire prompt in one parallel forward pass, building the KV cache and producing the first token — it's compute-bound and its length drives time-to-first-token. Decode then generates the answer one token at a time, each step a small pass that reads the cache and depends on the previous token — it's sequential and memory-bandwidth-bound, and it drives per-token latency. Same model, two very different performance profiles.

How to say it out loud say it

“Prefill reads the whole prompt in parallel and sets TTFT; decode writes the answer one token at a time and sets per-token latency. Prefill is compute-bound, decode is memory-bound.”

“Why does inference often cost more than training over a model's lifetime?”Core
Model answer

Training is a single, large, upfront cost. Inference is paid every single time the model is used — and a popular model serves billions of requests over its life. Summed up, that recurring cost typically exceeds the one-time training cost, which is exactly why squeezing a few percent out of inference (via batching, quantization, caching) is worth so much engineering effort.

How to say it out loud say it

“Training is one-time; inference is per-request and runs forever. At scale the recurring inference bill dominates, so inference efficiency is where the money is.”
