Speculative decoding IV NEW

Decode is slow because it's sequential — one token at a time, each waiting on the last. Speculative decoding is a brilliant cheat that breaks the chain: a small, fast model guesses several tokens ahead, and the big, slow model checks all the guesses in a single pass. When the guesses are good, you get multiple tokens for the price of one big forward pass — and, crucially, the output is identical to what the big model would have produced alone.

01  The bottleneck it attacks

From the KV cache page: decode is memory-bandwidth-bound. Each step, the GPU drags the model's weights out of memory just to produce one token, then does it again. The expensive part is loading the weights; the actual math for one token barely taxes the GPU. So here's the key insight: checking five candidate tokens in one pass costs almost the same as generating one, because you load the weights once either way. If you could somehow know the next few tokens in advance, you could verify them all together and skip several slow steps.

An intern drafts, the expert checks in bulk analogy

A senior lawyer bills a fortune per hour, so you don't want them writing every word. Instead a junior drafts the next few sentences quickly and cheaply, then the senior reads the whole draft at once and either signs off or strikes through from the first mistake onward. If the junior is decent, the senior approves most of it in a single glance — far faster than dictating every word personally, and the final document is exactly what the senior would have written.

02  Draft → verify → accept NEW

The core loop has three beats. A small draft model proposes k tokens; the big target model verifies them all in one parallel pass; you keep the longest correct prefix and discard the rest.

Say the draft guesses 5 tokens and the target agrees with the first 3 — you commit 3 tokens (plus 1 the target generates at the mismatch = 4) from a single big-model pass, instead of 4 separate passes. Then the loop repeats from the new position.

The win scales with how often the draft is right. A good draft that gets ~3 tokens accepted per pass roughly triples decode speed; a draft that's usually wrong wastes its proposals and you fall back to near-normal speed. Either way you never go far backwards, because verification is cheap relative to the weight-loading you'd do anyway.

03  Why it's lossless IV

This is the part interviewers love, because it's counterintuitive: speculative decoding changes speed, not output. The draft model never decides the final answer — it only proposes. The target model's verification uses a rejection-sampling rule that accepts or rejects each proposed token so that the final distribution is mathematically identical to sampling from the target model alone. A wrong guess is simply rejected and replaced by the target's own token.

"A weaker draft model must lower quality" — no gotcha

A natural worry: if a tiny model is drafting, won't the answers get dumber? No. The draft only suggests; every token is ratified by the big model, and rejected guesses are overwritten. A poor draft model hurts your speed-up (low acceptance rate, more rejected guesses) but never your quality. Don't confuse speculative decoding with quantization or distillation, which do trade quality for size — speculative decoding is exact.

04  Flavours of "who does the drafting" NEW

The draft can come from several places. They all share the draft-verify-accept loop; they differ in where the guesses originate and what you have to ship.

VariantWhere guesses come fromNote
Draft-modelA separate small model from the same familyThe classic form; needs a second model in memory
Self-speculativeThe big model itself, with some layers skipped, acts as its own drafterNo second model to host
Medusa / EAGLE-styleExtra lightweight "heads" bolted onto the target predict several future tokensTrained add-ons; high acceptance, popular in 2025–26
N-gram / prompt lookupNo model at all — copy likely continuations from the prompt/context itselfFree; shines when output echoes the input (summaries, code edits, RAG)

The n-gram trick is worth remembering for interviews: when the answer largely repeats text already in the context — editing a code file, quoting a retrieved passage — you can "draft" by simply looking up what came next last time, with zero extra model. EAGLE-style trained heads are the current sweet spot for general chat because they push acceptance rates high without a full second model.

05  The acceptance-rate trade-off

The whole technique lives or dies on acceptance rate — the fraction of proposed tokens the target ratifies. It's a balancing act on two dials:

Bigger / smarter draft
Higher acceptance (more tokens kept per pass) but each draft step costs more — past a point the draft itself becomes the bottleneck.
More tokens proposed (k)
More potential tokens per pass, but lower marginal acceptance (later guesses are likelier wrong) and more wasted compute on rejects.
Domain match
Acceptance is high on predictable text (boilerplate, code, structured output) and lower on surprising, knowledge-dense prose. Speculative gains vary by workload.
Batch interaction
At very high batch sizes the GPU is already busy, so spare verification capacity shrinks and the speed-up can fade — it helps most at low-to-medium load.
How to say it out loud say it

“Speculative decoding speeds up decode by having a small draft model propose several tokens that the big target model verifies in one parallel pass — and since decode is memory-bandwidth-bound, checking many tokens costs about the same as generating one. It's lossless: a rejection-sampling rule guarantees the output distribution matches the target model exactly, so a weak draft only lowers the speed-up, never the quality. Variants include a separate draft model, self-speculative layer-skipping, EAGLE/Medusa trained heads, and free n-gram lookup from the prompt. The lever is the acceptance rate — how often the target ratifies the guesses.”

06  Self-check

Your colleague worries that adding a tiny draft model for speculative decoding will make answers lower quality. What's the correct response?
Speculative decoding is exact. The draft only proposes tokens; the target model verifies them with a rejection-sampling rule that preserves its own output distribution, and any rejected guess is overwritten by the target's token. So a poor draft model lowers the acceptance rate (less speed-up) but never changes what the model would have said. This is unlike quantization or distillation, which genuinely trade quality for size.
“Explain speculative decoding and why it's faster.”Core
Model answer

A small draft model proposes the next k tokens cheaply; the big target model verifies all k in a single parallel forward pass and accepts the longest correct prefix, then supplies the next token at the first mismatch. It's faster because decode is memory-bandwidth-bound — loading the big model's weights dominates, and verifying several tokens in one pass costs about the same as generating one. So when the draft is right, you commit multiple tokens per expensive pass instead of one. And it's lossless: rejection sampling keeps the output identical to the target alone.

How to say it out loud say it

“Draft proposes k tokens, target verifies them in one pass and keeps the matching prefix. It's faster because verifying many tokens is as cheap as generating one when you're memory-bound — and it's lossless.”

“When would n-gram / prompt-lookup speculation beat a draft model?”Stretch
Model answer

When the output heavily reuses text already in the context — editing or refactoring a code file, summarizing while quoting, or RAG answers that echo retrieved passages. There, the "next tokens" are literally sitting in the prompt, so you can propose them by lookup with no second model to host and no draft compute. Acceptance is high precisely because the continuation is copied. For free-form, knowledge-dense generation with little overlap with the prompt, a trained draft (or EAGLE-style heads) wins instead.

How to say it out loud say it

“When the answer copies the context — code edits, quoting, RAG — n-gram lookup proposes the next tokens for free, no draft model needed. For novel prose, a trained draft or EAGLE heads do better.”
