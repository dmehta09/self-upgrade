Inference & serving · the KV cache

The KV cache IV NEW

If you remember one idea from this whole module, make it this one. To generate each new token, a transformer has to attend back over every earlier token. Recomputing all of that, every single step, would be hopelessly slow — so we cache the per-token Keys and Values and reuse them. That cache is the reason generation is fast; it's also, at long context, the thing that eats your GPU memory alive. Nearly every serving trick you'll meet is a way to make the KV cache smaller or cheaper.

01  The "redo everything" problem

Recall from attention that each token produces three vectors: a Query (what am I looking for?), a Key (what do I offer?), and a Value (what do I pass on?). To compute attention for the newest token, its Query is compared against the Keys of all previous tokens, and the matching Values are blended in. Here's the catch: those earlier Keys and Values don't change as you generate. Token 500's Key is the same whether you're producing token 501 or token 900.

Don't re-read the whole book for each new word analogy

Imagine writing a summary of a long book, one word at a time. The naive way: before writing each word, you re-read the entire book from page one. Absurd — you'd never finish. The sane way: you take notes as you read, then for each new word you just glance at your notes. The KV cache is those notes. The Keys and Values of every token you've already seen are written down once and reused for every future token, so you never re-read the book.

So the deal is: compute each token's Key and Value exactly once, store them, and reuse them for the rest of the generation. Without the cache, generating n tokens costs work that grows with n²; with it, each step only does the work for the one new token. This is the difference between "usable" and "unusably slow."

02  Why it gets huge: sequence × layers × heads

The cache isn't one little notepad — it's a separate set of Keys and Values for every token, in every layer, for every KV head. Stack those dimensions up and the memory adds fast:

What the KV cache stores
× sequence length
One K and one V entry per token in the context — and it grows with every token generated. A 100k-token conversation has 100k slots.
× number of layers
The cache exists independently in each transformer block. A 64-layer model stores 64 copies' worth.
× number of KV heads
Each attention head keeps its own K and V (this is the dimension GQA and MLA attack).
× 2, × bytes per number
Two tensors (K and V), each number taking 2 bytes in FP16/BF16 (or 1 byte if you quantize the cache).
Multiply it all out and a long-context request can need tens of gigabytes of KV cache — often more memory than the model's own weights. And it's per-request: 50 simultaneous long chats need 50 of these.

The crucial property: KV-cache memory scales linearly with context length and with the number of concurrent users. Model weights are a fixed cost you pay once; the KV cache is a per-request, per-token cost that balloons exactly when your product gets popular and your contexts get long. That's why, in 2026, KV-cache management is the heart of LLM serving.

It's not the math that's slow — it's the memory traffic gotcha

During decode the GPU is mostly idle on compute and bottlenecked on memory bandwidth: every step it must read the entire KV cache (plus the relevant weights) out of memory just to produce one token. That's why a bigger cache directly means slower per-token generation, and why shrinking the cache is one of the most effective speed-ups. "Add more FLOPs" rarely helps; "move fewer bytes" almost always does.

03  PagedAttention: virtual memory for the cache NEW

Early serving systems allocated the KV cache as one big contiguous block per request, sized for the maximum possible length. That wasted enormous memory: a request that might generate 4,000 tokens but stops at 200 still held the whole reservation, and the leftover gaps couldn't be reused. The fix, introduced by vLLM, borrows a 50-year-old operating-system idea.

Paging — like an OS managing RAM analogy

Your operating system doesn't hand each program one giant contiguous slab of RAM. It chops memory into fixed-size pages and hands them out on demand, tracking which page belongs to whom in a table. PagedAttention does the same for the KV cache: it splits GPU memory into small fixed-size blocks and gives each request only the blocks it actually fills, growing block-by-block as the answer lengthens. No giant reservations, almost no wasted gaps.

The payoff is dramatic: memory fragmentation drops from "most of it wasted" to near-zero, so the same GPU can hold many more concurrent requests — which is exactly what raises throughput. As a bonus, because the cache is now made of shareable blocks, two requests can point at the same physical blocks when their text overlaps — which leads straight to the next idea.

04  Prefix caching & RadixAttention: reuse shared starts NEW

Tons of real requests begin with the same tokens: a long shared system prompt, a few-shot example block, a document everyone asks questions about, or the growing history of one chat. With paged blocks, there's no reason to recompute that shared prefix's KV entries over and over.

Prefix caching
Keep the KV cache for a common prefix (e.g. your system prompt) and reuse it across requests instead of recomputing it. The prefill phase skips straight past the cached part — a big TTFT win when prompts share a heavy preamble.
RadixAttention (SGLang)
Generalises this: store all cached prefixes in a radix tree (a prefix tree) so any shared beginning — not just one fixed system prompt — is matched and reused automatically. Branching chats, tree-of-thought, and multi-turn sessions all share their common ancestors.

Concretely: if 1,000 users hit the same 2,000-token system prompt, prefix caching computes that prefill once and reuses it 1,000 times. That's why prefix/prompt caching is now a standard feature — both in open engines and in commercial APIs, where cached input tokens are billed at a steep discount. (Exact discounts vary by provider, as of June 2026.)

05  Shrinking the cache at the source: GQA & MLA

PagedAttention and prefix caching manage the cache cleverly; GQA and MLA make it smaller to begin with, by attacking the "× number of KV heads" factor from section 02. These are architecture choices (covered in Transformer architecture) but they're really KV-cache shrinkers, so they belong in this conversation.

TechniqueWhat it does to the cacheTrade-off
MHA (multi-head)One full K/V per query head — the baseline, biggest cacheTop quality, heaviest memory
GQA (grouped-query)Many query heads share a few K/V heads → cache shrinks several-foldNear-MHA quality; the 2026 default
MQA (multi-query)One K/V head for all queries → smallest of theseCheapest, slight quality cost
MLA (multi-head latent)Stores K/V compressed into a small latent, expands on the flyDramatically smaller cache at long context (DeepSeek line)
KV quantizationStores each cached number in 8 or 4 bits instead of 162–4× smaller cache; tiny quality risk (see quantization)

These stack with each other and with PagedAttention. A modern long-context model typically combines GQA (or MLA), paged allocation, and prefix caching — that's how a single GPU serves many users at 100k+ context without falling over.

06  "What is the KV cache, and why does it dominate memory?"

This is one of the most common inference interview questions. Here's the clean, complete answer in plain terms:

What it is
A store of the Keys and Values that every past token produced, kept so the model can attend back without recomputing them each step.
Why it exists
Generation is one-token-at-a-time and each token attends to all previous tokens; caching turns O(n²) recompute into O(n) reuse.
Why it dominates memory
Its size is sequence × layers × KV-heads × 2 × bytes, growing linearly with context length and with the number of concurrent requests — so at long context it often exceeds the model weights themselves.
Why it dominates speed too
Decode is memory-bandwidth-bound: each step must read the whole cache from memory, so a bigger cache means slower tokens.
How to say it out loud say it

“The KV cache stores the Keys and Values of every previous token so we don't recompute them at each decode step — it turns quadratic recompute into linear reuse. But it scales with sequence length, layers, KV heads, and the number of concurrent requests, so at long context it can use more memory than the model weights and it bottlenecks bandwidth. We manage it with PagedAttention — virtual-memory-style paging to kill fragmentation — and prefix caching or RadixAttention to reuse shared prompts, and we shrink it at the source with GQA, MLA, or KV quantization.”

07  Self-check

What problem does PagedAttention primarily solve?
PagedAttention applies operating-system-style paging to the KV cache: instead of reserving one big contiguous block per request (which wastes memory on unused capacity and gaps), it hands out small fixed-size blocks as the sequence grows. Near-zero fragmentation lets many more requests fit on a GPU, raising throughput — and the shareable blocks also enable prefix reuse.
“Why does the KV cache grow with context length, and why is that a problem?”Core
Model answer

Because we store one Key and one Value per token, per layer, per KV head — so every additional token in the context adds another full slice of cache. It's a problem on two fronts: memory, because the cache grows linearly with length and with concurrent users until it can exceed the model weights; and speed, because decode is memory-bandwidth-bound and every step must read the whole cache. So long context plus many users is precisely where serving falls over, which is why we page it, share prefixes, and shrink it with GQA/MLA or KV quantization.

How to say it out loud say it

“It stores K and V per token per layer per head, so it grows linearly with context and with users — eventually past the weight size — and since decode is bandwidth-bound, a bigger cache means slower tokens.”

“When does prefix caching actually help, and when doesn't it?”Core
Model answer

It helps whenever many requests share the same leading tokens — a big shared system prompt, fixed few-shot examples, a document everyone queries, or the unchanged history of a multi-turn chat. You compute that prefix's KV once and reuse it, cutting prefill work and TTFT. It does nothing for the unique parts of each prompt, and gives little benefit if every request is short and totally distinct. RadixAttention extends it to match any shared prefix automatically via a prefix tree, not just one fixed preamble.

How to say it out loud say it

“It reuses the KV of shared leading tokens — system prompts, few-shot blocks, chat history — to skip prefill and cut TTFT. It does nothing for the unique tail of each prompt. RadixAttention generalises it to any shared prefix via a tree.”
