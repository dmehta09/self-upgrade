Inference & serving · serving engines

Serving engines IV NEW

A trained model is just a pile of weights. A serving engine is the software that wraps it into a fast, multi-user service — scheduling thousands of requests onto a GPU, managing the KV cache, and squeezing out throughput without wrecking latency. The single idea that changed everything here is continuous batching; the rest of this page builds on it, then maps the 2026 engine landscape.

01  Static vs continuous batching NEW

GPUs love doing the same work on many items at once — that's batching. The naive approach, static batching, gathers a fixed group of requests, runs them together until all of them finish, then starts the next group. The problem: requests finish at wildly different times (one wants 10 tokens, another wants 800), so the short ones sit idle waiting for the long one, and the GPU wastes huge stretches of time.

Static batching wastes the gaps; continuous batching fills them
static
finish together
short requests idle until the longest one ends, then the whole batch swaps
continuous
swap per step
a finished request leaves immediately; a waiting one takes its slot on the very next token step
Continuous batching (a.k.a. in-flight or iteration-level batching) reschedules the batch after every token step, not every request. Done slots are freed instantly and refilled, so the GPU stays busy. This is the headline throughput win of modern engines.
A shared taxi vs a bus that waits for everyone analogy

Static batching is a tour bus that won't leave a stop until every passenger from the last stop has been dropped off — even if most got off early, the bus idles. Continuous batching is a shared taxi that, the instant a passenger reaches their destination, immediately picks up someone from the waiting line for that now-empty seat. Same vehicle, far less idle time, many more riders per hour.

02  Chunked prefill: stop letting long prompts stall everyone NEW

Recall the two phases from the overview: a big parallel prefill, then one-token-at-a-time decode. When a new request arrives with a 50k-token prompt, its prefill is a giant compute chunk. If the scheduler runs it all in one go, every other user's decode freezes for that whole time — their token stream visibly stutters.

Chunked prefill fixes this by slicing a long prefill into smaller pieces and interleaving them with ongoing decode steps. Each scheduler iteration does a bit of the newcomer's prefill plus a token for everyone already streaming. The newcomer's TTFT goes up slightly, but nobody else's stream stalls — far smoother tail latency across all users.

Prefill and decode fight over the same GPU gotcha

A common mistake is thinking the engine just "runs requests." In reality the scheduler is constantly refereeing a fight: compute-hungry prefills want to monopolize the GPU, while latency-sensitive decodes need a steady drip of attention. Chunked prefill and (next) disaggregation exist precisely because these two phases have opposite appetites and will starve each other if you let them.

03  Prefill/decode disaggregation NEW

If prefill and decode have opposite needs, why force them onto the same hardware at all? Disaggregation (a.k.a. P/D disaggregation) splits them across different GPU pools: one set of GPUs does nothing but prefill, another does nothing but decode. When a prefill finishes, its KV cache is handed off to a decode worker that streams the answer.

Why bother
Each pool can be tuned and scaled for its job: prefill nodes optimize for raw compute throughput, decode nodes for memory bandwidth and steady low TPOT. No more interference between the phases.
The cost
You have to ship the KV cache between machines, which needs fast interconnect — so it's a large-scale technique, not something a single-GPU setup needs. It became a mainstream serving pattern through 2025–26 for big deployments.

Mental model: chunked prefill shares one GPU politely; disaggregation separates the work onto specialised GPUs. Big fleets often use both.

04  The engine landscape IV

You don't write a serving engine — you pick one. Here's the 2026 lay of the land. Names and rankings churn, so treat this as "(as of June 2026)."

The split that matters for interviews: vLLM / SGLang / TensorRT-LLM are server-side engines for serving many users on GPUs, while Ollama and llama.cpp are local-first for single-user, on-device use (paired with GGUF quantization). Managed cloud APIs run engines like these for you behind the scenes.

05  The throughput-vs-latency knobs

Whatever engine you pick, you tune the same fundamental dials, and they all trade the two goals from the overview against each other:

Max batch size / concurrency
Higher → more throughput (cheaper per token) but higher per-user TPOT. Lower → snappier individual responses, fewer users per GPU.
Max sequence length
Caps how much KV cache one request can claim — protects against a single giant context starving everyone.
Chunked-prefill chunk size
Smaller chunks → smoother decode for others but slightly higher prefill latency for the newcomer.
Quantization level
Lower precision weights/cache → more requests fit per GPU (covered in quantization).
How to say it out loud say it

“A serving engine turns model weights into a multi-user service. The big win is continuous batching — rescheduling the batch every token step so finished requests free their slot immediately, instead of static batching where short requests wait on the longest. On top of that, chunked prefill slices long prompts so they don't stall everyone's decode, and prefill/decode disaggregation splits the two phases onto separate GPU pools. In 2026 vLLM is the most adopted default, SGLang adds RadixAttention prefix reuse, TensorRT-LLM is fastest on NVIDIA with FP8/FP4, and Ollama or llama.cpp run quantized models locally.”

06  Self-check

Why is continuous batching a big deal compared to static batching?
With static batching, requests in a batch must all finish before the GPU moves on, so short requests idle while the longest one runs — wasting GPU time. Continuous (iteration-level) batching swaps requests in and out after every token step: done requests leave instantly and waiting ones take their place, dramatically raising throughput. It doesn't speed up a single request's per-token rate; it eliminates the idle gaps across many requests.
“Which serving engine would you pick, and why?”Core
Model answer

It depends on the deployment. For general GPU serving I'd default to vLLM — most adopted, broad support, PagedAttention built in. If my traffic has heavy shared prefixes (big system prompts, few-shot, agentic multi-turn), SGLang's RadixAttention reuses those prefixes automatically. If I'm locked to NVIDIA and want peak performance with FP8/FP4, TensorRT-LLM is typically fastest, at the cost of build complexity. And for local or on-device, llama.cpp/Ollama with a GGUF model needs no cluster. (All as of June 2026 — the landscape moves fast.)

How to say it out loud say it

“vLLM as the default; SGLang when prefixes are shared; TensorRT-LLM for peak NVIDIA performance with FP8/FP4; llama.cpp/Ollama for local. It's a fit-to-workload choice, not a single winner.”

“What is chunked prefill and what problem does it solve?”Core
Model answer

It slices a long prompt's prefill into smaller chunks and interleaves them with the ongoing decode steps of other requests. The problem it solves: without it, one giant prompt's prefill monopolizes the GPU and freezes everyone else's token stream — a visible stutter. With it, each scheduler iteration does a slice of prefill plus a token for the active streams, so the big request's TTFT rises a little but no one else stalls. It's one of the tools that lets prefill and decode coexist on the same GPU.
