Inference & serving · quantization

Quantization for inference IV NEW

A model's weights are billions of numbers. Store each one in 16 bits and a big model needs more memory than your GPU has. Quantization stores those numbers in fewer bits — 8, 4, sometimes fewer — so the model gets smaller and faster, at the cost of a little precision. It's how a model that "wouldn't fit" suddenly runs on one GPU, or even your laptop. The art is shedding bits where the model won't miss them.

01  The big idea: lossy compression for weights

Each weight is normally a high-precision floating-point number. But most of those decimal places barely affect the output — a weight of 0.4172 behaves almost exactly like 0.42. Quantization rounds the numbers onto a coarser grid and stores the small integer index instead of the full float. Fewer bits per weight means a smaller file, less memory traffic, and faster inference (remember: decode is memory-bandwidth-bound, so moving fewer bytes directly speeds it up).

JPEG for model weights analogy

A raw photo is huge; a JPEG throws away detail your eye won't notice and gets 10× smaller while still looking great — until you crank compression too hard and it turns blocky. Quantization is JPEG for a neural network: drop the precision your output won't notice and the model shrinks dramatically with barely any quality loss. Push it too far (too few bits) and, like an over-compressed image, it starts to degrade.

This page is about quantizing an LLM's weights for generation. Quantizing embedding vectors for search is a related-but-separate topic, covered in Embeddings & vectors → quantization & scale.

02  The precision ladder NEW

Precision is measured in bits per number. Here's the ladder you'll hear named, from roomy to tiny:

PrecisionBitsWhere it's used
FP16 / BF1616The "full-precision" baseline for serving; what most models ship in
FP88Mainstream on modern NVIDIA GPUs; ~2× smaller, minimal quality loss — a 2026 default for clusters
FP44Newest frontier (latest NVIDIA hardware); ~4× smaller, with care to preserve quality
INT88Integer, hardware-friendly everywhere; common for weight quantization
INT44Aggressive; the workhorse for fitting big models on small GPUs / laptops

Two families to keep straight: FP (floating point — FP16/FP8/FP4) keeps a tiny exponent so it handles a wide range of magnitudes gracefully; INT (integer — INT8/INT4) is simpler and ubiquitous but needs scaling tricks to cover outliers. Each rung roughly halves memory versus the one above it. Below 4 bits, quality usually starts to suffer noticeably.

03  GPTQ vs AWQ vs GGUF IV NEW

These three names dominate open-model quantization, and interviewers love asking you to compare them. The trap is thinking they're rivals doing the same thing — they're not quite. GPTQ and AWQ are methods for choosing how to round weights well; GGUF is a file format for packaging a quantized model.

GPTQ
A post-training method that quantizes weights layer-by-layer using a small calibration dataset, adjusting to minimize the error each rounding introduces. Mature, GPU-oriented, widely supported.
AWQ (Activation-aware Weight Quantization)
Notices that a few weight channels matter far more (they see large activations) and protects those while squeezing the rest. Often better quality at 4-bit and fast on GPU — a common pairing with vLLM.
GGUF
Not a method but the file format used by llama.cpp/Ollama for local inference. It bundles the quantized weights with everything needed to run, and offers many quant levels — the popular default being Q4_K_M (a balanced 4-bit "K-quant").
GGUF isn't "another GPTQ" gotcha

The cleanest way to say it: GPTQ and AWQ answer "how do we round the weights with least damage?"; GGUF answers "what file do we ship so llama.cpp can run it on a CPU or laptop?". They live at different layers. If you say "GGUF vs AWQ" as if picking a rounding algorithm, you'll get corrected — frame it as method (GPTQ/AWQ) vs format/runtime (GGUF for local).

04  What you quantize: weights, activations, and the KV cache NEW

"Quantize the model" is vague — there are three different things you can shrink, and they have different difficulty and payoff:

Weight-only
Compress just the stored weights; expand them back to higher precision for the math. The easy, common win — big memory savings, low quality risk. GPTQ and AWQ are usually weight-only.
Weight + activation
Also quantize the live activations flowing through the model so the math itself runs in low precision (e.g. FP8 end-to-end). Faster compute, but harder — activations have outliers that can wreck quality if mishandled.
KV-cache quantization
Store the KV cache in 8 or 4 bits instead of 16. Since the cache often out-weighs the model at long context, this is a big lever for fitting longer contexts and more users — a small, manageable quality risk.

For interviews: weight-only is the default ask; mentioning KV-cache quantization shows you understand that at long context the cache, not the weights, is the memory you most need to shrink.

05  Deployment recipes NEW

Match the quantization to where you're running. These are the common pairings (as of June 2026):

TargetRecipeWhy
GPU serverAWQ (or GPTQ) 4-bit weights + vLLMBig memory savings, strong 4-bit quality, fits the most-adopted engine
Laptop / CPU / edgeGGUF Q4_K_M + llama.cpp/OllamaRuns with no GPU; Q4_K_M is the balanced local default
NVIDIA cluster, peak perfFP8 (or FP4) + TensorRT-LLMHardware-native low precision, typically the fastest path on NVIDIA
memory_estimate.py
# Rough VRAM for the weights of a dense model at a given precision.
# (Real serving also needs room for the KV cache and activations.)
params_billion = 70          # e.g. a 70B model
bits_per_weight = 4          # 16 = FP16/BF16, 8 = FP8/INT8, 4 = INT4/AWQ/GPTQ
gb = params_billion * bits_per_weight / 8
print(f"~{gb:.0f} GB for weights")   # 70B @ 4-bit -> ~35 GB; @ 16-bit -> ~140 GB

That one division — params × bits ÷ 8 — is the back-of-envelope every serving engineer carries. It's why a 70B model that needs ~140 GB at FP16 (multiple GPUs) drops to ~35 GB at 4-bit and fits on a single big card.

06  Quality vs size vs speed

The whole game is a three-way trade. Lower bits → smaller and faster, but eventually worse. The sweet spot for most open models in 2026 sits around 4-bit, where quality loss is small and the savings are huge.

PrecisionRelative sizeQualityVerdict
FP16 / BF161× (baseline)ReferenceBest quality, biggest footprint
FP8 / INT8~½Near-identicalLow-risk, often "free" — a safe default
INT4 / AWQ / Q4_K_M~¼Small, usually acceptable lossThe popular sweet spot for fitting big models
< 4-bit< ¼Noticeable degradationOnly when memory is truly desperate
How to say it out loud say it

“Quantization stores weights in fewer bits — FP16 down to FP8, FP4, or INT8/INT4 — to shrink memory and speed up the memory-bound decode, like JPEG for weights. GPTQ and AWQ are post-training methods for rounding weights with minimal damage — AWQ protects the few important channels — while GGUF is the file format for local llama.cpp/Ollama inference, with Q4_K_M the common default. You can quantize weights only, weights plus activations, or the KV cache, which matters most at long context. In practice: AWQ + vLLM on a GPU, GGUF on a laptop, FP8 + TensorRT-LLM on NVIDIA clusters. Four-bit is the usual sweet spot.”

07  Self-check

A teammate asks "GPTQ, AWQ, or GGUF — which rounding algorithm is most accurate?" What's the issue with the question?
GPTQ and AWQ are post-training methods for deciding how to round weights with least quality loss (AWQ protects high-impact channels). GGUF is the file format used by llama.cpp/Ollama to package and run a quantized model locally — it offers many quant levels (Q4_K_M is the common default) but isn't itself a rounding algorithm. So comparing "AWQ vs GGUF" as algorithms is a category error: it's method vs format/runtime.
“GPTQ vs AWQ vs GGUF — when would you use each?”Core
Model answer

GPTQ and AWQ are weight-quantization methods for GPU serving — both get you to ~4-bit; AWQ tends to edge out quality by protecting the few activation-heavy channels, and pairs well with vLLM. GGUF is the file format for local inference with llama.cpp/Ollama, where Q4_K_M is the go-to balanced default. So: AWQ or GPTQ when serving on a GPU, GGUF when running on a laptop/CPU/edge. They're not competing algorithms — two are methods, one is a format/runtime.

How to say it out loud say it

“AWQ or GPTQ for GPU serving — AWQ protects important channels; GGUF (Q4_K_M) for local llama.cpp/Ollama. Methods vs a format, not three rivals.”

“Why quantize the KV cache, not just the weights?”Stretch
Model answer

Because at long context the KV cache can use more memory than the weights themselves, and it grows with every token and every concurrent user. Quantizing weights is a fixed one-time saving; quantizing the cache to 8 or 4 bits scales with the thing that actually balloons, letting you fit longer contexts and more simultaneous requests on the same GPU. It carries a small quality risk, so it's tuned carefully — but it directly attacks the dominant memory cost in long-context serving.

How to say it out loud say it

“At long context the KV cache outweighs the weights and grows with tokens and users, so quantizing it — not just the weights — is what lets you fit longer contexts and more requests per GPU.”
