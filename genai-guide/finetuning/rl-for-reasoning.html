GRPO & RL for reasoning IV NEW

The previous lesson taught models taste — which answer humans prefer. This one teaches them to be right. When labs say a model was "trained with RL to reason," this is the recipe they mean: sample many attempts, check them against an answer key that can't be argued with, and reward the ones that beat their siblings. GRPO + verifiable rewards is how reasoning models are actually made — and as of June 2026 it's the most interview-relevant page in this module.

01  The story so far — and the gap

Thirty-second recap of the alignment ladder: SFT teaches by imitation (copy this good answer). RLHF trains a reward model on human "A beats B" labels, then runs PPO against it. DPO collapses that into a direct loss on chosen/rejected pairs — no reward model, no RL loop. All of these optimize for style and preference: tone, helpfulness, safety, taste.

Here's the gap: taste won't solve a competition math problem. "Sounds better to a judge" and "is actually correct" are different signals, and preference methods only have the first one. To make a model genuinely better at multi-step reasoning, you need RL where the reward is correctness itself — and a method cheap and stable enough to run it at scale. Enter GRPO.

Preference methods (RLHF/DPO)
Learn what humans like. Great for tone, format, harmlessness. Reward is a learned opinion — it can be wrong, and it can be gamed.
Reasoning RL (GRPO + RLVR)
Learn what is correct. Reward comes from checking the answer — a math verifier, a test suite. The model discovers longer, better chains of thought because they win more reward.

02  GRPO: grade on a curve, fire the critic NEW

GRPO (Group Relative Policy Optimization) is the RL algorithm popularised by the DeepSeek-R1 line, and the loop is simple enough to hold in your head. For each prompt, sample a group of G answers (say 8–64) from the current model. Score every answer with the reward function. Then compute each answer's advantage by comparing it to its own group: (reward − group mean) / group std. Answers that beat the group average get their tokens pushed up; below-average answers get pushed down. A KL penalty to a frozen reference model keeps the policy from drifting into high-reward gibberish.

The headline vs PPO: no critic / value network. PPO needs a whole second model just to estimate "how good is an average answer here?" — GRPO gets that baseline for free from the group mean. That roughly halves memory and removes an entire model you'd otherwise have to train and babysit.
Grading on a curve analogy

PPO hires a professional judge (the value network) who must learn to predict, for every student and every question, what a "typical" attempt deserves — expensive, and the judge itself can be wrong. GRPO just grades on a curve: the same student answers the question several times, and each attempt is compared to the class average of those attempts. No judge to hire, no judge to train, and the curve automatically adapts per question — a hard problem where every attempt scores 0.2 still produces useful "above/below average" signal.

GRPO advantage, in pseudo-code
# the whole trick: the group is its own baseline — no value network
for prompt in batch:
    answers = [policy.sample(prompt) for _ in range(G)]   # G = 8..64 attempts
    rewards = [verify(prompt, a) for a in answers]        # e.g. 1.0 correct, 0.0 not

    mu, sigma = mean(rewards), std(rewards)
    advantages = [(r - mu) / (sigma + 1e-4) for r in rewards]

    # push up tokens of above-average answers, push down the rest;
    # KL term keeps the policy anchored to the frozen reference
    loss = -sum(a * logprob(ans) for ans, a in zip(answers, advantages))
    loss += beta * kl_divergence(policy, reference)

03  RLVR: rewards that can't be sweet-talked NEW

The other half of the recipe is RLVR — Reinforcement Learning with Verifiable Rewards. Instead of a learned reward model guessing what humans would like, the reward is computed by a checker: a math answer is string/numerically matched against the known solution; generated code is actually run against unit tests; a formatting rule is validated by a parser. The reward is a fact, not an opinion.

This is why reasoning RL took off when it did. Verifiable domains need no human labels (you can mine millions of math problems with known answers) and there's no learned reward model to game — the model can't charm a unit test into passing. That makes huge amounts of RL safe to run: the signal stays honest at a scale where a learned reward model would long since have been exploited.

One nuance worth one paragraph: outcome vs process rewards. An outcome reward scores only the final answer (did the test pass?) — cheap, honest, but blind to how the model got there, so a lucky guess scores the same as a clean derivation. A process reward scores the intermediate steps too (usually via a trained process-reward model), giving denser signal but reintroducing a learned judge that can be gamed. The R1-style result that surprised people: plain outcome rewards, at scale, were enough — good chains of thought emerged because they win more often.

Verifiable (RLVR-friendly)
Math with known answers, code with test suites, logic puzzles, exact formats, games with win conditions.
Not verifiable
"Make it friendlier," brand voice, summarization quality, taste. Stay with DPO/RLHF (or an LLM judge, with eyes open) for these.

04  Reward hacking & the messy bits

Even a verifiable reward only verifies exactly what it checks — and an RL loop is a tireless lawyer hunting loopholes in that contract. Classic exploits: producing the right answer with nonsense reasoning (the checker only reads the final line); learning formatting tricks that satisfy the answer-extraction regex without solving anything; and verbose padding — if longer answers ever correlate with reward, the model learns to ramble. Weak test suites are gameable too: code that special-cases the three visible tests "passes" without being correct.

The grader is part of the model now gotcha

Whatever your verifier rewards is what the model becomes. Anchors that keep it honest: the KL penalty (don't drift far from the sane reference model), hidden/held-out test cases, strict answer-format checks, and explicitly not rewarding length. And know the readability story: models trained with pure RL (DeepSeek's "R1-Zero" experiment) got the answers right but produced messy, language-mixing, barely-readable chains of thought. The fix in the actual R1 pipeline was to interleave stages — cold-start SFT → RL → SFT (on filtered good traces) → RL — using SFT to repeatedly pull the model back toward human-readable reasoning while RL pushes capability. Quote that pipeline in an interview and you sound like you've read the paper.

05  Thinking time & distilled traces

Connect this to Reasoning & test-time compute: RL on verifiable problems is where the thinking behaviour comes from. Nobody hand-wrote "think step by step for 4,000 tokens." The model discovered, under GRPO, that longer self-checking chains of thought win more reward on hard problems — so it learned when to think longer and when a short answer suffices. Test-time compute is the inference-side dial; RL is what trained the model to use it well.

Second connection: distillation of reasoning traces. RL training is expensive and finicky — so once a big teacher model has been RL-trained, you can have it generate thousands of high-quality chains of thought and simply SFT a small model on those traces (full treatment in Distillation & tooling). The well-replicated, slightly counter-intuitive finding: for small models this often beats running RL on the small model directly — the small model lacks the raw capacity to discover good reasoning through its own trial and error, but it can imitate a teacher's discovered reasoning just fine. That's how the wave of capable small "R1-distill"-style models was made.

RL (GRPO) on the big model
Discovers reasoning from scratch. Expensive, needs verifiable data, but pushes the frontier.
SFT small models on its traces
Cheap, stable, plain fine-tuning — and usually stronger than small-model RL. The default way reasoning reaches small models.

Rule of thumb: SFT first, always (it's the foundation everything else assumes). Add DPO when "better vs worse" matters and you can collect pairs. Reach for GRPO/RLVR only when correctness is mechanically checkable and worth the compute — and budget for grader-proofing, not just GPUs.

How to say it out loud say it

“GRPO samples a group of answers per prompt, scores each with a verifiable reward like a math check or unit tests, and uses the group's own mean as the baseline — advantage is just each answer's reward minus the group average, normalized. That kills PPO's separate critic network, roughly halving memory, while a KL penalty to a reference model prevents reward hacking. It's the recipe behind DeepSeek-R1-style reasoning models: chain-of-thought emerges because thinking longer wins more verifiable reward.”

07  Self-check

The headline difference between GRPO and PPO is…
PPO trains a separate value network just to estimate the baseline ("what would an average answer score here?"). GRPO samples a group of G answers and uses their mean (and std) instead — advantage = (reward − group mean) / group std. One whole model gone, roughly half the memory. It still uses a verifiable (or other) reward and very much keeps the KL anchor to the reference model.
Why did verifiable rewards (RLVR) make reasoning RL take off?
A checker's verdict is a fact: the math answer matches or it doesn't, the tests pass or they don't. That gives you unlimited cheap labels (mine problems with known answers) and a reward that can't be sweet-talked the way a learned reward model can — so you can safely run far more RL. It does not remove SFT: real pipelines (like R1's SFT → RL → SFT → RL) interleave SFT to keep the reasoning readable.
You want a 7B model to reason well on math, cheaply. The usual best move (as of 2026) is…
Distilling reasoning traces from a strong RL-trained teacher usually beats running RL on the small model directly: the small model struggles to discover good reasoning by trial and error, but imitating already-discovered reasoning is plain, cheap SFT. DPO optimizes preference, not correctness — wrong tool here.
“Walk me through how a reasoning model like R1 is trained.”Stretch
Model answer

Start from a strong pretrained base. The pure-RL experiment (R1-Zero) showed GRPO with verifiable rewards alone makes long chains of thought emerge — accuracy climbs, but the traces get messy and hard to read. So the production pipeline interleaves: a small cold-start SFT on clean reasoning examples, then large-scale GRPO on math/code with checkable answers, then another SFT round on filtered high-quality traces (plus general data to keep chat ability), then a final RL round folding in preference-style rewards. RL supplies capability; the SFT stages keep it readable and well-behaved. Finally, the teacher's traces are used to distill smaller models by plain SFT.

How to say it out loud say it

“Base model → cold-start SFT → GRPO on verifiable math/code → SFT on filtered traces → final RL. RL grows the reasoning; SFT keeps it readable; distillation hands it down to small models.”

“How would your verifiable reward get hacked, and what do you do about it?”Core
Model answer

The verifier only checks what it checks. Typical exploits: right final answer extracted from garbage reasoning; outputs shaped to please the answer-extraction regex; code that hard-codes the visible test cases; and length inflation if reward ever correlates with verbosity. Mitigations: held-out and randomized test cases, strict format checks that are themselves part of the reward, explicitly length-neutral rewards, the KL anchor to a reference model, and human/LLM spot-audits of high-reward traces. Treat the grader as adversarial-facing software — the policy will probe it millions of times.
