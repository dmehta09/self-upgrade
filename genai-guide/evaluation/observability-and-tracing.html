Evaluation & obs. · observability

Observability & tracing IV NEW

Offline eval tells you a change is good before you ship. But once real users arrive, you need to see what's actually happening on every request — which prompt ran, what the model said, which tools fired, how much it cost. That's observability, and for LLM apps the core primitive is the trace. This page covers traces, spans, the emerging OpenTelemetry standard, what to capture, and how you catch drift and regressions in the wild.

01  A flight recorder for every LLM call

When something goes wrong on a plane, investigators don't guess — they read the black box, a complete recording of every instrument and action. LLM observability is exactly that: a detailed record of every step a request took, so when a user reports a bad answer you can replay precisely what happened instead of shrugging.

The black box flight recorder analogy

A normal app logs a few lines. An LLM app is non-deterministic and multi-step — a single chat answer might involve a retrieval, three tool calls, and two model passes. Without a recording you literally cannot reconstruct why it failed. The flight recorder captures the whole chain, so debugging becomes "open the trace and look" rather than "try to reproduce it and pray."

02  Traces, spans, and the run tree

Three nested ideas, borrowed from classic distributed tracing:

Span
One unit of work — a single LLM call, one retrieval, one tool invocation. It records inputs, outputs, timing, and metadata.
Trace
The whole request, end to end — all the spans for one user interaction, stitched together.
Run tree
Spans nest: a top-level "agent run" span contains a "retrieve" span and an "LLM call" span, which may contain a "tool call" span. The tree shows causality and where the time went.
One trace = a tree of spans

03  OpenTelemetry GenAI semantic conventions NEW

Early on, every vendor logged traces in its own shape, so you were locked in. The emerging fix as of June 2026 is the OpenTelemetry (OTel) GenAI semantic conventions: a shared vocabulary for naming the things an LLM span records — model name, input/output tokens, temperature, tool calls, cost — on top of the OTel tracing standard the rest of the industry already uses.

Why a standard matters info

If your traces follow OTel conventions, any compatible backend can read them — you can switch observability vendors without re-instrumenting, and one dashboard understands spans from your LLM, your vector DB, and your web service alike. It's the same "speak one language" win that MCP brought to tools. Still maturing, but the clear direction of travel.

04  What to capture on every span NEW

The minimum useful payload per LLM request — memorise this list, it's a frequent prompt:

Prompt & completion
The exact input (including the assembled system prompt + retrieved context) and the raw output. Without these you can't debug a bad answer.
Tokens
Input and output token counts — the basis for cost and for spotting context-window bloat.
Cost
Dollars per call (tokens × price). Aggregate to catch a prompt change that quietly tripled spend.
Latency
Per-span and end-to-end; track p50/p95 so tail latency doesn't hide behind the average.
Tool calls
Which tool, the arguments, the result, and whether it errored — essential for agents.
Vector queries
The query, the retrieved chunk IDs and scores — so you can see if retrieval (not the model) caused a bad answer.
Metadata
Model + version, temperature, user/session id, and feedback (thumbs up/down) to join traces to outcomes.
Traces contain user data — handle with care gotcha

Capturing full prompts and completions means your traces hold whatever users typed — PII, secrets, proprietary text. That's a privacy and compliance surface: scrub or redact sensitive fields, set retention limits, and lock down who can read traces. "Log everything forever" is a data-breach waiting to happen, not a best practice.

05  Online eval, drift & regression detection

Traces are the raw material; the payoff is acting on them. On live traffic you:

Run online evals
Sample a slice of production traces and score them with the same LLM-judge/metrics from your offline suite (you can't score everything — cost). This is your continuous quality pulse.
Watch for drift
Inputs shift over time (new user topics, a new product) and quality silently degrades even though nothing in your code changed. Track metric trends to catch it.
Detect regressions
Compare today's scores to a rolling baseline; a sudden drop after a deploy flags a regression — sometimes auto-rolling-back. Pair with a golden offline set in CI so silent failures (prompt typo, bad index rebuild) never reach production.
Ops SLOs beside quality
Alert on p95 latency, cost/request, and tool/retriever call count — not only faithfulness. An ops regression is still a ship-blocker when SLAs exist.
Alert
Page someone when faithfulness dips, error rate spikes, cost balloons, or p95 latency blows past its SLO — the same alerting discipline as any production service.

How to say it out loud say it

“Observability for LLM apps is tracing: every request is a trace made of nested spans — one per LLM call, retrieval, or tool call — capturing prompt, output, tokens, cost, and latency. I'd follow the OpenTelemetry GenAI conventions so it's vendor-portable. On top of that I run online evals on sampled traffic, track metric trends to catch drift, compare against a baseline to detect regressions after deploys, and alert on faithfulness, error rate, cost, and p95 latency.”

06  Self-check

In LLM tracing, what's the relationship between a trace and a span?
A span is one unit of work; a trace is the full end-to-end request composed of many spans, nested into a run tree that shows causality and where time/cost went.
“What would you capture in a trace for an LLM app, and why?”Core
Model answer

Per span: the exact prompt and completion (to debug answers), input/output tokens and cost (to track spend), latency p50/p95 (to find slow steps), tool calls with args and results (for agents), and vector queries with chunk IDs and scores (to tell if retrieval caused a bad answer). Plus metadata — model version, temperature, session id, user feedback. I'd follow OTel GenAI conventions for portability and redact PII.

How to say it out loud say it

“Prompt, output, tokens, cost, latency, tool calls, vector queries, and metadata — enough to replay and debug any request — following OTel conventions and scrubbing PII.”

“What is drift, and how would you catch it?”Core
Model answer

Drift is quality degrading over time even though your code didn't change — usually because the input distribution shifted (new topics, new users, a changed upstream model). You catch it by running online evals on sampled production traces and tracking metric trends; a downward trend or a sudden drop versus a rolling baseline triggers an alert. The flagged examples become new offline eval cases.

How to say it out loud say it

“Drift is silent quality decay from shifting inputs. I catch it with online evals on sampled traffic plus trend/baseline alerting — and feed the bad cases back into the offline set.”
