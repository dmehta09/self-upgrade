Evaluating RAG & agents IV NEW

A RAG pipeline and an agent each have multiple moving parts, and a bad final answer could be any one of them. The skill — and the interview gold — is evaluating each stage separately so you know where it broke. This page covers RAGAS (the standard RAG metric set), the classic retrieval metrics, how you grade an agent's whole trajectory, and which framework to reach for.

01  Evaluate the stages, not just the answer

RAG has two stages that can fail independently: retrieval (did we fetch the right context?) and generation (did the model use it well?). If you only score the final answer, you can't tell which to fix — and as the RAG module hammered home, the problem is usually retrieval.

A kitchen inspection, course by course analogy

If a restaurant meal is bad, "the food was bad" doesn't help the chef. A good inspector checks each step: were the ingredients fresh (retrieval)? was the cooking faithful to the recipe (generation)? RAG eval is that course-by-course inspection — separate scores for "did we get the right chunks" and "did the model stick to them" — so you fix the actual broken step instead of guessing.

02  RAGAS core metrics NEW

RAGAS ("RAG Assessment") is the de-facto metric set for RAG, mostly computed by an LLM-judge and largely reference-free — it scores the triplet of question, retrieved context, answer. The four you must know:

MetricQuestion it answersCatches
FaithfulnessIs every claim in the answer supported by the retrieved context?Hallucination — the model inventing facts
Answer relevanceDoes the answer actually address the question?On-topic-but-useless or evasive answers
Context precisionOf the chunks we retrieved, how many are actually relevant (and ranked high)?Noisy retrieval — junk chunks crowding the prompt
Context recallDid we retrieve all the context needed to answer?Missing retrieval — the key chunk never showed up

The split is the whole point: faithfulness + answer relevance grade the generation stage, while context precision + recall grade the retrieval stage. Low context recall means fix your retriever; high recall but low faithfulness means the model is ignoring good context.

RAG Triad (map it to RAGAS) name it

TruLens popularised the RAG Triad: context relevance (did retrieval bring the right stuff?), groundedness / faithfulness (is the answer supported by that context?), and answer relevance (does the answer address the question?). Same three lenses as RAGAS — context precision/recall ≈ context relevance; faithfulness ≈ groundedness; answer relevance is shared. In an interview, either vocabulary is fine; the skill is separating retrieval failures from generation failures.

03  RAG security & ops eval axes NEW

Quality metrics alone miss failure modes that still ship. Treat these as first-class eval axes — often as a separate pipeline from “was the answer good?”:

AxisWhat you measureTypical check
Toxicity / unsafe contentHostile, hateful, or policy-breaking answers (or retrieved snippets that poison the reply)Safety classifier / LLM-judge rubric on outputs (+ optional on retrieved text)
LeakageSecrets, PII, or internal docs quoted when they shouldn't bePattern detectors + judge; red-team prompts that try to exfiltrate
Scope driftAnswers wander off the allowed corpus / product scope (e.g. medical advice from a refund bot)Cite-or-refuse policy; judge “in-scope?”; retrieval grader as a rail
Ops (latency / cost)p95 latency, tokens/request, retriever + rerank spendSLO thresholds next to quality gates — a “better” answer that 3× cost may fail
RegressionSilent quality drops after prompt/index/model changesFixed golden set in CI + online score vs baseline (see observability)

Pair with runtime guardrails (cite-or-refuse, input/output filters). Eval proves the rails still work; rails stop bad answers in production.

04  Classic retrieval metrics

When you have labelled relevant documents, you can score retrieval with the same metrics search engines use for decades. These are deterministic — no LLM needed:

Hit rate / recall@k
Did at least one relevant chunk land in the top-k? The simplest, most-quoted retrieval number.
MRR (Mean Reciprocal Rank)
How high up was the first relevant result? Rewards putting the right answer at rank 1 (score = 1/rank).
nDCG
Normalized Discounted Cumulative Gain — the richest: rewards relevant results and ranking them in the right order, with diminishing credit further down the list.

Rule of thumb: hit rate for a quick health check, MRR when rank-1 matters (the model mostly reads the top chunk), nDCG when the whole ordering matters (e.g. before a reranker).

05  Agent eval — trajectory vs outcome NEW

Agents add a new axis: they take steps — calling tools, looping, deciding. So there are two things to grade:

Two lenses on an agent run
user goal
"book a flight"
the task
trajectory
the steps taken
which tools, in what order
final outcome
was it achieved?
flight actually booked
Outcome eval asks "did it succeed?" Trajectory eval asks "did it get there sensibly?" — both matter, because an agent can fluke a right answer via a wasteful or unsafe path.
Final-outcome eval
Did the agent achieve the goal? End-state check (was the ticket created? did the test pass?). Simple, but blind to how.
Trajectory eval
Was the path sound — sensible plan, no needless loops, right tools? Compare against a reference trajectory or judge the steps.
Tool-call correctness
For each step: did it pick the right tool, with valid arguments, and recover gracefully from errors? The most actionable agent metric.
Outcome-only eval hides expensive, unsafe agents gotcha

An agent that reaches the right answer after 30 redundant tool calls, or by deleting a file it shouldn't have touched, scores a perfect "success" on outcome alone. That's how you ship an agent that's correct in the demo and ruinous (cost, latency, side-effects) in production. Always pair outcome with trajectory/tool-call checks — and watch step count and cost as first-class metrics.

06  Frameworks & what each is best at NEW

You rarely hand-roll all of this. The common open-source toolkits (as of June 2026):

FrameworkSweet spot
RAGASThe reference metric set for RAG — faithfulness, answer relevance, context precision/recall. Reach for it first on a RAG pipeline.
DeepEvalA "Pytest for LLMs" — unit-test-style assertions, a broad metric library, and CI integration. Great when you want eval to feel like a test suite / gate.
TruLensFeedback functions + tracing focused on the "RAG triad" (context relevance, groundedness, answer relevance); strong for instrumenting and observing apps.

They overlap a lot and all lean on LLM-judges under the hood. The interview-safe summary: RAGAS for RAG metrics, DeepEval for test-suite-style gating, TruLens for tracing-plus-feedback. Pick one; don't reinvent the metrics.

How to say it out loud — “how do you measure if RAG is hallucinating?” say it

“Hallucination in RAG is a faithfulness failure — claims in the answer not supported by the retrieved context. I'd measure it with RAGAS faithfulness: an LLM-judge decomposes the answer into claims and checks each against the context, giving a 0–1 score. But I'd first confirm the context was even there — low context recall means the retriever missed it, so the model had nothing to be faithful to. So I separate retrieval metrics (recall, context precision) from generation metrics (faithfulness, answer relevance) to know whether to fix the retriever or the prompt.”

07  Self-check

Your RAG system scores high on faithfulness but low on context recall. What does that tell you?
High faithfulness means the answer sticks to the retrieved context — no hallucination. Low context recall means the retriever failed to fetch all the relevant context. The model is being honest about incomplete evidence, so the fix is upstream in retrieval, not in generation.
“What are the four RAGAS metrics and which stage does each grade?”Core
Model answer

Faithfulness (are claims supported by context?) and answer relevance (does it address the question?) grade generation. Context precision (are retrieved chunks relevant and well-ranked?) and context recall (did we fetch all needed context?) grade retrieval. Splitting them tells you whether to fix the retriever or the generator.

How to say it out loud say it

“Faithfulness and answer relevance score generation; context precision and recall score retrieval. The split localises the bug.”

“How do you evaluate an agent, beyond 'did it get the right answer'?”Stretch
Model answer

Combine outcome and trajectory. Outcome eval checks the end-state (goal achieved?). Trajectory eval checks the path: was the plan sound, were tool calls correct (right tool, valid args, error recovery), and were there wasteful loops? I also track step count and cost as metrics, because an agent can reach a correct answer via an expensive or unsafe route — outcome-only eval would miss that entirely.

How to say it out loud say it

“Outcome plus trajectory: did it succeed, and did it get there sensibly — right tools, valid args, no wasteful or unsafe steps? I treat step count and cost as metrics too.”
