Evaluation & obs. · overview

How do you know it actually works? IV NEW

You've built a RAG pipeline or an agent. It looks great in the demo. But will it be right next week, on inputs you've never seen, after you tweak the prompt? Evaluation is how you answer that with evidence instead of vibes — and observability is how you watch it once real users arrive. In 2026 this stopped being a nice-to-have: a failing eval now blocks the deploy, just like a failing test.

01  Eval is unit tests — for fuzzy output

In normal software you write a test: add(2, 2) must equal 4. Run it, green or red, done. LLM evaluation is the same instinct — pin down "what does good look like?" and check the system against it automatically — but with one brutal twist: the output is fuzzy. There's no single string the model must produce.

Grading an essay, not a multiple-choice test analogy

A math quiz has one right answer per question — easy to auto-grade. An essay has a hundred good answers and a thousand bad ones, so you need a rubric: is it on-topic? accurate? clear? Evaluating an LLM is grading essays at scale. Sometimes you can use a simple key (did it return valid JSON?), but most of the time you're checking against a rubric — and increasingly, another model does the grading.

02  Why LLM eval is genuinely hard

Three properties make this harder than testing a normal function. State them cleanly in an interview and you sound senior:

Non-deterministic
The same prompt can give different answers run to run (sampling temperature, even at temp 0 there's hardware non-determinism). A test that sometimes passes and sometimes fails is useless — so eval has to tolerate variation and measure distributions, not exact strings.
No single right answer
"Summarise this email" has countless correct outputs. Exact-string matching is hopeless for open-ended text, so you need fuzzy or semantic scoring.
Quality is multi-dimensional
One answer can be accurate but rude, or fluent but wrong, or correct but too long. You usually score several axes (faithfulness, relevance, tone, safety) rather than one pass/fail.
"It worked in the demo" is not evaluation gotcha

Eyeballing five hand-picked examples is the most common anti-pattern. It tells you nothing about the inputs you didn't try — and you'll subconsciously pick examples that work. Real eval runs a fixed, representative dataset of dozens-to-thousands of cases every time you change something, so you can see whether a tweak helped or quietly broke ten other things.

03  Eval is now a production gate, not an afterthought NEW

The biggest shift to know for 2026: teams treat eval like CI for prompts and models. You don't merge a prompt change, swap a model, or update a retriever unless the eval suite says quality held or improved. A regression on your eval set blocks the deploy — exactly like a red unit test blocks a merge.

“Evaluation is unit testing for fuzzy output. It's hard because LLMs are non-deterministic, there's no single right answer, and quality is multi-dimensional — so I run a fixed dataset and score several axes rather than eyeball a demo. 05  Self-check

Why can't you evaluate a summarizer by checking its output against one "correct" summary with exact-string match?
Open-ended tasks have no single gold string. Two summaries can both be excellent while sharing few exact words, so exact match punishes good answers. You score meaning (semantic similarity) or quality axes (a rubric / LLM-judge) instead.
“Why is evaluating an LLM harder than testing a normal function?”Warm-up
Model answer

A normal function is deterministic with one right answer, so a single assertion suffices. LLMs are non-deterministic, have many valid outputs for open-ended tasks, and have multi-dimensional quality (accurate vs safe vs concise). So you run a representative dataset and score distributions across several axes, rather than asserting one exact string.

How to say it out loud say it

“Same idea as unit tests, but the output is fuzzy: non-deterministic, no single right answer, and quality is multi-axis — so I measure over a dataset, not a single assertion.”

“What does it mean that eval is a 'production gate' in 2026?”Core
Model answer

It means a quality regression on your eval set blocks the release, exactly like a failing unit test blocks a merge. You run an offline eval suite in CI on every prompt/model/retriever change; if scores drop versus the baseline, it doesn't ship. Production observability then feeds new failures back into the eval set, so the gate keeps getting stricter over time.

How to say it out loud say it

“Eval runs in CI and gates the deploy. No change ships unless the eval set holds or improves — and live failures become new eval cases.”
