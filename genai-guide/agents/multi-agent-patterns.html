Agents · multi-agent

Multi-agent patterns IV NEW

One agent juggling ten tools and a sprawling prompt gets confused — same as one person doing ten jobs. Multi-agent systems split the work across several specialised agents that talk to each other. This page walks the five patterns you'll be asked about — fan-out, pipeline, debate, supervisor (today's production default), and swarm (the frontier) — plus the cost trick everyone uses, the ways they fail, and when a single agent quietly beats the whole orchestra.

01  Why more than one agent?

Two reasons. First, specialisation: a focused agent with five relevant tools and a tight prompt outperforms one generalist drowning in fifty tools and conflicting instructions. Second, context isolation: each agent keeps its own clean window, so a researcher's messy intermediate notes don't pollute the writer's context. The cost is coordination — and coordination is where most of the difficulty (and the interview questions) live.

A company, not a one-person shop analogy

A solo founder can do everything — until they can't. Then you hire specialists: a researcher, a writer, an editor, and a manager to keep them pointed at the goal. Each person is sharper in their lane, but now you need meetings, handoffs, and someone deciding who does what. Multi-agent systems are exactly that trade: more capability and focus, paid for with the overhead of getting everyone to cooperate.

02  The five patterns NEW

Here are the five named arrangements, from simplest to most autonomous. Learn the shape of each and the one-line “when.”

Fan-out (parallel)
Split a task into independent sub-tasks, run agents in parallel, then merge the results. Fast; great when sub-tasks don't depend on each other (research five competitors at once).
Pipeline (sequential)
Agents in a line, each one's output feeding the next: research → draft → edit → fact-check. Like an assembly line; clear stages, but as slow as the chain is long.
Debate
Several agents argue or critique each other (or a judge picks a winner) to improve quality and catch errors. More reliable on hard reasoning; expensive — you're paying several models to think.
Supervisor (orchestrator–worker)
One supervisor agent owns the goal and delegates to specialist workers, routing each sub-task and combining results. The production default in 2026 because control and debugging stay centralised.
Swarm (decentralised)
No central boss: peer agents hand control to whichever teammate is best suited, coordinating through shared state. Flexible and the frontier as of June 2026, but the hardest to predict and debug.

03  Supervisor = default, swarm = frontier NEW

If you remember one sentence from this page, make it this: as of June 2026, supervisor is the production default and swarm is the frontier. Here's why the industry settled there.

SupervisorSwarm
ControlCentralised — one agent decides routingDecentralised — peers hand off to each other
DebuggabilityHigh — one place to trace decisionsLow — control bounces around
FlexibilityBounded by the supervisor's viewHigh — emergent collaboration
Maturity (Jun 2026)Production defaultFrontier / experimental

Supervisor wins in production for the same reason companies have managers: a single point of coordination makes the system observable and steerable — when something goes wrong, there's one decision-maker to inspect. Swarm's peer-to-peer handoffs unlock more emergent, flexible collaboration, but that same lack of a central authority makes behaviour harder to predict, trace, and contain — which is why it's still the frontier rather than the default.

04  The cost pattern, handoffs & shared state NEW

Three practical pieces tie a multi-agent system together:

The cost pattern
Use an expensive frontier model for the supervisor (it does the hard planning and routing) and cheaper, faster models for the workers (they do narrow, well-scoped jobs). You pay top dollar only for the thinking that needs it — the standard way to keep a multi-agent bill sane.
Handoffs
The act of one agent passing control (and the relevant context) to another. A clean handoff includes just what the next agent needs — not the whole transcript — or you reintroduce the context-bloat you split the system up to avoid.
Shared state
A common scratchpad/blackboard all agents read and write, so work-in-progress is visible without stuffing everything into every message. Especially central to swarms, where there's no supervisor to hold the thread.
Over-delegation: the classic failure mode gotcha

A supervisor that spawns a worker for every trivial step — or workers that keep punting back instead of just answering — turns into an expensive game of hot potato. Each handoff is more LLM calls, more context copied around, more latency, and more chances to garble the goal in translation. The fix: give workers enough scope to actually finish their piece, keep handoff payloads lean, and let the supervisor do simple things itself rather than delegating reflexively. Delegation is a cost, not a virtue.

05  When a single agent wins

Multi-agent is fashionable, which makes “do you actually need it?” a favourite interview trap. Every extra agent adds coordination overhead, latency, cost, and failure surface. For most tasks, a single well-equipped agent (or even a plain workflow) is simpler, cheaper, and more reliable.

Don't reach for a committee to answer one email gotcha

Reach for multiple agents only when the work genuinely splits into distinct specialities, benefits from parallelism, or overwhelms one agent's tool set and context. If a single agent with the right tools passes your eval, ship that — it's far easier to debug and orders of magnitude cheaper than a swarm. The senior move is to start with one agent and add agents only when you can point to the specific bottleneck they remove.

06  The framework landscape NEW

You don't build the orchestration from scratch. The names worth recognising (as of June 2026):

LangGraph
Graph-based orchestration; ships supervisor and swarm templates and lets you wire agents as nodes/subgraphs over shared state. The go-to when you want explicit control of the flow.
OpenAI Agents SDK
A lightweight framework built around agents, tools, handoffs, and guardrails — handoffs are a first-class primitive.
Claude sub-agents
Anthropic's approach: a main agent delegates to specialised sub-agents, each with its own context and tools — a supervisor pattern in practice.
CrewAI
Role-based “crews” — you define agents by role and goal and they collaborate on tasks. Popular for its intuitive, team-of-coworkers mental model.
AutoGen
Microsoft's framework centred on conversational, message-passing agents that solve tasks by talking to each other.
Google ADK
Google's Agent Development Kit for building and deploying multi-agent systems, with first-class support for the A2A (agent-to-agent) communication direction.

MCP vs A2A — two different buses

MCP (Model Context Protocol)
Tools & context into one agent. An agent (or host) talks to MCP servers that expose tools, resources, and prompts. See MCP lesson.
A2A (Agent-to-Agent)
Agents talking to other agents as peers/services — discovery, task handoff, status — not “give me a calculator tool.”
Interview framing
MCP = how an agent gets capabilities. A2A = how multiple agents coordinate. You can use both: supervisors call workers over A2A-style handoffs while each worker uses MCP tools.
Say it out loud

“MCP is the USB-C for tools and context into an agent. A2A is agents calling other agents. Don’t conflate them in a design interview.”

Building it? Start from a template note

We teach the patterns here; you implement them with a framework. On LangGraph there are ready-made supervisor and swarm templates, and you compose specialists as subgraphs over a shared state. For that code see the Lang Stack guide's LangGraph section.

07  Self-check

Why is the supervisor pattern the production default in 2026 while swarm remains the frontier?
Both can use tools and vary in agent count. The decisive factor is control: a supervisor gives one place to route, observe, and debug — vital in production — whereas a swarm's peer-to-peer handoffs trade that predictability for emergent flexibility, keeping it at the frontier.
“Compare the supervisor and swarm patterns.”Core
Model answer

Both coordinate multiple specialist agents, but control differs. In supervisor, one orchestrator owns the goal, routes sub-tasks to workers, and combines their results — workers always report back to it. In swarm, there's no central boss: peer agents hand control directly to whichever teammate fits next, coordinating through shared state. Supervisor is observable and easy to debug, so it's the production default; swarm is more flexible and emergent but harder to predict, so it's the frontier. The common cost optimisation is a frontier model for the supervisor and cheaper models for workers.

How to say it out loud say it

“Supervisor = one boss routes to workers who report back — centralised, debuggable, the default. Swarm = peers hand off to each other, no boss — flexible but hard to trace, the frontier.”

“A candidate proposes five agents for a simple Q&A bot. What do you say?”Core
Model answer

I'd push back. Each extra agent adds coordination overhead, latency, cost, and failure surface, and over-delegation makes it worse — handoffs that copy context around and garble the goal. For a simple Q&A bot, a single agent (or even a retrieval workflow) with the right tools is simpler, cheaper, and far easier to debug. I'd only add agents when the work splits into genuine specialities, benefits from parallelism, or overflows one agent's context — and I'd be able to name the specific bottleneck each new agent removes.

“Start with one agent. Multi-agent adds coordination cost, latency, and failure surface — only worth it for real specialisation, parallelism, or context overflow. Name the bottleneck before adding an agent.”
