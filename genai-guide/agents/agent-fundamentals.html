Agents · anatomy

Anatomy of an agent IV

Pop the hood on any agent and you'll find the same four parts: a model (the brain), a set of tools (the hands), some memory (the notepad), and a control loop (the heartbeat that keeps it going). This page walks each part, then the three ways an agent thinks — ReAct, plan-and-execute, and reflection — and finishes with the unglamorous but career-saving topic: how to stop a loop before it burns your whole budget.

01  The four pieces

An agent is less a single thing than an assembly. Take any one piece away and it stops being an agent:

Model (the brain)
The LLM that does the reasoning and decides what to do next. Usually a capable instruction-following model; for hard planning you'll reach for a reasoning model.
Tools (the hands)
Functions the model can call to affect or read the world — web search, a database query, a calculator, a code runner, an API. Without tools, the model can only talk. (See function calling and MCP.)
Memory (the notepad)
What the agent carries between steps and across sessions: the running scratchpad of this task, plus longer-term facts. Big enough topic that it gets its own page.
Control loop (the heartbeat)
The code that runs the cycle: call the model, execute any tool it asked for, feed the result back, and decide whether to go again or stop. This is what makes the whole thing autonomous.
A handyman on a job analogy

Picture a handyman fixing a leak. Their brain figures out what's wrong; their toolbox (wrench, tape, torch) lets them act; their notepad tracks what they've tried and what the landlord asked for; and their working rhythm — look, try, check, repeat — is the loop. A brilliant handyman with no tools is just talking about plumbing. A full toolbox with no one thinking is a pile of metal. The agent is all four, working together.

02  ReAct: reason → act → observe

ReAct (“Reasoning + Acting”) is the default way agents think, and the one interviewers expect you to name. The model interleaves thinking out loud with taking actions: it writes a short thought about what to do, emits an action (a tool call with arguments), receives an observation (the tool's result), and repeats — each thought now informed by what it just saw.

The “reason” step is why ReAct beats blind tool-calling: writing down a thought first makes the model's tool choices more deliberate and lets you read its logic when debugging.

Why bother making the model narrate? Because the thought grounds the action. A model that just blurts tool calls tends to flail; one that first writes “the user asked for last quarter's revenue, so I should query the finance DB filtered to Q1” picks better tools and gives you a readable trace. Here's the shape of one turn:

react_trace.txt

Action: get_account(user_id="u_8821")
Observation: {"plan": "Pro", "seats": 5, "api_limit": 100000}
Thought: They're on Pro with a 100k limit. That answers it.
Answer: You're on the Pro plan, which includes 100,000 API calls/month across 5 seats.
You rarely hand-write the loop note

In practice you don't code the perceive/act cycle yourself — frameworks ship a battle-tested ReAct loop. 03  Plan-and-execute

ReAct decides one step at a time, which is flexible but can wander on long tasks. Plan-and-execute splits the work in two: a planner first writes the whole multi-step plan up front, then an executor carries out each step (often with its own little ReAct loop), and the plan is revised only if something breaks.

A road trip with a map vs. turn-by-turn analogy

ReAct is driving with turn-by-turn navigation: you only know the next instruction, which is great when roads close unexpectedly but easy to take the scenic route by accident. Plan-and-execute is laying out the whole route on a map before leaving — you stay on course over a long drive, but if a bridge is out you have to stop and re-plan. Long, well-understood journeys favour the map; chaotic city errands favour turn-by-turn.

04  Reflection & self-critique

Reflection adds a step where the agent grades its own work and tries again. After producing a draft (an answer, some code, a plan), a critique step asks “is this actually right? what's missing?” and feeds that critique back in for a revision. It's the agent equivalent of re-reading your email before hitting send.

Reflection shines when there's a signal to reflect on — test results, a linter, a rubric. Pure self-critique with no external feedback helps less, because the model that made the mistake is also the one grading it.

Reflection is strongest when the critique can lean on something objective: running the generated code and feeding back the error, checking output against a schema, or scoring against a rubric. That external signal is what turns “the model second-guessing itself” into real improvement.

05  Stopping conditions & runaway loops NEW

An agent that can loop is an agent that can loop forever. The single most important piece of production hygiene is deciding — explicitly — when the loop must stop. There are two healthy ways to end, and several limits you set so a stuck agent ends anyway:

Goal reached
The model signals it's done (e.g. it stops requesting tools and returns a final answer). The happy path.
Iteration ceiling (max steps)
A hard cap on loop turns — say 10 or 25. Hit it and the agent stops regardless, returning its best effort or an error. Your seatbelt against infinite loops.
Budget / token / time limit
Stop once the task has cost more than X tokens, dollars, or wall-clock seconds. Protects you when a single run goes pathological.
No-progress detection
Notice when the agent repeats the same tool call with the same args, or cycles between two states, and break out — it's spinning, not working.
The cost & latency of agent loops gotcha

Every loop iteration is a fresh LLM call, and each call resends the growing transcript — so an agent's cost and latency don't add up linearly, they balloon. A task that takes one chatbot call might take fifteen agent calls, each on an ever-longer context. Without a max-iteration cap and a budget guard, a single confused agent can quietly rack up a huge bill while a user stares at a spinner. Always set the ceiling before you ship, trace every step, and treat an agent that needs 30+ turns as a signal that the task wants a workflow or a better tool, not more looping.

How to say it out loud say it

“An agent is a model, tools, memory, and a control loop. The default reasoning pattern is ReAct — reason, act, observe, repeat; plan-and-execute plans everything up front for long tasks; reflection adds a self-critique pass, best when there's an objective signal like test results. The thing I always get right in production is stopping: a hard max-iteration cap, a token/cost budget, and no-progress detection — because every loop is another LLM call on a longer context, so cost and latency blow up fast if a loop runs away.”

06  Self-check

In the ReAct pattern, what is the purpose of the “Thought” the model writes before each tool call?
ReAct interleaves reasoning with acting. The thought makes each tool choice deliberate instead of reflexive, and the visible chain of thoughts/actions/observations is what lets you debug where an agent went wrong.
“Walk me through what ReAct is and why it works.”Core
Model answer

ReAct interleaves reasoning and acting. Each step the model writes a thought, emits an action (a tool call), and reads the observation, then loops with that new information until it can answer. It works because the thought makes tool selection deliberate rather than reflexive, and because the explicit thought/action/observation trace is readable — so when it misbehaves I can see exactly which step went wrong. It's the loop most prebuilt agents implement.

How to say it out loud say it

“Reason, act, observe, repeat. The model thinks, calls a tool, reads the result, and loops. The thinking step makes tool choices better and the trace debuggable.”

“How do you keep an agent from looping forever or blowing the budget?”Core
Model answer

Explicit stopping conditions. A hard max-iteration cap so it can't loop indefinitely; a token/cost/time budget per task; and no-progress detection that breaks out when it repeats the same action or cycles. I also trace every step so I can see where it spins. This matters because each iteration is another LLM call on a growing context, so an unbounded loop balloons cost and latency — and an agent that needs many turns usually signals the task should be a workflow instead.

How to say it out loud say it

“Max-iteration cap, a token/cost budget, and no-progress detection — plus tracing. Every loop is another call on a longer context, so without limits cost and latency run away.”
