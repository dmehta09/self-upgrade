Agents — overview IV

A chatbot answers your question. An agent gets the job done: it makes a plan, picks up tools, takes actions, checks the result, and tries again until the task is finished. Same language model underneath — the difference is that you hand it a loop and a set of tools and let it drive. This module is your interview-ready tour of how that loop works, how agents remember things, how several agents team up, and how to keep them from going off the rails.

01  A chatbot answers; an agent gets it done

The clearest way to define an agent is by contrast. A plain chat model is a brilliant one-shot responder: you ask, it replies, the turn ends. It can't book the flight, run the test suite, or check whether its own answer was right — it just produces text. An agent wraps that same model in a loop and gives it tools (functions it can call: search, a database, a code runner, an API). Now the model can decide what to do next, do it, look at what happened, and keep going.

A recipe vs. a chef analogy

Ask a chatbot “how do I make soup?” and it reads you the recipe — every time, word for word, whether or not you have onions. An agent is the chef: it opens the fridge (a tool), notices the onions are gone, walks to the shop (another tool), tastes the broth, decides it needs salt, and adjusts — looping until dinner is actually on the table. The recipe is knowledge; the chef gets the job done. An agent is a model that can act, observe, and adapt, not just recite.

One sentence for the interview: an agent is an LLM that runs in a loop, choosing and calling tools to accomplish a goal, using what it observes to decide the next step. The model is the brain; the tools are the hands; the loop is what makes it autonomous.

02  The agent loop

Every agent, no matter how fancy, runs the same four-beat cycle. It perceives the current situation (the goal plus everything observed so far), reasons about what to do, acts by calling a tool, and observes the result — then loops back with that new information. It stops when the goal is met (or when a safety limit says “enough”).

The core agent loop
perceive
read the state
goal + history so far
reason
decide next step
think / pick a tool
act
call a tool
search / API / code
observe
read the result
feed it back & repeat
The loop back from observe to perceive is the whole idea: the agent feeds each tool result into the next decision. Agent fundamentals unpacks the named version of this — ReAct (reason → act → observe).

If that shape looks familiar, it should: the agentic RAG loop is exactly this pattern with retrievers as the tools. An agent is the general case; agentic RAG is one specialised instance.

03  Agent vs. workflow vs. chain

Interviewers love this distinction because it separates people who think “agent” means “anything with an LLM” from people who understand control flow. The real question is: who decides what happens next — your code, or the model?

ChainWorkflowAgent
Who controls the stepsYou — fixed lineYou — fixed graph with branchesThe model — decides at runtime
PathA → B → C, alwaysPredefined branches/loops you wroteOpen-ended; chosen step by step
PredictabilityHighestHighLowest (flexible, but variable)
Good for“Summarize then translate”“Route by intent, then retrieve”“Figure out how to fix this bug”

A useful framing (popularised by Anthropic, as of June 2026): workflows are systems where LLMs and tools are orchestrated through predefined code paths you wrote; agents are systems where the LLM dynamically directs its own process and tool use. A chain is the simplest workflow — a straight line. The more the model decides at runtime, the more “agentic” it is.

When you DON'T need an agent gotcha NEW

Agents are powerful and expensive, slow, and harder to debug — every loop is another LLM call, another chance to wander off. The senior instinct is to reach for the least autonomy that solves the problem. If the steps are known in advance, write a workflow; you'll get predictable latency, lower cost, and far easier testing. Use a full agent only when the path genuinely can't be planned ahead of time — when the work depends on what you discover along the way. “We added an agent” is not a feature; solving the task reliably is.

How to say it out loud say it

“A chatbot answers; an agent gets the job done by running a model in a loop with tools — perceive, reason, act, observe, repeat. The dividing line from a workflow is who controls the next step: in a workflow my code picks the path; in an agent the model does, at runtime. Because that flexibility costs latency, money, and debuggability, I default to the simplest thing — a chain or a fixed workflow — and only reach for a true agent when the steps can't be known in advance.”

05  Self-check

A teammate proposes building an “agent” for a task whose steps are completely fixed: fetch a record, format it, email it. What's the strongest objection?
Autonomy is only worth its cost when the path can't be planned ahead. A fixed three-step task is a textbook workflow: hard-code it and you get predictable latency, lower spend, and trivial debugging. Reserve agents for open-ended work.
“What's the difference between a chatbot and an agent?”Warm-up
Model answer

A chatbot produces a response and stops — one turn, no actions. An agent runs the same model in a loop with tools: it reasons about the goal, calls a tool, observes the result, and repeats until the task is done. The chatbot answers; the agent acts to accomplish something in the world.

How to say it out loud say it

“A chatbot answers; an agent gets the job done. It's an LLM in a loop with tools — reason, act, observe, repeat — so it can take actions and adapt, not just reply.”

“Where's the line between a workflow and an agent?”Core
Model answer

Control flow. In a workflow, my code defines the path — even if it branches and loops, the steps are predetermined. In an agent, the model decides the next step at runtime based on what it observes. A chain is the simplest workflow (a straight line). I pick based on whether the steps can be known ahead of time: if yes, a workflow is more predictable and cheaper; if the task is genuinely open-ended, an agent earns its keep.

How to say it out loud say it

“Workflow = my code picks the path; agent = the model picks the path at runtime. Chains are the simplest workflow. Default to a workflow for known steps; use an agent only when the path can't be planned in advance.”
