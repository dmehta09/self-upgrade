Agents · reliability & eval

Reliable agents IV NEW

A demo agent that works once is easy. An agent you'd trust in production — that doesn't loop forever, misuse a tool, or quietly delete the wrong row — is the hard part, and the part interviews probe. This page covers why agents fail, the guardrails and human-in-the-loop gates that catch trouble, how to evaluate an agent by its trajectory and not just its final answer, and why agents are stubbornly hard to make reproducible.

01  Why agents fail

A single LLM call can be wrong. An agent chains many calls, so its failures compound and mutate in ways a one-shot model's don't. The three you must be able to name:

Compounding errors
A small mistake early — a misread tool result, a wrong assumption — gets carried forward and built upon, so the agent confidently marches in the wrong direction. If each of 10 steps is 95% reliable, the run is only ~60% reliable end-to-end. Errors multiply, they don't average.
Tool misuse
Calling the wrong tool, passing malformed or hallucinated arguments, or misreading what a tool returned. A tool that changes the world (delete, send, pay) makes this dangerous, not just unproductive.
Infinite / runaway loops
Without a stop condition the agent cycles — re-running the same call, oscillating between two states — burning tokens and time with nothing to show. (Covered in Anatomy of an agent.)
A wrong turn early in a road trip analogy

Miss your exit in the first five minutes and every careful, correct turn afterward takes you further from home — you can't out-drive a wrong start. That's compounding error: agents don't just make isolated mistakes, they build on them. It's why catching a problem early (a guardrail, a check) is worth ten fixes later.

02  Guardrails & human-in-the-loop gates NEW

You make agents reliable not by hoping the model behaves, but by constraining what it can do and pausing before anything risky. Two layers:

Guardrails
Programmatic checks around the agent: validate tool arguments before executing, allow-list which tools can run, cap iterations and budget, sanity-check outputs against a schema, and run a separate safety classifier on inputs/outputs. Crucially, these live in your code, not in the model's good intentions.
Human-in-the-loop (HITL) approval gates
For high-stakes or irreversible actions — sending money, deleting data, emailing a customer, merging a PR — the agent pauses and asks a human to approve, edit, or reject before proceeding. The agent proposes; a person disposes.
An approval gate before a risky action
agent proposes
“delete 1,204 rows”

Reserve gates for irreversible/high-stakes steps — gate everything and you've just built a slow chatbot with extra clicks. The skill is choosing which actions need a human.
How frameworks pause an agent note

An approval gate needs the agent to suspend, persist its state, wait for a human, then resume exactly where it left off. On LangGraph that's the interrupt primitive (human-in-the-loop) on top of a checkpointer, and you watch what the agent did via LangSmith traces. We teach the concept here; for the code see the Lang Stack guide.

03  Evaluating agents: trajectory vs. outcome NEW

Evaluating a chatbot is “was the answer good?” Evaluating an agent is harder, because how it got there matters as much as where it ended up. Two complementary lenses:

Outcome (final-answer) evalTrajectory eval
Asks“Did it get the right result?”“Did it take a sensible path to get there?”
Looks atThe final output onlyThe full sequence of steps & tool calls
CatchesWrong answersRight answer by luck, wasteful detours, wrong-but-recovered tool calls
Blind spotA correct answer reached by a broken processA clean path that still ends wrong

You need both. Outcome eval alone rewards an agent that stumbles into the right answer through ten wrong turns — fragile and expensive even when it “passes.” A key trajectory metric is tool-call correctness: did the agent call the right tools, in a reasonable order, with valid arguments? You can check the exact path against a reference, or — more flexibly — let an LLM-as-judge grade whether the trajectory was reasonable.

04  Determinism & reproducibility

Agents are hard to reproduce, which makes them hard to test and debug. The causes stack up: LLM sampling is non-deterministic (even at temperature 0 you're not fully guaranteed identical output); tools touch a changing world (today's search results differ from yesterday's); and a tiny early difference cascades through the loop into a wholly different trajectory. So the same input can produce different runs.

“It worked when I ran it” isn't evidence gotcha

Because runs vary, a single successful (or failed) trace tells you little — the next run may differ. Don't trust one-shot demos or one-off bug repros. Evaluate over a dataset across multiple runs and report a success rate; mock or pin tools and fix seeds in tests so behaviour is repeatable; and log full traces so a rare failure can be inspected even if you can't reproduce it on demand. Treat agent reliability as a statistical property, not a yes/no.

How to say it out loud say it

“Agents fail by compounding small errors, misusing tools, and looping — so reliability comes from constraint, not hope: guardrails in my code (validate args, allow-list tools, cap iterations and budget) and human-in-the-loop approval gates for irreversible actions. I evaluate on two axes — outcome, did it get the right answer, and trajectory, did it take a sensible path with correct tool calls — because a right answer reached by a broken process is fragile. And because runs are non-deterministic and tools touch a changing world, I treat reliability statistically: eval over a dataset for a success rate, pin tools and seeds in tests, and log full traces.”

05  Self-check

Your agent passes outcome eval — it returns the correct final answer 90% of the time. Why might trajectory eval still reveal a problem?
Outcome eval grades only the final result, so it's blind to how the answer was reached. Trajectory eval inspects the steps and tool calls, catching agents that stumble into correctness through detours or invalid calls — behaviour that's brittle and costly even when the final answer is right.
“How do you make an agent reliable enough for production?”Core
Model answer

Constrain and verify rather than trust. Guardrails in code: validate tool arguments, allow-list tools, cap iterations and budget, schema-check outputs, and run a separate safety classifier. Human-in-the-loop approval gates for irreversible or high-stakes actions, so the agent proposes and a person approves. Then I evaluate on a dataset across multiple runs — both outcome and trajectory, including tool-call correctness — and report a success rate. And I trace everything, because runs are non-deterministic so I need observability to debug rare failures.

How to say it out loud say it

“Guardrails in code, human gates for irreversible actions, eval on a dataset for a success rate across outcome and trajectory, and trace everything. Reliability is engineered, not hoped for.”

“Why are agents so hard to test, and what do you do about it?”Core
Model answer

Because they're non-deterministic and stateful: sampling varies run to run (even at temperature 0 it isn't guaranteed identical), tools hit a changing world, and a tiny early difference cascades into a totally different trajectory. So one passing run proves little. I handle it statistically — eval over a dataset across multiple runs for a success rate rather than a binary pass — and I make tests repeatable by mocking or pinning tools and fixing seeds. Full trace logging lets me inspect a rare failure even when I can't reproduce it on command.

How to say it out loud say it

“They're non-deterministic and stateful, so one run proves nothing. Eval over a dataset for a success rate, pin tools and seeds in tests, and log traces to debug the rare failures.”
