Using Claude · lesson 9

Shipping with the API

The prototype works — it answered your test prompt and everyone clapped. This lesson is everything that changes when real traffic hits it: errors you must read instead of ignore, rate limits you must live within, retries that are polite instead of frantic, tool schemas that hold up under a million weird inputs, and a bill you can actually predict.

01  Read the error, then react

Every API failure comes back with an HTTP status code and a typed error. The single most important production skill is knowing which errors mean "you made a mistake — fix the request" and which mean "bad timing — try again in a moment." Retrying a 401 in a loop fixes nothing; not retrying a 529 throws away a request that would have succeeded two seconds later.

CodeError typeRetry?What it means
400invalid_request_errorNo — fix the requestMalformed body, missing params, bad model ID format. Your bug.
401authentication_errorNo — fix the keyMissing, invalid, or revoked API key.
403permission_errorNoKey is valid but lacks access to this model or feature.
404not_found_errorNoUsually a typo in the model ID (claude-sonnet-4.6 vs claude-sonnet-4-6).
413request_too_largeNoRequest exceeds size limits — trim history, shrink images, chunk documents.
429rate_limit_errorYes — with backoffToo many requests or tokens per minute. Honor the retry-after header.
500api_errorYesSomething went wrong on Anthropic's side. Transient.
529overloaded_errorYes — with backoffThe API is at capacity. Wait and retry; it passes.
The golden rule tip

4xx is your bug — retrying replays the same mistake (the one exception is 429). 5xx and 429 are weather — nothing is wrong with your request, the conditions just aren't right. Fix bugs; wait out weather, politely.

02  Retries: politely persistent

Redialing a busy line analogy

When a phone line is busy, you don't redial instantly a hundred times — you wait a bit, then a bit longer. That's exponential backoff: 1s, then 2s, then 4s, then 8s. And if a whole office redials at the exact same second, they jam the line again — so everyone adds a small random delay. That's jitter. Backoff + jitter is how thousands of clients recover from a hiccup without piling onto it.

Good news: the official SDKs already do this. Connection errors, 429s, and 5xx responses are retried automatically with exponential backoff — you just configure how persistent to be via max_retries. Your own code only needs to handle the case where retries run out:

resilient_call.py
import anthropic

# The SDK retries 429s and 5xx with backoff + jitter automatically.
client = anthropic.Anthropic(max_retries=4)  # default is 2

try:
    response = client.messages.create(
        model="claude-sonnet-4-6",
        max_tokens=1024,
        messages=[{"role": "user", "content": "Classify this ticket: ..."}],
    )
except anthropic.RateLimitError:
    # Retries exhausted — queue the job for later instead of hammering.
    enqueue_for_retry(job)
except anthropic.APIStatusError as e:
    if e.status_code >= 500:
        enqueue_for_retry(job)   # transient server trouble
    else:
        raise                    # 4xx: a real bug — surface it loudly

Notice what's not here: no hand-rolled sleep loops. Let the SDK be polite for you, and design your app for the rare moment politeness runs out — a queue, a fallback message, a degraded mode.

Your service just got a 429 rate_limit_error. Best reaction?
Right. A 429 is the API telling you exactly how long to wait — retry-after is in the response headers. Tight-loop retries make the congestion worse (and burn your quota faster), and key-juggling is against the spirit of the limits and gets your whole org throttled anyway.

03  Rate limits & tiers

Your organization has three meters running at once: requests per minute (RPM), input tokens per minute, and output tokens per minute. Cross any of them and you get a 429 — even if the other two have plenty of headroom. A few huge prompts can exhaust the token meter long before the request meter notices.

Limits grow with usage tiers: as your spend history builds, your caps rise automatically. And you never have to guess where you stand — every response carries x-ratelimit-remaining-* headers reporting how much of each budget is left this minute, plus retry-after when you do hit the wall.

Spread bursts
A spike of 100 requests in one second can 429 even when 100/minute is fine. Smooth traffic at your edge.
Queue on your side
When the remaining-budget headers run low, hold jobs in your queue instead of letting the API bounce them.
Batch the non-urgent
Bulk work that can wait an hour belongs on the Batch API — separate capacity, half the price (see the cost section).
Ask for a higher tier
If you're sustainably near your caps, request a tier increase — limits are meant to grow with real usage.

04  Long requests want streaming

A request that generates tens of thousands of tokens can take minutes — and idle HTTP connections get dropped by proxies, load balancers, and the SDK's own timeout long before the model finishes. The fix isn't a bigger timeout; it's streaming. With streaming, tokens flow back as they're generated: the connection is never idle, your user sees progress immediately, and a multi-minute generation completes without a single byte of dead air.

Stream anything long
The SDKs even refuse very large non-streaming max_tokens values because timeouts are near-certain. Use the stream helper and grab the final message at the end.
Budget max_tokens sanely
max_tokens is a hard cap, not a target. Set it to what the task actually needs — a classifier doesn't get 32K tokens to say "billing".
Many minutes? Batch it
If a job is so big you'd babysit the connection, it isn't an interactive request. Send it to the Batch API and poll for the result.

05  Tool schemas that hold up

In Tool use you defined tools that worked on your test prompts. Production tool schemas face a harder exam: thousands of users phrasing things in ways you never imagined. The model picks the right tool with the right arguments only as reliably as your schema teaches it to.

Precise names
verb_noun: search_orders, refund_payment. Never just orders — names are the model's first signal of what a tool does.
Rich descriptions
The model reads descriptions like documentation. Say when to use the tool, what it returns, and when NOT to use it ("for order status only — do not use for refunds").
Enums over free strings
"enum": ["pending", "shipped", "delivered"] beats a free-text status field. Closed sets remove a whole class of invented values.
Few params, sane defaults
Mark only the truly required fields required; give the rest defaults. Every extra mandatory parameter is another chance to get one wrong.
Structured errors back
When a tool fails, return a message the model can act on — "order_id not found; ask the user to confirm it" — not a bare stack trace.
Structured outputs at the end
When the final answer feeds code (not a human), use structured outputs so the response is schema-guaranteed JSON — no regex parsing of prose.
tool_schema.py
tools = [{
    "name": "search_orders",
    "description": (
        "Search a customer's orders by status. Call this when the user asks "
        "about order status, shipping, or delivery dates. Do NOT use it for "
        "refunds or returns — use refund_payment for those. Returns up to "
        "10 orders, newest first."
    ),
    "input_schema": {
        "type": "object",
        "properties": {
            "customer_id": {"type": "string", "description": "Internal customer ID"},
            "status": {
                "type": "string",
                "enum": ["pending", "shipped", "delivered", "any"],
                "description": "Filter by order status; 'any' returns all",
            },
        },
        "required": ["customer_id"],   # status defaults to "any" server-side
    },
}]
The #1 wrong-tool cause gotcha

Vague tool descriptions. When two tools have one-line descriptions like "handles orders" and "handles payments", the model is guessing at the boundary between them. Almost every "the model used the wrong tool" bug is fixed by rewriting descriptions to state explicit when-to-use and when-not-to-use rules.

06  Engineer the bill

You're billed per token, in and out. At prototype scale that's pocket change; at a million requests a day it's a line item the CFO asks about. The good news: the bill is an engineering surface with real levers, and the biggest ones cut cost by 50–90% without touching quality.

LeverSavesWhen it applies
Prompt cachingUp to ~90% on cached inputThe same big context (system prompt, docs, tool list) repeats across requests. Cache the stable prefix once, pay pennies to reread it.
Batch API~50% on everythingWork that doesn't need an answer in seconds — nightly classification, backfills, evals. Submit in bulk, collect within hours.
Model ladderingOften the biggest leverRoute easy calls to Haiku, default traffic to Sonnet, the genuinely hard cases to Opus or Fable 5 — see the model family.
max_tokens budgetsCaps the worst caseOutput tokens cost the most. A hard per-route cap turns "occasionally writes an essay" into a bounded line item.
Trim few-shot examplesInput tokens, every requestFive examples that taught the prototype may do no more than two. Test, then cut — they're paid on every single call.
Build first, optimize second tip

Same rule as in Power features: get it correct on a strong model first, then optimize. A cheap pipeline that's wrong costs infinitely more than an expensive one that's right. Once quality is proven, ladder down model by model and watch your eval scores — stop one rung above where they drop.

Your support-ticket classifier runs millions of requests a day and the bill just exploded. First lever to pull?
Right. Classification is exactly the high-volume, low-difficulty shape Haiku is built for, and a classifier's prompt (instructions + label definitions) is identical on every call — a textbook prompt-caching win. More max_tokens raises the bill, and retries don't change per-request cost at all.

07  Watch it & test it

Two disciplines round out a production deployment, each big enough to be its own guide. Observability: dashboards for latency, error rates, and cost per route, so a creeping 429 rate or a runaway prompt shows up on a graph before it shows up on the invoice. The observability field guide covers logs, metrics, traces, and alerting end to end.

Evals: a fixed test set of real inputs with known-good answers, run automatically whenever you change a prompt, swap a model, or ladder down a tier. Without evals, "did quality hold?" is a vibe; with them, it's a number. The GenAI guide goes deep on building and scoring eval suites.
