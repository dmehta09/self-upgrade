Claude Code · lesson 13

Headless & CI

Everything you've learned still works when nobody is at the keyboard. claude -p turns Claude Code into a scriptable unix tool — one question in, one answer out, pipeable like grep — and CI is where that pays off: review bots, log triage, nightly audits, all running while you sleep.

01  One question in, one answer out

claude -p (alias --print) runs a single query and exits. No REPL, no prompts — it reads stdin, does its work, prints the answer to stdout, and returns an exit code. That means it composes with everything else in your shell:

terminal
# pipe data in, get an answer out
cat error.log | claude -p "what caused this crash? one paragraph"

# or point it at a file with an instruction
claude -p "summarize the breaking changes in CHANGELOG.md for a tweet"
Pairing vs. a note on the desk analogy

Interactive Claude Code is pairing at a desk — you talk, steer, interrupt. Headless is leaving a precise note for a colleague: they read it, do exactly that one thing, leave the answer, and go. The quality of the result is the quality of the note.

02  Pick your output shape

Plain text is great for humans; scripts want structure. --output-format gives you three shapes:

FormatWhat you getUse it for
text (default)Just the answer, as prose.Humans reading a terminal or a log.
jsonOne JSON object: the result plus metadata — cost, duration, session_id, turn count.Scripts and pipelines that parse, branch, and track spend.
stream-jsonA stream of events emitted as Claude works — each tool call, each message.Dashboards, live progress UIs, log processing.
terminal
$ claude -p "list the public endpoints" --output-format json
{
  "type": "result",
  "result": "GET /health, GET /notes, POST /notes, DELETE /notes/:id",
  "total_cost_usd": 0.0214,
  "duration_ms": 8342,
  "num_turns": 3,
  "session_id": "a7f3…"
}

Pipe that through jq -r .result for the answer, or jq .total_cost_usd to watch your budget.

Your script needs the answer and the cost metadata so it can log spend per run. Which flag?
Right. json is the scripting format: the answer and run metadata in one parseable object. text is just prose for humans, and --verbose changes log detail, not the output contract.

03  Permissions when nobody's watching

Interactively, a permission prompt is a conversation. Headless, it's a dead end — so you set the policy up front with flags:

--permission-mode
Set the stance for the whole run. plan is the read-only analysis mode — perfect for review bots that should never touch a file.
--allowedTools / allow rules
Grant exactly the tools the job needs and nothing more — e.g. "Bash(git diff:*)" and Read, scoped tight.
--dangerously-skip-permissions
Auto-approves everything. Only acceptable inside a throwaway sandbox or container with no credentials and no network worth protecting.
ANTHROPIC_API_KEY
The auth story in CI: set it as an env var from your secrets store; no interactive login required.
A headless run can't ask you gotcha

An unanswered permission prompt means a stuck or failed job — there's nobody to click “allow.” Decide the policy before the run: allow exactly what the job needs, deny the rest, and treat any unexpected prompt as a bug in your config, not a reason to skip permissions entirely.

04  The PR review bot

The classic first automation: every pull request gets a Claude review before a human looks at it. The simple path is the official action; the workflow fits in a screen:

.github/workflows/claude-review.yml
name: claude-review
on: pull_request

jobs:
  review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          prompt: |
            Review this PR's diff for bugs, missed edge cases,
            and risky changes. Be specific; cite file and line.
            Post your verdict as a PR comment.
The raw-CLI alternative note

The action is a wrapper; you can do the same with plain steps: install the CLI, run claude -p "review this diff" --output-format json, then post the result with gh pr comment. Same machine, more control over each step.

05  When a script outgrows -p

If your automation needs multi-turn loops, programmatic tool control, a custom system prompt, or its own UI, you've outgrown a shell one-liner. The Claude Agent SDK is the same engine as a library:

triage_bot.py
import anyio
from claude_agent_sdk import query

async def main():
    async for message in query(prompt="Triage today's failed builds and file issues for real bugs"):
        print(message)   # your code sees every step — route it anywhere

anyio.run(main)

Rule of thumb for which tool fits:

One-shot question
claude -p — a note on the desk; the answer is the product.
Pipeline step
claude -p --output-format json — structured result your script parses and acts on.
Long-lived product or agent
The Agent SDK — your loop, your prompts, your UI, the same engine underneath.

06  Rails for robots

An automated run repeats whatever it does — good and bad — on every trigger. Put the rails down first:

Pin versions
Set DISABLE_AUTOUPDATER=1 and install a fixed release (claude install <version>) so CI behavior doesn't change under you overnight.
Deny rules for secrets & infra
Block reads of .env and key files, block deploy/terraform commands — the same deny rules you'd use locally, but non-negotiable here.
Network-restricted runners
A runner that can only reach what the job needs limits the blast radius of any mistake or prompt injection.
Budget caps
Cap max turns and wall time per run, and read total_cost_usd from the json output into your metrics so a runaway loop shows up fast.
Least-privilege tokens
The GitHub token should be able to comment — not merge, not push to main, not touch settings.
Start advisory tip

Let the bot comment for a few weeks before any automation is allowed to change anything. You'll learn its failure modes while the cost of a bad call is one wrong comment, not one wrong commit.

Your CI review bot must never edit code. What actually enforces that?
Right. Same lesson as hooks: prompts are advice, permissions are guarantees. A read-only permission mode makes editing impossible, not just discouraged — and “never” always wants a guarantee.

07  Five one-liners to steal

Changelog
git log --oneline v1.2..HEAD | claude -p "draft changelog entries, grouped by area"
Test triage
cat test-output.log | claude -p "which test failed first, and what's the likely cause?"
Lint decoder
ruff check . 2>&1 | claude -p "explain these errors in plain English, worst first"
PR description
git diff main...HEAD | claude -p "draft a PR description: what changed, why, how to test"
Nightly TODO audit
claude -p "list every TODO and FIXME in src/ with file:line, oldest-looking first" --output-format json — cron it and diff against yesterday's.

Each one is a precise note on the desk. The habit transfers: anything you'd ask interactively, you can script.
