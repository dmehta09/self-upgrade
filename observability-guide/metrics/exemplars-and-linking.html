Metrics · exemplars & linking

Exemplars & cross-signal linking.

A metric spike without a request is a rumor. An exemplar pins a real trace_id to a histogram bucket so Grafana can jump from “p99 is high” to the exact slow trace — then to the logs for that same id.

01 What an exemplar is

An exemplar is a sample attached to a metric data point (usually a histogram bucket) that carries a trace_id (and often span_id) from a real request observed in that bucket.

OpenMetrics and Prometheus 3.x carry exemplars natively; Remote-Write 2.0 preserves them on the way to Mimir/Thanos. OTel SDKs can attach the active span context when recording histogram measurements.

In plain English analogy

A bar chart of wait times with sticky notes on a few bars: “ticket #4821 waited 12 minutes.” The bar (metric) shows the distribution; the sticky note (exemplar) is your passport into the full case file (trace + logs).

OpenMetrics exemplars
Standard way to attach trace references to metric samples. Prometheus scrapes and stores them with the series.
Histogram + exemplars
Best pairing: latency/error histograms keep exemplars in the buckets that hurt (the p99 tail).
Grafana click-to-trace
Exemplar dots on a panel; click opens Tempo/Jaeger for that trace_id.
Not a high-card label
The trace_id lives on the exemplar, not as a Prometheus label — so you do not explode cardinality.

02 Metric ↔ trace ↔ log

Exemplars close the metrics→traces gap. Shared trace_id in structured logs closes traces→logs. Together they are the standard incident cascade.

03 Cardinality: why exemplars beat labels

Putting trace_id or user_id on a metric label creates one series per value — a classic cardinality bomb. Exemplars store the id beside the sample without multiplying series.

Do
Low-cardinality metric labels (service, route, status_class) + exemplars for per-request proof.
Don’t
trace_id, request_id, raw user_id, or full URLs as metric labels.
Detail store
High-cardinality context belongs in spans and structured logs; metrics stay cheap aggregations.
Common trap gotcha

Enabling exemplars in the SDK but forgetting Grafana data-source exemplar configuration (trace data source mapping). You see the metric spike and no dots — the link was never wired in the UI.

Practical tip tip

Prefer exemplars on the latency histogram you alert on. When burn-rate fires, the same panel that pages you should offer a one-click path into Tempo.

You need to jump from a p99 spike to a slow request. What should you attach to the latency histogram?

Right. Exemplars give click-to-trace without the cardinality explosion of per-trace labels.

04 Interview rapid-fire

What is a trace exemplar?warm
Model answer

A sample on a metric data point — typically a histogram bucket — that includes a trace_id from a real request. In Grafana you click the exemplar and open the correlated trace in Tempo. It is part of OpenMetrics and supported in Prometheus 3.x / Remote-Write 2.0.

Say it out loud say it

“A trace_id glued to a histogram point so I can click from p99 straight into Tempo.”

How do you link metrics, traces, and logs without blowing cardinality?core
Model answer

Keep metric labels low-cardinality. Attach exemplars for metric→trace. Put trace_id (and span_id) on structured logs for trace↔log. Never promote unbounded ids to Prometheus labels.

Say it out loud say it

“Exemplars for metrics-to-traces; trace_id in logs; ids never become metric labels.”

Walk the cascade for a sudden error-rate surge.stretch
Model answer

RED dashboard shows error rate up → click an error exemplar → Tempo waterfall shows the failing span → jump to Loki with that trace_id for the exception payload → optionally open Pyroscope if the failure is actually a timeout from CPU saturation. Fix is informed by code + logs, not by the aggregate alone.

Say it out loud say it

“RED → exemplar → Tempo → Loki on the same trace_id — that’s the cascade.”
