Traces · spans & propagation

Spans & context propagation.

A trace is a tree of spans — timed checkpoints that follow a request across every service it touches. The magic glue that stitches them together is context propagation: a tiny header passed with every outbound call.

01 Anatomy of a span

A span = one timed operation with a name, start/end timestamps, attributes, and a status code.

Every span carries a trace_id (shared across the whole request) and a span_id (unique to this operation). A parent_span_id links child to parent, building the tree.

In plain English analogy

A span is one stamped checkpoint in parcel tracking — "left warehouse at 10:02, arrived sorting facility at 10:47." The trace is the entire delivery journey: every scan, every hand-off, every leg, linked by the same tracking number.

trace_id
128-bit ID shared by every span in the request. The "tracking number."
span_id
64-bit ID unique to this operation. The "scan event."
parent_span_id
Points to the calling span. Absent on the root span.
attributes
Key-value metadata: http.method, db.statement, user_id, etc.
status
OK | ERROR | UNSET. Set ERROR on exceptions.
events
Timestamped log-like notes on a span (e.g., "cache miss at +12 ms").

03 Context propagation across services

When a service makes an outbound HTTP call, the OTel SDK injects the current trace context as a traceparent header (W3C Trace Context standard). The downstream service extracts it and creates a child span — linking its work into the same trace tree.

W3C traceparent header
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             ^^ ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ ^^^^^^^^^^^^^^^^ ^^
             version   trace_id (128-bit hex)   parent_span_id   flags
1

Inject (client side)

OTel SDK writes traceparent (and optional tracestate) into the outbound request headers automatically via an instrumentation library.

2

Extract (server side)

Receiving service's OTel SDK reads the header and creates a new span with parent_span_id = the caller's span_id.

3

Export

Both services export their spans via OTLP to a Collector or backend. The backend reconstructs the tree using the shared trace_id.

Common trap gotcha

Async boundaries silently break propagation. If you spawn a goroutine, thread-pool task, or background job without explicitly carrying the context, the child span gets a new random trace_id instead of inheriting the parent's — and your trace appears as two disconnected fragments in the UI. Always pass the context object explicitly into async work.

04 Span kinds & semantic conventions

OTel defines span kinds to model the role of each operation. Backends use these for service graph topology and latency attribution.

KindWhat it representsCommon attributes
SERVERInbound RPC/HTTP handlerhttp.method, http.route, http.status_code
CLIENTOutbound call (HTTP, gRPC)server.address, url.full
PRODUCERPublishes to a queue/topicmessaging.system, messaging.destination
CONSUMERReceives from a queue/topicmessaging.operation

Semantic Conventions v1.41 — HTTP and database attributes are stable; use OTEL_SEMCONV_STABILITY_OPT_IN=http to opt into the stable HTTP names.

Service A calls Service B over HTTP. Which span kind should Service A's outbound span be?

Right. CLIENT means "outbound call." The receiving Service B creates a SERVER span. This pairing tells the backend's service graph who called whom.

05 Interview rapid-fire

What's the difference between a span and a trace?warm
Model answer

A span is a single timed operation with a name, timestamps, and attributes. A trace is the full tree of spans that share one trace_id — it represents a complete request end-to-end, stitching together work from every service that touched it.

Say it out loud say it

"A span is one checkpoint — a single service doing one thing. A trace is the whole journey: all the checkpoints linked by the same tracking ID."

How does context propagation work across microservices?core
Model answer

The OTel SDK injects the current trace_id and span_id into outbound request headers as a W3C traceparent. The downstream service extracts that header, making its new span a child of the caller's span. Both export their spans to the backend via OTLP, which reconstructs the tree.

Say it out loud say it

"The SDK piggybacks the trace context on every outbound request header. The next service reads the header and becomes a child span, so all services end up in the same trace tree."

Follow-ups to expect
  • What happens if the header is missing?
  • How does this work across async queues?
  • What's the difference between traceparent and tracestate?
Why might a trace appear split into two disconnected trees in your backend?core
Model answer

Broken context propagation. The most common causes: an async task was spawned without carrying the context (a new trace_id is minted), a service in the chain doesn't have OTel instrumentation and drops the header, or a reverse proxy strips unknown headers.

Say it out loud say it

"The traceparent header got dropped somewhere — a thread boundary, an uninstrumented service, or a proxy that strips custom headers. Without it, the downstream span starts a brand-new trace."
