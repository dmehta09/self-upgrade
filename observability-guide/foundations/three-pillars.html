Foundations · three pillars

The three pillars + signals.

Logs, metrics, and traces each answer a different class of question at a different cost. Knowing which pillar to reach for — and when they overlap — is the first mental model every observability interview probes.

01 Three tools, three questions

Logs = narrative events. Metrics = cheap aggregatable numbers. Traces = causal path across services.

Each pillar answers a different first question: What happened? (logs) → How many / how fast? (metrics) → Why did this request take so long? (traces). A mature system emits all three and correlates them via a shared trace_id.

In plain English analogy

Logs are your diary — every event recorded in narrative detail. Metrics are your dashboard gauges / vital signs — heart rate, blood pressure, a single number you glance at. Traces are a package-tracking timeline — "left warehouse → in transit → customs → delivered" for one specific request.

02 Pillars compared

Each pillar has a different cost driver and a different primary question it answers best. Use the table as a quick decision framework.

Pillar Answers Cost driver Example question Best tool
Logs What happened & when? Volume × retention "What was in the request body when the error occurred?" Loki, Splunk
Metrics How many / how fast / trending? Cardinality (unique label combos) "What is p99 latency over the last 7 days?" Prometheus, Datadog
Traces Why did this specific request slow down? Sampling rate × span size "Which downstream service added the most latency to order #42?" Tempo, Jaeger v2, Honeycomb

03 When to reach for each

Reach for logs when…
You need the raw narrative: payloads, error messages, audit trails. Expensive for high-throughput paths — sample or use structured events.
Reach for metrics when…
You need aggregates over time: rates, percentiles, counts. Cheap per data point but scale with label cardinality, not request volume.
Reach for traces when…
You're chasing latency or failure across service boundaries. Distributed tracing is the only tool that shows the causal path end-to-end.
Common trap gotcha

The three pillars are converging. Honeycomb's "wide structured events" model shows that a single rich event can be indexed as a trace span, aggregated like a metric, and queried like a log. OTel's goal is one pipeline for all signals — treat the pillars as conceptual categories, not rigid tool buckets.

04 Emerging signals: beyond the three

Two newer signal types are becoming mainstream: wide structured events and Profiles (continuous profiling).

Wide structured events
A single JSON event with 100+ attributes per request — no loss of cardinality, no pre-aggregation. Popularized by Honeycomb. OTel spans are effectively this.
Profiles (4th OTel signal)
Continuous CPU/memory flame graphs per service, via Pyroscope / OTel Profiles (public alpha, Mar 2026). Answers: "which code path is burning CPU?" without a profiler session.

A team says "we don't need traces — we already have detailed logs." What critical capability are they missing?

Right. Logs tell you what happened inside one service. Traces show you the end-to-end causal chain — service A called B which called C — and which hop added latency. You cannot reconstruct that from per-service logs alone.

05 Interview rapid-fire

Walk me through logs vs metrics vs traces — what does each answer?core
Model answer

Logs are discrete narrative events — rich detail, high cost at volume. Metrics are cheap aggregatable numbers over time — great for dashboards and alerts, but limited to pre-defined dimensions. Traces follow a single request across every service it touches — the only way to answer "which hop is slow?" in a distributed system.

Say it out loud say it

"Logs answer 'what happened,' metrics answer 'how fast or how many,' traces answer 'why did this request take so long across services.' Different cost model for each."

What drives cost for each pillar?core
Model answer

Logs cost ≈ volume × retention — the more bytes you ship and keep, the more you pay. Metrics cost ≈ cardinality — the number of unique label-value combinations, not the request volume. Traces cost ≈ sampling rate × span size — most teams sample aggressively to keep costs under control.

Say it out loud say it

"Logs: bytes in and retained. Metrics: cardinality — it's not request volume that hurts, it's unique label combinations. Traces: how aggressively you sample."

Are the three pillars separate — or is the model changing?stretch
Model answer

They're converging. "Wide structured events" — a single rich event per request with many attributes — can be indexed as a trace, aggregated like a metric, and queried like a log. OTel's single-wire protocol (OTLP) reflects this: one pipeline for all signals. Honeycomb pioneered this model; OTel formalizes it. Profiles is now a 4th official signal.

Say it out loud say it

"The boundaries are blurring. A single wide structured event can be treated as a trace, aggregated as a metric, or searched as a log. OTel's one-pipeline model reflects that trend."
