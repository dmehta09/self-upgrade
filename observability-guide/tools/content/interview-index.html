Interview prep · method

How observability interviews work.

Interviewers probe mental models, trade-offs, and how you walk through a real incident. They rarely ask trivia — they want to hear you reason from signal to root cause, out loud.

01 What interviewers actually test

Three categories: conceptual trade-offs, incident walkthroughs, and design for observability.

In plain English analogy

Think of observability as a hospital triage system. Metrics are the vital-sign monitor that screams "something is wrong." Traces are the MRI that shows exactly which organ has the problem. Logs are the surgeon's notes that explain why. An interviewer wants to know you use all three in that order.

02 The three-signal narration framework

Metrics tell you SOMETHING is wrong → traces localize WHERE → logs explain WHY.

Anchor every incident story to this progression. It shows you know the purpose of each signal, not just their definitions.

03 Core trade-offs to have ready

These come up in every senior observability interview. Know the short answer for each.

Push vs pull
Pull (Prometheus scrape) = simpler auth + no retry storms. Push = works behind firewalls + ephemeral jobs. OTLP supports both.
Head vs tail sampling
Head sampling decides at trace start — cheap, but misses rare slow/error traces. Tail sampling buffers the full trace then decides — keeps the interesting ones, costs memory.
Cardinality
High-cardinality labels (user_id, request_id) explode the time-series count. Logs and traces handle high cardinality; metrics don't.
Structured vs unstructured logs
Structured logs (JSON key-value) are machine-parseable — you can filter by service=checkout status=500. Unstructured requires regex, which is fragile and slow.
SLI vs SLO vs SLA
SLI = the measurement. SLO = the target. SLA = the contract with the user (usually looser than SLO to give a buffer).

04 How to tell an incident story (STAR)

Use STAR to narrate incident walkthroughs — it keeps you focused and shows structured thinking.

S

Situation

Set context: which service, what the SLO is, what the alert said. "Our checkout p99 SLO is 500 ms; a multi-burn alert fired at 14× the 1-hour window."

T

Task

What you needed to find out: "Is this user-impacting? Which endpoint? What's the root cause?"

A

Action

Your signal cascade: RED dashboard → exemplar trace → slow span → correlated log. Name the specific tools: Grafana, Tempo, Loki.

R

Result

What you fixed and how fast the error budget recovered. Tie back to the SLO.

06 Meta interview questions

How would you add observability to a completely un-instrumented service?core
Model answer

Start with the boundaries: instrument HTTP in/out with the OTel SDK (auto-instrumentation often covers frameworks like Django or Express). That gets you traces + basic RED metrics for free. Then add structured logging with a trace_id field for correlation. Finally, define SLIs for the service's SLO — what's the right success criterion? — and add a counter and histogram for those specific signals.

Say it out loud say it

"I'd start with OTel auto-instrumentation at the boundary — traces and RED metrics with near-zero code changes. Then structured logs with trace_id. Then define SLIs and wire up SLO dashboards."

Follow-ups to expect
  • What if the service is a legacy monolith with no framework?
  • How do you avoid instrumenting everything at once?
What's the difference between observability and monitoring?warm-up
Model answer

Monitoring is alerting on known failure modes via pre-defined dashboards and thresholds — you know the question before you ask it. Observability means you can ask novel questions about system state from its outputs (logs, metrics, traces) without predicting the failure mode in advance. Observability subsumes monitoring; it's more powerful but requires richer instrumentation.

Say it out loud say it

"Monitoring answers known questions on a schedule. Observability lets you ask unknown questions ad-hoc. You need both, but observability is the foundation for debugging anything you didn't predict."
