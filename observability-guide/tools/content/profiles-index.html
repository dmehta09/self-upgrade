Profiles · Module Overview

Profiles — the 4th signal.

Logs tell the story, metrics cheaply ask “how much?”, traces show causality. Profiles answer the question the other three can’t: which lines of code are burning CPU and allocating memory right now?

01 The fourth pillar

A profile is a statistical sample of where a process spends time or memory — usually rendered as a flame graph. In 2026, OpenTelemetry treats Profiles as a first-class signal alongside logs, metrics, and traces.

Classic one-shot profiling (pprof, perf record, a heap dump) is a deliberate session you start when something already looks wrong. Continuous profiling flips that: the agent samples lightly all the time, so when p99 spikes you already have the evidence.

In plain English analogy

Metrics say the restaurant is busy. Traces show which tables waited longest. A profile is the kitchen camera: you see the exact station — prep, grill, or plating — that is the bottleneck, not just that tickets are slow.

CPU profile
Samples the call stack on a timer. Wide frames = hot functions. Answers: “where is the CPU going?”
Heap / alloc profile
Samples allocations (and often retained memory). Answers: “what is allocating, and what is leaking?”
Flame graph
Stacked visualization: x-axis = proportion of samples, y-axis = stack depth. Width, not height, means cost.
OTel Profiles
The fourth signal in the OpenTelemetry data model — public alpha (Mar 2026). Same OTLP pipeline as the other signals.

02 Continuous vs one-shot pprof

Both produce flame graphs. The difference is when you collect and how you correlate.

One-shot (pprof / perf)Continuous (Pyroscope / OTel Profiles)
WhenYou SSH in after the alertAlways on; query any window later
OverheadCan be high for the sessionDesigned low (~1–5% CPU with eBPF)
CoverageOne pod, one momentFleet-wide time series of profiles
CorrelationManual guessworkLink to trace_id / service labels
Best forDeep dive on a known suspectIncidents, regressions, capacity trends
Practical tip tip

Keep one-shot tools in your belt for language-specific deep dives (Go pprof heap objects, Java flight recorder). Use continuous profiling as the default “what changed?” signal after a deploy.

03 Profiles ↔ traces

A slow span tells you which operation hurt. A profile tells you which function inside that operation burned the time.

Modern stacks attach profile samples to the same resource labels as traces (service.name, deployment) and, where supported, to active span context. In Grafana you jump from a hot Tempo span into a Pyroscope flame for that service and time window.

Metrics detect, traces localize the service/span, profiles name the functions. Without the third hop you stop at “orders is slow.”
Common trap gotcha

Reading flame-graph height as cost. Height is stack depth (how nested the call is). Width is the proportion of samples — that is the cost. A tall thin spike is usually not your bottleneck.

p99 jumped after a deploy. Traces show orders-svc is slow. What does a profile uniquely add?

Right. Metrics and logs won’t name the function. Traces name the span. Profiles name the code paths under that span’s process.

05 Interview rapid-fire

What is the fourth observability signal and why was it added?warm
Model answer

Profiles — continuous CPU/memory sampling exported through OpenTelemetry (public alpha Mar 2026). Logs, metrics, and traces still leave a gap between “this span is slow” and “this function is hot.” Profiles close that gap without requiring an ad-hoc profiler session during the incident.

Say it out loud say it

“Profiles are the fourth pillar — always-on flame graphs so you can name the hot code path, not just the slow span.”

How do profiles relate to traces in a modern Grafana stack?core
Model answer

You typically start from a RED or latency spike, follow an exemplar into Tempo, identify the slow service/span, then open Pyroscope for that service and time range. Shared resource attributes (and increasingly span-linked samples) make the jump mechanical instead of “guess which pod and attach pprof.”

Say it out loud say it

“Metric → exemplar → Tempo span → Pyroscope flame for the same service and window.”

When would you still use a one-shot profiler instead of continuous profiling?stretch
Model answer

When you need language-runtime detail continuous agents don’t expose yet — Go heap object graphs, Java JFR events, allocation sites with full type info, or a short high-frequency capture on a single suspect pod. Continuous profiling is the always-on map; one-shot is the microscope.

Say it out loud say it

“Continuous for fleet regressions; one-shot when I need runtime-deep detail on one process.”
