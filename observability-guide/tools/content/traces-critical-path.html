Reading a trace: the critical path.

A trace waterfall is more than a pretty picture — it's a latency budget broken into named segments. Knowing how to find the critical path is the skill that turns a 2-second trace into a one-line root cause.

01 What is the critical path?

The critical path is the chain of spans that directly determines end-to-end latency — shortening anything off this chain has zero effect on the user.

Spans run serially or in parallel. Parallel spans overlap in time; only the longest sibling matters. The critical path = the continuous chain from root span to leaf where no parallel shortcut exists.

In plain English analogy

The critical path is the longest pole in a tent. The tent height is set by that one pole — shortening any other pole does nothing. Lowering the roof means shortening that specific pole.

02 Reading the waterfall

The trace below shows a checkout request. The Redis cache read and the inventory gRPC call run in parallel — but inventory takes longer, so it owns the critical path. The payment call is strictly serial after inventory completes.

Serial span
Starts after the previous one completes. Adds its full duration to end-to-end latency.
Parallel span
Overlaps with a sibling. Only the slowest sibling contributes to the critical path.
Critical span
Any span on the critical path — shortening it directly improves user latency.

03 The N+1 pattern

A dead giveaway in traces: a parent span spawning N identical short sequential spans — usually DB queries in a loop. The loop is invisible in metrics (aggregate latency looks reasonable) but jumps off a trace waterfall.

N+1 (loop)
orders = db.query("SELECT id FROM orders")
for o in orders:
    # N round-trips
    items = db.query(
        "SELECT * FROM items WHERE order_id=?", o.id
    )
Batch (1 query)
orders = db.query("SELECT id FROM orders")
ids = [o.id for o in orders]
# Single round-trip
items = db.query(
    "SELECT * FROM items WHERE order_id = ANY(?)", ids
)
Common trap gotcha

Optimizing a span that isn't on the critical path has zero effect on user-visible latency. In the checkout trace above, halving the Redis read from 40 ms to 20 ms saves nothing — it was already finishing before inventory did. Always identify the critical path before optimizing.

04 Tail latency & fan-out

When a service fans out to N downstream calls in parallel and waits for all of them, the response time = max(all N), not the average. One slow dependency drives every request's tail latency.

Reducing shard-1–3 to 10 ms saves nothing. Only shard-4 matters.

A service fans out to 5 parallel DB shards: times are 28 ms, 31 ms, 29 ms, 180 ms, 25 ms. What is the end-to-end latency contribution from this fan-out?

Right. Parallel calls complete when the last one finishes. The 180 ms shard sets the pace — the other four results just sit waiting. This is why one hot shard or GC pause causes p99 spikes across your whole service.

05 Interview rapid-fire

How do you find the root cause of a latency spike using a trace?core
Model answer

Find the critical path — the chain of spans from root to leaf with no parallel shortcut. Whichever span on that chain is longest is your bottleneck. Look at its attributes: is it a slow query, a network hop, a lock wait? That's your root cause.

Say it out loud say it

"I walk the trace waterfall looking for the critical path — the serial chain. The widest bar on that chain is my bottleneck. Everything else is noise until I've dealt with that one."

What is an N+1 query and why does it matter in distributed tracing?core
Model answer

An N+1 is a loop that issues one query per item instead of fetching all items in a single batch. It's invisible in aggregated metrics but shows up immediately in a trace as N identical sequential DB spans on the critical path. Fix: JOIN or batch query.

Say it out loud say it

"It's when you loop and fire one DB call per row instead of one batch. Metrics show it as 'slightly slow DB'; traces show it as 30 identical SELECT spans in a waterfall — the fix is obvious the moment you see it."

Why can optimizing a non-critical span waste engineering effort?warm
Model answer

If a span runs in parallel with a slower sibling, it's already done by the time the bottleneck finishes. Making it even faster doesn't change when the parent span ends. Only work on the critical path has observable impact on end-to-end latency.

Say it out loud say it

"If it's off the critical path, it's already finishing before the bottleneck. Speed it up and the user notices nothing. Always trace the critical path before picking what to optimize."
