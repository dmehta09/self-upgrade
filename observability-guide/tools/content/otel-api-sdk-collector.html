API, SDK & Collector.

OTel splits responsibilities across three layers so you can change your backend, sampling policy, or export destination without touching application code. All three speak one protocol: OTLP.

01 The three layers

The API defines what to call. The SDK defines what happens when you call it. The Collector decouples your app from any backend.

This separation is deliberate. A library can depend on the API (stable, no-op by default) without pulling in a concrete SDK. Ops teams swap the SDK config or Collector pipeline without asking developers to change a line of code.

In plain English analogy

The API is the standard wall-socket shape — every appliance uses it. The SDK is the wiring behind your wall — it decides voltages, circuit breakers, and routing. The Collector is a smart power strip: plug any socket into it, and it routes current to whichever outlet (backend) you want, without rewiring the house.

OTel API
Language interfaces for creating spans, recording metrics, emitting logs. No-op when no SDK is present — safe for library authors to call unconditionally.
OTel SDK
The concrete implementation: sampling decisions, batching, resource detection, export via OTLP.
OTel Collector
A standalone process (or sidecar) that receives → processes → exports telemetry. Decouples your app from every backend.
OTLP
OpenTelemetry Protocol — the single wire format for all signals (gRPC or HTTP/JSON). Every layer speaks it.

03 Why the Collector matters

Skipping the Collector and pointing your SDK directly at a vendor endpoint is the most common OTel mistake. It looks simpler — until you need to add a second backend, apply sampling, or switch vendors.

Anti-pattern — direct export

SDK → Vendor A endpoint. Changing backend = edit every service's config. No central sampling, no PII scrubbing, no fan-out.

Better — Collector in the middle

SDK → Collector → any backend(s). Add a second exporter in one YAML block. Apply tail sampling once, centrally. Swap vendors with no app redeployment.

Common trap gotcha

Exporting directly to one vendor's OTLP endpoint couples every service to that vendor. When you add a second backend (e.g., a Tempo sidecar for traces and Datadog for alerts), you have to touch every service. Put the Collector between them from day one.

Your team wants to send traces to both Grafana Tempo and Datadog simultaneously. Where is the minimal-change place to do this?

Right. The Collector is the single fan-out point. One exporter config change sends the same telemetry to multiple backends — no service restarts required.

04 Interview rapid-fire

What's the difference between the OTel API and the OTel SDK?core
Model answer

The API is the interface — the calls you make in your code. It's a no-op if nothing else is loaded, which makes it safe for library authors. The SDK is the concrete implementation that wires up sampling, batching, and export. You ship the API with your library; your app configures the SDK at startup.

Say it out loud say it

"The API is the socket shape — safe for libraries to use, does nothing on its own. The SDK is the wiring that makes it actually work: sampling, batching, OTLP export."

Why run an OTel Collector instead of exporting directly from the app?core
Model answer

The Collector decouples your app from any specific backend. It lets you apply tail sampling, enrichment, and PII scrubbing centrally, fan out to multiple backends from one config change, and absorb backend outages with a retry buffer — none of which is practical if every service talks directly to a vendor endpoint.

Say it out loud say it

"The Collector is the swap point. I can add a backend, change sampling, or scrub PII in one place — without redeploying any application."

Follow-ups to expect
  • What are the Collector's three stages? (Receivers → Processors → Exporters.)
  • What protocol does it speak? (OTLP — gRPC or HTTP.)
What is OTLP and why does it matter?warm
Model answer

OTLP (OpenTelemetry Protocol) is the single wire format for all three OTel signals — traces, metrics, and logs — over gRPC or HTTP/JSON. Before OTLP every vendor had its own agent format; OTLP means any OTel-instrumented app can talk to any OTLP-capable backend without format translation.

Say it out loud say it

"OTLP is the one wire protocol for all OTel signals. It ended the era where each vendor needed its own proprietary agent format."
