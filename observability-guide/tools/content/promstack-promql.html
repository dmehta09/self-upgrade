Prometheus & Grafana · PromQL

PromQL, hands-on.

PromQL is the query language for Prometheus time-series data. Learn five patterns — selectors, rate(), aggregations, percentiles, recording rules — and you can answer almost any metrics question an interviewer throws at you.

01 The mental model

PromQL is SQL for time series: you select a metric, filter by labels, apply functions, and aggregate. The key distinction from SQL is the time dimension — every result is a vector of current values or a range of values over a window.

Two core types: an instant vector (one value per matching series, at one point in time) and a range vector (a window of values, like [5m]). Functions like rate() require a range vector as input.

In plain English analogy

SQL lets you SELECT rows from a table and GROUP BY a column. PromQL does the same but every "row" is a time-stamped sample and your "columns" are labels. The range window ([5m]) is like saying "give me the last 5 minutes of rows" before you aggregate.

Instant vector
http_requests_total{status="500"} — one latest value per matching series.
Range vector
http_requests_total{status="500"}[5m] — all samples in the last 5 minutes per series. Required by rate(), increase().
Scalar
A single number — e.g. 1024 or the result of arithmetic.

02 Selectors, matchers, and rate()

Label matchers filter which series you get. rate() turns a monotonically increasing counter into a per-second rate — the most useful function in PromQL.

selectors.promql
# Exact match
http_requests_total{service="checkout", status="200"}

# Regex match — all 5xx errors
http_requests_total{status=~"5.."}

# Negative match — exclude internal health checks
http_requests_total{path!="/healthz"}

# Rate of requests over a 5-minute window (per second)
rate(http_requests_total[5m])
rate() needs a counter, not a gauge gotcha

rate() computes the per-second increase of a monotonically increasing counter. Applying it to a gauge (like memory_bytes, which can go up and down) produces nonsense. Use avg_over_time() or delta() for gauges.

03 Aggregation with sum by

Raw series are per-instance. sum by (...) collapses them into meaningful aggregates — total RPS by service, error rate fleet-wide, etc.

aggregation.promql
# Total RPS across all instances, grouped by service
sum by (service) (rate(http_requests_total[5m]))

# Error ratio — errors / total, by service
sum by (service) (rate(http_requests_total{status=~"5.."}[5m]))
/
sum by (service) (rate(http_requests_total[5m]))
Don't sum before rate() gotcha

Always apply rate() first, then sum by. Summing counters across instances before computing the rate gives wrong results whenever an instance restarts — the counter resets to zero and the sum jumps.

Which expression correctly computes the per-second request rate summed across all pods of the api service?

Right. rate() must operate on individual series before aggregation. Summing the raw counter first and then rate-ing would produce incorrect results when any pod restarts.

04 Percentiles & recording rules

Latency percentiles require a histogram metric. histogram_quantile() reconstructs a percentile estimate from the bucket counts. Recording rules precompute expensive queries so dashboards load instantly.

percentiles.promql
# p95 request latency by service
histogram_quantile(0.95,
  sum by (service, le) (
    rate(http_request_duration_seconds_bucket[5m])
  )
)
recording-rule.yaml
groups:
  - name: slo_precompute
    rules:
      - record: job:http_requests_total:rate5m
        expr: |
          sum by (service) (
            rate(http_requests_total[5m])
          )
le label
Histogram buckets carry an le (less-than-or-equal) label. histogram_quantile reads these bucket counts to interpolate the requested percentile.
Recording rule
Prometheus evaluates the expression on a schedule and stores the result as a new metric name. Dashboards query the cheap pre-built metric instead of recomputing every load.

05 Interview rapid-fire

What's the difference between an instant vector and a range vector in PromQL?core
Model answer

An instant vector gives one current value per matching series. A range vector (with a duration selector like [5m]) gives a set of timestamped samples over that window — it's the required input for functions like rate() that need to measure change over time.

Say it out loud say it

"Instant is a snapshot; range is a window. Rate needs the window so it can see how much the counter moved."

How do you compute a p95 latency in Prometheus?core
Model answer

You need a histogram metric (with _bucket, _count, _sum). Apply rate() to the bucket series over a window, then pass it to histogram_quantile(0.95, sum by (le) (...)). The le label (bucket upper bound) is required.

Say it out loud say it

"Rate the histogram buckets, sum by le, then histogram_quantile of 0.95."

Model answer

Recording rules let Prometheus evaluate an expression on a schedule and store the result as a new time series. Use them for expensive aggregations that dashboards query repeatedly — like pre-computing per-service error rates. Dashboards hit the cheap pre-built metric instead of re-executing the heavy query on every load.
