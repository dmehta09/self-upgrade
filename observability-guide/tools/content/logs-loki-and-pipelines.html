Logs · Loki & log pipelines

Loki & log pipelines.

Loki stores logs cheaply by indexing only a small set of labels and compressing everything else as raw chunks. You query the body with LogQL — fast, affordable, and natively integrated with Grafana’s metrics and traces.

01 The Loki storage model

Loki indexes labels (a handful), stores log lines as compressed chunks, and searches content at query time with LogQL.

Traditional log backends full-text-index every word. That’s powerful but expensive. Loki trades index size for storage cost: label queries are fast; content search is a grep over compressed chunks.

In plain English analogy

A library that only indexes shelf labels — floor, row, section — not every word in every book. Finding a shelf is instant. Once you’re on the right shelf, you skim pages (grep the chunk). You trade some search speed for a fraction of the index cost.

Labels
Low-cardinality metadata used to route and filter chunks. Examples: app, env, region. Keep to <10 per stream.
Chunks
Compressed, time-ordered log lines stored in object storage (S3/GCS). Cheap to store; scanned at query time.
Streams
A unique combination of labels — e.g., {app="checkout", env="prod"}. One stream = one chunk sequence.
LogQL
Loki’s query language. First select streams by label, then filter/parse the body.

02 LogQL in one minute

Every LogQL query starts with a stream selector in {}, then pipes the body through filters and parsers.

The two-stage structure mirrors Prometheus: first narrow to the right streams (cheap, index-based), then process the body (content scan).

logql-examples
# All logs from checkout that contain "error"
{app="checkout"} |= "error"

# Parse JSON body, filter by status field
{app="checkout"} | json | status = "500"

# Count errors per minute (metric query)
sum(rate({app="checkout"} |= "error" [1m]))
1

Stream selector

{app="checkout"} — hits the label index; returns matching chunk addresses. This is O(labels), not O(log-lines).

2

Line filter

|= "error" — scans decompressed chunk content; fast substring match.

3

Parser + field filter

| json | status = "500" — parse JSON fields from the body, then filter on extracted values.

High-cardinality labels will destroy you gotcha

Using user_id, request_id, or trace_id as a Loki label creates a unique stream per value — millions of streams, index explosion, and query times that collapse. Keep labels low-cardinality (app, env, region). Put user_id inside the log body and filter it with | json | user_id = "42".

04 Cost control & vendor landscape

Cost = ingestion volume × retention. Control both, and avoid high-cardinality label explosion (the same trap as metrics).

Retention
Set per-stream or globally. Hot/warm/cold tiers: recent data on fast storage, old data on cheap object storage. Drop noisy DEBUG streams in prod.
Sampling / filtering
Drop or downsample high-volume INFO lines in Alloy before they reach Loki. Keep all WARN/ERROR.
Label cardinality
Same trade-off as Prometheus cardinality — N label values = N streams. High-cardinality labels kill performance and cost.

A teammate proposes adding user_id as a Loki label so they can filter logs by user instantly. What’s the problem?

Right. The cardinality trap: a unique label value per user creates a unique stream per user. Put user_id in the log body and use | json | user_id = "42" — slightly slower, but the index stays small and healthy.

05 Interview rapid-fire

How does Loki differ from Elasticsearch for log storage?warm
Model answer

Loki indexes only the label set, not the log body. This makes storage very cheap (compressed chunks in object storage) but shifts search cost to query time. Elasticsearch full-text-indexes every token, so arbitrary field searches are fast but storage is expensive and operational overhead is high. The trade-off is index cost vs. query flexibility.

Say it out loud say it

“Loki indexes only the labels, not the body — cheap to store but you grep chunks at query time. Elastic indexes everything — fast queries, expensive storage.”

Why are high-cardinality Loki labels dangerous, and how do you fix it?core
Model answer

Each unique label combination creates a separate stream. A million users as a label means a million streams — the label index explodes, ingestion slows, and queries time out. Fix: put high-cardinality values (user_id, request_id) in the log body, not in labels. Then filter them at query time with | json | user_id = "42".

Say it out loud say it

“High-cardinality labels blow up the index. Keep labels like app and env — put user_id in the log body and filter it in the query.”

Your log ingestion costs are too high. What levers do you pull?stretch
Model answer

Four levers: (1) level filtering — drop DEBUG entirely in production at the Alloy pipeline stage; (2) sampling — downsample high-volume INFO lines for noisy services; (3) retention — shorten retention for low-value streams; (4) label audit — remove high-cardinality labels creating unnecessary stream proliferation. Profile ingestion by service first to find the 20% driving 80% of cost.

Say it out loud say it

“Drop DEBUG in prod, sample noisy INFO, shorten retention, and audit labels for cardinality blowouts. Find the noisiest service first.”
