OpenTelemetry · semantic conventions

Semantic conventions.

Semantic conventions are the agreed-upon names for telemetry attributes — http.request.method, db.system, service.name. They turn ad-hoc attribute names into a portable vocabulary that every dashboard, alert, and query can rely on.

01 Why naming matters

Without conventions, one team writes method, another writes http_verb, a third writes request.method. No single dashboard works for all three.

Semantic conventions fix this by standardising attribute names across every language and vendor. When your Python service and your Go service both emit http.request.method, one dashboard template works for both.

In plain English analogy

Every country agreeing to call it "city" — not town, municipality, commune, or ort — so that one address form works everywhere in the world. Semantic conventions are that agreement for telemetry attributes: one canonical name, all backends and dashboards just work.

Resource attributes
Who emitted the telemetry: service.name, service.version, host.name, k8s.pod.name. Set once at SDK startup, attached to every span/metric/log.
Span / metric attributes
About the operation: http.request.method, http.response.status_code, db.system, db.operation.name. Set per span or metric data point.
~v1.41 (current)
HTTP, database, and messaging attribute groups are stable. The gen_ai group (LLM/AI operations) is experimental. New groups start experimental, graduate to stable.

02 Common attributes in practice

These are the attributes interviewers expect you to recall. They're the basis for every SLO query, every latency dashboard, every error-rate alert.

service.name
Resource. The logical name of your service — the primary grouping key in most backends.
http.request.method
Span. GET, POST, etc. Stable (v1.41). Old name was http.method — migration opt-in via env var.
http.response.status_code
Span. HTTP status integer. Use to compute error rates.
url.path
Span. The request path. Watch for high cardinality — templatise paths like /user/{id}, not raw values.
db.system
Span. Database type: postgresql, redis, mysql. Stable (v1.41).
db.operation.name
Span. SQL verb or operation: SELECT, INSERT.
messaging.system
Span. Message broker: kafka, rabbitmq, sqs. Stable (v1.41).
gen_ai.system
Span. LLM provider: openai, anthropic. Experimental — subject to change.

03 Stability tiers & migration

OTel attribute groups graduate through stability tiers. Stable groups get a long-term compatibility guarantee; experimental groups can still break between versions.

Common trap gotcha

Inventing custom attribute names — myapp.http_method, request_verb — breaks shared dashboards and alert templates the moment any other service or team touches the same data. Even if it "works" locally, no vendor template will pick it up, and cross-service queries silently return partial results.

Heads up note

Migrating from old HTTP attribute names (e.g., http.method) to the stable v1.41 names (http.request.method) is opt-in per the OTel spec — set OTEL_SEMCONV_STABILITY_OPT_IN=http to start emitting the new stable names without a hard cutover.

Your new Python service emits http_method. Your Go service emits http.request.method. What breaks?

Right. Backends store whatever you send. If two services use different attribute names for the same concept, queries and dashboards built on the canonical name return incomplete data — silently. Semantic conventions exist precisely to prevent this.

04 Interview rapid-fire

What are OTel semantic conventions and why do they matter?core
Model answer

Semantic conventions are standardised attribute names defined by OTel — things like http.request.method and db.system. They matter because they make telemetry portable: any dashboard, alert, or query built on those names works across every language, SDK, and backend without custom mapping. Without them, every team invents its own names and shared tooling breaks.

Say it out loud say it

"They're the agreed vocabulary for attribute names. If every service calls the HTTP method 'http.request.method', one dashboard template works for all of them — across languages and backends."

Follow-ups to expect
  • What groups are stable today? (HTTP, database, messaging in ~v1.41.)
  • What's experimental? (gen_ai, Profiles.)
What's the difference between resource attributes and span attributes?core
Model answer

Resource attributes describe who emitted the telemetry — the service, host, pod, or environment. They're set once at SDK startup and attached to every span, metric, and log. Span (or metric) attributes describe what happened in a specific operation — the HTTP method, DB system, status code. They vary per data point.

Say it out loud say it

"Resource attributes are identity — who sent this: service name, host, pod. Span attributes are context — what happened in this operation: the HTTP method, status code, DB system."

OTel is adding a 4th signal beyond traces, metrics, and logs. What is it and where is it today?stretch
Model answer

Profiles is the 4th signal — continuous CPU and memory profiling integrated into the OTel pipeline. It reached public alpha in March 2026, with a low-overhead eBPF agent donated by Elastic. The API is still evolving; it's not yet stable. It completes the "pillars" picture: you can correlate a slow trace to its CPU flame graph without a separate profiling tool.

Say it out loud say it

"Profiles — continuous CPU and memory profiling as a first-class OTel signal. It's in public alpha since March 2026, with an eBPF agent from Elastic. Not stable yet, but it closes the gap between slow traces and hot code paths."
