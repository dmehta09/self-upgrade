Profiles · continuous profiling

Continuous profiling & Pyroscope.

Always-on, low-overhead sampling turns “attach a profiler during the outage” into “query the flame graph for the minute the alert fired.” Pyroscope is the usual OSS backend; OTel Profiles is the emerging wire format.

01 Always-on sampling

Continuous profiling runs a sampler in every process (or via eBPF on the host) and stores time-indexed profiles so you can diff “before deploy” vs “after deploy” without replaying the incident.

Typical cadence: sample stacks tens of times per second, aggregate into short windows (e.g. 10s–1m), ship via OTLP or the Pyroscope ingest API. You trade a small fixed CPU tax for the ability to answer performance questions after the fact.

In plain English analogy

Dashcams vs pulling over to set up a tripod. The dashcam footage is already there when the crash happens. Continuous profiling is the dashcam for CPU and allocations.

Pyroscope
Grafana’s continuous profiling backend (OSS + Grafana Cloud). Stores profiles cheaply; UI integrates with Tempo/Loki/Prometheus.
FlameQL
Pyroscope’s query language — select by service/labels and time range, then render or diff flames.
eBPF agent
Kernel-level sampler (Elastic-donated path into OTel) that profiles without language-specific SDKs. Low overhead; great for polyglot fleets.
Language SDKs
In-process agents (Go, Java, Python, …) when you need runtime-aware frames the eBPF view can’t symbolize as cleanly.

03 When to use it — and the cost

Turn continuous profiling on for services where CPU, allocation, or latency regressions are plausible after every deploy. Skip it on tiny sidecars that never show up in RED burn.

Use when
Frequent deploys; Go/Java/Python services with real CPU budgets; post-incident “what changed?” reviews; capacity planning.
Skip / defer when
Trivial cron jobs; already CPU-starved edge devices; you have zero Grafana/Tempo correlation yet (fix metrics+traces first).
CPU overhead
Target low single-digit percent with eBPF. If you see double-digit tax, lower sample rate or exclude noisy namespaces.
Storage cost
Profiles are cheaper than raw traces but not free — retain days–weeks of high-res, downsample or drop idle services for longer retention.
Common trap gotcha

Enabling continuous profiling without symbolization. A flame full of 0x7f8a… addresses is useless in an interview and in an incident. Ship debug symbols (or build IDs + a symbol server) with the same care you ship container images.

Practical tip tip

Diff profiles across the deploy boundary first. Interviewers love “v142 vs v143 FlameQL diff showed json.Marshal double in width” — that is a concrete root cause, not a vibe.

Why prefer an eBPF profiling agent in a polyglot Kubernetes cluster?

Right. eBPF samples from the kernel’s view of stacks. You still may add language SDKs later for richer frames, but you can cover the fleet quickly.

04 Interview rapid-fire

What is continuous profiling and how is it different from pprof on demand?warm
Model answer

Continuous profiling samples stacks (or allocations) all the time at low overhead and stores them as a time series. On-demand pprof is a session you start after you already suspect a process. Continuous lets you query the exact minute of an alert; on-demand is for deeper one-process investigation.

Say it out loud say it

“Always-on sampling so the flame graph exists before the page fires — not after I SSH in.”

Name the backend and query language you’d reach for in a Grafana stack.core
Model answer

Pyroscope stores the profiles; FlameQL selects by labels and time. Grafana links those flames next to Tempo traces and Prometheus metrics so the cascade stays in one UI.

Say it out loud say it

“Pyroscope + FlameQL, wired into Grafana beside Tempo.”

What cost knobs would you mention for running this in production?stretch
Model answer

Sample rate / agent overhead (~1–5% target), retention vs resolution, which services are profiled, and symbolization pipeline cost. Also call out that Profiles are still public alpha in OTel — expect API churn while the eBPF agent path matures.

Say it out loud say it

“I’d budget a few percent CPU, short high-res retention, and symbols — and note OTel Profiles is still alpha.”
