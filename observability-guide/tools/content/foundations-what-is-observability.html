Monitoring vs observability.

Monitoring watches known dashboards for known failure modes. Observability lets you ask brand-new questions of a running system — from its outputs alone — to explain behavior you've never seen before, without shipping new code.

01 The core distinction

Monitoring = alerting on known-unknowns. Observability = the ability to answer unknown-unknowns from output data alone.

The term comes from control theory: a system is "observable" if you can fully infer its internal state from its external outputs. Applied to software: if your system is observable, you can explain any novel failure from telemetry — no code change needed.

In plain English analogy

A car's dashboard shows speed, fuel, and temperature — fixed gauges for known problems. That's monitoring. The mechanic's OBD-II diagnostic port lets you query any sensor in real time and ask "why is cylinder 3 misfiring?" That's observability.

02 The "can you debug it?" test

The sharpest test: can you debug a brand-new production problem without deploying new code or logging?

If you have to add a log line, redeploy, and wait — your system is not observable. Observability means the telemetry you already ship is rich enough to answer questions you haven't thought of yet.

Known-unknown
CPU spike on host A — you have a CPU alert. Monitoring handles this.
Unknown-unknown
Checkout latency spikes for users with >50 items in cart, only in the EU region, only after 18:00. No alert covers this. Observability lets you discover it from trace data.
The key property
Telemetry carries enough context (high-cardinality attributes) that you can slice any dimension after the fact.

03 How systems become observable

Observability comes from the richness of your telemetry, not the number of dashboards. Three properties matter: structured (machine-parseable), correlated (logs linked to traces, traces to metrics), and high-cardinality (enough attributes to slice by any dimension).

1

Instrument

Emit structured events: logs with context, spans, metrics with labels. OTel is the standard.

2

Correlate

Attach a trace_id to logs and metrics so you can jump from a slow span to its logs instantly.

3

Explore

Query after an incident with a question you didn't know you'd need to ask. No redeploy.

Common trap gotcha

More dashboards ≠ observability. Fifty static dashboards still only answer the fifty questions you thought to ask when you built them. Observability is about arbitrary exploration, not more pre-built views.

Your CPU-spike alert fires. A colleague says "we have full observability — we have 30 dashboards." Is that correct?

Right. Dashboards are monitoring artifacts. Observability is the property of being able to explore unknown-unknowns from raw telemetry — dashboards are output, not the property itself.

04 Interview rapid-fire

What's the difference between monitoring and observability?core
Model answer

Monitoring alerts on known failure modes — you define the condition upfront. Observability is a property of the system: the ability to infer internal state from external outputs and answer novel questions without shipping new code. Monitoring handles known-unknowns; observability handles unknown-unknowns.

Say it out loud say it

"Monitoring watches for things you already knew could go wrong. Observability means you can debug surprises — novel failures you've never seen — without touching the codebase."

Follow-ups to expect
  • Can you have monitoring without observability? (Yes — legacy dashboards.)
  • What makes telemetry "observable"? (Structured, correlated, high-cardinality.)
Where does the term "observability" come from?warm
Model answer

Control theory. Rudolf Kalman (1960) defined observability as the ability to infer a system's complete internal state from its external outputs over time. Software engineers borrowed it: if your logs, metrics, and traces are rich enough, you can reconstruct what happened inside — without attaching a debugger.

Say it out loud say it

"It's from control theory — a system is observable if you can reconstruct its internal state purely from outputs. We apply that to software: rich telemetry lets you infer what happened without redeploying."

What practical test tells you if a system is observable?core
Model answer

Ask: "Can I debug a brand-new production problem I've never seen before, using only existing telemetry, without redeploying?" If you need to add a log line and redeploy to answer the question, the system is not fully observable for that failure class.

Say it out loud say it

"The test is: can I debug a novel failure right now, from telemetry I already have? If I have to redeploy to get the answer, that's a gap in observability."
