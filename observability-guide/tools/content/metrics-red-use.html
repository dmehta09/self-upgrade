Metrics · RED & USE

RED & USE methods.

Two complementary checklists tell you exactly which metrics to look at first. RED watches your services from the user's perspective; USE watches your infrastructure from the inside. Together they map to Google's Four Golden Signals.

01 The mental model

RED = "is the service doing its job?"   USE = "is the resource holding up?"

Neither framework replaces the other. A database can be saturated (USE) before any user-facing error appears (RED). Conversely, high error rates in RED rarely show up in CPU utilisation.

In plain English analogy

RED = the front-of-house: are diners being seated quickly, are they getting the right food, how long is the wait? USE = the kitchen equipment: is the oven at 100% capacity, is the fridge queue backing up, are appliances throwing errors?

02 RED — for request-driven services

Coined by Tom Wilkie (Grafana Labs). Apply it to every microservice or API endpoint.

RED checklist
R
Rate
Requests/sec arriving at this service
E
Errors
Fraction of requests returning an error
D
Duration
Latency distribution (p50 / p95 / p99)
Start here for every service alert or incident triage.
Rate
rate(http_requests_total[5m]) — tells you load and whether a drop means traffic fell or the service is rejecting requests.
Errors
rate(http_requests_total{status=~"5.."}[5m]) / rate(http_requests_total[5m]) — the fraction that failed.
Duration
histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m])) — the felt latency.

03 USE — for resource health

Coined by Brendan Gregg. Apply it to every resource: CPU, memory, disk I/O, network, connection pools, queues.

Letter Meaning Example metric
Utilization % of time the resource is busy (0–100%) CPU usage %, disk busy %
Saturation Extra work queued that the resource can't serve yet CPU run-queue depth, disk I/O wait, thread pool queue length
Errors Error events from the resource itself Network packet drops, disk I/O errors, OOM kills

Saturation is the leading signal — a resource can hit 100% utilisation and still serve requests, but once the queue grows, latency degrades and the service is on borrowed time.

04 Four Golden Signals — the overlap

Google's SRE book defined four signals: Latency, Traffic, Errors, Saturation. They overlap heavily with RED and USE.

Golden Signal Maps to RED Maps to USE
Latency Duration (D) —
Traffic Rate (R) Utilization (U)
Errors Errors (E) Errors (E)
Saturation — Saturation (S)

In practice: use RED to build service dashboards and alerts; use USE for infra runbooks and capacity planning; treat the Four Golden Signals as the vocabulary when talking to SREs.

Common trap gotcha

Alerting on causes (CPU 80%) instead of symptoms (latency > SLO, error rate > threshold). A CPU alert fires at 2 AM for batch jobs nobody cares about. A latency alert fires when users are actually hurting. Alert on user-facing symptoms; use resource metrics for diagnosis after the alert fires.

05 Check yourself

Your checkout service returns 500s for 3% of requests. Which letter in RED does this map to?

Right. Errors in RED is specifically the error ratio. Rate is volume; Duration is latency. They can correlate, but each is a distinct signal.

06 Interview rapid-fire

Explain RED and USE and when you'd use each.core
Model answer

RED (Rate, Errors, Duration) applies to every request-driven microservice — it tells you how well the service is serving users. USE (Utilization, Saturation, Errors) applies to every underlying resource — CPU, memory, queues — and tells you whether the resource is healthy. In an incident I reach for RED first to confirm there's a user-facing symptom, then use USE to identify which resource is the root cause.

Say it out loud say it

"RED = front-of-house — are users being served? USE = kitchen — is the equipment holding up? I triage with RED and diagnose with USE."

Why should you alert on symptoms rather than causes?core
Model answer

Cause-based alerts (CPU > 80%) fire constantly for workloads that never hurt users, causing alert fatigue. Symptom-based alerts (latency > SLO, error rate > threshold) fire only when users are impacted, making every alert actionable. Resource metrics are invaluable for post-alert diagnosis, not for the alert predicate itself.

Say it out loud say it

"Alert on user pain — latency and errors. Use CPU and queue depth to explain why after you've been paged, not as the page itself."

How do RED and USE relate to Google's Four Golden Signals?stretch
Model answer

The Four Golden Signals (Latency, Traffic, Errors, Saturation) span both frameworks. Latency maps to RED's Duration; Traffic maps to RED's Rate and USE's Utilization; Errors appear in both; Saturation maps to USE's Saturation. They're the same ideas under two lenses — service-centric (RED) and resource-centric (USE).

Say it out loud say it

"Golden Signals is Google's vocabulary; RED and USE are Brendan Gregg and Tom Wilkie's implementations. They largely cover the same ground — I use whatever vocabulary the team already speaks."
