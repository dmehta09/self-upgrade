Foundations · cardinality

Cardinality & the cost model.

Cardinality is the number of unique label-value combinations your metrics system must store. It's the single biggest surprise on a Prometheus or Datadog bill — and a very common reason Prometheus OOMs in production.

01 What cardinality means

Each unique combination of label values creates one time series. Metric storage scales with the count of those series — not with request volume.

A metric http_requests_total with labels method (3 values) × status (5 values) × region (4 values) = 60 series. Add user_id with one million users and you instantly have 60 million series.

In plain English analogy

Imagine a filing cabinet with one drawer per unique label combination. Labels like method=GET and status=200 give you a handful of drawers — totally manageable. Add user_id=… and you need a drawer for every user. Your office collapses.

02 Cost model by signal type

Each signal has a different cost driver. Knowing this tells you where to put detail — and where not to.

Metrics cost
≈ cardinality (unique label combos). Adding one unbounded label multiplies every existing series count.
Logs cost
≈ volume × retention. 10 GB/day × 30 days = 300 GB stored. Reduce with sampling or shorter retention.
Traces cost
≈ sampling rate × span size. Most teams keep 1–10% of traces; errors and slow traces at 100%.
Where high-cardinality data belongs
Metric label
Low cardinality only
method, status, region, env — bounded, small
Trace / Log attribute
High cardinality OK
user_id, order_id, request_id, email — use traces & logs for per-entity detail
Exemplar
Bridge the gap
Attach a trace_id to a metric sample — link a p99 spike to its specific trace
Keep metrics low-cardinality. Put high-cardinality detail in traces and logs. Use exemplars to link them.

03 The high-cardinality trap

The most common production incident with Prometheus: someone adds user_id, email, or a full URL path as a metric label, then wonders why Prometheus OOMs overnight.

Anti-pattern — explodes cardinality
app.py
# ❌ user_id is unbounded — one series per user
requests_total = Counter(
    "http_requests_total",
    ["method", "status", "user_id"]  # DANGER
)
requests_total.labels(
    method="GET", status="200",
    user_id=current_user.id   # millions of values
).inc()
Better — use trace/log for per-user detail
app.py
# ✅ metric: low-cardinality labels only
requests_total = Counter(
    "http_requests_total",
    ["method", "status"]
)
requests_total.labels(
    method="GET", status="200"
).inc()
# per-user detail goes in the trace span attribute:
# span.set_attribute("user.id", current_user.id)
Common trap gotcha

Unbounded IDs in metric labels — user_id, email, raw URL paths, request_id — are the #1 cardinality bomb. Use traces and logs for per-entity detail. Use exemplars to link a metric spike back to a specific trace without increasing metric cardinality.

04 Check your model

Your team doubles traffic from 10 k req/s to 20 k req/s. Your Prometheus memory usage…

Right. Prometheus stores one time series per unique label combination. Doubling throughput doesn't add new label combinations — it just adds more samples to existing series, which compress well. Cardinality is the memory driver, not volume.

05 Interview rapid-fire

What is cardinality in metrics, and why does it matter?core
Model answer

Cardinality is the count of unique label-value combinations — i.e., the number of time series stored. Metrics storage and memory scale with cardinality, not with request volume. One unbounded label (like user_id) multiplies the existing series count by the number of users, easily OOM-ing Prometheus.

Say it out loud say it

"Cardinality is unique label combos — that's the number of time series. Prometheus memory scales with cardinality, not throughput. Add one unbounded ID label and you can OOM the cluster overnight."

Follow-ups to expect
  • How do you handle high-cardinality detail? (Traces + logs + exemplars.)
  • How would you debug a cardinality explosion? (Prometheus TSDB status page at /tsdb-status.)
A developer wants to track per-user request counts in Prometheus. How do you advise them?core
Model answer

Don't add user_id as a metric label — it's unbounded and will create one series per user. Instead, keep the metric low-cardinality and put per-user detail in trace span attributes or structured logs. If they need to correlate a metric spike to a specific user's trace, use exemplars.

Say it out loud say it

"I'd tell them not to use user_id as a label — that blows up cardinality. Per-user detail belongs in trace attributes or logs. Use an exemplar on the metric to link back to a specific trace if needed."

How does cost scaling differ across logs, metrics, and traces?stretch
Model answer

Logs scale with bytes shipped and retained — volume × retention. Metrics scale with cardinality — unique label combinations — not request rate. Traces scale with sampling rate and span count — most teams tail-sample to keep 1–10% of traffic. Understanding this lets you optimize spend per signal rather than across the board.

Say it out loud say it

"Logs: volume times retention. Metrics: cardinality — how many unique label combos, not how much traffic. Traces: sampling rate — keep errors at 100%, normal traffic at 1–5%."
