Auto vs manual instrumentation.

Auto-instrumentation gives you HTTP, database, and framework spans for free. Manual instrumentation adds the business-logic context that makes those spans actually debuggable. Use both — they answer different questions.

01 Two kinds of instrumentation

Auto-instrumentation patches known libraries at load time. Manual instrumentation adds spans and attributes around your own logic.

Auto-instrumentation (agents, bytecode injection, monkey-patching) works at the framework boundary. It sees requests and DB calls but knows nothing about what your code does in between. Manual instrumentation fills that gap with business context.

In plain English analogy

Auto-instrumentation is a dashcam that records the entire drive — every turn, every stop, automatically. Manual instrumentation is you narrating the turns that matter: "taking the shortcut via Route 9 because of traffic." Without the narration, you have timestamps but no context.

Auto-instrumentation
  • Zero code changes — agent patches at startup
  • Covers: HTTP clients/servers, DB drivers, gRPC, message queues
  • Misses: your business logic, domain-specific attributes
  • Example: span for every SELECT query, but no user_id or order_id
Manual instrumentation
  • Requires code — you call the OTel API explicitly
  • Covers: business transactions, domain events, computed values
  • Adds: order.id, cart.item_count, payment.method
  • Example: a checkout span with every attribute an SRE needs to debug

02 Writing a manual span

The OTel Python API is three calls: get a tracer, start a span as a context manager, set attributes. The span automatically becomes a child of whatever is currently active.

checkout.py
from opentelemetry import trace

tracer = trace.get_tracer("orders.service")

def process_checkout(cart):
    with tracer.start_as_current_span("checkout") as span:
        span.set_attribute("cart.item_count", len(cart.items))
        span.set_attribute("cart.total_usd", cart.total)
        span.set_attribute("user.id", cart.user_id)
        # auto-instrumented DB call becomes a child span automatically
        order = db.insert_order(cart)
        span.set_attribute("order.id", order.id)
        return order
get_tracer(name)
Gets a tracer scoped to your component. name shows up as the instrumentation scope in backends.
start_as_current_span
Creates the span and sets it as the active context — child spans (from auto-instrumented calls) nest under it automatically.
set_attribute
Key-value pairs attached to this span. These are what you filter and group by in your backend.

03 What to instrument — and what not to

Over-instrumenting is as harmful as under-instrumenting. Every span has a storage cost and a cardinality cost. Instrument the decisions and data that an SRE would need to answer "why did this fail for this user?"

Common trap gotcha

Adding attributes that are useful dimensions is fine: http.status_code, payment.method. Adding attributes that are high-cardinality leaf values — like raw SQL queries or full request bodies — explodes your index and billing. user.id is fine (bounded). raw_sql_query is a time bomb.

1

Start with auto-instrumentation

Get HTTP, DB, and queue spans for free. This covers 80% of production latency questions.

2

Add spans at business boundaries

Wrap operations with business meaning: checkout, fraud-check, inventory-reserve. Not every private function.

3

Add attributes that are useful dimensions

Ask: "would an SRE group-by or filter this?" order.tier = yes. full_request_json = no.

Auto-instrumentation captures every HTTP call in your app. A slow checkout is still hard to debug. What's missing?

Right. Auto-instrumentation sees the structure of calls but not the domain context. Manual attributes like cart.item_count or user.tier are what let you pivot from "checkout is slow" to "checkout is slow for premium users with large carts."

04 Interview rapid-fire

What's the difference between auto and manual instrumentation? When do you need both?core
Model answer

Auto-instrumentation patches known libraries at startup — you get HTTP, DB, and framework spans for free with zero code changes. Manual instrumentation is where you call the OTel API directly to add spans and attributes around your own business logic. You need both: auto covers infrastructure-level calls; manual adds the domain context that makes those calls debuggable.

Say it out loud say it

"Auto gives me the skeleton — every HTTP call and DB query. Manual adds the flesh — the business attributes that let me understand why a specific user's checkout is slow."

What span attributes are worth adding manually, and which should you avoid?core
Model answer

Add attributes that are useful filter or group-by dimensions: user tier, payment method, cart item count, order ID. Avoid raw high-cardinality strings like full SQL queries, request bodies, or session tokens — they explode index size and cost while being near-impossible to query on.

Say it out loud say it

"I add attributes an SRE would filter or group by — things like payment method or user tier. I avoid unbounded strings like raw SQL that cost a lot and answer nothing specific."

How does a manually created span relate to the surrounding auto-instrumented spans?warm
Model answer

OTel maintains a context propagation stack. When you call start_as_current_span inside a request handler that auto-instrumentation already wrapped, your span automatically becomes a child of the active span and inherits the same trace ID. Any auto-instrumented calls inside your span (e.g., a DB query) nest under it as further children.

Say it out loud say it

"It slots in automatically. OTel's context propagation makes my manual span a child of whatever is currently active — same trace ID, proper nesting in the waterfall."
