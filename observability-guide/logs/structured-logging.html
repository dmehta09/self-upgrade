Structured logging.

A log line you can’t query is just noise. Structured logs are machine-readable records with named fields — you can filter, aggregate, and join them the same way you query a database.

01 Structured vs unstructured

Unstructured logs are prose; structured logs are records. The difference is queryability at scale.

A free-text log requires regex to extract facts. A JSON log has named keys — any log backend can filter on order_id, count by user_id, or group by status instantly.

In plain English analogy

Unstructured logs are a junk drawer — everything’s in there but you rummage by hand. Structured logs are labeled, stackable boxes — you read the tag, pull the right one instantly. Same information; very different retrieval cost.

Unstructured (hard to query)
app.log
2026-06-04 12:01:33 INFO Order 8821 placed by user 42 for $99.00 - payment OK
Structured JSON (queryable)
app.log
{"ts":"2026-06-04T12:01:33Z","level":"INFO",
 "event":"order.placed","order_id":"8821",
 "user_id":"42","amount_usd":99.00,
 "payment_status":"ok"}

02 Log levels & when to use them

A log level is a severity signal — it tells operators which lines deserve attention and lets them mute the rest.

Choose the level by answering: “Does an operator need to act on this right now?” Flooding ERROR with noise trains people to ignore it.

DEBUG
Diagnostic detail for development; disable in production to avoid noise and cost.
INFO
Normal business events — request received, order placed, payment processed.
WARN
Unexpected but recoverable — retry succeeded, config fallback used, rate-limit approaching.
ERROR
A request or operation failed; operator attention warranted. One error log per failure, not per retry.

A database call fails but the service retries and succeeds on the second attempt. Which level is correct?

Right. WARN is for unexpected-but-recovered situations. Save ERROR for actual failures. If every retry fires an ERROR, on-call engineers start ignoring the alert.

03 What to log — and what never to log

Log decisions, IDs, and outcomes. Never log secrets, PII, or raw payloads.

Good log fields help you answer “what happened to this request?” without needing to reproduce it.

Do log
request_id, user_id (opaque), order_id, HTTP status, duration, decision made, error message (not stack trace in prod).
Never log
Passwords, API keys, tokens, full card numbers, email addresses, SSNs, request/response bodies without scrubbing.
orders.py
import logging, structlog

log = structlog.get_logger()

def place_order(user_id: str, order_id: str, amount: float) -> None:
    # Good: structured fields, no PII payload
    log.info("order.placed",
             user_id=user_id,
             order_id=order_id,
             amount_usd=amount)

    # Bad (never do this):
    # log.info(f"Order for user email {user.email} card {card.number}")
Common trap gotcha

Logging PII/secrets is a compliance breach waiting to happen — logs are often shipped to multiple backends, retained for months, and accessed by tooling teams. Scrub before you emit, not after. And logging in a hot inner loop (e.g., per-item in a batch of thousands) buries signal in noise and spikes your ingestion bill.

04 Interview rapid-fire

Why use structured logging instead of print statements?warm
Model answer

Structured logs have named fields that log backends can index and query. You can filter level=ERROR, count by service, or join on order_id without regex. Free-text strings require parsing at query time, which doesn’t scale and breaks when the message wording changes.

Say it out loud say it

“Structured logs are machine-readable records. You query them like data, not grep them like text — that’s what makes them useful at scale.”

What should you never put in a log line and why?core
Model answer

Secrets (API keys, tokens), PII (emails, card numbers, SSNs), and unscrubbed request/response bodies. Logs are forwarded to multiple systems, stored for long retention windows, and often accessed by more people than the app itself. A leaked secret in logs is just as exploitable as one in code.

Say it out loud say it

“Secrets and PII — logs get shipped everywhere and retained for months. One accidental token in a log line is a full credential leak.”

An engineer wants to log at DEBUG inside a loop processing 50 000 items. What’s the problem?stretch
Model answer

Volume and cost. 50 000 log lines per invocation multiplies into millions per hour. Ingestion is priced by GB — the bill spikes and the signal-to-noise ratio collapses, making real errors invisible. Log a summary at INFO (e.g., items processed, errors count) rather than one line per item.

Say it out loud say it

“Hot-loop logging destroys your bill and buries errors in noise. Log summaries, not per-item lines.”

Follow-ups to expect
  • How would you keep visibility without per-item logs? (counters + one summary line, or a metric)
  • How does sampling help here?
