Correlation IDs & context.

A log line in isolation tells you nothing about the request it belongs to. A correlation ID makes every log line part of a searchable, joinable story — and lets you jump straight from a log to the trace that explains the latency.

01 The idea

A correlation ID (or request ID) is a single identifier generated at the edge and forwarded in every log, every downstream call, and every response header.

Without it, logs from five services handling the same request look like five unrelated events. With it, one query — request_id="abc-123" — surfaces the complete story across all services.

In plain English analogy

Think of it as a parcel tracking number. Every depot (service) scans that same barcode as the package passes through. At any point you enter the number and see the full journey — dispatched, in transit, out for delivery — stitched together from independent scans at independent locations.

correlation_id / request_id
Generated at the entry point (API gateway or client); forwarded in HTTP headers (X-Request-ID); included in every log line.
trace_id
The OpenTelemetry trace identifier; a 128-bit hex string. When OTel instrumentation is active, it is the correlation ID — no need for a separate one.
span_id
Identifies the current unit of work inside the trace. Log lines carrying both trace_id + span_id can be pinned to the exact span in Jaeger or Tempo.

03 OTel auto-injects trace context into logs

With OpenTelemetry, you don’t manually thread IDs — the SDK injects trace_id and span_id into every log record automatically.

Configure a log bridge (e.g., opentelemetry-instrumentation-logging) and every logging.info() call gains trace context from the active span. The snippet below shows a manual fallback for context where OTel isn’t running.

context_log.py
from opentelemetry import trace
import structlog

log = structlog.get_logger()

def charge_card(order_id: str, amount: float) -> None:
    span = trace.get_current_span()
    ctx = span.get_span_context()
    log.info("payment.attempted",
             order_id=order_id,
             amount_usd=amount,
             trace_id=format(ctx.trace_id, "032x"),
             span_id=format(ctx.span_id, "016x"))
    # With OTel log bridge active, the two lines above
    # are injected automatically — no manual code needed.
Common trap gotcha

Logs without a correlation ID are useless islands during an incident. You see the error, but you can’t find the upstream cause or the downstream blast radius. Retrofitting IDs across a live microservice fleet is painful — add them at service inception.

You have OTel tracing active. A customer reports a failed order. What’s the fastest path from the error log to the root cause?

Right. The trace_id is a direct pointer into the trace backend. One click in Grafana’s “Explore” view links from the log line to the waterfall showing which span failed and why.

04 Interview rapid-fire

What is a correlation ID and why does every log line need one?warm
Model answer

A correlation ID (or request ID) is a unique token generated when a request enters the system, forwarded in every outbound call, and stamped on every log line. Without it, logs from different services handling the same request are unrelated rows. With it, you reconstruct the entire request journey across ten services with a single query.

Say it out loud say it

“It’s a tracking number. Every service stamps the same ID on its logs so you can query the full journey in one go.”

How does OTel relate to correlation IDs? Do you still need a separate request ID?core
Model answer

When OTel tracing is active, the trace_id is the correlation ID. The OTel log bridge auto-injects trace_id and span_id into every log record from the active span context. A separate request ID is redundant; you get a richer identifier that links directly to the trace waterfall in Jaeger or Tempo.

Say it out loud say it

“With OTel, trace_id is your correlation ID, and the log bridge injects it automatically. You get logs and traces linked for free.”

What context fields beyond trace_id should you propagate in a multi-tenant system?stretch
Model answer

At minimum: tenant_id and an opaque (hashed or internal) user_id. These let you scope incident impact (“which tenants were affected?”) and satisfy per-tenant SLAs. In regulated domains you might also carry a session_id for audit trails. All context fields should flow through OTel Baggage so every service picks them up without manual threading.

Say it out loud say it

“tenant_id and an opaque user_id at minimum — they scope every query to the right customer without leaking PII into the log pipeline.”
