Prometheus & Grafana · the pull model

The Prometheus model.

Prometheus is a pull-based metrics system: it scrapes a /metrics endpoint on every target, on a schedule, and stores the results in a local time-series database. Understanding pull vs push, and the label-based data model, is the foundation for everything else.

01 Pull / scrape model

Prometheus reaches out to each target on a configurable interval (default 15 s) and reads its /metrics endpoint — targets don't call home.

Each target exposes metrics in the Prometheus text format (or OTLP — see below). Prometheus stores the scraped samples with a timestamp and the target's labels. No agent push loop; the scrape schedule is Prometheus's job.

In plain English analogy

A census taker who visits every house on a fixed schedule and asks "how many people live here?" (pull) — versus every household mailing in a form whenever something changes (push). Pull means one authoritative schedule; push means each sender controls its own timing.

02 Exporters & service discovery

Not every service natively exposes Prometheus metrics. Exporters translate third-party systems into the text format. Service discovery lets Prometheus find targets automatically instead of hardcoding IPs.

node_exporter
Host-level CPU, memory, disk, network — the standard Linux exporter.
blackbox_exporter
Probes endpoints from the outside (HTTP/TCP/ICMP ping). Measures availability, not internals.
mysqld_exporter / redis_exporter
Database-specific translators — expose query latencies, connections, hit rates.
Service discovery
Kubernetes SD, Consul SD, EC2 SD — Prometheus calls the SD API and gets a fresh target list, so you never hand-edit scrape configs when pods scale.
Common trap gotcha

The Pushgateway is not a general push solution. It's for short-lived batch jobs that finish before the next scrape. Treating it as a universal push endpoint leads to stale metrics and missed scrape gaps.

03 TSDB & the label-based data model

Every metric is identified by its name + a set of key=value labels. Each unique label combination is a separate time series stored in the local TSDB.

Labels make aggregation and filtering powerful — e.g. http_requests_total{method="POST", status="200", service="checkout"}. But each new label value spawns new series.

example metrics
# HELP http_requests_total Total HTTP requests
# TYPE http_requests_total counter
http_requests_total{method="GET",status="200",service="api"} 1024
http_requests_total{method="POST",status="500",service="api"} 3
High-cardinality labels blow up the TSDB gotcha

Adding a label like user_id or request_id creates one series per unique value — potentially millions. Prometheus's local TSDB is not designed for this. Keep label values bounded (tens to low hundreds, not millions).

You add a user_id label to a counter scraped from 1,000 users. How many new time series does that create?

Right. Each unique label-set combination is an independent series in the TSDB. 1,000 users × existing combinations = explosive cardinality. This is why you never put unbounded IDs in labels.

04 Prometheus 3.x & scaling out

Prometheus 3.x (3.7 shipped Oct 2025) added three features worth knowing for interviews: native OTLP ingestion, Remote-Write 2.0, and native histograms.

Native OTLP ingestion
Prometheus 3.x exposes /api/v1/otlp/v1/metrics — OTel SDKs can push directly without a separate Collector or sidecar.
Remote-Write 2.0
The push-to-remote-storage protocol — carries metadata, exemplars, created timestamps, and native histograms. Used to fan out to Mimir/Thanos.
Native histograms
Exponential bucket histograms that eliminate the fixed-bucket configuration problem. Still experimental (opt-in: --enable-feature=native-histograms).
Mimir / Thanos
Horizontal scale-out: Prometheus's single-node TSDB tops out in practice around a few million active series. Mimir and Thanos add multi-tenancy, long-term storage, and global query.
Single Prometheus
  • One node, one TSDB
  • Limited retention (days–weeks)
  • No global query across regions
Prometheus + Mimir/Thanos
  • Remote-Write to object storage
  • Months–years of retention
  • Global query over multiple shards

05 Interview rapid-fire

Why does Prometheus use a pull model instead of push?core
Model answer

Pull gives Prometheus control over the scrape schedule and makes it immediately obvious when a target is down (missed scrape). It also means targets are passive — no agent needs credentials to send data. Push can work (via the Pushgateway for batch jobs) but it shifts reliability to each sender.

Say it out loud say it

"Pull means Prometheus owns the schedule and a missing scrape is instantly visible as a gap — push makes each target responsible for its own timing, which is harder to monitor."

Follow-ups to expect
  • When would you use the Pushgateway?
  • How does native OTLP ingestion change this?
What is high-cardinality and why is it a problem for Prometheus?core
Model answer

High cardinality means a label has a huge number of distinct values — like user_id or request_id. In Prometheus, each unique label combination is a separate in-memory time series. Too many series exhausts RAM and degrades query performance. The fix is to keep labels bounded — use traces or logs for per-request detail.

Say it out loud say it

"Each label combo is its own series, so a million user IDs means a million series. Metrics are for aggregates — use traces for per-request detail."

How do you scale Prometheus beyond a single node?stretch
Model answer

Use Remote-Write 2.0 to ship samples to Mimir or Thanos. Both add multi-tenancy, long-term object-storage retention, and a global query layer that federates across multiple Prometheus shards. Prometheus stays as the local scraper; the remote backend handles scale and durability.

Say it out loud say it

"Keep Prometheus as the local scraper and remote-write to Mimir or Thanos for long-term storage and global queries."
