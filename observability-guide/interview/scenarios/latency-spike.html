Scenario: p99 latency spike.

Your multi-burn-rate alert fires at 2 a.m. p99 for POST /checkout has crossed the SLO threshold. Walk through the investigation exactly as you'd narrate it in an interview.

01 The situation

SLO: p99 latency ≤ 500 ms for POST /checkout. The alert fired at a 14.4× burn rate on the 1-hour window.

In plain English analogy

14.4× burn rate means at the current rate you'd exhaust the entire 30-day error budget in one hour. It's the equivalent of a fire alarm — something is badly wrong and users are experiencing it right now.

SLO
99.9% of POST /checkout requests complete within 500 ms
Burn rate
14.4× — the threshold that triggers an immediate page
Time window
1-hour fast window + 6-hour slow window both elevated (multi-window alert)
First question
Is the user actually impacted? Check the RED dashboard before digging further.

02 Step-by-step investigation

1

Confirm impact on the RED dashboard

Open the Grafana RED panel for the checkout service. p99 latency is sitting at ~2 400 ms — nearly 5× the SLO threshold. Error rate is normal. Traffic is normal. This is a pure latency problem, not errors.

2

Click the exemplar — jump to the slow trace

The latency histogram panel shows a cluster of exemplar dots at ~2 400 ms. Click one. Grafana opens the correlated trace in Tempo. The trace waterfall appears below.

3

Read the trace waterfall — find the critical path

The gateway span is 2 350 ms end-to-end. Expanding it: a Redis cache read completes in 12 ms (not the issue); the createOrder span runs 2 310 ms; inside it, INSERT orders (Postgres) takes 2 100 ms and sits on the critical path. The DB write is the smoking gun.

4

Jump to logs — confirm the DB hypothesis

From the slow span, click "View logs" (Tempo → Loki, filtered by trace_id). The log line reads: {"event": "db_query_slow", "table": "orders", "duration_ms": 2089, "query_type": "INSERT", "plan": "sequential_scan"}. The orders table is doing a sequential scan — a missing index.

5

Fix — add index; watch SLO recover

A concurrent index creation runs against the orders table. p99 drops to 180 ms within minutes. The burn rate falls back below 1×. Error budget starts recovering.

03 The smoking-gun trace

This is the trace that the exemplar linked to. The INSERT orders span is on the critical path — it directly determines the end-to-end latency of the checkout request.

Common trap gotcha

The average latency looked fine for most of the day — ~220 ms. Averages hid the slow tail. Only p99 revealed that 1% of checkouts were taking 2+ seconds. Always alert on percentiles, never on mean.

04 How to narrate this in an interview

Use the STAR structure. Keep it under 3 minutes — the interviewer will probe deeper where they want detail.

STARWhat to say
Situation"Our checkout p99 SLO is 500 ms. A 14× multi-burn alert fired at 2 a.m."
Task"Confirm user impact, find the root cause, resolve before the budget was exhausted."
Action"RED dashboard confirmed high p99 only — no error spike. Exemplar jumped me to the slow trace. Waterfall showed INSERT orders on the critical path at 2 100 ms. Loki logs for that trace_id showed a sequential scan. Added a concurrent index."
Result"p99 dropped to 180 ms within 5 minutes. Burn rate fell below 1×. Budget recovered."

The Redis cache span in the trace takes 12 ms. Should you optimize it to fix the p99?

Right. The critical path is the longest sequential chain. Redis runs in parallel with the createOrder flow, so optimizing it changes nothing about the 2 350 ms end-to-end time. Fix the DB span — that's what's on the critical path.

05 Interview rapid-fire

How did you get from the metric to the trace without manual searching?core
Model answer

Via a histogram exemplar — a data point on the histogram that carries a trace_id from a real request in that latency bucket. Clicking it in Grafana opens the exact trace in Tempo. This is the key integration between the metrics layer and the traces layer, and it's why you instrument histograms with exemplars in production.

Say it out loud say it

"The histogram had an exemplar — a data point with a trace_id embedded in it. I clicked it and Grafana jumped me directly to the slow trace in Tempo. Zero manual correlation."

What would you have done if the trace had no obvious slow span?stretch
Model answer

First, check if the slow time is between spans (network overhead or serialization), not within a single span. Second, look for missing spans — a service that wasn't instrumented. Third, aggregate: use TraceQL in Tempo to query all traces in the spike window where total duration > 1 s and group by service — you might see a pattern that a single trace hides. Finally, check infra metrics (CPU, network I/O) alongside the trace window.

Say it out loud say it

"I'd look at gaps between spans first — those are network time. Then I'd run a TraceQL query to find all slow traces in the window and group by service. Maybe one service is slow across all of them."
