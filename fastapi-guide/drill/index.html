Practice · drills & flashcards

Reading about it isn't knowing it.

Three timed drills test the judgment the lessons build: which mechanism does this job, which status code fits this moment, and what broke given only the symptom. Wrong answers come with the why — and a link back to the lesson. Two flashcard decks round it out.

00  How a round works

the clock
Each question has its own countdown (30–45 s). Run out of time and it counts as wrong — speed IS the skill being trained.
the chips
Click an answer or press 1–9. Every question explains itself afterwards; the near-miss answers carry a "the trap" note.
the score
Your best per mode is saved in this browser (localStorage). Questions reshuffle every round, so replaying is the point.
Be honest with yourself

If you guessed and got lucky, count it as a miss in your head and read the linked lesson anyway. The drills only work if a green chip means "I could justify this to a teammate."

01  Pick the tool 45 s / question

The FastAPI judgment call: dependency or middleware? Background task or lifespan? WebSocket or SSE? Eight chips, fixed positions — these are the pairs that get confused in real designs.

02  Status codes 30 s / question

401 vs 403. 404 vs 422. 200 vs 201 vs 204. The codes are the vocabulary of your API — answer fast enough that they become reflex.

03  Debug it 45 s / question

Every lesson's gotcha callouts, weaponized: you get the symptom — a frozen server, a leaked password hash, a row that never appears — and you name the cause. This is the drill that pays off at 2 a.m.

04  Flashcards

Two decks for the in-between minutes. Click a card to flip it; mark what you know — your marks persist, and Shuffle floats the cards you're still learning to the top.

Deck 1 · Status codes

0/0 known

  • 200 OK

    Plain success with a body. The default for GET, and for PUT/PATCH when you return the updated object.

  • 201 Created

    A new resource now exists — the right answer for a successful creating POST. Declare it: status_code=201 on the decorator.

  • 204 No Content

    Success with a deliberately empty body — the natural answer for DELETE. Don't return a body with it; that breaks the contract.

  • 307 Temporary Redirect

    FastAPI's trailing-slash redirect: declare /items/, call /items, get a 307 to the slashed path (method preserved). Surprising in logs, harmless — usually.

  • 401 vs 403

    401: "I don't know who you are" — missing/invalid/expired credentials; re-login can fix it. 403: "I know exactly who you are — no." Re-login fixes nothing.

  • 404 vs 422

    404: the data was valid but the resource doesn't exist (you raise it). 422: the request itself failed validation (FastAPI raises it before your code runs).

  • 409 Conflict

    The request is valid but clashes with current state — duplicate username, double-booking, version conflict. Pairs naturally with unique constraints.

  • 422 Unprocessable Entity

    FastAPI's signature: the request reached the route but failed Pydantic validation. The body lists loc (where), msg, and type for every failure.

  • 429 Too Many Requests

    Rate limit exceeded. Send Retry-After so well-behaved clients know when to come back; gateways often emit this before your app ever sees the request.

  • 500 Internal Server Error

    An unhandled exception escaped your code. Users should see a generic envelope — never the stack trace. Your logs (with a request-id) get the details.

  • 503 Service Unavailable

    The app is up but can't serve — DB down, overloaded, draining for deploy. Health checks and load balancers act on it.

  • Who sends 422 — you or FastAPI?

    FastAPI, automatically, when type hints don't validate — your function never runs. You raise the business errors: 404, 403, 409 via HTTPException.

Deck 2 · Core concepts

0/0 known

  • Annotated[T, Depends(f)]

    The modern dependency declaration: the type for your editor, the Depends for FastAPI. Alias it once (SessionDep) and reuse everywhere.

  • A dependency with yield

    Setup before yield, the yielded value is injected, teardown after the response (in finally). How DB sessions get reliably closed.

  • response_model

    The output filter: whatever your function returns, only the declared schema's fields leave the building. The defense against leaking hashed_password.

  • Field(...) constraints

    Validation rules on model fields: Field(gt=0), min_length, pattern. For params: Query(le=100), Path(ge=1) inside Annotated.

  • lifespan

    An @asynccontextmanager passed to FastAPI(lifespan=…): before yield runs at startup (load models, open pools), after yield at shutdown. Replaces the deprecated @app.on_event.

  • async def vs def endpoints

    async def: runs on the event loop — only await-friendly code. def: FastAPI threads it — blocking code is safe. Never blocking code inside async def.

  • UploadFile

    The file-upload parameter type (needs python-multipart). Spooled to disk past a size threshold; read in chunks for big files instead of await file.read() whole.

  • TestClient + dependency_overrides

    TestClient calls your app in-process (no server). app.dependency_overrides[get_session] = fake swaps real deps for test doubles — a throwaway DB in one line.

  • BackgroundTasks — and its limit

    tasks.add_task(f, …) runs after the response — great for quick fire-and-forget. In-process though: heavy or must-not-be-lost jobs belong in Celery/ARQ.

  • StreamingResponse vs SSE vs WebSocket

    Streaming: one response in chunks. SSE: long-lived one-way pushes, auto-reconnect. WebSocket: two-way conversation. Pick the least power that works.
