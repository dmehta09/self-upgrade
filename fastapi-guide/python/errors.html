Python · errors & exceptions

When things go wrong — on purpose.

An exception is Python's way of saying “I can't continue normally.” Instead of returning a bad value, code raises an exception that travels up until something catches it. You handle the failures you can, and let the rest surface. FastAPI builds right on top of this: a raised HTTPException becomes a real HTTP error response.

01  What an exception is

When an operation fails, Python raises an exception object. If nothing catches it, it propagates up the call stack and crashes the program with a traceback. Different problems raise different types, and every type descends from Exception:

Exceptions you'll meet constantly
ValueError
right type, wrong value — int("oops")
KeyError
a dict key that isn't there — data["missing"]
TypeError
an operation on the wrong type — "a" + 1
ZeroDivisionError
dividing by zero — 10 / 0
FileNotFoundError
opening a file that doesn't exist

You catch an exception by name, and you can read its message. Here we coerce two strings to int — one works, one doesn't:

raised.py
42
ValueError: invalid literal for int() with base 10: 'oops'

02  try / except / else / finally

The full shape, in plain words: try the risky thing; except handles a specific failure; else runs only if no exception happened; finally runs no matter what — perfect for cleanup that must always occur.

flow.py
division ok
done
5.0
can't divide by zero
done
None
Catch narrow, not except Exception

Catching every exception hides real bugs. Name the specific error you expect (except ZeroDivisionError). A bare except: can even swallow Ctrl-C. We dig into why broad catches are dangerous on the silent-failures front throughout the FastAPI pages.

03  Raising & custom exceptions

You don't only catch exceptions — you raise them when your rules are broken. For domain-specific failures, define your own type by subclassing Exception. A named exception (InsufficientFunds) reads far better than returning None or -1 and hoping the caller checks.

declined: need 150, have 100
70

04  Chaining with raise … from …

Often you catch a low-level error and want to re-raise a clearer, higher-level one — without losing the original cause. raise NewError(...) from original links them, so the traceback shows both. The original is stored on __cause__.

chain.py
bad port: 'abc'
caused by: ValueError
Friendly message, full context

Chaining gives your users a clean message (“bad port”) while keeping the gritty cause (a ValueError) for your logs. You get readability and debuggability — no trade-off.

05  EAFP vs LBYL

Two styles for risky operations. LBYL — “Look Before You Leap” — checks conditions first. EAFP — “Easier to Ask Forgiveness than Permission” — just tries it and catches the failure. Python leans EAFP: it's often cleaner and avoids a race where the thing you checked changes before you use it.

no age (LBYL)
no age (EAFP)

When does the finally block run?

Right. finally always runs, which is why it's the home for cleanup like closing files or database sessions. That guarantee is exactly what yield dependencies rely on (Generators page).

06  How FastAPI uses exceptions

Everything above powers FastAPI's error model. You raise HTTPException(...) and FastAPI converts it into a real HTTP response with the right status code and JSON body. And when request data fails validation, Pydantic raises an error that FastAPI catches for you and returns as the 422 you met on the Validation page.

main.py
from fastapi import FastAPI, HTTPException

app = FastAPI()
items = {1: "book"}

@app.get("/items/{item_id}")
def read_item(item_id: int):
    if item_id not in items:
        raise HTTPException(status_code=404, detail="Item not found")
    return {"item": items[item_id]}
# Missing id -> a real 404 with {"detail": "Item not found"}
Custom exceptions → custom responses

You can register an @app.exception_handler(MyError) so that whenever your own exception is raised anywhere in a request, FastAPI returns a consistent JSON error. Your domain exceptions and your API errors become one clean system.

Exercise

Write set_age(age) that returns the age, but raises a ValueError("age cannot be negative") when age is below zero.

The loop should print 25 for a valid age and rejected: age cannot be negative for -5.

exercise.py
(write your solution and press Run)
Show solution solution
solution.py
def set_age(age):
    if age < 0:
        raise ValueError("age cannot be negative")
    return age

for a in [25, -5]:
    try:
        print(set_age(a))
    except ValueError as e:
        print(f"rejected: {e}")

Validating inputs and raising a precise exception is exactly what a Pydantic @field_validator does for you on a request model — same idea, wired into the request pipeline.
