Python · classes & OOP

Bundling data and behavior together.

A class is a blueprint for making objects that carry their own data and the functions that act on it. You'll meet classes everywhere in FastAPI — every Pydantic model and every SQLModel table is one. We start from a plain class and build up to @dataclass.

01  Why classes?

So far your data has lived in dicts and your logic in separate functions. A class glues them together: an object knows its own data and what it can do with it. In plain words — a class is a blueprint, and each object you build from it is an instance.

Cookie cutter vs cookies analogy

The class is the cookie cutter — it defines the shape. Each instance is a cookie stamped out from it: same shape, but its own icing. One blueprint, many independent objects.

The vocabulary: an attribute is a piece of data on the object; a method is a function defined inside the class that acts on the object.

02  __init__, self & attributes

__init__ is the constructor — Python runs it automatically when you create an instance, and it's where you set up the object's data. self is the instance itself; Python passes it in as the first argument of every method, so self.name = name means “store name on this object.”

Two kinds of attribute: instance attributes (set on self, unique per object) and class attributes (defined on the class, shared by all instances).

You write book.discounted(0.1), and Python turns it into Item.discounted(book, 0.1) — quietly slotting the instance in as self. It's a normal parameter with a conventional name, nothing magic.

03  Inheritance & super()

A subclass inherits everything from its parent and can add to it or override parts. Plain English: “a Lion is an Animal, with extras.” super() calls the parent's version of a method — most often super().__init__(...) to reuse the parent's setup instead of repeating it.

This is how every Pydantic model is built

When you write class Item(BaseModel): ..., your Item inherits all of Pydantic's validation and serialization machinery from BaseModel. SQLModel tables do the same. Understanding inheritance is understanding why those models “just work”.

model.py
from pydantic import BaseModel

class Item(BaseModel):       # a subclass of BaseModel — inheritance!
    name: str
    price: float

# Your Item now has validation, .model_dump(), JSON parsing… all inherited.

04  Dunder (special) methods

“Dunder” = double underscore. These are methods Python calls for you in response to syntax: __init__ on creation, __repr__ when printing/inspecting, __eq__ for ==, __add__ for +, __len__ for len(). Implement them and your objects behave like built-in types.

Right. == calls __eq__. Without it, Python falls back to “are these the exact same object in memory?”, so two equal-looking Money values would compare False.

05  @property, @classmethod, @staticmethod

These three decorators (next lesson explains what a decorator is) change how a method behaves:

Three method flavors
@property
access a method like an attribute — obj.area, no parentheses. Great for computed values.
@classmethod
receives the class as cls instead of an instance — handy for alternative constructors.
@staticmethod
receives neither self nor cls — just a plain function grouped inside the class.

06  Dataclasses

Writing __init__, __repr__, and __eq__ by hand gets repetitive. @dataclass generates them for you from your annotated fields — you just declare the data.

data.py
Point(x=1, y=2, label='origin')
True
1 origin
Pydantic = a dataclass that also validates

A Pydantic BaseModel looks almost identical to a dataclass — fields with type hints — but it enforces those types at runtime, parsing and rejecting bad data. That's the leap FastAPI relies on.

compare.py
from dataclasses import dataclass
from pydantic import BaseModel

@dataclass
class PointDC:          # stores x, y — but won't stop you passing "abc"
    x: int
    y: int

class PointPD(BaseModel):   # same shape, but VALIDATES: "abc" -> error
    x: int
    y: int
Exercise

Write a Rectangle class with width and height, an area property, and a friendly __repr__.

Calling print(r, "->", r.area) on a 3×4 rectangle should print Rectangle(3x4) -> 12. Try it, then check the solution.

exercise.py
(write your solution and press Run)
Show solution solution
solution.py
class Rectangle:
    def __init__(self, width, height):
        self.width = width
        self.height = height

    @property
    def area(self):
        return self.width * self.height

    def __repr__(self):
        return f"Rectangle({self.width}x{self.height})"

r = Rectangle(3, 4)
print(r, "->", r.area)   # -> Rectangle(3x4) -> 12

The @property turns area into a computed attribute (no parentheses at the call site), and __repr__ controls how the object prints. Together they make Rectangle feel like a built-in type.
