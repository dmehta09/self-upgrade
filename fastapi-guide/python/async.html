Python · async in depth

Doing other work while you wait.

A web server spends most of its life waiting — on a database, another API, the network. async lets one process serve many requests during that idle time instead of sitting blocked. The refresher introduced async/await; here we go deeper: the event loop, running things concurrently, and the one mistake that quietly ruins it.

01  The event loop & coroutines

An async def function is a coroutine: it can pause at every await and hand control back, then resume later. The event loop is the scheduler that runs many coroutines on a single thread, switching to another whenever the current one is waiting. await means “pause me here until this finishes; run something else meanwhile.”

coroutine.py
hello Ada

In a real script there's no loop yet, so you start one with asyncio.run(main()) — that's the single entry point that creates the loop, runs your top coroutine, and closes it:

script.py
import asyncio

async def main():
    print(await greet("Ada"))

asyncio.run(main())     # creates the loop, runs main(), cleans up

02  await & asyncio.gather

Awaiting calls one after another is still sequential — each finishes before the next starts. To overlap the waiting, hand several coroutines to asyncio.gather: it runs them concurrently and returns all results once they're done, in the order you passed them (not the order they finished).

gather.py
['users done', 'orders done', 'stats done']
gather vs create_task

gather(...) is the quick way to fan out and wait for everything. asyncio.create_task(coro) schedules a coroutine to run in the background now and hands you a handle to await later — useful when you want work started but not yet joined.

03  Concurrency vs parallelism

Crucial distinction. Concurrency is one worker juggling many tasks by switching whenever one waits — that's asyncio, on a single thread. Parallelism is many workers running at the literal same instant on multiple CPU cores. Async gives you the first, not the second.

One thread, taking turns
I/O-bound work
waiting on network/disk/DB → async wins (overlap the waiting)
CPU-bound work
crunching numbers, no waiting → async does not help; use processes
asyncio
concurrency on one thread (cooperative switching at await)
multiprocessing
true parallelism across cores

You can see the cooperative switching: both tasks start before either resumes, because each yields control at its await.

interleave.py
A: start
B: start
A: resume
B: resume

Will marking a CPU-heavy function async def make it run faster?

Right. Async overlaps waiting. CPU-bound work never waits, so it just hogs the single thread — and worse, blocks every other task. Reach for multiprocessing or a worker queue instead.

04  async with & async for

The async cousins of two things you already know. async with is a context manager whose setup and teardown are themselves async — an async HTTP client or database session. async for iterates an async generator that awaits between items — perfect for streaming data as it arrives.

2
3

In real code, async with is everywhere an HTTP client or DB session appears:

client.py
import httpx

async def fetch_json(url: str):
    async with httpx.AsyncClient() as client:   # async setup + teardown
        response = await client.get(url)
        return response.json()

05  Don't block the loop

The golden rule: async only helps if you await async libraries. A blocking call inside a coroutine — time.sleep, a synchronous DB driver, a heavy computation — freezes the entire event loop, so every request stalls until it returns. When you must run blocking work, offload it to a thread with asyncio.to_thread, keeping the loop free.

offload.py
computed
One blocking line stalls the whole server

Because everything shares one thread, a single time.sleep(5) in an async handler pauses every other in-flight request for 5 seconds. If a library isn't async-aware, either don't await it on the loop, or push it to a thread/process.

06  How this maps to FastAPI

FastAPI is built on the event loop, and it's smart about it. Write async def for a route and it runs on the loop — perfect when you await async DB/HTTP calls. Write a plain def route and FastAPI automatically runs it in a threadpool, so a blocking call there won't freeze the loop.

Which one do I write?
async def route
when you await async libraries (httpx, async DB) — runs on the loop
def route
when your code is sync/blocking — FastAPI offloads it to a threadpool for you
BackgroundTasks
fire-and-forget work after the response is sent
lifespan
an @asynccontextmanager for startup/shutdown (async with!)
The decision in one line

Awaiting something async? Use async def. Calling blocking/sync code? A plain def route is safer — let FastAPI's threadpool handle it. The Advanced page applies exactly this to real routes, background tasks, and lifespan.

Exercise

Write code that runs three say(word) coroutines concurrently with asyncio.gather and prints the uppercased results.

Given say("a"), say("b"), say("c"), the result should be ['A', 'B', 'C'].

exercise.py
(write your solution and press Run)
Show solution solution
solution.py
import asyncio

async def say(word):
    await asyncio.sleep(0)
    return word.upper()

results = await asyncio.gather(say("a"), say("b"), say("c"))
print(results)        # ['A', 'B', 'C']  — order matches the arguments

All three coroutines run concurrently; gather waits for the slowest and returns the results in argument order. Swap asyncio.sleep for a real await on an async client and this is a genuine concurrent fan-out.
