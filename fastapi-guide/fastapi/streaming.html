Advanced · beyond request/response

When one answer isn't enough.

Everything so far has been a polite exchange: one request in, one response out, goodbye. But some conversations don't fit in an envelope — a 2 GB export, a live progress feed, a chat room. This page covers FastAPI's three escapes from request/response — StreamingResponse, Server-Sent Events, and WebSockets — plus file uploads and downloads.

01  One answer isn't always enough

The HTTP model you've used everywhere in this guide is request → response → done. The client asks, you answer once, the connection's work is finished. That's perfect for CRUD — and awkward for three kinds of jobs:

Huge CSV export, big file, LLM tokens as they generate
StreamingResponse — still one request, one response, but the body arrives in chunks instead of one giant blob. One-way, ends when the data ends.
Live progress bar, notification feed, "server pushes, client listens"
Server-Sent Events (SSE) — a long-lived response the server keeps appending events to. One-way (server → client), plain HTTP, browsers auto-reconnect.
Chat, multiplayer games, live cursors, collaborative editing
WebSocket — a long-lived, two-way connection. Either side can talk at any time, no request needed.
Letter, radio, phone call analogy

A normal response is a letter: written, sealed, delivered, done. A streaming response is a letter mailed page by page as you write it. SSE is a radio broadcast: tune in once and the station keeps talking — you only listen. A WebSocket is a phone call: the line stays open and both sides can speak whenever they like.

Pick the simplest tool that fits. Most "real-time" features are one-way (server pushing updates), which means SSE or streaming covers them — a WebSocket is only worth its keep when the client also needs to talk mid-conversation.

02  StreamingResponse + generators

Remember lazy generators from the Generators lesson? This is where they earn rent. A StreamingResponse takes any (async) generator and sends each yield to the client the moment it's produced:

stream_csv.py
from fastapi import FastAPI
from fastapi.responses import StreamingResponse

app = FastAPI()

@app.get("/export")
async def export_heroes():
    async def generate():
        yield "id,name,power\n"                  # header goes out immediately
        async for hero in fetch_heroes():        # rows from an async DB cursor
            yield f"{hero.id},{hero.name},{hero.power}\n"

    return StreamingResponse(generate(), media_type="text/csv")

The memory story is the whole point. With a normal response, a million-row export means building a million-row string in RAM before the first byte leaves the server. With a generator, you hold one row at a time — the client starts downloading instantly, and your server's memory stays flat whether the export is ten rows or ten million.

A blocking generator blocks the loop

The async vs def rule applies inside the generator too. If each chunk comes from a blocking call (a sync DB cursor, slow disk reads), a plain def generate() yielding from inside an async endpoint will stall the event loop between chunks. Either make the generator genuinely async (async def + an async source), or hand FastAPI a sync generator — it will iterate it in the threadpool for you.

03  Server-Sent Events

SSE is just a streaming response with a dress code. The media type is text/event-stream, and every event is a line starting with data: followed by a blank line — that \n\n is what tells the browser "event complete, deliver it."

events.py
import asyncio
import json
from fastapi import FastAPI
from fastapi.responses import StreamingResponse

app = FastAPI()

@app.get("/events")
async def progress_feed():
    async def event_stream():
        for pct in range(0, 101, 10):
            payload = json.dumps({"progress": pct})
            yield f"data: {payload}\n\n"          # "data: ..." + blank line = one event
            await asyncio.sleep(0.5)              # async sleep — the loop stays free

    return StreamingResponse(event_stream(), media_type="text/event-stream")

The browser side is delightfully small — EventSource is built in, no library needed:

browser.js
const source = new EventSource("/events");

source.onmessage = (event) => {
  const { progress } = JSON.parse(event.data);
  bar.style.width = `${progress}%`;
};
// If the connection drops, EventSource reconnects automatically.

When does SSE beat a WebSocket? When the data flows one way. It's plain HTTP — it rides through proxies, load balancers, and auth middleware like any other request — and the browser handles reconnection for free. Live LLM token streams, dashboards, notification feeds: SSE is usually all you need.

You're building a "model is thinking…" feed that streams LLM tokens to the browser as they generate. The browser never sends anything back mid-stream. Best fit?

Correct. "Real-time" doesn't automatically mean WebSocket. The flow here is strictly server → client, which is exactly SSE's shape — simpler to deploy (plain HTTP), and EventSource reconnects on its own. Save WebSockets for genuinely two-way traffic.

04  WebSockets

When both sides need to talk — chat, games, live collaboration — you open the phone line. A WebSocket endpoint uses @app.websocket instead of @app.get, and instead of returning once, it loops:

ws.py
from fastapi import FastAPI, WebSocket, WebSocketDisconnect

app = FastAPI()

@app.websocket("/ws")
async def echo(ws: WebSocket):
    await ws.accept()                        # pick up the phone
    try:
        while True:
            text = await ws.receive_text()   # wait for the client to speak
            await ws.send_text(f"you said: {text}")
    except WebSocketDisconnect:
        print("client hung up")              # always handle the hang-up

Read that shape carefully: accept() once, then an endless receive/send loop. When the client closes the tab, receive_text() raises WebSocketDisconnect — catching it is how you do cleanup. The browser side:

browser.js
const ws = new WebSocket("ws://localhost:8000/ws");

ws.onopen    = () => ws.send("hello");
ws.onmessage = (event) => console.log(event.data);   // "you said: hello"
ws.onclose   = () => console.log("connection closed");
DI still works — automatic docs don't

WebSocket endpoints can use Depends like any other (great for auth: validate a token before accept()), and you can validate incoming JSON by parsing it into Pydantic models yourself. But WebSockets don't appear in /docs — OpenAPI describes request/response endpoints, not open phone lines.

05  A tiny chat: the broadcast pattern

An echo server is a phone call with yourself. The classic next step is a connection manager: keep a list of everyone on the line, and when one person speaks, repeat it to all of them.

chat.py
from fastapi import FastAPI, WebSocket, WebSocketDisconnect

class ConnectionManager:
    def __init__(self) -> None:
        self.active: list[WebSocket] = []

    async def connect(self, ws: WebSocket) -> None:
        await ws.accept()
        self.active.append(ws)

    def disconnect(self, ws: WebSocket) -> None:
        self.active.remove(ws)

    async def broadcast(self, message: str) -> None:
        for ws in self.active:
            await ws.send_text(message)

manager = ConnectionManager()
app = FastAPI()

@app.websocket("/chat/{name}")
async def chat(ws: WebSocket, name: str):
    await manager.connect(ws)
    try:
        while True:
            text = await ws.receive_text()
            await manager.broadcast(f"{name}: {text}")
    except WebSocketDisconnect:
        manager.disconnect(ws)
        await manager.broadcast(f"{name} left the chat")

That's a working chat room in ~30 lines — open two browser tabs and talk to yourself. One honest caveat: manager.active lives in one process's memory. The moment you scale to multiple workers or servers, a user on worker A can't see connections held by worker B. The fix is a message bus — typically Redis pub/sub — where every worker publishes messages and subscribes to the same channel. That's a Production-patterns-sized topic; for now, just know the single-process version has a ceiling.

06  File uploads & downloads

Last stop: moving files. Uploads use UploadFile — declare it like any parameter and FastAPI handles the multipart form parsing:

upload.py
# pip install python-multipart   <- required for any form/file endpoint
from fastapi import FastAPI, UploadFile

app = FastAPI()

@app.post("/upload")
async def upload(file: UploadFile):
    contents = await file.read()             # fine for small files
    return {"filename": file.filename, "size": len(contents)}

@app.post("/upload-big")
async def upload_big(file: UploadFile):
    with open(f"uploads/{file.filename}", "wb") as out:
        while chunk := await file.read(1024 * 1024):   # 1 MB at a time
            out.write(chunk)
    return {"saved": file.filename}

Same lesson as section 02, in reverse: await file.read() with no argument pulls the whole file into memory. For an avatar, fine. For a 4 GB video, stream it to disk in chunks like upload_big does.

There is no size limit by default

FastAPI won't stop a client from uploading something enormous. Check file.size (or count bytes as you stream) and reject oversized uploads with a 413 — and set a hard cap at your reverse proxy (e.g. nginx's client_max_body_size) so junk never reaches Python at all.

Downloads go the other way. For a file that already exists on disk, FileResponse is the easy button — it streams from disk efficiently and sets Content-Length and the download filename for you:

download.py
from fastapi.responses import FileResponse

@app.get("/report")
def download_report():
    return FileResponse("reports/q2.pdf", filename="q2-report.pdf")

Rule of thumb: file already on disk → FileResponse. Content generated on the fly (a CSV built from a query, a zip assembled per-request) → StreamingResponse with a generator, since there's no file to point at.

An endpoint builds a 500 MB CSV from a database query and returns it. What's the right move?

Correct. Building the string means 500 MB in RAM per request before the first byte is sent. FileResponse only works if the file already exists on disk (and writing it first just moves the problem). A generator yields row by row — flat memory, instant first byte.
