The habits of APIs that don't fall over.

An API that works on your laptop and an API that strangers depend on are different animals. The difference is a handful of habits: never return unbounded lists, never break clients silently, always fail in the same shape, say no politely when someone hammers you, don't recompute what you just computed, and leave footprints you can follow at 2 a.m. This page is those habits, one by one.

01  Pagination: never return everything

GET /heroes returning all heroes is fine with 50 rows and a disaster with 5 million — one curious client can flatten your database and your memory at once. Rule one of production lists: every list endpoint takes a limit, and the limit has a ceiling.

pagination_offset.py
from typing import Annotated
from fastapi import FastAPI, Query
from pydantic import BaseModel
from sqlmodel import select, func

app = FastAPI()

class HeroPage(BaseModel):
    items: list[Hero]          # the page itself
    total: int                 # how many exist overall
    limit: int
    offset: int

@app.get("/heroes", response_model=HeroPage)
def list_heroes(
    session: SessionDep,
    limit: Annotated[int, Query(ge=1, le=100)] = 20,   # ceiling: 100, no exceptions
    offset: Annotated[int, Query(ge=0)] = 0,
):
    total = session.exec(select(func.count()).select_from(Hero)).one()
    items = session.exec(select(Hero).offset(offset).limit(limit)).all()
    return HeroPage(items=items, total=total, limit=limit, offset=offset)

The envelope matters as much as the limit. Returning a bare array means clients can never tell "that's all of them" from "that's the first page" — wrapping it in {items, total, limit, offset} tells them exactly where they stand. And Query(le=100) means even ?limit=999999 gets a clean 422 instead of melting the server.

Offset pagination is the right starting point — but it has two quiet problems at depth. First, OFFSET 100000 doesn't skip 100,000 rows; the database still walks past every one of them before returning yours, so page 5,000 is dramatically slower than page 1. Second, pages drift: if a row is inserted while a client is paging, everything shifts by one and they see a duplicate (or miss a row) on the next page.

A bookmark vs counting pages analogy

Offset is "open the book and count 4,000 pages from the front" — slow, and if someone glued in a new page overnight, you land somewhere different. A cursor is a bookmark: "continue from exactly here." No counting, and new pages elsewhere in the book can't move your bookmark.

The fix is cursor (keyset) pagination: instead of "skip N rows," the client says "give me rows after this id." The database jumps straight there via the index.

pagination_cursor.py
@app.get("/heroes")
def list_heroes(
    session: SessionDep,
    cursor: Annotated[int, Query(ge=0)] = 0,            # "after this id"
    limit: Annotated[int, Query(ge=1, le=100)] = 20,
):
    items = session.exec(
        select(Hero)
        .where(Hero.id > cursor)      # WHERE id > :cursor — index jump, no scan
        .order_by(Hero.id)
        .limit(limit)
    ).all()
    next_cursor = items[-1].id if len(items) == limit else None
    return {"items": items, "next_cursor": next_cursor}
    # client: keep calling /heroes?cursor={next_cursor} until it's null

Trade-off: cursors can't jump to "page 47" and need a unique, ordered column (an id or a (created_at, id) pair). Offset for small admin tables and page-number UIs; cursor for big or busy data and infinite scroll.

02  API versioning

Once anyone you don't sit next to uses your API, its shape is a promise. Some changes keep the promise; some break it:

Non-breaking
Adding a new optional field to a response, adding a new endpoint, adding an optional query param. Old clients ignore what they don't know. Ship freely.
Breaking
Renaming or removing a field, changing a type (id: int → id: str), making an optional param required, changing a status code. Old clients crash. This needs a version.

The pragmatic pattern: put the version in the path, one router per version, both mounted on the same app. You already know everything required — it's just include_router with a prefix.

main.py
from fastapi import FastAPI
from routers import heroes_v1, heroes_v2

app = FastAPI()
app.include_router(heroes_v1.router, prefix="/v1")   # GET /v1/heroes -> {"name": ...}
app.include_router(heroes_v2.router, prefix="/v2")   # GET /v2/heroes -> {"full_name": ...}

# routers/heroes_v2.py — same endpoint, the *new* response shape
from fastapi import APIRouter
from pydantic import BaseModel

router = APIRouter(prefix="/heroes", tags=["heroes-v2"])

class HeroV2(BaseModel):
    id: int
    full_name: str        # v1 called this "name" — that rename is the break

@router.get("", response_model=list[HeroV2])
def list_heroes(session: SessionDep):
    ...

Old clients keep calling /v1 and nothing changes for them; new clients adopt /v2 on their own schedule. When /v1 traffic finally dries up, you announce a sunset date and delete a router — one line.

Version when you must break — not before

A new version is a cost: two routers to maintain, two docs pages, clients to migrate. Additive changes never need one. Teams that bend over backwards to stay additive (add full_name alongside name, deprecate later) often live on /v1 for years — that's a feature, not laziness.

Header-based versioning exists too

Some APIs (notably Stripe) version via a request header instead of the path, which keeps URLs stable. It's elegant but harder to test in a browser, cache, and document. Path versioning is the boring, visible, pragmatic default — start there.

03  Consistent errors with exception handlers

By the time an app has thirty endpoints, "item missing" is handled thirty slightly different ways. The production move: raise a domain exception anywhere, shape it into JSON in exactly one place — an @app.exception_handler. The envelope below follows the RFC 9457 "problem details" style: a type (machine-readable), a title (short human label), and a detail (the specifics).

errors.py
from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse

class ItemNotFound(Exception):
    def __init__(self, item_id: int):
        self.item_id = item_id

app = FastAPI()

@app.exception_handler(ItemNotFound)
async def item_not_found_handler(request: Request, exc: ItemNotFound):
    return JSONResponse(
        status_code=404,
        content={
            "type": "https://api.example.com/errors/item-not-found",
            "title": "Item not found",
            "detail": f"No item with id {exc.item_id} exists.",
        },
    )

@app.get("/items/{item_id}")
def read_item(item_id: int, session: SessionDep):
    item = session.get(Item, item_id)
    if item is None:
        raise ItemNotFound(item_id)   # raise from anywhere — handler shapes it
    return item

Endpoints stay clean — they raise and move on — and every 404 in your whole API now looks identical. Clients write their error handling once.

One error still won't match: FastAPI's built-in 422, whose default {"detail": [...]} shape you met on the Validation page. You can re-shape it into the same envelope by catching RequestValidationError:

errors_422.py
from fastapi.exceptions import RequestValidationError

@app.exception_handler(RequestValidationError)
async def validation_handler(request: Request, exc: RequestValidationError):
    return JSONResponse(
        status_code=422,
        content={
            "type": "https://api.example.com/errors/validation",
            "title": "Validation failed",
            "detail": [
                {"field": ".".join(str(loc) for loc in err["loc"]),
                 "message": err["msg"]}
                for err in exc.errors()
            ],
        },
    )
Never leak internals in error bodies

Stack traces, SQL fragments, file paths, library names — all of it is a gift to attackers and a confusing mess for clients. Your catch-all 500 handler should return a bland {"title": "Internal error", "detail": "Something went wrong."} and log the juicy traceback server-side, tagged with the request id from section 06.

Thirty endpoints can each hit a missing database row. What's the cleanest way for all of them to return the same 404 shape?

Correct. Endpoints just raise ItemNotFound(id) and stay focused on their job; the single registered handler turns it into the one true 404 envelope. Change the shape later and you edit one function, not thirty.

04  Rate limiting

Three reasons your API needs a speed limit: abuse (someone brute-forcing your login endpoint), runaway clients (a bugged retry loop calling you 500 times a second — usually your own front-end), and cost (every request touches a database, and maybe a paid LLM API). A rate limit converts all three from outages into polite 429s.

The classic mental model is the token bucket. Each client has a bucket that refills at a steady drip — say 5 tokens per minute. Every request spends one token; a request that finds the bucket empty gets a 429 Too Many Requests. Because the bucket can hold a few tokens, short bursts are fine — only sustained overuse gets throttled.

ratelimit.py
# pip install slowapi
from fastapi import FastAPI, Request
from slowapi import Limiter, _rate_limit_exceeded_handler
from slowapi.errors import RateLimitExceeded
from slowapi.util import get_remote_address

limiter = Limiter(key_func=get_remote_address)   # bucket per client IP

app = FastAPI()
app.state.limiter = limiter
app.add_exception_handler(RateLimitExceeded, _rate_limit_exceeded_handler)

@app.get("/search")
@limiter.limit("5/minute")           # the 6th call within a minute -> 429
def search(request: Request, q: str):
    return {"results": do_expensive_search(q)}

The rejection comes back as a 429 with a Retry-After header — the standard way of saying "not no, just not yet":

the 429
HTTP/1.1 429 Too Many Requests
Retry-After: 42

{"error": "Rate limit exceeded: 5 per 1 minute"}
In real deployments, the gateway often does this

At scale, rate limiting usually lives in front of your app — nginx, an API gateway, or a Redis-backed limiter shared across replicas (per-IP counters in one process don't see traffic hitting the other three replicas). The contract stays identical either way: clients get a clean 429 + Retry-After, and well-behaved ones back off.

05  Caching

The cheapest request is the one you never have to compute. Reach for HTTP's built-in caching first — it's free, standardized, and the browser already speaks it. Two headers do most of the work: Cache-Control: max-age=60 ("don't even ask me again for 60 seconds") and ETag ("here's a fingerprint of this response — next time, ask if it changed").

The ETag conversation looks like this:

etag flow
GET /heroes/1 HTTP/1.1            # first visit

HTTP/1.1 200 OK                   # full body + a fingerprint
Cache-Control: max-age=60
ETag: "v7"

{"id": 1, "name": "Deadpond", ...}

GET /heroes/1 HTTP/1.1            # later: "only if it changed"
If-None-Match: "v7"

HTTP/1.1 304 Not Modified         # empty body — "your copy is still good"
ETag: "v7"

Serving that from FastAPI is a handful of lines — compare the client's fingerprint, and skip the body if it matches:

etag.py
from fastapi import FastAPI, Request, Response

@app.get("/heroes/{hero_id}")
def read_hero(hero_id: int, request: Request, response: Response, session: SessionDep):
    hero = session.get(Hero, hero_id)
    etag = f'"{hero.updated_at.timestamp()}"'        # any value that changes when data does

    if request.headers.get("if-none-match") == etag:
        return Response(status_code=304)             # no body — client reuses its copy

    response.headers["ETag"] = etag
    response.headers["Cache-Control"] = "max-age=60"
    return hero

For responses that are expensive to compute rather than transfer — a dashboard aggregation, a report — cache server-side with a tiny dict-with-expiry:

ttl_cache.py
import time

_cache: dict[str, tuple[float, dict]] = {}     # key -> (stored_at, value)

def cached(key: str, ttl: float, compute):
    hit = _cache.get(key)
    if hit and time.monotonic() - hit[0] < ttl:
        return hit[1]                          # fresh enough — skip the work
    value = compute()
    _cache[key] = (time.monotonic(), value)
    return value

@app.get("/stats")
def stats(session: SessionDep):
    return cached("stats", ttl=30, compute=lambda: compute_stats(session))

For values that load once and never change while the process runs — parsed config, a public key — @functools.lru_cache on a zero-argument function is perfect (it's the standard trick for caching the Settings() object). But lru_cache has no expiry: cache anything per-user or time-sensitive with it and you'll serve stale — or worse, someone else's — data forever.

Never cache user-specific responses in a shared cache

If /me gets cached under the key "me", the second user to call it receives the first user's profile. Every cache entry for authenticated data must include the user in its key (f"me:{user.id}") — and HTTP responses that vary per user should send Cache-Control: private so shared proxies never store them. This exact bug has caused real-world data leaks at big companies.

06  Seeing your API in production

In production you can't drop into a debugger — your only window into the running app is what it tells you. So make it tell you things a machine can search: structured (JSON) logs, one line per request, each carrying a request id you can follow through the whole story of a single call.

The pattern: accept an X-Request-ID header if the caller (or your load balancer) sent one, generate one otherwise, log it with every line, and return it in the response so a user can read you the id from their error screen:

request_id.py
import json, logging, time, uuid
from fastapi import FastAPI, Request

logger = logging.getLogger("api")
app = FastAPI()

@app.middleware("http")
async def request_id_middleware(request: Request, call_next):
    rid = request.headers.get("X-Request-ID") or uuid.uuid4().hex[:12]
    start = time.perf_counter()
    response = await call_next(request)
    response.headers["X-Request-ID"] = rid           # echo it back to the caller
    logger.info(json.dumps({
        "request_id": rid,
        "method": request.method,
        "path": request.url.path,
        "status": response.status_code,
        "duration_ms": round((time.perf_counter() - start) * 1000, 1),
    }))
    return response

Now "the app feels slow" becomes a query: filter for duration_ms > 1000, group by path, done. And when a user reports a failure, one grep for their request id shows you everything that request touched.

Next, give your platform a way to ask "are you alive?" — a health endpoint. Keep it cheap: it gets called every few seconds by load balancers and orchestrators, so it should not hit the database by default (or a slow DB makes the platform think your app is dead and restart it, making everything worse):

healthz.py
@app.get("/healthz", include_in_schema=False)   # hide it from /docs
def healthz():
    return {"status": "ok"}                     # process up + event loop responsive

Logs and a health check are the floor. The next rungs are metrics (counters and latency histograms you can graph and alert on) and traces (the request-id idea, upgraded to follow a request across services) — usually via OpenTelemetry and Prometheus.

A user emails: "something failed around 3pm." What makes finding their exact request in the logs trivial?

Correct. The user reads you the id from their error screen (your front-end shows it because the API returned it in X-Request-ID), and one search pulls up every log line for exactly that request. Logging full bodies is a privacy hazard, and /healthz only says the process is up — it knows nothing about individual requests.
