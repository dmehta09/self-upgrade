FastAPI · async & structure

The bits that turn a script into an app.

You can build a lot with what you know. This page covers the production touches: when to use async def, running work in the background, middleware and CORS, splitting routes into routers, loading settings safely, and running setup code at startup.

01  async def vs def

FastAPI accepts both. The rule is simple:

async def
Use when you await async libraries (an async DB driver, httpx.AsyncClient). Runs on the event loop.
def
Use for normal blocking code (most DB drivers, file I/O). FastAPI runs it in a thread pool so it won't block the server.
The dangerous middle ground

Putting blocking code inside an async def (e.g. a synchronous DB call or time.sleep) blocks the whole event loop and stalls every other request. If a library isn't async, use a plain def endpoint and let FastAPI thread it.

02  Background tasks

Need to do something after responding — send an email, write a log — without making the client wait? Add a BackgroundTasks parameter and schedule work on it.

background.py
from fastapi import FastAPI, BackgroundTasks

app = FastAPI()

def write_log(message: str):
    with open("log.txt", "a") as f:
        f.write(message + "\n")

@app.post("/signup")
def signup(email: str, tasks: BackgroundTasks):
    tasks.add_task(write_log, f"new signup: {email}")   # runs after the response
    return {"ok": True}

For heavy or critical jobs (video processing, retries), reach for a real task queue like Celery or ARQ instead — background tasks are best for quick, fire-and-forget work.

03  Middleware & CORS

Middleware wraps every request/response — for logging, timing, headers. The one you'll almost certainly need is CORS, which lets a browser front-end on a different origin call your API.

cors.py
from fastapi import FastAPI
from fastapi.middleware.cors import CORSMiddleware

app = FastAPI()

app.add_middleware(
    CORSMiddleware,
    allow_origins=["https://myfrontend.com"],   # who may call us
    allow_methods=["*"],
    allow_headers=["*"],
    allow_credentials=True,
)
“CORS error” = missing this

If your browser console says a request was “blocked by CORS policy,” you almost always just need to add CORSMiddleware with your front-end's origin. Avoid allow_origins=["*"] together with allow_credentials=True — browsers reject that combination.

04  Routers & project structure

One giant main.py doesn't scale. Split related endpoints into an APIRouter and include them in the app — like a mini-FastAPI per feature.

routers/heroes.py

router = APIRouter(prefix="/heroes", tags=["heroes"])

@router.get("")          # becomes GET /heroes

    return [...]

# --- in main.py ---
from fastapi import FastAPI
from routers import heroes

app = FastAPI()
app.include_router(heroes.router)

A clean starting layout for a real project:

project tree
app/
  main.py          # creates FastAPI(), includes routers, lifespan
  database.py      # engine, get_session
  models.py        # SQLModel tables + schemas
  config.py        # Settings (pydantic-settings)
  security.py      # hashing + JWT helpers
  routers/
    heroes.py
    auth.py
tests/
  test_heroes.py

05  Settings & secrets

Never hard-code secrets. pydantic-settings reads configuration from environment variables (and a .env file), validated just like any Pydantic model.

config.py
# pip install pydantic-settings
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    app_name: str = "Hero API"
    secret_key: str                       # required -> must be set in env/.env
    access_token_minutes: int = 30
    model_config = SettingsConfigDict(env_file=".env")

settings = Settings()   # reads SECRET_KEY, APP_NAME, ... from the environment

06  Lifespan: startup & shutdown

To run code once when the app starts (create tables, open a connection pool) and once when it stops, use a lifespan context manager. This replaces the old @app.on_event("startup") decorators.

main.py
from contextlib import asynccontextmanager
from fastapi import FastAPI

@asynccontextmanager
async def lifespan(app: FastAPI):
    create_db_and_tables()      # startup: before serving requests
    yield
    print("shutting down")      # shutdown: after the last request

app = FastAPI(lifespan=lifespan)

Which is the current way to run code at startup?

Correct. @app.on_event(...) is deprecated. The lifespan context manager — setup before yield, teardown after — is the modern, recommended approach.
