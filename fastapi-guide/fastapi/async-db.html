Databases · async & migrations

One waiter, no standing around.

The last lesson used plain def endpoints and let FastAPI's threadpool absorb the blocking database calls. That works. But there's a second, sharper option: an async driver, where one event loop juggles hundreds of in-flight queries without ever standing still. This lesson makes the database fully async — and then teaches the tool you'll need the moment your schema changes with real data in it: Alembic.

01  Why async DB access?

Quick recap of the rule from the loop lab on the Async & structure page: a sync DB call inside async def blocks the entire event loop. While that one query waits on the database, every other request on your server waits too — the loop is a single waiter, and you've sent it to stand in the kitchen.

There are exactly two correct ways to talk to a database from FastAPI:

Plain def + threadpool
What the SQLModel lesson did. FastAPI runs the endpoint in a worker thread, so blocking calls only occupy that thread. Simple, correct, and fine for most apps.
async def + async driver
The endpoint awaits every database call. While a query is in flight, the loop serves other requests. Scales to many concurrent, I/O-bound requests without burning a thread per request.
The restaurant, again

The threadpool model hires one waiter per table — works, but waiters are expensive and there's a fixed number of them. The async model has one waiter who takes your order, hands it to the kitchen (the database), and immediately moves to the next table. They come back when the kitchen rings the bell (await resolves). Nobody ever just stands there. The catch: that waiter must never get stuck stirring a pot themselves — one blocking call and the whole restaurant freezes.

When does async actually pay off? When you have many concurrent requests that spend most of their time waiting on I/O — a chat backend, a dashboard polling endpoint, anything fronting a slow upstream. If your traffic is ten requests a second against a fast local database, the threadpool version is indistinguishable. We'll make that trade-off concrete in section 07.

02  The async engine & session

Going async means swapping three pieces, each the async twin of something you already know: the engine, the session class, and a session factory. The driver changes too — async needs a driver that speaks non-blocking I/O, and you name it right in the connection string.

terminal
pip install sqlmodel aiosqlite
# for PostgreSQL later: pip install asyncpg
db.py
from sqlalchemy.ext.asyncio import create_async_engine, async_sessionmaker
from sqlmodel import SQLModel
from sqlmodel.ext.asyncio.session import AsyncSession

#                         driver ↓ named in the URL
engine = create_async_engine("sqlite+aiosqlite:///app.db")
# PostgreSQL would be:  "postgresql+asyncpg://user:pass@localhost/app"

async_session = async_sessionmaker(engine, class_=AsyncSession,
                                   expire_on_commit=False)

async def create_db_and_tables():
    async with engine.begin() as conn:
        await conn.run_sync(SQLModel.metadata.create_all)
create_async_engine
The async twin of create_engine. Still created once, still your pool of connections — but every conversation through it is awaitable.
AsyncSession
The async twin of Session. We import SQLModel's flavour (sqlmodel.ext.asyncio.session) so it keeps the nice .exec() API; plain SQLAlchemy's AsyncSession works with SQLModel models too and looks almost identical — you'd just write .execute() and unwrap .scalars().
async_sessionmaker
A factory: call async_session() to get a fresh session. expire_on_commit=False keeps your objects readable after commit() instead of forcing a (now awkward, because async) reload on attribute access.
SQLModel rides on SQLAlchemy 2.0

None of this async machinery is SQLModel magic — it's SQLAlchemy 2.0 underneath, with your SQLModel classes as the table definitions on top. That's good news: every SQLAlchemy async doc, blog post, and Stack Overflow answer applies directly.

03  The async session dependency

In the sync lesson, a yield dependency opened a session per request and closed it afterwards. The async version is the same shape with two extra keywords — async def and async with:

db.py (continued)
from typing import Annotated
from fastapi import Depends

async def get_session():
    async with async_session() as session:   # opens, then auto-closes
        yield session

SessionDep = Annotated[AsyncSession, Depends(get_session)]

Put them side by side and the symmetry is the whole lesson:

Sync (last lesson)Async (this lesson)
def get_session():async def get_session():
with Session(engine) as session:async with async_session() as session:
yield sessionyield session
Annotated[Session, Depends(...)]Annotated[AsyncSession, Depends(...)]
Endpoints don't change their signature

Routes still just declare session: SessionDep. FastAPI handles async yield dependencies natively — the cleanup after yield runs on the loop, no threadpool involved. Your dependency tree can mix sync and async dependencies freely.

04  CRUD, awaited

Same Hero models as the last lesson, same operations — but the endpoints are async def and everything that actually touches the database grows an await:

routes.py
from fastapi import FastAPI, HTTPException
from sqlmodel import select

app = FastAPI()

@app.post("/heroes", response_model=HeroPublic, status_code=201)
async def create_hero(hero: HeroCreate, session: SessionDep):
    db_hero = Hero.model_validate(hero)
    session.add(db_hero)              # no await — just bookkeeping in memory
    await session.commit()            # await — actually talks to the DB
    await session.refresh(db_hero)    # await — reloads to get the new id
    return db_hero

@app.get("/heroes", response_model=list[HeroPublic])
async def list_heroes(session: SessionDep, offset: int = 0, limit: int = 20):
    result = await session.exec(select(Hero).offset(offset).limit(limit))
    return result.all()

@app.get("/heroes/{hero_id}", response_model=HeroPublic)
async def get_hero(hero_id: int, session: SessionDep):
    hero = await session.get(Hero, hero_id)
    if not hero:
        raise HTTPException(404, "Hero not found")
    return hero

The mental model: await anything that crosses the wire to the database — exec, get, commit, refresh, delete's commit. session.add() stays plain because it only marks the object as pending in the session's in-memory notebook; nothing hits the database until commit (or a query that flushes first).

The silent killer: a forgotten await

Write session.commit() without await and Python doesn't error — it just creates a coroutine object and throws it away. Nothing persists. Your endpoint returns 201, the data is gone after the request, and the only clue is a RuntimeWarning: coroutine 'commit' was never awaited buried in the logs. If async data "mysteriously disappears," grep your code for un-awaited session calls first.

05  The async lazy-loading trap

Here's the one place async is genuinely harder, not just differently spelled. In sync code, hero.team on a relationship quietly fires a second query the moment you touch the attribute — "lazy loading." In async code, an attribute access can't await anything (Python has no await hero.team for plain attributes), so when lazy loading would need the database, SQLAlchemy raises instead:

the_trap.py
@app.get("/heroes/{hero_id}/team-name")
async def team_name(hero_id: int, session: SessionDep):
    hero = await session.get(Hero, hero_id)
    return {"team": hero.team.name}     # 💥 sqlalchemy.exc.MissingGreenlet:
                                        # greenlet_spawn has not been called;
                                        # can't call await_only() here

Two clean fixes. Either tell the query up front to fetch the relationship too (eager loading), or run an explicit second query yourself:

the_fixes.py
from sqlalchemy.orm import selectinload

# Fix 1 — eager load: relationship arrives with the hero
result = await session.exec(
    select(Hero).where(Hero.id == hero_id)
                .options(selectinload(Hero.team))
)
hero = result.one()
hero.team          # ✅ already loaded, no hidden query

# Fix 2 — just ask explicitly
hero = await session.get(Hero, hero_id)
team = await session.get(Team, hero.team_id)   # ✅ a visible, awaited query
Honestly? This trap is a feature

Lazy loading in sync code is how you accidentally ship the N+1 query problem — one query per hero in a list of 500. Async forces every database round-trip to be a visible await, so the cost is on the page where you can see it. selectinload fetches a whole list's relationships in one extra query, not 500.

Your async endpoint returns a hero fine, but accessing hero.team raises MissingGreenlet. What's going on?

Right. In async SQLAlchemy, implicit I/O is forbidden — an attribute access has no way to await. Load the relationship in the original query with .options(selectinload(Hero.team)), or fetch it yourself with a second awaited query.

06  Migrations with Alembic

The SQLModel lesson ended with a warning: SQLModel.metadata.create_all() only creates tables that don't exist. It will never add a column, rename one, or change a type on a table that's already there. The day you add power: int to Hero with real users in the database, you need a tool that says "here's how to get from schema version 3 to version 4 without losing a row." That tool is Alembic — think of each migration as a numbered git commit for your database schema.

terminal
pip install alembic
alembic init -t async migrations    # -t async: scaffolding that works
                                    # with create_async_engine

That creates alembic.ini and a migrations/ folder. Two edits wire it to your app — tell it where the database is, and which metadata describes "the schema my code wants":

migrations/env.py
from sqlmodel import SQLModel
import app.models                     # noqa — import so every table registers

config.set_main_option("sqlalchemy.url", "sqlite+aiosqlite:///app.db")
target_metadata = SQLModel.metadata   # replace the default `None`

Now the loop you'll repeat for the rest of the project's life. Change a model — say, add power: int = 0 to Hero — then:

terminal
# 1. compare models vs live DB, draft a migration script
alembic revision --autogenerate -m "add hero.power"

# 2. READ the generated file in migrations/versions/ (see below)

# 3. apply every migration the DB hasn't seen yet
alembic upgrade head

Step 2 is not optional ceremony. Open the generated script and check it says what you meant:

migrations/versions/a1b2c3_add_hero_power.py
def upgrade() -> None:
    op.add_column("hero",
        sa.Column("power", sa.Integer(), nullable=False,
                  server_default="0"))

def downgrade() -> None:
    op.drop_column("hero", "power")
Autogenerate is a draft, not a verdict

Alembic diffs structures, not intent. It sees a rename as "drop column, add column" — which deletes the data — and it can't detect some changes (server defaults, some type tweaks) at all. Always read the script before upgrade head, the way you'd read a diff before committing.

Where migrations run in real life

In CI/deploy, run alembic upgrade head as a release step before the new app version starts — the code should never boot against a schema older than it expects. Once Alembic owns the schema, drop the create_all() call from your lifespan; one tool should be in charge.

07  Sync or async? Choosing honestly

Async is not a tier you graduate to — it's a trade. You gain concurrency on I/O waits; you pay with the lazy-loading rules, the silent un-awaited-coroutine failure mode, and a slightly smaller library ecosystem. Pick by situation:

Your situationPickWhy
Small app, modest traffic, fast queriesSync defThe threadpool absorbs the blocking calls; you keep the simpler programming model. The bottleneck is nowhere near the thread count.
High concurrency, I/O-bound (slow queries, slow upstreams, long-polling, thousands of simultaneous clients)AsyncThis is exactly what the event loop is for — waiting on thousands of things at once costs almost nothing.
CPU-bound work (image processing, ML inference, heavy number-crunching)Neither helpsThe loop can't await arithmetic and threads fight over the interpreter. Scale with more worker processes, or push the job to a task queue.
Mixed-experience team, straightforward CRUD productSyncCorrect sync code beats subtly-wrong async code every time. You can migrate later — section 03 showed how mechanical the change is.

And whichever you choose: don't mix the failure modes. A sync DB call inside async def is the one combination that's always wrong.

Your endpoint resizes uploaded images and is too slow under load. Will switching the database layer to async fix it?

Exactly. Async shines when requests spend their time waiting on I/O. CPU work occupies the core no matter how you spell the function — the loop just sits hostage behind it. Scale CPU-bound work with worker processes (e.g. multiple uvicorn workers) or offload it to a background task queue.
