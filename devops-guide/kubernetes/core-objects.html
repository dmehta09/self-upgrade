Kubernetes · objects

Core Kubernetes objects.

A handful of objects compose into every app on Kubernetes: Pods run containers, Deployments keep them alive and roll them out, and Services give them a stable address. Learn how they nest and how traffic reaches a pod.

01 The cast of objects

You mostly write a Deployment (it owns ReplicaSets → Pods) and a Service (a stable address in front of those pods). The rest — config, secrets, routing, namespaces — wrap around that core.

In plain English analogy

A Deployment is a shift manager who keeps N identical workers staffed — someone calls in sick, they pull in a replacement. A Service is the front-desk phone number: callers always reach whoever is on shift right now, never a specific person who might have gone home.

Pod
The smallest unit. One (or a few) containers that share a network + storage — same IP, same localhost, same volumes. Mortal: it gets a new IP when replaced.
ReplicaSet
Keeps N identical pods running. You rarely touch it directly.
Deployment
Manages ReplicaSets to do rollouts + rollbacks. This is what you actually write.
Service
A stable virtual IP + DNS name that load-balances across the current matching pods.
Ingress / Gateway API
L7 HTTP routing into the cluster (host/path rules, TLS).
ConfigMap / Secret
Inject non-secret config / sensitive config into pods.
Namespace
Logical isolation — a folder to group and scope objects (teams, environments).

02 Deployment → ReplicaSet → Pod

The nesting is the mental model: a Deployment creates a ReplicaSet, which creates Pods. The selector labels glue an object to the pods it owns or targets.

deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: web }
spec:
  replicas: 3              # desired pod count
  selector:
    matchLabels: { app: web }   # owns pods with this label
  template:               # the pod blueprint
    metadata:
      labels: { app: web }
    spec:
      containers:
        - name: web
          image: ghcr.io/acme/web:1.4.2   # pin by tag/SHA

You declare a Deployment; it owns a ReplicaSet; the ReplicaSet keeps the desired number of Pods running.

03 How traffic reaches a pod

Pods are mortal and get fresh IPs, so clients never target them directly. A Service gives a stable address; an Ingress/Gateway handles HTTP routing from outside. Follow one request in.

Service types: ClusterIP (internal-only, the default) → NodePort (opens a port on every node) → LoadBalancer (provisions a cloud LB, e.g. an AWS NLB/ALB). Ingress/Gateway usually sits in front for HTTP.

Common trap gotcha

Two traps. (1) Pods are mortal — they get new IPs on every restart, so never hard-code a pod IP; always go through a Service's stable name. (2) Secrets are only base64-encoded, not encrypted by default — anyone with read access decodes them in a second. Enable encryption-at-rest (KMS on EKS) or use an external store like AWS Secrets Manager.

Your app talks to a database by its pod's IP. After a node reboot, connections fail. Why?

Right. Pod IPs are ephemeral by design. A Service gives a fixed virtual IP + DNS name (db.ns.svc.cluster.local) that always routes to the current pods — that's exactly the problem Services solve.

04 Config vs secrets

Keep configuration out of the image so the same artifact runs everywhere. ConfigMap holds plain config; Secret holds sensitive values. Both inject into pods as env vars or mounted files.

ConfigMap
  • Non-secret: log level, feature flags, URLs.
  • Stored as plain text in etcd.
  • Safe to commit (the values, not the rendered manifest of secrets).
Secret
  • Sensitive: DB passwords, API keys, TLS certs.
  • Only base64-encoded — encrypt at rest with KMS.
  • Better: source from AWS Secrets Manager / External Secrets.
Pro tip tip

Mount secrets as files, not env vars, where you can — env vars leak into crash dumps, child processes, and kubectl describe. And never commit a raw Secret manifest to Git; use sealed-secrets or an external store so Git holds only an encrypted reference.

05 Interview rapid-fire

Pod vs Deployment vs Service — what does each do?warm-up
Model answer

A Pod is the smallest unit — one or more containers sharing a network and storage. A Deployment manages ReplicaSets to keep N pods running and to do rolling updates and rollbacks. A Service is a stable virtual IP and DNS name that load-balances across whichever pods currently match its selector. You write Deployments and Services; pods are created for you.

Say it out loud say it

"Pod runs the containers, Deployment keeps the right number of pods and rolls them out safely, and a Service is the stable address in front of them — pods come and go behind it."

Follow-ups to expect
  • Where does the ReplicaSet fit? (Deployment owns it; it's the thing that actually keeps N pods alive.)
  • What ties a Service to its pods? (Label selectors — the Service targets pods whose labels match.)
How does an external request reach a pod? And what are the Service types?core
Model answer

External traffic hits an Ingress or Gateway (L7 — TLS + host/path routing), which forwards to a Service, which load-balances to one of the healthy pods behind it. Service types are ClusterIP (internal-only, default), NodePort (a port on every node), and LoadBalancer (provisions a cloud LB — an AWS NLB/ALB on EKS). The client never sees a pod IP.

Say it out loud say it

"Ingress or Gateway does HTTP routing and TLS, hands off to a Service, and the Service balances across pods. ClusterIP is internal, NodePort opens a node port, LoadBalancer spins up a cloud LB."

ConfigMap vs Secret — and are Secrets actually secure?stretch
Model answer

Both inject config into pods as env vars or mounted files; ConfigMap is for non-sensitive data, Secret for sensitive. The catch: a Secret is only base64-encoded, not encrypted — anyone with read access decodes it instantly, and by default it sits as good-as-plaintext in etcd. You harden it by enabling encryption-at-rest (KMS-backed on EKS) and/or sourcing from AWS Secrets Manager via External Secrets, keeping raw secrets out of Git.

Say it out loud say it

"ConfigMap for plain config, Secret for sensitive — but base64 is encoding, not encryption. I turn on encryption-at-rest with KMS and pull real secrets from Secrets Manager instead of committing them."
