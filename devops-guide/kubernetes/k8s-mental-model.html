Kubernetes · the model

The Kubernetes mental model.

Kubernetes is one big control loop: you declare the state you want, and the cluster works nonstop to make reality match. You never run the steps yourself — you describe the destination.

01 Desired state, not steps

Kubernetes is declarative: you POST the desired state (YAML), and controllers run a reconcile loop that continuously drives the actual state toward it.

You don't say "start container, then on crash restart it, then on node death reschedule it." You say "I want 3 healthy replicas." Something dies? The loop notices the gap and acts — forever, without you.

In plain English analogy

Kubernetes is a thermostat. You set "I want it 21°C" (desired state) and walk away. The thermostat keeps measuring the room and nudging the heater until reality matches — and re-acts whenever someone opens a window. You never toggle the heater by hand; you just declare the temperature.

Desired state
What you declared — the YAML you applied (e.g. replicas: 3).
Actual state
What's really running right now in the cluster.
Reconcile loop
A controller compares the two, sees the drift, and acts to close the gap — on repeat, forever.

02 The control plane

The control plane is the brain. You talk to exactly one part of it — the API server — and four components cooperate to turn your YAML into running containers.

API server
The front door — the only thing you (and every component) talk to. Validates requests, then reads/writes state.
etcd
The cluster's state store: a consistent key-value database that is the single source of truth for what should exist.
Scheduler
Decides which node a new pod runs on, based on resources, taints, and affinity.
Controller-manager
Runs the reconcile loops (Deployment, ReplicaSet, node, …) that make reality match etcd.

Worker nodes run the kubelet (the node's agent — it makes the assigned pods real) and a container runtime (containerd) that actually pulls images and starts containers.

Heads up aws

On EKS, AWS runs and patches the control plane (API server + etcd) for you. You manage worker nodes — via managed node groups, self-managed EC2, or Fargate (no nodes at all).

03 What happens on kubectl apply

Walk one request end to end. The pattern — declare to the API server, persist in etcd, let controllers and the kubelet make it real — is the whole system in miniature.

Common trap gotcha

It's declarative — you declare what you want, never the steps. Hand-editing prod with kubectl edit or kubectl scale creates drift: the live state no longer matches Git, and your next apply silently reverts it (or worse, surprises you). Change the manifest in Git and apply from there.

You run a Deployment with replicas: 3. Someone kills a pod by hand. What does Kubernetes do?

Right. That's the reconcile loop. Desired state lives in etcd (3 replicas); the controller continuously closes any gap. Self-healing is the whole point of declarative orchestration.

04 Interview rapid-fire

Imperative vs declarative — what's the difference, and which is Kubernetes?warm-up
Model answer

Imperative = you issue the steps ("create this, then scale to 3"). Declarative = you describe the end state ("I want 3 replicas") and the system figures out how to get and stay there. Kubernetes is declarative: you apply a manifest and controllers reconcile toward it continuously, so it self-heals.

Say it out loud say it

"Imperative is a recipe of steps; declarative is a destination. Kubernetes is declarative — I declare desired state, and it reconciles reality to match, over and over."

What is the reconcile (control) loop?core
Model answer

A controller continuously: observes actual state, compares it to the desired state in etcd, and acts to close any gap — then repeats. Kill a pod and the ReplicaSet controller makes a new one; cordon a node and pods get rescheduled. It's a never-ending feedback loop, which is exactly why Kubernetes is self-healing.

Say it out loud say it

"It's observe, diff against desired, act, repeat — forever. That loop is why a killed pod just comes back without anyone touching it."

Follow-ups to expect
  • What causes "drift"? (Hand-editing live state so it no longer matches Git — fixed by GitOps + reconcile.)
  • Are controllers level- or edge-triggered? (Level — they act on the current state gap, not on one-off events, so they're robust to missed events.)
What lives in the control plane, and what is etcd?core
Model answer

The control plane has four parts: the API server (the only front door — everything talks to it), etcd (a consistent key-value store that is the cluster's source of truth for desired state), the scheduler (assigns pods to nodes), and the controller-manager (runs the reconcile loops). Worker nodes run the kubelet + containerd. etcd is the database — lose it without a backup and you lose the cluster's state.

Say it out loud say it

"API server is the front door, etcd is the source-of-truth database, the scheduler places pods, and the controller-manager reconciles. On EKS, AWS runs all of that for me — I just manage the worker nodes."
