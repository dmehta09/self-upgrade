IAM, storage & data.

Who can do what (IAM), where bytes live (S3, EBS, EFS), where your data sits (RDS/Aurora), and how secrets and encryption are handled (Secrets Manager, SSM, KMS). This is the security-and-state backbone interviewers probe hardest.

Exam depth lives next door sibling

This page is interview-depth AWS for DevOps. For SAA-C03 exam design decisions, scenarios, and timed mocks, open the sibling AWS SAA Field Guide.

01 IAM: users, roles & least privilege

An IAM user is a permanent identity with long-lived credentials. A role is assumed temporarily and yields short-lived credentials. Strongly prefer roles. Permissions come from policies — JSON allow/deny statements — and you grant the least privilege needed.

In plain English analogy

An IAM role is a temporary visitor badge that opens exactly the rooms you need for the next hour, then expires. A long-lived access key is a permanent master key — if someone copies it (or you paste it in a log), it's a disaster, and it keeps working until you notice. Hand out expiring badges, not master keys.

Workloads get credentials without any long-lived keys by assuming roles automatically:

EC2 instance role
Attach an instance profile; the SDK auto-fetches rotating temporary creds from the instance metadata service. No keys on disk.
EKS pods
IRSA (IAM Roles for Service Accounts) or EKS Pod Identity — a pod's service account maps to an IAM role; the pod gets scoped, short-lived creds.
CI pipelines
OIDC federation: the CI provider issues a token, the pipeline assumes a role — no AWS_SECRET_ACCESS_KEY stored anywhere.
least-privilege-policy.json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:GetObject", "s3:PutObject"],
    "Resource": "arn:aws:s3:::acme-uploads/*"
  }]
}

This grants read/write to objects in one bucket — not s3:* on *. Scope the action and the resource; that's least privilege.

Common trap gotcha

Never embed access keys in code, env files, or AMIs — use roles. Hard-coded keys leak into Git history, logs, and images, and they don't expire. This is the single most common finding in a cloud security review.

02 Storage: S3 vs EBS vs EFS

Three storage shapes for three different jobs. The interview question is almost always "which one, and why?"

ServiceTypeAttaches toUse it for
S3Object store (buckets/keys)Anything, over HTTPSFiles, backups, static assets, data lakes, artifacts.
EBSBlock volume (a virtual disk)One EC2 instance at a timeA boot disk or database volume on a single instance.
EFSShared network filesystem (NFS)Many instances at onceShared files multiple machines mount together.
S3 essentials
Versioning (keep old object versions), lifecycle rules (auto-tier to cheaper storage or expire), and Block Public Access (on by default — keep it on).
One-liner
S3 = buckets of objects; EBS = a disk for one VM; EFS = a shared drive for many VMs.
Common trap gotcha

An accidentally public S3 bucket is a classic breach — countless leaks trace back to one. Keep Block Public Access enabled at the account and bucket level; serve public content through CloudFront, not by opening the bucket.

03 Data, secrets & encryption

RDS / Aurora are managed relational databases — AWS runs the engine, patching, and backups. Turn on Multi-AZ for high availability: a standby in another Availability Zone takes over on failure.

Secrets Manager
Stores secrets (DB passwords, API keys) with automatic rotation and fine-grained IAM access. The default for credentials.
SSM Parameter Store
Config + secrets store; SecureString params are KMS-encrypted. Cheaper, no built-in rotation — good for plain config and simple secrets.
KMS
Key Management Service — manages the encryption keys behind encryption at rest. S3, EBS, RDS, and Secrets Manager all encrypt using KMS keys.

So: your app's DB password lives in Secrets Manager (rotated), the app reads it at runtime via its IAM role (no key in code), and KMS encrypts both the secret and the database's storage.

Heads up note

Secrets Manager vs SSM Parameter Store in one line: reach for Secrets Manager when you need rotation and richer secret features; reach for SSM Parameter Store for cheap config and simple secrets. Both integrate with KMS for encryption.

An EKS pod needs to read an object from S3. What's the right way to give it access?

Right. Use roles, not keys. IRSA / EKS Pod Identity hands the pod temporary, scoped credentials with nothing to leak or rotate. Baking keys into images and making buckets public are both classic security failures.

04 Interview rapid-fire

IAM user vs role — and how does a workload get credentials without keys?core
Model answer

A user is a permanent identity with long-lived keys; a role is assumed temporarily and gives short-lived credentials — prefer roles. Workloads get creds with no keys by assuming a role automatically: EC2 instance roles for instances, IRSA / EKS Pod Identity for pods, and OIDC + assume-role for CI. All grant least-privilege, auto-rotating credentials.

Say it out loud say it

"Roles over users — a role is a temporary badge with short-lived creds. EC2 uses instance roles, pods use IRSA or Pod Identity, CI uses OIDC to assume a role. No long-lived keys anywhere."

Follow-ups to expect
  • What does least privilege mean? (Grant only the specific actions on the specific resources needed.)
  • Where do EC2 temp creds come from? (The instance metadata service, rotated automatically.)
S3 vs EBS vs EFS — when do you use each?warm-up
Model answer

S3 is object storage over HTTPS — files, backups, static assets, artifacts. EBS is a block volume (a virtual disk) attached to one EC2 instance — a boot or database disk. EFS is a shared NFS filesystem many instances mount at once. Object vs single-instance disk vs shared drive.

Say it out loud say it

"S3 is buckets of objects, EBS is a disk for one VM, EFS is a shared drive many VMs mount. Pick by access pattern: HTTP objects, single-instance block, or shared file."

Where do you store DB credentials, and what is KMS?core
Model answer

Store DB credentials in Secrets Manager (with automatic rotation) or SSM Parameter Store as a SecureString — never in code. The app reads them at runtime via its IAM role. KMS is the Key Management Service that holds the encryption keys behind encryption at rest; S3, EBS, RDS, and Secrets Manager all encrypt their data using KMS keys.

Say it out loud say it

"DB creds go in Secrets Manager with rotation, read at runtime through the app's IAM role — never hard-coded. KMS manages the keys that encrypt everything at rest."
