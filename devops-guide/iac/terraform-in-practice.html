IaC · Terraform in practice

Terraform in practice.

Knowing plan and apply isn't enough — interviewers want the team workflow: reusable modules, remote locked state, multiple environments, drift, importing existing infra, and running it all in CI as GitOps for infrastructure.

01 Modules: functions for infrastructure

A module is reusable, parameterized infrastructure — write the pattern once (a VPC, an ECS service) and call it with different inputs. Variables are its parameters; outputs are its return values.

Modules kill copy-paste. One audited "service" module, called per team, beats fifty hand-tweaked copies that drift apart and each hide their own bug.

In plain English analogy

A module is a function you wrote once and now call with arguments. module "api" { source = "./service" name = "api" cpu = 512 } is just service(name="api", cpu=512). Variables are the parameters, outputs are the return value, and you reuse it everywhere instead of pasting the body again.

prod/main.tf
module "api" {
  source       = "../modules/service"
  name         = "api"
  cpu          = 512
  desired_count = 3
}

output "api_url" {
  value = module.api.url
}

02 Remote state & locking

Store state remotely (S3 with native lockfile, or Terraform Cloud) so the whole team shares one source of truth. State locking stops two concurrent applys from corrupting it — and the modern default is S3's own lock, not a separate DynamoDB table.

Local state on one laptop is a disaster waiting to happen: nobody else can apply, the file gets lost, and two people running apply at once race each other into a corrupt state. The S3 backend holds the encrypted state and the lockfile beside it.

In plain English analogy

Remote state with locking is a shared document with edit-locking — like a Google Doc that grabs a lock while one person types. Everyone reads the same latest version, and two people can't overwrite each other mid-save. Local state is emailing a Word doc around and praying nobody edits the stale copy. The modern twist: the lock lives in the same filing cabinet (S3) as the doc — you no longer need a separate lock binder (DynamoDB) on another shelf.

backend.tf
terraform {
  backend "s3" {
    bucket       = "acme-tfstate"
    key          = "prod/terraform.tfstate"
    region       = "us-east-1"
    encrypt      = true
    use_lockfile = true   # S3 native locking (modern default)
  }
}
Local state on a laptop
  • Only one engineer can run Terraform.
  • Disk dies → state (and secrets) lost.
  • Two applies = corrupted state, no lock.
  • Often accidentally committed to Git.
Remote, locked, encrypted
  • S3 holds one shared, versioned state file.
  • S3 native lockfile serializes every apply.
  • Encrypted at rest; never in the repo.
  • CI and humans use the same backend.
Legacy note history

Older tutorials pair S3 with a DynamoDB lock table (dynamodb_table = "tf-locks"). That still works, but it's the legacy pattern — an extra service, extra IAM, and another thing to operate. Prefer use_lockfile = true (S3 conditional writes) for new backends; migrate when you touch existing ones.

Common trap gotcha

Local state on one laptop leads to lost or conflicting state, and two applies without a lock corrupt the state file — which can orphan or double-create real resources. Always use a remote backend with locking, even for a solo project that might grow a second contributor.

03 Multiple environments & drift

Each environment (dev/staging/prod) needs its own state so a bad prod apply can't touch dev. Two common patterns:

Per-env directories
Separate folders (envs/prod, envs/staging), each with its own backend state, all calling the same modules. Explicit, recommended for clear blast-radius separation.
Workspaces
One config, multiple named states (terraform workspace). Lighter, but easy to apply to the wrong workspace — risky for prod.
Drift detection
Run terraform plan on a schedule; a non-empty plan means reality has drifted from code (someone clicked in the console). Re-apply to converge, or import the change.
Pro tip tip

To bring an existing (ClickOps'd) resource under Terraform, write the matching resource block, then terraform import aws_instance.web i-0abc123 — it records the resource in state without recreating it. Modern Terraform also supports declarative import blocks. After import, a plan should show no changes.

04 Terraform in CI: GitOps for infra

Run Terraform in a pipeline, not from laptops: plan on the pull request so reviewers see the exact diff, and apply on merge to main. Git becomes the source of truth for infrastructure.

1

Write

Open a PR changing the HCL. The change is now reviewable code, not a console click.

2

Plan in the PR

CI runs terraform plan and posts the diff as a comment. Reviewers see exactly what will be created, changed, or destroyed.

3

Review & approve

A human reads the plan and approves. A surprise destroy in the diff gets caught here — before it touches prod.

4

Apply on merge

Merge to main triggers terraform apply. CI authenticates to AWS via OIDC (assume a role, no long-lived keys) and uses the remote locked backend.

Heads up link

This is the same review-then-merge discipline as application CI/CD — the diff just happens to be infrastructure. Identity and OIDC-to-assume-role details live on the AWS IAM, storage & data page.

A teammate ran terraform apply from their laptop using local state. Why is this a problem on a team?

Right. State is the shared source of truth. Local state means a private, unlocked, possibly-secret-leaking copy that diverges from everyone else's and can be clobbered by a concurrent run. Use a remote backend with locking, driven from CI.

05 Interview rapid-fire

How do you manage Terraform state for a team, and what is state locking?core
Model answer

Use a remote backend — typically S3 with encryption and native state locking via use_lockfile = true (or Terraform Cloud). Everyone reads and writes the same shared, versioned state. State locking takes an exclusive lock during apply so two people can't run concurrently and corrupt it; the second apply waits for the lock. DynamoDB lock tables are the older pattern — still valid, but not what I'd set up new.

Say it out loud say it

"Encrypted S3 for shared state, with S3 native lockfile locking — no DynamoDB table needed anymore. Locking serializes applies so two people can't corrupt state at once. Never local state on a laptop."

Follow-ups to expect
  • Why encrypt the state? (It can hold secrets like DB passwords in plaintext.)
  • What about DynamoDB locks? (Legacy — still works; new backends use use_lockfile.)
  • What if a lock gets stuck? (terraform force-unlock with the lock ID — carefully.)
How do you structure multiple environments, and run Terraform in CI?core
Model answer

Give each environment its own state — usually per-env directories (clear blast-radius separation) calling shared modules, sometimes workspaces. In CI, run terraform plan on the PR so reviewers see the exact diff, and apply on merge to main — GitOps for infrastructure, with the pipeline assuming an AWS role via OIDC.

Say it out loud say it

"Per-env directories with separate state, shared modules for reuse. Plan on the PR for review, apply on merge — infra goes through the same code-review gate as app code."

How do you bring existing infrastructure under Terraform?stretch
Model answer

Write a resource block matching the existing resource, then terraform import it (or use a declarative import block) so it's recorded in state without recreating it. Then run plan and iterate on the config until the plan shows no changes — meaning code now matches reality. After that it's fully managed.

Say it out loud say it

"Write the matching resource, then terraform import the real ID into state — no recreate. Tweak the config until plan is clean, then it's managed like anything else."
