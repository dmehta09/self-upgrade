Deploy strategies · releasing safely

Release strategies.

Once CI hands you a tested image, how you swap it into production decides whether a bad version takes everyone down or a handful of requests. Each strategy is a different bet on blast radius, cost, and rollback speed.

01 Five ways to ship v2

The whole game is blast radius vs cost vs rollback speed. Recreate is cheapest and worst; canary is safest; blue-green is instant but doubles capacity; feature flags split deploy from release entirely.

The artifact is identical across all of them — what changes is how traffic moves from old to new, and how fast you can move it back.

In plain English analogy

A canary is the canary in the coal mine — send a few in first, watch them, and only follow if they're fine. Blue-green is two identical stages side by side: the show is fully rehearsed on the dark stage, and you "release" by just flipping the spotlight from one to the other.

Recreate stops all pods then starts v2 (downtime). Rolling swaps pods one at a time (no downtime, slow rollback). Blue-green stands up a full second environment then flips traffic instantly (needs ~2× capacity). Canary sends a small percentage to v2 first and widens only if it stays healthy.

Recreate
Stop all old, start all new. Accepts downtime for simplicity — fine for batch jobs or single-instance internal tools.
Rolling
Replace instances gradually. Kubernetes' default; no extra capacity, but both versions run at once mid-rollout.
Blue-green
Two identical environments; flip traffic in one switch. Instant cutover and rollback, but ~2× capacity while both live.
Canary
Route a small % to the new version, watch health, widen only if good. Smallest blast radius.
Feature flag
Decouple deploy from release: ship code dark, turn it on later, kill-switch instantly. Not a traffic strategy — a visibility one.

02 The rollback story per strategy

Interviewers care less about how you ship than how you un-ship. Each strategy has a very different "undo" — and that, not deploy speed, is usually the deciding factor.

StrategyRollback moveSpeedCost / caveat
RecreateRedeploy v1 (stop all, start old)Slow + another outageCheap; downtime both ways
RollingRoll the Deployment back the other waySlow-ish (pod by pod)No spare capacity needed
Blue-greenFlip the router back to blueInstant~2× capacity; blue kept warm
CanaryCut canary traffic to 0%Instant, tiny blast radiusNeeds a trustworthy health signal
Feature flagToggle the flag offInstant, no redeployFlag debt; code still deployed

Notice the pattern: traffic-level rollbacks (blue-green flip, canary cut, flag toggle) are near-instant because the old code is still running. Pod-level rollbacks (recreate, rolling) are slow because you must rebuild the old fleet.

Pro tip tip

"How do we undo this in 60 seconds?" should have an answer before you deploy. Keep the last known-good image one promotion away, and prefer strategies whose rollback is a traffic switch rather than a fresh rollout.

03 Deploy ≠ release: where flags fit

Deploy = new code is running on prod servers. Release = users can see it. Blue-green and canary move traffic; a feature flag moves visibility — and they compose.

You can deploy a new version via rolling update with every new feature behind an off flag, then "release" later by flipping flags — no redeploy, no traffic shuffle. The kill-switch is the fastest rollback you have.

Traffic strategies (canary / blue-green)
  • Decide which version of the code runs for a request.
  • Rollback = shift traffic back.
  • All-or-some users get the whole new build.
Feature flags
  • Decide which features are visible, independent of deploy.
  • Rollback = toggle off, no redeploy.
  • Target per-user / per-cohort, many flags per build.

They pair: a common pattern is canary the version, then dark-launch risky features behind flags on top of it — two independent safety nets. The continuous-delivery page covers the deploy-vs-release split in more depth.

Common trap gotcha

Three classic traps: (1) rolling makes rollback slow — you re-roll pod by pod. (2) blue-green needs ~2× capacity and a backward-compatible database — the green app and blue app hit the same DB during the flip. (3) canary is only as good as the health signal you watch — a canary nobody monitors is just a slow rolling deploy.

04 The database makes "zero-downtime" hard

Code rolls back in seconds; a schema change usually can't. During any gradual rollout, old and new code hit the same database at once — so the schema must satisfy both. The fix is expand → migrate → contract.

1

Expand

Add the new column/table additively — nullable, no drops, no renames. Old code ignores it; new code can use it. Both versions still work.

2

Migrate

Deploy code that writes both old and new shapes, then backfill data. The canary/rolling deploy happens entirely in this both-compatible window.

3

Contract

Once all instances are on v2 and stable, a later deploy drops the old column. Never in the same release as the rollout.

The rule of thumb: a destructive migration (drop/rename a column) and the code that stops using it must ship in separate, sequential deploys — otherwise a rollback lands on a schema the old code can't read.

Heads up scope

Canary and auto-rollback decisions hinge on health signals — error rate, latency, saturation. The metrics, dashboards, and SLO burn-rate alerts behind those signals live in the companion Observability guide. Here we cover the deploy-side decision: which strategy, and when to roll back.

You're doing a blue-green deploy of v2, which renames a DB column. You flip 100% to green, then need to roll back to blue. What breaks?

Right. The traffic flip is instant, but both environments share one database. A rename is destructive, so the moment green migrates, blue can no longer read the schema — your rollback target is broken. Use expand/contract: add the new column, migrate, and only drop the old one a release later.

05 Interview rapid-fire

Blue-green vs canary — when do you pick which?core
Model answer

Blue-green runs two full environments and flips all traffic at once — instant cutover and instant rollback, at the cost of ~2× capacity. Canary shifts a small percentage first and widens gradually while you watch health — smallest blast radius, but slower and only as safe as your monitoring. Pick blue-green when you need an atomic switch and can afford double capacity; pick canary when you want to limit exposure and have good signals.

Say it out loud say it

"Blue-green flips everyone at once — instant rollback, double the cost. Canary exposes a few percent first and widens on good signals — smallest blast radius, but it lives or dies by your health metrics."

Follow-ups to expect
  • Capacity cost of each? (Blue-green ~2× during the flip; canary roughly 1× plus a sliver.)
  • Which handles a bad DB migration better? (Neither — both share the DB; you need expand/contract regardless.)
How do you roll back each strategy — and which is fastest?core
Model answer

Recreate: redeploy v1, which means another outage. Rolling: roll the Deployment the other way, pod by pod — slow. Blue-green: flip the router back to blue — instant. Canary: drop canary traffic to 0% — instant, and only a few percent were ever affected. Feature flag: toggle it off — instant, no redeploy at all. The fast ones win because the old code is still running, so rollback is a traffic change, not a fresh rollout.

Say it out loud say it

"If the old version is still running, rollback is just shifting traffic — that's blue-green, canary, and flags, all near-instant. Recreate and rolling have to rebuild the old fleet, so they're slow."

How do database migrations complicate zero-downtime deploys?stretch
Model answer

During any gradual rollout, old and new code run against the same database simultaneously, so the schema has to satisfy both — and unlike code, a destructive schema change can't be rolled back instantly. The pattern is expand/contract: first ship an additive change (new nullable column, no drops/renames), deploy the code that writes both shapes and backfill, and only in a later release drop the old column once everything's on v2. Coupling a drop with the rollout means a rollback lands on a schema the old code can't read.

Say it out loud say it

"Old and new code share one DB mid-deploy, so I make every migration backward-compatible — expand first, drop later in a separate release. That way any rollback still finds a schema it understands."

Follow-ups to expect
  • How do you rename a column with zero downtime? (Add new, dual-write, backfill, switch reads, drop old — five steps across releases.)
  • What about long-running backfills? (Run them as separate batch jobs, not in the deploy's migration step.)
