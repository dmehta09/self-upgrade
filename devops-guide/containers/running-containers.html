Containers · runtime

Running containers.

Building an image is half the job; running it well is the other half. Where state lives, how config is injected, and what's allowed to disappear on restart decide whether your service survives a node dying at 3 a.m.

01 Registries: push & pull

A registry stores and serves images. CI pushes a built image; every host that runs it pulls it. The registry is the handoff point between build and run.

On AWS the default is ECR (Elastic Container Registry) — private, IAM-controlled, in your account. Public options are GHCR (GitHub) and Docker Hub.

In plain English analogy

A registry is an app store for images: developers publish versions, machines install them by name. And docker compose is a recipe that starts the whole meal at once — app, database, and cache come up together with one command.

Reference images by tag (movable label, e.g. :1.4) or digest (immutable hash, @sha256:…). In production, pin the digest so every node runs the exact same bytes.

02 The knobs of docker run

Running a container means wiring it into the host: ports, storage, network, config, and a policy for when it dies.

Ports
-p 8080:80 maps a host port to the container port so traffic can reach it.
Volumes
-v data:/var/lib/app mounts persistent storage outside the container's lifecycle.
Networks
Containers on a user-defined network reach each other by name (service discovery).
Env / secrets
-e LOG_LEVEL=info or an injected secret — config comes from the environment, not the image.
Healthcheck
A periodic probe (e.g. GET /healthz) the orchestrator uses to restart or route around a sick container.
Restart policy
--restart on-failure / unless-stopped — what happens when the process exits.
GET/healthzliveness — is the process up?
GET/readyzreadiness — should it receive traffic yet?

Containers should log to stdout/stderr — the runtime collects the stream; the app shouldn't manage log files itself.

03 Cattle, not pets: the ephemeral principle

Treat containers as disposable. Anything written to the container's own filesystem is lost on restart — design so losing a container is a non-event.

"Pets" are hand-fed, named, nursed back to health. "Cattle" are interchangeable and replaced without ceremony. Containers are cattle: kill one, the orchestrator starts an identical replacement.

Pet (stateful container)
  • Writes uploads to /app/data on the local FS.
  • Keeps session state in memory only.
  • SSH in to "fix" a single instance.
  • Restart = data gone, users logged out.
Cattle (stateless container)
  • Uploads go to S3; data to RDS.
  • Sessions in Redis/ElastiCache or a token.
  • Never patch a live container — ship a new image.
  • Restart anywhere = zero data loss.
Common trap gotcha

Containers are ephemeral: the writable top layer vanishes when the container is replaced, rescheduled, or scaled in. Anything you wrote there — uploads, a SQLite file, "temporary" cache — is gone, silently. Persist state in a volume or an external store (S3, RDS, ElastiCache). The container's own disk is scratch space only.

04 Compose for local multi-service

docker compose declares a multi-container app in one YAML file and brings it all up with docker compose up — great for local dev, not your production scheduler.

compose.yaml
services:
  app:
    image: myapp@sha256:9f2...   # pin by digest
    ports: ["8080:8080"]
    environment:
      DB_URL: postgres://db:5432/app
    depends_on: [db]
  db:
    image: postgres:16
    volumes: ["pgdata:/var/lib/postgresql/data"]
volumes:
  pgdata: {}

Config (the DB_URL) lives in env vars, the database's state lives in a named volume — the same two principles you carry to production, just expressed locally.

Heads up note

Compose is for one host (local dev / small jobs). In production an orchestrator — ECS, EKS, or another Kubernetes — handles scheduling, scaling, health, and rollout across many nodes.

05 VM vs container vs serverless

The container isn't always the answer. Pick the compute model by how much control you need versus how much ops you want to own — and what idle costs you.

EC2 gives the most control but the most ops and poor idle economics; containers (ECS/EKS) balance portability and effort and are the default; Lambda removes ops and is cheapest at idle but adds cold starts and runtime limits.

Idle cost
An EC2 box or always-on container costs money doing nothing; Lambda scales to zero — you pay per invocation.
Cold start
Lambda may spin a new environment on a cold request (added latency). Long-running containers are always warm.
Lock-in / portability
A container image runs anywhere; a Lambda is shaped around the provider's runtime + event model.

A nightly job processes an upload, then nothing runs for 23 hours. Which compute model fits best?

Right. Spiky, event-driven, short work is the serverless sweet spot — no idle bill, no servers to patch. A reserved instance or cluster would sit 95% idle paying full price.

06 Interview rapid-fire

Where does container state go?warm-up
Model answer

Not in the container. The writable layer is ephemeral — it disappears when the container is replaced, rescheduled, or scaled in. State goes to a volume (for local persistence) or, in the cloud, an external store: S3 for files, RDS/Aurora for relational data, ElastiCache/Redis for sessions. Containers are cattle; treat their disk as scratch.

Say it out loud say it

"Never in the container — its disk is scratch. Persistent state lives in a volume or an external store like S3 or RDS, so killing a container loses nothing."

Follow-ups to expect
  • What about a stateful workload like a database in K8s? (StatefulSet + persistent volume, but managed RDS is usually simpler.)
Tag or digest in production — and why?core
Model answer

Digest. A tag like :1.4 or :latest is a movable pointer — it can be re-pushed to different bytes, so two deploys of the "same" tag can run different code, and a rollback isn't reproducible. Pinning @sha256:… guarantees every node runs the identical, tamper-evident image you tested. Tag for humans, deploy by digest.

Say it out loud say it

"Tags move, digests don't. Prod pins the sha256 digest so every replica is byte-identical and rollbacks are exact — no surprise re-push under the same tag."

When would you pick serverless over containers?stretch
Model answer

When the workload is spiky or event-driven and idle cost matters — a webhook handler, a queue consumer, a nightly job. Lambda scales to zero and charges per invocation, with almost no ops. I'd stay on containers (ECS/EKS) for steady high-traffic services, long-running processes, anything beyond Lambda's runtime limits, or when I need fine control and portability. The axes are idle cost, cold-start tolerance, control, and ops burden.

Say it out loud say it

"Serverless when traffic is bursty and idle cost hurts — it scales to zero with near-zero ops. Containers when it's steady, long-running, or needs control. It's idle cost and cold-start tolerance versus how much I want to manage."
