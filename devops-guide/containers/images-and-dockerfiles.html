Containers · images

Images & Dockerfiles.

An image is a sealed, layered snapshot of your app and everything it needs to run — built once, run identically on any host. The Dockerfile is the recipe; the build cache is what makes it fast.

01 Container vs VM

A VM virtualizes hardware and ships a whole guest OS; a container shares the host kernel and isolates only your process — so it's smaller, starts in milliseconds, and packs more densely.

Containers get their isolation from two Linux kernel features: namespaces (each container sees its own PIDs, network, mounts) and cgroups (limit its CPU/memory). No second OS to boot.

In plain English analogy

A VM is a whole house — its own foundation, plumbing, and walls. A container is an apartment in a shared building: it has its own locked door and rooms, but plumbing and structure (the kernel) are shared. Far cheaper to add one more apartment than to build one more house.

02 An image is a stack of layers

Each Dockerfile instruction (FROM, COPY, RUN) produces one read-only layer. The final image is those layers stacked; a running container adds a thin writable layer on top.

Layers are content-addressed and cached. Rebuild and only the layers whose inputs changed (and everything after them) are redone — the rest are reused instantly.

Heads up note

Picture layers as transparent sheets stacked on a projector — base at the bottom, your code on top. Swap only the top sheet and the rest stay exactly as they were. That reuse is why a small code change rebuilds in seconds.

03 Dockerfile basics

A Dockerfile is an ordered list of instructions. Four carry most of the meaning:

FROM
The base image you build on. Sets the starting layers (OS + runtime).
COPY
Copy files from your build context into the image (e.g. source, deps manifest).
RUN
Execute a command at build time and bake the result into a layer (e.g. install packages).
CMD vs ENTRYPOINT
ENTRYPOINT = the fixed executable the container runs; CMD = its default arguments (and is what gets overridden on docker run … args).
CMD alone
Dockerfile
CMD ["python", "app.py"]
# docker run img -- bash
# replaces the WHOLE command
ENTRYPOINT + CMD
Dockerfile
ENTRYPOINT ["python", "app.py"]
CMD ["--port=8080"]
# run img --port=9090
# overrides only the ARGS

Use exec form (["python","app.py"], JSON array) not shell form, so signals like SIGTERM reach your process directly for a clean shutdown.

04 Multi-stage builds & small, secure bases

A multi-stage build uses a fat stage to compile/install, then copies only the artifacts into a slim runtime stage — so compilers, build deps, and caches never ship to production.

Dockerfile
# build stage (fat: has compilers)
FROM python:3.12 AS build
WORKDIR /app
COPY requirements.txt .
RUN pip install --prefix=/install -r requirements.txt

# runtime stage (slim, non-root)
FROM python:3.12-slim
COPY --from=build /install /usr/local
COPY . /app
WORKDIR /app
USER 1001                       # never root
ENTRYPOINT ["python", "app.py"]

Shrink and harden the image with a smaller base and a non-root user:

-slim
Same distro, stripped of docs/extras. Easy first win, broad compatibility.
Alpine
Tiny (musl libc). Watch for glibc-compatibility surprises with some wheels/binaries.
distroless
Just your app + runtime, no shell or package manager — smallest attack surface.
non-root USER
Drop from root so a container escape can't act as root on the host.
Heads up note

Images are an OCI (Open Container Initiative) standard — a build from Docker/BuildKit runs on containerd, Podman, or any OCI runtime, on any registry. "Docker image" really means "OCI image."

05 Cache order, tags vs digests, secrets

Order instructions so dependencies cache before app code: copy the deps manifest and install first, then copy your fast-changing source last.

Cache buster
Dockerfile
COPY . .
RUN pip install -r requirements.txt
# any code edit busts the
# install cache → slow rebuilds
Deps cached first
Dockerfile
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
# code edits reuse the
# cached install layer

Reference images two ways. A tag is a movable label; a digest is an immutable content hash.

Tag
myapp:1.4 — readable, but can be re-pushed to point at different bytes (:latest is the worst offender).
Digest
myapp@sha256:9f2… — the exact bytes, forever. Pin digests in production for reproducible, tamper-evident deploys.
Common trap gotcha

Never bake a secret into a layer — ENV API_KEY=… or COPY .env persists in image history forever, even if a later step deletes it. Anyone who pulls the image can recover it. Inject secrets at run time (env/Secrets Manager) or use BuildKit build secrets. And don't run as root: it's the most common image-security finding.

You edit one line of source and rebuild — but pip install runs from scratch every time. Why?

Right. Cache invalidation cascades downward. Copy requirements.txt and install before copying the full source, so the dependency layer stays cached when only app code changes.

06 Interview rapid-fire

Container vs VM — what's the real difference?warm-up
Model answer

A VM virtualizes hardware and runs a full guest OS on a hypervisor — heavy, slow to boot, strongly isolated. A container shares the host kernel and isolates the process with namespaces and cgroups — MBs not GBs, starts in milliseconds, denser. You trade some isolation for speed and density; on AWS that's EC2 (VM) vs ECS/Fargate or EKS (containers).

Say it out loud say it

"A VM ships a whole OS; a container shares the host kernel and just fences off your process. So containers are smaller, start instantly, and pack denser — at the cost of weaker isolation."

Why use a multi-stage build, and how else do you shrink/secure an image?core
Model answer

Multi-stage keeps build-time junk — compilers, dev deps, caches — out of the shipped image: a fat stage builds, then I COPY --from only the artifacts into a slim runtime stage. On top of that: a small base (-slim, Alpine, or distroless), a non-root USER, ordering layers so deps cache before code, and no secrets baked into any layer.

Say it out loud say it

"Build fat, ship slim — copy just the artifacts into a distroless, non-root runtime stage. Smaller image, smaller attack surface, faster pulls."

Follow-ups to expect
  • Distroless vs Alpine? (Distroless has no shell/pkg manager → safer but harder to debug; Alpine is tiny but musl can break some binaries.)
  • Why run as non-root? (A container escape inherits your UID — root in the container risks root on the host.)
Tag vs digest — which do you deploy in production?stretch
Model answer

Deploy by digest (@sha256:…). A tag like :1.4 or :latest is a movable pointer — someone can re-push different bytes under the same tag, so the same tag can deploy two different images. A digest is the immutable content hash: same hash, same bytes, every time — reproducible and tamper-evident. Tags for humans, digests for machines.

Say it out loud say it

"Tags move, digests don't. I tag for readability but pin the deploy to the sha256 digest so prod runs the exact bytes I tested — never a surprise re-push."
