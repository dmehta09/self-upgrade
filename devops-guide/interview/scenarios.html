Interview prep · scenarios

Scenario walkthroughs.

The open-ended design and debugging prompts. For each one: what the interviewer asks, how to clarify before you dive in, the approach, and exactly what a strong answer lands. Reason out loud — that's most of the score.

01 Design a zero-downtime deploy on AWS

Prompt: "We deploy a service on AWS and users see errors during every release. Design a zero-downtime deployment."

Clarify first
  • Where does it run — EC2 + ASG, ECS/Fargate, or EKS? (Decides the rollout mechanism.)
  • Is it behind an ALB with health checks already?
  • Does this release touch the database schema? (The hardest part of "zero downtime.")
  • How fast must rollback be, and how much extra infra cost is acceptable?
Approach — pick the right strategy

Recreate causes downtime (the problem). Rolling swaps instances gradually behind the ALB. Blue-green runs a full second environment and flips the ALB target group for an instant, reversible cutover. Canary sends a small % to v2 first and widens only if healthy.

Pro tip tip

Land on blue-green (instant, reversible cutover) or canary (smallest blast radius). Either way, the two non-negotiables are real health checks on the ALB target group and backward-compatible DB migrations (expand/contract) so both versions can run during the switch.

What a strong answer hits
  • Names a concrete strategy and why — blue-green for instant rollback, canary for high-traffic risk control.
  • ALB health/readiness checks gate traffic; connection draining on the old targets.
  • Backward-compatible migrations (expand/contract) — the most common follow-up trap.
  • A clear, fast rollback: flip the target group back, or cut canary traffic to 0%.
  • Mentions how it verifies health post-deploy (and defers the metric internals to observability).

02 Build a CI/CD pipeline from scratch

Prompt: "Design a CI/CD pipeline from scratch for a containerized web app."

Clarify first
  • Language/framework, and where it deploys — ECS/Fargate, EKS, or Lambda?
  • Which CI tool, or is it open? (GitHub Actions is a safe default in 2026.)
  • Branching model — trunk-based with PRs? And do we need continuous delivery (human gate) or full deployment?
  • How do we authenticate to AWS — can we use OIDC instead of stored keys?
Approach — the pipeline, left to right
Common trap gotcha

Don't rebuild per environment, and don't store long-lived AWS keys in CI. Build once, promote the same image (config-only differences) and authenticate with OIDC assuming a least-privilege role. Both are classic interview follow-ups.

What a strong answer hits
  • Webhook-triggered, ephemeral runner; fast PR feedback (cache, parallel matrix, fail-fast lint).
  • Build the artifact once, tag by SHA, promote the identical image staging → prod.
  • Image goes to ECR; auth via OIDC + least-privilege IAM role, not stored keys.
  • A gate (smoke tests + optional human approval) and a one-command rollback.
  • Shift-left checks (Trivy scan, dependency/secret scan) in the pipeline.

03 Triage a stuck rollout / CrashLoopBackOff

Prompt: "A Kubernetes rollout is stuck and pods are in CrashLoopBackOff. Walk me through triaging it." This scores your method, not memorized fixes.

Clarify first
  • What changed in this release — image tag, config, resources, or manifest?
  • Is it all new pods or just some? Is the old version still serving traffic?
  • Do we want to recover first (rollback) or root-cause live? (Usually: stop the bleeding first.)
Triage playbook
1

Check rollout status

kubectl rollout status deploy/app and kubectl get pods — confirm it's stuck and see how many pods are bad vs healthy old ones.

2

Describe the pod & read events

kubectl describe pod <pod> — the Events at the bottom usually name it: ImagePullBackOff, OOMKilled, failed probe, or unschedulable.

3

Read the container logs

kubectl logs <pod>, and --previous for the crashed instance. A crash on startup is usually a bad config, a missing env var/secret, or a failed dependency connection.

4

Check the usual suspects

Probes too aggressive (liveness killing a slow-starting pod)? Resources — limit too low → OOMKilled? Image pull — wrong tag or missing ECR pull permission? Map the symptom to one of these.

5

Recover, then fix

kubectl rollout undo deploy/app to revert to the last good ReplicaSet and restore service. Then fix the root cause in the manifest/config and re-deploy through the pipeline.

Heads up scope

Reading kubectl logs to triage is fine here. The centralized logging/metrics stack that aggregates this across the fleet — and the dashboards behind it — lives in the companion Observability guide. Stay at the process level: form a hypothesis, narrow it with evidence.

What a strong answer hits
  • An ordered method (status → describe/events → logs → suspects → rollback), not random guessing.
  • Knows where the signal is: describe Events name most failures; logs --previous for crashes.
  • Maps symptoms to causes: ImagePull, OOMKilled, failed probe, unschedulable, bad config/secret.
  • Recovers first (rollout undo) — mitigation before root cause — then fixes properly in code.

04 Stand up production infra on AWS

Prompt: "Stand up production infrastructure for a web app on AWS." They want a resilient, secure, reproducible baseline — and to hear you say IaC and Multi-AZ unprompted.

Clarify first
  • Traffic shape and expected scale? Stateless web tier, or stateful components too?
  • Containers (ECS/EKS) or plain EC2? Managed database or self-run?
  • Compliance/region constraints, and what's the budget vs resilience appetite?
Approach — the baseline topology
VPC across two AZs · public edge, private compute & data
edge
Route 53 + ALB
DNS → load balancer in public subnets
compute
ASG / EKS
private subnets, spread across 2+ AZs
data
RDS Multi-AZ
primary + standby in another AZ
Internet hits a public ALB; compute and data sit in private subnets with no public IPs. Egress via NAT.
1

Network

A VPC with public subnets (IGW route, hold the ALB + NAT) and private subnets (compute + data), each spread across 2+ AZs. Security groups stateful and least-open.

2

Edge + compute

ALB in the public subnets fronts an Auto Scaling Group (or EKS) in private subnets, with health checks and scaling policies. No instance gets a public IP.

3

Data

RDS/Aurora Multi-AZ for automatic failover; in a DB-only private subnet reachable just from the app's security group. Backups + point-in-time recovery on.

4

Identity + secrets

IAM least-privilege roles per component (instance role / IRSA), secrets in Secrets Manager / SSM with KMS — no static keys, no public S3.

5

Provision it as code

Define all of the above in Terraform/CloudFormation, with remote locked state, and deploy/update it through CI/CD — never click-ops.

What a strong answer hits
  • Multi-AZ everywhere (subnets, ASG, RDS) — resilience is the headline.
  • Public/private split: only the ALB is internet-facing; compute + data are private, egress via NAT.
  • Least-privilege IAM, secrets in Secrets Manager/SSM + KMS, encryption at rest, no public S3.
  • It's all IaC with remote locked state, shipped via CI/CD — reproducible, not hand-built.
  • Names cost/resilience trade-offs (NAT cost, Multi-AZ vs single-AZ) rather than over-building blindly.

05 What interviewers are really scoring

Across every scenario above, the rubric is the same. The "right answer" matters less than demonstrating these five behaviors out loud.

Clarifies requirements
Asks about scale, stack, constraints, and rollback appetite before designing. Jumping straight to a solution is the most common miss.
Reasons out loud
Narrates the thinking and assumptions so the interviewer can follow — and correct — the path. Silence reads as being stuck.
Names trade-offs
Every choice has a cost (speed vs control, blast radius vs effort, cost vs resilience) and they say it explicitly.
Considers failure & rollback
Plans for "what breaks, and how do we undo it in 60 seconds?" — not just the happy path.
Builds in security
Least privilege, no stored keys, secrets managed, private by default — mentioned unprompted, not bolted on at the end.
A scenario prompt is deliberately vague. What's your first move?core
Model answer

Treat the vagueness as part of the test and clarify before designing: scale, stack, where it runs, constraints, and how fast rollback must be. State the assumptions you're making so the interviewer can redirect you early. Then design to those stated assumptions — and revisit them out loud as you go.

Say it out loud say it

"Before I design, let me pin down scale, the stack, where it runs, and rollback expectations. I'll state my assumptions so you can steer me, then build to those."

How do you keep a design answer from rambling?warm-up
Model answer

Give the shape first — "I'll cover network, compute, data, security, then CI/CD" — and walk it in that order so the interviewer can follow and interrupt. Land each piece with its trade-off, and check in ("want me to go deeper on rollback?") rather than dumping everything at once.
