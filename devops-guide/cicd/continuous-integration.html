Git & CI/CD · continuous integration

Continuous integration.

Every commit is built and tested automatically against shared main, so breakage surfaces in minutes — not on release day. CI is the heartbeat of a delivery pipeline.

01 What CI actually is

CI = merge small changes often, and have a robot build + test every change before it reaches the trunk. The goal is a main branch that is always releasable.

A push (or pull request) fires a webhook; a fresh runner checks out the code, installs dependencies, runs lint + tests, and builds a deployable artifact. Green means safe to merge; red blocks it.

In plain English analogy

CI is a spell-checker that runs on every sentence as you type, instead of proofreading the whole book the night before it prints. Catch the typo in the sentence you just wrote and it's a one-second fix; find it after 500 pages and you're hunting for which edit broke it.

Trigger
A push or pull request fires a webhook — CI reacts to git, not a schedule.
Runner
An ephemeral machine/container, fresh each run, so builds are reproducible and isolated.
Gate
Required checks (tests, lint, security scan) that must pass before merge.
Artifact
The one immutable output (a versioned container image or package) promoted, unchanged, to every later stage.

02 Anatomy of a pipeline

A CI job is just ordered steps in a YAML file the platform runs for you. Here's a minimal GitHub Actions workflow — the shape is the same on GitLab CI or Jenkins.

.github/workflows/ci.yml
on: pull_request
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.12", cache: pip }
      - run: pip install -r requirements.txt
      - run: ruff check .          # lint
      - run: pytest -q             # tests = the gate
1

Checkout + cache

Pull the exact commit; restore dependency caches so you don't re-download the world every run.

2

Lint & test

Fast static checks first, then unit tests. Fail fast — a broken lint shouldn't wait on a 5-minute test suite.

3

Build the artifact

On success, build one versioned image. Tag it by commit SHA so it's traceable.

4

Publish

Push the image to a registry (ECR/GHCR). CD takes over from here — same artifact, every environment.

Common trap gotcha

A 30-minute pipeline is a broken pipeline — people stop waiting for it and merge on faith. Keep PR feedback under ~10 minutes: cache dependencies, run jobs in parallel (a test matrix), and push slow end-to-end suites to a nightly or post-merge run.

03 Keep main green

CI only pays off if changes are small and frequent. Long-lived branches defeat the point: you integrate rarely, so conflicts and surprises pile up — the exact pain CI exists to kill.

Defeats CI
  • Feature branch lives for 3 weeks.
  • One giant PR, hundreds of files.
  • Tests run only before release.
  • "Works on my machine" merges.
Trunk-based + CI
  • Small PRs merged daily behind feature flags.
  • Required green checks block merge.
  • Every commit builds the same way on a clean runner.
  • Broken main = top priority to fix.
Pro tip tip

Build the artifact once in CI and promote that identical image through staging → prod. Rebuilding per environment means "tested in staging" no longer guarantees "the same bytes run in prod."

Your test suite passes locally but fails in CI. What's the most likely cause?

Right. The whole value of an ephemeral runner is that it's clean. "Works locally, fails in CI" almost always means your machine has something the runner doesn't — pin versions and declare every dependency.

04 Interview rapid-fire

What's the difference between continuous integration, delivery, and deployment?warm-up
Model answer

CI = every change is automatically built and tested against main. Continuous delivery = every green build is automatically packaged and ready to release, but a human clicks "go." Continuous deployment = that release step is automatic too — green reaches production with no manual gate.

Say it out loud say it

"CI keeps main always-buildable. Delivery keeps it always-shippable with a human approval. Deployment removes even that click."

A flaky test fails ~10% of CI runs. What do you do?core
Model answer

Quarantine it (mark it non-blocking) so it stops eroding trust in the pipeline, file a ticket, and fix the root cause — usually a timing/order/shared-state dependency. Don't "fix" flakiness with blanket retries; that hides real intermittent bugs and slows every run.

Say it out loud say it

"A flaky test is worse than no test — it teaches the team to ignore red. Quarantine it fast, then fix the determinism: time, ordering, or shared state."

Follow-ups to expect
  • When are automatic retries acceptable? (Network-bound integration tests, with a low cap and an alert.)
  • How do you keep a suite fast as it grows? (Parallel matrix, test sharding, only run affected tests.)
How should CI authenticate to AWS to push an image to ECR?stretch
Model answer

Use OIDC: the CI provider issues a short-lived token, and the pipeline assumes an IAM role scoped to just ECR push. No long-lived AWS_SECRET_ACCESS_KEY stored as a secret — nothing to leak or rotate. Storing static keys in CI is the classic finding in a security review.

Say it out loud say it

"Federate with OIDC and assume a least-privilege role per pipeline. Short-lived credentials beat long-lived keys you have to store, rotate, and pray nobody prints to a log."
