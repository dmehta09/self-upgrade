Pipeline auth, OIDC & reusable workflows.

Stop storing long-lived cloud keys in CI. OIDC federation lets GitHub Actions assume a short-lived AWS role; environments add protection rules; reusable workflows keep every repo from reinventing the pipeline.

01 OIDC → assume role (no static keys)

The runner requests an OIDC token from GitHub; AWS trusts that issuer and mints temporary credentials for a role. The trust policy pins repo, branch, or environment — so a fork PR can't assume prod.

In plain English analogy

Static keys are a house key under the mat — anyone who finds it walks in forever. OIDC is a hotel keycard that expires when checkout ends: GitHub vouches "this job is from repo X on main," AWS hands a short-lived card, and the trust policy decides which rooms that card opens.

.github/workflows/deploy.yml
jobs:
  deploy:
    runs-on: ubuntu-latest
    permissions:
      id-token: write   # OIDC token
      contents: read
    environment: production
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123:role/gha-prod
          aws-region: us-east-1
      - run: ./deploy.sh

02 Environments & protection rules

GitHub Environments gate jobs that name them: required reviewers, wait timers, and branch restrictions. Pair with OIDC trust on environment:production so only protected jobs can assume the prod role.

Required reviewers
A human must approve before the job runs — change control without a separate tool.
Deployment branches
Only main (or release tags) can deploy to prod.
Environment secrets
Scoped secrets not available to unprotected workflows.
Trust condition
IAM sub / environment claim must match — forks and feature branches fail STS.
Common trap gotcha

OIDC with a trust policy of repo:org/*:* is barely better than a static key — any workflow in any branch can assume the role. Pin to ref:refs/heads/main and/or a specific environment, and use separate roles for staging vs prod.

03 Reusable workflows & composite actions

Reusable workflows (workflow_call) share whole job graphs across repos. Composite actions share a sequence of steps. Centralize lint/test/OIDC-deploy once; version them so callers pin a tag or SHA.

.github/workflows/ci.yml (caller)
jobs:
  test:
    uses: acme/platform-workflows/.github/workflows/node-ci.yml@v3
    with:
      node-version: "22"
  deploy:
    needs: test
    uses: acme/platform-workflows/.github/workflows/oidc-deploy.yml@v3
    secrets: inherit
    with:
      environment: production
Reusable workflow
  • Whole jobs / pipeline shape.
  • Caller passes inputs + secrets.
  • Best for org-standard CI/CD.
Composite action
  • A few steps inside a job.
  • Like a scripted function.
  • Best for checkout+setup+scan snippets.

Why prefer OIDC role assumption over storing AWS_SECRET_ACCESS_KEY as a GitHub secret?

Right. Blast radius and rotation: temporary STS creds expire quickly, and the IAM trust policy decides which workflows may assume the role.

04 Interview rapid-fire

How does GitHub Actions authenticate to AWS without long-lived keys?core
Model answer

Enable OIDC: the job requests an id-token, AWS has an identity provider for GitHub, and an IAM role trust policy allows assume-role when claims match (org/repo, ref, environment). configure-aws-credentials exchanges the JWT for temporary STS credentials. No static access keys in secrets.

Say it out loud say it

"GitHub mints a short-lived OIDC token for the job; AWS trusts that issuer and hands temporary role credentials. The trust policy pins which repo and environment can assume prod."

What are GitHub Environments for in a deploy pipeline?warm-up
Model answer

They attach protection rules to jobs that target them — required reviewers, wait timers, allowed branches — and hold environment-scoped secrets. Combined with OIDC trust on that environment name, only approved deploys to production can assume the prod role.

Say it out loud say it

"Environments are the approval gate and secret scope for deploys — required reviewers plus branch rules, and the IAM trust can require that environment claim."

Reusable workflows vs composite actions?stretch
Model answer

Reusable workflows share entire called workflows (jobs, needs, environments) across repositories — ideal for org-standard CI/CD. Composite actions bundle steps inside a single job — ideal for small shared snippets. Pin both by version/SHA so callers don't float on main.

Say it out loud say it

"Reusable workflows share whole pipelines; composite actions share a few steps. Platform team owns the versions; app repos call them pinned."
