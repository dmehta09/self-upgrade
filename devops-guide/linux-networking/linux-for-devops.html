Linux for DevOps.

Every container, every EC2 box, every CI runner is a Linux machine. You don't need to be a kernel hacker — but processes, signals, permissions, and systemd are the wiring behind everything you deploy.

01 The mental model

A running program is a process with a PID. The kernel talks to it with signals, the filesystem gates it with permissions, and systemd keeps long-lived ones alive. Master these four and Linux stops being a black box.

Almost every DevOps incident bottoms out here: a process that won't die, a file the app can't read, a service that didn't restart, a script that swallowed an error. The vocabulary below is what you debug with.

In plain English analogy

Linux is the building your apps live in. Processes are the tenants, signals are the messages you slip under their doors ("please leave" vs. "the building is on fire, OUT now"), permissions are who has keys to which rooms, and systemd is the building manager who notices a tenant collapsed and calls a replacement. You can't run the building without knowing the wiring and plumbing.

Process
An instance of a running program, identified by a PID (process ID). It has an owner, an environment, and open files.
Signal
A tiny message the kernel delivers to a process — e.g. SIGTERM (please stop) or SIGKILL (die now).
Permissions
r/w/x bits plus an owning user and group decide who can read, write, or execute a file.
Daemon
A long-running background service (a web server, an agent). On modern Linux, systemd supervises them.

02 Signals & graceful shutdown

SIGTERM is a polite "please stop and clean up." SIGKILL (kill -9) is forced — the kernel reaps the process instantly, no chance to react. This single distinction governs whether your deploys lose in-flight requests.

When an orchestrator rolls a deployment it sends SIGTERM first, waits a grace period, then sends SIGKILL. A well-behaved app traps SIGTERM, stops accepting new work, drains open connections, flushes buffers, and exits — that's connection draining done right.

"finish up & exit"

signals.sh
ps aux | grep gunicorn       # find the PID
kill 4821                    # SIGTERM (default) — polite stop
kill -TERM 4821             # same thing, explicit
kill -9 4821               # SIGKILL — forced, NO cleanup
trap 'echo draining; exit 0' TERM   # an app trapping SIGTERM
Common trap gotcha

kill -9 gives the app zero chance to flush, commit, or finish in-flight requests — you can drop user traffic or corrupt state. Containers must trap SIGTERM and exit cleanly within the grace period. Bonus trap: a shell-form CMD runs your app as a child of /bin/sh (PID 1), which doesn't forward signals — use exec/JSON form so your process is PID 1 and actually receives SIGTERM.

03 Permissions, users & systemd

Files carry rwx bits for owner / group / others, plus an owning user. The rule for production: run as a non-root user with only the access it needs. systemd is how Linux starts, supervises, and restarts your daemons.

Read -rwxr-x--- left to right: a regular file the owner can read/write/execute, the group can read/execute, others get nothing. chmod changes the bits; chown changes the owner. Least privilege on the filesystem is the same instinct as least-privilege IAM.

GroupMust-know commands

A systemd unit file declares how to run a service: the command, the user, and the restart policy. systemctl is the control surface; service logs land in journald (read with journalctl -u app — the deeper telemetry story is its own topic).

/etc/systemd/system/app.service
[Service]
ExecStart=/usr/bin/python /app/main.py
User=app                 # NOT root
Restart=on-failure      # systemd respawns a crashed daemon
[Install]
WantedBy=multi-user.target
Heads up scope

Package managers differ by distro family: apt (Debian/Ubuntu), yum/dnf (RHEL/Amazon Linux), apk (Alpine — common in slim container images). Same job, different verbs.

04 Robust shell & "a container is just a process"

Every command returns an exit code in $? — 0 means success, non-zero means failure. CI and shells branch on it. A safe script starts with set -euo pipefail so failures stop the script instead of silently rolling on.

Pipelines (|) stream one command's output into the next; combine with exit codes and env vars (config via the environment, the twelve-factor way) and you have most DevOps glue.

deploy.sh
#!/usr/bin/env bash
set -euo pipefail        # -e exit on error, -u undefined var = error,
                        #   -o pipefail a failed pipe stage fails the line
: "${IMAGE_TAG:?must be set}"      # require an env var or bail
docker build -t app:"$IMAGE_TAG" .
echo "exit code was $?"           # 0 on success
Pro tip tip

Tie it all together: a container is just a Linux process with namespaces + cgroups. Namespaces give it its own isolated view (its own PIDs, network, mounts); cgroups cap how much CPU and memory it can use. There's no magic VM inside — it's a normal process the kernel has fenced off. That's why signals, permissions, and exit codes apply to containers exactly as they do to any process.

Your container ignores the orchestrator's stop request and is always SIGKILLed after the 30s grace period, dropping requests. What's the most likely cause?

Right. Graceful shutdown depends on the app actually receiving SIGTERM. Run it as PID 1 (exec/JSON-form CMD) and trap SIGTERM to drain. A longer grace period just delays the same forced kill.

05 Interview rapid-fire

SIGTERM vs SIGKILL — and why does it matter for containers?core
Model answer

SIGTERM is catchable: the app can trap it, stop accepting new requests, drain in-flight ones, flush state, and exit cleanly. SIGKILL (kill -9) can't be caught — the kernel kills the process instantly with no cleanup. Orchestrators send SIGTERM, wait a grace period, then SIGKILL; so to deploy without dropping traffic, your container must trap SIGTERM and shut down gracefully within that window.

Say it out loud say it

"SIGTERM is 'please wrap up' — catchable, so you can drain connections. SIGKILL is 'die now' — uncatchable. Roll-outs send TERM then KILL, so a clean deploy means trapping TERM and draining inside the grace period."

Follow-ups to expect
  • Why might your app never get the SIGTERM? (It's not PID 1 — shell-form CMD wraps it in /bin/sh, which doesn't forward signals.)
  • What sends the SIGKILL? (The orchestrator/kubelet, after terminationGracePeriodSeconds elapses.)
Why run containers as a non-root user?core
Model answer

Container isolation isn't a perfect security boundary — root inside the container is closer to root on the host than people assume, so a compromised app or a container-escape bug has a far bigger blast radius if it runs as root. Running as a dedicated non-root user (a USER line in the Dockerfile) is least privilege applied to the process: the app can only touch what it actually needs. It also catches accidental writes to paths that should be read-only.

Say it out loud say it

"The container boundary can leak, so root-in-container is a risk to the host. Drop to a non-root user with a USER line — least privilege shrinks the blast radius if the app is ever popped."

What does set -euo pipefail do, and why use it in scripts?stretch
Model answer

-e exits the script the moment any command returns non-zero; -u treats an unset variable as an error instead of silently expanding to empty; -o pipefail makes a pipeline fail if any stage fails, not just the last. Without it, a Bash script happily marches past a failed step — in a deploy script that means shipping on top of a broken build. It turns "silent partial failure" into "loud, early stop."

Say it out loud say it

"It makes Bash fail fast: stop on any error, error on unset vars, and don't let a failing pipe stage hide behind a passing last command. Default-on for any script that runs in CI or a deploy."
