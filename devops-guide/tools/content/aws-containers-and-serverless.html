AWS · containers & serverless

Containers & serverless.

Once you have a container image, AWS gives you three places to run code: ECS/Fargate (AWS-native containers), EKS (managed Kubernetes), and Lambda (event-driven functions). The interview test is knowing which to reach for — and why.

01 ECS & Fargate: containers, AWS-native

ECS is AWS's own container orchestrator — it schedules and runs your containers. Fargate is a launch mode where AWS runs them for you with no servers to manage; you just declare CPU/memory per task. Images come from ECR, AWS's private registry.

In plain English analogy

Fargate is renting a fully-staffed kitchen per dish — you hand over the recipe and walk away; there's no kitchen to clean or maintain. EKS is running your own Kubernetes kitchen while AWS keeps the building standing (the control plane). Lambda is a food truck that only fires up its grill when an order arrives, then shuts off — you pay only while it's cooking.

A tiny ECS task definition — the contract for "run this image with these resources":

task-def.json
{
  "family": "web",
  "requiresCompatibilities": ["FARGATE"],
  "cpu": "512", "memory": "1024",
  "containerDefinitions": [{
    "name": "app",
    "image": "1234.dkr.ecr.us-east-1.amazonaws.com/web@sha256:9f2...",
    "portMappings": [{ "containerPort": 8080 }]
  }]
}

No node count, no SSH, no patching — Fargate places the task and bills for the CPU/memory you reserved. ECS handles scheduling, health, and rollout.

02 EKS: managed Kubernetes

EKS is AWS-managed Kubernetes — AWS runs the control plane; you get the full K8s API and its entire ecosystem. Reach for it when you want portability or the K8s tooling (Helm, operators, GitOps with Argo/Flux), or you already run Kubernetes.

The trade is power versus effort. ECS speaks AWS and is operationally light; EKS gives you a portable, vendor-neutral platform but you now own Kubernetes upgrades, add-ons, and its learning curve.

Pick ECS/Fargate when…
  • You're all-in on AWS and want the least ops.
  • The team doesn't know (or want) Kubernetes.
  • You value "it just runs" over portability.
Pick EKS when…
  • You need the K8s ecosystem — Helm, operators, CRDs, Argo CD.
  • You want portability across clouds / on-prem.
  • You already run Kubernetes elsewhere.
Heads up note

EKS data-plane nodes can also run on Fargate — so "serverless" and "Kubernetes" aren't opposites. The split is really: do you want the Kubernetes API surface (EKS) or AWS's simpler native one (ECS)?

03 Lambda: event-driven functions

Lambda runs a function in response to an event — no servers, pay per invocation, scales to zero. You write the handler; AWS runs it when a trigger fires.

Triggers are the point: a function wires to an event source and runs only when something happens.

API Gateway fronts HTTP; EventBridge, SQS, and S3 events drive async work. The function spins up per event and stops when done.

Know the limits cold — they decide where Lambda fits:

~15-min ceiling
A single invocation is capped at 15 minutes. Long batch jobs don't fit.
Cold starts
A new environment adds startup latency on the first request after idle (or on scale-out).
Stateless
No durable local state between invocations — persist to S3 / DynamoDB / RDS.
Concurrency limits
Account/function concurrency caps how many run at once; bursts can throttle.
Common trap gotcha

Lambda is wrong for long-running or stateful work. The ~15-minute cap, cold starts, and statelessness rule out batch jobs, persistent connections, and anything latency-critical that can't tolerate a cold start. Reach for Lambda for short, spiky, event-driven tasks — not a websocket server or a 2-hour ETL.

04 ECS vs EKS vs Lambda: the decision

Decide on four axes: ops burden, portability, cost model, and latency / cold-start. Most teams in 2026 default to ECS/Fargate, add EKS when they need the K8s ecosystem, and sprinkle Lambda for glue and spiky events.

A team runs steady, long-lived microservices on AWS, wants minimal operational overhead, and has no need for the Kubernetes ecosystem. Best fit?

Right. Steady, long-running + minimal ops + no K8s need = ECS/Fargate. EKS adds Kubernetes operational overhead they don't want; Lambda's cold starts, 15-minute cap, and statelessness make it a poor fit for always-on services.

05 Interview rapid-fire

ECS vs EKS — when do you choose each?core
Model answer

Both run containers; the difference is the API and the ops burden. ECS is AWS-native and operationally light — great when you're all-in on AWS and don't need Kubernetes. EKS is managed Kubernetes: pick it when you want the K8s ecosystem (Helm, operators, Argo CD) or portability across clouds/on-prem, or you already run K8s. EKS is more powerful but you own the upgrades and add-ons.

Say it out loud say it

"ECS if you just want containers running on AWS with minimal ops. EKS if you need the Kubernetes ecosystem or portability — more power, but you own the operational overhead."

Follow-ups to expect
  • What does AWS manage on EKS? (The control plane — API server, etcd, scheduler.)
  • Where do images live either way? (ECR — AWS's private registry.)
Fargate vs the EC2 launch type for ECS/EKS?warm-up
Model answer

It's who owns the nodes. With Fargate, AWS runs the underlying capacity — no instances to patch, scale, or right-size; you just declare CPU/memory per task and pay for that. With the EC2 launch type, you manage a fleet of instances yourself: more control and often cheaper at steady high utilisation, but you own patching, scaling, and bin-packing. Fargate trades a little cost for far less ops.

Say it out loud say it

"Fargate means AWS owns the nodes — no servers to patch or scale, pay per task. EC2 launch type means I manage the instances myself: more control, cheaper at high utilisation, but more ops."

When is Lambda the right call, and what are its limits?core
Model answer

Lambda shines for short, spiky, event-driven work — an API Gateway handler, an S3-upload processor, a queue consumer, cron glue. It scales to zero and you pay per invocation. The limits that rule it out: a ~15-minute max duration, cold-start latency, statelessness, and concurrency caps. So no long batch jobs, no persistent connections, nothing latency-critical that can't absorb a cold start — those belong on containers.

Say it out loud say it

"Lambda for short, event-driven, spiky work — it scales to zero and you pay per call. But the 15-minute cap, cold starts, and statelessness mean long or stateful jobs belong on ECS or EKS instead."
