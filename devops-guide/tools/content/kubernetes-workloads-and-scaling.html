Kubernetes · running workloads

Workloads, health & scaling.

Once pods run, Kubernetes manages them for you: it rolls out new versions without downtime, probes health to restart or shield pods, packs them by resource requests, and autoscales to load. Pick the right workload type for the job.

01 Rolling updates & rollback

A Deployment ships a new version by a rolling update: it swaps pods a few at a time, governed by maxSurge (extra pods allowed) and maxUnavailable (how many can be down) — so the Service never goes dark.

In plain English analogy

Resource requests are the table you reserve at a restaurant — the host plans seating around it (this is how the scheduler places you). Limits are the hard spending cap on your card — blow past the memory cap and you're cut off (OOMKilled); push CPU past it and the kitchen just slows your orders (throttling).

1

New ReplicaSet

The Deployment creates a fresh ReplicaSet for v2 and starts a few v2 pods (up to maxSurge).

2

Wait for ready

It waits until new pods pass their readiness probe before sending them traffic, then retires the same number of v1 pods.

3

Repeat

Step by step, v1 shrinks and v2 grows. maxUnavailable caps how many can be missing — capacity holds throughout.

4

Rollback

Bad release? kubectl rollout undo flips back to the previous ReplicaSet from revision history — fast, because v1 pods just scale back up.

Heads up scope

Fancier strategies (canary, blue-green with metric analysis via Argo Rollouts/Flagger) live on the release-strategies page. The judging signal behind them — error rates, latency, dashboards — is covered in the companion Observability guide; here we stay on the rollout mechanics.

02 Health probes

The kubelet checks each container with up to three probes. They answer different questions — confusing them causes outages.

Liveness
"Is it dead/stuck?" Fails → restart the container. For deadlocks a restart can't-not-fix-itself out of.
Readiness
"Can it serve right now?" Fails → pull the pod out of the Service (no traffic) but leave it running. For warm-up, full caches, or a busy dependency.
Startup
"Has it finished booting?" Holds off liveness/readiness for slow starters so they aren't killed mid-boot.
probes.yaml
livenessProbe:                # restart if dead
  httpGet: { path: /healthz, port: 8080 }
  periodSeconds: 10
readinessProbe:               # gate traffic until ready
  httpGet: { path: /ready, port: 8080 }
  periodSeconds: 5
Common trap gotcha

An over-aggressive liveness probe (short timeout, no startup probe, or pointed at a slow dependency) kills a perfectly healthy-but-busy pod — it restarts, fails again, and you get a CrashLoopBackOff spiral. Rule of thumb: liveness checks only itself (cheap, local); readiness checks whether it can serve; use a startup probe for slow boots.

03 Requests, limits & autoscaling

Requests guide scheduling (the seat you reserve); limits cap consumption (the hard ceiling). The Horizontal Pod Autoscaler (HPA) then adds or removes replicas based on CPU or custom metrics.

Requests — for the scheduler
  • What the pod is guaranteed; the scheduler sums requests to place pods on nodes.
  • Too low → over-packed nodes, noisy neighbors.
  • Missing → scheduler flies blind.
Limits — the hard cap
  • The ceiling a container may use.
  • Memory over limit → OOMKilled (terminated).
  • CPU over limit → throttled (slowed, not killed).

HPA watches a metric (e.g. avg CPU) and scales the replica count between min and max to hit a target — more load, more pods; quiet, fewer. It needs requests set to compute CPU utilization at all.

Common trap gotcha

Omitting resource requests wrecks everything downstream: the scheduler can't bin-pack, pods land on already-stuffed nodes (noisy-neighbor contention), and the HPA can't compute utilization so it never scales. Always set requests; set limits deliberately (memory limit = OOM protection, but a too-tight CPU limit silently throttles you).

04 Beyond Deployment

Deployment is for stateless apps where any replica is interchangeable. When pods need identity, run per-node, or run-to-completion, reach for a different workload object.

WorkloadUse it forKey property
DeploymentStateless services (web/API).Interchangeable pods; easy rolling updates + rollback.
StatefulSetDatabases, queues, clustered stores.Stable identity (db-0, db-1) + its own persistent volume per pod; ordered start.
DaemonSetPer-node agents (log shipper, CNI, node exporter).One pod on every node (auto-added to new nodes).
Job / CronJobBatch tasks / scheduled tasks.Run to completion (Job) or on a cron schedule (CronJob), then stop.

You're deploying a 3-node PostgreSQL cluster where each node needs a stable name and its own durable disk. Which workload?

Right. Deployment pods are interchangeable and share nothing stable — wrong for a DB. A StatefulSet gives each pod a sticky identity (pg-0…) and its own volume, which clustered, stateful systems require.

05 Interview rapid-fire

Liveness vs readiness probe — what's the difference?warm-up
Model answer

Liveness asks "is it dead/stuck?" — if it fails, Kubernetes restarts the container. Readiness asks "can it serve right now?" — if it fails, Kubernetes removes the pod from the Service (stops sending traffic) but leaves it running. Use readiness for warm-up or a temporarily-unavailable dependency; use liveness only for unrecoverable hangs. A startup probe protects slow boots.

Say it out loud say it

"Liveness restarts a dead container; readiness just pulls a busy pod out of rotation until it can serve. Mixing them up — a strict liveness probe on a slow dependency — causes restart loops."

Requests vs limits — and what's OOMKilled?core
Model answer

Requests are what a pod is guaranteed and what the scheduler uses to place it on a node. Limits are the hard ceiling. Exceed the memory limit and the kernel kills the container — that's OOMKilled. Exceed the CPU limit and it's throttled, not killed. Always set requests (or scheduling and the HPA break); set memory limits to contain leaks.

Say it out loud say it

"Requests guide scheduling, limits cap usage. Blow the memory limit and you're OOMKilled; blow the CPU limit and you're just throttled. Skipping requests breaks the scheduler and the autoscaler."

Follow-ups to expect
  • What does the HPA need? (Requests set, so it can compute CPU % utilization.)
  • QoS classes? (Guaranteed = requests == limits; Burstable; BestEffort = none — the first evicted under pressure.)
How does a rolling update and rollback work? When would you use a StatefulSet instead?stretch
Model answer

A Deployment spins up a new ReplicaSet and swaps pods incrementally — bounded by maxSurge/maxUnavailable, waiting for readiness before shifting traffic — so there's no downtime. Rollback is kubectl rollout undo, which scales the previous ReplicaSet back up from revision history. Use a StatefulSet instead of a Deployment when pods need stable identity and their own persistent storage — databases and clustered stateful systems — rather than being interchangeable.

Say it out loud say it

"Rolling update swaps pods a few at a time and waits for readiness, so no downtime; rollback just scales the old ReplicaSet back up. I reach for a StatefulSet when pods need sticky identity and their own volumes — like a database."
