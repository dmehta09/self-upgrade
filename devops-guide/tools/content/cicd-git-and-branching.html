Git & branching.

Git is the single source of truth for your code — and increasingly your infra too. How you branch decides how fast you can ship: short-lived branches feed CI, long-lived ones starve it. This is the workflow interviewers probe first.

01 Git as the source of truth

Git records every change as an immutable commit on a branch; main is the authoritative state of the product. The branching model you pick is a contract for how work merges back — and it directly enables or sabotages continuous integration.

Two models dominate interviews: trunk-based development (short-lived branches, merge to main at least daily) and GitFlow (long-lived develop/release/feature/hotfix branches). The right answer is almost always "trunk-based for a service that ships continuously."

In plain English analogy

Trunk-based is everyone editing one shared Google Doc with small, frequent saves — you see each other's changes constantly, so conflicts are tiny. GitFlow is everyone emailing versioned copies of the document around and merging them at release time — fine for shipping a boxed product on a schedule, but a recipe for "merge hell" when ten people each hoarded changes for weeks.

Commit
An immutable snapshot with a SHA, author, and parent — the unit of history.
Branch
A movable pointer to a commit. Cheap to create; the question is how long it lives.
Trunk / main
The shared, always-releasable line everyone integrates into.
Feature flag
A runtime toggle that hides unfinished work, so you can merge to main before the feature is user-ready.

02 Trunk-based vs GitFlow

Trunk-based: branch off main, do a day's work, open a small PR, merge — unfinished features hide behind feature flags. GitFlow: parallel long-lived branches with a heavier merge ritual, suited to versioned or desktop releases.

GitFlow — heavyweight
  • Long-lived develop, release/*, feature/*, hotfix/*.
  • Integrate rarely → big, painful merges.
  • Good fit: versioned/desktop products, multiple supported releases.
  • Fights CI: main isn't continuously integrated.
Trunk-based — default for services
  • Short-lived branches; merge to main ≥ daily.
  • Tiny PRs, fast review, fewer conflicts.
  • Unfinished work behind feature flags.
  • Feeds CI/CD — every merge is releasable.

Common trap gotcha

Long-lived branches cause merge hell and quietly defeat CI: if you don't integrate for two weeks, CI was only ever testing your island, not the real combined state. The whole point of CI is integrating continuously — a three-week feature branch is integrating occasionally. Keep branches under a day or two and hide incomplete work behind flags.

03 Merge vs rebase

Merge joins two branches with a merge commit — true history, but a tangled graph. Rebase replays your commits on top of the latest main — a clean, linear history. The iron rule: never rebase a shared/pushed branch, because it rewrites commits others already have.

Pro tip tip

Most teams enforce a squash-and-merge on PRs: rebase/clean up locally, then squash the PR into one tidy commit on main. You get a linear, readable history on the trunk without anyone ever rebasing a branch others depend on.

04 PR workflow, tags & repo shape

Changes reach main through a pull request gated by required reviews and status checks (CI must be green). Releases are cut by tagging a commit with a semantic version. And you'll be asked: monorepo or polyrepo?

1

Open a PR

Small diff off a short-lived branch. Branch protection blocks direct pushes to main.

2

Required checks

At least one approving review + green CI status checks before the merge button unlocks.

3

Merge to main

Squash-merge keeps history clean; main stays releasable.

4

Tag the release

Tag the commit v2.3.0; that tag (an immutable pointer) is what you build and ship.

Semantic versioning is MAJOR.MINOR.PATCH: bump MAJOR for breaking changes, MINOR for backward-compatible features, PATCH for fixes. A Git tag marks the exact commit a version was cut from — reproducible and traceable.

release.sh
git checkout main && git pull
git tag -a v2.3.0 -m "release 2.3.0"   # annotated tag on this commit
git push origin v2.3.0                # pushing the tag triggers the release pipeline

You've pushed feature/login, two teammates branched off it, and now you git rebase main and force-push it. What happens?

Right. Rebasing rewrites commits into new SHAs. Anyone who already based work on the old commits is now diverged from a history that vanished. Rebase only un-pushed, private branches; for shared branches, merge instead.

05 Interview rapid-fire

Trunk-based vs GitFlow — which do you use and why?core
Model answer

For a service that ships continuously, trunk-based: short-lived branches merged to main at least daily, with unfinished work behind feature flags. It keeps PRs small, conflicts tiny, and — crucially — actually delivers on CI, because the team integrates continuously instead of occasionally. GitFlow's long-lived develop/release/feature/hotfix branches make sense for versioned or desktop products that support multiple releases at once, but for a web service they cause merge hell and slow delivery.

Say it out loud say it

"Trunk-based for anything we ship continuously — short branches, merge daily, hide unfinished work behind flags so CI tests the real combined state. GitFlow only for versioned products with multiple supported releases."

Follow-ups to expect
  • How do you ship half-finished work safely? (Feature flags / dark launches.)
  • What enforces small, integrated changes? (Branch protection + required green CI on every PR.)
Merge vs rebase — when do you use each?core
Model answer

Rebase to tidy your own un-pushed branch — replay your commits onto the latest main for a clean, linear history before opening the PR. Merge to integrate shared branches; it preserves the real history and never rewrites commits others hold. The hard rule is never rebase a branch that's been pushed and that others have based work on, because rewriting those commits' SHAs breaks everyone's history. In practice: rebase locally, squash-merge the PR.

Say it out loud say it

"Rebase my own local branch for a clean linear history; merge to bring shared branches together. Never rebase a pushed shared branch — it rewrites SHAs and breaks everyone who pulled it."

How do you cut a release? (tags + semver)stretch
Model answer

Pick the releasable commit on main and create an annotated Git tag with a semantic version — MAJOR.MINOR.PATCH: MAJOR for breaking changes, MINOR for new backward-compatible features, PATCH for fixes. Pushing the tag triggers the release pipeline, which builds and ships the artifact for that exact commit. Because the tag is an immutable pointer to one SHA, every release is reproducible and traceable, and a rollback is just deploying the previous tag's artifact.

Say it out loud say it

"Tag the commit on main with a semver — major for breaking, minor for features, patch for fixes. Pushing the tag fires the release pipeline, and because the tag pins one SHA, every release is reproducible and rollback is just the prior tag."
