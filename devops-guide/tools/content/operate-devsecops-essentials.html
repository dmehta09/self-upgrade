DevSecOps essentials.

Security isn't a gate at the end — it's baked into the pipeline. Scan early, store secrets safely, grant least privilege, and prove what you ship — so vulnerabilities die in CI, not in a breach report.

01 Shift-left security

"Shift left" means moving security checks earlier — into the developer's PR and the CI run — instead of a security review the week before launch. The earlier a flaw is caught, the cheaper and safer it is to fix.

It's the same logic as CI testing: a vulnerable dependency flagged on the PR is a one-line bump; the same flaw found in prod is an incident, a patch scramble, and maybe a disclosure.

In plain English analogy

Shift-left is catching contraband at the factory door, not at the airport gate. Screening every part as it enters the assembly line is cheap and routine; discovering a smuggled bomb in a finished plane full of passengers is a catastrophe. Earlier is cheaper and safer.

02 Secrets management

Secrets never belong in Git or in an image. Store them in a vault — AWS Secrets Manager / SSM Parameter Store or HashiCorp Vault — and inject them at runtime. Better still: skip long-lived keys entirely with short-lived credentials via OIDC.

Anti-pattern
  • AWS keys hardcoded in source.
  • .env baked into the image layers.
  • Long-lived AWS_SECRET_ACCESS_KEY in CI.
  • Same static key, shared, never rotated.
Better
  • Secrets in Secrets Manager / Vault.
  • Injected at runtime, never built in.
  • CI assumes an IAM role via OIDC.
  • Short-lived, auto-expiring, auto-rotated.

Short-lived creds shrink the blast radius: an OIDC-issued token expires in minutes, so a leak is worthless within the hour. A static key is valid until a human remembers to rotate it — which is to say, often never.

Common trap gotcha

A secret committed to Git lives in history forever — deleting it in the next commit does nothing; it's still in the log and every clone. Rotate it immediately (assume it's compromised), then purge history. Don't just git rm and hope.

03 Least privilege & scanning

Two foundations that limit damage: grant only the permissions actually needed, and let machines find known vulnerabilities for you — and block on the bad ones.

Least privilege
Every identity gets the minimum it needs — scoped IAM policies, K8s RBAC roles, one role per workload. A compromised component can only reach what its role allows.
Dependency / image scanning
Trivy, Grype, and npm audit / pip audit match your packages and image layers against CVE databases.
Policy that blocks
Critical findings fail the build, not just print a warning. Lower severities can warn-and-track.
.github/workflows/scan.yml
- name: Scan image with Trivy
  uses: aquasecurity/trivy-action@v0
  with:
    image-ref: myapp:${{ github.sha }}
    severity: CRITICAL,HIGH
    exit-code: "1"        # fail the build on a hit
    ignore-unfixed: true  # don't block on CVEs with no patch yet
Common trap gotcha

A scanner that only warns and never blocks gets ignored — the warnings scroll past in green builds and rot. If a finding can't fail the build, it isn't a control, it's noise. Pick a severity threshold that blocks, and tune false positives via an allowlist rather than disabling the gate.

04 Supply-chain security

You don't just ship your code — you ship every dependency and base image too. Supply-chain controls answer "what exactly is in this artifact, and can I prove it's the one we built?"

SBOM
Software Bill of Materials — a manifest of every component/version in the artifact (formats: SPDX, CycloneDX). When the next Log4j drops, you grep the SBOM instead of guessing.
Signing
Cryptographically sign artifacts (Sigstore / cosign) so deploy can verify "this image came from our pipeline, untampered."
Provenance (SLSA)
Tamper-evident proof of how/where an artifact was built — which commit, which builder.
Pin by digest
Reference images by immutable @sha256:… digest, not a moving tag like latest.
Common trap gotcha

The latest tag is an unpinned supply-chain risk: it's mutable, so the bytes behind it can change under you — two deploys of "latest" can run different (or compromised) images, and rollback becomes guesswork. Pin by digest so what you tested is exactly what runs.

Why pin a base image by its @sha256: digest instead of the latest tag?

Right. A tag is a movable pointer; a digest is a content hash. Pinning the digest means a poisoned upstream "latest" can't silently swap your base image, and a rebuild produces the same artifact.

05 Interview rapid-fire

Where do secrets belong, and why prefer short-lived credentials?warm-up
Model answer

In a secrets manager — AWS Secrets Manager/SSM or Vault — injected at runtime, never in Git or baked into an image. Prefer short-lived creds (OIDC-issued tokens, IAM role assumption) over long-lived keys because they auto-expire: a leaked token is worthless within minutes, while a static key stays valid until someone remembers to rotate it.

Say it out loud say it

"Secrets live in a vault, injected at runtime — never in Git or an image. And I'd rather hand out tokens that expire in minutes than keys that live forever and have to be rotated."

How do you secure a CI/CD pipeline?core
Model answer

Layer controls by stage: secret scanning on commits; dependency + image scans in CI that block on critical CVEs; no long-lived cloud keys — the pipeline assumes a least-privilege IAM role via OIDC; then generate an SBOM, sign the artifact (cosign), and deploy only verified, digest-pinned images. The theme is shift-left plus least privilege at every step.

Say it out loud say it

"Scan early and block on criticals, give the pipeline a scoped OIDC role instead of static keys, and sign what you ship so deploy only runs verified, digest-pinned images."

Follow-ups to expect
  • What if a critical CVE has no fix yet? (Ignore-unfixed so it doesn't block forever, but track it and add a compensating control.)
  • How do you stop the pipeline itself from being the weak link? (Least-privilege runners, pinned action versions by SHA, protected branches and required reviews.)
What's an SBOM, and why sign artifacts?stretch
Model answer

An SBOM (SPDX/CycloneDX) is an ingredient list of every component and version in an artifact — so when the next critical CVE drops, you query the SBOM to find what's affected instead of guessing. Signing (Sigstore/cosign) cryptographically proves the artifact came from your pipeline untampered; deploy verifies the signature so a swapped or poisoned image is rejected. Together with SLSA provenance, that's supply-chain integrity.

Say it out loud say it

"An SBOM is the ingredient list — when the next Log4j hits I grep it instead of guessing. Signing proves the image is ours and untampered, so deploy only trusts what our pipeline actually built."

A key leaked in a public repo — what limits the blast radius?core
Model answer

First, rotate/revoke it immediately — assume it's already scraped (bots watch public GitHub in seconds). What limits the damage beforehand: least privilege (the key could only touch its narrow scope), short-lived OIDC creds (so there's no long-lived key to leak in the first place), and secret scanning that blocks the commit. Then purge the history and audit for misuse.

Say it out loud say it

"Rotate it now — assume it's already stolen. The real blast-radius limiter is upstream: least privilege so the key barely could do anything, and short-lived creds so there's no permanent key to leak at all."
