Continuous delivery.

CI ends with a tested artifact. Continuous delivery is everything after: that one artifact is promoted through environments — same bytes, different config — until it's sitting on the loading dock, ready to ship the instant a human says "go."

01 Delivery vs deployment

Continuous delivery = every green build is automatically packaged and always ready to release; a human approves the prod push. Continuous deployment = that final push is automatic too — green reaches prod with no gate.

The pipeline is identical up to the last step. Delivery keeps a human in the loop for the production release; deployment removes that click. The difference is one approval, not one technology.

In plain English analogy

Delivery = the package is boxed, labelled, and sitting on the loading dock — it ships the second someone says "go." Deployment = the package ships itself automatically the moment it's boxed, no one waiting at the door.

Continuous delivery
  • Auto-built, auto-tested, auto-staged.
  • Always releasable at a button press.
  • Human approves the prod release.
  • Fits regulated/high-blast-radius systems.
Continuous deployment
  • Everything above, plus auto-release.
  • Green commit → prod, no manual gate.
  • Needs strong tests + safe rollout (canary).
  • Highest velocity; demands confidence.

02 Promote one artifact across environments

After CI, the same image walks through dev → staging → prod, passing gates. You don't rebuild per environment — you promote the identical bytes and only swap config.

Same image
The artifact pinned by digest is byte-identical from staging to prod.
Different config
Per-environment env vars + secrets (DB URLs, keys) injected at deploy — pulled from SSM Parameter Store / Secrets Manager.
Gate
An automated check (tests, scan) and/or a manual approval that must pass to advance.
Common trap gotcha

Rebuilding the artifact for each environment breaks the core guarantee: "tested in staging == runs in prod." A fresh build can pull a newer base layer or dependency, so prod runs different bytes than you validated. Build once, promote the identical image — vary only config, never the binary.

03 Deploy is not release

Deploy = the new code is running on prod servers. Release = users can actually see it. A feature flag lets you deploy code "dark" and flip it on later — decoupling shipping risk from launch timing.

1

Deploy dark

The new version is live in prod but the feature is behind an off flag. Zero user impact.

2

Validate in prod

Enable for internal users / 1% of traffic. Real environment, tiny blast radius.

3

Release

Flip the flag to 100%. No redeploy — and if it misbehaves, flip it off instantly.

This is also your fastest rollback: toggling a flag is instant and reversible, whereas redeploying the previous artifact takes a full pipeline cycle. Keep the prior image one promotion away so a code rollback is also quick.

Pro tip tip

Rollback readiness is a feature, not an afterthought. Always be able to answer "how do we undo this in 60 seconds?" — usually a flag flip, or re-promoting the last known-good digest.

You merged a risky feature and it's now running in production behind an off feature flag. Has it been released?

Right. Deploy and release are separate events. The bytes are on prod (deployed), but the flag gates visibility (not released) — which is exactly what lets you ship continuously yet launch on your own schedule.

Model answer

Deploy = the new code is running on production infrastructure. Release = users can actually experience it. Decouple them with a feature flag: deploy dark (flag off), validate in prod on a sliver of traffic, then flip the flag to release. How do you promote one build across environments without rebuilding?stretch
Model answer

CI builds one image, tagged by commit SHA and pinned by digest. That same digest is deployed to dev, then staging, then prod — config (env vars + secrets from SSM/Secrets Manager) is injected per environment at deploy time. The binary never changes; only configuration does. That's what makes "passed in staging" a real guarantee for prod, and lets a rollback re-promote the last known-good digest.

Say it out loud say it

"Build once, pin the digest, promote the same image through every environment and inject config per env. The bytes are constant, so staging genuinely predicts prod — and rollback is just re-promoting the last good digest."
