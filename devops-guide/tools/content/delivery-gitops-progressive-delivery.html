Deploy strategies · GitOps

GitOps & progressive delivery.

Stop running kubectl apply from a laptop or a CI step holding cluster keys. With GitOps, a Git repo is the single source of truth for what should be running, and an in-cluster agent continuously makes reality match it.

01 What GitOps actually is

GitOps = Git holds the desired state of the cluster, and an in-cluster agent (Argo CD or Flux) continuously reconciles the live cluster to match it — auto-healing any drift. Deploys become git commits; rollbacks become git revert.

You never push to the cluster. You change a YAML manifest in Git; the agent notices the diff and applies it. The repo is your audit log, your rollback button, and your change-control all at once.

In plain English analogy

GitOps is a thermostat whose target temperature is a number written in a shared, version-controlled notebook. Change the notebook to 21°C and the room follows; cross it out and write 19°C back (a git revert) and the room cools again. If someone props a window and the room drifts, the thermostat quietly heats it back to the number in the book.

Desired state
Declarative manifests (Deployments, Services, Helm/Kustomize) committed to a config repo — the source of truth.
Reconcile loop
The agent constantly compares Git vs cluster and applies the diff until they match.
Drift / auto-heal
A manual kubectl edit in the cluster is drift; the agent reverts it back to what Git says.
Rollback
git revert the bad commit — the agent rolls the cluster back to the prior known-good state.

02 The reconcile loop

Commit to the config repo → the agent detects a diff → it syncs the cluster → cluster matches Git. Same loop catches and heals drift: tamper with the cluster directly and it gets pulled back.

Common trap gotcha

GitOps deploys but does not build — there's no compiler or test runner in the reconcile loop. You still need CI to build, test, and push the image; GitOps only syncs manifests. And secrets must never sit in Git in plaintext — use Sealed Secrets or External Secrets Operator so Git stores only an encrypted reference, not the real value.

03 Pull vs push delivery

Pull (GitOps): an agent inside the cluster pulls from Git — no external system holds cluster credentials. Push: CI reaches into the cluster with kubeconfig/keys and applies. Pull wins on security, audit, and drift; push wins on initial simplicity.

Higher credential exposure is worse; higher auditability, drift detection, and simplicity are better. The takeaway: pull trades a little upfront complexity for a much smaller attack surface and free drift-healing.

04 CI builds, GitOps deploys + progressive delivery

Clean division of labor: CI builds and pushes the image; it then writes the new image tag into the config repo. GitOps sees that commit and deploys it. Add Argo Rollouts / Flagger and the agent automates canary/blue-green with promotion gates.

The image registry and the config repo are the seam: CI owns everything left of "bump tag," GitOps owns everything right of it.

The boundary is sharp: nothing in the cluster builds code, and CI never touches the cluster directly. Argo Rollouts and Flagger extend GitOps to canary/blue-green — they shift traffic in steps, run an automated analysis at each step, and either promote or auto-roll-back.

In a GitOps setup, your CI pipeline finishes building and pushing a new image. What does it do next to get that image deployed?

Right. In pull-based GitOps, CI never touches the cluster. Its last act is to update the desired state in Git (bump the image tag); the in-cluster agent detects that diff and syncs. CI builds, Git records intent, the agent deploys — and the agent never builds anything.

05 Interview rapid-fire

What is GitOps, in one breath?warm-up
Model answer

GitOps means a Git repo holds the declarative desired state of your infrastructure, and an in-cluster agent like Argo CD or Flux continuously reconciles the live cluster to match it. You deploy by committing a manifest change, not by running commands at the cluster; the agent applies the diff and auto-heals any drift. Git becomes the audit log, change-control, and rollback button in one.

Say it out loud say it

"Git is the source of truth for what should be running, and an agent in the cluster constantly makes reality match Git. Deploys are commits, rollbacks are reverts, and drift gets healed automatically."

Push vs pull deployment — and why does pull win for prod?core
Model answer

In push, CI reaches into the cluster with stored credentials and runs kubectl/Helm — simple, but every runner is a path into prod and nothing watches for drift afterward. In pull (GitOps), an agent inside the cluster pulls from Git, so no external system holds cluster keys; Git history is a full audit trail and the agent continuously heals drift. Pull costs a bit more setup complexity but wins decisively on credential exposure, auditability, and drift detection — which is why it's the prod default.

Say it out loud say it

"Push means CI holds cluster keys and applies directly — easy but a bigger attack surface. Pull means an agent in the cluster syncs from Git, so no outside system needs credentials, you get a full audit trail, and drift self-heals."

Follow-ups to expect
  • Name the common pull-based tools. (Argo CD, Flux — both CNCF-graduated.)
  • How are secrets handled? (Sealed Secrets / External Secrets — never plaintext in Git.)
How do you roll back with GitOps, and how do CI and GitOps split responsibilities?stretch
Model answer

Rollback is git revert on the offending commit (or reset the manifest to the last good digest); the agent reconciles the cluster back to that state — same mechanism as a deploy, just pointed backward. On responsibilities: CI builds, tests, and pushes the image, then commits the new image tag into the config repo. GitOps watches that repo and deploys. Nothing in the cluster builds code, and CI never applies to the cluster directly — the registry and config repo are the clean seam between them. Add Argo Rollouts/Flagger and GitOps also drives canary/blue-green with automated analysis and promotion.

Say it out loud say it

"Rollback is just git revert — the agent syncs the cluster back. CI builds and pushes the image then bumps the tag in Git; GitOps deploys from Git. CI never touches the cluster, and the cluster never builds."

Follow-ups to expect
  • What automates progressive delivery here? (Argo Rollouts / Flagger — stepped traffic + automated analysis.)
  • What does the agent NOT do? (Build, test, or run pipelines — that's CI's job.)
