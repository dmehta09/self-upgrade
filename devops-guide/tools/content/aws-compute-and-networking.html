AWS · compute & networking

Compute & networking.

EC2 instances are the raw compute; an Auto Scaling Group keeps the right number of healthy ones; a load balancer fans traffic to them; and a VPC is the private network they all live in. This is the backbone every AWS architecture question circles back to.

01 EC2: instances, AMIs & families

An EC2 instance is a virtual server you rent by the second. You boot it from an AMI (a machine image — OS + your baked-in software) and pick an instance type from a family sized for your workload.

Families map to a shape: t/m general-purpose, c compute-heavy, r/x memory-heavy. Each comes in Graviton (ARM) variants — AWS's own silicon that's typically ~20% cheaper for the same throughput.

In plain English analogy

A VPC is your own gated neighbourhood: public-facing shops sit on the street (public subnets), private back-offices sit behind the gate (private subnets), and the front gate (the Internet Gateway) is the only way in or out. An Auto Scaling Group is the shift manager who hires more workers when the queue grows, sends them home when it's quiet, and instantly replaces anyone who quits mid-shift.

Instance
A running virtual machine. Billed per second; stop it and you stop most of the bill.
AMI
The image it boots from — OS plus pre-installed software. Bake one in CI so every instance starts identical.
Family / size
Shape (t, m, c, r) × size (large, xlarge…). Match it to CPU-vs-memory needs.
Graviton (ARM)
AWS ARM CPUs — best price/perf for most modern, recompiled workloads. Default to it unless something needs x86.
Pro tip tip

Don't hand-build "pet" servers. Bake an AMI (or use a container image) so an instance is disposable — the ASG can replace it from the same image with zero ceremony. Cattle, not pets, applies to VMs too.

02 Auto Scaling Groups & load balancers

An ASG keeps your fleet between min and max, tracking a desired count. Scaling policies grow or shrink it to match load, and it self-heals — a failed health check means the instance is killed and replaced automatically.

min / desired / max
Floor, current target, ceiling. The ASG never drops below min or above max.
Scaling policy
Add/remove instances on a signal — typically target tracking (e.g. hold CPU at 50%).
Self-healing
Unhealthy instance → terminated and replaced from the same launch template. No human paged.
Multi-AZ
Spread the ASG across Availability Zones so one AZ failing just means fewer healthy targets, not an outage.

In front of the fleet sits a load balancer. Pick by OSI layer:

ALB — Application LB (L7)
  • Understands HTTP/HTTPS.
  • Host- and path-based routing (/api → one target group, shop.example.com → another).
  • TLS termination, WebSockets, gRPC.
  • Default for web apps & microservices.
NLB — Network LB (L4)
  • Operates on TCP/UDP — no HTTP awareness.
  • Ultra-high throughput, very low latency, static IPs.
  • Preserves the client source IP.
  • For non-HTTP, extreme scale, or when you need a fixed IP.
Common trap gotcha

Single-AZ is not high availability. An ASG with min=2 in one Availability Zone still drops to zero when that AZ has an outage. HA means spreading instances across two or more AZs behind a load balancer that only routes to healthy targets.

03 VPC: subnets, routing & egress

A VPC is a private network defined by a CIDR block (e.g. 10.0.0.0/16), carved into subnets across multiple AZs. Public subnets have a route to the Internet Gateway; private subnets do not — they reach the internet outbound only through a NAT gateway.

CIDR & subnets
The VPC owns an IP range; each subnet is a slice of it, pinned to one AZ. Spread subnets across AZs for HA.
Route table
Per-subnet rules for where traffic goes. Public = a 0.0.0.0/0 route to the IGW; private = no such route.
Internet Gateway
The VPC's bidirectional door to the internet. Public subnets route through it.
NAT gateway
Lets private subnets make outbound connections (pull packages, call APIs) without being reachable inbound.
Common trap gotcha

Two classics: (1) putting databases in public subnets — your RDS should sit in private subnets, reachable only from the app tier. (2) Forgetting NAT gateways cost real money — an hourly charge plus a per-GB data-processing fee on all egress. Heavy private-subnet egress (image pulls, S3 traffic) can quietly become a top line item; use VPC endpoints to keep AWS-bound traffic off the NAT.

04 Security groups vs NACLs

Two firewall layers. A security group wraps an instance/ENI and is stateful — allow traffic out and the reply is automatically allowed back. A NACL guards a whole subnet and is stateless — you must allow both directions explicitly.

Attaches toAn instance / ENIA subnet
StateStateful — return traffic auto-allowedStateless — allow each direction yourself
RulesAllow onlyAllow and deny
Everyday useYour primary control — 99% of the timeCoarse subnet-wide guardrail / explicit blocks

Mental model: the security group is the bouncer at each door who remembers who he let out; the NACL is the perimeter fence with a blunt allow/deny list and no memory.

Instances in a private subnet need to pip install from the public internet, but must never accept inbound connections from it. What do you add?

Right. A NAT gateway gives outbound-only internet access: private instances can initiate connections out, but nothing on the internet can initiate one in. Routing the private subnet to an IGW (or giving it public IPs) would expose it; opening a NACL does the opposite of what's asked.

05 Sizing the web tier

Interviewers love "how many instances?" The answer is back-of-envelope: turn users into peak QPS, divide by what one server handles, and round up. Drag the sliders to feel how traffic drives fleet size.

For ~2M daily users at 5 writes each with a 20:1 read:write ratio, average write QPS is small but reads dominate; multiplied by a peak factor this yields peak QPS, which divided by ~800 QPS per server gives the number of stateless app servers the ASG should target, plus a rough total-storage estimate.

Why it matters
That "servers" number is your ASG's desired count at peak; set max above it with headroom and min for a quiet floor.
Round up, add headroom
Never size to exactly 100% — instances die, AZs drain, deploys briefly double capacity. Target ~50–70% utilisation.

06 Interview rapid-fire

ALB vs NLB — when do you reach for each?warm-up
Model answer

The ALB is a Layer-7 (HTTP) load balancer: it routes by host and path, terminates TLS, and speaks WebSockets/gRPC — my default for web apps and microservices. The NLB is Layer-4 (TCP/UDP): no HTTP awareness, but extreme throughput, very low latency, static IPs, and it preserves the client source IP. I pick NLB for non-HTTP protocols, massive scale, or when I need a fixed IP.

Say it out loud say it

"ALB is Layer 7 — it routes on host and path and handles TLS, so it's my default for HTTP. NLB is Layer 4 — raw TCP at huge throughput with static IPs, for non-HTTP or extreme scale."

Public vs private subnet — what goes where, and why?core
Model answer

A public subnet has a route to the Internet Gateway; a private one doesn't. Internet-facing things go public — the load balancer, NAT gateways, bastions. Everything else goes private: app servers and especially databases. The app tier is reached only through the load balancer, and it gets outbound internet via a NAT gateway. Minimising public surface area is the whole point.

Say it out loud say it

"Only the internet-facing layer — the load balancer and NAT — lives in public subnets. App servers and databases stay private, reachable through the LB, with outbound via NAT. Smallest possible public surface."

Follow-ups to expect
  • Why is a public RDS a red flag? (No reason to expose your data store to the internet; it's a breach vector.)
  • What pins a subnet to one AZ? (A subnet lives in exactly one AZ — that's why HA needs subnets in several.)
How does an ASG give you both HA and self-healing?core
Model answer

Two mechanisms. Self-healing: the ASG watches health checks; a failing instance is terminated and a fresh one is launched from the same template — no human in the loop. HA: you spread the ASG across multiple AZs, so if one AZ fails, the others keep serving and the ASG launches replacements in the healthy AZs to restore desired capacity. Together: a node dying or an AZ dropping both self-correct.

Say it out loud say it

"It replaces unhealthy instances automatically from the launch template — that's self-healing. Span it across AZs and it survives an AZ outage too, relaunching capacity in the zones that are still up."

How do instances in a private subnet reach the internet?stretch
Model answer

Through a NAT gateway. The NAT lives in a public subnet (which routes to the IGW); the private subnet's route table sends 0.0.0.0/0 to the NAT. That gives outbound-only access — instances can call out, but nothing inbound can reach them. It costs an hourly fee plus per-GB processing, so for AWS-bound traffic (S3, ECR) I'd add VPC endpoints to bypass the NAT and save money.

Say it out loud say it

"A NAT gateway gives private instances outbound-only internet — they can initiate connections out, nothing can reach in. It's not free, so I route AWS traffic through VPC endpoints to cut the NAT bill."
