The delivery lifecycle & toolchain.

A change flows down one conveyor — plan → code → build → test → release → deploy → operate — and the build produces one artifact that is promoted, unchanged, all the way to production.

01 One conveyor, seven stages

The lifecycle is a pipeline: each stage adds something and hands a standard part to the next. The golden rule — build once, promote the same artifact everywhere.

You don't recompile per environment. CI builds a versioned image; staging and prod run those exact bytes. That's what makes "tested in staging" actually mean "this will behave in prod."

In plain English analogy

Think of a car assembly line. Each station bolts on one part and passes a standard chassis down the belt. You'd never re-stamp the body at the paint station — same idea here: the artifact built at the start is the exact thing inspected and shipped at the end.

02 What each stage does

Two halves: the left side (plan→test) is mostly developer flow and CI; the right side (release→operate) is delivery and running the service. The handoff between them is the artifact.

Plan
Decide what to build — issues, tickets, design. The backlog feeds the conveyor.
Code
Write it; commit to a branch; open a pull request against main.
Build
Compile and package into a deployable unit — typically a container image.
Test
Lint, unit, integration. This is the gate: red blocks the merge.
Release
Cut a version and decide it's eligible to ship (tag, changelog, approval).
Deploy
Put that version on infrastructure — to staging, then production.
Operate
Run it, respond to incidents, and feed what you learn back into Plan.
Heads up scope

The telemetry behind "Operate" — metrics, traces, dashboards, SLO burn-rate alerts — lives in the companion Observability guide. Here we cover the DevOps side: pipelines, infra, deploys, and the human process.

03 The 2026 toolchain map

Don't memorize every product — memorize the categories and one or two AWS-first defaults per slot. Tools change; the shape of the pipeline doesn't.

Common trap gotcha

Two failure modes: tool sprawl (five overlapping CI systems nobody fully owns) and building the artifact differently per stage. If staging compiles its own image and prod compiles another, "tested == shipped" is a lie — you tested bytes that never reach production.

04 Why "build once" matters

An artifact is the single immutable output of the build — usually a versioned container image, tagged by commit SHA. It's the contract between CI and CD: CI produces it, CD only ever promotes it.

promote.sh
# Built ONCE in CI, tagged by commit:
IMG=123.dkr.ecr.us-east-1.amazonaws.com/api:git-9af2c1

# Staging and prod deploy the SAME digest — no rebuild:
kubectl set image deploy/api api=$IMG -n staging
kubectl set image deploy/api api=$IMG -n prod   # identical bytes
Rebuild per stage
  • Each env runs docker build again.
  • Base image or a dep drifted between builds.
  • Prod ships bytes nobody tested.
  • "Worked in staging" guarantees nothing.
Build once, promote
  • One image, tagged by SHA, in the registry.
  • Every env deploys the exact same digest.
  • Traceable: tag maps back to a commit.
  • Rollback = redeploy a previous tag.

Why build the deployable artifact exactly once and promote it, instead of rebuilding for each environment?

Right. Immutable promotion means "tested == shipped." Rebuilding lets a transitive dependency or base-image change sneak in, so prod runs something you never actually tested.

05 Interview rapid-fire

Walk me through your delivery pipeline.warm-up
Model answer

A push to Git fires a webhook to CI (GitHub Actions). CI checks out the commit, runs lint + tests, and on green builds one versioned image and pushes it to ECR. CD (Argo CD) then promotes that exact image through staging to prod. The same artifact rides the whole conveyor, and operating it feeds the next plan.

Say it out loud say it

"Git triggers CI, CI builds and tests and pushes one image to ECR, and CD promotes that exact image to staging then prod. Build once, promote the same bytes — so what we tested is what ships."

Where does Infrastructure as Code fit relative to CI/CD?core
Model answer

CI/CD ships the application artifact; IaC provisions and changes the infrastructure it runs on — VPCs, clusters, databases — as versioned code (Terraform, CloudFormation/CDK). They're parallel tracks that meet at deploy: the platform must exist (IaC) for the app (CI/CD) to land on. Both flow from Git and are reviewed like code.

Say it out loud say it

"CI/CD delivers the app; IaC delivers the infrastructure underneath it. Two pipelines, both from Git — IaC builds the runway, CI/CD lands the plane."

Follow-ups to expect
  • Same repo or separate? (Often separate — infra changes at a different cadence and blast radius.)
  • Terraform vs CloudFormation? (Cloud-agnostic + huge ecosystem vs AWS-native, no extra state to manage.)
What's an artifact, and why build it once?stretch
Model answer

An artifact is the single immutable output of the build — typically a versioned container image tagged by commit SHA, stored in a registry like ECR. You build it once so the exact bytes you tested are the bytes that deploy to every environment. Rebuilding per stage lets a base image or transitive dependency drift, which silently invalidates your tests and your rollback story.

Say it out loud say it

"The artifact is the immutable image we built and tested. We promote that same digest everywhere so prod runs exactly what we tested — and rollback is just redeploying a previous tag."
