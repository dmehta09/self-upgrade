Networking · CloudFront Domain 3 · High-performing

Put the edge in front of your origin.

CloudFront is AWS’s CDN: cache static (and some dynamic) content at edge locations, terminate TLS close to users, and shield origins. Pair with S3 (OAC), ALB, or custom origins — and remember edge performance ≠ origin Multi-AZ.

01 How CloudFront fits the request path

Viewer → edge (cache hit or miss) → optional regional edge cache → origin. Cache behaviors map path patterns to origins, TTLs, and viewer protocols.

In plain English analogy

CloudFront is a chain of neighborhood libraries. Popular books (static assets) sit on local shelves so readers don’t trek to the central archive (S3/ALB) every time. When someone needs a rare manuscript, the library fetches it once, maybe keeps a copy, and the archive still needs its own fire protection (Multi-AZ).

Origin
S3 bucket (REST via OAC), ALB/NLB, MediaStore, or custom HTTP origin.
Behaviors
Path → origin, allowed methods, cache policy, origin request policy, response headers.
Price classes / Anycast
Trade global footprint vs cost; still an edge network, not your VPC.

02 S3 origins the modern way

Use Origin Access Control (OAC) so the bucket stays private and only CloudFront can read it. Prefer OAC over legacy OAI. Don’t make the bucket public “for the CDN.”

Anti-pattern
  • Public S3 website endpoint as origin
  • Bucket policy allows *
  • Assuming CloudFront encrypts objects at rest for you without SSE settings
Exam default
  • Private bucket + OAC
  • Bucket policy allows only the distribution
  • HTTPS viewer policy; optional WAF / Shield on the distribution
Common trap gotcha

Caching authenticated or highly dynamic HTML by accident. Wrong cache policy can serve User A’s page to User B or stale API responses. Use managed cache policies thoughtfully; forward cookies/Authorization only when required, and prefer short TTLs or CachingDisabled for personalized paths. Invalidate sparingly — it’s not a deploy strategy.

03 Performance, security, and failover extras

CloudFront + WAF for L7 filters; Shield Standard included, Shield Advanced optional. Origin groups give primary/secondary origin failover. Lambda@Edge / CloudFront Functions for lightweight request surgery at the edge.

1

Static global

S3 + CloudFront + OAC; Route 53 alias to the distribution.

2

Dynamic web

CloudFront in front of Multi-AZ ALB; cache only /static/*.

3

Origin HA

Origin group failover + Multi-AZ origins; don’t pretend CDN replaces AZ design.

Global users download large static assets from S3. You must keep the bucket private and minimize origin load. Best design?

Right. CDN + private S3 via OAC is the standard secure, high-performing pattern. Public buckets fail Domain 1. DIY regional proxy fleets add ops without beating CloudFront for static.

For ALB/ASG origin tiers, see DevOps compute & networking.

04 Exam rapid-fire

Why put CloudFront in front of S3?warm-up
Model answer

Lower latency via edge caching, lower S3 request/data cost for hot objects, HTTPS at the edge, and the ability to keep the bucket private with OAC while still serving the world.

Say it out loud say it

"CloudFront caches at the edge, shields S3, and lets me keep the bucket private with OAC."

OAC vs making the bucket public?core
Model answer

OAC grants CloudFront permission to read a private bucket. Public buckets expose a bypass path around the CDN and fail least-privilege design — avoid unless a rare public-website constraint forces it.

Say it out loud say it

"Private bucket plus OAC — never open the bucket just to feed CloudFront."

Does CloudFront replace Multi-AZ for an ALB origin?stretch
Model answer

No. Cache hits may mask origin issues briefly, but misses and dynamic paths still need a Multi-AZ origin. Use origin failover groups for coarser origin outages, plus Multi-AZ behind each origin.

Say it out loud say it

"CDN is performance and shielding — the origin still needs Multi-AZ for real HA."
