Networking · endpoints & PrivateLink Domain 1 · Secure

Stay private to AWS — and cut the NAT bill.

VPC endpoints keep traffic to AWS services on the Amazon network without IGW/NAT. Gateway endpoints cover S3 and DynamoDB; interface endpoints (PrivateLink) bring many APIs into your subnets as ENIs. PrivateLink also exposes your own services to other VPCs without peering.

01 Why endpoints show up constantly

Exam stems that say no internet, private only, or reduce data transfer/NAT cost almost always want VPC endpoints — not “add a NAT and open 443 everywhere.”

In plain English analogy

Without endpoints, private apps leave campus through the highway tollbooth (NAT) just to visit the company warehouse next door (S3). A gateway endpoint is a private service road to that warehouse — no toll, no public highway. PrivateLink is a secure loading dock you can offer to partner campuses without merging entire road networks (peering).

  nat --> s3public[S3_public_endpoint]
  app -->|good_path| gw[Gateway_endpoint]
  gw --> s3priv[S3_via_AWS_network]

02 Gateway vs interface endpoints

Gateway endpoints: S3 & DynamoDB only — route-table targets, no ENI hourly charge. Interface endpoints: PrivateLink ENIs in your subnets — security groups, DNS private names, hourly + data processing charges.

Common trap gotcha

Forgetting the route / DNS. Gateway endpoints only work for associated route tables — miss a private subnet and that subnet still hairpins via NAT. Interface endpoints need private DNS (or custom DNS) so SDKs resolve to the ENI, not the public service address. Also: endpoint policies can deny what IAM allows — both must permit.

03 PrivateLink for your services

Expose an NLB-fronted service via an endpoint service; consumers create interface endpoints in their VPCs. No overlapping CIDR fights, no transitive peering mess — ideal for SaaS-to-customer private connectivity.

Choose PrivateLink when
  • Many consumer VPCs need one producer service
  • CIDRs overlap (peering impossible)
  • You want consumers to only reach one service, not the whole VPC
Choose peering / TGW when
  • Broad many-to-many VPC connectivity
  • Shared whole network segments
  • Hybrid with on-prem at scale (TGW)

Private EC2 instances pull objects from S3. Security requires no internet gateway path, and finance wants to minimize NAT charges. Best fit?

Right. S3 supports gateway endpoints — the cost- and privacy-friendly default. Don’t attach IGW to “private” subnets. (S3 also has interface endpoints in some designs, but gateway is the classic exam answer for private + cheap.)

04 Exam rapid-fire

Which services get gateway endpoints?warm-up
Model answer

Amazon S3 and DynamoDB. Everything else that supports PrivateLink uses interface endpoints.

Say it out loud say it

"Gateway endpoints: S3 and DynamoDB. Other AWS APIs use interface PrivateLink endpoints."

PrivateLink vs VPC peering — elevator pitch?core
Model answer

Peering connects CIDR networks (non-overlapping) for broad connectivity. PrivateLink exposes a specific service via ENIs — works with overlapping CIDRs and minimizes blast radius to one service.

Say it out loud say it

"Peering joins networks; PrivateLink publishes one service privately — better for overlapping CIDRs and least exposure."

How do endpoint policies interact with IAM?stretch
Model answer

Both must allow. An endpoint policy can restrict which principals/buckets are reachable through that endpoint even if IAM is broader — defense in depth for private S3 access paths.

Say it out loud say it

"IAM and the endpoint policy are an AND — either deny blocks the call."
