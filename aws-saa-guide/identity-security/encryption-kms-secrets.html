Encryption, KMS & secrets.

Encrypt data at rest and in transit; keep keys in KMS; keep credentials in Secrets Manager or SSM — never in code. Exam scenarios mix SSE-S3 vs SSE-KMS, CMK key policies, and rotation.

01 KMS mental model

KMS manages cryptographic keys. You rarely encrypt big blobs with KMS directly — services use envelope encryption: a data key encrypts the object; KMS encrypts the data key.

In plain English analogy

Think of a locked filing cabinet (your S3 object) and a small key in a sealed envelope (the data key). KMS is the vault that opens that envelope. You don’t ship the vault key around — you ask the vault to unwrap the small key when the IAM principal is allowed.

Acme tickets
S3 objects use SSE-KMS with a CMK so CloudTrail shows who decrypted ticket PDFs. IAM + key policy both must allow.
Ledger Co
RDS password in Secrets Manager with rotation; app role fetches at runtime. No passwords in images or Git.
AWS owned / managed / CMK
Owned = least control. Managed (aws/s3, …) = visible, AWS rotates. CMK = you own key policy — exam favorite for “control who decrypts.”
CloudHSM / external key store
When compliance demands HSM or keys outside AWS — rare on SAA but know it exists.

In transit: TLS everywhere — ALB/NLB listeners, CloudFront, API Gateway, VPC endpoints. Prefer HTTPS-only bucket policies and HSTS at the edge.

Common trap gotcha

For CMKs, both the caller’s IAM policy and the KMS key policy must allow kms:Decrypt / GenerateDataKey. Fixing only IAM is a classic “AccessDenied on KMS” failure — same pattern as S3 bucket policies. Same dual-permission pattern shows up on S3 bucket policies — see S3 access.

03 Secrets Manager vs Parameter Store

Secrets Manager
  • Built for credentials & API keys
  • Automatic rotation (Lambda rotators, RDS integration)
  • Cross-account sharing patterns
  • Higher per-secret cost
SSM Parameter Store
  • Config + simple secrets (SecureString + KMS)
  • Hierarchical paths, cheap standard params
  • No built-in rotation like Secrets Manager
  • Great for non-secret config flags

Apps retrieve secrets at runtime with their IAM role — never bake DB passwords into images. Prefer PrivateLink / VPC interface endpoints so secret fetches never need a NAT path to the public API (PrivateLink mindset).

Compliance requires annual automatic rotation of a database password and an audit trail of decrypts. Best pair?

Right. Secrets Manager owns rotation; KMS CMKs give decrypt audit via CloudTrail. Env vars and non-secure strings fail both requirements.

04 Interview rapid-fire

SSE-S3 vs SSE-KMS — when do you pick KMS?core
Model answer

SSE-S3 encrypts with AWS-managed S3 keys — simple and fine for many workloads. Choose SSE-KMS when you need a customer-managed key policy, separate IAM grants for decrypt, CloudTrail visibility into key use, or cross-account decrypt control.

Say it out loud say it

"SSE-S3 for simple at-rest encryption. SSE-KMS when I need key policy control and an audit trail of who decrypted."

Where do DB credentials live?warm-up
Model answer

In Secrets Manager (preferred when rotation matters) or SSM SecureString. The app reads them via its role at runtime. KMS encrypts the secret storage. Never commit secrets or put long-lived IAM keys next to them.

Say it out loud say it

"Secrets Manager with rotation, fetched through the task or instance role — KMS underneath, nothing in Git."

What is envelope encryption?stretch
Model answer

A data key encrypts the payload; KMS encrypts that data key. You store ciphertext + encrypted data key together. Performance stays high because bulk crypto is local; KMS only wraps/unwraps small keys and enforces policy.

Say it out loud say it

"Data key locks the file; KMS locks the data key. That’s envelope encryption — scale without calling KMS for every byte."
