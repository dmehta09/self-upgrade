IAM users, roles & policies.

Who can call which API on which resource. SAA-C03 defaults (Sep 2026): roles + short-lived credentials, not long-lived access keys; humans via Identity Center; workloads via instance profiles, task/execution roles, or OIDC.

01 Users, groups, roles — pick the right principal

An IAM user is a long-lived login (password and/or access keys). A role is assumed and yields temporary credentials. A group only bundles policies for users — never grant “everyone” with wildcard principals.

In plain English analogy

A role is a visitor badge that unlocks specific rooms for the next hour, then expires. A long-lived access key is a permanent master key — if it leaks into Git or a log, it keeps working until someone notices. Hand out badges, not master keys.

Prefer (2026 default)
  • IAM roles for EC2, Lambda, ECS tasks, EKS pods
  • Identity Center for humans (SSO)
  • OIDC federation for CI (GitHub Actions, etc.)
  • Cross-account assume-role with ExternalId when needed
Avoid on the exam
  • Long-lived IAM user access keys in apps
  • Sharing one IAM user across a team
  • Action: "*" + Resource: "*" “for now”
  • Embedding keys in AMIs, Lambda env, or Docker images

Related in this guide: S3 access and KMS & secrets.

02 Policies: identity, resource & ceilings

Permissions are JSON. Evaluation is not “any Allow wins” — explicit Deny always wins, then Allow must grant the action, and org ceilings (SCPs) or permission boundaries can still block.

flowchart TD
  request["API request"] --> deny{"Explicit Deny?"}
  deny -->|yes| blocked["Denied"]
  deny -->|no| scp{"SCP and boundary allow?"}
  scp -->|no| blocked
  scp -->|yes| idPol{"Identity policy Allows?"}
  idPol -->|no| blocked
  idPol -->|yes| resPol{"Resource policy OK?"}
  resPol -->|no| blocked
  resPol -->|yes| allowed["Allowed"]
Identity policy
On the user/group/role — “what this principal can do.”
Resource policy
On the resource (S3 bucket, KMS key, SQS) — “who can access me,” including other accounts.
Permission boundary
A ceiling: the max a role/user can ever receive — used to safely let teams create roles.
Session policy
Extra shrink-wrap when you assume a role (STS) — can only reduce permissions.
least-privilege.json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "ReadOneBucket",
    "Effect": "Allow",
    "Action": ["s3:GetObject"],
    "Resource": "arn:aws:s3:::acme-invoices/*",
    "Condition": {
      "StringEquals": { "aws:RequestedRegion": "us-east-1" }
    }
  }]
}

Scope Action and Resource; add Condition keys (aws:SourceVpce, MFA, tags) when the scenario demands it.

Common trap gotcha

Trust policy ≠ permissions policy. Trust says who may assume the role. Permissions say what the session can do. Cross-account access fails when people only edit one of them.

03 Workload credentials without keys

Apps never store access keys. The host or platform hands them a role; the SDK fetches short-lived creds and refreshes them.

EC2
Instance profile → role; SDK pulls rotating creds from IMDS. Prefer IMDSv2.
Lambda / ECS
Execution / task role attached at deploy — no keys in env.
EKS
Pod Identity or IRSA maps a service account to an IAM role.
CI/CD
OIDC → assume role with web identity; no static AWS_SECRET_ACCESS_KEY for AWS auth.

An app on EC2 must read from one S3 bucket. What is the SAA-correct design?

Right. Roles via instance profiles are the default. Long-lived keys and public buckets are exam distractors — and real-world anti-patterns.

04 Worked: three mini-stems

Underline the who (human, EC2, CI, other account), then pick role + trust. Kill long-lived keys unless the stem forces a legacy exception.

1

Stem · EC2 → S3

Constraint: app on EC2 reads one bucket. Kill IAM user keys in /etc/environment. Kill public bucket. Answer: instance profile + role with s3:GetObject on that ARN.

2

Stem · GitHub OIDC

Constraint: GitHub Actions must deploy to an account; no long-lived keys in secrets. Kill static access keys. Kill shared IAM user. Answer: OIDC identity provider + role trust for the repo; workflow assumes the role.

3

Stem · cross-account

Constraint: Account A app reads a bucket in Account B. Kill “copy keys between accounts.” Kill only editing the bucket policy. Answer: role in B with trust for A (+ ExternalId if third party); permissions on the role and bucket policy allowing that role.

05 Exam rapid-fire

User vs role — when is each correct?core
Model answer

Prefer roles for anything that needs AWS API access: workloads, federation, cross-account. Humans should use Identity Center. Roles issue temporary STS credentials that expire automatically. Long-lived user keys in apps are an anti-pattern.

Say it out loud say it

"Roles over users — temporary badges, not master keys. EC2 uses instance profiles, CI uses OIDC. No long-lived keys in apps."

How does IAM evaluate Allow vs Deny?core
Model answer

Default deny. An explicit Deny in any applicable policy wins. Otherwise every layer that applies (SCP, permission boundary, identity policy, and resource policy when relevant) must Allow. That is why an Allow in a role can still fail under a Deny SCP.

Say it out loud say it

"Explicit Deny always wins. Then SCPs and boundaries can still cap you. Allow alone in the role is not enough if the org or resource policy blocks it."

What is a permission boundary for?stretch
Model answer

A permission boundary sets the maximum permissions an identity can ever have, even if someone attaches a broader policy. Use it when you let developers create roles safely without granting themselves full admin.

Say it out loud say it

"A boundary is a ceiling — the intersection of identity policies and the boundary is what actually applies. Perfect for delegated IAM."
