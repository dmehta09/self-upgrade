EC2, ASG & placement.

VMs when you need OS control. Sep 2026 defaults: Graviton where software allows, Multi-AZ ASGs, IMDSv2, instance profiles (no keys), and the right purchase model for steady vs spiky load.

01 Instance shape & Graviton

Pick family for the bottleneck (compute, memory, storage, GPU, network), then generation. Prefer Arm/Graviton (e.g. m7g, c7g) for better price-performance when binaries support it.

In plain English analogy

EC2 is renting a computer in someone else’s datacenter. An ASG is a smart fleet manager that keeps N healthy computers running and replaces dead ones. Graviton is choosing the more efficient engine that goes further on the same fuel — if your app can run on it.

AMI
Boot template (OS + baked config). Prefer hardened images; patch via SSM. ASG replacements must boot the same launch template/AMI.
Instance profile
Role for the instance — SDKs get temporary creds from IMDS. Prefer IMDSv2.
User data / launch templates
Bootstrap once; launch templates version ASG/Spot settings.
EBS vs instance store
EBS persists; instance store is ephemeral and fast — fine for caches, not sole source of truth.
Common trap gotcha

Stopping/starting a non-Elastic-IP public instance changes its public IPv4. Use Elastic IP or put instances behind an ALB/NLB and never teach clients a transient instance IP. Also: don’t store long-lived access keys on the box — use an instance role.

02 Auto Scaling groups

Exam stems expect an ASG that spans ≥2 AZs, replaces unhealthy targets, and scales on a metric (often target tracking). Know min / desired / max as floor / target / ceiling.

flowchart TD
  users[Users] --> alb[ALB]
  alb --> asg["Auto Scaling Group"]
  asg --> azA["Instances · AZ-a"]
  asg --> azB["Instances · AZ-b"]
  metrics["CPU / ALB / custom"] --> policy["Scaling policy"]
  policy --> asg
min / desired / max
Floor, current target, ceiling. Capacity never goes below min or above max.
Target tracking
Hold a metric near a goal (CPU or RequestCountPerTarget). Common “automatically maintain” answer on the exam.
Health checks
Behind an ALB, prefer ELB health so bad apps are replaced — not only EC2 status checks.
Multi-AZ
Required for AZ failure. min=2 in a single AZ is still an AZ outage.
Scale out when…
  • CPU / RequestCountPerTarget high
  • Queue depth (custom / SQS backlog)
  • Scheduled known peaks
Capacity types
  • On-Demand — baseline reliability
  • Spot — fault-tolerant, flexible workloads
  • Mixed instances — OD + Spot, multiple families

03 Placement & purchase trade-offs

Cluster placement group
Low latency / high PPS inside one AZ — HPC, tight chatter.
Spread placement group
Distinct hardware racks — reduce correlated failure (max constraints apply).
Partition placement group
Large distributed stores (Cassandra/Kafka-style) across partitions.
Dedicated Host / Instance
Licensing / compliance isolation — costlier.

A stateless web tier must survive an AZ outage and scale with traffic. Best compute pattern?

Right. Multi-AZ ASG + ALB is the resilient web pattern. Placement groups don’t span Regions; a single instance is an AZ SPOF.

04 Interview rapid-fire

Why Graviton on SAA scenarios?core
Model answer

AWS’s Arm-based instances usually deliver better price-performance for many general-purpose and compute workloads. Choose Graviton families when the OS/runtime supports Arm; fall back to x86 when binary dependencies block it.

Say it out loud say it

"Default to Graviton for cost-performance when the stack supports Arm — Savings Plans on the steady baseline."

ASG health check: ELB vs EC2?warm-up
Model answer

EC2 health means the hypervisor status check. ELB health means the load balancer’s target health (app actually answering). For web tiers behind ALB, use ELB health checks so bad apps get replaced, not just crashed kernels.

Say it out loud say it

"Behind an ALB I use ELB health checks — replace instances that fail the app probe, not only EC2 status checks."

Cluster vs spread placement?stretch
Model answer

Cluster packs instances close for network performance in one AZ. Spread separates instances across distinct hardware to reduce correlated failure. Don’t use cluster when your goal is HA across failures — use Multi-AZ ASG instead.

Say it out loud say it

"Cluster for latency HPC in one AZ; spread for anti-affinity; Multi-AZ ASG for real high availability."
