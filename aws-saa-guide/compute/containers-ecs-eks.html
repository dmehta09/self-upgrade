Containers: ECS vs EKS.

Run images from ECR on ECS (AWS-native) or EKS (managed Kubernetes). Default 2026 bias for AWS-only teams: ECS on Fargate + Graviton; choose EKS when you need the Kubernetes ecosystem or portability.

01 Shared building blocks

Both orchestrators schedule containers; neither replaces IAM. Tasks/pods get roles (task roles / IRSA / Pod Identity) — no long-lived keys in images.

In plain English analogy

ECS/Fargate is a fully staffed kitchen per dish — hand over the recipe, no kitchen to mop. EKS is your own restaurant franchise: AWS keeps the building standing (control plane), but you still run the kitchen workflows (Kubernetes). Lambda remains the food truck for short orders.

ECR
Private registry; image scanning; immutable tags; pull through task/execution roles.
Fargate
Serverless data plane for ECS or EKS — declare CPU/memory, no node patching.
EC2 launch type
You manage capacity (GPU, weird kernels, denser packing, Spot fleets).
Service discovery / LB
ALB/NLB target groups; Cloud Map; for EKS also Ingress/Gateway API.

02 ECS patterns

task-def-sketch.json
{
  "family": "web",
  "requiresCompatibilities": ["FARGATE"],
  "runtimePlatform": { "cpuArchitecture": "ARM64" },
  "cpu": "512", "memory": "1024",
  "taskRoleArn": "arn:aws:iam::123:role/web-task",
  "executionRoleArn": "arn:aws:iam::123:role/ecs-exec",
  "containerDefinitions": [{
    "name": "app",
    "image": "123.dkr.ecr.us-east-1.amazonaws.com/web:1.4.2",
    "portMappings": [{ "containerPort": 8080 }]
  }]
}
flowchart TD
  cicd[CI_OIDC] --> ecr[ECR]
  ecr --> svc[ECS_Service]
  svc --> fargate[Fargate_tasks_Multi_AZ]
  alb[ALB] --> svc
  svc --> role[Task_IAM_role]
  role --> s3[S3_Secrets_etc]
  • Service keeps desired task count; rolling / blue-green (CodeDeploy) deployments.
  • Execution role pulls images & writes logs; task role is what the app uses.
  • Prefer ARM64 / Graviton on Fargate for cost; Multi-AZ services behind ALB.
  • Private subnets + VPC endpoints (ECR, S3, Logs, Secrets) — PrivateLink mindset, less NAT.
Common trap gotcha

Mixing up execution role vs task role: if the app can’t read Secrets Manager, fix the task role; if the task can’t pull from ECR, fix the execution role. Same class of bug as IRSA misconfiguration on EKS.

03 EKS when — and identity

Pick ECS/Fargate when…
  • AWS-centric team, minimal K8s appetite
  • Want least ops for long-running services
  • Standard microservices + ALB is enough
Pick EKS when…
  • Need Helm, operators, CRDs, GitOps (Argo/Flux)
  • Multi-cloud / on-prem portability
  • Existing Kubernetes skills & platform

Pod AWS access: IRSA or EKS Pod Identity — map ServiceAccount → IAM role. Never mount access keys as Secrets for AWS API calls.

AWS-only team, steady APIs, no Kubernetes requirement, wants minimal node ops and lower compute cost. Best default?

Right. ECS+Fargate+Graviton matches AWS-native low-ops steady services. Single-AZ DIY K8s with baked keys fails HA and security; Lambda is a poor fit for always-on sockets.

04 Interview rapid-fire

ECS vs EKS in one breath?core
Model answer

Both run containers from ECR. ECS is AWS-native and operationally lighter. EKS gives the Kubernetes API and ecosystem at the cost of upgrades, add-ons, and expertise. Fargate can remove node management on either.

Say it out loud say it

"ECS if we just want containers on AWS with low ops; EKS if we need Kubernetes portability or its ecosystem."

Fargate vs EC2 launch type?warm-up
Model answer

Fargate: AWS owns the nodes — pay per task resources, no patching. EC2: you own the fleet — denser packing, GPUs, special AMIs, often cheaper at high steady utilization, more ops.

Say it out loud say it

"Fargate trades a bit of cost for zero node ops; EC2 launch type when I need control, GPUs, or denser bin-packing."

How do pods call S3 securely?core
Model answer

Use IRSA or EKS Pod Identity so the pod’s service account assumes a least-privilege IAM role and receives temporary credentials. Mirror of ECS task roles — never bake keys into the image.

Say it out loud say it

"IRSA or Pod Identity — service account maps to an IAM role, short-lived creds, no keys in the image."
