Storage · AWS Backup Domain 2 · Resilient · Domain 1 · Secure

One plan. One vault. Tested restores.

AWS Backup centralizes plans, vaults, and restores across EBS, EFS, RDS, DynamoDB, FSx, and more. On the exam, “centralized backup plan,” Vault Lock, or org backup account almost always means this service — not ad-hoc snapshot scripts.

01 The idea

A backup plan schedules what to protect; a vault holds recovery points; tags select targets. Restore (and cross-Region/account copy) is the other half of the story.

In plain English analogy

Think of a corporate records room. The plan is the clerk's schedule (“every night, copy these drawers”). The vault is the locked room where copies live. Vault Lock is pouring concrete over the lock — even the clerk can't shred tapes early.

flowchart TD
  tags["Tagged resources"] --> plan["Backup plan · schedule"]
  plan --> jobs["Backup jobs"]
  jobs --> vault["Backup vault"]
  vault --> restore["Restore recovery point"]
  vault --> copy["Copy · cross-Region or account"]
  copy --> lock["Optional Vault Lock · WORM"]

02 RPO mapping — three stories

RPO (how much data you can lose) drives backup frequency and continuous options. Map the resource type to what AWS Backup actually captures.

Acme · EBS volumes
RPO ≈ hours: nightly / hourly snapshot rules in the plan. Crash-consistent unless you quiesce the app. Pair with AMI strategy for boot volumes when rebuild speed matters.
Nova · RDS / Aurora
Tighter RPO: plan frequency plus service PITR where supported. Multi-AZ is HA for AZ failure — still keep backups for deletes, bad deploys, and ransomware.
Ledger · DynamoDB
On-demand / continuous backups via AWS Backup (and Dynamo PITR patterns). Global Tables are Region HA, not a substitute for immutable recovery points.

EBSHours (schedule)Volume / AMI recovery; tag → plan

03 Design checklist & immutability

Tag production, assign by tag, copy to a dedicated backup account, enable Vault Lock for WORM when compliance or ransomware is in the stem, and practice restores.

Ad-hoc
  • Manual EBS snapshots only
  • Different scripts per service
  • No cross-account isolation
AWS Backup
  • One plan across services
  • Tag-based assignment
  • Vault Lock + org copies
Common trap gotcha

Backup ≠ Multi-AZ. Multi-AZ keeps you up through an AZ failure. Backups (and locked cross-account vaults) undo deletes, corruption, and ransomware. Stem says “AZ failure / stay available” → HA; “deleted table / ransomware / immutable” → AWS Backup + Vault Lock.

Compliance requires immutable backups of RDS and EFS that attackers with admin in the app account cannot delete. Which feature matters most?

Right. Immutability + separation of duty → Vault Lock and/or cross-account copies. Multi-AZ is HA, not ransomware protection. Instance store is ephemeral.

04 Exam rapid-fire

What problem does AWS Backup solve?warm-up
Model answer

It centralizes backup plans, vaults, and restores across many AWS resource types so you apply one policy (tags, schedules, retention, copies) instead of per-service snapshot scripts.

Say it out loud say it

"One backup plan and vault across EBS, EFS, RDS — tag-based, with optional cross-Region copies."

Backup vs Multi-AZ vs cross-Region DR?core
Model answer

Multi-AZ = automatic failover for infrastructure failure in another AZ. Backups = recover from data corruption, deletes, ransomware. Cross-Region copies = Region-level disaster. Serious designs use HA and backups.

Say it out loud say it

"Multi-AZ keeps me up; backups undo bad data; cross-Region survives a Region event."

What is Vault Lock?stretch
Model answer

A configuration that makes recovery points in a backup vault WORM for a retention period — even privileged users can't delete early. Used for compliance and ransomware resilience, often with a separate backup account.

Say it out loud say it

"Vault Lock is WORM on the backup vault — retention you can't quietly erase."
