Databases · ElastiCache Domain 3 · High-performing

Cache the hot path. Keep the DB breathing.

ElastiCache is managed Redis / Valkey or Memcached in your VPC. Put it in front of RDS or DynamoDB for hot keys, sessions, and leaderboards — then invalidate carefully. The exam picks engine, HA, and ElastiCache vs DAX.

01 The idea

App asks the cache first (cache-aside). Hit → done. Miss → read the database, populate the cache, return. Stale data is a silent bug — TTL or explicit invalidate on write.

In plain English analogy

Your database is the library stacks. ElastiCache is the cart of popular books already pulled for today — grab in milliseconds. Update a title and you must refresh the cart, or readers see yesterday's edition.

flowchart TD
  req["App needs data"] --> cache{"In ElastiCache?"}
  cache -->|yes| hit["Cache hit · return"]
  cache -->|no| miss["Cache miss"]
  miss --> db["Read RDS or DynamoDB"]
  db --> fill["Write key into cache"]
  fill --> ret["Return to caller"]

02 Three stories that stick

Same product, three exam shapes: shared sessions, sorted-set leaderboards, and RDS read offload.

Acme tickets
Stateless web fleet behind an ALB. Sessions live in Multi-AZ Redis so any instance can serve any user — no sticky EBS on one host.
Nova games
Live leaderboard needs sorted sets and fast increments. Redis (or Valkey) wins; Memcached has no sorted sets.
Ledger Co
Product catalog reads hammer RDS. Cache-aside on hot SKUs cuts DB CPU; writes invalidate or short TTL so stock counts stay honest.
Redis / Valkey
  • Structures: strings, hashes, sorted sets, pub/sub
  • Replication + Multi-AZ failover
  • Cluster mode for scale-out
  • Sessions, leaderboards, queues-ish patterns
Memcached
  • Simple key/value only
  • Multithreaded horizontal scale
  • No rich structures / HA story like Redis
  • When you only need a dumb object cache

03 ElastiCache vs DAX

DAX is DynamoDB's own microsecond cache (Dynamo APIs). ElastiCache is a general Redis/Memcached tier you wire yourself in front of RDS, DynamoDB, or APIs.

Pick ElastiCache
  • RDS / Aurora / multi-backend caching
  • Redis features (sessions, sorted sets)
  • You control cache-aside and TTL
Pick DAX
  • DynamoDB-only access path
  • Want API-compatible acceleration
  • Microsecond eventually consistent reads
Common trap gotcha

ElastiCache is VPC-bound — private subnets, security groups only from the app tier. Caching does not replace Multi-AZ on the primary database for durability. Also: Memcached ≠ Redis sorted sets — stem says leaderboard → Redis.

Acme tickets needs shared sessions and a sorted-set leaderboard behind an ALB Auto Scaling group. Choose?

Right. Redis gives shared sessions and sorted sets. Memcached lacks those structures. Local EBS sessions break a stateless scale-out story.

04 Exam rapid-fire

Redis vs Memcached on ElastiCache?warm-up
Model answer

Redis / Valkey for rich structures, replication/failover, and advanced features. Memcached for simple, multithreaded key/value when you do not need those features.

Say it out loud say it

"Redis for features and HA; Memcached for simple horizontal key/value."

How do you keep the web tier stateless?core
Model answer

Move sessions into ElastiCache Redis so any instance behind the load balancer can serve any user. Pair with Auto Scaling — no dependency on one host's memory or disk.

Say it out loud say it

"Sessions in Redis, instances disposable — that's a stateless web tier."

ElastiCache vs DynamoDB DAX?stretch
Model answer

DAX is purpose-built for DynamoDB APIs. ElastiCache is a general cache you wire (cache-aside) in front of RDS, DynamoDB, or APIs. Pick DAX for seamless Dynamo microsecond reads; ElastiCache for Redis features or multi-backend caching.

Say it out loud say it

"DAX is Dynamo's own accelerator; ElastiCache is the general Redis/Memcached tier."
