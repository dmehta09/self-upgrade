RDS & Aurora high availability.

Managed relational engines with Multi-AZ failover, read replicas, and Aurora's shared storage. As of 2026, for spiky or unpredictable relational load, prefer Aurora Serverless v2 (ACUs) over older Serverless v1 thinking.

01 RDS vs Aurora

RDS runs engines (Postgres, MySQL, SQL Server, …) on managed instances with automated backups. Aurora is AWS's cloud-native MySQL/Postgres-compatible engine with storage that auto-grows and replicates across AZs.

In plain English analogy

RDS Multi-AZ is a primary cashier with a trained backup at another register — if the primary leaves, the standby takes the drawer (failover). Aurora is one shared digital ledger in the building's basement (storage across AZs) with several cashiers reading it; Serverless v2 is cashiers that clock in/out by the minute as the line grows.

RDS
  • Familiar engines + licensing options
  • Multi-AZ standby (sync)
  • Read replicas (async) for scale-out reads
  • Storage autoscaling on many engines
Aurora
  • 6-copy storage across 3 AZs
  • Faster failover / crash recovery
  • Up to 15 Aurora replicas
  • Serverless v2 scales ACUs fine-grained

02 HA patterns

flowchart TD
  app["App tier"] --> writer["Writer endpoint"]
  writer --> primary["Primary instance"]
  primary -->|"Sync · Multi-AZ HA"| standby["Standby · other AZ · no reads"]
  primary -->|"Async · scale / DR"| replica["Read replica"]
  app --> reader["Reader endpoint"]
  reader --> replica
Acme tickets
Survive AZ loss for checkout Postgres → RDS Multi-AZ (or Aurora). The standby is HA, not a read scaler.
Nova analytics
Reporting hammers the primary → add read replicas (or Aurora readers). Multi-AZ alone does not offload SELECTs on classic RDS.
Multi-AZ ≠ replica
Multi-AZ = sync standby for automatic failover. Read replicas = async copies for scale-out reads / cross-Region promote.
Aurora Global / Proxy
Global Database for low-RPO Region DR. RDS Proxy pools connections for Lambda/spiky apps.
Common trap gotcha

Multi-AZ ≠ read replica. “Scale reads” → replicas / Aurora readers. “Survive AZ failure with automatic failover” → Multi-AZ / Aurora storage. Mixing them is a classic distractor.

03 Aurora Serverless v2 (2026 default)

Serverless v2 scales Aurora Capacity Units (ACUs) up and down in fine increments, can mix with provisioned instances in the same cluster, and fits variable / unpredictable relational workloads without the coarse pauses of older Serverless v1.

  • Set min/max ACUs to bound cost and headroom.
  • Use for dev/test, spiky SaaS tenants, or variable reporting — still transactional relational.
  • For steady 24/7 high load, provisioned (or mixed) may be cheaper — cost domain tradeoff.

Variable traffic Postgres app needs AZ resilience and fine-grained scale. Best fit?

Right. Relational + variable load → Aurora Serverless v2. Single-AZ fails the resilience ask. DynamoDB is for key-value access patterns, not “we need Postgres SQL.”

04 Interview rapid-fire

RDS Multi-AZ vs read replica?core
Model answer

Multi-AZ is a sync standby for automatic failover — HA, not read traffic. Read replicas are async copies that serve reads and can be promoted; use them for scale-out and cross-Region DR.

Say it out loud say it

"Multi-AZ keeps me alive; replicas scale reads and help with DR."

Why Aurora Serverless v2 in 2026?warm-up
Model answer

It scales capacity in fine-grained ACUs for unpredictable relational load, coexists with provisioned instances, and avoids the old Serverless v1 cold-start / coarse scaling story. Default recommendation when the stem says variable traffic + SQL.

Say it out loud say it

"Variable SQL load → Aurora Serverless v2 ACUs, not a fixed oversized instance."

How does Aurora storage change the HA story?stretch
Model answer

Aurora storage is shared and replicated across three AZs (six copies). Compute nodes are separate — failover attaches a new writer to the same storage volume, so recovery is typically faster than classic RDS storage failover.

Say it out loud say it

"Aurora keeps the data volume across AZs; instances are replaceable readers and writers on top."
