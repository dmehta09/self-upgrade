DynamoDB access patterns.

Key-value / document store that scales with the right partition key design. As of 2026, prefer on-demand capacity when traffic is unpredictable; use provisioned + auto scaling when steady and cost-sensitive.

01 Keys & access patterns first

You design tables around how you query, not around normalized ERDs. Every item needs a partition key (and optional sort key). Hot partitions and table-scan habits fail both the exam and production.

In plain English analogy

DynamoDB is a giant set of labeled filing cabinets (partitions). The partition key chooses the cabinet; the sort key orders folders inside it. A GSI is a second index card system so you can find files by a different label without dumping every cabinet on the floor (a scan).

flowchart TD
  req[QueryRequirement] --> pk[ChoosePartitionKey]
  pk --> sk[OptionalSortKey]
  sk --> gsi[AddGSIIfNeeded]
  gsi --> mode{CapacityMode}
  mode -->|unpredictable| ondemand[OnDemand]
  mode -->|steady| provisioned[ProvisionedPlusAS]
GetItem / Query
Efficient. Query needs PK (+ optional SK conditions).
Scan
Reads the whole table — avoid on the exam unless “rarely / admin.”
GSI / LSI
Alternate query shapes. GSI can be eventual; watch projected attributes & cost.
Single-table
Optional advanced pattern: many entity types in one table with composite keys.

02 On-demand vs provisioned (2026)

On-demand
  • Default for spiky / unknown
  • Pay per request
  • No capacity planning
  • Great for new apps & events
Provisioned
  • Steady, predictable RCU/WCU
  • Auto Scaling for gentle drift
  • Often cheaper at high constant load
  • Reserved capacity options
Common trap gotcha

Strongly consistent reads cost more and aren't available on all GSI patterns. Default is eventually consistent. Also: a “popular product ID” as the only PK creates a hot partition — add entropy or redesign the key.

Workload identity to call DynamoDB: roles, not keys — see DevOps · IAM, storage & data.

03 Adjacent features

DAX
Microsecond cache for eventually consistent reads — when ElastiCache-style caching is in-process for Dynamo.
Streams
Change data capture → Lambda, analytics, fan-out.
TTL
Expire items automatically (sessions, temp data).
Global Tables
Multi-Region active-active with conflict resolution.
Transactions
ACID across items (limited size) when the stem requires multi-item atomicity.

New social app expects unpredictable spikes. Primary access is get/query by userId. Capacity mode?

Right. Unpredictable → on-demand (2026 default). Fixed peak provisioned wastes money; Scan-on-RDS is the wrong access pattern story.

04 Interview rapid-fire

How do you design a DynamoDB table?core
Model answer

List access patterns first. Choose a partition key that spreads load and a sort key for range queries. Add GSIs only for additional patterns. Prefer Query/GetItem over Scan. Pick on-demand if traffic is unknown; provisioned when steady.

Say it out loud say it

"Access patterns first, then keys and GSIs — Query not Scan, on-demand when spikes are unknown."

On-demand vs provisioned?warm-up
Model answer

On-demand for unpredictable or spiky workloads — pay per request, no capacity planning. Provisioned (+ auto scaling) when traffic is steady and you optimize cost at scale.

Say it out loud say it

"Spiky or unknown → on-demand. Flat and known → provisioned with auto scaling."

When do you add DAX or Global Tables?stretch
Model answer

DAX when read latency must be microsecond-class for eventually consistent access patterns. Global Tables when you need multi-Region active-active with local writes. Neither replaces a bad key design.

Say it out loud say it

"DAX for ultra-low-latency reads; Global Tables for multi-Region active-active — keys still come first."
