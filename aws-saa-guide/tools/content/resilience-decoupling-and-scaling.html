Queues absorb shock. Autoscaling absorbs load.

Tight coupling turns one slow dependency into a site-wide outage. SQS / SNS / EventBridge and ASG / Lambda concurrency let producers and consumers fail and scale independently — a constant SAA theme.

01 Why decoupling wins

If service A calls B synchronously and B is down, A is down. A queue or topic makes the failure temporary backlog instead of user-facing errors.

In plain English analogy

A restaurant ticket rail is a queue: the kitchen can spike without the host crashing. A megaphone to all cooks is pub/sub (SNS). The reservation system reacting to "table freed" events is EventBridge.

Tight coupling
  • Sync HTTP between every hop
  • One slow service stalls callers
  • Scale both sides in lockstep
Decoupled
  • SQS buffer / SNS fan-out
  • Consumers retry independently
  • Scale producers ≠ consumers

02 Pick the right messaging tool

SQS
Pull queue between producers and workers. Standard = at-least-once + best-effort order. FIFO = exactly-once processing + order per message group.
SNS
Push pub/sub fan-out to many subscribers (Lambda, SQS, HTTP, email). Use SNS→SQS for durable fan-out.
EventBridge
Event bus with content filtering, SaaS partners, schedule rules — "when X happens, do Y."
DLQ
Dead-letter queue after max receives — poison messages don't block the main queue forever.
Common trap gotcha

Long polling and visibility timeout matter: too-short visibility → duplicate processing; no DLQ → endless poison retries. FIFO is not free — use it when order/dedup is required, not by default.

03 Scaling patterns

  • ASG on CPU, ALB request count, or SQS ApproximateNumberOfMessages — classic worker farm.
  • Target tracking policies over manual step thresholds when the stem wants "automatically maintain."
  • Lambda scales with concurrency; use reserved concurrency to protect downstream.
  • DynamoDB on-demand vs provisioned + auto scaling; Aurora Serverless v2 for spiky relational.
  • Read replicas / ElastiCache for read-heavy paths without oversizing the primary.

Upload spikes overwhelm image processors. Users must get a fast API response; processing can finish later. Best change?

Right. Decouple with a queue so the API acknowledges quickly and workers scale independently on backlog.

04 Exam rapid-fire

SQS vs SNS vs EventBridge — when?core
Model answer

SQS = buffer work for consumers. SNS = fan-out the same message to many endpoints. EventBridge = route events with rules/filters across apps and AWS services. Combine SNS→SQS for durable multi-consumer.

Say it out loud say it

"Queue to absorb, topic to fan out, event bus to route by content."

How do you scale workers on SQS?warm-up
Model answer

Put workers in an ASG (or Lambda event source mapping) and scale on queue depth / age of oldest message so backlog shrinks without over-provisioning idle capacity.

Say it out loud say it

"Scale on the backlog, not on a guess — queue depth is the signal."

Why visibility timeout + DLQ?core
Model answer

Visibility timeout hides an in-flight message so others don't steal it; if the worker dies, it reappears. After N failed receives, a DLQ isolates poison messages for debugging instead of infinite retries.

Say it out loud say it

"Hide while working, resurface if we crash, quarantine if we keep failing."
