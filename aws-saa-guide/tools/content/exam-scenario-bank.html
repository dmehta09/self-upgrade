01 Secure architectures

App on EC2 must call S3 without long-lived keys on the instance.Secure
Flagship walkthrough
Story

Acme’s order service runs on EC2 and uploads receipts to a private S3 bucket. A junior engineer pasted access keys into userdata “just for now.”

Underline constraint

The app must reach S3 without long-lived keys on the instance.

Eliminate
  • IAM user access keys in files or userdata — permanent credentials on disk.
  • Public bucket “so the app doesn’t need auth” — security failure, not a shortcut.
Best answer

Attach an IAM role via instance profile with least-privilege S3 permissions; use the SDK default credential chain (IMDS).

Why

Roles issue temporary credentials. The exam punishes keys on instances every time the stem forbids them.

Say it out loud say it

"EC2 talks to AWS with a role on the instance profile — never paste long-lived keys onto the box."

flowchart TD
  start["EC2 needs S3 access"] --> q{"Long-lived keys OK?"}
  q -->|no| role["Instance profile + IAM role"]
  q -->|yes · trap| keys["Access keys in userdata"]

Private EC2 must reach S3 without internet / NAT.Secure
Flagship walkthrough
Story

A batch worker in a private subnet must pull objects from S3. Security banned internet egress and refused a NAT “just for AWS APIs.”

Underline constraint

Reach S3 without internet or NAT — traffic must stay private.

Eliminate
  • NAT Gateway in a public subnet — works, but uses a public path and adds cost the stem forbids.
  • Make the bucket public and curl from the instance — fails “private” and least privilege.
Best answer

Gateway VPC endpoint for S3 (associate private route tables) + endpoint policy; keep the bucket private.

Why

Gateway endpoints put S3 on the AWS network via prefix-list routes. Interface endpoints also work but gateway is the classic S3/DynamoDB answer.

Say it out loud say it

"No internet to S3? Gateway VPC endpoint on the private route tables — not NAT."

flowchart TD
  need["Private subnet needs S3"] --> q{"Internet / NAT allowed?"}
  q -->|no| gw["S3 gateway VPC endpoint"]
  q -->|yes · costly| nat["NAT Gateway"]

Enforce encryption on all new S3 buckets org-wide.Secure
Flagship walkthrough
Story

Compliance wants every new bucket across dozens of member accounts to start encrypted. Teams keep creating unencrypted buckets in sandbox accounts.

Underline constraint

Policy must apply org-wide to all new buckets, not one account’s IAM.

Eliminate
  • Attach an IAM policy only in the security account — member accounts ignore it.
  • Train teams to click “enable encryption” — not enforceable at create time.
Best answer

Organizations SCP denying create/put without encryption (and/or Config + remediation); SSE-S3 or SSE-KMS as the floor.

Why

SCPs set a permission ceiling for every account under the OU. Account IAM alone cannot police the org.

Say it out loud say it

"Org-wide encryption floor means an SCP — IAM in one account is not a governance boundary."

Web app needs protection from common Layer-7 exploits and volumetric DDoS.Secure
Best answer

CloudFront + AWS WAF (+ Shield Standard included; Shield Advanced only if the stem demands premium DDoS features).

Why

WAF filters HTTP rules; Shield absorbs volumetric attacks at the edge. Security groups alone are L3/L4.

  • SG-only / NACL tweaks — miss SQLi/XSS and edge absorption.
  • ALB without WAF — no managed L7 rule set at the edge.

DB credentials must not live in code or AMI; rotate automatically.Secure
Best answer

Secrets Manager (or Parameter Store SecureString + rotation Lambda) with IAM fetch at runtime; KMS encryption.

Why

Secrets Manager rotates RDS/Aurora credentials natively. Hardcoded secrets fail security and ops stems.

  • Bake password into the AMI — rotates never, leaks everywhere.
  • Plaintext env vars in userdata — still long-lived secrets on disk.

02 Resilient architectures

Survive AZ failure for a three-tier web app with RDS.Resilient
Flagship walkthrough
Story

Shopfront runs ALB → app ASG → RDS. Last outage took one AZ offline and the site went dark because everything lived in that AZ.

Underline constraint

Must survive a single AZ failure — Region loss is out of scope.

Eliminate
  • Multi-Region active-active — overkill when only AZ failure is stated.
  • Single-AZ RDS with frequent snapshots — RTO/failover won’t meet “survive AZ.”
Best answer

ALB + ASG across ≥2 AZs; RDS Multi-AZ; subnets in multiple AZs.

Why

Multi-AZ is the default HA pattern inside a Region. Spread every tier; let RDS fail over the standby.

Say it out loud say it

"AZ failure: Multi-AZ everywhere — ALB, ASG, and RDS Multi-AZ. Don’t jump to multi-Region."

flowchart TD
  stem["Survive AZ failure"] --> q{"Region loss in stem?"}
  q -->|no| maz["ALB + ASG multi-AZ · RDS Multi-AZ"]
  q -->|yes| mr["Pilot light / warm standby"]

Order API must accept requests even if fulfillment is slow/down.Resilient
Flagship walkthrough
Story

Checkout returns 5xx whenever the warehouse microservice stalls. Product wants “order accepted” even if packing happens minutes later.

Underline constraint

API must accept requests even when fulfillment is slow or down — buffer, don’t couple.

Eliminate
  • Sync HTTP from API to fulfillment with retries only — still fails open when the dependency is down.
  • Bigger ASG on fulfillment alone — doesn’t protect the API from dependency latency.
Best answer

API writes to SQS; workers consume asynchronously; DLQ for poison messages.

Why

Decoupling turns dependency failure into backlog instead of user-facing 5xx.

Say it out loud say it

"Accept now, process later — API enqueues to SQS; workers and a DLQ own the backlog."

flowchart LR
  api["Order API"] --> q["SQS queue"]
  q --> workers["Fulfillment workers"]
  q --> dlq["DLQ"]

RTO < 1 hour, RPO near-zero, tolerate Region loss, control cost.Resilient
Best answer

Pilot light or warm standby in a second Region with continuous DB replication + Route 53 failover.

Why

Cold daily backups miss RPO/RTO; full active-active overspends when “control cost” appears.

  • Cold backup restore only — usually blows a sub-hour RTO / near-zero RPO.
  • Active-active dual Region — fails the cost constraint.

Notify email, Lambda, and a queue from one business event.Resilient
Best answer

SNS topic with those subscriptions (SQS for durability), or EventBridge rules to multiple targets.

Why

Pub/sub fan-out; SQS alone is pull, not multi-protocol fan-out.

  • One SQS queue polled by everything — not email/Lambda fan-out.
  • Three separate API calls from the producer — couples and duplicates logic.

Need point-in-time restore for DynamoDB tables.Resilient
Best answer

Enable DynamoDB PITR (continuous backups) and/or on-demand backups; AWS Backup for centralized policy.

Why

PITR covers fine-grained RPO; EBS snapshots don’t apply to DynamoDB.

  • EBS / EC2 snapshots — wrong storage plane.
  • S3 versioning on an export only — not continuous table PITR.

03 High-performing architectures

Global users, mostly static assets, lowest latency — keep origin private.High-performing
Flagship walkthrough
Story

Marketing hosts a static site on S3 for worldwide visitors. Security wants no public bucket ACL — only CloudFront should read the origin.

Underline constraint

Global static content with lowest latency and a private S3 origin.

Eliminate
  • Multi-Region active app stacks — overkill for static assets.
  • Public S3 website endpoint alone — higher RTT and open origin.
Best answer

S3 + CloudFront with OAC (Origin Access Control); cache at the edge; block public bucket access.

Why

Edge caches cut origin load and RTT; OAC is the modern private-origin pattern (prefer over legacy OAI).

Say it out loud say it

"Static global = CloudFront in front of S3 with OAC — private origin, cache at the edge."

Read-heavy relational DB; writes are modest — Multi-AZ alone isn’t enough.High-performing
Flagship walkthrough
Story

Reporting queries slam the primary RDS instance. Someone enabled Multi-AZ and expected the standby to soak up SELECTs. Latency barely moved.

Underline constraint

Need to scale reads; Multi-AZ standby is not a read replica.

Eliminate
  • Rely on Multi-AZ standby for reads — standby is failover-only on classic RDS.
  • Vertically scale the primary forever — expensive and doesn’t teach the pattern.
Best answer

Aurora/RDS read replicas (or Aurora readers) + route reads there; add ElastiCache if hot keys dominate.

Why

Replicas scale read capacity horizontally. Multi-AZ buys HA, not read throughput.

Say it out loud say it

"Multi-AZ is HA. Read replicas are for reads. Don’t confuse the standby with a reader."

Millions of key-value lookups with single-digit ms latency.High-performing
Best answer

DynamoDB (DAX if microsecond cache) or ElastiCache in front of a DB — pick based on whether Dynamo is already the system of record.

Why

Single-node RDS won’t meet that scale/latency; design for access patterns.

  • One large RDS instance — wrong scaling model for millions of KV lookups.
  • S3 GetObject for hot keys — object storage, not single-digit ms KV.

TCP/UDP ultra-low latency load balancing to game servers.High-performing
Best answer

Network Load Balancer (NLB) — L4, preserves source IP, extreme performance.

Why

ALB is L7 HTTP/HTTPS. Classic CLB is legacy. NLB fits non-HTTP and latency-sensitive.

  • ALB — wrong layer for raw TCP/UDP game traffic.
  • Classic Load Balancer — legacy; exam prefers NLB for L4.

Shared POSIX file system for many EC2 across AZs.High-performing
Best answer

EFS (Regional, Multi-AZ). FSx when Windows/Lustre/NetApp features are required.

Why

EBS is single-AZ. S3 is object, not POSIX. Instance store is ephemeral and local.

  • EBS multi-attach assumptions across AZs — EBS is AZ-scoped.
  • S3 as a “shared disk” — not a POSIX filesystem.

04 Cost-optimized architectures

Steady 24×7 fleet to discount; interruptible batch should go Spot.Cost
Flagship walkthrough
Story

Platform runs a steady web/API fleet all week, plus nightly analytics that can restart. Finance wants lower bills without locking every workload into one purchase model.

Underline constraint

Steady 24×7 wants commitment discount; fault-tolerant batch wants cheapest interruptible capacity.

Eliminate
  • All On-Demand forever — leaves easy savings on the table for the steady fleet.
  • Savings Plans / RIs on interruptible batch alone — wrong tool; Spot fits batch.
Best answer

Compute Savings Plans (after right-sizing) for the steady fleet; Spot (diversified pools, checkpoints) for the batch.

Why

Commit where usage is predictable and flexible across families; Spot where interruption is boring.

Say it out loud say it

"Steady fleet → Compute Savings Plans. Interruptible batch → Spot. Don’t mix the tools."

Petabytes in S3; rarely accessed after 90 days.Cost
Best answer

Lifecycle rules to IA / Glacier Instant / Deep Archive — or Intelligent-Tiering if access is unpredictable.

Why

Storage class is the cost lever; replication alone doesn’t reduce $/GB.

  • Cross-Region replication only — durability/DR, not cold-storage savings.
  • Keep everything in Standard — pays hot rates for cold data.

Spiky API, idle most of the night; minimize idle cost.Cost
Best answer

API Gateway + Lambda (or Aurora Serverless v2 / Fargate scale-to/near-zero as fit).

Why

Pay per use beats always-on ASG for sparse traffic.

  • Fixed ASG min=N overnight — pays for idle capacity.
  • Reserved Instances for spiky idle — commitment on the wrong shape.

05 Mixed / trick stems

Secure + resilient: public web, private app/DB, Multi-AZ.Secure
Best answer

Public subnets: ALB only. Private: app ASG. DB: private Multi-AZ RDS; SG least privilege; prefer SSM Session Manager over bastion keys.

Why

Classic three-tier VPC — security groups as primary firewall, Multi-AZ for resilience.

  • Public app/DB subnets “for simplicity” — expands blast radius.
  • Single-AZ “cheaper HA” — fails the Multi-AZ requirement.

Perf + cost: cache session data for a fleet of web servers.High-performing
Best answer

ElastiCache (Redis) shared across instances — not sticky sessions alone on one node.

Why

Externalized sessions enable scale-out and survive instance replace; cheaper than oversized sticky singles.

  • Sticky sessions only on one large instance — doesn’t scale or survive replace.
  • Local disk session files — lost on termination, not shared.
