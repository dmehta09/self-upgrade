Domain 3 · High-performing Databases · cache

ElastiCache.

Managed in-memory cache (Redis / Valkey-compatible and Memcached) to cut database load and latency. The exam asks engine choice, HA, and when cache belongs in front of RDS/DynamoDB vs when the DB feature (DAX) is enough.

01 When caching wins

Put ElastiCache in front of a relational or document store for hot keys, session stores, leaderboards, and read-heavy pages. Invalidate or TTL carefully — stale cache is a silent bug.

In plain English analogy

Your database is the library stacks. ElastiCache is the cart of books already pulled for today's popular titles — grab in milliseconds, but if someone updates the catalog you must refresh the cart or readers see yesterday's edition.

Cache-aside

Client → App → ElastiCache (hit) · miss → RDS / DynamoDB → populate cache

02 Redis vs Memcached

Redis / Valkey
  • Rich data structures, persistence options
  • Replication + Multi-AZ failover
  • Cluster mode for scale-out
  • Pub/Sub, Lua, sorted sets
Memcached
  • Simple key/value
  • Multithreaded, easy horizontal scale
  • No fancy structures / persistence story
  • When you only need a dumb cache
Common trap gotcha

ElastiCache is VPC-bound — not a public internet cache. Place nodes in private subnets; open security groups only from app tiers. Also: caching does not replace Multi-AZ on the primary database for durability.

03 Patterns & HA

Cache-aside
App reads cache → miss → DB → populate cache. Most common exam pattern.
Session store
Sticky-user sessions in Redis so ASG instances stay stateless.
Multi-AZ Redis
Primary + replica with automatic failover for HA.
vs DAX
DAX is DynamoDB-specific microsecond cache; ElastiCache is general-purpose for many backends.

Stateless web tier behind an ALB needs shared sessions and sorted-set leaderboards. Choose?

Right. Redis gives shared sessions and rich structures. Memcached lacks sorted sets. Local EBS sessions break horizontal scale.

04 Interview rapid-fire

Redis vs Memcached on ElastiCache?warm-up
Model answer

Redis for rich structures, replication/failover, and advanced features. Memcached for simple, multithreaded key/value caching when you don't need those features.

Say it out loud say it

"Redis for features and HA; Memcached for simple horizontal key/value."

How do you keep the web tier stateless?core
Model answer

Move sessions (and other shared hot state) into ElastiCache Redis so any instance behind the load balancer can serve any user. Combine with Auto Scaling — no sticky dependency on a single host's memory/disk.

Say it out loud say it

"Sessions in Redis, instances disposable — that's a stateless web tier."

ElastiCache vs DynamoDB DAX?stretch
Model answer

DAX is a write-through/read cache purpose-built for DynamoDB APIs. ElastiCache is a general cache you wire yourself (cache-aside) in front of RDS, DynamoDB, or APIs. Pick DAX for seamless Dynamo microsecond reads; ElastiCache when you need Redis features or multi-backend caching.

Say it out loud say it

"DAX is Dynamo's own accelerator; ElastiCache is the general Redis/Memcached tier."
