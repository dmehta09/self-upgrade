Networking · routing · SG · NACL Domain 1 · Secure

Routes decide reachability; firewalls decide permission.

Route tables answer “where does this packet go?” Security groups and NACLs answer “is it allowed?” Master stateful vs stateless — it’s one of the highest-frequency SAA networking discriminators.

01 Route tables that matter

Each subnet associates with one route table. Longest-prefix match wins. Default local route keeps VPC-internal traffic private; you add IGW, NAT, endpoints, peering, TGW, or VPN targets.

In plain English analogy

The route table is the campus map: “to leave campus, use Gate A.” Security groups are bouncers at each building door who remember who they let out. NACLs are the perimeter fence checklist — they don’t remember conversations, so you must list both directions.

Implicit; covers the VPC CIDR(s). You don’t delete it.
IGW route
Makes a subnet public for internet-bound traffic.
NAT route
Private subnet egress to the internet.
More specific routes
Endpoint prefix lists, peering CIDRs, TGW — often preferred over default for AWS/on-prem paths.

02 Security groups vs NACLs

Security groups attach to ENIs: stateful, allow-only, evaluated as a set. NACLs attach to subnets: stateless, numbered allow/deny, first match wins.

Security groupNACL
ScopeENI / instance / LB / RDSSubnet
StateStatefulStateless
RulesAllow onlyAllow and deny
DefaultDeny all inbound; allow all outbound (customizable)Custom NACLs deny all until you add rules
Everyday usePrimary micro-segmentationCoarse guardrails / explicit subnet deny
Common trap gotcha

Ephemeral ports on NACLs. Because NACLs are stateless, allowing inbound 443 isn’t enough for return traffic — you must allow outbound ephemeral ranges (and vice versa). Security groups don’t need this for established connections. Also: reference other security groups as sources, not wide 0.0.0.0/0, for tier-to-tier traffic.

03 Tier patterns that pass the exam

ALB SG allows 443 from the world (or CloudFront prefix). App SG allows only from ALB SG. DB SG allows only from app SG. NACLs stay permissive unless you need an explicit deny.

Loose
  • App SG: inbound 0.0.0.0/0 on 8080
  • DB SG: inbound from whole VPC CIDR
  • Rely on NACL alone for app isolation
Tight
  • App SG: inbound from sg-alb only
  • DB SG: inbound from sg-app on 5432
  • SG as primary; NACL for subnet-wide deny if required

Traffic is allowed by the security group but still fails. You recently added a custom NACL. What’s the likely cause?

Right. Packets must pass both NACL and SG. Stateless NACLs often break return traffic; both layers apply — neither “overrides” the other.

04 Exam rapid-fire

Stateful vs stateless — say it cleanly.warm-up
Model answer

Security groups are stateful: allow outbound and the response is automatically allowed. NACLs are stateless: every direction needs an explicit rule.

Say it out loud say it

"SG remembers the conversation; NACL makes you allow both directions yourself."

When would you use a NACL deny?core
Model answer

When you need an explicit subnet-wide block (e.g., block a bad actor CIDR at the perimeter) that security groups can’t express as a deny. Day-to-day allow rules still live in SGs.

Say it out loud say it

"NACLs for coarse allow/deny at the subnet; security groups for the real workload policy."

Route exists, SG allows — still unreachable. What else?stretch
Model answer

Check NACLs, public IP/EIP presence, IGW attachment, NACLs on both subnets, OS firewall, and whether the target is in a different VPC without peering/PrivateLink/TGW. Also DNS: wrong private hosted zone or unresolved name.

Say it out loud say it

"I verify route, NACL both ways, SG, and that the instance actually has the IP path I think it does."
