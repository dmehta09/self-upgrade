Resilience & DR · Multi-AZ vs multi-Region Domain 2 · Resilient

Survive a zone. Survive a region.

Multi-AZ is the default HA pattern inside one Region. Multi-Region is for disasters that take the whole Region down — rarer, slower to build, and much more expensive. The exam wants you to pick the right blast radius.

01 AZ vs Region — blast radius

An Availability Zone is one or more data centers with independent power and networking. A Region is a geographic cluster of AZs. Losing an AZ ≠ losing a Region.

In plain English analogy

Think of a city with three power substations (AZs) and a whole metro area (Region). If one substation fails, the others keep the lights on. If the entire metro floods, you need a second city — that's multi-Region.

Multi-AZ
  • Survives one AZ failure
  • Same Region latency
  • Managed failover for RDS / Aurora / ALB / ASG
  • Default for stateful data on the exam
Multi-Region
  • Survives Region-wide events
  • Cross-Region latency + complexity
  • Needs replication, DNS failover, dual stacks
  • Only when RTO/RPO and risk justify cost

02 Service patterns that get Multi-AZ "for free"

Spread compute and data across AZs; let AWS manage failover where it can.

ALB + ASG / ECS
Targets in ≥2 AZs; health checks drain bad nodes. Subnets must span AZs.
RDS Multi-AZ
Synchronous standby in another AZ; automatic failover (~1–2 min). Not a read replica.
Aurora
Storage is already Multi-AZ; add reader instances across AZs for HA + scale-out reads.
S3 / DynamoDB / SQS
Regional services — data is Multi-AZ by design inside the Region.
EBS
Tied to one AZ. Snapshot → recreate volume in another AZ/Region for DR.
Common trap gotcha

Putting an ASG in one AZ, or an ALB with targets only in AZ-a, is not Multi-AZ. You need subnets and capacity in multiple AZs. Also: RDS Multi-AZ is HA, not read scaling — use read replicas for that.

03 When the exam wants multi-Region

Choose multi-Region when the stem says Region failure, compliance data residency in two places, or global users with low latency — not for routine AZ HA.

  • S3 Cross-Region Replication + versioning for object DR.
  • Aurora Global Database / DynamoDB Global Tables for active-active or fast failover.
  • Route 53 failover / latency health checks to shift traffic.
  • CloudFront + multi-origin for edge delivery (not the same as full app DR).

An app must stay up if an Availability Zone fails, with minimal cost and complexity. Best starting design?

Right. AZ failure is the common case; Multi-AZ in one Region is the cost-effective default. Multi-Region is for Region-level risk.

04 Exam rapid-fire

Multi-AZ vs multi-Region — one sentence each.warm-up
Model answer

Multi-AZ keeps the app running when one data center / AZ fails inside a Region. Multi-Region keeps (or restores) the app when an entire Region is unavailable — more replication, DNS, and cost.

Say it out loud say it

"Multi-AZ is the default HA tax. Multi-Region is the disaster tax — only pay it when RTO and Region risk say so."

Is RDS Multi-AZ a read replica?core
Model answer

No. Multi-AZ is a synchronous standby for failover — you don't send read traffic there. For read scale-out, add read replicas (async, can be same or cross-Region).

Say it out loud say it

"Multi-AZ = stay alive. Read replica = read more. Don't mix them up on the exam."

How do regional services like S3 fit Multi-AZ?core
Model answer

S3 (and DynamoDB, SQS, etc.) already replicate across AZs in the Region. You design Multi-AZ for your compute and for AZ-scoped resources (EBS, single-AZ RDS without Multi-AZ). Cross-Region needs explicit replication.

Say it out loud say it

"Regional services already survive an AZ. I still Multi-AZ my app tier and choose CRR only when Region failure is in scope."
