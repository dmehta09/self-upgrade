AWS Backup & protection.

Central policies for backups across EBS, EFS, RDS, DynamoDB, FSx, and more — vaults, retention, cross-account/Region copies, and immutability with Vault Lock. On the exam, “centralized backup plan” usually means AWS Backup.

01 Mental model

A backup plan schedules what to protect; a vault holds recovery points; tags / resource assignments select targets. AWS Backup orchestrates native snapshots/exports so you don't glue cron + scripts per service.

In plain English analogy

Think of a corporate records room. The plan is the clerk's schedule (“every night, copy these drawers”). The vault is the locked room where copies live. Vault Lock is pouring concrete over the lock — even the clerk can't shred tapes early.

Backup flow

Tagged resources → Backup plan → jobs → Vault → restore / cross-Region·account copy

02 Exam-critical features

Lifecycle in the plan
Transition cold storage / expire recovery points to match RPO and cost.
Cross-Region / cross-account
Copy rules for DR and blast-radius isolation (org backup account pattern).
Vault Lock
WORM retention on the vault — compliance scenarios.
PITR
Point-in-time recovery where the underlying service supports continuous backup (e.g. some RDS / DynamoDB patterns).
IAM & KMS
Separate roles for backup vs restore; encrypt vaults with customer managed keys when required.
Ad-hoc
  • Manual EBS snapshots only
  • Different scripts per service
  • No cross-account isolation
AWS Backup
  • One plan across services
  • Tag-based assignment
  • Vault Lock + org copies
Common trap gotcha

Backup ≠ Multi-AZ. Multi-AZ is high availability for a live failure in another AZ. Backups (and cross-Region copies) address data loss, ransomware, and Region events. Exam stems that mix RTO/RPO with “AZ failure” want HA; “deleted table / bad deploy / ransomware” want backup + immutable vault.

Overlap with encryption/roles: DevOps · IAM, storage & data.

03 Design checklist

  • Map RPO/RTO → schedule frequency and restore testing cadence.
  • Tag production resources; assign plans by tag — don't list ARNs forever.
  • Send copies to a dedicated backup account with tighter IAM.
  • Enable Vault Lock only after a cooling-off / compliance review — it's hard to undo.
  • Practice restores; untested backups are fiction.

Compliance requires immutable backups of RDS and EFS that attackers with admin in the app account cannot delete. Which feature matters most?

Right. Immutability + separation of duty → Vault Lock and/or cross-account copies. Multi-AZ is HA, not ransomware protection. Instance store is ephemeral.

04 Interview rapid-fire

What problem does AWS Backup solve?warm-up
Model answer

It centralizes backup plans, vaults, and restores across many AWS resource types so you apply one policy (tags, schedules, retention, copies) instead of per-service snapshot scripts.

Say it out loud say it

"One backup plan and vault across EBS, EFS, RDS — tag-based, with optional cross-Region copies."

Backup vs Multi-AZ vs cross-Region DR?core
Model answer

Multi-AZ = automatic failover for infrastructure failure in another AZ (short RTO, same Region). Backups = recover from data corruption, deletes, ransomware. Cross-Region copies/replicas = Region-level disaster. Most serious designs use HA and backups.

Say it out loud say it

"Multi-AZ keeps me up; backups undo bad data; cross-Region survives a Region event."

What is Vault Lock?stretch
Model answer

A configuration that makes recovery points in a backup vault WORM for a retention period — even privileged users can't delete early. Used for compliance and ransomware resilience, often with a separate backup account.

Say it out loud say it

"Vault Lock is WORM on the backup vault — retention you can't quietly erase."
