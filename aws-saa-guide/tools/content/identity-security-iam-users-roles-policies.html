Domain 1 · Secure Architectures Identity & Security · IAM

IAM users, roles & policies.

Who can call which API on which resource. SAA-C03 defaults (Sep 2026): roles + short-lived credentials, not long-lived access keys; humans via Identity Center; workloads via instance profiles, IRSA/Pod Identity, or OIDC.

01 Users, groups, roles — pick the right principal

An IAM user is a long-lived principal (password and/or access keys). A role is assumed and yields temporary credentials. A group is only a permission bundle for users — never attach policies to “everyone” via wildcard principals.

In plain English analogy

A role is a visitor badge that unlocks specific rooms for the next hour, then expires. A long-lived access key is a permanent master key — if it leaks into Git or a log, it keeps working until someone notices. Hand out badges, not master keys.

Prefer (2026 default)
  • IAM roles for EC2, Lambda, ECS tasks, EKS pods
  • Identity Center for humans (SSO)
  • OIDC federation for CI (GitHub Actions, etc.)
  • Cross-account assume-role with ExternalId when needed
Avoid on the exam
  • Long-lived IAM user access keys in apps
  • Sharing one IAM user across a team
  • Action: "*" + Resource: "*" “for now”
  • Embedding keys in AMIs, Lambda env, or Docker images

Interview depth for IAM + storage lives in the sibling guide: IAM, storage & data.

02 Policies: identity, resource & permission boundaries

Permissions are JSON. Evaluation is not “any Allow wins” — explicit Deny always wins, then Allow must grant the action on the resource, and SCPs / boundaries can still block.

flowchart TD
  request[API_request] --> deny{Explicit_Deny?}
  deny -->|yes| blocked[Denied]
  deny -->|no| scp{SCP_and_boundary_allow?}
  scp -->|no| blocked
  scp -->|yes| idPol{Identity_policy_Allow?}
  idPol -->|no| blocked
  idPol -->|yes| resPol{Resource_policy_ok?}
  resPol -->|no| blocked
  resPol -->|yes| allowed[Allowed]
Identity-based
Attached to user/group/role — “what this principal can do.”
Resource-based
On the resource (S3 bucket policy, KMS key policy, SQS) — “who can access me,” including other accounts.
Permission boundary
Max permissions a role/user can ever receive — used to safely delegate IAM administration.
Session policies
Further restrict credentials when assuming a role (STS).
least-privilege.json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "ReadOneBucket",
    "Effect": "Allow",
    "Action": ["s3:GetObject"],
    "Resource": "arn:aws:s3:::acme-invoices/*",
    "Condition": {
      "StringEquals": { "aws:RequestedRegion": "us-east-1" }
    }
  }]
}

Scope Action and Resource; add Condition keys (aws:SourceVpce, MFA, tags) when the scenario demands it.

Common trap gotcha

Trust policy ≠ permissions policy. The role’s trust policy says who may assume it. The permissions policy says what the assumed session can do. Cross-account access fails when people only edit one of them.

03 Workload credentials without keys

EC2
Instance profile → role; SDK pulls rotating creds from IMDS. Prefer IMDSv2.
Lambda / ECS
Execution / task role attached at deploy time — no keys in env.
EKS
IRSA or EKS Pod Identity maps a service account to an IAM role. See containers & serverless.
CI/CD
OIDC → AssumeRoleWithWebIdentity; no AWS_SECRET_ACCESS_KEY in secrets stores for AWS auth.

An app on EC2 must read from one S3 bucket. What is the SAA-correct design?

Right. Roles via instance profiles are the default. Long-lived keys and public buckets are exam distractors — and real-world anti-patterns.

04 Interview rapid-fire

User vs role — when is each correct?core
Model answer

Prefer roles for anything that needs AWS API access: workloads, federation, cross-account. IAM users with long-lived keys are legacy for apps; humans should use Identity Center. Roles issue temporary STS credentials that expire automatically.

Say it out loud say it

"Roles over users — temporary badges, not master keys. EC2 uses instance profiles, pods use IRSA or Pod Identity, CI uses OIDC. No long-lived keys in apps."

How does IAM evaluate Allow vs Deny?core
Model answer

Default deny. An explicit Deny in any applicable policy wins. Otherwise every layer that applies (SCP, permission boundary, identity policy, and resource policy when relevant) must Allow. That is why an Allow in a role can still fail under a Deny SCP.

Say it out loud say it

"Explicit Deny always wins. Then SCPs and boundaries can still cap you. Allow alone in the role is not enough if the org or resource policy blocks it."

What is a permission boundary for?stretch
Model answer

A permission boundary sets the maximum permissions an identity can ever have, even if someone attaches a broader policy. Use it when you let developers create roles safely without granting themselves full admin.

Say it out loud say it

"A boundary is a ceiling — the intersection of identity policies and the boundary is what actually applies. Perfect for delegated IAM."
