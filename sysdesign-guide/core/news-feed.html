Core · Twitter / X feed

Design a news feed.

A stream of recent posts from everyone you follow. It's the most iconic system-design question because it forces the field's most famous trade-off — fan-out on write vs read: do the work when someone posts, or when someone reads? Get that right, handle the celebrity who breaks it, and layer on the ML ranking that every real feed now runs.

01  Requirements & scale

✅

Functional

Post. View a home timeline (posts from people you follow). Follow/unfollow. Start chronological; ranking is a layer on top.

📐

Non-functional

Extremely read-heavy (~100:1) — people scroll far more than they post. Timelines load < 200 ms. Eventual consistency is fine (a post a second late is invisible) — except read-your-own-writes for your own posts.

The hidden cost is fan-out amplification: 500M posts/day × ~200 avg followers ≈ 10¹¹ timeline writes/day (~1.2M/s avg). Reads dwarf writes ~100:1, so make reads cheap even if writes do more work.

02  API & data model

POST/v1/posts{ text, media_ids?, reply_to?, idempotency_key } → 201 { post_id, created_at }
GET/v1/timeline/home?limit=20&cursor=…→ { items[], next_cursor } · cursor, never offset
PUT/v1/follows/{target}follow / unfollow → 204
posts
sharded by author_id (co-locates an author's posts → one shard hit to pull a celebrity's recent posts); post_id is a Snowflake (time-sortable). Secondary index (author_id, post_id DESC).
Social graph
stored both directions — followers partitioned by followee (fan-out target) and following by follower (read-pull/merge). Real systems back this with a write-through graph cache (Meta's TAO over MySQL).
Per-user timeline (Redis)
LPUSH tl:home:{u} {post_id}; LTRIM 0 799 — store IDs, not objects, so a celebrity post is one cached object, not N copies. Hydrate at read with MGET (posts + authors + counts).

Cursors are opaque (encode snowflake_id for chronological, or (score, post_id) + a session seed for ranked) — never offset, which is O(n) deep and breaks under inserts.

04  Architecture — fan-out on write

For most users, precompute. On post, the write service persists to the source of truth, then an async fan-out worker pushes the post id into each follower's timeline list — so the author's request returns instantly and each follower's read is a single lookup.

05  The celebrity problem → hybrid

Fan-out on write breaks for celebrities

A 100M-follower account would trigger 100M Redis writes per post — at ~1 ms each that's ~28 hours to deliver one post. The fix is a hybrid gated by a follower-count threshold (a runtime config flag, not an architecture change): fan out for normal accounts, but for celebrities store once and pull at read time, merging into the precomputed timeline.

fanout.py
CELEB_THRESHOLD, CAP = 10_000, 800

def on_post_created(ev):                       # fan-out worker (Kafka consumer)
    if graph.follower_count(ev.author) >= CELEB_THRESHOLD:
        redis.lpush(f"author:recent:{ev.author}", ev.post_id)   # celeb: park, don't fan out
        redis.ltrim(f"author:recent:{ev.author}", 0, CAP - 1)
        return
    for batch in graph.iter_followers(ev.author, batch=5000):   # regular: push to each follower
        pipe = redis.pipeline()
        for f in batch:
            pipe.lpush(f"tl:home:{f}", ev.post_id)
            pipe.ltrim(f"tl:home:{f}", 0, CAP - 1)
        pipe.execute()

def get_home_timeline(user, cursor, limit=20):                 # read = push list + celeb pull
    ids = set(redis.lrange(f"tl:home:{user}", 0, 400))
    for celeb in graph.followed_celebrities(user):             # bounded set
        ids |= set(redis.lrange(f"author:recent:{celeb}", 0, 50))
    ranked = sorted(ids, reverse=True)                          # snowflake id ~ time order
    return hydrate(paginate(ranked, cursor, limit))            # MGET posts + authors + counts

One cached celebrity post is shared by all followers — the read does O(celebs followed) extra work instead of the write doing O(followers).

06  Ranking (the 2026 reality: ML, not chronological)

The default "For You" feed on X, Instagram, and Threads is ML-ranked (chronological survives as an opt-in tab). Fan-out produces candidates; ranking decides order, on the read path, as a multi-stage funnel:

Candidate sourcing
Narrow hundreds of millions of posts to ~1,500 — roughly half in-network (people you follow) and half out-of-network (graph/embedding signals: SimClusters, TwHIN).
Heavy ranker
A neural net scoring each candidate's engagement probabilities, combined as a weighted sum (with strong negative weights for "report"/negative feedback).
Heuristics & filters
Visibility/safety filters, author diversity, dedupe — applied last.
2026 shift
X open-sourced a rewrite (Jan 2026) replacing the classic light/heavy-ranker funnel with a single Grok transformer that learns from engagement sequences — trading ML-pipeline complexity for heavier inference (GPU) cost.

07  Failure modes, multi-region & cost

🌊

Fan-out backlog

A celebrity past the threshold or a spike backs up Kafka → "post-to-visible" balloons. Mitigate with the threshold itself, per-author rate limits, priority lanes, autoscaled workers, and a DLQ. Alert on consumer lag.

🧊

Timeline cache loss

Redis is a cache, not truth. On node loss, rebuild a timeline lazily on read from posts + graph (pull followees' recent posts, re-materialize). Cap blast radius with sharding + replicas; warm hot users.

🌍

Multi-region

Geo-pin users; replicate graph + timeline cache near them; eventual consistency cross-region (hundreds of ms). For read-your-own-writes, route the author's reads to their home region and/or merge their own recent posts on top.

💰

Cost

Timeline-cache RAM (~13 TB working set × replication) is the big fixed cost — cache only active users, cap length, store IDs not objects. Fan-out compute scales with posts × followers; ML inference is now a first-order driver.

Observability: home-timeline read p99 (SLO < ~200 ms), fan-out lag / post-to-visible (SLO p99 < ~5 s), cache hit ratios. Alert on a hit-ratio drop combined with a DB-read surge — the classic cache-failure → stampede signature.

08  Trade-offs & interview recap

A feed is 100:1 read-heavy and most users have modest follower counts. What's the right default, and the exception?

Right: with reads dominating, precomputing timelines on write makes the common read a single lookup. The only thing that breaks it — accounts with millions of followers — is handled by pulling their posts on read. That hybrid is the canonical answer.
Say this to nail it

"It's 100:1 read-heavy, so I precompute timelines: fan-out on write pushes post IDs into each follower's Redis list, and reads are one lookup + hydration. The celebrity case would be a fan-out storm, so I gate on a follower threshold and pull celebrities' posts at read time, merging them in. Timelines store IDs not objects so a viral post is one cached object. On top, a multi-stage ML ranker reorders the candidate set. The costs I'd watch are timeline-cache RAM and fan-out lag, and I'd guarantee read-your-own-writes by merging the author's own recent posts."
