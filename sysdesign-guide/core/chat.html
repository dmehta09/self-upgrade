Core · WhatsApp / Messenger

Design a chat system.

Real-time messaging flips request/response: the server must push a message the instant it arrives. That one requirement pulls in persistent connections (WebSockets), a registry to find which gateway holds a user's socket, careful delivery/ordering guarantees, and presence. The deep truth at scale: connections are nearly free if you use epoll — the engineering goes into fan-out.

01  Requirements & scale

✅

Functional

1:1 and group messaging; delivered/read receipts; online presence; history; offline delivery (deliver on reconnect); multi-device.

📐

Non-functional

Feels instant; hundreds of millions of concurrent connections; messages never lost and ordered within a conversation; available + horizontally scalable.

02  Capacity estimation

QuantityAssumptionResult
Message rate100B msg/day (WhatsApp scale), peak 3–5×~1.16M/s avg → ~3.5–6M msg/s peak
Concurrent connections~300M onlineat 1M conns/box → ~300+ gateway boxes (+ redundancy)
Memory/connectionepoll + zero-copy ≈ 4–5 KB (naive 10 MB!)1M conns ≈ ~4 GB socket state — trivial on a 64 GB box
Real ceilingnot RAMfile descriptors, ephemeral ports, msg rate (CPU)

Real data point: WhatsApp ran ~1M connections/box (demonstrated 2M) and 147M peak concurrent on ~550 servers — with ~50 engineers. Connection memory is cheap with epoll; fan-out (group + presence) is what you optimise.

03  API & transport

WSsend(conv_id, client_msg_id, ciphertext)client → server over the open socket
WSreceive / delivery_ack / read_receiptserver → client push; receipts fan back to sender

WebSocket is the fit: one full-duplex TLS connection, low per-message overhead, server-initiated push. Long-poll is the fallback through hostile proxies (higher latency); SSE is server→client only (fine for presence, no native send path). Use WebSocket with long-poll fallback.

04  Data model

messages (wide-column)
partition key (conversation_id, time_bucket), clustering key = sequence/timestamp. "Last N in conversation X" is a single-partition range scan, not a scatter-gather. Why wide-column (Cassandra/ScyllaDB/HBase): append-heavy, time-ordered, range-read — exactly the LSM-tree sweet spot (memtable → immutable SSTables sustains very high write rates).
conversation_membership
conv_id → [user_ids] and reverse.
mailbox / device_sessions
per-user offline queue (TTL ~30 d); user_id → [device → {gateway, last_seen}] for multi-device. WhatsApp historically kept only in-transit state (Mnesia), deleting messages after delivery.

05  Routing a message across gateways

The core question: the recipient's socket lives on gateway G2, the sender on G1. On connect, each gateway writes user → {gateway, conn} into a session registry (Redis / consistent-hashed store). To deliver, look up the recipient's gateway and route via a pub/sub backplane; that gateway writes the frame to the local socket. Offline → mailbox + push.

route.py
def handle_send(sender, conv_id, client_msg_id, ciphertext):
    if dedup.seen(conv_id, client_msg_id):              # at-least-once -> effectively-once
        return ack(dedup.server_id(conv_id, client_msg_id))

    seq = seq_allocator.next(conv_id)                   # monotonic PER CONVERSATION (cheap)
    msg = Message(conv_id, seq, sender, client_msg_id, ciphertext, ts=now())

    store.append(conv_id, seq, msg)                     # STORE-BEFORE-ACK: durable first
    dedup.record(conv_id, client_msg_id, msg.id)
    ack_to_sender(sender, client_msg_id, seq)           # only NOW ack the sender

    for r in members(conv_id):                          # 1:1 -> one; group -> G recipients
        route_to_recipient(r, msg)

def route_to_recipient(user, msg):
    sess = session_registry.get(user)                  # user -> {gateway, conn} or None
    if sess and sess.alive:
        backplane.publish(sess.gateway, msg)           # cross-gateway hop
    else:
        mailbox.enqueue(user, msg)                     # offline queue (TTL ~30d)
        push.notify(user, msg.meta)                    # APNs / FCM wake-up

06  Delivery, ordering & groups

At-least-once + dedup
Reconnects cause resends; the client_msg_id is the idempotency key — "already seen → skip + re-ack."
Ordering
A per-conversation monotonic sequence (not global — users only order within a conversation, so it's one cheap counter per partition). Clients reorder by seq.
Store-before-ack
Persist durably before acking the sender, so a crash never loses a message. (A latency-optimised variant acks first and persists via a Kafka consumer — faster ack, small loss window. State the trade-off.)
Receipt ladder & groups
sent (one tick) → delivered (two ticks) → read (blue) — separate flows. Groups fan out to each member's inbox; large groups deliver one copy per gateway then fan out locally (turning "10k across 50 gateways" into 50 cross-network sends), the way Discord's Manifold parallelizes fan-out.

07  Presence & failure modes

🟢

Presence is expensive

Heartbeats update last_seen in Redis. One presence change notifies all F subscribers → N×F amplification that dwarfs message traffic (presence fires far more often than messages). Mitigate: reuse the existing socket for presence frames, coalesce/batch updates, and subscribe only to visible conversations.

💥

Gateway crash

Sockets drop; clients reconnect to any gateway (state is external — no pinning), re-register, and resume from last seq (server replays after it). Persist-before-ack prevents loss.

🌩️

Reconnect storm

A region failure makes millions reconnect at once, keeping the fleet down longer than the outage. Use exponential backoff with jitter, server Retry-After hints, staggered token TTLs, and edge admission control.

🐌

Slow consumers

A client that can't drain its socket must not OOM the gateway — apply back-pressure and load-shedding (Discord uses GenStage).

08  Multi-region, E2E, observability & cost

Multi-region
Connect to the nearest gateway region (GeoDNS/anycast); the session registry is region-aware so cross-region pairs route over the backplane. Messages favour availability + eventual consistency (per-conversation order preserved via seq); Cassandra/ScyllaDB give multi-DC replication natively.
E2E encryption
Signal Protocol (X3DH/PQXDH + Double Ratchet). The server routes ciphertext only — it can't read, search, rank, or moderate content; it still sees metadata (who→whom, when). Push carries placeholders, decrypted on-device.
Observability & cost
Message delivery latency p99 (headline SLO), concurrent-connection count, reconnect rate (spike = failure/storm), undelivered-mailbox depth, per-conversation seq gaps (loss detector). Cost = persistent-connection memory (cheap with epoll: ~1.5 TB for 300M conns) but is dominated by fan-out CPU/network — which is why these systems run on tiny teams using BEAM/epoll gateways.

09  Trade-offs & interview recap

Why are WebSockets preferred over plain HTTP request/response for chat delivery?

Right: chat needs server-initiated delivery. A persistent WebSocket lets the server push instantly; with plain request/response the client would have to keep asking "anything new?", adding latency and load.
Say this to nail it

"Persistent WebSockets on a gateway fleet, with a session registry mapping user → gateway and a pub/sub backplane to route across gateways. Persist before ack so messages are never lost; order with a per-conversation sequence; dedup by client message id for at-least-once. Offline → mailbox + APNs/FCM. The hard part isn't connections — those are ~4 KB each with epoll — it's fan-out: group delivery is O(members) and presence is N×F, so I deliver one copy per gateway and coalesce presence. Cross-region uses a region-aware registry; E2E means the server only ever handles ciphertext."
