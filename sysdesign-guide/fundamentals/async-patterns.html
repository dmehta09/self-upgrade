CQRS, outbox, sagas & idempotency.

Once you leave a single database transaction, "update A and B together" becomes a distributed problem. The patterns below — CQRS, the transactional outbox, sagas, and idempotency keys — are how mid-senior designs keep money and inventory correct without 2PC. You'll reuse them on every checkout and payments case.

01  CQRS — separate write model from read model

Command Query Responsibility Segregation means: writes go to a normalized source of truth; reads come from one or more denormalized projections tuned for the query. The two models sync asynchronously (events / CDC).

✍️

Write side

Orders, inventory reservations, ledger entries — strong invariants, few indexes, optimized for correctness and conflict detection.

📖

Read side

Catalog search, order history, "my feed" — denormalized, cached, eventually consistent. Rebuildable from the event stream.

When to reach for it

Read and write shapes diverge hard (e-commerce catalog vs checkout), or you need many read models from one write stream (audit, search, analytics). Skip it for CRUD apps where one Postgres table serves both. See checkout (write) vs catalog (read).

02  Transactional outbox — reliable events without 2PC

The dual-write trap: write the DB, then publish to Kafka. Crash between them → lost event or orphan event. The outbox fixes it: in one local transaction, write the business row and an outbox row; a relay (poller or Debezium CDC) publishes to the bus.

Canonical on payments and checkout: order state + outbox event share one local transaction so a crash never silently drops "order.placed."

03  Sagas — choreography vs orchestration

A saga is a long-running business transaction across services: each local step has a compensation (semantic undo). Prefer sagas over distributed 2PC for anything spanning inventory, payment, and order.

Orchestration
A central orchestrator (checkout service, Temporal workflow) tells each participant what to do next and runs compensations in reverse on failure. Easy to visualize and debug; orchestrator is a coordination hotspot (make it durable).
Choreography
Services react to each other's events ("InventoryReserved" → Payment listens). No central brain; coupling moves into the event graph. Harder to see the whole flow; watch for cyclic surprises.
Say the compensation

Every forward step needs a named undo: reserve → release; authorize → void; capture → refund. If the release fails, the hold's TTL is the backstop. Walk this on the whiteboard for checkout — interviewers grade the unhappy path.

04  Idempotency keys & the exactly-once illusion

Networks retry. Clients double-click. Workers redeliver. At-least-once delivery is the realistic default; exactly-once end-to-end across independent systems is an illusion you approximate with idempotency.

Idempotency key
Client-generated UUID on "create payment / place order." Server stores key → result; a retry returns the original outcome instead of charging twice. Same pattern at the PSP boundary.
At-least-once
Message may arrive twice. Consumers must be safe to replay (dedupe table, upsert, or natural uniqueness).
"Exactly-once"
In practice: at-least-once + idempotent handler (+ maybe transactional consume). Kafka EOS is within the log/consumer group — not a free pass across your DB and a card network.

The payment API times out after you called the PSP. What's the safe next move?

Right: a timeout is an unknown, not a failure. The same key makes the PSP return the original result; a new key risks a double charge. Park in a transitional state and reconcile — see payments.
One sentence that lands

"I don't promise exactly-once across the wire — I promise at-least-once delivery plus idempotent handlers keyed by a client idempotency id, with an outbox so the event isn't lost between commit and publish."
