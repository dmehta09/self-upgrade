Consistency, CAP & PACELC.

When data lives on many machines, "what's the current value?" stops being obvious — different replicas can briefly disagree. Consistency is the promise about how fresh a read is. CAP and its 2026-standard refinement PACELC tell you the unavoidable trade-offs. This is the concept interviewers probe hardest, so we'll make it concrete.

01  Strong vs eventual consistency

Two ends of a spectrum:

🎯

Strong consistency

Every read returns the most recent write, always. Simple to reason about, but requires coordination between replicas — which costs latency and availability.

🌊

Eventual consistency

Replicas may briefly disagree, but converge "eventually" (usually milliseconds). Fast and highly available; you must tolerate reading slightly stale data.

In plain English analogy

Two bank tellers sharing one ledger. Strong: they lock the book so only one writes at a time — never wrong, sometimes you wait. Eventual: they each scribble in their own copy and reconcile every few seconds — never blocked, but for a moment your balance might look off. A bank picks strong; a "likes" counter happily picks eventual.

Between those poles sit precise models (linearizability, sequential consistency) and per-client session guarantees. Interviewers care that you pick the right word, not that you recite a textbook.

02  Linearizability vs sequential vs eventual

These three words get swapped carelessly. Use the precise one — interviewers notice:

Linearizability (strict / "strong")
There is a single global real-time order. Once a write completes, every subsequent read (any client, any replica) sees it — as if one copy existed. Requires coordination (leader, consensus, or quorum with W+R>N). Say this for money, inventory locks, leader election, and "acceptOffer must be exactly-once."
Sequential consistency
Operations from all clients appear in some total order that respects each client's program order — but that order need not match wall-clock time. Rarer in product talk; useful when you mean "ordered, but not real-time fresh." Don't say it unless you mean it.
Eventual consistency
Replicas converge if writes stop; for a while, different clients can see different values. No global "now." Say this for feeds, likes, presence, shopping carts, CDN objects — and always name the conflict policy (LWW, CRDT, merge).

"I'd make acceptOffer linearizable (single-owner shard / consensus) so a driver is never double-booked, but the location stream is eventually consistent — a 4-second stale fix is fine and self-heals." Per-data-type, not per-system.

03  Session guarantees

Full linearizability is expensive. Many products only need guarantees for one client session — the middle ground that feels "correct" without global coordination:

Lab: pick the guarantee

Walk these aloud. (1) User edits a profile, refreshes, and sees the old bio → missing RYOW (route reads to the write replica or home region). (2) Feed shows post #50, refresh shows #48 → missing monotonic reads (sticky replica or version watermark). (3) Parent comment missing while the reply is visible → missing causal (store dependency or deliver via a single ordered log per thread). Session guarantees are the cheapest "feels consistent" fix — name them before escalating to linearizable.

A user posts a tweet, immediately opens their profile, and the tweet is missing — but other users already see it. Which guarantee failed for the author?

Right: others seeing it proves the write landed somewhere; the author just read a lagging replica. Fix RYOW (sticky primary / merge own recent posts) without paying for full linearizability.

04  Tunable consistency with quorums

Leaderless stores (Dynamo, Cassandra) dial freshness with N replicas, write quorum W, read quorum R. If W + R > N, every read overlaps a write and you get strong-ish freshness without a single leader. Dial W/R and break replicas yourself — same lab as on the replication page:

Three experiments

(1) W=1, R=1, lag a replica, write, read — catch a stale read. (2) Partition one replica, "Write to far side" with W=1, heal — split-brain / LWW. (3) Same with W=2: the far side can't reach quorum and refuses — that refusal is the CP choice.

05  The CAP theorem

CAP says: when a network partition happens (some machines can't talk to others — and at scale, it will), you must choose between two of three:

C — Consistency
Every read sees the latest write (or an error).
A — Availability
Every request gets a non-error response (possibly stale).
P — Partition tolerance
The system keeps working despite dropped messages between nodes.

Since partitions are a fact of distributed life, P is non-negotiable — so the real choice during a partition is C vs A:

  • CP (consistency over availability): refuse requests on the minority side rather than risk stale data. Banking, inventory, locks.
  • AP (availability over consistency): keep answering everywhere, reconcile later. Feeds, likes, shopping carts, presence.

06  PACELC — the part interviewers want in 2026

CAP only describes behaviour during a partition — which is rare. PACELC adds the everyday case: "if Partition, then A or C; Else (normal operation), Latency or Consistency." Even with a healthy network, keeping replicas in lockstep costs latency. So the deeper trade-off is constant: how much latency will you pay for fresher reads?

How to use this in an interview

Decide per-data, not per-system. In one design you might keep payments strongly consistent and the activity feed eventually consistent. Saying "I'd use strong consistency here because a double-charge is unacceptable, but eventual for the like-count because a 2-second lag is invisible" is exactly the judgement they're listening for.

During a network partition, a shopping-cart service keeps accepting "add to cart" on both sides and merges later. Which choice is that?

Right: staying available on both sides and reconciling later is the AP choice — a great fit for carts, where losing a "stay available" moment costs sales and the rare merge conflict is easy to resolve.
