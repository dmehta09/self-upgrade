Expert · multi-tenant SaaS

Design a multi-tenant SaaS architecture.

One codebase and one fleet serving thousands of isolated customers. The defining decision is isolation vs density: how strongly do you separate tenants, and how many can you pack onto shared infrastructure? Get it wrong one way and you bleed money; the other way and one tenant's bad query — or worse, a missing WHERE tenant_id — leaks another tenant's data. The 2026 answer is tiered isolation: pool the long tail, silo the whales.

01  Requirements & scale

✅

Functional

One application serves many tenants (companies/workspaces). Each sees only its own data, config, and branding. Onboard a tenant in seconds; offboard (export + delete) cleanly.

📐

Non-functional

Hard tenant isolation (no cross-tenant leak — ever), high density/low cost for small tenants, no noisy-neighbour starvation, per-tenant compliance/residency, and migrations that don't take everyone down at once.

The whole design hangs on one question: what is the tenant boundary, and how is it enforced on every read and write?

02  Isolation models: silo, pool, bridge

Tiered isolation is the staff answer: the same code, and the tenant's tier in the catalog decides its footprint — pool for self-serve, silo for enterprise, with a migration path between them.

03  Capacity & density

Density is why pooling exists. Worked example for 10,000 small tenants (a few MB, low QPS each):

ModelPacking~DB cost/tenant/mo
Pool (shared tables)10,000 tenants in 1 DB~$180/mo ÷ 10k ≈ $0.018
Silo (DB per tenant)~100 small DBs/instance → ~100 instances*~$18,000/mo ÷ 10k ≈ $1.80 (~100×)
Schema-per-tenantshared catalog bloats"won't scale past a few hundred"

*Connection pooling is the real silo killer: PgBouncer pools are per database, so 10k DBs blow past max_connections long before storage matters. Pooling wins by ~1–2 orders of magnitude for small tenants; silo earns its cost only where per-tenant revenue + compliance justify it.

04  Data model: tenant_id everywhere

The discriminator
Every business table carries tenant_id NOT NULL; it's the leading column of every composite index and PK ((tenant_id, id)) and the shard/distribution key. FKs stay within a tenant.
The tenant catalog (control plane)
Authoritative registry: tenant_id → {tier, isolation model, shard/cell, region, feature flags, plan limits, KMS key}. Every request resolves identity → catalog → connection target.
Shared vs per-tenant config
Global reference data (countries, plans) in shared tables; per-tenant config (flags, limits, branding) keyed by tenant_id.

05  Tenant routing & context propagation

Resolve the tenant once at the edge, then enforce it automatically at every layer. Never trust a tenant id from the request body — derive it from the subdomain, a verified JWT claim, or the API key.

Automated onboarding (manual doesn't scale): create the catalog record → provision shard/schema/DB → configure DNS → apply default flags + limits → welcome email.

06  Pool isolation with Postgres RLS

In the pool model, the discriminator is just an app convention — one missing WHERE tenant_id anywhere = a breach. Push the predicate into the database with Row-Level Security so the engine enforces it even if the app forgets.

rls.sql
-- App connects as a NON-OWNER, non-superuser role (owners/superusers bypass RLS).
ALTER TABLE events ENABLE ROW LEVEL SECURITY;
ALTER TABLE events FORCE  ROW LEVEL SECURITY;          -- apply even to the table owner

CREATE POLICY tenant_isolation ON events TO application
  USING      (tenant_id = NULLIF(current_setting('app.current_tenant', TRUE), '')::uuid)
  WITH CHECK (tenant_id = NULLIF(current_setting('app.current_tenant', TRUE), '')::uuid);
-- USING filters reads/updates/deletes; WITH CHECK blocks writing into another tenant.

-- Per transaction: SET LOCAL (not SET) so the value dies at COMMIT and never
-- leaks across a pooled (PgBouncer) connection to the next tenant's request.
BEGIN;
  SET LOCAL app.current_tenant = 'c4062d63-...';
  SELECT * FROM events;        -- unscoped query, engine scopes it to this tenant
COMMIT;
The three RLS footguns

(1) Table owners and superusers bypass RLS unless you FORCE it and connect as a non-owner role; (2) any role with BYPASSRLS ignores policies — the app role must have neither; (3) plain SET persists on a pooled connection → the next request inherits the previous tenant's GUC → leak. Use SET LOCAL. RLS is defense-in-depth: keep ORM/query-rewrite scoping and RLS.

07  The noisy-neighbour problem

Pooling shares CPU, memory, disk IO, connections, and locks — so one tenant's spike can starve the rest. Mitigations, by contention vector:

Per-tenant rate limits / quotas
Token-bucket at the gateway; return 429 early (backpressure) rather than degrading everyone. Salesforce's "governor limits" (e.g. 100 SOQL / 50k rows per transaction) are the canonical example.
Connection-pool partitioning
Cap concurrent DB connections per tenant by tier (e.g. Enterprise 50 / Basic 5) so no tenant floods the pool; per-tier statement_timeout.
Fair queuing
Weighted round-robin on async work so a free tenant gets a small share but is never fully starved.
Tier the hot tenant
When a pooled tenant outgrows fair-share, promote it to its own silo/cell — the bridge model as an escape hatch.

08  Sharding tenants & cell architecture

Shard by tenant_id (e.g. Citus distribution column) so all of a tenant's rows + co-distributed tables live on one node → local joins, no cross-node traffic; reference tables replicate everywhere. A tenant can be rebalanced by relocating its shard.

Cells bound the blast radius

A cell is a complete, self-contained stack serving a subset of tenants, with a fixed capacity ceiling — you scale by adding cells, not growing them. With N cells, a single-cell failure hits at most 1/N of tenants (10 cells → ≤10% impact). A thin routing layer maps tenant→cell (consistent hashing so adding a cell remaps ~1/N), you deploy cell-by-cell in waves (bad deploys are contained too), and shuffle sharding assigns each tenant a distinct combination of cells so two tenants rarely share the same set. Pin a cell to one region for residency.

09  Migrations & schema drift

🟢

Pool

Migration runs once for everyone — the operational win. Risk: a long-locking DDL hits all tenants at once → use online expand-contract, CREATE INDEX CONCURRENTLY, batched backfills.

🟠

Schema/DB per tenant

The same migration must run across thousands of schemas/DBs → per-tenant version tracking, partial failures, and schema drift (a tenant stuck on an old version) become the dominant ops cost; catalog bloat slows every query.

10  Compliance, residency & per-tenant keys

Residency
Silo makes it trivial (host the tenant DB in-region). In pool/cell, pin residency at the cell/shard level — group EU tenants into EU cells, US into US cells.
Per-tenant encryption / BYOK
One customer-managed KMS key per tenant (~$1–3/mo each → key sprawl is real); BYOK / external key store lets the customer hold the key and crypto-shred (revoke the key → data is inert) — the fastest compliant "delete" at scale, and a premium-tier feature.
Export / delete
Because tenant_id threads every table, export/delete is scoped by it (pool) or a DB drop (silo). Enumerating every table is a data-model completeness problem.

11  Observability & cost

Cross-tenant leak detection
RLS as a backstop; automated tests asserting tenant A can't read tenant B; lint/ORM guards that every query carries a tenant predicate; alert if any query returns rows whose tenant_id ≠ the session tenant.
Tenant-aware telemetry
Stamp tenant_id on every metric, log line, and trace span. Track latency/error/throughput per tenant and per tier so a noisy tenant is visible and SLOs can differ by tier.
Cost per tenant
Silo segments cost by account naturally; pool requires metering actual consumption (requests, compute-s, storage, IO) and apportioning shared cost — the unit-economics number that decides pricing.

12  Trade-offs & interview recap

In the pool model, what's the single most dangerous failure, and the primary defense?

Right: logical isolation means one forgotten predicate = cross-tenant breach. RLS pushes the filter into the engine as defense-in-depth — but only if you FORCE it, connect as a non-owner role with no BYPASSRLS, and set the tenant with SET LOCAL so it doesn't leak across pooled connections.
Say this to nail it

"I'd default to tiered isolation: pool small tenants (shared tables, tenant_id on every row, Postgres RLS as a hard backstop) for density, and silo enterprise/regulated tenants for isolation + residency + BYOK. Resolve the tenant once at the edge from the subdomain or a verified claim — never the body — and propagate context so every query is scoped. I'd shard by tenant and group tenants into cells to bound the blast radius to 1/N, rate-limit per tenant to kill noisy neighbours, and meter per-tenant cost for unit economics. The one thing I never compromise is the tenant predicate — RLS plus tests that prove A can't read B."
