Expert · authorization

Design authorization.

"What can you do?" — the decision made on every request, often many times per request, that decides whether a known principal may act on a resource. The arc of the field is RBAC → ABAC → ReBAC: from coarse roles, to attribute policies, to Google Zanzibar's relationship graph that powers Drive/Docs-style per-object sharing. This is the canonical permissions page; authentication proves identity, and this consumes it.

01  Requirements & the three models

✅

Functional

check(user, action, resource); answer "who can access X?" and "what can U access?"; scoped per tenant/org; policy + relationship changes are audited.

📐

Non-functional

On the hot path → single-digit-ms p99 even with fan-out; correct (no cross-tenant or stale-after-revoke leaks); fails closed.

Sequencing: start with RBAC for coarse policy; add ABAC only for genuine contextual rules; add ReBAC only when users share resources with each other. Modern engines (Cedar, SpiceDB, OpenFGA) express all three.

02  RBAC deep dive

Users → roles → permissions, with the role assignment scoped per org (the binding lives on the membership, not the global user):

rbac.sql
roles(id, org_id, name)                       -- roles are tenant-scoped
permissions(id, resource, action)             -- e.g. ('document','edit')
role_permissions(role_id, permission_id)
user_roles(user_id, org_id, role_id)          -- the (user, org) -> role binding

-- The permission check (flat). The org_id predicate is what prevents escalation.
SELECT EXISTS (
  SELECT 1 FROM user_roles ur
  JOIN role_permissions rp ON rp.role_id = ur.role_id
  JOIN permissions p       ON p.id = rp.permission_id
  WHERE ur.user_id = :user AND ur.org_id = :org      -- MANDATORY tenant scope
    AND p.resource = :resource AND p.action = :action
);

NIST role hierarchies (senior inherits junior) handle role→role inheritance; that's different from resource-hierarchy inheritance (folder→doc), which is fundamentally ReBAC.

03  Zanzibar / ReBAC: the relationship graph

Zanzibar (Google) stores ACLs as relation tuples object#relation@user, e.g. doc:readme#viewer@user:anne. A userset (@group:eng#member) points at a set; rewrites compute relations — computed_userset (viewer ⊇ editor) and tuple_to_userset (a doc's viewers = its parent folder's viewers — the inheritance primitive). Check is graph reachability:

Anatomy of a relation tuple
One grammar expresses direct grants, group membership, and folder→doc inheritance — which is why a single Check API can answer any per-object sharing question.
check.py
# Zanzibar-style Check via graph walk (object#relation@user)
def check(obj, relation, user, seen):
    if (obj, relation) in seen: return False          # cycle guard
    seen.add((obj, relation))
    rule = config[obj.type][relation]                 # the rewrite

    for t in tuples(obj, relation):                   # 1) direct tuples
        if t.user == user: return True
        if t.is_userset and check(t.group, t.rel, user, seen):  # group:eng#member
            return True
    for r2 in rule.computed_usersets:                 # 2) same object, e.g. viewer⊇editor
        if check(obj, r2, user, seen): return True
    for ttu in rule.tuple_to_usersets:                # 3) inheritance: doc -> parent folder
        for t in tuples(obj, ttu.tupleset_relation):  # doc#parent@folder:Y
            if check(t.target, ttu.computed_relation, user, seen): return True
    return False

For deeply nested groups, the recursive walk is too slow → the Leopard index precomputes a flattened, transitively-closed membership set and answers "is U in G?" as a set intersection. 2026 implementations: OpenFGA (CNCF Incubating), SpiceDB (Authzed, full set algebra + arrow inheritance), Ory Keto, AWS Cedar / Verified Permissions.

04  Consistency: the "new enemy" problem

Why a global ordering matters

Alice removes Bob from a doc, then adds sensitive content. If a check reads a stale ACL replica, Bob — the "new enemy" — sees content he should never have. Zanzibar runs on Spanner/TrueTime for external consistency and hands clients a zookie (an opaque timestamp): pass it on a check to demand "at least this fresh," so a check observes all ACL writes causally prior to the content it protects. SpiceDB calls it a ZedToken; the consistency knobs are fully_consistent / at_least_as_fresh / minimize_latency.

05  Policy-as-data vs policy-as-code; PEP/PDP/PIP

The reference architecture: the PEP (enforcement point — your middleware/gateway) asks the PDP (decision point) "allowed?", which evaluates policy using data from the PIP (information point — attributes/tuples).

Policy-as-code: OPA/Rego (general PDP, often a sidecar), Cedar (AWS; PARC model, statically analyzable, "RBAC+ABAC+ReBAC in one language"), Casbin. Policy-as-data: the decision is a relationship lookup (Zanzibar/OpenFGA/SpiceDB). Centralized PDP = simple to audit but a hop + SPOF (make it HA); sidecar = sub-ms, no hop, but you must distribute policy + data to every node.

06  Performance: the hot path

Authz runs on every request, often many times (a list page → N object checks: the "N+1 authz" problem). The budget is brutal:

QuantityAssumptionResult
Authz QPS50k req/s × ~8 checks/req≈ 400k checks/s — batch the fan-out
Latency budgetp99 API budget ~200 mseven a 20 ms check is 10% per check → cache + denormalize
Zanzibar published>2 trillion tuples, >10M QPSCheck p50 ~3 ms / p99 ~20 ms, >99.999% avail

Mitigations: cache decisions (and sub-results), denormalize/precompute (Leopard-style flattened membership), batch the fan-out, and read from bounded-staleness replicas (at_least_as_fresh) rather than fully-consistent every time.

07  API, multi-tenancy & failure modes

CHECKcheck(user, action, resource) · batch-check([…])the hot-path decision; batch cures N+1
EXPANDexpand(obj, rel) · list-objects(user, action)"who can access X?" / "what can U access?"
Multi-tenancy
Every tuple/role is scoped to a tenant (prefix object ids tenant_42/doc:readme or carry org_id and predicate every check). The cardinal bug is a check resolving across a tenant boundary — make tenant scope a non-optional parameter.
Fail-closed vs fail-open
On PDP outage, fail-closed (deny) for security-sensitive systems; mitigate the availability cost with HA + local cache (fail-static = serve last-known-good), not by failing open.
Other failure modes
Stale-after-revoke (the new-enemy problem — bound staleness); role explosion / over-broad roles (least privilege); confused deputy — always thread the caller's identity into the check, never act with ambient service authority.

08  Observability & 2026

Metrics
Decision latency p50/p99 + batch sizes (watch N+1 fan-out); allow/deny rates (a deny spike = misconfig/attack, an allow spike = policy regression); policy/tuple change audit log (who changed what, when); decision logging (principal, action, resource, decision, policy version) for forensic replay.
Reverse-query reporting
expand/list-objects drive access reviews ("who has access to X?", "what can U access?") for offboarding + least-privilege audits.
2026
Zanzibar-inspired ReBAC (OpenFGA / SpiceDB / Cedar) is the modern standard for fine-grained, sharing-heavy authz; externalized PDPs over scattered if user.is_admin checks; AWS Bedrock AgentCore Policy (Cedar) extends authz to AI agents.

09  Trade-offs & interview recap

Your product is Google-Docs-style: any user can share any document with any other, and folders grant access to the docs inside them. Which model?

Right: per-object, per-user, hierarchical sharing is exactly what RBAC can't express (you'd need an unbounded role per document). ReBAC models access as a graph — "is Anne related to this doc via viewer, possibly through its parent folder or a group?" — answered by reachability.
Say this to nail it

"I'd start with org-scoped RBAC for coarse policy, then reach for ReBAC if the product has per-object sharing — Zanzibar relationship tuples with computed-userset and tuple-to-userset rewrites for inheritance, where Check is a graph walk. I'd externalize it into a PDP (OpenFGA/SpiceDB/Cedar) behind a PEP, batch checks to kill N+1, cache decisions within a freshness bound (zookies prevent the new-enemy stale-revoke leak), and fail closed. Every check carries the tenant scope and the caller's identity to avoid cross-tenant leaks and confused-deputy bugs."
