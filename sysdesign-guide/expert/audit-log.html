Expert · audit log & activity feed

Design an audit log / activity feed.

Two systems that share an ingestion path but diverge hard on guarantees. A compliance audit log optimizes for durability, immutability, tamper-evidence, and multi-year retention — every privileged action, provable to an auditor. A product activity feed ("Sarah commented on your doc") optimizes for read latency and freshness. Conflating them is the #1 smell: build one immutable write path, then derive the user-facing feed as a projection off it.

01  Requirements & scale

✅

Functional

Append an event (who/what/when/where/outcome); query by actor/resource/time for compliance; export for auditors; serve a per-user/per-resource activity feed.

📐

Non-functional

Never lose an event (durability is paramount); tamper-evident (an admin can't quietly edit history); append-only; multi-year retention; tenant-scoped.

QuantityAssumption (10M MAU, audit-everything)Result
Event rate~50 auditable actions/user/day~5,800/s avg, ~30k peak (large platforms: billions/day)
Volume~1 KB/event~500 GB/day raw → 6-yr HIPAA ≈ ~1.1 PB
Cold costGlacier Deep Archive ~$1/TB-mo vs S3 Std ~$23/TB-mo~23× cheaper → the reason for hot/cold tiering

02  API & data model

POST/v1/eventsIdempotency-Key: … → { id, seq, hash }
GET/v1/events?actor=&resource=&from=&to=&tenant=compliance query (cursor-paginated, tenant-scoped)
GET/v1/verify?from_seq=&to_seq= · /v1/feeds/{user}chain consistency proof; activity-feed read

The event is structured and immutable — who (actor: type/id/name), what (namespaced action + before/after diff), when (UTC + a monotonic per-tenant seq for gap detection), where (ip, user-agent, request/trace id, tenant_id), outcome (success/denied/error), plus prev_hash + hash + signature. This maps ~1:1 to AWS CloudTrail and WorkOS Audit Logs.

03  Architecture & ingestion

Don't lose events, don't block the business transaction, don't 2PC across DB + Kafka. The answer is the transactional outbox: write the audit row in the same DB transaction as the business change; a CDC relay ships it onward. The immutable store is the system of record; search + feed are disposable, rebuildable projections.

04  Tamper-evidence: hash chaining

Each entry binds the previous one: entry.hash = H(prev_hash ‖ payload). Edit any entry and its hash changes — which breaks every entry after it. You can't silently alter the middle (exactly how AWS CloudTrail's chained, signed digest files and QLDB's journal worked):

chain.py
import hashlib, json
GENESIS = "00" * 32

def entry_hash(prev_hash, payload):
    h = hashlib.sha256()
    h.update(bytes.fromhex(prev_hash))                    # bind the predecessor
    h.update(json.dumps(payload, sort_keys=True,          # DETERMINISTIC serialization
                         separators=(",", ":")).encode()) #   or hashes won't reproduce
    return h.hexdigest()

def append(log, payload):
    prev = log[-1]["hash"] if log else GENESIS
    log.append({"seq": len(log), "payload": payload,
                "prev_hash": prev, "hash": entry_hash(prev, payload)})  # never mutate prior

def verify(log):
    prev = GENESIS
    for e in log:
        if e["prev_hash"] != prev:                  return False   # chain broken
        if e["hash"] != entry_hash(prev, e["payload"]): return False   # entry tampered
        prev = e["hash"]
    return True

At scale, a Merkle tree beats a flat chain — inclusion + append-only consistency proofs are O(log n) (the RFC 9162 Certificate-Transparency model; ~30 hashes for billions of entries).

05  Anchoring, WORM & retention

Anchoring / notarization
Hash chaining alone is defeatable by an operator who rewrites the whole chain — so publish the current Merkle root (a signed checkpoint) to an external witness on a cadence (a second account, a customer bucket, a transparency log). Once witnessed, history up to that checkpoint is frozen.
WORM at rest
S3 Object Lock in compliance mode — can't be overwritten or deleted by anyone, including the root user; the retention period can't be shortened. Cohasset-assessed for SEC 17a-4 / FINRA. This is what makes the log evidentiary.
Hot / cold tiering
Hot (~90 days) in OpenSearch for investigations; cold (years) in S3 Object Lock → Glacier Deep Archive (cheap, slow restore — for "auditor asks once a year"). Time-partition so expiry is a partition drop; legal hold overrides retention. Design to the strictest bar: PCI ≥12 mo (3 mo hot), HIPAA 6 yr, SOX ~7 yr.

06  Query, the feed & consistency

🔎

Compliance search

Filter by actor/resource/action/time/outcome, tenant-scoped (mandatory tenant_id filter — cross-tenant leakage in a shared log is the catastrophic bug). The compliance log never fans out — it's query-on-read.

📰

Activity feed

This is the news-feed problem — hybrid fan-out (push for normal actors, pull for high-fan-out), and the feed may aggregate ("3 people liked this") and expire. Only the product feed fans out.

🔒

Append-only & GDPR

No updates, no deletes — corrections are new entries. GDPR erasure ≠ delete: crypto-shred (encrypt PII per subject, destroy the key) so hashes/integrity proofs over ciphertext stay intact. (Whether that legally counts as erasure is unsettled — get counsel sign-off.)

🧮

Gap detection

Monotonic seq + empty checkpoints (CloudTrail emits a digest even for zero-activity hours) make "nothing happened" provable, not assumed.

07  Failure modes, observability & 2026

Failure modes
Dropped events / chain gaps (seq-gap alert = Sev incident; outbox replay); ingestion lag (autoscale, backpressure — never drop); chain-verification failure (freeze writes, forensic review — a potential breach); legal-hold/retention violation (alarm on Object Lock config changes).
SLOs
Ingest durability ≥ 99.999%+ (the one that matters); end-to-end visibility lag p99 < a few minutes; compliance-search p95 < 1–2 s on hot; continuous chain verification; zero tolerance for silent event loss.
2026
CloudTrail (chained signed digests + Object Lock) is the reference; QLDB is end-of-life (Jul 2025) → teams roll hash-chaining/Merkle on commodity stores (or Azure SQL ledger / immudb); Datadog Audit Trail + Cloud SIEM; WorkOS Audit Logs as a tenant-facing model; RFC 9162 for third-party-verifiable logs.

08  Trade-offs & interview recap

An admin with database access quietly edits an old audit entry to hide an action. How does the system make that detectable?

Right: permissions and backups don't make tampering provable. Hash chaining cryptographically links entries so any edit cascades into a detectable break; WORM (S3 Object Lock compliance mode) stops even root from deleting; and anchoring a signed Merkle root externally defeats a whole-chain rewrite. That's what gives a log evidentiary value for SOC 2 / HIPAA / SOX.
Say this to nail it

"I'd separate the tamper-evident compliance log from the activity feed, sharing one immutable write path. Events arrive via the transactional outbox (so a crash never loses evidence), get hash-chained into an append-only ledger on WORM storage, with the Merkle root periodically anchored to an external witness — that combination makes tampering provable, not just discouraged. I tier hot (OpenSearch, ~90 days) vs cold (Glacier, years) for the PB-scale retention, scope every query by tenant, and handle GDPR via crypto-shredding rather than deletion since the log is append-only."
