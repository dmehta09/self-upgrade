Expert · e-commerce (write side)

Design e-commerce: checkout, inventory & orders.

The write path is all about correctness: never sell the same last item twice, never double-charge a double-click, never lose a paid order. There's no distributed ACID transaction across inventory + payment + order — so correctness comes from a saga with compensations, idempotency, an atomic stock decrement, and the transactional outbox. The read side — catalog, search & cart — is a separate page.

01  Requirements & scale

✅

Functional

Reserve stock, take payment, create an order, hand to fulfillment, track order state. Refunds + cancellation.

📐

Non-functional

Zero oversell as a hard target; exactly-once order despite retries; strong consistency where money/stock lives; survive flash-sale contention (100k req/s on one SKU).

QuantityAssumptionResult
Orders/s10M orders/day, peak 3–5×~116/s avg → ~350–580/s peak (Amazon Prime Day ~1,700/s)
Flash sale1 hot SKU, 1,000 units100k+ req/s on one row — a contention problem, not throughput
Order size~5 KB (header + lines + history)10M/day ≈ ~50 GB/day — a correctness, not storage, problem

03  The checkout saga

Checkout spans inventory + payment + order across services. No 2PC — use a saga: a sequence of local transactions, each with a compensating transaction that semantically undoes it. Orchestrate the money-critical core (a durable-execution engine like Temporal makes compensations ordinary code with crash-replay); choreograph the post-order fulfillment fan-out.

04  Inventory reservation & oversell prevention

The race: two buyers both read qty=1, both decide "in stock," both write qty=0 → you sold 2 of 1. Read-then-write without atomicity = oversell. The strategies:

reserve.sql
-- Conditional update: the WHERE guard makes oversell impossible; rows-affected is the signal.
UPDATE inventory
   SET available = available - :qty
 WHERE sku_id = :sku
   AND available >= :qty;        -- never go negative
-- rows_affected == 1 -> reserved OK ;  == 0 -> OUT OF STOCK, do NOT proceed

-- Flash sale: front the hot SKU with a Redis counter as gatekeeper (atomic DECRBY admits
-- exactly N winners); the DB only ever sees the <= N PAID orders. Reconcile periodically.
-- Shopify's 2026 design: ONE ROW PER UNIT in MySQL + SELECT ... FOR UPDATE SKIP LOCKED,
-- co-locating the reservation with the ledger so deduction is one ACID txn.

Over-sell vs under-sell: oversell → cancellations + refunds + reputational damage; under-sell → conservative TTLs + abandoned holds strand stock. Most retailers bias to never oversell and eat some under-sell — but the reaper that releases expired holds must run.

05  Order state machine + the outbox

The order is a guarded state machine: created → payment_pending → paid → fulfilling → shipped → delivered (+ cancelled / refunded), every transition appending to a history table. You can't atomically "write the order row" and "publish OrderCreated to Kafka" (two systems) — so use the transactional outbox:

place_order.sql
BEGIN;
  -- Idempotent create: a double-click carries the SAME key; the 2nd is a no-op.
  INSERT INTO orders (id, idempotency_key, customer_id, status, total)
  VALUES (:id, :key, :cust, 'paid', :total)
  ON CONFLICT (idempotency_key) DO NOTHING;
  -- Same local txn: enqueue the event in the outbox (no dual-write).
  INSERT INTO outbox (aggregate_id, event_type, payload)
  VALUES (:id, 'OrderCreated', :json);
COMMIT;
-- A relay (Debezium CDC on the WAL) ships outbox rows to Kafka within ~ms,
-- partitioned by order_id (per-order ordering). At-least-once -> idempotent consumers.

If the txn commits, the event is durably queued; if it rolls back, neither happened. Fulfillment, warehouse, and notifications consume the event and advance the order via inbound events (ShipmentDispatched → shipped).

06  Payment & consistency

PSP call outside the DB txn
Never hold a DB transaction open across a network call to Stripe/Adyen — it pins a connection and risks a DB timeout vs PSP success. Thread your idempotency key through to the PSP's key (see payments).
The "did payment succeed?" unknown state
On a PSP timeout you genuinely don't know. Don't blindly retry (double charge) or fail (lost order): retry with the same idempotency key (PSP returns the original result), leave the order in payment_pending, and reconcile against PSP records/webhooks.
Consistency
Strong where money/stock lives (atomic decrement, linearizable order/payment writes); eventual on the read side. Exactly-once is engineered as at-least-once transport + idempotent processing — there is no true exactly-once delivery.

07  Failure modes, multi-region & observability

💸

Payment ok, order write fails

Outbox + saga compensation: retry the order write; if permanently failing, idempotent refund. A reconciliation job matches PSP charges to orders.

⏲️

Reserved but abandoned

Reservation TTL + reaper (or Redis key expiry): reserved → available. Must run, or stock silently strands.

🌍

Multi-region

Per-region/per-warehouse stock pools avoid one global hot row; order + payment writes pinned to a home region for strong consistency; cross-region rebalancing async.

📊

Observability

Oversell count = 0 (hard), reservation conflict/retry rate (rows-affected=0 ratio), checkout abandonment, saga compensation rate, outbox relay lag, PSP unknown-state rate. Instrument transaction duration, not just QPS.

08  Trade-offs & interview recap

Two shoppers race to buy the last unit. How do you guarantee you don't oversell — without serializing every buyer of that SKU?

Right: read-then-write in app code is the race itself. The conditional UPDATE makes the check-and-decrement a single atomic statement, the database rejects the loser (0 rows affected), and no lock is held across application logic — so it scales far better than SELECT … FOR UPDATE under contention.
Say this to nail it

"Checkout is a saga with compensations — reserve, pay, create order — because there's no distributed ACID across those services. Stock is an atomic conditional decrement (rows-affected is the truth), with a Redis gatekeeper + queue for flash sales and a TTL'd reservation for the checkout window. Orders are idempotent on a client-generated key (double-click safe) and published via the transactional outbox so I never dual-write. The PSP call sits outside the DB txn, and the unknown-payment-state case is resolved by same-key retry + reconciliation, never a blind retry. Oversell-count-zero is my hard SLO."
