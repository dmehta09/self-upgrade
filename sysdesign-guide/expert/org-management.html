Expert · organizations & teams

Design organizations & teams.

B2B SaaS isn't one user per account — it's a company (org/workspace) full of users, with teams, roles, and invitations. The whole thing rests on one structural insight: the membership is its own entity, a join between user and org that carries the role. Get that right and every permission check is tenant-aware by construction; get it wrong and you leak roles across customers.

01  Requirements & the core model

✅

Functional

Create orgs; invite/remove members with roles; nested teams; seats for billing; ownership transfer; org-scoped resources that survive members leaving.

📐

Non-functional

A user belongs to many orgs; an org has many users — and a user's role is per-org. Membership changes are audited (SOC 2); invites can't be abused.

Why membership is its own entity

Role is not a property of the user and not a property of the org — it's a property of the edge. The same person is owner in their startup and guest in a client's org simultaneously. Putting role on the (user, org) membership makes every authz decision tenant-scoped by construction — a role literally cannot exist outside an org boundary. The org is almost always == the tenant from multi-tenancy.

02  Data model: the membership graph

The membership graph — junctions, not nesting
Many-to-many through a junction row: dana is admin of Acme; sam is a member of Acme and owner of Beta. Roles belong to the relationship — a user has no global role.
org.sql
CREATE TABLE organizations ( id uuid PRIMARY KEY, name text, slug text UNIQUE );

-- THE junction: one row = one user's relationship to one org. Carries role + status.
CREATE TABLE memberships (
  user_id           uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  org_id            uuid NOT NULL REFERENCES organizations(id) ON DELETE CASCADE,
  role              text NOT NULL DEFAULT 'member',  -- owner|admin|member|billing|guest
  status            text NOT NULL DEFAULT 'active',  -- pending|active|inactive
  directory_managed boolean NOT NULL DEFAULT false,  -- true if owned by SCIM (don't hand-edit)
  joined_at         timestamptz,
  PRIMARY KEY (user_id, org_id)                       -- a user is in an org at most once
);
CREATE INDEX idx_mem_user ON memberships(user_id, org_id);  -- "list my orgs"
CREATE INDEX idx_mem_org  ON memberships(org_id, status);   -- "list org members" + seat count

CREATE TABLE teams (
  id             uuid PRIMARY KEY,
  org_id         uuid NOT NULL REFERENCES organizations(id) ON DELETE CASCADE,
  parent_team_id uuid REFERENCES teams(id) ON DELETE CASCADE,  -- nesting
  name           text NOT NULL, UNIQUE (org_id, name)
);
-- Every tenant-owned resource carries org_id NOT NULL — the isolation invariant.

The org_id on every resource is the load-bearing invariant of shared-pool multi-tenancy; app code always filters by the session's active-org, with Postgres RLS as a backstop.

03  Roles & seats

The role ladder
owner (full control incl. delete + transfer; ≥1 always required) · admin (manage members/settings, can't destroy) · member (default) · billing · guest (external/limited). Plus custom roles (a "logical grouping of permissions"; the deep model is on the authorization page).
Per-org, not global
The role lives on the membership, so it's resolved per active org — usually baked into the session/JWT so runtime checks need no extra DB call.
Seats for billing
The membership table is the source of truth for seats. Emit a billing meter event on every add/remove/deactivate/reactivate; map to the subscription quantity; reconcile periodically (seat drift is a classic bug). Whether guest/inactive count is a product policy.

04  Nested teams & inheritance

Teams nest via parent_team_id; permission flows down the tree — a member of a parent team implicitly belongs to all descendants for access. Resources can be owned at org, team, or user level (layered inheritance with local overrides, Notion-style):

Deep, recursive permission resolution over this graph is exactly where teams migrate from RBAC to ReBAC (see authorization).

05  Invitations

The challenge: you invite an email, which may not have an account yet. So the invitation exists independently of any user, keyed by (org, email), and resolves to a membership only on accept.

accept_invite.py
def accept_invite(raw_token, user):               # user is authenticated by here
    inv = db.one("""SELECT * FROM invitations
                    WHERE token_hash = %s AND status = 'pending'
                    FOR UPDATE""", sha256(raw_token))     # row lock => single-use, no race
    if inv is None or now() > inv.expires_at:
        raise Invalid("expired or already used")
    if user.email.lower() != inv.email:           # token bound to the invited address
        raise Forbidden("invite not for this account")
    with tx():
        db.upsert(memberships, user_id=user.id, org_id=inv.org_id,
                  role=inv.role, status='active', joined_at=now())   # the grant
        db.update(invitations, id=inv.id, status='accepted')
        emit_seat_event(inv.org_id)               # bump billing quantity
        audit_log('member.invite.accepted', org=inv.org_id, actor=user.id)

The FOR UPDATE lock + a partial-unique index on (org_id, email) WHERE status='pending' together close the documented invite-race (concurrent accepts / invite-limit bypass). Domain-based JIT: an org verifies a domain via DNS TXT, then matching emails auto-join (you can't verify a public domain like @gmail.com).

06  API & the graph queries

POST/orgs/{org}/invitations · /invitations/acceptinvite by email; accept by token
GET/me/organizations · /orgs/{org}/memberships"my orgs" (idx_mem_user); "org members" (idx_mem_org, paginate)
PUT/memberships/{id} · /orgs/{org}/transfer-ownershipchange role (last-owner guard); atomic owner swap

"Who can access resource Y?" → resolve Y's org_id → members, then expand team nesting via a recursive CTE down parent_team_id (members of a parent team reach children).

07  Ownership transfer & last-owner protection

You may never delete or demote the only owner. Enforce server-side inside the same transaction, with a lock so two concurrent "demote owner" requests can't both pass:

last_owner.sql
-- Inside the demote/remove transaction, before committing:
SELECT count(*) FROM memberships
 WHERE org_id = :org AND role = 'owner' AND status = 'active'
   AND user_id != :target
FOR UPDATE;          -- must be >= 1, else abort: "org must keep an owner"

Transfer = atomic two-row update (promote new, demote old) + reassign billing contact + audit. Leaving an org and deleting an org (cascade, usually soft-delete first) hit the same guard.

08  Scale

QuantityAssumptionResult
Memberships100k orgs × ~20 members≈ 2M rows (~400 MB) — trivially indexed, never the bottleneck
"List my orgs"bounded by orgs/user (single digits)sub-ms via (user_id, org_id); cache in the session

The membership table is small; the real pressure is member-list pagination, permission resolution over team trees, and seat-count fan-out on the few giant tenants.

09  Failure, multi-region, observability & cost

Failure modes
Orphaned resources → own them at the org, not the user, so they survive departures. Invite abuse → rate-limit + hashed single-use tokens + FOR UPDATE on accept. Seat drift → reconcile membership counts vs billing. Last-owner races → lock inside the demote/remove transaction. Dual demote → both must see the same locked owner count.
Multi-region
Pin an org (tenant) to a home region for membership writes (strong, low-conflict); replicate read models for "my orgs" / member lists. Cross-region invite accept forwards to home. Residency: keep org PII and membership rows in the org's legal region.
Observability
Invite accept success / race abort rate; membership mutation lag to authz caches; seat-count vs billed seats drift; permission-check p99 over team trees; audit-log write failures (page — SOC 2). Alert on "org with zero owners" invariant breaks.
Cost
DB + indexes are cheap at millions of memberships; spend is on authz fan-out (team tree resolution, cache invalidation) and giant-tenant member-list pagination. Cache session-scoped "my orgs"; don't N+1 team inheritance on every request.
Security
Append-only membership audit log (invited / accepted / role.changed / removed / ownership.transferred) retained ~15 months. Hash invite tokens at rest; expire invites; never leak other orgs' membership via global user search without scope checks.

10  Trade-offs & interview recap

Why model role on a memberships join table instead of putting a role column on the user?

Right: a global role column can't express different roles in different orgs and invites cross-tenant role leaks. The membership edge carries role + status + provenance, and a role literally can't exist outside an org boundary.
Say this to nail it

"Three entities: user, org, and the membership edge that carries the per-org role and status — so authz is tenant-scoped by construction and the membership table is the source of truth for seats. Teams nest with parent_team_id and permissions inherit downward; deep resolution pushes me toward ReBAC. Invitations are keyed by email (the invitee may have no account), with a hashed single-use token and a FOR UPDATE accept to kill the invite-race. I protect the last owner inside a locked transaction and audit every membership change for SOC 2."
