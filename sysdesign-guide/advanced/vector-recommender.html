Design vector search & a recommender.

Modern search and recommendations rest on embeddings: turn every item and query into a point in high-dimensional space so "similar in meaning" becomes "close together." Finding good results is then "find the nearest points" — a job for approximate nearest-neighbour (ANN) indexes. Real recommenders wrap this in a two-stage funnel: cheaply retrieve candidates, then expensively rank them. This is the same shape behind 2026's RAG pipelines.

01  Embeddings & nearest neighbours

Embeddings are dense semantic vectors; nearby vectors are semantically similar (cosine / dot product). "Search" and "recommend" become the same operation: find the nearest points to the query/user.

Exact nearest-neighbour is O(N·dim) per query — for 1B × 768-dim that's ~10¹² FLOPs per query, impossible at QPS. So ANN trades a few % recall for 100–1000× speedup. Common dims: 768 (BERT-class), 1536/3072 (OpenAI text-embedding-3).

02  Capacity estimation

QuantityAssumptionResult
Raw vectors1B × 768 × 4 B (float32)≈ 3.07 TB raw
HNSW resident+ graph links (~1.5–2×)≈ 3–5 TB RAM (the cost driver)
Product quantization768-dim → 96 B/vector (~32×)≈ 96 GB (lossy → re-rank with full vectors)
DiskANN (SSD)compressed in RAM, full on SSD~64 GB RAM serves 1B @ <3 ms, 95%+ recall
Feature-store QPS1 req × hundreds of candidates × features100–1000× the recommendation QPS

The headline trade: memory dominates HNSW cost; disk dominates DiskANN. A real case compressed a 1B-vector index from a 3 TB-RAM HNSW cluster to a single 96 GB-RAM DiskANN machine (~31× less RAM) searching in ~15 ms — the cost crossover arrives well before 1B vectors.

ANN index + vector/metadata store
vectors + payload (category, price, in_stock) for filtered ANN ("similar AND in_stock"), separate from the index structure.
Feature store
precomputed + real-time features for ranking, with online (low-latency KV) / offline (training) parity — serves 100–1000× the rec QPS due to user→item fan-out.
User profile
often multiple interest embeddings per user (not one), e.g. partitioned by category.

The three families span the cost/quality triangle (recall ↑ costs latency ↑ and/or memory ↑; the curve steepens sharply from 0.95→0.99):

Knobs: HNSW's M / ef_search, IVF's nlist / nprobe. Pushing the last few points of recall (0.95→0.99) can cost 3–5× latency.

05  The two-stage recommender

You can't run an expensive cross-feature ranker over a billion items per request. So the funnel: candidate generation (cheap, recall-oriented ANN — billions → hundreds) then ranking (expensive deep model scores those hundreds with rich features → dozens). In practice multiple retrieval sources run in parallel and merge — a DAG, not a line.

two_tower.py
# Item embeddings are precomputed OFFLINE for the whole catalog and loaded into ANN.
# Only the user tower runs online -> new items need just an item-tower pass + upsert
# (no model retrain), so item freshness is cheap.

def recommend(user, k=20):
    u = user_tower(user.features)                 # online, ~1 ms
    cands = ann_index.search(u, k=500)            # Stage 1: dot-product top-K (retrieval)
    scored = rank_model.score(u, cands, features.fetch(user, cands))  # Stage 2: rich
    return business_rules(scored)[:k]             # dedup / diversity / already-seen

The two towers (user + item) share an embedding space; the item tower is run offline over the whole catalog, only the user tower runs at request time. Towers deliberately can't see cross-features — that's stage 2's job.

06  Freshness, the stack & RAG

Online vs offline
Offline batch embed + index rebuild is simplest but stale (hours); HNSW supports incremental inserts, while IVF needs periodic re-clustering. Deletes are hard — removing an HNSW node breaks graph links, so use tombstones + periodic compaction (frequent deletes fragment the graph and degrade recall).
2026 stack
Vector DBs: pgvector (Postgres), Milvus, Qdrant, Weaviate, Pinecone; libraries FAISS / ScaNN / DiskANN (now in SQL Server 2025).
RAG — the dominant new driver
The same two-stage funnel: hybrid retrieval (dense + BM25) → top-20/50 → cross-encoder re-rank (query+doc scored jointly — the highest-ROI single improvement, +15–30% on RAG metrics) → top-3/5 → LLM. Retrieval, not generation, is the 2026 bottleneck.

07  Failure, multi-region, observability & cost

🧊

Stale embeddings

Retrain the model but not re-embed the catalog → query and item vectors live in different spaces → silent recall collapse. Version embeddings; re-embed on model change.

❄️

Cold-start

New user (no vector) / new item (not indexed). Mitigate with content-based item embeddings (item tower needs no history), popularity fallbacks, and exploration (bandits).

🧩

Sharding

Graph indexes resist partitioning (dense global connectivity) → scatter-gather: query all shards in parallel, merge top-K. Replicate shards for read QPS; leader-follower (slightly stale reads OK).

📊

Observability

Recall@K vs brute-force ground truth (alert on regression), p99 latency split by stage (ranking is usually the tail), feature-store fetch latency (its 100–1000× fan-out dominates), index staleness, fallback rate. End-to-end SLO ~200 ms p99.

Cost: quantize aggressively (PQ/int8) and re-rank survivors with full-precision vectors; DiskANN cuts RAM ~90% vs in-RAM HNSW at 1B scale. How the platforms do it: YouTube/Google two-tower + deep ranker (ScaNN); Spotify two-stage + multiple interest vectors; Meta generative recommenders (HSTU); RAG + cross-encoder rerank everywhere.

08  Trade-offs & interview recap

Why split a recommender into candidate generation then ranking, instead of ranking everything?

Right: it's a cost/latency split — broad-and-cheap retrieval (ANN over two-tower embeddings) followed by narrow-and-expensive ranking with rich cross-features. This two-stage shape is how virtually all large-scale search, recsys, and RAG systems hit their latency budget.
Say this to nail it

"Embed items and queries into one space; retrieval is ANN nearest-neighbour. I'd use a two-tower model — item tower offline over the catalog, user tower online — then ANN for candidate generation and a heavy ranker on the few hundred survivors. Index choice is the cost lever: HNSW for best recall in RAM, DiskANN to serve a billion vectors from SSD at ~90% less RAM. I'd version embeddings to avoid the stale-space trap, use tombstones for deletes, and scatter-gather across shards. The same funnel powers RAG, with a cross-encoder re-ranker as the highest-ROI add."
