Advanced · 2026 · LLM serving

Design an LLM serving system.

Serving a large language model breaks the usual rules: work happens on scarce, expensive GPUs; each request generates token by token over seconds; and throughput hinges on batching many requests together. The mental model to anchor on: generation has two phases — prefill (process the whole prompt at once, compute-bound) and decode (one token per step, memory-bandwidth-bound) — and the KV cache usually dominates GPU memory.

01  Requirements & what's different

✅

Functional

Accept a prompt, run inference, stream tokens back as produced. Many concurrent users, variable-length prompts/outputs.

📐

Non-functional

Low TTFT (time-to-first-token), high tokens/s, efficient use of very expensive GPUs (utilisation = cost), graceful overload. Stateful within a request (the KV cache must persist for the whole generation).

Why decode loves batching: producing one token still loads all model weights from HBM, so it's bandwidth-bound at low arithmetic intensity — batching amortises that weight load across many sequences. Prefill is already compute-bound, so it doesn't.

02  Capacity: the KV-cache budget

GPU memory = model weights + KV cache + activations. The KV cache is the variable that decides how many concurrent tokens you can serve:

KV_bytes = 2 (K and V) × layers × kv_heads × head_dim × bytes × seq_len × batch

03  API & the request path

OpenAI-compatible is the de-facto standard: messages + sampling params + stream: true, emitting data-only SSE deltas (server→client, plain HTTP, proxy-friendly) ending with [DONE]. The router does auth, rate-limiting, and — increasingly — prefix/KV-aware routing (send requests sharing a system prompt to the replica that already holds those KV blocks).

04  Continuous batching

Static batching fixes a batch and runs it to completion — so the whole batch waits for the longest sequence (head-of-line blocking) while finished sequences leave their GPU slots idle. Continuous (in-flight) batching operates per token-step: add waiting requests and evict finished ones every step, so a slot frees the instant a sequence hits EOS. Up to ~23× throughput over static.

scheduler.py
running, waiting = [], deque()

def step():
    # 1) SCHEDULE: top up the batch from the queue under the token budget
    while waiting and kv_cache.has_free_blocks() and token_budget_left():
        seq = waiting.popleft()
        if not kv_cache.allocate(seq):       # not enough KV blocks
            waiting.appendleft(seq); break
        running.append(seq)                  # prefill happens this step

    # 2) FORWARD: one fused pass over all running seqs -> next token each
    tokens = sample(model.forward(running))  # prefill chunks + decodes, batched

    # 3) RETIRE finished sequences, freeing their slot THIS step
    for seq, tok in zip(running, tokens):
        seq.append(tok); stream_to_client(seq, tok)      # SSE delta
        if tok == EOS or seq.len >= seq.max_tokens:
            kv_cache.free(seq); running.remove(seq)

    # 4) OVERLOAD: out of KV blocks -> preempt a low-priority seq (recompute later)
    if kv_cache.exhausted():
        victim = lowest_priority(running)
        kv_cache.free(victim); running.remove(victim); waiting.appendleft(victim)

05  KV cache & PagedAttention

Classic systems store each sequence's KV in one contiguous buffer pre-sized to the max length — wasting 60–80% of KV memory to internal fragmentation. PagedAttention (vLLM) treats KV like OS virtual memory: fixed-size blocks (16 tokens), non-contiguous in HBM, mapped via a per-sequence block table. Allocate blocks on demand → fragmentation drops under 4%, enabling far larger batches (up to ~24× throughput over naive HF).

Prefix caching is the biggest cost lever

Because blocks are content-addressable, identical prefixes share physical KV blocks — a large shared system prompt's prefill is paid once across all requests. Stable prompts (agents, RAG) hit 80%+ prefix-cache hit rates, the single biggest TTFT and cost win. This is why the router is prefix-aware.

06  2026 techniques, autoscaling & failure

🔀

Disaggregated prefill/decode

The big 2025→2026 shift: prefill is compute-bound, decode is bandwidth-bound, so co-locating them interferes. Put them on separate GPU pools (transfer KV over the interconnect) → up to ~7.4× more requests / 12.6× tighter SLO. In Dynamo, llm-d, vLLM, SGLang.

⚡

Quantization & spec decoding

FP8 mainstream, FP4 native on Blackwell (~2× FP8 TFLOPS, ~1.4× cheaper/token). Speculative decoding: a small draft proposes K tokens, the target verifies in one pass. Chunked prefill interleaves long prompts with decodes.

📈

Autoscaling

Scale on queue depth / KV-cache utilisation / TTFT — not CPU, not raw GPU util (which pegs at 100% during batching). Cold start is brutal (load 70–140 GB weights) → keep a warm pool, avoid scale-to-zero for latency tiers.

💥

Failure modes

KV exhaustion → preempt a running seq (drop + recompute later). Pathologically long sequences starve others → cap max_tokens. Replica crash loses all in-flight KV (it's ephemeral, in-GPU) → retry from scratch; router re-routes.

07  Multi-region, cost & observability

Cost
GPU cost dominates — optimise throughput per dollar (cost/M tokens), not raw latency. Levers: quantization (FP8→FP4), continuous batching + high KV utilisation, prefix caching (skip repeated prefill), disaggregation, bigger batches for throughput tiers. Tier: interactive (warm pools, tight SLO, small batches) vs batch/async (scale-to-zero OK, huge batches, cheapest hardware).
Multi-region
Route to regions with GPU capacity (GPUs are scarce); accept some cross-region latency to land on a warm, in-region replica with prefix-cache hits.
Metrics & SLOs
TTFT + TPOT/inter-token latency (joint SLO, e.g. "p95 TTFT < 500 ms AND p95 TPOT < 50 ms" — goodput is the north star), tokens/s, KV-cache utilisation (alert > 85–90%), queue depth, preemption rate (KV thrashing), prefix-cache hit rate.
2026 stack
vLLM (reference: PagedAttention + prefix caching + V1 scheduler), TensorRT-LLM, SGLang, TGI; NVIDIA Dynamo + llm-d for orchestration/disaggregation.

08  Trade-offs & interview recap

Why is continuous batching so central to serving LLMs efficiently?

Right: a GPU producing one token still loads all weights from HBM, so one request wastes it. Continuous batching packs many sequences through together and frees slots the instant a sequence finishes — maximising tokens/s/GPU, which (since GPUs dominate cost) is the whole game.
Say this to nail it

"Generation is prefill (compute-bound) then decode (bandwidth-bound), and the KV cache dominates memory. So: continuous batching to keep the GPU full, PagedAttention to kill KV fragmentation, and prefix caching so shared system prompts prefill once — the biggest TTFT/cost lever. I'd autoscale on KV utilisation and queue depth (not CPU), shed load via admission control, and in 2026 disaggregate prefill and decode onto separate pools with FP4 on Blackwell. SLOs are joint TTFT + TPOT, and the optimisation target is cost per million tokens."
