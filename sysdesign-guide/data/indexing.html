Data at scale · indexing

Indexing.

An index is a separate, sorted data structure that lets the database jump to the rows you want instead of scanning every one. It's the difference between flipping to a word in a book's index and reading the whole book. Indexes make reads fast — but each one slows writes and costs storage, so the skill is indexing exactly what you query and nothing more.

01  Full scan vs lookup

In plain English analogy

Finding every mention of "caching" in a 500-page book: without an index you read all 500 pages (a full table scan). With the index at the back, you flip to "caching → p. 142, 287" and go straight there. The book's index is sorted alphabetically so you can binary-search it — exactly what a database index does.

Without an index, WHERE email = 'x' on 100 million rows reads all 100 million. With an index on email, it's a handful of jumps — O(log n) instead of O(n).

index.sql
-- Slow on a big table: scans every row
SELECT * FROM users WHERE email = 'ada@x.com';

-- Create an index once; lookups become ~O(log n)
CREATE INDEX idx_users_email ON users(email);

-- Composite index: order matters — this serves
-- WHERE user_id = ? ORDER BY created_at DESC
CREATE INDEX idx_posts_user_time ON posts(user_id, created_at);

02  How indexes work — B-trees & friends

B-tree (the default)
A balanced, sorted tree. Great for equality and range queries (>, <, BETWEEN, ORDER BY). What most relational indexes use.
LSM-tree
The B-tree's write-optimised mirror image: buffer writes in memory, flush them to immutable sorted files, and merge those in the background (compaction). Turns random writes into fast sequential ones — the engine behind write-heavy stores like Cassandra, RocksDB & LevelDB, at the cost of extra read and compaction work.
Hash index
O(1) equality lookups, but no ranges or ordering. Good for exact-match key-value access.
Composite index
An index on several columns, e.g. (user_id, created_at). Works left-to-right — it helps queries filtering on user_id (optionally plus created_at), but not ones filtering only on created_at.
Covering index
Includes every column a query needs, so the DB answers from the index alone without touching the table — the fastest reads.
Inverted index
Maps each term → the documents containing it. The engine behind full-text search (Elasticsearch). See the crawler and search designs.

03  The cost of an index

Indexes aren't free, and naming the cost is what separates a thoughtful answer from a reflexive "add an index":

✍️

Slower writes

Every INSERT/UPDATE/DELETE must update every index on the table. Ten indexes = ten extra little writes per row change.

💾

More storage

Indexes can rival the table itself in size. On a write-heavy table, fewer, well-chosen indexes win.

Index for your queries, not your columns

Look at the actual WHERE, JOIN, and ORDER BY clauses you run, and index those. A composite index ordered to match your most common query often replaces several single-column ones.

You add an index on (user_id, created_at). Which query does it not help much?

Right: a composite index is used left-to-right. Filtering only on the second column (created_at) can't use it efficiently — you'd want a separate index on created_at, or reorder the composite to match.
