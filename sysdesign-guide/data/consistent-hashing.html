Data at scale · consistent hashing

Consistent hashing.

When you spread keys across N nodes with hash(key) % N, changing N — adding or removing a single node — reshuffles almost every key. At scale that's catastrophic: every cache entry invalidated, terabytes moved. Consistent hashing fixes this so that adding or removing a node moves only about 1/N of the keys. It's the algorithm behind distributed caches, Dynamo, Cassandra, and load balancers everywhere.

01  The problem with hash % N

In plain English analogy

Imagine assigning students to dorms by "ID number mod number-of-dorms." Build one new dorm and suddenly almost everyone has to move rooms, because every remainder changed. Consistent hashing is a smarter rule where opening a new dorm only makes the students nearest it move in — everyone else stays put.

With % N, going from 4 to 5 nodes changes the target of roughly 80% of keys. For a cache, that's a near-total wipe and a stampede onto the database. We need a scheme where the mapping barely changes when the node count does.

02  The ring

Hash both servers and keys onto the same circle (say 0…2³²). A key is owned by the first server clockwise from it. Now adding a server only steals the keys in the arc just before it — everyone else is untouched. Step through adding a node:

03  Virtual nodes & the lookup

One problem remains: with few servers, the arcs are uneven, so some servers own far more of the ring than others. The fix is virtual nodes — place each physical server at many points around the ring (e.g., 150 each). The load smooths out, and when a server leaves, its share is redistributed across many others instead of dumping on a single neighbour.

The lookup is a binary search: keep the servers' ring positions sorted, and for a key's hash, find the next position clockwise.

The ring in ~15 lines of Python code
ring.py
import bisect, hashlib

class Ring:
    def __init__(self, nodes, vnodes=150):
        self.vnodes = vnodes
        self.ring = {}          # position -> node
        self.sorted_keys = []
        for n in nodes:
            self.add(n)

    def _hash(self, key):
        return int(hashlib.md5(key.encode()).hexdigest(), 16)

    def add(self, node):
        for i in range(self.vnodes):           # many points per node
            pos = self._hash(f"{node}#{i}")
            self.ring[pos] = node
            bisect.insort(self.sorted_keys, pos)

    def get(self, key):
        h = self._hash(key)
        i = bisect.bisect(self.sorted_keys, h) % len(self.sorted_keys)
        return self.ring[self.sorted_keys[i]]   # first node clockwise

A 100-node cache cluster adds one node (now 101). Roughly what fraction of keys must move?

Right: consistent hashing moves only ~1/N of keys when a node joins or leaves — here ~1/100. That minimal reshuffling is the whole reason it underpins distributed caches and databases.
