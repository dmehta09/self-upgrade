Warm-up · rate limiter

Design a rate limiter.

Cap how many requests a client may make in a window — to stop abuse, absorb spikes, and protect fragile downstreams. The interesting part isn't the counting; it's making one global limit hold atomically across a fleet of gateways, choosing an algorithm whose burst behaviour matches the requirement, and deciding what happens when the limiter's own datastore fails.

01  Requirements & scale

✅

Functional

Given a key (user / API-key / IP), allow or reject each request against a configured limit (e.g. 1000 req/min). Return 429 with Retry-After on reject. Support per-route and per-tier limits; ideally tunable without redeploy.

📐

Non-functional

Correct globally, not per-instance. Sub-millisecond added latency on the hot path. Highly available — the limiter must not become the outage. Memory-cheap per key (millions of active keys).

Two questions decide the design: how strict must the limit be? (exact vs approximate changes the coordination cost) and what burst behaviour is acceptable? (a smooth hard cap vs allowing short bursts up to a ceiling).

02  Capacity estimation

The limiter sees every request, so its load equals total API traffic. Size the counter store's ops/s, not its storage — state per key is a few bytes.

QuantityAssumptionResult
API traffic (peak)1M req/s1M limiter checks/s
State per key2 fields (tokens + ts) ≈ 64 B10M active keys ≈ ~640 MB RAM
Redis throughput~50–100k rate-checks/s per shard*1M ÷ 75k ≈ ~14 shards (round up for hot keys)
Added latency1 same-AZ Redis round trip~0.2–0.5 ms p99 with pooling + EVALSHA

*A check is one atomic Lua call (several internal ops), not a bare GET — budget well below raw GET throughput. These are order-of-magnitude planning figures, not guarantees.

Shape of the problem: tiny state, enormous request rate. The scaling lever is Redis ops/s (shard the keyspace) and shaving round trips — never storage.

03  API & response contract

Internally the limiter is one call; externally it shapes the HTTP response a client sees.

CALLallow(key, cost=1)→ { allowed, remaining, retry_after }
HTTP429 Too Many RequestsRetry-After: 30 · RateLimit: "default";r=0;t=30
429 + Retry-After
The standard reject (RFC 6585); Retry-After tells the client how long to back off. Reserve 503 for server-side overload shedding, not per-client quota.
Legacy headers
X-RateLimit-Limit / -Remaining / -Reset — ubiquitous but inconsistent across vendors (Reset has meant seconds, ms, or a timestamp).
Standards-track (2026)
The IETF RateLimit / RateLimit-Policy structured-field headers (draft-ietf-httpapi-ratelimit-headers) replace that ambiguous triplet — still an Internet-Draft, not yet an RFC. Ship both during the transition.

04  The algorithm choice

Five algorithms span the accuracy / memory / burst trade-off. Drag through them:

Default pick: token bucket when short bursts are fine (most public APIs); sliding-window counter for a smooth approximate cap with trivial memory; GCRA (CL.THROTTLE) for an exact rolling window in a single atomic command. Avoid the sliding log at scale (memory) and the fixed window where the 2× boundary leak matters.

05  Making it correct across many servers

Traffic is spread over many gateways. Per-instance counters are wrong: a user doing 50 req on gateway A and 50 on B looks compliant on each but did 100 globally. So the counter must be shared — typically Redis — and the check must be atomic.

The read-modify-write race

The naive GET → check → SET is not atomic: two concurrent requests both read tokens=1, both decide "allow", both write back — 2 requests pass on 1 token. Put the whole read-compute-write in one atomic Lua script (Redis runs Lua single-threaded), or use a single atomic command like CL.THROTTLE.

token_bucket.lua
-- KEYS[1]=bucket key   ARGV: rate, capacity, now(seconds), cost
local rate, cap = tonumber(ARGV[1]), tonumber(ARGV[2])
local now, cost = tonumber(ARGV[3]), tonumber(ARGV[4])

local st     = redis.call("HMGET", KEYS[1], "tokens", "ts")
local tokens = tonumber(st[1])
local last   = tonumber(st[2])
if tokens == nil then tokens, last = cap, now end   -- first sight: start full

local elapsed = math.max(0, now - last)             -- guard backward clocks
tokens = math.min(cap, tokens + elapsed * rate)     -- refill, capped

local allowed = tokens >= cost
if allowed then tokens = tokens - cost end

redis.call("HMSET", KEYS[1], "tokens", tokens, "ts", now)
redis.call("EXPIRE", KEYS[1], math.ceil(cap / rate * 2))  -- idle keys self-expire
return { allowed and 1 or 0, tokens }               -- flag + remaining (for headers)

Pass now from a single trusted clock (or Redis TIME) so gateway clock skew can't corrupt the refill. For very hot keys, lease a batch of tokens to each instance (say 100 at once) and serve locally until drained — ~100× fewer Redis round trips, at the cost of slight over-admission near boundaries.

06  Where the limiter lives

Client SDK
Courtesy throttle to save bandwidth; untrusted — never the enforcement point.
API gateway / edge
The standard 2026 enforcement point (Kong, Cloudflare, AWS API Gateway, NGINX). Blocked traffic never touches app servers. Lacks deep business context.
Sidecar / mesh
Envoy extracts descriptors and calls an external ratelimit gRPC service (Redis-backed) — shared global counters across all proxies, language-agnostic, with shadow_mode to test a limit before enforcing it.
Dedicated service
Richest context (per-tenant plans, billing tiers), reusable across entrypoints; costs an extra hop.

The pragmatic answer is layered: coarse volumetric / IP limits at the WAF/edge, fine per-API-key or per-tenant limits at the gateway or a dedicated service backed by Redis.

07  Failure modes & multi-region

🔌

Redis down → fail-open or fail-closed?

Fail-open (allow when undecidable) keeps the API up but risks flooding an unprotected backend during the outage. Fail-closed protects the backend but takes you down. Usual call: fail-open for normal APIs, fail-closed where the limiter guards a fragile/expensive downstream — with a local in-memory fallback so you degrade to per-instance limiting, not all-or-nothing.

🔥

Hot keys

A shared NAT IP or celebrity user hammers one shard. Prefer authenticated per-user keys over per-IP; split a hot key into K sub-counters and sum; lease tokens locally to absorb load off Redis.

🌍

Per-region vs global limits

Per-region Redis is fast and HA, but the effective global limit becomes ≈ limit × regions unless you partition the quota by traffic share. Exact global limits need one authoritative counter — a cross-region round trip (50–150 ms) or consensus — so reserve them for billing/abuse and enforce asynchronously.

⏰

Clock skew

Token-bucket / GCRA refill is time-delta math. Compute time inside Redis (TIME) rather than trusting each caller, run NTP in slew mode, and guard against negative elapsed (max(0, now-last)).

08  Observability & cost

Metrics
Allowed vs blocked (429) rate per route/tenant; near-limit ratio (passed but close — a capacity early-warning); limiter decision latency p99; Redis error/timeout rate; per-shard ops imbalance (hot-shard detection); fail-open activation count.
SLOs
Added latency p99 < ~2–5 ms; limiter availability ≥ 99.99%; a stated correctness budget (acceptable over-admission % when local-token mode is on).
Alerts
429 spike (attack, misconfigured client, or a too-tight limit); Redis error rate over threshold; fail-open engaged → page (you are currently unprotected); rising near-limit ratio.
Cost
Dominated by the Redis fleet (RAM is small; ops/s drives shard count) and gateway compute. State storage is negligible. Cloud-native limits (API Gateway / WAF rules) trade per-request fees for zero ops burden.

09  Trade-offs & interview recap

Why must the counter check run as one atomic operation rather than read-then-write?

Right: the read-modify-write race lets two requests both pass on one token. Redis runs a Lua script single-threaded and atomically, so no command interleaves between the read and the write — the limit holds.
Say this to nail it

"I'd enforce at the gateway with a token bucket for burst tolerance, backed by a shared Redis counter updated by one atomic Lua script so the limit holds globally across instances. I'd shard the keyspace for throughput, lease tokens locally to cut round trips on hot keys, and fail-open with a local fallback unless the limiter guards something fragile. Per-region limits with quota partitioning; exact global limits only where billing demands it, enforced asynchronously."
