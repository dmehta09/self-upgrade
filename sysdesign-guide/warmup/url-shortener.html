Warm-up · TinyURL / Bitly

Design a URL shortener.

Turn long.example.com/a/very/long/path into sho.rt/abc123 and redirect visitors back. The core is simple — which is exactly why it's the canonical warm-up for the full method: scope it, estimate it, design an API and store, choose a code-generation strategy, then make a massively read-heavy redirect path fast, global, and resilient.

01  Requirements & scale

✅

Functional

Create a short URL from a long one (optional custom alias + expiry). Redirect a short URL to its long URL. Click analytics is a common nice-to-have.

📐

Non-functional

Massively read-heavy (~100:1 to 1000:1 reads:writes). Redirects fast (< 100 ms) and highly available. Codes unique and not bulk-guessable. Storage is never the bottleneck — read QPS and cache memory are.

The shape: cheap writes, hot reads, modest storage. The product question that drives the design — do we need per-click analytics and mutable destinations? — decides 301 vs 302 (see §6).

02  Capacity estimation

Anchor on a realistic read-heavy model: ~100M DAU each following a few links/day → hundreds of millions of redirects/day; new-URL creation is tiny by comparison.

Takeaways: only a few hundred writes/s but tens of thousands of reads/s — so optimise hard for reads (cache!) — and a few TB over five years, which one well-chosen store (or a modest shard count) holds easily.

Write volume is an assumption, not a fact

Reference designs disagree by ~1000× on writes (ByteByteGo's 100M new URLs/day vs Hello Interview's 100k/day; real Bitly ≈ 8.5M created/day, ~10B clicks/month). State your assumption, present capacity as a range, and note that the read-heavy framing (~100:1+) is what everyone agrees on.

03  API & data model

POST/urls{ long_url, alias?, expiry? } → { short_url }
GET/{short_code}→ 301/302 redirect to long_url

The data model is almost nothing — a single mapping with the short code as primary key:

short_code
Primary key, e.g. abc123 (7 chars). Looked up on every redirect. Keep a UNIQUE constraint as the last-line safety net against any generation bug.
long_url
The original URL (~200–500 B).
created_at / expiry / owner
Metadata; expiry powers TTL cleanup.

Access is a pure point lookup by primary key — no ranges, joins, or multi-row transactions on the hot path. A key-value store (DynamoDB, Cassandra) or a plain relational table both work; since writes are ~1/s, the deciding factor is read scale + global replication, not query power. Shard by hash(short_code) so every read hits exactly one partition with even distribution — never by created_at (hot shard on recent writes).

04  Generating short codes

Mint a unique 7-char code in base62 (0-9 a-z A-Z; not base64 — +// are URL-unsafe). 62⁷ ≈ 3.52 trillion codes; 6 chars (≈56.8B) is borderline, 7 has headroom.

🔢

Counter → base62

Encode a monotonic id in base62. Zero collisions, no existence check. But a single counter is a SPOF and codes are sequential (guessable).

🗝️

KGS / range allocation

Pre-generate random codes offline, or lease ranges of ids to each app node (etcd/Redis INCRBY) so it mints locally and re-leases only when drained. No hot-path coordination; non-sequential codes.

base62.py
ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"
BASE = 62

def encode(num: int) -> str:
    if num == 0:               # loop below never runs for 0
        return ALPHABET[0]
    if num < 0:
        raise ValueError("id must be non-negative")
    out = []
    while num:
        num, rem = divmod(num, BASE)
        out.append(ALPHABET[rem])
    return "".join(reversed(out))   # remainders come out least-significant first
Why not just hash the long URL?

Truncated hashes (MD5 → 7 chars) collide — two URLs map to one code — forcing a check-and-retry on every write. Counters and KGS sidestep collisions entirely. Pitfalls to name: the alphabet ordering is a permanent contract (reorder it and every existing code breaks); sequential counters are enumerable, so XOR/Feistel-permute the id before encoding if guessability matters; keep a profanity denylist.

05  High-level architecture

Two paths: a rare write (create) and a hot read (redirect). The redirect path carries ~99.9% of traffic and is served almost entirely from cache; click events fire async so logging never blocks the redirect.

06  Caching & 301 vs 302

Caching is the single biggest lever. The access pattern is Zipfian — a small hot set of links gets most clicks — so a modest Redis footprint covers the working set and yields 90–95%+ hit ratios, making p99 redirects single-digit ms.

301 (permanent)
Browsers/CDNs cache it, so repeat clicks never reach you — lowest load and latency — but you lose per-click analytics on cached hits and can't change or expire the destination.
302 (temporary)
Not cached by default, so every click hits your service → accurate analytics and a mutable/expirable/geo-targetable destination. Cost: full origin load on every click (size your cache/QPS for total clicks, not unique users).

Bitly-class products default to 302 precisely because analytics and dynamic destinations are the product. The choice is "free clicks but lost control (301)" vs "full traffic but full control (302)."

07  Failure modes & resilience

🧊

Cache death / cold start

The dangerous one: a flushed cache sends 100% of reads to a DB provisioned for ~5% → thundering herd. Mitigate with a replicated cache (Sentinel/Cluster failover), request coalescing / single-flight on misses, jittered TTLs to avoid synchronized expiry, and gradual warming.

💾

DB death

Reads still served from cache for the hot set (graceful degradation); cold codes 503. Writes (create) fail — acceptable, since create is low-volume and non-critical. Multi-AZ replicas + managed KV restore it.

🗝️

ID coordinator death

With pre-allocated id ranges in memory, writes keep working until a node's block drains — the coordinator need only be up to lease the next block. A single Redis INCR with no range buffering is the anti-pattern (its death stops all writes).

📊

Analytics pipeline death

Click logging is fire-and-forget into a queue (Kafka) — a logging outage must never affect redirects.

08  Multi-region & the edge

Serve redirects close to users. The modern (2026) pattern collapses the classic "cache + DB" tiers into a single globally-replicated edge KV layer:

Edge KV
Run redirect logic at the edge against Cloudflare Workers KV or DynamoDB Global Tables — global single-digit-ms redirects from the durable store itself.
Consistency
Replication is async/eventually consistent: a brand-new link may not resolve in a distant region for a short window (DynamoDB Global Tables ~1–2 s; Workers KV up to ~60 s). That's fine — only the user who just created a link is affected, and the mapping is immutable once written.
Strong cross-region
DynamoDB Multi-Region Strong Consistency (GA 2025) exists for the rare case that can't tolerate the lag — usually overkill here.

Shorteners are an eventual-consistency-friendly workload: immutable mapping, read-heavy, read-your-own-write window measured in seconds.

09  Failure, multi-region, observability & cost

Failure modes
Cache cold / node loss → miss storm on KV (stampede protection + replicas). KGS / counter range exhaustion → pre-allocate ranges with headroom alerts. DB primary fail → promote replica; redirects stay on edge KV while create path degrades. Poison short codes → rate-limit create, quarantine abusive destinations.
Multi-region
Serve redirects from edge / regional KV (eventual OK); pin creates to a home write region or multi-master with conflict-free codes (range-per-region). Accept a seconds-long RYOW window after create, or sticky-read the author to home. Cross-region lag is a metric, not a blocker for redirects.
Observability
Redirect latency p99 (SLO < 50–100 ms at the edge); cache hit ratio (SLO ≥ 90–95% — alert below ~85%); redirect availability ≥ 99.99%; create success rate ≥ 99.9%; replication lag; 404 rate (expired/invalid). Alert on hit-ratio drop, 5xx > 0.1%, lag beyond budget, id-range exhaustion.
Cost
Driven by cache memory (dominant at high read QPS) and egress / CDN request fees (billions of tiny redirects); compute scales with read QPS; storage is a rounding error (even 365B records ≈ tens of TB on managed KV).
Security
Open-redirect / phishing abuse: malware URL scanning, destination allowlists for enterprise, rate-limit create, CAPTCHA on burst. Don't log full destination PII longer than needed; short-code enumeration is mitigated by enough entropy + rate limits.

10  Trade-offs & interview recap

Why is generating codes from a counter (or a key-generation service) usually better than hashing the long URL?

Right: the problem with hashing is collisions — you'd check the store and retry on every create. A counter or a pre-generated key pool gives guaranteed-unique codes with no hot-path collision check.
Say this to nail it

"It's read-heavy and tiny per record, so: base62 codes from range-allocated counters to avoid collisions and a single-counter SPOF, a key-value store as source of truth, and an aggressive cache (or edge KV) so ~99% of redirects never touch the DB. Default to 302 because analytics and mutable destinations are the product. Serve globally from edge KV, accepting a seconds-long read-your-own-write window. The real constraints are read QPS and cache memory — storage never is."
