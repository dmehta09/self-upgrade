Expert · user management

Design a user management system.

The service that owns the user as a durable entity — accounts, profiles, lifecycle — and that every other system foreign-keys to. The senior move is to draw the boundary first: this page owns who exists; authentication owns how they prove it and authorization owns what they can do. The hardest part isn't CRUD — it's that you usually cannot actually DELETE a user, so "right to erasure" becomes anonymize-in-place.

01  Requirements & the scope boundary

✅

Functional

Create accounts, verify email, manage profile/preferences, deactivate, delete (GDPR), export data. Self-service and admin/DSAR flows.

📐

Non-functional

The user object is a fan-in dependency (everything reads it) → must be highly available + cached; PII-safe + GDPR/CCPA-compliant; correct under concurrent signups.

A "user" is not an "identity"

A person can present multiple identities (Email+Password, Google, corporate SAML) — what ties them together is the email address: control of that inbox grants access to every account based on it. So the user is the stable anchor; auth identities attach to it many-to-one. That's exactly why credentials don't live in the users table.

02  The account lifecycle & email verification

An account is a state machine: invited → registered → (verify) → active → suspended/locked → deactivated → deleted. Suspended (admin/policy) and locked (security, e.g. failed-login throttle) are distinct — different reactivation paths. Verification gates trust:

Enterprise note: SCIM deprovisioning maps active:false to suspended/deactivated (not hard delete), with a 30–90 day retention window so accidental offboarding is recoverable.

03  Data model: separate identity, profile & emails

Separate things that change at different rates and have different sensitivity: the small hot anchor, the security-critical identities, and the read-hot profile.

One user, three tables — split by heat and sensitivity
The anchor stays tiny so it can be cached and FK'd by every other service; emails and PII live in side tables you can rotate, verify, or anonymize without touching the anchor.
users.sql
-- THE ANCHOR: small, hot, cached everywhere; FK target for the whole company.
CREATE TABLE users (
  id           uuid PRIMARY KEY DEFAULT uuidv7(),   -- time-ordered, index-local
  status       text NOT NULL DEFAULT 'registered',  -- registered|active|suspended|...
  created_at   timestamptz NOT NULL DEFAULT now(),
  deleted_at   timestamptz                          -- soft-delete tombstone (NULL = live)
);

CREATE EXTENSION IF NOT EXISTS citext;              -- case-insensitive email compare
CREATE TABLE emails (
  id          uuid PRIMARY KEY DEFAULT uuidv7(),
  user_id     uuid NOT NULL REFERENCES users(id),
  email       citext NOT NULL,
  is_primary  boolean NOT NULL DEFAULT false,
  verified_at timestamptz
);
CREATE UNIQUE INDEX uq_email   ON emails (email);                       -- global uniqueness
CREATE UNIQUE INDEX uq_primary ON emails (user_id) WHERE is_primary;    -- one primary/user

-- One row per login method; credentials themselves live in the AUTH store, not here.
CREATE TABLE identities (
  user_id      uuid NOT NULL REFERENCES users(id),
  provider     text NOT NULL,            -- 'password' | 'google' | 'saml:acme' | 'passkey'
  provider_uid text NOT NULL,
  UNIQUE (provider, provider_uid)
);
-- Profile/preferences: bigger, mutable, read-hot, lower sensitivity, safe to cache hard.
CREATE TABLE profiles ( user_id uuid PRIMARY KEY REFERENCES users(id),
                        display_name text, avatar_url text, locale text, timezone text );

Why split? Blast radius (a profile read never touches credentials), cardinality (one human, many login methods → one user_id), and change-rate/caching. UUIDv7 gives index-local inserts; expose an opaque external handle in public URLs since v7 leaks creation time.

05  GDPR/CCPA erasure: you can't just DELETE

Financial ledgers, fraud/audit logs, and immutable event stores must survive (GDPR Art. 17(3) carves out legal-obligation + legal-claims retention). So "right to erasure" in practice = anonymize the PII in place and leave a tombstone, deleting only what you're free to. Anonymized data — if truly irreversible — falls outside GDPR because it's no longer personal data.

erase.sql
BEGIN;
  UPDATE users SET status='deleted', deleted_at=now() WHERE id=:uid;   -- tombstone
  -- Replace PII with an UNRECOVERABLE placeholder (not a reversible hash).
  UPDATE emails  SET email=('deleted+'||gen_random_uuid()||'@anonymized.invalid')::citext,
                     verified_at=NULL WHERE user_id=:uid;
  UPDATE profiles SET display_name=NULL, avatar_url=NULL, locale=NULL WHERE user_id=:uid;
  DELETE FROM identities WHERE user_id=:uid;        -- cut auth links
  INSERT INTO erasure_log(user_id, completed_at, method)               -- record the FACT
       VALUES (:uid, now(), 'anonymize+tombstone'); --   (not the PII) for accountability
COMMIT;
-- Then emit user.deleted -> fan out async: revoke sessions, scrub search index,
-- bust caches, notify downstream services + processors (CCPA), backup-exclusion list.

Crypto-shredding elegantly solves immutable backups: encrypt PII with a per-user key; "delete" = destroy the key → ciphertext is inert. CCPA's right-to-delete also fans out downstream (notify service providers/third parties) — deletion is a distributed operation, not one SQL statement.

06  Lifecycle → session revocation fan-out

Token mechanics belong to the auth page; what user-management owns is the trigger. On suspend/lock/deactivate/delete, emit a user.suspended event and revoke access. Because access tokens are short-lived JWTs you can't instantly kill one — so either revoke refresh tokens (≤15-min exposure) or bump a token-version / epoch on the user that every token carries and resource servers check (instant mass revocation). The event bus fans the change out to every node holding a session.

07  Uniqueness, normalization & account merge

Email uniqueness
Enforce with a DB UNIQUE constraint, not a read-then-write check — two concurrent signups both pass a SELECT and both INSERT; only the constraint stops the dupe (handle 23505 gracefully).
Normalization
Treat email case-insensitively (store lowercased / use citext); keep the original for display. Don't globally strip +tags/dots — that's Gmail-specific; you'd wrongly collide distinct accounts. Compute a provider-specific anti-abuse key only for fraud dedup.
Account merge
"Signed up with Google, then password, same email." Never silently auto-link on an unverified email (account-takeover vector); require proof of control of both, re-parent child rows to a surviving record, keep an immutable audit trail.
Email change
Verify the new address before flipping primary, and notify the old (detect takeover, allow "this wasn't me").

08  Scale: the user service is fan-in

QuantityAssumptionResult
Population100M users × ~250 B core≈ 25 GB — RAM-resident; you don't shard for size
Read QPS20M DAU × ~50 user-resolving reads/day≈ 11.6k/s avg, ~35–60k peak (it's fan-in)
With 95% cache hitcache the user object by idorigin sees ~600/s avg → trivial on primary + replicas

Everything reads the user object (auth, billing, feed, notifications), so a per-request cache miss is a company-wide latency tax. Cache hard, invalidate on user.updated/user.suspended.

09  Failure modes & observability

🧱

Critical dependency

If the user service is down, everything that resolves "who is this" degrades. Aggressive caching (serve stale on failure), circuit breakers on callers, read replicas + multi-AZ.

📉

Funnel metrics

Signups started → completed → email-verification rate (a drop usually means deliverability: SPF/DKIM/DMARC), invite-acceptance, reactivation.

⚖️

Compliance SLAs

Erasure/export request volume + SLA (GDPR: respond within 1 month); duplicate-account + merge rates.

🎯

SLOs

Read availability ~99.99% (it's everyone's dependency); read p99 single-digit-ms from cache; export/delete jobs get a throughput SLO (done < 24h).

10  Trade-offs & interview recap

A user invokes their GDPR right to erasure, but they have years of immutable transaction-ledger entries. What do you do?

Right: you can't delete records you're legally required to keep, and you can't truly delete from immutable stores. Anonymize (irreversibly scrub identifying fields) so the rows stop being "personal data," keep the tombstone for referential integrity, and crypto-shred where backups make in-place deletion impossible.
Say this to nail it

"The user is the stable anchor; identities (password, Google, SAML) attach to it many-to-one, linked by email — so I separate identity, profile, and the small cached users anchor everything FKs to. Uniqueness is a DB constraint, not a read-then-write. Lifecycle is a state machine, and a status change fans out to revoke sessions. Erasure is anonymize-in-place plus a tombstone, because ledgers and immutable stores can't be truly deleted — with crypto-shredding for backups. And because the user object is fan-in, I cache it hard and treat a miss as a company-wide cost."
