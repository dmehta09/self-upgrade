Design a real-time ML feature store.

Every ML-powered product — fraud checks, ETA prediction, feed ranking, dynamic pricing — needs features: the input signals a model consumes. A feature store is the system that computes them once and serves them twice: in bulk to training (months of history) and in milliseconds to inference (the freshest value right now). The two consumers want opposite things from the same data, and the bugs that arise when they disagree — training-serving skew and data leakage — are silent: the model just quietly gets worse. Increasingly asked at ML-heavy companies in 2026.

01  Requirements & scale

✅

Functional

Define a feature once (e.g. user_txn_count_7d); serve point lookups at inference (online); generate point-in-time-correct training sets (offline); discover/share features across teams via a registry.

⚙️

Non-functional

Online reads p99 < 10 ms (the model call already eats the budget); freshness from daily (churn score) to seconds (fraud velocity); training reads scan terabytes; exactly the same feature values in both paths.

A worked scale: a payments company scoring fraud on 5,000 transactions/s, each model call fetching ~50 features for 2–3 entities (user, card, merchant) → ~500K feature reads/s against the online store, while nightly training jobs replay 6 months of history offline. The read amplification (features × entities per inference) is the number candidates forget to compute.

In plain English analogy

A restaurant kitchen preps ingredients once, then uses them two ways: the line cooks need small, ready-to-grab portions right now (online store), while the test kitchen developing next month's menu needs the full pantry history of what was used when (offline store). If the test kitchen develops a recipe with ingredients the line cooks won't actually have at dinner time, the dish fails in service — that's training-serving skew.

02  The two silent killers

Training-serving skew
The feature is computed twice — once in the training pipeline (Spark SQL over the warehouse), once in the serving path (hand-written Java) — and the two implementations drift: different null handling, different time windows, different rounding. The model trains on one distribution and serves on another. Fix: define the transformation once, in the feature store, and have both paths consume its output.
Data leakage (time travel)
A training row for a prediction made on March 3 must only see feature values as they were on March 3. Join against today's values and the model "sees the future" — it scores brilliantly offline and collapses in production. Fix: point-in-time-correct joins (below).
Point-in-time correctness — the ASOF join
The offline store keeps every historical value with timestamps precisely so training can ask "what did we know then?" — the single most important sentence on this page.

03  Architecture: one definition, two stores

The canonical shape (Feast's design, Tecton/Databricks/SageMaker manage the same parts): a registry holds feature definitions; pipelines materialize values into an offline store (warehouse / lakehouse tables — complete history) and an online store (Redis / DynamoDB / Bigtable — latest value per key only); a thin serving API does the millisecond lookups.

Online store choice
Redis (sub-ms, RAM cost) vs DynamoDB/Bigtable (ms, cheaper at huge entity counts). Key = entity_key + feature_view; value = packed latest features. It's a cache-shaped workload — but one you cannot lazily refill on miss, because the source is a pipeline, not a DB row.
Offline store choice
Lakehouse tables (Parquet/Iceberg/Delta) or the warehouse (BigQuery/Snowflake). Append-only, partitioned by time; cheap scans, time travel.
Registry
Feature names, owners, schemas, freshness SLAs, lineage. The governance layer that makes features shared infrastructure instead of every team's private scripts.

05  Failure modes & the 2026 landscape

🥶

Stale features

A stuck streaming job silently serves yesterday's velocity counts — fraud models miss in production with zero errors anywhere. Monitor feature freshness lag per feature view against its SLA; alert on lag, not on job failure.

🕳️

Missing values at inference

New user → no features yet. Define defaults per feature in the registry (and train with them!), never null-crash the scoring path. The cold-start default is part of the feature definition.

🪞

Online/offline divergence

Run a continuous consistency audit: sample online reads, log them, replay the same keys offline, diff. Drift = a materialization bug you'd otherwise discover via model decay months later.

💥

Online store down

Inference must degrade, not die: serve defaults / cached vectors and let the model run slightly dumber, or fail over to a replica. A fraud model scoring with stale features beats no fraud scoring at all.

2026 landscape

Feast remains the open-source reference architecture (registry + materialization + online/offline duality); Tecton the managed leader for streaming features; warehouse-native stores (Databricks, SageMaker, Vertex) won the "we're already there" crowd. The notable shift: feature stores now also serve embeddings alongside scalar features — the online store doubles as the profile-vector source for RAG and recommender pipelines, which is why this page and that one increasingly appear in the same interview.

06  Trade-offs & interview recap

Your fraud model performs superbly in offline evaluation but degrades badly in production. Training joins features by user id against the feature tables' current values. What's the most likely cause?

Right: joining against current values lets each training row "see the future" (e.g. a chargeback count that only exists because of the fraud being predicted). Offline metrics soar; production, which can only see the past, can't match them. Every offline read must be an ASOF join at the label's timestamp.
Say this in the interview

"A feature store is one definition with two materializations: an append-only offline history for point-in-time-correct training, and a latest-value online store for sub-10 ms inference. The two failure modes I design against are training-serving skew — killed by defining the transform once — and leakage, killed by ASOF joins. Freshness is per-feature: batch by default, streaming only where seconds change the prediction."
