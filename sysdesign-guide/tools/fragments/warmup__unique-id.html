Warm-up · unique IDs

Design a unique-ID generator.

Many systems need globally unique IDs at high volume — tweets, orders, messages — ideally time-sortable (cheap "newest first", index-friendly inserts) and generated without coordination (no central bottleneck). The real decision in 2026 is which scheme: Snowflake's compact 64-bit packing, or the now-standard UUIDv7. We'll build both and name the trade-off.

01  Requirements & scale

✅

Functional

Produce IDs that are globally unique and roughly ordered by creation time, generated locally by any node, with no duplicates ever.

📐

Non-functional

High throughput (10⁴–10⁶ IDs/s fleet-wide), no per-ID coordination on the hot path, compact enough to index well, and resilient to clock skew and node restarts.

Capacity sanity check: a large app peaks near ~100k IDs/s. A single Snowflake node mints 4,096/ms = ~4.1M IDs/s, so even one node covers it — the design goal isn't throughput, it's uniqueness + ordering without a central counter.

02  The options

Five schemes span the trade-off between sortability, coordination, size, and index-friendliness:

Pick: UUIDv7 as the modern default when 128 bits is acceptable (native DB support makes it a one-line swap); Snowflake when you need compact 8-byte numeric IDs or a sortable shard key. Both leak creation time and are loosely enumerable — never use them as security tokens.

03  Snowflake — the 64-bit layout

Snowflake packs four fields into a 64-bit integer; each node reads its clock, stamps its machine id, and counts within the millisecond:

Snowflake — 64 bits
1
unused (sign)
41 bits
timestamp (ms since epoch)
10 bits
machine id
12 bits
sequence
Timestamp first → IDs sort by time. Machine id → no two nodes collide. Sequence → up to 4,096 IDs per node per millisecond.
  • 41-bit timestamp → 2⁴¹ ms ≈ 69.7 years from a custom epoch (not 1970, to maximise lifespan). In the high bits so IDs increase over time.
  • 10-bit machine id → 1,024 nodes, often split 5-bit datacenter + 5-bit worker. This is what removes coordination.
  • 12-bit sequence → 4,096 IDs/node/ms = ~4.1M IDs/s/node. Exhaust it within a ms → spin to the next tick.

04  The generator & the clock-skew gotcha

snowflake.py
class Snowflake:
    def __init__(self, machine_id: int, epoch: int = 1704067200000):
        self.machine_id = machine_id          # 0..1023, leased per node
        self.epoch = epoch                    # custom epoch (ms)
        self.last_ms = -1
        self.seq = 0

    def next_id(self, now_ms: int) -> int:
        if now_ms < self.last_ms:             # CLOCK WENT BACKWARDS
            raise RuntimeError("clock moved back; refuse until it catches up")
        if now_ms == self.last_ms:
            self.seq = (self.seq + 1) & 0xFFF  # 12-bit sequence
            if self.seq == 0:                  # exhausted this ms
                while now_ms <= self.last_ms:
                    now_ms = self.clock_ms()   # spin to next ms
        else:
            self.seq = 0
        self.last_ms = now_ms
        return (((now_ms - self.epoch) << 22)   # timestamp in high bits
                | (self.machine_id << 12)       # then machine id
                | self.seq)                     # then sequence
Time can go backwards

Snowflake trusts the wall clock. NTP slew mode adjusts gradually (safe), but step mode can jump the clock backward — then a node could mint an ID with a smaller timestamp than one already issued, risking a duplicate. Mitigations: refuse until the clock catches up (shown), wait if the regression is tiny, or advance a logical clock max(now, last_ms) and borrow sequence bits. Operationally: run NTP slew-only and alert on backward jumps. Raising this unprompted is a strong senior signal.

05  UUIDv7 — the 2026 default

UUIDv7 (RFC 9562, 2024) puts a 48-bit Unix-ms timestamp in the most-significant bits, then version/variant bits and 74 random bits. Same k-sortable, index-friendly property as Snowflake, but 128-bit, coordination-free, and standardised — and as of 2026 it's built in:

uuidv7.py
# Python 3.14 ships uuid.uuid7() (monotonic within a ms)
import uuid
id = uuid.uuid7()        # 0190c3e2-... time-ordered, coordination-free

# PostgreSQL 18 ships it natively:
#   CREATE TABLE orders (id uuid PRIMARY KEY DEFAULT uuidv7(), ...);
# The leading 48-bit ms timestamp makes inserts land at the right
# edge of the B-tree -> index locality like auto-increment, but global.
Why v7 beats v4 as a primary key

A B-tree appends most efficiently when keys increase monotonically — inserts hit the hot rightmost leaf, no page splits. UUIDv4's random bits scatter inserts across the whole keyspace (random I/O, write amplification, poor buffer-pool hits — brutal under InnoDB clustered indexes). v7's timestamp prefix restores that locality while staying globally unique. RFC 9562 defines counter methods to keep multiple IDs within the same ms monotonic too.

06  Scaling without per-ID coordination

Snowflake's only coordination is worker-id assignment at startup — leased from a strongly-consistent coordinator (ZooKeeper ephemeral node / etcd lease). After that, every ID is minted locally. If you instead want a monotonic counter (Flickr ticket / Meituan Leaf style), avoid a single DB sequence by segment allocation: each node leases a block (e.g. 1,000 IDs) in one transaction and hands them out from memory, re-leasing only when drained — ~1,000× fewer DB hits, and writes keep flowing while the coordinator is briefly down.

07  Failure modes & multi-region

⏰

Clock skew

Backward jumps break monotonicity and risk duplicate (ts, seq) tuples. Run NTP slew-only; refuse / wait / borrow-sequence on regression. Forward jumps are harmless (skip ms).

⚠️

Worker-id collision

Two nodes sharing a worker id in the same ms → duplicate IDs, the worst failure. Assign via etcd/ZK lease, renew it, and halt generation if it lapses. Avoid deriving worker-id from anything that can clash.

🔢

Sequence overflow

>4,096 IDs in one ms on a node → spin-wait to the next ms (rare; one node already does ~4.1M/s).

🌍

Multi-region

Subdivide the machine bits as 5-bit datacenter + 5-bit worker (32 DCs × 32 workers) so each region owns a disjoint ID-space slice — globally unique by construction, with no cross-region coordination.

08  Observability & cost

Metrics
IDs/s per node; sequence-exhaustion (spin) rate; clock-regression events (alert immediately); worker-id lease renewals/failures; coordinator availability.
SLOs
Zero duplicate IDs (the only hard invariant); generation latency p99 sub-microsecond (it's local arithmetic); coordinator availability ≥ 99.99% (only needed at startup/renew).
Cost
Effectively free on the hot path — no datastore, no network per ID. The only cost is running the small HA coordinator (etcd/ZK quorum) for worker-id leases. UUIDv7 costs nothing beyond the 16 bytes per row (vs 8 for Snowflake) — the storage/index trade for skipping coordination entirely.

09  Trade-offs & interview recap

Why put the timestamp in the high bits of the ID rather than the low bits?

Right: with the timestamp in the most-significant bits, a larger ID means a later time. IDs become roughly sortable by creation time and index inserts stay near the right edge of the B-tree — the whole reason v7/Snowflake beat random UUIDv4 as primary keys.
Say this to nail it

"For a new system in 2026 I'd default to UUIDv7 — it's time-ordered, coordination-free, and native in Postgres 18 / Python 3.14, so it indexes far better than random UUIDv4. If I need compact 8-byte numeric IDs or a sortable shard key, I'd use Snowflake: 41-bit timestamp + 10-bit worker + 12-bit sequence, with worker-ids leased from etcd at startup and clock-skew handled by refusing on a backward jump. Both leak creation time, so I'd use a separate random token where unguessability matters."
