Core · notifications

Design a notification system.

A shared pipe that takes "notify user X about Y" and reliably delivers it across push, SMS, email, and in-app — fast, deduplicated, and without each team rebuilding queues and retries. It's a masterclass in asynchronous, decoupled design, and the two ideas that separate a real answer from a toy are the transactional outbox (so a notification is never silently lost) and the fact that SMS throughput is carrier-gated, not yours to scale.

01  Requirements & scale

✅

Functional

Accept a request from any service; resolve template + user preferences/opt-outs; deliver via the right channel(s); expose delivery status (provider webhooks).

📐

Non-functional

High throughput with spiky load (a blast = millions at once), at-least-once delivery with retries, no duplicates, and one slow channel must not block the others.

02  Capacity estimation

Model a 10M-user blast you want drained in an hour, fanning out push + email:

QuantityAssumptionResult
Ingest rate10M ÷ 3,600 s, peak 3–5×~2,800/s avg → size ingest for ~10–14k/s
Channel fan-outpush + email per user10M recipients → ~20M channel sends
Push ceiling (FCM)600,000 msg/min per project= 10k/s — fine for the blast
SMS ceiling (A2P 10DLC)best registered brand ≈ 225 MPS10M ÷ 225 ≈ ~12.3 hours (long code: ~116 days!)

The headline: SMS is the bottleneck, and it's carrier-gated — you physically cannot blast 10M SMS in an hour through one brand. SMS campaigns are planned over hours/days; the queue absorbs the rest. Your queues are never the limit — the providers are.

03  API

Accept fast (202), do all real work async behind queues:

POST/v1/notificationsIdempotency-Key: … · { user_id, template_id, data, channels?, priority } → 202 { id, status:queued }
GET/v1/notifications/{id}→ per-channel delivery status (updated by provider webhooks)
PUT/v1/users/{id}/preferencesper-category × per-channel matrix + quiet hours + frequency caps

Templates are versioned and server-side, rendered after preference resolution into channel-specific variants (short SMS vs rich HTML email vs push title/body). Providers push state transitions (sent → delivered → opened, bounces) via webhooks into the audit log.

04  Data model

notification
id, user_id, template_id, priority, payload, status, dedup_key.
outbox
id, event, payload, published_at — written in the same transaction as the notification (see §6).
delivery_attempt
append-only audit log: notification_id, channel, provider, provider_msg_id, status, error_code, attempt_no — keyed to provider_msg_id so webhooks reconcile.
user_preference / device_token
per-category/channel opt-in + quiet hours; push tokens per (user, platform), pruned on invalid-token feedback.
dedup_keys
unique key + TTL — the idempotency backstop (§6).

05  Queues all the way down

A thin API persists + enqueues; a router resolves preferences/templates and fans out to per-channel queues (with priority sub-lanes); channel workers call the providers. Per-channel isolation matters because providers have wildly different ceilings — a shared queue lets the slowest (SMS) head-of-line-block the fastest (push).

06  Reliability: idempotency, retries & the outbox

Delivery is at-least-once, never exactly-once (impossible across a network — the two-generals problem). So make the consumer idempotent: claim a dedup key before calling the provider, with a TTL bounding the window.

idempotent_send.sql
-- Atomically claim the dedup key; only the first caller proceeds.
INSERT INTO dedup_keys (dedup_key, notification_id, created_at)
VALUES ($1, $2, now())
ON CONFLICT (dedup_key) DO NOTHING
RETURNING notification_id;
-- 1 row  -> first time: call the provider, then record provider_msg_id
-- 0 rows -> duplicate: skip the provider call (already sent / in flight)

-- Redis equivalent: SET dedup:<key> <id> NX EX <ttl>   (false = duplicate)
Retries with backoff + jitter
Retry only retryable errors (5xx, 429, timeouts) — never 4xx. Honor Retry-After; ~5–8 attempts over ~20 min with jitter (so retries don't synchronize), then drop to a DLQ. FCM's own rule: drop after ~60 min.
Dead-letter queue
Exhausted messages move to a per-channel DLQ for inspection/redrive — a poison message can't block the live queue.
Transactional outbox
"Write DB, then publish to queue" is a dual write: a crash between them loses a notification or orphans a message. Fix: commit the business row and an outbox row in one local transaction, then a relay (poller or Debezium CDC) publishes it. The relay is still at-least-once → loops back to needing idempotent consumers.

07  Per-channel concerns & prioritization

📲

Push (APNs/FCM)

Tokens rotate — prune on invalid-token feedback. APNs payload ≤4 KB over persistent HTTP/2. FCM per-device throttle: 240/min, 5,000/hr.

✉️

Email deliverability

Authenticate with SPF + DKIM (+ DMARC). Bounce/complaint handling is reputation-critical: SES reviews at ≥5% bounce / ≥0.1% complaint and may pause sending — process bounce webhooks and suppress immediately.

💬

SMS (A2P 10DLC)

Carrier-gated MPS + mandatory brand/campaign registration in the US; dominant per-message cost. Honor STOP opt-out at the platform level.

⚡

Priority & quiet hours

OTP/2FA → dedicated urgent lane, bypass batching + quiet hours. Marketing/digest → bulk lane, throttled, quiet-hours-aware. Per-user frequency caps fight notification fatigue.

08  Failure, multi-region, observability & cost

Failure modes
Provider outage → a secondary provider per channel + circuit breaker (push is harder — APNs/FCM are sole upstreams, so degrade gracefully). Backlog → monitor consumer lag, shed/queue marketing to protect transactional.
Multi-region
Route via in-region provider endpoints; keep PII (phone, email, body) in the user's home region for data residency, replicating only non-PII metadata.
Observability
Funnel rates (accepted→sent→delivered→opened) and failure rate per channel/provider; queue depth + consumer lag; DLQ depth, arrival rate, oldest-message age. Alert on error-budget burn: DLQ arrival >1% of main volume, or oldest DLQ message >5× SLO → page.
Cost
SMS dominates by ~100×: 10M emails on SES ≈ $1,000; 10M SMS ≈ $128,000 (~$0.013 each incl. carrier). Push is effectively free. Prefer push/email/in-app for bulk; reserve SMS for high-value transactional.

09  Trade-offs & interview recap

Why give each channel (push/SMS/email) its own queue and worker pool rather than one shared pipeline?

Right: providers have very different ceilings (SES thousands/s vs SMS ~hundreds/s). Isolating channels means a slow SMS provider can't stall push, and you scale + rate-limit each channel independently.
Say this to nail it

"Thin API returns 202 and writes the notification + an outbox row in one transaction, so a crash never loses it. A relay publishes to per-channel queues with priority lanes; workers are idempotent — they claim a dedup key before calling the provider, so at-least-once + idempotency gives effectively-once. Retries use backoff + jitter into a DLQ. The real constraint isn't my system, it's SMS: carrier-gated MPS means blasts span hours, and SMS costs ~100× email, so I route bulk to push/email and reserve SMS for OTP and critical alerts."
