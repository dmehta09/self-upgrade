Advanced · Uber / Lyft

Design ride-hailing.

Match a rider to a nearby driver in seconds while millions of drivers stream GPS continuously. The signature challenge is geospatial — "find the closest available drivers to this point" — which ordinary databases are bad at. The deeper asymmetry: the write side (location updates, ~1M+/s) is the scaling problem; the read side (matching) is tiny by comparison.

01  Requirements & scale

✅

Functional

Drivers publish location every ~4 s. A rider requests a trip; the system finds nearby drivers, offers the ride, tracks it. Plus ETA + surge pricing.

📐

Non-functional

Enormous write volume; sub-second matching; real-time location to the rider; mostly regional — the world partitions naturally by geography (a Tokyo trip never touches São Paulo).

02  Capacity estimation

QuantityAssumptionResult
Location writes5M online drivers ÷ 4 s~1.25M updates/s — the write storm
Live location state5M × ~64 B≈ ~320 MB RAM — tiny; the cost is write throughput, not size
Match requests~25M rides/day, peak 5–10×≈ ~1.5–3k/s — 5+ orders below the write rate
Trip storage~42M trips/day × ~1–2 KB≈ ~50–80 GB/day durable (sharded by region)

This asymmetry is the whole point: at ~1.25M writes/s with single-digit-ms read latency, no durable store qualifies for live location — it's RAM-only and unreplicated, because the data is worthless within one 4 s tick (the next fix overwrites it, and a crashed node's drivers re-register for free).

04  The hard part: "who's nearby?"

Computing distance to every driver is O(N) per request — hopeless at thousands of requests/s. A spatial index turns it into O(1) cell lookup + O(k) neighbor scan: examine only the rider's cell and a ring of adjacent cells.

nearby.py
import h3

def update_location(driver_id, lat, lng, res=9):     # write path: O(1) move
    cell = h3.latlng_to_cell(lat, lng, res)
    old = driver_cell.get(driver_id)
    if old != cell:
        if old: cell_index[old].discard(driver_id)
        cell_index[cell].add(driver_id)              # H3 cell -> {driverIds}
        driver_cell[driver_id] = cell

def nearby_drivers(lat, lng, res=9, want=10, max_k=4):   # read path: O(k) ring
    origin = h3.latlng_to_cell(lat, lng, res)
    found = []
    for k in range(max_k + 1):
        for c in h3.grid_disk(origin, k):            # 1 + 3k(k+1) cells
            found.extend(cell_index.get(c, ()))
        if len(set(found)) >= want:
            break                                    # widen the ring until enough
    return list(set(found))                          # then rank by ETA, not distance

05  Architecture, matching & dispatch

Two flows: a torrent of location updates into the in-memory geo-index (sharded across nodes by cell), and matching — read the index, rank candidates by ETA, offer the ride. Avoiding double-dispatch (one driver offered to two riders) needs a linearizable accept.

06  ETA, routing & surge

ETA & ranking
Rank by road-network ETA, not Euclidean distance ("0.5 km across a river" can be a 10-min drive). ETA is the inner loop of every dispatch (tight p99 budget) — contraction hierarchies precompute shortcuts so a route is a few ms, and an ML model (Uber's DeepETA) predicts the residual between graph ETA and reality.
Surge pricing
Per H3 cell, compare supply (available drivers) vs demand; over threshold → multiplier > 1, which rations demand and pulls in supply — a closed-loop market. Smoothing (geospatial + temporal) prevents price flapping at cell borders; hex uniform adjacency helps.

07  Failure modes & geo-sharding

📍

Lost location update

Stale position for ≤4 s — self-healing: the next tick overwrites it; treat fixes older than N intervals as offline.

🤝

Matching race

Two riders, one driver → double-dispatch. Single-owner linearizable accept (consistent-hash the driver key to one node) + soft-lock; the loser gets 409 ALREADY_TAKEN.

💥

Index node crash

That shard's driver set is lost — but no durability is needed: drivers re-register within ~4 s. Gossip (SWIM) detects the down node and reshards.

🌍

Geo-sharding

Shard by city/region — rides are local, so cross-shard traffic is near-zero, a region outage degrades only its cities, and capacity scales by adding city shards.

08  Observability & cost

Metrics & SLOs
Match latency p99 (SLO < ~1 s), match success/fulfillment rate per city, location-update freshness (alert if % of drivers with a stale fix rises), ETA error (MAE vs actual → retrain trigger), surge accuracy, cluster membership churn.
Cost
Dominated by the durable trip store + the matching/ETA compute and the in-memory geo-index fleet. Location state itself is cheap; the spend is on routing/ETA inference and keeping the index hot and sharded.
2026 reality
Uber open-sourced H3 (now a geospatial standard well beyond Uber); the dispatch index historically leaned on Google S2; application sharding via gossip (Ringpop/SWIM). Routing = graph (contraction hierarchies) + ML-on-top (DeepETA).

09  Trade-offs & interview recap

Why use a geohash/QuadTree/H3 index instead of computing the distance to every driver?

Right: spatial indexes bucket the map so "who's nearby?" reads only the rider's cell and its k-ring. Without one, every match would scan all drivers in the city — far too slow at Uber's volume.
Say this to nail it

"The scaling problem is the location write storm — ~1M+ updates/s — so I keep live positions in a sharded in-memory geo-index, not a DB; it's disposable and self-heals every 4 s. I'd index with H3 hexagons because uniform adjacency makes k-ring neighbor search and surge smoothing clean, and rank candidates by road-network ETA, not raw distance. The one thing that must be strongly consistent is acceptOffer — single-owner linearizable so a driver is never double-dispatched. Everything shards by city because rides are local."
