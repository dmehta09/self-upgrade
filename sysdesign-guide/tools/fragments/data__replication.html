Data at scale · replication

Replication & quorums.

Replication keeps copies of your data on multiple machines. It buys you two things: durability (one machine dies, the data survives) and read scaling (spread reads across copies). The catch is keeping the copies in step — and the choices you make there (synchronous vs asynchronous, leader-based vs quorum) are pure CAP/PACELC trade-offs in practice.

01  Leader–follower replication

In plain English analogy

One person keeps the master notebook (the leader); a few others keep photocopies (followers) they update from it. Everyone writes to the master, but anyone can read from a copy. If the master is lost, a copy is promoted to be the new master. The only worry: a copy might be a few seconds behind.

The dominant model: one leader (primary) takes all writes and streams them to followers (replicas), which serve reads. To scale reads — and most systems are read-heavy — you simply add followers. When the leader fails, a follower is promoted (failover).

Replication lag bites

If you write to the leader then immediately read from a follower that hasn't caught up, you see old data — "I posted a comment but it vanished!" Fixes: read your own writes from the leader, or wait for the follower to catch up. This is the classic read-after-write consistency problem.

03  Leaderless & quorums

Some stores (Dynamo, Cassandra) drop the single leader entirely: the client writes to several replicas and reads from several, using a quorum to stay consistent. With N replicas, a write needs W acks and a read queries R of them. If W + R > N, any read overlaps at least one node with the latest write — so it sees fresh data.

Step through why that inequality works. With N = 3, a write to W = 2 replicas and a later read from R = 2 replicas cannot miss each other — their sets are too big to be disjoint, so they must share a node:

W = N, R = 1
Fast reads, slow/fragile writes. Good for read-heavy, rarely-written data.
W = 1, R = N
Fast writes, slow reads. Good for write-heavy data.
W = R = ⌈(N+1)/2⌉
The balanced quorum (e.g., N=3, W=R=2): tolerate one node down and still stay consistent. The common choice.

Tuning W and R is literally dialling the PACELC trade-off per workload — strong-ish consistency, or lower latency and higher availability.

With N = 3 replicas, you set W = 2 and R = 2. Is a read guaranteed to see the latest acknowledged write?

Right: W + R > N (4 > 3) guarantees at least one node in the read set also received the latest write — so the freshest value is always seen. This is the quorum rule, and it survives one node being down.
