Building blocks · messaging

Queues, pub/sub & streams.

A message queue lets one part of your system hand work to another asynchronously — the sender drops a message and moves on; a worker picks it up later. This one idea buys you decoupling, spike absorption, and resilience. It's how you keep the user's request fast while the slow work (emails, video encoding, analytics) happens in the background.

01  Producers, queues, consumers

In plain English analogy

It's the order rail in a kitchen. The waiter (producer) clips a ticket to the rail (queue) and immediately goes back to serving — they don't stand and watch it cook. Whichever chef (consumer) is free grabs the next ticket. If a rush hits, tickets pile up on the rail rather than blocking the waiters; chefs work through the backlog.

02  Queue vs pub/sub vs stream

Work queue
Each message is processed by one consumer from a pool — work is shared out. (RabbitMQ, SQS.) Use for tasks: send email, resize image, charge card.
Pub/sub
Each message is delivered to every subscriber. (SNS, Redis pub/sub.) Use for fan-out: one event, many independent reactions.
Log / stream
An ordered, replayable log of events, partitioned for scale; consumers track their own position (offset). (Kafka, Kinesis, Pulsar.) Use for analytics, event sourcing, and high-throughput pipelines where you may re-read history.

The big win in all three: the producer doesn't wait, and a slow or down consumer just makes the backlog grow rather than failing the user's request. That's decoupling and load-levelling — a queue absorbs a traffic spike that would otherwise crush a synchronous system.

Queue vs log — the structural difference
A queue distributes disposable work; a log is shared, replayable history. The moment two systems need the same events — or you need to reprocess the past — you want the log.

03  Delivery guarantees & idempotency

Distributed messaging can't promise perfection. You choose:

1️⃣

At-most-once

May drop a message, never duplicates. Fine for telemetry where a lost sample doesn't matter.

🔁

At-least-once (the common default)

Never drops, but may deliver twice (e.g., a worker crashes after doing the work but before acking). You must handle duplicates.

"Exactly-once" = at-least-once + idempotency

True exactly-once delivery is nearly impossible, so the real-world recipe is at-least-once delivery plus idempotent consumers: design the work so doing it twice is harmless (e.g., key each message by a unique ID and skip ones you've already processed). This exact trick is the heart of the payments design.

Messages that keep failing go to a dead-letter queue for inspection rather than blocking the line forever.

Your queue is at-least-once. A "charge the customer" worker occasionally sees the same message twice. The fix?

Right: at-most-once would risk dropping charges entirely. Keep at-least-once and make processing idempotent: record processed IDs (or use the payment's idempotency key) so a duplicate delivery charges no one twice.
