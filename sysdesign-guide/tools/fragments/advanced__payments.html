Advanced · Stripe / payments

Design a payment system.

Payments flip the usual priorities: correctness beats availability and speed — charging twice or losing a transaction is unacceptable. Two invariants drive everything: exactly-once charging (idempotency, so retries don't double-charge) and never creating or destroying money (a double-entry ledger under ACID). Everything else — async state machines, reconciliation — serves those two.

Webhooks deliver async transitions (captured/settled/failed/disputed) — but they're hints; the PSP status API is authoritative for reconciliation, and webhook consumers must be idempotent (events get redelivered).

03  Idempotency: the no-double-charge rule

A charge is a non-idempotent, irreversible external side effect. If a client retries after a lost response, a naive system fires a second charge. The fix: a client-supplied idempotency key; the server stores the first request's result (success or failure) and replays it for any repeat.

charge.sql
BEGIN;
-- 1. Claim the idempotency key. ON CONFLICT short-circuits a retry.
INSERT INTO idempotency_keys (idempotency_key, user_id, recovery_point, locked_at)
VALUES ($1, $2, 'started', now())
ON CONFLICT (user_id, idempotency_key) DO NOTHING
RETURNING id;
-- 0 rows  -> key exists: load + replay stored response (or 409 if still locked)

-- 2. One BALANCED journal entry (header + lines): debits must equal credits.
WITH e AS (
  INSERT INTO journal_entries (idempotency_key, description)
  VALUES ($1, 'capture') RETURNING id
)
INSERT INTO journal_lines (entry_id, account_id, direction, amount)
SELECT e.id, v.account_id, v.direction, v.amount
FROM e, (VALUES (:cust,'debit',2000), (:mrch,'credit',1971), (:fee,'credit',29))
        AS v(account_id, direction, amount);
-- DB enforces sum(debit) = sum(credit) per entry (trigger / deferred CHECK)
COMMIT;
-- The PSP charge call lives OUTSIDE this transaction (its own idempotency key).

You can't wrap a network call in a DB transaction — so split work into atomic phases (local txns) separated by the PSP call, persisting a recovery_point after each so a retry resumes from the last checkpoint instead of re-charging.

04  The double-entry ledger

Every movement is a balanced pair — a debit and an equal credit — so the books always sum to zero and money is never created or lost. The journal is append-only and immutable: you never edit an entry, you add a reversing one. That's event sourcing for money: balance = a fold over the journal, with a perfect audit trail.

Capture example
DEBIT customer_funds 2000 · CREDIT merchant_payable 1971 · CREDIT fees_revenue 29 → 2000 = 1971 + 29, balanced.
Enforce in the DB
Balance at the transaction layer (trigger/constraint), not app code — no partial failure can leave an unbalanced entry. Any single unbalanced entry is a detectable bug, not silent corruption.
Why ACID / strong consistency

Balances are read-modify-write under concurrency; without isolation you get lost updates, double-spends, and negative balances. This is the textbook "choose CP over AP" case — a temporarily unavailable ledger is recoverable; a double-spend is not. Single-writer-per-account, ACID, strict serializability (what purpose-built ledgers like TigerBeetle provide).

06  Reconciliation & the unknown-state problem

Two independent systems (you and the bank) drift, so reconciliation compares your ledger against external truth. The 2026 best practice is three-way: internal ledger ↔ PSP settlement file ↔ bank statement — two-way recon gives false confidence (it never confirms funds actually landed).

"Did the charge succeed?"

The PSP processed the charge but the response was lost — the worst failure. Never blindly retry. Resolve with (a) the same idempotency key on retry (the PSP returns the original result, no duplicate), and (b) a background worker that scans payments stuck in transitional states and queries the PSP status API as the source of truth to drive the transition. Pull-based recovery → eventual consistency even after crashes, without the user re-attempting.

07  Compliance, multi-region & observability

PCI-DSS scope minimization
Keep raw PAN out of your systems via tokenization + a dedicated vault; network tokens (EMVCo / Apple-Google Pay DPANs) are the 2026 default and also lift auth rates (~2–5%) and cut fraud.
3DS2 / SCA (PSD2)
Strong Customer Authentication in the EU/UK; tokenized traffic scores better with issuer risk models → more frictionless 3DS2.
Data residency
Some jurisdictions (India RBI, China PBOC) mandate in-country storage → regional sharding of the cardholder-data environment + ledger. GDPR and PCI-DSS must be satisfied independently.
Metrics & SLOs
Authorization rate (the top KPI — segment by issuer/BIN/region; a drop signals an issuer/PSP outage), payment success rate, settlement lag, reconciliation breaks (count, aging, $). Common target: 99.9% success at <1 s; API uptime up to 99.9999%.
