Core · Dropbox / Google Drive

Design file sync.

Edit a file on your laptop and seconds later it's on your phone. Behind that simplicity is the defining split: content (big, immutable, content-addressed blobs in object storage) is handled completely differently from metadata (small, structured, strongly-consistent rows in a DB). The efficiency tricks — content-defined chunking, dedup, and delta sync — are the heart of it.

01  Requirements & scale

✅

Functional

Upload/download (chunked, resumable); sync across a user's devices; share; version history; work offline and reconcile on reconnect.

📐

Non-functional

Exabyte-scale storage; minimise bandwidth (never re-upload a whole file for a one-line change); 12-nines durability; fast propagation between devices.

02  Capacity estimation

Real anchors (Dropbox): 700M+ users, multiple EB stored, >600k drives, >12-nines durability. Model 500M registered / 100M MAU:

QuantityAssumptionResult
Logical storage500M × 50 GB/user≈ 25 EB logical
After dedup + EC~2× dedup, erasure-coded ~1.4×≈ ~13 EB physical (every 10% dedup ≈ 1 EB of disk)

Two takeaways: blob storage dominates metadata by ~3–4 orders of magnitude (the whole reason to split the tiers), and with delta sync the binding constraint is usually metadata DB QPS, not bandwidth (each edit = a tiny chunk upload + a metadata commit).

03  API (chunked, resumable, dedup-first)

POST/need_blocks { manifest:[hash…] }→ { missing:[hash…] } · dedup BEFORE bytes move
POST/upload_session/{start,append,finish}resumable: re-send from last acked offset after a crash
GET/list_folder/continue?cursor=… · /longpoll?cursor=…paginated delta + change notification

The client computes chunk hashes + a manifest, asks which the server is missing, uploads only those, then commits the manifest. Content-addressing makes a mid-upload crash safe to fully retry — re-uploading an existing chunk is a no-op dedup hit. Downloads are ranged GETs per chunk hash, infinitely CDN-cacheable (immutable).

04  Data model

file / version
file = (namespace, parent, name); each version is immutable and points at a manifest. Versioning is free.
manifest
the ordered list of chunk hashes — a Merkle "recipe" for a file version. Diffing two manifests instantly identifies changed chunks.
chunk
hash PK (content-addressed), size, storage locator, refcount for GC. Shared across users/files.
namespace + device_cursor
sharing = a namespace mounted into multiple users' trees (not file copies). Each device stores last_seen_version; sync replays a per-namespace journal past that cursor.

05  Chunking: why content-defined beats fixed-size

Fixed-size chunking (cut every 4 MB by offset) breaks on insertion: add one byte at the front and every later boundary shifts, so every chunk's hash changes — delta sync sees the whole file as new. Content-defined chunking (CDC) places boundaries by content (cut where a rolling hash matches a pattern), so an insert re-anchors only the one chunk around it.

fastcdc.py
MIN, AVG, MAX = 2*1024, 8*1024, 64*1024      # reference 2k / 8k / 64k
bits   = 13                                   # log2(8192)
MASK_S = (1 << (bits + 2)) - 1                 # strict below target -> smaller chunks
MASK_L = (1 << (bits - 2)) - 1                 # loose above target  -> larger chunks
GEAR   = [rand64() for _ in range(256)]       # fixed table, shared by all peers

def next_cut(data, start):
    end = min(start + MAX, len(data))
    if end - start <= MIN:
        return end                            # tail / tiny file -> one chunk
    fp, i = 0, start + MIN                     # cut-point skipping: skip below MIN
    normal = start + AVG
    while i < end:
        fp = (fp << 1) + GEAR[data[i]]         # Gear rolling hash (shift + add)
        mask = MASK_S if i < normal else MASK_L
        if (fp & mask) == 0:                   # content-defined boundary
            return i + 1
        i += 1
    return end                                # forced cut at MAX

FastCDC (USENIX ATC '16) is ~10× faster than Rabin-based CDC at the same dedup ratio — Gear hash + cut-point skipping + normalized chunking (two masks tighten the size distribution).

06  Metadata/content split & the sync flow

Two services: the metadata service (DB — needs transactions, strong consistency, low-latency point reads) tracks files/versions/manifests; the block service stores chunks in cheap, immutable, throughput-oriented object storage. Different durability/latency/cost profiles → never couple them.

07  Conflicts, failure & the ordering invariant

🔀

Conflicts

Two offline edits → two versions. File sync keeps both ("conflicted copy"), never silently merging opaque bytes. OT/CRDT merge is only for collaborative documents (Docs/Paper), not binary blobs.

⛓️

Block-before-metadata

Always durably write blocks, then commit metadata. Reverse it and a crash leaves a manifest pointing at a missing chunk — a dangling, unreadable file. The chosen order risks only orphaned chunks (reclaimed by refcount GC) — bias toward orphans over data loss.

📴

Resumable uploads

Sessions keyed by id + offset; content-addressing makes retries idempotent. A block-store outage still leaves metadata reads/listing working (split tiers).

🧹

Background scrubber

Verifies every committed manifest's chunks exist + checksum; refcount GC deletes chunks at refcount 0 (with a grace period to avoid racing in-flight commits).

08  Multi-region, observability & cost

Multi-region
Erasure-code blobs across zones (Dropbox replicates a fresh block to a second zone within ~1 s, then EC); accept uploads at the nearest PoP; pin a namespace's metadata to a home region for low-latency commits + residency.
Observability & SLOs
Sync latency (edit → visible on peer), dedup ratio + delta-sync efficiency (a bad client rollout that breaks CDC tanks dedup → cost spike), upload success/resume rate, conflict rate, scrubber checksum mismatches, GC backlog. Durability target >12 nines, availability 99.99%.
Cost
Object storage dominates (×10³⁻⁴ over metadata) — Dropbox built Magic Pocket and adopted SMR drives + erasure coding (~1.4× vs 3× replication ≈ 2× capacity saving) purely for $/TB. Dedup + delta sync are the primary levers: dedup cuts stored bytes, delta sync cuts bandwidth.

09  Trade-offs & interview recap

You change one line in a 2 GB video project file. With content-defined chunking + delta sync, what gets uploaded?

Right: only the chunks whose hashes changed are uploaded; the rest are already stored and referenced by hash. Content-defined boundaries mean an insert re-anchors just one chunk instead of shifting all of them.
Say this to nail it

"Split metadata (strongly-consistent DB: files, versions, manifests of chunk hashes) from content (immutable, content-addressed chunks in object storage). Chunk with content-defined chunking — FastCDC — so an insert re-anchors one chunk and delta sync ships only changed chunks; identical chunks dedup globally by hash. Always write blocks before committing metadata so I never get a dangling reference. Conflicts keep both copies. The dominant cost is object storage, so dedup + erasure coding are the levers."
