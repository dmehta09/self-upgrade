Core · web crawler

Design a web crawler.

Systematically download the web — following links page to page — to feed a search index. The web is enormous, looping, and trap-laden, so the design is about scale and discipline: never re-fetching a URL, being polite to each host, deduping near-identical content, and spreading the work across thousands of machines. The non-obvious staff insight: at modern scale a crawler is CPU-bound on TLS handshakes, not bandwidth.

01  Requirements & scale

✅

Functional

Start from seed URLs, download each page, extract + normalize links, store content for indexing, and re-crawl on a freshness schedule.

📐

Non-functional

Billions of pages → massively parallel. Polite (one in-flight request/host, respect robots.txt). Robust to traps (infinite calendars, session-id loops). No duplicate work; durable progress.

03  The crawl loop (BFS over the link graph)

The pipeline (Mercator-style): the frontier hands out a URL (politely), a fetcher downloads it, a parser extracts links, dedup decides what's new, and unseen URLs flow back to the frontier — a breadth-first traversal of the web's link graph.

04  The URL frontier (Mercator)

Two FIFO stages do priority and politeness at once:

Front queues — priority
One queue per priority band; a URL's priority comes from its importance / change rate. Selection is biased toward higher-priority queues. This is "BFS with priorities."
Back queues — politeness
One queue per host, plus a host→queue map (guarantees one open connection/host) and a min-heap of next-allowed-fetch-times. A worker pops the heap root, sleeps until that host is allowed, then fetches its head URL. Rule of thumb: ~3× as many back queues as worker threads so threads rarely starve while staying polite.

05  Dedup: URL-seen & near-duplicate content

URL-seen across tens of billions of URLs would need hundreds of GB in a hash set — a Bloom filter answers it in a fraction of the space, accepting a tiny false-positive rate (≈10 bits/URL → ~1%; ~14–15 bits → ~0.1–0.2%) where a rare FP just skips a page (never loops, never re-crawls).

bloom.py
import math, mmh3
from bitarray import bitarray

class BloomFilter:
    def __init__(self, n, fp=0.01):
        self.m = max(1, int(-(n * math.log(fp)) / (math.log(2) ** 2)))  # bits
        self.k = max(1, int((self.m / n) * math.log(2)))                # hashes
        self.bits = bitarray(self.m); self.bits.setall(0)

    def _idx(self, item):
        for i in range(self.k):
            yield mmh3.hash(item, i) % self.m      # i = per-hash seed

    def add(self, item):
        for j in self._idx(item):
            self.bits[j] = 1

    def contains(self, item):                       # False = definitely absent
        return all(self.bits[j] for j in self._idx(item))   # True = maybe present

Content near-duplicates need more: exact hashing (MD5/SHA) flips on one changed byte (an ad, a timestamp), missing the ~29% of pages that are near-dupes. Use simhash (Google: 64-bit fingerprint, near-dup if Hamming distance ≤ 3) or minhash/LSH (Jaccard similarity over shingles) — locality-sensitive, so similar docs get similar fingerprints.

06  Politeness, traps & freshness

robots.txt (RFC 9309)
Standardizes only User-agent / Allow / Disallow (parse ≥500 KiB, cache ≤24h, treat 5xx as full-disallow). Crawl-delay and Sitemap are NOT in the standard — a common interview gotcha. Per-host rate-limit anyway (Mercator's adaptive "next = now + 10× last download time").
Traps
Infinite calendars and session-id/sort/filter params create unbounded near-dup spaces. Cap crawl depth + URL length, blocklist tracking params, budget pages/host, and normalize URLs (lowercase host, strip default ports, sort/strip params).
Freshness
Model changes as Poisson; surprisingly, a uniform re-visit policy beats a proportional one for average freshness — ignore pages that change too fast, and increase re-visit frequency sub-linearly with change rate, evenly spaced.

07  Failure modes & distributed coordination

🧵

Fetcher crash

Fetchers are stateless — restart and re-pull from the frontier. In-flight URLs need at-least-once redelivery (visibility timeout / un-acked offset).

💾

Frontier durability (the critical one)

Lose the frontier and you lose the crawl's progress. Back it with a durable log — Kafka with acks=all, consumers commit offsets after processing — and checkpoint the seen-set + per-host state.

🧩

Partition by host

Partition the frontier by hash(hostname) so all of a host's URLs land on one scheduler → per-host rate-limiting is correct and a domain is fetched by at most one worker.

☠️

Poison hosts

Tarpits and giant single-host frontiers (real case: yahoo.com/wikipedia.org ballooning to tens of GB). Per-host caps, timeouts, and circuit breakers.

08  Failure, multi-region, observability & cost

Failure modes
Frontier loss → durable log + checkpoint seen-set (a crash must not forget progress). Poison / tarpit hosts → per-host caps, timeouts, circuit breakers. Worker death → reclaim leased URLs via lease TTL. Dedup Bloom false-positive storm → rebuild from durable URL log if hit-rate collapses.
Multi-region
Partition frontier by hash(host) so politeness stays correct; place fetch workers near target ASNs when possible. Seen-set / Bloom can be regional with periodic merge, or global with higher coordination — prefer regional + accept rare cross-region re-fetches. Don't geo-replicate raw WARC eagerly — ship summaries / indexes.
Observability
Pages/s vs target, fetch p50/p99, URL-seen + near-dup hit rates (≈29% dupes; a drop means dedup broke), per-host politeness violations (must be zero — page immediately), frontier depth + hot-host runaway, 4xx/5xx/429 rates, TLS-handshake CPU%, consumer lag on the frontier log.
Cost
Drivers, biggest first: JS rendering compute, fetch CPU (TLS), then storage (compress WARC + dedup before store — the 2025 case used instance storage because S3 for one day was $2k–5k). Bandwidth is rarely the wall. Render selectively, gated by crawl budget.
Security / politeness
Respect robots.txt + crawl-delay; identify with a clear User-Agent; never ignore 429/Retry-After. Isolate crawl credentials; treat fetched HTML as untrusted (XSS in render farm). Blocklist malware / illegal destinations at the frontier.

09  Trade-offs & interview recap

Why is a Bloom filter a good fit for the crawler's "have I seen this URL?" check?

Right: Bloom filters trade a small false-positive rate for huge space savings and no false negatives. For dedup, "occasionally skip a page" is harmless, while "never loop / never re-crawl" is exactly the guarantee we need — and it fits in memory.
Say this to nail it

"It's a BFS over the link graph with a Mercator frontier — front queues for priority, per-host back queues + a time heap for politeness. URL-seen is a Bloom filter (≈10 bits/URL), content near-dups via simhash with Hamming ≤ 3. I'd partition the frontier by host hash so politeness is correct and back it with a durable log so a crash doesn't lose progress. The real bottleneck at scale is TLS-handshake CPU, not bandwidth, so I'd reuse connections and cache DNS, and render JS selectively because it's far more expensive."
