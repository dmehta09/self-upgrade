Case studies · the playbook

The design playbook.

You have ~40 minutes and a blank board. This is the choreography that keeps you in control: what to say, in what order, and how long to spend. Every case study in this guide is solved with these same moves, so by the third one it's muscle memory — and a calm, structured candidate reads as a senior one.

01  Spend your 40 minutes wisely

In plain English analogy

Think of a pilot's pre-flight checklist. Pilots aren't forgetful — they run the list precisely because skipping a step under pressure is how things crash. These moves are your checklist: follow them in order and you'll never freeze, never forget the boring-but-critical parts (like estimating scale), and always read as calm and in control.

The most common failure isn't a wrong answer — it's spending 25 minutes on requirements and never drawing the architecture, or jumping to databases before scoping. A rough budget:

PhaseTimeWhat you produce
Clarify & scope~5 minAgreed feature list, explicit out-of-scope.
Requirements + estimates~5 minFunctional + non-functional, rough QPS/storage.
API + data model~5 minKey endpoints, core tables/entities.
High-level architecture~10 minThe box diagram and the request path.
Deep dives + scaling~10 minThe 2–3 hard parts, bottlenecks, trade-offs.
Wrap-up~5 minRecap, what you'd do with more time.

02  The seven moves — a checklist

1

Clarify & scope

"Who uses it? Which features matter? What scale?" Lock a small core; name what you're cutting.

2

Requirements

Functional (features) and non-functional (scale, latency, availability, consistency). Say "read-heavy or write-heavy?" out loud.

3

Estimate

QPS, storage/year, bandwidth. Numbers justify every later choice.

4

API

A few endpoints. This pins the contract and surfaces missing requirements.

5

Data model

Core entities; SQL vs NoSQL chosen from the access pattern.

6

High-level design

Draw the boxes and the request path. Start simple — one server, one DB — then scale it on the board.

7

Deep-dive & scale

Pick the hard parts. Add caches, shards, replicas, queues where the numbers demand. Name the trade-offs.

03  What earns (and loses) points

✅

Green flags

Driving the conversation, justifying choices with numbers, naming trade-offs ("I'd accept eventual consistency here because…"), starting simple then scaling, knowing when not to add complexity.

🚩

Red flags

Silent whiteboarding, name-dropping tech with no reason, designing for a scale nobody asked for, ignoring the interviewer's hints, never mentioning failure or bottlenecks.

Start simple, then scale

Resist building the final 50-box diagram immediately. Draw the naïve version (one app server, one database), then ask "what breaks at 10× traffic?" and fix it live.
