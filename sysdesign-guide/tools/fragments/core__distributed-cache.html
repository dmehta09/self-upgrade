Core · Redis / Memcached at scale

Design a distributed cache.

A single Redis box is easy. The real problem is a cache spanning hundreds of machines that stays fast as nodes join and leave, survives a node dying without stampeding the database, and copes with one wildly popular key. It pulls together consistent hashing, replication, and eviction — the in-memory layer half your other designs depend on.

01  Requirements & scale

✅

Functional

get(key), put(key, value, ttl), delete(key), plus atomic ops (incr, CAS) and batch (mget). Values are small blobs; any entry may be evicted.

📐

Non-functional

Sub-millisecond reads, millions of ops/s, horizontally scalable, tolerant of node failure (a lost node must not lose everything or stampede the DB). It's a performance optimisation — AP over CP: a stale or missing entry is recoverable from the source of truth.

02  Capacity estimation

Size the hit ratio (it decides DB load), memory (the working set, not the whole DB), and ops/s per node. Worked example fronting a read-heavy DB at 1M reads/s:

QuantityAssumptionResult
DB load @ 95% hit1M reads/s × 5% miss50k reads/s reach the DB (20× shielding)
DB load @ 99% hit1M reads/s × 1% miss10k reads/s — a 4-pt hit gain → 5× less DB load
Working set50M hot objects × 1 KB + ~100 B/key overhead≈ 55 GB → provision ~70 GB (frag + replicas)
Ops/node~100k–200k ops/s/shard (planning)1M reads/s → a handful of shards, not hundreds
Network950k hits/s × ~1.1 KB≈ 8 Gbps egress — big values go NIC-bound first

Takeaway: hit ratio matters super-linearly near the top, and memory + NIC bandwidth — not CPU — are the usual ceilings. Keep values small.

03  API & data model

GETget(key) / mget(k1,k2,…)→ value | null · batch collapses N round trips into 1
SETset(key, value, EX ttl) [NX|XX]TTL is first-class · NX/XX = set-if-absent/present (CAS)
ATOMICincr · getdel · WATCH/MULTI · Luaserver-side atomicity for counters & leases

Stored values are small, self-contained, eviction-eligible blobs (serialized objects, rendered fragments, query results, sessions). Memcached caps items at 1 MB and uses a slab allocator (fixed size-classes, 1.25× growth → no external fragmentation, some internal slack); Redis uses jemalloc over one keyspace and actively defrags. In a cluster, multi-key ops must hit the same shard, so co-locate related keys with hash tags {user123}:profile.

04  Partitioning & the read path

Data is too big for one box, so shard it with consistent hashing (or Redis Cluster's 16384 CRC16 slots — keys→slots→nodes, so resharding moves slots, not keys). A smart client owns the topology, hashes the key, and talks straight to the owning node — no proxy on the hot path.

05  Consistent hashing deep dive

hash(key) % N is fatal for a cache: change N and ~N/(N+1) of keys remap — adding 1 node to 10 moves ~91% of keys to cold nodes → mass miss → DB stampede. The ring maps nodes and keys into one hash space; a key is owned by the first node clockwise, so membership changes move only ~1/N of keys. Virtual nodes (100–200 points/node) even out load and spread an orphaned slice across many survivors.

ring.py
import bisect, hashlib

class HashRing:
    def __init__(self, nodes=(), vnodes=150):
        self.vnodes = vnodes
        self._keys = []        # sorted ring positions
        self._ring = {}        # position -> node
        for n in nodes:
            self.add(n)

    def _h(self, k):
        return int(hashlib.md5(k.encode()).hexdigest(), 16)

    def add(self, node):
        for i in range(self.vnodes):       # scatter many points per node
            h = self._h(f"{node}#{i}")
            bisect.insort(self._keys, h)
            self._ring[h] = node

    def get_node(self, key):
        if not self._ring:
            return None
        i = bisect.bisect(self._keys, self._h(key))   # first vnode clockwise
        if i == len(self._keys):
            i = 0                                       # wrap around the ring
        return self._ring[self._keys[i]]

Traps the snippet handles: find the next point clockwise (bisect), and wrap around when the key hashes past the last point. With 150 vnodes this distributes ~evenly and moves ≈1/N of keys on a membership change.

06  Replication & failure

Each shard = one primary + async replicas. On primary death a coordinator (Redis Sentinel, or cluster gossip + quorum) promotes a replica in single-digit seconds; consistent hashing confines the impact to that shard. Replication is async, so an acked write can be lost on failover — an accepted trade for a cache (the DB is truth).

Why a cache picks AP

A node with no surviving replica loses its slice → those keys become misses and refill from the DB. The danger is a correlated miss storm on the DB for the lost slice — which is why you keep replicas (limit loss to ~1/N), use consistent hashing, and add stampede protection (next section). A cache that blocked to guarantee consistency would defeat its own purpose.

07  Eviction, hot keys & the stampede

At maxmemory, evict by LRU/LFU + TTL. Redis approximates LRU by sampling (default 5 keys) and LFU with an 8-bit decaying counter. Two scaling traps remain. First, the hot key: consistent hashing balances keys, not request rate, so one viral key melts its single shard.

Second, the cache stampede: when a hot key expires, every concurrent request misses at once and hammers the DB. Fix with single-flight (first miss recomputes; others wait for that one result), TTL jitter (so keys written together don't expire in lockstep), and serve-stale while one worker refreshes. RESP3 client-side caching (server pushes invalidations) productises the local-cache layer.

08  Write policies & consistency

How writes touch the cache vs the DB is its own trade-off:

Default: cache-aside + TTL (keeps the cache off the write path; TTL is a staleness bound, not a consistency mechanism). Delete, don't update on writes, and drive invalidation from the DB change log (CDC) when correctness matters.

09  Multi-region, observability & cost

Multi-region
Default to a local cache per region (low latency, blast-radius contained), filled from a regional DB; rely on TTL or a cross-region invalidation fan-out. A globally-replicated cache (Redis Enterprise Active-Active / CRDTs) is eventually consistent across regions (tens–hundreds of ms lag).
Metrics & SLOs
Hit ratio (top-line; alert on level and slope), evictions/s + memory pressure, p99 GET (SLO sub-ms to low-ms), per-shard ops skew (hot-shard detection), connection/NIC saturation. Alert when one shard's load far exceeds the median.
Cost
RAM-dominated — pay for memory-optimised nodes 24×7 plus replicas (~2×). Levers: keep values small/compressed, and push the hottest keys into a free in-process local cache so you buy fewer shards.
2026 landscape
Redis is tri-licensed (AGPL added, Redis 8 GA May 2025); Valkey (Linux Foundation fork) is a cheaper drop-in on AWS/GCP/Azure; Memcached for a lean blob cache; DynamoDB DAX for write-through in front of DynamoDB; Dragonfly for multi-threaded single-box scale.

10  Trade-offs & interview recap

Why is consistent hashing preferred over hash(key) % N for a cache cluster?

Right: with % N, changing N reshuffles almost every key — catastrophic for a cache. Consistent hashing limits churn to one node's share. (It doesn't solve hot keys — that needs replicating the key itself.)
Say this to nail it

"Shard with consistent hashing + virtual nodes so a membership change moves ~1/N of keys, not everything. Primary + async replica per shard, AP because the DB is the source of truth. Cache-aside with TTL and delete-on-write. The two things that bite are hot keys — fix with key replication or an in-process local cache — and stampedes on expiry — fix with single-flight, TTL jitter, and serve-stale. Hit ratio is the metric I'd watch, because a few points of hit ratio is a multiple of DB load."
