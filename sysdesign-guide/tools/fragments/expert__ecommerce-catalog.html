Design e-commerce: catalog, search & cart.

The read side of a store — browse, search, and the cart — is overwhelmingly read-dominated (browse-to-buy ratios of 100:1+). So it's an exercise in caching, a denormalized search read-model over an inverted index, and one subtle correctness rule: a cart does not reserve stock. The write side — checkout, inventory & orders — is a separate page where correctness, not throughput, rules.

01  Requirements & scale

✅

Functional

Browse categories, full-text + faceted search (filter by brand/size/price with counts), product detail (variants), add to cart, see prices/promotions.

📐

Non-functional

Read-heavy (100:1+); fast (p99 detail < ~150 ms, search < ~300 ms); survives flash-sale spikes (3–5× + a viral "hot product"); catalog/price eventual consistency is fine.

04  Data model: product vs SKU

Product → variant/SKU
The product is the sellable concept ("Acme Trail Runner"); the SKU/variant is the purchasable unit ("red, size 10"). Product-level: title, description, category, brand, attribute schema. SKU-level: the immutable SKU code, distinguishing attributes, images, price, inventory.
Attributes (EAV)
Every product type has different attributes (a shoe has size, a laptop has RAM) → an EAV/pivot model for schema-free attributes, at the cost of expensive multi-attribute filtering joins (which is exactly why filtering moves to the search index).
Store choice
Relational as the source of truth (constraints, joins, price/inventory FKs); a denormalized document / search read-model (fed async via CDC) for fast point reads and facets. Category tree = closure table / materialized path for "all descendants of Electronics" in one range query.

05  Architecture: a derived search read-model

Catalog is the system of record; search is a denormalized, async-fed read model that owns full-text, facets, and ranking — and is allowed to lag. Category browse is "search with an empty query + a category filter."

06  Search & faceted navigation

SQL LIKE '%term%' is a leading wildcard → full table scan, hopeless at 10⁶–10⁸ products. The right tool is an inverted index (term → posting list of doc ids; queries are set intersections, sublinear and shardable). Facets are value counts over the filtered set (so users never click into a zero-result filter), computed as bucket aggregations — and you must flatten nested SKU attributes to top-level keyword fields:

Inverted index — a query is set intersection
Each filter is a pre-sorted posting list; the query result is their intersection, and facet counts are bucket aggregations over that result — which is why facet numbers always match what users will actually see.
search.json
POST /products/_search
{
  "query": { "bool": {
    "must":   { "multi_match": { "query": "running shoes",
                "fields": ["title^3","brand^2","description"], "fuzziness": "AUTO" } },
    "filter": [ { "term": { "category": "footwear" } },          // filter = not scored,
                { "term": { "brand": "Nike" } },                 //   CACHED as a bitset
                { "range": { "price": { "gte": 50, "lte": 150 } } } ]
  } },
  "aggs": {                                    // facet COUNTS over the filtered set
    "brands": { "terms": { "field": "brand", "size": 20 } },
    "price":  { "range": { "field": "price",
                "ranges": [ {"to":50}, {"from":50,"to":150}, {"from":150} ] } }
  },
  "size": 24
}

Relevance = BM25 base + multiplicative business boosts (popularity, margin, stock, personalization), plus typo tolerance (fuzzy), synonyms, and autocomplete. 2026: hybrid lexical + vector search (BM25 + embeddings fused with RRF) — pure keyword misses natural-language intent, pure vector misses exact SKUs.

07  The cart (and why it doesn't reserve stock)

Cart ≠ reservation

Adding to cart does not hold inventory — almost every major platform works this way. Reserving on add-to-cart would let idle/abandoned carts lock stock indefinitely. The consequence is an oversell window: the availability check and the stock decrement aren't atomic, so two carts can both hold "the last one." That's resolved on the write side at checkout (atomic decrement / short reservation), never in the cart.

Guest vs persistent
Guest cart keyed by session id in Redis (hash per cart, native TTL ~7 days so abandoned carts self-evict); logged-in cart keyed by user id, durable (write-through to DB so an eviction can't lose it). Merge on login with an explicit conflict policy.
Price-at-checkout
The cart may display an add-time price, but the authoritative price is recomputed at checkout — never trust a stale/client price as the charge amount.

08  Pricing, promotions & read scaling

Pricing is computed, not flat
The price a user sees is a function of a price book (per currency/segment) + active promotions + loyalty tier + region/tax + time. A flat column can't express "Nike 20% off this weekend for loyalty members in EUR" — a rules engine evaluates it on every cart mutation. Search indexes a representative base price for facets/sort, then overlays the personalized/promo price at render.
Caching layers
CDN (product pages/images/JSON for anonymous traffic — the bulk), Redis (hot products, category trees, facet results; TTL tiered by volatility), read replicas behind. Event-driven invalidation on price/inventory change.
The hot-product stampede
A viral item's cache key expires → thousands of concurrent misses hit the DB. Fix with TTL jitter, probabilistic early recompute, and single-flight (one request recomputes; others wait) — the same stampede pattern as the distributed cache.

09  Consistency, failure modes & observability

🔁

Eventual is fine here

Catalog/price propagating to the index + caches in seconds is acceptable; "only 2 left" is an approximate, cached nudge, not a guarantee. Strong consistency is needed exactly once — the stock decrement at checkout.

🔎

Search index lag

New/edited products missing from results → monitor indexer lag (event→searchable time); alert + reindex jobs.

📊

Business metrics

Zero-result rate (a direct conversion leak), search→click→add→buy funnel, search-influenced revenue. Use p99, not averages — tail latency kills conversion.

🧩

2026 stack

Headless / composable (MACH) with best-of-breed search/cart/checkout; semantic/vector + hybrid retrieval mainstream; catalog/search increasingly served to AI shopping agents via structured product feeds, not just HTML.

10  Trade-offs & interview recap

Why not implement product search with SELECT … WHERE name LIKE '%term%', and why doesn't the cart reserve inventory?

Right: %term% forces an O(N) scan with no relevance/facets; a dedicated inverted index gives sublinear search, ranking, typo tolerance, and facet counts. And cart ≠ reservation: the oversell window is closed at checkout with an atomic decrement, not by holding stock for every browser.
Say this to nail it

"It's read-dominated, so I push everything to the edge + cache and serve search from a denormalized inverted index (Elasticsearch/Algolia) with flattened SKU attributes for facets — BM25 plus business boosts, now hybrid with vector for intent. Product vs SKU is the core model. The cart lives in Redis with a TTL and deliberately holds no stock — reservation happens at checkout. Pricing is computed from a price book + promo engine, not stored flat. The risk to watch is the hot-product stampede, which I'd handle with TTL jitter, early recompute, and single-flight."
