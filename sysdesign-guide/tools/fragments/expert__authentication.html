Expert · authentication

Design authentication.

"Who are you?" — proving identity, then carrying that proof safely on every request. The two decisions that define the system are how you store credentials (Argon2id, never a fast hash) and how you carry the session (revocable server-side sessions vs stateless JWTs, which can't be revoked before they expire). Authorization — what you can do — is a separate page; authn produces the identity that authz consumes.

01  Requirements & scope

✅

Functional

Register/login; sessions; password reset; MFA; social login (OAuth/OIDC); enterprise SSO (SAML/OIDC) + SCIM provisioning; logout / "log out everywhere".

📐

Non-functional

Phishing-resistant where possible; token validation on the API hot path (every request); a hard-availability dependency; resilient to credential stuffing + ATO.

02  Password storage: Argon2id

Passwords are never encrypted (reversible) — they're run through a slow, salted, memory-hard function. The 2026 OWASP default is Argon2id (min 19 MiB / 2 iterations / 1 parallelism); bcrypt (cost ≥ 10, 72-byte limit) only for legacy. Never a fast hash — GPUs do tens of billions of SHA-256/s.

password.py
from argon2 import PasswordHasher          # OWASP minimum params
ph = PasswordHasher(memory_cost=19456, time_cost=2, parallelism=1)

def hash_password(plain, pepper):
    pre = hmac_sha384(key=pepper, data=plain)     # pepper: app-wide secret in KMS, NOT the DB
    return ph.hash(pre)            # PHC string embeds algo + params + a random per-pw SALT

def verify_password(stored, plain, pepper):
    try:
        ph.verify(stored, hmac_sha384(key=pepper, data=plain))   # constant-time internally
    except Exception:
        return False
    if ph.check_needs_rehash(stored):   # params bumped over time -> upgrade transparently
        rehash_and_store(plain)
    return True

Salt (per-password, in the hash) defeats rainbow tables; pepper (one app-wide secret, stored separately in KMS) makes a DB-only dump uncrackable. Never compare hashes with == — the PHF does a timing-safe compare. NIST SP 800-63B-4 (2025): ≥15 chars for single-factor, no composition rules, no forced rotation, mandatory breach screening.

03  Sessions vs JWT, & refresh rotation

The core trade-off is revocability vs statelessness:

The standard 2026 design: 5–15 min access token + a rotating refresh token (each refresh issues a new one, single-use). If an already-used refresh token reappears, it's theft — revoke the whole token family (RFC 9700):

refresh.py
def refresh(presented):
    rec = store.get_refresh(hash(presented))         # tokens stored HASHED, never raw
    if rec is None:
        raise Reject("unknown")
    if rec.used:                                     # a rotated token replayed = THEFT
        store.revoke_family(rec.family_id)           # nuke the whole lineage
        alert_security(rec.user_id); raise Reject("reuse detected")
    if rec.revoked or now() > rec.expires_at:
        raise Reject("revoked or expired")
    rec.used = True; store.save(rec)                 # mark old as spent (single-use)
    new_rt = random_token()
    store.put_refresh(hash(new_rt), family_id=rec.family_id, user_id=rec.user_id)
    new_at = sign_jwt(sub=rec.user_id, exp=now()+ACCESS_TTL, jti=uuid())
    return new_at, new_rt

Where tokens live (SPA gold standard): refresh token in an httpOnly; Secure; SameSite cookie (XSS can't read it), access token in memory only (re-minted via refresh). localStorage is CSRF-immune but fully XSS-exposed — don't put session tokens there.

04  MFA & passkeys

Passkeys / WebAuthn (FIDO2)
The 2026 direction: a keypair bound to the origin, so a proxy phishing site can't get a usable signature — phishing-resistant by construction, defeating the AitM attack that breaks passwords/TOTP/SMS. The private key never leaves the device; the server stores only a public key (a breach yields nothing). Synced passkeys (iCloud/Google) solve device-loss; ~5B in use by mid-2026.
TOTP
Authenticator app, 30-s codes. Good baseline MFA, but real-time relay/AitM-phishable.
SMS OTP
Discouraged — NIST 800-63B-4 made it a "restricted authenticator" (SIM-swap, SS7). Treat a recent SIM change as a risk signal.

Direction: passwords + SMS → app TOTP/push → passkey-primary (passwordless), with a hardware key or recovery codes as fallback.

05  OAuth2 / OIDC

OAuth 2.0 = delegated authorization; OIDC adds an identity layer (the id_token) for authentication. The 2026 default for all client types is the authorization code flow + PKCE (OAuth 2.1 removes implicit + password grants). PKCE binds the code to the originating client, so a stolen code is useless without the verifier.

OIDC adds the signed id_token (who logged in: sub, email, nonce), a UserInfo endpoint, and discovery (/.well-known/openid-configuration + JWKS). Use OAuth/OIDC for delegated access and social login.

06  Enterprise SSO & SCIM

SAML vs OIDC
SAML 2.0 still dominates the enterprise install base; OIDC is preferred for new/mobile. Prefer SP-initiated flows (request-bound, replay-resistant; OIDC mandates it).
SCIM
Login (SAML/OIDC) only handles the moment of auth; SCIM handles lifecycle — the IdP creates/updates/deprovisions accounts (offboarding kills access, which SSO alone wouldn't).
Per-org SSO
Each B2B tenant brings its own IdP + config (entity id, ACS URL, certs / OIDC issuer), keyed per org, with IdP discovery by email domain and a self-serve admin portal. This is what WorkOS/Clerk productize.

Validate JWTs with the AS public key (RS256/ES256 via JWKS, cached) and pin the algorithm (reject the header's alg — stops alg:none / confusion). Asymmetric signing means a compromised service can't forge tokens for the fleet (unlike HS256's shared secret).

08  Failure modes & security

🎯

Credential stuffing

The #1 vector (billions of attempts/mo). Defend with a breached-password check (HIBP k-anonymity — send the first 5 hex of the SHA-1, match the rest locally; the password never leaves you), per-account + per-IP rate limits, and MFA/passkeys.

🔓

Token theft

Short access TTL + refresh rotation/reuse-detection + sender-constrained tokens (DPoP / mTLS) so a stolen token is useless without the key.

🪤

Session fixation

Regenerate the session id on login/privilege change; never accept a session id from a URL.

🤖

Bots / brute force

Exponential backoff + lockout; escalate to CAPTCHA only on suspicion (protect UX); device fingerprinting + WAF.

09  Observability, SLOs & 2026 notes

Metrics & SLOs
Login success/failure rate (a failure spike = stuffing in progress; segment by IP/ASN/geo), MFA + passkey adoption, token-validation latency (p99 < 10 ms), Argon2id verify latency, refresh-reuse/family-revocation events (security alerts). Auth-service availability ≥ 99.99% — it's a hard dependency for everything.
2026 shifts
OAuth 2.1 (PKCE mandatory, implicit/ROPC removed) + RFC 9700 security BCP; passkeys mainstream; CAEP / Shared Signals — trusted transmitters push near-real-time events (session revoked, risk changed) so receivers attenuate access mid-session instead of waiting for token expiry (the ecosystem answer to "JWTs can't be revoked").
Build vs buy
Most teams buy the IdP (Auth0/Okta, WorkOS, Clerk, Stytch) and own the session + authorization model.

10  Trade-offs & interview recap

You use stateless JWTs for scale. How do you handle "log this user out everywhere right now"?

Right: JWTs can't be revoked before exp, so you bound exposure with short TTLs + refresh rotation, and bump a per-user token-version (or denylist the jti) for immediate revocation. The trade-off is the whole sessions-vs-JWT decision: statelessness costs you revocability.
Say this to nail it

"Store passwords with Argon2id (salt + a KMS pepper), never a fast hash. For sessions I'd use short-lived access JWTs + rotating refresh tokens with reuse detection — stateless validation scales, and the short TTL + rotation bounds the revocation gap; refresh token in an httpOnly cookie, access token in memory. Login is OIDC auth-code + PKCE; enterprise tenants bring their own IdP via SAML/OIDC plus SCIM for provisioning. I'd push toward passkeys because they're phishing-resistant by origin-binding, screen passwords against HIBP, and pin the JWT algorithm to avoid alg-confusion."
