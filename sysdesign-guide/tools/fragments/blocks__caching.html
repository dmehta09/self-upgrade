Caching.

A cache is a small, fast store (usually in-memory, like Redis) that holds copies of hot data so you don't recompute or re-fetch it. It's the single biggest scaling lever in most systems: a good cache turns a 10 ms database read into a 1 ms lookup and shields your database from the bulk of traffic. The whole art is deciding what to cache, how to write through it, and when to evict.

03  Eviction, TTLs & the hard parts

A cache is small, so it must throw things out. LRU (least-recently-used) is the default; LFU (least-frequently-used) suits skewed popularity. A TTL caps how stale data can get. Two classic failure modes to name in interviews:

🔥

Hot key

One key (a celebrity, a viral post) gets so much traffic it overloads the single cache node holding it. Fix: replicate that key across nodes, or add a local in-process cache.

🌩️

Cache stampede

A popular key expires and thousands of requests miss at once, all hammering the DB. Fix: add jitter to TTLs, or let one request recompute while others serve stale ("request coalescing").

There are only two hard things…

"…cache invalidation and naming things." Keeping the cache in step with the source of truth is genuinely hard — which is why "what's your cache freshness requirement?" is one of the most useful questions you can ask in a design.

Right: for high-volume, loss-tolerant counters, write-back (increment in the cache, flush to the DB periodically) gives huge write throughput. Reserve write-through for data that must always be fresh.
