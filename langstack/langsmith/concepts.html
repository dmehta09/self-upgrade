LangSmith · core concepts

From a single trace to a tested, monitored app.

Eleven ideas take you from "what's a trace?" to grading your app on a dataset and watching it in production. Each comes with a picture, runnable Python, and the gotcha that trips up beginners. Remember: LangSmith works with LangChain, LangGraph, or any plain code.

01  Traces, runs & the run tree key idea

Three words form the backbone of LangSmith:

trace
One complete execution of your app — everything that happened to handle a single user request.
run
One step inside a trace: an LLM call, a tool call, or a function. Runs nest into a tree.
project
A named bucket that groups related traces together (e.g. all traces from my-first-app).

Every run records the same useful details: its inputs and outputs, how long it took (latency), how many tokens it used (which is how you see cost), any error it threw, and free-form metadata you attach (user ID, version tag, and so on).

A run tree — and what each run captures
trace · the whole request
rag_pipeline("What's our refund policy?")
captures: total latency 1.8s · 2,140 tokens · status OK · metadata {user: "u_42"}
run · retrieval
retrieve_docs(query)
inputs: the query · outputs: 3 chunks · 90ms · no tokens (not an LLM)
run · llm
call_llm(prompt + docs)
inputs: full message list · outputs: AI reply · 1.6s · 2,140 tokens · ~$0.01
run · child
format_prompt(...)
inputs: docs + question · outputs: messages · 3ms
run · child
parse_output(...)
inputs: AI message · outputs: clean string · 1ms
Click any run in the LangSmith UI to expand exactly these fields. The trace's cost is just the sum of its runs.

What's the difference between a trace and a run?

Exactly. A trace is the full record of one user request; the individual steps inside it (LLM calls, tool calls, functions) are runs. Runs nest to form the run tree, and a project is the bucket that groups many traces.

02  Enabling tracing

There are three ways to get traces into LangSmith — pick whichever matches your code.

1) Environment variables (automatic for LangChain & LangGraph)

Set these and you're done — every LangChain/LangGraph call is traced with no code change.

terminal
$ pip install langsmith
$ export LANGSMITH_TRACING=true
$ export LANGSMITH_API_KEY="lsv2_..."
$ export LANGSMITH_PROJECT="my-first-app"

2) The @traceable decorator (any function)

For plain Python, decorate the functions you want to record. Use run_type to tell LangSmith what kind of step it is, so the UI renders it nicely.

traceable.py
from langsmith import traceable

@traceable
def retrieve(query: str):
    return ["doc A", "doc B"]

@traceable(run_type="llm")          # mark this run as an LLM call
def call_model(prompt: str):
    return "...the model's reply..."

@traceable
def answer(query: str):
    docs = retrieve(query)          # nested as a child run
    return call_model(f"{docs}\n{query}")

answer("What is LangSmith?")        # the whole call tree becomes one trace

3) A context manager (fine control)

When you want to trace just a block of code — not a whole function — wrap it in trace().

context.py
from langsmith import trace

with trace(name="retrieve-step", run_type="retriever") as run:
    docs = my_search("refund policy")
    run.end(outputs={"docs": docs})   # record what this block produced
Mix and match

These three combine freely. A LangChain app traced via env vars can also have your own helper functions decorated with @traceable — they all land in the same run tree.

03  The Playground

The Playground is an in-browser scratchpad. From any traced LLM call you can hit "Open in Playground," and LangSmith loads that exact call — same prompt, same inputs — into an editor.

There you can change the prompt wording, switch the model, nudge the temperature, and re-run instantly to compare the new answer with the original. Because it's all in the browser, a product manager or writer can iterate on a prompt without touching code, a terminal, or a deploy.

Debug → tweak → re-run, in one place

The Playground closes the loop: you spot a bad answer in a trace, open it, fix the prompt, and confirm the fix — all without leaving the browser.

04  Prompt Hub & versioning

The Prompt Hub is like GitHub, but for prompts. You push a prompt to save a version, pull to fetch the latest (or a specific version), and roll back if a new version turns out worse. Each push is recorded, so your prompts have a history just like code.

The payoff: a prompt lives outside your codebase. The product team can edit and ship a better prompt without waiting on an engineering deploy — your app just pulls the latest version at runtime.

prompt_hub.py
from langsmith import Client
client = Client()

client.push_prompt("support-reply", object=my_prompt)   # save a version
prompt = client.pull_prompt("support-reply")             # fetch latest
prompt = client.pull_prompt("support-reply:abc123")      # fetch a specific version

05  Datasets & examples

A dataset is a test set for your LLM app: a collection of examples, where each example pairs an input with the expected output. It's your regression suite — the fixed set of questions you re-grade every time you change a prompt or model.

You can build a dataset by hand, import a CSV, or (very common) save real traces you liked straight from production into a dataset.

datasets.py
from langsmith import Client
client = Client()

dataset = client.create_dataset(
    dataset_name="qa-examples",
    description="Question -> expected answer pairs for our support bot.",
)

client.create_examples(
    dataset_id=dataset.id,
    examples=[
        {"inputs": {"question": "What's the refund window?"},
         "outputs": {"answer": "30 days with a receipt."}},
        {"inputs": {"question": "Is shipping free?"},
         "outputs": {"answer": "Yes, on orders over $50."}},
    ],
)

06  Evaluation: grading your app key idea

This is the half of LangSmith that turns "I think it got better" into a number. You run your app over a dataset and score each output with one or more evaluators. There are three flavors:

Heuristic

Plain code or simple rules — exact match, regex, "is it valid JSON?", length checks. Fast, free, deterministic.

LLM-as-judge

A strong model reads the answer (and a reference) and grades it — perfect for open-ended text no rule can score.

Pairwise

Compare two versions of your app head-to-head and pick the better answer — great for "did v2 beat v1?"

The evaluate() function ties it together: give it your app, the dataset name, and a list of evaluators.

evaluate.py
from langsmith import evaluate

def my_app(inputs: dict) -> dict:
    return {"answer": run_my_chain(inputs["question"])}

# a heuristic evaluator
def is_correct(outputs: dict, reference_outputs: dict) -> bool:
    return outputs["answer"].strip() == reference_outputs["answer"].strip()

results = evaluate(
    my_app,
    data="qa-examples",            # the dataset name
    evaluators=[is_correct],
    experiment_prefix="baseline-gpt-4o",
)
What "LLM-as-judge" means

When answers are free-form sentences with no single right string, you hand the answer to a strong model and ask it to grade — e.g. "Is this answer correct and helpful given the reference? Score 0–1." It judges what a simple rule can't.

Your answers are free-form sentences with no single "right" string. Which evaluator fits best?

Right. Exact-match rules break the moment two correct answers are worded differently. An LLM-as-judge reads the meaning and grades against a reference, so it handles open-ended text that no simple rule could score.

07  Experiments & comparison

Each time you call evaluate(), LangSmith records the whole run as an experiment — a snapshot of how one version of your app scored on a dataset. The experiment_prefix you passed becomes its name.

The real value is comparison. Run evaluate() again with a different model or a new prompt, then open both experiments side-by-side in the UI. LangSmith lines up every example and shows you, per row and in aggregate, how accuracy, latency, and cost changed — so "v2 is better" becomes a table you can point at.

08  Monitoring in production

Once your app is live, the same traces power dashboards. Out of the box you get charts for request volume, latency (median p50 and tail p99), token cost, error rate, and any feedback scores you collect.

Two production-only features build on that:

  • Online evaluation — automatically run an evaluator (often an LLM-as-judge) on a sample of live traffic, so you keep scoring quality on real users without a fixed dataset.
  • Alerts — get notified when error rate spikes, latency climbs, or cost suddenly jumps, before users complain.
p50 vs p99

p50 is the median — half of requests are faster. p99 is the slow tail — only 1% are slower. Watching p99 catches the painful outliers that an average would hide.

09  Annotation queues & human feedback

Some traces need a human eye. An annotation queue is a review inbox: you route uncertain or important traces to people, who label them good or bad and leave notes — right inside LangSmith, no spreadsheet needed.

You can also capture user feedback directly — the 👍 / 👎 a user clicks in your app attaches to that trace as a feedback score. Either way, those human labels are gold:

  • Use them to improve your evaluators — check whether your LLM-as-judge agrees with humans.
  • Collect the good examples into a dataset for regression testing.
  • Gather labeled data to fine-tune a model later.

10  Cloud vs self-hosted & pricing

LangSmith comes in two deployment shapes. Most people start on the cloud; large organizations with strict data rules self-host.

Cloud
Sign up and start in minutes. Usage-based pricing, with a free Developer tier (~5,000 traces/month, ~14-day trace retention, no credit card). The default for almost everyone.
Self-hosted
Runs inside your own infrastructure on Enterprise plans. For teams with strict data-residency or compliance needs — your trace data never leaves your network.
Numbers move

Exact free-tier limits, retention windows, and per-trace pricing change over time — treat the figures here as a ballpark and check the current pricing page before you plan around them.

11  Tips & gotchas

A few things that save beginners a lot of confusion:

Tracing barely costs you anything

Traces are sent asynchronously and batched in the background, so adding LangSmith adds negligible latency to your app. Leave it on.

Never log secrets or PII into traces

Inputs and outputs are stored verbatim. Scrub API keys, passwords, and personal data before they hit a traced function — once it's in a trace, it's stored.

Mind the free-tier trace cap

The free Developer tier caps you at roughly 5,000 traces per month. A chatty app can burn through that quickly — sample or upgrade if you're tracing every request in production.

"I see nothing!" — check two things

If no traces appear, confirm LANGSMITH_TRACING is set to true and a valid LANGSMITH_API_KEY is present. Miss either one and your app runs fine but records nothing.
