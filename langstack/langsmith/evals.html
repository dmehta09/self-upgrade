LangSmith · evaluation in depth

Stop eyeballing it. Start grading it.

You've seen evaluate() in Core concepts. This lesson takes you the rest of the way: datasets that actually catch bugs, evaluators you write yourself, an LLM judge you can trust, humans in the loop, evals on live traffic — and finally a regression suite your CI runs on every pull request.

01  Designing datasets that catch bugs

An eval is only as good as its dataset. Twenty examples that probe your app's weak spots beat five hundred easy ones — a suite full of softballs scores 100% forever and tells you nothing.

Where do good examples come from? Real traces. The best source is production: in the LangSmith UI, any trace is one click away from "Add to dataset." When a user hits a bad answer, that trace — with its real, messy input — becomes a test case. Hand-written examples are fine for day one, but real failures are where the bugs live.

The harvest loop: production failures become test cases

Each harvested failure makes the suite permanently harder to pass — that's the point.

Most teams end up with three kinds of examples, often as separate datasets or tagged subsets:

golden set
Representative, everyday inputs with carefully checked expected outputs. Answers the question "does the normal stuff still work?"
adversarial set
Inputs designed to break things: weird phrasing, prompt-injection attempts, off-topic questions, edge-case data. Answers "does it fail safely?"
regression set
One example per bug you've ever fixed, harvested from real traces. Answers "did the old bug come back?" — and it only ever grows.
Analogy: the driving test route

A driving examiner doesn't pick a random street — the route deliberately includes the hard left turn across traffic, the steep hill start, the tight parallel park. And if a student crashed at a particular junction last month, that junction is on the route now. Your dataset is the route: it must include every turn that has ever caused a crash.

Two structural features make datasets scale beyond a flat list:

  • Splits — named slices of one dataset (e.g. billing, shipping, multilingual). Run an experiment and read scores per split: "v2 improved billing questions but tanked multilingual" is a far more useful sentence than "v2 scored 84%."
  • Versions — datasets are append-only with versions: every time you add or edit examples, LangSmith records a new version, and you can evaluate against a specific one (e.g. data="qa-examples:v3" or an as-of timestamp). Pin a version in CI so a teammate adding ten hard examples doesn't make your PR look like it caused a regression.

Your eval suite has scored 100% on every run for three months. What's the most likely explanation?

Almost certainly the dataset. (Check the evaluator too — but) a suite that never fails isn't proving quality, it's proving the route has no hard turns. Harvest failing production traces into a regression set and add adversarial inputs until the score has room to move.

02  Custom evaluators: just Python functions

Here's the secret that makes evaluation approachable: an evaluator is just a Python function. It receives the example's inputs, your app's outputs, and the expected reference_outputs — and returns a score. That can be a bool, a number, or a dict when you want to name the metric yourself.

evaluators.py
import re

# 1) Exactness — a bool is a perfectly good score
def exact_match(outputs: dict, reference_outputs: dict) -> bool:
    return outputs["answer"].strip() == reference_outputs["answer"].strip()

# 2) Contains / regex — "did it cite a source like [doc-name §N]?"
def contains_citation(outputs: dict) -> bool:
    return bool(re.search(r"\[[\w\-]+ §\d+\]", outputs["answer"]))

# 3) Multi-key return — name the metric and score it yourself
def conciseness(outputs: dict) -> dict:
    words = len(outputs["answer"].split())
    return {"key": "conciseness", "score": max(0.0, 1 - words / 200)}
    # e.g. {"key": "conciseness", "score": 0.8} for a 40-word answer

Wire them in with evaluate() — same call you met in Core concepts, now with your own graders:

run_evals.py
from langsmith import evaluate

def target_fn(inputs: dict) -> dict:
    return {"answer": rag_pipeline(inputs["question"])}

results = evaluate(
    target_fn,
    data="my-dataset",
    evaluators=[exact_match, contains_citation, conciseness],
    experiment_prefix="rag-v2",
)

LangSmith inspects each function's signature and passes only the arguments it asks for — contains_citation above never mentions reference_outputs, so it works even on examples (or live traces) that have no expected answer.

Deterministic evaluators first

Before you reach for an LLM judge, squeeze everything you can out of plain code: exact match, contains, regex, "is it valid JSON?", length limits. They're free, fast, and never disagree with themselves — the same answer always gets the same score. Save the judge for the qualities code genuinely can't measure.

03  LLM-as-judge, calibrated

Some qualities no regex can score: was the answer helpful? Was the tone right for an apology email? Did it actually address the question? For these you hand the answer to a strong model and ask it to grade. That works — but a judge is itself an LLM, with its own failure modes. Trust it the way you'd trust a new intern grader: only after you've checked their work.

position bias
In side-by-side comparisons, judges favor whichever answer comes first. Fix: evaluate both orders (A-then-B and B-then-A) and keep only consistent verdicts.
verbosity bias
Longer answers score higher even when they say less. Fix: tell the judge length is not a virtue — and pair it with a deterministic conciseness check.
score inflation
Ask for 1–10 and everything lands at 7–9; the scale compresses and signal vanishes. Fix: use binary pass/fail or a short rubric (0 / 0.5 / 1), with the rubric written in the prompt.
judge drift
The judge model gets updated or swapped, and your scores shift with no change to your app. Fix: pin the judge's model version, and spot-check the judge against human labels (see §05) before trusting a trend.

A calibrated judge in code — structured output so you get a clean verdict and the reasoning behind it:

judge.py
from pydantic import BaseModel, Field
from langchain.chat_models import init_chat_model

class Verdict(BaseModel):
    reasoning: str = Field(description="One or two sentences explaining the grade.")
    correct: bool = Field(description="Does the answer match the reference in substance?")

judge = init_chat_model("gpt-4o").with_structured_output(Verdict)

def correctness(inputs: dict, outputs: dict, reference_outputs: dict) -> dict:
    verdict = judge.invoke(
        "You are grading a support bot. Rubric: PASS only if the answer "
        "states the same facts as the reference; wording may differ. "
        "Extra length earns nothing. FAIL on any contradiction or omission.\n\n"
        f"Question: {inputs['question']}\n"
        f"Reference: {reference_outputs['answer']}\n"
        f"Answer: {outputs['answer']}"
    )
    return {"key": "correctness", "score": int(verdict.correct),
            "comment": verdict.reasoning}

Note what's in there: the rubric lives inside the prompt (the judge isn't left to invent standards), the output is a bool (no inflated 7/10s), and the comment lands in LangSmith next to the score so you can audit why something failed.

Why do practitioners prefer pass/fail (or a tiny rubric) over asking the judge for a 1–10 score?

Right. A 1–10 scale invites score inflation: the judge hedges toward the top, the difference between 7 and 8 means nothing, and trends get noisy. A binary question against an explicit rubric ("PASS only if…") is a decision the judge can make consistently — and a human can check.

04  Experiments & pairwise comparison

Every evaluate() call produces an experiment: one dataset × one version of your app, with every example's output and every evaluator's score recorded. Change the prompt, run again, and you have two experiments to put side-by-side in the UI — LangSmith aligns them row by row, so you see exactly which examples got better and which regressed, not just the aggregate.

Two refinements matter once you compare seriously:

  • Pairwise evals — for subjective qualities ("which reply sounds more empathetic?"), absolute scores are mushy. Instead, give a judge both experiments' answers to the same example and ask it to pick A or B (remember position bias: run both orders). A preference is a much easier question than a grade.
  • Repetitions — LLMs are nondeterministic, so a single run can flatter or slander a version. evaluate(..., num_repetitions=3) runs each example several times and averages, taming variance before you conclude "v2 is better."

Evaluators cost money too

Notice the judge run above burned 412 tokens — per example, per repetition. The regex check cost nothing. This is the economic argument for §02's gotcha: deterministic checks scale to thousands of examples for free; judges should be reserved for the questions worth paying for.

05  Annotation queues & human feedback

Some judgments still need a person: subtle correctness in a specialist domain, policy and brand-voice calls, anything where you wouldn't trust the intern or the judge. LangSmith's tool for this is the annotation queue — an inbox of runs routed to human reviewers.

The flow: you (or a rule) send runs to a queue — say, every run a user thumbed-down, or a 2% random sample. Reviewers open the queue, see one run at a time with your rubric alongside it, and attach feedback: scores and notes that stick to the run permanently. No spreadsheets, no copy-pasting transcripts into Slack.

An annotation queue is an inbox with a rubric
routing rule

Reviewers grade in LangSmith itself — no spreadsheet export, no lost context.

Those human labels are the most expensive data you'll ever collect, so spend them twice:

  • Build datasets — runs labeled "bad" become regression examples (§01); runs labeled "great" become golden examples with trusted reference outputs.
  • Calibrate your judge — run your LLM judge over the same runs humans labeled and measure agreement. 90%+ agreement: trust the judge to scale. 60%: your judge prompt needs work before its scores mean anything.
End users are annotators too

The 👍/👎 buttons in your app can call client.create_feedback(run_id, key="user-score", score=0) — that lands in the same feedback system as reviewer labels. Filter for thumbed-down traces, route them to a queue for a closer look, and graduate the confirmed failures into your regression set.

You have 200 production runs labeled by human reviewers. Beyond fixing the bad ones, what's the highest-leverage use of those labels?

Yes — spend them twice. Human labels are ground truth: comparing the judge's verdicts against them tells you whether you can trust the judge at scale, and the labeled runs themselves become golden/regression examples. (Fine-tuning may come later, but 200 examples is calibration-sized, not training-sized.)

06  Online evaluation: grading live traffic

Offline evals grade a fixed dataset. But production has a habit of inventing inputs your dataset never predicted — a new product launch shifts every question, a retriever index goes stale, an upstream model update changes behavior overnight. Online evaluation runs evaluators automatically on a sample of live traces as they arrive.

The crucial difference: live traffic has no reference answers. Nobody wrote down the expected output for a question a user asked thirty seconds ago. Online evaluators therefore judge inputs and outputs only — reference-free questions like:

  • Does the answer actually address the question? (LLM judge, no reference needed)
  • Is the output valid JSON / does it carry a citation? (your deterministic checks from §02 — they never needed a reference anyway)
  • Did the answer leak a system prompt, refuse unnecessarily, or use a forbidden phrase?
Online evaluation: the loop that closes itself

page the team

Drift caught by a sampled judge today becomes a deterministic regression test tomorrow.

Scores attach to the live traces and flow into the same dashboards as everything else — so you set an alert on "answer-relevance dropped below 0.85 this hour" and hear about drift from a pager, not from a customer. When the alert fires, the low-scoring traces are right there: triage them, send the confirmed failures to an annotation queue, and add them to the regression set. The loop closes.

Online judges bill you per sampled trace

Every sampled trace triggers a real LLM call to the judge. At 100% sampling on a busy app, your evaluation bill can rival your application's model bill. Sample 1–5% of traffic — drift is a trend, and a trend shows up fine in a sample. Run cheap deterministic checks at a higher rate if you like; they're free.

Why can't your offline exact_match evaluator be used as-is for online evaluation?

Exactly. Live traffic is reference-free — nobody pre-wrote the right answer to a question a user just invented. Online evaluators may only look at inputs and outputs: format checks, citation regexes, and reference-free judges ("does the answer address the question?") all work; anything that needs reference_outputs doesn't.

07  Wiring evals into CI

Everything so far is still optional until it runs automatically. The end state: a teammate opens a PR that tweaks a prompt, CI runs the eval suite, and the PR goes red if quality regressed — exactly like unit tests, because that's what these are.

Two ways to wire it. The pytest integration marks tests so their runs land in LangSmith:

test_quality.py
import pytest

@pytest.mark.langsmith                       # logs this test as a LangSmith experiment
def test_refund_question_cites_source():
    out = rag_pipeline("What's the refund window for sale items?")
    assert "14 days" in out
    assert "[refund-policy.md" in out        # the §04 regression, now a permanent test

Or a plain script: run evaluate() over a pinned dataset version and assert on the aggregate — one threshold, one exit code, any CI system:

ci_eval.py
import sys
from langsmith import evaluate

results = evaluate(
    target_fn,
    data="qa-regressions:v7",        # PIN the version — same exam for every PR
    evaluators=[exact_match, contains_citation, correctness],
    experiment_prefix=f"ci-{GIT_SHA[:7]}",
    max_concurrency=8,               # keep the suite fast
)

df = results.to_pandas()
score = df["feedback.correctness"].mean()
print(f"correctness: {score:.2%}")
if score < 0.85:                     # the regression gate
    sys.exit(1)                      # red PR — quality dropped

Most teams split the work between two tiers:

per-PR suite
The regression split + deterministic evaluators only. Sampled, concurrent, done in 2–3 minutes — fast enough that nobody is tempted to skip it.
nightly suite
The full golden + adversarial sets with LLM judges and repetitions. Slower and pricier, but it runs while you sleep and posts a morning report.

Keeping it healthy in practice:

  • Pin the dataset version (§01) so score changes mean code changes, not dataset changes.
  • Keep it under a few minutes. Run a sampled subset (or just the regression split) on every PR with concurrency turned up; save the full golden + judge suite for a nightly job.
  • Fail loudly, link richly. Print the experiment URL in the CI log — a red build that links straight to the failing rows gets fixed; a bare exit code gets ignored.
Start embarrassingly small

Twenty examples and one strict deterministic evaluator, wired into CI today. A small suite that runs on every PR catches more regressions than a five-hundred-example masterpiece that's "almost ready." Grow it one harvested production failure at a time.
