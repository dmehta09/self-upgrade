LangGraph · core concepts

From one node to a stateful agent.

Eleven ideas take you from "what's a node?" to a persistent, human-in-the-loop, multi-agent system. Each comes with a picture, runnable Python, and the gotcha that trips up beginners.

01  Graphs, nodes & edges

A LangGraph app is a graph: a set of nodes (boxes that do work) connected by edges (arrows that decide what runs next). You add nodes and edges to a StateGraph, then .compile() it into something runnable.

Two rules make the whole model work:

a node returns
A dict of state updates — never a mutated copy of the whole state. LangGraph merges that dict back in for you.
an edge decides
What runs after a node. Edges can be fixed (always go to B) or dynamic (a function picks the next node at runtime).
graph.py
from langgraph.graph import StateGraph, START, END

builder = StateGraph(State)        # State defined in the next section
builder.add_node("step_a", step_a)
builder.add_node("step_b", step_b)

builder.add_edge(START, "step_a") # entry point
builder.add_edge("step_a", "step_b")
builder.add_edge("step_b", END)   # exit point

graph = builder.compile()
START and END are special

START is where execution begins; END is where it stops. They aren't nodes you write — they're built-in markers you connect your real nodes to.

02  State & the StateGraph

The state is the shared notebook that flows through the graph. You define its shape with a TypedDict. Each key is called a channel, and a node returns a partial update — just the channels it wants to change.

state.py
from typing_extensions import TypedDict
from langchain_core.messages import AnyMessage

class State(TypedDict):
    messages: list[AnyMessage]   # the conversation so far
    user_name: str               # anything else you want to carry

# A node only returns the channels it changes:
def greet(state: State):
    return {"user_name": "Sam"}  # 'messages' is left untouched
MessagesState is the chat-app shortcut

Nearly every chat agent needs a growing list of messages. LangGraph ships MessagesState — a prebuilt state with a messages channel that already knows to append new messages instead of replacing them. Subclass it and add your own fields.

03  Reducers: how updates merge key idea

When a node returns {"answer": "hi"}, what happens to the old value of answer? By default it gets replaced. A reducer changes that rule for a specific channel — most commonly, to append instead.

Wrap a channel's type in Annotated[..., reducer]. This is essential for accumulating a message list, and it's required when two parallel nodes might write the same channel (otherwise LangGraph can't decide whose value wins).

A reducer merges parallel writes
node A
returns logs: ["a"]
reducer · add
logs = ["a", "b"]
both writes appended
node B
returns logs: ["b"]
Without a reducer, A and B both writing logs is a conflict. The add reducer merges them into one combined list.
reducers.py
from typing import Annotated
from operator import add
from typing_extensions import TypedDict

class State(TypedDict):
    answer: str                       # default: new value REPLACES old
    logs: Annotated[list, add]        # reducer: new value is APPENDED
This is exactly what MessagesState does

Its messages channel is annotated with a reducer (add_messages) so every node's reply gets appended to the conversation instead of overwriting it.

04  Conditional edges & routing key idea

A conditional edge is how a graph makes decisions. Instead of always going to the same next node, you give LangGraph a routing function: it reads the state and returns the name of the next node. This is what lets a graph branch — and, crucially, loop back to an earlier node.

One node, two possible destinations
node
agent
route()
needs a tool?
reads the state
yes →
tools
loops back to agent
If the model asked for a tool, route to tools (which loops back). If it's done, route to END.
routing.py
def route(state: State) -> str:
    if state["needs_tool"]:
        return "tools"
    return END

builder.add_conditional_edges("agent", route, {"tools": "tools", END: END})
builder.add_edge("tools", "agent")    # loop back -> this is what makes an agent loop

Run it in slow motion. This is the exact graph above — step through one question and watch the router pick an edge, the tool loop fire, and the state grow:

What makes a LangGraph agent able to LOOP (call a tool, then think again)?

Exactly. The loop lives in the graph structure, not inside a node. A conditional edge points back to an earlier node (tools → agent), so the agent runs again and again until the router decides to head for END.

05  Compile, invoke & stream

Once nodes and edges are wired, builder.compile() turns the blueprint into a runnable graph. Then you run it:

.invoke(input)
Run the whole graph to completion and return the final state.
.stream(input, stream_mode="updates")
Yield each node's update as it happens — great for showing progress.
.stream(input, stream_mode="values")
Yield the full state after each step instead of just the change.
run.py
graph = builder.compile()

# Run once, get the final state:
final = graph.invoke({"messages": [{"role": "user", "content": "Hi!"}]})

# Or watch each node finish, live:
for update in graph.stream({"messages": [{"role": "user", "content": "Hi!"}]},
                           stream_mode="updates"):
    print(update)   # -> {'agent': {...}}, then {'tools': {...}}, ...

06  Checkpointers & threads: real memory key idea

This is how production memory actually works. A checkpointer saves the state at every step of the graph. A thread_id labels one conversation. Pass the same thread_id again and the graph replays the saved checkpoints — so it remembers everything. Use a new thread_id and you get a fresh start.

Same thread_id = the graph remembers
turn 1
"I'm Sam."
checkpoint
state saved
keyed by thread_id
turn 2
"What's my name?"
reads saved state → "Sam"
The checkpointer also means a crashed run can resume from its last saved step instead of starting over.
persistence.py
from langgraph.checkpoint.memory import InMemorySaver

graph = builder.compile(checkpointer=InMemorySaver())  # or SqliteSaver / PostgresSaver in prod

config = {"configurable": {"thread_id": "user-1"}}
graph.invoke({"messages": [{"role": "user", "content": "Hi, I'm Sam."}]}, config)
graph.invoke({"messages": [{"role": "user", "content": "What's my name?"}]}, config)
# -> remembers "Sam", because the same thread_id replays the saved checkpoints

See the replay happen. Two invocations, one thread_id — watch the second call restore everything the first one saved:

You call the graph twice with the SAME thread_id. What happens on the second call?

Right. The checkpointer reloads every saved step for that thread_id, so the second call picks up exactly where the first left off — that's how the agent "remembers." A different thread_id would start fresh.

07  Human-in-the-loop

Sometimes you want a human to approve a step before the agent continues — a draft email, a refund, a database write. Call interrupt(...) inside a node to pause the graph and hand control back to you. Later, resume with Command(resume=...) and the graph picks up right where it stopped.

Pause, let a human decide, resume
step 1
run
graph executes
interrupt
paused
control returns to you
resume
human reviews
Command(resume=…)
The graph state was checkpointed at the pause, so it waits as long as you need — seconds or days.
hitl.py
from langgraph.types import interrupt, Command

def review(state: State):
    decision = interrupt({"draft": state["draft"]})   # graph pauses, returns the draft to you
    return {"approved": decision["approved"]}

# ...much later, after a human decides:
graph.invoke(Command(resume={"approved": True}), config)
Don't put side effects before interrupt()

When the graph resumes, the node runs again from the top. Any code before interrupt() — sending an email, charging a card — will run a second time. Do side effects after the interrupt, once you have the human's decision.

08  Short-term vs long-term memory & the Store

LangGraph has two kinds of memory, and they answer different questions:

Short-term

The per-thread state and checkpoints — everything about this conversation. It lives and dies with the thread_id.

Long-term

Facts that should outlive any single conversation — a user's preferences, things they told you last week. Kept in a Store and queried across threads.

The Store is a simple key-value memory you can read and write from any node, independent of the current thread:

store.py
from langgraph.store.memory import InMemoryStore

store = InMemoryStore()                       # SqliteStore / PostgresStore in prod
graph = builder.compile(checkpointer=InMemorySaver(), store=store)
# nodes can now store.put(...) and store.search(...) facts that persist across threads

09  Subgraphs & multi-agent patterns

A graph can be used as a node inside another graph — that's a subgraph. It's how you build multi-agent systems: each agent is its own little graph, composed into a bigger one. Two patterns dominate:

Supervisor

One router agent sits on top and delegates each task to the right specialist (a researcher, a coder, a writer), then collects the results.

Swarm

Peer agents hand off directly to each other — whoever is best suited takes over next, with no central boss.

Supervisor delegating to specialists

The supervisor routes to a worker, the worker reports back, and the supervisor decides what's next — a conditional edge at a larger scale.

10  Prebuilt: create_react_agent & ToolNode

You rarely wire the standard agent loop by hand. LangGraph's langgraph.prebuilt module ships the common pieces:

  • create_react_agent — builds the entire think → act → observe loop from a model and a list of tools.
  • ToolNode — a ready-made node that executes whatever tools the model asked for and feeds the results back as tool messages. It's the "tools" box in every diagram above.
prebuilt.py
from langgraph.prebuilt import create_react_agent, ToolNode

# 1. The whole agent loop in one line:
agent = create_react_agent(model="gpt-4o", tools=[search, calculator])

# 2. Or use just the tool-executing node when hand-building a graph:
tool_node = ToolNode([search, calculator])
builder.add_node("tools", tool_node)
Start prebuilt, drop down when needed

Begin with create_react_agent. When you need a custom branch, an interrupt, or a second agent, you reach for the raw StateGraph — and reuse ToolNode for the tool step.

11  Common gotchas

Four mistakes catch nearly every newcomer. Watch for them:

Nodes must RETURN updates

Don't mutate the state object in place (state["x"] = 1). Return a dict of changes (return {"x": 1}). LangGraph relies on those returned dicts to merge state and to checkpoint correctly.

Parallel writes need a reducer

If two nodes that run in parallel both write the same channel, you'll get an error unless that channel has a reducer (like Annotated[list, add]) telling LangGraph how to merge the two values.

Side effects before interrupt() can double-run

Code before an interrupt() re-executes when the graph resumes. Keep emails, charges, and writes after the interrupt so they only fire once.

A missing thread_id silently starts over

Forget to pass a consistent thread_id (or change it by accident) and the graph quietly begins a brand-new conversation with no memory. If "it forgot everything," check the thread_id first.
