LangGraph · agent architectures

One loop, many shapes.

You know nodes and edges. Now meet the patterns people actually ship: the basic agent loop, ReAct, supervisors with specialist workers, swarm-style handoffs, and planner–executor — plus how to pick one without over-engineering.

01  What "agent" actually means

Strip the hype away and an agent is a remarkably small idea: a model with tools, run in a loop until it decides it's done. The model looks at the conversation, either calls a tool or writes a final answer, and if it called a tool, the result comes back and the model looks again. That's it. Every architecture on this page is a variation of that one loop.

a model
The brain. It reads the message history and decides the next step — never the whole plan at once.
tools
The hands. Functions the model can ask to run: search, a database query, a calculator, an API call.
a loop
The patience. After each tool result, control returns to the model — until it answers without asking for a tool.

As a graph, the loop is exactly the conditional-edge pattern from Core concepts: model → a router → either tools (which loops back to model) or END.

No tool call from the model? The router heads to END and the last message is your answer.
An intern with a phone

Picture an intern you hand a task to. They can't know everything, but they have a phone (tools): they can call accounting, look something up, run a number. They make a call, listen to the answer, think, maybe make another call — and they keep going until the task is done, then report back. The intern is the model; the phone calls are tool calls; "keep going until done" is the loop.

02  ReAct, demystified key idea

ReAct stands for Reason + Act. It sounds academic, but it's just the agent loop with a name: the model reasons about what to do, acts by calling a tool, observes the result, and repeats. The whole dance is visible in the message history. One trip around the loop looks like this:

1 · assistant msg
Contains a tool call: "call get_weather(city="Paris")" — the act step, with the reasoning that led to it.
2 · tool msg
The tool's result, appended as a message: "18°C, light rain" — the observation.
3 · assistant msg
With the result in context, the model writes the final answer — no tool call this time, so the loop ends.

In June 2026 you build this in one line with LangChain 1.3's create_agent — which compiles down to a LangGraph graph under the hood:

react_quick.py
from langchain.agents import create_agent

agent = create_agent("gpt-4o", tools=[get_weather, search])

result = agent.invoke({"messages": [{"role": "user", "content": "Weather in Paris?"}]})
print(result["messages"][-1].content)   # the final assistant answer

And here is the same thing hand-built in LangGraph, so you can see there's no magic — just the model node, a ToolNode, and the loop-back conditional edge from Core concepts §04:

react_by_hand.py
from langgraph.graph import StateGraph, MessagesState, START, END
from langgraph.prebuilt import ToolNode

model = chat_model.bind_tools([get_weather, search])

def call_model(state: MessagesState):
    return {"messages": [model.invoke(state["messages"])]}

def route(state: MessagesState) -> str:
    last = state["messages"][-1]
    return "tools" if last.tool_calls else END   # no tool calls = done

builder = StateGraph(MessagesState)
builder.add_node("model", call_model)
builder.add_node("tools", ToolNode([get_weather, search]))
builder.add_edge(START, "model")
builder.add_conditional_edges("model", route, {"tools": "tools", END: END})
builder.add_edge("tools", "model")               # the loop
graph = builder.compile()

What actually ENDS a ReAct loop?

Yes. The loop's exit condition is simply "the assistant message has no tool calls." The router reads that and routes to END. Tools can be called as many times as the model wants — which is exactly why the next section exists.

03  Tool-loop failure modes

The loop's power — "keep going until done" — is also its danger. Four failure modes account for most broken agents in production, and each has a standard fix:

infinite loops
The model keeps calling tools and never answers. Fix: cap the iterations — pass {"recursion_limit": 25} in the run config so a runaway loop errors out instead of burning money forever.
wrong tool args
The model calls get_user(id="bob") when ids are integers. Fix: validate inputs (typed/Pydantic schemas) and return the error to the model as a tool message so it can retry with corrected args.
tool spam
Given 40 tools, the model picks badly or dithers between near-duplicates. Fix: fewer, better-described tools — a tight set with crisp docstrings beats a kitchen sink every time.
context bloat
Long loops stuff the history with huge tool results; quality drops and cost climbs. Fix: trim or summarize old turns, and have tools return compact results instead of raw dumps.
Return tool ERRORS to the model — don't raise

When a tool fails, the instinct is to raise an exception. But raising kills the whole loop. Instead, catch the error and return it as the tool's result message ("Error: user id must be an integer"). The model reads it on the next turn and usually self-corrects — retrying with fixed arguments or choosing a different tool. ToolNode does this for you by default.

04  The supervisor pattern key idea

One agent with twelve tools and three jobs gets confused. The supervisor pattern splits the work: a router agent sits in the middle and delegates each step to a specialist worker (a researcher, a writer, a coder). Workers do their piece and always report back to the supervisor, which decides what happens next — another worker, the same one again, or done.

Structurally it's the agent loop one level up: instead of "model → tools → model," it's "supervisor → worker → supervisor." The conditional edge out of the supervisor is the whole trick:

supervisor.py
def supervisor(state: State):
    # An LLM (with structured output) picks: "researcher", "writer", or "done"
    decision = router_model.invoke(render_progress(state))
    return {"next": decision.next_worker}

def route(state: State) -> str:
    return END if state["next"] == "done" else state["next"]

builder.add_node("supervisor", supervisor)
builder.add_node("researcher", researcher_agent)   # each worker = its own agent
builder.add_node("writer", writer_agent)
builder.add_edge(START, "supervisor")
builder.add_conditional_edges("supervisor", route,
                              {"researcher": "researcher", "writer": "writer", END: END})
builder.add_edge("researcher", "supervisor")       # workers ALWAYS report back
builder.add_edge("writer", "supervisor")

Watch one task flow through. The supervisor routes a writing task to research first, then to the writer, then calls it done:

Each worker can be a full agent

The researcher box above can itself be a create_agent loop with its own tools, mounted as a subgraph. The supervisor doesn't care how a worker does its job — it only reads the state updates that come back.

05  Handoffs & the swarm style

The supervisor pattern has a boss. The swarm style doesn't: peer agents hand control directly to each other, like support reps transferring your call to the right department. The mechanism is Command — a node's return value that says both "update the state like this" and "go to that node next," replacing the conditional edge for that step:

handoff.py
from langgraph.types import Command

def triage_agent(state: MessagesState) -> Command:
    decision = classify(state["messages"])        # the triage LLM decides
    if decision == "billing":
        return Command(
            goto="billing_agent",                  # control transfers directly
            update={"handoff_reason": "double charge on invoice"},
        )
    return Command(goto="tech_agent", update={"handoff_reason": decision})

One handoff, start to finish. A billing question lands on triage, gets handed off, and is answered by the specialist:

Supervisor vs swarm: who decides where control goes next?

That's the whole distinction. Supervisor = workers always report back to a central decider (easier to control and debug). Swarm = peers transfer control directly with Command(goto=...) (fewer hops, more conversational). Same loop, different topology.

06  Planner–executor

Pure ReAct decides one step at a time — fine for short tasks, but on a long multi-step job it can wander, repeat work, or lose the thread. Planner–executor splits thinking from doing: a planner first writes the whole step list ("1. gather sales data, 2. compute trends, 3. draft summary"), then an executor works through the steps one by one. After each step, a checker can ask the planner to re-plan if the world changed.

Plan first, then execute (and maybe re-plan)
planner
write step list
executor
do step n
a small agent loop
check
done?
next step · re-plan · finish
The check step loops back: more steps → executor; plan stale → planner; all steps done → finish.

The trade is explicit: you get structure and steadiness on long tasks with dependencies, but you pay more LLM calls (planning, executing, checking, occasionally re-planning). For a two-step question, that overhead is pure waste — for a twenty-step research job, it's what keeps the agent on the rails.

Keep the plan in state

Store the step list in a state channel (plan: list[str], done: list[str]). Every node can see what's left, the checker's routing function becomes trivial, and with a checkpointer a crashed run resumes mid-plan instead of starting over.

07  Choosing an architecture

Architecture choice is mostly about who decides the next step and how long the task is. The honest decision table:

ArchitectureReach for it when…Watch out for
Single ReAct agentMost things. One job, a handful of well-described tools. Always your starting point.Long tasks wander; too many tools confuse it.
SupervisorDistinct specialist skills (research vs write vs code) and you want central control and an audit trail.Every hop goes through the boss — extra latency and tokens.
SwarmConversational handoffs between peers — triage → billing → tech, where the current agent knows best who's next.Harder to trace; no single place sees the whole flow.
Planner–executorLong multi-step tasks with dependencies, where step 4 needs step 2's output.Most LLM calls of all; plans go stale without re-planning.
When NOT to go multi-agent

Multi-agent multiplies cost, latency, and failure surface — every extra agent is another LLM call per hop and another place for state to go wrong. Before splitting, try making one agent better: sharper system prompt, fewer and better-described tools, trimmed context. Most "we need a supervisor" problems are actually "our tool descriptions are vague" problems.

Your single agent with 6 tools answers support questions well, but a new requirement adds 30 more tools across three unrelated domains. Best first move?

Right. Three unrelated domains with their own tool sets is the textbook supervisor case: each worker sees a small, focused tool list (fixing the tool-spam failure mode), and the supervisor only chooses which specialist, not which of 36 tools. Planner–executor solves long tasks, not wide tool sets.
"Better" needs a measuring stick

Whichever shape you pick, you can't compare architectures by vibes. Build a small eval set and measure — that's exactly what LangSmith · Evaluation in depth covers.
