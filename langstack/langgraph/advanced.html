LangGraph · advanced

The production toolbox.

Six things separate a demo from a deployed agent: composing graphs out of graphs, streaming the right events to the UI, pausing mid-run for a human, surviving crashes, and shipping it all with Studio & Platform. Here's each one, with the gotchas.

01  Subgraphs: graphs made of graphs

Here's the trick that makes multi-agent systems possible: a compiled graph IS a node. Anything you can pass to add_node — a function, a ToolNode — can also be a whole compiled graph. So you build a research agent as its own graph, a writing agent as another, and compose them into a parent graph that orchestrates the team.

Departments inside a company

The parent graph is the company org chart: research → writing → review. But zoom into the "research" box and it has its own org chart inside — search, summarize, fact-check. Each department runs itself; the company only sees what goes in and what comes out.

There are exactly two wiring styles, and which one you need depends on one question: do the parent and the subgraph share state keys?

subgraph_shared.py
# Style 1 — SHARED state keys: just add the compiled graph as a node.
research_builder = StateGraph(ResearchState)   # ResearchState has "messages"
# ... add research nodes & edges ...
research_graph = research_builder.compile()

parent = StateGraph(ParentState)               # ParentState ALSO has "messages"
parent.add_node("research", research_graph)    # a graph, dropped in as a node
parent.add_edge(START, "research")
# LangGraph passes the overlapping keys in, and merges them back out.
subgraph_mapped.py
# Style 2 — DIFFERENT schemas: wrap the subgraph in a translator function.
def call_research(state: ParentState):
    # map parent state -> subgraph input
    sub_out = research_graph.invoke({"topic": state["question"]})
    # map subgraph output -> parent state update
    return {"findings": sub_out["summary"]}

parent.add_node("research", call_research)     # the function is the node
No shared keys, no function? No data.

If you add a compiled graph directly (Style 1) but its state schema shares zero keys with the parent's, there's nothing to pass in or merge out. Subgraph keys must overlap with the parent's — or you must explicitly map state in and out with a wrapper function (Style 2).

Your parent graph's state has question and findings. Your research subgraph's state has topic and summary. How do you wire it in?

Right. The schemas share no keys, so LangGraph has no way to pass state across the boundary. A translator function maps question → topic on the way in and summary → findings on the way out. (If the keys did overlap, Style 1's direct add_node would work — and only matching keys need to overlap, not all of them.)

02  Streaming, properly key idea

An agent that "thinks" for 30 silent seconds feels broken. Streaming is how you show progress — and LangGraph gives you four different feeds to choose from, each answering a different question:

values
The full state after every step. Heavy, but you always have the complete picture — great for debugging or syncing a UI that renders whole state.
updates
Just each node's delta as it finishes — {"agent": {...}}, then {"tools": {...}}. The "what just happened?" feed.
messages
LLM tokens as they generate — the typewriter effect. Each chunk arrives the instant the model produces it.
custom
Your own progress events, emitted from inside a node via get_stream_writer() — "searching 1,200 docs…", "page 3 of 9…".

You can combine modes in one call — each event arrives tagged with which feed it came from:

streaming.py
from langgraph.config import get_stream_writer

def search_node(state: State):
    writer = get_stream_writer()
    writer({"progress": "searching 1,200 docs..."})   # a "custom" event
    ...

# Combine modes: each event is a (mode, chunk) pair.
for mode, chunk in graph.stream(inputs, stream_mode=["updates", "messages"]):
    if mode == "messages":
        token, metadata = chunk
        print(token.content, end="")    # the typewriter, token by token
    elif mode == "updates":
        print(chunk)                    # {'agent': {...}} -> node-level progress

What the user sees, mode by mode:

modewhat arrivesuse it for
valuesthe whole state, after each stepdebugging; UIs that re-render full state
updatesone node's returned deltastep indicators: "✓ searched, ✓ summarized…"
messagesindividual LLM tokens + metadatathe chat typewriter effect
customwhatever your nodes writer(...)progress bars inside long-running nodes

You're building a chat UI and want the reply to appear token by token as the model writes it. Which stream mode?

Yes. messages is the token feed — chunks arrive as the model generates them, which is exactly the typewriter effect. values only fires after a node completes (the whole reply at once), and custom would be reinventing what messages already does.

03  Interrupts & human-in-the-loop, for real key idea

Core concepts introduced the idea; here's the full machinery. Calling interrupt(payload) pauses the graph mid-node — and because the state is checkpointed at that exact moment, it can stay paused for seconds or days, even across a process restart. A checkpointer is required: no checkpointer, no pause to come back to.

Three moving parts:

interrupt(payload)
Called inside a node. Execution stops; the payload travels out to your code.
__interrupt__
Where the payload surfaces: the result of invoke() (or a stream event) carries an __interrupt__ entry describing what the graph is waiting for.
Command(resume=...)
How you answer. Invoke the graph again with this (same thread_id!) and the paused node re-runs from its start — this time interrupt() returns your resume value instead of pausing.

The classic use: an approval gate in front of a dangerous tool.

approval_gate.py
from langgraph.types import interrupt, Command

def approval(state: State):
    decision = interrupt({                       # graph PAUSES right here
        "action": state["draft_action"],         # "refund $120 on order #4912"
    })
    # On resume this node re-runs from the top — side effects go AFTER:
    return {"approved": decision == "approve"}

graph = builder.compile(checkpointer=checkpointer)   # REQUIRED for interrupt
config = {"configurable": {"thread_id": "ticket-88"}}

result = graph.invoke({"request": "Refund order #4912"}, config)
print(result["__interrupt__"])     # -> what the graph is waiting for

# ...a human reviews it in your UI, then:
graph.invoke(Command(resume="approve"), config)      # picks up mid-graph

Watch the pause happen. Step through a refund request — note the frame where the graph stops cold, checkpointed, waiting for a human:

Code before interrupt() RE-RUNS on resume

Resuming doesn't continue from the interrupt line — it re-executes the node from its first line, then hands the resume value to interrupt(). Anything above the interrupt (sending an email, charging a card, incrementing a counter) runs twice. Keep side effects after the interrupt, where they run exactly once.

A node logs "charging card…", charges the card, THEN calls interrupt() to confirm. The human resumes. What happened to the card?

Twice — and that's the bug. Resume re-runs the whole node from the top; nothing before the interrupt() is cached or rolled back. The fix: interrupt first (asking permission with the draft), and only charge after the approval comes back.

04  Durability & fault tolerance

You met the checkpointer as "memory." In production it's something bigger: crash insurance. Because state is saved at every step, a pod that dies mid-run can resume from its last checkpoint instead of replaying expensive LLM calls from scratch. The knob that controls when saves happen is the durability mode:

"exit"
Checkpoint only when the run finishes. Fastest — but a mid-run crash loses everything. Fine for cheap, retryable graphs.
"async"
Checkpoint after each step, in the background while the next step starts. The default tradeoff: nearly as fast, tiny crash window.
"sync"
Checkpoint after each step and wait for the write before continuing. Slowest, safest — every completed step is guaranteed on disk.

For flaky nodes — rate-limited APIs, wobbly networks — attach a retry policy instead of writing try/except loops:

durability.py
from langgraph.types import RetryPolicy

# Retry just the flaky node, with exponential backoff:
builder.add_node("fetch_prices", fetch_prices,
                 retry=RetryPolicy(max_attempts=3, retry_on=(TimeoutError,)))

# Pick how aggressively state is persisted, per run:
graph.invoke(inputs, config, durability="sync")   # or "async" / "exit"
Make tool side effects idempotent

Retries and resume-after-crash both mean a node might run twice. Design tools so a repeat is harmless: pass an idempotency key to payment APIs, use INSERT ... ON CONFLICT DO NOTHING for database writes, check "did I already send this?" before emailing. Durable execution plus idempotent tools is what makes "just re-run it" a safe answer.

05  LangGraph Studio: the visual IDE

Studio is where graphs stop being invisible. Point it at your project and you get a live picture of your agent that you can poke at:

  • See the graph — nodes, edges, conditional branches, rendered from your actual code.
  • Run it — type an input, watch execution light up node by node, inspect every state update.
  • Time-travel — jump back to any checkpoint, fork from there, and replay with changes.
  • Edit state mid-run — fix a bad tool result by hand and continue, instead of restarting.
  • Hot reload — edit your Python, and the running graph updates in place.

It runs against a local dev server. Two pieces: the CLI, and a langgraph.json telling it where your graph lives:

terminal
pip install -U "langgraph-cli[inmem]"
langgraph dev      # starts the local server + opens Studio in your browser
langgraph.json
{
  "dependencies": ["."],
  "graphs": { "agent": "./my_agent/graph.py:graph" },
  "env": ".env"
}
Studio needs the langgraph-cli

Studio isn't a separate install — it's the UI that langgraph dev serves. No CLI, no Studio. The [inmem] extra runs everything in-process locally, no Docker required.

06  LangGraph Platform: deploying it

Eventually the graph has to leave your laptop. LangGraph Platform wraps your compiled graph in a production server that exposes it as an API — with built-in Postgres checkpointing, task queues, and autoscaling handled for you. The API speaks four nouns:

assistant
A configured graph — your graph plus a specific config (model, prompt, tools). One graph can back many assistants.
thread
One conversation — the same thread_id idea, now a first-class API object with stored checkpoints.
run
One execution of an assistant on a thread. Runs queue, stream, retry, and can run in the background.
cron
A scheduled run — "summarize this inbox every morning at 8" with no extra scheduler infrastructure.

Two ways to run it: cloud — push your repo and LangChain hosts, scales, and upgrades the server for you; self-hosted — run the same server as a container on your own infrastructure, your data never leaves.

Do you actually need it?

Not on day one. A plain FastAPI service + a Postgres checkpointer is a perfectly good first deployment — it's just your graph behind an endpoint you already know how to run. Reach for Platform when its problems become your problems: background queues for long runs, bursty autoscaling, cron runs, or the Studio-connected debugging of live deployments.

Built. Shipped. Now: is it any good?

You can compose, stream, pause, survive crashes, and deploy. The last discipline is proving the agent actually works — and keeps working as you change prompts and models. That's evaluation, and it's LangSmith's home turf: Evaluation in depth →
