LangChain · Agent middleware

Customize the agent loop — keep the graph.

create_agent already returns a LangGraph. Middleware is how you intercept that loop — summarize, redact PII, pause for humans, retry, fall back — without hand-rolling a StateGraph for every cross-cutting concern.

01  Why middleware

Once you ship agents past the demo, the same five needs show up everywhere: shrink history, block secrets, approve dangerous tools, survive flaky APIs, switch models when a provider hiccups. You could fork the agent graph and bake those into nodes. You will regret it the third time product asks for "just one more guardrail."

Middleware is the extension point on create_agent: pass a list, keep the stock think → tool → think loop, and compose behavior like Express/FastAPI middleware — except the hooks are agent-shaped.

Two ways to customize — pick the cheap one first

Middleware rides inside the compiled graph create_agent returns. Rewrite the graph when you need a new topology — not when you need a policy.

You still get the default ReAct-style loop, streaming, and checkpointer wiring. Middleware plugs in; it doesn't replace the runtime.
compose, don't fork
Order the list. Before-hooks run forward; wrap-hooks nest; after-hooks run reverse. Same mental model as HTTP middleware stacks.
drop into larger graphs
The agent (middleware and all) is still a node/subgraph you can embed in a bigger StateGraph for classification → route → agent patterns.
Say it out loud say it

"Middleware customizes create_agent without rewriting StateGraph. I reach for a custom graph when the topology changes — branching, parallel fan-out, multi-agent routing — not when I need summarization or PII redaction."

02  Hook timeline key idea

The agent loop is: call the model → maybe run tools → repeat until the model stops calling tools. Middleware exposes hooks around that loop. Lifecycle hooks see/update state; wrap hooks sit around the actual model or tool call like a decorator.

One turn through the agent loop

retry · fallback · swap

If the model requested tools, wrap_tool_call wraps each execution. When the loop exits, after_agent runs. Then you're done — or the next user turn starts before_agent again.
HookWhen it firesTypical job
before_agentOnce at the start of an invocationInit counters, load side context, hard abort
before_modelBefore every model call in the loopSummarize/trim messages, dynamic system prompts
wrap_model_callAround the model invocationRetries, fallbacks, provider swap, latency budgets
after_modelAfter the model returnsValidate output, strip secrets, force stop
wrap_tool_callAround each tool executionError → ToolMessage, timeouts, audit logs
after_agentWhen the agent finishesMetrics flush, final redaction, cleanup
before_* vs wrap_*

before_model mutates state (messages list) and returns updates. wrap_model_call receives a request + handler — you decide whether to call it, how many times, or with a different model. Same split for tools.

Say it out loud say it

"before_model reshapes state; wrap_model_call wraps the call itself — that's where retries and fallbacks live. Tools get the same treatment with wrap_tool_call."

03  Built-in middleware

Ship the common policies from the box. Compose them in one list — order matters for before/after hooks.

Summarization

SummarizationMiddleware watches token (or message) pressure and compresses older turns while keeping a recent window. Prefer this over hand-rolled trimming when the conversation must stay coherent across a long thread.

summarize.py
from langchain.agents import create_agent
from langchain.agents.middleware import SummarizationMiddleware

agent = create_agent(
    model="gpt-4.1",
    tools=[search_tool],
    middleware=[
        SummarizationMiddleware(
            model="gpt-4.1-mini",          # cheaper model for the summary
            trigger=("tokens", 4000),      # fire when history crosses this
            keep=("messages", 20),         # retain the last N messages intact
        ),
    ],
)

Human-in-the-loop

HumanInTheLoopMiddleware interrupts before named tools run. Pair it with a checkpointer — interrupts need a thread to resume.

hitl.py
from langchain.agents import create_agent
from langchain.agents.middleware import HumanInTheLoopMiddleware
from langgraph.checkpoint.memory import InMemorySaver

agent = create_agent(
    model="gpt-4.1",
    tools=[read_email, send_email],
    middleware=[
        HumanInTheLoopMiddleware(
            interrupt_on={"send_email": True},
            description_prefix="Tool execution pending approval",
        ),
    ],
    checkpointer=InMemorySaver(),
)

PII, retries, fallback

guardrails.py
from langchain.agents import create_agent
from langchain.agents.middleware import (
    PIIMiddleware,
    ModelRetryMiddleware,
    ModelFallbackMiddleware,
    ToolRetryMiddleware,
)

agent = create_agent(
    model="gpt-4.1",
    tools=[customer_tool],
    middleware=[
        PIIMiddleware("email", strategy="redact", apply_to_input=True),
        PIIMiddleware("credit_card", strategy="mask", apply_to_input=True),
        ModelRetryMiddleware(max_retries=3, backoff_factor=2.0, initial_delay=1.0),
        ModelFallbackMiddleware("gpt-4.1-mini", "claude-sonnet-4-5"),
        ToolRetryMiddleware(
            max_retries=2,
            retry_on=(ConnectionError, TimeoutError),
            on_failure="continue",
        ),
    ],
)
HITL needs a checkpointer

Without a checkpointer, the interrupt has nowhere to pause. Same rule as LangGraph HITL nodes — thread state is the resume key.

04  Custom hooks

Decorators are enough for most one-off policies. Subclass AgentMiddleware when you need config + multiple hooks in one object.

custom_hooks.py
from collections.abc import Callable
from typing import Any

from langchain.agents import create_agent
from langchain.agents.middleware import before_model, wrap_tool_call, AgentState
from langchain.messages import ToolMessage
from langchain.tools.tool_node import ToolCallRequest
from langgraph.runtime import Runtime


@before_model
def log_before_model(state: AgentState, runtime: Runtime) -> dict[str, Any] | None:
    print(f"About to call model with {len(state['messages'])} messages")
    return None  # or return {"messages": [...]} to update state


@wrap_tool_call
def handle_tool_errors(
    request: ToolCallRequest,
    handler: Callable[[ToolCallRequest], ToolMessage],
) -> ToolMessage:
    try:
        return handler(request)
    except Exception as e:
        return ToolMessage(
            content=f"Tool error: check inputs and retry. ({e})",
            tool_call_id=request.tool_call["id"],
        )


agent = create_agent(
    model="gpt-4.1",
    tools=[search_tool, write_db],
    middleware=[log_before_model, handle_tool_errors],
)
Say it out loud say it

"I decorate with @before_model to reshape state before the LLM, and @wrap_tool_call to turn tool exceptions into ToolMessages the model can recover from — then pass both into middleware=[...]."

05  Context engineering: summarize vs trim

Context windows are a budget. Agents burn it on tool transcripts, retries, and "helpful" system prompts. Two levers:

Trim

Drop oldest messages (or hard-cut by token count). Cheap, deterministic, lossy. Fine when early turns are scaffolding and the last N messages carry the task. Often a few lines in before_model with trim_messages.

Summarize

Compress older turns into a running synopsis via SummarizationMiddleware. Costs an extra model call; preserves decisions, IDs, and constraints that trimming would erase.

trim.py
from langchain.agents import create_agent
from langchain.agents.middleware import before_model
from langchain_core.messages.utils import (
    trim_messages,
    count_tokens_approximately,
)

@before_model
def keep_recent_context(state, runtime):
    """Cheap budget control — drop early turns, keep a valid chat shape."""
    trimmed = trim_messages(
        state["messages"],
        strategy="last",
        token_counter=count_tokens_approximately,
        max_tokens=4000,
        start_on="human",
        end_on=("human", "tool"),
    )
    return {"messages": trimmed}


agent = create_agent(
    model="gpt-4.1",
    tools=[search_tool],
    middleware=[keep_recent_context],
)

Rule of thumb: trim for ephemeral chat; summarize when the agent must remember earlier tool results or user constraints across a long session.

Say it out loud say it

"Trim when early turns are disposable; summarize when I need the gist of a long thread. Middleware is the switch — the strategy still comes from context engineering."

06  MCP: tools without reinventing the protocol

Middleware does not replace tool discovery. Model Context Protocol (MCP) is how you expose external tool servers to an agent — filesystem, browsers, SaaS APIs — with a standard handshake. Wire MCP tools into create_agent; use middleware for policies around those tools (HITL on writes, retries on flaky servers, PII on results).

Don't duplicate MCP here

Transports, servers, and client wiring are covered in the GenAI tool-use track — start at Tool use & MCP (see Model Context Protocol). This page stays on agent hooks.

07  Check yourself

Say it out loud say it

"create_agent + middleware for policies; custom StateGraph for topology. Summarize vs trim is a context budget call. HITL interrupts need a checkpointer. MCP brings tools; middleware governs them."

You need retries when the chat provider 503s, without rewriting the agent graph. Where does that live?

Wrap the call. Retries and fallbacks sit around the model invocation. Lifecycle hooks like before_agent aren't the right shape for "call handler again with backoff."

When do you leave middleware and write a custom StateGraph?

Topology vs policy. Summarization, PII, HITL, and retries are middleware. Custom graphs are for structure the stock agent loop can't express.

HumanInTheLoopMiddleware(interrupt_on={"send_email": True}) — what's also required?

State has to survive the pause. Interrupts are LangGraph persistence — without a checkpointer there's no thread to resume.
