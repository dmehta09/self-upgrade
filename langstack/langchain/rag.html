LangChain · RAG in production

Naive RAG gets you a demo. This gets you to prod.

You built the basic loop — embed, retrieve, stuff, answer — in Core concepts. It works great on five PDFs and falls apart on five thousand. This page is the upgrade path: better chunks, hybrid search, reranking, query rewriting, and citations.

01  Why naive RAG plateaus

Naive RAG makes one optimistic bet: the user's question, embedded once, will land near the right chunk, and the model will use it faithfully. On a demo corpus that bet usually pays off. In production, every link in that chain breaks in its own way:

wrong chunks retrieved
The nearest vectors are about the topic but don't contain the answer. Recall looks fine in a demo; on a big corpus, near-misses crowd out the one chunk that matters.
answer buried mid-chunk
The chunk is technically correct, but the answer is one sentence inside 1,500 characters of context the model has to dig through — and sometimes it stops digging.
question wording ≠ document wording
Users say "how do I get my money back?"; the doc says "refund eligibility policy". Pure embedding similarity can bridge that gap — but exact IDs, SKUs, and jargon often slip through.
model ignores context
Retrieval was perfect, but the model answers from its training data anyway — or blends the two. Without grounding, you can't even tell which happened.
The librarian who only matches titles

Naive RAG is a librarian who finds books whose titles sound like your question. Ask for "that book about the whale and the obsessed captain" and you might get Whales of the North Atlantic. A production librarian also checks the index (keyword search), skims the candidates before handing them over (reranking), and asks "do you mean Moby-Dick?" (query rewriting). The rest of this page builds that librarian.

Each section below fixes one failure mode. The good news: they're independent upgrades — you can adopt them one at a time, in any order, and measure each.

02  Chunking strategies foundation

Chunking is where most RAG quality is won or lost — before a single query runs. The core tension: small chunks embed precisely (one idea per vector, easy to match) but lose context; big chunks keep context but their embedding becomes a mushy average of many ideas. chunk_overlap softens the cut: each chunk repeats the tail of the previous one, so a sentence sliced in half still appears whole in one of them.

Two upgrades beyond fixed-size splitting:

structure-aware splitting
Split on headings, paragraphs, and code blocks — the document's natural seams — instead of every N characters. A code example cut in half is worse than useless. RecursiveCharacterTextSplitter already tries separators in order (paragraph → line → word) for exactly this reason.
the parent-document trick
Search small, feed big. Embed small, precise child chunks for matching — but when a child matches, hand the model its parent (the full section it came from). You get pinpoint retrieval and full context. In LangChain this is the ParentDocumentRetriever pattern.

The tiny child wins the similarity search; its parent — with the limits table, the exceptions, the footnote — is what goes into the prompt.
chunking.py
from langchain_text_splitters import RecursiveCharacterTextSplitter

# Typical starting points (tune with evals, not vibes):
#   content type        chunk_size   chunk_overlap
#   chat / FAQ snippets   300-500       50
#   prose docs / wikis    800-1200     100-200
#   code / API refs      1200-1500     150   (split on functions if you can)
splitter = RecursiveCharacterTextSplitter(
    chunk_size=1000,
    chunk_overlap=150,        # ~15% of chunk_size is a sane default
    separators=["\n\n", "\n", " ", ""],   # tries paragraph first, then line...
)
chunks = splitter.split_documents(docs)

What problem does chunk_overlap actually solve?

That's it. Overlap repeats the tail of each chunk at the head of the next, so any idea that straddles a boundary appears intact in at least one chunk. It costs a little storage (the repeated text is embedded twice) — a cheap price for never losing a boundary sentence.

03  Hybrid search & RRF key idea

Dense vectors and keyword search fail in opposite directions. Embeddings are great at paraphrase ("get my money back" ≈ "refund policy") but blur out exact tokens — error codes, SKUs, ERR_TLS_402, "Form 16B". Keyword search (BM25) nails exact tokens but has zero idea that "refund" and "money back" are the same thing. So run both, and fuse the results with Reciprocal Rank Fusion: each document scores 1 / (k + rank) in each list, sum across lists, re-sort. Documents that rank well in either list — or decently in both — float to the top.

BM25 catches ERR_TLS_402 exactly; the vector side catches "refund" phrased ten different ways. RRF merges both lists into one.
hybrid.py
from langchain_community.retrievers import BM25Retriever
from langchain.retrievers import EnsembleRetriever

keyword = BM25Retriever.from_documents(chunks, k=10)   # exact-token search
semantic = vector_store.as_retriever(search_kwargs={"k": 10})

hybrid = EnsembleRetriever(                # fuses with Reciprocal Rank Fusion
    retrievers=[keyword, semantic],
    weights=[0.4, 0.6],                    # nudge toward the semantic side
)
docs = hybrid.invoke("ERR_TLS_402 refund eligibility")
Fuse RANKS, not scores

A cosine similarity of 0.82 and a BM25 score of 14.7 live on completely different scales — adding or averaging them is meaningless. RRF sidesteps this by ignoring scores entirely and using only each document's position in each list. That's the whole reason it works across any pair of search systems.

04  Reranking: the funnel key idea

Why are embeddings imprecise in the first place? Because each document is squeezed into a vector before it ever sees your question. A cross-encoder reranker does the opposite: it reads the question and a candidate together, token by token, and outputs one relevance score. Far more accurate — and far too slow to run against a million documents:

Bi-encoder (vector search)

Embeds query and documents separately; docs are pre-computed once, so comparing is just fast vector math. Scales to millions — but each side is summarized blind, without seeing the other.

Cross-encoder (reranker)

Reads query + document together in one pass — every word can attend to every word. Far more accurate, but nothing can be pre-computed, so it only works on a short list.

So you build a funnel:

Cheap and wide, then expensive and narrow

1,000,000 chunks

Retrieval optimizes for recall (don't miss it); the reranker optimizes for precision (put it first). Scoring 25 pairs is fast; scoring a million would take minutes.
rerank.py
from langchain.retrievers import ContextualCompressionRetriever
from langchain_community.cross_encoders import HuggingFaceCrossEncoder
from langchain.retrievers.document_compressors import CrossEncoderReranker

wide = hybrid_retriever          # cast a wide net: k=25
reranker = CrossEncoderReranker(
    model=HuggingFaceCrossEncoder(model_name="BAAI/bge-reranker-v2-m3"),
    top_n=4,                     # keep only the best 4 for the prompt
)
retriever = ContextualCompressionRetriever(
    base_retriever=wide, base_compressor=reranker,
)
docs = retriever.invoke("refund eligibility after a TLS checkout error")

Where does the reranker sit in the pipeline?

Between, always. A cross-encoder must see the live query paired with each candidate, so it can't pre-compute anything — and it's too slow for the full corpus. The funnel is the compromise: cheap search narrows a million to 25, the reranker reads those 25 carefully and keeps the best 4.

05  Query rewriting & multi-query

Everything so far improves the search. This section improves the query. Real users ask vague follow-ups: after discussing the enterprise plan, they type "and how much is that for 50 seats?" Embed that literally and "that" matches nothing. The fix: a small, cheap LLM call that rewrites the follow-up into a standalone query using the conversation so far — before retrieval runs.

rewrite.py
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

rewrite_prompt = ChatPromptTemplate.from_messages([
    ("system", "Rewrite the user's last message as ONE standalone search "
               "query. Resolve pronouns using the conversation. Query only."),
    ("placeholder", "{history}"),
    ("human", "{question}"),
])
rewrite_chain = rewrite_prompt | small_model | StrOutputParser()   # plain LCEL

q = rewrite_chain.invoke({"history": history,
                          "question": "and how much is that for 50 seats?"})
# -> "enterprise plan pricing for 50 seats"
docs = retriever.invoke(q)        # NOW retrieval has something to bite on

The same trick scales up to multi-query fan-out: ask the model for 3–4 different phrasings of the question ("refund policy", "money-back eligibility", "cancellation reimbursement"), retrieve for each, then dedupe the union by document id. Any single phrasing might miss; the union rarely does. LangChain ships this as MultiQueryRetriever — and RRF (section 03) is again the right way to merge the lists.

Rewriting is the cheapest upgrade here

It's one extra call to a small, fast model — no re-indexing, no new infrastructure. If your bot handles conversations (not one-shot questions), do this first: no retrieval trick can save a query that literally says "that".

A user's follow-up is "does it work offline too?". What should hit the retriever?

Rewrite it. "It" only means something inside the conversation — the vector store wasn't in the room. Resolving the pronoun first gives retrieval real words to match. (Embedding the whole history is the mushy-average problem from section 02 all over again.)

06  Citations & grounding

A RAG answer without citations says "trust me." An answer with citations says "check me" — and that single change is what makes RAG deployable in places where wrong answers cost money. The recipe has two halves: label every chunk with an id when you stuff the context (you saw [kb-104] in the pipeviz above), and force the model to return the ids it used via structured output:

citations.py
from pydantic import BaseModel, Field

class CitedAnswer(BaseModel):
    answer: str = Field(description="Answer based ONLY on the given context.")
    sources: list[str] = Field(
        description="Ids of the context chunks that support the answer.")

cited_model = model.with_structured_output(CitedAnswer)
result = cited_model.invoke(stuffed_messages)

result.answer    # -> "ERR_TLS_402 means the charge never settled, so..."
result.sources   # -> ["kb-104", "kb-031"]   ...link these in your UI

Three things have to line up for citations to be trustworthy:

stable chunk ids
Each chunk keeps the same id across re-indexes (hash the source + position) so a citation from last week still points somewhere real.
ids visible in the context
The model can only cite what it can see — prefix every chunk with its id when you format the context (the [kb-104] labels in the pipeviz above).
empty list = honest "I don't know"
If sources comes back empty, don't show the answer — show "I couldn't find this in the docs." An uncited answer is a guess wearing a suit.

Now your app can render each source as a link to the original document, and — just as important — your evals can check the citations: do the cited chunks actually contain the claim? An answer citing chunks that don't support it is a hallucination you can detect automatically — no human in the loop needed.

Citations also fix "model ignores context"

Asking for sources nudges the model to actually read the chunks: it can't cite what it didn't use. Teams consistently see grounding improve just from requiring a sources list — the structure is the leash.

07  When naive RAG is actually enough

Every upgrade on this page adds latency, cost, or moving parts. Don't install all five because a blog post said so — diagnose the symptom, apply the matching fix, and re-measure. The map:

Symptom you observeUpgrade to reach forWhy it's the match
Bad recall on jargon, IDs, error codesHybrid search (§03)BM25 matches exact tokens that embeddings blur out
Right document found, wrong snippet fedParent-document chunking (§02)Search small for precision, feed big for context
Vague follow-ups retrieve junkQuery rewriting (§05)Resolves "it"/"that" before the vector store sees them
Relevant chunks retrieved, but not ranked firstReranking (§04)A cross-encoder reads query + chunk together for precision
Good retrieval, wrong answer anywayPrompting / reranking (§04)Fewer, better chunks + firmer grounding instructions
"It lies" — confident unsupported claimsCitations + evals (§06)Makes hallucinations detectable, then measurable

And if you have a small, clean corpus, one-shot questions, and users who phrase things like the docs do — congratulations, naive RAG is your production architecture. Simple and measured beats fancy and unmeasured.

Measure before you upgrade

You can't pick from this table without knowing which symptom you actually have. Build a small eval set of real questions with known-good answers and score retrieval before touching anything — LangSmith · Evaluation in depth shows exactly how. Every upgrade here should move a number you're tracking.
