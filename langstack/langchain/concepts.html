LangChain · core concepts

The building blocks, one at a time.

Eleven ideas take you from "what's a chat model?" to building a retrieval-powered agent. Each comes with a picture, runnable Python, and the gotcha that trips up beginners.

01  Chat models & the standard interface

A chat model is your connection to an LLM (GPT, Claude, Gemini, a local model…). LangChain wraps every provider in one identical interface, so your code doesn't care which company's model is behind it.

You send it a list of messages and it returns one AI message back. The key methods (shared by everything in LangChain):

.invoke(input)
Run once, wait for the full answer.
.stream(input)
Get the answer token-by-token as it's generated (for typewriter UIs).
.batch([a, b])
Run many inputs efficiently in parallel.
models.py
from langchain.chat_models import init_chat_model

model = init_chat_model("gpt-4o", model_provider="openai", temperature=0)

# Swap providers by changing ONE string — your app code stays identical:
# model = init_chat_model("claude-haiku-4-5", model_provider="anthropic")

answer = model.invoke("What's the tallest mountain on Earth?")
print(answer.content)        # -> "Mount Everest..."
print(answer.usage_metadata) # -> token counts, handy for cost tracking
temperature = creativity dial

temperature=0 makes the model deterministic and focused (great for facts & tools). Higher values (0.7–1) make it more varied and creative. Start at 0 while learning.

02  Messages: the units of a conversation

Chat models don't think in plain strings — they think in messages, each with a role. LangChain gives you a type for each role:

⚙️

SystemMessage

The standing instructions — who the assistant is, rules to follow. Set once at the top.

🧑

HumanMessage

What the user said.

🤖

AIMessage

What the model replied (may include requests to call tools).

🔧

ToolMessage

The result of running a tool, fed back so the model can continue.

messages.py
from langchain_core.messages import SystemMessage, HumanMessage

conversation = [
    SystemMessage("You are a witty geography tutor. Keep answers short."),
    HumanMessage("Why is the sky blue?"),
]
reply = model.invoke(conversation)
print(reply.content)

# A conversation is just this list growing over time — append the AI's
# reply and the next human turn, then invoke again. That IS chat history.
Shortcut

You can also pass plain dicts like {"role": "user", "content": "hi"} or even a bare string. The message classes just make intent explicit.

03  Prompt templates

Hard-coding prompts with f-strings gets messy fast. A prompt template is a reusable blueprint with {placeholders} you fill in at runtime — testable, shareable, and tidy.

prompts.py
from langchain_core.prompts import ChatPromptTemplate

prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a translator. Translate into {language}."),
    ("human", "{text}"),
])

# Fill the blanks -> ready-to-send messages
messages = prompt.invoke({"language": "French", "text": "Good morning!"})
print(model.invoke(messages).content)   # -> "Bonjour !"

04  Output parsers & structured output

Models return text, but your program usually wants data — a number, a list, a typed object. Two approaches:

A) Simple parsers

StrOutputParser just pulls the .content string out of the AI message — the most common final step in a chain.

B) Structured output (the modern way)

Define the shape you want with a Pydantic model and call .with_structured_output(). LangChain uses the model's native tool-calling to guarantee the reply matches your schema — no fragile text parsing.

structured.py
from pydantic import BaseModel, Field

class Movie(BaseModel):
    title: str
    year: int = Field(description="release year")
    rating: float

structured_model = model.with_structured_output(Movie)

movie = structured_model.invoke("Tell me about the film Inception.")
print(movie.title, movie.year)   # -> Inception 2010
print(type(movie))               # -> <class 'Movie'>  (a real object, not text!)

05  LCEL & the Runnable interface key idea

Here's the concept that makes LangChain click. Every block is a Runnable — it has .invoke(), .stream(), .batch(). Because they all match, you connect them with the pipe |. The output of each becomes the input of the next.

A chain reads left → right, like a pipeline
input
{"topic": "otters"}
prompt
fills the template
→ messages
model
calls the LLM
→ AI message
parser
extracts text
→ "string"
The | just feeds each block's output into the next.
lcel.py
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

prompt = ChatPromptTemplate.from_template("Write a haiku about {topic}.")
parser = StrOutputParser()

chain = prompt | model | parser          # <- the whole pipeline, one line

print(chain.invoke({"topic": "otters"})) # run it
for chunk in chain.stream({"topic": "rain"}):  # or stream it word by word
    print(chunk, end="", flush=True)

The payoff: streaming, batching, and async come for free on any chain, because every piece already supports them.

Watch the data change shape. The pipe is easiest to believe when you can see what each stage actually hands to the next — step through it:

In chain = prompt | model | parser, what does the model receive as its input?

Right idea: data flows left-to-right. prompt turns the dict into messages, and those messages are what model receives. The model's output then flows on to parser.

06  Tools & tool calling

A tool is just a Python function the model is allowed to call — to search the web, do math, hit your database. You write the function, decorate it with @tool, and "bind" it to the model. The model then decides when to call it and with what arguments.

The model doesn't run the tool — you do key point

The model only requests a call: "please run get_weather(city='Paris')". Your code runs it and hands the result back as a ToolMessage. The model then continues with that information.

tools.py
from langchain_core.tools import tool

@tool
def get_weather(city: str) -> str:
    """Get the current weather for a city."""   # docstring tells the model what it does
    return f"It's 22°C and sunny in {city}."

model_with_tools = model.bind_tools([get_weather])

response = model_with_tools.invoke("What's the weather in Paris?")

# The model didn't answer in words — it asked to call the tool:
for call in response.tool_calls:
    print(call["name"], call["args"])   # -> get_weather {'city': 'Paris'}

Doing this handoff loop by hand is tedious — which is exactly why agents (below) and LangGraph exist: they run the call-the-tool-then-think-again loop for you.

07  The retrieval stack

To let a model answer questions about your documents, you first turn those documents into something searchable-by-meaning. Five pieces do this, in order:

Turning documents into a searchable knowledge base
1 · loader
Document loader
reads PDFs, web, files
2 · splitter
Text splitter
chops into chunks
3 · embeddings
Embedding model
text → vectors
4 · vector store
Vector database
stores & searches
A retriever (5) is the thin wrapper that takes a question and returns the most relevant chunks.
What's an embedding, really? go deeper

An embedding turns a piece of text into a long list of numbers (a "vector") that captures its meaning. Texts about similar things end up with similar vectors — so "How do I reset my password?" lands near a support doc about password resets, even if they share no exact words. The vector store finds nearest neighbours by this numeric similarity. That's "semantic search."

08  RAG: Retrieval-Augmented Generation key idea

RAG is the most common real-world LangChain pattern. The idea in one line: before asking the model, fetch relevant facts and paste them into the prompt. The model then answers grounded in your data instead of guessing.

The RAG request flow
question
"What's our refund policy?"
retrieve
search your docs
→ top matching chunks
augment
stuff into prompt
context + question
generate
model answers
grounded reply
Retrieve → Augment → Generate. That's literally where the name comes from.
rag.py
from langchain_openai import OpenAIEmbeddings
from langchain_core.vectorstores import InMemoryVectorStore
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_core.runnables import RunnablePassthrough

# 1. Build a tiny knowledge base (normally you'd load + split real files)
docs = ["Refunds are accepted within 30 days with a receipt.",
        "Shipping is free over $50."]
store = InMemoryVectorStore.from_texts(docs, embedding=OpenAIEmbeddings())
retriever = store.as_retriever()

# 2. A prompt that has a slot for retrieved context
prompt = ChatPromptTemplate.from_template(
    "Answer using ONLY this context:\n{context}\n\nQuestion: {question}"
)

def format_docs(docs):
    return "\n".join(d.page_content for d in docs)

# 3. Wire it as an LCEL chain
rag_chain = (
    {"context": retriever | format_docs, "question": RunnablePassthrough()}
    | prompt | model | StrOutputParser()
)

print(rag_chain.invoke("Can I get a refund after 2 weeks?"))
# -> "Yes — refunds are accepted within 30 days with a receipt."

What's the main reason to use RAG instead of just asking the model directly?

Exactly. The model only knows its training data and can hallucinate. RAG feeds it the relevant facts at question time, so answers stay accurate, current, and traceable to a source.

09  Memory & chat history

Models are stateless — each call is a blank slate. To make a chatbot "remember," you simply keep the growing list of messages and resend it every turn. For short chats that's all you need.

memory.py
history = [SystemMessage("You are a helpful assistant.")]

def chat(user_text):
    history.append(HumanMessage(user_text))
    reply = model.invoke(history)
    history.append(reply)           # remember the AI's turn too
    return reply.content

chat("My name is Sam.")
print(chat("What's my name?"))      # -> "Your name is Sam." (it remembered)
For real apps, memory lives in LangGraph

Resending a list works until conversations get long, span sessions, or need to survive a restart. That's where LangGraph's checkpointers come in — automatic, persistent memory keyed by a conversation ID. We cover it in the LangGraph section.

10  Agents

An agent is a model in a loop with tools: it thinks, optionally calls a tool, reads the result, thinks again, and repeats until it can answer. You no longer wire this loop by hand — create_agent builds it for you.

agent.py
from langchain.agents import create_agent
from langchain_core.tools import tool

@tool
def add(a: int, b: int) -> int:
    """Add two numbers."""
    return a + b

@tool
def multiply(a: int, b: int) -> int:
    """Multiply two numbers."""
    return a * b

agent = create_agent(model="gpt-4o", tools=[add, multiply])

result = agent.invoke({"messages": [{"role": "user", "content": "What is 12 * 7 + 5?"}]})
print(result["messages"][-1].content)   # -> "89" (it called multiply, then add)
This is the bridge to LangGraph

create_agent returns a graph that runs on LangGraph. So the moment you build an agent, you're already using LangGraph — even if you never imported it. Learn the graph model next to unlock loops, memory, and human approval.

11  What changed in 1.0 & common gotchas

LangChain 1.0 (late 2025) was a big cleanup. If you find an old tutorial, watch for these:

Old agent classes are gone

AgentExecutor, initialize_agent, and "ReAct agent" prompt-parsing are legacy. Use create_agent. Truly old code now lives in a separate langchain-classic package.

Pre-built chains were removed

RetrievalQA, ConversationalRetrievalChain, etc. are gone. Build the same thing with LCEL (|) — it's a few more lines but far clearer, as in the RAG example above.

Keep package versions aligned

If langchain-openai and langchain-core drift far apart you'll see odd errors. Pin minor ranges, e.g. langchain>=1.3,<1.4.
