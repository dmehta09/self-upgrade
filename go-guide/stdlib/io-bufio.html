The standard library · io & bufio

io, bufio & readers/writers.

Two one-method interfaces — io.Reader and io.Writer — are the universal plumbing of Go I/O. Files, sockets, buffers, HTTP bodies, gzip streams: they all speak the same two methods, so they connect like Lego. bufio wraps them with buffering and line-scanning.

01 Reader & Writer: the universal abstraction

io.Reader is one method — Read(p []byte) (n int, err error) — "fill this buffer with some bytes." io.Writer is Write(p []byte) (n int, err error) — "consume these bytes." Any source of bytes is a Reader; any sink is a Writer.

In plain English analogy

Think of plumbing fittings. Every pipe in Go's I/O world has the same standard thread: a Reader is a tap (bytes come out), a Writer is a drain (bytes go in). Because the threads match, you can screw any tap into any drain — a file into the terminal, a network socket into a gzip compressor — without the pipes knowing what's on the other end.

This is the same idea as the small-interface design in the interfaces lesson: program against io.Reader/io.Writer, not *os.File, and your code works with files, network connections, strings.Reader, bytes.Buffer, and the dozens of wrappers in the stdlib.

io.Reader
Read(p []byte) (n int, err error) — a source of bytes.
io.Writer
Write(p []byte) (n int, err error) — a sink for bytes.
io.EOF
The sentinel error a Reader returns when there's nothing left.

02 io.Copy and the meaning of io.EOF

io.Copy(dst, src) pumps bytes from any Reader to any Writer until EOF, in one line. io.EOF is not a failure — it's the normal, expected signal that a stream ended. io.Copy treats it as "done," not "error."

Gotcha trap

Three I/O traps: (1) Don't treat io.EOF as a real error — it's the normal end of a stream. In a manual Read loop, check if err == io.EOF { break } separately from genuine errors. (2) A bufio.Scanner has a default token cap of 64 KB (bufio.MaxScanTokenSize) — a longer line stops the scan with bufio.ErrTooLong; call scanner.Buffer(buf, max) to raise it. (3) A bufio.Writer holds bytes in memory — if you don't Flush() (or defer w.Flush()), the tail of your output is silently lost.

03 Composing readers: Multi, Tee, Limit

Because Readers share one interface, the io package ships combinators that wrap a Reader and return a new one — chain them like Unix pipes without buffering everything in memory.

io.MultiReader(r1, r2, …)
Concatenate readers — reads r1 to EOF, then r2, as one stream.
io.TeeReader(r, w)
Returns a Reader that also writes everything it reads into w — perfect for hashing or logging a stream as it flows.
io.LimitReader(r, n)
A Reader that stops after n bytes — caps untrusted input.

MultiReader glued two strings into a 15-byte stream; LimitReader capped the read at 12 bytes, so ReadAll returned "Hello, Gophe". Each wrapper is itself an io.Reader, so they nest freely.

04 bufio: Scanner for lines, Writer for buffering

bufio.Scanner reads a stream token by token — by default, line by line — so you don't manage buffers. bufio.Writer batches small writes into one big write to the underlying Writer; just remember to Flush().

Scan a multi-line string a line at a time with scanner.Scan() + scanner.Text() (the newline is stripped). The default bufio.ScanLines split function makes this the idiomatic way to read input:

For output, wrap a Writer with bufio.NewWriter, do many small WriteString calls, then Flush() once. The buffering turns hundreds of tiny syscalls into a few large ones:

flush.go
w := bufio.NewWriter(os.Stdout)
defer w.Flush()                 // <- without Flush, buffered bytes are lost
for i := 0; i < 1000; i++ {
    fmt.Fprintf(w, "line %d\n", i) // buffered, not yet written
}
// the deferred Flush() pushes the buffer to os.Stdout

05 Check yourself

You write thousands of lines through a bufio.NewWriter(os.Stdout) in a loop, the program ends, and the last chunk of output is missing. Why?

Right. A bufio.Writer accumulates bytes in memory and only writes to the underlying Writer when the buffer fills or you call Flush(). If the program exits with data still in the buffer, that data is lost. Always defer w.Flush() right after creating the writer.
