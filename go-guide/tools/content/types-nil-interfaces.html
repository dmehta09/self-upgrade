Types & interfaces · the nil trap

The nil interface trap.

A function returns an error. You return a nil pointer to your error type. The caller's if err != nil fires anyway. This is the most famous footgun in Go — and a top interview question. Here's exactly why it happens.

01 An interface value has two parts

An interface value is a (type, value) pair: a slot for the dynamic type and a slot for the value. It is nil only when both slots are empty.

In plain English analogy

Think of an interface as a shipping box with two labels: "what's inside" (the type) and "the contents" (the value). An empty box has both labels blank. But a box labelled "contains: a *MyError" is not empty — even if the thing inside is itself an empty pointer. The label "what's inside" is filled in, so the box is not nil.

So there are two very different kinds of "nothing": a nil interface (both slots blank) and an interface that holds a nil pointer (the type slot says *MyError, the value slot is a nil pointer). They look the same when you print them — and they compare differently to nil.

02 A typed nil is NOT == nil

Put a typed nil pointer into an interface and the interface is not nil — its type slot is set. (*T)(nil) wrapped in any compares != nil.

Watch the headline behaviour directly. A nil *int is nil as a pointer, but once it's boxed into an any the box knows its type, so it isn't a nil interface:

The interface i carries (type=*int, value=nil). The type slot is occupied, so i == nil is false even though the pointer inside is nil. Printing it shows <nil>, which is exactly what makes the bug so sneaky — it looks nil.

03 The if err != nil failure

Gotcha trap

This is THE nil-interface trap. If a function declares it returns error (an interface) but you return a concrete *MyError that happens to be nil, the returned error is not nil — its type slot is *MyError. Every if err != nil upstream now treats success as failure. The fix: never return a typed nil pointer through an error interface.

04 How to avoid it

In any function that returns error, return the literal nil on the success path — never a typed nil pointer variable. Keep the concrete error type out of your return slot until you actually have an error.

Leaks a typed nil
func do() error {
    var e *MyError
    // ... e stays nil on success ...
    return e   // non-nil interface!
}
Returns a true nil interface
func do() error {
    if bad {
        return &MyError{"boom"}
    }
    return nil // literal nil interface
}
Pro tip rules of thumb

(1) Declare error variables as error, not *MyError, where they flow to a return. (2) On success, write return ..., nil explicitly. (3) Be wary of helpers that return a concrete pointer error type — assign through an error first. (4) go vet and linters like nilness/staticcheck can catch some of these; the habit catches the rest.

05 Check yourself

A function returns error. On success it does var e *MyError; return e (so e is a nil *MyError). The caller writes if err != nil. What happens on the success path?

Right. Boxing a typed nil pointer into the error interface fills the type slot, so the interface is non-nil even though the pointer is nil. The if err != nil branch fires on a success — the textbook nil-interface trap. Fix: return nil literally on success.
