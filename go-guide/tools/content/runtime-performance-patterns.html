Runtime & performance · allocation control

Performance patterns & allocation control.

Most Go slowdowns at scale aren't slow algorithms — they're too many allocations hammering the garbage collector. A handful of disciplined patterns (reuse buffers, preallocate, build strings the right way, keep values off the heap) cut that allocation rate dramatically. But every one of them is earned with a profile first.

01 Profile first, optimize the hot path only

The order is non-negotiable: profile, find the hot path, then optimize just that. A 200×/sec allocation in your inner loop matters; the same allocation in startup code does not.

In plain English analogy

Allocations are like printing a brand-new sheet of paper every time you need scratch space, then handing it to a cleanup crew (the GC) to shred later. The patterns here are about reusing the same sheet, or asking for the whole notepad up front instead of one page at a time. But you only bother on the desk you actually work at all day — not the one you visit once a month.

Each pattern below removes allocations. The win shows up as fewer allocs/op under -benchmem and less GC time in a heap profile — measured, not assumed.

See also prerequisite

These patterns are pointless without numbers. First learn to get them: profiling & diagnosing with pprof shows how to find the hot path and prove a fix worked.

02 Preallocate when you know the size

Appending to a slice that starts at nil reallocates and copies the backing array as it grows. If you know (or can estimate) the final length, give make the capacity up front — the appends then never reallocate:

Grows & reallocates
out := []int{}            // cap 0
for _, v := range src {   // realloc at 1,2,4,8,16…
    out = append(out, v*v)
}
One allocation
out := make([]int, 0, len(src)) // cap known
for _, v := range src {         // no realloc
    out = append(out, v*v)
}

03 Build strings with strings.Builder

Strings are immutable, so s += piece in a loop allocates a brand-new string every iteration — O(n²) copying. strings.Builder writes into one growing buffer and produces the final string once:

+= in a loop
s := ""
for i := 0; i < n; i++ {
    s += strconv.Itoa(i) // new string each time
}
strings.Builder
var b strings.Builder
for i := 0; i < n; i++ {
    b.WriteString(strconv.Itoa(i))
}
s := b.String() // one result
Pro tip presize

Call b.Grow(n) when you can estimate the final length — it allocates the buffer once instead of doubling it as you write. The same idea applies to bytes.Buffer for byte output.

04 Reuse buffers: sync.Pool & value vs pointer

sync.Pool keeps a free-list of reusable objects so a hot path can borrow a buffer instead of allocating one each call — ideal for per-request scratch buffers:

pool.go
var bufPool = sync.Pool{
    New: func() any { return new(bytes.Buffer) },
}

func handle(w io.Writer, data []byte) {
    buf := bufPool.Get().(*bytes.Buffer)
    buf.Reset()              // always reset a reused buffer
    defer bufPool.Put(buf)   // return it for the next caller

    buf.Write(data)
    buf.WriteTo(w)
}

Two more allocation levers:

Avoid interface boxing on hot paths
Putting a value into any (e.g. via fmt.Sprintf) often heap-allocates to box it. In a tight loop, use a concrete type or strconv instead of fmt.
Value vs pointer
Passing a small struct by value stays on the stack; taking its address can force it to the heap. "Pointer is cheaper" is frequently false — let escape analysis decide.
Reuse byte buffers
For repeated I/O, keep one []byte and buf = buf[:0] to clear it without freeing the backing array.

Whether a value stays on the stack or escapes to the heap is the whole game here — stack, heap & escape analysis shows how the compiler decides and how to read -gcflags=-m.

05 The trap: premature optimization

Gotcha trap

Two real traps. (1) sync.Pool objects can be garbage-collected at any GC — Get may return a fresh object, so never assume pooled state persists, and always Reset before use. (2) Micro-optimizing cold code that hurts readability for no measured gain is a net loss — you've added complexity and traded nothing. If a benchmark doesn't show the win, revert it. Clear code first; optimize the hot path the profile pointed at, and only that.

The discipline, repeated: clear code → profile → optimize the proven hot path → re-measure. Anything you "optimize" without a before/after number is a guess wearing a costume.

See also design judgment

"Is this optimization worth the complexity?" is a design-judgment question, not just a Go one. Ousterhout's take in performance & what matters is the same lesson at the design level: measure, then spend complexity only where it buys real performance.

06 Check yourself

You replace s += piece in a hot loop with a strings.Builder. A teammate asks why it's faster even though both produce the same string. What's the real reason?

Right. Because Go strings are immutable, each += must allocate and copy the whole accumulated string so far — quadratic work and a fresh allocation every time. strings.Builder amortizes growth into one buffer (presizable with Grow) and only allocates the final string at String(). Same output, far fewer allocations — which is exactly what a heap profile would confirm.
