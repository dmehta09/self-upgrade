Runtime & performance · memory

Stack, heap & escape analysis.

Go gives you pointers but hides where things live. The compiler decides — per variable — whether it can sit cheaply on the stack or must "escape" to the garbage-collected heap. Understanding that decision is the difference between code that allocates nothing and code that hammers the GC.

01 Two places memory lives

A function's locals live on its stack frame — created on call, thrown away on return, essentially free. Anything that must outlive the call goes on the heap, which the garbage collector manages later.

In plain English analogy

The stack is the scratch paper on your desk: you scribble while working on one task and bin the whole sheet when you're done — instant, no bookkeeping. The heap is the filing cabinet: things you'll need after this task ends go there, but now someone (the GC) has to remember to throw them out later. Filing is slower than scribbling, so you only file what truly must survive.

You never call malloc or free in Go. Instead the compiler runs escape analysis at build time and decides each variable's home for you. Most locals never escape.

03 What forces a heap escape

The compiler is conservative: if it can't prove a value stays within the frame, it heap-allocates. The common triggers:

Returning a pointer to a local
return &x — the address escapes the frame.
Closures that outlive the call
A goroutine or returned function that captures a local by reference.
Storing into an interface
Putting a value in an any/interface (e.g. fmt.Println(v)) often boxes it on the heap.
Unknown or large size
A slice that grows at runtime, or a value too big to sit comfortably on the stack.
Sharing via a channel
A pointer sent on a channel escapes — another goroutine may hold it.

04 Seeing it for yourself

The compiler will tell you. go build -gcflags=-m (or -gcflags="-m -m" for more detail) prints every escape decision. Profilers and testing.B's -benchmem show the allocation count.

Run go build -gcflags=-m on this and you'll see moved to heap: p for escapes but nothing for stackOnly.

05 Why it matters — and why not to obsess

Gotcha trap

"Pass a pointer, it's cheaper" is often wrong. Passing &big can force big onto the heap (an allocation + GC work), whereas copying a small struct by value stays on the stack and is faster. Don't guess — profile, read the -m output, and only then optimize the hot path. Heap allocations matter at scale (GC pressure), not in glue code.

The practical takeaway: write clear code first. When a benchmark says a hot function allocates too much, use -gcflags=-m to find the escape, then restructure (reuse buffers with sync.Pool, accept a value instead of returning a pointer, preallocate slices) to keep it on the stack.
