Getting started · values

Variables, constants & zero values.

Go's value model is small and strict: a few declaration forms, a fixed set of basic types, and one rule that removes a whole class of bugs — every variable starts at its type's zero value. No uninitialised memory, ever.

01 Declarations: var, :=, and inference

Declare with var x int = 3, let the type be inferred (var x = 3), or use the short form x := 3 inside a function. := both declares and assigns.

In plain English analogy

Think of var as filling out the full form — name, type, value — where any field can be left blank. := is the express lane: you write the name and the value, and Go reads the type off the value for you. The express lane only opens inside a function; at package level you must use var.

decl.go
var a int = 3      // explicit type + value
var b = 3          // type inferred from the value (still int)
var c int          // no value → zero value (0)
d := 3             // short form: declare + assign, function bodies only

var (              // grouped block, common for package-level vars
    name = "ada"
    age  = 36
)

Use := for locals (it's the everyday form); reach for var when you want an explicit type, a package-level variable, or the zero value with no initialiser.

02 The basic types

The core set: int/int64 (whole numbers), float64 (decimals), bool, string. Two aliases matter: byte = uint8 (a raw byte) and rune = int32 (a Unicode code point).

03 Zero values: nothing is uninitialised

Every type has a zero value, and an uninitialised variable starts there: 0 for numbers, false for bool, "" for string, and nil for pointers, slices, maps, channels, funcs & interfaces. Go has no uninitialised memory.

In plain English analogy

In C, a fresh variable is a hotel room the last guest left in any state — read it before you set it and you get garbage. In Go, housekeeping always resets the room first: numbers to 0, text to empty, references to "nothing here yet" (nil). You can read a brand-new variable safely; you'll get a sensible, documented default, never random bytes.

This makes structs especially pleasant — a freshly declared struct has every field at its zero value, so a zero-valued value is often already usable:

04 Constants & iota enums

const values are fixed at compile time and are untyped until used, so they fit any compatible type. iota is an auto-incrementing counter that resets to 0 in each const block — the idiomatic way to build enums.

Inside a const (...) block, iota is 0 on the first line and increments by one each line. A blank _ skips a value; an expression on the first line repeats down the block:

The 1 << (10 * iota) trick reads once and applies to every following line — Go repeats the previous expression when a const line has no value of its own.

05 The conversion gotcha

Gotcha trap

Go has no implicit numeric conversion. You cannot add an int to an int64, or an int to a float64, without an explicit cast — int64(x), float64(n). And remember integer division truncates: 3 / 2 == 1, not 1.5. Convert to float64 before dividing if you want the fraction.

Won't compile / surprises you
var n int = 3
var x float64 = 4.5
y := n + x          // mismatched types int + float64 → error

avg := 3 / 2        // integer division → 1 (the .5 is gone)
Explicit & correct
var n int = 3
var x float64 = 4.5
y := float64(n) + x // 7.5 — convert first

avg := float64(3) / 2 // 1.5 — one operand is float, so float division

The strictness is on purpose: an implicit int→float64 can silently lose precision, and an implicit narrowing can silently overflow. Go makes you write the cast so the lossy step is visible in the code.

06 Check yourself

What does fmt.Println(7 / 2) print, and why?

Right. 7 and 2 are both integer constants, so / is integer division: the result is 3, the .5 is dropped. To get 3.5 you must make an operand a float — 7.0 / 2 or float64(7) / 2. Go never promotes silently.
