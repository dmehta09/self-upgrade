Getting started · toolchain

The toolchain & modules.

Go ships as one command — go — that builds, runs, tests, formats, vets, and manages dependencies. No package manager to pick, no build system to configure. Learn a handful of subcommands and the module system, and you can drive any Go project.

01 One tool does it all

The single go binary bundles the compiler, test runner, formatter, linter, and dependency manager: go build, run, test, fmt, vet, mod.

In plain English analogy

In a lot of ecosystems, starting a project means assembling a kit: a build tool here, a package manager there, a formatter, a test runner, a linter — each a separate install with its own config file. Go hands you a single Swiss-army knife. Every blade (build, test, fmt…) is already attached, already agrees with the others, and needs no setup.

terminal
go build ./...   # compile every package in the tree
go run .         # compile + run this package, no binary left behind
go test ./...    # run every _test.go in the tree
go fmt ./...     # rewrite files to the one canonical style
go vet ./...     # static checks: printf args, lost cancels, shadowing…
go mod tidy      # sync dependencies to what the code actually imports

The ./... pattern means "this directory and everything below it." There's no separate "install the tools" step — they came with Go.

02 Modules: go.mod, go.sum & versions

A module is a unit of versioned code rooted at a go.mod file. It declares the module path (the import prefix) and the dependency versions; go.sum pins cryptographic checksums. Dependencies use semantic versioning.

You start a project with go mod init <module-path>. The module path is usually the repo URL — it's both the project's identity and the prefix other code uses to import its packages.

go.mod
module github.com/acme/widgets   // the module path = import prefix

go 1.26                          // language/toolchain version

require (
    github.com/google/uuid v1.6.0
    golang.org/x/sync v0.10.0
)
Module path
The import prefix. A package at ./store imports as github.com/acme/widgets/store.
go.sum
A lockfile of checksums for every dependency (and its dependencies). Commit it — it makes builds verifiable and tamper-evident.
SemVer
v1.6.0 = MAJOR.MINOR.PATCH. A new MAJOR (v2+) changes the import path itself (/v2), so breaking changes can't sneak in.
GOPATH
History. Pre-2018 Go forced all code under one $GOPATH/src tree. Modules ended that — your project lives anywhere.
See also tip

The go directive (go 1.26) gates which language features the file may use — bumping it is how a module opts in to, say, per-iteration loop variables or range-over-func. The separate toolchain line (below) pins which compiler binary builds it.

03 toolchain, workspaces & replace

Modules scale past one repo with three tools: the toolchain directive (which Go binary builds you), go.work (local multi-module workspaces), and replace (temporary local overrides — keep them out of published modules).

toolchain go1.26.0
In go.mod: the exact toolchain the go command should download/use. Distinct from the language go 1.26 line. Teams pin this so CI and laptops compile with the same binary.
go.work
A workspace file listing local modules (use ./svc-a, use ./svc-b). Lets you edit sibling modules without publishing or replace hacks. Do not commit go.work to library repos; it's a local developer tool (commit only in monorepo roots that intend it).
replace
replace github.com/acme/lib => ../lib forces a local path. Fine for a one-off debug; prefer go.work for ongoing multi-module work, and never leave a machine-local replace in a module others will go get.
go.mod
module github.com/acme/widgets

go 1.26

toolchain go1.26.0

require golang.org/x/sync v0.10.0
go.work
go 1.26

use (
    ./widgets
    ./widgets-cli
)
Gotcha trap

Shipping a replace that points at /Users/you/... breaks every other machine. Workspaces fix the local-edit problem without poisoning go.mod. If you must replace for a fork, use a relative path inside the repo or a public fork URL.

04 Everyday commands

Adding a dependency is just importing it and running go mod tidy (or go get). The tool resolves versions, downloads, and updates both go.mod and go.sum for you.

terminal
go mod init github.com/acme/widgets   # create go.mod for a new project
# ...add  import "github.com/google/uuid"  to your code, then:
go mod tidy                           # add missing + drop unused deps
go get github.com/google/uuid@v1.6.0  # pin/upgrade a specific version
go get -u ./...                       # upgrade deps to latest minor/patch
go list -m all                        # print the full dependency graph
go test -race ./...                   # run tests with the race detector

The typical loop is tight: edit code, go test ./..., go build. Because compiles are fast, you rarely think about the toolchain at all — it stays out of the way.

05 The build output: one static binary

go build emits a single, statically-linked executable — no runtime, no shared libraries to ship. Set GOOS and GOARCH to cross-compile for any platform from your laptop.

In plain English analogy

Other runtimes ship you a recipe plus a list of ingredients the host must already have (a JVM, a Python interpreter, the right shared libs). Go ships a sealed, ready-to-eat meal — the binary contains everything it needs. Drop it on a fresh Linux box (even an empty scratch container) and it just runs.

terminal
go build -o widgets .                 # → ./widgets, a self-contained binary

# Cross-compile for Linux/ARM64 from a Mac — no extra toolchain:
GOOS=linux GOARCH=arm64 go build -o widgets-linux-arm64 .

GOOS=windows GOARCH=amd64 go build -o widgets.exe .

go tool dist list                     # every GOOS/GOARCH pair Go supports

This is why Go dominates ops tooling: one go build per platform produces artifacts you can scp anywhere and run. Container images can be a few megabytes — just the binary on top of scratch.

06 The go.mod gotcha

Gotcha trap

Don't hand-edit go.mod to bump a version, and don't forget go mod tidy. go.mod is a managed file — typing a version by hand skips the resolver, so it can disagree with go.sum or pull a version whose own dependencies you never recorded. Worse, if your imports and go.mod drift apart (you added an import but never tidied, or removed one and left the require behind), CI builds fail with missing go.sum entry or "inconsistent vendoring." The fix is the same command every time: go get pkg@version to change a version, then go mod tidy to reconcile.

Don't
# open go.mod in an editor, change the line by hand:
#   github.com/google/uuid v1.6.0  ->  v1.7.0
# ...then push. go.sum still pins v1.6.0 → broken build.
Do
go get github.com/google/uuid@v1.7.0   # resolver updates go.mod + go.sum
go mod tidy                             # reconcile with actual imports

07 Check yourself

You add import "github.com/google/uuid" to a file. Which single command makes the build work — downloading the dependency and recording it in go.mod and go.sum?

Right. go mod tidy reconciles your dependency files with what the code actually imports — adding missing modules and dropping unused ones, updating both go.mod and go.sum. Hand-editing go.mod skips the resolver and the checksum, which is exactly how builds break. (go build/go test will also auto-add a single missing module, but tidy is the command that fully syncs the manifest.)
