Testing & tooling · synctest

testing/synctest: fake clocks for concurrency.

Code that sleeps, waits on timers, or races the wall clock used to force flaky tests or hour-long timeouts. Go 1.25 stabilized testing/synctest: a bubble of goroutines on a fake clock that advances only when everyone is blocked — so a one-hour timeout finishes in milliseconds, deterministically.

01 Why fake time beats real sleep

Real time.Sleep in tests is slow and flaky. Injecting a clock interface works, but every call site must cooperate. synctest runs the real time package APIs inside a bubble whose clock the test controls.

In plain English analogy

It's a flight simulator for time. Outside, an hour is an hour. Inside the bubble, the instructor advances the dial the moment every pilot is waiting — nobody twiddles thumbs for sixty real minutes.

synctest.Test
Entry point (stable in 1.25): runs a function in an isolated bubble with a fake clock.
Durability
Only code that uses time (Sleep, After, NewTimer, Tickers, deadlines) sees the fake clock. External I/O still uses wall time — keep network out of the bubble.
vs clock interface
Interfaces are still great for production seams. synctest is for testing code that already calls time directly.

02 The shape of a synctest

Wrap the scenario in synctest.Test(t, func(t *testing.T) { ... }). Start goroutines that block on timers; the bubble advances automatically when all are idle, or you can assert after controlled sleeps.

timeout_test.go
package cache_test

import (
    "testing"
    "testing/synctest"
    "time"
)

func TestExpiresAfterTTL(t *testing.T) {
    synctest.Test(t, func(t *testing.T) {
        c := New(time.Hour) // real TTL, fake clock
        c.Put("k", "v")

        if _, ok := c.Get("k"); !ok {
            t.Fatal("expected hit before TTL")
        }

        time.Sleep(time.Hour + time.Second) // advances instantly in the bubble
        if _, ok := c.Get("k"); ok {
            t.Fatal("expected miss after TTL")
        }
    })
}

No time.Now injection required if the cache uses time.Now / timers from the standard library — inside the bubble those calls see fake time.

03 When to reach for it

Good fit

Timeouts, TTLs, rate-limit windows, backoff, lease expiry, anything that selects on time.After.

Poor fit

Tests that need real wall-clock scheduling against OS threads, or that dial the network — keep those outside the bubble.

Race detector

Still run go test -race; synctest does not replace race finding — it replaces sleeping.

Clock seams

Production code that must swap clocks in non-test builds should keep an interface; use synctest for stdlib-time paths.

Pro tip with seams

Prefer a narrow Clock interface when many packages need injectable time. Prefer synctest when you're testing a package that already sleeps on real time APIs and you refuse to rewrite it for the test. See also Test doubles & seams.

04 Gotchas

Gotcha trap

(1) Blocking on channels/mutexes that never unblock deadlocks the bubble — same as a real deadlock, just faster to notice. (2) Mixing bubble goroutines with work that uses the real clock (HTTP client timeouts to a live server) confuses the model — isolate. (3) Don't assert on wall-clock duration of the test; assert on logical outcomes after fake sleeps.

05 Check yourself

You need to test that a worker cancels after a 30-minute idle timeout implemented with time.After. What's the best approach in Go 1.25+?

Right. synctest keeps production timeouts honest while making the test instant and deterministic. Real multi-minute sleeps are flaky and slow; shipping a 10ms timeout to make tests pass is a production foot-gun.
