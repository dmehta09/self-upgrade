Methods & receivers.

A Go method is just a function with an extra parameter — the receiver — that binds it to a type. The one decision that bites everyone: should the receiver be a value or a pointer? Get it wrong and your mutations silently vanish.

01 A method is a func with a receiver

A method is a function declared with a receiver in parentheses before the name: func (c Counter) Value() int. The receiver is how you say "this function belongs to Counter."

In plain English analogy

Other languages put methods inside the class, like tools bolted to a machine. Go keeps them outside and just labels each one with a sticker that says which type it operates on. c.Value() is honestly the same as Value(c) — the receiver is the hidden first argument.

There's no this keyword; you name the receiver (idiomatically a short letter or two from the type name). Calling c.Inc() is sugar for passing c as that receiver.

02 Value vs pointer receiver

A value receiver works on a copy; a pointer receiver works on the original. To mutate the thing you called the method on, the receiver must be a pointer.

Value receiver — change is lost
func (c Counter) Inc() {
    c.n++          // bumps a COPY
}                  // caller's Counter unchanged
Pointer receiver — change sticks
func (c *Counter) Inc() {
    c.n++          // c.n is (*c).n — the real field
}                  // caller's Counter updated

Go auto-takes the address for you: on an addressable value c.Inc() becomes (&c).Inc() automatically, and on a pointer p.Value() becomes (*p).Value(). You rarely write the &/* yourself — but the declared receiver kind is what decides whether a copy is made.

The method set, precisely deeper

The method set of type T includes methods with value receivers. The method set of *T includes both value- and pointer-receiver methods. This matters for interface satisfaction: if Inc has a pointer receiver, only *Counter (not Counter) satisfies an interface that requires Inc. We chase this exact trap in the interfaces-in-practice lesson.

03 Why didn't my change stick?

Gotcha trap

A value receiver can't mutate the original — it gets a copy, the copy is modified, and the copy is thrown away when the method returns. The compiler gives no error; your data is simply unchanged. If a method is meant to change state, declare the receiver as *T. This is the single most common "why is my counter still zero?" bug in Go.

04 When to use which — and be consistent

Use a pointer receiver when the method mutates the receiver or the struct is large (avoid copying). Otherwise a value receiver is fine. The senior rule: be consistent per type — don't mix.

Mutates state?
Pointer. A copy can't change the caller's value.
Big struct?
Pointer — copying every call is wasteful (a pointer is one word).
Holds a lock, or shouldn't be copied?
Pointer. Types embedding sync.Mutex must not be copied.
Tiny, immutable value (a Point, an ID)?
Value receiver reads clean and is safe to copy.
Pro tip consistency

If any method on a type needs a pointer receiver, give them all pointer receivers. A type with a mixed method set is confusing and can silently fail to satisfy an interface. go vet flags some of these mistakes; consistency avoids the rest.

05 Methods on any named type — not just structs

You can attach methods to any type you define in your package, including a named type over int, string, or a slice — not only structs.

06 Check yourself

A Wallet has func (w Wallet) Deposit(n int) { w.balance += n }. You call w.Deposit(100) twice, then print w.balance (started at 0). What prints?

Right. Deposit has a value receiver, so each call works on a throwaway copy of w. The compiler is happy, but the original balance stays 0. Fix it with a pointer receiver: func (w *Wallet) Deposit(n int).
