Runtime & performance · diagnostics

Profiling & diagnosing with pprof.

Guessing where a Go program spends its time is how you waste a week optimizing the wrong loop. pprof is the built-in profiler that measures it for you — CPU, allocations, goroutines, blocking — and the execution tracer shows the whole runtime timeline. The rule is simple: never optimize without a profile.

01 Measure, don't guess

Performance work is a loop: measure → find the hot spot → fix → re-measure. A profile tells you where the cost actually is — which is almost never where you'd guess.

In plain English analogy

Optimizing without a profile is like a doctor prescribing surgery without an X-ray. The profiler is the X-ray: it samples your program many times a second and shows which functions the bone-saw should actually touch. Operate on the part that hurts — not the part you assume hurts. Nine times out of ten the real cost is somewhere boring you'd never have looked.

A profiler works by sampling: many times per second it records what the program is doing (which function is on the CPU, who allocated, who's blocked). Sampling is cheap, so the picture is statistically accurate without slowing things to a crawl.

02 The profile types

Each profile answers a different question. Pick the one that matches your symptom:

CPU (profile)
Where wall-clock CPU time goes. Samples the running goroutine ~100×/sec. Use it for "this is slow / pegs a core."
Heap (heap / allocs)
What's allocating. inuse_space shows live memory now; alloc_space shows total allocated over time (GC pressure). Use it for "high memory / GC churn."
Goroutine
A snapshot of every goroutine and its stack. A growing count is the classic leak signature.
Block
Time spent blocked on channels, mutexes, sync waits. Off by default — enable with runtime.SetBlockProfileRate.
Mutex
Contended lock holders. Off by default — enable with runtime.SetMutexProfileFraction.

Match the symptom to the profile: slow CPU → CPU profile; memory/GC → heap profile; stuck or leaking → goroutine profile; lock waits → block/mutex.

03 Capturing a profile

Two main ways. In tests/benchmarks, flags write a profile file directly:

terminal
# benchmark, capturing CPU + heap profiles
go test -bench=. -cpuprofile=cpu.out -memprofile=mem.out

# -benchmem also prints allocs/op and bytes/op inline
go test -bench=. -benchmem

In a running service, import the HTTP handler. The blank import registers handlers under /debug/pprof on the default mux — then you scrape them live:

main.go
package main

import (
    "net/http"
    _ "net/http/pprof" // registers /debug/pprof/* on http.DefaultServeMux
)

func main() {
    // Keep this on an INTERNAL port, never public.
    go http.ListenAndServe("localhost:6060", nil)
    // ... your real server ...
    select {}
}
Pro tip capture live

Grab a 30-second CPU profile straight from a live process: go tool pprof http://localhost:6060/debug/pprof/profile?seconds=30. For a heap snapshot, hit /debug/pprof/heap; for goroutines, /debug/pprof/goroutine?debug=2 dumps every stack as readable text.

04 Analyzing with go tool pprof

Point go tool pprof at a profile file or endpoint; it drops into an interactive shell. The commands you actually use:

CommandWhat it shows
topThe functions costing the most (flat = self, cum = including callees). Your first move.
list FnSource of Fn annotated line-by-line with cost — pinpoints the exact hot line.
webOpens a callgraph SVG in the browser (needs Graphviz).
-http=:8080Launches the web UI with an interactive flame graph — width = time, the standard way to read a CPU profile.
terminal
# interactive: top, then drill into the hottest function
go tool pprof cpu.out
(pprof) top
(pprof) list parseRow

# or jump straight to the flame-graph web UI
go tool pprof -http=:8080 cpu.out

Read the flame graph top-down by width: the widest box at any level is where the time goes. Click to zoom. A wide plateau of one function = your hot spot.

05 Counting goroutines & the execution tracer

For a leak you often don't even need a full profile — runtime.NumGoroutine() returns the live count. If it climbs forever, goroutines aren't exiting:

Because we wg.Wait() for every goroutine to finish before reading the count again, the result is deterministic: 0 leaked. Drop the Wait() in real code and a growing after would betray a leak. For allocation counts you'd reach for runtime.ReadMemStats, but those numbers depend on GC timing — read them in a benchmark, not a snippet:

memstats.go
var m runtime.MemStats
runtime.ReadMemStats(&m)
fmt.Println(m.Mallocs, m.HeapAlloc) // nondeterministic: depends on GC + runtime

The execution tracer is the deepest tool — it records every scheduling event, GC, and syscall:

trace.go
import "runtime/trace"

f, _ := os.Create("trace.out")
trace.Start(f)
defer trace.Stop()
// ... run the workload ...
// then: go tool trace trace.out  → opens the timeline UI

A goroutine profile (or a climbing NumGoroutine) is how you confirm a leak you suspect. For the patterns that cause them — and how to avoid them — see leaks, deadlocks & races.

06 The cost — and the discipline

Gotcha trap

Two traps. First, don't optimize without a profile — your intuition about the hot spot is usually wrong, and you'll waste effort (and add complexity) for no measured gain. Second, block and mutex profiling are not free — they're off by default and you must enable them (SetBlockProfileRate / SetMutexProfileFraction). CPU and heap sampling, by contrast, are cheap enough to leave on /debug/pprof in production behind an internal port — the sampling overhead is negligible.

The whole discipline in one sentence: profile to find the hot spot, change one thing, re-profile to prove it helped. If the second profile doesn't show improvement, revert — you added complexity for nothing.

07 Check yourself

A long-running Go service slowly consumes more and more memory, and its runtime.NumGoroutine() keeps climbing over hours. Which profile most directly pinpoints the cause?

Right. A forever-climbing goroutine count is the textbook leak signature, and the goroutine profile (/debug/pprof/goroutine?debug=2) shows exactly where they're all parked — usually blocked on a channel that never receives or a missing cancel(). The retained memory is a symptom of the stuck goroutines holding references. CPU and heap profiles work on live services too; mutex contention is a different problem.
