Getting started · control flow

Control flow & functions.

Go's control flow is deliberately spare: one loop keyword, a switch with no surprise fall-through, and functions that can hand back several values at once. Fewer constructs, fewer ways to trip.

01 if and for — the only loop

Go has one loop keyword: for. Drop the clauses and it's a while; drop them all and it's an infinite loop. if can carry an init statement whose variable is scoped to the if.

In plain English analogy

Most languages give you three loop words (for, while, do-while) that mostly overlap. Go gives you one dial with three clauses — init, condition, post — and you leave blank whichever you don't need. Same dial, every loop; nothing new to learn for "loop while" vs "loop N times."

loops.go
for i := 0; i < 3; i++ { }   // classic three-clause loop

for x < 100 { x *= 2 }        // condition only — a "while"

for { /* … */ break }         // no clauses — infinite, exit with break

for i := range 3 { }          // range-over-int (Go 1.22): i = 0,1,2

// if with an init statement — err is scoped to the if/else
if v, err := strconv.Atoi(s); err == nil {
    use(v)
} else {
    log.Println(err)
}

The if v, err := …; cond form is everywhere in Go: it keeps the temporary (here v and err) tightly scoped to the branch that uses it, instead of leaking into the function body.

02 switch — no implicit fall-through

A Go switch does not fall through by default — the matching case runs and the switch ends, no break needed. Omit the value and it becomes switch true: a clean ladder of conditions.

In plain English analogy

In C-family languages a switch is a slide: land on a case and you keep sliding into the next one unless you jam a break in. Go flips the default — each case is its own room with the door closed. You only slide on if you explicitly say fallthrough, which almost nobody does.

switch.go
switch day {
case "sat", "sun":          // one case, multiple values
    fmt.Println("weekend")
default:
    fmt.Println("weekday")
}                            // no break needed — cases don't fall through

switch {                    // "switch true" — a condition ladder
case score >= 90:
    grade = "A"
case score >= 80:
    grade = "B"
default:
    grade = "C"
}

The switch { case cond: … } form replaces a long if/else if chain and reads top-to-bottom like a decision table. Cases are tested in order; the first true one wins.

03 Functions: multiple & named returns

Functions can return several values — the idiom is (result, error). Returns can be named (pre-declared, zero-valued, returned by a bare return), and a trailing ...T parameter makes a function variadic.

Multiple returns are why Go needs no exceptions for ordinary failure: the failure travels back as an explicit second value you check, right where it happened.

04 Closures: functions are values

Functions are first-class values — assign them, pass them, return them. A closure captures the variables of its surrounding scope by reference, so it can carry private, mutable state between calls.

In plain English analogy

A closure is a function with a backpack. When you create it inside another function, it quietly packs the local variables it mentions into a backpack it carries everywhere. Call it later — even after the outer function has long returned — and it still reaches into that backpack. Two closures made from the same loop can share a backpack, or each get their own; which is exactly the trap below.

05 The loop-variable capture gotcha

Gotcha trap

Closures capture the loop variable, not a snapshot. Before Go 1.22, a for loop had one shared loop variable for the whole loop — so every closure created in the body captured the same variable and saw its final value (a goroutine/closure-in-a-loop classic). Go 1.22 fixed this: the loop variable is now per-iteration, so each closure captures its own copy. Code that needed the old i := i shadow trick no longer does.

Pre-1.22 behaviour (one shared i)
var fns []func()
for i := 0; i < 3; i++ {
    fns = append(fns, func() { fmt.Print(i) })
}
for _, f := range fns { f() }
// prints 333 — all closures share the one i, now == 3
Go 1.22+ (a fresh i per iteration)
var fns []func()
for i := 0; i < 3; i++ {
    fns = append(fns, func() { fmt.Print(i) })
}
for _, f := range fns { f() }
// prints 012 — each closure captured its own i

The pre-1.22 workaround was to shadow the variable at the top of the body — i := i — making a new per-iteration binding by hand. On Go 1.26 that's unnecessary, but you'll still see it in older code; it's now a harmless no-op.

06 Check yourself

You build three closures in a for i := 0; i < 3; i++ loop, each printing i, then call them all afterward. On Go 1.22+, what prints?

Right. Go 1.22 made for-loop variables per-iteration, so each closure closes over its own copy and prints 0, 1, 2. On Go 1.21 and earlier the same code prints 333 (one shared variable left at its final value) — which is exactly the bug the change was made to kill.
