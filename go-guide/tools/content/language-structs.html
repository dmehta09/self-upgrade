The language core · structs

Structs, embedding & tags.

Structs are Go's way to group fields into a value type. Embedding gives you composition (not inheritance), tags attach metadata for libraries, and good Go aims for a useful zero value.

01 Structs are value types

A struct groups named fields into one value. It's a value type: assigning or passing a struct copies all its fields. Build one with a composite literal, ideally with field names.

In plain English analogy

A struct is a labeled form — name, age, email boxes filled in. Hand someone the form and (because it's a value) they get a photocopy: scribbling on their copy doesn't touch yours. To let them edit your original, you hand over a pointer to it instead.

02 Embedding is composition, not inheritance

Declare a field with no name — just a type, and you embed it. The outer struct promotes the inner type's fields and methods, so you can call them directly. This is composition: "has-a", wired for convenience — not a class hierarchy.

See also design

Promotion is delegation, not subtyping: a Manager that embeds Person is not a Person in Go's type system — there's no upcast. The method just gets forwarded to the embedded value.

If the outer struct declares a field or method with the same name, it shadows the promoted one — the inner is still reachable via the explicit path e.Person.Name.

03 Struct tags: metadata for libraries

A struct tag is a backtick string after a field. It's inert metadata read via reflection — encoders like encoding/json use it to map a Go field to an external name, omit zero values, or skip a field entirely.

Email vanished thanks to omitempty, and the unexported pwd is invisible to the encoder (it can't reflect on it). Tags are just strings — a typo like jsno:"x" compiles fine and is silently ignored, so go vet has a check for it.

04 Design for a useful zero value

Idiomatic Go makes the zero value useful: a freshly declared struct should work without a constructor. sync.Mutex and bytes.Buffer are the canonical examples — var mu sync.Mutex and var buf bytes.Buffer are ready to use.

Gotcha trap

Comparability: == works on a struct only if every field is comparable. Add a slice, map, or func field and the struct becomes non-comparable — a == b is a compile error, and you can't use it as a map key. (A struct of strings/numbers/bools/pointers/arrays is fine.)

05 Check yourself

You add a Tags []string field to a struct, then try to use that struct as a map key. What happens?

Right. Map keys must be comparable with ==, and slices (like maps and funcs) are not comparable — so a struct containing one isn't either, and the program won't compile. Workarounds: key by a comparable projection (e.g. a joined string), or use an array field instead of a slice.
