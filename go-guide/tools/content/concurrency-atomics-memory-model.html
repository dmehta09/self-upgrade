Concurrency · atomics & the memory model

Atomics & the Go memory model.

A mutex guards a region of code; sync/atomic guards a single word — a counter or a flag — with no lock at all. But the deeper lesson is the one that bites in interviews: without a synchronizing operation, one goroutine's write may never become visible to another. That's the Go memory model, and it's why a plain shared flag is a bug.

01 sync/atomic: lock-free single-word ops

sync/atomic does one indivisible read-modify-write on one machine word — no Lock/Unlock. Reach for it for counters and flags, nothing more.

In plain English analogy

A mutex is a meeting room you book, walk into, do several things, then leave. An atomic is a turnstile: one person clicks through and the counter ticks up by exactly one, indivisibly — no booking, no room. It's blisteringly fast, but it only does the one click. The moment you need to update two things together, you're back to booking a room.

The classic free functions take a pointer to the word you're mutating:

atomic.go
var n int64
atomic.AddInt64(&n, 1)              // n += 1, indivisibly
v := atomic.LoadInt64(&n)           // read the current value safely
atomic.StoreInt64(&n, 42)           // write 42 safely
old := atomic.SwapInt64(&n, 7)      // set 7, return the previous value
ok := atomic.CompareAndSwapInt64(&n, 7, 8) // if n==7 set 8; report success

Since Go 1.19 there are typed wrappers — treat these as the standard, idiomatic form today. They carry their own value (no stray pointer), and go vet can't catch a missing atomic.* on a plain field, so wrapping it is self-documenting:

typed.go
var hits atomic.Int64           // methods: Add, Load, Store, Swap, CompareAndSwap
hits.Add(1)
fmt.Println(hits.Load())

var ready atomic.Bool           // a correct shared flag
ready.Store(true)
if ready.Load() { /* ... */ }

var cfg atomic.Pointer[Config]  // swap a whole *Config atomically (hot-reload)
cfg.Store(&Config{Region: "eu"})
c := cfg.Load()

var v atomic.Value              // holds any value — but see the gotcha
v.Store("hello")
atomic.Int64 / Int32 / Uint64
Lock-free counters. Add returns the new value; Swap returns the old.
atomic.Bool
A correct one-bit flag — the right fix for the broken done pattern below.
atomic.Pointer[T]
Atomically swap a *T — config hot-reload, copy-on-write snapshots. Type-safe (1.19+).
atomic.Value
The pre-generics box for "store any value". Prefer atomic.Pointer[T] in new code.

02 The memory model & happens-before

The Go memory model defines exactly when a read is guaranteed to observe a write. The rule: a write is visible to a read only if a happens-before edge connects them — and that edge comes only from a synchronizing op (channel, mutex, atomic). No edge, no guarantee, ever.

In plain English analogy

Each goroutine writes in its own private notebook. There is no shared whiteboard. Goroutine B sees what goroutine A wrote only if A hands B a note through an official channel — a mailbox (channel), a signed-out key (mutex), or an atomic stamp. Without that handoff, B is reading a notebook it was never given, and what it sees is undefined — possibly forever stale.

"Happens-before" is just an ordering of memory events that the runtime promises to honor. Within a single goroutine, statements happen-before in program order. Across goroutines, the only way to create an edge is a synchronizing operation:

  • A send on a channel happens-before the corresponding receive completes.
  • A mu.Unlock() happens-before the next mu.Lock() that returns.
  • An atomic.Store happens-before an atomic.Load that reads the stored value.

Each edge also drags along everything written before it. So when B receives from a channel, B is guaranteed to see all the writes A made before A's send — not just the message. That's how a channel "publishes" data safely.

03 The broken flag, made visible

Here's the canonical trap. One goroutine sets a plain bool done; another spins reading it, expecting to see true. With no synchronizing op between them, there is no happens-before edge — so the compiler may hoist the read out of the loop, or the CPU may keep a stale cached copy. The reader can spin forever:

The fix is to add an edge. Any one of these makes the write visible: an atomic.Bool (done.Store(true) / done.Load()), a channel (close a done chan struct{} and the reader's <-done unblocks), or a mutex around both accesses. The channel version is the most idiomatic Go: signal completion by closing a channel, not by polling a flag.

Gotcha trap

Atomics protect one word, not an invariant. Three points bite people: (1) An atomic counter is safe, but if x.Load() > 0 { x.Add(-1) } is a race — the check and the decrement aren't one operation; use CompareAndSwap or a mutex. (2) Mixing atomic and plain access to the same variable is still a data race; once a variable is atomic, every access must be atomic. (3) atomic.Value panics if you Store two different concrete types into it — keep the type consistent (or use atomic.Pointer[T], which can't).

04 Atomic or Mutex? Don't get clever

Reach for an atomic when you mutate exactly one word — a counter, a flag, a swappable pointer. Reach for a Mutex the instant correctness spans two or more fields or a multi-step invariant.

Atomic fits
  • A hit/error counter incremented from many goroutines.
  • A one-shot flag (shuttingDown, ready).
  • Swapping a whole immutable snapshot via atomic.Pointer[T] (config hot-reload).
Use a Mutex instead
  • Two fields that must agree (e.g. balance and a txns log).
  • Read-then-decide-then-write where the steps must be one unit.
  • Anything that touches a map, slice, or several variables together.

05 Check yourself

A goroutine writes a plain var done bool = true, then another goroutine spins in for !done {}. There is no channel, mutex, or atomic anywhere. What does the memory model guarantee about whether the loop ends?

Right. Visibility in Go comes from happens-before, not from real-time or scheduling. With no synchronizing operation between the write and the read, the compiler may cache done in a register and the CPU may never propagate the write — the reader can be frozen at false indefinitely. Fix it with an atomic.Bool, a closed channel, or a mutex, all of which establish the edge that publishes the write.
