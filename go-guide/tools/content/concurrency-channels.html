Concurrency · channels

Channels: typed pipes between goroutines.

Channels are how goroutines talk. Instead of sharing a variable and guarding it with a lock, one goroutine sends a value and another receives it — the handoff itself carries the synchronization. Once you can see the buffer and the blocked waiters, channels stop being mysterious.

01 Send, receive, and the zero-buffer rendezvous

A channel is a typed conduit: ch := make(chan int). Send with ch <- v, receive with v := <-ch. An unbuffered channel (the default) is a rendezvous — the sender blocks until a receiver is ready, and vice versa.

In plain English analogy

An unbuffered channel is a baton pass in a relay race: the runner with the baton must wait, hand outstretched, until the next runner's hand is there — then the pass happens in one instant and both keep moving. A buffered channel adds a small shelf between them: the sender can drop a few batons on the shelf and carry on, until the shelf is full.

Because the rendezvous synchronizes both goroutines, a successful send/receive is also a happens-before edge — the receiver sees everything the sender did before the send. That's why "share memory by communicating" works.

03 Direction, close & range

Channels can be directional in a signature — chan<- int (send-only) and <-chan int (receive-only) — which lets the compiler enforce who sends and who receives. A sender signals "no more values" with close(ch); receivers can range until it's closed:

pipeline.go
func produce(out chan<- int) {   // send-only
    for i := 1; i <= 3; i++ {
        out <- i
    }
    close(out)                   // the SENDER closes, once it's done
}

func main() {
    ch := make(chan int)
    go produce(ch)
    for v := range ch {          // ranges until ch is closed and drained
        fmt.Println(v)
    }
}

The two-result receive v, ok := <-ch tells you whether the channel is still open: after a closed channel is drained, ok is false and v is the zero value.

04 Closing: drain, zero-value, and the panic

Gotcha trap

Sending on a closed channel panics, and closing a closed channel panics. The rule that prevents both: only the sole sender closes, exactly once, after all sends. Receivers never close. With multiple senders, coordinate the close (e.g. a separate "done" signal) instead.

06 Check yourself

Two goroutines both send on the same channel; when each finishes it calls close(ch). What happens?

Right. Closing a closed channel panics, just like sending on one. With multiple senders, no single sender owns the close — use a separate done-signal (or a sync.WaitGroup that a coordinator waits on, then it closes) so the channel is closed exactly once.
