The language core · maps

Maps.

A map is Go's hash table — fast key→value lookup with a built-in literal and the v, ok idiom. The two things that bite people: iteration order is deliberately random, and writing to a nil map panics.

01 The idea: map[K]V

A map[K]V maps comparable keys to values. Create one with make(map[K]V) or a composite literal; missing keys read back as the value's zero value.

In plain English analogy

A map is a coat-check. You hand over a ticket (the key) and get back your coat (the value). Hand over a ticket nobody checked a coat for, and instead of an error you get an empty hanger — the zero value. There's no inherent order to the racks, and the attendant rearranges them between visits.

The key type must be comparable (usable with ==): strings, numbers, bools, pointers, and structs of those all work; slices, maps, and funcs do not. The value can be anything.

02 The comma-ok idiom

A plain read m[k] can't tell "absent" from "present but zero". The two-value form v, ok := m[k] reports presence in ok — the canonical way to check membership.

Pro tip idiom

A set is just map[T]struct{} — struct{} is zero-width, so it stores no value bytes. Membership is _, ok := set[x]; add with set[x] = struct{}{}.

03 Iteration order is randomized

range over a map visits keys in a deliberately randomized order — it differs run to run. The runtime does this on purpose so you can't accidentally depend on an order that the hash table never promised.

If you need a stable order, collect the keys, sort them, then range over the sorted slice. The gopad below does exactly that — its output is deterministic because we sorted; a bare range m would print the same pairs in an unpredictable order each run.

See also stdlib

In Go 1.21+ you can skip the make/append boilerplate: slices.Sorted(maps.Keys(m)) returns a sorted slice of the keys in one call (maps.Keys yields an iterator; slices.Sorted drains and sorts it).

04 Reading vs writing a nil map

A nil map (the zero value of a map type, or var m map[K]V) is a readable empty map — but it has no storage, so writing to it panics.

Gotcha trap

Writing to a nil map panics (assignment to entry in nil map). Reading is fine — a lookup returns the zero value and ok is false; len is 0; range does nothing; delete is a no-op. The fix is to make the map (or use a literal) before the first write. This bites most often with a struct field of map type you forgot to initialize.

05 Check yourself

You have var counts map[string]int and run counts["a"]++. What happens?

Right. counts["a"]++ reads the zero value (0) and writes back 1 — and the write is to a nil map, so it panics with "assignment to entry in nil map". Maps never auto-allocate; you must make or use a literal first. (Reading counts["a"] alone would have been safe, returning 0.)
