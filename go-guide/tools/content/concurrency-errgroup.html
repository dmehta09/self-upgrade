Concurrency · structured concurrency

Structured concurrency with errgroup.

Run a batch of goroutines, wait for all of them, surface the first failure, and cancel the rest — in about four lines. errgroup is Go's practical answer to "fan out work, then collect the result or the error" without hand-wiring a WaitGroup, an error channel, and a context yourself.

01 The team lead that waits — and pulls the team back

errgroup.Group launches sibling goroutines, waits for all of them, returns the first non-nil error, and (with WithContext) cancels the rest the moment one fails.

In plain English analogy

Think of a team lead handing out parallel tasks. They stand at the door and won't leave until everyone is back — and the instant one teammate reports a failure, the lead radios the whole team: "stop, come home, we're done here." You get one verdict (the first failure) and nobody is left wandering the building.

That bundle of behaviour — bounded lifetimes, one place that waits, one place that fails — is what people mean by structured concurrency: goroutines that don't outlive the call that started them. Go doesn't have a dedicated language construct for it yet (the topic is recent and evolving), so errgroup from golang.org/x/sync is the idiomatic, battle-tested take.

02 The whole API is three calls

Make a group tied to a context, launch each unit with g.Go(func() error{…}), then block on g.Wait(), which hands you the first error or nil.

g, ctx := errgroup.WithContext(parent)
Make a group whose ctx is cancelled on the first error (or when Wait returns). Pass that ctx into your workers so they can bail.
g.Go(func() error { … })
Run one unit of work in its own goroutine. Returning a non-nil error trips the group.
err := g.Wait()
Block until every g.Go finishes; return the first non-nil error (or nil if all succeeded).
g.SetLimit(n)
Cap concurrency to at most n active goroutines — g.Go blocks until a slot frees. Use it to bound parallel work (e.g. don't open 10 000 sockets at once).

04 Before & after: what errgroup deletes

Hand-rolling the same behaviour means a WaitGroup, a buffered error channel, a manual context.WithCancel, and careful "report only the first error" logic. errgroup collapses all of it.

By hand: WaitGroup + error channel + cancel
ctx, cancel := context.WithCancel(parent)
defer cancel()

var wg sync.WaitGroup
errCh := make(chan error, len(tasks))

for _, t := range tasks {
    wg.Add(1)
    go func() {
        defer wg.Done()
        if err := t.Run(ctx); err != nil {
            errCh <- err
            cancel()        // pull the siblings back
        }
    }()
}
wg.Wait()
close(errCh)

var firstErr error          // dig the first error out
for err := range errCh {
    if firstErr == nil {
        firstErr = err
    }
}
if firstErr != nil {
    return firstErr
}
With errgroup
g, ctx := errgroup.WithContext(parent)

for _, t := range tasks {
    g.Go(func() error {
        return t.Run(ctx) // first non-nil cancels ctx
    })
}
return g.Wait()             // first error, or nil

Same semantics — wait for all, cancel on first failure, surface that failure — but the WaitGroup bookkeeping, the channel sizing, the close, and the "keep only the first error" loop all vanish into the library.

05 The traps

Gotcha trap

Cancellation only works if your workers honour ctx. WithContext cancels the context, but a goroutine busy in a tight loop or a blocking call that ignores ctx keeps running anyway. Pass ctx into every call that accepts one (http.NewRequestWithContext, db.QueryContext, …) or select on <-ctx.Done() — otherwise "cancel the siblings" cancels nothing.

Gotcha trap

Two more sharp edges. (1) g.Wait() returns only the first error — every other goroutine's error is dropped. If you need them all, collect into a slice yourself or wrap with errors.Join. (2) Loop-variable capture: on Go 1.22+ each iteration gets a fresh i/v, so g.Go(func() error { use(v) }) is safe; on Go 1.21 and earlier you must shadow it (v := v) or every goroutine sees the last value.

Pro tip bound it

Unbounded fan-out over a big input will happily spawn thousands of goroutines and exhaust file descriptors or connections. Reach for g.SetLimit(n) to turn the group into a bounded worker pool — it's the simplest semaphore you'll ever write.

06 Where this fits

Inside the language, errgroup sits on top of three things you've already met: a WaitGroup to wait, a context to cancel, and the fan-out / fan-in pattern to structure the work. It just packages them with the right defaults.

07 Check yourself

You run five tasks with errgroup.WithContext. Task 2 returns an error almost immediately; the others are slow time.Sleep loops that never look at the context. What does g.Wait() return, and when?

Right. Wait blocks until all g.Go functions return; it can't forcibly kill a goroutine. The context is cancelled on task 2's failure, but a worker that never checks <-ctx.Done() runs to completion regardless — so you wait for the slowest one and then get the first error (task 2's). That's exactly why "honour ctx in your workers" is the headline gotcha.
