Concurrency · patterns

Patterns: pool, fan-in/out, pipeline, semaphore.

Channels and goroutines are the primitives; these four patterns are how real Go programs use them. Once you can recognize a worker pool, a fan-out/fan-in, a pipeline, and a semaphore, most concurrent Go reads like prose — and most interview questions become "pick the pattern, then wire the channels."

01 Worker pool: N goroutines on one jobs channel

A worker pool is one jobs channel feeding a fixed number of worker goroutines, plus a results channel coming back. You cap concurrency by choosing how many workers to start — not by how much work arrives.

In plain English analogy

Picture a bank with one queue of tickets and a fixed line of three clerks. Customers (jobs) take a numbered ticket and wait; whichever clerk is free calls the next ticket. You never have more than three customers being served at once, no matter how long the queue gets — that's your concurrency cap. When the "now serving" sign goes dark (the jobs channel closes), each clerk finishes their current customer, then goes home.

Every worker runs the same loop: for job := range jobs. Closing jobs ends all of those loops cleanly. A sync.WaitGroup lets a coordinator know when the last worker has returned, so it can safely close results.

pool.go
func worker(jobs <-chan int, results chan<- int, wg *sync.WaitGroup) {
    defer wg.Done()
    for j := range jobs {        // ends when jobs is closed & drained
        results <- j * j
    }
}

func main() {
    jobs := make(chan int, 6)
    results := make(chan int, 6)
    var wg sync.WaitGroup

    for w := 0; w < 3; w++ {      // start a FIXED 3 workers
        wg.Add(1)
        go worker(jobs, results, &wg)
    }
    for j := 1; j <= 6; j++ {     // feed the queue
        jobs <- j
    }
    close(jobs)                  // tells every worker "no more work"

    go func() { wg.Wait(); close(results) }() // coordinator closes results
    for r := range results {     // drain until results is closed
        _ = r
    }
}

Note the two distinct closes and who owns each: the producer closes jobs (it is the sole sender); a small coordinator goroutine closes results after wg.Wait(), because no single worker knows it is the last one done.

02 Fan-out / fan-in: spread work, then merge

Fan-out = many goroutines receiving from one channel (several workers share the same jobs source). Fan-in = one goroutine merging many result channels into one. They are mirror images, and you usually use them together.

Multiple receivers on one channel is automatic load-balancing: whichever worker is idle grabs the next value. The runtime hands each sent value to exactly one receiver, so no two workers process the same job.

For fan-in, give each worker its own output channel (or share one — sharing is simpler), then a merge goroutine reads them all into a single channel. With a shared output channel the merge is implicit; with per-worker channels you spin up a goroutine per input and a WaitGroup to close the merged channel once:

fanin.go
// merge fans IN: many <-chan int into one.
func merge(ins ...<-chan int) <-chan int {
    out := make(chan int)
    var wg sync.WaitGroup
    for _, in := range ins {     // per-iteration loop var (Go 1.22) — safe to capture
        wg.Add(1)
        go func() {
            defer wg.Done()
            for v := range in {  // copy this input into the merged stream
                out <- v
            }
        }()
    }
    go func() { wg.Wait(); close(out) }() // close ONCE, after all inputs drain
    return out
}

03 Pipeline: stages joined by channels

A pipeline is a chain of stages where each stage is func(in <-chan T) <-chan U: it ranges its input, sends transformed values to its own output channel, and closes that output when the input is exhausted.

In plain English analogy

Think of an assembly line: one station washes, the next paints, the next packs. Each station takes a part off the belt coming in, does its one job, and puts the result on the belt going out. When the incoming belt stops (channel closed), the station turns off its own outgoing belt and clocks out. Every stage is its own goroutine, so all stations run at the same time on different parts.

pipeline.go
func gen(nums ...int) <-chan int {        // source stage
    out := make(chan int)
    go func() {
        defer close(out)
        for _, n := range nums {
            out <- n
        }
    }()
    return out
}

func square(in <-chan int) <-chan int {   // transform stage
    out := make(chan int)
    go func() {
        defer close(out)                  // close MY output when MY input ends
        for n := range in {
            out <- n * n
        }
    }()
    return out
}

// wire stages: gen -> square -> consume
for v := range square(gen(2, 3, 4)) { fmt.Println(v) } // 4, 9, 16

Each stage owns exactly one channel — its output — and is the sole closer of it. Closing cascades naturally: when gen closes its output, square's range ends, so square closes its output, so the consumer's range ends. The <-chan int return type makes outputs receive-only, so the compiler stops a downstream stage from accidentally sending or closing upstream's channel.

04 Semaphore: a buffered channel as a token bucket

When you can't use a fixed pool — say you must launch one goroutine per item but still cap how many run at once — use a buffered channel of size N as a semaphore: acquire a token (send) before the work, release it (receive) after. At most N tokens exist, so at most N goroutines run.

In plain English analogy

It's a parking lot with N spaces and a gate. To enter you must grab a parking pass; if all N passes are out, you wait at the gate. When you leave, you drop your pass back and the next car can take it. The lot never holds more than N cars — that's your concurrency cap, enforced by a bucket of exactly N passes.

sem.go
sem := make(chan struct{}, 3)   // bucket of 3 tokens (zero-size = free)
var wg sync.WaitGroup
for _, url := range urls {
    wg.Add(1)
    go func() {
        defer wg.Done()
        sem <- struct{}{}        // ACQUIRE: blocks if 3 are already running
        defer func() { <-sem }() // RELEASE on the way out
        fetch(url)              // at most 3 of these run at once
    }()
}
wg.Wait()

The token type is struct{} — an empty struct costs zero bytes, so a semaphore channel carries no real payload, only the count. (For a richer version with context cancellation, the golang.org/x/sync/semaphore package offers a weighted semaphore.)

05 The traps: who closes, leaked workers, unbounded fan-out

Gotcha trap

Who closes a channel with multiple senders? In fan-out, many workers send on the shared results channel — so no worker may close it (a second close, or a send after close, panics). The rule: only the coordinator closes, exactly once, after a WaitGroup confirms every sender is done (go func(){ wg.Wait(); close(results) }()). Receivers never close.

Gotcha trap

Leaked workers. Two classic leaks: (1) you never close(jobs), so every worker's for range jobs blocks forever waiting for a value that never comes — goroutines pile up. (2) You stop draining results early (e.g. you break on the first answer), so workers block forever on results <- v. Fix: always close the source, and either drain fully or give workers a cancellable exit (a ctx.Done() case in a select).

Gotcha trap

Unbounded fan-out. for _, x := range millions { go work(x) } launches a goroutine per item with no cap — exhausting memory, file descriptors, or the remote service you're hammering. A worker pool (fixed N) or a semaphore (token bucket of N) bounds it. "go in a loop with no limit" is the single most common production concurrency bug.

See also sibling guide

07 Check yourself

In a fan-out, five workers each send results on a shared results channel. To close results safely, who closes it and when?

Right. With multiple senders, no worker owns the close — the first worker to close would make the others panic on their next send (send-on-closed), and a second close panics too. The fix is the standard idiom: go func(){ wg.Wait(); close(results) }(). And never the consumer (a receiver) — closing is the sender's job.
