Generics · the generic stdlib

slices, maps, cmp & the builtins.

Generics didn't just land a language feature in Go 1.18 — in Go 1.21 they paid off with slices, maps and cmp: type-safe, reusable helpers that replace a decade of hand-rolled loops. Plus three new universe builtins: min, max, clear.

01 One toolbox for every slice and map

The slices and maps packages (Go 1.21) are generic — written once with type parameters, they work on []T and map[K]V for any element type, fully type-checked.

In plain English analogy

For years everyone carried their own pocketknife: a hand-written contains(), a fresh indexOf(), a copy-pasted sort. Go 1.21 handed out a standard multi-tool — slices.Contains, slices.Index, slices.Sort — that fits every slice you own. Same tool, any blade size, no whittling your own.

The headline helpers, by package:

slices
Sort, SortFunc, Contains, Index, BinarySearch, Equal, Insert, Delete, Clone, Compact, Max, Min — operate on any []T.
maps
Keys, Values (iterators since 1.23), Clone, Equal, DeleteFunc — operate on any map[K]V.
cmp
Compare, Less, Or, and the Ordered constraint — the comparison glue the others build on.

02 Sorting: slices.Sort & cmp.Compare

slices.Sort(s) sorts in place for any cmp.Ordered element. For structs (no built-in ordering), use slices.SortFunc with a comparator that returns negative / zero / positive — exactly what cmp.Compare gives you.

A comparator is "how do a and b rank?": return <0 if a comes first, 0 if equal, >0 if b comes first. cmp.Compare(a.Age, b.Age) produces precisely that — no hand-written if ladder, and no overflow risk from a.Age - b.Age.

Pro tip tie-breaks

Need a secondary sort key? cmp.Or returns the first non-zero of its arguments — so cmp.Or(cmp.Compare(a.Age, b.Age), cmp.Compare(a.Name, b.Name)) sorts by age, then by name for ties, in one readable line.

03 The universe builtins: min, max, clear

Go 1.21 added three predeclared functions — no import. min/max take two or more ordered args; clear empties a container — but it does different things to a map vs a slice.

  • min(a, b, …) / max(a, b, …) — variadic, any cmp.Ordered type. max(3, 7, 1) → 7.
  • clear(m) on a map — deletes every key; afterwards len(m) == 0.
  • clear(s) on a slice — zeroes every element in place; len(s) is unchanged.

04 Clone is shallow · Keys/Values return iterators

slices.Clone and maps.Clone make a shallow copy: a new top-level array/map, but inner pointers and sub-slices are shared. And since Go 1.23, maps.Keys/maps.Values return an iter.Seq, not a slice.

slices.Clone(s) gives you a fresh backing array — appends to the clone no longer touch the original, fixing the classic re-slice aliasing bug. But if s is []*User or [][]int, both copies still point at the same inner data; mutating clone[0].Name shows up in the original.

See also aliasing

"Shallow" is the same sharing you met with re-slices. If the distinction between a new header and a shared backing array is fuzzy, revisit Arrays vs slices: the len/cap model — slices.Clone is the clean fix for that lesson's #1 bug.

About maps.Keys: in Go 1.23 it returns iter.Seq[K] — a range-able sequence, not a []K. You usually for k := range maps.Keys(m), or materialize a slice with slices.Sorted(maps.Keys(m)) for deterministic output (map order is random!).

keys.go
m := map[string]int{"b": 2, "a": 1, "c": 3}

// maps.Keys(m) is an iter.Seq[string], not a []string.
// Sort it into a slice for stable, deterministic order:
keys := slices.Sorted(maps.Keys(m)) // []string{"a","b","c"}

for _, k := range keys {
    fmt.Println(k, m[k])
}
See also iterators

What is an iter.Seq, and how does range drive a function? That's the range-over-func machinery from Go 1.23 — see Range-over-func iterators.

05 The traps

Gotcha trap

slices.Sort requires cmp.Ordered elements — call it on a []Person and it won't compile. For any type without built-in ordering (structs, or "by a non-default key"), reach for slices.SortFunc with a comparator. And don't confuse the two clears: on a slice it zeroes elements but keeps len; on a map it deletes all keys.

  • The comparator's contract is sign, not boolean. SortFunc's func returns an int (neg/zero/pos), not a bool like the old sort.Slice less-func. Returning a bool is a common porting bug.
  • slices.BinarySearch assumes the slice is already sorted ascending. On an unsorted slice the result is meaningless — sort first.
  • slices.Compact only removes consecutive duplicates. To dedupe fully, Sort then Compact.

06 Check yourself

You have s := []int{1, 2, 3} and call clear(s). What is s and its length afterward?

Right. clear is overloaded by container kind. On a map it deletes every key (length → 0). On a slice it writes the zero value to every element in [0:len) and leaves len untouched — so [1 2 3] becomes [0 0 0], still length 3. Mixing these up is the classic clear trap.
