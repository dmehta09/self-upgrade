Testing & tooling · fuzzing & coverage

Fuzzing, coverage & race testing.

Unit tests check the inputs you thought of. Three built-in tools push past that: fuzzing invents inputs you didn't, coverage shows what your tests never touched, and the race detector catches data races at runtime. All ship with go test — no third-party libraries.

01 Native fuzzing: let the machine find the input

A fuzz test is func FuzzXxx(f *testing.F). You add seed inputs with f.Add, then f.Fuzz(func(t, in){...}) runs your assertion on the seeds — and, under -fuzz, on millions of mutated inputs the engine generates.

In plain English analogy

A unit test is you knocking on the front door to check the lock works. Fuzzing is hiring a thousand toddlers to mash every key, kick the frame, and post pizza menus through the slot until something breaks. You don't write the weird inputs — the fuzzer breeds them, keeping the ones that reach new code paths and mutating from there.

The standout fuzz targets are round-trip invariants: anything that parses then formats (or encodes then decodes) should return what it started with. You assert the property, not a specific output, so one tiny test guards an infinite input space.

The same logic written as a real fuzz target — this is the shape the verifier and CI run with -fuzz:

roundtrip_test.go
func FuzzRoundTrip(f *testing.F) {
    f.Add(42)          // seed corpus: a few known-interesting inputs
    f.Add(-2147483648)
    f.Fuzz(func(t *testing.T, n int) {
        s := strconv.Itoa(n)
        got, err := strconv.Atoi(s)
        if err != nil {
            t.Fatalf("Atoi(%q): %v", s, err)
        }
        if got != n {
            t.Errorf("round-trip: got %d, want %d", got, n) // invariant!
        }
    })
}
Pro tip where it lands

Run a target with go test -fuzz=FuzzRoundTrip -fuzztime=30s. Without -fuzz, a Fuzz test just runs the seed corpus like a normal test — so fuzz targets are safe to keep in CI as fast regression checks.

02 When it breaks, the input is saved for you

The first time a fuzz target fails, Go writes the exact failing input to testdata/fuzz/FuzzXxx/ and adds it to the corpus. That file is a permanent, replayable regression test — commit it.

From then on, plain go test (no -fuzz) replays every saved corpus entry. A bug the fuzzer found once can never silently come back: the crashing input is now part of your suite. The supported flow is a tight loop:

terminal
# explore for inputs that break the invariant
$ go test -fuzz=FuzzRoundTrip -fuzztime=20s

--- FAIL: FuzzRoundTrip (0.03s)
    failing input written to testdata/fuzz/FuzzRoundTrip/a1b2c3...

# fix the bug, then replay the saved corpus forever (no -fuzz needed)
$ go test ./...
ok   example/codec   0.012s
See also recent Go

For concurrent code, Go 1.25's testing/synctest runs a goroutine "bubble" against a fake clock: timers and time.Sleep advance instantly and deterministically, so a test for a 5-second timeout finishes in microseconds with no flakiness. It pairs naturally with the race detector below.

03 Coverage: see what your tests never ran

go test -cover prints a percentage; -coverprofile=c.out records which lines ran, and go tool cover -html=c.out paints them green (covered) or red (never executed) in your browser.

terminal
$ go test -cover ./...
ok   example/codec   0.011s   coverage: 78.4% of statements

# record a profile, then open the annotated source map
$ go test -coverprofile=cover.out ./...
$ go tool cover -html=cover.out          # red = untested lines
$ go tool cover -func=cover.out          # per-function summary
Gotcha trap

Coverage % is not correctness. A line that ran isn't a line you asserted anything about — you can hit 100% with tests that check nothing. Use coverage to find the red (untested branches you forgot), never as a quality score to chase. The interview tell: "we mandate 90% coverage" buys far less than "we fuzz the parser and assert invariants."

04 The race detector: go test -race

-race instruments memory accesses and reports any two goroutines that touch the same memory concurrently with at least one write and no synchronisation. Run it in CI — a clean -race run is the cheapest concurrency insurance Go offers.

In plain English analogy

It's a CCTV that watches every shared variable. The moment two workers reach for the same shelf at once and one of them is restocking, the camera flags exactly who, where, and in what order. It doesn't predict races — it catches them red-handed when your test happens to trigger one.

Gotcha trap

-race only catches races that actually execute. It's a dynamic detector — if your test never schedules the two goroutines to collide, it stays silent, even with the bug present. So write tests that exercise concurrency (loops, many goroutines, t.Parallel()), run them under -race repeatedly in CI, and never assume "no report" means "no race."

05 Check yourself

Your CI shows 92% coverage and a clean go test -race ./.... A teammate says "so the concurrent cache is definitely race-free." What's the precise problem with that claim?

Right. The race detector is a dynamic tool: it flags only conflicts that the test schedule actually produced. High line-coverage doesn't imply you exercised the interleaving that triggers the race. The fix is to stress the concurrent paths (many goroutines, parallel subtests, repeated runs) under -race — and remember coverage % is about execution, never correctness.
