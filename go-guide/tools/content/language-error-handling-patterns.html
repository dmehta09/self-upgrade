The language core · errors

Error handling, the senior way.

Returning errors is easy; handling them well is a craft. The senior moves: wrap with context instead of swallowing, match with errors.Is/As not ==, and handle each error exactly once.

01 Add context with %w

Wrap an error with fmt.Errorf("doing X: %w", err) to add context while preserving the original. The %w verb keeps the cause reachable; plain %v would flatten it to a string and lose it.

In plain English analogy

An error travelling up the stack is a parcel. Each layer that re-throws it should add a routing label — "couldn't load config: …", "couldn't open file: …" — without tearing off the labels beneath. %w staples a new label on top; the original receipt is still inside the box, so a caller upstream can read it.

The result is an error chain: load config: open users.json: not found. Each layer says what it was doing, and the leaf says what actually went wrong.

load.go
func loadConfig(path string) error {
    f, err := os.Open(path)
    if err != nil {
        return fmt.Errorf("load config %q: %w", path, err) // wrap, keep cause
    }
    defer f.Close()
    // …
    return nil
}

02 Sentinel vs typed: errors.Is & errors.As

Two flavors of "what kind of error is this?" A sentinel is a known value — match it with errors.Is(err, ErrNotFound). A typed error carries data — extract it with errors.As(err, &myErr). Both walk the %w chain.

errors.Is
Compares against a sentinel value (io.EOF, sql.ErrNoRows, your ErrNotFound). True if that value appears anywhere in the chain.
errors.As
Finds the first error in the chain that is a given type and assigns it to your pointer, so you can read its fields (e.g. an HTTP status, a path).

03 Wrap, annotate, or return raw?

Not every error needs %w. Wrap when callers may match the cause; annotate (with %v) when the cause is an internal detail you don't want exposed; return raw when you'd add nothing.

Pro tip message hygiene

Error strings are lowercase and don't end with punctuation, because they get composed: "load config: open file: not found" reads cleanly only if no fragment shouts or adds a period. (go vet's errorf/ST1005 checks enforce this.)

04 Handle once · errors.Join for many

Handle an error exactly once. The classic anti-pattern is log-and-return — you log it and hand it up, so it gets logged again at every layer. Either handle it here (log/recover) or return it with context — not both.

Gotcha trap

Comparing errors with == instead of errors.Is silently breaks the moment someone wraps the error — err == ErrNotFound is false for fmt.Errorf("…: %w", ErrNotFound), because the top of the chain is a different value. Worse is matching on err.Error() strings: a reworded message breaks your code with no compiler warning. Always match by value with errors.Is or by type with errors.As.

05 Check yourself

A function returns fmt.Errorf("query: %w", sql.ErrNoRows). A caller checks if err == sql.ErrNoRows. What's the result, and the fix?

Right. == compares the top-level error value, and fmt.Errorf returns a brand-new *wrapError — not sql.ErrNoRows — so the check is false and the no-rows case is missed. errors.Is walks the %w chain and finds the sentinel. Never compare wrapped errors with ==, and never match on err.Error() text.
