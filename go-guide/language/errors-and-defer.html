The language core · errors & defer

Errors, defer, panic & recover.

Go has no exceptions for ordinary failure. Errors are plain values you return and check; defer guarantees cleanup; panic/recover are the rare escape hatch. Here's how they fit together.

01 Errors are values

A function that can fail returns an error as its last result. You check it with if err != nil — no try/catch, no hidden control flow.

In plain English analogy

An exception is a fire alarm that yanks you out of the building from anywhere. A Go error is a note handed back at each step: “here's your result, and here's whether it went wrong.” You read the note before moving on — the failure path is right there in the code, not teleporting up the stack.

Wrap errors with %w to add context while preserving the original, then test the chain with errors.Is (sentinel match) or errors.As (typed match).

02 defer: cleanup you can't forget

defer schedules a call to run when the surrounding function returns — in LIFO order. It's how Go does “close this no matter how we leave.”

The classic use is pairing acquire/release on adjacent lines, so the release can't be lost down some early-return path:

read.go
f, err := os.Open(name)
if err != nil {
    return err
}
defer f.Close()        // runs on every return path below
// … use f, return early if you like …

03 defer evaluates its arguments now

Gotcha trap

A deferred call's arguments are evaluated when defer runs, not when the call fires. So defer fmt.Println(i) captures i's value now. (To capture the final value, defer a closure: defer func(){ fmt.Println(i) }().) Also beware defer in a loop — they all stack up until the function returns.

04 panic & recover

panic unwinds the stack, running deferred calls as it goes; a recover() inside a deferred function stops the unwind and lets the function return normally. Use it sparingly — at process boundaries, not for ordinary errors.

05 Check yourself

Where must recover() be called to actually stop a panic?

Right. recover only does something when called directly by a deferred function during unwinding, in the same goroutine that panicked. Called anywhere else it returns nil and does nothing — which is why an unrecovered panic in another goroutine still crashes the program.
