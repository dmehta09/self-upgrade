Concurrency · select

select: wait on many channels at once.

A single channel handles one conversation. Real programs juggle several — work arriving, a timeout ticking, a cancellation request, a result coming back. select is Go's way to block on all of them together and wake up on whichever fires first. It's the heart of every timeout, every cancel, every multiplexer you'll write.

01 One statement, many channels

A select blocks until one of its case channel operations can proceed, runs that one case, and ignores the rest. It's a switch whose conditions are channel readiness, not boolean expressions.

In plain English analogy

A select is a receptionist watching several phone lines. They sit still while every line is silent — doing nothing, blocked. The moment a line rings they pick up that line and handle the call. They don't poll each phone in turn; they wait on all of them at once and respond to whichever rings first. When the call's done, they loop back and wait again.

Each case is a send (case ch <- v:) or a receive (case v := <-ch:). The runtime parks the goroutine until exactly one of those operations becomes possible, then commits to it. No busy-waiting, no CPU spin — the scheduler wakes you precisely when there's something to do.

multiplex.go
for {
    select {
    case job := <-jobs:        // a job is ready to receive
        process(job)
    case res := <-results:     // OR a result came back
        report(res)
    case <-quit:               // OR someone asked us to stop
        return
    }
}

02 If several are ready, Go picks at random

Block until one case is ready, sure — but what if two or three are ready at the same instant? Go does not prefer the first case listed. It chooses uniformly at random among the ready cases.

When multiple cases are ready, select picks one pseudo-randomly — a deliberate fairness rule that prevents starvation. A hot channel listed first can never permanently crowd out the others.

Gotcha trap

Do not assume case order encodes priority. Both of these read identically to the runtime — a fast producer on a will not block b, and you cannot make it by listing a first. If you genuinely need priority (drain high before low), you must build it: a nested select where the inner one has a default, checked before the outer blocking select.

Myth: order = priority
select {
case v := <-a:   // NOT "checked first"
    use(v)
case v := <-b:   // both equally likely
    use(v)
}
// if a AND b ready → 50/50, every time
Real priority: try high first
select {
case v := <-high:   // prefer high…
    use(v)
default:            // …only if it's ready right now
    select {        // else block on either
    case v := <-high:
        use(v)
    case v := <-low:
        use(v)
    }
}

04 default, timeouts, and cancellation

Three patterns turn select from "block on channels" into the everyday tool you'll reach for constantly.

① default makes it non-blocking. If no case is ready, a default runs immediately instead of parking — a try-send / try-receive that never waits:

trysend.go
select {
case ch <- v:
    // sent
default:
    // buffer full / no receiver — drop or handle, don't block
}

② Timeouts with time.After — a channel that delivers one value after the duration, so it becomes "ready" only once time is up:

timeout.go
select {
case res := <-work:
    return res, nil
case <-time.After(2 * time.Second):
    return zero, errors.New("timed out")
}

③ Cancellation — the idiomatic case <-ctx.Done():. ctx.Done() is a channel that closes when the context is cancelled or its deadline passes; a closed channel is always ready, so the case fires the instant cancellation happens:

cancel.go
select {
case res := <-work:
    return res, nil
case <-ctx.Done():
    return zero, ctx.Err()   // context.Canceled or DeadlineExceeded
}
See also cancellation

Prefer <-ctx.Done() over a bare time.After when the deadline belongs to the whole request: it cancels the entire goroutine tree, not just this one wait, and a stale time.After timer leaks until it fires. Full story in context: cancellation, deadlines & values.

05 The nil-channel trick: switching cases on and off

A nil channel blocks forever on both send and receive — so a case whose channel is nil is permanently not ready and effectively disabled. Set a channel variable to nil to switch its case off; restore it to switch it back on.

This is the clean way to drive a state machine inside for { select { … } }. The classic use: a merge that should stop selecting on an input once that input closes, without spinning.

merge.go
for a != nil || b != nil {        // loop until BOTH are disabled
    select {
    case v, ok := <-a:
        if !ok {
            a = nil               // a is drained → disable its case
            continue
        }
        out <- v
    case v, ok := <-b:
        if !ok {
            b = nil               // disable b's case the same way
            continue
        }
        out <- v
    }
}

Without the trick, a closed channel is always ready and yields the zero value instantly — so a naive merge would busy-spin, slamming the CPU as it receives 0, false millions of times. Nilling the variable parks that case for good.

Gotcha trap

Two opposite ways to wedge a select. (1) A select whose every case channel is nil and that has no default blocks forever — an instant deadlock (the runtime even reports "all goroutines are asleep" if nothing else runs). (2) Putting a default inside a tight for { select { … } } turns a blocking wait into a busy-spin: with nothing ready, default fires every iteration and burns 100% of a core. Use default for a genuine one-shot try, almost never inside a spin loop.

07 Check yourself

Inside a for loop, you write select { case v := <-in: use(v); default: }. Channel in receives a value about once a second. What's the behavior?

Right. The default makes the select non-blocking, so when in is empty (almost always, between the one-per-second arrivals) the loop spins flat-out and burns CPU. Drop the default to let the select block until in is ready — that's the whole point of select. Reserve default for a true one-shot "try, then move on", not a tight loop.

Both a and b have a value ready when main reaches select { case <-a: …; case <-b: … }. Which case runs?

Right. When several cases are ready, Go picks one uniformly at random — this fairness rule prevents a perpetually-ready channel from starving the others. Case order is not priority, and a select only ever runs one case per execution.
