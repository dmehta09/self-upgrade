Concurrency · the runtime scheduler

The G-M-P scheduler.

A Go program can have a million goroutines and still run on a handful of OS threads. The trick is a small, elegant scheduler with three moving parts — G, M, and P — that keeps every CPU busy and never blocks a whole thread waiting on one goroutine.

01 A million workers, a handful of desks

Goroutines are cheap (a few KB of stack, grown on demand) and managed entirely in user space. The runtime multiplexes many goroutines onto a few OS threads — so creating 100,000 of them is normal, not reckless.

In plain English analogy

Imagine an office with thousands of tasks but only as many desks as you have CPU cores. A desk (a P) holds one worker (an M, an OS thread) doing one task (a G, a goroutine) at a time. When a task stops to wait — say, for a phone call — the worker doesn't sit idle at the desk; the task steps aside and the next task takes the desk. That hand-off, done thousands of times a second, is the scheduler.

02 G, M, P — the three letters

The whole model is three structures and the rules connecting them:

G — goroutine
A unit of work: its stack, instruction pointer, and state. Cheap to create; there can be millions.
M — machine
An OS thread. The thing the kernel actually schedules onto a core. Expensive; there are few.
P — processor
A scheduling context — the right to run Go code. Each P has a local run queue of ready Gs. GOMAXPROCS sets how many Ps exist (default = CPU cores).

To run Go code you need the triple G on M holding P. The number of Ps caps how many goroutines run truly in parallel; the number of Ms can briefly exceed it (e.g. threads stuck in syscalls).

Ready goroutines wait in queues: each P has a fast local run queue, and there's one shared global run queue for overflow and freshly-woken Gs. When a P's local queue runs dry, it doesn't idle — it goes looking for work.

04 Blocking syscalls: handing off the P

When a goroutine makes a blocking syscall (a disk read, a DNS lookup), its thread M blocks in the kernel with it. The runtime detaches the P and gives it to another thread, so the other queued goroutines keep running.

This is the key difference from a naive thread pool: one goroutine doing slow I/O can't stall the others, because the P (the right to run Go code) is handed to a fresh M while the old M waits in the kernel. When the syscall returns, its goroutine needs a P again — grabbing one if free, otherwise going to the global queue.

Preemption since 1.14

A goroutine that never blocks (a tight CPU loop) used to be able to hog its P. Since Go 1.14 the scheduler is asynchronously preemptible — the runtime can interrupt a long-running G at almost any instruction, so one busy goroutine can't starve the rest.

05 GOMAXPROCS & fairness

runtime.GOMAXPROCS(n) (or the GOMAXPROCS env var) sets the number of Ps — the ceiling on parallelism. The default is the number of CPUs the process can use.

Gotcha containers

In a container with a CPU limit (say 2 cores) on a 64-core host, older Go versions set GOMAXPROCS to 64 — spawning far too many Ps, causing throttling and latency spikes. Go 1.25 made the runtime container-aware: it reads the cgroup CPU quota and sizes GOMAXPROCS to the limit automatically. On older versions, set it yourself (or use automaxprocs).

More goroutines than Ps is fine and normal — they take turns. More Ps than you have cores rarely helps and often hurts (context-switch and cache thrash). Leave it at the default unless a benchmark says otherwise.

06 Check yourself

A goroutine calls a blocking syscall that takes 50 ms. What happens to the other ready goroutines that were queued on the same P?

Right. The blocking M stays in the kernel with its goroutine, but its P is handed to another (possibly new) M so the remaining ready goroutines run without delay. That P-handoff is exactly why slow I/O in one goroutine doesn't freeze the others.
