Concurrency · context

context: cancellation, deadlines & values.

A request comes in, fans out to a database, a cache, and two other services — then the client hangs up. How does all that work stop, promptly, without leaking goroutines? That's context: a stop-work order that flows down the call tree.

01 The problem it solves

A context.Context carries a cancellation signal and a deadline down through every API boundary and goroutine it touches, so a whole tree of work can be told to stop at once.

In plain English analogy

A context is a stop-work order that flows down the org chart. The CEO (the incoming request) hands it to a VP, who hands copies to managers, who hand copies to everyone doing the actual work. When the order is cancelled — the customer left, or the clock ran out — it propagates down every branch at once. Each worker is responsible for watching their copy and downing tools when it fires. The order only ever flows downward; a worker can't cancel the CEO.

Without it, a cancelled request leaves goroutines blocked on a slow database forever — a classic leak. With it, every layer watches ctx.Done() and bails the moment the signal arrives.

02 The constructors & the Done channel

You start from a root (Background / TODO) and derive children that add cancellation or a deadline. Each derive returns a cancel func; watch <-ctx.Done() and read ctx.Err() to learn why it closed.

context.Background()
The empty root. Use it at the top of main, in tests, and in the inbound request of a server.
context.TODO()
A placeholder for "I haven't wired a real context here yet." Identical behaviour to Background; signals intent to the reader (and to linters).
WithCancel(parent)
Returns (ctx, cancel). Calling cancel() closes ctx.Done(); ctx.Err() is then context.Canceled.
WithTimeout(parent, d)
Cancels automatically after duration d (sugar for WithDeadline(parent, now+d)). On expiry ctx.Err() is context.DeadlineExceeded.
WithDeadline(parent, t)
Cancels at an absolute time t. Same DeadlineExceeded error on expiry.
WithValue(parent, k, v)
Derives a context carrying one request-scoped key/value. Read it back with ctx.Value(k).

The two things you read off a context: <-ctx.Done() (a channel that closes when cancelled — so a receive unblocks) and ctx.Err() (nil while live, then Canceled or DeadlineExceeded).

See also recent additions

Go 1.21 added two useful tools: context.WithoutCancel(parent) — a child that keeps the parent's values but ignores its cancellation (for fire-and-forget cleanup after a request ends), and context.AfterFunc(ctx, f) — register f to run in its own goroutine once ctx is done, no manual <-ctx.Done() loop needed.

04 The rules (and the trap)

Pass context as the first parameter, named ctx. Never store it in a struct. Always call cancel(), even on the timeout path. Use WithValue only for request-scoped data — never for optional arguments.

Don't

Store a context in a struct field; pass it second or buried in options; use ctx.Value as a grab-bag for config and tunables; skip cancel() because "the timeout will handle it."

Do

Make ctx context.Context the first param of any function that does I/O or blocks. defer cancel() immediately after deriving. Put only request-scoped values (request ID, auth principal) in WithValue, behind a typed key.

Gotcha trap

Forgetting cancel() leaks the context (G15): WithCancel/WithTimeout attach a child to the parent and arm a timer; until you cancel, that goroutine/timer stays alive even after the deadline passes. go vet warns: "the cancel function returned by context.WithTimeout should be called, not discarded." Two more traps: passing a nil context (pass context.TODO() instead) panics deep inside callees; and using WithValue as a grab-bag for things that should be explicit parameters — it hides dependencies and is unchecked at compile time.

05 Check yourself

You write ctx, cancel := context.WithTimeout(parent, 5*time.Second) and your work finishes in 50 ms. Do you still need cancel()?

Right. cancel() releases the context's resources now instead of when the deadline eventually trips. Skip it and you leak a timer and a child node on the parent for up to five seconds — multiply that across a busy server and you have a real leak. The idiom is to defer cancel() on the line right after deriving, which is why go vet flags a discarded cancel.
