Concurrency · debugging the failures

Goroutine leaks, deadlocks & the race detector.

Concurrency that works is half the job; the capstone skill is debugging concurrency that breaks. Three failure families cause nearly every Go concurrency bug — a goroutine that can never exit (leak), every goroutine stuck waiting (deadlock), and unsynchronised access to shared memory (data race). Learn to spot each one and the tools that catch them.

01 Goroutine leaks: started, never finished

A goroutine blocked forever — on a channel nobody will send to, or a receiver that already left — is never collected. It pins its stack and everything it captured, so leaks show up as slow memory and goroutine-count growth, not a crash.

In plain English analogy

You send a waiter to fetch a dish from a kitchen that's already closed. They stand at the hatch forever, waiting for a plate that will never come. They don't error, they don't go home — they just occupy a spot. Start a thousand such waiters and the restaurant fills with people frozen mid-wait. That's a goroutine leak: not a crash, just quiet accumulation.

The GC can't help: a blocked goroutine is, by definition, still reachable work. The classic shape is launching a producer onto an unbuffered channel, then returning early (timeout, error, first-result-wins) so nobody ever receives:

leak.go
func leaky() int {
    ch := make(chan int)          // unbuffered
    go func() { ch <- expensive() }()  // send blocks until someone receives
    return 0                      // we return WITHOUT receiving — the goroutine is stuck on the send forever
}

The fix is a rule, not a trick: every goroutine must have a guaranteed way to exit. Give it a done / ctx.Done() channel to abandon the send, a buffered channel so the send never blocks, or an input that is eventually closed. Spot leaks at runtime with runtime.NumGoroutine() trending upward, or capture a goroutine profile (pprof) and read which line N goroutines are all parked on.

See also note

The goroutine profile that pinpoints a leak — "N goroutines blocked at chan send, file:line" — is covered in Profiling with pprof.

03 Deadlocks: everyone waiting on everyone

A deadlock is when every goroutine is blocked, each waiting on a condition only another blocked goroutine could satisfy. If all goroutines are asleep, the runtime aborts with fatal error: all goroutines are asleep - deadlock!

In plain English analogy

Two people meet in a narrow doorway, each holding a gift the other wants. "I'll hand you mine once you hand me yours." "No, you first." Neither moves. They'll stand there until the building closes — each one's progress depends on the other already having moved. That's a lock-ordering deadlock: a cycle of waits with no one able to take the first step.

The three classic causes — and their one-line fixes:

CauseWhat happensFix
Unbuffered send, no receiverch <- v blocks because nothing is reading; if it's the only goroutine, the runtime calls it.Buffer the channel, or guarantee a receiver runs concurrently.
Lock-ordering (the deadly embrace)G1 locks A then wants B; G2 locks B then wants A. Each holds what the other needs.Always acquire multiple locks in a single global order.
WaitGroup never reaches zerowg.Wait() blocks forever because a Done() was missed (early return, panic, wrong Add count).defer wg.Done() at the top of every worker; or use wg.Go() (Go 1.25).

04 Data races & the race detector

A data race is two goroutines touching the same memory concurrently with at least one write and no synchronisation. The behaviour is undefined. Go's answer is -race: go test -race / go run -race instruments every memory access and prints the conflicting goroutines with their stacks.

In plain English analogy

The race detector is a security camera wired to every shared variable. It can't predict trouble, but the moment two goroutines reach for the same memory without taking turns, it freezes the frame and shows you both hands — "this write at line 12, that read at line 19, and no lock between them." It only catches what actually happened on camera, so you have to make the bad scene play out.

Read it top-down: a write by goroutine 8 conflicts with a previous read by goroutine 7 at the same address and the same line (count++), with nothing synchronising them. The fix is always real synchronisation — a sync.Mutex, an atomic.Int64, or a channel that hands ownership across. Never paper over a race with time.Sleep: it changes the timing, hides the report, and leaves the bug.

Gotcha trap

Three traps in one. (1) -race is for tests, not production — it adds large CPU and memory overhead (roughly 5–10× / 5–10×); never ship a -race binary. (2) A green -race run does not prove the code is race-free — the detector only sees races that actually execute, so a rare interleaving stays hidden until it doesn't. Run it in CI under realistic load and concurrency. (3) Deadlock detection only fires when ALL goroutines block; a partial deadlock (two stuck, the rest fine) just hangs with no fatal error.

05 Check yourself

Your service's memory and runtime.NumGoroutine() climb steadily under load, but there's no crash, no fatal error, and go test -race passes clean. What's the most likely culprit?

Right. Growing goroutine count plus growing memory with no crash is the signature of a leak, not a deadlock or a race. A full deadlock would abort with fatal error: all goroutines are asleep immediately; a data race is a correctness bug that -race reports rather than a steady resource climb. The detector passing is expected — leaks aren't races. Capture a goroutine profile with pprof, find the line N goroutines are all parked on, and give that goroutine an exit path (a done/ctx.Done() channel, a buffered or closed channel, or a timeout).
See also note

These single-process failures have distributed cousins — partial failures, clock skew, and "is it slow or dead?" When you scale out, see DDIA · The trouble with distributed systems.
