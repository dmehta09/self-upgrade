Concurrency · the centerpiece

Concurrency, the big picture.

This is the part everyone comes to Go for. Before the mechanics — goroutines, channels, select — get the mental model straight: what concurrency is, why Go makes it cheap, and the one sentence that runs through the whole module.

01 Concurrency is not parallelism

Concurrency is structuring a program as independently-executing pieces. Parallelism is actually running several at the same instant. Concurrency is about design; parallelism is about execution.

In plain English analogy

One barista juggling three drink orders — pulling a shot, then steaming milk for the next, then ringing up the first — is concurrent: the work is split into pieces she switches between. Add a second barista and the drinks now come out in parallel. The clever part was always the structure of the orders, not the number of baristas. A well-structured concurrent program can run in parallel — but it's correct and useful even on one core.

This is Rob Pike's famous talk in one line: concurrency enables parallelism, but doesn't require it. You write goroutines to organize independent work; the runtime decides how many CPUs actually run them at once (controlled by GOMAXPROCS, which since Go 1.25 is container-CPU-aware by default).

02 The Go model, in one breath

Spin up work as cheap goroutines, let them communicate over channels instead of sharing memory, and let the runtime multiplex them onto a small pool of OS threads.

Goroutines, not threads
A goroutine starts at ~2 KB of stack (an OS thread is ~1 MB) and grows on demand. You can have hundreds of thousands. Launch one with go f() — that's the whole syntax.
Share by communicating
Go's motto: "Do not communicate by sharing memory; instead, share memory by communicating." Pass a value down a channel and ownership moves with it — only one goroutine touches it at a time, so there's nothing to lock.
The runtime multiplexes
The scheduler maps your Goroutines onto OS threads (Machines) via logical Processors (G-M-P). A blocked goroutine parks; its thread picks up another. You never manage threads yourself.

04 Two schools: channels vs mutexes

CSP-style channels move data between goroutines; shared-memory + mutex guards a value in place. Go gives you both — and the pragmatic answer is use whichever is simplest.

Channels (CSP) — when data flows

Reach for channels when a value is moving between goroutines: a pipeline stage handing work to the next, a result coming back, a cancellation signal. Ownership travels with the message; nobody shares.

Mutex — when state sits still

Reach for a sync.Mutex when you're guarding a piece of state that several goroutines read and write in place — a counter, a cache, a connection pool. Often it's the clearer, faster choice.

Pro tip the Go answer

The Go team's own guidance: "Use whatever is most expressive and/or most simple." A Mutex protecting a map is often clearer than a channel-fed goroutine that owns it. Don't force everything through channels because they're the flashy feature — reach for the lock when you're just guarding state.

05 Check yourself

A program structured with goroutines runs on a single-core machine (GOMAXPROCS=1). Which statement is true?

Right. Concurrency is about structure, parallelism about simultaneous execution. On one core the scheduler interleaves goroutines (concurrency) but never runs two at once (no parallelism). The structure is still useful: a goroutine blocked on I/O parks and lets another run, so even one core stays busy.
