Concurrency · goroutines

Goroutines: concurrency for the price of a function call.

A goroutine is just a function the Go runtime runs alongside the rest of your program. You start one by writing go f(x) — and because each costs only a couple of kilobytes, a single Go program can hold hundreds of thousands of them. The whole art is starting them; the trap is making sure you wait for them.

01 The idea: one keyword, a new line of execution

A goroutine is a function scheduled by the Go runtime, started with go f(x). The call returns immediately; f runs concurrently, and your code carries on without waiting.

In plain English analogy

Calling a function normally is like asking a colleague to run an errand and standing at the door until they're back — you can't do anything else meanwhile. Writing go errand() is like handing the errand off and turning straight back to your own desk: the colleague goes off and does it on their own, and you keep working. The word go is "you handle that — I'm not waiting."

Mechanically, go f(x) evaluates f and its arguments in the current goroutine, then schedules the call to run independently. There's no handle, no thread object, no return value — control returns to the next statement at once. The main function is itself the first goroutine.

spawn.go
func work(id int) {
    fmt.Println("working", id)
}

func main() {
    go work(1)   // schedules work(1); returns immediately
    go work(2)   // and again — both run concurrently with main
    // ... main keeps going right here, NOT after work() finishes
}

02 Why they're cheap: tiny stacks, multiplexed onto threads

A goroutine starts with a ~2 KB stack that grows and shrinks on demand, and the runtime multiplexes many goroutines onto a handful of OS threads. So 100,000 goroutines is routine, not reckless.

An OS thread reserves a large fixed stack (often ~1 MB) and is scheduled by the kernel — heavyweight enough that you pool them. A goroutine is a user-space object: its stack is allocated small and copied to a bigger region only if it actually needs more. That's why you create goroutines freely instead of guarding a thread pool.

04 The classic trap: main exits and the lights go out

Gotcha trap

When main returns, the program exits immediately — and any goroutines still running are killed mid-flight, no cleanup. So go fmt.Println("hi") followed by a return often prints nothing: main reaches the end before the goroutine is scheduled. The fix is to synchronize (a sync.WaitGroup or a channel), never time.Sleep — sleep is a guess, and a guess is a race.

The opposite failure is just as common: a goroutine that never finishes because it blocks forever on a channel nobody feeds. That goroutine leaks — it holds memory until the process dies. We cover leaks, deadlocks, and data races in Leaks, deadlocks & races.

05 Waiting for many: sync.WaitGroup done right

A sync.WaitGroup is a counter: Add(n) before you spawn, Done() when each goroutine finishes, and Wait() blocks main until the count hits zero. Each goroutine writing to its own slice index needs no lock, and reading the slice after Wait() is deterministic.

This is the safe pattern: hand each goroutine a slot it alone owns, wait for all of them, then read. No shared write collides, and the order of the printed result never depends on which goroutine finished first.

Pro tip 1.22 / 1.25

This works because Go 1.22 made the loop variable per-iteration: each goroutine's i is its own. Before 1.22, every closure captured the same i and you'd see [9 9 9] or a panic — the infamous loop-var capture trap; the old fix was i := i inside the loop. Newer still, Go 1.25's wg.Go(func(){...}) folds the Add(1)/defer Done() into one call.

Gotcha trap

Call wg.Add(1) before the go, never inside the goroutine — otherwise Wait() can run before Add does and return too early. And if two goroutines wrote the same index (or appended to one shared slice without a lock), that's a data race — undefined behaviour, not just wrong output.

06 Check yourself

A program does go fmt.Println("done") as the very last thing in main, then returns. What's the most likely output?

Right. When main returns the whole process exits immediately, killing any unfinished goroutines — so the print usually never happens. Go does not wait for stray goroutines, and there's no panic (a leaked goroutine just dies with the process). To guarantee the line prints, synchronize with a WaitGroup or a channel — not time.Sleep, which only hides the race.
