Interfaces in practice: errors, Stringer, sort.

The standard library is held together by a few tiny interfaces you implement constantly: error, fmt.Stringer, and the sort hooks. Learn these three and you'll recognise the pattern everywhere — plus the receiver gotcha that quietly skips your method.

01 error is just an interface

error is a one-method interface: interface { Error() string }. Any type with an Error() method is an error — so you can build rich, typed errors that carry fields.

In plain English analogy

There's nothing magic about error — it's not a built-in exception type, it's an ordinary interface anyone can implement. It's like a "must answer the question what went wrong?" contract. Sign the contract (write Error() string) and your struct counts as an error, fields and all.

A custom error type lets callers recover structured detail with errors.As. Note the method, not a magic keyword, is what makes it an error:

02 fmt.Stringer — friendly printing

Implement String() string (the fmt.Stringer interface) and fmt uses it whenever it prints your type with %v, %s, or Println — your own to-string hook.

03 The receiver gotcha that skips your method

Gotcha trap

If you implement String() (or Error()) on a pointer receiver *T but then print a value T, the method isn't in the value's method set — so fmt doesn't call it and you get the default {field …} dump. Either implement it on the value receiver, or always pass a pointer (&t).

Watch it: the value prints the raw struct, the pointer prints via String():

See also method sets

This is the method-set rule from Methods & receivers biting in practice: *T's method set is a superset of T's. For Stringer, prefer a value receiver unless the method must mutate.

04 Sorting: sort.Interface vs slices.SortFunc

Classic sorting implements three methods (Len/Less/Swap) — the sort.Interface. Modern Go (1.21+) usually skips that ceremony with slices.SortFunc and a comparison function returning -1/0/+1.

Classic — three methods
type byName []Color
func (s byName) Len() int           { return len(s) }
func (s byName) Less(i, j int) bool { return s[i].name < s[j].name }
func (s byName) Swap(i, j int)      { s[i], s[j] = s[j], s[i] }
// sort.Sort(byName(colors))
Modern — one closure (Go 1.21+)
slices.SortFunc(colors, func(a, b Color) int {
    return cmp.Compare(a.name, b.name) // -1, 0, or +1
})

05 Design tiny interfaces at the consumer

Don't pre-declare a sprawling interface beside your implementation. Define the smallest interface the caller needs, in the caller's package — that keeps abstractions sharp and tests trivial.

One method beats five
Easier to satisfy, easier to fake in tests, fewer reasons to change.
Owned by the consumer
The package that uses the behaviour declares the interface; the provider just exports a concrete type that happens to fit.
Name by behaviour
Reader, Notifier, Stringer — the -er convention names the single capability.
See also design

Small interfaces at the consumer are the Go expression of deep modules and information hiding from the APOSD guide — a narrow contract over a capable implementation.

06 Check yourself

You give Temp a func (t *Temp) String() string, then call fmt.Println(myTemp) with a Temp value (not a pointer). What prints?

Right. A pointer-receiver String() belongs to *Temp's method set, not Temp's. Printing a value falls back to the default format. Fix it by using a value receiver, or by printing &myTemp.
