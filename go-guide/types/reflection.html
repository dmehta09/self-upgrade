Types & interfaces · reflection

Reflection & struct tags (use sparingly).

Reflection lets a program inspect and manipulate its own types at runtime — it's how encoding/json reads your json:"name" tags. It's powerful, and a trap: slow, panic-prone, and blind to the compiler. Reach for it last.

01 reflect.TypeOf & reflect.ValueOf

Reflection's two entry points: reflect.TypeOf(x) hands you the runtime type (name, kind, fields); reflect.ValueOf(x) hands you the runtime value you can read (and, if addressable, write).

In plain English analogy

Normally code knows the shape of its data at compile time, like a worker who memorised the blueprint. Reflection is handing that worker a flashlight and saying "figure out the shape now, whatever it is." Flexible — but they're slower than someone who already knew, and they'll trip if the room isn't what they expected.

02 Reading struct tags — how json finds names

A struct tag is a string literal after a field (`json:"name"`). It's metadata, invisible to normal code; libraries read it via reflection — that's exactly how encoding/json knows to emit "name" instead of "Name".

03 The cost: slow, panicky, unchecked

Reflection trades away Go's best guarantees. It is much slower than direct code, it panics at runtime for misuse the compiler would normally catch, and it loses compile-time type safety — typos become crashes, not build errors.

CostWhat it means
SpeedField access via reflect is far slower than x.Field — it can't be inlined and does runtime bookkeeping.
PanicsWrong kind, unexported field, unaddressable value → panic at runtime, not a compile error.
SafetyThe compiler can't check reflective code. Refactors and renames slip through silently.
ReadabilityReflective code is harder to read and to follow in a debugger.

04 The trap: reflection panics & bypasses the checker

Gotcha trap

Reflective writes panic on the slightest misuse. reflect.ValueOf(x) gives an unaddressable copy, so calling Set… on it panics; so does touching an unexported field. None of this is caught at compile time — reflection bypasses the type checker. Reach for a generic or an interface first; use reflection only when the type truly is unknown until runtime.

To write through reflection you must pass a pointer and start from reflect.ValueOf(&u).Elem() — which is exactly the awkwardness that makes a plain assignment or a generic the better tool most of the time.

05 When it's justified — vs when it isn't

Reflection earns its place in serializers, decoders and ORMs — code that must work with types it can't know in advance. For "same logic, many known types," a generic is faster and type-safe; for "varying behaviour," an interface is cleaner.

Reflection where a generic fits
// runtime, slow, panics on non-numbers
func Sum(xs any) float64 { /* reflect over a slice */ }
Generic — compile-time & fast (Go 1.18+)
func Sum[T int | float64](xs []T) T {
    var total T
    for _, x := range xs { total += x }
    return total
}
Use reflection
encoding/json, encoding/xml, ORMs, generic printers, validators, dependency injection — the type is decided by data at runtime.
Prefer a generic
One algorithm over many known element types, with full type-checking and speed.
Prefer an interface
Different types, different behaviour — let method dispatch do the work.
See also json

Struct tags pay off most in serialization — see how encoding/json uses them in the encoding/json lesson.

06 Check yourself

You do v := reflect.ValueOf(u) on a struct value u, then call v.FieldByName("Name").SetString("x"). What happens?

Right. Passing a value (not a pointer) to reflect.ValueOf yields an unaddressable copy; any Set… panics at runtime, not compile time — reflection sidesteps the checker. To write, use reflect.ValueOf(&u).Elem(). Better still, avoid reflection here entirely.
