Generics · type parameters

Type parameters & constraints.

Since Go 1.18 you can write one function or type that works for many types — no any + type-assertion dance, no copy-pasted MaxInt/MaxFloat. The trick is a type parameter [T …] plus a constraint that promises which operations T supports.

01 Why generics

A type parameter lets a function or type be written once against a placeholder type, and the compiler stamps out a real version per concrete type — type-safe, no boxing, no assertions.

In plain English analogy

Think of a cookie cutter with an adjustable shape dial. You design the dough-rolling routine once; the dial (the type parameter) sets whether this batch is stars or hearts. Before generics you either rolled every shape by hand (copy-paste) or made a shapeless blob with any and squinted at it later (type assertions). A type parameter keeps the routine single and the shape known.

The two old workarounds both hurt. any + assertions throws away the compiler's knowledge — x.(int) can panic at runtime. Copy-pasting MaxInt, MaxFloat, MaxString is three places to fix one bug. Generics give you a single, checked definition.

Before — any erases the type
func Max(a, b any) any {
    // can't even write a < b — no operators on any!
    // need reflection or a giant type switch. ugh.
}
After — one checked definition
func Max[T cmp.Ordered](a, b T) T {
    if a < b {
        return b
    }
    return a
}

02 Syntax: parameter lists, functions & generic types

A type parameter list goes in square brackets after the name: func F[T any], func M[K comparable, V any]. Types can be generic too — type Stack[T any] struct{ … } — and their methods reuse the type parameter.

Each parameter is name constraint. The constraint (here any, comparable) tells the compiler what you're allowed to do with that type inside the body. Methods on a generic type repeat the receiver's parameter: func (s *Stack[T]) Push(v T).

stack.go
type Stack[T any] struct {
    items []T
}

func (s *Stack[T]) Push(v T) { s.items = append(s.items, v) }

func (s *Stack[T]) Pop() (T, bool) {
    var zero T                 // the zero value of T, whatever T is
    if len(s.items) == 0 {
        return zero, false
    }
    last := s.items[len(s.items)-1]
    s.items = s.items[:len(s.items)-1]
    return last, true
}

// instantiate with a concrete type:
var nums Stack[int]            // Stack[int]
var names Stack[string]        // a different, distinct type

Since Go 1.24, type aliases can be generic too: type Set[T comparable] = map[T]struct{}. Handy for naming a parameterized shape without a fresh defined type. (Earlier Go rejected type parameters on an alias.)

03 Constraints: any, comparable, unions & the ~ tilde

A constraint is an interface describing what operations T must support. any = anything (no operations). comparable = usable with ==/!= (so it can be a map key). A constraint can also list a union of types — ~int | ~float64 — to permit operators like <.

any
Every type. No operations beyond assignment — you can store and move T, nothing else.
comparable
Supports == / !=. Required to use T as a map key or compare two Ts.
cmp.Ordered
Since Go 1.21 — the stdlib set of all types supporting < <= > >= (ints, floats, strings). Use it for Max/Min/sort.
union ~int | ~float64
A custom set: "any type whose underlying type is int or float64." Enables arithmetic / ordering operators.

The tilde ~int means "int or any type whose underlying type is int." So type Celsius float64 satisfies ~float64 but not a bare float64 union. Almost always you want the ~ form so named types still fit.

constraints.go
// A constraint is just an interface with type elements.
type Number interface {
    ~int | ~int64 | ~float64      // ~ → named types count too
}

func Sum[T Number](xs []T) T {
    var total T
    for _, x := range xs {
        total += x                // legal: every type in the set has +
    }
    return total
}

type Celsius float64
// Sum([]Celsius{...}) works because Celsius's underlying type is float64
// and the union used ~float64.

04 Type inference: you rarely write the type args

When you call a generic function, the compiler infers the type arguments from the ordinary arguments. You write Max(3, 9), not Max[int](3, 9) — though the explicit form is legal when inference can't see enough.

05 The traps

Gotcha trap

You cannot add type parameters to a method — only to functions and to types. func (s Set) Map[U any](f …) is a compile error. If a method needs its own type parameter, make it a top-level generic function that takes the receiver as an argument. (That's why stdlib has slices.Collect, not a method on a slice.)

  • Constraints are about operations, not inheritance. A constraint says "T supports <" or "T is comparable" — it is not a base class. There's no subtyping; you're declaring a capability, not a hierarchy.
  • Over-constraining kills reuse. If your function only ever stores and returns T, constrain it with any, not cmp.Ordered. A tighter constraint than you use just shrinks the set of callers for no benefit.
  • No operators from thin air. Inside a body you may only use operations the constraint guarantees. With [T any] you cannot write a + b or a < b — you'd need a numeric/ordered constraint.

06 Check yourself

You write func Largest[T any](xs []T) T and inside the body do if xs[i] > best. The compiler rejects it. Why?

Right. A constraint enumerates the operations you may use on the type parameter. any allows only assignment, so the > operator is illegal. Switch the constraint to cmp.Ordered (Go 1.21+) — the set of types supporting < <= > >= — and the body compiles. This is the "operations, not inheritance" rule in action.
