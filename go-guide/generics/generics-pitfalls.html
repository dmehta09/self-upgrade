Generics & modern Go · judgment

Generics: when NOT to, and the gotchas.

Type parameters are a power tool, and like every power tool the skill is knowing when to leave it in the drawer. This lesson is about judgment: where generics earn their keep, where they only add ceremony, and the sharp edges to know either way.

01 When generics earn their keep

Reach for a type parameter when you have real, repeated code that differs only by the element type: containers, algorithms over many types, or code that today leans on any + type assertions.

In plain English analogy

A type parameter is an adjustable wrench. One wrench fits many bolt sizes — brilliant when you genuinely face many sizes. But if every bolt in your shop is 10mm, a fixed 10mm spanner is lighter, clearer, and never slips. Generics shine across many concrete types; for a single one they're just a wrench you have to keep re-adjusting.

  • Container & data structures — a Stack[T], Set[T], ordered tree, or LRU cache: the logic is identical for every element type.
  • Algorithms over many element types — Map/Filter/Reduce, slices.Sort, min/max: one definition, compile-time type safety, no boxing.
  • Replacing any + assertions — if a function takes any and immediately does v.(int), a type parameter keeps the static type and deletes the runtime risk.

02 Write code, not types

The community rule of thumb: don't design generics speculatively. Write the concrete code first; extract a type parameter only when you can see the duplication in front of you.

See also design judgment

This is a complexity decision, not a syntax one. A generic API you added "just in case" is speculative generality — extra interface surface paying for benefit that may never arrive. The APOSD guide on general-purpose modules frames the same trade-off: make something general only when the generality is real, or you're adding complexity (more to read, more to constrain) for a flexibility nobody needs yet. Concrete first; generalise on the second real use.

Rob Pike's older proverb still applies: "the bigger the interface, the weaker the abstraction." The same caution holds for type parameters — a function bristling with [K comparable, V any, S ~[]V] is often harder to read than two honest concrete functions. Extract on duplication, not on anticipation.

03 any + assertion vs a type parameter

Same task, two tools. A type parameter wins when the caller wants their concrete type back with no cast; any (or a small interface) wins when the values are genuinely heterogeneous or an interface reads clearer.

any + assertion — erases the type
func First(s []any) any { // caller must cast back
    return s[0]
}

x := First([]any{1, 2, 3})
n := x.(int) + 1 // runtime assertion, can panic
Type parameter — keeps the type
func First[T any](s []T) T { // keeps T end-to-end
    return s[0]
}

n := First([]int{1, 2, 3}) + 1 // n is int, no cast

But flip the task. If you're writing a logger, a JSON encoder, or a fmt.Print-style sink that must accept anything and treat it uniformly, any (or io.Writer, or fmt.Stringer) is the honest signature — a type parameter there just constrains callers without buying type safety you can use.

Gotcha trap

A type parameter that appears only in the return type, never in the arguments, can't be inferred — and a function whose type parameter is used just once usually wants a plain any or an interface instead. If T doesn't tie two or more positions together (input ↔ output, or several inputs), it isn't earning its keep; it's just noise the caller may have to spell out by hand.

04 Concrete sharp edges

Even where generics fit, four facts bite: no new type params on methods, inference has limits, ~ changes who fits a constraint, and generics aren't a speed trick.

Methods can't add type params
A method may use its receiver's type parameters, but it cannot introduce its own. func (s Set[T]) Map[U any](f func(T) U) Set[U] does not compile — make it a package-level function func Map[T, U any](s Set[T], f func(T) U) Set[U] instead.
Inference has limits
Go infers type arguments from value arguments. When T appears only in results, or you pass an untyped nil, you must spell it: New[int](), not New().
~ vs no tilde
constraints ~[]E (with tilde) admits any type whose underlying type is []E — so type IntSlice []int qualifies. Without the tilde the constraint matches only the literal type, locking out every named type built on it. Forgetting ~ is the classic "why won't my named type fit?" puzzle.
Not a performance win
Go compiles generics with GC-shape stenciling + dictionaries: types that share a memory shape (all pointers, say) share one compiled body and pass a runtime dictionary. So a generic call is not automatically faster than an interface — sometimes it's the same or slower. Choose generics for type safety and clarity, never as a speed hack.
comparable subtleties
comparable means == is defined — fine for a map key constraint. But any satisfies comparable too (since 1.20), and comparing interface values holding non-comparable dynamic types (a slice, a map, a func) panics at runtime. comparable is a compile-time promise about == existing, not a guarantee it can't panic.

05 Over-constraining kills reuse

A constraint is a contract: the tighter you make it, the fewer types qualify. Ask for exactly the operations you use — no more — or you needlessly shut out callers.

If your function only ever ==-compares its inputs, constrain with comparable, not cmp.Ordered — demanding < when you never order anything bars string-keyed structs and every non-ordered type for no reason. Pro tip least power

Constrain to the least power that works: any if you only move values around, comparable if you only test equality, cmp.Ordered only when you actually order. Each step up the ladder excludes more callers — climb only as far as the code forces you to.

06 Check yourself

You wrote func Sum[T Number](xs []T) T and a caller can't pass their type Celsius float64 values. The likeliest fix?

Right. A constraint element written float64 matches only the literal type; Celsius (underlying float64) is excluded. Writing ~float64 in the constraint admits any type whose underlying type is float64. The other options are non-fixes: methods can't add type parameters, and dropping to []any throws away the very type safety generics gave you.
