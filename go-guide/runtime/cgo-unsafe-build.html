cgo, unsafe & build internals.

Go's superpower is a single static binary that cross-compiles to any platform from any platform. Two escape hatches — cgo (call C) and unsafe (bypass the type system) — let you reach outside that safe, portable world. Both are sometimes necessary and almost always a mistake to reach for first.

01 The build pipeline: one static binary

A normal Go build runs compile → link → one self-contained binary with no external runtime, no shared libraries, no interpreter. You copy the file to a server and run it.

In plain English analogy

A pure-Go binary is a flat-pack box that ships with every screw, panel, and the Allen key glued inside — set it on the floor and it stands up anywhere. The moment you add cgo, you're shipping IKEA furniture that needs a specific drill the customer must already own (a C toolchain on the build machine). The box no longer travels freely.

That self-contained binary is why Go dominates containers and CLIs: a FROM scratch image with just the binary, and nothing to install at the destination.

02 Cross-compilation: GOOS & GOARCH

Because the toolchain knows every target, you build for another OS/CPU by setting two environment variables — no emulator, no remote machine:

terminal
# from a Mac, build a Linux arm64 binary for a container
GOOS=linux GOARCH=arm64 go build -o app ./cmd/app

# a Windows amd64 build, same machine
GOOS=windows GOARCH=amd64 go build -o app.exe ./cmd/app

# see every supported pair
go tool dist list

GOOS picks the operating system, GOARCH the CPU architecture. This just works for pure Go — and is one of the language's biggest practical strengths.

Pro tip reproducible builds

Add CGO_ENABLED=0 to guarantee a static pure-Go binary even when a dependency could pull in cgo — the standard recipe for tiny, portable container images.

03 Build tags & //go: directives

Build constraints compile a file only for certain targets. The modern form is a //go:build line at the very top of the file (above package), and a filename suffix is an implicit constraint:

cache_linux.go
//go:build linux && amd64
// +build linux,amd64

package cache

// Compiled ONLY for linux/amd64. A file named *_linux.go is
// constrained to GOOS=linux automatically, no tag needed.

Other //go: directives instruct the compiler. The common ones:

//go:build
Conditional compilation per OS/arch/custom tag (e.g. build with -tags=debug).
//go:embed
Bake a file into the binary at build time (templates, assets) — keeps the single-file deploy.
//go:generate
A command go generate runs (codegen, mocks). Not part of go build.
//go:noinline
A compiler hint — rare, mostly for benchmarks/diagnostics.

04 cgo: calling C, and what it costs

The pseudo-package "C" lets you call C code. The C lives in a comment directly above import "C":

hash.go
/*
#include <stdlib.h>
int add(int a, int b) { return a + b; }
*/
import "C"
import "fmt"

func main() {
    sum := C.add(C.int(2), C.int(3)) // a call across the Go↔C boundary
    fmt.Println(int(sum))
}
Gotcha trap

cgo looks convenient but the costs are steep: it breaks easy cross-compilation (you now need a C cross-toolchain for every target), adds a C toolchain build dependency, makes each Go↔C call far slower than a Go call (the runtime must hand the goroutine off a managed stack), and forfeits memory safety on the C side. Rule of thumb: avoid cgo unless you genuinely must — wrapping an irreplaceable C library (SQLite, a vendor SDK). For "I want it faster," pure Go is almost always the right answer.

05 unsafe: bypassing the type system

unsafe.Pointer is the one pointer that can be converted to and from any other pointer type, letting you reinterpret memory — used for zero-copy conversions and talking to syscalls. Since Go 1.20, unsafe.Slice and unsafe.String make a couple of these patterns less error-prone:

zerocopy.go
import "unsafe"

// zero-copy []byte -> string (NO allocation/copy).
// Caller MUST never mutate b afterward, or the string changes too.
func bytesToString(b []byte) string {
    if len(b) == 0 {
        return ""
    }
    return unsafe.String(&b[0], len(b)) // Go 1.20+
}
Gotcha trap

The package is named unsafe as a warning, not a brand. It voids Go's memory-safety guarantees — a wrong conversion is undefined behavior, a crash, or silent corruption, and the race detector/GC assumptions no longer protect you. Worse, its rules are not covered by the Go 1 compatibility promise: code relying on a struct's layout or the reflect.SliceHeader shape can break across Go versions. Use it only with extreme care, isolate it behind a tested function, and never reach for it where a normal copy would do.

06 When to reach for each

Default: stay pure Go
  • Single static binary, trivial cross-compile.
  • Memory safety + the race detector hold.
  • Stable across Go versions (Go 1 promise).
Escape hatch: only if forced
  • cgo: an irreplaceable C library you must bind.
  • unsafe: a measured zero-copy hot path or syscall plumbing.
  • Both: isolate, test hard, document the cost.

Reach for the escape hatch last, not first: prove with a profile that pure Go can't do the job before you trade away portability or safety.

07 Check yourself

Your team's Go service builds and cross-compiles cleanly to linux/arm64 from a Mac with one command. A new PR adds import "C" to bind a C library. What breaks?

Right. The instant a build uses cgo, cross-compilation requires a matching C toolchain for the target OS/arch — the seamless GOOS/GOARCH workflow is gone, and the build now depends on a C compiler being present. That portability loss (plus slower C calls and the C-toolchain dependency) is exactly why cgo is a last resort. Setting CGO_ENABLED=0 keeps you in the easy, pure-Go world.
