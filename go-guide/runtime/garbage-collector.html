Runtime & performance · the GC

The garbage collector.

Go's collector is a concurrent, tricolor mark-and-sweep that runs alongside your program, keeping pauses well under a millisecond. You rarely tune it — but knowing how it decides what to keep, and what makes it run more often, turns mysterious latency into something you can reason about.

01 The collector's one job

The GC finds heap objects your program can still reach (from stacks, globals, registers — the roots) and frees everything else. It trades a little CPU and memory for never having to call free yourself.

In plain English analogy

Imagine a warehouse where you tie a string from the front door to every box you still care about, following the strings box-to-box. Anything with no string leading to it from the door is unreachable — nobody can ask for it again — so it's junk and gets cleared out. The GC is the worker walking those strings.

02 Tricolor mark & sweep, visualized

Every object is white (assumed garbage), grey (reachable, not yet scanned), or black (reachable and fully scanned). Marking greys the roots' targets, then blackens them as it follows their pointers. Step through it:

The clever part: this runs concurrently with your goroutines. A write barrier catches the case where running code rewires a pointer mid-scan, so nothing reachable is ever collected by mistake.

03 When does it run? GOGC & the memory limit

The GC is paced by how fast you allocate. By default (GOGC=100) it aims to run when the heap has grown ~100% since the last collection — so a program that allocates more, collects more often.

GOGC
The growth target. Higher (e.g. GOGC=200) = fewer collections, more memory used; lower = more frequent, less memory. Default 100.
GOMEMLIMIT
A soft memory ceiling (Go 1.19+). The GC works harder as the heap approaches it — invaluable in containers to avoid OOM kills. Pair it with GOGC.
The pauses
Two brief stop-the-world points (start & end of mark) — typically well under a millisecond; the bulk of marking is concurrent.

04 Reducing GC pressure

Gotcha trap

The GC's cost scales with the number of live objects and allocations, not bytes alone. The fix for GC-bound latency is almost never "tune GOGC" — it's allocate less: reuse buffers (sync.Pool), preallocate slices/maps with a capacity, avoid needless pointers (keep values on the stack — see escape analysis), and don't box into any on hot paths. Measure with -benchmem and the heap profile first.

Tactics that actually move the needle, in order: cut allocations in the hot path; set GOMEMLIMIT in memory-constrained deployments; only then consider raising GOGC to trade memory for fewer cycles.

See also sibling guide

GC trade-offs echo the storage-engine compaction trade-offs in Designing Data-Intensive Applications — reclaiming space without stalling the system is the same tension at a different layer.

05 Check yourself

During concurrent marking, a running goroutine stores a pointer to a white object into an already-black object. What stops the white object from being wrongly swept?

Right. The write barrier intercepts pointer writes during marking and shades the target grey, preserving the tricolor invariant (no black object points to a white one). That's what lets marking run concurrently with your program. Go's collector is not generational and does not move objects.
