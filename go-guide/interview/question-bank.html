Interview · question bank

The Go question bank.

A curated bank of the questions Go interviews actually ask — grouped by topic, each answer crisp and senior-level, with a line to rehearse out loud and the follow-ups to expect. Answer before you open the card. June 2026, Go 1.26 era.

00 How to use this

Read the prompt, answer aloud, then open the card and compare. Aim to explain the mechanic and name the trap, not recite. Difficulty chips: warm opener, core expected, stretch senior. Each answer links to the lesson that proves it; the same traps drive the gotchas index and the timed drills.

01 Slices, maps & data

What is a slice, and why can two slices alias the same data?core
Model answer

A slice is a small header — a pointer to a backing array, a length, and a capacity. Slicing or assigning copies the header, not the array, so two slices can point at the same backing storage. A write through one is visible through the other for any index they both cover. copy into a fresh slice when you need true independence.

Say it out loud say it

“A slice is a pointer-len-cap header over a shared array. Re-slicing copies the header, not the data — so writes leak between aliases until I copy.”

Follow-ups to expect
  • When does append stop aliasing the parent? (When it reallocates — or use a 3-index slice s[lo:hi:hi] to force it.)
  • What does range over a slice copy? (The element value — mutate via the index.)
How can append silently corrupt a shared slice?stretch
Model answer

If a sub-slice still has spare capacity, append writes into that spare cell — which belongs to the parent’s backing array — instead of allocating. So append to a function’s slice argument can overwrite data the caller still holds. The fix is a 3-index slice s[lo:hi:hi], which caps capacity at the length so the next append is forced to reallocate.

Say it out loud say it

“append into spare capacity writes the parent’s array. I cap with a 3-index slice so it’s forced to realloc and can’t clobber.”

See arrays & slices for the len/cap model.

Three things about Go maps that trip people up?core
Model answer

One: a write to a nil map panics, though reads are fine — make it first. Two: iteration order is deliberately randomized, so anything order-dependent must sort the keys. Three: reading an absent key returns the zero value silently, so use comma-ok (v, ok := m[k]) to tell “absent” from “present and zero.” Maps aren’t safe for concurrent writes.

Say it out loud say it

“Nil-map writes panic, iteration order is random, and a missing key reads as zero — so I make it, sort keys, and use comma-ok.”

See maps.

02 Interfaces, methods & generics

Why is a non-nil error returned from a function that “returned nil”?stretch
Model answer

An interface value is a (type, value) pair and is only nil when both are nil. If you return a typed nil pointer — say var p *MyError; return p — the interface carries a concrete type with a nil value, so err != nil is true even though the pointer is nil. The fix: return a bare nil on success, never a typed nil.

Say it out loud say it

“An interface is a type-value pair; it’s nil only if both are. A typed-nil pointer in an error makes it non-nil — so I return a literal nil.”

See nil interfaces vs nil pointers.

Value receiver vs pointer receiver — how do you choose?core
Model answer

A value receiver operates on a copy, so it can’t mutate the original and is wasteful for large structs. Use a pointer receiver to mutate, to avoid copying, or when the type holds a sync.Mutex (copying the lock is a bug). Keep the method set consistent: don’t mix value and pointer receivers on one type. Note only *T satisfies an interface if any method has a pointer receiver.

Say it out loud say it

“Pointer receiver to mutate, to avoid a big copy, or if it holds a lock. I keep receivers consistent across the type’s methods.”

See methods & receivers.

How does Go satisfy interfaces, and why does that matter for design?core
Model answer

Interfaces are satisfied structurally — a type implements one just by having the methods, with no implements keyword. So you define small interfaces at the consumer, and existing types satisfy them for free. The idiom is “accept interfaces, return structs,” and keep interfaces tiny — io.Reader is one method.

Say it out loud say it

“Structural typing — no implements. I define small interfaces where they’re consumed; accept interfaces, return structs.”

See interfaces.

When do generics earn their place over interface{}?stretch
Model answer

When you need the same type relationship preserved — in and out, or across params — with compile-time safety and no boxing. A generic Map[T, U] or a Min[T cmp.Ordered] keeps types exact; any would erase them and need a runtime assertion. Reach for generics for container/algorithm code, not to abstract behavior — that’s still an interface’s job.

Say it out loud say it

“Generics when I must preserve the type relationship without boxing — containers and algorithms. Interfaces are still for abstracting behavior.”

See type parameters.

03 Goroutines, channels & select

What is a goroutine, and how is it different from an OS thread?core
Model answer

A goroutine is a lightweight, runtime-scheduled task — it starts with a tiny growable stack (a couple of KB) and the runtime multiplexes many goroutines onto a few OS threads. The scheduler is the G-M-P model: goroutines (G) run on logical processors (P), each bound to a thread (M). That’s why launching thousands is cheap where thousands of threads wouldn’t be.

Say it out loud say it

“A goroutine is a cheap runtime task with a tiny growable stack, multiplexed onto OS threads by the G-M-P scheduler — so thousands are fine.”

See goroutines and the scheduler.

Buffered vs unbuffered channels — what changes?core
Model answer

An unbuffered channel is a rendezvous: the send blocks until a receiver is ready, so it also synchronizes the two goroutines. A buffered channel accepts up to its capacity without a waiting receiver, decoupling sender and receiver and smoothing bursts — it blocks only when full (send) or empty (receive). Buffer for throughput, not to “avoid” blocking.

Say it out loud say it

“Unbuffered is a rendezvous that also synchronizes; buffered decouples up to its capacity and blocks only when full or empty.”

See channels.

Walk the closed-and-nil channel matrix.stretch
Model answer

On a closed channel: receive returns immediately with the zero value and ok == false (drains buffered values first); sending panics; closing again panics. On a nil channel: both send and receive block forever. That nil behavior is a feature — setting a channel to nil disables its select case so a loop can stop watching it.

Say it out loud say it

“Closed: recv yields zero/false, send panics. Nil: both block forever — which I use to switch off a select case.”

See channels.

What does select do, and what does default change?core
Model answer

select waits on several channel operations and proceeds with whichever is ready; if more than one is ready it picks uniformly at random to avoid starvation. Adding a default case makes it non-blocking — if nothing is ready, default runs immediately. A select with no cases (select{}) blocks forever.

Say it out loud say it

“select takes whichever case is ready, random among ties. A default makes it non-blocking; no cases blocks forever.”

See select & multiplexing.

Did the loop-variable closure bug go away?warm
Model answer

Mostly, yes — Go 1.22 made the loop variable per-iteration, so a goroutine or closure capturing it now sees its own copy. Before 1.22 every closure shared one variable and usually printed the final value. On older code (or to be explicit) you still write v := v to shadow it inside the loop.

Say it out loud say it

“Since 1.22 the loop variable is per-iteration, so closures capture their own copy. Pre-1.22 I’d shadow with v := v.”

See goroutines.

04 Synchronization & the memory model

Mutex vs channel vs atomic — when each?core
Model answer

A sync.Mutex guards a critical section over shared state — simplest when state stays put. A channel transfers ownership of data between goroutines — “don’t communicate by sharing memory; share memory by communicating.” sync/atomic is for a single counter or flag where a full lock is overkill. Rule of thumb: mutex to protect state, channels to move it, atomics for one word.

Say it out loud say it

“Mutex to protect shared state, channels to hand off ownership, atomics for a single counter or flag. Match the tool to the shape of the sharing.”

See sync primitives.

Explain “happens-before” and why an unsynchronized read can see a stale value.stretch
Model answer

The Go memory model only guarantees one goroutine sees another’s write if there’s a happens-before edge between them — established by a channel send/receive, a Mutex, sync/atomic, or WaitGroup. Without one, the compiler and CPU may reorder or cache, so a reader can observe a stale value or never see the write at all. A “done” bool flipped without synchronization is the classic example — and a data race is undefined behavior, not just “the old value.”

Say it out loud say it

“Visibility needs a happens-before edge — a channel, lock, or atomic. Without one it’s a data race, which is undefined behavior, not a stale-but-defined read.”

See atomics & the memory model.

Why must you never copy a sync.Mutex or WaitGroup?core
Model answer

Their internal state is the synchronization. Copy the struct — for example a value receiver, or passing a struct by value — and the copy has its own independent lock/counter, so two goroutines “guarding” the same data actually take different locks and the protection evaporates. Always share by pointer; go vet flags lock copies.

Say it out loud say it

“The lock’s state is the sync — a copy guards nothing. I share by pointer and let go vet catch copies.”

See sync primitives.

05 context, errors & defer

What is context for, and what’s the cardinal rule?core
Model answer

context.Context carries cancellation, deadlines, and request-scoped values across API boundaries. You pass it as the first argument, and goroutines watch <-ctx.Done() to stop early. The cardinal rule: whenever you create a cancelable context (WithCancel/WithTimeout/WithDeadline) you must defer cancel() — even on the success path — or you leak the context and its timer.

Say it out loud say it

“Context propagates cancellation and deadlines, first arg by convention. And I always defer cancel() — even on success — or I leak.”

See context.

How do you wrap errors, and how do errors.Is and errors.As differ?core
Model answer

Wrap with fmt.Errorf("doing X: %w", err) — %w (not %v) keeps the underlying error reachable. errors.Is(err, target) walks the chain to test for a specific sentinel value like io.EOF; errors.As(err, &target) walks it to find an error of a specific type and binds it so you can read its fields. Is for identity, As for type.

Say it out loud say it

“%w to wrap, errors.Is for a sentinel value, errors.As to pull out a concrete type. Is = identity, As = type.”

See error handling patterns.

Explain defer, panic, and recover — and the two defer traps.stretch
Model answer

Deferred calls run when the function returns, in LIFO order, even during a panic — which is what makes recover() work, but only when called inside a deferred function in the same goroutine. Two traps: defer’s arguments are evaluated immediately (defer a closure if you need the later value), and a defer inside a loop piles up until the function returns — move the body into a helper so each cleanup runs per iteration.

Say it out loud say it

“Defers run LIFO at return; recover only works inside a deferred func. Args snapshot immediately, and defers in a loop stack up — so I use a helper.”

See errors, defer & panic.

06 Runtime: GC, escape analysis & tooling

How does Go’s garbage collector work at a high level?stretch
Model answer

It’s a concurrent, tri-color mark-and-sweep collector that runs alongside your program to keep pauses sub-millisecond. Objects are white (unreachable), grey (reached, not scanned), or black (scanned); a write barrier catches pointers mutated mid-mark so nothing reachable is collected. There’s no generational compaction — it’s non-moving — and GOGC (or 1.19’s soft memory limit) tunes how often it runs.

Say it out loud say it

“Concurrent tri-color mark-sweep with a write barrier for sub-millisecond pauses; non-moving, tuned by GOGC or the memory limit.”

See the garbage collector.

What is escape analysis, and why should you care?core
Model answer

At compile time Go decides whether a value can live on the goroutine’s stack (freed automatically when the function returns) or must escape to the heap (managed by the GC). It escapes when its lifetime outlives the function — typically because a pointer to it is returned, stored, or captured by a closure. Fewer escapes mean fewer allocations and less GC pressure. Inspect with go build -gcflags=-m.

Say it out loud say it

“The compiler decides stack vs heap; a value escapes when its pointer outlives the function. I check with -gcflags=-m to cut allocations.”

See stack vs heap.

Concurrency vs parallelism — what’s the distinction?warm
Model answer

Concurrency is structure — composing independently progressing tasks (goroutines, channels). Parallelism is execution — running tasks literally at the same instant on multiple cores. A concurrent program may run on one core and still be correct; GOMAXPROCS controls how many run in parallel. Rob Pike’s line: “concurrency is about dealing with many things at once; parallelism is about doing many things at once.”

Say it out loud say it

“Concurrency is how I structure independent tasks; parallelism is running them at once on many cores. GOMAXPROCS turns one into the other.”

See the scheduler.

How do you find a data race, and what does go test -race actually do?core
Model answer

Run the suite with -race: the race detector instruments memory accesses and reports when two goroutines touch the same location concurrently with no happens-before edge and at least one write — printing both stacks. It only catches races on code paths your tests actually exercise, so it’s a dynamic tool, not a proof; it also slows execution, so it’s a CI gate, not a production flag.

Say it out loud say it

“-race instruments accesses and flags concurrent unsynchronized access with a write. It only sees exercised paths — a CI gate, not a guarantee.”

See leaks, deadlocks & races.
