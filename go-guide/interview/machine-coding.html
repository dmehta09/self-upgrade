Concurrency machine-coding.

Three classics that come up again and again in Go onsites: a worker pool, a rate limiter, and a concurrent cache with single-flight de-duplication. Each has a runnable solution below — deterministic on purpose, so you can read the output and trust it. The point isn’t to memorize; it’s to recognize the shape and wire the channels under the clock.

01 Worker pool

Spin up a fixed number of workers reading from one jobs channel, push results back on a results channel, and use a WaitGroup so a coordinator knows when to close results. You cap concurrency by the worker count, not the amount of work.

Problem. Square the integers 1..8 using exactly three worker goroutines, collect every result, and print them. The catch: results arrive in whatever order workers finish, so a naive print is non-deterministic — collect, then sort before printing.

Three design decisions to say out loud: (1) close jobs from the producer so every for range jobs loop ends cleanly; (2) a WaitGroup tracks the workers so a separate goroutine can close(results) only after the last send; (3) the main goroutine ranges over results until it’s closed, then sorts.

Gotcha trap

Who closes results, and when? Close it too early and a worker panics on send-on-closed; never close it and the for range results loop blocks forever. The fix is the wg.Wait(); close(results) goroutine — close only once, only after every sender is done.

This is the worker-pool pattern in its barest form. Real variants add a context for cancellation and bound the result buffer.

02 Rate limiter

A token bucket holds up to capacity tokens and refills at a fixed rate; each request spends a token if one is available, otherwise it’s denied (or waits). The bucket allows short bursts up to its capacity while holding the long-run rate to the refill rate.

Problem. Limit requests with a bucket of capacity 3 that refills one token per tick. Over 6 ticks, two requests arrive each tick — report how many were allowed and how many denied. To keep the output deterministic we step a logical clock by hand instead of racing a real time.Ticker; the production version reads <-ticker.C, but the arithmetic is identical.

Design decisions: the bucket is just {tokens, capacity}; refill() adds one token per tick, capped at capacity; allow() spends a token and reports success. Wrapping the counts (allowed/denied) rather than printing per-request keeps the result a single deterministic number.

Gotcha trap

Cap the refill at capacity — an unbounded counter would let an idle bucket accumulate infinite tokens and then allow an unlimited burst, defeating the limiter. And in a real concurrent version the bucket is shared state: guard tokens with a Mutex or use atomic, or the count itself races.

The first two ticks drain the initial burst (3 spare tokens + 1 fresh), then the bucket settles into its steady state: one token in, one request allowed, one denied — the refill rate is the long-run limit.

03 Concurrent cache (single-flight)

Guard a map with a Mutex, and when many goroutines miss on the same key, let exactly one perform the expensive load while the rest wait and reuse the result. This single-flight trick collapses a thundering herd into a single backend call.

Problem. 50 goroutines simultaneously ask the cache for the same key. The loader is “expensive” — every caller must get the same value, and the loader must run exactly once. Print the distinct values seen and the load count to prove de-duplication.

Design decisions: store a per-key *call with a WaitGroup. The first caller to miss publishes its call into the map while holding the lock, then unlocks before doing the slow load (so it doesn’t block readers). Later callers find the in-flight call, drop the lock, and wg.Wait() on it — reusing the value once it’s ready.

Gotcha trap

Never hold the mutex across the slow load — that serializes every caller and kills throughput. The trick is to publish the in-flight call under the lock, then release the lock and let waiters block on the WaitGroup, not the Mutex. (The standard library packages exactly this as golang.org/x/sync/singleflight.)

Fifty callers, one distinct value, one load — the herd collapsed. The Mutex protects the map; the WaitGroup de-duplicates the load. See sync primitives for the building blocks.

04 How to talk through it

Under the clock, narrate in this order — it shows judgment even before the code compiles:

Name the pattern
“This is a worker pool / token bucket / single-flight cache” — recognition is half the score.
State the concurrency contract
Who owns each channel, who closes it, what each goroutine waits on. Channels move data; the WaitGroup says when we’re done.
Call the trap before they do
Send-on-closed, holding a lock across slow work, an uncapped bucket — saying it first signals seniority.
Make it provable
Collect and sort, or aggregate counts, so the output is deterministic. Then say “I’d run this under go test -race.”
