Getting started · why Go

Why Go exists (and where it wins).

Go was built at Google to fix a specific kind of pain: huge codebases that built slowly, sprawled into accidental complexity, and broke at runtime. The cure was a tiny language with a fast compiler, memory safety, and concurrency in the box.

01 The problem Go solved

Go targets the pain of large-scale server software: slow C++ builds, accidental complexity from over-rich languages, and the runtime fragility of dynamic ones. Its answer — fast compile, tiny spec, memory-safe, concurrent.

In plain English analogy

Imagine a workshop where the table saw takes 40 minutes to warm up (C++ builds), the toolbox has nine tools that all do the same job slightly differently (feature-rich languages), and half the tools only tell you they're broken once your hand is already on them (dynamic typing). Go is a deliberately small toolbox: fewer tools, each obvious, that turn on instantly and won't cut you by surprise.

The three founders — Rob Pike, Ken Thompson, Robert Griesemer — were staring at C++ builds that took many minutes, dependency graphs that pulled in the world, and big teams where one engineer's cleverness became another's puzzle. So they optimised for the thing that actually dominates a large project's life: reading and maintaining code, and getting a working binary fast.

Fast compilation
Simple grammar + no header re-parsing → builds in seconds, not minutes. The edit→run loop stays tight even on a million-line codebase.
Small spec
The whole language fits in your head. Fewer features means fewer ways to write the same thing — and far less to argue about in review.
Memory-safe with a GC
No manual malloc/free, no dangling pointers, no buffer overruns of the C kind. The garbage collector removes a whole category of bugs.
Concurrency built in
Goroutines and channels are part of the language, not a bolted-on library — cheap concurrency is the default tool, not an expert move.

02 Where Go wins

Go's sweet spot is networked services and infrastructure: APIs, CLIs, and cloud plumbing. A program compiles to one self-contained static binary — copy it to a box (or a scratch container) and it runs, no runtime to install.

This isn't theoretical. A huge slice of the cloud-native world is Go:

Docker

The container runtime that defined the era — Go.

Kubernetes

The orchestration standard — Go.

Terraform

Infrastructure-as-code — Go.

Prometheus

The metrics/monitoring backbone — Go.

Caddy / etcd / Consul

Web server, key-value store, service mesh — all Go.

The Go toolchain itself

The compiler and tools are written in Go.

Why those, specifically? They're long-lived servers and operator tools where throughput under concurrency, predictable latency, and trivial deployment matter more than squeezing the last cycle out of a tight numeric loop. The "one binary" property is the quiet superpower: no interpreter, no virtual machine, no node_modules to ship — just an executable.

deploy.txt
// A whole web service is one file you can copy and run.
package main

import "net/http"

func main() {
    http.HandleFunc("/healthz", func(w http.ResponseWriter, r *http.Request) {
        w.Write([]byte("ok"))
    })
    http.ListenAndServe(":8080", nil) // no framework, no app server
}

03 The design values

Go optimises for readability over cleverness and one obvious way to do a thing. gofmt auto-formats every file to a single canonical style — so style debates simply end.

In plain English analogy

Most languages are a kitchen where everyone plates the dish their own way. Go ships with a robot (gofmt) that plates every dish identically before it leaves the pass. You stop arguing about tabs vs spaces or where the brace goes, because there's exactly one answer and the tool enforces it. The code you read is the code everyone reads.

The philosophy is openly stated: code is read far more often than it's written, so a feature only earns its place if it makes the common case clearer. That's why Go has no ternary operator, no implicit conversions, no exceptions for ordinary errors, and (until 1.18) no generics — each was weighed against the cost of one more thing to learn and one more way to be surprised.

obvious.go
// No ternary `cond ? a : b`. There is exactly one way: an if.
label := "even"
if n%2 != 0 {
    label = "odd"
}
// Reads the same in every codebase — nothing clever to decode.
See also design

"Readability over cleverness" and "make the obvious thing the easy thing" are the same instincts Ousterhout argues for in the APOSD guide — Go just bakes them into the language and tooling.

04 The tradeoffs — where Go is a poor fit

Small spec means Go omits things on purpose: no sum types/enums, terse error handling (if err != nil everywhere), historically no generics. And the GC makes it soft-realtime, not hard-realtime.

Gotcha trap

Don't reach for Go for CPU-bound numeric/ML/GPU work or hard-realtime systems. There's no rich numeric/array ecosystem (that world lives in Python+CUDA, C++, or Rust), and the garbage collector can pause the program — pauses are tiny and well-tuned, but they exist, which makes Go soft-realtime only. A pacemaker or an engine-control loop with a hard microsecond deadline wants C or Rust, not Go.

Great fit
  • HTTP/gRPC services and APIs
  • CLIs and developer tooling
  • Cloud infra, controllers, agents, daemons
  • Network proxies, schedulers, pipelines
  • Anything that ships as one binary and runs many things at once
Poor fit
  • Heavy numeric / scientific computing, ML training
  • GPU kernels and SIMD-heavy hot loops
  • Hard-realtime / deterministic-latency control systems
  • Rich native GUI / game-engine work
  • Tiny embedded targets with no room for a runtime + GC

Even the verbosity is a deliberate trade: the famous if err != nil ritual is more typing, but it puts every failure path on the page where you can see it — the cost is paid in keystrokes and bought back in fewer surprises.

05 Check yourself

A team needs to ship a high-throughput JSON API and a CLI that deploys to bare containers — and separately, a hot loop that multiplies large matrices on a GPU. Which is the better fit for Go?

Right. Services and CLIs are Go's home turf: cheap concurrency, predictable latency, and a static binary you can drop into a scratch container. CPU-bound numeric/GPU work has no rich Go ecosystem and is sensitive to GC pauses — that's a job for CUDA/C++/Rust. Knowing where a tool doesn't fit is half of choosing it well.
