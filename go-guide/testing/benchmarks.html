Benchmarks & profiling.

Go's benchmark harness measures with the same go test command you already use. Since Go 1.24 the loop got simpler — for b.Loop() {} — and the numbers it prints (ns/op, allocs/op) point straight at pprof when you need to know why. The trick is making the measurement honest.

01 BenchmarkXxx(b *testing.B) and the loop

A benchmark is func BenchmarkXxx(b *testing.B) in a _test.go file. You run the work in a loop the harness controls; it scales the iteration count until the timing is statistically stable, then reports nanoseconds per operation.

In plain English analogy

You can't time one heartbeat with a wall clock — it's over too fast. So you count beats for a whole minute and divide. The benchmark harness does the same: it runs your operation thousands or millions of times, measures the total, and divides to get a trustworthy per-operation figure. Your job is just to write the single operation inside the loop; the harness decides how many beats to count.

The modern form (Go 1.24) is for b.Loop() { ... }. It replaces the old for i := 0; i < b.N; i++, automatically keeps setup out of the timing, and stops the compiler from deleting "dead" loop bodies.

Pre-1.24 — manual b.N
func BenchmarkSum(b *testing.B) {
    for i := 0; i < b.N; i++ {
        Sum(data)
    }
}
Go 1.24+ — b.Loop()
func BenchmarkSum(b *testing.B) {
    for b.Loop() {
        Sum(data)   // result kept "live" automatically
    }
}

02 Running it and reading the numbers

Run with go test -bench=. -benchmem. The line tells you the iteration count, ns/op (time), B/op (bytes allocated), and allocs/op (allocation count). -benchmem is what surfaces the allocation columns — always pass it.

terminal
$ go test -bench=. -benchmem
goos: linux
goarch: amd64
BenchmarkConcat-8     1234567       972 ns/op     512 B/op      9 allocs/op
BenchmarkBuilder-8    9876543       121 ns/op      64 B/op      1 allocs/op
PASS
-8 suffix
GOMAXPROCS the benchmark ran with (here 8 cores).
iteration count
How many times b.Loop() ran — chosen by the harness, not something you read for meaning.
ns/op
Average nanoseconds per operation — the headline speed number.
B/op · allocs/op
Bytes and allocation count per op. Fewer allocations usually means less GC pressure and faster code.

Use b.ResetTimer() after expensive setup so it doesn't pollute the measurement, and b.ReportAllocs() to force the allocation columns on for a single benchmark even without the global flag.

03 Stopping the compiler from cheating

If a benchmark's result is never used, the optimizer may delete the work entirely and you'll "measure" a near-zero. Assign the result to a package-level sink variable to keep it live. (b.Loop() handles much of this for you, but the sink pattern is still the safe habit.)

You can't trust a single time.Since reading in a runnable sandbox — it's nondeterministic. 04 Allocations are a deterministic signal

Time wobbles run to run, but allocation behaviour is structural — you can reason about it without a stopwatch. Pre-sizing a slice with make([]T, 0, n) turns many re-allocations into one. The gopad counts the grow events deterministically to show the difference an idea makes:

Gotcha microbenchmarks lie · trap

Three classic traps. (1) Treating b.N as "how many items to process" — it's the harness's iteration count, not your data size; loop your work inside it. (2) Forgetting -benchmem, so you optimise ns/op while a hidden allocation storm drives real-world GC cost. (3) Believing the micro number: a tight loop over warm cache and one fixed input can be 10× faster than production, where data is cold, varied, and contended. A microbenchmark answers "which of these two lines is faster"; only a profile of the real workload tells you which line even matters.

05 From benchmark to profile: pprof

A benchmark says how slow; a profile says where. Add -cpuprofile or -memprofile to a benchmark run and feed the output to go tool pprof to see the hot functions, the flame graph, and the allocation sources.

terminal
# Capture a CPU profile while benchmarking
$ go test -bench=BenchmarkConcat -cpuprofile=cpu.out
# Capture allocations
$ go test -bench=BenchmarkConcat -memprofile=mem.out

# Explore: top hot functions, or an interactive web flame graph
$ go tool pprof -top cpu.out
$ go tool pprof -http=:0 mem.out
See also profiling · judgment

The full workflow — reading flame graphs, allocation profiles and goroutine dumps — lives in Profiling & diagnosing with pprof. And before you optimise anything, decide whether it's worth it: Performance & what matters argues for measuring first and tuning only the critical path.

06 Check yourself

Your benchmark computes Hash(data) in the loop but never uses the result, and it reports an impossibly fast 0.31 ns/op. What's going on?

Right. Dead-code elimination is the classic benchmark lie: with no observable use of Hash(data), the compiler is free to remove it, so you "measure" nothing. Store the result in a package-level var sink ... (or rely on Go 1.24's b.Loop(), which marks loop results as used). -benchmem only adds allocation columns; it doesn't fix this.
