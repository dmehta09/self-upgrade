The tooling belt: vet, staticcheck, modules.

Go ships a batteries-included command-line belt. go vet flags suspicious code the compiler allows; gofmt ends every formatting argument before it starts; go mod manages dependencies and versions. Knowing the belt is what separates "writes Go" from "ships Go."

01 go vet: the compiler's stricter sibling

go vet reports code that compiles but is almost certainly a bug: Printf format/argument mismatches, copied locks, unreachable code, struct tags that don't parse, loops that misuse goroutines.

In plain English analogy

The compiler is a spell-checker: it rejects words that aren't words. go vet is a grammar-checker: every word is valid, but "your going to love this" is still wrong. It reads intent — your Printf says %d but you handed it a string — and flags the mismatch the compiler happily waved through.

go test runs a subset of go vet automatically before your tests, so format bugs often surface during a normal test run. Run the full go vet ./... separately in CI to catch the rest.

02 staticcheck, golangci-lint & the non-negotiable: gofmt

vet is the floor. staticcheck adds hundreds of deeper checks; golangci-lint bundles many linters behind one command. And gofmt/goimports mean Go has one canonical format — formatting is not a debate.

ToolWhat it doesTypical invocation
gofmtCanonical formatting (tabs, spacing, alignment). Mandatory in Go culture.gofmt -w .
goimportsgofmt plus auto-add/remove & group imports.goimports -w .
go vetBuilt-in correctness checks (printf, locks, tags…).go vet ./...
staticcheckDeep static analysis: dead code, bad APIs, bugs vet misses.staticcheck ./...
golangci-lintRuns many linters (incl. the above) fast, in one pass.golangci-lint run
Bikeshedding (other languages)

Tabs vs spaces, brace placement, import order — endless PR threads, a 40-page style guide, and a linter config nobody agrees on.

Go

gofmt decides. Your editor runs it on save; CI fails if a file isn't formatted. The argument simply does not exist — all idiomatic Go looks the same.

Gotcha trap

Three rookie tells: ignoring vet/staticcheck findings ("it works, ship it" — until the printf bug hits prod logs); committing unformatted code (a reviewer instantly knows you skipped gofmt); and treating linters as optional. In real Go shops, gofmt -l . returning any filename fails the build. Wire all three into CI and a pre-commit hook.

03 Modules: go.mod, go.sum & semantic import versioning

A module is a versioned unit of code rooted at a go.mod file. go.mod lists your dependencies and their versions; go.sum pins cryptographic checksums so builds are reproducible and tamper-evident.

go mod init example/app
Create go.mod, naming the module's import path.
go get pkg@v1.5.0
Add/upgrade a dependency at a chosen version.
go mod tidy
Add what's imported, remove what isn't, sync go.sum.
go.work
A workspace stitching several local modules together for cross-repo / monorepo dev — prefer this over long-lived replace directives. See Toolchain & modules.
toolchain
Pin the Go binary in go.mod (toolchain go1.26.0) so CI and laptops use the same compiler; distinct from the language go 1.26 line.

Semantic import versioning is the rule that surprises newcomers: a v2+ major version puts the major in the import path itself. So v1 and v2 of a library are different import paths and can coexist in one build — no "dependency hell" where two packages need incompatible majors:

go.mod
module example/app

go 1.26

require (
    github.com/go-chi/chi/v5 v5.1.0   // v2+ → /vN in the import path
    golang.org/x/sync v0.10.0
)
main.go
// the /v5 is part of the path, not just the go.mod version
import "github.com/go-chi/chi/v5"
Gotcha trap

Forgetting go mod tidy is the classic. You delete an import but leave the require line; or add one and never record it. CI then fails on a clean checkout, or ships unused dependencies. Run go mod tidy before every commit and let CI verify go.mod/go.sum are unchanged afterward — a diff means you forgot.

04 The everyday verbs & tool directives

go build compiles, go run compiles-and-runs, go test tests. Since 1.24, tool dependencies live in go.mod via tool directives, so your linters and codegen tools are versioned with the project.

go run .

Compile to a temp binary and run it — for quick iteration, not for shipping.

go build ./...

Compile every package; produce a binary for main packages. Fast, cached.

go test ./...

Run all tests (and a vet subset) across the module.

go tool

Run a tool tracked in go.mod (e.g. go tool staticcheck) at the pinned version.

Pin a tool so every contributor and CI runs the same version — no "works on my machine" from a globally-installed linter that drifted:

terminal
# Go 1.24+: record a tool dependency in go.mod
$ go get -tool honnef.co/go/tools/cmd/staticcheck

# now everyone runs the pinned version, no global install
$ go tool staticcheck ./...

Build tags let one file compile only on certain platforms or build modes — the //go:build line gates the whole file. Below, the file is included only on Linux:

net_linux.go
//go:build linux

package net

// compiled only when GOOS=linux; ignored elsewhere

A solid Go CI step: gofmt -l . (must be empty), go vet ./..., go tool staticcheck ./..., go test -race ./..., and a go mod tidy + git-diff check. Five commands, zero third-party platform — the toolchain does the heavy lifting.

06 Check yourself

You depend on github.com/foo/bar at v2.3.0. What does the import line in your Go source look like?

Right. For v2 and above, the major version is part of the import path (/v2), and go.mod reads require github.com/foo/bar/v2 v2.3.0. This is what lets v1 and v2 of the same library coexist in one build. (v0/v1 keep the bare path — no suffix.) The full @version form is for go get on the command line, not for source imports.
