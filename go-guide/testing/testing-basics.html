Testing & tooling · testing

Tests, table tests & subtests.

Go's testing story is deliberately small: a _test.go file, a func TestXxx(t *testing.T), and the standard library's testing package. No assertion DSL, no annotations — just got vs want and plain Go. Master the table-driven pattern and you can test almost anything.

01 The anatomy of a Go test

A test is a function named TestXxx taking *testing.T, living in a file ending _test.go. You compare got to want and call t.Errorf when they differ — the package is the framework.

In plain English analogy

Other ecosystems hand you a whole laboratory of assertion gadgets — expect(x).to.equal(y), matchers, fluent chains. Go hands you a notepad and a pen: "run the code, look at what you got, compare it to what you wanted, write down what's wrong." The discipline is in you, not in a framework — and a Go test reads like the rest of your Go.

Run with go test ./.... The tooling discovers every TestXxx, runs them, and reports PASS/FAIL. A test "fails" the moment you call a failing method on t — there is no return value to inspect.

abs_test.go
package math

import "testing"

func TestAbs(t *testing.T) {
    got := Abs(-3)
    want := 3
    if got != want {
        t.Errorf("Abs(-3) = %d, want %d", got, want)
    }
}

02 Errorf vs Fatalf, and t.Helper

t.Errorf records a failure but keeps going; t.Fatalf records it and stops this test immediately. Use Fatalf when continuing is pointless (a nil you'd dereference); use Errorf to report several independent problems in one run.

t.Errorf(...)
Mark failed, continue the function. Best for "check many fields."
t.Fatalf(...)
Mark failed, call runtime.Goexit — this test stops here. Best after setup that must succeed.
t.Helper()
Marks a function as a helper, so failures report the caller's line, not the helper's.
t.Cleanup(fn)
Registers fn to run when the test (or subtest) finishes — LIFO, like defer but test-aware.
t.TempDir()
A fresh directory auto-removed at test end. Perfect for filesystem tests.
Gotcha trap

t.Fatalf only stops the goroutine it runs on. Calling it from a goroutine you spawned inside the test (not the test's own goroutine) won't stop the test — it just kills that goroutine, and the test may pass anyway. Always Fatal from the test goroutine; report failures from spawned goroutines via t.Errorf after a sync.WaitGroup join.

03 Table-driven tests: a slice of cases

The dominant Go pattern: define a slice of case structs (name, inputs, want), then loop and assert. Adding a case is one line; the logic stays in one place. This is how the standard library tests itself.

The gopad below replicates the mechanics so you can see it run: a function under test, a table of cases, and a loop that prints a PASS/FAIL line per case exactly as go test -v would summarise. (A real _test.go can't be executed here — so we emulate the runner.)

04 t.Run subtests & t.Parallel

Wrap each table case in t.Run(c.name, func(t *testing.T){ ... }) to get a named subtest. Subtests can be filtered (-run TestAbs/zero), isolated, and made parallel with t.Parallel().

Gotcha loop-var capture · trap

The classic table-test bug: a parallel subtest that closes over the loop variable. Before Go 1.22 every iteration shared one c, so by the time the parallel subtests ran, they all saw the last case. The old fix was c := c inside the loop. Since Go 1.22 the loop variable is per-iteration, so for _, c := range cases { t.Run(c.name, func(t *testing.T){ t.Parallel(); ... }) } is finally safe without the shadow. Also beware shared mutable state across parallel subtests — a map or counter written by several parallel subtests is a data race; give each its own state or guard it.

05 t.Cleanup & t.TempDir — tidy by construction

Resources opened in a test should be torn down with t.Cleanup (runs even on Fatal), and any files should live under t.TempDir() so the OS scratch space is wiped automatically. No manual os.RemoveAll, no leaks between runs.

Manual, leaky on Fatal
dir, _ := os.MkdirTemp("", "t")
defer os.RemoveAll(dir)   // skipped if Fatal jumps out early?
db := open(dir)
// if a later t.Fatalf fires, db is never closed
Test-aware
dir := t.TempDir()        // auto-removed at test end
db := open(dir)
t.Cleanup(func() { db.Close() })  // always runs
// every subtest gets its own fresh dir, too

Each subtest's t.TempDir() is distinct, so parallel subtests never collide on the filesystem. t.Cleanup functions run in reverse order of registration, mirroring defer.

06 Check yourself

In a table-driven test you write got := f(c.in); if got != c.want { t.Fatalf(...) } inside the loop (no subtests). The first case fails. What happens to the remaining cases?

Right. Without t.Run, the loop body is one test function, and t.Fatalf aborts it (via runtime.Goexit) — you lose visibility into every later case. Use t.Errorf in a plain loop to see all failures, or wrap each case in t.Run so a Fatalf only kills that one subtest.
