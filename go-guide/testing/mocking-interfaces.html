Testing & tooling · seams

Test doubles, interfaces & dependency seams.

Go has no built-in mocking magic and rarely needs a library. You test by depending on small interfaces and injecting hand-written fakes at the seam. The same design that makes code testable — narrow interfaces, dependencies passed in — is the design that makes it good.

01 A seam is a place you can substitute

A seam is a point where you can swap the real collaborator for a test one without editing the code under test. In Go the seam is almost always a small interface accepted as a parameter or struct field.

In plain English analogy

Think of a wall socket. Your lamp doesn't care whether the other end is the city grid or a battery in your test bench — it just needs the shape of the plug. An interface is that socket: your code asks for "something that can Save(user)," and in production you plug in Postgres, in tests you plug in a tiny in-memory map. The lamp never changes.

Because Go interfaces are implicit and structural, a fake satisfies the interface just by having the methods — no base class, no @Mock, no codegen required.

02 Hand-written fakes are idiomatic

Define the interface at the consumer, then write a fake struct in your _test.go that implements it. A fake is usually 10 lines — a struct holding canned answers or an in-memory map. Inject it; assert on the outcome.

03 Fake clocks & IO behind interfaces

Anything nondeterministic — the wall clock, the network, random, the filesystem — becomes testable once it sits behind an interface. A fake clock returns a fixed time, so time-dependent logic is suddenly deterministic.

Pro tip synctest

For code that actually sleeps or waits on timers, Go 1.25 promoted testing/synctest to stable: it runs your goroutines on a fake clock that fast-forwards when everything is blocked, so a test of a one-hour timeout finishes instantly and deterministically — no real waiting, no flakiness.

04 httptest.Server for HTTP dependencies

When the dependency is an HTTP API, you often don't even need an interface: httptest.NewServer spins up a real local server with a handler you control, hands you its URL, and your client talks to it over the loopback — no internet, fully deterministic.

client_test.go
func TestFetchName(t *testing.T) {
    srv := httptest.NewServer(http.HandlerFunc(
        func(w http.ResponseWriter, r *http.Request) {
            w.Write([]byte(`{"name":"Ada"}`))
        }))
    defer srv.Close()

    got, err := FetchName(srv.Client(), srv.URL) // talk to the fake
    if err != nil {
        t.Fatalf("FetchName: %v", err)
    }
    if got != "Ada" {
        t.Errorf("got %q, want %q", got, "Ada")
    }
}

This tests the real HTTP round-trip — headers, status codes, JSON decoding — against a server you script, which catches far more than a stubbed-out client method would.

05 Don't over-mock; keep seams small

Mock the edges you don't own (DB, network, clock) — not your own logic. And keep interfaces tiny: a fat interface is miserable to fake and couples the test to every method. "Accept interfaces, return structs," and define those interfaces at the consumer, as small as the job needs.

Gotcha over-mocking · trap

The trap is testing the calls, not the behaviour. A test that asserts "store.Save was called exactly once with these args" passes even when the saved data is wrong, and shatters the moment you refactor the internals — it's coupled to how the code works, not what it produces. Prefer a state-based fake (an in-memory store you read back from) over a call-recording mock. Likewise, a 12-method interface is a smell: nobody wants to write a fake for all 12, and most callers use two. Split it. The bigger the interface, the weaker the abstraction.

See also design

Small, deep modules behind narrow interfaces are exactly what makes code both testable and maintainable — see Information hiding in the Philosophy of Software Design guide.

06 Check yourself

You need to test a service that depends on a payment gateway. Which is the most idiomatic Go approach?

Right. Depend on a narrow interface defined at the consumer and inject a fake — that's the Go grain: no codegen, no framework, a fake you can read in one screen. Mock libraries that record calls couple you to internals; live sandboxes make tests slow and flaky. Mock the edges you don't own, keep the seam small, and assert on the result.
