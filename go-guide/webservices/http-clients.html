HTTP clients, timeouts & resilience.

Calling another service is where Go programs hang in production. http.Get and the default client have no timeout — one slow upstream can pin a goroutine forever. This lesson is the safe way to make outbound requests: a configured http.Client, per-request deadlines via context, body draining, and connection reuse.

01 http.Get is a production footgun

http.Get and http.DefaultClient have Timeout == 0, which means wait forever. For anything real, create your own http.Client with a Timeout set.

In plain English analogy

The default client is a phone call with no hang-up button. If the other side never answers, you hold the line forever — and every held line is a goroutine and a socket you can't get back. A Timeout is the "I'll wait 5 seconds, then hang up" rule that keeps you from running out of phones.

No timeout — can hang forever
// http.Get uses http.DefaultClient: Timeout == 0
resp, err := http.Get("https://api.example.com/x")
A bounded, reusable client
var client = &http.Client{Timeout: 5 * time.Second}
resp, err := client.Get("https://api.example.com/x")

Client.Timeout is a whole-request budget: connect + send + read headers + read the entire body. For finer control — or to cancel mid-flight — reach for context (next).

02 Per-request deadlines with context

Build the request with http.NewRequestWithContext(ctx, ...). A ctx from context.WithTimeout gives that one call its own deadline and lets a caller cancel it (e.g. the user disconnected).

Gotcha trap

The zero-value default client has no timeout. http.Get, http.Post and a bare &http.Client{} will all block indefinitely on a dead or slow peer. Always set Client.Timeout and pass a context deadline (they cover different scopes), and remember defer cancel() — skipping it leaks the timer until the deadline fires.

03 Always close — and drain — the body

When err == nil, resp.Body is an open stream you must defer resp.Body.Close(). To let the connection be reused, also read the body to EOF (drain it) before closing.

An unread, unclosed body holds a TCP connection out of the pool — do it on every request and you leak connections until the process dies. The canonical shape:

call.go
resp, err := client.Do(req)
if err != nil {
    return err // on error, resp is nil — nothing to close
}
defer resp.Body.Close()                  // 1. always close

var out User
if err := json.NewDecoder(resp.Body).Decode(&out); err != nil {
    return err
}
io.Copy(io.Discard, resp.Body)           // 2. drain leftovers so the
                                         //    connection can be reused
if resp.StatusCode >= 400 {
    return fmt.Errorf("upstream: %s", resp.Status)
}
Pro tip check status yourself

A non-2xx response is not a Go error — err is only set for transport failures (DNS, connection, timeout). You must inspect resp.StatusCode / resp.Status yourself. A "successful" Do can still be a 500.

04 Reuse one client; tune the Transport

Create one http.Client and share it. Its Transport holds the connection pool, so a per-request client throws pooling away and re-dials (and re-TLS-handshakes) every time.

For high-throughput callers, tune the shared Transport — raise idle connections per host, set dial/TLS sub-timeouts. We build the client and print its config back (no network call needed) so the values are exact:

Gotcha trap

A new Client (or Transport) per request defeats connection pooling. Each fresh transport keeps its own idle-connection pool, so connections are never reused — you pay a TCP+TLS handshake every call and can exhaust ephemeral ports under load. The default MaxIdleConnsPerHost is just 2, which silently throttles a hot path even with one shared client. Make the client once, raise per-host idle conns if you call one host hard.

05 Retries & backoff (sketch)

Retry only idempotent requests and only retryable failures (timeouts, connection resets, 429/503). Back off exponentially with jitter and cap attempts, and always respect the parent context's deadline.

retry.go
func getWithRetry(ctx context.Context, url string) (*http.Response, error) {
    var lastErr error
    backoff := 100 * time.Millisecond
    for attempt := 0; attempt < 3; attempt++ {
        req, _ := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
        resp, err := httpClient.Do(req)
        if err == nil && resp.StatusCode < 500 {
            return resp, nil                 // success or a non-retryable 4xx
        }
        if resp != nil {
            io.Copy(io.Discard, resp.Body)   // drain before discarding
            resp.Body.Close()
        }
        lastErr = err
        select {
        case <-ctx.Done():
            return nil, ctx.Err()            // honour the deadline
        case <-time.After(backoff):
            backoff *= 2                     // exponential (add jitter in prod)
        }
    }
    return nil, lastErr
}
See also in this guide

Cancellation and deadlines flow through context.Context — the same value you pass to NewRequestWithContext. See Context: cancellation & deadlines for how WithTimeout, WithCancel and ctx.Done() work end to end.

06 Check yourself

Your service calls one upstream thousands of times a second and creates &http.Client{Timeout: 5*time.Second} inside each handler. Latency is fine but you keep running out of ephemeral ports. Why?

Right. The connection pool lives on the Transport, which lives on the Client. A per-request client gets a brand-new transport whose idle pool starts empty, so nothing is reused — every request dials a fresh TCP (and TLS) connection, burning ephemeral ports. Create one shared client (a single http.Client is safe for concurrent use) and reuse it everywhere.
