Building JSON APIs & validation.

A clean JSON handler is four moves: decode the body safely, validate the input, respond in one consistent envelope, and fail with the right status and a sanitized message. Two tiny helpers — decodeJSON and writeJSON — make every handler read the same.

01 Decode the body — safely

Decode with json.NewDecoder(r.Body).Decode(&req), but first cap the body with http.MaxBytesReader and call dec.DisallowUnknownFields(). Then actually check the returned error — a swallowed Decode error is the #1 JSON-API bug.

In plain English analogy

Decoding a request body is like accepting a parcel at a loading dock. You weigh it at the door (MaxBytesReader) so nobody backs a truck in, you reject boxes with mystery extra labels (DisallowUnknownFields), and you sign for it only after checking the contents (the Decode error). Skip any step and you've let the warehouse fill with junk you can't account for.

A decoder ignores unknown JSON keys by default, so a typo'd field like "emial" silently becomes the zero value. DisallowUnknownFields turns that into a clear 400 instead of a confusing "why is email empty?" bug at 2am.

decode.go
// decodeJSON caps the body, rejects unknown fields, and surfaces the error.
func decodeJSON[T any](w http.ResponseWriter, r *http.Request, dst *T) error {
    r.Body = http.MaxBytesReader(w, r.Body, 1<<20) // 1 MiB ceiling
    dec := json.NewDecoder(r.Body)
    dec.DisallowUnknownFields()                     // typos/extra keys -> error
    if err := dec.Decode(dst); err != nil {
        return err                                  // NEVER ignore this
    }
    return nil
}

02 Validate before you trust

Decoding proves the JSON is well-formed; it does not prove the data is valid. A separate Validate() method (or a struct-tag validator) is where "email required, age > 0" lives — and it returns a clear, per-field reason.

For small APIs a hand-rolled Validate() on the request type is plenty and dependency-free. Reach for a library (e.g. go-playground/validator with validate:"required,email" tags) once the rules multiply. Either way, run it right after decode, before any business logic touches the value.

validate.go
type CreateUser struct {
    Name  string `json:"name"`
    Email string `json:"email"`
    Age   int    `json:"age"`
}

func (c CreateUser) Validate() error {
    var errs []error
    if c.Name == "" {
        errs = append(errs, errors.New("name is required"))
    }
    if !strings.Contains(c.Email, "@") {
        errs = append(errs, errors.New("email is invalid"))
    }
    if c.Age < 0 {
        errs = append(errs, errors.New("age must be >= 0"))
    }
    return errors.Join(errs...) // nil when no problems
}

03 One envelope, one writeJSON

Respond through a single writeJSON helper that sets Content-Type: application/json, writes the status code first, then encodes the body. Wrap every payload in a consistent envelope so clients parse success and failure the same way.

The order matters: WriteHeader(status) must come before the first Write (encoding the body counts). Set the header, then the status, then the body — and the status you send must match the body you send (don't return 200 with an error envelope).

respond.go
type envelope struct {
    Data  any    `json:"data,omitempty"`
    Error string `json:"error,omitempty"`
}

func writeJSON(w http.ResponseWriter, status int, body any) {
    w.Header().Set("Content-Type", "application/json")
    w.WriteHeader(status)                 // status BEFORE the body
    _ = json.NewEncoder(w).Encode(body)   // encoder adds the trailing \n
}

func writeError(w http.ResponseWriter, status int, msg string) {
    writeJSON(w, status, envelope{Error: msg}) // status matches the body
}

04 The handler, end to end

Decode → validate → do work → respond. The handler stays flat and readable because the messy parts live in decodeJSON/writeJSON; each failure exits early with the matching status code (400 bad JSON, 422 invalid data, 201 created).

05 Don't leak internals; match status to body

Send the client a safe, generic message and put the gory detail in your logs. A raw err.Error() in the response can leak a SQL query, a file path, or a host name — and a 500 body with a 200 status confuses every client.

Leaks internals, wrong status
// returns 200 with the raw DB error in the body
w.WriteHeader(http.StatusOK)
fmt.Fprintf(w, `{"error":%q}`, err.Error())
// -> {"error":"pq: relation \"users\" ..."}
Generic to client, detail to logs
// log the cause; tell the client only what's safe
slog.Error("create user", "err", err)
writeError(w, http.StatusInternalServerError,
    "something went wrong") // body matches the 500
Gotcha trap

Three quiet killers in JSON handlers: (1) ignoring the Decode error — malformed JSON sails through and fields are zero values; (2) no http.MaxBytesReader — a single huge or slow body can exhaust memory (a denial-of-service); (3) status/body mismatch — calling WriteHeader(200) and then writing an error envelope, or writing the body before the status so Go silently sends 200 anyway. Decode-check, cap the body, and send the status that matches what you're about to write.

06 Check yourself

A handler does json.NewDecoder(r.Body).Decode(&req) but never checks the returned error, and never calls DisallowUnknownFields. A client POSTs {"naem":"Ada"} (note the typo). What happens?

Right. By default encoding/json ignores keys that don't map to a struct field, so "naem" is dropped and Name stays "". With the error unchecked, nothing flags it. The fix is two lines: call dec.DisallowUnknownFields() so the typo becomes an error, and actually check the Decode error to return a clean 400.
