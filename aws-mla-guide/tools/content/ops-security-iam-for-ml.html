Operate · IAM for ML

Execution roles for every ML job — no long-lived keys.

SageMaker jobs and endpoints assume IAM execution roles with least-privilege policies. Training reads S3; endpoints invoke nothing unless you allow it. MLA-C02 punishes access keys in notebooks and overly broad s3:* on production roles.

01 Role per workload

Separate roles for Studio users, training, processing, endpoint, and Pipeline execution. Each gets only the S3 prefixes, KMS keys, and ECR repos it needs.

Training role
Read train/validation S3; write output/model; optional VPC access; PassRole only if needed.
Processing role
Read/write processing I/O buckets; Glue catalog read if joining tables.
Endpoint role
Pull model artifact from S3; decrypt with KMS; often no broad S3 write.
Pipeline role
Start jobs, register models, create endpoints — scoped to account resources.

02 Least privilege patterns

Do
  • Resource-scoped S3 ARNs per prefix
  • KMS via key policy + role
  • Condition keys: vpc, source account
  • Separate dev vs prod roles
Don’t
  • IAM user keys in Studio notebook
  • s3:* on entire account
  • Same role for train and human admin
  • Star actions on sagemaker:*
PassRole trap gotcha

Pipeline/training must iam:PassRole to the specific execution role ARN — not *. Stems about “pipeline fails to start training” often missing PassRole.

03 Bedrock & Lambda IAM

Bedrock invoke from Lambda/Agent: role needs bedrock:InvokeModel on allowed FM ARNs. Knowledge Bases add OpenSearch/S3/Vectors permissions. Use resource-based policies where Bedrock writes to your bucket.
