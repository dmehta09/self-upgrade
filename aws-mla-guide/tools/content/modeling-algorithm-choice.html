Model development · algorithm choice

Match the problem to the algorithm.

MLA-C02 stems rarely ask you to derive math — they ask which AWS-friendly approach fits the data shape, interpretability need, and latency budget. Tabular vs text, linear vs tree ensemble, classic NLP vs foundation models: pick from constraints, not brand loyalty.

01 Tabular: linear vs tree ensembles

Structured rows with mixed numeric/categorical features → start with linear models when you need speed and interpretability; reach for XGBoost / tree ensembles when interactions and non-linearity dominate and you have enough rows.

In plain English analogy

Linear models are a straight ruler on a whiteboard — fast to draw, easy to explain to a regulator. XGBoost is a contour map — it bends around hills in the data but is harder to justify line-by-line.

30-day readmission risk from vitals + ICD codes. Regulators want feature weights → logistic regression or linear learner with Clarify. XGBoost only if accuracy gap justifies opaque scores.
Ledger Bank
Fraud on millions of card swipes with weak labels and heavy feature crosses → XGBoost or built-in SageMaker tabular algorithms; scale with managed training, not hand-tuned rules.
Linear wins when…
Interpretability, sparse high-dim text (TF-IDF), baseline speed, or regulatory “show the coefficient.”
Trees win when…
Non-linear interactions, heterogeneous tabular features, leaderboard accuracy on structured data.

02 Cross-validation & NLP classic vs FM

Use k-fold cross-validation on tabular sets when data is limited and i.i.d.; hold out a final test set you never tune on. For NLP, classic pipelines (tokenize → TF-IDF → linear) still win on small, domain-specific keyword tasks; foundation models win on open-ended language understanding.

Classic NLP
  • Fixed label set, keyword/regex-ish patterns
  • Tiny data, must run on CPU cheaply
  • Blazing latency, no GPU budget
  • SageMaker built-in BlazingText / linear on bag-of-words
Foundation model
  • Open-ended generation or nuanced intent
  • RAG over policy docs (Bedrock + KB)
  • Multilingual or long-context reasoning
  • Fine-tune/PEFT when prompt+RAG plateau
Common trap gotcha

FM for every text stem. “Classify support tickets into five queues” with 10k labeled rows → classic NLP or small fine-tune beats invoking a large FM per ticket on cost and latency. Reserve FMs for language-heavy, open-vocabulary tasks.

03 Exam chooser quiz

Acme Health must explain which vitals drive readmission scores for auditors. Data is tabular, 50k rows. Best first algorithm?

Right. “Explain to auditors” + tabular → linear first. Transformers on raw vitals is overkill; XGBoost without Clarify/SHAP fails the explainability constraint.

04 Exam rapid-fire

When do you pick XGBoost over linear on tabular data?core
Model answer

When non-linear feature interactions matter, you have enough rows to avoid severe overfit, and interpretability is not the top constraint — or you pair trees with SageMaker Clarify for post-hoc explanations.

Say it out loud say it

"Linear when explainability or speed wins; XGBoost when tabular interactions need accuracy and I can justify with Clarify if asked."

Why k-fold CV instead of a single train/validation split?warm-up
Model answer

Limited data → k-fold gives a stabler estimate of generalization and reduces luck of one split. Still keep a untouched holdout for final reporting.

Say it out loud say it

"K-fold when data is scarce; never tune on the final test set."

Ledger Bank: classify merchant category from short descriptions — FM or classic?stretch
Model answer

Fixed MCC taxonomy + millions of short strings → start classic (BlazingText / linear on embeddings) or small fine-tune for cost. FM per transaction fails latency/cost unless volume is low or labels are noisy/open-ended.

Say it out loud say it

"Closed label set at scale → classic NLP or small model; FM when language is open-ended or RAG is required."
