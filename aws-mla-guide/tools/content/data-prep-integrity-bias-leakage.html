Data preparation · integrity · bias · leakage

Clean data beats a fancier algorithm.

Domain 1 heavy hitters: leakage (future info in training), label quality, and bias in datasets. SageMaker Clarify catches many issues pre-training — but only if your splits and features are designed correctly first.

01 Leakage — the silent killer

Leakage means the model sees information at train time that won't exist at predict time. Metrics look amazing; production fails. Underline any feature derived from after the prediction moment.

In plain English analogy

Leakage is studying for a spelling test using the answer key. You ace practice and fail the real exam because you never learned — you cheated with future information.

Target leakage
Feature encodes the label (e.g., "readmitted=yes" column in readmission model).
Temporal leakage
Future hospital visits, future transactions included in aggregates.
Preprocessing leakage
Fit scaler/encoder on full dataset including test — fit on train only.
Duplicate patients / cards
Same entity in train and test via random split — use group splits.

02 Acme Health leakage story

Acme's first readmission model scored 0.98 AUC in Studio — then failed in the ward. Root cause: "days_until_followup" was computed from post-discharge appointments, unavailable at admission scoring time.

1

Symptom

Training metrics too good; live scores barely beat random.

2

Diagnosis

Feature timeline audit — map each column to "available at admission?"

3

Fix

Drop leaky columns; rebuild Processing job with point-in-time joins only.

4

Prevent

Time-based split + Clarify + Model Monitor on feature distributions in prod.

Common trap gotcha

Fix leakage with more HPO. No amount of tuning saves a feature that smuggles the answer. Exam: drop or redesign features before retraining.

03 Label quality & Clarify bias cues

Garbage labels → garbage model. Clarify measures pre-training bias (dataset representation) and post-training bias (prediction disparities). Run both before Registry approval.

Label issues
  • Delayed fraud confirmations (Ledger)
  • Mis-coded discharge statuses (Acme)
  • Class imbalance — 0.1% fraud
  • Fix: relabel pipeline, weights, sampling
Clarify bias metrics
  • CI (Class Imbalance) — label ratio by group
  • DPL (Difference in Positive Labels)
  • DI (Disparate Impact) — exam favorite
  • Runs in Processing or training step

Stem: "Model shows high approval for one zip code segment vs others on the same income band. Check dataset before retraining." First step?

Right. Dataset disparity → Clarify pre-training bias. Guardrails are GenAI text filters; bigger instances don't fix label imbalance.

Pre-training vs post-training Clarify?stretch
Model answer

Pre-training bias metrics analyze the dataset (label distribution across facets). Post-training analyzes model predictions vs labels for disparate impact. Both gate promotion — pre catches bad data; post catches bad model behavior.
