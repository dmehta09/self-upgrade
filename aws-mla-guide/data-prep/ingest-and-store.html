Data preparation · ingest & store

Land ML data in the right place — lake, catalog, stream.

Domain 1 starts here: S3 as the default lake, Glue Data Catalog for discoverable metadata, Kinesis / Firehose for streaming ingest. Pick Athena vs Processing based on whether you need one-off SQL or repeatable heavy transforms.

01 S3 lake + Glue Catalog

Raw ML data lives in S3 prefixes with lifecycle and encryption. Glue Crawlers and the Data Catalog make tables visible to Athena, Glue ETL, and SageMaker — without copying data into a proprietary warehouse first.

In plain English analogy

S3 is the warehouse floor where pallets arrive. Glue Catalog is the inventory system on a clipboard — it doesn't hold the boxes, but everyone knows which aisle has what schema.

S3 prefixes
raw/, curated/, features/ — partition by date/tenant for cost and query speed.
Glue Data Catalog
Central metadata: databases, tables, schemas, partitions — shared by Athena, Glue jobs, EMR, SageMaker.
Lake Formation
Column/row-level permissions on cataloged data — exam cue for multi-team governance.
Encryption
SSE-S3 or SSE-KMS; bucket policies block public access; VPC endpoints for private ingest.

02 Batch vs streaming ingest

Nightly EHR dumps → S3 batch upload or DataSync. Live card swipes → Kinesis Data Streams or Firehose into S3/OpenSearch. Match velocity to the fraud or clinical use case.

flowchart TD
  src["Data source"] --> vel{"Velocity?"}
  vel -->|batch files| s3["S3 + Crawler"]
  vel -->|streaming events| kin{"Need transforms?"}
  kin -->|minimal| fh["Kinesis Firehose → S3"]
  kin -->|custom / ML prep| ks["Kinesis Data Streams → Lambda / Flink"]
  s3 --> cat["Glue Data Catalog"]
  fh --> cat
  ks --> cat

03 Athena vs SageMaker Processing

Athena = ad hoc SQL over cataloged S3 (explore, filter, aggregate). SageMaker Processing = repeatable, heavy transforms with custom code/containers feeding training. Glue ETL sits between for scheduled Spark jobs.

Athena
  • Serverless SQL on S3 via Glue Catalog
  • Quick exploration, feature prototyping
  • Pay per data scanned — partition to save cost
  • Not the answer for complex Python feature pipelines
SageMaker Processing
  • Managed compute for sklearn/Pandas/custom scripts
  • Input/output S3 paths wired to Training jobs
  • Repeatable in Pipelines — prod feature prep
  • Exam pick when stem says "same transform every night"
Common trap gotcha

Athena for nightly 2 TB sklearn feature engineering. Athena is SQL exploration. Complex row-level ML prep → Glue ETL or SageMaker Processing. Acme's de-identification joins are a Glue/Processing job, not a one-off SELECT.

Acme lands nightly 500 GB FHIR bundles in S3. Data scientists need to explore row counts by ward before building features. First tool?

Right. Exploration/SQL → Athena. Training comes after curated features exist.

04 Exam rapid-fire

Default store for ML raw data on AWS?warm-up
Model answer

S3 data lake with governed prefixes, encryption, and Glue Data Catalog metadata. Streaming sources feed in via Kinesis/Firehose.

Say it out loud say it

"S3 lake + Glue Catalog — stream in with Kinesis or Firehose when events are live."

Firehose vs Kinesis Data Streams?core
Model answer

Firehose = fully managed delivery to S3/Redshift/OpenSearch with optional format conversion — least ops for "stream to lake." Data Streams = lower-level shards for custom consumers, real-time analytics, or multiple parallel apps.

Say it out loud say it

"Firehose to land streams in S3; Data Streams when I need custom real-time consumers."

When Athena vs Processing for feature prep?stretch
Model answer

Athena for SQL exploration and simple aggregations on cataloged S3. SageMaker Processing (or Glue ETL) for repeatable, code-heavy transforms that must run on a schedule and feed Training jobs with identical logic every time.

Say it out loud say it

"Athena to explore; Processing or Glue to productionize transforms."
