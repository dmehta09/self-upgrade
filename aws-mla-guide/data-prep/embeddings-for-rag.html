Data preparation · embeddings for RAG

Chunk, embed, index — the data path behind Knowledge Bases.

RAG quality is mostly data prep: split documents into chunks, embed with a Bedrock embedding model, store vectors in OpenSearch Serverless (or another supported vector store). Bedrock Knowledge Bases automates ingest → embed → retrieve for GenAI exams.

01 RAG data path

At query time the FM doesn't memorize your PDFs — it retrieves similar chunks and grounds the answer. Bad chunking = wrong citations and hallucinations dressed as policy.

flowchart LR
  docs["S3 docs / PDFs"] --> chunk["Chunk · split"]
  chunk --> embed["Bedrock embed model"]
  embed --> vec["Vector store · OpenSearch"]
  query["User query"] --> qembed["Embed query"]
  qembed --> vec
  vec --> topk["Top-K chunks"]
  topk --> llm["Bedrock FM + prompt"]
Chunking
Split by page, heading, or fixed token windows with overlap — balance context vs precision.
Embedding model
Bedrock Titan Embeddings, Cohere Embed, etc. — same model family for ingest and query.
Vector store
OpenSearch Serverless vector collection — default exam pairing with Knowledge Bases.
Knowledge Bases
Managed sync from S3 → chunk → embed → index; wires retrieval into Bedrock invoke.

02 Chunking decisions

Smaller chunks = precise retrieval, less context per hit. Larger chunks = more context, muddier matches. Clinical protocols (Acme) often chunk by section header; regulatory PDFs (Ledger) by article number.

Small chunks (~256 tokens)
  • Better precision for narrow questions
  • More index rows — higher storage cost
  • May miss cross-paragraph reasoning
Large chunks (~512–1024 tokens)
  • Richer context per retrieval
  • Risk of irrelevant filler in prompt
  • Good for narrative clinical guidelines
Overlap matters tip

Use 10–20% token overlap between chunks so sentences split across boundaries still appear whole in at least one chunk. Acme's discharge checklist spans pages — overlap prevents half-steps from vanishing.

03 Acme Health Knowledge Base setup

Acme stores clinical guidelines in S3. A Knowledge Base syncs nightly, embeds with Titan Text Embeddings, indexes in OpenSearch Serverless. Clinicians query via Bedrock — citations point to source chunks.

Common trap gotcha

Fine-tune the FM to memorize PDFs. Exam stems about internal document Q&A with fresh doc updates → RAG (Knowledge Base + embeddings), not full fine-tune. Fine-tune when behavior/style must change, not for weekly policy PDF drops.

Acme adds new sepsis guidelines weekly. They need cited answers without retraining Claude each time. Data architecture?

Right. Frequently updated unstructured docs + citations → RAG stack. Feature Store is tabular; scratch LLM training violates least-ops.

04 Exam rapid-fire

What are the three RAG data prep steps?warm-up
Model answer

Chunk documents, embed chunks with a Bedrock embedding model, store vectors in a vector database (OpenSearch Serverless with Knowledge Bases). At query time embed the question and retrieve top-K similar chunks.

Say it out loud say it

"Chunk, embed, index — then retrieve at query time."

Why OpenSearch Serverless in AWS RAG answers?core
Model answer

Bedrock Knowledge Bases natively integrates with OpenSearch Serverless as a vector store — managed sync, metadata filtering, and retrieval API without building a custom vector DB on EC2.

Say it out loud say it

"Knowledge Bases + OpenSearch Serverless is the managed RAG vector path."

New docs land daily. Re-embed everything or incremental sync?stretch
Model answer

Knowledge Base incremental sync from S3 — new/changed objects are chunked and embedded without rebuilding the entire index manually. Exam "least ops" prefers managed KB sync over DIY Lambda re-embed scripts unless custom logic is required.

Say it out loud say it

"Daily doc drops → Knowledge Base sync from S3, not full manual re-embed."
