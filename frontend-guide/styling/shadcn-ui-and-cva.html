shadcn/ui & the cn()/cva pattern

shadcn/ui isn’t a component library you install — it’s accessible component source you copy into your repo and own. It pairs Radix primitives for behavior with cva for typed variants and cn() for class merging.

00 The idea

shadcn/ui is copy-in components you own — not an installed dependency. Behavior comes from Radix; variants come from cva; classes merge via cn().

You run a CLI that drops real .tsx files into your project. From then on the code is yours: edit markup, restyle, delete what you don’t need. No version pinning, no fighting a library’s API to change a border.

Think of it like… analogy

A traditional component library is a sealed appliance — it works, but you can’t open the case, and you’re stuck with the vendor’s knobs. shadcn is IKEA furniture: it ships as parts you assemble and own, so when you want a different leg, you just swap it. The trade: you also maintain it.

What you get
Real source files in components/ui/ — not a node_modules package re-exported.
Accessibility
Built on Radix primitives (focus management, keyboard nav, ARIA) so the hard a11y is handled.
Styling
Tailwind utilities + CSS variables for theming; June-2026 default style is new-york with OKLCH colors.

01 Adding a component

The CLI is npx shadcn@latest. It writes the component into your tree, wiring up cn() and your theme. (The old shadcn-ui package was renamed — shadcn is the current CLI.)

terminal
# one-time init, then add components you own
npx shadcn@latest init
npx shadcn@latest add button dialog
# → writes components/ui/button.tsx, dialog.tsx into YOUR repo

02 The cva + cn() pattern

cva (class-variance-authority) declares a base class plus named variants and gives you a fully typed function. cn() then merges the generated classes with any caller overrides — twMerge(clsx(...)) so conflicts resolve cleanly.

button.tsx
const button = cva("inline-flex items-center rounded-md", {
  variants: {
    variant: { default: "bg-primary text-white", ghost: "bg-transparent" },
    size:    { sm: "h-8 px-3", md: "h-10 px-4" },
  },
  defaultVariants: { variant: "default", size: "md" },
});

// data-slot, ref as a normal prop (no forwardRef in 2026)
function Button({ className, variant, size, ...props }: Props) {
  return <button data-slot="button"
    className={cn(button({ variant, size }), className)} {...props} />;
}

Variant props are type-checked from the cva config, so <Button variant="ghost" size="sm" /> autocompletes and a typo fails to compile. The trailing className through cn() lets callers override safely.

Common trap gotcha

shadcn/ui is not a dependency — there’s no package to bump. The code lives in your repo, so you maintain it; upstream fixes aren’t auto-applied. Also note the CLI rename: it’s npx shadcn@latest, not the old shadcn-ui. And modern components use ref as a normal prop — no forwardRef.

03 shadcn vs a traditional library

The difference is ownership. A packaged library gives you upgrades for free but hides the source; shadcn gives you the source but makes you the maintainer.

Dimensionshadcn/uiTraditional library (e.g. MUI)
OwnershipSource in your repo — you own itInstalled package — vendor owns it
CustomizationEdit the file directly, unlimitedTheme API / overrides; bounded by what’s exposed
AccessibilityRadix primitives under the hoodLibrary’s own a11y implementation
UpgradesManual — you maintain the codeBump the version
BundleOnly the components you copied inWhatever the package ships (tree-shaking varies)

Your designer wants a Button with a totally custom focus ring and layout that the library’s theme API can’t express. Why does shadcn/ui make this easy?

Right. shadcn copies real source into your project, so customization is just editing your own file. The trade-off is that you also own maintenance — there’s no package to upgrade.

04 Interview rapid-fire

What actually is shadcn/ui?core
Model answer

It’s a collection of accessible components you copy into your project via a CLI — not an installed dependency. Behavior comes from Radix primitives, styling from Tailwind plus CSS variables, and variants from cva. Once added, the source is yours to edit.

Say it out loud say it

“It’s copy-in components built on Radix, not a library you install. The CLI drops the source into your repo and you own it from there.”

Explain the cva + cn() pattern.core
Model answer

cva defines a base class plus typed variants (variant, size) and returns a function that produces the right class string for given props. cn() — twMerge(clsx(...)) — merges that with any caller className, joining conditionals and resolving Tailwind conflicts so overrides win predictably.

Say it out loud say it

“cva gives me typed variants, cn() merges them with caller overrides via twMerge(clsx(...)) — so variants are safe and overridable.”

What’s the trade-off of “owning the code”?stretch
Model answer

Total customization in exchange for maintenance. Because the components live in my repo, I can change anything — but upstream bug fixes and improvements aren’t auto-applied; I pull them in deliberately. For a design system I control, that ownership is usually a win; for a team that wants hands-off upgrades, a packaged library may fit better.

Say it out loud say it

“You trade free upgrades for full control. The code is yours, so customization is unlimited — but you own maintenance and pull upstream fixes manually.”
