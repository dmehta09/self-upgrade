TanStack Query: server-state

Server data isn’t your state — it’s a borrowed copy that can go stale. TanStack Query treats it that way: it caches, deduplicates, and quietly refreshes, deleting the whole useEffect-fetch-into-useState ritual.

00 The idea

TanStack Query is an async server-state cache, not a client store. You describe what to fetch; it owns the when, the caching, and the freshness.

Each query has a key (the cache address) and a fetcher. Query gives you data, isPending, and error, dedupes concurrent requests for the same key, and shares one cache entry across every component that asks for it.

Think of it like… analogy

A smart fridge with best-before dates. It keeps a copy of what you fetched so you eat instantly. staleTime is the “best before”: once it passes, the fridge quietly restocks in the background while you keep eating what’s there. gcTime is the bin schedule — how long untouched leftovers sit before they’re thrown out entirely.

Query key
A serializable array like ['todos', userId] that identifies a cache entry. Same key = shared data & one in-flight request.
isPending vs isFetching
isPending (renamed from isLoading) = no cached data yet, first load. isFetching = a request is in flight, even a background refresh over existing data.
staleTime vs gcTime
staleTime = how long data is considered fresh (no refetch). gcTime (renamed from cacheTime) = how long an unused entry survives before garbage collection. They’re unrelated knobs.

01 Reading data with useQuery

One hook replaces a fetch effect, a loading flag, an error flag, and a cache. Set staleTime to control how eagerly it revalidates — the single most useful knob.

useTodos.ts
const { data, isPending, error, isFetching } = useQuery({
  queryKey: ['todos', userId],   // cache address
  queryFn: () => fetchTodos(userId),
  staleTime: 60_000,             // fresh for 60s — no refetch in that window
  // gcTime defaults to 5min: how long an UNUSED entry survives
});

if (isPending) return <Spinner />;   // first load, no cached data
if (error) return <Error />;
// isFetching can be true here during a quiet background refresh
Common trap gotcha

TanStack Query is not a Redux replacement. It only manages server data — the cached copy of what an API owns. True client state (theme, modals, the logged-in user, form drafts) still belongs in Zustand, Context, or useState. Don’t shove UI flags into query keys.

02 Writes: mutate, then invalidate

A useMutation sends the change; afterwards you invalidateQueries the affected keys so the cache refetches and the UI reflects the new truth. This is how you keep lists in sync after a create/update/delete.

useAddTodo.ts
const qc = useQueryClient();
const addTodo = useMutation({
  mutationFn: (text: string) => api.addTodo(text),
  onSuccess: () => {
    // mark the list stale -> Query refetches it from the server
    qc.invalidateQueries({ queryKey: ['todos', userId] });
  },
});

addTodo.mutate('Ship it');

For instant feedback, optimistically write the cache in onMutate and roll back in onError if the server rejects it.

optimistic.ts
useMutation({
  mutationFn: toggleTodo,
  onMutate: async (id) => {
    await qc.cancelQueries({ queryKey: ['todos'] });
    const prev = qc.getQueryData(['todos']);        // snapshot
    qc.setQueryData(['todos'], (t) => toggle(t, id)); // optimistic write
    return { prev };                                 // pass to onError
  },
  onError: (_e, _id, ctx) => qc.setQueryData(['todos'], ctx.prev), // rollback
  onSettled: () => qc.invalidateQueries({ queryKey: ['todos'] }),  // resync
});

After a successful useMutation that adds a todo, how do you make the cached list show it?

Right. Query can’t know a write happened on the server. You tell it by invalidating the affected key (refetch) or by editing the cache with setQueryData — never by mirroring into useState.

03 Interview rapid-fire

Is TanStack Query a state manager like Redux?core
Model answer

No. It manages server state — a cache of async data the backend owns, with deduping, background refetch, and revalidation. Redux/Zustand manage client state. They’re complementary: Query for fetched data, a client store for UI/session.

Say it out loud say it

“It’s a server-state cache, not a Redux replacement. Fetched data goes in Query; theme and session go in a client store.”

What’s the difference between staleTime and gcTime?core
Model answer

staleTime controls freshness: how long data is trusted before a refetch can fire. gcTime (formerly cacheTime) controls retention: how long an entry with no active observers lingers before garbage collection. One governs refetching; the other governs deletion.

Say it out loud say it

“staleTime is best-before — when it refetches. gcTime is the bin schedule — when an unused entry gets dropped. Independent knobs.”

How do you keep the UI in sync after a mutation?stretch
Model answer

Two ways. Simplest: invalidateQueries the affected keys in onSuccess so Query refetches the source of truth. For snappy UX: optimistically setQueryData in onMutate, snapshot the old value, roll back in onError, and invalidateQueries in onSettled to reconcile.

Say it out loud say it

“Invalidate the key to refetch, or optimistically patch the cache with a snapshot to roll back on error, then invalidate on settled.”
