Forms: react-hook-form + Zod

react-hook-form keeps inputs uncontrolled so typing doesn’t re-render your whole form, and Zod gives you one schema that defines the shape once — then validates it on both the client and the server.

00 The idea

RHF tracks inputs via refs, not state, so keystrokes don’t re-render the tree. Zod is the single source of truth for the form’s shape, reused everywhere.

You register each field to wire it up, handleSubmit to validate-then-submit, and read formState.errors to show messages. The zodResolver bridges your Zod schema into RHF’s validation.

Think of it like… analogy

One Zod schema is the master blueprint for the form — the door frame everything must fit. The browser checks the blueprint for fast feedback while the user types; the server checks the same blueprint before trusting anything. One drawing, two checkpoints — so client and server can never drift apart.

register / handleSubmit
register('email') wires an input to RHF. handleSubmit(onValid) runs validation first and only calls your handler with typed, valid data.
zodResolver
From @hookform/resolvers/zod. It runs your Zod 4 schema as RHF’s validator and maps each issue into formState.errors.

01 Schema → form

Define the schema, infer the TypeScript type from it for free, then hand it to useForm through the resolver.

schema.ts
import { z } from 'zod'; // Zod 4

export const signupSchema = z.object({
  email: z.string().email('Enter a valid email'),
  password: z.string().min(8, 'At least 8 characters'),
});
export type Signup = z.infer<typeof signupSchema>; // single source of truth
SignupForm.tsx
import { useForm } from 'react-hook-form';
import { zodResolver } from '@hookform/resolvers/zod';

const { register, handleSubmit, formState: { errors } } =
  useForm<Signup>({ resolver: zodResolver(signupSchema) });

<form onSubmit={handleSubmit(onValid)}>
  <input {...register('email')} />
  {errors.email && <p>{errors.email.message}</p>}
</form>

02 Reuse the schema on the server

Import the very same schema in a server action and parse the payload. Client validation is for fast UX; the server check is the one that actually protects you.

actions.ts
'use server';
import { signupSchema } from './schema'; // SAME schema as the client

export async function signup(raw: unknown) {
  const data = signupSchema.parse(raw); // throws on bad input -> never trust the client
  await db.users.create(data);
}
Common trap gotcha

Client validation is UX, not security. Anyone can bypass the browser and POST raw JSON, so you must re-validate on the server with the same schema (schema.parse). Skipping the server check is how invalid or malicious data reaches your database.

Why is react-hook-form uncontrolled by default?

Right. RHF reads values from the DOM via ref on submit instead of mirroring each keystroke into React state — that’s why it re-renders far less than a fully controlled form.

03 Interview rapid-fire

Why is RHF uncontrolled, and why does that matter?core
Model answer

It subscribes to inputs through refs rather than React state, so each keystroke doesn’t trigger a re-render of the form. On large forms that’s a major perf win versus a fully controlled approach where every change re-renders the component.

Say it out loud say it

“It reads inputs via refs, not state, so typing doesn’t re-render the form — which keeps big forms fast.”

What does zodResolver actually do?core
Model answer

It adapts a Zod schema into RHF’s validation pipeline. On submit (or per the mode), RHF runs the schema, and the resolver maps any Zod issues into formState.errors keyed by field — plus you get the inferred type for free.

Say it out loud say it

“It plugs a Zod schema into RHF as the validator and maps Zod errors onto formState.errors per field.”

How do you share validation between client and server?stretch
Model answer

Define one Zod schema in a shared module. The client uses it via zodResolver for inline UX feedback; the server imports the same schema and calls parse on the payload before persisting. One definition guarantees the rules can’t drift, and the server check is the real security boundary.

Say it out loud say it

“One schema in a shared file — zodResolver on the client for UX, schema.parse on the server for security. No drift.”
