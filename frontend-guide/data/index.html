Data & state — three buckets

Most state bugs are filing errors: the right value lives in the wrong place. Sort every piece of state into one of three buckets first, and the tool to use picks itself.

00 The three buckets

Decide who owns the truth before you decide which library: the server, the whole client app, or one screen.

Almost every value in a React app belongs to one of three owners. Confusing them — especially stuffing fetched data into a global store — is the root of stale UIs, refetch storms, and tangled reducers.

Think of it like… analogy

A desk with three drawers. The server-cache drawer holds photocopies of files that really live at the office — they can go out of date. The global-client drawer holds notes only you keep: theme, who’s logged in. The local/URL drawer holds the sticky note on the screen you’re looking at right now. Filing a photocopy in the “your notes” drawer is how copies rot.

Who owns this value?
bucket 1
Server cache
data you fetched → TanStack Query
bucket 2
Global client state
UI / session → Zustand or Context
bucket 3
Local / URL state
one screen → useState or search params
Server cache
A copy of data the server owns — lists, profiles, search results. It can go stale, so it needs refetching, not just storing. Home: TanStack Query.
Global client state
Truth that only the client knows and many screens need — theme, sidebar, the logged-in user object. Home: Zustand (or React Context for low-churn).
Local / URL state
Belongs to one view. Ephemeral toggles → useState; anything shareable or bookmarkable (filters, tabs, page) → the URL. Forms get their own tool, RHF.

01 Start here

Read these in order. The first three are the tools, one per bucket; the last is the decision procedure that ties them together.

TanStack Query

The server-state cache: fetch, dedupe, refresh, and mutate without useEffect spaghetti.

Zustand

A tiny global store for true client state — a shared whiteboard, no prop-drilling.

Forms: RHF + Zod

Uncontrolled, low-re-render forms with one Zod schema shared by client and server.

Where should this state live?

The decision page: a flowchart that routes any value to the right home.
Common trap gotcha

“Global state manager” is not one bucket. Server data does not belong in Redux or Zustand — it’s a remote copy that needs caching and revalidation, which is exactly what TanStack Query gives you. Mixing the two is the most common state-architecture mistake.
