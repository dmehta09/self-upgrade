Hooks, identity & memoization

Hooks let a plain function hold state across renders. The pro-level insight isn’t the API surface — it’s identity: which values stay the same object between renders, and why that decides what re-renders.

00 The idea

A hook is React remembering something for this component across renders — matched up by call order, not by name.

Your function runs top to bottom every render. React doesn’t see your variable names; it lines up each hook call with the slot it used last time, in the same order. That single rule explains the rules of hooks, stale closures, and why refs differ from state.

Think of it like… analogy

Hooks are a row of labeled drawers React opens in the exact same order every render. The 1st useState always opens drawer #1, the 2nd opens drawer #2. Put them behind an if and you open the drawers in the wrong order — now drawer #2’s contents land in the wrong hand.

useState
A value React remembers; updating it schedules a render. Updates batch within an event.
useRef
A mutable box (.current) React keeps around — changing it does not render.
useMemo / useCallback
Cache a value / a function by identity so it’s stable across renders when deps don’t change.

01 useState: functional updates, lazy init, batching

Reach for the functional updater whenever the next value depends on the previous one — it reads the latest state, not the value captured when the closure was created. Pass a function to useState to compute the initial value only once.

Counter.tsx
// Lazy init: readHeavy() runs once, not every render.
const [items, setItems] = useState(() => readHeavy());

function addThree() {
  // Both run; React batches into ONE render.
  setCount(c => c + 1); // functional updater sees latest
  setCount(c => c + 1); // ...so this adds to the first
}

In React 18+ updates are batched even inside promises, timeouts, and native handlers — so multiple setState calls in one tick produce a single re-render.

02 useRef: the mutable box that doesn’t render

A ref is for values that should survive renders but not drive the UI: a DOM node, a timer id, the previous value of a prop. Writing ref.current is a side effect — React neither tracks it nor re-renders.

useInterval.tsx
const timer = useRef<number | null>(null);
// Mutating .current never re-renders the component.
timer.current = window.setInterval(tick, 1000);
// Need the UI to update? That has to be state, not a ref.

Rule of thumb: if changing it should repaint the screen, it’s state. If not, it’s a ref.

03 Identity: useMemo vs useCallback vs useRef

All three exist to keep something stable across renders. They differ in what they stabilize and when it changes. With React Compiler 1.0 (GA, stable in 19.2) most memoization is now automatic — reserve manual ones for measured hotspots.

useMemoThe result of a functionA dependency changesCaching an expensive computation; a stable object/array prop

useRefA mutable { current } boxNever (same object for the component’s life)Holding a value across renders without re-rendering

useCallback(fn, deps) is just useMemo(() => fn, deps) — same machinery, sugar for functions.

Common trap gotcha

Stale closures. A useCallback (or effect) captures the variables in scope when it was created. Omit a value from the deps and the function keeps reading the old one forever — the classic “my counter is stuck at 1” bug. Fix: list every value you read, or use a functional updater to dodge the capture entirely.

04 Rules of hooks & custom hooks

Two rules, both downstream of the call-order model: call hooks only at the top level (never inside conditions, loops, or nested functions), and only from React functions or other hooks. That guarantees a stable call order every render.

A custom hook is just a function whose name starts with use that calls other hooks. It composes stateful logic for reuse — it does not share state between components; each call gets its own.

Breaks call order
function Profile({ id }) {
  if (!id) return null;
  // hook is now conditional
  const [user, setUser] = useState(null);
  return <div>{user?.name}</div>;
}
Stable call order
function Profile({ id }) {
  const [user, setUser] = useState(null);
  // condition AFTER the hooks
  if (!id) return null;
  return <div>{user?.name}</div>;
}

Why must hooks be called in the same order every render?

Right. Hooks are stored in a list keyed by the order they’re called. A conditional hook shifts every later index, so React hands back the wrong slot’s state.

06 Interview rapid-fire

What are the rules of hooks, and why do they exist?core
Model answer

Call hooks only at the top level and only from React functions or custom hooks. React tracks hook state by call order, so a conditional or looped hook shifts the indices and returns the wrong state.

Say it out loud say it

“Top level only, and only from React functions. Hooks are matched by call order, so conditionals would scramble which state you get back.”

useMemo vs useCallback — what’s the difference?core
Model answer

useMemo caches the result of calling a function; useCallback caches the function itself. useCallback(fn, d) is literally useMemo(() => fn, d). Both stabilize identity so a memo child or effect doesn’t see a “new” value every render.

Say it out loud say it

“useMemo memoizes a value, useCallback memoizes a function — same machinery. And in React 19 the compiler does most of it for me anyway.”

Why doesn’t mutating a ref trigger a re-render?stretch
Model answer

A ref is a plain mutable object React hands you and never inspects again. There’s no setter and no subscription, so writing .current can’t schedule work. State has a dedicated setter that tells React to re-render; a ref deliberately doesn’t.

Say it out loud say it

“A ref is just a box React doesn’t watch — no setter, no subscription. If a change needs to show on screen, it has to be state.”
