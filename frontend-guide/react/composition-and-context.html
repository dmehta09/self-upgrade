React · composition

Composition & context

React’s real power isn’t any single API — it’s composition: building complex UIs from small, swappable pieces. Context fits the gaps composition can’t reach, but it’s a sharp tool that’s easy to misuse.

00 The idea

Prefer composition over configuration: pass UI (children/slots) instead of piling up boolean and string props.

When a component takes a dozen flags to cover every variation, it’s usually begging to be split so callers compose the pieces themselves. Context is the escape hatch for values that many distant components need — theme, the current user — without threading props through every layer.

Think of it like… analogy

Lego bricks vs. one giant molded toy. Small bricks snap together into anything — you recombine them endlessly. A single molded toy does exactly one thing; want a variation and you must remold the whole piece. Composable components are bricks; a 12-prop mega-component is the molded toy.

01 Composition over configuration

The simplest lever is children (and named slots). Instead of describing the inside of a component with props, let the caller pass the actual UI. This kills prop-drilling: a value passed through children never threads through the intermediate component.

Prop-drilling
// user threaded through Layout
// only to reach Avatar
<Layout user={user}>
  <Sidebar user={user} />
</Layout>
// Layout & Sidebar both forward `user`
Composition (slots)
// caller passes the UI directly;
// Layout never knows about `user`
<Layout sidebar={<Avatar user={user} />}>
  <Feed />
</Layout>

Compound components take this further: a parent shares implicit state with a related set of children (e.g. <Tabs> with <Tabs.List> and <Tabs.Panel>), so the caller arranges the markup while the parent wires up behavior.

02 Context: for cross-cutting concerns

Context broadcasts a value to every descendant that reads it — ideal for theme, auth, locale: things that are truly global and change rarely. It is not a general state manager. Every consumer re-renders whenever the context value changes, by reference.

In React 19 you render <ThemeContext value={…}> directly as the provider — no .Provider needed. Two guardrails keep context fast: split contexts so unrelated consumers don’t re-render together, and memoize the value so it isn’t a brand-new object every render.

Common trap gotcha

Passing a fresh object literal as the context value re-renders every consumer on each provider render — even when nothing meaningful changed. value={{ user, logout }} is a new object every time. Wrap it in useMemo (or rely on the React Compiler) so identity is stable.

03 Controlled vs uncontrolled

A controlled component’s value lives in React state — you own it via value + onChange. An uncontrolled one keeps its own internal state in the DOM and you read it with a ref when needed. Controlled gives you live validation and a single source of truth; uncontrolled is lighter for simple, fire-and-forget inputs.

Inputs.tsx
// Controlled: React is the source of truth
<input value={name} onChange={e => setName(e.target.value)} />

// Uncontrolled: DOM holds it; read via ref on submit
<input defaultValue="" ref={nameRef} />

Your app is sluggish; profiling shows every screen re-renders whenever anything in a big context object changes. Best first fix?

Right. Context re-renders all consumers on value change. Splitting by concern (plus a memoized value) means a theme change doesn’t re-render auth consumers, and vice-versa. For high-churn shared state, a store like Zustand with selectors is the better tool.

04 Interview rapid-fire

When do you reach for context vs a state library?core
Model answer

Context for low-frequency, truly global values — theme, auth, locale. For frequently changing or finely-sliced shared state, a store (Zustand, or a server-cache like TanStack Query) with selectors, because context re-renders every consumer on any change.

Say it out loud say it

“Context for rarely-changing globals like theme and auth. For hot, granular state I use a store with selectors — context re-renders all consumers, so it’d thrash.”

What’s the classic context re-render pitfall?core
Model answer

Providing a new object literal as the value each render. Since context compares by reference, every consumer re-renders even if the data is identical. Memoize the value, and split contexts so unrelated state doesn’t share a provider.

Say it out loud say it

“A fresh object as the value re-renders every consumer because context checks by reference. I memoize the value and split contexts by concern.”

What do compound components buy you?stretch
Model answer

A flexible, declarative API: the parent owns shared state while the caller arranges the children’s markup freely (<Tabs><Tabs.List/><Tabs.Panel/></Tabs>). You avoid a prop explosion and let consumers compose structure without prop-drilling internal state.

Say it out loud say it

“They give a flexible API — the parent manages shared state, the caller arranges the pieces. No giant prop list, no drilling internal state.”
