React · the render model

Render vs re-render

A “render” is just React calling your component function to get a description of the UI. Knowing what triggers one — and what it actually costs — is the line between guessing at performance and engineering it.

00 The idea

Rendering is React calling your function. Committing is React touching the DOM. Only the second one is expensive.

When state changes, React re-runs your component to get fresh JSX, diffs it against the previous result (reconciliation), and then updates only the real DOM nodes that actually differ (commit). Most “React is slow” instincts are really about confusing step one with step three.

Think of it like… analogy

An architect redrawing a blueprint vs. a builder changing the actual house. Every re-render is a fresh blueprint — cheap to draw. The builder (commit) only swaps the bricks that differ. People panic about “too many blueprints” when the costly part is moving bricks.

Triggers a render
Its own state changed, its parent re-rendered, or a context it reads changed.
Does not, alone
Props “changing” (that only happens because the parent re-rendered), a ref mutating, or a module variable changing.

01 What actually triggers a render

There are exactly three triggers. Internalize them and most “why did this render?” questions answer themselves.

  • State update — setState / useReducer dispatch (with a different value).
  • Parent re-rendered — a parent rendering re-renders its children by default.
  • Context changed — every consumer of that context value re-renders.
Parent.tsx
function Parent() {
  const [count, setCount] = useState(0);
  // Clicking re-renders Parent — and its children, by default.
  return (
    <button onClick={() => setCount(count + 1)}>
      Clicked {count} times
    </button>
  );
}
Common trap gotcha

“Passing new props” doesn’t cause a child to render — the parent re-rendering does. You can’t hand a child new props without re-rendering the parent first, so the parent render is always the real cause.

02 Re-render ≠ DOM update

A re-render that produces the same output commits nothing. React reconciles the new tree against the old one and only the differences reach the DOM. That’s why “it re-rendered” is rarely the problem — an expensive render body or a giant committed diff is.

Under the hood: fiber, in one paragraph optional

React builds a “fiber” tree — a work-in-progress copy of your component tree. Rendering walks it to compute the next UI; the commit phase then applies the minimal set of DOM mutations. Rendering is interruptible; the commit is synchronous and is the part the browser pays for in layout/paint.

03 Stopping wasted renders

React.memo skips a child’s re-render when its props are shallow-equal to last time. The catch: a fresh inline object, array, or arrow function is a new value every render, so it quietly defeats memo.

Defeats memo
function Parent() {
  const [n, setN] = useState(0);
  // ❌ new object each render
  return <Child style={{ margin: 8 }} />;
}
const Child = memo(function Child({ style }) {
  return <div style={style}>hi</div>;
});
Lets memo work
const STYLE = { margin: 8 }; // stable
function Parent() {
  const [n, setN] = useState(0);
  // ✅ same object identity each render
  return <Child style={STYLE} />;
}

A parent re-renders and passes the same primitive prop count={5} to a memo-wrapped child. Does the child re-render?

Right. memo does a shallow prop compare; equal primitives mean React skips the child. It breaks the instant you pass a new inline {}, [], or () =>.

04 React 19 & the compiler

As of React 19.2 (June 2026), the React Compiler 1.0 is stable (GA since Oct 2025). It auto-memoizes components and values at build time, so most hand-written useMemo/useCallback/memo becomes unnecessary.

Pro framing note

Don’t reach for manual memoization reflexively. With the compiler on, optimize by measuring a hotspot first; reserve hand-tuned memo for the cases the compiler can’t prove safe (or where you’ve confirmed a real cost).

05 Interview rapid-fire

What causes a component to re-render?core
Model answer

Three things: its own state changing, its parent re-rendering, or a context it consumes changing. Props “changing” only matters because the parent had to re-render to pass them.

Say it out loud say it

“State, parent, or context. Props aren’t a separate trigger — a parent re-render is what delivers new props in the first place.”

Is re-rendering bad?core
Model answer

Usually no. A render is just a function call; React only mutates the DOM where output actually differs. You optimize when a render body is expensive or fires far too often — not reflexively.

Say it out loud say it

“Re-rendering is cheap; committing to the DOM is the cost. I optimize measured hotspots, not the render count itself.”

When does memo / useMemo actually help — and does the React Compiler change that?stretch
Model answer

When a subtree or computation is genuinely expensive and its inputs are stable. With React Compiler 1.0 (stable in 19.2) most of this is automatic, so manual memo is for measured hotspots or cases the compiler can’t safely optimize.

Say it out loud say it

“Expensive work plus stable inputs. And in React 19 the compiler auto-memoizes, so I lean on it and hand-tune only what I’ve profiled.”
