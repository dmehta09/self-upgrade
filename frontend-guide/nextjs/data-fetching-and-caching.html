Next.js · Data fetching & caching

Data fetching & caching

In the App Router you fetch data right inside async server components — no client round-trip. Caching is the big shift: it’s now opt-in via the "use cache" directive, with tag-based revalidation when data changes.

00 The idea

Fetch inline with await; everything is dynamic by default; opt into caching with "use cache" and invalidate by tag.

A server component can await its data directly. Nothing is cached unless you ask: wrap a function or component in "use cache" and Next derives a cache key for you. When the underlying data changes, you revalidate the matching tag.

Think of it like… analogy

A kitchen pass with labeled tickets. Each cached result gets a tag (“products”, “user-42”). When something changes, you don’t throw out the whole pass — you pull just the tickets with that label and have them re-made. revalidateTag is “re-make everything tagged X.”

01 Caching with "use cache"

Put "use cache" at the top of a function (or file/component) and its result is cached. Tune lifetime with a cacheLife profile and label it with cacheTag so you can invalidate it later.

lib/products.ts
import { cacheLife, cacheTag } from "next/cache";

export async function getProducts() {
  "use cache";                 // opt this result into the cache
  cacheLife("hours");          // a built-in freshness profile
  cacheTag("products");        // label it so we can revalidate later
  const res = await fetch("https://api.shop.com/products");
  return res.json();
}
Heads up note

The compiler derives the cache key from the function’s arguments and closed-over values, so getProducts() and getProduct(id) cache independently per argument — no manual key strings.

02 Revalidating after a write

After a mutation, tell Next which cache to refresh. revalidateTag now takes a cacheLife profile as a 2nd arg; updateTag() gives read-your-writes inside a Server Action; refresh() re-fetches uncached data. revalidatePath still works for path-based invalidation.

app/actions.ts
"use server";
import { revalidateTag, updateTag } from "next/cache";

export async function publishProduct(data: FormData) {
  await db.product.create(data);
  // invalidate everything tagged "products", with a profile arg
  revalidateTag("products", "max");
  // ...or updateTag for read-your-writes within this action
  // updateTag("products");
}
Common trap gotcha

Two shifts from older Next. unstable_cache is superseded by "use cache" — stop reaching for it. And caching is now opt-in: a plain fetch isn’t cached by default anymore, so don’t assume your data is being reused unless you added the directive.

You cached getProducts() with cacheTag("products"). An admin adds a product. How do you make the list show it?

Right. Tag-based invalidation: you labeled the cache "products", so revalidateTag("products") (optionally with a profile) refreshes exactly that entry on the next read.

03 Interview rapid-fire

How do you cache data in Next 16?core
Model answer

Caching is opt-in: add the "use cache" directive to a function or component and Next caches its result, deriving the key from the arguments. Tune lifetime with cacheLife and label it with cacheTag. unstable_cache is superseded by this.

Say it out loud say it

“Add ‘use cache’ to the function. It’s opt-in now — the compiler derives the key, and I set cacheLife and cacheTag to control freshness and invalidation.”

How do you revalidate after a mutation?core
Model answer

Tag the cache, then call revalidateTag(tag, profile) in the Server Action after the write — the profile is the new 2nd arg. For read-your-writes within the same action use updateTag(); for uncached data use refresh(). revalidatePath still handles path-based invalidation.

Say it out loud say it

“revalidateTag with the tag and a profile after the write. updateTag if I need to read my own write in the same action; refresh for uncached data.”

What makes a route static vs. dynamic here?stretch
Model answer

It’s dynamic by default. Wrapping data access in "use cache" makes that part static/cached; reading request data like cookies() or dynamic searchParams forces it dynamic. Within a single render, identical fetches are memoized so they hit the network once.

Say it out loud say it

“Dynamic unless you opt in with ‘use cache’. Reading request data forces dynamic; identical fetches in one render are deduped automatically.”
