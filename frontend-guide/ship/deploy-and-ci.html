Deploy & CI

Deploying is the easy part — safely deploying is the skill. A pro pipeline gives every pull request a live preview and runs automated gates that block a merge until the code typechecks, lints, tests, and builds. This is how broken changes never reach production.

00 A pipeline with gates

CI is a factory line: code only advances to production after it passes every quality gate. The gates run automatically on each PR, so “works locally” is never enough to merge.

Continuous Integration runs your checks on a server for every push. Continuous Delivery then deploys what passes. The point isn’t the deploy command — it’s that nothing ships without clearing the same gates every time, removing “I forgot to run tests” from the equation.

Think of it like… analogy

A factory assembly line with inspection stations. A part moves down the belt and hits gate after gate — dimensions, stress test, paint — and only a unit that clears them all gets boxed and shipped. CI is those stations; a failed gate stops the line before a defect ever leaves the building.

01 The Vercel model in 2026

Vercel’s platform is built on Fluid compute, and the Node.js runtime is the default for Vercel Functions. Standalone Edge Functions were deprecated (Apr 2026) — the Edge runtime now lives where it’s genuinely needed: routing and proxy (e.g. proxy.ts), not your general server logic.

Fluid compute
The execution model: functions stay warm and share resources, so you get low latency without paying per-request cold starts everywhere.
Default runtime
Node.js on Fluid compute. Full Node APIs, no edge constraints — the recommended default for app code.
Edge runtime
Still used for lightweight routing/proxy at the network edge; not the place for your data-heavy handlers anymore.
Env & secrets
Set per environment (preview vs production) in project settings; secrets are injected at build/runtime, never committed.
Common trap gotcha

Don’t reach for the Edge runtime by default “because it’s faster.” Since Apr 2026 the recommendation is Node on Fluid compute — it avoids edge limitations (restricted APIs, bundle limits) while Fluid keeps latency low. Reserve Edge for true routing/proxy work.

02 From PR to production

Open a PR and the flow runs itself: a preview deployment goes live at a unique URL so reviewers (and QA, and design) click the real thing, while CI runs the gates in parallel. Only when both are green does it merge and promote to production.

The CI gates run cheapest-first so failures surface fast. A typical command sequence in the pipeline:

ci script
# Run in order; first failure stops the merge.
pnpm typecheck   # tsc --noEmit — catch type errors
pnpm lint        # eslint / biome — patterns & bugs
pnpm test        # vitest run — unit/integration
pnpm build       # next build — must compile clean

03 Check yourself

For a data-heavy API route in a Next.js app on Vercel in mid-2026, which runtime is the recommended default?

Right. Standalone Edge Functions were deprecated in Apr 2026. Node on Fluid compute is the default — it keeps latency low without the Edge runtime’s API and bundle constraints. Edge is reserved for routing/proxy.

04 Interview rapid-fire

What do preview deployments give you?core
Model answer

Every PR gets its own live, production-like URL built from that branch. Reviewers, QA, and design can click the real running app instead of reading a diff or trusting screenshots — you catch UX and integration issues before merge, and each preview is isolated with its own env.

Say it out loud say it

“A real, shareable URL per PR. People review the running app, not a diff — so UX and integration bugs get caught before it ever merges.”

Which CI gates do you run, and in what order?core
Model answer

Typecheck, lint, test, then build — cheapest and fastest-failing first so feedback is quick. All of them are required status checks that block the merge, so a red gate physically prevents shipping. The build gate ensures the app actually compiles for production, not just in dev.

Say it out loud say it

“Typecheck, lint, test, build — fast checks first. They’re required status checks, so a failure blocks the merge instead of relying on discipline.”

Edge vs Node runtime on Vercel — how do you pick?stretch
Model answer

As of 2026, default to the Node.js runtime on Fluid compute — full Node APIs, no bundle or API limits, and Fluid keeps latency low without per-request cold starts. Standalone Edge Functions were deprecated; the Edge runtime now earns its place only for lightweight routing/proxy work at the network edge.

Say it out loud say it

“Node on Fluid compute by default — full APIs, low latency, no edge limits. Standalone Edge Functions are deprecated; I only use Edge for routing or proxy.”
