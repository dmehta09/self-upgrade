Data & state · decision guide

Where should this state live?

The senior skill isn’t knowing the tools — it’s routing each piece of state to its rightful home. Run every value through one short decision procedure and the choice becomes mechanical.

00 The idea

Don’t ask “which library?” Ask who owns this value and how far it travels — the home falls out of the answer.

Every value has a natural owner: the server, the URL, the whole app, or one component. Pick the narrowest home that still works; lifting or globalizing prematurely is what creates tangled, stale state.

Think of it like… analogy

Four drawers, labelled. Server cache: photocopies of files the office owns. URL: the address on the envelope — whatever someone needs to land on this exact view. Global UI: house rules everyone follows (theme, who’s home). Local & form: the sticky note on this one screen. Filing a value in the wrong drawer is most state bugs.

1

Is it server data?

Anything fetched from an API — lists, profiles, search results. → TanStack Query (cache + revalidate). Stop here.

2

Should it survive a reload or be shareable?

Filters, tabs, page number, a selected id. → the URL (search params). Bookmarkable and back-button-friendly.

3

Is it cross-cutting client state many screens read?

Theme, logged-in user, sidebar. → Context for low-frequency, or Zustand for anything that changes often.

4

Is it a form?

Field values, validation, submit state. → react-hook-form + a Zod schema.

5

Otherwise — one component?

A toggle, an input draft, a hover flag. → useState. Lift it only when a sibling genuinely needs it too.

Common trap gotcha

Two classics: don’t store server data in Redux/Zustand — it’s a remote copy that needs caching/revalidation (use Query). And don’t duplicate URL state into useState — you get two sources of truth that drift; read it from the URL and write back to the URL.

02 Worked examples

Four real values, run through the procedure:

Table filters & sort
Shareable and should survive reload → URL search params, not useState. A teammate can paste the link and see the same view.
Logged-in user
Cross-cutting client state many screens read → Context (low churn) or Zustand. The user record may be fetched, so hydrate it from Query and expose identity globally.
Fetched list of orders
Server data, full stop → TanStack Query. Never mirror it into a global store or useState.
A single form field
Belongs to the form → react-hook-form (uncontrolled), validated by the shared Zod schema. Not app-global, not URL.

A data table’s active filters and current page should be shareable via a pasted link. Where do they live?

Right. “Shareable / bookmarkable” is the tell for URL state. A store or useState would lose the filters on reload and can’t be linked — and duplicating them into useState creates a second source of truth.

03 Interview rapid-fire

How do you decide where a piece of state should live?core
Model answer

I ask a short chain: server data? → TanStack Query. Shareable/bookmarkable? → URL. Cross-cutting client state? → Context or Zustand. A form? → RHF + Zod. Otherwise local useState, lifted only when a sibling needs it. Pick the narrowest home that works.

Say it out loud say it

“Server → Query, shareable → URL, cross-cutting → Context/Zustand, form → RHF, else useState. Narrowest home that works.”

When is the URL the right place for state?core
Model answer

Whenever the state should be shareable, bookmarkable, or survive a reload and the back button — filters, search query, active tab, pagination, a selected id. Put it in search params so the link fully describes the view, and read it back from the URL rather than copying it into useState.

Say it out loud say it

“If a pasted link should reproduce the view — filters, tabs, pagination — it’s URL state. The address describes the screen.”

What’s the difference between server state and client state?stretch
Model answer

Server state is data the backend owns; the client holds a copy that can go stale, so it needs caching and revalidation — that’s TanStack Query. Client state is owned entirely by the app: UI toggles, theme, session, form drafts. Treating fetched data as client state (stuffing it in Redux) is the classic mistake.

Say it out loud say it

“Server state is a cached copy of remote data that can go stale — Query owns it. Client state is the app’s own UI/session. Don’t mix them.”
