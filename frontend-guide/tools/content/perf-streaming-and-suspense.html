Streaming SSR & Suspense

Old SSR made the user wait for the slowest query before sending a single byte. Streaming flips that: send a usable shell instantly, then flush the slow pieces as they finish. <Suspense> is how you mark which pieces can arrive late.

00 The idea

Stream the shell now, stream the slow parts as they’re ready. A <Suspense> boundary is the seam between “send immediately” and “hold and stream later.”

The server starts sending HTML before the page is fully rendered. Anything wrapped in <Suspense> can be deferred: React sends its fallback first, keeps the connection open, and flushes the real content (plus a tiny script to swap it in) the moment that data resolves.

Think of it like… analogy

A good restaurant brings warm bread to your table the second you sit down, while the main course is still cooking. You’re seated, fed, and happy — the kitchen didn’t make you stare at an empty table until everything was plated. Streaming serves the “bread” (the shell) instantly and the “main” (slow data) when it’s ready.

“Streaming” on the wire
One HTTP response sent as chunked HTML — the browser starts parsing and painting before the body is complete.
The boundary’s job
A <Suspense> wrapper says “render the fallback now; stream the real subtree in when its data resolves.”

01 Drawing a Suspense boundary

Wrap the slow part. The shell around it streams instantly with a fallback in the gap; React patches in the real content when the awaited data lands — no client round-trip needed.

app/page.tsx
export default function Page() {
  return (
    <main>
      <Header />            {/* fast — streams in the shell */}
      <Suspense fallback={<ReviewsSkeleton />}>
        <Reviews />         {/* slow server component — streamed later */}
      </Suspense>
    </main>
  );
}

async function Reviews() {
  const reviews = await getReviews(); // awaited on the server
  return <ReviewList items={reviews} />;
}

In the Next.js App Router, a route-level loading.tsx is just sugar for wrapping that route’s page in a <Suspense> with your loading UI as the fallback.

Common trap gotcha

A boundary placed too high blocks everything below it. Wrap your whole layout in one <Suspense> and a single slow query holds the entire page at the fallback — you’ve recreated blocking SSR. Put the boundary around the slow part, so the fast shell paints first.

02 Boundary placement is the whole game

The shell — everything outside your boundaries — is what paints first. So boundaries are a design decision: too high and nothing paints early; too granular and the page flickers with skeletons. Put one around each independently-slow region.

Boundary too high
<Suspense fallback={<PageSkeleton />}>
  <Header />     {/* fast, but */}
  <Feed />       {/* one slow query */}
  <Footer />     {/* now blocks ALL */}
</Suspense>
Boundary around the slow part
<Header />       {/* streams instantly */}
<Suspense fallback={<FeedSkeleton />}>
  <Feed />       {/* only this waits */}
</Suspense>
<Footer />       {/* streams instantly */}

You wrap your entire root layout in a single <Suspense>. One widget makes a 2-second API call. What does the user see?

Right. Everything inside a boundary waits for the slowest thing in it. Move the boundary down to just the slow widget so the rest of the layout streams as the shell.

03 Interview rapid-fire

What does streaming SSR actually buy you?core
Model answer

A much earlier first paint. Instead of blocking the response until every query resolves, the server flushes a usable shell immediately and streams slow regions as they finish. The user reads and sees structure while data is still loading — better perceived performance and a faster LCP candidate in the shell.

Say it out loud say it

“It decouples first paint from the slowest query. Shell goes out instantly; slow parts stream in — so the page feels fast even when data is slow.”

How does Suspense work on the server during streaming?stretch
Model answer

React renders the boundary’s fallback into the initial HTML and keeps the response open. When the suspended subtree’s data resolves, the server flushes that content in a later chunk plus a tiny inline script that swaps the fallback for the real markup — all over one chunked HTTP response, no client refetch.

Say it out loud say it

“Fallback ships first, the connection stays open, and React flushes the resolved subtree plus a swap-in script in a later chunk — one streamed response.”

Where should you place Suspense boundaries?core
Model answer

Around each independently-slow region — not at the top of the tree. The content outside your boundaries is the shell that paints first, so keep fast UI out of any boundary and isolate slow data fetches in their own. One boundary per slow area; avoid one giant one or a flood of tiny ones.

Say it out loud say it

“Wrap the slow part, not the page. Whatever’s outside the boundary is the shell that paints first, so I isolate each slow fetch.”
