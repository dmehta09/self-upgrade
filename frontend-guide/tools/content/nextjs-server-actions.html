Server Actions & mutations

A Server Action is a "use server" function you call straight from a form or an event — no hand-written API route, no fetch boilerplate. It runs on the server, mutates data, and revalidates the cache, with progressive enhancement for free.

00 The idea

A "use server" function is a type-safe server endpoint you invoke directly from the client — usually via <form action={fn}>.

You write the mutation as a normal async function, mark it "use server", and pass it to a form’s action. Next wires up the network call. Because it’s a real form post, it works before JS loads, then upgrades to a fetch once hydrated.

Think of it like… analogy

A form that posts straight into a typed function on the server — like running a wire from the submit button directly to your backend code. No envelope to address (an API route), no postal service to configure (fetch + JSON). You just call the function; Next runs the wire.

01 Define & call an action

Mark the function, read the FormData, mutate, then revalidate. Pass it straight to a form — the markup is plain HTML.

app/todos/actions.ts
"use server";
import { revalidateTag } from "next/cache";
import { z } from "zod";

const Todo = z.object({ title: z.string().min(1) });

export async function createTodo(_prev: unknown, form: FormData) {
  const parsed = Todo.safeParse({ title: form.get("title") });
  if (!parsed.success) return { error: "Title required" };
  await db.todo.create(parsed.data);   // mutate
  revalidateTag("todos");              // refresh the list
  return { ok: true };
}

02 Pending & error state

Wrap the action in useActionState for the returned value and a pending flag; useFormStatus reads pending from inside the form (e.g. a submit button). Before JS loads, the form still posts — that’s progressive enhancement.

app/todos/todo-form.tsx
"use client";
import { useActionState } from "react";
import { useFormStatus } from "react-dom";
import { createTodo } from "./actions";

function Submit() {
  const { pending } = useFormStatus();          // pending from the form
  return <button disabled={pending}>{pending ? "Saving…" : "Add"}</button>;
}

export function TodoForm() {
  const [state, action] = useActionState(createTodo, null);
  return (
    <form action={action}>
      <input name="title" />
      {state?.error && <p>{state.error}</p>}
      <Submit />
    </form>
  );
}
Common trap gotcha

A Server Action is a public HTTP endpoint — anyone can POST to it, form or not. The "use server" directive is not authorization. Authenticate the session and validate the input inside the action (e.g. with Zod), exactly as you would a hand-written API route.

Why does a form using a Server Action still submit if the user’s JavaScript hasn’t loaded yet?

Right. Next renders a native form that posts to the action’s endpoint. Without JS it submits the old-school way; once hydrated, React intercepts it for a smoother fetch — same handler either way.

03 Interview rapid-fire

What is a Server Action?core
Model answer

A function marked "use server" that runs on the server and is callable from the client — typically via a form’s action or an event handler. It replaces a hand-written API route for mutations: you write the logic, Next handles the transport, and you revalidate the cache afterward.

Say it out loud say it

“A ‘use server’ function you call from the client — a typed mutation endpoint without writing an API route. Mutate, then revalidate.”

What does progressive enhancement mean here?core
Model answer

The form is rendered as a real HTML form pointing at the action’s endpoint, so it submits and mutates even before (or without) client JS. Once hydrated, React intercepts the submit for a smoother in-page fetch — same server handler, just a better experience when JS is available.

Say it out loud say it

“It works as a plain form post without JS, then upgrades to a client fetch after hydration — same endpoint, resilient by default.”

How do you secure a Server Action?stretch
Model answer

Treat it as a public endpoint. Check the session/auth at the top of the action, authorize the specific operation, and validate every input (Zod) — never trust client-sent IDs. The "use server" marker only exposes it; it grants no protection, so the security lives inside the function.

Say it out loud say it

“It’s a public POST endpoint, so I authenticate, authorize, and validate inputs inside the action — the directive isn’t security.”
