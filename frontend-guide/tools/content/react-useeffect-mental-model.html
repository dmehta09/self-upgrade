useEffect — the right mental model

Most useEffect pain comes from one wrong belief: that it’s a lifecycle hook. It isn’t. It’s a tool to synchronize your component with an external system — and most of the time you don’t need it at all.

00 The idea

An effect syncs React with the outside world — a subscription, the DOM, a timer, an analytics SDK. It is not “run code after render.”

You declare: “given this state, this external thing should be set up like so.” React runs the effect after commit, re-runs it when the dependencies change, and runs your cleanup before each re-run and on unmount. Think continuous synchronization, not a sequence of lifecycle events.

Think of it like… analogy

A thermostat. You set a target (your state); the thermostat keeps the room (an external system) in sync with it. When the target changes it adjusts; when you leave it shuts off the heating (cleanup). It’s not “do X once” — it’s “keep the world matching this value.”

01 Dependencies & cleanup

The deps array means “re-sync when any of these change.” It is not an optimization knob — it is the list of every reactive value the effect reads. Cleanup is the inverse of setup: it undoes whatever the effect did, and runs before every re-run and on unmount.

ChatRoom.tsx
useEffect(() => {
  const conn = createConnection(roomId); // setup
  conn.connect();
  return () => conn.disconnect();        // cleanup
}, [roomId]); // re-sync whenever roomId changes

Change roomId and React tears down the old connection, then opens the new one — automatically. That’s synchronization, expressed declaratively.

02 When you don’t need an effect

Two huge categories don’t belong in effects. Derived data — anything you can compute from existing props/state — should be computed during render. Event logic — “do X when the user clicks” — belongs in the event handler, not a reactive effect.

Anti-pattern: derive in an effect
const [list, setList] = useState(items);
const [full, setFull] = useState("");
// ❌ extra render + stale risk
useEffect(() => {
  setFull(first + " " + last);
}, [first, last]);
Better: derive during render
const [first, setFirst] = useState("");
const [last, setLast] = useState("");
// ✅ just compute it — no effect, no extra state
const full = first + " " + last;

If a value can be calculated from what you already have, calculate it in render. Reserve effects for genuinely external systems.

03 Strict Mode & non-reactive values

In development, Strict Mode mounts each component, unmounts it, and mounts it again — so every effect runs setup → cleanup → setup. This is a feature: it surfaces missing or wrong cleanup loudly. A correct effect is unbothered by it.

Sometimes an effect reads a value it should not re-sync on (the latest callback, say). React 19.2’s useEffectEvent extracts that non-reactive logic so it always sees fresh values without becoming a dependency.

useEffectEvent.tsx
// onConnected always sees the latest theme,
// but theme is NOT a dependency — no needless re-sync.
const onConnected = useEffectEvent(() => {
  showToast("Connected!", theme);
});
useEffect(() => {
  const conn = createConnection(roomId);
  conn.on("open", onConnected);
  return () => conn.disconnect();
}, [roomId]); // theme intentionally absent
Common trap gotcha

Don’t lie to the deps array. Removing a value just to silence the lint rule doesn’t stop the effect needing it — it just makes the effect read a stale copy. Either list every reactive value you read, or restructure (functional updaters, useEffectEvent) so you genuinely don’t depend on it.

In React Strict Mode (dev), your effect’s setup and cleanup each run twice on mount. What does that usually indicate?

Right. Strict Mode double-invokes effects in development only, to expose missing/incorrect cleanup. If the second cleanup+setup leaves you in a bad state, your cleanup is incomplete — that’s the bug it’s catching.

04 Interview rapid-fire

What is useEffect actually for?core
Model answer

Synchronizing your component with an external system — subscriptions, the DOM, timers, non-React widgets. It’s not a lifecycle hook. Derived data goes in render; user-action logic goes in event handlers.

Say it out loud say it

“It synchronizes React with the outside world. If I’m not touching an external system, I probably don’t need an effect — I compute in render or handle it in an event.”

Why does my effect run twice in development?core
Model answer

Strict Mode deliberately mounts, unmounts, and remounts components in dev, so effects run setup–cleanup–setup. It’s a probe for missing cleanup; production runs once. A correctly written effect handles it without side effects leaking.

Say it out loud say it

“Strict Mode double-invokes effects in dev to catch missing cleanup. If that breaks something, the cleanup’s wrong — not the double-invoke.”

What are the classic deps-array footguns?stretch
Model answer

Omitting values to dodge re-runs (causes stale reads), and unstable deps — an inline object/function that’s new each render — causing an infinite re-sync loop. Fix with functional updaters, stable identities, or useEffectEvent for non-reactive values.

Say it out loud say it

“Two traps: lying about deps gives stale values, and an unstable dep loops forever. I never trim the array to silence lint — I restructure instead.”
