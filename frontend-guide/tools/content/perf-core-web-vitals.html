Core Web Vitals: LCP, INP, CLS

Three numbers summarize how a page feels: how fast it loads, how quickly it reacts, and whether it holds still. Google grades real users on them, so they’re both a UX signal and an SEO one. Know the thresholds, the culprits, and the fix for each.

00 The idea

Three gauges: LCP = load, INP = responsiveness, CLS = stability. “Good” means passing all three at the 75th percentile of field data.

Core Web Vitals are user-centric: each maps to a felt experience rather than a lab number. They’re measured on real visitors (field data), and the bar is the 75th percentile — so the slowest quarter of your users is what counts.

Think of it like… analogy

It’s a car’s dashboard with three gauges. One shows how fast you got up to speed (LCP — load). One shows how sharply the car responds when you touch the pedal (INP — responsiveness). One shows whether the ride is smooth or the whole thing lurches (CLS — stability). A great drive needs all three in the green.

LCP
Largest Contentful Paint		 When the largest element (hero image, headline) finishes painting — perceived load. ≤ 2.5 s Slow server/TTFB, render-blocking JS/CSS, an unoptimized hero image. Stream/cache the shell, preload the LCP image, prioritize it, trim blocking resources.
INP
Interaction to Next Paint		 Latency from a user interaction to the next frame — overall responsiveness. ≤ 200 ms Long main-thread tasks: heavy hydration, big handlers, expensive re-renders. Cut/split client JS, break up long tasks, defer non-urgent work, ship fewer islands.
CLS
Cumulative Layout Shift		 How much visible content jumps around during load — visual stability. ≤ 0.1 Images/ads/embeds with no reserved size; late-loading fonts; content injected above. Set width/height (or aspect-ratio), reserve space for dynamic slots, use font-display wisely.

01 Field vs lab — and why INP, not FID

Field data (CrUX) is what real users experienced; it’s what Search actually ranks on. Lab data (Lighthouse) is a single synthetic run — great for debugging, but it can’t see your real traffic. They disagree, and field wins.

Field (CrUX)
Real-user measurements, aggregated at the 75th percentile. The basis for “passing” Core Web Vitals.
Lab (Lighthouse)
One controlled run on a synthetic device/network. Reproducible for debugging; not a substitute for field.
Common trap gotcha

Don’t cite FID — INP replaced it as a Core Web Vital in March 2024. FID only measured the delay of the first input; INP captures the worst interaction latency across the whole visit, so it’s far stricter. Also remember the thresholds are at the 75th percentile of field data, not your median.

02 Diagnosing a poor score

Each metric has a different failure mode, so the first move is to identify which gauge is red — then apply the matching fix rather than optimizing blindly.

1

Poor LCP → speed up the largest paint

Find the LCP element, then attack what delays it: improve TTFB (cache/stream), preload and prioritize that image, and remove render-blocking JS/CSS.

2

Poor INP → free the main thread

Long tasks are the enemy. Ship less client JS, split long handlers, defer non-urgent work, and reduce hydration so the first interactions respond within a frame.

3

Poor CLS → reserve space

Give images and embeds explicit dimensions or aspect-ratio, reserve room for late content (ads, banners), and avoid inserting content above what the user is reading.

Which Core Web Vital replaced First Input Delay (FID), and what does it capture?

Right. INP became a Core Web Vital in 2024, replacing FID. FID only timed the first input’s delay; INP measures responsiveness across all interactions, so it’s the stricter, more representative metric.
