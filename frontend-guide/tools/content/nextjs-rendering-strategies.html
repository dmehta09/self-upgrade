Rendering strategies: SSR/SSG/ISR/PPR

SSG, SSR, ISR and PPR are all answers to one trade-off: freshness vs. latency vs. cost. In Next 16 the rules flipped — rendering is dynamic by default and PPR ships through Cache Components, not an experimental flag.

00 The idea

Pick where each route sits on three axes: how fresh the data is, how fast it arrives, and what it costs to produce.

Static (SSG) is instant but can be stale; dynamic (SSR) is fresh but renders per request; ISR re-bakes on a schedule; PPR serves a static shell instantly and streams the dynamic parts in. There’s no “best” — only the right point for each route.

Think of it like… analogy

A bakery. SSG = bake overnight and sell off the shelf — instant, but it can go stale. SSR = bake to order — fresh, but you wait. ISR = re-bake a tray every few hours. PPR/Cache Components = a pre-stocked shelf plus your custom topping added while you watch — instant base, fresh finish.

Static (SSG)
Rendered at build, served from the CDN. Fastest, cheapest; data is frozen until the next build.
Dynamic (SSR)
Rendered per request. Always fresh and request-aware; costs a render every hit.
ISR
Static + background revalidation on an interval — near-static speed with periodic freshness.
PPR
One route = static shell + streamed dynamic holes. Best of both, per route.

01 PPR now ships via Cache Components

The old experimental.ppr flag is gone. Partial prerendering is now part of Cache Components — turn it on with cacheComponents: true. Rendering is dynamic by default; you opt static parts in with the "use cache" directive, and Next prerenders those into the shell while streaming the rest.

next.config.ts
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  cacheComponents: true,   // enables PPR + the "use cache" directive
  // experimental: { ppr: true }  // ❌ removed in Next 16 — don't use
};

export default nextConfig;
Common trap gotcha

Don’t reference experimental.ppr — it no longer exists. And remember caching is now opt-in: a route that reads request data or fetches without "use cache" renders dynamically every time. If something feels “uncached,” that’s the new default, not a bug.

02 Choosing per route

The mode isn’t a global setting — Next infers it per route from what you do. Read request data ⇒ dynamic. Wrap work in "use cache" ⇒ static/cached. Mix both ⇒ PPR.

StrategyUse it when…
SSG (static)Content rarely changes: marketing, docs, blog posts. Bake once, serve from CDN.
Dynamic (SSR)Per-user or per-request data: dashboards, authed pages, anything reading cookies().
ISRMostly-static but periodically updated: an hourly price list, a product catalog.
PPR / Cache ComponentsA static shell with a few personalized holes: a product page with live stock + your cart.
1

Marketing site → SSG

No request data. Pre-render at build; the whole page is static HTML on the CDN.

2

User dashboard → dynamic

Reads cookies()/session, so it renders per request — always fresh and authed.

3

Hourly price → ISR

Cache it with a 1-hour cacheLife; Next serves cached HTML and re-bakes in the background.

4

Shell + personalization → PPR

Cache the layout and product info; stream the cart and live stock as dynamic holes.

In Next 16, how does a route end up rendering dynamically?

Right. Next 16 is dynamic-by-default. A route is static only for the parts you opt in with "use cache"; touching request data or uncached fetches makes it render per request.

03 Interview rapid-fire

SSG vs SSR vs ISR — one line each.core
Model answer

SSG renders at build and serves static HTML — fastest, but stale until rebuilt. SSR renders per request — always fresh, costs a render each hit. ISR is SSG plus timed background revalidation — static speed with periodic freshness. The axis is freshness vs. latency vs. cost.

Say it out loud say it

“SSG: build-time, static, can go stale. SSR: per-request, always fresh. ISR: static plus background revalidation on an interval.”

What problem do PPR / Cache Components solve?core
Model answer

The all-or-nothing choice between static and dynamic. PPR lets one route be a static, instantly-served shell with dynamic holes streamed in — so a page can be CDN-fast yet still show per-user data. In Next 16 it ships via cacheComponents: true plus "use cache".

Say it out loud say it

“They kill the static-vs-dynamic either/or — one route serves a static shell instantly and streams the personalized parts. It’s Cache Components now, not the old experimental flag.”

How does the App Router decide a route’s rendering mode?stretch
Model answer

It’s inferred, not declared. The route is dynamic by default; parts wrapped in "use cache" are prerendered. Reading request data (cookies(), headers(), dynamic searchParams) forces those parts dynamic. A route mixing cached and dynamic regions becomes PPR.

Say it out loud say it

“Next infers it: dynamic by default, static where you add ‘use cache’, dynamic where you read request data — and a mix becomes partial prerendering.”
