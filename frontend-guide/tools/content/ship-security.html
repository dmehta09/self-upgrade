Frontend security: XSS, CSP & CSRF

React escapes what you render and browsers lock cookies down — most frontend security work is not undoing those defaults. Interviewers probe three letters: XSS (the sinks that bypass escaping), CSP (the safety net under it), and CSRF (why Server Actions are mostly covered, and what’s still on you).

00 Layers, not a checklist

React escapes rendered text by default, so frontend security is about the handful of places that bypass that protection — plus the layers behind them: CSP, SameSite cookies, and origin checks.

You don’t write escaping code in 2026; the framework does it. Your job is to know the side doors — dangerouslySetInnerHTML, URL props, env vars, public endpoints — and to keep a second layer in place for the day one of them slips.

Think of it like… analogy

User input is an unscreened package arriving at a building. The framework x-rays everything that comes through the front door — that’s JSX escaping. But there are side doors you can open yourself (dangerouslySetInnerHTML hands the package straight to the mailroom unopened), and CSP is the second checkpoint inside: even a smuggled package can’t detonate without the day’s passcode.

XSS
Cross-site scripting — an attacker’s script runs in your user’s session, with their cookies and their DOM. The attack is injection; the defense is escaping + sanitizing.
CSP
Content-Security-Policy — a response header telling the browser which scripts are allowed to run at all. The net that catches what escaping missed.
CSRF
Cross-site request forgery — a hostile site makes the victim’s browser send an authenticated request to yours. Defended by SameSite cookies + origin checks, not by anything in your components.

01 Where React’s escaping stops

JSX text and attributes are escaped — a pasted <script> tag inside {userInput} comes out as inert text. Three side doors bypass that:

  • dangerouslySetInnerHTML with user-influenced HTML — the name is the warning. If you truly must render rich text, sanitize with DOMPurify first.
  • URL props — <a href={userUrl}> with a javascript: scheme runs code on click. Escaping doesn’t help; the string is a valid attribute. Allow-list schemes.
  • Data injected into <script> tags — serializing server state into inline JSON-in-HTML by hand. A </script> inside the data breaks out of the tag.
Raw innerHTML render
// Any stored <img onerror=...> payload
// now runs in every reader's browser
<div dangerouslySetInnerHTML={{
  __html: comment.body
}} />
Sanitize + allow-list
// Plain text? Let React escape it.
<div>{comment.body}</div>

// Rich text? Sanitize to an allow-list.
const clean = DOMPurify.sanitize(
  comment.body,
  { ALLOWED_TAGS: ['b', 'i', 'a', 'p'] }
);
<div dangerouslySetInnerHTML={{ __html: clean }} />

URLs are a sink of their own — allow-list the scheme before it reaches href:

SafeLink.tsx
// 'javascript:alert(1)' is a perfectly valid href —
// escaping can't save you, only an allow-list can.
function SafeLink({ url, children }: SafeLinkProps) {
  const safe = /^https?:\/\//i.test(url) ? url : '#';
  return <a href={safe} rel="noopener noreferrer">{children}</a>;
}
Common trap gotcha

Sanitizing only in the React client isn’t enough. The API serves that same comment to your mobile app, your emails, and next year’s rewrite — none of which run your DOMPurify call. Store sanitized (or re-sanitize on every render path), and treat the database as holding untrusted input forever.

03 CSP: the second layer

A Content-Security-Policy header tells the browser which scripts may execute. With a nonce-based policy, every legitimate <script> carries a fresh per-request token — so even if attacker markup slips past your escaping, their inline script lacks the nonce and the browser simply refuses to run it. Injection still happens; execution dies.

In Next.js 16 you set it per request in proxy.ts (the successor to the deprecated middleware.ts) — a sketch, not a full config:

proxy.ts
// Sketch: per-request nonce + strict CSP
import { NextRequest, NextResponse } from 'next/server';
export default function proxy(request: NextRequest) {
  const nonce = btoa(crypto.randomUUID());
  const csp =
    `script-src 'nonce-${nonce}' 'strict-dynamic'; ` +
    `object-src 'none'; base-uri 'none'`;
  const headers = new Headers(request.headers);
  headers.set('x-nonce', nonce); // app reads it for its scripts
  const res = NextResponse.next({ request: { headers } });
  res.headers.set('Content-Security-Policy', csp);
  return res;
}

The pairing to name in an interview: script-src 'nonce-…' 'strict-dynamic'. The nonce blesses your entry scripts; 'strict-dynamic' lets those blessed scripts load the chunks they import — which is what makes a strict CSP workable with a code-splitting framework.

04 CSRF & the server boundary

CSRF rides the browser’s habit of attaching cookies to every request — a hostile page auto-submits a form to your domain and the victim’s session goes with it. The App Router story is decent by default: Server Actions are POST-only and Next compares the Origin header to the Host, rejecting mismatches; and SameSite=Lax cookie defaults stop the browser sending your session on most cross-site requests anyway.

What’s still on you: a Server Action compiles to a public HTTP endpoint. Anyone can invoke it directly with crafted input — so validate the session and check authorization inside every action and route handler, and never trust hidden fields. Validation in the form ≠ authorization in the action.

NEXT_PUBLIC_*
Inlined into the public JS bundle at build time. Treat as published — fine for analytics IDs, never for secrets.
Everything else
Server-only. Readable in Server Components, route handlers, and Server Actions; a client component sees undefined. Secrets live here.
Supply chain
Commit the lockfile and run pnpm audit in CI — your node_modules compiles into the bundle you ship to users.

A Server Action deletes a project when the submitted form includes <input type="hidden" name="role" value="admin"> — rendered only for admins. Safe?

Right. Hidden fields are client input like any other. The Origin check only stops cross-site forgery — a logged-in user on your own site can still hand-craft the request. Authorization must come from the session, inside the action.

05 Interview rapid-fire

How does XSS happen in React if it escapes by default?core
Model answer

Escaping covers JSX text and attributes — the sinks that bypass it are dangerouslySetInnerHTML with user-influenced HTML, URL props where a javascript: scheme survives escaping because it’s a valid string, and hand-serializing data into inline <script> tags. The fixes: render as text, sanitize rich text with DOMPurify, allow-list URL schemes, and let the framework do serialization.

Say it out loud say it

“React escapes everything you render normally — XSS comes from the opt-outs: dangerouslySetInnerHTML, javascript: URLs in href, and hand-rolled script-tag serialization. I sanitize, allow-list schemes, and keep CSP as the net underneath.”

What does a nonce-based CSP buy that escaping doesn’t?core
Model answer

Defense in depth at a different layer. Escaping prevents injection; CSP prevents execution — if hostile markup slips through anyway, its inline script lacks the per-request nonce and the browser won’t run it. 'strict-dynamic' lets nonce’d scripts load their own chunks, which is what makes a strict policy practical with Next’s code splitting.

Say it out loud say it

“Escaping stops the injection; CSP stops the execution. With a per-request nonce and strict-dynamic, even markup that slips through can’t actually run a script.”

Are Server Actions CSRF-safe?stretch
Model answer

Largely, by default: they only accept POST, Next rejects requests whose Origin doesn’t match the Host, and SameSite=Lax cookies don’t ride along on most cross-site sends. But CSRF protection isn’t authorization — the action is a public endpoint anyone can call with crafted arguments, so I still validate the session and check permissions inside every action.

Say it out loud say it

“POST-only plus an Origin-vs-Host check plus SameSite cookies covers the cross-site case. What it doesn’t cover is authorization — every action is a public endpoint, so the permission check lives inside it.”
