Server vs Client Components

React Server Components render on the server and ship zero JS; "use client" marks the boundary where code starts shipping to the browser. Knowing where to draw that line is the single biggest lever on your bundle size.

00 The idea

Server Components run only on the server and send finished HTML. "use client" opts a subtree into the browser bundle.

By default every component in app/ is a Server Component: it can be async, read the DB or secrets, and never ships its JS. You add "use client" only where you need interactivity — state, effects, event handlers, browser APIs.

Think of it like… analogy

A restaurant. The kitchen (server) has the full pantry — the database, the secrets — and sends out finished plates (HTML). Only the things diners actually touch — the call bell, the salt shaker (interactivity) — live in the dining room ("use client"). You don’t ship the whole pantry to every table.

Server Component
Default. Renders on the server, can be async, touches DB/secrets, ships no JS.
Client Component
Marked "use client". Ships to the browser; can use state, effects, handlers, browser APIs.
The boundary
Everything imported below a "use client" file becomes client too.

01 Server Components fetch directly

A Server Component can be async and await data inline — no useEffect, no client fetch, no loading flash. Secrets stay on the server because the code never reaches the browser.

app/products/[id]/page.tsx
// Server Component (default) — runs only on the server.
import { db } from "@/lib/db";
import { AddToCart } from "./add-to-cart";

export default async function Page(
  { params }: { params: Promise<{ id: string }> }
) {
  const { id } = await params;
  const product = await db.product.find(id);   // DB access, no API route
  return (
    <section>
      <h1>{product.name}</h1>
      <AddToCart id={product.id} />   {/* island of interactivity */}
    </section>
  );
}

02 Mark the interactive island

"use client" at the top of a file makes it (and its imports) part of the browser bundle. Put it on the leaf that needs state — not the page.

app/products/[id]/add-to-cart.tsx
"use client";
import { useState } from "react";

export function AddToCart({ id }: { id: string }) {
  const [qty, setQty] = useState(1);          // state ⇒ must be client
  return (
    <button onClick={() => addItem(id, qty)}>
      Add {qty} to cart
    </button>
  );
}

A client component can still render server components — if you pass them as children. The server renders them and hands the client wrapper finished output to slot in.

app/dashboard/page.tsx
// Server page passes a Server Component INTO a client wrapper.
import { Collapsible } from "./collapsible";   // "use client"
import { Report } from "./report";             // server, async

export default function Page() {
  return (
    <Collapsible>
      <Report />   {/* stays server — it's children, not imported by the client file */}
    </Collapsible>
  );
}
Common trap gotcha

Two traps. (1) Props crossing the boundary must be serializable — you can’t pass a function or a class instance from a server parent to a client child. (2) Slapping "use client" on a big parent drags its whole imported subtree into the browser. Push the directive down to the leaf.

You add "use client" to your top-level Layout so one button can have an onClick. What happens?

Right. "use client" marks a boundary: every component imported under it ships to the browser. Extract the button into its own "use client" leaf and keep the layout on the server.

03 Interview rapid-fire

Why do Server Components improve performance?core
Model answer

They render on the server and ship no JavaScript, so the client bundle shrinks to just the interactive islands. Data fetching happens next to the data (no client round-trips), and the user gets HTML immediately. Less JS means faster hydration and better INP.

Say it out loud say it

“They ship zero JS and fetch next to the data. The browser only downloads the interactive islands, so the bundle and hydration cost drop.”

What can’t cross the server–client boundary?core
Model answer

Props passed from a server component to a client component must be serializable — plain objects, arrays, primitives, dates. Functions, class instances and JSX-producing render props can’t cross. The exception is children: a server component rendered as children is sent as already-rendered output.

Say it out loud say it

“Only serializable props — no functions or class instances. You can still pass a server component as children, because that’s sent as rendered output.”

Where should you put "use client"?stretch
Model answer

As far down the tree as possible — on the smallest leaf that actually needs state, effects or handlers. The directive turns its whole imported subtree into client code, so a high boundary balloons the bundle. Keep data-heavy parents on the server and isolate interactivity into small islands.

Say it out loud say it

“On the smallest interactive leaf. Pushing the boundary down keeps parents on the server and ships the least JS.”
