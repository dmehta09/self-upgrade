Tailwind v4: CSS-first

Tailwind v4 moves configuration out of JavaScript and into your CSS. One @import turns it on, an @theme block defines your design tokens as real CSS variables, and the Oxide engine makes it fast. No tailwind.config.js required.

00 The idea

v4 is CSS-first: a single @import "tailwindcss"; plus @theme tokens that are live CSS variables — the JS config is gone.

The three old @tailwind directives collapse into one import. Your design tokens live in CSS and compile to custom properties, so they’re readable in DevTools and usable in plain CSS too. The Oxide engine handles the heavy lifting.

Think of it like… analogy

v3 was a factory that needed a separate spec sheet (a JS config) handed over before it could run. v4 builds the product and writes its spec in the same place — your CSS. And the spec values aren’t printed on paper; they’re live wires (CSS variables) you can read and rewire at runtime.

Turn it on
One line: @import "tailwindcss"; — replaces the old @tailwind base/components/utilities trio.
Design tokens
@theme { --color-brand: … } compiles to real CSS variables and to utilities like bg-brand.
Oxide engine
The Rust-powered core: faster builds, automatic content detection, smaller output.

01 Tokens live in CSS now

Define your design system in an @theme block. Every token becomes both a CSS variable and a matching utility — one source of truth for colors, spacing, radius, and fonts.

app.css
@import "tailwindcss";

@theme {
  --color-brand: oklch(0.7 0.18 195);
  --radius-card: 1rem;
}

/* Usable as utilities (bg-brand, rounded-card)
   AND as plain CSS: var(--color-brand) */

v4 also adds first-class extension points: @utility for your own utilities, @custom-variant for new variants, and native @container queries — all in CSS, no plugin file.

02 Composing classes with cn()

When classes are conditional or come from props, string concatenation breaks down — conflicting utilities both end up in the list. The cn() helper = clsx (conditional join) + tailwind-merge (dedupe conflicts, last wins).

cn.ts
import { clsx, type ClassValue } from "clsx";
import { twMerge } from "tailwind-merge";

export function cn(...inputs: ClassValue[]) {
  return twMerge(clsx(inputs));
}

cn("p-2", "p-4");                 // → "p-4"  (conflict resolved)
cn("rounded", isActive && "bg-brand"); // conditional join
Template string: conflict survives
// ❌ both paddings ship; CSS-order decides — fragile
<div className={`p-2 ${big ? "p-4" : ""}`} />
cn(): conflict resolved
// ✅ tailwind-merge keeps the last p-* only
<div className={cn("p-2", big && "p-4")} />

Variants and states read the same way as always — e.g. className="md:flex hover:bg-brand" — v4 just generates them from your CSS-defined theme.

Common trap gotcha

Migrating from v3? The @tailwind base/components/utilities directives and tailwind.config.js are gone. There’s one @import "tailwindcss"; and an @theme block instead. A JS config still loads via @config, but it’s a legacy bridge — not the v4 way.

03 Interview rapid-fire

What changed from Tailwind v3 to v4?core
Model answer

v4 is CSS-first. The three @tailwind directives become one @import "tailwindcss";, and tailwind.config.js is replaced by an @theme block whose tokens are real CSS variables. The new Oxide engine is faster, and there are CSS-native extension points like @utility, @custom-variant, and @container.

Say it out loud say it

“v4 went CSS-first: one import, no JS config, tokens defined in @theme as real CSS variables, with the faster Oxide engine.”

Why use cn() instead of a template string?core
Model answer

Because conditional classes often conflict, and a template string ships both — leaving the result up to CSS source order. cn() runs clsx to join conditionals, then tailwind-merge to dedupe conflicting utilities so the last one deterministically wins. It’s essential once classes come from props.

Say it out loud say it

“cn() is clsx plus tailwind-merge — it joins conditionals and resolves conflicting utilities, so prop-driven classes are predictable.”

How do you theme an app in v4 without a JS config?stretch
Model answer

Define tokens in an @theme block in CSS — colors, spacing, radius, fonts. Each becomes a CSS custom property and a matching utility, so I get bg-brand and var(--color-brand) from one declaration. Because they’re real variables, I can override them per scope (e.g. a .dark selector) for theming without rebuilding config.

Say it out loud say it

“Tokens go in @theme and compile to CSS variables plus utilities — so theming is just overriding those variables per scope, no JS config.”
