Rendering & performance — overview

Fast apps aren’t a mystery — they’re a budget. This module follows a request from the server to the moment a user can actually click, and shows where the milliseconds hide: streaming, hydration, and the three numbers Google grades you on.

00 Follow where the time goes

Performance is one timeline: request → server render → stream → hydrate → interactive. Every page in this module attacks a different segment of it.

A user types a URL, the server renders HTML, it streams down the wire, the browser paints it, then JavaScript hydrates it so clicks work. “Slow” is just one of those stages taking too long — so the fix depends entirely on which stage.

Think of it like… analogy

Think of a meal arriving at your table. The kitchen cooks (server render), a waiter carries plates out as they’re ready (streaming), the food looks done (painted HTML), but you can’t actually eat until the cutlery shows up (hydration). Optimizing performance is asking which step kept you waiting.
