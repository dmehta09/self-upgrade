Interview prep · design round

Design a live feed

Chat, notifications, activity streams — every product has one, and it’s THE realtime frontend interview. A strong answer is four decisions: which transport, what happens when the connection drops, where messages live, and how to render a stream without chaos. Most candidates only say “WebSockets” and stop.

00 The idea

The prompt: “Design the live feed for a team chat” (or a notifications panel). The senior answer is transport choice + reconnection/catch-up + cache strategy + calm rendering — “use WebSockets” is only a quarter of it.

Run the six-step method as usual, but the weight shifts: requirements decide the transport, and the data step splits in two — the live stream and the recovery path when the stream breaks. Plan the failure path first; the happy path is easy.

Think of it like… analogy

Polling is calling the post office every minute to ask if anything arrived — mostly wasted calls. SSE is the mail carrier’s one-way delivery round: mail comes to you as it arrives, but you can’t send anything back on that route. WebSocket is a phone line held open in both directions — powerful, but someone has to keep the line up and redial when it drops.

Transport
WebSocket, SSE, or polling — pick from the requirements, not from habit.
Resilience
Reconnect with backoff, catch up missed events via a cursor, heartbeat dead sockets.
State
One cache as the source of truth; optimistic sends that reconcile or visibly fail.
Rendering
Virtualize long histories, respect the reader’s scroll, announce politely.

01 Pick the transport

Three real options. The interviewer wants to hear you choose, with reasons — not default to the fanciest one.

WebSocketSSEPolling
DirectionBidirectionalServer → client onlyClient pulls on a timer
ReconnectDIY — you write backoff + catch-upNative auto-retry; browser resends Last-Event-ID so the server can resumeFree — every poll is a fresh request
Infra costStateful long-lived connections; load balancers and proxies need carePlain HTTP — proxies, CDNs, and auth middleware just workCheapest — it’s just an endpoint
Wins whenChat, typing indicators, collaborative cursors — the client pushes tooNotifications, tickers, progress, AI token streams — one-wayData changes every few minutes; freshness is non-critical

The verdict to say out loud: chat needs WebSocket (messages and typing indicators flow both ways). A notifications panel is server→client only, so SSE is the boring-and-right answer — less infra, free reconnection. And for low-frequency data, polling with TanStack Query’s refetchInterval is legitimate; saying so is a senior signal, not a cop-out.

You’re building a read-only notifications panel — the client never sends, only receives. First-choice transport?

Right. You’d pay WebSocket’s stateful-infra and hand-rolled-reconnect tax for a direction you never use. SSE gives push, proxy-friendliness, and automatic resume for free. (Sub-second polling is just a self-inflicted DDoS.)

02 Survive disconnects

Connections will drop — laptop lids, flaky wifi, deploys, idle load-balancer timeouts. Plan for it or the feed silently goes stale.

Backoff + jitter
Reconnect at 1s, 2s, 4s… capped, with randomness — so ten thousand clients don’t hammer the server in lockstep after a deploy.
Cursor catch-up
Track the last event/message id you saw. On reconnect, fetch the gap over plain HTTP first, then resume the stream. The socket is for live; history is just a GET.
Heartbeats
Ping/pong every ~30s. A dead socket can look open for minutes — TCP won’t tell you promptly; silence will.
useFeedSocket.ts
useEffect(() => {
  let retry = 0, stop = false, ws: WebSocket;
  function connect() {
    ws = new WebSocket(WS_URL);
    ws.onopen = () => { retry = 0; catchUp(cursor.current); }; // fetch the gap over HTTP first
    ws.onmessage = (e) => { const m = JSON.parse(e.data); cursor.current = m.seq; apply(m); };
    ws.onclose = () => {
      if (stop) return;
      const wait = Math.min(30_000, 1000 * 2 ** retry++) * (0.5 + Math.random()); // backoff + jitter
      setTimeout(connect, wait);
    };
  }
  connect();
  return () => { stop = true; ws.close(); }; // effect cleanup IS the unsubscribe
}, []);

Note the shape: subscribe in the effect, unsubscribe in the cleanup — same contract as any external store. If you reach for SSE instead, the browser does the retry loop and the cursor (Last-Event-ID) for you; say that and you’ve justified the choice twice.

03 Where messages live

Don’t invent a parallel store. Make the TanStack Query cache the source of truth: history loads via useQuery, and socket events write into the same cache with queryClient.setQueryData.

One list, one owner. Components just read the query; whether a message arrived by HTTP or by socket is invisible to them. Because pushes keep the cache fresh, you can set a long staleTime — the socket is your freshness mechanism.

onMessage.ts
socket.onmessage = (e) => {
  const msg: Message = JSON.parse(e.data);
  queryClient.setQueryData<Message[]>(["chat", roomId], (old = []) => {
    if (old.some((m) => m.id === msg.id)) return old;   // dedupe: at-least-once delivery
    return [...old, msg].sort((a, b) => a.seq - b.seq); // order by server sequence
  });
};

Sending is the optimistic-update pattern: append immediately with a temp id and status: "sending", reconcile to the server id on ack, and mark it failed with a retry affordance on timeout. Never silently drop a user’s message — that’s the one unforgivable bug in chat.

Common trap — trusting arrival order gotcha

Events arrive out of order (catch-up fetch races the live stream) and more than once (at-least-once delivery means reconnects replay). If you render the raw arrival order, you get duplicated and shuffled messages. Always render from a deduped-by-id, sorted-by-server-sequence source — arrival order is a lie.

04 Render the feed calm

A stream that constantly mutates the screen is hostile. Three habits keep it calm:

Virtualize history
A months-old channel has tens of thousands of messages; window the list so only the visible slice mounts — same move as the data-table scenario.
Smart auto-scroll
Auto-scroll on new messages only if the user is already at the bottom. If they’ve scrolled up, hold position and show a “New messages ↓” pill that jumps down on click.
Polite announcements
An aria-live="polite" region — but announce batched summaries (“3 new messages”), not every message. Screen-reader users shouldn’t get machine-gunned by a busy channel.
Common trap — the auto-scroll yank gotcha

Unconditional scrollIntoView on every message rips the page out from under someone reading history — the fastest way to make users hate a live feed. Track “is the user pinned to the bottom?” before the new message renders, and only auto-scroll when they are.

05 Interview rapid-fire

WebSocket or SSE for a notifications feed?core
Model answer

SSE. Notifications flow one way — server to client — so WebSocket’s bidirectionality buys nothing while costing stateful infra and a hand-rolled reconnect loop. SSE rides plain HTTP through proxies and auth middleware, and the browser reconnects automatically, resuming from Last-Event-ID. I’d reserve WebSocket for chat, typing indicators, or collaborative editing, where the client pushes too.

Say it out loud say it

“It’s server-to-client only, so SSE — plain HTTP, free auto-reconnect with Last-Event-ID. I’d only pay the WebSocket tax once the client needs to push.”

How do you not lose messages across a reconnect?stretch
Model answer

Keep a cursor — the last server sequence id I’ve applied. On reconnect, first fetch everything after that cursor over plain HTTP, then resume the live stream. Since catch-up and live can overlap, I dedupe by id and render sorted by server sequence, so replays and races are harmless.

Say it out loud say it

“I track the last event id, fetch the gap over HTTP on reconnect, then resume the stream — and dedupe by id so the overlap can’t double-render.”

A user hits send and the request times out. What does the UI do?core
Model answer

The message was appended optimistically with a temp id and a sending status, so it’s already on screen. On ack I swap in the server id and sequence; on timeout I flip it to a visible failed state with a retry button. The one thing I never do is silently drop it.

Say it out loud say it

“Optimistic append with a temp id, reconcile to the server id on ack, and mark it failed-with-retry on timeout — never silently lose a user’s message.”
