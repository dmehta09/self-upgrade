Ship it · accessibility

Accessibility interviewers test

Accessibility isn’t a checklist you bolt on at the end — it’s mostly using the right HTML element. Interviewers probe a narrow, high-signal set: semantic markup, accessible names, and keyboard support. Get those and you cover the vast majority of real-world a11y.

00 Semantic HTML first

The browser gives you accessibility for free when you use the right element. A real <button>, <nav>, or <label> is focusable, announced, and keyboard-operable with zero extra code.

Native elements carry a built-in role, name, state, and keyboard behavior. Reach for ARIA only to patch gaps semantics can’t cover — never as a substitute for the correct tag. The first rule of ARIA is: don’t use ARIA if a native element does the job.

Think of it like… analogy

Ramps and clear signage in a building. A ramp isn’t a special add-on for “some” people — it’s how everyone with a stroller, cart, or wheelchair gets in. Semantic HTML is the ramp: build it in and the place works for everyone. Bolt-on ARIA is a hand-painted sign taped over a doorway with no door.

01 div-soup vs a real button

The classic mistake: a clickable <div>. It looks identical on screen but is invisible to keyboards and screen readers — no role, no focus, no Enter/Space handling.

div-soup (inaccessible)
// Not focusable, no role, ignores keyboard
<div className="btn" onClick={save}>
  Save
</div>
a real button
// Focusable, announced as "button",
// fires on Enter and Space for free
<button type="button" onClick={save}>
  Save
</button>
Common trap gotcha

A <div onClick> isn’t keyboard-focusable and isn’t announced as interactive. Slapping role="button" on it doesn’t fix that — you’d also need tabIndex={0} and manual Enter/Space handlers. ARIA describes; it never adds behavior. Just use <button>.

02 Accessible names & keyboard

Every interactive control needs an accessible name — the text a screen reader announces. Prefer a visible <label> or real text content; use aria-label only when there’s no visible text (e.g. an icon-only button).

  • Form fields — a <label htmlFor> tied to the input’s id (clicking the label also focuses the field).
  • Icon buttons — no visible text, so add aria-label="Close".
  • Keyboard — everything reachable by Tab, with a visible focus ring; never outline: none without a replacement.
PatternAccessibility requirement
Modal / dialogMove focus in on open, trap focus inside, restore it to the trigger on close; Esc closes.
Menu / dropdownArrow-key navigation, Esc to close, focus returns to the trigger button.
Form fieldA real <label> linked by htmlFor/id; errors associated via aria-describedby.
ImageMeaningful alt text; empty alt="" for purely decorative images so they’re skipped.

The quick audit before you ship: tab through the whole page — can you reach and operate everything, and can you always see where focus is? Then run axe DevTools or Lighthouse to catch the rest automatically.

03 Check yourself

A teammate ships an icon-only delete button as <div role="button" onClick={del}>🗑</div>. What’s still broken for accessibility?

Right. role describes but adds no behavior or name. You’d need tabIndex, key handlers, and an aria-label — or just use <button aria-label="Delete">, which gives all three for free.

04 Interview rapid-fire

Why “semantic HTML first” before ARIA?core
Model answer

Native elements come with the correct role, accessible name, state, and keyboard behavior built in — a <button> is focusable and fires on Enter/Space automatically. ARIA only describes semantics to assistive tech; it adds no behavior, so it can’t rescue a non-semantic element. Use it to fill gaps, not replace tags.

Say it out loud say it

“The right element gives you role, name, and keyboard for free. ARIA only describes — it can’t add behavior — so I reach for semantics first and ARIA only to patch gaps.”

How do you handle focus in a modal?core
Model answer

On open, move focus into the dialog (the first control or the dialog itself) and trap it so Tab cycles only within the modal. Esc closes it, and on close you restore focus to the element that opened it. Mark it up as role="dialog" with aria-modal="true" and an accessible name.

Say it out loud say it

“Focus in on open, trap it while open, restore it to the trigger on close, and Esc to dismiss. Most component libraries do this for you — the point is knowing why.”

What common a11y bugs do interviewers probe?stretch
Model answer

Clickable <div>s instead of buttons, missing form labels, icon buttons with no accessible name, removed focus outlines, images without alt, and modals that don’t trap or restore focus. The fast way to surface most of them: tab through the page, then run axe or Lighthouse.

Say it out loud say it

“div-buttons, unlabeled fields, icon buttons with no name, killed focus rings, missing alt, leaky modal focus. I tab through first, then let axe or Lighthouse catch the rest.”
