Make this page fast

“This page is slow — fix it.” The trap is jumping to fixes. The senior move is to measure first, find the one biggest culprit, fix that, and re-measure — tying every symptom back to LCP, INP, or CLS.

00 The idea

Performance work is a loop: measure → find the biggest culprit → fix → re-measure. Anchor it to the three Core Web Vitals so “slow” becomes a specific number.

“Slow” is vague; LCP 4.2 s is actionable. Lead with measurement, identify whether the pain is load (LCP), responsiveness (INP), or stability (CLS), and attack the single largest contributor before touching anything else.

Think of it like… analogy

A good doctor diagnoses before prescribing. They don’t hand you medication the moment you walk in — they run tests, find the actual cause, treat that, then re-check. “Optimizing” a page by guessing is prescribing blind; you measure first so you treat the real disease, not a symptom.

01 The three numbers (June 2026)

Every fix should move one of these. Targets are the 75th-percentile field thresholds.

LCP — load
≤ 2.5 s. Largest Contentful Paint: when the main content (hero image, headline) is visible.
INP — responsiveness
≤ 200 ms. Interaction to Next Paint — replaced FID. How fast the UI reacts to clicks/taps.
CLS — stability
≤ 0.1. Cumulative Layout Shift: how much the page jumps around as it loads.

Measure with Lighthouse (lab) for a repeatable diagnosis, then CrUX / field data for what real users actually experience — they often disagree, and the field is what Google grades.

02 The diagnose-fix loop

Say these four steps out loud and repeat until you’re in budget. The discipline is the point.

1

Measure

Run Lighthouse and check field data. Capture the actual LCP/INP/CLS numbers and a trace — no guessing what’s slow.

2

Find the biggest culprit

Read the waterfall and main-thread flamechart. One thing usually dominates — a giant JS bundle, an unoptimized hero image, a long task.

3

Fix that one thing

Apply the targeted fix for that metric — ship less JS, optimize the LCP image, reserve space to stop a shift. Resist scattershot tweaks.

4

Re-measure

Confirm the number actually moved, then loop. Without re-measuring you don’t know if the fix helped — or if the bottleneck just moved.

03 Symptom → cause → fix

Once you know which vital is failing, the usual suspects and their fixes are well-trodden. This is the map to recite.

SymptomLikely causeFix (and which vital)
Hero takes ages to appearHuge/late LCP image, render-blocking resourceOptimize & preload the image, modern formats, prioritize it — LCP
Long blank then everything pops inToo much client JS; whole page waits on hydrationServer Components, code-split, lazy-load, stream — LCP
Clicks feel laggy / frozenLong tasks blocking the main threadBreak up work, defer non-critical JS, reduce hydration — INP
Content jumps as it loadsImages/ads/fonts with no reserved spaceSet width/height, reserve slots, font-display: optional — CLS
Slow on repeat visits tooNo caching; refetching everythingCache/stream responses, CDN, TanStack Query — LCP/INP
Heads up — the modern lever note

In Next.js 16, the biggest LCP/INP win is usually shipping less JavaScript: keep components as Server Components, push "use client" down to small leaves, and stream. Less client JS means less to download, parse, and hydrate — which moves load and responsiveness at once.

04 The cardinal sin & a quick check

Common trap gotcha

Optimizing without measuring. Sprinkling useMemo or micro-tuning a render loop while the real bottleneck is a 2 MB hero image and 800 KB of JS wastes time and can make code worse. Always profile first, fix the dominant cost, and don’t chase micro-opts before the big one is gone.

Asked to make a slow page faster, what’s your first step?

Right. Diagnose before you prescribe. Without a measurement you don’t know whether the problem is LCP, INP, or CLS — and blind memoization usually targets the wrong thing.

05 Interview rapid-fire

A page is slow — walk me through your approach.core
Model answer

I measure first with Lighthouse and field data to see which of LCP, INP, or CLS is failing. I read the waterfall to find the single biggest culprit, fix just that, then re-measure and repeat. I never optimize blind.

Say it out loud say it

“Measure, find the biggest culprit, fix it, re-measure — tied to LCP, INP, and CLS. Diagnose before you prescribe.”

What are the Core Web Vitals and their targets?core
Model answer

LCP — largest content paint — under 2.5 s for load. INP — interaction to next paint, which replaced FID — under 200 ms for responsiveness. CLS — cumulative layout shift — under 0.1 for visual stability. All at the 75th percentile of field data.

Say it out loud say it

“LCP under 2.5 seconds, INP under 200 milliseconds, CLS under 0.1 — load, responsiveness, stability, measured on real users.”

The page ships too much JavaScript — what do you do?stretch
Model answer

Move work to Server Components so it never reaches the client, push "use client" down to small leaves, code-split and lazy-load below-the-fold pieces, and stream. Less JS to download, parse, and hydrate improves both LCP and INP.

Say it out loud say it

“Ship less JS — keep things server-rendered, push client boundaries to small leaves, code-split, and stream. That moves load and responsiveness together.”
