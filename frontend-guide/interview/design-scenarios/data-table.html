Design a data table

Sortable, filterable, paginated — and it has to stay smooth at 100k rows. The whole game is one question asked over and over: does this operation belong on the client or the server, and how do we render a huge dataset without melting the DOM.

00 The idea

A data table is a view over a dataset with sort, filter, and pagination. The two pivotal calls: client vs server for each operation, and virtualization once rows get large.

A column config drives what renders; table state (sort, filters, page) drives what data you show. Small data → do everything in the browser. Big data → push the work to the server and only paint what’s visible.

Think of it like… analogy

A spreadsheet that stays smooth at 100k rows. You never see all 100k cells at once — the app only draws the few dozen rows in your viewport and reuses them as you scroll (virtualization). Sorting a million rows is a server’s job; redrawing the screen is the browser’s job. Keep those separate.

01 The six steps, on a table

Quick pass first — then we go deep on the two decisions that actually carry the answer.

1 · Requirements
How many rows (100 or 100k)? Which columns are sortable/filterable? Server-paginated API or full dataset in memory? Row selection?
2 · API & state
A columns config (key, header, sortable, render). Table state: sort, filters, page, selection — ideally driven by the URL.
3 · Data flow
Small data: fetch once, derive sorted/filtered rows. Large data: send sort/filter/page to the server and render the returned slice.
4 · Rendering & perf
Virtualize rows past a few hundred; sticky header; memoize row components; don’t refetch on every keystroke.
5 · A11y & edges
Real <table> semantics, aria-sort on headers, keyboard selection, and empty/loading/error states.
6 · Trade-offs
Client = instant but bounded by memory; server = scales but adds latency. URL state = shareable but more plumbing.

02 Client vs server — per operation

This table is the answer to most of the round. Decide each operation by dataset size and whether the full set even lives in the browser.

OperationDo it client-side when…Do it server-side when…
SortingThe full dataset is already loaded and small (< ~10k rows).Data is paginated/huge; you can only see one page, so the server must sort the whole set.
FilteringRows are in memory and filters are simple field matches.Filtering must run across all rows you don’t have, or needs DB indexes/full-text search.
PaginationYou hold every row and just slice locally for display.The dataset is too big to ship — fetch page N on demand (offset or cursor).
SearchInstant client filter over a small loaded list.Backed by a search index; debounce the query and fetch matches.

Rule of thumb: if the whole dataset fits comfortably in memory, do it on the client for instant feedback. The moment it doesn’t, every operation moves to the server — because you can only act on the rows you actually have.

03 Render all rows vs virtualize

Even with server pagination, a single page of a few thousand rows can stutter. Virtualization renders only what’s on screen.

Mount every row
// 100k rows -> 100k DOM nodes
<tbody>
  {rows.map((r) => (
    <Row key={r.id} data={r} />
  ))}
</tbody>
// scroll jank, huge memory, slow paint
Virtualize the viewport
// only ~30 visible rows in the DOM
const v = useVirtualizer({
  count: rows.length,
  estimateSize: () => 40,
  getScrollElement: () => ref.current,
});
// render v.getVirtualItems(), absolutely
// positioned inside a tall spacer
Common trap gotcha

Two killers. Don’t mount 100k DOM rows — the browser chokes on layout and memory; virtualize instead. And don’t refetch the whole table on every keystroke in a filter box — debounce the input and send one request, or filter in memory if the data’s already there.

04 A column config & URL-driven state

Drive the table from a declarative columns array, and keep sort/filter/page in the URL so a view is shareable and survives refresh.

columns.ts
type Column<T> = {
  key: keyof T;
  header: string;
  sortable?: boolean;
  render?: (row: T) => React.ReactNode;
};

const columns: Column<User>[] = [
  { key: "name", header: "Name", sortable: true },
  { key: "email", header: "Email" },
  { key: "role", header: "Role", sortable: true,
    render: (u) => <Badge>{u.role}</Badge> },
];
// table state lives in the URL: ?sort=name:asc&page=2&role=admin
Pro tip tip

URL-as-state makes the table shareable, bookmarkable, and back-button friendly. Pair it with TanStack Query keyed on those params — changing the URL changes the key, which triggers the right refetch automatically. Row selection usually stays in local state (it’s ephemeral, not worth sharing).

A table must show and sort 100k rows from a paginated API. Where should sorting happen?

Right. With pagination you only have one slice in memory, so a client sort would just reorder that slice. The server sorts across all rows, then returns the correct page.

05 Interview rapid-fire

When do you sort/filter on the client vs the server?core
Model answer

If the full dataset is already loaded and small, do it on the client for instant feedback. Once it’s paginated or too big to ship, the server must do it — you can only sort or filter the rows you actually hold.

Say it out loud say it

“Small, in-memory data sorts on the client for speed. Big or paginated data has to sort on the server — you can’t sort rows you don’t have.”

How do you keep a 100k-row table smooth?core
Model answer

Virtualize the rows so only the ~30 visible ones are in the DOM, with a tall spacer to keep the scrollbar honest. Combine that with server pagination/filtering and memoized row components so re-renders stay cheap.

Say it out loud say it

“Virtualization — render only the rows in the viewport, not all 100k. Add server paging and memoized rows and it stays buttery.”

Where should the table’s sort/filter/page state live?stretch
Model answer

In the URL query string. That makes the view shareable, bookmarkable, and back-button friendly, and it becomes a natural cache key for the data fetch. Ephemeral things like row selection can stay in local state.

Say it out loud say it

“I put sort, filter, and page in the URL so views are shareable and it doubles as the query key. Selection stays local since it’s throwaway.”
