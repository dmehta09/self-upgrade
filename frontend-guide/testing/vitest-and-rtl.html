Vitest + React Testing Library

This is the trophy’s sweet spot. Vitest 4 runs your tests fast on top of your Vite config; React Testing Library drives components the way a user does. The whole philosophy: assert on what the user can see and do — never on internal state or props.

00 The idea

Test the app the way a user experiences it, not the way the code is written. Query by role/label/text, interact with userEvent, assert on visible behavior.

RTL deliberately gives you no access to component internals. You find elements the way a person (or screen reader) would — by their accessible role and name — act on them, and check the resulting UI. Tests written this way survive refactors because behavior, not structure, is what they pin down.

Think of it like… analogy

A restaurant critic reviews the meal that arrives at the table — taste, presentation, timing. They don’t march into the kitchen to inspect which pan was used. RTL is the critic: it judges the experience the diner gets (the rendered UI), not the chef’s private technique (your state and props).

PriorityQueryFinds elements byUse when
1getByRoleAccessible role + name (button, link, heading…)Almost always — the default first choice.
2getByLabelTextA form control’s associated labelForm fields.
3getByPlaceholderTextAn input’s placeholderOnly if there’s no real label.
4getByTextVisible text contentNon-interactive text (a paragraph, a message).
5getByDisplayValueA filled-in form valueAsserting current input values.
lastgetByTestIdA data-testid escape hatchOnly when nothing user-facing works.

01 A component test, top to bottom

The shape is always: render → query by role → act with userEvent → assert on what changed. Note what’s missing — no peeking at state, no checking which handler fired.

Counter.test.tsx
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { test, expect } from "vitest";

test("increments when the button is clicked", async () => {
  const user = userEvent.setup();
  render(<Counter />);

  const button = screen.getByRole("button", { name: /count: 0/i });
  await user.click(button);

  // assert on visible output, not internal state
  expect(screen.getByRole("button", { name: /count: 1/i })).toBeInTheDocument();
});

For values that appear after async work, prefer findBy* (it auto-retries) over a manual wait.

Common trap gotcha

Don’t test internal state, and don’t reach for getByTestId when a role works. Asserting on a hook’s value or a private handler couples the test to the implementation, so it breaks on every refactor — while a real bug (a button that stops working) can still slip through. Query the way a user would.

02 Why Vitest 4

Vitest 4 is Vite-native: it reuses your project’s Vite config and transforms, so TS/JSX/aliases “just work” with no separate pipeline. It’s fast (Rolldown-powered), has a Jest-compatible API, and its Browser Mode can run the same tests in a real browser when you need DOM fidelity.

Querying by structure
// ❌ brittle: ties test to markup + ids
const { container } = render(<Login />);
container.querySelector("#submit-btn")?.click();
expect(store.getState().submitted).toBe(true);
Querying by behavior
// ✅ resilient: role + visible result
render(<Login />);
await user.click(screen.getByRole("button", { name: /sign in/i }));
expect(await screen.findByText(/welcome/i)).toBeInTheDocument();

Per React Testing Library’s guidance, which query should you reach for first?

Right. getByRole is the top of the priority list because it reflects the accessible UI a user perceives. getByTestId is the last resort, used only when nothing user-facing identifies the element.

03 Interview rapid-fire

What does “test behavior, not implementation” mean?core
Model answer

Assert on what the user observes — rendered text, roles, what happens after an interaction — not on internal state, props, or which function fired. Behavior-focused tests survive refactors because they only break when the user-facing result actually breaks, which is exactly when you want a failure.

Say it out loud say it

“I test what the user sees and does, not internal state. Then refactors don’t break tests — only real regressions do.”

What’s RTL’s query priority and why?core
Model answer

getByRole first, then getByLabelText for form fields, then text-based queries, with getByTestId dead last. The order tracks how close each query is to the real user/accessibility experience — roles are what assistive tech exposes, while test IDs are invisible to users, so they’re only an escape hatch.

Say it out loud say it

“Role, then label, then text — test ID last. The order mirrors how a real user and a screen reader find things on the page.”

Vitest vs Jest — why pick Vitest in a Vite project?stretch
Model answer

Vitest reuses your Vite config and transform pipeline, so ESM, TypeScript, JSX, and path aliases work with zero extra setup — with Jest you maintain a parallel config and transformer. Vitest is also faster, has a near-identical Jest-compatible API (easy migration), and offers Browser Mode for real-DOM tests.

Say it out loud say it

“Vitest shares the Vite config, so there’s no second toolchain to maintain. It’s faster, the API matches Jest, and Browser Mode is there when I need a real DOM.”
