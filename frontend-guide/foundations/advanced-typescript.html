Advanced TypeScript for React

Past props and Partial lives the TypeScript that wins senior loops: types computed from other types. Generic components, state-machine unions, mapped and conditional types, satisfies and brands — the tools that make invalid states fail at compile time instead of in production.

00 The idea

The type system is a small functional language that runs at compile time. You can compute types from other types, so invalid states don’t compile.

Junior TypeScript annotates values. Senior TypeScript derives them: one source of truth, and everything downstream — props, handlers, state arms — is calculated from it. Change the source and every dependent type updates or turns red.

Think of it like… analogy

A spreadsheet. Your core types are the source cells; mapped and conditional types are the formulas. You never retype a number into a formula cell — it recomputes. Rename a column in the source and every formula either updates instantly or flags #REF!. Copy-pasted types are hand-typed numbers: silently stale the moment the source changes.

01 Generics where React actually needs them

Three moves cover most real generic code in a React app: a component generic over its data, a hook generic over its payload, and inheriting another component’s props with ComponentProps. Everything else is usually <T> for sport — don’t make it generic until a second call site needs it.

generics.tsx
// 1 — generic component: T flows from options into every callback
function Select<T>(props: {
  options: T[];
  label: (o: T) => string;
  onChange: (o: T) => void;
}) { /* render options; each click calls props.onChange(o) */ }

// 2 — generic hook: the caller picks T once at the call site
const me = useFetch<User>("/api/me"); // me.data: User | null

// 3 — inherit props instead of re-declaring them
type IconButtonProps =
  React.ComponentProps<typeof Button> & { icon: React.ReactNode };

Note what T buys you in each: Select infers T from options, so label and onChange are exactly typed at every call site with zero annotations. And ComponentProps<typeof Button> means when Button grows a prop, IconButton gets it for free — no copy-paste to rot.

Heads up see also

Typing a custom hook is half the job — the other half is its identity rules: stable returns, dependency arrays, when its callbacks need to be referentially stable. That side lives in Hooks deep dive; pair the two.

02 Discriminated unions as state machines

Model async React state as one union of legal shapes, not parallel booleans. Each arm carries only the data that exists in that state.

The classic trio — isLoading, error, data as three independent fields — encodes eight combinations when only four are real. What does isLoading: true with data present mean? Nobody knows, and someone will render it. A discriminated union deletes the question.

FetchState.tsx
type FetchState<T> =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: T }   // data exists ONLY here
  | { status: "error"; error: Error };

function View({ state }: { state: FetchState<User[]> }) {
  switch (state.status) {
    case "idle":    return <Hint />;
    case "loading": return <Spinner />;
    case "success": return <UserList users={state.data} />;
    case "error":   return <ErrorBox error={state.error} />;
    default: { const impossible: never = state; return impossible; }
  }
}

This is a state machine: the tag names the state, the arm carries its payload, and the switch is the transition table’s read side. Drive it with useReducer (or useState<FetchState<T>>) and the component can’t touch state.data outside the "success" branch — the compiler narrows it away.

The never default is the senior signature. never is the type with no values, so the assignment only compiles if every arm above handled its case. Add a "refreshing" status next sprint and every switch in the codebase turns red — a to-do list generated by the compiler.

You add a fifth arm { status: "refreshing"; data: T } to FetchState. What does the never default in existing switches do?

Right. Exhaustiveness checking is compile-time: if any arm goes unhandled, the narrowed type in default is no longer never, so the assignment errors. Every stale switch becomes a build failure, not a silent fall-through.

03 Mapped, conditional & infer

Mapped types loop over keys; template literal types compute new key names; conditional types with infer pattern-match a type and pull a piece out. Spreadsheet formulas, all three — they read from a source type and recompute.

type-math.ts
// Mapped + template literal: derive handler names from a record
type Fields = { email: string; age: number };
type Handlers = {
  [K in keyof Fields as `on${Capitalize<K>}Change`]:
    (value: Fields[K]) => void;
};
// => { onEmailChange(v: string): void; onAgeChange(v: number): void }

// Conditional + infer: pattern-match a type, pull a piece out
type UnwrapPromise<T> = T extends Promise<infer U> ? U : T;
type User = UnwrapPromise<ReturnType<typeof fetchUser>>;

Add a field to Fields and Handlers grows the matching on…Change automatically — forget to pass it and the compiler says so. (UnwrapPromise ships built-in as Awaited<T>; the interview point is being able to write it.)

Where this earns its keep day-to-day: you mostly consume these tools rather than write them. The everyday case is z.infer<typeof schema> — your form-values type computed from the runtime validator, one source of truth for both checking and types. The data module’s forms lesson covers Zod itself; here, just know z.infer is a conditional type doing exactly this trick.

04 satisfies, brands & the any problem

Three precision tools, then the one rule about escape hatches. Each solves a “the compiler knows less than it should” problem without lying to it.

satisfies
Checks a value against a type without widening it. const routes = { home: "/", user: "/u/:id" } satisfies Record<string, string> — validated as the record, but routes.home stays the literal "/", so autocomplete and narrowing keep working. An annotation (: Record<…>) would throw the narrow types away. The go-to for config objects.
as const for unions
const SIZES = ["sm", "md", "lg"] as const then type Size = (typeof SIZES)[number] — one runtime array to map over, one compile-time union for props, never out of sync.
Branded types
type UserId = string & { readonly __brand: "UserId" }. At runtime it’s a plain string; at compile time getUser(postId) refuses to build. Mint values with one audited cast at the boundary: const toUserId = (s: string) => s as UserId.
any: the checker goes silent
// ❌ any disables checking transitively
function handle(msg: any) {
  msg.payload.user.id.toUpperCase();
  // compiles — even if msg is undefined,
  // and everything msg touches is any too
}
unknown: prove the shape first
// ✅ unknown forces narrowing before use
function handle(msg: unknown) {
  if (isChatMessage(msg)) {
    msg.payload.text; // narrowed, safe
  }
}
Common trap gotcha

as doesn’t convert anything — it overrules the checker, and as unknown as T overrules it completely. The value at runtime is whatever it was; you’ve just told the compiler to stop looking. Prefer narrowing, a type guard, or satisfies; reserve as for boundaries where you genuinely know more than the compiler — and back it with a runtime check (that’s what Zod is for).

05 Interview rapid-fire

How do you type async data in React state so impossible states can’t compile?core
Model answer

A discriminated union on a status tag, with each arm carrying only its own payload: data exists on "success", error on "error", nothing on "idle"/"loading". The switch narrows per arm, and a never default makes it exhaustive — adding a status later breaks the build everywhere it’s unhandled, instead of silently falling through.

Say it out loud say it

“One union tagged by status, payload per arm, exhaustive switch with a never default — you can’t read data outside the success branch, and new states become compile errors, not bugs.”

Follow-ups to expect
  • Why is { isLoading, error, data } as three fields worse? (8 representable states, 4 legal.)
  • Would you hand-roll this or use TanStack Query’s status union?
Where do conditional types and infer show up in everyday React work?core
Model answer

Mostly consumed, rarely written: z.infer computes form-value types from a Zod schema, Awaited/ReturnType/Parameters unwrap function and promise types, and ComponentProps extracts a component’s props. I write my own when I need to pull a piece out of a library type that isn’t exported — T extends Promise<infer U> ? U : T is the pattern-match.

Say it out loud say it

“Day to day it’s z.infer and the built-ins like Awaited and ComponentProps; infer is the pattern-matching keyword underneath all of them.”

What does satisfies give you that a type annotation doesn’t?stretch
Model answer

An annotation both checks and widens: declare routes: Record<string, string> and every value becomes plain string — literal keys and values are gone. satisfies runs the same check but keeps the inferred narrow type, so the object is validated against the contract while autocomplete, literal unions, and narrowing still work downstream. It’s the right default for config maps, theme tokens, and route tables.

Say it out loud say it

“An annotation checks and widens; satisfies checks and keeps inference — the config is validated but its literal types survive.”
