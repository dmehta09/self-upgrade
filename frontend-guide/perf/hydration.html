Performance · hydration

Hydration, explained

Server HTML paints fast — but it’s a photograph, not a working machine. Hydration is React re-running on the client to wire up event handlers over that markup. The window between “painted” and “wired” is exactly where INP goes to die.

00 The idea

Hydration = React re-running on the client over server HTML to attach handlers and state. The page is visible before it’s interactive.

The server sends finished HTML, so it paints quickly. But buttons do nothing until the JS bundle loads and React walks the same tree, reconnecting event listeners and rebuilding component state. Until that finishes, every click is dropped or queued — the page looks done but isn’t.

Think of it like… analogy

It’s a film set you can already see — walls up, furniture placed, perfectly lit (the server HTML is painted). But the actors aren’t mic’d and the lighting board isn’t plugged in yet. You can shout from the audience all you like; until the crew wires it (the JS hydrates), nothing on stage responds.

The cost driver
Hydration work scales with the number and size of client components — React must walk and wire each one.
Why INP suffers
Clicks during the gap are dropped or queued; the main thread is busy hydrating, so the first interaction feels laggy.

01 Mismatches: when client ≠ server HTML

Hydration assumes the client’s first render produces the same tree the server sent. Non-deterministic render — Date, Math.random(), reading window — breaks that, and React warns (and may discard the server HTML for that subtree).

Causes a mismatch
function Clock() {
  // ❌ server time ≠ client time
  return <time>{new Date().toLocaleTimeString()}</time>;
}
Deterministic on first paint
"use client";
function Clock() {
  const [now, setNow] = useState<string>("");
  // ✅ render time only after mount, client-side
  useEffect(() => setNow(new Date().toLocaleTimeString()), []);
  return <time>{now}</time>;
}
Common trap gotcha

suppressHydrationWarning is a scalpel, not a fix. It silences the warning for genuinely unavoidable cases (a timestamp, a locale-formatted number) — it does not reconcile the difference. Reach for it sparingly; fix the non-determinism first.

02 Making hydration cheaper

Less client JS = less to hydrate. The lever is the client/server boundary: keep components as server components by default and mark only genuinely interactive leaves with "use client", so you ship a few small islands instead of one giant tree.

  • Static content = ~no hydration. A server-rendered article (RSC) ships almost no JS — nothing to wire up.
  • Isolate the island. Push "use client" down to the smallest interactive leaf (a like button), not its whole page.
  • RSC + streaming compound. Fewer client components shrink the hydration bill; streaming spreads the rest across paint.
article/page.tsx
// Server component — zero client JS, nothing to hydrate.
export default function Article({ post }) {
  return (
    <article>
      <Prose html={post.body} />
      <LikeButton id={post.id} />  {/* the only "use client" island */}
    </article>
  );
}

Two pages paint at the same time, but one is interactive far sooner. The likeliest reason?

Right. Paint depends on HTML; interactivity depends on hydration. Fewer, smaller client islands mean React finishes wiring handlers sooner — closing the “looks ready but isn’t” gap and helping INP.

03 Interview rapid-fire

What is hydration and why is it costly?core
Model answer

Hydration is React re-running on the client over the server’s HTML to attach event handlers and rebuild component state — it makes a painted page interactive. It’s costly because it’s main-thread work that scales with how many client components you ship, and clicks during it are dropped or delayed, which hurts INP.

Say it out loud say it

“Hydration is React replaying on the client to wire handlers over server HTML. It’s the gap where the page looks ready but isn’t — and it scales with client JS.”

What causes hydration mismatches?core
Model answer

Non-deterministic rendering — the client’s first render differs from the server’s HTML. Classic causes are Date/Date.now(), Math.random(), and reading browser-only globals like window or localStorage during render. The fix is to defer that work to useEffect so the first client render matches the server.

Say it out loud say it

“Anything non-deterministic at render — time, randomness, window. The first client render must equal the server HTML, so I move that into an effect.”

How do you reduce hydration cost?stretch
Model answer

Ship less client JS. Keep components as server components by default and push "use client" down to the smallest interactive leaves, so you hydrate a few small islands instead of the whole tree. RSC plus streaming compounds the win — less to hydrate, and what remains is spread across paint.

Say it out loud say it

“Fewer, smaller client islands. Server components by default, "use client" only on the interactive leaves — and lean on RSC plus streaming.”
