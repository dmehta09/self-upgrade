Production Debugging & Incident Investigation

Interviewers use production debugging to test whether you can isolate a failure hop-by-hop under pressure, not whether you memorize nginx flags. They want a calm structure: classify the status code, pick a correlation id, walk the path from edge to app, and prove each layer with logs and health signals. Seniors name concrete artifacts — ALB target health, nginx error.log, upstream timeouts, docker events — instead of vague 'check the logs'.

01  Decision cheat strip

502 vs 504502 = bad gateway / upstream dead or reset; 504 = gateway waited and timed out
Correlation idPropagate X-Request-Id from ALB/nginx into app logs before comparing layers
Health ≠ latencyGreen /health can coexist with hanging workers and slow upstreams
p95 > meanTail latency reveals queueing, GC, lock contention, and slow deps mean hides
Isolate one hopBypass ALB → hit nginx → hit container port → hit app; change one variable
Recent changeDeploy time, config reload, AMI, security group, and cert expiry first

d01-q01Your request flow is DNS -> AWS Load Balancer -> Nginx -> EC2 -> Docker -> application. You receive a 502 response. How will you debug it step by step?
First 30 seconds
I treat 502 as 'proxy got a bad/empty upstream response,' not a client timeout. I'll pick one failing request id, then walk DNS → ALB target health → nginx upstream → container port → app process, proving each hop with a concrete signal before moving inward.
Model answer
  1. Confirm the 502 source: response headers / ALB access logs vs nginx access.log. Note whether ALB generated it (target reset) or nginx (upstream prematurely closed).
  2. Check ALB target group health: Unhealthy targets, deregistration, failing health checks, security group blocking health path, or wrong port/path.
  3. On the instance: curl -v localhost: and localhost: with the same Host/path. Connection refused vs reset vs HTTP error narrows Docker vs app.
  4. Read nginx error.log for upstream timed out / connect() failed / no live upstreams / SSL handshake — pair with the $request_id or X-Request-Id.
  5. docker ps / docker events: exited containers, restarts, OOMKilled. Inspect app logs for crash at that timestamp.
  6. Verify listen address: app bound to 127.0.0.1 only, wrong published port, or nginx proxy_pass to a dead container IP after recreate.
  7. Check recent deploys/config: nginx reload with bad upstream, new AMI, changed target port, or ALB stickiness sending to a bad node.
  8. Mitigate: drain bad targets, roll back last change, fix health check path, then re-verify one synthetic request end-to-end with correlation id.
Diagram
flowchart TB
  Client --> DNS
  DNS --> ALB
  ALB --> Nginx
  Nginx --> Docker
  Docker --> App
  ALB -.->|target_health| Health
  Nginx -.->|error.log| UpstreamErr
  Docker -.->|events_OOM| Restart
Code / ops
bash
# Prove the hop that returns 502
curl -sv -H "X-Request-Id: debug-$(date +%s)" https://api.example.com/v1/orders
aws elbv2 describe-target-health --target-group-arn "$TG_ARN"
sudo tail -n 200 /var/log/nginx/error.log
docker ps -a --filter name=api && docker events --since 30m --filter event=oom --filter event=die
Nest / Node: Same hop walk applies to Nest behind nginx; Node process crashes still show as upstream resets. Distinguish Express/Nest uncaughtException exits from nginx proxy_read_timeout (that tends toward 504).
Say it out loud
Say it spoken

A 502 means some hop returned an invalid gateway response — usually connection refused, reset, or crash mid-write — not a patient timeout. I correlate one request id across ALB and nginx, prove target health and local curl to the container, then fix the dead upstream before touching application business logic.

Traps / weak answers
  • Jumping straight into application business logic without checking ALB target health or nginx upstream errors
  • Confusing 502 (bad/empty upstream) with 504 (gateway waited too long)
  • Assuming green DNS or a prior successful deploy means the current container is still listening on the expected port
Follow-ups
  • How do you distinguish an ALB-generated 502 from an nginx-generated 502 in logs?
  • What if only one AZ's targets are unhealthy — what do you check next?

d01-q02Users intermittently receive 504 responses, while application health checks remain green. How will you determine where the timeout occurs?
First 30 seconds
504 means a gateway gave up waiting — I map every timeout knob (ALB idle, nginx proxy_read_timeout, app/server, outbound HTTP client) and find which one fired first using timestamps and correlation ids. Green health only proves the cheap probe path, not that workers finish real requests in time.
Model answer
  1. Pull one 504 sample: ALB access log target_processing_time / request_processing_time vs nginx $upstream_response_time and $request_time.
  2. Compare timeout budgets: ALB idle timeout (often 60s), nginx proxy_connect/send/read_timeout, uvicorn/gunicorn timeout, httpx/aiohttp client timeouts to deps.
  3. If ALB time ≈ ALB idle and nginx never logged completion → bottleneck before nginx finished, or nginx itself hung waiting on upstream.
  4. If nginx error.log shows upstream timed out → app or something behind nginx exceeded proxy_read_timeout while health still passed on /health.
  5. Instrument slow handlers: DB query time, lock waits, outbound API p95 — hanging workers keep /health green if health bypasses the pool or hits a separate process.
  6. Check connection pool exhaustion and thread/async worker saturation under concurrency spikes that match the intermittent window.
  7. Reproduce with load: raise concurrency until 504s appear; confirm whether raising only nginx timeout masks the symptom or moves the failure to the client.
  8. Fix the true slow hop (query, dep, pool size) or align timeouts intentionally (client < nginx < ALB) with fail-fast, not infinite waits.
Code / ops
bash
# Compare budgets (example)
# ALB idle_timeout.timeout_seconds vs nginx:
# proxy_read_timeout 60s; proxy_connect_timeout 5s;
# App: httpx.Timeout(connect=2.0, read=10.0)
grep upstream /var/log/nginx/error.log | tail
aws logs filter-log-events --log-group-name /aws/applicationloadbalancer/... --filter-pattern '"elb_status_code":"504"'
Nest / Node: In Nest, long-running interceptors or sync CPU in the event loop produce the same pattern: health on a separate route stays 200 while ALB/nginx hit 504. Prefer timeouts on HttpService/axios and queue heavy work.
Say it out loud
Say it spoken

Intermittent 504s with green health are almost always a timeout-budget mismatch on the real path — slow dependency or saturated workers — not a dead process. I line up ALB and nginx timings for one request id, find which timer fired first, then fix the slow work instead of blindly raising every timeout.

Traps / weak answers
  • Raising all timeouts until 504s disappear without finding the slow dependency
  • Trusting /health as proof that request workers are free
  • Ignoring that client, ALB, and nginx may have different idle timeouts
Follow-ups
  • How would you order timeout values across client, ALB, nginx, and the app?
  • What metrics prove worker pool saturation versus a single slow SQL query?
d01-q03Nginx is running, but one API route returns the Nginx default 404 page instead of the backend response. How will you trace the request?
First 30 seconds
Default nginx 404 means the request never matched a location that proxies to the app — or the upstream returned nothing and a static/default server answered. I'll dump the effective server/location selection for that Host and URI, then prove whether the backend even saw the request.
Model answer
  1. Capture Host header, exact path, method, and whether HTTP vs HTTPS — default_server and SNI mismatches often hit the wrong server block.
  2. nginx -T (or include dump) and find which server{} and location{} win for that URI; look for missing trailing slash, regex location order, or alias vs root mistakes.
  3. Confirm proxy_pass exists for that location and that try_files / static root is not short-circuiting before proxy.
  4. Check access.log: upstream status empty vs 404 from upstream — default HTML 'nginx' page is usually nginx itself, not FastAPI's JSON 404.
  5. Hit the container directly with the same path; if app returns JSON 404, the route isn't registered; if app 200, nginx routing is wrong.
  6. Verify strip-prefix behavior: proxy_pass http://upstream/api/ vs http://upstream; without URI rewrite, /api/v1 may become wrong path on the app.
  7. Reload only after validating config; use a canary location or temporary return 418 to prove which block matched.
  8. Fix the winning location/upstream, add a regression curl in CI for that Host+path, and alert on nginx 404 rate for API vhosts.
Code / ops
bash
nginx -T 2>/dev/null | less
curl -i -H 'Host: api.example.com' http://127.0.0.1/v1/orders
curl -i http://127.0.0.1:8000/v1/orders  # direct to uvicorn
Nest / Node: Nest global prefix (e.g. setGlobalPrefix('api')) must match what nginx forwards after rewrite; a mismatch yields framework 404 JSON, whereas default nginx HTML means the proxy never reached Nest.
Say it out loud
Say it spoken

An nginx-branded 404 almost always means the wrong server or location won, not that FastAPI threw NotFound. I prove Host and URI selection with nginx -T, curl the container with the same path, and fix proxy_pass or location precedence before changing application routes.

Traps / weak answers
  • Assuming the app route is missing because the browser shows 404 — without checking the response body fingerprint
  • Editing the wrong server block while default_server still catches the Host
  • Forgetting proxy_pass URI slash semantics that strip or preserve path prefixes
Follow-ups
  • How do you prove which location block matched in production without guessing?
  • What is the difference between an nginx default 404 page and a FastAPI JSON 404?
d01-q04An application works when called directly on its port but fails through the load balancer. What would you check and in what order?
First 30 seconds
Direct-port success isolates the app; failure via LB means edge config — listeners, target groups, security groups, health checks, Host/TLS, or path routing. I compare one request that works to localhost with one that fails through the ALB and diff headers, ports, and health.
Model answer
  1. Confirm direct success: curl instance_ip:app_port and docker-published port; note status, body, and timing.
  2. ALB listener rules: host/path conditions, HTTPS cert, redirects, and whether traffic hits the intended target group.
  3. Target group: protocol/port matching the process, health check path/matcher (200 vs 302), interval, and healthy host count.
  4. Security groups: ALB SG → instance SG on the app/nginx port; NACL; public vs private subnet reachability from ALB.
  5. If nginx is in path: ALB → nginx port works? nginx → app fails? Re-run hop isolation.
  6. Header/TLS differences: X-Forwarded-Proto/For, Host, sticky sessions, HTTP/2, request body size limits, WAF blocks.
  7. Idle timeout / deregistration: long requests fail only via ALB; connection drains mid-deploy.
  8. Fix the mismatched hop (usually health check path or SG), verify ALB access logs show 200, then remove temporary direct-port access.
Code / ops
bash
curl -i http://$INSTANCE:8000/healthz
curl -i https://api.example.com/healthz
aws elbv2 describe-target-health --target-group-arn "$TG_ARN"
aws ec2 describe-security-groups --group-ids "$APP_SG"
Say it out loud
Say it spoken

If localhost works and the load balancer fails, I treat the app as innocent until proven otherwise and walk listener → target group → security group → health check → nginx. Most of these incidents are wrong port, wrong health path, or SG rules — not application bugs.

Traps / weak answers
  • Rewriting application code before verifying target group port and health check matcher
  • Opening the instance to 0.0.0.0/0 as a 'fix' instead of ALB security-group peering
  • Ignoring that health checks may use HTTP while the listener is HTTPS-only for clients
Follow-ups
  • Health checks fail but manual curl to the instance succeeds — what are the usual causes?
  • How do X-Forwarded-Proto mismatches break cookie Secure or redirect loops behind an ALB?
d01-q05One EC2 instance behind the load balancer is failing while the others work normally. How would you isolate the fault?
First 30 seconds
I quarantine the bad target so users stop hitting it, then compare that host to a healthy peer: processes, disk, time, container state, and recent node-local changes. Fleet-wide config bugs don't usually single out one instance.
Model answer
  1. Identify the bad target from ALB target health / 5xx spiked host; deregister or set unhealthy weight to stop traffic.
  2. Compare curl through ALB with Availability-Zone / target sticky disabled vs direct to the instance IP.
  3. On the bad node: docker ps, nginx -t, disk full (df -h), inode exhaustion, clock skew, file descriptor limits.
  4. diff against a healthy sibling: AMI/launch template version, user-data, env files, mounted secrets, nginx upstream file.
  5. Check instance-local events: OOM, kernel logs, NVMe failures, ENI issues, security group accidentally unique to that instance.
  6. App metrics labeled by instance_id/host: error rate, restart count, GC, connection errors to Redis/DB from that AZ.
  7. If AZ-specific: subnet route, NAT, VPC endpoint, or AZ outage — not just 'the box'.
  8. Replace or repair the node (ASG instance refresh), verify healthy, re-register, and add host-dimension alerts so one bad canary is obvious.
Code / ops
bash
aws elbv2 deregister-targets --target-group-arn "$TG_ARN" --targets Id=$BAD_ID
ssh $BAD_HOST 'df -h; docker ps -a; free -m; sudo journalctl -u docker --since "1 hour ago" | tail'
Say it out loud
Say it spoken

One bad instance is a gift — I drain it from the target group immediately, then diff that host against a healthy twin. Disk full, drifted container, or AZ networking usually explains it; I don't restart the whole fleet first.

Traps / weak answers
  • Rolling all instances when only one target is unhealthy
  • Leaving the bad instance in rotation while 'investigating'
  • Ignoring AZ-scoped networking and blaming application code on a single host
Follow-ups
  • How do you safely drain an instance without dropping in-flight requests?
  • What metrics dimensions do you need to spot a single bad host quickly?
d01-q06Production API latency increases from 100 ms to 2 seconds immediately after a deployment. How would you prove whether the deployment caused it?
First 30 seconds
I align latency charts to the exact deploy marker and compare canary versus baseline, not vibes. Proof means the regression starts at deploy time, affects only new versions or new config, and rolls back when we revert — with the same traffic shape.
Model answer
  1. Mark deploy timestamp (CI, ECS/ASG deploy, or feature flag). Overlay p50/p95 latency, error rate, and saturation.
  2. Split metrics by version/build SHA, task definition, or canary target group — only new version slow ⇒ deploy-caused.
  3. Check what changed: dependency versions, ORM queries, N+1, removed cache, sync calls in async path, lower worker count, new middleware.
  4. Compare DB: slow query log, lock waits, plan changes after migration shipped in the same deploy.
  5. Rule out coincidence: traffic spike, dependency incident, noisy neighbor — look at shared graphs without a deploy marker.
  6. Run controlled rollback or shift 100% to previous target group; latency returning to 100 ms is strong causal proof.
  7. If canary-only: hold canary, dump profiles/traces (OpenTelemetry) for the new build's hot spans.
  8. Document root cause, add a latency SLO burn alert on deploy, and require canary + automatic rollback next time.
Code / ops
text
# Pseudo: compare latency by version label after deploy
# rate(http_request_duration_seconds_bucket{version="2.14.0"}[5m])
# vs version="2.13.2" around deploy timestamp
Say it out loud
Say it spoken

Correlation with deploy time isn't enough — I need version-dimensioned latency and a successful rollback or canary contrast. If only the new SHA is slow and reverting restores p95, the deployment caused it; then I dig into the diff for queries, cache, or blocking I/O.

Traps / weak answers
  • Blaming the deploy because it was recent without version-split metrics
  • Rolling forward with 'one more fix' instead of proving with rollback
  • Looking only at mean latency and missing a p95 cliff
Follow-ups
  • What is your canary and automatic rollback criteria for latency regressions?
  • How do you separate a bad migration from bad application code in the same release?
d01-q07Your API returns 200 responses but users report that requests occasionally hang until the client times out. How would you investigate?
First 30 seconds
Hangs with eventual 200 or client-side timeouts mean the server accepted work but didn't finish in time — often queueing, blocked workers, or a missing response flush. I'll look at in-flight request age, worker utilization, and traces for spans that never end, not just status-code dashboards.
Model answer
  1. Instrument in-flight gauge and request age histogram; alert when age exceeds SLO while status still pending.
  2. Check whether clients time out first (browser/ALB) while the app later logs a 200 — classic slow handler finishing after the client left.
  3. Inspect concurrency: uvicorn workers, anyio thread limits, DB pool wait, Redis connection pool — all busy waiting on I/O.
  4. Distributed traces: find orphaned/long spans (DB, HTTP client) around hang windows; enable sampling for slow traces.
  5. nginx access: requests with large $request_time and empty/partial upstream; upstream keepalive issues.
  6. Look for deadlocks: asyncio tasks waiting on each other, sync ORM inside async route, or lock ordered wrong under load.
  7. Reproduce with concurrent load matching production; a single curl will miss pool exhaustion.
  8. Mitigate with deadlines (asyncio.wait_for / httpx timeout), shed load, fix blocking call, and return 503 when queue depth is too high instead of hanging.
Code / ops
python
import asyncio
from fastapi import FastAPI
import httpx

app = FastAPI()

@app.get("/orders/{oid}")
async def get_order(oid: str):
    async with httpx.AsyncClient(timeout=2.0) as client:
        # Bound outbound wait — never hang the worker unbounded
        r = await asyncio.wait_for(client.get(f"http://billing/orders/{oid}"), timeout=2.5)
        return r.json()
Nest / Node: In Nest/Node, an await that never resolves (missing timeout on axios) pins the request; forEach(async) fire-and-forget can also leave clients waiting on something else. Use AbortSignal timeouts and concurrency limits.
Say it out loud
Say it spoken

Occasional hangs aren't visible on a 200-rate graph — I need in-flight age and traces. Usually every worker is stuck on a slow dependency or a sync call in an async path, so clients time out while health stays green and some requests still finish as 200 late.

Traps / weak answers
  • Only graphing HTTP status codes and declaring the API healthy
  • Reproducing with a single sequential curl under no load
  • Infinite client retries that amplify worker saturation
Follow-ups
  • How do you expose 'requests older than 5s' as a metric in FastAPI/uvicorn?
  • When should the API return 503 with Retry-After instead of letting clients hang?
d01-q08The service has normal CPU and memory but p95 and p99 latency suddenly increase. What signals would you inspect?
First 30 seconds
Flat CPU/memory with a bad tail means waiting, not computing — I inspect dependency latency, queue/pool wait, locks, GC/event-loop lag, and noisy neighbors. Mean can look fine while p99 burns the SLO.
Model answer
  1. Break latency by span: app handler, DB, Redis, HTTP deps — find which component's p95 moved.
  2. Connection pool metrics: checkout wait time, pool size vs in-use, timeouts acquiring connections.
  3. DB: lock waits, slow queries, buffer cache hit, vacuum/autovacuum spikes, connection count.
  4. Event-loop lag / asyncio delay metrics; GC pause if using a threaded or JVM sidecar (less common in CPython but relevant for workers).
  5. Queue depth: Kafka consumer lag, Celery/RQ depth, or internal anyio task queues.
  6. Network: DNS latency spikes, TLS handshake time, AZ packet loss, NAT gateway exhaustion.
  7. Saturation elsewhere: thread pool for run_in_executor, file descriptors, ephemeral port exhaustion.
  8. Correlate with deploys, traffic shape (fanout), and dependency status pages; fix the waiting hop and add tail-latency SLOs.
Nest / Node: Node: monitor event-loop delay (perf_hooks) and libuv threadpool usage for fs/crypto; same 'flat CPU, bad p99' pattern.
Say it out loud
Say it spoken

When resources look fine but p95 explodes, the process is blocked on I/O or locks. I split latency by dependency and pool wait — the answer is usually a slow DB, exhausted connection pool, or outbound API — not 'add more CPU'.

Traps / weak answers
  • Scaling CPU horizontally when the bottleneck is DB locks or pool wait
  • Watching only average latency
  • Ignoring outbound dependency SLIs
Follow-ups
  • Which RED/USE signals would you put on a single dashboard for this?
  • How do you tell lock contention from missing indexes using p95 alone?
d01-q09A container repeatedly restarts in production. How would you determine whether the cause is OOM, health checks, process crashes, or infrastructure?
First 30 seconds
I classify the restart using docker/kube exit codes and events first — OOMKilled, non-zero exit, or health-check kill look different. Then I align timestamps with app logs, probe failures, and node events so I don't guess.
Model answer
  1. docker inspect / kubectl describe: LastState, OOMKilled, ExitCode, RestartCount, reason (Error vs OOMKilled).
  2. docker events / kube events around restarts: health unhealthy, killed, deadline exceeded.
  3. Distinguish liveness kill (probe fail) from crash: app logs show clean listen then probe 404/5xx vs traceback then exit.
  4. Memory: cgroup limit vs RSS/working set; sudden jump ⇒ leak or cache; flat then OOM ⇒ limit too low for peak.
  5. Process crash: uncaught exception, segfault (native deps), failed migration on boot — read previous container logs.
  6. Infrastructure: node pressure, spot interruption, disk pressure, docker daemon restart, failed image pull after GC.
  7. ALB/target: flapping health if container isn't ready — fix readiness vs liveness so traffic doesn't hit booting tasks.
  8. Remediate specifically: raise memory or fix leak, correct probe path, fix crash, or replace bad node; add restart-reason metrics.
Code / ops
bash
docker inspect -f '{{.State.OOMKilled}} {{.State.ExitCode}} {{.RestartCount}}' api
docker events --since 2h --filter container=api
docker logs api --previous --tail 200
Say it out loud
Say it spoken

Restart loops are a taxonomy problem: OOMKilled, exit code, or probe kill. I read the container's last state and events before changing application code, then fix the matching cause — memory limit, bad liveness path, crash on boot, or a sick node.

Traps / weak answers
  • Increasing replicas without reading OOMKilled or ExitCode
  • Using the same probe for liveness and a heavy dependency check, causing kill loops
  • Assuming every restart is an application exception
Follow-ups
  • How should readiness and liveness probes differ for a FastAPI service?
  • What ExitCode patterns suggest segfault versus unhandled Python exception?
d01-q10A production problem occurs only during high concurrency and cannot be reproduced with one request. How would you investigate it?
First 30 seconds
Concurrency bugs need concurrent load, shared-resource metrics, and race-aware tracing. I'll reproduce with controlled parallelism, watch pools/locks/limits, and capture dumps when contention peaks — a single curl will never show it.
Model answer
  1. Define the symptom under load: error type, latency cliff, or wrong data — and the concurrency threshold where it starts.
  2. Load-test in staging with production-like pools (DB, Redis, httpx limits) and ramp RPS/concurrency.
  3. Watch shared resources: DB connections, row locks, unique constraint races, Redis hot keys, rate limits, file descriptors, ephemeral ports.
  4. Check async pitfalls: shared mutable state without locks, non-thread-safe clients used across tasks, missing idempotency under double-submit.
  5. Capture evidence at peak: slow-query log, pg_stat_activity, thread/task dump, connection pool wait histograms.
  6. Feature-flag mitigations: lower concurrency, shed load, serialize critical section, or enable idempotency keys.
  7. Add regression test: concurrent integration test that fails before the fix (e.g. 100 parallel creates).
  8. Fix root cause (pooling, locking, idempotency, backpressure) and set alerts on pool wait and lock time, not only CPU.
Code / ops
python
import asyncio, httpx

async def hammer():
    async with httpx.AsyncClient(base_url="http://localhost:8000", timeout=5.0) as c:
        sem = asyncio.Semaphore(50)
        async def one(i):
            async with sem:
                r = await c.post("/orders", json={"sku": "x", "key": f"idemp-{i%10}"})
                return r.status_code
        codes = await asyncio.gather(*[one(i) for i in range(500)])
        print(sorted(set(codes)), codes.count(409), codes.count(500))

asyncio.run(hammer())
Nest / Node: Node cluster/PM2 multi-process can hide in-memory race bugs that appear on a single Nest process under async concurrency — test both shapes.
Say it out loud
Say it spoken

If it only fails under concurrency, I refuse to debug with one request. I ramp load, watch connection pools and locks, and look for races or exhaustion — then I ship a concurrent regression test so we don't 'fix' it with a quiet afternoon.

Traps / weak answers
  • Trying to reproduce only with Postman one-at-a-time
  • Increasing DB max_connections without fixing pool sizing or query time
  • Calling it a 'Heisenbug' without capturing pool/lock metrics at failure
Follow-ups
  • How do you size an asyncio HTTP client and DB pool relative to worker count?
  • What race conditions appear when two requests create the same order without an idempotency key?

03  Self-check

Users see 502 from the ALB while target health is intermittent. What does 502 most strongly imply?
502 Bad Gateway means the proxy got an invalid/empty response from upstream (connection refused, reset, crash mid-response). 504 is the timeout case.
App /health is green but clients hang until the browser times out. Where should you look first?
Health checks use a cheap path and may bypass the saturated pool. Hanging 200-path work often means all workers are busy on slow I/O or blocking CPU.
p95 jumps while CPU and memory stay flat. Which signal set is most useful?
Flat resources with bad tails usually mean waiting on network/DB/locks/pools, not raw compute exhaustion.
docker events show OOMKilled. What should you correlate next?
OOMKilled is a hard memory limit signal — confirm limit vs usage and what allocated (cache, leak, spike).
