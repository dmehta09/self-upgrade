Distributed Systems & Failure Handling

Interviewers use distributed-systems questions to see whether you design for partial failure, not the happy path. Seniors talk about sagas, idempotency, timeout budgets, backpressure, and load shedding as operational controls—not buzzwords. FastAPI services that call other APIs or queues must make duplicates and crashes safe by default.

01  Decision cheat strip

SagaLocal tx + compensate; never distributed 2PC across services
ConsistencyStrong for money/inventory; eventual for feeds/counters with repair
Exactly-oncePractically = at-least-once delivery + idempotent write + dedupe key
CascadesTimeouts + circuit breaker + bulkhead isolation per dependency
OverloadBackpressure queues work; load shedding drops low-priority early
JobsQueue + visibility timeout + heartbeat; catch-up is idempotent + cursor

d09-q01Service A succeeds but service B fails halfway through a business workflow. How would you recover without corrupting state?
First 30 seconds
I treat this as a saga, not a distributed transaction. Name the workflow id, list completed steps, and define compensations for each success so we can unwind or resume without double-applying effects.
Model answer
  1. Model the business flow as an orchestrated (or choreographed) saga: each local step commits in its own DB transaction and records progress against a workflow_id.
  2. On B failure after A succeeded: either retry B with the same idempotency key, or run A's compensation (e.g. release reservation, void hold) if B is terminal.
  3. Persist saga state (PENDING / STEP_A_DONE / COMPENSATING / FAILED / COMPLETED) so a crash mid-recovery can resume safely.
  4. Make every step and compensation idempotent: unique constraints or upserts keyed by workflow_id + step name.
  5. Emit metrics and alerts on stuck sagas; operators need a replay/compensate path, not manual SQL.
  6. Prefer orchestration in FastAPI for complex money flows (clear ownership); choreography only when teams own independent domains and accept eventual repair.
Diagram
flowchart LR
  start[Start] --> A[StepA_commit]
  A --> B{StepB_ok}
  B -->|yes| done[Completed]
  B -->|no| comp[Compensate_A]
  comp --> fail[Failed_or_retry]
Code / ops
python
async def place_order(workflow_id: str, item_id: str):
    await inventory.reserve(workflow_id, item_id)  # idempotent on workflow_id
    try:
        await payments.charge(workflow_id)
    except PaymentFailed:
        await inventory.release(workflow_id)  # compensation
        raise
Nest / Node: In Nest, put saga orchestration in a dedicated service or Temporal/Cadence worker; use interceptors only for cross-cutting retries/logging, not for business compensation logic.
Say it out loud
Say it spoken

I wouldn't reach for 2PC across services. I'd run a saga with idempotent steps and compensations keyed by a workflow id, so a mid-flight failure either retries the failed step or unwinds completed ones without corrupting inventory or money.

Traps / weak answers
  • Proposing XA/2PC across microservices as the default.
  • Compensating without idempotency keys (double-release or double-charge).
Follow-ups
  • Would you use orchestration or choreography for a three-step checkout?
  • How do you detect and alert on stuck sagas older than N minutes?

d09-q02When should a system prefer strong consistency, and when is eventual consistency acceptable?
First 30 seconds
I start from the business invariant: if two concurrent writers can create an illegal state (oversell, double-pay, duplicate ledger), I need strong consistency on that write path. Everything else can be eventual with clear repair.
Model answer
  1. Prefer strong consistency for financial ledgers, inventory decrement, unique username assignment, and any invariant that must never be temporarily false for user-visible correctness.
  2. Use a single source of truth (one Postgres row/partition, SERIALIZABLE or careful locking, or a consensus store) for those critical writes.
  3. Eventual consistency is fine for feeds, search indexes, analytics counters, recommendation caches, and cross-region replicas where stale reads are tolerable.
  4. When eventual: define lag SLO, conflict policy (LWW, merge, CRDT), and a reconciliation job that repairs drift.
  5. Hybrid is common: strong write to primary, async project to read models; clients that need fresh data read-your-writes from primary or wait on a version token.
  6. Say the CAP tradeoff in product terms: during partition, do we refuse writes (CP) or accept divergent writes and merge later (AP)?
Code / ops
text
# Strong: single-row inventory update with CHECK (qty >= 0)
# Eventual: outbox → Kafka → search indexer with lag metrics
Nest / Node: Nest CQRS modules often separate command (strong) from query (eventual); document which handlers are authoritative.
Say it out loud
Say it spoken

Strong consistency for money and stock; eventual for projections and caches. I'd put the invariant in one strongly consistent write path and let read models catch up with an explicit lag budget and repair job.

Traps / weak answers
  • Saying 'eventual consistency everywhere' without naming what can be wrong temporarily.
  • Claiming a multi-master write model is strongly consistent without conflict resolution.
Follow-ups
  • How would you implement read-your-writes after a profile update?
  • What metrics prove your eventual projection is healthy?
d09-q03How would you make an end-to-end workflow safe when both API requests and asynchronous messages can be duplicated?
First 30 seconds
Duplicates are normal—client retries, LB retries, at-least-once queues. I design one idempotency key that travels from HTTP through the outbox into every consumer so side effects apply once.
Model answer
  1. Require clients to send Idempotency-Key (or derive from natural business key) on mutating FastAPI endpoints; store key → response/status in Postgres with a unique constraint.
  2. On replay of the same key, return the original result without re-executing side effects.
  3. When publishing async work, include the same key (or a deterministic event_id) in the message payload and outbox row.
  4. Consumers upsert into a processed_events table (or unique business constraint) before/within the same transaction as the side effect.
  5. Make downstream calls idempotent too (payment providers, email with message-id) so a retried consumer does not double-charge or double-send.
  6. Propagate correlation_id for tracing; never use only timestamps for dedupe.
Diagram
flowchart TB
  client[Client_retry] --> api[FastAPI_idem_store]
  api --> outbox[Outbox_event_id]
  outbox --> q[Queue_at_least_once]
  q --> worker[Worker_dedupe_upsert]
Code / ops
python
@app.post("/orders")
async def create_order(key: str = Header(alias="Idempotency-Key"), body: OrderIn = ...):
    existing = await store.get(key)
    if existing:
        return existing.response
    result = await create_once(key, body)
    await store.put(key, result)
    return result
Nest / Node: Nest: IdempotencyInterceptor + Redis/Postgres store; guards authenticate before the interceptor reserves the key.
Say it out loud
Say it spoken

I'd carry one idempotency key from the HTTP API through the outbox into every consumer, with unique constraints at each write. Retries become safe no-ops instead of double side effects.

Traps / weak answers
  • Idempotency only on the API while queue consumers re-apply effects freely.
  • Using UUID generated inside the handler (new id on every retry) as the dedupe key.
Follow-ups
  • How long do you retain idempotency keys and what happens after expiry?
  • How do you handle two different payloads with the same Idempotency-Key?

d09-q04What does 'exactly once' mean in a practical distributed system, and where can it break down?
First 30 seconds
True exactly-once across independent systems is essentially impossible under crashes and networks. In practice we mean effectively-once: at-least-once delivery plus an idempotent effect.
Model answer
  1. Clarify: brokers may claim EOS within a closed ecosystem (e.g. Kafka transactions), but end-to-end with HTTP + DB + email still needs application dedupe.
  2. Practical recipe: unique message/business id + idempotent write (INSERT … ON CONFLICT / conditional update) + commit offsets/acks after durable effect.
  3. Breaks when: side effects are non-idempotent (SMS send without provider message-id), multi-step updates without a single transactional boundary, or dedupe store TTL expires while retries continue.
  4. Breaks when: process crashes after side effect but before recording dedupe/ack → redelivery must no-op.
  5. Breaks when: two different keys map to the same business action, or clocks/partitions reorder dependent events.
  6. Interview close: say 'effectively once' and name your dedupe table and unique constraints.
Code / ops
python
async with db.begin():
    inserted = await db.execute(
        "INSERT INTO processed(event_id) VALUES ($1) ON CONFLICT DO NOTHING", event_id
    )
    if inserted.rowcount == 0:
        return  # duplicate
    await apply_effect(payload)
# then ack / commit offset
Nest / Node: Nest microservices: use the same transactional outbox/inbox pattern; don't trust transport 'exactly once' alone.
Say it out loud
Say it spoken

I treat exactly-once as effectively-once: at-least-once delivery with an idempotent write and a dedupe key. It breaks when the side effect isn't idempotent or you ack before the durable write.

Traps / weak answers
  • Claiming the message broker guarantees exactly-once for all downstream side effects.
  • Acknowledging the message before the DB commit succeeds.
Follow-ups
  • How do Kafka transactions change (or not change) this answer?
  • How would you make email sends effectively-once?
d09-q05How would you prevent cascading failures when a downstream service becomes slow?
First 30 seconds
Slow dependencies exhaust thread/connection pools and amplify latency. I fail fast with timeouts, isolate with bulkheads, and trip a circuit breaker so we shed waiters instead of melting the whole process.
Model answer
  1. Set aggressive, measured timeouts on every outbound call (connect + read) shorter than the caller's remaining budget.
  2. Limit concurrency per dependency (bulkhead / semaphore) so one slow peer cannot consume all workers.
  3. Add a circuit breaker: after error-rate or slow-call threshold, open and fail fast / serve fallback for a cool-down.
  4. Use bounded retries with jitter only on idempotent/safe calls; never retry storms on 500s without a breaker.
  5. Isolate thread/async pools and DB pools; monitor queue depth, pool wait, and dependency p99.
  6. Prefer degradation (cached/stale/default) over blocking the critical user path; page on breaker open duration.
Diagram
flowchart TB
  req[Incoming] --> bh[Bulkhead_limit]
  bh --> cb{Circuit}
  cb -->|closed| call[Downstream]
  cb -->|open| fb[Fallback_failfast]
  call -->|slow_error| cb
Code / ops
python
# httpx timeout + semaphore bulkhead sketch
sem = asyncio.Semaphore(50)
async with sem:
    async with httpx.AsyncClient(timeout=httpx.Timeout(0.8)) as client:
        r = await client.get(url)
Nest / Node: Nest: use a resilience library (e.g. cockatiel/opossum-style) in an interceptor or dedicated client wrapper; keep breaker state per upstream, not global.
Say it out loud
Say it spoken

Timeouts, bulkheads, and a circuit breaker—fail fast, cap in-flight calls to the sick dependency, and degrade instead of letting one slow service exhaust our pools.

Traps / weak answers
  • Infinite retries without backoff or breaker.
  • One shared unbounded connection pool for all dependencies.
Follow-ups
  • What fallback is safe for a payments dependency versus a recommendations dependency?
  • How do you tune breaker thresholds without flapping?

d09-q06How would you design backpressure when incoming work is greater than worker capacity?
First 30 seconds
Backpressure means producers slow down or buffer in a controlled place when consumers can't keep up—never an unbounded in-memory queue that OOMs the process.
Model answer
  1. Push work to a durable queue (SQS/Kafka) with a defined max lag SLO; scale consumers on lag/depth, not only CPU.
  2. At the HTTP edge: limit concurrency (uvicorn workers, asyncio semaphores); return 429/503 when saturated instead of accepting infinite work.
  3. Use bounded in-process queues with drop/reject policies; never queue.Queue without maxsize for production ingress.
  4. Propagate pressure: if Redis/DB pool wait exceeds budget, stop accepting new non-critical jobs.
  5. Separate interactive API capacity from batch/async capacity so batch cannot starve user traffic.
  6. Observe: queue depth, age of oldest message, reject rate, consumer lag—alert before meltdown.
Code / ops
python
from fastapi import HTTPException
sem = asyncio.Semaphore(200)

@app.post("/jobs")
async def enqueue(job: JobIn):
    if sem.locked() and sem._value == 0:
        raise HTTPException(429, "saturated")
    async with sem:
        await queue.send(job)
Nest / Node: Nest: use BullMQ/SQS with concurrency settings; apply ThrottlerGuard or custom middleware for HTTP admission control.
Say it out loud
Say it spoken

I'd absorb spikes in a durable queue with lag-based autoscaling, bound in-process concurrency, and return 429 at the edge when we're saturated—unbounded memory queues are not backpressure.

Traps / weak answers
  • Buffering everything in process memory 'temporarily'.
  • Autoscaling only on CPU while queue lag grows unbounded.
Follow-ups
  • How does Kafka consumer lag differ from SQS ApproximateNumberOfMessages?
  • Where should backpressure live in a sync vs async API?
d09-q07How would you design graceful load shedding during an overload event?
First 30 seconds
Load shedding deliberately drops or degrades lower-value work so the core path stays healthy. I'd shed early, signal clearly, and protect auth'd critical writes first.
Model answer
  1. Define priority classes: health/auth/checkout > reads > batch/export/analytics.
  2. Shed at the edge first (ALB/WAF/rate limits, API gateway) before app CPU melts.
  3. In-app: when event-loop lag, queue age, or pool wait crosses thresholds, reject low-priority with 503 + Retry-After.
  4. Degrade features: disable expensive recommendations, serve cached reads, skip non-essential fan-out.
  5. Keep health checks cheap and independent so the instance isn't killed while shedding correctly.
  6. Runbook + game day: verify shedding activates and recovers; page on sustained shed rate.
Code / ops
python
def admit(priority: str) -> bool:
    if event_loop_lag_ms() > 200 and priority != "critical":
        return False
    return True
Nest / Node: Nest middleware can short-circuit low-priority routes; combine with guards so shedding decisions see auth/tenant context.
Say it out loud
Say it spoken

Graceful shedding means dropping low-priority work early with 503/Retry-After while protecting checkout and auth. I'd trigger on lag and pool wait, not after the process is already thrashing.

Traps / weak answers
  • Returning 200 with empty bodies silently (clients don't back off).
  • Failing health checks during intentional shed, causing a death spiral.
Follow-ups
  • How do you avoid shedding your own retries into a worse storm?
  • What client contract do you publish for 429 vs 503?
d09-q08How would you choose timeouts and retry policies across a chain of dependent services?
First 30 seconds
I work a timeout budget from the outermost SLA inward. Each hop gets a slice; inner calls must finish before the outer deadline, and retries must fit inside the remaining budget.
Model answer
  1. Start from client/UX SLA (e.g. 3s p99). Reserve margin for LB/proxy; assign remaining budget down the call graph.
  2. Set child timeout < parent remaining time; propagate a deadline (header or context) so deep hops abort early.
  3. Retries: only on idempotent/safe operations; exponential backoff + jitter; cap attempts so total time ≤ budget.
  4. Avoid retry-on-timeout amplifying load—pair with breakers; prefer fail fast when budget nearly exhausted.
  5. Align Nginx/ALB idle timeouts with app budgets (ALB > Nginx > app outbound) to avoid opaque 504s.
  6. Instrument per-hop latency and deadline-exceeded counts; tune from production histograms, not guesses.
Diagram
flowchart LR
  client[Client_3s] --> alb[ALB]
  alb --> api[API_2_2s]
  api --> pay[Pay_800ms]
  api --> inv[Inv_600ms]
Code / ops
python
deadline = time.monotonic() + 2.0
remaining = lambda: max(0.05, deadline - time.monotonic())
await call_pay(timeout=remaining() * 0.6)
await call_inv(timeout=remaining())
Nest / Node: Nest/Node: store deadline on AsyncLocalStorage/request context; interceptors enforce remaining ms on Axios/fetch clients.
Say it out loud
Say it spoken

Timeouts are a budget, not a single magic number. I'd slice the outer SLA across hops, propagate deadlines, and only retry when the remaining budget and idempotency allow it.

Traps / weak answers
  • Same 30s timeout on every hop with three retries each (minutes of amplification).
  • ALB timeout shorter than the app's outbound calls, producing unexplained 504s.
Follow-ups
  • How do you propagate deadlines across HTTP and a queue hop?
  • What changes for a non-idempotent POST in the chain?
d09-q09How would you design a job so work is not lost when a worker process crashes or the EC2 instance is terminated?
First 30 seconds
Durability lives in the queue, not the worker. I'd use visibility timeouts, heartbeats for long jobs, and idempotent handlers so a crash simply redelivers.
Model answer
  1. Enqueue durable messages (SQS/Kafka) before acknowledging the user-facing write (or via transactional outbox).
  2. On receive: extend visibility/heartbeat while working; if the worker dies, visibility expires and another worker gets the message.
  3. Process idempotently so redelivery after partial work is safe.
  4. Handle SIGTERM on EC2/ECS: stop taking new jobs, finish or release current message, then exit (deregistration delay covers in-flight).
  5. Dead-letter after N failures; alert on DLQ depth; never delete a message before durable success.
  6. Store progress checkpoints for long jobs so resume doesn't restart from zero.
Code / ops
python
msg = await sqs.receive()
try:
    while not done:
        await sqs.change_visibility(msg, timeout=60)
        done = await work_chunk(msg)
    await sqs.delete(msg)
except Exception:
    pass  # visibility expires → retry
Nest / Node: Nest + BullMQ: use job.lock/renew; onModuleDestroy should pause the queue and wait for active jobs within the ECS stopTimeout.
Say it out loud
Say it spoken

Jobs survive crashes because the queue owns the work: visibility timeout plus heartbeat, idempotent handlers, and clean SIGTERM that releases the message. Workers are disposable.

Traps / weak answers
  • Storing the only copy of work in process memory or a local disk scratch file.
  • Deleting the SQS message at start of processing.
Follow-ups
  • How long should visibility timeout be relative to p99 job duration?
  • How do you drain workers during a deploy?

d09-q10How would you design a reliable scheduled job that can safely recover after missed executions?
First 30 seconds
Schedulers miss runs—deploys, outages, clock skew. I design catch-up that is idempotent and cursor-based, not 'run once at cron time and hope'.
Model answer
  1. Persist schedule state: last_success_watermark / next_run_at in DB; cron is a trigger, not the source of truth.
  2. On wake: compute the work window from watermark → now; process in chunks with idempotent keys per window/item.
  3. Use leader election or a DB lock so multiple instances don't double-run the same catch-up.
  4. Cap catch-up rate (backpressure) so a long outage doesn't stampede downstream systems.
  5. Distinguish 'missed' vs 'failed': failed batches go to retry/DLQ; missed windows are enumerated and closed only after success.
  6. Alert if watermark lag exceeds SLO; support manual replay of a time range.
Diagram
flowchart TB
  cron[Cron_tick] --> lock[Acquire_lease]
  lock --> win[Load_watermark_to_now]
  win --> chunk[Process_chunks_idempotent]
  chunk --> mark[Advance_watermark]
Code / ops
python
async def run_schedule():
    async with advisory_lock("billing_daily"):
        start = await get_watermark()
        for window in windows(start, utcnow(), size="1h"):
            await process_window(window)  # idempotent on window_id
            await set_watermark(window.end)
Nest / Node: Nest @Cron is fine as a tick; put catch-up logic in a service with a distributed lock (Redis/Postgres), not only in-process ScheduleModule assumptions.
Say it out loud
Say it spoken

A reliable scheduler stores a watermark, catch-up from last success to now with idempotent chunked work, and a lock so only one leader runs. Cron alone is not recovery.

Traps / weak answers
  • Assuming the cron always fires and skipping watermark tracking.
  • Replaying the entire history without rate limits after a two-day outage.
Follow-ups
  • How do you handle overlapping runs if a job lasts longer than its interval?
  • Would you use EventBridge Scheduler, Celery beat, or an external orchestrator—and why?

03  Self-check

Service A reserved inventory, then payment failed. What is the safest recovery pattern?
Cross-service 2PC is fragile at scale. Model the workflow as steps with compensations and make each step idempotent on a workflow/idempotency key.
What makes 'exactly-once' practical in a queue-backed FastAPI worker?
Brokers and networks duplicate. Effectively-once = tolerate duplicates and make the side effect happen at most once via unique keys.
A downstream dependency is slow. Which combination best prevents cascading failure?
Fail fast, open the circuit when error rates spike, and cap in-flight calls so one slow peer cannot exhaust your process.
During overload, what should load shedding do first?
Protect the core path. Shed early with explicit signals so clients can back off while critical writes still succeed.
