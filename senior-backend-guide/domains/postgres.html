PostgreSQL: Performance, Transactions & Concurrency

Senior Postgres answers start with evidence: EXPLAIN (ANALYZE, BUFFERS), then indexes and plans, then concurrency control. MVCC explains why reads do not block writers, but isolation level and locking still decide lost updates, overselling, and deadlocks. Production safety means connection pooling (PgBouncer), CREATE INDEX CONCURRENTLY, and expand-contract migrations so old and new app versions coexist.

01  Decision cheat strip

OversellSELECT … FOR UPDATE or atomic UPDATE … WHERE stock > 0
Lost updateOptimistic version column or pessimistic row lock

MigrationsCONCURRENTLY + expand/contract, never big exclusive locks

d05-q01A PostgreSQL query is fast with one million rows but becomes slow with one hundred million. How would you investigate?
First 30 seconds
Scale changed the plan or I/O profile — I would capture the slow query, run EXPLAIN (ANALYZE, BUFFERS) on production-like data, and check whether we flipped to seq scan, nested loop explosion, or bad cardinality estimates.
Model answer
  1. Reproduce with realistic data volume and the same parameters; compare EXPLAIN plans at 1M vs 100M.
  2. Look for seq scans on large tables, nested loops with huge inner rows, hash/sort spills to disk, and misestimated rows (ANALYZE / extended stats).
  3. Check indexes: missing composite indexes matching WHERE/JOIN/ORDER BY, unused indexes, and whether the planner can use an index-only scan (visibility map).
  4. Inspect table/index bloat, vacuum/autovacuum lag, and shared_buffers / OS cache hit ratio from BUFFERS.
  5. Fix with the right index or rewrite (avoid SELECT *), update statistics, partition if appropriate, then re-measure latency and I/O.
Code / ops
sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT …;
Nest / Node: Log slow queries via ORM/query logger with bind params; never tune against empty staging tables.
Say it out loud
Say it spoken

At 100M the plan or cache behavior changed. EXPLAIN ANALYZE with BUFFERS tells me if it's a bad join, missing index, or I/O — I fix the plan before throwing hardware at it.

Traps / weak answers
  • Adding random indexes without reading the plan
  • Assuming 'it worked at 1M' means the same plan still applies
  • Tuning only on EXPLAIN without ANALYZE (estimates lie)
Follow-ups
  • When would you partition vs just index?
  • How do you tell bloat from a genuinely expensive join?
d05-q02How would you use EXPLAIN or EXPLAIN ANALYZE to debug a slow PostgreSQL query?
First 30 seconds
EXPLAIN shows the planned tree; EXPLAIN ANALYZE runs it and shows actual time and rows. I always want BUFFERS so I can separate CPU from disk.
Model answer
  1. Start with EXPLAIN (ANALYZE, BUFFERS) on a safe replica or low-traffic window; use FORMAT TEXT for readability.
  2. Read bottom-up: find the node with the largest actual time; compare estimated vs actual rows — large skew means bad stats or correlated predicates.
  3. Flag seq scans on big tables, nested loops with huge inner loops, and sorts/hashes that spill (temp files).
  4. Use BUFFERS: high 'read' vs 'hit' means cold cache or working set larger than memory; high 'hit' with high time means CPU/CPU-bound plan shape.
  5. Iterate: add/adjust indexes, rewrite predicates to be sargable, ANALYZE, or break the query — re-run until actual time drops.
Code / ops
sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT o.id
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.created_at >= now() - interval '7 days'
  AND c.tier = 'gold';
Nest / Node: Wrap debug in a transaction you ROLLBACK if the statement mutates; prefer a replica for heavy ANALYZE.
Say it out loud
Say it spoken

I run EXPLAIN ANALYZE with BUFFERS, find the hottest node, and fix estimate skew or I/O — not guesswork indexes.

Traps / weak answers
  • Using EXPLAIN alone and trusting estimates
  • Ignoring BUFFERS and blaming 'CPU' when it's disk
  • Running ANALYZE on the primary at peak without thinking about load
Follow-ups
  • What is an index-only scan and when does it fail?
  • How do you capture a plan from a prepared statement / ORM?
d05-q03Two users try to purchase the last available item at exactly the same time. How would you prevent overselling?
First 30 seconds
This is a concurrency invariant: stock must never go negative. I would make the decrement atomic under a row lock or a single conditional UPDATE, not read-modify-write in the app.
Model answer
  1. Model inventory as a row (or SKU row) and update stock in one statement: UPDATE … SET stock = stock - 1 WHERE id = $1 AND stock >= 1 RETURNING *.
  2. If zero rows returned, treat as sold out — no separate check-then-update race.
  3. Alternatively: BEGIN; SELECT … FOR UPDATE; check stock; UPDATE; COMMIT — pessimistic lock serializes buyers on that row.
  4. Keep the transaction short; never hold FOR UPDATE across external payment calls — reserve/hold pattern with TTL if payment is slow.
  5. Add a CHECK (stock >= 0) as a last line of defense and monitor constraint violations.
Code / ops
sql
UPDATE inventory
SET stock = stock - 1
WHERE sku = $1 AND stock >= 1
RETURNING stock;
Nest / Node: In Nest/TypeORM use a transactional repository method; do not load entity, mutate, save without version/lock.
Say it out loud
Say it spoken

I never trust check-then-update in app memory. One conditional UPDATE or SELECT FOR UPDATE on the stock row, short transaction, sold-out if zero rows.

Traps / weak answers
  • Read stock in app, decrement, write back without locking
  • Holding FOR UPDATE while calling Stripe
  • Relying only on unique constraints that don't model quantity
Follow-ups
  • How do soft holds / reservations differ from hard decrements?
  • Would SERIALIZABLE alone be enough here?
d05-q04When would you use optimistic locking versus pessimistic locking?
First 30 seconds
Optimistic: version column, retry on conflict — best when conflicts are rare. Pessimistic: SELECT FOR UPDATE — best when contention is expected and you must serialize.
Model answer
  1. Optimistic: add version (or updated_at) column; UPDATE … WHERE id = $1 AND version = $2; if 0 rows, conflict → reload/retry or fail to client.
  2. Use optimistic for user-edited documents, admin forms, and low-contention aggregates where most writes do not collide.
  3. Pessimistic: SELECT … FOR UPDATE (or FOR NO KEY UPDATE) inside a short transaction when you expect races (inventory, seats, wallet balance).
  4. Avoid long-lived pessimistic locks; they increase wait time and deadlock risk.
  5. Hybrid: optimistic by default; escalate to row locks for hot money paths.
Code / ops
sql
UPDATE accounts
SET balance = balance - $1, version = version + 1
WHERE id = $2 AND version = $3
RETURNING version;
Nest / Node: @Version() in TypeORM / Prisma version fields map to optimistic updates; still use raw SQL for tight inventory paths.
Say it out loud
Say it spoken

Optimistic version columns when collisions are rare; FOR UPDATE when I know two writers will fight over the same row and must serialize.

Traps / weak answers
  • Optimistic locking with silent overwrite on 0-row updates
  • Pessimistic locks held across HTTP round-trips
  • Confusing MVCC snapshots with mutual exclusion
Follow-ups
  • What is FOR UPDATE SKIP LOCKED used for?
  • How do you backoff retries under optimistic conflicts?
d05-q05A read-then-update workflow produces lost updates under concurrency. How would you redesign it?
First 30 seconds
Lost update means two transactions read the same version and both write — last write wins. I redesign to a single atomic UPDATE or add a version check.
Model answer
  1. Eliminate read-modify-write in application memory where possible: push the delta into SQL (SET counter = counter + $1).
  2. If business logic needs the old value, SELECT FOR UPDATE then update in the same short transaction.
  3. Or use optimistic concurrency: WHERE version = :read_version and bump version; surface 409 on conflict.
  4. Raise isolation only if needed — SERIALIZABLE can detect write skew, but app-level versioning is clearer for lost updates.
  5. Add tests that run concurrent workers and assert final state; monitor conflict/retry rates.
Code / ops
sql
-- Bad: SELECT balance; …; UPDATE balance = $new
-- Good:
UPDATE wallets SET balance = balance + $1 WHERE id = $2;
Nest / Node: Service layer should expose incrementBalance(), not get+set, to prevent accidental RMW.
Say it out loud
Say it spoken

Lost updates are a smell of check-then-act. I make the write atomic or version it so concurrent writers cannot silently clobber each other.

Traps / weak answers
  • Assuming READ COMMITTED prevents lost updates (it doesn't for this pattern)
  • Retrying blindly without re-reading state
  • Using UNIQUE constraints as a substitute for numeric invariants
Follow-ups
  • How does write skew differ from lost update?
  • Would Redis INCR be appropriate for this counter?
d05-q06How would you choose between READ COMMITTED, REPEATABLE READ, and SERIALIZABLE for a business operation?
First 30 seconds
Default READ COMMITTED for most OLTP. REPEATABLE READ when a transaction needs a stable snapshot. SERIALIZABLE when multi-row invariants must look as if transactions ran one at a time.
Model answer
  1. READ COMMITTED (Postgres default): each statement sees latest committed rows; fine for simple CRUD; watch non-repeatable reads and lost-update patterns.
  2. REPEATABLE READ: transaction-wide snapshot — good for consistent reports, multi-step reads, and some compare-and-set designs; may get serialization failures on conflicts.
  3. SERIALIZABLE: strongest; Postgres SSI aborts transactions that would violate serializability (write skew). Use for complex invariants across rows.
  4. Prefer explicit locks or atomic SQL for hot paths instead of raising isolation globally — cheaper and clearer.
  5. Always handle retry on serialization_failure (40001) when using RR/SERIALIZABLE.
Code / ops
sql
BEGIN ISOLATION LEVEL SERIALIZABLE;
-- critical multi-row invariant
COMMIT;
Nest / Node: Set isolation per transaction in the unit-of-work, not as a global Nest middleware default.
Say it out loud
Say it spoken

I stay on READ COMMITTED unless the business needs a snapshot or true serializability — and I design for retries when I raise isolation.

Traps / weak answers
  • Raising isolation 'to be safe' without retry logic
  • Thinking RR in Postgres matches MySQL RR anomaly set exactly
  • Using SERIALIZABLE as a substitute for application idempotency
Follow-ups
  • What anomalies does READ COMMITTED still allow?
  • How do you test for write skew?
d05-q07Two transactions deadlock in production. How would you investigate and reduce the likelihood of future deadlocks?
First 30 seconds
Postgres detects deadlocks and aborts one transaction. I pull the deadlock detail from logs, map the lock order, and make all code paths acquire locks in a consistent order.
Model answer
  1. Enable/inspect deadlock logs (log_lock_waits, deadlock details): which relations, PIDs, and lock modes.
  2. Reproduce with the same statement order; identify cycles (A locks row1 waits row2; B locks row2 waits row1).
  3. Fix by canonical lock ordering (e.g. always lock account ids sorted), shorter transactions, and fewer multi-row updates in one TX.
  4. Prefer single-statement updates; use SKIP LOCKED for worker queues; avoid lock escalation patterns from ORM batch saves.
  5. Add metrics/alerts on deadlock count; retry the aborted transaction safely if idempotent.
Code / ops
sql
-- Example: always lock in id order
SELECT * FROM accounts WHERE id = ANY($1) ORDER BY id FOR UPDATE;
Nest / Node: Centralize money-move in one service method so all call sites share lock order.
Say it out loud
Say it spoken

Deadlocks are lock-order cycles. I read the log, enforce a global lock order, shrink transactions, and retry the loser idempotently.

Traps / weak answers
  • Retrying forever without backoff or idempotency
  • Blaming 'Postgres is broken' instead of application lock order
  • Holding locks while doing HTTP I/O
Follow-ups
  • How do advisory locks differ from row locks?
  • What does deadlock_timeout control?
d05-q08Your application opens far more PostgreSQL connections than expected. How would you find the source and fix it?
First 30 seconds
I'd query pg_stat_activity for count by application_name/state, then trace app pools — missing pooling, pool-per-pod explosion, or leaked connections.
Model answer
  1. Inspect SELECT usename, application_name, state, count(*) FROM pg_stat_activity GROUP BY 1,2,3; look for idle in transaction and connection storms after deploys.
  2. Map expected max: replicas × workers × pool_size. Cap pool_size; set statement/idle timeouts.
  3. Introduce PgBouncer (transaction pooling for most apps) so Postgres sees far fewer server connections than client connections.
  4. Fix leaks: ensure connections return to pool, no long idle-in-transaction, ORM session scoped correctly per request.
  5. Alert on connection saturation and idle-in-transaction age; load-test pool settings before raising max_connections.
Code / ops
sql
SELECT application_name, state, count(*)
FROM pg_stat_activity
GROUP BY 1, 2
ORDER BY 3 DESC;
Nest / Node: One Nest process ≠ one pool forever if you fork workers; configure pool per process deliberately.
Say it out loud
Say it spoken

Connection storms are usually pool math or leaks. I count pg_stat_activity, fix pool sizing, and put PgBouncer in front so Postgres isn't the connection radiator.

Traps / weak answers
  • Raising max_connections instead of pooling
  • Session pooling features incompatible with transaction pooling (temp tables, prepared stmts) without checking
  • Ignoring idle in transaction as a connection holder
Follow-ups
  • Transaction vs session pooling in PgBouncer — when does each break?
  • How do you set application_name for attribution?
d05-q09How would you perform a schema migration or index creation on a large production table without unacceptable downtime?
First 30 seconds
Avoid ACCESS EXCLUSIVE locks that block writes for long periods. Use CREATE INDEX CONCURRENTLY, additive migrations, and batch backfills.
Model answer
  1. Prefer additive changes: nullable new columns, new tables, new indexes — avoid rewriting the whole table in one transaction.
  2. CREATE INDEX CONCURRENTLY (and DROP INDEX CONCURRENTLY); monitor for invalid indexes and REINDEX CONCURRENTLY if needed.
  3. For column backfills: batched UPDATEs with primary-key ranges, throttling, and progress table; never UPDATE entire table in one TX.
  4. Use tools (pt-like patterns / gh-ost style thinking) or Postgres-native expand techniques; schedule heavy work off-peak.
  5. Validate with locks query (pg_locks / pg_stat_progress_create_index) and a rollback plan.
Code / ops
sql
CREATE INDEX CONCURRENTLY IF NOT EXISTS orders_created_at_idx
  ON orders (created_at);
Nest / Node: Run concurrent index builds from a migration job that can retry; do not wrap CONCURRENTLY in an explicit transaction block.
Say it out loud
Say it spoken

No big-bang locks on hot tables. CONCURRENTLY for indexes, batched backfills for data, additive schema first.

Traps / weak answers
  • Running CREATE INDEX (non-concurrent) on a 100M-row hot table
  • Wrapping CONCURRENTLY inside a transaction (fails)
  • Single UPDATE that rewrites every row and bloats the table
Follow-ups
  • What locks does ALTER TABLE ADD COLUMN with default take on modern Postgres?
  • How do you detect an INVALID index after a failed concurrent build?
d05-q10How would you design a zero-downtime database migration when old and new application versions must run simultaneously?
First 30 seconds
Expand-contract: ship schema both versions understand, dual-write or backfill, switch reads, then remove the old shape after old pods are gone.
Model answer
  1. Expand: add new columns/tables/indexes compatible with old code (old code ignores new fields).
  2. Deploy code that writes both old and new shapes (or writes new and backfills asynchronously).
  3. Backfill historical rows in batches; verify with checksums/counts.
  4. Switch reads to the new shape; deploy code that only needs the new schema.
  5. Contract: drop old columns/tables only after all instances and jobs no longer reference them; keep migrations reversible where practical.
Diagram
flowchart LR
  A[Expand schema] --> B[Dual-write / backfill]
  B --> C[Switch reads]
  C --> D[Contract old shape]
Code / ops
sql
-- Expand
ALTER TABLE users ADD COLUMN email_normalized text;
-- later Contract
-- ALTER TABLE users DROP COLUMN email_legacy;
Nest / Node: Feature-flag the read path so you can flip without another schema deploy.
Say it out loud
Say it spoken

Rolling deploys need expand-contract. Schema stays compatible with both versions until the fleet and backfill are done — then contract.

Traps / weak answers
  • Renaming/dropping columns in the same deploy that changes app code
  • Assuming blue/green means you can break old readers immediately
  • Backfill without idempotency or resume cursors
Follow-ups
  • How do you migrate a primary key without downtime?
  • What changes are unsafe even with expand-contract?

BUFFERS shows buffer hits/reads so you know whether time is CPU planning/execution or disk I/O.
