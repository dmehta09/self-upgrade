My projects deep dive

Senior project deep-dives test whether you can narrate architecture, tradeoffs, and operability across real platforms—not recite a feature list. Anchor answers on three guide labels: document intelligence RAG platform (NestJS orchestration + FastAPI AI worker), institutional LMS (federated GraphQL, search, chat, data lifecycle), and healthcare diagnostics platform (DDD, strangler cutover, CQRS, HIPAA-aligned controls). Lead with the failure mode you prevent, name the metric that proves safety, and close with how you would detect regression in production.

d13-q01Walk through the end-to-end architecture of a document intelligence RAG platform from ingest to generate. Who owns what between NestJS and FastAPI?
First 30 seconds
I'd narrate a staged pipeline: ingest and tenancy in NestJS, parse/table/chunk/embed/retrieve/generate in a FastAPI AI worker, with typed contracts, idempotent jobs, and org-scoped storage at every hop.
Model answer
  1. Clarify the pipeline stages and ownership: NestJS owns auth, org tenancy, job orchestration, and product APIs; FastAPI owns parse, table extraction, chunking, embedding, retrieval, and generation because those are CPU/GPU-heavy and model-versioned.
  2. Ingest accepts documents per org, persists metadata and S3 object keys, and enqueues a job with an idempotency key so retries never double-bill embedding or duplicate index rows.
  3. Parse/table extraction preserves structure before semantic chunking; chunks carry document_id, org_id, page/section, and table refs so retrieve can filter before similarity search.
  4. Embed and index into an org-scoped vector store; retrieve combines vector hits with metadata filters; generate uses versioned prompts and structured outputs back to Nest for persistence.
  5. Tradeoff: monolith one process vs Nest orchestrator + FastAPI worker—split because model deps, scale axes, and blast radius differ; cost is HMAC/service auth and schema versioning across the hop.
  6. Failure modes: silent partial ingest, cross-org chunk leakage, and generate succeeding while Nest never records results—detect with job state machine and end-to-end correlation ids.
  7. Prevent/ops: dashboard job stage latency and failure rate per stage; alert when embed or retrieve lag exceeds SLO or when dead-letter depth crosses threshold.
  8. Runbook covers reprocess-by-document_id, prompt/model rollback, and a game-day that injects worker timeouts to verify Nest compensating cleanup and retry budgets.
Diagram
flowchart LR
  ingest[Nest_ingest] --> parse[FastAPI_parse_table]
  parse --> chunk[Chunk_embed]
  chunk --> retrieve[Hybrid_retrieve]
  retrieve --> generate[Generate]
  generate --> nestOut[Nest_persist]
Code / ops
text
# Stage ownership
# Nest: auth, org, job FSM, S3 keys, product API
# FastAPI: parse/table, chunk, embed, retrieve, generate
# Contract: HMAC + org_id + idempotency_key + correlation_id
Nest / Node: Nest modules: DocumentsModule + JobsModule orchestrate; HttpModule/client to FastAPI with signed headers; never let the AI worker invent tenant context from the request body alone.
Say it out loud
Say it spoken

Nest owns tenancy and orchestration; FastAPI owns the AI stages. Every hop is org-scoped, idempotent, and observable by stage so we can reprocess safely without guessing where the pipeline stalled.

Traps / weak answers
  • Letting FastAPI invent org_id from the upload payload — unsigned tenant context is a cross-tenant leak waiting to happen.
  • Collapsing all stages into one HTTP request — timeouts and partial writes become undiagnosable and unblockable.
  • Skipping idempotency on reprocess — duplicate embeddings and conflicting chunk versions corrupt retrieval quality silently.
Follow-ups
  • Where do you put retries: Nest job FSM or FastAPI internal?
  • How do you version embedding models without reindexing the world at once?
d13-q02On planning PDFs, why prefer table extraction over naive PDF text extraction for LLM grounding?
First 30 seconds
I'd contrast structure-preserving extractors with text dumps: tables carry label–value alignment that prose flattening destroys, so retrieval and generation start wrong before the model even reasons.
Model answer
  1. Clarify the failure: naive PDF text often serialises cells left-to-right or out of reading order, so a 'Budget' label and a currency amount detach—LLMs then invent plausible but wrong figures.
  2. Table extraction keeps row/column/header relationships, enabling chunking that cites table_id, row, and cell ranges instead of orphaned sentences.
  3. For planning PDFs, merged cells, multi-line headers, and footnotes are semantic; structure-aware parsers flag uncertainty instead of silently dropping alignment.
  4. Tradeoff: OCR/table pipelines cost more latency and ops complexity vs cheap text extract—pay it because wrong numbers in plans are high-blast integrity failures, not cosmetic RAG misses.
  5. Downstream design: store both rendered markdown/HTML of tables and structured JSON so hybrid retrieve can boost table chunks when queries mention metrics or line items.
  6. Failure modes: false-confident flat text, header rows treated as data, and currency/unit loss—detect with golden PDF fixtures and numeric checksum probes in CI.
  7. Prevent/ops: track table-extraction confidence and human-review rate as quality metrics; alert when extraction confidence drops below threshold after a parser upgrade.
  8. Monitor grounded-answer evals on a fixed planning corpus after each parse model change; runbook includes rollback to last known-good extractor and reprocess of affected document_ids.
Code / ops
text
# Prefer structured table JSON + markdown render
# over page.get_text() alone
# Fixture: assert label-cell alignment on golden PDFs
Nest / Node: Nest stores extraction artifacts and quality scores; FastAPI returns typed table payloads so Nest can gate indexing on confidence without re-parsing.
Say it out loud
Say it spoken

Structure is the ground truth for planning numbers. I preserve tables so retrieval cites real cells; naive text dumps manufacture confident hallucinations.

Traps / weak answers
  • Shipping vector search on flattened text and calling hallucinations a 'prompt issue' — the data lost structure before the prompt existed.
  • Ignoring merged cells and multi-page tables — partial rows look complete and poison embeddings.
  • No golden-PDF regression suite — parser upgrades silently degrade the highest-value documents.
Follow-ups
  • How do you chunk a multi-page financial table?
  • When do you escalate low-confidence extractions to humans?
d13-q03How would you design semantic chunking and metadata for planning PDFs on a document intelligence RAG platform?
First 30 seconds
I'd chunk by semantic units—sections, tables, figures—not fixed token windows, and attach org, document, section, page, table, and sensitivity metadata so filters prune before similarity.
Model answer
  1. Clarify goals: chunks must be self-contained enough for retrieval yet small enough to fit context; planning PDFs need section-aware splits plus whole-table or row-group chunks for numeric fidelity.
  2. Semantic chunking uses headings, list boundaries, and table regions; overlapping windows only at narrative prose, never mid-cell, because mid-cell splits destroy value alignment.
  3. Metadata minimum: org_id, document_id, version, page_range, section_path, chunk_type (prose|table|caption), sensitivity, and extraction_confidence for filter and audit.
  4. Tradeoff: larger table chunks preserve context vs smaller row chunks improve precision—hybridise: store parent table summary plus child row groups linked by parent_chunk_id.
  5. Index design: vector on content; filterable fields on metadata; deny queries missing org_id at the API so the vector store never becomes the tenancy enforcer of last resort.
  6. Failure modes: overlong chunks that drown signal, orphan table rows, and metadata drift after reprocess—detect with chunk-size histograms and parent/child integrity checks.
  7. Prevent/ops: dashboard median chunk tokens and filter hit-rate; alert when chunk_type mix shifts sharply after a parser change.
  8. SLO on retrieve latency with metadata filters enabled; runbook for rechunk-by-document_id when embedding or chunker versions bump.
Code / ops
json
{
  "org_id": "...",
  "document_id": "...",
  "chunk_type": "table_row_group",
  "section_path": "Q3/Budget",
  "parent_chunk_id": "tbl-12",
  "page_range": [4, 5]
}
Nest / Node: Nest validates and persists metadata contracts; FastAPI chunker must echo the same schema version so reprocess jobs stay compatible with Nest's index writer.
Say it out loud
Say it spoken

Chunk by meaning, not by arbitrary tokens, and make metadata the first retrieval gate. Planning PDFs especially need table-aware parents and children, always org-scoped.

Traps / weak answers
  • Fixed 500-token windows through tables — splits numbers from labels and tanks answer quality.
  • Metadata only in the prompt, not in the index filters — similarity search returns cross-section noise and riskier cross-tenant bugs if org is missing.
  • No parent/child links for tables — you cannot reassemble context or reprocess a single table safely.
Follow-ups
  • How do you handle annexes and footnotes that clarify a table?
  • What changes when documents are multi-lingual?
d13-q04Compare hybrid retrieval (vector + metadata filters + relevance scoring) to vector-only search for document intelligence RAG.
First 30 seconds
I'd argue vector-only is a recall starting point, not a product: metadata filters enforce tenancy and document scope, then a relevance layer re-ranks so generation sees grounded, permitted chunks.
Model answer
  1. Clarify: vector-only returns nearest embeddings; hybrid applies hard filters (org, document set, chunk_type, time) then scores with vector similarity plus optional lexical/boost signals.
  2. Filters are security and product correctness first—org_id and ACL are not 'optional ranking features'—then quality: boost table chunks for numeric queries, recency for versioned plans.
  3. Relevance scoring merges dense similarity with BM25 or structured boosts and may use a cross-encoder re-ranker on the shortlist because top-k embedding hits still include near-miss sections.
  4. Tradeoff: hybrid adds latency and index complexity vs vector-only simplicity—accept cost because wrong-tenant or wrong-document hits are integrity incidents, not UX nits.
  5. Operationalise: log filter predicates, candidate counts pre/post filter, and final scores so you can debug empty results vs over-filtered queries.
  6. Failure modes: filters too tight (empty context), filters too loose (noisy context), and score ties that flip answers—detect with offline eval sets and online groundedness sampling.
  7. Prevent/ops: monitor retrieve p95, empty-result rate, and cross-org zero-hit assertions; alert when empty-result rate spikes after a metadata schema change.
  8. Dashboard top abort reasons (no candidates post-filter vs LLM refusal); game-day injects missing org filter to prove the API fails closed rather than vector-scanning the world.
Diagram
flowchart TB
  q[Query] --> filt[Metadata_filters]
  filt --> vec[Vector_topk]
  vec --> score[Relevance_rerank]
  score --> ctx[Bounded_context]
  ctx --> gen[Generate]
Code / ops
text
# Pseudo
cands = filter(org_id, doc_ids, chunk_type)
hits = vector.search(cands, embedding, k=50)
ranked = rerank(query, hits)[:8]
Nest / Node: Nest composes allowed document_ids from authz before calling FastAPI retrieve; the worker must re-check org_id on every returned chunk as defense in depth.
Say it out loud
Say it spoken

Hybrid retrieval is how RAG stays tenant-safe and answerable. Vectors find candidates; metadata and scoring decide what the model is allowed to see.

Traps / weak answers
  • Vector-only across a shared index — tenancy becomes a prompt instruction, which is not an access control.
  • Filtering only after generation — wastes tokens and can leak snippets into logs or traces.
  • No logging of pre/post filter counts — empty answers look like model failure when the filter was wrong.
Follow-ups
  • When would you add a cross-encoder re-ranker?
  • How do you evaluate retrieval quality without reading every answer?
d13-q05How do you make LLM calls production-grade with structured outputs, versioned prompts, bounded retries, and typed errors?
First 30 seconds
I'd treat the model like an unreliable dependency: versioned prompts, schema-validated outputs, explicit error types, and bounded retries with backoff—never 'parse whatever JSON it returned'.
Model answer
  1. Clarify contracts: each prompt has an id/version, input schema, and output schema; Nest and FastAPI share typed error codes (validation, rate_limit, model_timeout, unsafe_content) rather than free-text failures.
  2. Structured outputs (JSON schema / tool mode) are validated before persistence; on schema miss, classify as retryable vs poison and route accordingly.
  3. Versioned prompts live in config with changelog; pin model+prompt versions on jobs so reprocess is reproducible and A/B is intentional, not accidental drift.
  4. Bounded retries: only transient errors, exponential backoff + jitter, max attempts, and idempotency keys so duplicate successes do not double-write.
  5. Tradeoff: strict schemas reject some good answers vs loose parsing that corrupts stores—prefer fail-fast validation because silent bad JSON becomes silent bad product data.
  6. Failure modes: infinite retry storms, prompt edits changing production mid-flight, and swallowing model errors as empty 200s—detect with attempt counters and error-class metrics.
  7. Prevent/ops: alert on elevated schema-validation failure rate and on retry exhaustion; track prompt version as a label on latency and quality dashboards.
  8. SLO on generate success rate after retries; runbook maps each typed error to page/owner and includes kill-switch to freeze a bad prompt version.
Code / ops
text
# retry policy
# retryable: timeout, 429, 5xx
# non-retryable: schema_invalid, unsafe_content, authz
# max_attempts=3, backoff=exp+jitter, idempotency_key=job_id
Nest / Node: Nest persists prompt_version and model_id on the job record; FastAPI returns typed Problem Details so Nest can map to HTTP status and user-visible error without string matching.
Say it out loud
Say it spoken

Prompts and schemas are versioned APIs. I validate structured outputs, classify typed errors, and bound retries so the model cannot silently corrupt or melt the worker pool.

Traps / weak answers
  • json.loads on free-form model text with no schema — one extra trailing comma poisons an entire document version.
  • Unlimited retries on 429 — turns a rate limit into a self-inflicted outage.
  • Editing the live prompt without version pin — yesterday's evals stop predicting today's answers.
Follow-ups
  • How do you roll back a bad prompt version safely?
  • What belongs in the prompt vs in deterministic post-processing?
d13-q06How do you ensure per-document and per-action idempotency when reprocessing documents on a RAG platform?
First 30 seconds
I'd key every side effect—store write, embed upsert, index delete/replace, notify—by document_id+action+content_version so retries and reprocess jobs converge to one correct state.
Model answer
  1. Clarify: reprocessing is normal (parser upgrade, failed mid-pipeline); without idempotency you get duplicate chunks, double embedding cost, and conflicting versions in retrieve.
  2. Per-document keys: (org_id, document_id, content_hash|version); per-action keys: (document_id, stage, version) recorded in a job ledger before external side effects.
  3. Replace semantics for indexes: delete-by-document_id then upsert new chunks in one logical unit, or versioned namespaces with atomic pointer flip after success.
  4. Tradeoff: ledger + careful upserts vs 'just run again'—ledger cost is mandatory because vector stores and S3 do not give you business-level exactly-once.
  5. Downstream consumers (notifications, billing meters) must also key on action ids; never emit 'document_processed' twice for the same version without a new version bump.
  6. Failure modes: partial stage success, ledger write after side effect, and clock-skewed 'latest wins'—detect with stage checksums and reconcile jobs.
  7. Prevent/ops: metric duplicate-suppress hits and reprocess success rate; alert when the same document_id exceeds retry threshold without terminal state.
  8. Dashboard stuck-in-stage jobs; runbook for force-complete vs safe-replay, and game-day that crashes mid-embed to prove replace semantics leave one coherent version.
Code / ops
text
# idempotency
key = f"{org}:{doc_id}:{stage}:{content_version}"
if ledger.seen(key): return prior_result
result = do_stage()
ledger.record(key, result)
Nest / Node: Nest owns the job ledger and document version pointer; FastAPI stages must accept client-supplied idempotency keys and return prior results on replay.
Say it out loud
Say it spoken

Reprocess is a first-class path. I ledger per-document and per-action keys and use replace semantics so retries converge—never accumulate duplicate chunks.

Traps / weak answers
  • Generating a new UUID inside the worker per attempt — every retry looks like new work and doubles embeddings.
  • Appending chunks on reprocess instead of replace — retrieve quality collapses under duplicate near-identical vectors.
  • Acking the queue before the ledger commit — crashes recreate work without dedupe.
Follow-ups
  • How long do you retain idempotency ledger rows?
  • How do you reprocess a single stage without invalidating the whole document?
d13-q07Design org-scoped multi-tenancy and HMAC authentication between NestJS and FastAPI. What isolation failure modes matter most?
First 30 seconds
I'd make org_id a hard dimension on every store and cache key, authenticate Nest→FastAPI with HMAC service identity, and assume any missing filter is a Sev-1 design bug.
Model answer
  1. Clarify trust boundary: browsers never talk to FastAPI; Nest authenticates users, derives org_id from session/RBAC, and calls FastAPI with HMAC-signed headers including org_id, timestamp, and body hash.
  2. FastAPI verifies signature, skew window, and that path/body org_id matches the signed claim—reject on mismatch; never trust unsigned JSON fields for tenancy.
  3. Data isolation: separate vector namespaces or mandatory org filter, S3 prefixes per org, Redis key prefixes, and DB row predicates; defense in depth across all four.
  4. Tradeoff: shared cluster with strict filters vs fully isolated clusters—start shared+strict for cost, isolate noisy/high-risk tenants when blast radius demands it.
  5. Failure modes: worker trusting client org_id, shared embedding index without filter, cache keys missing org, and signed-but-stale requests replayed—detect with canary cross-tenant probes in staging.
  6. Logging redacts document content but keeps org_id + correlation_id so incidents are diagnosable without leaking payloads.
  7. Prevent/ops: continuous test that a token for org A cannot retrieve org B chunks; alert on HMAC failures and on queries executed without org predicate.
  8. Monitor authz deny rate and cross-tenant canary results on a dashboard; runbook covers key rotation and emergency disable of a compromised worker identity.
Code / ops
text
# Headers (conceptual)
# X-Timestamp, X-Org-Id, X-Signature=HMAC(secret, ts+org+body_hash)
# Reject if |now-ts|>skew or org mismatch
Nest / Node: Nest signing interceptor on the outgoing FastAPI client; rotate shared secrets via secrets manager; never embed long-lived raw secrets in env without rotation runbooks.
Say it out loud
Say it spoken

Tenancy is enforced in signatures and storage keys, not in prompts. HMAC proves Nest called us; org-scoped indexes and caches prove we cannot leak across customers.

Traps / weak answers
  • Passing org_id only in the JSON body without signing — attackers who reach the worker pick any tenant.
  • One global vector collection with optional metadata filter — one missed filter is a multi-tenant breach.
  • Caching embeddings by content hash alone — identical public PDFs could leak across orgs if ACLs differ.
Follow-ups
  • How do you rotate HMAC secrets without downtime?
  • Would you isolate vector indexes per org from day one?
d13-q08How do you design S3 handoff between NestJS and FastAPI with compensating cleanup when the downstream stage fails?
First 30 seconds
I'd treat S3 objects as staging artifacts with ownership and TTL: Nest writes, FastAPI reads, and compensating actions delete or quarantine orphans when the job terminal-fails.
Model answer
  1. Clarify handoff: Nest uploads original + intermediate artifacts under org-prefixed keys, records keys on the job, and passes signed references—not unbounded public URLs—to FastAPI.
  2. FastAPI reads via short-lived credentials or pre-signed GET scoped to that key; it never lists the whole bucket as a substitute for a job contract.
  3. On success, Nest promotes artifacts to durable locations and indexes; on terminal failure, compensating cleanup deletes staging keys or moves them to a quarantine prefix for forensics.
  4. Tradeoff: eager delete vs quarantine TTL—quarantine helps debug poison PDFs; TTL caps cost; choose quarantine+TTL for production.
  5. Saga-style: each stage records 'wrote:key' in the ledger so compensation is precise; never 'delete whole prefix' after a partial multi-doc batch.
  6. Failure modes: orphan objects after worker crash, deleting durable inputs on retryable errors, and permission gaps that leave public ACLs—detect with bucket inventory vs job ledger reconcile.
  7. Prevent/ops: metric orphan-bytes and compensation success rate; alert when staging prefix growth exceeds threshold or reconcile lag grows.
  8. Dashboard S3 vs ledger drift; runbook for manual quarantine purge; game-day kills FastAPI mid-parse to prove Nest compensation runs and retries remain idempotent.
Diagram

  nestPut[Nest_put_staging] --> apiRead[FastAPI_read]
  apiRead -->|success| promote[Promote_durable]
  apiRead -->|terminal_fail| comp[Compensate_delete_or_quarantine]
  promote --> ledger[Ledger_done]
  comp --> ledger

# compensation
# on terminal_fail:
#   for key in job.staging_keys: quarantine_or_delete(key)
#   ledger.mark(job_id, COMPENSATED)
# never delete durable input on retryable errors
Nest / Node: Nest JobsModule owns the compensation saga; FastAPI reports stage outcomes with typed errors so Nest can distinguish retryable vs terminal before deleting anything.
Say it out loud
Say it spoken

S3 is a staged handoff with a ledger, not a junk drawer. Success promotes; failure compensates with delete or quarantine so orphans do not become a silent cost and compliance problem.

Traps / weak answers
  • Leaving staging forever 'for debugging' — unbounded cost and broader data exposure surface.
  • Deleting the source object on the first worker timeout — destroys evidence and blocks safe retry.
  • Pre-signed URLs with long TTL and broad prefixes — expands the blast radius if a URL leaks.
Follow-ups
  • How do you reconcile bucket inventory against the job ledger?
  • What retention do auditors require for failed document artifacts?
d13-q09How would you operate federated GraphQL across 7+ NestJS services on an institutional LMS—gateway ownership and schema evolution?
First 30 seconds
I'd put a gateway in charge of composition and authz at the edge, while each Nest service owns its schema slice, publish contract, and backwards-compatible evolution rules.
Model answer
  1. Clarify ownership: gateway owns authentication, query budgeting, composition, and client-facing errors; domain services own types/resolvers for courses, users, enrolments, chat, search, etc.
  2. Schema evolution: additive changes preferred; deprecations with sunset dates; breaking changes require dual-run fields or a new major and coordinated client migration.
  3. Federation contracts: each service publishes a subgraph; CI composition checks catch key conflicts and missing @key fields before deploy.
  4. Tradeoff: BFF per client vs one federated graph—federation reduces duplicate joins across LMS domains but concentrates edge risk; mitigate with complexity limits and persisted queries.
  5. Failure modes: noisy-neighbour queries, schema drift breaking composition, and partial outages returning inconsistent graphs—detect with subgraph health and gateway error-class metrics.
  6. Authz stays in resolvers/services for object-level rules; gateway enforces coarse tenant/session presence so a missing token never fans out to seven internals.
  7. Prevent/ops: monitor gateway p95, subgraph error rates, and composition CI failures; alert when any subgraph exceeds error threshold or schema publish fails.
  8. SLO on gateway availability separate from individual services; runbook for schema rollback and for shedding expensive operations during incidents.
Code / ops
text
# CI gate
# 1. rover/composition validate
# 2. contract tests for @key entities
# 3. deny breaking changes without dual-run plan
Nest / Node: Each Nest codebase exposes a subgraph module; shared scalars/enums live in a versioned package; gateway config lists subgraph endpoints with health checks and timeouts.
Say it out loud
Say it spoken

The gateway composes and protects; services own their slices. We evolve additively with composition CI so seven Nest subgraphs do not become seven ways to break the client.

Traps / weak answers
  • Letting any service push breaking schema without composition checks — clients fail in production first.
  • Putting all business authz only in the gateway — object-level rules rot and leak across resolvers.
  • Unbounded nested queries — one client request fans into a self-inflicted LMS outage.
Follow-ups
  • How do you handle a subgraph outage without blanking the whole page?
  • Persisted queries vs free-form clients—when do you require them?
d13-q10How do you keep Elasticsearch course search consistent with Mongo as the source of truth on an institutional LMS?
First 30 seconds
I'd treat Mongo as SoT and ES as a derived index: reliable change capture, idempotent upserts/deletes, lag metrics, and rebuild playbooks—never dual-write without a reconcile story.
Model answer
  1. Clarify: course create/update/delete commits in Mongo first; an outbox or change stream publishes index commands so ES is eventually consistent with bounded lag.
  2. Indexer consumers upsert by course_id idempotently; deletes tombstone by id; mapping changes go through versioned indexes with alias flip.
  3. Consistency model told to product: search may lag writes by N seconds; read-your-writes for authors can bypass ES via Mongo for the edit UI.
  4. Tradeoff: sync dual-write in the request vs async outbox—prefer outbox because ES blips must not fail enrolments or course saves.
  5. Failure modes: poison messages, mapping explosions, and silent lag growth—detect with outbox age, consumer lag, and sample Mongo↔ES checksum jobs.
  6. Rebuild path: reindex from Mongo into a new index, verify counts/sample hashes, then atomic alias swap with rollback alias.
  7. Prevent/ops: alert on consumer lag and outbox depth; dashboard search freshness and index doc count vs Mongo active courses.
  8. SLO on lag threshold for catalogue freshness; runbook for pause/unpause consumers and for alias rollback after a bad mapping deploy.
Code / ops
text
# outbox row: {id, aggregate:course, course_id, op, payload, created_at}
# consumer: upsert/delete by course_id; commit offset after ES ack
Nest / Node: Course Nest service writes outbox in the same Mongo transaction as the course doc when possible; a dedicated search-indexer worker owns ES credentials and mappings.
Say it out loud
Say it spoken

Mongo is truth; Elasticsearch is a projection. Outbox plus lag alerts and rebuild aliases keep search useful without making ES a write dependency.

Traps / weak answers
  • Dual-writing ES inside the HTTP handler — ES downtime blocks course administration.
  • No rebuild/alias strategy — mapping changes become multi-hour outages.
  • Ignoring delete events — withdrawn courses linger in search and confuse learners.
Follow-ups
  • How do you provide read-your-writes for course authors?
  • What is your max acceptable search lag and why?
d13-q11Design WebSocket chat for 1000+ concurrent users on an institutional LMS: persistence, reliable delivery, and fan-out/backpressure.
First 30 seconds
I'd separate connection fan-out from durable persistence: write path commits messages first, then fans out with backpressure, and clients recover via catch-up cursors—not by hoping sockets stay up.
Model answer
  1. Clarify roles: gateway/socket tier holds connections; chat service persists messages and receipts; Redis/pubsub or a broker fans events across nodes for 1000+ concurrent users.
  2. Reliable delivery: assign monotonic per-room sequence or cursor; client ACKs; on reconnect, catch-up query from last cursor so disconnects do not drop history.
  3. Persistence before fan-out for messages that must not vanish; ephemeral typing indicators can be best-effort and rate-limited.
  4. Backpressure: per-connection outbound buffers with drop/slow-consumer disconnect policies; server-side rate limits on send to protect persistence and fan-out.
  5. Tradeoff: sticky sessions vs fully pub/sub mesh—prefer pub/sub so scale-out does not pin rooms to one box; cost is slightly higher fan-out complexity.
  6. Failure modes: hot rooms melting a node, unbounded reconnect storms, and duplicate delivery on retry—detect with connection count, outbound buffer depth, and duplicate-suppress metrics.
  7. Prevent/ops: alert on connection spike, message persist lag, and fan-out error rate; dashboard concurrent sockets and room hotness.
  8. SLO on persist success and catch-up latency after reconnect; runbook for shedding non-critical events and for draining a bad node without dropping durable messages.
Code / ops
text
# delivery
# 1. persist message + seq
# 2. publish room event
# 3. local sockets write; slow consumer → disconnect
# 4. catchup: GET /messages?after=seq
Nest / Node: Nest gateway or a dedicated WS service authenticates on connect, maps user→rooms, and uses a Redis adapter for multi-instance fan-out; business rules stay in a chat domain module.
Say it out loud
Say it spoken

Persist first, fan out second, catch up by cursor. Backpressure and rate limits keep a hot room from taking down the institutional LMS chat tier.

Traps / weak answers
  • Fan-out before durable write — acknowledged UI messages disappear on crash.
  • Infinite server buffers for slow clients — memory death under 1000+ sockets.
  • No catch-up cursor — every blip forces full history reload or silent gaps.
Follow-ups

  1. Clarify the framework: Detect (symptom + blast radius) → Mitigate (stop patient/learner/customer harm) → Diagnose (evidence) → Permanent fix (systemic) → Verify (metric + game-day)—portable across all three platforms.
  2. Detect: name the SLI that moved (error rate, lag, empty retrieve, chat disconnects, projection lag, authz anomalies) and the dashboard/alert that should have fired—or the gap if it did not.
  3. Mitigate first: feature flag off, traffic shed, reprocess pause, dual-run rollback, raise review strictness—choose the reversible control that shrinks blast radius fastest.
  4. Diagnose with evidence: correlation ids, stage metrics, queue lag, canary org diffs—avoid blame narratives; write a timeline of facts.
  5. Permanent fix changes the system: idempotency, filter, index, lock, schema gate, alert, or runbook—not only 'restarted the pod'.
  6. Tradeoff: long RCA theatre vs quick mitigate—always mitigate first; schedule deep fix with owners and dates once harm is contained.
  7. Prevent/ops: add or fix the alert that should have detected earlier; define threshold and page routing; attach a runbook link to the alert.
  8. Close with verification: metric returns to SLO, shadow/canary stays clean, and a game-day re-injects the failure mode to prove detection and mitigation still work on that platform.

03  Self-check

On a document intelligence RAG platform, why is table-aware extraction preferred over naive PDF text extraction?
Planning and financial PDFs encode meaning in grid structure; flattening to prose loses alignment between labels and values and produces confident wrong answers.
Institutional LMS activity is ~16M docs / ~160GB. Safest first move to reduce working set?
Seniors separate hot working set from cold archive and prove learner-metric safety; they reject asymmetric risk for negligible savings.
Healthcare diagnostics: lab results via GPT vision. What must surround the model output?
Vision transcription is probabilistic; typed validation, unit normalisation, and human review for high-risk fields keep patient safety above automation speed.
NestJS↔FastAPI on org-scoped multi-tenant RAG. Primary isolation failure to design against?
Cross-tenant leakage usually comes from unsigned trust of tenant context or shared indexes/caches—not from using object storage itself.
