MongoDB: Modeling, Indexing & Scaling

MongoDB performance is query-driven: indexes follow real filters and sort keys, not the ER diagram. Embedding wins for co-accessed bounded data; references win when data is shared, large, or unbounded. At scale, shard key cardinality and hotspot avoidance matter more than 'just add shards,' and scatter-gather queries punish bad access patterns.

d06-q01A MongoDB collection has 100 million documents and a frequently used query became slow. What would you inspect first?
First 30 seconds
I would capture the exact filter/sort/projection, run explain('executionStats'), and check whether we still hit an index or started scanning millions of docs.
Model answer
  1. Confirm the query shape from production logs (filter, sort, collation, hint) — small predicate changes kill index use.
  2. Run explain('executionStats'): winning plan, IXSCAN vs COLLSCAN, keysExamined / docsExamined / nReturned ratio.
  3. Check index list and usage (existing indexes, partial/sparse, ESR rule: Equality, Sort, Range).
  4. Look at working set vs RAM, replication lag, and whether the collection recently grew past cache.
  5. Fix with a compound index matching the query, covered projection if possible, then re-measure; only then consider schema or shard changes.
Code / ops
text
db.orders.find({ status: 'open', customerId: 42 })
  .sort({ createdAt: -1 })
  .explain('executionStats')
Nest / Node: Log slow queries with filter keys (not necessarily full PII values) from the Mongo driver.
Say it out loud
Say it spoken

First explain executionStats. If docsExamined ≫ nReturned, the index or query shape is wrong — I fix that before talking about sharding.

Traps / weak answers
  • Adding indexes blindly without explain
  • Sorting in memory because the index doesn't include the sort key
  • Blaming 'Mongo is slow' when the query is a collection scan
Follow-ups
  • What is a covered query?
  • How do you find unused indexes safely?
d06-q02How would you decide between embedding and referencing for a MongoDB document model?
First 30 seconds
Embed when data is read together, has clear ownership, and stays bounded. Reference when shared, independently updated, or unbounded.
Model answer
  1. Ask access patterns: one read should ideally get what the API needs — embed those fields.
  2. Embed: address on order, small config blobs, bounded comment previews — atomic updates with the parent.
  3. Reference: users shared across docs, large media metadata, infinite event histories.
  4. Hybrid: embed a denormalized snapshot (product name at order time) and keep a reference for the source of truth.
  5. Revisit when document size, update contention, or fan-out updates become painful.
Code / ops
text
// Embed bounded line items on order
// { _id, customerId, items: [{ sku, qty, price }] }
// Reference unbounded events
// order_events: { orderId, type, at }
Nest / Node: Avoid generic repository patterns that force relational joins via $lookup everywhere.
Say it out loud
Say it spoken

Modeling follows queries. Embed co-read bounded data; reference shared or unbounded data — and denormalize snapshots when history must not change.

Traps / weak answers
  • Embedding unbounded arrays 'for convenience'
  • Referencing everything and $lookup-joining like SQL by default
  • Forgetting denormalized snapshots go stale on purpose (or not)
Follow-ups
  • When is $lookup acceptable in hot paths?
  • How do you update denormalized fields across many documents?
d06-q03An aggregation pipeline is slow in production. How would you identify the expensive stage and optimize it?
First 30 seconds
I explain the aggregation, find the stage with the biggest time/docs, and push $match/$sort early with indexes — avoid blowing up with $lookup or unbounded $group.
Model answer
  1. Run aggregate([...], { explain: true }) / explain('executionStats') and identify costly stages.
  2. Move selective $match (and $sort+$limit) as early as possible so later stages see fewer docs; ensure indexes support that match/sort.
  3. Watch $lookup (N+1 style blowups), $unwind on large arrays, and $group spilling to disk.
  4. Project only needed fields early; avoid returning huge intermediate documents.
  5. Consider pre-aggregations, materialized collections, or changing the schema if the pipeline is a permanent hot path.
Code / ops
text
db.orders.aggregate([
  { $match: { createdAt: { $gte: ISODate('2026-01-01') } } },
  { $group: { _id: '$status', n: { $sum: 1 } } }
], { explain: true })
Nest / Node: Prefer indexed finds for simple queries; aggregation is for multi-stage transforms.
Say it out loud
Say it spoken

Find the expensive stage, filter early with an index, and treat $lookup/$unwind/$group as suspects until proven cheap.

Traps / weak answers
  • $match after $lookup on the full collection
  • Using aggregation when a compound index + find would suffice
  • Ignoring allowDiskUse as a permanent crutch
Follow-ups
  • How do you index for $match + $sort + $limit?
  • When would you use a materialized view collection?
d06-q04How would you choose MongoDB indexes from real query patterns rather than from the schema alone?
First 30 seconds
I inventory the top queries by frequency and latency, then design compound indexes for those predicates — schema fields alone don't tell me selectivity or sort order.
Model answer
  1. Collect slow/query logs or APM: filter keys, sort, projection, frequency.
  2. Apply ESR: Equality fields first, then Sort, then Range — build compound indexes accordingly.
  3. Prefer one compound index that serves a critical query over many single-field indexes.
  4. Use partial indexes for hot subsets (e.g. status: 'open') and TTL indexes for expiring data.
  5. Drop unused indexes after verifying; every index costs write amplification and RAM.
Code / ops
text
// Query: { tenantId, status } sort createdAt
db.orders.createIndex({ tenantId: 1, status: 1, createdAt: -1 })
Nest / Node: Review indexes in PR checklist whenever a new repository query is added.
Say it out loud
Say it spoken

Indexes follow the workload. I rank real queries, build compound keys with ESR, and delete indexes that only look good on the schema.

Traps / weak answers
  • Indexing every field 'just in case'
  • Left-prefix mistakes (index unused because equality order wrong)
  • Ignoring collation / case-insensitive needs
Follow-ups
  • How do multikey indexes on arrays behave?
  • What's the cost of too many indexes on a write-heavy collection?
d06-q05A document contains an array that grows indefinitely and is frequently queried. How would you redesign the model?
First 30 seconds
Unbounded arrays are a modeling smell — I'd move events into a child collection keyed by parent id, or bucket by time, and keep only a bounded recent slice embedded if needed.
Model answer
  1. Diagnose: document size growth, slow $push/$pull, multikey index bloat, risk of 16MB limit.
  2. Extract the array into a separate collection: { parentId, …, createdAt } with indexes on parentId + createdAt.
  3. Optionally keep a bounded embedded preview (last N) for fast reads of the parent.
  4. For high-volume time series, use bucketing (one doc per day/hour) instead of one mega-array.
  5. Migrate with batched reads/writes; update queries to page the child collection.
Code / ops
text
// Before: { _id, events: [ ...growing ] }
// After:
// parent: { _id, lastEvents: [ /* max 20 */ ] }
// events: { parentId, type, at } indexed { parentId: 1, at: -1 }
Nest / Node: API pagination should target the events collection, not load the whole parent.
Say it out loud
Say it spoken

Infinite arrays don't belong in one document. Child collection or time buckets, maybe a small embedded preview for the hot read.

Traps / weak answers
  • Capping with $slice in queries but still storing unbounded data
  • Using $unwind on huge arrays in hot aggregations
  • One document per user that accumulates lifetime history
Follow-ups
  • How do you migrate without dual-write races?
  • When are bucket patterns better than one-doc-per-event?
d06-q06How would you choose a shard key for a high-write MongoDB workload?
First 30 seconds
I need high cardinality and even write distribution so inserts don't hammer one chunk/shard, while still supporting targeted queries with that key.
Model answer
  1. List write pattern and top queries that must be targeted (avoid scatter-gather on hot paths).
  2. Prefer a key with high cardinality and monotonic-write awareness — pure increasing _id/timestamps can hotspot on one shard.
  3. Common pattern: { tenantId, _id } or hashed field when range queries aren't needed; compound keys for tenant isolation + uniqueness.
  4. Avoid low-cardinality keys (status, country) that create jumbo hot chunks.
  5. Load-test distribution; plan for resharding cost if the key is wrong — choosing carefully beats early sharding.
Code / ops
text
// Example: tenant-scoped compound shard key
sh.shardCollection('app.orders', { tenantId: 1, _id: 1 })
Nest / Node: Include shard key fields in repository query helpers so developers can't omit them easily.
Say it out loud
Say it spoken

Shard key = cardinality + even writes + targeted reads. I won't shard on status or plain timestamps that create hot shards.

Traps / weak answers
  • Sharding on low-cardinality fields
  • Assuming more shards fix a hotspot key
  • Picking a key that forces scatter-gather on every API read
Follow-ups
  • Hashed vs ranged shard keys — trade-offs?
  • What is a jumbo chunk?
d06-q07What characteristics can make a MongoDB shard key a hotspot?
First 30 seconds
Low cardinality, monotonically increasing values, or a popular tenant/key that attracts most writes — all funnel inserts to one chunk or shard.
Model answer
  1. Monotonic keys (Date, ObjectId time portion, auto-inc) send new writes to the highest chunk — right-hand hotspot.
  2. Low cardinality (enum status, boolean) creates few fat chunks that can't split usefully.
  3. Skewed real-world distribution: one celebrity tenantId dominates traffic.
  4. Hot documents updated constantly on one shard key value.
  5. Mitigations: hashed keys, compound keys with high-cardinality suffix, isolate whales, or rethink access patterns.
Say it out loud
Say it spoken

Hotspots come from monotonic inserts, low cardinality, or traffic skew. The key must spread writes, not just unique them.

Traps / weak answers
  • Thinking 'unique' equals 'well distributed'
  • Hashing away range queries you still need without a plan
  • Ignoring one mega-tenant after choosing tenantId alone
Follow-ups
  • How do you detect imbalance across shards in metrics?
  • Can you change a shard key later and what does it cost?
d06-q08A query becomes scatter/gather in a sharded cluster. What does that mean for performance and how would you reduce it?
First 30 seconds
Scatter-gather means mongos fans the query to many/all shards and merges results — latency and load scale with shard count. I reduce it by including the shard key in queries or redesigning the key/access path.
Model answer
  1. Confirm in explain: shards touched, sorting/merging on mongos, high cumulative docs examined.
  2. Add shard-key equality (or selective prefix) to hot queries so they become targeted.
  3. For pagination/sort without shard key, expect merge cost — prefer targeted queries or precomputed views.
  4. If the business query can never include the shard key, reconsider shard key or duplicate data into a query-optimized collection.
  5. Monitor mongos CPU and per-shard ops; scatter-gather under load becomes a cluster-wide amplification bug.
Code / ops
text
// Targeted: includes shard key
db.orders.find({ tenantId: 'acme', _id: orderId })
// Scatter: missing tenantId on sharded { tenantId: 1, _id: 1 }
Nest / Node: Lint or wrapper: require tenantId in find criteria for sharded tenant collections.
Say it out loud
Say it spoken

Scatter-gather fans out to every shard. Hot paths must be targeted by shard key — otherwise each read taxes the whole cluster.

Traps / weak answers
  • Assuming secondary indexes make queries targeted (they don't replace shard key routing)
  • Adding shards to 'fix' scatter-gather (often makes it worse)
  • Sorting globally without limits on scatter queries
Follow-ups
  • How does mongos merge sorted results?
  • When is scatter-gather acceptable?
d06-q09You need to update tens of millions of MongoDB documents. How would you make the migration safe, resumable, and observable?
First 30 seconds
Batched bulkWrite by _id ranges with a checkpoint, idempotent updates, rate limits, and metrics — never one multi-update that can't resume.
Model answer
  1. Design idempotent document transforms (safe to re-run) and a migration version field if needed.
  2. Iterate with a cursor/_id range; bulkWrite ordered:false in batches (e.g. 500–1000); persist lastProcessedId checkpoint.
  3. Throttle (sleep/token bucket) to protect WT cache and replication lag; pause when lag or CPU exceeds SLO.
  4. Observe: documents/sec, errors, lag, percent complete; dead-letter failed _ids.
  5. Verify with sampling/checksums; support resume after crash from checkpoint.
Code / ops
python
let lastId = checkpoint.load();
while (true) {
  const batch = await col.find({ _id: { $gt: lastId } }).sort({ _id: 1 }).limit(1000).toArray();
  if (!batch.length) break;
  await col.bulkWrite(batch.map(doc => ({ updateOne: { filter: { _id: doc._id }, update: { $set: { … } } } })), { ordered: false });
  lastId = batch[batch.length - 1]._id;
  checkpoint.save(lastId);
}
Nest / Node: Run as a worker job with lock so two migrators don't double-load the cluster.
Say it out loud
Say it spoken

Big migrations are checkpointed bulkWrite loops — idempotent, throttled, observable, and resumable from last _id.

Traps / weak answers
  • updateMany on the whole collection with no resume story
  • Unordered bulk without tracking per-doc failures
  • Migrating at full speed until secondary lag pages someone
Follow-ups
  • How do you dual-write during expand-contract in Mongo?
  • When would you use change streams for migration?
d06-q10How would you design multi-tenant data isolation in MongoDB?
First 30 seconds
Choose isolation tier: shared collection with tenantId, database-per-tenant, or cluster-per-tenant for the noisiest/compliance-heavy customers — enforce tenant predicates in every query.
Model answer
  1. Default: shared collection(s) with tenantId on every document; compound indexes starting with tenantId; shard key often includes tenantId.
  2. Enforce isolation in the data access layer (mandatory filter), not only in controllers; consider atlas/server-side validation or wrappers.
  3. Stronger isolation: separate database per tenant for compliance/noisy neighbors; highest: dedicated cluster.
  4. Never trust client-supplied tenantId alone — bind from authenticated session.
  5. Test for cross-tenant leakage; audit queries missing tenantId; watch jumbo tenants for hotspot/shard skew.
Code / ops
text
db.orders.createIndex({ tenantId: 1, createdAt: -1 })
db.orders.find({ tenantId: auth.tenantId, … })
Nest / Node: Nest middleware/CLS can inject tenantId into repositories so handlers can't omit it.
Say it out loud
Say it spoken

tenantId on every doc and every query, indexes and shard key aligned, auth-bound tenant — escalate to DB- or cluster-per-tenant when compliance or noise demands it.

Traps / weak answers
  • Filtering tenant only in the UI
  • Unique indexes that aren't tenant-scoped (email global vs per-tenant)
  • One mega-tenant melting a shared shard
Follow-ups
  • How do unique constraints work per tenant?
  • When do you move a tenant to its own database?
