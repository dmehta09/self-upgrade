Third-Party APIs & Dependency Failures

Production systems fail at the seams with vendors, payments, and partner APIs. Interviewers want timeouts, bulkheads, retries with jitter, circuit breakers, and idempotency — not 'we would hope they are up'. Seniors explain how a slow dependency becomes your outage via thread pools and sync waits, and how to degrade without corrupting money or inventory.

01  Decision cheat strip

Timeouts firstEvery outbound call needs connect/read deadlines tighter than your client SLO
BulkheadIsolate pools/semaphores per dependency so one vendor cannot consume all workers
Retry wiselyOnly idempotent/safe calls; exponential backoff + jitter; honor Retry-After
Circuit breakerOpen on error rate/latency; shed fast; half-open probe; avoid retry storms
Idempotency keysRequired for payments and any 'maybe succeeded' timeout ambiguity
DegradeCached/partial/feature-off beats hanging the entire request path

d03-q01Your application integrates three third-party APIs and one becomes slow. How would you prevent it from degrading the entire request path?
First 30 seconds
Slow dependencies exhaust shared workers and connection pools — I isolate them with timeouts, per-dependency concurrency limits, and optional circuit breaking so the other two APIs and our handlers keep moving.
Model answer
  1. Put aggressive timeouts on the slow vendor's client (connect + read), separate from other clients.
  2. Bulkhead: dedicated asyncio.Semaphore / httpx limits / thread pool for that dependency.
  3. Run independent calls concurrently; don't let the slow one sit on the critical path if the feature is optional.
  4. Circuit breaker: open when p95 or error rate exceeds threshold; return cached/degraded data.
  5. Fail partial: return 200 with missing widget vs block checkout if that vendor is non-critical.
  6. Monitor per-dependency latency and in-flight; alert before global p95 burns.
  7. Move non-interactive calls off-request into queues when possible.
  8. Load-test with one dependency delayed (toxiproxy/fault injection) to prove isolation.
Code / ops
python
import asyncio, httpx

# Per-dependency bulkhead
payments_sem = asyncio.Semaphore(20)
search_sem = asyncio.Semaphore(50)

async def call_payments(client: httpx.AsyncClient, path: str):
    async with payments_sem:
        return await client.get(path, timeout=httpx.Timeout(0.5, read=2.0))
Nest / Node: Nest: separate HttpModule registrations or axios instances per vendor with maxSockets; use a circuit-breaker library (opossum) around each client.
Say it out loud
Say it spoken

One slow vendor should not own our worker pool. I give it its own timeout and concurrency bulkhead, degrade that feature when the breaker opens, and keep the rest of the request healthy.

Traps / weak answers
  • Sharing one global timeout and one connection pool across all vendors
  • Waiting on optional enrichment APIs before returning core data
  • Retrying the slow dependency aggressively without a breaker
Follow-ups
  • How do you decide which dependency is on the critical path?
  • What dashboards prove a bulkhead is working during a vendor incident?
d03-q02A third-party API normally responds in 200 ms but sometimes takes 15 seconds. How would you design the integration?
First 30 seconds
Design for the tail, not the mean: short client timeouts, retries only when safe, hedges or async fallback for rare spikes, and SLOs that assume p99 can be awful. A 15s wait is usually worse than a fast failure.
Model answer
  1. Set read timeout around a small multiple of healthy p99 (e.g. 1–2s), not 15s.
  2. Classify the call: user-critical sync vs acceptable eventually — push the latter to a queue.
  3. For sync path: timeout → cached value / default / 503 with Retry-After.
  4. Optional hedging: duplicate request to a secondary after 300ms if the API is idempotent and cost-acceptable.
  5. Record latency histogram; alert on p95, not only averages.
  6. Negotiate vendor SLA and status webhooks; don't discover 15s only from user complaints.
  7. Ensure nginx/ALB timeouts are higher than your client timeout so users get your error, not a generic 504.
  8. Document degraded mode behavior in the API contract.
Code / ops
python
import httpx

TIMEOUT = httpx.Timeout(connect=0.3, read=1.5, write=1.5, pool=0.3)

async def fetch_profile(client: httpx.AsyncClient, user_id: str):
    try:
        r = await client.get(f"/profiles/{user_id}", timeout=TIMEOUT)
        r.raise_for_status()
        return r.json()
    except httpx.TimeoutException:
        return {"id": user_id, "name": "Unknown", "degraded": True}
Say it out loud
Say it spoken

I won't budget 15 seconds for a call that is usually 200 ms — that turns rare vendor lag into our outage. Short timeout, safe fallback, and move non-critical work async.

Traps / weak answers
  • Matching timeout to the worst observed 15s 'just in case'
  • No fallback, so every spike becomes a user-facing hang
  • Averaging latency and missing the 15s tail
Follow-ups
  • When is request hedging a good idea versus harmful?
  • How do you align browser, ALB, nginx, and outbound timeouts?
d03-q03A payment provider times out, but you do not know whether the payment was actually processed. How would you design the workflow?
First 30 seconds
Timeouts create uncertainty — I never invent a second charge. I use idempotency keys, persist a pending payment intent, and reconcile with the provider's status API or webhooks before confirming success to the user.
Model answer
  1. Create a local payment record in pending with a unique idempotency key before calling the provider.
  2. Send the same key on all retries so the provider dedupes.
  3. On timeout: leave status pending_uncertain; do not mark paid or immediately create a new charge.
  4. Reconcile: poll provider GET-by-idempotency-key / payment id, or wait for signed webhooks.
  5. Expose user state honestly: 'processing' not 'failed' until reconciliation says so.
  6. Background reconciler with backoff; alert on pending older than N minutes.
  7. Make fulfillment (inventory, email) wait on confirmed paid — never on HTTP 200 from an uncertain call.
  8. Runbook: manual tools to inspect provider dashboard by idempotency key during incidents.

  CreatePending --> CallProvider
  CallProvider -->|timeout| Reconcile
  CallProvider -->|ok| MarkPaid
  Reconcile -->|found_paid| MarkPaid
  Reconcile -->|not_found| RetrySameKey
  RetrySameKey --> CallProvider

Say it spoken

After a payment timeout I assume the charge might have succeeded. Same idempotency key, pending state, reconcile via status or webhook — never a blind second capture.

Traps / weak answers
  • Retrying with a new idempotency key after timeout
  • Marking the order failed and allowing the user to pay again immediately
  • Trusting only the client timeout as source of truth for money movement
Follow-ups
  • How do you handle duplicate webhooks for the same payment?
  • What do you show the user while reconciliation is in progress?
d03-q04An external API returns intermittent 5xx errors. How would you decide whether and how to retry?
First 30 seconds
I retry only if the operation is idempotent or safe to duplicate, with exponential backoff and jitter, capped attempts, and respect for Retry-After. Non-idempotent POSTs need idempotency keys or no automatic retry.
Model answer
  1. Classify method/semantics: GET/PUT with idempotency ⇒ retryable; POST charge without key ⇒ don't auto-retry.
  2. Retry on 502/503/504 and selected network errors; usually not on 400/401/403/404.
  3. Use exponential backoff + full jitter; honor Retry-After on 429/503.
  4. Cap attempts (e.g. 3) and total retry budget inside the request SLO.
  5. Prefer idempotency keys when the vendor supports them for POST.
  6. Stop retrying when circuit breaker is open.
  7. Log attempt count and final outcome; metric retry rate by dependency.
  8. Document which errors are retried in the client library so all callers share policy.
Code / ops
python
import random, asyncio, httpx

async def get_with_retry(client: httpx.AsyncClient, url: str, attempts=3):
    delay = 0.2
    for i in range(attempts):
        try:
            r = await client.get(url, timeout=2.0)
            if r.status_code in (502, 503, 504) and i < attempts - 1:
                raise httpx.HTTPStatusError("retry", request=r.request, response=r)
            r.raise_for_status()
            return r
        except (httpx.TransportError, httpx.HTTPStatusError):
            if i == attempts - 1:
                raise
            await asyncio.sleep(delay * random.random())
            delay *= 2
Nest / Node: axios-retry or custom Nest interceptor with the same idempotency rules; never globally retry all methods.
Say it out loud
Say it spoken

Intermittent 5xx gets a small number of jittered retries only when safe. No key, no retry on money-moving POSTs — and I never retry harder than the dependency can handle.

Traps / weak answers
  • Retrying every POST by default
  • Fixed synchronized sleep that aligns all clients
  • Infinite retries until the client times out
Follow-ups
  • How do you implement full jitter vs equal jitter?
  • Which 4xx codes might still be worth retrying and why?
d03-q05When can retries make an outage worse?
First 30 seconds
Retries amplify load when the dependency is already saturated — especially synchronized client retries, missing jitter, or retrying non-idempotent calls that create duplicate side effects. That's how a blip becomes a multi-hour incident.
Model answer
  1. Thundering herd: all instances retry at the same delay after a timeout.
  2. Retry storms: each layer (browser, API, worker) retries independently without a shared budget.
  3. Non-idempotent retries duplicate orders, emails, or charges.
  4. Retrying while circuit should be open keeps beating a dead dependency.
  5. Huge fan-out (Promise.all 1000) + retry multiplies traffic 3–5x.
  6. Hot-key contention: retries pile onto the same failing shard.
  7. Mitigations: jitter, caps, breaker, hedge carefully, backoff at every layer, load shedding.
  8. Prefer queued processing with limited concurrency over eager request-path retries.
Say it out loud
Say it spoken

Retries are a privilege, not a default. Without jitter, budgets, and idempotency, they turn a vendor hiccup into a self-DDoS — so I cap, spread, and trip a breaker.

Traps / weak answers
  • Adding more retries as the first response to rising 5xx
  • Retrying at API gateway, service, and worker simultaneously with no coordination
  • Ignoring Retry-After and hammering on 429
Follow-ups
  • What is a retry budget and how would you enforce one?
  • How do you test for retry amplification in staging?
d03-q06One dependency is unavailable for 30 minutes. How should your application behave for requests that depend on it?
First 30 seconds
Thirty minutes is longer than any sensible sync retry — fail fast or degrade intentionally. Critical paths should return a clear error or queued acceptance; non-critical paths should serve cache or hide the feature.
Model answer
  1. Trip circuit breaker quickly after sustained failures; stop waiting on full timeouts each request.
  2. Critical dependency (payments, auth): return 503 with Retry-After / status page link; don't pretend success.
  3. Non-critical: cached data, last-known-good, or omit the section with a degraded flag.
  4. Accept-and-queue when work can complete later (e.g. send email) — return 202.
  5. Protect core invariants: don't mark paid, ship, or delete without the dependency confirming.
  6. Communicate: feature flags to disable the integration UX during the outage.
  7. Keep reconciling pending work when the vendor recovers.
  8. Post-incident: adjust timeouts/breaker thresholds using the 30-minute timeline.
Say it out loud
Say it spoken

For a half-hour outage I fail fast or go degraded — I don't burn workers on hopeless retries. Critical flows get an honest 503 or queued processing; everything else serves cache or turns the feature off.

Traps / weak answers
  • Leaving users spinning on spinners for the entire 30 minutes
  • Silently succeeding without performing the side effect
  • Blocking unrelated endpoints that share the same worker pool
Follow-ups
  • How do you product-communicate degraded mode without lying in the API?
  • What pending work piles up and how do you drain it safely after recovery?
d03-q07How would you implement circuit breaking for an unreliable dependency?
First 30 seconds
A circuit breaker tracks recent failures/latency, opens to fail fast, half-opens to probe, and closes on success. I'll define thresholds from SLOs, isolate state per dependency, and emit metrics for open/half-open transitions.
Model answer
  1. States: closed (normal) → open (fail fast) → half-open (limited probes) → closed.
  2. Trip on error rate, consecutive failures, or extreme latency — measured on a rolling window.
  3. On open: immediate fallback/error without outbound I/O; sleep for open duration.
  4. Half-open: allow one or N trial calls; success closes, failure re-opens.
  5. Scope breakers per dependency and optionally per tenant/shard to avoid global trips.
  6. Combine with timeouts — breakers don't replace deadlines.
  7. Libraries: resilience4j-inspired patterns, aiobreaker, opossum (Node) — or a small in-process implementation with Redis for multi-instance coordination when needed.
  8. Alert when open; dashboards show rejected-fast vs upstream errors.
Diagram
flowchart LR
  Closed -->|error_rate_high| Open
  Open -->|cooldown_elapsed| HalfOpen
  HalfOpen -->|probe_ok| Closed
  HalfOpen -->|probe_fail| Open
Code / ops
python
class CircuitBreaker:
    def __init__(self, failure_threshold=5, recovery_timeout=30):
        self.failure_threshold = failure_threshold
        self.recovery_timeout = recovery_timeout
        self.failures = 0
        self.opened_at = 0.0
        self.state = "closed"

    def before_call(self, now: float):
        if self.state == "open" and now - self.opened_at >= self.recovery_timeout:
            self.state = "half_open"
        if self.state == "open":
            raise RuntimeError("circuit_open")

    def on_success(self):
        self.failures = 0
        self.state = "closed"

    def on_failure(self, now: float):
        self.failures += 1
        if self.failures >= self.failure_threshold or self.state == "half_open":
            self.state = "open"
            self.opened_at = now
Nest / Node: opossum around Nest HttpService calls; share state carefully across cluster instances or accept per-process breakers.
Say it out loud
Say it spoken

Circuit breaking is fail-fast with a recovery probe. I open on sustained errors, stop calling the vendor, serve fallback, then half-open carefully so we don't flap or storm.

Traps / weak answers
  • One global breaker for all dependencies
  • Half-open allowing full traffic immediately
  • No metrics — breaker opens silently and looks like an app bug
Follow-ups
  • Should breaker state be local per instance or centralized?
  • How do you avoid flapping when errors are borderline?
d03-q08Two external providers offer the same capability. How would you design failover between them?
First 30 seconds
I'd treat them as active/standby or weighted primary with health-aware failover, keeping response mapping and idempotency consistent. Failover must not double side effects — keys and reconciliation matter as much as DNS switching.
Model answer
  1. Normalize both providers behind an interface (ports/adapters) with a common domain model.
  2. Primary with health score (latency, errors); fail over when breaker opens or SLO burns.
  3. Idempotency: store which provider owns a given operation; don't replay the same logical op to both blindly.
  4. For reads: failover is easy; for writes: prefer sticky provider per entity until terminal state.
  5. Map errors and statuses carefully — provider A 'pending' ≠ provider B 'failed'.
  6. Run periodic synthetic probes to the secondary so cold standby isn't broken.
  7. Config/feature-flag traffic split for canarying the secondary.
  8. Observe cost and rate limits — failover can slam the backup's quota.
Code / ops
python
class ProviderRouter:
    def __init__(self, primary, secondary, primary_breaker):
        self.primary, self.secondary = primary, secondary
        self.breaker = primary_breaker

    async def fetch(self, key: str):
        try:
            self.breaker.before_call(now())
            out = await self.primary.fetch(key)
            self.breaker.on_success()
            return out
        except Exception:
            self.breaker.on_failure(now())
            return await self.secondary.fetch(key)
Say it out loud
Say it spoken

Failover is an interface plus safe ownership of each operation. I trip off the primary when its breaker opens, stick writes to one provider per intent, and keep the secondary warm with synthetics so failover isn't a surprise.

Traps / weak answers
  • Calling both providers on every write 'for safety'
  • Failing over without testing the secondary under production load
  • Mixing provider transaction ids in one database column without a provider discriminator
Follow-ups
  • How do you fail back to primary without a flip-flop?
  • What contract tests do you run against both providers?
d03-q09A provider imposes strict rate limits and your traffic suddenly increases 20x. How would you protect your system?
First 30 seconds
I shed and shape load before we get banned: client-side rate limiting, queues, caching, and bulkheads keyed to the provider's quota. A 20x spike without a queue will burn the rate limit and then cascade into our own 5xx.
Model answer
  1. Enforce an outbound rate limiter (token bucket) matching the provider's documented RPS/quota.
  2. Buffer excess in a durable queue; process at sustained allowed rate.
  3. Cache idempotent GETs aggressively; collapse duplicate in-flight requests (singleflight).
  4. Priority lanes: checkout beats batch sync when quota is scarce.
  5. Backoff on 429 using Retry-After; never busy-spin.
  6. Graceful degradation: disable non-essential features that call the provider.
  7. Request more quota / burst capacity from the vendor with evidence graphs.
  8. Load-test the limiter so our API returns 503/429 cleanly instead of hanging.
Code / ops
python
import asyncio, time

class TokenBucket:
    def __init__(self, rate_per_sec: float, capacity: float):
        self.rate, self.capacity = rate_per_sec, capacity
        self.tokens, self.updated = capacity, time.monotonic()
        self.lock = asyncio.Lock()

    async def acquire(self):
        async with self.lock:
            now = time.monotonic()
            self.tokens = min(self.capacity, self.tokens + (now - self.updated) * self.rate)
            self.updated = now
            if self.tokens < 1:
                await asyncio.sleep((1 - self.tokens) / self.rate)
                return await self.acquire()
            self.tokens -= 1
Nest / Node: Use Bottleneck or a Redis rate limiter shared across Nest replicas so each instance doesn't take the full quota.
Say it out loud
Say it spoken

When traffic jumps 20x against a strict vendor quota, I rate-limit outbound calls and queue the rest. Better an honest 503 or delayed job than a ban and a total outage.

Traps / weak answers
  • Scaling API replicas 20x and multiplying outbound RPS
  • Ignoring 429 bodies and Retry-After
  • No product prioritization — batch jobs starve checkout
Follow-ups
  • How do you share a token bucket across multiple service replicas?
  • What user-facing behavior do you choose when the queue depth is too high?
d03-q10How would you make an external API integration idempotent from your application's point of view?
First 30 seconds
Idempotency means retries don't create duplicate side effects. I generate a stable key per business intent, persist it before the call, send it to the provider when supported, and dedupe webhook/response handling on my side.
Model answer
  1. Define the idempotency scope: one key per user intent (place order, capture payment), not per HTTP attempt.
  2. Persist key + request hash + state in your DB with a unique constraint before outbound I/O.
  3. Send Idempotency-Key / provider equivalent on mutating calls.
  4. On replay: return the original result if the same key+hash arrives; conflict if same key different body.
  5. Dedupe inbound webhooks by event id with an processed_events table.
  6. Make local effects transactional with state transitions (pending→succeeded).
  7. TTL/retention for keys long enough to cover retries and late webhooks.
  8. Test chaos: timeout, retry, duplicate webhook — assert single side effect.
Code / ops
python
from fastapi import FastAPI, Header, HTTPException

app = FastAPI()

class CreateOrder(BaseModel):
    sku: str
    qty: int

@app.post("/orders")
async def create_order(body: CreateOrder, idempotency_key: str = Header(...)):
    existing = await db.fetch_order_by_key(idempotency_key)
    if existing:
        if existing.request_hash != hash(body):
            raise HTTPException(409, "Idempotency key reuse with different body")
        return existing.response
    # insert pending with key, call provider with same key, finalize
    ...

Say it out loud
Say it spoken

From our side, idempotency is a durable key tied to business intent, unique constraints, and deduped webhooks. Retries may hit the network twice, but inventory and money move once.

Traps / weak answers
  • Using random keys on each retry
  • Only deduping in memory on one instance
  • Ignoring webhook duplicates after a successful sync response
Follow-ups
  • How long should you retain idempotency keys and why?
  • What happens if two different bodies reuse the same key?
