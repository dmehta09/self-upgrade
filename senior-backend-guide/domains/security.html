Security & Multi-Tenancy

Interviewers probe whether you separate authentication from authorization, design token lifecycles you can revoke, and enforce tenant isolation in every query—not only in the UI. Seniors also own secrets hygiene, webhook authenticity, and safe patterns for private S3 content.

01  Decision cheat strip

TokensShort-lived access + rotating refresh; revoke via denylist/family
Tenancytenant_id from token; row filters + app checks; never from client body alone
RBAC+ReBACRoles for coarse; relationships for resource-level
SecretsSecrets Manager/SSM; rotate; never commit; IR = rotate first
Webhooks/S3HMAC+timestamp; private buckets + short presigned URLs

d11-q01How would you secure a public FastAPI or NestJS API against common abuse and unauthorized access?
First 30 seconds
I'd layer edge controls with app controls: TLS, authn on protected routes, authz per action, rate limits, input validation, and least-privilege DB/IAM—never 'security through obscurity'.
Model answer
  1. Terminate TLS at the edge; redirect HTTP; set security headers (HSTS, etc.) appropriately.
  2. Authenticate with Bearer JWT/session; FastAPI dependencies / Nest guards on every protected route.
  3. Authorize explicitly (RBAC/ReBAC); deny by default; validate payloads with Pydantic / class-validator.
  4. Rate-limit by IP and by user/tenant at API GW/WAF and in-app; protect login and expensive endpoints harder.
  5. CORS allowlist; disable verbose errors in prod; structured audit logs with correlation ids.
  6. Dependency scanning, secret-free config, and least-privilege IAM for the runtime role.
Code / ops
python
from fastapi import Depends, HTTPException

async def require_user(user=Depends(get_current_user)):
    if not user:
        raise HTTPException(401)
    return user
Nest / Node: Nest: AuthGuard + RolesGuard/CASL policies as interceptors/guards; ValidationPipe whitelist+forbidNonWhitelisted globally.
Say it out loud
Say it spoken

Public APIs get defense in depth: TLS, authn, authz, validation, and rate limits at the edge and in the app. Deny by default and never trust client-supplied tenancy or roles.

Traps / weak answers
  • Only checking auth on the frontend.
  • Returning stack traces and internal hostnames on 500s.
Follow-ups
  • How do you authenticate service-to-service calls differently from browsers?
  • Where do you put rate limits—WAF, gateway, or app?

d11-q02How would you design access-token and refresh-token handling for a large application?
First 30 seconds
Short-lived access tokens for API calls; longer-lived refresh tokens used only at the token endpoint, preferably rotating and stored httpOnly/secure. Access tokens stay small and verifiable.
Model answer
  1. Access JWT: 5–15 minutes, signed (RS256/ES256), claims: sub, tenant, roles/scopes, jti, exp.
  2. Refresh token: opaque or JWT stored server-side (hash in DB), bound to device/session; rotate on every use.
  3. Browser: refresh in httpOnly Secure SameSite cookie; access in memory (or also cookie with CSRF strategy).
  4. Mobile/native: secure storage OS APIs; still rotate refresh tokens.
  5. Resource servers validate access tokens locally (JWKS) without hitting DB each time; revocation via short TTL + denylist for emergencies.
  6. Separate audiences/issuers for admin vs customer APIs; never put secrets in JWT payloads.
Diagram
flowchart LR
  login[Login] --> pair[Access_plus_Refresh]
  pair --> api[API_accepts_access]
  pair --> refresh[Refresh_endpoint_rotates]
Code / ops
python
# On refresh: rotate — invalidate old refresh jti, issue new pair
# Store only hash(refresh_token) server-side
Nest / Node: Nest Passport JWT strategy for access; separate refresh controller with stricter rate limits and cookie parsing.
Say it out loud
Say it spoken

Short access JWTs plus rotating refresh tokens—refresh only hits the auth service, access is verified via JWKS. Rotation and short TTL limit the blast radius of theft.

Traps / weak answers
  • Week-long access tokens in localStorage.
  • Reusable refresh tokens that never rotate (theft lasts forever until password change).
Follow-ups
  • How do you handle refresh token reuse detection?
  • When would you choose opaque access tokens over JWTs?
d11-q03How would you revoke a refresh token or session without forcing every user to log in again?
First 30 seconds
Revoke one session or one token family—not the whole user population. I'd denylist the refresh jti/family and optionally denylist access jtis until their short TTL expires.
Model answer
  1. Model sessions: session_id / refresh family_id per device; logout deletes or marks that row revoked.
  2. On refresh rotation, detect reuse of an old refresh → revoke the entire family (stolen token signal).
  3. Access tokens: short TTL so revocation is eventual; for emergency, maintain a Redis denylist of jti/user until exp.
  4. Admin 'logout all devices' revokes all families for the user; current access dies within TTL or denylist.
  5. Password change / security event triggers global session revoke for that user only.
  6. Don't rotate signing keys for one user logout—that forces mass re-auth; use key rotation for compromise of the issuer key.
Code / ops
python
await db.execute("UPDATE sessions SET revoked_at=now() WHERE id=$1 AND user_id=$2", sid, uid)
await redis.setex(f"deny:jti:{jti}", ttl_remaining, "1")
Nest / Node: Nest can check a Redis denylist in a guard after JWT signature verification.
Say it out loud
Say it spoken

I revoke at session/family granularity: kill that refresh chain in the DB and denylist access jtis if needed. Short access TTLs mean other users keep working uninterrupted.

Traps / weak answers
  • Rotating the global JWT signing key to log out one user.
  • Storing refresh tokens without a server-side revoke bit.
Follow-ups
  • How do you revoke a JWT access token instantly at scale?
  • How does this interact with multiple API audiences?
d11-q04How would you protect login and password-reset endpoints against brute-force attacks?
First 30 seconds
These endpoints are high-value and unauthenticated. I'd combine rate limits, account lockout/backoff, CAPTCHA after thresholds, constant-time responses, and monitoring—not just a strong password policy.
Model answer
  1. Rate-limit by IP and by username/email (Redis counters) with exponential backoff; return generic errors.
  2. After N failures: temporary lock or CAPTCHA/challenge; alert on distributed spray patterns.
  3. Password reset: single-use time-limited tokens, rate-limit requests, do not reveal whether an email exists (or use careful anti-enumeration strategy).
  4. Use Argon2/bcrypt with proper cost; never invent crypto; constant-time compare.
  5. WAF/API GW rules for known bad bots; optional device fingerprinting for risk-based MFA.
  6. Log auth failures with correlation; page on spikes; MFA for privileged accounts.
Code / ops
python
key = f"login:{ip}:{email}"
if await redis.incr(key) == 1:
    await redis.expire(key, 900)
if int(await redis.get(key)) > 10:
    raise HTTPException(429, "Too many attempts")
Nest / Node: Nest ThrottlerGuard with multiple named limits for /auth/login and /auth/reset; custom Redis store for per-account counters.
Say it out loud
Say it spoken

Brute-force protection is layered rate limits, backoff/lockout, CAPTCHA at thresholds, and safe password-reset tokens—plus MFA for high privilege. Generic errors avoid account enumeration.

Traps / weak answers
  • Locking only by IP (easy to bypass with botnets) or only by account (easy DoS of a victim).
  • Verbose 'user not found' vs 'wrong password' messages.
Follow-ups
  • How do you defend against credential stuffing specifically?
  • Where should MFA challenge sit in the login flow?
d11-q05How would you enforce tenant isolation so one SaaS customer can never access another customer's records?
First 30 seconds
Tenant identity comes from the verified token, not the request body. Every query and object key includes that tenant_id, with defense-in-depth at the ORM and storage layers.
Model answer
  1. Put tenant_id (or org_id) in access-token claims after membership check at login.
  2. FastAPI dependency injects TenantContext; repositories always filter WHERE tenant_id = :ctx.
  3. Add DB constraints/RLS (Postgres row-level security) as a backstop so a buggy query still cannot cross tenants.
  4. Object storage keys prefixed by tenant; IAM/presign scoped to that prefix.
  5. Forbid client-supplied tenant overrides; admin cross-tenant tools use separate break-glass roles and audit logs.
  6. Automated tests: attempt cross-tenant GET/PATCH by ID and expect 404/403; include in CI.
Code / ops
python
async def get_order(order_id: UUID, tenant: TenantCtx = Depends(get_tenant)):
    row = await db.fetchone(
        "SELECT * FROM orders WHERE id=$1 AND tenant_id=$2", order_id, tenant.id
    )
    if not row:
        raise HTTPException(404)
Nest / Node: Nest: TenantMiddleware sets ALS/request scope; TypeORM global scopes or CASL conditions include tenantId on every ability.
Say it out loud
Say it spoken

Isolation starts with tenant from the token, then every SQL and S3 key is scoped to it—ideally with Postgres RLS as a seatbelt. Client-sent tenant IDs are never authoritative.

Traps / weak answers
  • Looking up by resource UUID alone without tenant predicate.
  • Relying only on UI route prefixes like /t/{tenant}/....
Follow-ups
  • When do you choose separate databases/schemas per tenant vs shared tables?
  • How do background jobs propagate tenant context safely?
d11-q06How would you design authorization when users can have both roles and resource-level permissions?
First 30 seconds
I'd combine RBAC for coarse capabilities with ReBAC/resource ACLs for instance-level checks—evaluate deny-by-default in one policy layer the API always calls.
Model answer
  1. RBAC: roles like admin, billing, viewer mapped to permissions (invoice:read).
  2. ReBAC/ACL: relationships such as user U is editor of document D; check on that resource id.
  3. Centralize Authorize(action, resource) used by FastAPI dependencies—controllers never ad-hoc if-else forever.
  4. Support role grant at tenant scope plus per-resource shares; explicit deny if needed.
  5. Cache permission decisions carefully with invalidation on membership changes.
  6. Audit who granted what; prefer policy-as-data (CASL, Oso, Cedar, OpenFGA) over scattered checks.
Code / ops
python
def authorize(user, action: str, resource) -> None:
    if rbac.allows(user.roles, action):
        return
    if rebac.allows(user.id, action, resource):
        return
    raise HTTPException(403)
Nest / Node: Nest guards + CASL PoliciesGuard pattern; load abilities once per request in an interceptor.
Say it out loud
Say it spoken

Roles cover broad capabilities; relationships cover 'can edit this record'. One authorize() entry point on every mutation keeps FastAPI handlers honest and testable.

Traps / weak answers
  • Only checking roles and forgetting shared documents outside the role.
  • Embedding authorization only in the UI menus.
Follow-ups
  • How do you authorize list endpoints without N+1 permission queries?
  • How would OpenFGA/Zanzibar-style graphs help here?
d11-q07How would you securely handle secrets for AWS credentials, database passwords, and third-party API keys?
First 30 seconds
Secrets live in AWS Secrets Manager or SSM Parameter Store, injected at runtime via IAM roles—not baked into images or git. Prefer role assumption over long-lived access keys.
Model answer
  1. EC2/ECS/Lambda task roles with least privilege; avoid static AWS keys on servers.
  2. DB passwords and API keys in Secrets Manager; rotate on a schedule; app refreshes cache on rotation.
  3. Inject via env from task definition secrets, or fetch at startup with short in-memory cache.
  4. Separate secrets per environment; deny prod secret IAM to non-prod roles.
  5. Encrypt at rest (KMS CMKs); audit GetSecretValue via CloudTrail.
  6. Locally: developer .env gitignored or 1Password/direnv—never commit.
Code / ops
text
# ECS secrets example (conceptual)
# "secrets": [{"name": "DATABASE_URL", "valueFrom": "arn:aws:secretsmanager:..."}]
Nest / Node: Nest ConfigModule should read already-injected env; a SecretsManager loader can refresh without restart if you design for it.
Say it out loud
Say it spoken

IAM roles beat access keys; Secrets Manager beats .env in git. Least privilege, rotation, and CloudTrail on secret reads are the baseline.

Traps / weak answers
  • Long-lived AWS keys in environment variables committed to the repo.
  • One shared prod secret readable by every engineer and every service.
Follow-ups
  • How do you rotate a DB password with zero downtime?
  • When is SSM Parameter Store enough vs Secrets Manager?

d11-q08A secret is accidentally committed to source control. What actions should follow?
First 30 seconds
Treat it as compromised immediately: rotate/revoke first, then remove from git history, then audit usage. .gitignore alone is not remediation.
Model answer
  1. Revoke/rotate the secret in the provider (AWS key deactivate, DB password change, API key regenerate) before or while cleaning git.
  2. Purge from git history (BFG/git filter-repo) and force-protect main; invalidate caches/mirrors/forks.
  3. Scan CloudTrail/provider logs for unauthorized use during the exposure window.
  4. Redeploy services with the new secret; confirm old secret fails.
  5. Add pre-commit secret scanning (gitleaks) and CI blockers; educate the author without blame theater.
  6. Incident write-up: timeline, blast radius, preventive controls.
Code / ops
bash
gitleaks detect -v
# rotate AWS key via IAM
# git filter-repo --path .env --invert-paths
Say it out loud
Say it spoken

Rotate first—assume the secret is public. Then scrub history, audit access, redeploy, and add scanning so it can't happen silently again.

Traps / weak answers
  • Deleting the file in a new commit but leaving history intact with the secret.
  • Waiting to rotate until after a long history rewrite.
Follow-ups
  • What if the secret was a shared production DB credential?
  • How do you handle secrets in container image layers?
d11-q09How would you protect a webhook endpoint from spoofed or replayed requests?
First 30 seconds
Verify an HMAC signature over the raw body with a shared secret, enforce a timestamp window, and dedupe event IDs so replays fail closed.
Model answer
  1. Provider shares a signing secret; compute HMAC-SHA256 over raw body (or signed payload string) and compare with constant-time equals.
  2. Include timestamp (and optional nonce) in the signed content; reject if skew > 5 minutes.
  3. Store processed event_id for idempotency; duplicate deliveries become no-ops.
  4. Use a dedicated FastAPI route that reads raw body before JSON parse so signatures match.
  5. TLS only; optionally restrict source IPs if the vendor publishes them (defense in depth, not sole control).
  6. Rotate webhook secrets with dual-secret acceptance during cutover.
Code / ops
python
import hmac, hashlib, time

def verify(sig: str, body: bytes, ts: int, secret: bytes):
    if abs(time.time() - ts) > 300:
        raise HTTPException(401)
    expect = hmac.new(secret, body, hashlib.sha256).hexdigest()
    if not hmac.compare_digest(expect, sig):
        raise HTTPException(401)
Nest / Node: Nest: raw-body middleware for the webhook route; guard performs HMAC verify before the controller.
Say it out loud
Say it spoken

Webhooks need HMAC over the raw body, a tight timestamp window, and event-id dedupe. Without that, anyone who can POST your URL can forge events.

Traps / weak answers
  • Verifying against JSON.dumps(parsed) instead of the raw bytes (canonicalization mismatch or bypass).
  • Accepting any request from the internet with a shared guessable path.
Follow-ups
  • How do Stripe/GitHub signature schemes differ from a custom HMAC?
  • How do you rotate the webhook secret without downtime?
d11-q10How would you securely serve private images or documents stored in S3?
First 30 seconds
Keep the bucket private. Authorize in the app, then issue a short-lived presigned URL (or stream via the app/CloudFront signed URLs) scoped to that object.
Model answer
  1. Block public access on the bucket; encrypt with SSE-S3/SSE-KMS.
  2. FastAPI checks authz/tenant ownership of the object metadata in DB.
  3. Generate presigned GET with 60–300s expiry and minimal permissions; return URL or 302.
  4. For browsers at scale: CloudFront with signed URLs/cookies and Origin Access Control to S3.
  5. Never proxy large files through the API unless required for watermarking/audit—presign is cheaper.
  6. Audit downloads for sensitive docs; use separate prefixes per tenant; virus-scan uploads on ingest.
Code / ops
python
url = s3.generate_presigned_url(
    "get_object",
    Params={"Bucket": bucket, "Key": key},
    ExpiresIn=120,
)
Nest / Node: Nest: same pattern with AWS SDK v3 getSignedUrl; keep credentials on the server role only.
Say it out loud
Say it spoken

Private bucket, authorize in FastAPI, then short-lived presigned GET—or CloudFront signed URLs at scale. No public-read ACLs on customer documents.

Traps / weak answers
  • Public-read bucket 'because the app needs to show images'.
  • Presigned URLs with multi-day expiry posted into logs or emails.
Follow-ups
  • How do you allow upload safely (presigned PUT) without letting users overwrite others' keys?
  • When do you choose app-streaming vs presigning?

03  Self-check

Best default for API access tokens in a browser SPA + FastAPI backend?
Minimize blast radius of theft with short access TTL and rotating refresh tokens you can revoke server-side.
How should tenant_id be chosen for a query?
Never trust the client for tenancy. Derive tenant from auth context and apply defense-in-depth filters.
A webhook arrives without a valid HMAC. What do you do?
Authenticity and replay protection come from HMAC + timestamp/nonce checks before any side effects.
First action after a secret is committed to git?
Assume compromise. Rotation first; gitignore does not unpublish a leaked credential.
