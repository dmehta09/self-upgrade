API Design & Backend Architecture

API design questions test whether you protect correctness under retries, scale reads without OFFSET tax, and keep controllers thin. Interviewers listen for idempotency keys, cursor pagination, async jobs for long work, and consistent error contracts. Seniors separate validation, business, dependency, and unexpected failures so clients and on-call can act differently.

01  Decision cheat strip

Idempotency-KeyClient-supplied key + server unique constraint for safe POST retries
Long work202 + job id + poll/webhook — never hold HTTP for minutes
Cursor > offsetKeyset/cursor for large/stable pages; offset drifts and gets slow
Error envelopeStable code, message, details, correlation_id across FastAPI/Nest
Thin controllersHTTP in, DTO validation, call service/use-case; no SQL in routes
Sync vs asyncSync only what the user must know before response; else queue

d04-q01How would you design an idempotent create-order API?
First 30 seconds
Clients will retry — so create-order needs an Idempotency-Key scoped to the intent, durable dedupe, and a deterministic response on replay. I'll sketch header, unique constraint, request hash, and state machine before talking about Kafka or microservices.
Model answer
  1. Require Idempotency-Key header (UUID from client) on POST /orders.
  2. Begin transaction: insert into idempotency_keys(key, request_hash, status) with UNIQUE(key).
  3. If key exists with same hash, return the stored order response (200/201 as originally).
  4. If key exists with different hash, return 409 conflict.
  5. Create order row + reserve inventory in the same transaction or with compensating workflow.
  6. Call payment with the same idempotency key; keep order pending until paid if needed.
  7. Return 201 with order id and Location; persist response body for replays.
  8. Expire keys after a retention window (e.g. 24–72h) with care for late retries.
Code / ops
python
from fastapi import FastAPI, Header, HTTPException, Response
from pydantic import BaseModel

app = FastAPI()

class OrderIn(BaseModel):
    sku: str
    qty: int

@app.post("/orders", status_code=201)
async def create_order(body: OrderIn, response: Response, idempotency_key: str = Header(...)):
    row = await repo.get_idempotency(idempotency_key)
    if row:
        if row.hash != body.model_dump_json():
            raise HTTPException(409, detail="Idempotency key reuse with different body")
        response.status_code = row.status_code
        return row.body
    order = await repo.create_order(body, idempotency_key)
    return order
Nest / Node: Nest: IdempotencyInterceptor reads header, uses a repository with UNIQUE constraint; controllers stay free of dedupe logic.
Say it out loud
Say it spoken

Idempotent create-order is a durable key plus unique constraint, not hope. Same key and body returns the same order; same key different body is 409; payments reuse the key so retries don't double-charge.

Traps / weak answers
  • Generating the idempotency key on the server per attempt
  • Deduping only in Redis without considering eviction before retry window ends
  • Returning 500 on replay instead of the original 201 body
Follow-ups
  • How do you handle partial failure after the order row inserts but before the response is stored?
  • Should GET /orders/{id} also be the recovery path for clients that lost the response?
d04-q02An API operation can take 20 minutes. Would you keep the HTTP request open? How would you design it?
First 30 seconds
I would not keep HTTP open for 20 minutes — ALB, nginx, and clients will time out. Accept the work asynchronously: 202, job id, status endpoint, and optional webhook or WebSocket for completion.
Model answer
  1. POST /reports returns 202 Accepted with { job_id, status_url } immediately after durable enqueue.
  2. Persist job record (queued/running/succeeded/failed) before ACK to the queue when possible.
  3. Workers process with heartbeat/lease so crashed workers redeliver safely (idempotent job handler).
  4. GET /jobs/{id} returns status, progress, error, and result location when done.
  5. Optional webhook/callback URL or subscribe channel for completion.
  6. Align timeouts: request path milliseconds; workers free to run 20 minutes with their own deadlines.
  7. Authorize status reads so users only see their jobs.
  8. Provide cancel if business allows; document retention of results.
Diagram
flowchart LR
  Client -->|POST| API
  API -->|202_job_id| Client
  API --> Queue
  Queue --> Worker
  Worker --> Store
  Client -->|GET_status| API
  API --> Store
Code / ops
python
from fastapi import FastAPI, status
from pydantic import BaseModel
import uuid

app = FastAPI()

class ReportReq(BaseModel):
    from_date: str
    to_date: str

@app.post("/reports", status_code=status.HTTP_202_ACCEPTED)
async def start_report(body: ReportReq):
    job_id = str(uuid.uuid4())
    await jobs.insert(job_id, body, state="queued")
    await queue.enqueue("build_report", job_id)
    return {"job_id": job_id, "status_url": f"/jobs/{job_id}"}

@app.get("/jobs/{job_id}")
async def job_status(job_id: str):
    return await jobs.get(job_id)
Nest / Node: Nest + Bull/BullMQ: controller enqueues, processor updates job entity; gateway timeouts never see the 20-minute work.
Say it out loud
Say it spoken

Twenty minutes does not belong on an open HTTP socket. I accept with 202, process in a worker, and let the client poll or get a webhook — proxies won't punish us with 504s.

Traps / weak answers
  • Raising every proxy timeout to 30 minutes
  • Returning 200 before the job is durably queued
  • No authz on job status endpoints
Follow-ups
  • Exactly-once vs at-least-once: how does the worker stay safe?
  • How do you expire or clean up large report artifacts?
d04-q03How would you design an asynchronous job-submission API with job status tracking?
First 30 seconds
Same spine as long operations: validated submit, durable job record, queue, worker updates, status API with clear terminal states. I'll also cover errors, retries, and idempotent submission so double-clicks don't spawn two jobs.
Model answer
  1. POST /jobs with payload schema validation; support Idempotency-Key for submit.
  2. States: queued → running → succeeded | failed | canceled (explicit enum).
  3. Store created_at, started_at, finished_at, progress, error_code, result_ref.
  4. Workers update state with optimistic locking / lease to avoid double runners.
  5. GET list with filters (mine, status); GET by id; optional SSE/websocket for progress.
  6. Dead-letter after N failures; surface last_error to operators.
  7. Metrics: queue depth, time-to-start, time-to-finish, failure rate.
  8. OpenAPI documents status machine and polling recommendations (intervals, backoff).
Nest / Node: Mirror with Bull job ids mapped to your DB row if you need richer queryable status than the queue UI provides.
Say it out loud
Say it spoken

A job API is a state machine with a queue behind it. Clients get an id immediately, poll a boring status resource, and we make submission idempotent so retries don't duplicate work.

Traps / weak answers
  • Using only in-memory job maps on one instance
  • Ambiguous statuses like 'done' without success/failure
  • Letting clients poll every 50ms without guidance
Follow-ups
  • How do you design cursor pagination for listing millions of historical jobs?
  • When do you choose webhooks over polling?
d04-q04How would you design pagination for a table containing hundreds of millions of rows?
First 30 seconds
I avoid deep OFFSET. Keyset/cursor pagination on a stable indexed sort (e.g. created_at, id), bounded page size, and no COUNT(*) on every request. Total counts, if needed, are estimated or async.
Model answer
  1. Choose a deterministic sort key: (created_at DESC, id DESC) with a matching index.
  2. API: GET /items?limit=50&cursor=opaque_token encoding the last key seen.
  3. Query: WHERE (created_at, id) < (:ts, :id) ORDER BY created_at DESC, id DESC LIMIT 51.
  4. If 51 rows, return next_cursor from row 50; do not scan the rest of the table.
  5. Keep cursors opaque/signed to prevent clients inventing filters that break indexes.
  6. Avoid exact total count on hot paths; use estimated counts or omit.
  7. For jumps to arbitrary page numbers, accept they are expensive or unsupported at this scale.
  8. Monitor p95 of list queries; add covering indexes for common filters + sort.
Code / ops
text
-- Keyset page
SELECT id, created_at, ...
FROM orders
WHERE (created_at, id) < ($1, $2)
ORDER BY created_at DESC, id DESC
LIMIT 51;
Say it out loud
Say it spoken

At hundreds of millions of rows I paginate with keyset cursors on an indexed sort key, not OFFSET. Clients get a next cursor; I don't COUNT the galaxy on every page view.

Traps / weak answers
  • OFFSET/LIMIT deep paging in production
  • SELECT COUNT(*) FROM huge_table on every list call
  • Nullable sort columns that make keyset comparisons wrong
Follow-ups
  • How do you paginate with additional filters (tenant_id, status) safely?
  • What happens when new rows insert at the top while the user pages?
d04-q05When would you choose cursor pagination over offset pagination?
First 30 seconds
Cursor when the dataset is large, pages are deep, or results must stay stable under inserts/deletes. Offset is fine for tiny admin tables or true 'page 7 of 10' UI on small collections.
Model answer
  1. Choose cursor/keyset for feeds, audit logs, orders, any high-cardinality table.
  2. Offset causes drifting pages when rows insert/delete above the current page.
  3. Offset cost grows with page depth; cursor seeks the index.
  4. Offset is OK for low-cardinality admin UIs with total pages under a few hundred.
  5. Hybrid: offset for page 1–3 UX, but most APIs should still expose cursors.
  6. Cursors struggle with arbitrary 'jump to page 50' — product should prefer 'load more'/'next'.
  7. Document that cursors may expire if encoding includes filters/versions.
  8. Be honest with PM: infinite scroll maps to cursors; numbered pages at scale do not.
Say it out loud
Say it spoken

Cursors for scale and stability; offset for small, static lists. If users can page into the middle of millions of rows, offset is already the wrong design.

Traps / weak answers
  • Defaulting to offset because ORMs make it easy
  • Exposing raw SQL offsets in public APIs
  • Promising total page counts on unbounded datasets
Follow-ups
  • How do bidirectional cursors (prev/next) work with keyset pagination?
  • When would search-after in Elasticsearch mirror this choice?
d04-q06How would you design consistent error responses across a large FastAPI/NestJS codebase?
First 30 seconds
One error envelope and centralized handlers — not ad-hoc JSON per route. Every error carries a stable machine code, human message, optional details, HTTP status, and correlation id so clients and support share a vocabulary.
Model answer
  1. Define a schema: { error: { code, message, details?, correlation_id } }.
  2. FastAPI: exception handlers for RequestValidationError, domain errors, and catch-all.
  3. Nest: ExceptionFilter hierarchy mapping domain exceptions to HTTP.
  4. Map codes to statuses once (VALIDATION_ERROR→400, NOT_FOUND→404, CONFLICT→409, DEPENDENCY→502/503).
  5. Never leak stack traces or SQL to clients; log them server-side with the same correlation_id.
  6. OpenAPI components.document the error schema; generate clients that understand codes.
  7. Lint/code review: ban bare HTTPException(detail=str(e)) without a code.
  8. Include correlation_id from middleware (X-Request-Id) in every error body.
Code / ops
python
from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse

app = FastAPI()

class AppError(Exception):
    def __init__(self, code: str, message: str, status_code: int = 400):
        self.code, self.message, self.status_code = code, message, status_code

@app.exception_handler(AppError)
async def app_error_handler(request: Request, exc: AppError):
    cid = request.headers.get("x-request-id")
    return JSONResponse(
        status_code=exc.status_code,
        content={"error": {"code": exc.code, "message": exc.message, "correlation_id": cid}},
    )
Nest / Node: Implement a BaseExceptionFilter and domain exceptions (NotFoundError, ConflictError); avoid returning res.status().json({}) ad hoc in each controller.
Say it out loud
Say it spoken

Consistency comes from a single envelope and centralized handlers. Routes throw typed domain errors; the framework edge turns them into the same JSON shape with a correlation id.

Traps / weak answers
  • Different error shapes per microservice with no translation at the BFF
  • Returning plain strings as bodies
  • Exposing internal exception class names as the public contract
Follow-ups
  • How do you version error codes when messages change?
  • Where should localization of message happen — client or server?
d04-q07How would you separate validation errors, business errors, dependency errors, and unexpected errors?
First 30 seconds
Four classes, four client behaviors: 422/400 fix the request, 409/422 business rule, 502/503 retry or degrade, 500 file a bug. I'll map each to exception types, logs, and metrics so on-call knows whether to page the vendor or us.
Model answer
  1. Validation: schema/input problems → 400/422, code VALIDATION_ERROR, details as field list; no pager.
  2. Business: conflict, insufficient funds, state machine violation → 409/422 with stable business codes.
  3. Dependency: timeouts, 5xx from vendors → 502/503, code DEPENDENCY_UNAVAILABLE, maybe Retry-After.
  4. Unexpected: unhandled bugs → 500, generic message, full stack in logs/Sentry with correlation_id.
  5. Implement distinct exception types so handlers don't guess from strings.
  6. Metrics labeled by class; alert on unexpected and dependency, not on validation spikes from bad bots.
  7. Do not convert dependency failures into 500 — that misleads operators.
  8. Document the taxonomy in the API guidelines for all teams.
Code / ops
python
class ValidationAppError(AppError): ...
class BusinessAppError(AppError): ...
class DependencyAppError(AppError): ...
# unexpected: bare Exception → 500 handler
Nest / Node: HttpException vs custom BusinessException vs UpstreamException filters; map Axios errors to DependencyAppError in a single anti-corruption layer.
Say it out loud
Say it spoken

Validation is the client's fault, business rules are domain conflicts, dependencies are someone else's SLO, and unexpected is ours. Separating them in types and status codes makes both UX and paging correct.

Traps / weak answers
  • Returning 500 for 'sku out of stock'
  • Returning 400 for payment provider downtime
  • Logging validation errors at error level and waking on-call
Follow-ups
  • Should business rule violations be 400 or 409? How do you decide?
  • How do multi-cause validation errors appear in the details array?
d04-q08One endpoint is generating excessive database traffic. How would you redesign it?
First 30 seconds
First measure: which queries, QPS, and whether it's N+1, missing cache, chatty pagination, or over-fetching. Then redesign with fewer round-trips — join/batch, cache, denormalize read models, or split the chatty UI need from the write path.
Model answer
  1. Trace the endpoint: count queries per request, rows read, and p95 DB time.
  2. Fix N+1 with joinedload/selectinload or a single SQL join/aggregation.
  3. Return only needed fields; stop SELECT * for list endpoints.
  4. Add read-through cache (Redis) for hot keys with TTL and invalidation on writes.
  5. Introduce a read model / materialized view if the endpoint aggregates many tables.
  6. Batch APIs: allow clients to fetch many ids in one call instead of loops.
  7. Rate-limit abusive patterns; add pagination cursor limits.
  8. If fan-out is inherent, move to async precompute and serve snapshot.
Code / ops
python
# Before: N+1
# for order in orders: await get_customer(order.customer_id)
# After: batch
customers = await repo.get_customers({o.customer_id for o in orders})
Nest / Node: TypeORM relations default can N+1 — use QueryBuilder joins or DataLoader-style batching in Nest resolvers/services.
Say it out loud
Say it spoken

I don't 'add indexes' blindly — I count queries per request. Usually it's N+1 or a hot list without cache; I batch, cache, or precompute a read model so one user action isn't a hundred SQL round-trips.

Traps / weak answers
  • Caching before understanding write invalidation
  • Adding replicas without reducing query count
  • Returning unbounded lists that force full table reads
Follow-ups
  • How do you safely invalidate cache when the write path is a different service?
  • When is CQRS worth it for this endpoint?
d04-q09How would you structure a large FastAPI or NestJS application so controllers do not contain business logic?
First 30 seconds
Controllers are HTTP adapters: parse, authz, call an application service, map results/errors. Business rules live in services/use-cases/domain, with repositories at the edge — same idea in FastAPI modules and Nest providers.
Model answer
  1. Layers: transport (routers/controllers) → application/use-case services → domain → infrastructure (DB, HTTP clients).
  2. FastAPI routers depend on service classes via Depends; no raw SQL in route functions.
  3. Nest: controllers inject services; services inject repositories — avoid logic in controllers.
  4. DTOs/schemas at the edge; domain entities/value objects inward.
  5. Transactions orchestrated in application services, not in controllers.
  6. Shared exception types bubble to centralized handlers.
  7. Package by module/bounded context (orders, billing) rather than one giant utils.
  8. Test use-cases without TestClient/HTTP when logic is heavy.
Code / ops
python
# FastAPI sketch
@router.post("/orders")
async def create(body: OrderIn, svc: OrderService = Depends(get_order_service)):
    return await svc.create(body)
Nest / Node: Nest naturally pushes logic to injectable services — keep controllers to one-liners that call this.orders.create(dto) and map to HTTP codes via filters.
Say it out loud
Say it spoken

If a route function knows SQL and discount rules, the structure is wrong. Controllers adapt HTTP; services own business decisions; repositories speak to the database — FastAPI Depends and Nest DI both support that if we use them with discipline.

Traps / weak answers
  • Anemic 'service' that is just a pass-through while logic stays in the controller
  • Circular imports from dumping everything in one package
  • Reaching into other modules' repositories bypassing their services
Follow-ups
  • How do you draw boundaries between modules in a modular monolith?
  • Where do you put authorization checks — controller, service, or both?
d04-q10How would you decide what belongs in the synchronous request path versus asynchronous processing?
First 30 seconds
Sync only what the user must know before the response to make a correct next decision. Everything else — emails, analytics, slow reports, non-critical enrichment — goes async with clear eventual consistency and failure handling.
Model answer
  1. Ask: does the client need this result to continue safely? If yes, sync (with tight timeouts).
  2. Money/inventory invariants that must hold before 201 → sync transaction or explicit pending state.
  3. Side effects user can learn later (email, notifications, search indexing) → queue.
  4. Work longer than ~1–2s user budget → async job API.
  5. Fan-out to many deps → often async or partial sync with degraded fields.
  6. Document consistency: read-your-writes vs eventual for each feature.
  7. Provide compensation/retry for async failures; surface dead letters.
  8. Measure: if sync path p95 threatens SLO, reclassify work as async.
Nest / Node: Nest: await critical service calls in the request; @InjectQueue for mail/indexing. Don't await five non-critical providers in the controller.
Say it out loud
Say it spoken

Synchronous means the user can't proceed without it. Emails, indexes, and 20-minute reports are async. I keep the request path short, durable where it matters, and honest about eventual consistency.

Traps / weak answers
  • Awaiting Slack notifications on the checkout path
  • Returning 201 before the durable write commits
  • Async everything including authz checks
Follow-ups
  • How do you explain eventual consistency to product when search lags orders by seconds?
  • What belongs in an outbox pattern versus a simple queue publish after commit?

03  Self-check

A create-order POST may be retried by the client after a timeout. What do you require?
Retries need a stable key so the server returns the original result instead of creating duplicates.
Why avoid OFFSET 10_000_000 on a huge table?
Large OFFSET is O(offset) work on typical plans; keyset/cursor seeks by indexed columns.
A report takes 20 minutes. Best HTTP shape?
Proxies and clients time out long requests; async job APIs are the standard pattern.
Where should business rules live in a large FastAPI/Nest app?
Controllers handle transport; domain/application services own rules so they stay testable and reusable.
