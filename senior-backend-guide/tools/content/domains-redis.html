Redis, Caching & Rate Limiting

Redis is for hot paths: cache-aside, counters, locks, and rate limits — not a second source of truth. Design for stampede, hot keys, and TTL freshness, and always plan what happens when Redis dies so PostgreSQL does not avalanche. Atomicity comes from single-command ops (INCR/INCRBY) or Lua for conditional multi-step RMW; bare MULTI/EXEC alone is not peer to Lua for check-and-set (use WATCH+MULTI or Lua) — never get-modify-set in application code.

TTLMatch freshness SLO; jitter to avoid sync expiry
Rate limitSliding window ZSET or INCR+EXPIRE

d07-q01When should an API use Redis instead of querying PostgreSQL directly?
First 30 seconds
When the same read is hot, tolerates slight staleness, and DB cost or latency dominates — not for every query by default.
Model answer
  1. Clarify the job: Redis earns its place when the same key is read at high QPS, the payload is cheap to serialize, and the business tolerates TTL-bounded staleness — not because 'we should cache everything.'
  2. Hypothesis before adding Redis: p95/p99 DB time, rows scanned, and estimated hit rate on stable keys (session, product config, permission bitsets, feed fragments) justify the ops cost.
  3. Evidence path: measure origin QPS and latency with and without cache on a canary; only keep Redis when hit rate and p95 delta clear a documented bar.
  4. Tradeoff vs read replicas: replicas help complex/ad-hoc SQL and stronger freshness; Redis wins on microsecond hot-path lookups and ephemeral coordination — because replicas still pay SQL planning and connection cost.
  5. Failure mode: caching unique one-off queries or money ledgers creates low hit rate, stale balances, and a second source of truth that diverges under failover.
  6. Fix: keep PostgreSQL as system of record for durable transactional writes; use cache-aside with explicit TTL/invalidation, never dual-write critical balances only to Redis.
  7. Also use Redis where it is the right primitive: rate limits, distributed locks, short-lived idempotency keys — coordination, not durable ledger.
  8. Prevent/ops: track cache hit rate, origin QPS after rollout, and p95 latency SLO; alert when hit rate collapses or DB QPS rises as if the cache were bypassed.

d07-q02Redis goes down during peak traffic. How should the application degrade?
First 30 seconds
Fail fast on Redis with timeouts, then either serve stale/local data, skip non-critical cache, or shed load — never unbounded synchronous fallback to the DB.
Model answer
  1. Clarify: Redis unavailable is an expected failure mode, not a surprise — the question is which features fail open vs closed and how hard Postgres gets hit.
  2. Evidence first: short connect/command timeouts and a circuit breaker around Redis so request threads do not pile up waiting on a dead pool.
  3. Per-feature policy: cache reads may fail-open to DB with a concurrency cap; rate limiting and auth abuse paths usually fail-closed — because open limits during outage invite floods.
  4. Tradeoff: serving last-known-good from process-local soft state buys availability vs freshness; skipping non-critical endpoints sheds load vs trying to preserve every feature.
  5. Failure mode: uncapped synchronous DB fallback turns a Redis blip into a Postgres avalanche and a wider outage.
  6. Fix: bulkhead fallback with a semaphore, load-shed optional routes, and optionally longer L1 TTL while Redis is open-circuit.
  7. Warm carefully on recovery: controlled refill or lazy population so reconnect does not stampede both Redis and DB.
  8. Prevent/ops: alert on Redis health, breaker open rate, and DB QPS spike during fallback; rehearse degradation in game days with pass/fail on DB ceiling.

d07-q03How would you implement cache-aside for a read-heavy endpoint?
First 30 seconds
Read Redis by key; on miss load Postgres, SET with TTL, return. Invalidate or overwrite on writes. Add stampede protection for hot keys.
Model answer
  1. Clarify cache-aside: the app owns population — GET Redis; on miss load Postgres, SET with TTL, return — Postgres remains source of truth, Redis is a disposable acceleration layer.
  2. Key design: namespaced, versioned keys including tenant/id (e.g. prod:user:{id}:profile:v2) so schema changes and multi-tenant bleed cannot share a key accidentally.
  3. Read path steps: GET → hit return; miss → singleflight/lock for hot keys → DB → SET EX ttl (+ jitter) → return; negative-cache empty/not-found with a short TTL so hot 404s do not hammer the DB.
  4. Write path and consistency window: COMMIT in Postgres, then DEL or SET the key; accept a brief race where concurrent readers can refill stale data until TTL or a second invalidation — because Redis and Postgres are not one transaction.
  5. Invalidation graph: map every derived key (profile, list membership, permission bitset); forgetting secondary keys is the usual 'we invalidated but still stale' failure — tags help but can be expensive at scale.
  6. Stampede vs ordinary miss: popular keys need NX lock or in-process singleflight on miss; jitter alone is not enough when one celebrity key expires.
  7. Tradeoff vs write-through: write-through shrinks some races but couples write latency to Redis; cache-aside keeps writes on the DB critical path and accepts invalidate races with TTL as backstop.
  8. Prevent/ops: metrics for hit rate, miss latency, DB QPS on misses, null-cache hit rate, and stampede lock wait; alert when miss rate or origin QPS spikes after deploys.

Say it spoken

Cache-aside is GET, miss to Postgres, SET with TTL, and invalidate after commit — with an explicit consistency window and an invalidation graph for derived keys. I null-cache short, singleflight hot misses, and watch hit rate plus origin QPS so a broken invalidation shows up as metrics, not only as user reports.

Traps / weak answers
  • Caching without TTL — missed invalidations become permanent wrong answers
  • Updating DB but forgetting invalidation — consistency window becomes unbounded until someone notices
  • Caching personalized responses under a shared key — cross-tenant data leaks and wrong UX
  • No null-cache on hot not-found — repeated misses amplify DB load on the worst keys

d07-q04How would you handle stale cache data after a PostgreSQL update?
First 30 seconds
Invalidate or overwrite the cache key in the same request after a successful DB commit — and accept TTL as a backstop for missed invalidations.
Model answer
  1. Clarify: after a successful Postgres COMMIT, the cache is wrong until you DEL/SET or TTL expires — treat that as a designed window, not an accident.
  2. Preferred fix: in the request (or post-commit hook), DELETE affected keys or SET the fresh value only after commit succeeds — invalidating before commit leaves holes on rollback.
  3. Evidence of completeness: maintain an invalidation graph or key inventory for the entity (detail, lists, aggregates); hierarchical tags help but add write amplification.
  4. Tradeoff: short TTL heals missed deletes quickly vs higher miss rate; long TTL needs reliable invalidation or you ship stale reads for hours.
  5. Replica failure mode: invalidate then read-your-writes from a lagging replica can refill the cache with old data — version-stamp payloads or read primary after write.
  6. For schema changes, bump key version (v2) so old payloads cannot be deserialized as new shape.
  7. When freshness is a hard SLO, skip cache on that path rather than pretending TTL equals strong consistency.
  8. Prevent/ops: measure stale-read complaints, post-write cache hit of old version, and invalidation error rate; alert when DEL fails or refill-from-replica races spike.

Say it spoken

I commit Postgres first, then invalidate or overwrite every key in the entity's invalidation graph, with TTL as the safety net for races and missed deletes. Replica lag can refill stale values, so I version payloads or read primary after write when freshness matters. Metrics on stale reads and failed DELs catch silent invalidation bugs.

  • Infinite TTL with best-effort invalidation only — one missed DEL becomes permanent staleness
  • Forgetting secondary keys derived from the entity — detail is fresh while list/search stays stale

d07-q05What is a cache stampede scenario and how would you prevent it?
First 30 seconds
Stampede is many requests missing the same key at once and all hitting the DB. Prevent with singleflight, a lock, probabilistic early refresh, or serving stale while one refreshes.
Model answer
  1. Clarify stampede: hot key TTL expires or cold start → N concurrent misses → N identical origin queries — a thundering herd on Postgres, not Redis CPU saturation alone.
  2. Distinguish hot-key: a hot key that always hits still hammers one Redis shard/CPU; stampede is synchronized miss → origin overload. Fixes differ (L1/shard vs singleflight/lock/SWR).
  3. In-process singleflight: coalesce loaders on one instance; losers wait on the same future — cheap but insufficient across many app instances.
  4. Distributed lock: SET lock:{key} NX EX ; winner loads DB and fills cache; waiters retry GET with a bounded waiter timeout — lock TTL must outlive worst refresh but expire if the winner dies (no deadlock).
  5. Stale-while-revalidate: keep soft TTL / stale payload; serve stale to waiters while one refresher runs — availability over freshness when the business allows.
  6. Tradeoff: probabilistic early refresh reduces synchronized expiry vs extra origin load; jitter helps many keys but will not save one celebrity key.
  7. Failure modes: lock without TTL (deadlock), waiters with infinite retry (latency storm), treating stampede as 'add Redis nodes' (miss still hits DB).
  8. Prevent/ops: monitor miss spikes, lock acquire fail rate, waiter timeouts, and origin QPS on expiry boundaries; game-day expire a hot key and verify single-origin refresh.
Diagram
flowchart TD
  Miss[N concurrent GET miss] --> Lock{SET lock NX EX}
  Lock -->|winner| Load[DB fetch + SET cache]
  Lock -->|losers| Wait[waiter timeout / GET retry]
  Wait -->|SWR| Stale[serve soft-TTL stale]
  Load --> Unlock[DEL lock]

Code / ops
python
ok = redis.set(f'lock:{key}', '1', nx=True, ex=5)  # lock TTL > refresh p99

        val = db.fetch()
        redis.setex(key, ttl, val)
    finally:

    for _ in range(20):

        val = redis.get(key)
        if val is not None:
            return val
    return serve_stale_or_db_with_shed()  # SWR / degrade

Say it out loud
Say it spoken

Stampede is a synchronized miss herd on the origin; hot-key is sustained traffic on one Redis slot — different problems. I use singleflight plus an NX lock with TTL, bounded waiter timeout, and stale-while-revalidate when freshness allows. Lock TTL and waiter budgets are part of the design, and I watch miss spikes at expiry.

Traps / weak answers
  • Only jittering TTL but not locking the hottest key — celebrity keys still stampede on expiry
  • Lock without TTL — refresher crash deadlocks the key until manual intervention
  • Retry loops without backoff/waiter timeout while lock held — turns stampede into a latency storm
  • Confusing stampede with hot-key CPU saturation — scaling Redis nodes does not fix synchronized DB misses

d07-q06A popular Redis key becomes a hot key. How would you handle it?
First 30 seconds
A hot key saturates one shard/CPU. I'd add a local in-process cache, or split the keyspace across N sibling keys and aggregate.
Model answer
  1. Clarify: a hot key concentrates GET/INCR traffic on one cluster hash slot/CPU — horizontal shard count does not help if one key owns one slot.
  2. Evidence: Redis hot-key metrics, proxy stats, elevated latency on one node, and CPU skew across the cluster — confirm before redesigning keys.
  3. First mitigation: L1 in-process cache with short TTL on app instances to absorb read QPS without changing the data model.
  4. Shard the keyspace: replicate a read-mostly blob onto key:0..N-1 and pick randomly; for counters, INCR a random shard and SUM on read (approximate or exact merge tradeoff).
  5. Tradeoff: L1 is simple and loses cross-instance coherence quickly; sharding increases write fan-out and read merge cost vs single-key simplicity.
  6. Failure modes: hash tags that pin many hot entities onto one slot; storing a huge value that amplifies network CPU; global locks on every hot-key read.
  7. Fix size/shape: compress, split fields, or move rarely changing config to local files/feature flags when Redis is the wrong store.
  8. Prevent/ops: dashboards for per-node CPU and hot-key reports; alert on slot imbalance; revisit key design when a celebrity entity appears in top-N.

I confirm with hot-key and per-node CPU metrics, then absorb reads in-process or fan out to sibling keys with an explicit merge story. Hash tags and oversized values are common ways we accidentally create the hotspot.

Traps / weak answers
  • Adding Redis nodes without splitting the key — the hot slot moves hosts but stays hot
  • Hash tags that force many hot keys onto one slot — Cluster mode concentrates load by design of the tag
  • Global locks on the hot key for every read — serializes the hottest path and worsens latency

d07-q07How would you choose TTLs for data with different freshness requirements?
First 30 seconds
TTL follows the business freshness SLO: seconds for volatile counters, minutes for profiles, hours for rare config — always with jitter and an invalidation story for critical updates.
Model answer
  1. Clarify: TTL is a freshness SLA expressed as time — classify data by how wrong a stale read can be before it is a bug.
  2. Buckets: strict freshness (skip cache or seconds + hard invalidate), eventual (minutes), near-static (hours/days); document per key-family policy.
  3. Set TTL slightly above typical update interval; use explicit DEL on writes when the SLO is tighter than TTL alone can guarantee.
  4. Always add random jitter (±10–20%) so millions of keys do not expire in the same second and stampede the origin.
  5. Negative caching: short TTL for misses/404s — long enough to protect DB, short enough that creates appear quickly.
  6. Tradeoff vs eviction policy: volatile-LRU still needs TTLs for correctness; allkeys-lru without TTL turns memory pressure into random staleness deletion without a freshness story.
  7. Failure mode: one global TTL or eternal keys for changing data — either constant stampede risk or unbounded staleness.
  8. Prevent/ops: review TTLs against hit rate, stale-read rate, and miss spikes at expiry; alert when a key family drifts from its documented freshness SLO.
Code / ops
python
ttl = base_ttl + random.randint(0, jitter)
# negative cache example
redis.setex(key, 30 if value is None else base_ttl + random.randint(0, jitter), serialize(value))
Say it out loud
Say it spoken

TTL is a freshness SLA, not a random constant: short plus invalidate for volatile data, longer for static, jitter everywhere, and short negative cache for hot misses. Eviction policy is memory management, not a substitute for that SLA. I revisit TTLs when hit rate or stale-read metrics say the policy drifted.

Traps / weak answers
  • One global TTL for all keys — over-fresh expensive paths and under-fresh critical paths at once
  • No jitter on millions of keys with the same expiry — synchronized stampede every TTL boundary
  • Eternal keys for data that does change — invalidation bugs become permanent production incidents

d07-q08How would you design a distributed per-user and per-IP rate limiter using Redis?
First 30 seconds
I'd use Redis atomic counters or a sliding-window ZSET, with separate keys for userId and IP, evaluated in the gateway/middleware before expensive work.
Model answer
  1. Clarify goal: enforce per-user and per-IP budgets early (gateway/middleware) before expensive work, with atomic Redis ops so multi-instance counts do not race.
  2. Fixed window: INCR key; on first INCR set EXPIRE windowSeconds; reject when count > limit — simple, but bursty at window boundaries.
  3. Sliding window: ZADD timestamps, ZREMRANGEBYSCORE old, ZCARD — smoother; wrap in Lua so the multi-step update is atomic across clients.
  4. Keys and policy: rl:user:{id}:{bucket} and rl:ip:{ip}:{bucket}; evaluate both (AND) because IP-only fails under NAT and user-only fails pre-auth.
  5. Tradeoff: fixed window is cheap vs sliding accuracy; token bucket via Lua gives smoother refill when UX needs it.
  6. Redis-down policy: usually fail-closed on login/abuse paths — fail-open invites credential stuffing during the outage.
  7. Hot IP under attack: shard or approximate the IP key; return standard remaining/reset headers for clients.
  8. Prevent/ops: metrics for reject rate, top offenders, Redis latency on RL path, and fail-closed engagements; alert when RL Redis errors spike or reject rate collapses unexpectedly.

d07-q09Two application instances update the same Redis-based counter concurrently. How would you make the operation safe?
First 30 seconds
Use Redis atomic primitives — INCR/INCRBY or a Lua script — never GET, add in process, SET.
Model answer
  1. Clarify the race: GET → add in app → SET across instances loses updates; safety must live inside Redis's single-threaded command execution.
  2. Prefer INCR/INCRBY/DECR for a single counter — one round-trip, atomic, correct under concurrency without application locks.
  3. Conditional multi-step RMW (compare-and-set, multi-key invariants): use Lua EVAL so check+write runs atomically server-side — this is the peer for conditional logic, not bare MULTI/EXEC.
  4. MULTI/EXEC alone queues commands without optimistic concurrency; for check-then-act you need WATCH+MULTI (retry on conflict) or, more often, Lua — do not teach MULTI/EXEC as equivalent to Lua for conditional RMW.
  5. Tradeoff: INCR is simplest; Lua adds scripting complexity but expresses multi-key atomicity; WATCH+MULTI works but retry storms under contention are painful vs Lua.
  6. Money / audit failure mode: Redis AOF/RDB and async replication are not Postgres crash-safe ledger semantics — keep durable financial counters in Postgres and use Redis for approximate or rate metrics.
  7. Cluster caveat: multi-key Lua requires keys in the same hash slot (hash tags); otherwise the script is rejected.
  8. Prevent/ops: concurrency tests with multiple workers; monitor script errors, WRONGTYPE, and divergence vs a durable source of truth when the counter matters for billing.

d07-q10How would you prevent a cache outage from causing a database avalanche?
First 30 seconds
Treat Redis failure as expected: circuit-break, admit only a bounded number of DB fallbacks, shed non-critical traffic, and keep a small local stale cache.
Model answer
  1. Clarify avalanche: Redis down or mass expiry → uncapped miss path → Postgres saturates → cascading API failure — the outage multiplier is unbounded fallback, not Redis itself.
  2. Fail fast: timeouts + circuit breaker on Redis so the app stops waiting and enters a known degradation mode.
  3. Bulkhead: semaphore on cache-miss/DB-fallback concurrency — size from Postgres max_connections, pool size, and safe QPS headroom (e.g. admit only N% of normal miss concurrency).
  4. Shed order: drop optional/expensive list/search first, preserve auth and critical reads, serve stale L1 where safe — ordered shedding beats random 500s.
  5. Tradeoff: fail-open cache with a tight semaphore preserves partial UX vs fail-closed features that cannot be correct without Redis.
  6. Coalesce remaining misses (singleflight) during partial outages so 1000 waiters do not become 1000 identical queries.
  7. Failure mode: retry storms and unlimited fallback recreate the avalanche after you thought you fixed Redis.
  8. Prevent/ops: game-day kill Redis in staging with pass/fail = DB QPS stays under ceiling and critical SLO holds; alert on fallback rate, semaphore rejects, and origin saturation.

Say it out loud
Say it spoken

Avalanche prevention is bounded fallback: breakers, a sized semaphore, ordered load shedding, and stale serve — not 'just query Postgres.' I size the bulkhead from DB headroom, coalesce misses, and run a game-day with a clear pass/fail on DB QPS. Fallback rate and semaphore rejects are the metrics that prove the guardrails work.

Traps / weak answers
  • Silent unlimited DB fallback — converts Redis loss into a full database outage
  • Retry storms compounding load — amplify QPS exactly when Postgres has no spare capacity
  • No distinction between critical and optional reads — shed order is random and critical paths die first
  • Game-day without a DB QPS pass/fail — rehearsal that cannot fail teaches nothing
