Redis, Caching & Rate Limiting

Redis is for hot paths: cache-aside, counters, locks, and rate limits — not a second source of truth. Design for stampede, hot keys, and TTL freshness, and always plan what happens when Redis dies so PostgreSQL does not avalanche. Atomicity comes from INCR, MULTI/EXEC, or Lua — not from get-modify-set in application code.

01  Decision cheat strip

PatternCache-aside: read Redis → miss → DB → SET TTL
StampedeLock / singleflight so one refreshes
Hot keyLocal cache or shard keyspace (key:0..N)
TTLMatch freshness SLO; jitter to avoid sync expiry
Rate limitSliding window ZSET or INCR+EXPIRE
AvalancheTimeouts, bulkheads, serve stale, shed load

d07-q01When should an API use Redis instead of querying PostgreSQL directly?
First 30 seconds
When the same read is hot, tolerates slight staleness, and DB cost or latency dominates — not for every query by default.
Model answer
  1. Use Redis for high-QPS reads with stable keys (session, product config, permission bitsets, feed fragments) where TTL/staleness is acceptable.
  2. Keep PostgreSQL as source of truth for durable, transactional, strongly consistent writes and complex queries.
  3. Cache after measuring: p95 DB time, QPS, and hit-rate potential — don't cache unique one-off queries.
  4. Prefer cache-aside with explicit invalidation/TTL; avoid dual-writing critical money state only to Redis.
  5. Also use Redis for ephemeral coordination: rate limits, locks, short-lived idempotency keys.
Nest / Node: Inject a cache port in Nest providers so services don't scatter raw Redis calls.
Say it out loud
Say it spoken

Redis for hot, slightly stale reads and coordination. Postgres for truth and transactions — I cache when the hit rate and latency win are proven.

Traps / weak answers
  • Caching everything including low-hit unique keys
  • Treating Redis as the system of record for balances
  • No TTL and no invalidation plan
Follow-ups
  • What hit rate justifies the complexity?
  • When would you use read replicas instead of Redis?
d07-q02Redis goes down during peak traffic. How should the application degrade?
First 30 seconds
Fail fast on Redis with timeouts, then either serve stale/local data, skip non-critical cache, or shed load — never unbounded synchronous fallback to the DB.
Model answer
  1. Short connect/command timeouts and circuit breaker around Redis so threads don't pile up.
  2. Decide policy per feature: fail-open (skip cache, hit DB with cap) vs fail-closed (rate limiter denies / feature disables).
  3. Protect PostgreSQL with concurrency limits, cached-in-process soft state, and load shedding on non-critical endpoints.
  4. Optionally serve last-known-good from local/memory cache with longer TTL during outage.
  5. Alert on Redis health and DB QPS spike; rehearse the degradation in game days.
Nest / Node: Separate Redis modules (cache vs rate-limit) so one policy doesn't blindly apply to both.
Say it out loud
Say it spoken

Redis down: timeout fast, degrade by feature, and cap DB fallback — an uncapped fallback is an outage multiplier.

Traps / weak answers
  • Infinite retries to Redis on the request path
  • Failing open on rate limiting (abuse flood)
  • No circuit breaker → thread pool exhaustion
Follow-ups
  • Should rate limiting fail open or closed?
  • How do you warm the cache after Redis recovers?
d07-q03How would you implement cache-aside for a read-heavy endpoint?
First 30 seconds
Read Redis by key; on miss load Postgres, SET with TTL, return. Invalidate or overwrite on writes. Add stampede protection for hot keys.
Model answer
  1. Key design: versioned, namespaced keys including tenant/id (e.g. prod:user:{id}:profile:v2).
  2. Read path: GET → hit return; miss → DB → SET EX ttl → return.
  3. Write path: update DB then DEL/SET the key (invalidate or write-through); accept brief race windows consciously.
  4. Add jittered TTLs; singleflight/lock on miss for popular keys.
  5. Metrics: hit rate, miss latency, DB load on misses; negative-cache empty results carefully.
Diagram
sequenceDiagram
  Client->>API: GET
  API->>Redis: GET key
  alt hit
    Redis-->>API: value
  else miss
    API->>Postgres: SELECT
    API->>Redis: SET EX
  end
  API-->>Client: response
Code / ops
python
val = redis.get(key)
if val is None:
    val = db.fetch()
    redis.setex(key, ttl, serialize(val))
return val
Nest / Node: Serialize JSON/msgpack consistently; include schema version in the key or payload.
Say it out loud
Say it spoken

Cache-aside: GET, miss to DB, SET with TTL; invalidate on write; singleflight so misses don't herd.

Traps / weak answers
  • Caching without TTL
  • Updating DB but forgetting invalidation
  • Caching personalized responses under a shared key
Follow-ups
  • Write-through vs cache-aside trade-offs?

d07-q04How would you handle stale cache data after a PostgreSQL update?
First 30 seconds
Invalidate or overwrite the cache key in the same request after a successful DB commit — and accept TTL as a backstop for missed invalidations.
Model answer
  1. After COMMIT, DELETE the affected keys (or SET the fresh value). Prefer explicit invalidation for correctness-sensitive data.
  2. Keep TTLs short enough that missed invalidations self-heal; use key versioning when payload shape changes.
  3. For multi-key entities, maintain a key inventory or hierarchical tags (careful: tag systems can be expensive).
  4. If using replicas, beware read-your-writes: invalidate then read primary, or version stamp the payload.
  5. Measure stale-read complaints; for strong freshness, skip cache on that path.
Code / ops
python
async with db.transaction():
    await db.update(...)
await redis.delete(cache_key)  # after commit
Nest / Node: Hook invalidation in the repository/unit-of-work after commit callbacks.
Say it out loud
Say it spoken

Commit first, then invalidate or SET the new value. TTL is the safety net for races and missed deletes.

Traps / weak answers
  • Invalidating before commit (rollback leaves hole or race)
  • Infinite TTL with best-effort invalidation only
  • Forgetting secondary keys derived from the entity
Follow-ups
  • How do you invalidate lists that contain the entity?
  • Would CDC/outbox-driven invalidation help?
d07-q05What is a cache stampede scenario and how would you prevent it?
First 30 seconds
Stampede is many requests missing the same key at once and all hitting the DB. Prevent with singleflight, a lock, probabilistic early refresh, or serving stale while one refreshes.
Model answer
  1. Scenario: hot key TTL expires (or cold start) → N concurrent misses → N identical DB queries.
  2. Singleflight / request coalescing in-process: one loader, others wait.
  3. Distributed: SET lock key NX EX; winner loads DB and fills cache; losers wait/retry or serve stale.
  4. Probabilistic early expiration / soft TTL: refresh before hard expiry under load.
  5. Jitter TTLs so many keys don't expire in the same second; monitor miss spikes.
Code / ops
python
ok = redis.set(f'lock:{key}', '1', nx=True, ex=5)
if ok:
    val = db.fetch()
    redis.setex(key, ttl, val)
    redis.delete(f'lock:{key}')
else:
    # wait briefly and GET again, or serve stale
    ...
Nest / Node: In multi-instance Node, in-process singleflight alone is not enough — need Redis NX lock or similar.
Say it out loud
Say it spoken

Stampede = thundering herd on miss. One refresher via lock or singleflight; others wait or get stale.

Traps / weak answers
  • Only jittering TTL but not locking the hottest key
  • Lock without TTL (deadlock if refresher dies)
  • Retry loops without backoff while lock held
Follow-ups
  • How does 'serve stale-while-revalidate' work with Redis?
  • What's the difference between stampede and hot-key CPU saturation?
d07-q06A popular Redis key becomes a hot key. How would you handle it?
First 30 seconds
A hot key saturates one shard/CPU. I'd add a local in-process cache, or split the keyspace across N sibling keys and aggregate.
Model answer
  1. Confirm with Redis hot-key metrics / proxy stats / latency on one cluster node.
  2. L1 local cache (with short TTL) on app instances to absorb read QPS.
  3. Shard the key: value replicated on key:0..N-1 randomly read; for counters, INCR random shard and SUM on read (approximate or exact merge).
  4. Reconsider storing a huge value; compress or split fields.
  5. If Cluster mode, note hash-tag pinning can concentrate load — avoid accidental hot hash slots.
Code / ops
python
# read sharding for a hot blob
shard = random.randint(0, N - 1)
return redis.get(f'config:{shard}')
Say it out loud
Say it spoken

Hot keys need L1 caching or key sharding — scaling the cluster alone won't help if one key owns one slot.

Traps / weak answers
  • Adding Redis nodes without splitting the key
  • Hash tags that force many hot keys onto one slot
  • Global locks on the hot key for every read
Follow-ups
  • How do you shard a hot counter accurately?
  • When is client-side caching (TRACKING) appropriate?
d07-q07How would you choose TTLs for data with different freshness requirements?
First 30 seconds
TTL follows the business freshness SLO: seconds for volatile counters, minutes for profiles, hours for rare config — always with jitter and an invalidation story for critical updates.
Model answer
  1. Classify data: strict freshness (skip cache or TTL seconds + invalidate), eventual (minutes), static (hours/days).
  2. Set TTL slightly above typical update interval; use explicit DEL on writes for stricter paths.
  3. Add random jitter (±10–20%) to prevent synchronized expiry stampedes.
  4. Negative caching: short TTL for misses to avoid DB hammering on hot 404s.
  5. Review TTLs with hit-rate and stale-read metrics; document per-key-family policy.
Code / ops
python
ttl = base_ttl + random.randint(0, jitter)
Say it out loud
Say it spoken

TTL is a freshness SLA. Short + invalidate for volatile data, longer for static, jitter everything, short negative cache for misses.

Traps / weak answers
  • One global TTL for all keys
  • No jitter on millions of keys with the same expiry
  • Eternal keys for data that does change
Follow-ups
  • How do you expire keys that are too large to scan with KEYS?
  • Volatile-LRU vs allkeys-lru eviction — when does TTL still matter?
d07-q08How would you design a distributed per-user and per-IP rate limiter using Redis?
First 30 seconds
I'd use Redis atomic counters or a sliding-window ZSET, with separate keys for userId and IP, evaluated in the gateway/middleware before expensive work.
Model answer
  1. Fixed window: INCR key; on first INCR set EXPIRE windowSeconds; reject when count > limit (simple, bursty at boundaries).
  2. Sliding window: ZADD timestamps, ZREMRANGEBYSCORE old, ZCARD — more accurate; often via Lua for atomicity.
  3. Keys: rl:user:{id}:{bucket}, rl:ip:{ip}:{bucket}; apply both limits (AND).
  4. Fail-closed or fail-open policy when Redis is down — usually fail-closed for auth abuse paths.
  5. Return standard headers (remaining/reset); shard hot IP keys if under attack; observe top offenders.
Code / ops
text
-- simplified fixed window
local c = redis.call('INCR', KEYS[1])
if c == 1 then redis.call('EXPIRE', KEYS[1], ARGV[1]) end
return c
Nest / Node: Apply in Nest guard/middleware before controllers; don't rely only on per-instance memory limits.
Say it out loud
Say it spoken

Per-user and per-IP keys with atomic INCR or sliding-window Lua, checked early in the middleware, with an explicit Redis-down policy.

Traps / weak answers
  • Non-atomic get/set rate counters
  • Only IP limits (NAT) or only user limits (pre-auth flood)
  • Failing open on login endpoints during Redis outage
Follow-ups
  • Token bucket vs sliding window?
  • How do you rate-limit at API gateway vs app?
d07-q09Two application instances update the same Redis-based counter concurrently. How would you make the operation safe?
First 30 seconds
Use Redis atomic primitives — INCR/INCRBY or a Lua script — never GET, add in process, SET.
Model answer
  1. Prefer INCR/INCRBY/DECR for single counters; they are atomic across clients.
  2. For multi-key or conditional updates, use Lua (EVAL) or MULTI/EXEC transactions.
  3. Avoid read-modify-write in app code across instances — classic race.
  4. If absolute accuracy across Redis failover matters, understand Redis persistence/replication limits or keep durable counters in Postgres.
  5. Test with concurrent workers; monitor for script errors and key type mismatches.
Code / ops
python
redis.incrby('metrics:signup', 1)
# or Lua for compare-and-swap style logic
Say it out loud
Say it spoken

INCR or Lua — not get-add-set. Redis atomic ops are the concurrency control.

Traps / weak answers
  • GET + SET across instances
  • Using MULTI without understanding WATCH for optimistic cases
  • Storing counters only in Redis when finance needs auditability
Follow-ups
  • When do you need Lua vs a single INCR?
  • How does Redis Cluster affect multi-key Lua?
d07-q10How would you prevent a cache outage from causing a database avalanche?
First 30 seconds
Treat Redis failure as expected: circuit-break, admit only a bounded number of DB fallbacks, shed non-critical traffic, and keep a small local stale cache.
Model answer
  1. Timeouts + circuit breaker on Redis so the app fails fast instead of wedging.
  2. Bulkhead: limit concurrent DB queries on cache-miss/fallback paths (semaphore).
  3. Serve stale L1 content where safe; disable expensive list endpoints under degradation mode.
  4. Load shed / adaptive concurrency at the edge when DB saturation rises.
  5. Game-day: kill Redis in staging and verify DB QPS stays within ceiling; alert on fallback rate.
Nest / Node: Feature-flag 'degraded_mode' to flip caches off intentionally during incidents with known DB headroom.
Say it out loud
Say it spoken

Avalanche prevention is bounded fallback: breakers, semaphores, stale serve, and shedding — not 'just query Postgres.'

Traps / weak answers
  • Silent unlimited DB fallback
  • Retry storms compounding load
  • No distinction between critical and optional reads
Follow-ups
  • How do you size the fallback semaphore?
  • What's the role of request coalescing during partial outages?

03  Self-check

Cache-aside on read means:
Cache-aside keeps the app in control of read path population; DB remains source of truth.
Best primitive for an atomic counter across instances?
INCR is atomic server-side; get-modify-set races across instances.
Cache stampede is:
Synchronized expiry or cold start causes thundering herd on the origin.
Redis outage protection should include:
Degrade deliberately; uncapped DB fallback creates an avalanche.
