AWS / Nginx / Networking

Senior interviews expect you to place FastAPI behind real AWS edges: DNS, load balancers, private subnets, Multi-AZ data stores, and Nginx as a reverse proxy. They care about TLS termination tradeoffs, client-IP trust, zero-downtime deregistration, and what actually fails when an AZ dies—not diagram wallpaper.

d10-q01How would you design a highly available backend using Route 53, ALB, EC2/ECS, Nginx, PostgreSQL, Redis, and S3?
First 30 seconds
I'd put DNS on Route 53 health-checking an ALB spanning two AZs, run FastAPI behind Nginx on ECS/EC2 in private subnets, and use Multi-AZ RDS, clustered Redis, and S3 for durable objects.
Model answer
  1. Route 53 alias to ALB (or failover/weighted if multi-region); health checks on the ALB/target group.
  2. ALB in public subnets across ≥2 AZs; target group to Nginx+app tasks/instances in private subnets across the same AZs.
  3. Nginx terminates or proxies to uvicorn/gunicorn; keep config identical via AMI/user-data or container image.
  4. RDS PostgreSQL Multi-AZ for automatic standby failover; app uses the cluster endpoint with connection retry.
  5. Redis: ElastiCache Multi-AZ/failover group for sessions/cache; treat cache as disposable, DB as source of truth.
  6. S3 for media/artifacts (versioning + SSE); no local disk as durable store. IAM task roles, not long-lived keys.
Diagram

  r53 --> alb[ALB_multiAZ]
  alb --> ngx1[Nginx_AZ_a]
  alb --> ngx2[Nginx_AZ_b]

  api1 --> rds[RDS_MultiAZ]
  api2 --> rds

Nest / Node: Same topology for Nest; put the Node process behind Nginx or ALB directly—don't expose container ports publicly.

Say it spoken

HA for me is Multi-AZ at every hop: Route 53 to a cross-AZ ALB, private ECS/EC2 with Nginx, RDS Multi-AZ, Redis failover, and S3. One AZ loss should drop capacity, not the product.

Traps / weak answers
  • Single-AZ RDS or a lone EC2 'for cost' with no failover story.
  • Storing uploads on instance disk instead of S3.
Follow-ups
  • How do you handle Redis failover without stampedes to Postgres?
  • When would you add a second region?

d10-q02How would you decide whether TLS should terminate at the load balancer or Nginx?
First 30 seconds
Default: terminate TLS at the ALB with an ACM certificate for operational simplicity. Re-encrypt to Nginx/app only when compliance requires encryption in transit on the private hop.
Model answer
  1. ALB termination: ACM auto-renewal, easy HTTPS listener, HTTP to targets on a private network—good for most SaaS APIs.
  2. Nginx termination: when you need custom TLS policies, mTLS, or the ALB is TCP/NLB and cannot do HTTP features you need.
  3. ALB → Nginx re-encrypt (TLS to target): defense-in-depth / regulated environments; costs CPU and cert management on targets.
  4. Never send cleartext across untrusted networks; inside a locked-down VPC, HTTP to targets is a conscious tradeoff, not ignorance.
  5. Document trust: apps must still know original proto via X-Forwarded-Proto for redirect/cookie Secure flags.
  6. Prefer ACM on ALB; if terminating at Nginx, automate cert issuance (ACM PCA, Let's Encrypt carefully) and rotation.
Code / ops
bash
# Nginx trust forwarded proto from ALB only
set_real_ip_from 10.0.0.0/8;
real_ip_header X-Forwarded-For;
Nest / Node: Nest behind ALB: enable `app.set('trust proxy', hopCount)` or equivalent so `req.secure` reflects X-Forwarded-Proto.
Say it out loud
Say it spoken

I'd terminate at the ALB with ACM unless compliance forces TLS to the instance—then re-encrypt to Nginx. Either way I honor X-Forwarded-Proto for secure cookies and redirects.

Traps / weak answers
  • Terminating at ALB then assuming the app sees HTTPS without trusting proxy headers.
  • Managing wildcard certs on every EC2 by hand with no rotation.
Follow-ups
  • How does mTLS change the termination point?
  • Where do you enforce HSTS?
d10-q03How would you troubleshoot a request that works by IP address but not through the domain name?
First 30 seconds
That pattern screams DNS, TLS/SNI, or Host-header routing—not the app itself. I'd verify what name resolves to, then what certificate and virtual host that name selects.
Model answer
  1. dig/nslookup the hostname; confirm it points at the expected ALB/CloudFront, not a stale IP or wrong account.
  2. Compare curl -v by IP vs by Host: `curl -vk https://IP -H 'Host: api.example.com'` to separate DNS from vhost.
  3. Check TLS: certificate CN/SAN must include the hostname; SNI must be sent (modern clients do).
  4. ALB listener rules and Nginx `server_name` may only match the hostname; default server may 404/wrong cert on bare IP.
  5. Check Route 53 record type (alias vs A), propagation, and split-horizon/private zones if on VPN.
  6. Browser-only failures: HSTS, cached DNS, or corporate proxy—verify with curl from the same network.
Code / ops
bash
dig +short api.example.com
curl -vk https://api.example.com/health
curl -vk https://<alb-ip>/health -H 'Host: api.example.com'
Say it out loud
Say it spoken

If IP works but the domain doesn't, I chase DNS first, then TLS SANs/SNI, then ALB/Nginx Host-based rules. The app is usually fine—the name path isn't.

Traps / weak answers
  • Immediately restarting the app or redeploying ECS.
  • Ignoring that ALB HTTPS requires matching cert for the hostname.
Follow-ups
  • How would CloudFront in front change this debugging path?
  • What if HTTP works but HTTPS fails only on the domain?
d10-q04How would you preserve and validate client IP information across a proxy/load-balancer chain?
First 30 seconds
Client IP is only trustworthy if we know how many hops append X-Forwarded-For and we ignore anything clients spoof. I'd configure real_ip at Nginx and trust proxy at FastAPI with an explicit hop count.
Model answer
  1. ALB appends the client IP to X-Forwarded-For; the immediate peer IP is the ALB node.
  2. Nginx: `set_real_ip_from` for VPC CIDRs / ALB; `real_ip_header X-Forwarded-For`; `real_ip_recursive on` as appropriate.
  3. FastAPI/uvicorn: configure proxy headers / trusted hosts so `request.client` reflects the real client after N trusted hops.
  4. Never blindly trust the leftmost XFF from the open internet without verifying the chain.
  5. Prefer ALB's `X-Amzn-Trace-Id` plus structured logs; for rate limits, use the validated client IP.
  6. Document the hop count in runbooks; mis-counting causes rate limits to key on the ALB IP (one bucket for everyone).
Diagram
flowchart LR
  c[Client] --> alb[ALB_appends_XFF]
  alb --> ngx[Nginx_real_ip]
  ngx --> api[FastAPI_trust_hops]
Code / ops
python
# FastAPI / Starlette TrustedHost + careful forwarded handling
# Prefer a middleware that takes the rightmost untrusted → leftmost trusted hop
Nest / Node: Nest/Express: `app.set('trust proxy', 1)` (or hop count matching ALB→Nginx). Wrong value breaks IP-based throttling.
Say it out loud
Say it spoken

I only trust X-Forwarded-For from known load-balancer CIDRs with a fixed hop count. Spoofed client-supplied XFF is ignored so rate limits and audit logs key on the real client.

Traps / weak answers
  • Using the first XFF entry blindly (attacker-controlled).
  • Logging only the TCP peer (always the LB) and thinking it's the user.
Follow-ups
  • How does PROXY protocol on NLB change this?
  • How do you rate-limit users behind CGNAT?
d10-q05How would you decide between ALB, NLB, and API Gateway for a backend service?
First 30 seconds
ALB for HTTP APIs with path routing and WAF; NLB for raw TCP/ultra-low latency/static private IP; API Gateway when you want managed auth, throttling, and serverless/productized API edges.
Model answer
  1. ALB: L7 HTTP/HTTPS, host/path routing, OIDC, WAF, target groups to ECS/EC2/Lambda—default for FastAPI microservices.
  2. NLB: L4 TCP/UDP, preserves source IP (with caveats), extreme scale/low latency, AWS PrivateLink—good for databases' proxies, gRPC at scale, or non-HTTP.
  3. API Gateway (HTTP/REST/WebSocket): API keys, usage plans, JWT authorizers, request validation, fan-out to Lambda/HTTP; higher per-request cost, great for public API products.
  4. Combine: API GW → VPC link → NLB/ALB for private services when you need GW features plus container backends.
  5. Choose on protocol, routing needs, auth/throttle features, latency budget, and cost model—not fashion.
  6. For a single internal FastAPI service behind Cognito/custom auth in-app, ALB alone is usually enough.
Say it out loud
Say it spoken

ALB for normal HTTP FastAPI, NLB when I need L4/PrivateLink/static IP, API Gateway when the product needs managed API edge features. I pick from requirements, not defaults.

Traps / weak answers
  • Using API Gateway for every internal service and paying latency/cost without using its features.
  • Putting HTTP path routing expectations on an NLB.
Follow-ups
  • When is CloudFront + ALB better than API Gateway?
  • How do you expose a private ALB via PrivateLink?

d10-q06How would you keep application servers private while exposing the system securely to the internet?
First 30 seconds
Public subnet holds only the ALB (and maybe NAT/bastion). App tasks live in private subnets with no public IPs; egress goes through NAT; security groups allow ALB→app only.
Model answer
  1. Split VPC: public subnets (ALB, NAT Gateway) and private subnets (ECS/EC2, RDS, Redis).
  2. Security groups: ALB accepts 443 from world (or CloudFront); app SG accepts only from ALB SG on app port; RDS accepts only from app SG.
  3. No SSH from 0.0.0.0/0—use SSM Session Manager or a tightly locked bastion.
  4. NAT Gateway for outbound package mirrors, webhooks, third-party APIs; VPC endpoints for S3/ECR/Secrets to cut NAT cost and exposure.
  5. WAF on ALB for common exploits/rate rules; Force HTTPS at the listener.
  6. Private DNS inside VPC for service discovery; never publish private instance IPs in public DNS.
Diagram
flowchart TB
  inet[Internet] --> alb[ALB_public]
  alb --> app[App_private]
  app --> rds[RDS_private]
  app --> nat[NAT_egress]
  nat --> inet
Say it out loud
Say it spoken

Internet stops at the ALB. Apps and data stores stay in private subnets with SG chains ALB→app→RDS, egress via NAT or VPC endpoints, and admin access via SSM—not open SSH.

Traps / weak answers
  • Assigning public IPs to ECS tasks 'so health checks work' (fix the ALB health check path instead).
  • Wide SG rules like 0.0.0.0/0 on app port.
Follow-ups

  • How do Lambda functions in VPC reach the internet?
d10-q07How would you design autoscaling for a backend where CPU is not a reliable signal of demand?
First 30 seconds
CPU-idle services still drown—queue lag, in-flight requests, and p99 latency are better signals. I'd publish custom CloudWatch metrics and scale on those with sensible cooldowns.
Model answer
  1. Identify the real bottleneck: SQS depth, Kafka lag, active DB connections, request concurrency, event-loop lag.
  2. Emit custom metrics from the app or queue (ApproximateNumberOfMessagesVisible, consumer lag, concurrent requests).
  3. Target tracking or step scaling on that metric; keep CPU as a secondary safeguard.
  4. Scale out early on lag; scale in slowly to avoid thrash; set min capacity for cold-start protection.
  5. For ECS: scale services on ALB RequestCountPerTarget or custom metrics; ensure deploy + scale policies don't fight.
  6. Load-test to correlate metric → capacity; alert when scaling hits max and lag still grows (shed load).
Code / ops
text
# PutMetricData sketch: ConcurrentRequests / worker
# ASG policy: target tracking on that metric
Nest / Node: Nest workers consuming BullMQ should scale on waiting job count, not Node process CPU alone.
Say it out loud
Say it spoken

When CPU lies, I scale on queue lag or concurrent requests via custom CloudWatch metrics, with slow scale-in and a floor capacity. CPU stays a backup signal only.

Traps / weak answers
  • Only scaling on CPU for an I/O-bound FastAPI service.
  • Scale-in that's too aggressive during traffic troughs between bursts.
Follow-ups
  • How do you prevent autoscaling from launching into a broken deploy?
  • What metric would you use for a WebSocket-heavy service?
d10-q08How would you make an EC2-based deployment highly available across Availability Zones?
First 30 seconds
Spread instances across at least two AZs behind a cross-AZ ALB, use an ASG with multi-AZ subnets, and put stateful dependencies on Multi-AZ managed services.
Model answer
  1. ASG spanning private subnets in ≥2 AZs; ALB target group with instances in each AZ.
  2. Capacity balanced: don't put min=1 in a single AZ; use capacity rebalancing / diverse instance types if needed.
  3. Health checks: ALB HTTP health on /health that verifies critical deps carefully (avoid flapping on blips).
  4. RDS Multi-AZ, ElastiCache failover, EFS/S3 instead of AZ-local disk for shared assets.
  5. AMI/Launch Template identical; user-data/cloud-init registers to ALB automatically.
  6. Test AZ loss: verify remaining AZ can take 100% (or accept degraded capacity with known SLO).
Say it out loud
Say it spoken

Multi-AZ HA means ASG+ALB across subnets, Multi-AZ data stores, and enough spare capacity that losing one AZ still meets SLO. Identical Launch Templates so replacements are boring.

Traps / weak answers
  • Two instances in the same AZ thinking that's HA.
  • Local disk sessions that vanish when an AZ fails.
Follow-ups
  • How do you size capacity for N-1 AZ survival?
  • What breaks if you disable ALB cross-zone load balancing?
d10-q09How would you design zero-downtime deployment on EC2 behind an ALB?
First 30 seconds
I'd use rolling replace with connection draining: register healthy new instances, deregister old ones, wait deregistration_delay until in-flight requests finish, then terminate.
Model answer
  1. Launch new instances from the new AMI/Launch Template; wait until ALB health checks pass.
  2. Deregister old targets; set deregistration_delay (e.g. 30–120s) ≥ p99 request time + buffer.
  3. App handles SIGTERM: stop taking new work (or rely on ALB stopping new connections), finish in-flight, close pools.
  4. For ASG instance refresh / rolling update: set min healthy %, checkpoints, and bake health checks that prove the new version.
  5. Run dual versions only if migrations are forward-compatible (expand/contract).
  6. Verify with synthetic traffic during deploy; auto-rollback on health/alarm failure.
Diagram
flowchart LR
  new[Register_new] --> healthy[Health_pass]
  healthy --> drain[Deregister_old]
  drain --> wait[Wait_dereg_delay]
  wait --> term[Terminate_old]
Code / ops
bash
# Target group attribute
# deregistration_delay.timeout_seconds = 90
Nest / Node: Nest: enable shutdown hooks (`app.enableShutdownHooks()`) and set ECS/ASG stop timeout > longest request.
Say it out loud
Say it spoken

Zero-downtime on EC2+ALB is drain-then-kill: healthy new targets first, deregistration delay covering in-flight p99, and SIGTERM-aware processes. Never terminate before the ALB stops sending traffic.

Traps / weak answers
  • ASG terminating instances immediately on refresh without draining.
  • Health check that only hits Nginx while the new app process isn't ready.
Follow-ups
  • How does this differ on ECS rolling update vs EC2 ASG?
  • What deregistration delay do you choose for long uploads?

d10-q10One AWS Availability Zone fails during peak traffic. What components must fail over and what should you test beforehand?
First 30 seconds
I'd walk the dependency list: ALB nodes, ASG capacity in remaining AZs, RDS failover, Redis failover, and NAT. Game-day those failovers under load before peak season.
Model answer
  1. ALB: multi-AZ by design—confirm targets exist in surviving AZs and cross-zone balancing behavior.
  2. Compute: ASG should launch replacements in healthy AZs; ensure subnet IP capacity and service quotas allow it.
  3. RDS Multi-AZ: expect brief failover downtime (DNS/connection blip); apps must retry with backoff.
  4. ElastiCache: failover to replica; expect cache coldness and possible stampede—use request coalescing/soft TTLs.
  5. NAT Gateway is AZ-specific: apps in a dead AZ lose that NAT; surviving AZ NAT must handle egress or use HA NAT design.
  6. Game days: simulate AZ impairment, watch error budgets, verify alarms/runbooks, and document capacity headroom (N-1).
Say it out loud
Say it spoken

AZ failure is a capacity and failover event: remaining AZ apps take traffic, RDS/Redis fail over with retries, and NAT/IP capacity must already be sized. I'd prove it with a game day, not a slide.

Traps / weak answers
  • Assuming Multi-AZ RDS means zero connection errors (clients must reconnect).
  • Never testing that the surviving AZ has enough CPU/connection capacity for peak.
Follow-ups
  • What's your RTO/RPO if the RDS failover is insufficient and you need a region DR?
  • How do you prevent cache stampedes after Redis failover?

03  Self-check

Where should application tasks run in a secure VPC layout?
Internet clients hit the ALB in public subnets; app instances stay private. NAT provides controlled egress for patches and third-party APIs.
Why can a site work by IP but fail by hostname?
ALB listener rules, Nginx server_name, and TLS certificates all key off the Host/SNI name. Hitting the IP skips that path.
What is the main zero-downtime lever when removing an EC2 target from an ALB?
ALB stops new connections and waits the configured delay (and connection drain) before the target is gone—match it to your p99 request duration.
ALB vs NLB for a typical public FastAPI JSON API?
Most HTTP APIs want ALB features. NLB shines for TCP, extreme performance, or private-link style static IPs.
