Async Python / FastAPI / Node.js / TypeScript

Async interviews catch people who sprinkle await without understanding when work actually runs. Interviewers want you to explain coroutines vs promises, why decorators must await, and how unbounded concurrency melts production. FastAPI and Nest both hide event loops — seniors talk about blocking CPU, missing await, and semaphore limits with concrete failure modes.

d02-q01A class has an API method wrapped by a logging function, but the logging code runs immediately instead of after the API response. What could be wrong?
First 30 seconds
The wrapper is almost certainly treating an async method like a sync function — calling it without await, or decorating so the wrapper returns a coroutine and logs 'done' before the await happens. I'll inspect whether the method and decorator are both async and where the log line sits relative to await.
Model answer
  1. Check if the API method is async def; calling it returns a coroutine, so sync logging after the call runs before the body executes.
  2. Inspect the decorator: if it does result = func(*args) then log('done') without awaiting, logs fire immediately.
  3. Ensure the wrapper is async def wrapper(...): result = await func(...); log(...); return result.
  4. If using a sync decorator factory, return an async wrapper when inspect.iscoroutinefunction(func).
  5. Watch for @decorator without parentheses vs factory mistakes that call the logger at decoration time (import time), not request time.
  6. Verify FastAPI still sees an async route after decoration (functools.wraps / __wrapped__).
  7. Add a failing unit test: mock sleep in the route and assert log timestamp is after completion.
  8. Fix and confirm access logs / structured 'duration_ms' match real latency.
Code / ops
python
import functools, time

def log_duration(func):
    @functools.wraps(func)
    async def wrapper(*args, **kwargs):
        t0 = time.perf_counter()
        result = await func(*args, **kwargs)  # must await
        print(f"{func.__name__} took {time.perf_counter()-t0:.3f}s")
        return result
    return wrapper

@log_duration
async def get_order(order_id: str):
    ...
Nest / Node: Nest interceptors/middleware are Promise-aware if you return/await next.handle(); a tap that runs outside the observable/promise chain logs too early — same bug class as missing await.

Say it spoken

If the log says completed before the response exists, the wrapper didn't await. Async methods need async-aware decorators that await the call, then log — otherwise you only logged scheduling the coroutine.

Traps / weak answers
  • Logging at decoration/import time instead of call time
  • Sync wrapper around async def that never awaits
  • Assuming FastAPI 'awaits for you' inside your custom decorator
Follow-ups

d02-q02A function calls an async method without await. What behavior would you expect?
First 30 seconds
In Python you get an un-awaited coroutine object — usually a RuntimeWarning and no side effects from that call. In JavaScript you get a floating Promise that may reject as unhandled. Either way, the caller continues immediately with the wrong type of value.
Model answer
  1. Python: async_method() returns a coroutine; without await/create_task it does not run the body.
  2. Expect RuntimeWarning: coroutine was never awaited when the object is GC'd.
  3. If the return value is used, you pass a coroutine object downstream (serialization errors, truthy object bugs).
  4. create_task without retaining/awaiting can still run but errors become 'Task exception was never retrieved'.
  5. JavaScript/TypeScript: missing await yields a Promise; sync code proceeds; rejections need .catch or await.
  6. In FastAPI routes, forgetting await on httpx/db calls returns instantly with incomplete work.
  7. Lint/CI: enable ruff/flake8-async or TypeScript @typescript-eslint to catch floating promises.
  8. Fix: await, or explicitly schedule with asyncio.create_task and supervise completion/errors.
Code / ops
python
async def fetch_user(uid: str):
    return {"id": uid}

async def broken():
    user = fetch_user("1")  # coroutine object, not dict
    return user["id"]  # TypeError

async def fixed():
    user = await fetch_user("1")
    return user["id"]
Nest / Node: TS: enable no-floating-promises. Nest handlers that return a Promise are awaited by the framework, but internal calls still need await.
Say it out loud
Say it spoken

No await means no wait — in Python the coroutine never runs; in Node the Promise is fire-and-forget. I treat un-awaited async calls as bugs unless I deliberately create a supervised background task.

Traps / weak answers
  • Thinking the async function runs synchronously until the first await
  • Ignoring RuntimeWarning in logs
  • Using time.sleep in async code as a 'fix' for timing issues
Follow-ups
  • When is asyncio.create_task appropriate versus await?
  • How do you surface unhandled task exceptions in production?
d02-q03A decorator logs execution time as almost zero even though the wrapped API takes several seconds. How would you debug the decorator?
First 30 seconds
Near-zero duration means the timer stopped when the coroutine was created, not when it finished. I'll put start/stop around await func(...) and confirm the decorator detects coroutine functions.
Model answer
  1. Print type(result) after calling func — if it's a coroutine, the timer didn't include real work.
  2. Rewrite wrapper as async and await; measure with time.perf_counter around the await.
  3. If the route is sync def doing blocking I/O, duration may be real inside threadpool — separate issue from async decorator.
  4. Ensure functools.wraps preserves async nature so FastAPI schedules correctly.
  5. Check for double-wrapping or middleware that also times and confuses which layer logs.
  6. Validate with asyncio.sleep(2) inside the route — decorator must report ~2s.
  7. Prefer structured metrics (histogram) over print for production timing.
  8. Add a unit test asserting duration >= sleep time.
Code / ops
python
import functools, time, inspect

def timed(func):
    if inspect.iscoroutinefunction(func):
        @functools.wraps(func)
        async def aw(*a, **k):
            t0 = time.perf_counter()
            try:
                return await func(*a, **k)
            finally:
                print(time.perf_counter() - t0)
        return aw
    @functools.wraps(func)
    def sw(*a, **k):
        t0 = time.perf_counter()
        try:
            return func(*a, **k)
        finally:
            print(time.perf_counter() - t0)
    return sw

Say it spoken

A decorator that reports zero on a multi-second API didn't await. Timing must wrap the awaited call; otherwise you measured how long it took to build a coroutine object.

Traps / weak answers
  • Using time.time() around a non-awaited call
  • Decorating at class level incorrectly so self binding breaks

d02-q04A logging wrapper prints 'completed' before an async method actually completes. How would you redesign it?
First 30 seconds
I'd make the wrapper async-native: await the callee, log success/failure in a finally, and preserve exceptions. Optionally support background tasks only with explicit create_task and a completion callback — never implicit.
Model answer
  1. Redesign as async context-manager or async decorator that awaits the function.
  2. Log start before await; log completed/failed in finally with duration and correlation id.
  3. Re-raise exceptions after logging so FastAPI error handlers still run.
  4. For fire-and-forget, require explicit schedule_background(coro) that attaches done callbacks.
  5. Avoid printing from sync code that receives a Promise/coroutine.
  6. In libraries, use inspect.iscoroutinefunction to choose wrapper type.
  7. Emit structured logs (JSON) with request_id from contextvars.
  8. Test with delayed async mock to assert log order: start → work → completed.
Code / ops
python
from contextlib import asynccontextmanager
import logging

log = logging.getLogger(__name__)

@asynccontextmanager
async def log_op(name: str):
    log.info("%s start", name)
    try:
        yield
        log.info("%s completed", name)
    except Exception:
        log.exception("%s failed", name)
        raise

async def handler():
    async with log_op("get_order"):
        return await load_order()
Nest / Node: Use RxJS finalize/tap on next.handle(), or an async Nest interceptor that awaits the Promise result before logging completed.
Say it out loud
Say it spoken

I redesign the wrapper so 'completed' can only print after await returns or raises. If we need background work, that's an explicit supervised task with its own completion log — not a sneaky missing await.

Traps / weak answers
  • Logging completed in a finally that runs before await (wrong structure)
  • Swallowing exceptions inside the wrapper
  • Using print instead of logger with correlation ids

d02-q05A try/catch catches synchronous errors but misses failures from an async operation. What is wrong?
First 30 seconds
The async operation isn't being awaited inside the try — so the rejection happens later, outside the sync try/except. I'll move await into the try or attach explicit error handling on the task/promise.
Model answer
  1. Show the anti-pattern: try { const p = asyncOp(); } catch — catch never sees async rejection.
  2. Correct: try { await asyncOp(); } catch (e) { ... }.
  3. Python equivalent: try/except around await; bare call doesn't raise until awaited.
  4. If using create_task, add task.add_done_callback or await the task inside try.
  5. Promise chains need .catch or await in async functions; empty catch on sync block is useless.
  6. FastAPI: exceptions from awaited deps propagate to exception handlers; unawaited ones become warnings.
  7. For gather, decide return_exceptions vs raising first error.
  8. Add lint rules for floating promises / unawaited coroutines.
Code / ops
python
async def bad():
    try:
        fetch()  # forgot await — no exception here
    except Exception:
        return "handled"
    return "ok"

async def good():
    try:
        return await fetch()
    except httpx.HTTPError:
        return "handled"
Nest / Node: In Nest, filters catch errors from awaited providers; a floating Promise rejection bypasses the exception filter and can crash or log as unhandledRejection.
Say it out loud
Say it spoken

try/except only catches what runs inside it. If you don't await, the failure happens on another turn of the event loop and your catch is already gone — await inside the try, or supervise the task explicitly.

Traps / weak answers
  • Wrapping create_task in try/except without awaiting the task
  • Assuming .then errors are caught by outer sync try
  • Using bare except and returning 200 on failure
Follow-ups
  • How should asyncio.TaskGroup error handling differ from gather?
  • Where do you put retries — around await of a single call or the whole request?
d02-q06A Node.js service uses array.forEach(async item => ... ) and expects the caller to wait for all operations. What is wrong?
First 30 seconds
forEach doesn't await the Promises your async callback returns, so the caller continues immediately while work is still in flight. I'd switch to for...of with await, or map + Promise.all / allSettled with a concurrency limit.
Model answer
  1. Explain forEach signature: callback return values are ignored.
  2. Demonstrate: forEach starts all async ops and returns undefined immediately.
  3. Replace with for (const item of items) { await work(item); } for sequential.
  4. Or await Promise.all(items.map(work)) for parallel — watch unbounded concurrency.
  5. Prefer Promise.allSettled when partial failure is OK; inspect rejected reasons.
  6. For large arrays, use a pool (p-limit, generic-pool) so you don't open 10k sockets.
  7. Ensure errors propagate to the Express/Nest handler via await.
  8. Add a regression test that fails if the HTTP response returns before side effects finish.
Code / ops
typescript
// Broken
items.forEach(async (item) => {
  await save(item);
});
res.json({ ok: true }); // runs too early

// Fixed
await Promise.all(items.map((item) => save(item)));
res.json({ ok: true });
Nest / Node: Same bug in Nest services. Prefer for-await loops or Promise.all inside async service methods that the controller awaits.
Say it out loud
Say it spoken

forEach plus async is a classic false sense of waiting — the loop doesn't await. I use for...of or Promise.all with a concurrency cap, and I make sure the request handler awaits that aggregate Promise.

Traps / weak answers
  • Thinking async forEach magically sequentializes
  • Promise.all on huge arrays without limits
  • Swallowing per-item errors so the HTTP handler always 200s

d02-q07You need to call five independent third-party APIs from a FastAPI endpoint. How would you execute them?
First 30 seconds
Independent I/O should run concurrently with per-call timeouts and clear partial-failure policy. I'd asyncio.gather or TaskGroup the five httpx calls, bound total time, and decide whether any failure fails the request or returns degraded data.
Model answer
  1. Use one shared httpx.AsyncClient with connection limits for the process/app lifespan.
  2. Launch five coroutines with explicit Timeout(connect=..., read=...).
  3. asyncio.gather(*calls, return_exceptions=True) or TaskGroup depending on fail-fast needs.
  4. Set an overall deadline with asyncio.wait_for around the gather if the client SLO is tight.
  5. Map exceptions to 502/504/partial response; never hang on one slow vendor.
  6. Cache idempotent GETs when safe; add circuit breaker if a vendor is down.
  7. Emit per-dependency latency metrics labeled by vendor.
  8. Avoid sequential awaits unless ordering/quota requires it.
Code / ops
python
import asyncio, httpx
from fastapi import FastAPI

app = FastAPI()
client: httpx.AsyncClient

@app.on_event("startup")
async def startup():
    global client
    client = httpx.AsyncClient(timeout=httpx.Timeout(2.0, connect=0.5))

@app.get("/dashboard")
async def dashboard():
    urls = ["https://a/x", "https://b/y", "https://c/z", "https://d/u", "https://e/v"]
    results = await asyncio.gather(*[client.get(u) for u in urls], return_exceptions=True)
    return {"ok": [getattr(r, "status_code", None) for r in results]}

d02-q08You need to process 10,000 async operations but only want 20 in flight at any time. How would you design the concurrency limit?
First 30 seconds
I'd gate each operation with an asyncio.Semaphore(20) or a worker pool consuming a queue — never gather 10k tasks unbounded. The limit should reflect downstream quotas and local FD/connection caps.
Model answer
  1. Create sem = asyncio.Semaphore(20); wrap each op in async with sem: await work(item).
  2. Optionally use a queue with 20 workers for backpressure and clearer metrics.
  3. Avoid asyncio.gather(*[work(i) for i in range(10000)]) without a semaphore — memory and sockets explode.
  4. Tune 20 based on vendor rate limits, DB pool size, and experimentally measured p95.
  5. Track in_flight gauge and queue depth; reject or spill to a durable queue when overloaded.
  6. Handle cancellation: on request abort, don't leave 20 orphaned tasks without timeout.
  7. For CPU-bound map, use ProcessPoolExecutor with a small max_workers instead of asyncio semaphore.
  8. In Node, use p-limit(20) or a generic pool with the same idea.
Code / ops
python
import asyncio

async def process_all(items, limit=20):
    sem = asyncio.Semaphore(limit)
    async def one(item):
        async with sem:
            return await handle(item)
    return await asyncio.gather(*(one(i) for i in items))
Nest / Node: Use p-limit or bottleneck in Node; Nest Bull queues move the 10k off the request path entirely when work is heavy.
Say it out loud
Say it spoken

Ten thousand coroutines without a semaphore is an outage. I cap in-flight work at twenty with a semaphore or worker queue, sized to the dependency's quota and our connection pools.

Traps / weak answers
  • Gathering all tasks then hoping the OS schedules kindly
  • Setting limit higher than DB pool size
  • Losing error context by bare gather without return_exceptions when partial progress matters

d02-q09A Node.js endpoint uses Promise.all for 1,000 outbound requests and production becomes unstable. What could be happening?
First 30 seconds
Unbounded parallel outbound calls exhaust sockets, file descriptors, memory, and downstream rate limits — then the event loop and health checks suffer. Promise.all also fail-fasts on the first rejection while leaving other requests in flight.
Model answer
  1. 1,000 concurrent sockets → EMFILE, agent maxSockets queueing, or ephemeral port exhaustion.
  2. Downstream 429s and retries amplify load (retry storm).
  3. Memory spikes holding all response buffers until all settle.
  4. Promise.all rejects on first failure while other HTTP calls continue consuming resources.
  5. Libuv threadpool / DNS contention if many hostnames resolve at once.
  6. Fix: concurrency limit (e.g. 20–50), shared keep-alive agent, timeouts, and bulkheads per dependency.
  7. Move bulk fan-out off the request path into a queue workers process.
  8. Add metrics: active sockets, 429 rate, event-loop delay.
Code / ops
typescript
import pLimit from "p-limit";

const limit = pLimit(25);
const results = await Promise.all(
  urls.map((url) => limit(() => fetch(url, { signal: AbortSignal.timeout(2000) })))
);
Nest / Node: Configure HttpModule with maxRedirects and axios httpAgent maxSockets; prefer a job queue for large fan-out from Nest controllers.

Say it spoken

Promise.all of a thousand outbound calls is a thundering herd at yourself and your vendor. Cap concurrency, set timeouts, and don't do bulk fan-out on the user-facing request path.

Traps / weak answers
  • Raising UV_THREADPOOL_SIZE as the first fix
  • Retrying all 1000 immediately on failure

d02-q10An async endpoint performs CPU-heavy work and blocks unrelated requests. How would you redesign it?
First 30 seconds
CPU work on the event loop blocks every other coroutine on that worker. I'd move the heavy lift to a process pool, separate worker service, or precompute — and keep the request path to enqueue + poll/webhook.
Model answer
  1. Confirm with event-loop lag metrics while the endpoint runs.
  2. Offload via asyncio.to_thread only for light/blocking I/O — CPU-bound prefers ProcessPoolExecutor to escape the GIL.
  3. Better: accept request, enqueue job (RQ/Celery/ARQ/Bull), return 202 + job id.
  4. Scale CPU workers independently from API replicas.
  5. Chunk work and stream progress if users need feedback.
  6. Cache results when inputs repeat; avoid recomputing on the request path.
  7. Keep health checks on a separate process or ensure workers aren't all blocked (multiple uvicorn workers still share nothing for CPU across processes — more processes help).
  8. Document SLO: interactive APIs never do multi-hundred-ms CPU inline.
Code / ops
python
from concurrent.futures import ProcessPoolExecutor
from fastapi import FastAPI
import asyncio

app = FastAPI()
pool = ProcessPoolExecutor(max_workers=2)

def cpu_bound(n: int) -> int:
    return sum(i*i for i in range(n))

@app.post("/compute")
async def compute(n: int = 5_000_000):
    loop = asyncio.get_running_loop()
    result = await loop.run_in_executor(pool, cpu_bound, n)
    return {"result": result}
Nest / Node: In Nest/Node, CPU-heavy sync work blocks the single thread — use worker_threads, a child process, or a Bull queue consumers on separate processes; more Nest instances (PM2 cluster) only help if work is distributed.
Say it out loud
Say it spoken

Async isn't parallel CPU. I pull heavy compute off the event loop into a process pool or job queue and make the HTTP API async in the workflow sense — 202 and status — so unrelated requests keep moving.

Traps / weak answers
  • Wrapping CPU work in async def and expecting concurrency miracles
  • Using to_thread for multi-second GIL-bound pure Python compute
  • Running one uvicorn worker and wondering why all tenants stall
Follow-ups

03  Self-check

You call an async function without await in Python. What do you get?
Without await/ensure_future/create_task, you only built a coroutine object. It does not run until scheduled.
Why does array.forEach(async () => ...) fail to wait?
forEach invokes the callback and discards the return value; async callbacks return Promises that nobody awaits.
Best default for five independent HTTP calls in FastAPI?
Independent I/O should run concurrently with bounded timeouts; processes are for CPU, not simple HTTP fan-out.
CPU-heavy work inside an async FastAPI route typically causes:
The event loop is single-threaded; CPU work prevents scheduling other coroutines until it finishes (unless offloaded).
