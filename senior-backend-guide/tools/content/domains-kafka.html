Kafka / Messaging / Event-Driven Architecture

Kafka answers center on consumer groups, lag, and delivery semantics: at-least-once is the default, so consumers must be idempotent and commit offsets after side effects succeed. Partition keys buy ordering and can buy skew. Poison messages need bounded retries and a DLQ. Prefer an outbox when DB state and events must stay aligned, and choose Kafka only when fan-out, replay, or high throughput justify it.

01  Decision cheat strip

Lagconsumer group lag = produced - committed
Deliveryat-least-once → idempotent consumer
Offsetscommit after DB success (or transactional outbox)
Orderingper partition key only
Poisonretry budget → DLQ, don't block partition forever

d08-q01A Kafka consumer is processing messages slower than producers are publishing them. How would you diagnose and scale it?
First 30 seconds
I'd check consumer group lag by partition, see whether we're CPU-bound in processing or blocked on I/O, then scale partitions/consumers or speed up the handler — lag is the north star.
Model answer
  1. Measure lag (records/time) per partition and consumer; confirm it's growing, not a transient spike.
  2. Profile the handler: DB, external HTTP, serialization, batch size, sync vs async commits.
  3. Scale horizontally: increase partitions (plan carefully) so more consumers in the group can share work; adding consumers beyond partition count doesn't help.
  4. Optimize: batch writes, pipelining, reduce per-message DB round-trips, parallelize only where ordering allows.
  5. If one partition lags, suspect key skew; fix keying or processing isolation for whales.
Code / ops
bash
# conceptual
kafka-consumer-groups --describe --group orders-workers
Nest / Node: Expose lag metrics to Prometheus from the consumer client or burrow-like monitor.
Say it out loud
Say it spoken

Lag tells me I'm falling behind. I find whether it's handler time or skew, then add partitions/consumers or make each message cheaper.

Traps / weak answers
  • Adding consumers without adding partitions
  • Auto-scaling consumers blindly on CPU while lag is key-skew
  • Raising fetch sizes without measuring GC/DB impact
Follow-ups
  • How do you choose the initial partition count?
  • What's the cost of increasing partitions later?
d08-q02A consumer processes the same event twice. How should the application handle duplicates?
First 30 seconds
Treat duplicates as normal under at-least-once. Make processing idempotent with a dedupe key stored where the side effect lives.
Model answer
  1. Assume at-least-once: rebalances, retries, and commit failures cause redelivery.
  2. Define an idempotency key (event id, orderId+type, producer UUID) unique per business effect.
  3. Persist processed keys in Postgres (unique constraint) in the same transaction as the side effect.
  4. For non-DB effects, use Redis SET NX with TTL or upstream idempotent APIs.
  5. Don't 'fix' duplicates by committing offsets earlier — that risks loss.
Code / ops
sql
INSERT INTO processed_events (event_id) VALUES ($1)
ON CONFLICT DO NOTHING;
-- only apply side effects if insert happened
Say it out loud
Say it spoken

Duplicates are expected. I key every side effect and upsert under a unique constraint so the second delivery is a no-op.

Traps / weak answers
  • Assuming Kafka exactly-once means the business effect is exactly-once without work
  • Dedupe in memory only (lost on restart)
  • Side effects outside the dedupe transaction
Follow-ups
  • How does Kafka EOS / transactions change this?
  • How long do you retain idempotency keys?
d08-q03A consumer updates PostgreSQL and crashes before committing its Kafka offset. What could happen?
First 30 seconds
On restart the message is redelivered. If the DB write already committed, you get a duplicate side effect unless the consumer is idempotent.
Model answer
  1. Crash after DB commit + before offset commit ⇒ redelivery ⇒ duplicate processing attempt.
  2. Crash before DB commit ⇒ redelivery replays safely if the first write never landed.
  3. This is why commit-after-success + idempotent writes is the standard pattern.
  4. Opposite anti-pattern: commit offset first ⇒ crash ⇒ message skipped ⇒ data loss.
  5. Operationally: expect rebalances to extend this window; design for it, don't treat it as rare.
Nest / Node: Enable graceful shutdown that finishes the current record and commits before exit when possible.
Say it out loud
Say it spoken

DB committed, offset not: redelivery. That's at-least-once — idempotency makes it safe; committing early makes loss possible.

Traps / weak answers
  • Believing 'we commit sync so duplicates can't happen'
  • Committing offsets in a finally block before knowing DB success
  • No unique constraints on the write path
Follow-ups
  • How do store-offset-in-DB patterns work?
  • What happens during a rebalance mid-processing?
d08-q04How would you design an idempotent Kafka consumer?
First 30 seconds
Stable event id, transactional side effect + dedupe record, commit offsets only after success, and bounded retries for poison messages.
Model answer
  1. Require producers to send a unique eventId (or derive a deterministic hash of natural key + revision).
  2. In one DB transaction: insert dedupe row (unique on eventId) + apply business writes; skip if conflict.
  3. Keep handlers pure regarding retries: no non-idempotent external calls without their own idempotency keys.
  4. Commit Kafka offsets only after the transaction succeeds (or write offsets into the DB transaction).
  5. On repeated failure after N tries, route to DLQ and commit/skip so the partition progresses.
Diagram

  A[Poll] --> B{eventId seen?}
  B -->|yes| C[Skip / commit]
  B -->|no| D[TX: side effect + mark seen]
  D --> E[Commit offset]
Nest / Node: Nest/KafkaJS: disable auto-commit or commit explicitly after business TX.
Say it out loud
Say it spoken

Idempotent consumer = unique event id + transactional dedupe with the side effect + offset commit after success + DLQ for poison.

Traps / weak answers
  • Idempotency key that's not unique across retries (e.g. random UUID generated in consumer)
  • External payment call inside handler without provider idempotency key
  • Infinite retry blocking the partition
Follow-ups
  • How do you idempotently call a third-party API from a consumer?
  • At-least-once vs effectively-once in practice?
d08-q05How would you choose a Kafka partition key for an order or user domain?
First 30 seconds
Pick a key that preserves the ordering you need and spreads load — usually orderId for order lifecycle, userId for per-user streams — and watch for hot keys.
Model answer
  1. Ordering is per partition: all events for one orderId on the same partition keep causal order for that order.
  2. Use orderId when order state machine ordering matters; userId when per-user sequencing matters (feeds, balances).
  3. Avoid null/empty keys if you need ordering; avoid a single global key that serializes the topic.
  4. Balance cardinality: enough distinct keys to utilize partitions; monitor hotspot users/orders.
  5. Document the key so producers stay consistent — mixed keys destroy ordering assumptions.
Code / ops
python
producer.send({ topic: 'orders', key: orderId, value: event })
Say it out loud
Say it spoken

Partition key = ordering scope. orderId for order timelines, userId for user timelines — never one key for the whole topic.

Traps / weak answers
  • Random keys when you needed per-entity ordering
  • Using a low-cardinality status field as key
  • Changing key mid-stream without a migration plan
Follow-ups
  • How do you order across multiple entity types?
  • What if a single userId is too hot?
d08-q06One Kafka partition is receiving much more traffic than the others. How would you diagnose and fix the imbalance?
First 30 seconds
That's key skew. I'd measure produce rates per partition, find the hot keys, then re-key, split whales, or add processing isolation — more consumers alone won't fix one hot partition.
Model answer
  1. Confirm with broker/partition metrics: bytes-in, message rate, consumer lag on one partition.
  2. Sample keys in the hot partition; identify celebrity userId/orderId or bad constant key.
  3. Fixes: choose a higher-cardinality key; salt hot keys (trade ordering); split entity processing; dedicated topic for whales.
  4. Increasing partitions helps new keys redistribute but won't split an existing hot key's stream without changing the key.
  5. Long-term: producer guidelines + dashboards for partition imbalance.
Say it out loud
Say it spoken

Hot partition is key skew. Find the key, change keying or isolate the whale — extra consumers can't share one partition.

Traps / weak answers
  • Scaling consumer count expecting the hot partition to split
  • Salting keys without accepting lost per-key order
  • Ignoring producer-side constant keys
Follow-ups
  • How does sticky partitioning interact with skew?
  • Can you manually reassign partitions to stronger consumers?
d08-q07How would you design retries without allowing one poison message to block unrelated processing?
First 30 seconds
Bounded retries with backoff, then DLQ — never infinite retry on the same record while holding up the partition.
Model answer
  1. Classify errors: transient (retry) vs permanent/poison (don't tight-loop).
  2. Retry with backoff and a max attempts counter (headers or side store).
  3. After budget: publish to DLQ/retry topic with reason/payload; commit/skip the original so the partition advances.
  4. Process DLQ asynchronously with alerting and replay tools; don't require on-call to unblock the main topic.
  5. Where ordering allows, use pause/seek carefully; prefer per-record isolation over stopping the whole consumer.
Nest / Node: KafkaJS eachMessage handlers should not throw endlessly without a DLQ path.
Say it out loud
Say it spoken

Retry transient errors with a budget, then DLQ and move on — one bad message must not stall the partition.

Traps / weak answers
  • Infinite retries on deserialization errors
  • Blocking the consumer thread on long sleeps
  • DLQ without alerts or replay procedure
Follow-ups
  • Retry topic vs in-place retry — trade-offs?
  • How do you preserve ordering when skipping poison pills?
d08-q08When would you choose Kafka versus SQS, RabbitMQ, or a synchronous API call?
First 30 seconds
Sync API for request/response latency paths. SQS for simple durable queues on AWS. Rabbit for flexible routing/work queues. Kafka for high-throughput event logs, replay, and many independent consumers.
Model answer
  1. Synchronous HTTP/gRPC when the caller needs an immediate answer and the work is short.
  2. SQS: managed queue, at-least-once, easy workers, limited fan-out/replay story — great for job queues.
  3. RabbitMQ: routing keys, competing consumers, classic work-queue patterns; not an infinite retained log by default.
  4. Kafka: durable partitioned log, consumer groups, replay from offsets, high throughput event streaming and fan-out.
  5. Don't use Kafka as a RPC substitute; don't use sync HTTP for bursty fan-out work that can be async.
Say it out loud
Say it spoken

Sync for immediate answers, SQS/Rabbit for work queues, Kafka when I need a replayable event log and independent consumer groups at scale.

Traps / weak answers
  • Using Kafka for every tiny async job
  • Using sync calls for multi-minute workflows
  • Assuming SQS gives the same replay model as Kafka
Follow-ups
  • When is Kinesis a better AWS-native fit than Kafka?
  • How do you bridge Kafka to SQS consumers?
d08-q09How would you evolve an event schema without breaking existing consumers?
First 30 seconds
Prefer additive, backward-compatible changes with a schema registry — consumers must tolerate new fields; removals need a coordinated expand-contract.
Model answer
  1. Use Avro/Protobuf/JSON Schema with a registry and compatibility mode (BACKWARD/FORWARD/FULL) enforced in CI.
  2. Safe changes: add optional fields with defaults; avoid renaming/removing/changing types without a version plan.
  3. Expand-contract: publish both old and new fields, upgrade consumers, then drop old fields.
  4. Include eventType + schemaVersion in envelopes; don't overload one event name with incompatible meanings.
  5. Test consumers against new schemas in pipeline; canary producers first.
Say it out loud
Say it spoken

Additive evolution under registry compatibility rules. Breaking changes take expand-contract and versioned event types — never silent field deletes.

Traps / weak answers
  • Renaming fields in place
  • No compatibility checks in CI
  • Reusing event names for different semantics
Follow-ups
  • FORWARD vs BACKWARD compatibility — who upgrades first?
  • How do you handle poisoned messages with unknown schema versions?
d08-q10How would you use the outbox pattern to keep database state and published events consistent?
First 30 seconds
In the same Postgres transaction as the business write, insert an outbox row; a separate publisher drains the outbox to Kafka so you never dual-write across two systems unsafely.
Model answer
  1. Problem: commit DB then fail to publish (or vice versa) ⇒ inconsistency.
  2. Solution: BEGIN; business rows + INSERT outbox(event); COMMIT.
  3. Publisher polls outbox (or CDC) and produces to Kafka; mark published / delete with idempotent produce.
  4. Consumers remain idempotent; outbox publisher must handle retries without dup chaos (idempotent produce keys).
  5. Observe lag between outbox insert and Kafka publish; alert on stuck rows.
Diagram
sequenceDiagram
  App->>Postgres: TX business + outbox
  Publisher->>Postgres: read outbox
  Publisher->>Kafka: produce
  Publisher->>Postgres: mark published
Code / ops
sql
BEGIN;
UPDATE orders SET status = 'paid' WHERE id = $1;
INSERT INTO outbox (id, topic, payload) VALUES ($2, 'orders', $3);
COMMIT;
Nest / Node: Implement outbox publisher as a Nest worker; keep HTTP handlers free of Kafka produce retries.
Say it out loud
Say it spoken

Outbox: one DB transaction for state + event row, async relay to Kafka. No dual-write hope.

Traps / weak answers
  • Publishing to Kafka inside the request without an outbox
  • Deleting outbox rows before Kafka ack
  • No metrics on outbox depth
Follow-ups
  • Polling vs Debezium CDC for outbox?
  • How do you ensure exactly-once produce from the publisher?

03  Self-check

Kafka consumer groups scale parallelism primarily by:
Within a group, each partition is consumed by at most one consumer; more consumers than partitions sit idle.
Safer offset policy when writing to Postgres:
Commit-after-success yields at-least-once with possible duplicates; commit-before risks data loss.
Partition key skew means:
Popular keys concentrate load; consumers on cold partitions stay underutilized.
Transactional outbox solves:
Write row + outbox row atomically; a publisher relays outbox events to Kafka.
