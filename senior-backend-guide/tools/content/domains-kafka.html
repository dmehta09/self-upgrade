Domain · d08

Kafka / Messaging / Event-Driven Architecture

Kafka answers center on consumer groups, lag, and delivery semantics: at-least-once is the default, so consumers must be idempotent and commit offsets after side effects succeed. Partition keys buy ordering and can buy skew. Poison messages need bounded retries and a DLQ. Prefer an outbox when DB state and events must stay aligned, and choose Kafka only when fan-out, replay, or high throughput justify it.

01  Decision cheat strip

Lagconsumer group lag = produced - committed
Deliveryat-least-once → idempotent consumer
Offsetscommit after DB success (or transactional outbox)
Orderingper partition key only
Poisonretry budget → DLQ, don't block partition forever
Consistencytransactional outbox > dual-write

d08-q01A Kafka consumer is processing messages slower than producers are publishing them. How would you diagnose and scale it?
First 30 seconds
I'd check consumer group lag by partition, see whether we're CPU-bound in processing or blocked on I/O, then scale partitions/consumers or speed up the handler — lag is the north star.
Model answer
  1. Clarify: backlog is consumer group lag (produced − committed) growing over time — diagnose whether every partition lags or one hot partition does before scaling anything.
  2. Evidence: describe the group per partition; chart lag age and records; profile handler time (DB, HTTP, serialization, commit sync vs async, batch size).
  3. Scale horizontally only with headroom: more consumers help only up to partition count; plan partition increases carefully because they change key→partition mapping for new messages.
  4. Tradeoff: make each message cheaper (batch DB writes, pipeline, fewer round-trips) vs adding partitions/ops complexity — optimize before you re-partition production topics.
  5. Skew failure mode: one partition lags while others are idle — more consumers cannot share that partition; fix keying or isolate whales.
  6. Fetch/batch failure mode: huge fetch sizes that look like throughput wins can spike GC and DB pools — measure end-to-end, not only poll rate.
  7. Fix path: remove per-message chatty I/O, then add partitions if parallelism is the bottleneck, then add consumers to match.
  8. Prevent/ops: alert on lag SLO (records and age), per-partition imbalance, and handler p95; page when lag age breaches the business freshness budget.

  Scope -->|one| Skew[Key skew / whale]
  Prof --> Cheap[Cheapen message]
  Prof --> Parts[Add partitions then consumers]

  • Adding consumers without adding partitions — idle consumers and unchanged lag

d08-q02A consumer processes the same event twice. How should the application handle duplicates?
First 30 seconds
Treat duplicates as normal under at-least-once. Make processing idempotent with a dedupe key stored where the side effect lives.
Model answer
  1. Clarify: under at-least-once, rebalances, retries, and commit failures make duplicates normal — design for them, do not treat them as broker bugs.
  2. Idempotency key: stable event id / orderId+type / producer UUID unique per business effect; never mint a new UUID inside the consumer on each attempt.
  3. DB side effects (inbox pattern): INSERT processed_events(event_id) with UNIQUE in the same transaction as the business write; ON CONFLICT skip — dedupe and effect commit together.
  4. Outbox/inbox pairing: producers use outbox for reliable emit; consumers use inbox/dedupe table for reliable apply — both sides need keys when the pipe is at-least-once.
  5. Non-DB side effects: email, charge, webhook — use provider idempotency keys or Redis SET NX with TTL aligned to retry window; memory-only dedupe dies on restart.
  6. EOS scope: Kafka transactions / exactly-once reduce duplicates across Kafka←→Kafka or Kafka←→transactional sinks in-scope; they do not magically make arbitrary HTTP side effects exactly-once without app keys.
  7. Anti-pattern: commit offsets earlier to 'avoid' duplicates — that trades duplicates for silent loss.
  8. Prevent/ops: metric duplicate_skip_total vs apply_total; alert on sudden duplicate storms after rebalances; retain idempotency keys for the retry/replay window SLO.
Diagram
flowchart TD
  Redeliver[Redelivery] --> Key{idempotency key}
  Key --> DB[TX: inbox UNIQUE + business write]
  Key --> Ext[HTTP/email: provider key / Redis NX]
  DB -->|conflict| Skip[no-op + commit offset]
  DB -->|insert| Apply[apply + commit offset]
  Note1[EOS: Kafka-scoped; not a free HTTP exactly-once]
Code / ops
sql
BEGIN;
INSERT INTO processed_events (event_id) VALUES ($1)
ON CONFLICT DO NOTHING;
-- only apply side effects if insert happened (ROW_COUNT = 1)
-- UPDATE ... / business writes here
COMMIT;
-- then commit Kafka offset
-- non-DB: stripe_idempotency_key = event_id  OR  SET nx:event_id EX retry_window
Say it out loud
Say it spoken

Duplicates are expected under at-least-once, so every side effect carries a stable idempotency key. DB work uses an inbox unique constraint in the same transaction; non-DB work needs provider keys or durable SET NX. Kafka EOS narrows duplicates inside its scope — it does not replace business idempotency for arbitrary side effects.

Traps / weak answers
  • Assuming Kafka exactly-once means the business effect is exactly-once without work — EOS scope does not cover arbitrary side effects
  • Dedupe in memory only — restart or other instances re-apply the effect
  • Side effects outside the dedupe transaction — crash between apply and mark-seen double-applies
Follow-ups
  • How does Kafka EOS / transactions change this?
  • How long do you retain idempotency keys?
d08-q03A consumer updates PostgreSQL and crashes before committing its Kafka offset. What could happen?
First 30 seconds
On restart the message is redelivered. If the DB write already committed, you get a duplicate side effect unless the consumer is idempotent.
Model answer
  1. Clarify timelines: crash after Postgres COMMIT and before offset commit ⇒ broker still offers the message ⇒ redelivery ⇒ duplicate apply attempt unless idempotent.
  2. Opposite path: crash before DB commit ⇒ redelivery replays safely if the first write never landed — at-least-once favors reprocessing over loss.
  3. enable.auto.commit danger: background auto-commit can advance offsets while a batch is still processing — a crash then skips unprocessed records (loss) or creates confusing partial windows; prefer explicit commit after success.
  4. Partial batch: processing records 1..N in one poll, crash mid-batch — committed offset position decides which subset redelivers; commit only what succeeded, or use per-record commits carefully.
  5. Revoke/rebalance: partition revoke mid-handler extends the same window — another consumer may start from the last committed offset while your DB write already landed.
  6. Anti-pattern: commit offset first (or in finally before knowing DB success) ⇒ crash ⇒ message skipped ⇒ data loss.
  7. Standard fix: commit-after-success + idempotent writes (unique constraints / inbox); optionally store offsets in the DB transaction for a single commit point.
  8. Prevent/ops: disable risky auto-commit on stateful consumers; metric rebalance rate and duplicate applies; alert when commit lag after DB success grows; test kill -9 mid-batch in staging.
Diagram
sequenceDiagram
  Consumer->>Postgres: COMMIT business write
  Note over Consumer: crash / revoke before offset commit
  Consumer->>Kafka: (offset not committed)
  Consumer->>Kafka: rebalance / restart
  Kafka-->>Consumer: redeliver same records
  Consumer->>Postgres: idempotent apply (inbox UNIQUE)
Code / ops
text
# prefer explicit commits
enable.auto.commit=false
# for record in batch:
#   db_tx.apply_idempotent(record)
# consumer.commit(offsets_up_to=last_success)  # after DB success only
# on revoke: stop work; do not commit unfinished records
Nest / Node: Enable graceful shutdown that finishes the current record and commits before exit when possible.
Say it out loud
Say it spoken

If Postgres committed and the offset did not, redelivery is guaranteed — that is at-least-once, and idempotency makes it safe. Auto-commit, revoke mid-batch, and partial poll windows widen the hazard; committing early turns the same crash into data loss. I commit after success and rehearse kill-mid-batch.

Traps / weak answers
  • Believing 'we commit sync so duplicates can't happen' — sync commit after DB still races with crash between the two
  • enable.auto.commit=true on stateful consumers — offsets can advance past in-flight work and lose messages
  • Committing offsets in a finally block before knowing DB success — converts crashes into silent skips
  • No unique constraints on the write path — redelivery double-applies money or emails
Follow-ups
  • How do store-offset-in-DB patterns work?
  • What happens during a rebalance mid-processing?
d08-q04How would you design an idempotent Kafka consumer?
First 30 seconds
Stable event id, transactional side effect + dedupe record, commit offsets only after success, and bounded retries for poison messages.
Model answer
  1. Clarify: idempotent consumer means redelivery is a no-op for the business effect — not that Kafka will never deliver twice.
  2. Require producers to send a unique eventId (or deterministic hash of natural key + revision); consumers must not generate a new key per attempt.
  3. In one DB transaction: insert dedupe/inbox row (UNIQUE eventId) + apply business writes; skip cleanly on conflict.
  4. External calls: only with their own idempotency keys; otherwise move side effects behind an outbox or make them safely retryable.
  5. Offset policy: commit Kafka offsets only after the transaction succeeds, or write offsets into the same DB transaction — never auto-commit ahead of work.
  6. Poison path: bounded retries then DLQ + commit/skip so one bad record cannot stall the partition forever.
  7. Tradeoff: store-offset-in-DB simplifies atomicity vs dual commit points; slightly more ops complexity for the offset table.
  8. Prevent/ops: metrics for duplicate skips, DLQ depth, handler failures, and lag; alert when poison rate or DLQ backlog breaches SLO.
Diagram
flowchart TD
  A[Poll] --> B{eventId seen?}
  B -->|yes| C[Skip / commit]
  B -->|no| D[TX: side effect + mark seen]
  D --> E[Commit offset]
  D -->|fail N times| F[DLQ + commit/skip]
Code / ops
sql
BEGIN;
INSERT INTO inbox(event_id) VALUES ($1) ON CONFLICT DO NOTHING;
-- if inserted: apply writes
COMMIT;
-- commit offset only after COMMIT succeeded
Nest / Node: Nest/KafkaJS: disable auto-commit or commit explicitly after business TX.
Say it out loud
Say it spoken

An idempotent consumer pairs a stable event id with a transactional inbox and the business write, then commits offsets only after success. External calls need their own keys, and poison messages get a retry budget then DLQ so the partition keeps moving. Duplicate-skip and DLQ depth metrics prove the design under rebalances.

Traps / weak answers
  • Idempotency key that's not unique across retries (e.g. random UUID generated in consumer) — every retry looks new
  • External payment call inside handler without provider idempotency key — double charge on redelivery
  • Infinite retry blocking the partition — one poison message stops all later offsets

d08-q05How would you choose a Kafka partition key for an order or user domain?
First 30 seconds
Pick a key that preserves the ordering you need and spreads load — usually orderId for order lifecycle, userId for per-user streams — and watch for hot keys.
Model answer
  1. Clarify: Kafka ordering is per partition only — the key chooses both the ordering scope and the load distribution.
  2. Use orderId when order state-machine causality matters; userId when per-user sequencing (feeds, balances) matters — document the choice so all producers agree.
  3. Evidence of fit: enough distinct keys to utilize partitions; cardinality too low (status, country) creates permanent skew.
  4. Tradeoff: a single global key serializes the topic for total order vs kills throughput; random keys maximize spread vs destroy per-entity order.
  5. Hot-key failure: celebrity userId/orderId pins load to one partition — plan salting or isolation knowing you sacrifice that key's strict order if you salt.
  6. Null/empty keys: sticky or round-robin behavior may break ordering assumptions producers thought they had.
  7. Migration: changing keys mid-stream splits an entity across partitions — needs a cutover plan, not a silent config flip.
  8. Prevent/ops: monitor produce bytes and lag per partition; alert on imbalance; keep producer guidelines in the schema/contract review.
Diagram
flowchart LR
  E1[order events] -->|key=orderId| P[same partition = order]
  E2[user feed] -->|key=userId| Q[same partition = user]
  Bad[key=status] --> Skew[hot partition]
Code / ops

producer.send({ topic: 'orders', key: orderId, value: event })

Say it out loud
Say it spoken

Partition key equals ordering scope: orderId for order timelines, userId for user timelines — never one key for the whole topic and never a low-cardinality field. I watch per-partition lag for celebrity skew and treat key changes as migrations. Producer agreement on the key is part of the contract.

Traps / weak answers
  • Random keys when you needed per-entity ordering — state machines race across partitions
  • Using a low-cardinality status field as key — permanent hot partitions and idle ones
  • Changing key mid-stream without a migration plan — splits entity history and breaks consumers

d08-q06One Kafka partition is receiving much more traffic than the others. How would you diagnose and fix the imbalance?
First 30 seconds
That's key skew. I'd measure produce rates per partition, find the hot keys, then re-key, split whales, or add processing isolation — more consumers alone won't fix one hot partition.
Model answer
  1. Clarify: imbalance is key skew — one partition's bytes-in/message rate/lag dominates while sibling partitions idle.
  2. Evidence: broker partition metrics, consumer lag heatmap, and sampled keys from the hot partition to find celebrity userId/orderId or a constant producer key.
  3. Fix options: higher-cardinality key; salt hot keys (accept lost per-key order); dedicated topic/consumer for whales; split entity processing.
  4. Tradeoff: salting spreads load vs breaks ordering for that entity; isolation preserves order for the whale on a dedicated path at ops cost.
  5. Failure mode: adding consumers expecting the hot partition to split — within a group one partition still has one owner.
  6. Increasing partitions redistributes new keys but will not split an existing hot key's stream without changing the key.
  7. Producer hygiene: ban constant keys and document sticky partitioning behavior so 'helpful' defaults do not recreate skew.
  8. Prevent/ops: dashboards for partition imbalance ratio; alert when one partition's lag age diverges; review top keys periodically.
Diagram

  Fix --> Rekey[Higher cardinality]

d08-q07How would you design retries without allowing one poison message to block unrelated processing?
First 30 seconds
Bounded retries with backoff, then DLQ — never infinite retry on the same record while holding up the partition.
Model answer
  1. Clarify: within a partition, processing is sequential for a single consumer — infinite retry on one poison record blocks every later offset.
  2. Classify errors: transient (timeouts, 429, deadlock) vs permanent (deserialization, schema, bad payload) — only transients enter the retry budget.
  3. Retry with exponential backoff and max attempts (headers or side store); avoid sleeping the consumer thread so long that heartbeats miss and cause rebalances.
  4. After budget: publish to DLQ/retry topic with reason/payload/headers; commit/skip the original so the main partition advances.
  5. Tradeoff: in-place retry preserves order vs can stall; retry topic isolates poison at the cost of ordering across the delay.
  6. Ops: process DLQ asynchronously with alerts and a documented replay runbook — DLQ without owners is a silent trash can.
  7. Ordering caveat: skipping poison acknowledges that later messages may apply without the failed one — make that business-visible.
  8. Prevent/ops: metric retry_count, DLQ depth, poison rate; alert on DLQ backlog SLO; game-day inject a bad payload and verify lag on healthy records stays flat.
Diagram
flowchart TD
  Msg[Record] --> Err{error type}
  Err -->|transient| Retry[backoff ≤ N]
  Err -->|permanent| DLQ
  Retry -->|exhausted| DLQ[DLQ + commit/skip]
  Retry -->|success| Commit
  DLQ --> Alert[alert + replay tools]
Code / ops
python
# pseudo
for attempt in range(MAX):
    try:
        handle(record); commit(); break
    except Transient:
        sleep(backoff(attempt))  # keep short vs session timeout
    except Permanent:
        produce_dlq(record, reason); commit(); break
else:
    produce_dlq(record, 'retries_exhausted'); commit()
Nest / Node: KafkaJS eachMessage handlers should not throw endlessly without a DLQ path.
Say it out loud
Say it spoken

I retry only transient errors with a budget, then DLQ and commit forward so one poison pill cannot stall the partition. Long sleeps that miss heartbeats cause rebalances that make things worse. DLQ depth and a replay runbook are part of the design, not afterthoughts.

Traps / weak answers
  • Infinite retries on deserialization errors — partition lag grows forever on undrinkable poison
  • Blocking the consumer thread on long sleeps — missed heartbeats → rebalance storms
  • DLQ without alerts or replay procedure — failures become invisible data loss
Follow-ups
  • Retry topic vs in-place retry — trade-offs?
  • How do you preserve ordering when skipping poison pills?
d08-q08When would you choose Kafka versus SQS, RabbitMQ, or a synchronous API call?
First 30 seconds
Sync API for request/response latency paths. SQS for simple durable queues on AWS. Rabbit for flexible routing/work queues. Kafka for high-throughput event logs, replay, and many independent consumers.
Model answer
  1. Clarify the need: immediate answer, simple work queue, flexible routing, or replayable multi-consumer event log — the tool follows the shape of the problem.
  2. Synchronous HTTP/gRPC when the caller needs a short, immediate response and fan-out is not required.
  3. SQS: managed at-least-once queue, easy workers, limited fan-out/replay — strong default for AWS job queues without log semantics.
  4. RabbitMQ: routing keys, competing consumers, classic work-queue patterns; not an infinite retained log by default.
  5. Kafka: durable partitioned log, consumer groups, offset replay, high throughput streaming and independent fan-out — justified when those properties matter.
  6. Tradeoff: Kafka ops and conceptual weight vs SQS simplicity; sync simplicity vs burst absorption and decoupling.
  7. Failure mode: Kafka-for-every-tiny-job or sync HTTP for multi-minute fan-out workflows — wrong abstraction tax shows up as cost and incidents.
  8. Prevent/ops: document selection criteria in ADRs; measure whether consumers actually replay/fan-out; revisit if a Kafka topic has one consumer and no retention need.
Diagram
flowchart TD
  Need{need}
  Need -->|immediate answer| Sync[HTTP/gRPC]
  Need -->|AWS job queue| SQS
  Need -->|routing / work queue| Rabbit
  Need -->|replay + fan-out log| Kafka
Say it out loud
Say it spoken

I use sync APIs when the caller needs an immediate answer, SQS or Rabbit when I need a work queue, and Kafka when I need a replayable partitioned log with independent consumer groups at scale. Kafka is not a default RPC substitute, and SQS is not Kafka's replay model. The ADR should state which property justified the choice.

Traps / weak answers
  • Using Kafka for every tiny async job — pays cluster and ops cost without replay/fan-out value
  • Using sync calls for multi-minute workflows — ties client timeouts to backend batch work
  • Assuming SQS gives the same replay model as Kafka — retention and consumer-group semantics differ

d08-q09How would you evolve an event schema without breaking existing consumers?
First 30 seconds
Prefer additive, backward-compatible changes with a schema registry — consumers must tolerate new fields; removals need a coordinated expand-contract.
Model answer
  1. Clarify: event schemas are contracts across teams — breaking changes without expand-contract strand old consumers on poison payloads.
  2. Use Avro/Protobuf/JSON Schema with a registry and compatibility mode (BACKWARD/FORWARD/FULL) enforced in CI before produce.
  3. Safe changes: add optional fields with defaults; avoid rename/remove/type changes without a version plan.
  4. Expand-contract: publish both old and new fields, upgrade consumers, then drop old fields — never silent deletes.
  5. Envelope: eventType + schemaVersion; do not overload one event name with incompatible meanings.
  6. Tradeoff: BACKWARD lets consumers upgrade first vs FORWARD favors producers first — pick from who you can coordinate.
  7. Failure mode: in-place renames and reused event names cause deserialization poison and DLQ floods.
  8. Prevent/ops: canary producers; contract tests against new schemas in pipeline; alert on schema-id / deserialization error rate.
Diagram

d08-q10How would you use the outbox pattern to keep database state and published events consistent?
First 30 seconds
In the same Postgres transaction as the business write, insert an outbox row; a separate publisher drains the outbox to Kafka so you never dual-write across two systems unsafely.
Model answer
  1. Clarify the dual-write timeline: commit DB then fail to publish (or publish then fail to commit) leaves state and events permanently diverged — hope is not a protocol.
  2. Outbox fix: BEGIN; business rows + INSERT outbox(id, topic, payload, headers); COMMIT — one atomic commit point in Postgres.
  3. Publisher drains via poll (SELECT … FOR UPDATE SKIP LOCKED) or CDC (Debezium); produce to Kafka; mark published only after broker ack.
  4. Tradeoff: CDC lowers poll lag and load vs more infra; polling is simpler to operate vs higher publish latency under load.
  5. Idempotent produce: use stable Kafka key + idempotent producer (and/or outbox row id as key) so publisher retries do not create unbounded logical dup chaos for consumers.
  6. Consumers stay idempotent anyway — outbox reduces dual-write loss/duplication at the source but does not remove at-least-once on the consume side.
  7. Failure mode: delete outbox rows before Kafka ack, or publish from the HTTP request without outbox — recreates the dual-write race.
  8. Prevent/ops: lag SLO from outbox inserted_at → Kafka produce; alert on outbox depth and oldest unpublished age; dashboard dual-write forbidden in code review.
Diagram
sequenceDiagram
  App->>Postgres: TX business + outbox INSERT
  Note over App,Postgres: dual-write avoided here
  Publisher->>Postgres: poll/CDC outbox
  Publisher->>Kafka: produce idempotent key=outbox.id
  Publisher->>Postgres: mark published after ack
  Note over Publisher,Kafka: lag SLO: inserted_at → produce
Code / ops
sql
BEGIN;
UPDATE orders SET status = 'paid' WHERE id = $1;
INSERT INTO outbox (id, topic, payload) VALUES ($2, 'orders', $3);
COMMIT;
-- publisher: produce(key=outbox.id) then mark published AFTER ack
-- never DELETE outbox before Kafka ack
Nest / Node: Implement outbox publisher as a Nest worker; keep HTTP handlers free of Kafka produce retries.
Say it out loud
Say it spoken

Outbox keeps state and events aligned by writing both in one Postgres transaction, then relaying asynchronously with idempotent produce keys. CDC versus poll is an ops tradeoff on lag and complexity, not a different consistency story. I alert on outbox depth and publish lag SLO so a stuck publisher is visible before consumers starve.

Traps / weak answers
  • Publishing to Kafka inside the request without an outbox — classic dual-write race on crash
  • Deleting outbox rows before Kafka ack — crash loses the event after DB commit
  • No metrics on outbox depth / publish lag — stuck relay looks like 'Kafka is fine' while events never leave
Follow-ups
  • Polling vs Debezium CDC for outbox?
  • How do you ensure exactly-once produce from the publisher?

03  Self-check

Kafka consumer groups scale parallelism primarily by:
Within a group, each partition is consumed by at most one consumer; more consumers than partitions sit idle.
Safer offset policy when writing to Postgres:
Commit-after-success yields at-least-once with possible duplicates; commit-before risks data loss.
Partition key skew means:
Popular keys concentrate load; consumers on cold partitions stay underutilized.
Transactional outbox solves:
Write row + outbox row atomically; a publisher relays outbox events to Kafka.
