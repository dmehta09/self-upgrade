Flashcards

Leitner-style deck from every “say it” close plus common traps. Flip, mark Known/Review, shuffle unknowns first.

01  Scenario deck

0/0 known

  • Your request flow is DNS -> AWS Load Balancer -> Nginx -> EC2 -> Docker -> application. You receive a 502 response. How will you debug it step by step?

    A 502 means some hop returned an invalid gateway response — usually connection refused, reset, or crash mid-write — not a patient timeout. I correlate one request id across ALB and nginx, prove target health and local curl to the container, then fix the dead upstream before touching application business logic.

  • Users intermittently receive 504 responses, while application health checks remain green. How will you determine where the timeout occurs?

    Intermittent 504s with green health are almost always a timeout-budget mismatch on the real path — slow dependency or saturated workers — not a dead process. I line up ALB and nginx timings for one request id, find which timer fired first, then fix the slow work instead of blindly raising every timeout.

  • Nginx is running, but one API route returns the Nginx default 404 page instead of the backend response. How will you trace the request?

    An nginx-branded 404 almost always means the wrong server or location won, not that FastAPI threw NotFound. I prove Host and URI selection with nginx -T, curl the container with the same path, and fix proxy_pass or location precedence before changing application routes.

  • An application works when called directly on its port but fails through the load balancer. What would you check and in what order?

    If localhost works and the load balancer fails, I treat the app as innocent until proven otherwise and walk listener → target group → security group → health check → nginx. Most of these incidents are wrong port, wrong health path, or SG rules — not application bugs.

  • One EC2 instance behind the load balancer is failing while the others work normally. How would you isolate the fault?

    One bad instance is a gift — I drain it from the target group immediately, then diff that host against a healthy twin. Disk full, drifted container, or AZ networking usually explains it; I don't restart the whole fleet first.

  • Production API latency increases from 100 ms to 2 seconds immediately after a deployment. How would you prove whether the deployment caused it?

    Correlation with deploy time isn't enough — I need version-dimensioned latency and a successful rollback or canary contrast. If only the new SHA is slow and reverting restores p95, the deployment caused it; then I dig into the diff for queries, cache, or blocking I/O.

  • Your API returns 200 responses but users report that requests occasionally hang until the client times out. How would you investigate?

    Occasional hangs aren't visible on a 200-rate graph — I need in-flight age and traces. Usually every worker is stuck on a slow dependency or a sync call in an async path, so clients time out while health stays green and some requests still finish as 200 late.

  • The service has normal CPU and memory but p95 and p99 latency suddenly increase. What signals would you inspect?

    When resources look fine but p95 explodes, the process is blocked on I/O or locks. I split latency by dependency and pool wait — the answer is usually a slow DB, exhausted connection pool, or outbound API — not 'add more CPU'.

  • A container repeatedly restarts in production. How would you determine whether the cause is OOM, health checks, process crashes, or infrastructure?

    Restart loops are a taxonomy problem: OOMKilled, exit code, or probe kill. I read the container's last state and events before changing application code, then fix the matching cause — memory limit, bad liveness path, crash on boot, or a sick node.

  • A production problem occurs only during high concurrency and cannot be reproduced with one request. How would you investigate it?

    If it only fails under concurrency, I refuse to debug with one request. I ramp load, watch connection pools and locks, and look for races or exhaustion — then I ship a concurrent regression test so we don't 'fix' it with a quiet afternoon.

  • A class has an API method wrapped by a logging function, but the logging code runs immediately instead of after the API response. What could be wrong?

    If the log says completed before the response exists, the wrapper didn't await. Async methods need async-aware decorators that await the call, then log — otherwise you only logged scheduling the coroutine.

  • A function calls an async method without await. What behavior would you expect?

    No await means no wait — in Python the coroutine never runs; in Node the Promise is fire-and-forget. I treat un-awaited async calls as bugs unless I deliberately create a supervised background task.

  • A decorator logs execution time as almost zero even though the wrapped API takes several seconds. How would you debug the decorator?

    A decorator that reports zero on a multi-second API didn't await. Timing must wrap the awaited call; otherwise you measured how long it took to build a coroutine object.

  • A logging wrapper prints 'completed' before an async method actually completes. How would you redesign it?

    I redesign the wrapper so 'completed' can only print after await returns or raises. If we need background work, that's an explicit supervised task with its own completion log — not a sneaky missing await.

  • A try/catch catches synchronous errors but misses failures from an async operation. What is wrong?

    try/except only catches what runs inside it. If you don't await, the failure happens on another turn of the event loop and your catch is already gone — await inside the try, or supervise the task explicitly.

  • A Node.js service uses array.forEach(async item => ... ) and expects the caller to wait for all operations. What is wrong?

    forEach plus async is a classic false sense of waiting — the loop doesn't await. I use for...of or Promise.all with a concurrency cap, and I make sure the request handler awaits that aggregate Promise.

  • You need to call five independent third-party APIs from a FastAPI endpoint. How would you execute them?

    Five independent APIs are a gather with timeouts, not a chain of awaits. I share an AsyncClient, fail fast on the budget that matters to the user, and degrade or error based on whether each dependency is critical.

  • You need to process 10,000 async operations but only want 20 in flight at any time. How would you design the concurrency limit?

    Ten thousand coroutines without a semaphore is an outage. I cap in-flight work at twenty with a semaphore or worker queue, sized to the dependency's quota and our connection pools.

  • A Node.js endpoint uses Promise.all for 1,000 outbound requests and production becomes unstable. What could be happening?

    Promise.all of a thousand outbound calls is a thundering herd at yourself and your vendor. Cap concurrency, set timeouts, and don't do bulk fan-out on the user-facing request path.

  • An async endpoint performs CPU-heavy work and blocks unrelated requests. How would you redesign it?

    Async isn't parallel CPU. I pull heavy compute off the event loop into a process pool or job queue and make the HTTP API async in the workflow sense — 202 and status — so unrelated requests keep moving.

  • Your application integrates three third-party APIs and one becomes slow. How would you prevent it from degrading the entire request path?

    One slow vendor should not own our worker pool. I give it its own timeout and concurrency bulkhead, degrade that feature when the breaker opens, and keep the rest of the request healthy.

  • A third-party API normally responds in 200 ms but sometimes takes 15 seconds. How would you design the integration?

    I won't budget 15 seconds for a call that is usually 200 ms — that turns rare vendor lag into our outage. Short timeout, safe fallback, and move non-critical work async.

  • A payment provider times out, but you do not know whether the payment was actually processed. How would you design the workflow?

    After a payment timeout I assume the charge might have succeeded. Same idempotency key, pending state, reconcile via status or webhook — never a blind second capture.

  • An external API returns intermittent 5xx errors. How would you decide whether and how to retry?

    Intermittent 5xx gets a small number of jittered retries only when safe. No key, no retry on money-moving POSTs — and I never retry harder than the dependency can handle.

  • When can retries make an outage worse?

    Retries are a privilege, not a default. Without jitter, budgets, and idempotency, they turn a vendor hiccup into a self-DDoS — so I cap, spread, and trip a breaker.

  • One dependency is unavailable for 30 minutes. How should your application behave for requests that depend on it?

    For a half-hour outage I fail fast or go degraded — I don't burn workers on hopeless retries. Critical flows get an honest 503 or queued processing; everything else serves cache or turns the feature off.

  • How would you implement circuit breaking for an unreliable dependency?

    Circuit breaking is fail-fast with a recovery probe. I open on sustained errors, stop calling the vendor, serve fallback, then half-open carefully so we don't flap or storm.

  • Two external providers offer the same capability. How would you design failover between them?

    Failover is an interface plus safe ownership of each operation. I trip off the primary when its breaker opens, stick writes to one provider per intent, and keep the secondary warm with synthetics so failover isn't a surprise.

  • A provider imposes strict rate limits and your traffic suddenly increases 20x. How would you protect your system?

    When traffic jumps 20x against a strict vendor quota, I rate-limit outbound calls and queue the rest. Better an honest 503 or delayed job than a ban and a total outage.

  • How would you make an external API integration idempotent from your application's point of view?

    From our side, idempotency is a durable key tied to business intent, unique constraints, and deduped webhooks. Retries may hit the network twice, but inventory and money move once.

  • How would you design an idempotent create-order API?

    Idempotent create-order is a durable key plus unique constraint, not hope. Same key and body returns the same order; same key different body is 409; payments reuse the key so retries don't double-charge.

  • An API operation can take 20 minutes. Would you keep the HTTP request open? How would you design it?

    Twenty minutes does not belong on an open HTTP socket. I accept with 202, process in a worker, and let the client poll or get a webhook — proxies won't punish us with 504s.

  • How would you design an asynchronous job-submission API with job status tracking?

    A job API is a state machine with a queue behind it. Clients get an id immediately, poll a boring status resource, and we make submission idempotent so retries don't duplicate work.

  • How would you design pagination for a table containing hundreds of millions of rows?

    At hundreds of millions of rows I paginate with keyset cursors on an indexed sort key, not OFFSET. Clients get a next cursor; I don't COUNT the galaxy on every page view.

  • When would you choose cursor pagination over offset pagination?

    Cursors for scale and stability; offset for small, static lists. If users can page into the middle of millions of rows, offset is already the wrong design.

  • How would you design consistent error responses across a large FastAPI/NestJS codebase?

    Consistency comes from a single envelope and centralized handlers. Routes throw typed domain errors; the framework edge turns them into the same JSON shape with a correlation id.

  • How would you separate validation errors, business errors, dependency errors, and unexpected errors?

    Validation is the client's fault, business rules are domain conflicts, dependencies are someone else's SLO, and unexpected is ours. Separating them in types and status codes makes both UX and paging correct.

  • One endpoint is generating excessive database traffic. How would you redesign it?

    I don't 'add indexes' blindly — I count queries per request. Usually it's N+1 or a hot list without cache; I batch, cache, or precompute a read model so one user action isn't a hundred SQL round-trips.

  • How would you structure a large FastAPI or NestJS application so controllers do not contain business logic?

    If a route function knows SQL and discount rules, the structure is wrong. Controllers adapt HTTP; services own business decisions; repositories speak to the database — FastAPI Depends and Nest DI both support that if we use them with discipline.

  • How would you decide what belongs in the synchronous request path versus asynchronous processing?

    Synchronous means the user can't proceed without it. Emails, indexes, and 20-minute reports are async. I keep the request path short, durable where it matters, and honest about eventual consistency.

  • A PostgreSQL query is fast with one million rows but becomes slow with one hundred million. How would you investigate?

    At 100M the plan or cache behavior changed. EXPLAIN ANALYZE with BUFFERS tells me if it's a bad join, missing index, or I/O — I fix the plan before throwing hardware at it.

  • How would you use EXPLAIN or EXPLAIN ANALYZE to debug a slow PostgreSQL query?

    I run EXPLAIN ANALYZE with BUFFERS, find the hottest node, and fix estimate skew or I/O — not guesswork indexes.

  • Two users try to purchase the last available item at exactly the same time. How would you prevent overselling?

    I never trust check-then-update in app memory. One conditional UPDATE or SELECT FOR UPDATE on the stock row, short transaction, sold-out if zero rows.

  • When would you use optimistic locking versus pessimistic locking?

    Optimistic version columns when collisions are rare; FOR UPDATE when I know two writers will fight over the same row and must serialize.

  • A read-then-update workflow produces lost updates under concurrency. How would you redesign it?

    Lost updates are a smell of check-then-act. I make the write atomic or version it so concurrent writers cannot silently clobber each other.

  • How would you choose between READ COMMITTED, REPEATABLE READ, and SERIALIZABLE for a business operation?

    I stay on READ COMMITTED unless the business needs a snapshot or true serializability — and I design for retries when I raise isolation.

  • Two transactions deadlock in production. How would you investigate and reduce the likelihood of future deadlocks?

    Deadlocks are lock-order cycles. I read the log, enforce a global lock order, shrink transactions, and retry the loser idempotently.

  • Your application opens far more PostgreSQL connections than expected. How would you find the source and fix it?

    Connection storms are usually pool math or leaks. I count pg_stat_activity, fix pool sizing, and put PgBouncer in front so Postgres isn't the connection radiator.

  • How would you perform a schema migration or index creation on a large production table without unacceptable downtime?

    No big-bang locks on hot tables. CONCURRENTLY for indexes, batched backfills for data, additive schema first.

  • How would you design a zero-downtime database migration when old and new application versions must run simultaneously?

    Rolling deploys need expand-contract. Schema stays compatible with both versions until the fleet and backfill are done — then contract.

  • A MongoDB collection has 100 million documents and a frequently used query became slow. What would you inspect first?

    First explain executionStats. If docsExamined ≫ nReturned, the index or query shape is wrong — I fix that before talking about sharding.

  • How would you decide between embedding and referencing for a MongoDB document model?

    Modeling follows queries. Embed co-read bounded data; reference shared or unbounded data — and denormalize snapshots when history must not change.

  • An aggregation pipeline is slow in production. How would you identify the expensive stage and optimize it?

    Find the expensive stage, filter early with an index, and treat $lookup/$unwind/$group as suspects until proven cheap.

  • How would you choose MongoDB indexes from real query patterns rather than from the schema alone?

    Indexes follow the workload. I rank real queries, build compound keys with ESR, and delete indexes that only look good on the schema.

  • A document contains an array that grows indefinitely and is frequently queried. How would you redesign the model?

    Infinite arrays don't belong in one document. Child collection or time buckets, maybe a small embedded preview for the hot read.

  • How would you choose a shard key for a high-write MongoDB workload?

    Shard key = cardinality + even writes + targeted reads. I won't shard on status or plain timestamps that create hot shards.

  • What characteristics can make a MongoDB shard key a hotspot?

    Hotspots come from monotonic inserts, low cardinality, or traffic skew. The key must spread writes, not just unique them.

  • A query becomes scatter/gather in a sharded cluster. What does that mean for performance and how would you reduce it?

    Scatter-gather fans out to every shard. Hot paths must be targeted by shard key — otherwise each read taxes the whole cluster.

  • You need to update tens of millions of MongoDB documents. How would you make the migration safe, resumable, and observable?

    Big migrations are checkpointed bulkWrite loops — idempotent, throttled, observable, and resumable from last _id.

  • How would you design multi-tenant data isolation in MongoDB?

    tenantId on every doc and every query, indexes and shard key aligned, auth-bound tenant — escalate to DB- or cluster-per-tenant when compliance or noise demands it.

  • When should an API use Redis instead of querying PostgreSQL directly?

    Redis for hot, slightly stale reads and coordination. Postgres for truth and transactions — I cache when the hit rate and latency win are proven.

  • Redis goes down during peak traffic. How should the application degrade?

    Redis down: timeout fast, degrade by feature, and cap DB fallback — an uncapped fallback is an outage multiplier.

  • How would you implement cache-aside for a read-heavy endpoint?

    Cache-aside: GET, miss to DB, SET with TTL; invalidate on write; singleflight so misses don't herd.

  • How would you handle stale cache data after a PostgreSQL update?

    Commit first, then invalidate or SET the new value. TTL is the safety net for races and missed deletes.

  • What is a cache stampede scenario and how would you prevent it?

    Stampede = thundering herd on miss. One refresher via lock or singleflight; others wait or get stale.

  • A popular Redis key becomes a hot key. How would you handle it?

    Hot keys need L1 caching or key sharding — scaling the cluster alone won't help if one key owns one slot.

  • How would you choose TTLs for data with different freshness requirements?

    TTL is a freshness SLA. Short + invalidate for volatile data, longer for static, jitter everything, short negative cache for misses.

  • How would you design a distributed per-user and per-IP rate limiter using Redis?

    Per-user and per-IP keys with atomic INCR or sliding-window Lua, checked early in the middleware, with an explicit Redis-down policy.

  • Two application instances update the same Redis-based counter concurrently. How would you make the operation safe?

    INCR or Lua — not get-add-set. Redis atomic ops are the concurrency control.

  • How would you prevent a cache outage from causing a database avalanche?

    Avalanche prevention is bounded fallback: breakers, semaphores, stale serve, and shedding — not 'just query Postgres.'

  • A Kafka consumer is processing messages slower than producers are publishing them. How would you diagnose and scale it?

    Lag tells me I'm falling behind. I find whether it's handler time or skew, then add partitions/consumers or make each message cheaper.

  • A consumer processes the same event twice. How should the application handle duplicates?

    Duplicates are expected. I key every side effect and upsert under a unique constraint so the second delivery is a no-op.

  • A consumer updates PostgreSQL and crashes before committing its Kafka offset. What could happen?

    DB committed, offset not: redelivery. That's at-least-once — idempotency makes it safe; committing early makes loss possible.

  • How would you design an idempotent Kafka consumer?

    Idempotent consumer = unique event id + transactional dedupe with the side effect + offset commit after success + DLQ for poison.

  • How would you choose a Kafka partition key for an order or user domain?

    Partition key = ordering scope. orderId for order timelines, userId for user timelines — never one key for the whole topic.

  • One Kafka partition is receiving much more traffic than the others. How would you diagnose and fix the imbalance?

    Hot partition is key skew. Find the key, change keying or isolate the whale — extra consumers can't share one partition.

  • How would you design retries without allowing one poison message to block unrelated processing?

    Retry transient errors with a budget, then DLQ and move on — one bad message must not stall the partition.

  • When would you choose Kafka versus SQS, RabbitMQ, or a synchronous API call?

    Sync for immediate answers, SQS/Rabbit for work queues, Kafka when I need a replayable event log and independent consumer groups at scale.

  • How would you evolve an event schema without breaking existing consumers?

    Additive evolution under registry compatibility rules. Breaking changes take expand-contract and versioned event types — never silent field deletes.

  • How would you use the outbox pattern to keep database state and published events consistent?

    Outbox: one DB transaction for state + event row, async relay to Kafka. No dual-write hope.

  • Service A succeeds but service B fails halfway through a business workflow. How would you recover without corrupting state?

    I wouldn't reach for 2PC across services. I'd run a saga with idempotent steps and compensations keyed by a workflow id, so a mid-flight failure either retries the failed step or unwinds completed ones without corrupting inventory or money.

  • When should a system prefer strong consistency, and when is eventual consistency acceptable?

    Strong consistency for money and stock; eventual for projections and caches. I'd put the invariant in one strongly consistent write path and let read models catch up with an explicit lag budget and repair job.

  • How would you make an end-to-end workflow safe when both API requests and asynchronous messages can be duplicated?

    I'd carry one idempotency key from the HTTP API through the outbox into every consumer, with unique constraints at each write. Retries become safe no-ops instead of double side effects.

  • What does 'exactly once' mean in a practical distributed system, and where can it break down?

    I treat exactly-once as effectively-once: at-least-once delivery with an idempotent write and a dedupe key. It breaks when the side effect isn't idempotent or you ack before the durable write.

  • How would you prevent cascading failures when a downstream service becomes slow?

    Timeouts, bulkheads, and a circuit breaker—fail fast, cap in-flight calls to the sick dependency, and degrade instead of letting one slow service exhaust our pools.

  • How would you design backpressure when incoming work is greater than worker capacity?

    I'd absorb spikes in a durable queue with lag-based autoscaling, bound in-process concurrency, and return 429 at the edge when we're saturated—unbounded memory queues are not backpressure.

  • How would you design graceful load shedding during an overload event?

    Graceful shedding means dropping low-priority work early with 503/Retry-After while protecting checkout and auth. I'd trigger on lag and pool wait, not after the process is already thrashing.

  • How would you choose timeouts and retry policies across a chain of dependent services?

    Timeouts are a budget, not a single magic number. I'd slice the outer SLA across hops, propagate deadlines, and only retry when the remaining budget and idempotency allow it.

  • How would you design a job so work is not lost when a worker process crashes or the EC2 instance is terminated?

    Jobs survive crashes because the queue owns the work: visibility timeout plus heartbeat, idempotent handlers, and clean SIGTERM that releases the message. Workers are disposable.

  • How would you design a reliable scheduled job that can safely recover after missed executions?

    A reliable scheduler stores a watermark, catch-up from last success to now with idempotent chunked work, and a lock so only one leader runs. Cron alone is not recovery.

  • How would you design a highly available backend using Route 53, ALB, EC2/ECS, Nginx, PostgreSQL, Redis, and S3?

    HA for me is Multi-AZ at every hop: Route 53 to a cross-AZ ALB, private ECS/EC2 with Nginx, RDS Multi-AZ, Redis failover, and S3. One AZ loss should drop capacity, not the product.

  • How would you decide whether TLS should terminate at the load balancer or Nginx?

    I'd terminate at the ALB with ACM unless compliance forces TLS to the instance—then re-encrypt to Nginx. Either way I honor X-Forwarded-Proto for secure cookies and redirects.

  • How would you troubleshoot a request that works by IP address but not through the domain name?

    If IP works but the domain doesn't, I chase DNS first, then TLS SANs/SNI, then ALB/Nginx Host-based rules. The app is usually fine—the name path isn't.

  • How would you preserve and validate client IP information across a proxy/load-balancer chain?

    I only trust X-Forwarded-For from known load-balancer CIDRs with a fixed hop count. Spoofed client-supplied XFF is ignored so rate limits and audit logs key on the real client.

  • How would you decide between ALB, NLB, and API Gateway for a backend service?

    ALB for normal HTTP FastAPI, NLB when I need L4/PrivateLink/static IP, API Gateway when the product needs managed API edge features. I pick from requirements, not defaults.

  • How would you keep application servers private while exposing the system securely to the internet?

    Internet stops at the ALB. Apps and data stores stay in private subnets with SG chains ALB→app→RDS, egress via NAT or VPC endpoints, and admin access via SSM—not open SSH.

  • How would you design autoscaling for a backend where CPU is not a reliable signal of demand?

    When CPU lies, I scale on queue lag or concurrent requests via custom CloudWatch metrics, with slow scale-in and a floor capacity. CPU stays a backup signal only.

  • How would you make an EC2-based deployment highly available across Availability Zones?

    Multi-AZ HA means ASG+ALB across subnets, Multi-AZ data stores, and enough spare capacity that losing one AZ still meets SLO. Identical Launch Templates so replacements are boring.

  • How would you design zero-downtime deployment on EC2 behind an ALB?

    Zero-downtime on EC2+ALB is drain-then-kill: healthy new targets first, deregistration delay covering in-flight p99, and SIGTERM-aware processes. Never terminate before the ALB stops sending traffic.

  • One AWS Availability Zone fails during peak traffic. What components must fail over and what should you test beforehand?

    AZ failure is a capacity and failover event: remaining AZ apps take traffic, RDS/Redis fail over with retries, and NAT/IP capacity must already be sized. I'd prove it with a game day, not a slide.

  • How would you secure a public FastAPI or NestJS API against common abuse and unauthorized access?

    Public APIs get defense in depth: TLS, authn, authz, validation, and rate limits at the edge and in the app. Deny by default and never trust client-supplied tenancy or roles.

  • How would you design access-token and refresh-token handling for a large application?

    Short access JWTs plus rotating refresh tokens—refresh only hits the auth service, access is verified via JWKS. Rotation and short TTL limit the blast radius of theft.

  • How would you revoke a refresh token or session without forcing every user to log in again?

    I revoke at session/family granularity: kill that refresh chain in the DB and denylist access jtis if needed. Short access TTLs mean other users keep working uninterrupted.

  • How would you protect login and password-reset endpoints against brute-force attacks?

    Brute-force protection is layered rate limits, backoff/lockout, CAPTCHA at thresholds, and safe password-reset tokens—plus MFA for high privilege. Generic errors avoid account enumeration.

  • How would you enforce tenant isolation so one SaaS customer can never access another customer's records?

    Isolation starts with tenant from the token, then every SQL and S3 key is scoped to it—ideally with Postgres RLS as a seatbelt. Client-sent tenant IDs are never authoritative.

  • How would you design authorization when users can have both roles and resource-level permissions?

    Roles cover broad capabilities; relationships cover 'can edit this record'. One authorize() entry point on every mutation keeps FastAPI handlers honest and testable.

  • How would you securely handle secrets for AWS credentials, database passwords, and third-party API keys?

    IAM roles beat access keys; Secrets Manager beats .env in git. Least privilege, rotation, and CloudTrail on secret reads are the baseline.

  • A secret is accidentally committed to source control. What actions should follow?

    Rotate first—assume the secret is public. Then scrub history, audit access, redeploy, and add scanning so it can't happen silently again.

  • How would you protect a webhook endpoint from spoofed or replayed requests?

    Webhooks need HMAC over the raw body, a tight timestamp window, and event-id dedupe. Without that, anyone who can POST your URL can forge events.

  • How would you securely serve private images or documents stored in S3?

    Private bucket, authorize in FastAPI, then short-lived presigned GET—or CloudFront signed URLs at scale. No public-read ACLs on customer documents.

  • You are given a major new feature and two junior interns. How would you approach, decompose, delegate, review, and deliver it?

    I keep the risky design and integration, give juniors well-bounded slices with contracts, and review early so we don't discover architectural mistakes on merge day.

  • Requirements are ambiguous but the delivery date is fixed. How would you reduce risk before implementation?

    Fixed date plus ambiguity means write assumptions, confirm a thin slice, and protect irreversible decisions. I won't pretend uncertainty away or freeze until a perfect PRD.

  • How would you break a large feature into tasks that junior developers can implement safely and independently?

    Juniors stay safe when contracts exist first and tasks are vertical, small, and copy an established pattern. Independence without interfaces is just parallel confusion.

  • What parts of the feature would you own personally and what would you delegate?

    I keep the irreversible and high-blast-radius decisions, delegate patterned implementation, and co-own anything that can corrupt data or leak tenants. Outcome stays on me.

  • A junior engineer proposes an architecture you believe will fail under scale. How would you handle the situation?

    I challenge with scenarios and numbers, not ego. We converge on a design that survives load, and the junior still feels authorship of the fix.

  • The ideal architecture needs six weeks but the business needs something in two weeks. How would you decide what to ship?

    Two weeks means a safe thin slice plus honest debt—not a fragile full vision. Invariants stay; polish and generality wait with a dated plan.

  • A feature is almost complete when a major requirement changes. How would you reassess scope and implementation?

    Mid-flight change means pause, impact map, and explicit options with dates. I won't duct-tape incompatible requirements and call it done.

  • Two engineers are building related components and their APIs are drifting apart. How would you prevent integration problems?

    Prevent drift with a checked-in contract and CI that fails when either side changes it unilaterally. Integration week should be boring.

  • A production bug is discovered just before release. How would you decide whether to delay the release or proceed?

    Ship-or-delay is risk math: severity, blast radius, workaround, and rollback. I won't launch a known data-corrupting bug to hit a symbolic date.

  • How would you ensure a feature is operable in production, not just functionally correct in development?

    A feature isn't done until it has metrics, alerts, and a runbook. Functional demos in dev don't survive contact with production dependencies and real concurrency.

  • Trap — d01 / d01-q01: what's wrong with this instinct?

    Jumping straight into application business logic without checking ALB target health or nginx upstream errors

  • Trap — d01 / d01-q03: what's wrong with this instinct?

    Assuming the app route is missing because the browser shows 404 — without checking the response body fingerprint

  • Trap — d01 / d01-q05: what's wrong with this instinct?

    Rolling all instances when only one target is unhealthy

  • Trap — d01 / d01-q07: what's wrong with this instinct?

    Only graphing HTTP status codes and declaring the API healthy
