Services & endpoints.

A Service gives a stable virtual IP (and DNS name) in front of changing Pod IPs. Selectors populate Endpoints / EndpointSlices; kube-proxy (or equivalent) steers ClusterIP traffic to ready backends.

01 The idea

Clients dial the Service; the dataplane fans out to Pod IPs listed in EndpointSlice. Labels + readiness gate who is in the pool.

Analogy plain English

A Service is the restaurant’s front desk number. Chefs (Pods) come and go; the desk always answers the same number and hands the call to whoever is on shift (ready Endpoints). kube-proxy is the switchboard programming.

ClusterIP
Default. VIP reachable inside the cluster only.
NodePort
Opens the same high port on every node → forwards to ClusterIP backends.
LoadBalancer
Cloud (or MetalLB-style) external LB in front of NodePort/ClusterIP.
ExternalName
DNS CNAME to an outside name—no proxying of Pods.

02 Client → Service → Pod

Walk the request path. Empty Endpoints = labels wrong, wrong namespace, or Pods not Ready.

03 Types, ports, and kubectl

port is what clients dial on the Service; targetPort is the Pod/container port. They need not match numerically.

service-clusterip.yaml 
apiVersion: v1
kind: Service
metadata:
  name: api
  namespace: shop
spec:
  type: ClusterIP
  selector:
    app: api
  ports:
  - name: http
    port: 80
    targetPort: 8080
    protocol: TCP
create & verify 
$</span> kubectl -n shop expose deploy api --name=api --port=80 --target-port=8080
$</span> kubectl -n shop get svc,endpoints,endpointslices
$</span> kubectl -n shop describe svc api
$</span> kubectl -n shop get pods -l app=api --show-labels
$</span> kubectl -n shop patch svc api -p '{"spec":{"type":"NodePort"}}'
$</span> kubectl -n shop get svc api -o jsonpath='{.spec.ports[0].nodePort}{"\n"}'
Gotcha exam trap

Service exists but Endpoints are empty → selector/labels mismatch, or Pods failing readinessProbe. Fixing DNS won’t help until Endpoints populate. Also: headless Services (clusterIP: None) return Pod IPs via DNS A/AAAA records—no ClusterIP VIP.

You create a ClusterIP Service with selector app=web, but kubectl get endpoints shows no addresses. Pods are Running. Most likely cause?

Endpoints/EndpointSlices are derived from matching Ready Pods. Ingress is unrelated to whether Endpoints exist.

04 Exam rapid-fire

ClusterIP vs NodePort vs LoadBalancer in one breath? core

ClusterIP = internal VIP. NodePort = expose that VIP via a port on every node. LoadBalancer = provision an external address that fronts the Service (usually via NodePort underneath on many clouds).

Say it out loud

“ClusterIP inside, NodePort on nodes, LoadBalancer for an external IP—same selector backends underneath.”

What is kube-proxy’s job? core

Watch Services and EndpointSlices; program the node dataplane so traffic to a Service IP:port is load-balanced to Pod backends. Some CNIs replace kube-proxy with eBPF—conceptually the same responsibility.

Say it out loud

“kube-proxy turns Service VIPs into Pod destinations; it doesn’t assign Pod IPs—that’s CNI.”

port vs targetPort vs nodePort? warm

port: Service port clients use. targetPort: where it lands on the Pod. nodePort: host port when type is NodePort/LoadBalancer (allocated from the NodePort range if omitted).

Say it out loud

“Clients hit Service port; kube-proxy sends to targetPort on the Pod; nodePort is only the node’s published port.”
