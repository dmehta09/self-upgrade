Ingress controllers & resources.

Ingress is L7 HTTP(S) routing into the cluster: host + path rules to Services, optional TLS Secret. Still on CKA v1.35 alongside Gateway API—know both. An Ingress object does nothing without a controller.

01 The idea

You write an Ingress resource; an Ingress controller watches it and programs a reverse proxy / load balancer. Pick the controller with ingressClassName.

Analogy plain English

Ingress is the building directory: “example.com/api → floor 3, suite API.” The controller is the concierge who actually steers visitors. A directory on the wall with no concierge (no controller) changes nothing.

Gotcha exam trap

Creating kind: Ingress alone never opens the edge. Confirm a controller Pod is Running and ingressClassName matches an IngressClass. Annotations are controller-specific—prefer portable fields (pathType, ingressClassName, TLS) on the exam.

02 Host, path, TLS

pathType is required: Prefix, Exact, or ImplementationSpecific. TLS entries reference a Secret of type kubernetes.io/tls with tls.crt / tls.key.

ingress-shop.yaml 
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shop
  namespace: shop
spec:
  ingressClassName: nginx
  tls:
  - hosts:
    - shop.example.com
    secretName: shop-tls
  rules:
  - host: shop.example.com
    http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: api
            port:
              number: 80
      - path: /
        pathType: Prefix
        backend:
          service:
            name: frontend
            port:
              number: 80
TLS secret + apply 
$</span> kubectl -n shop create secret tls shop-tls --cert=tls.crt --key=tls.key
$</span> kubectl -n shop apply -f ingress-shop.yaml
$</span> kubectl -n shop get ingress shop -o wide
$</span> kubectl -n shop describe ingress shop
$</span> kubectl get ingressclass
Ingress (classic)
  • Single resource + many annotations
  • HTTP/HTTPS focused
  • Still valid on CKA v1.35
Gateway API (modern)
  • GatewayClass / Gateway / HTTPRoute
  • Role-oriented, portable features
  • Exam’s preferred ingress-traffic model

03 Worked task shape

Typical ask: expose two Services on one host with path split, or attach TLS. Verify ADDRESS / events on the Ingress, then curl with Host header if using a NodePort controller.

smoke test 
$</span> kubectl -n ingress-nginx get svc
$</span> curl -k -H "Host: shop.example.com" https://<controller-ip>/api/
$</span> kubectl -n shop get endpoints api frontend

You applied an Ingress with valid rules. kubectl get ingress shows no ADDRESS and traffic fails. First suspicion?

Ingress is declarative config for a controller. Without one (or with the wrong class), nothing advertises an address or routes traffic.

04 Exam rapid-fire

Ingress resource vs Ingress controller? core

The resource is API config (rules). The controller is the running software that implements those rules. Both are required for working HTTP ingress via the Ingress API.

Say it out loud

“Ingress YAML is the map; the controller is the proxy that follows it.”

How does TLS work on Ingress? core

spec.tls lists hosts and a secretName pointing at a TLS Secret in the same namespace. The controller terminates TLS (typical) and forwards HTTP to backend Services.

Say it out loud

“TLS block names the host and the tls Secret; controller presents that cert.”

Is Ingress gone on CKA v1.35? warm

No—Ingress remains on the curriculum. Gateway API is the modern focus for ingress traffic, but you should still create host/path Ingress and TLS when asked.

Say it out loud

“I know Ingress for classic tasks and Gateway API as the successor model the exam emphasizes.”
