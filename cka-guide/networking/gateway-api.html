Gateway API.

Modern CKA focus for ingress traffic: GatewayClass, Gateway, and HTTPRoute. Role-oriented, portable routing without annotation soup. Successor model to Ingress—exam expects you to attach routes to a Gateway.

01 The idea

GatewayClass = which controller implementation. Gateway = listeners (ports/protocols). HTTPRoute = host/path/header rules → Service backends.

Analogy plain English

GatewayClass is the approved bridge design (who builds bridges). Gateway is a concrete bridge with toll booths (listeners on 80/443). HTTPRoute is the road signs bolted onto that bridge: which host/path goes to which warehouse (Service). Infra teams own the bridge; app teams own the signs.

Ingress pain
  • One blob + vendor annotations
  • Weak portability across controllers
  • Limited traffic features in core API
Gateway API wins
  • Standard route matchers & filters
  • Clear ownership boundaries
  • Extensible without annotation sprawl

02 Objects you’ll touch

On many exam clusters the GatewayClass (and maybe a Gateway) already exist—you attach an HTTPRoute. Always kubectl get gatewayclass,gateway,httproute -A first.

gateway.yaml 
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: edge
  namespace: default
spec:
  gatewayClassName: cilium   # must match an existing GatewayClass</span>
  listeners:
  - name: http
    protocol: HTTP
    port: 80
    allowedRoutes:
      namespaces:
        from: All
httproute.yaml 
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: shop
  namespace: shop
spec:
  parentRefs:
  - name: edge
    namespace: default
  hostnames:
  - shop.example.com
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: /api
    backendRefs:
    - name: api
      port: 80
  - matches:
    - path:
        type: PathPrefix
        value: /
    backendRefs:
    - name: frontend
      port: 80
Gotcha exam trap

Wrong parentRefs (name/namespace) or Gateway allowedRoutes blocking your namespace → route never attaches. Check HTTPRoute status / Gateway conditions, not only that the YAML applied. Cross-namespace Service refs may need ReferenceGrant.

CKA posture

Prefer Gateway API when the task says “ingress traffic” or gives a Gateway. Still know classic Ingress when the prompt names Ingress explicitly. Don’t invent controllers—reuse the cluster’s GatewayClass name.

Which trio is the core Gateway API model for HTTP ingress on CKA?

Those three kinds implement the role-oriented edge. Routes attach to Gateways that declare a GatewayClass.

04 Exam rapid-fire

How is Gateway API “role-oriented”? core

Infrastructure defines GatewayClass/Gateway (how traffic enters). Application owners define HTTPRoutes (how their hosts/paths map to Services). Attachment is explicit and can be restricted per listener.

Say it out loud

“Ops owns the Gateway; apps own HTTPRoutes that parentRef into it.”

Gateway API vs Ingress—what do you say on the exam? core

Gateway API is the successor for expressive, portable ingress. Ingress still works and remains in curriculum. Use the API the task names; default modern answers lean Gateway + HTTPRoute.

Say it out loud

“Gateway API replaces annotation-heavy Ingress with GatewayClass, Gateway, and routes—CKA expects both familiarity.”

HTTPRoute applied but no traffic—checklist? stretch

GatewayClass controller healthy, Gateway Accepted/Programmed, parentRefs correct, allowedRoutes permits the route’s namespace, host/path match the client, backend Service has Endpoints.

Say it out loud

“I read Gateway and HTTPRoute status before I blame the app—attachment failures are silent from curl’s point of view.”
