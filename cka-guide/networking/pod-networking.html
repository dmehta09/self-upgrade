Pod networking.

Every Pod gets its own IP on a flat cluster network. Pods talk to other Pods by IP (and later by Service DNS) without you wiring NAT hop-by-hop. CKA expects you to explain the model, CNI’s job, and when hostNetwork breaks the rules.

01 The idea

Kubernetes assumes a flat Pod network: every Pod IP is unique and routable to every other Pod without NAT (in the usual model).

Analogy plain English

Think of Pods as desks on one big office floor. Each desk has a unique extension number (Pod IP). Anyone can dial anyone else directly. The CNI is the wiring crew that hangs the phones and keeps the floor plan consistent—Kubernetes does not invent L3 by itself.

The API schedules Pods; the CNI plugin (Calico, Cilium, Flannel, cloud VPC CNI, …) assigns IPs, programs routes/bridges/overlays, and connects the Pod’s network namespace to the node. Without a working CNI, Pods stay ContainerCreating with “network not ready” style events.

Every Pod
Gets at least one cluster-routable IP (usually from a Pod CIDR per node).
Pod ↔ Pod
Usually IP-to-IP, no NAT. Source IP you see is the real Pod IP.
CNI role
Implements the model: IPAM + connectivity. High level only on CKA—pick plugins in docs, don’t memorize vendor YAML.
hostNetwork
Rare escape hatch: Pod shares the node’s network namespace (and ports). Breaks isolation; use only when required.

02 Flat network model

Three classic guarantees (the “Kubernetes networking model”):

  1. Pods can reach Pods on any node without NAT.
  2. Nodes can reach Pods without NAT (kubelet, probes, etc.).
  3. The IP a Pod sees as itself is the same IP others use to reach it.
Normal Pod network
  • Unique Pod IP from CNI
  • Isolated netns + veth
  • Reachable cluster-wide
  • Works with NetworkPolicy (if CNI supports it)
hostNetwork: true
  • Uses node IP / interfaces
  • Port conflicts with host processes
  • Skips normal Pod IP model
  • Harder to reason about NP & Services
Gotcha exam trap

Pod-to-Pod traffic is usually not NATed. NAT shows up for Service ClusterIPs (kube-proxy / dataplane) and for some egress-to-outside paths—not as the default story between two Pod IPs. Don’t say “Kubernetes always NATs Pod traffic.”

03 Inspect Pod IPs (exam muscle)

On the exam, prove connectivity with -o wide, then curl/wget from a throwaway Pod. Confirm CNI is up if Pods never get IPs.

Exam tip

If a Pod has no IP and stays Pending/ContainerCreating, check node Ready, CNI DaemonSet pods in kube-system, and events (kubectl describe pod) before blaming the app image.

Two Pods on different nodes need to talk on TCP/8080. What is the default networking expectation?

The flat model + CNI is the foundation. Services add stable VIPs later; they are not required for raw Pod-IP reachability.

04 Exam rapid-fire

What does the CNI do versus kube-proxy? core

CNI gives Pods connectivity and IPs (the cluster’s Pod network). kube-proxy (or an equivalent dataplane) implements Service virtual IPs and load-balancing to Endpoints—not the basic Pod-to-Pod path.

Say it out loud

“CNI wires the flat Pod network. kube-proxy is about Services, not giving every Pod an IP.”

When would you set hostNetwork: true? warm

Only for special node-level agents that must bind host ports or see the host network stack. It is rare on CKA app workloads. Prefer normal Pod networking + a Service/Ingress/Gateway for exposure.

Say it out loud

“hostNetwork is an exception that shares the node’s netns—port conflicts and lost Pod IP semantics—so I avoid it unless the task forces it.”

Pods can’t ping each other across nodes. First checks? stretch

Node Ready + CNI DaemonSet healthy, Pods actually have IPs (-o wide), NetworkPolicies not denying, and security groups/firewall allowing the Pod/overlay CIDR. Then test with a debug Pod to a known Pod IP.

Say it out loud

“I verify CNI and Pod IPs before I touch application config—broken fabric looks like app failure.”
