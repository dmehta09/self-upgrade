RBAC.

Role-Based Access Control answers who can do what on which API objects. CKA loves creating Roles/ClusterRoles, binding them, and fixing Forbidden errors fast.

01 The idea

Role / ClusterRole = verbs + resources. RoleBinding / ClusterRoleBinding = attach that permission set to a user, group, or ServiceAccount.

Analogy plain English

A Role is a keyring labeled “Pods: get, list in this floor.” A Binding hangs that keyring on a badge (user/SA). ClusterRole is a master keyring; ClusterRoleBinding hangs it building-wide.

02 Objects & scope

Role
Namespaced rules.
ClusterRole
Cluster-wide rules (or reusable namespaced via RoleBinding).
RoleBinding
Grants a Role or ClusterRole inside one namespace.
ClusterRoleBinding
Grants a ClusterRole across the cluster.
role-binding.yaml 
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: demo
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: demo
subjects:
- kind: ServiceAccount
  name: app
  namespace: demo
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: pod-reader
Gotcha exam trap

roleRef is immutable — wrong kind/name means delete and recreate the binding. Forgetting apiGroups: [""] for core resources fails silently in your head until authorize says no. Subresources like pods/log need their own rule.

03 Exam kubectl

Prefer kubectl create … --dry-run=client -o yaml then edit. Debug with kubectl auth can-i.

RBAC commands 
$</span> kubectl -n demo create sa app
$</span> kubectl -n demo create role pod-reader --verb=get,list,watch --resource=pods
$</span> kubectl -n demo create rolebinding read-pods --role=pod-reader --serviceaccount=demo:app
$</span> kubectl auth can-i list pods -n demo --as=system:serviceaccount:demo:app
$</span> kubectl auth can-i --list --as=system:serviceaccount:demo:app -n demo
$</span> kubectl get role,rolebinding -n demo
$</span> kubectl describe clusterrole view | head

A ServiceAccount must list Nodes. Which binding type?

Node is cluster-scoped. Grant via ClusterRole and ClusterRoleBinding to the ServiceAccount.

04 Exam rapid-fire

Role vs ClusterRole? core

Role is namespaced. ClusterRole is cluster-scoped (and reusable). Binding type decides where the grant applies.

Say it out loud

“Role is floor keys; ClusterRole can be the building keyring.”

How do you verify a ServiceAccount can list pods? core

kubectl auth can-i list pods -n <ns> --as=system:serviceaccount:<ns>:<sa>

Say it out loud

“can-i --as the ServiceAccount before I call the task done.”

Forbidden on pods/log — what’s missing? stretch

A rule for resource pods/log (and maybe pods/exec). Listing pods ≠ reading logs.

Say it out loud

“Subresources are separate verbs — I add pods/log explicitly.”
