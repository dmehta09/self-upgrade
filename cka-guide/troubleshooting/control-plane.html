TROUBLESHOOTING · control plane Domain 1 · Troubleshooting · 30%

Troubleshoot control-plane components.

On kubeadm clusters, apiserver, etcd, scheduler, and controller-manager are often static Pods. Manifests and host logs beat random YAML edits.

01 Static Pods, host-owned

Control-plane Pods are declared on disk; kubelet starts them without the scheduler.

Pilot checklist in the cockpit analogy

In plain English: the control plane is the cockpit. Manifests under /etc/kubernetes/manifests are laminated checklists taped to the panel. The co-pilot (kubelet) reads the checklist and starts those Pods even if air traffic control (scheduler) is offline.

Static manifest dir
Typically /etc/kubernetes/manifests — drop/edit YAML → kubelet restarts the static Pod.
kube-apiserver
API front door. Down → kubectl fails. Fix certs, flags, etcd reachability.
etcd
Cluster state. Down → API may be up but writes fail. Check etcd Pod/logs/certs.
scheduler / CM
No new binds / no controllers. API may still answer get.

02 Symptom → component

Separate “API unreachable” from “API up, nothing reconciles.”

flowchart TD
  Q[kubectl fails?] -->|yes| API[apiserver / kubeconfig / certs]
  Q -->|no| W{What fails?}
  W -->|Pods Pending forever| SCH[kube-scheduler]
  W -->|replicas not healing| CM[controller-manager]
  W -->|API errors on write| ET[etcd]
  API --> M[Check static manifests + logs]
  SCH --> M
  CM --> M
  ET --> M

High-level only: journalctl on the host + crictl for container state — not a full etcd restore lab.

03 Inspect without panicking

Constraint: kubectl times out against the cluster. Control-plane node SSH works. Restore API access.

$</span> # On control-plane node
$</span> ls /etc/kubernetes/manifests
$</span> crictl ps -a | grep -E 'kube-apiserver|etcd|scheduler|controller'
$</span> journalctl -u kubelet -e --no-pager | tail -n 80
$</span> # After API recovers
$</span> kubectl get pods -n kube-system -o wide
Avoid
  • Deleting etcd data directories
  • Editing live Pods that kubelet will overwrite
  • Assuming Docker — use CRI/crictl
Prefer
  • Diff/fix static manifests
  • Validate cert paths & --etcd-servers
  • Restart kubelet after manifest fix
Gotcha · kubectl edit on static Pods

Editing the API mirror object is ephemeral. Persistent fixes belong in the manifest file on disk. Wrong flags there = CrashLoop of apiserver itself — keep a backup copy of the YAML.

04 Quick check

kubectl get nodes works. New Pods stay Pending with no scheduler Events. Most likely?

API works, so apiserver is up. No binds points at scheduler. DNS/NP/StorageClass cause different symptoms (name resolve, timeouts, Pending with volume Events).

05 Exam rapid-fire

Where do kubeadm control-plane manifests live? Warm

Say it out loud: /etc/kubernetes/manifests on the control-plane node — kubelet watches that directory.

Answer

Files like kube-apiserver.yaml, etcd.yaml, kube-scheduler.yaml, kube-controller-manager.yaml.

journalctl vs crictl — when each? Core

Say it out loud: journalctl for kubelet/systemd; crictl to see whether the container is created, running, or exited.

Answer

Use both: unit logs explain pull/config errors; crictl logs / ps show the static Pod container lifecycle when API is down.

Is deep etcd snapshot restore a CKA core skill now? Stretch

Say it out loud: Curriculum v1.35 de-emphasizes deep etcd backup labs — focus on recognizing etcd failure and restoring control-plane components.

Answer

Know that etcd holds state and that broken etcd breaks writes. Prefer component health, manifests, and certs over inventing a full DR procedure unless the task states it.
