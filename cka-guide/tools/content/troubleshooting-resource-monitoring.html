TROUBLESHOOTING · monitoring Domain 1 · Troubleshooting · 30%

Monitor cluster & app resources.

kubectl top needs metrics-server. Compare usage to requests to find noisy neighbors and Pending-by-CPU traps.

01 Usage is not requests

Requests drive scheduling; usage is live consumption from metrics-server.

Hotel booking vs room guests analogy

In plain English: requests are how many beds you reserved on the booking sheet (scheduler math). Usage is how many people are actually in the rooms tonight (metrics). A noisy neighbor reserved one bed but threw a party that pegs the floor’s power meter.

metrics-server
Aggregates resource metrics; powers kubectl top and HPA resource metrics.
kubectl top nodes
CPU/memory used per node — find saturated workers.
kubectl top pods
Per-Pod usage — find noisy neighbors in a namespace.
Requests vs limits
Requests: schedule + fair share. Limits: hard cap (CPU throttle / memory OOM).

02 Find the pressure

flowchart TD
  T[kubectl top nodes] --> H{Node hot?}
  H -->|yes| P[kubectl top pods -A --sort-by=cpu]
  P --> N[Identify noisy Pod]
  N --> F[Adjust requests/limits or move]
  H -->|no| S[Check Pending Events]
  S --> R[Requests too high vs Allocatable]
  MS[metrics-server down] -.->|top fails| FIX[Fix metrics-server first]

If top errors, fix metrics-server before chasing imaginary CPU charts.

03 Worked noisy-neighbor hunt

Constraint: New Pods Pending with Insufficient cpu on one node pool. Find who reserved or burned capacity.

$</span> kubectl top nodes
$</span> kubectl describe node worker-1 | sed -n '/Allocated resources/,/Events/p'
$</span> kubectl top pods -A --sort-by=cpu | head
$</span> kubectl top pods -A --sort-by=memory | head
$</span> kubectl get pods -A -o custom-columns=NS:.metadata.namespace,NAME:.metadata.name,REQ_CPU:.spec.containers[*].resources.requests.cpu
Usage high, requests low
  • Noisy neighbor / overcommit
  • Throttle or OOM risk
  • Raise requests or limits thoughtfully
Requests high, usage low
  • Wastes schedulable capacity
  • Causes artificial Pending
  • Trim requests; keep burst via limits
Gotcha · top without metrics-server

kubectl top fails with metrics API unavailable. Check kubectl -n kube-system get deploy,pods | grep metrics and APIService. Do not invent Prometheus unless the task installs it.

04 Quick check

Pod requests 2 CPU but top shows 50m average. Cluster has Pending Pods for CPU. Likely issue?

Scheduler packs by requests, not live usage. Fat requests with skinny usage leave CPU idle but unschedulable.

05 Exam rapid-fire

What powers kubectl top? Warm

Say it out loud: metrics-server exposing the metrics.k8s.io API.

Answer

Without it, top and resource HPA fail. Verify the Deployment and APIService health.

How do you spot a noisy neighbor quickly? Core

Say it out loud: top pods sorted by CPU or memory, then cross-check the node’s allocated resources.

Answer

kubectl top pods -A --sort-by=cpu plus describe node Allocated resources. Act on the offender’s requests/limits or placement.

Usage above limit — what happens? Stretch

Say it out loud: Memory over limit → OOMKilled; CPU over limit → throttle, not kill.

Answer

That asymmetry matters for CrashLoop vs mysterious latency. Check Last State for OOMKilled.
