NetworkPolicies.

Default is allow-all. NetworkPolicies isolate Pods at L3/L4 once a supporting CNI enforces them. CKA loves deny-all + selective allow with podSelector / namespaceSelector.

01 The idea

No policy → open. Any selecting policy with Ingress/Egress → that direction becomes deny-by-default for selected Pods, then allow-lists add holes.

Analogy plain English

An open-plan office (default allow). The first “security policy” on a team locks their door (isolate). Sticky notes on the door list who may enter or leave (ingress/egress allow rules). Policies only work if the building’s locks (CNI) support them—paper policies alone do nothing.

Gotcha exam trap

NetworkPolicy is an API object even when the CNI ignores it. Creating YAML is not proof of enforcement—cluster must run a CNI that implements NetworkPolicy (Calico, Cilium, etc.). Also: policies are namespace-scoped; they select Pods in their namespace.

02 Deny-all, then allow

Standard pattern: empty podSelector: {} selects all Pods in the namespace. Empty rule lists with policyTypes set = deny that direction.

default-deny.yaml 
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: secure
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  - Egress
  # no ingress/egress rules → deny both directions for all Pods</span>
allow-frontend-to-api.yaml 
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-allow-frontend
  namespace: secure
spec:
  podSelector:
    matchLabels:
      app: api
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: frontend
    - namespaceSelector:
        matchLabels:
          name: monitoring
    ports:
    - protocol: TCP
      port: 8080
DNS under deny-egress

If you deny all egress, allow DNS or nothing resolves: egress to kube-dns / CoreDNS (often labels k8s-app: kube-dns in kube-system) on UDP/TCP 53—plus your real backends.

allow-dns-egress.yaml 
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns
  namespace: secure
spec:
  podSelector: {}
  policyTypes:
  - Egress
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: kube-system
      podSelector:
        matchLabels:
          k8s-app: kube-dns
    ports:
    - protocol: UDP
      port: 53
    - protocol: TCP
      port: 53

Policy selects targets
  • spec.podSelector = which Pods are isolated
  • Rules describe allowed peers
  • Additive across policies
What NP is not
  • Not L7 / HTTP path filtering
  • Not a substitute for RBAC
  • Not enforced without CNI support

A namespace exam ask: deny all ingress to namespace prod, then allow only Pods labeled role=frontend to reach app=db on TCP 5432. What is the minimal shape?

NetworkPolicy is the L3/L4 isolation tool. Ingress/Gateway are HTTP edge routers; headless Services don’t enable NP.

04 Exam rapid-fire

What is the default connectivity without NetworkPolicies? core

Allow all Pod-to-Pod (and typical egress) unless something else blocks it. Isolation starts when a policy selects a Pod for that direction.

Say it out loud

“Default allow; NetworkPolicy flips selected Pods to deny-by-default for ingress and/or egress.”

podSelector vs namespaceSelector? core

podSelector alone = Pods in the same namespace as the policy. namespaceSelector = all Pods in matching namespaces. Both in one peer = Pods matching the podSelector in those namespaces.

Say it out loud

“Same-namespace peers use podSelector; cross-namespace needs namespaceSelector—and both together means AND.”

Why might a correct NetworkPolicy “do nothing”? stretch

CNI without NetworkPolicy support, wrong namespace, selectors that match zero Pods, or testing from a Pod that isn’t actually selected/isolated the way you think. Confirm with labels and a positive/negative curl test.

Say it out loud

“API admit ≠ enforcement—CNI must implement NetworkPolicy, and my selectors must hit the right Pods.”
