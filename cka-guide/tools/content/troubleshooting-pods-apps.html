TROUBLESHOOTING · pods & apps Domain 1 · Troubleshooting · 30%

Troubleshoot pods & apps.

Pending, CrashLoopBackOff, and ImagePullBackOff dominate CKA. Read status → Events → logs (current and previous) before changing YAML.

01 Triage order

Never guess from the name alone — describe tells you why; logs tell you what the process did.

ER triage, not surgery first analogy

In plain English: a medic checks airway, breathing, pulse before opening a chest. Pods are the same: phase and Events first, then container logs, then edit the Deployment. Skipping to kubectl delete pod only restarts the same crash.

Pending
Not scheduled (or waiting on volume). Control-plane / constraints — not yet a crash.
ImagePullBackOff
Runtime cannot pull. Wrong image, tag, registry auth, or network to registry.
CrashLoopBackOff
Container starts then exits. Backoff grows. Need exit reason + previous logs.
Running but not Ready
Probes failing or containers still starting. Check Ready condition and probe config.

02 Decision map

Use Events to pick the branch. Scheduler messages vs pull errors vs OOMKilled vs Error.

flowchart TD
  A[kubectl get pods] --> B{Phase?}
  B -->|Pending| C[describe Events]
  C --> C1[taints / affinity / PVC / resources]
  B -->|ImagePull*| D[Image / pullSecrets / registry]
  B -->|CrashLoop*| E[logs -p + describe]
  E --> E1[exit code · OOM · config]
  B -->|Running| F[Ready? probes / app]

Memorize the fork: Pending ≠ CrashLoop. Different tools, different fixes.

03 Worked triage

Constraint: Deployment web in apps shows 0/2 Ready. One Pod Pending, one CrashLoopBackOff. Fix or explain both.

$</span> kubectl -n apps get pods -o wide
$</span> kubectl -n apps describe pod <pending-pod>
$</span> kubectl -n apps describe pod <crash-pod>
$</span> kubectl -n apps logs <crash-pod> -c <container> --previous
$</span> kubectl -n apps get events --sort-by=.lastTimestamp | tail
Wrong reflex
  • Delete Pod and hope
  • Only logs without --previous
  • Ignore Events for Pending
Exam reflex
  • describe → last Events
  • logs + --previous after restart
  • Fix owner (Deployment/image/PVC)
Gotcha · empty logs on CrashLoop

After restart the current container may have no useful output yet. kubectl logs … --previous (or -p) reads the dead instance. Multi-container Pods need -c.

04 Quick check

A Pod never gets a nodeName. Events mention “Insufficient cpu”. What is the primary failure class?

No nodeName means the scheduler never bound the Pod. Resource requests that no node can satisfy keep it Pending. CrashLoop only happens after the container starts on a node.

05 Exam rapid-fire

First three commands for a failing Pod? Warm

Say it out loud: get, describe, then logs — and use previous when it restarted.

Answer

kubectl get pod → describe (Events + container state) → logs / logs -p. Only then edit the controller or Secret.

ImagePullBackOff vs ErrImagePull? Core

Say it out loud: ErrImagePull is the failed attempt; BackOff means kubelet is waiting before retrying the same pull.

Answer

Both mean pull failure. Fix image name/tag, imagePullSecrets, or registry reachability — not the app binary.

OOMKilled — requests or limits? Stretch

Say it out loud: The kernel kills when the container exceeds its memory limit; requests only affect scheduling.

Answer

Check Last State: Reason: OOMKilled. Raise limit or reduce app memory. Raising requests alone does not stop OOM if limit is still too low.
