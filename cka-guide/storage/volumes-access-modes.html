Volumes & access modes.

Pods are ephemeral; data that must survive restarts lives in volumes. CKA cares that you pick the right volume type and the right access mode so the Pod mounts cleanly.

01 The idea

A volume is a directory the kubelet mounts into a container. Access modes declare how many nodes may use the volume and whether writes are allowed.

Analogy plain English

The Pod is a hotel guest; the volume is a luggage locker. Ephemeral volumes are lockers that empty when checkout ends. Persistent volumes are lockers that keep bags after you leave — but the building still decides if one guest or many can open the same locker (access mode).

02 Volume types you’ll meet

Know which are Pod-lifetime scratch vs durable claims. On CKA, PVC-backed volumes dominate stateful tasks; emptyDir and projected volumes show up in config/scratch scenarios.

emptyDir
Scratch space on the node; dies with the Pod (unless sizeLimit / medium=Memory).
hostPath
Node filesystem path — useful for node agents, risky for apps; avoid unless the task demands it.
configMap / secret / projected
Inject config as files; not for app databases.
persistentVolumeClaim
Claim durable storage; the exam path for “keep data across Pod restarts.”
pod-with-volumes.yaml 
apiVersion: v1
kind: Pod
metadata:
  name: app
spec:
  containers:
  - name: app
    image: nginx:1.27
    volumeMounts:
    - name: cache
      mountPath: /cache
    - name: data
      mountPath: /data
  volumes:
  - name: cache
    emptyDir: {}
  - name: data
    persistentVolumeClaim:
      claimName: app-data

03 Access modes

Modes are capabilities of the volume (and StorageClass/PV), not wishes of the Pod alone. Mismatch → PVC stays Pending or mount fails.

Common modes
  • ReadWriteOnce (RWO) — one node, read/write
  • ReadOnlyMany (ROX) — many nodes, read-only
  • ReadWriteMany (RWX) — many nodes, read/write
  • ReadWriteOncePod — single Pod only (when supported)
Exam traps
  • Assuming every CSI driver supports RWX
  • Scaling a Deployment with RWO across nodes
  • Confusing access mode with reclaim policy
inspect mounts & modes 
$</span> kubectl get pvc,pv
$</span> kubectl get pv -o custom-columns=NAME:.metadata.name,MODE:.spec.accessModes,STATUS:.status.phase
$</span> kubectl describe pod app | sed -n '/Volumes:/,/Events:/p'
$</span> kubectl exec app -- df -h /data
Gotcha exam trap

RWO allows multiple Pods on the same node to mount read/write, but not across nodes. Multi-replica Deployments often need RWX — or a StatefulSet with one volume per Pod.

You need one shared writable volume for Pods scheduled on different nodes. Which access mode?

RWX is the multi-node read/write mode. RWO is single-node; ROX is read-only; emptyDir is not a durable shared claim.

04 Exam rapid-fire

emptyDir vs PVC — one sentence? core

emptyDir lasts for the Pod’s life on that node; a PVC claims durable storage that can outlive the Pod.

Say it out loud

“Scratch dies with the Pod; PVC is the claim for data that must survive.”

Name the four access modes CKA may mention. core

ReadWriteOnce, ReadOnlyMany, ReadWriteMany, and ReadWriteOncePod.

Say it out loud

“RWO one node, ROX many read-only, RWX many read/write, RWOP one Pod.”

Deployment with RWO PVC stuck Multi-Attach — what next? stretch

Replicas landed on different nodes. Reduce to one replica, use a StatefulSet volumeClaimTemplate, or switch to an RWX-capable StorageClass if the task allows.

Say it out loud

“RWO cannot follow replicas across nodes — I check Pods’ nodes and the PVC access mode first.”
