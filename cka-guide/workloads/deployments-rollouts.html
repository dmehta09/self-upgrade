Deployments, rollouts & rollbacks.

A Deployment owns ReplicaSets so you can change Pod templates safely. On CKA you must roll out, watch, pause, resume, and undo with kubectl under time pressure.

01 The idea

A Deployment is a desired-state controller; each revision is a ReplicaSet that actually keeps Pods alive.

Analogy

Think of a Deployment as a restaurant franchise HQ. Each menu revision opens a new kitchen (ReplicaSet). HQ gradually moves customers to the new kitchen, keeps the old one warm for a quick undo, then retires it.

flowchart TB
  D[Deployment web]
  RS1[ReplicaSet rev-1]
  RS2[ReplicaSet rev-2]
  P1[Pods v1]
  P2[Pods v2]
  D --> RS1
  D --> RS2
  RS1 --> P1
  RS2 --> P2
Controller
Deployment watches spec.replicas + Pod template
History
Each template change → new ReplicaSet revision
Default strategy
RollingUpdate (not recreate-all-at-once)

02 RollingUpdate knobs

RollingUpdate swaps Pods gradually. Two fields cap how far the live set can drift during the change.

maxUnavailable

How many Pods may go below desired replicas while updating.

  • Default often 25%
  • Protects capacity during drain
maxSurge

How many extra Pods may exist above desired replicas.

  • Default often 25%
  • Needs spare node capacity
rollout · create & watch 
kubectl create deployment web --image=nginx:1.27 --replicas=3
kubectl set image deployment/web nginx=nginx:1.28
kubectl rollout status deployment/web
kubectl get rs -l app=web -o wide
Gotcha exam

kubectl apply alone does not prove success. Always follow with kubectl rollout status. A CrashLooping new image can hang the rollout until timeout.

03 History, pause, undo

Revisions live in the Deployment’s rollout history. Pause freezes further template processing so you can batch several edits into one rollout.

1

Inspect history

kubectl rollout history deployment/web — note revision numbers before you undo.

2

Pause, edit, resume

Pause → change image/env/resources → resume → one combined rollout.

3

Undo

kubectl rollout undo deployment/web or --to-revision=N for a specific past ReplicaSet.

rollout · pause / undo 
kubectl rollout pause deployment/web
kubectl set image deployment/web nginx=nginx:1.29
kubectl set env deployment/web LOG_LEVEL=info
kubectl rollout resume deployment/web
kubectl rollout history deployment/web
kubectl rollout undo deployment/web --to-revision=2
kubectl rollout status deployment/web

A rollout is stuck on a bad image. Which command restores the previous ReplicaSet fastest?

Undo points the Deployment back at the prior ReplicaSet. Deleting ReplicaSets or scaling to zero is slower and riskier under exam time.

04 Exam task pattern

Constraint → change → verify. Record the revision before you touch anything so undo is precise.

task · verify 
kubectl get deploy web -o yaml | less
kubectl annotate deployment/web kubernetes.io/change-cause="bump nginx" --overwrite
kubectl set image deployment/web nginx=nginx:1.28
kubectl rollout status deployment/web --timeout=90s
kubectl get pods -l app=web -o jsonpath='{.items[*].spec.containers[*].image}{"\n"}'

Prefer kubectl set image / set env when the YAML is large — fewer typing mistakes than a full re-apply.

05 Exam rapid-fire

What does a Deployment actually create on each new revision? Warm-up
Say it out loud

“A new ReplicaSet with the updated Pod template. The Deployment scales that RS up and the previous RS down according to RollingUpdate.”

When do you pause a rollout instead of editing live? Core
Say it out loud

“When I need several template changes as one revision — pause, edit image and env, then resume so history stays clean.”

How do you prove a rollout finished successfully? Core
Say it out loud

“kubectl rollout status until it prints successfully rolled out, then spot-check Pod images and Ready counts.”
