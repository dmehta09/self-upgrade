Probes & self-healing.

Kubelet probes decide when a container is alive, ready for traffic, or still starting. Pair them with restartPolicy and controllers so failed Pods heal without you babysitting.

01 The idea

Liveness restarts sick containers; readiness removes them from Service endpoints; startup gates the other probes until boot finishes.

Analogy

Startup is “is the engine still cranking?” Readiness is “open the shop door for customers.” Liveness is “the cashier is frozen — reboot the register.” Mixing them up is how you thrash healthy Pods.

flowchart TD
  Boot[Container starts]
  SU{startupProbe OK?}
  RD{readinessProbe OK?}
  LV{livenessProbe OK?}
  EP[In Service Endpoints]
  OUT[Not Ready / no traffic]
  RST[Restart container]
  Boot --> SU
  SU -->|failing| Boot
  SU -->|pass / absent| RD
  RD -->|fail| OUT
  RD -->|pass| EP
  SU -->|pass / absent| LV
  LV -->|fail| RST
  LV -->|pass| LV

02 Three probes, three jobs

startupProbe
Protects slow boots; disables liveness/readiness until success
readinessProbe
Controls Endpoints — failed ≠ restart
livenessProbe
Failed → kubelet restarts the container
Mechanisms
httpGet, tcpSocket, exec, grpc
deployment · probes 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 2
  selector:
    matchLabels: { app: api }
  template:
    metadata:
      labels: { app: api }
    spec:
      containers:
      - name: api
        image: myapi:1.2
        ports:
        - containerPort: 8080
        startupProbe:
          httpGet: { path: /healthz, port: 8080 }
          failureThreshold: 30
          periodSeconds: 5
        readinessProbe:
          httpGet: { path: /ready, port: 8080 }
          periodSeconds: 5
        livenessProbe:
          httpGet: { path: /healthz, port: 8080 }
          periodSeconds: 10
Gotcha liveness

Pointing liveness at a dependency (database down → fail) causes restart storms. Liveness should mean “this process is wedged,” not “the world is unhealthy.” Use readiness for dependency checks.

03 restartPolicy & ReplicaSet heal

Containers restart according to restartPolicy. Controllers (ReplicaSet/Deployment) replace whole Pods when they disappear — that is self-healing at the Pod level.

Always (default for Deployments)
  • Kubelet restarts crashed containers
  • Right for long-running servers
OnFailure / Never
  • Jobs / one-shot Pods
  • Never → no container restart
observe self-heal 
kubectl get pods -l app=api -w
kubectl describe pod -l app=api | sed -n '/Conditions/,/Volumes/p'
kubectl get endpointslices -l kubernetes.io/service-name=api
kubectl delete pod -l app=api --force --grace-period=0
kubectl get rs
kubectl rollout status deployment/api

Delete a Pod owned by a ReplicaSet and a replacement appears with a new name. That is the exam “self-healing” demo — not magic, just desired replicas.

Readiness probe fails. What happens next?

Readiness ≠ restart. Only liveness (or crash) triggers container restart. Readiness steers traffic via Endpoints/EndpointSlices.

04 Timing knobs that matter

Know initialDelaySeconds, periodSeconds, timeoutSeconds, failureThreshold, and successThreshold. Startup probes replace long liveness delays for slow JVMs.

patch probes 
kubectl explain pod.spec.containers.livenessProbe --recursive
kubectl set probe deployment/api --liveness --get-url=http://:8080/healthz --period=10
kubectl rollout status deployment/api
kubectl describe deploy api | grep -A20 'Liveness\|Readiness\|Startup'

05 Exam rapid-fire

Liveness vs readiness in one sentence each? Warm-up
Say it out loud

“Liveness restarts a stuck container. Readiness keeps a not-yet-ready container out of the Service load balancer.”

Why add a startupProbe for a slow app? Core
Say it out loud

“So liveness doesn’t kill the container during a long boot. Startup must succeed before the other probes run.”

You delete a Deployment Pod. Who recreates it? Core
Say it out loud

“The ReplicaSet owned by the Deployment notices replicas dropped and creates a replacement Pod.”
