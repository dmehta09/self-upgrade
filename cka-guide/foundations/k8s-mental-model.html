FOUNDATIONS · mental model Domain 2 · Cluster Architecture

Kubernetes mental model.

CKA is not “run containers.” It is declare desired state, let the control plane reconcile, and verify on the data plane. Get this loop into muscle memory before any YAML drill.

01 Desired state, not scripts

You write what should be true; controllers keep nudging the cluster until reality matches.

Thermostat, not remote control analogy

In plain English: a thermostat holds a temperature. You do not pulse the heater every second. You set 22°C and the system corrects drift. Kubernetes objects in etcd are that setpoint. Controllers are the thermostat logic. Pods on nodes are the room temperature.

Imperative one-offs still create objects. After create, the same reconciliation rules apply. That is why kubectl apply and a Deployment both survive node loss better than a bare container SSH’d onto a host.

Declarative
Manifest (or API object) describes end state: replicas, image, ports, mounts.
Observed
What kubelets, Endpoints, and status fields report right now.
Reconcile
Controller loops compare desired vs observed and act (create Pod, patch Service, retry).

02 Control plane vs data plane

The control plane decides and remembers. The data plane runs workloads and moves packets. CKA tasks bounce between both: fix apiserver/RBAC, then prove Pods and Services on nodes.

Control plane
  • kube-apiserver — only public write path
  • etcd — cluster state store
  • scheduler — binds Pods to nodes
  • controller-manager — Deployments, Nodes, Jobs…
  • cloud-controller-manager — when cloud-specific
Data plane (nodes)
  • kubelet — Pod lifecycle via CRI
  • container runtime — usually containerd
  • kube-proxy or eBPF datapath — Service VIP
  • CNI plugin — Pod IPs, routes, policies
  • CSI node plugins — attach/mount volumes
Gotcha · “the master runs my app”

Exam clusters often taint control-plane nodes. Workloads land on workers unless you intentionally schedule otherwise. Debugging “Pending” starts with events and taints — not reinstalling etcd.

03 API → etcd → controllers → kubelet

Walk one write end-to-end. Every CKA create/apply follows this spine. When something “does nothing,” ask which hop failed.

Play the hops. Exam troubleshooting maps to “which box is stuck?”

04 Exam habit: declare → watch → verify

Treat every task as a reconciliation check. Create or edit the object, watch Events, then prove the observed state.

1

Set desired

Apply YAML or run a safe imperative create. Prefer --dry-run=client -o yaml when you need a template fast.

2

Watch the loop

kubectl get … -w and kubectl describe Events show scheduler, pull, and probe failures.

3

Verify observed

Ready replicas, Endpoints, DNS, and logs. Then move on — see Deployments & rollouts.

A Deployment shows READY 1/3. Who is primarily responsible for creating the missing Pod objects?

The controllers create Pod specs to match replica count. The scheduler only binds unbound Pods; kubelet only runs Pods already assigned to its node.

05 Exam rapid-fire

What is the reconciliation loop in one sentence? Warm

Say it out loud: Controllers continuously compare desired objects in the API with live cluster state and act until they match.

Answer

Desired state lives in etcd via the API. Controllers watch, compute diff, and mutate (create/update/delete) until observed state converges — then idle until the next change.

Why does kubectl talk only to the API server? Core

Say it out loud: The API server is the single validated front door to cluster state; clients never write etcd or poke kubelets directly.

Answer

Authentication, authorization, admission, and schema validation all sit on the apiserver. That keeps etcd consistent and lets controllers react through the same watch API you use with kubectl.

Pod is Pending forever — control or data plane? Core

Say it out loud: Pending usually means the control plane never bound the Pod — check scheduler Events, taints, and resource requests before blaming the runtime.

Answer

No nodeName → scheduler / constraints (taints, affinity, PVC). Bound but not Running → data plane (kubelet, image pull, CRI). Start with kubectl describe pod.
