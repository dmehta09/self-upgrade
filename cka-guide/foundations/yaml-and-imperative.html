YAML vs imperative.

CKA rewards correct end state, not purity. Use imperative commands when they are faster and safe; generate YAML with dry-run when you need fields imperative cannot express cleanly.

01 Choose the fastest correct path

Imperative for simple creates; YAML when the stem demands specific fields, volumes, or multi-object graphs.

Power drill vs full toolbox analogy

In plain English: kubectl create / run / expose is the power drill — one motion for a common hole. Manifests are the toolbox when the job needs hinges, levels, and three fasteners. Dry-run YAML is borrowing a template so you don’t invent the hinge from scratch.

flowchart TD
      Q[Read the task] --> C{Only name, image, port, replicas?}
      C -->|Yes| I[kubectl create / run / expose / scale]
      C -->|No — probes, mounts, affinity…| Y[Generate YAML skeleton]
      Y --> D["--dry-run=client -o yaml > file"]
      D --> E[Edit required fields]
      E --> A[kubectl apply -f]
      I --> V[Verify Ready / Endpoints]
      A --> V
      V --> T{Time left & unsure?}
      T -->|Flag & skip| S[Next question]
      T -->|Done| N[Next question]

02 Imperative kit that still works

These generators remain the exam speed layer. Confirm flags with --help if muscle memory blanks — help is local and fast.

IntentCommand shape
Deploymentkubectl create deployment NAME --image=IMG [-n NS]
Scalekubectl scale deploy/NAME --replicas=N
Exposekubectl expose deploy/NAME --port=80 --target-port=8080
ConfigMap / Secretkubectl create configmap / secret generic
Namespace / SAkubectl create namespace / serviceaccount
Job (quick)kubectl create job NAME --image=IMG -- …
Gotcha · kubectl run is not your 2019 muscle memory

On modern clusters, kubectl run creates a Pod by default — not a Deployment. If the question asks for a Deployment, use kubectl create deployment or dry-run YAML. Exposing a bare Pod also behaves differently under restarts.

imperative-happy-path.sh 
kubectl create namespace shop
kubectl create deployment api --image=nginx:1.27 -n shop
kubectl scale deployment/api --replicas=3 -n shop
kubectl expose deployment/api --port=80 --target-port=80 -n shop
kubectl get deploy,po,svc -n shop

03 Generate YAML, then edit

When you need probes, volumeMounts, nodeSelector, or precise labels, scaffold with dry-run and edit. This is the default pattern for partial-credit-friendly work — the file is your audit trail.

scaffold.sh 
kubectl create deployment api --image=nginx:1.27 -n shop \
  --dry-run=client -o yaml > api.yaml
# edit: replicas, labels, resources, probes…
kubectl apply -f api.yaml
kubectl rollout status deployment/api -n shop
Stay imperative
  • Namespace, SA, basic Deployment
  • Scale, expose ClusterIP
  • Simple ConfigMap from literals
  • Quick Job / CronJob create
Switch to YAML
  • Probes, lifecycle hooks
  • PVCs, mounts, SecurityContext
  • Affinity, taints/tolerations
  • NetworkPolicy, Gateway, multi-doc

After apply, prefer kubectl apply -f for further edits on that object so you keep a declarative file. Live kubectl edit is fine for tiny fixes — just re-verify.

04 Exam timeboxing tip

Two hours, roughly 15–20 tasks. Average ~6–8 minutes. Heavy YAML tasks can steal a whole domain’s worth of points if you dig in.

1

First pass: bank easy points

Anything solvable with create/scale/expose/label in under three minutes — do it immediately after context switch.

2

Cap YAML digs

If you are still hunting fields after ~7–8 minutes, flag the item, paste a stub if useful, and move on. Return with leftover time.

3

Always leave a verifiable state

Partial progress that is applied and Ready can score. A perfect YAML never applied scores zero. Pair with exam method.

The task requires a Deployment with an HTTP readiness probe on path /healthz. Best first move?

Probes are YAML fields. Scaffold, edit, apply, then confirm Ready. Imperative run/create won’t express a custom probe cleanly on the exam.

05 Exam rapid-fire

When is kubectl expose enough? Warm

Say it out loud: When you already have a labeled Deployment/Pod and only need a Service with matching selector and ports — no Ingress or policy yet.

Answer

Expose wires a Service selector from the workload’s labels. For NodePort specifics, sessionAffinity, or multi-port edge cases, generate YAML or edit the Service after.

Why redirect dry-run to a file instead of apply piping? Core

Say it out loud: A file lets you edit carefully, re-apply, and recover if the first apply fails — pipes are one-shot under stress.

Answer

Exam editors and retries favor > file.yaml. You can kubectl apply -f repeatedly and keep the artifact for the next tweak.

Imperative create then need a probe — what now? Core

Say it out loud: Get the live object as YAML, add the probe fields, apply — or kubectl edit for a tiny patch — then watch rollout Ready.

Answer

kubectl get deploy NAME -o yaml > file.yaml, strip status/managed noise if needed, add readinessProbe, apply, rollout status. Don’t recreate from scratch unless names collide.
