Complexity · the enemy

Strategic vs tactical programming.

Most complexity is self-inflicted, accumulated by a mindset that treats “it works” as the finish line. Ousterhout's antidote is a mindset shift: your real job isn't to produce working code — it's to produce a great design that also happens to work.

01 Working code isn't enough

If you only ever optimise for “make it work now,” you guarantee a complex system. Working code is the floor, not the goal.

In plain English analogy

It's the difference between paying down debt and maxing out the card. A tactical hack borrows speed today at interest — every future change pays the interest. Strategic work spends a little now to owe nothing later.

02 Two mindsets

Tactical

Goal: get this feature/fix done as fast as possible. Each shortcut is tiny — a special case here, a duplicated block there. They feel harmless and ship quickly.

Strategic

Goal: working code and a clean design. You invest continually in structure, so the system stays easy to extend. Slightly slower today, dramatically faster for months.

Red flag — the tactical tornado gotcha

The “productive” dev who churns out features by leaving complexity in their wake. They look fast on the leaderboard; everyone else slows down cleaning up after them. Speed that creates work for others isn't speed.

03 Same feature, two mindsets

Watch tactical creep: each promo is “just one more if.” The strategic version pays a small design cost once, then absorbs new promos for free.

Before · tactical
def price(cart):
    total = sum(i.price for i in cart.items)
    # promos bolted on, one if at a time
    if cart.code == "SAVE10":
        total *= 0.90
    if cart.code == "FREESHIP" and total > 50:
        total -= 5
    if cart.is_member:
        total *= 0.95
    if cart.code == "BOGO":
        cheapest = min(i.price for i in cart.items)
        total -= cheapest
    return total
# every new promo edits this function and risks the others
After · strategic
class Promo(Protocol):
    def apply(self, total: float, cart) -> float: ...

def price(cart, promos: list[Promo]):
    total = sum(i.price for i in cart.items)
    for promo in promos:           # uniform, order-independent
        total = promo.apply(total, cart)
    return total
# a new promo is a new small class — price() never changes

Why it's better: the strategic version turns “edit a growing function and pray” into “add an isolated class.” The dependency between promos disappears, so change amplification and cognitive load both drop.

04 The investment mindset

Spend a little design effort continually — Ousterhout's rule of thumb is roughly 10–20% extra — and treat it as an investment, not a tax.

The payoff isn't linear, because complexity compounds. Tactical teams feel faster for the first few weeks and are crawling within months; strategic teams pay a small steady premium and stay fast. There's no “we'll clean it up later” — later never has more slack than now, and the mess only grows.

See also lld guide

The strategic refactor above is the Open/Closed Principle in action — open for extension, closed for modification. See SOLID principles in the LLD guide.

05 Check yourself

A teammate ships features twice as fast as anyone, leaving small hacks everywhere. Is that good?

It's a tactical tornado. Individual velocity that injects complexity is borrowed against the whole team's future. Passing tests prove it works — they say nothing about whether the design will survive the next ten changes.
