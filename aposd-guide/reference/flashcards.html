01 The deck

0/0 known

  • What is complexity?

    Anything about a system's structure that makes it hard to understand or modify. It's structural and incremental.

  • The three symptoms of complexity

    Change amplification, cognitive load, and unknown unknowns (the worst — you can't tell what to change).

  • The two root causes of complexity

    Dependencies (can't change code in isolation) and obscurity (important information isn't obvious).

  • Tactical vs strategic programming

    Tactical = make it work now (accrues complexity). Strategic = working code and clean design, investing ~10–20% continually.

  • Tactical tornado

    The dev who ships features fast but leaves complexity behind — slowing everyone else down. Velocity that creates work isn't velocity.

  • Deep module

    A simple interface hiding a powerful implementation — high benefit, low cost. The book's central goal (e.g. Unix file I/O).

  • Shallow module

    Interface nearly as complex as its implementation — you pay to learn it and gain little. Getters/setters are the classic case.

  • Classitis

    The belief that more, smaller classes are always better. It breeds shallow modules and pushes complexity into the connections. Depth > size.

  • Information hiding

    Bury a design decision (format, algorithm, policy) behind an interface, so changing it touches only that module.

  • Information leakage

    One design decision reflected in multiple modules, coupling them so they change in lockstep. The opposite of hiding.

  • Temporal decomposition

    Structuring modules around the order operations run (read→process→write) instead of around knowledge — a reliable cause of leakage.

  • “Somewhat general-purpose”

    Make the interface general enough for several uses (today's implementation is enough). It's usually simpler and deeper than special-purpose.

  • Different layer, different abstraction

    Each layer should add a new abstraction. If adjacent layers look alike, suspect a pass-through.

  • Pass-through method

    A method that just forwards to another with the same signature — interface cost, no benefit. Remove it or make the layer earn its place.

  • Pull complexity downward

    A simple interface matters more than a simple implementation — let the module's author absorb complexity so its users don't.

  • When to bring code together

    If it shares information, is always used together, simplifies the interface, or removes duplication. Keep apart to separate general from special-purpose.

  • Define errors out of existence

    Redefine the API so the “error” case is a normal result (e.g. return a default), cutting the exception paths callers must handle.

  • Why write comments?

    To capture what code can't: the why, units, invariants, and contracts. Good comments are at a different level than the code, never a restatement.

  • Comments first

    Write the interface comment before the implementation — it's a design tool. If the comment is long or awkward, the abstraction is too complex.

  • What makes code “obvious”?

    A reader grasps it quickly and correctly without puzzling. You're a biased judge — reader confusion is the proof it's obscure.

  • Design it twice

    Sketch at least two genuinely different designs and compare trade-offs before committing. Even experts rarely get the best one first.

  • Designing for performance

    Clean design is usually fast enough. Don't trade clarity for speculative speed — measure first, then simplify the critical path.
