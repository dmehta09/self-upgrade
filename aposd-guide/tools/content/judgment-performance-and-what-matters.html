Judgment

Performance & deciding what matters.

Clean design and fast code are usually allies, not rivals: simple code does less work. And the deepest skill in all of design is the closing one — knowing which few things in a system deserve your effort at all.

01 Intuition lies — measure first

Programmers' instincts about performance are unreliable. Measure before you change anything, and measure again after to prove the change helped — if it didn't, revert it.

In plain English analogy

It's dieting by guessing calories. You confidently cut the salad dressing while the daily latte does the damage. Until you weigh things, you will optimise the wrong code with total conviction — most "obviously slow" guesses are wrong.

Measurement does two jobs: it finds the places that actually dominate, and it gives you a baseline so you can prove your "optimisation" was one. No measurable win, no extra complexity — put the code back.

measure.py
import cProfile, time

# 1) BEFORE touching anything: where does the time actually go?
cProfile.run("handle_request(req)", sort="cumulative")

# 2) AFTER your change: prove it helped against the same baseline
t0 = time.perf_counter()
for _ in range(1_000):
    handle_request(req)
print(f"{(time.perf_counter() - t0) / 1_000:.6f}s per request")

Profile to find the target; re-measure to keep the change honest.

02 Know what's expensive

You don't need to micro-optimise to write fast code — you need rough cost intuition. A few orders-of-magnitude facts let you make "naturally efficient" choices while designing, without contorting anything.

OperationRough costIntuition
Network round-triptens of µs in-datacenter; ms across the internetMillions of instructions per trip — batch, don't chat.
Disk / flash I/Otens of µs (flash) to ms (spinning disk)Vastly slower than memory — cache what you re-read.
Dynamic allocationhundreds of ns, plus GC/free churnCheap once; expensive a million times in a loop.
Cache miss to RAM~hundreds of cyclesMemory layout matters more than clever arithmetic.
Cached arithmeticsub-nanosecondEffectively free — never the thing to "optimise" first.

The pattern: each row is orders of magnitude dearer than the one below it. Knowing that, you'll instinctively avoid a network call per item or an allocation per iteration — design choices, not hacks.

03 Design around the critical path

For genuinely hot code, ask: what is the minimum work that must happen in the common case? Build the code around that critical path, and handle every rare case off it.

This is Ousterhout's key technique, and his RAMCloud story in one breath: chasing the lowest possible latency for small network reads, the fastest version of the system fell out of the simplest design for the common case — strip the main path to its essentials and the special cases stop costing anything.

Before · cluttered
def get(self, key):
    self.stats.lookups += 1
    log.debug("cache get %r", key)
    entry = self.entries.get(key)
    if entry is None:
        self.stats.misses += 1
        return self._load(key)
    if entry.expires_at < now():
        self.stats.expired += 1
        del self.entries[key]
        return self._load(key)
    if self.stats.lookups % 1000 == 0:
        self._flush_stats()    # in the hot path!
    return entry.value
After · critical path
def get(self, key):
    # critical path: one lookup, one check, return
    entry = self.entries.get(key)
    if entry is not None and entry.expires_at >= now():
        return entry.value
    return self._get_slow(key)   # every rare case lives here

def _get_slow(self, key):
    # off the path: miss, expiry, stats, logging
    log.debug("cache slow path %r", key)
    self.stats.record_miss(key, expired=key in self.entries)
    self.entries.pop(key, None)
    self.entries[key] = value = self._load(key)
    return value

Why it's better: the common case — a fresh hit — is now a few straight-line statements with no logging, stats, or branches in the way; all the rare work moved into one off-path helper. It's faster and easier to read: the special cases stopped obscuring the main one.

04 Simplicity vs performance: usually a false trade-off

Micro-optimising everywhere injects complexity for gains nobody can measure. Meanwhile simple code, by definition, does fewer things — so it is often already the fastest version, or close enough that nobody will ever notice. When the two genuinely conflict, you now have the tools: measure to confirm it matters, then redesign around the critical path rather than sprinkling hacks.

Red flag — premature optimisation gotcha

Complexity added for speed nobody measured: hand-inlined helpers, caches without hit-rate data, "fast paths" for code that runs once a day. You pay the complexity tax forever, for a benefit that may not exist. No profile, no optimisation.

05 Decide what matters

The closing skill of the whole book: find the few things that matter most in this system, design around them, and deliberately de-emphasise everything else.

  • Find what matters. It's always a short list: the core abstraction, the hot path, the data model. If your list is long, you haven't found it yet.
  • Design around it. Give those few things the cleanest interfaces, the most design-it-twice attention, the central place in the structure.
  • De-emphasise the rest. Move it off the critical path, hide it behind a module, let it be ordinary. Not everything deserves polish.
  • Minimise what matters. The best designs go further: they make fewer things matter at all. Every concern you can hide or eliminate is one nobody ever has to think about again.

And that ties off the book: deciding what matters is just complexity management at the highest altitude. What matters is what you must keep in your head; great design shrinks that set. As Ousterhout closes — it's all about complexity.

06 Check yourself

A teammate wants to rewrite the config parser in C "for speed" — no profile, no measurements. What does the book say?

Measure first. Intuition about where time goes is unreliable — a config parser that runs once at startup can't dominate anything. Without a profile this is the premature-optimisation red flag: permanent complexity (two languages, a build step, a fallback to maintain) bought with an unmeasured benefit.
