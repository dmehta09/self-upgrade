Red-flags cheatsheet.

Every design smell from the book on one page, each with a one-line fix and the principle behind it. Skim before a code review or when something “feels” complex but you can't name why.

01 The red flags

Modules & abstraction

Shallow module
Interface ≈ implementation. → Make it deeper, or merge it.
Information leakage
One decision in 2+ modules. → Hide it behind a single module.
Temporal decomposition
Structure follows execution order. → Organise by knowledge, not timing.
Overexposure
Common use needs rare features. → Sensible defaults; pull complexity down.
Pass-through method
Forwards with no new abstraction. → Remove it or give the layer a job.

Coupling & duplication

Repetition
Same snippet copied around. → Factor into one module.
Special-general mixture
Special case tangled into a general mechanism. → Split them apart.
Conjoined methods
Can't grasp one without the other. → Combine, or redraw the boundary.
Config-knob overload
Caller must tune values it can't judge. → Default inside; override optional.

Errors & comments

Exception for the normal case
Throws on common conditions. → Define the error out of existence.
Comment repeats the code
Restates the line. → Delete it, or raise/lower its level.
Implementation in the interface doc
Internals leak into the contract. → Keep interface comments about use.

Names & clarity

Vague name
tmp, data, do_it. → Name it precisely.
Hard to pick a name
No crisp name fits. → The entity does too much; reshape it.
Hard to describe
The comment runs long/awkward. → Simplify the abstraction.
Nonobvious code
Readers must puzzle it out. → Rename, restructure, add the missing why.
Inconsistency
Same concept, different names/patterns. → Pick one convention; never deviate.

02 Principles at a glance

Mindset

It's all about complexity
The thing every rule is fighting.
Complexity is incremental
Fight it continually, a grain at a time.
Be strategic
Working code isn't enough — invest ~10–20% in design.
Design it twice
Two real alternatives beat the first idea.

Modules

Make modules deep
Simple interface, powerful implementation.
Hide information
Bury each design decision; avoid leakage.
Somewhat general-purpose
A general interface is usually simpler.
Pull complexity down
The author absorbs it, not the users.

Code

Define errors away
Fewer exceptions = fewer paths.
Comment what code can't
Why, units, contracts — write them first.
Precise, consistent names
Make the code obvious; trust reader confusion.
