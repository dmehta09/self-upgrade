Deep modules · the core move

Different layer, different abstraction.

Software is built in layers, and every layer should offer a different abstraction than the ones above and below it. When two adjacent layers look the same, one of them probably isn't earning its keep — the symptom is a pass-through.

01 Each layer must add value

If a layer's interface is similar to the layer beneath it, that's a red flag: the layer isn't providing a new abstraction.

In plain English analogy

A good chain of command has each rank adding judgment. A manager who just forwards every email unchanged to their boss adds a delay and a name in the thread — nothing else. Delete that layer, or give it a real job.

02 Pass-through methods

A pass-through method does little but call another method with roughly the same signature. It inflates the interface (one more thing to learn and maintain) while adding zero abstraction. Either remove it, or make it earn its place by providing something the layer below doesn't.

Before · pass-through
class UserService:
    def __init__(self, repo):
        self.repo = repo

    def get_user(self, uid):        # adds nothing
        return self.repo.get_user(uid)

    def save_user(self, user):      # adds nothing
        return self.repo.save_user(user)
# the service is a hollow layer: same
# abstraction as the repo, one level up
After · earns its layer
class UserService:
    def __init__(self, repo, cache):
        self.repo, self.cache = repo, cache

    def get_user(self, uid):
        # a NEW abstraction the repo lacks:
        # transparent caching of reads
        if uid not in self.cache:
            self.cache[uid] = self.repo.get_user(uid)
        return self.cache[uid]
# (if you can't name what it adds — delete it
#  and let callers use the repo directly)

Why it's better: the “after” layer provides an abstraction the layer below doesn't (caching). A layer that can't articulate what it adds should be removed so callers talk straight to the layer beneath.

03 Pass-through variables

The same smell appears with data. A pass-through variable is threaded through a long chain of methods just to reach a deep one — every method in between must declare and forward a parameter it never uses. That's broad, shallow coupling: add one variable and you edit the whole chain.

Red flag gotcha

Pass-through methods, pass-through variables, and decorators/wrappers that forward without adding an abstraction. Fixes for variables: pass a small context object, or store shared state on an object both ends already see — so intermediates don't carry what they don't use.

04 Check yourself

You find a service method that just calls the repository method with identical arguments. What is it?

A pass-through. Routing calls through a service is only valuable when the service adds an abstraction the repo lacks (caching, authorization, mapping). Forwarding identical arguments is pure interface cost with no benefit.
