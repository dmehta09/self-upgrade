Everyday craft

Names, consistency & obvious code.

Three habits that decide whether reading your code is effortless or exhausting. Precise names create an accurate picture in one glance; consistency lets readers reason by analogy; and the sum of both is obvious code — understood quickly, correctly, without puzzling.

01 Names are tiny abstractions

A good name is precise: it forms an accurate image and rules out wrong meanings. Vague names (data, tmp, obj, do_it) are obscurity in disguise.

In plain English analogy

Names are the labels on moving boxes. “Stuff” forces you to open every box; “Kitchen — fragile” tells you what's inside and how to handle it before you touch it. Each precise name saves the reader from opening the box.

02 Precise names make code obvious

Before · obscure
def proc(d, t):
    r = []
    for x in d:
        if x[1] > t:
            r.append(x[0])
    return r
# what is d? t? x[1]? you must decode it all
After · obvious
def names_above(scores, threshold):
    """scores: list of (name, value).
    Returns the names whose value exceeds threshold."""
    return [name for name, value in scores
            if value > threshold]
# reads like the sentence it implements

Why it's better: precise names plus one contract comment turn a decode-it-yourself loop into a line you read like prose. Same behaviour, near-zero cognitive load.

03 Consistency lets readers reason by analogy

Consistency — same concept, same name; same task, same pattern; conventions everywhere — slashes cognitive load and shrinks unknown unknowns.

If user_id always means the same thing, parameters always go in the same order, and one pattern always handles errors, a reader who has seen one part of the system already understands the rest. Pick a convention and never deviate without a strong reason — an inconsistency makes readers stop and wonder whether this case is special.

04 The test for “obvious”

Code is obvious when a reader grasps it quickly and correctly without much thought; obscure when they must stop and puzzle. The catch: you're the worst judge of your own code, because you already hold the context in your head.

Red flag gotcha

“It's obvious to me.” If a reviewer pauses or misreads, the code is obscure — full stop. Treat reader confusion as data, not as a reader problem. Vague names and inconsistency are the two biggest culprits.

05 Check yourself

A reviewer says they can't tell what tmp holds in your function. Your move?

Rename it. Reader confusion is the definition of “not obvious,” and you're biased because you hold the context. A precise name fixes it permanently; a thread comment helps one person once, and # temporary restates the non-name.
