Comments: why & what.

Comments aren't a failure of code — they're how you record the things code can't express: the units, the contract, the reason. The goal of a comment is to put information that was in the designer's head into a form the next reader can recover. Good ones lower complexity by killing obscurity.

01 Why comments exist

Comments capture knowledge that cannot be expressed in the code itself — intent, rationale, units, invariants, contracts.

In plain English analogy

Code is the recipe steps; a comment is the chef's margin note — “this resting step is what keeps it from going rubbery.” The steps tell you what to do; the note tells you why, so the next cook doesn't “optimise” it away.

The usual excuses don't survive scrutiny: “good code is self-documenting” (names can't carry units, contracts, or rationale), “no time” (the reader pays far more time than you save), and “comments go stale” (true only if you put them in the wrong place — keep them next to the code they describe).

02 Different level, not the same level

A useful comment is at a different level of detail than the code — either lower (precision: units, edge cases, what None means) or higher (intuition: what this does and why). A comment that restates the code adds noise and rots.

Restates the code

i += 1 # add one to i — says nothing the code doesn't, and is one more thing to keep in sync.

Adds what code can't

# retries are capped at 5; beyond that the upstream rate-limits us — rationale the code can't show.

03 From noise to value

Before · noise
def poll(timeout):
    # set the deadline
    deadline = now() + timeout
    # loop until deadline
    while now() < deadline:
        # check readiness
        if ready():
            return True   # return true
    # return false
    return False
After · value
def poll(timeout):
    """Wait up to `timeout` SECONDS for readiness.

    Returns True as soon as ready, else False at the
    deadline. Busy-spins (no sleep) for sub-ms latency;
    pass a small timeout if CPU matters.
    """
    deadline = now() + timeout   # now(): monotonic seconds
    while now() < deadline:
        if ready():
            return True
    return False

Why it's better: the “after” comments state units (seconds), the contract (return values), and a non-obvious design choice (busy-spin) — none of which the code can say. The line-by-line restatements are deleted, so nothing can drift out of sync.

04 Write the comment first

Writing the interface comment before the implementation turns commenting into a design tool. If the comment is long or awkward, the abstraction is too complex — fix the design, not the prose. As a bonus, comments written first stay in sync because they shaped the code.

Red flag gotcha

Comments that echo the code (rot bait), and the “self-documenting code” myth used to skip comments entirely. A perfect name still can't tell you the units, the valid range, or why a surprising choice was made.

05 Check yourself

Which comment is worth writing?

The units/contract comment. It records something the code genuinely cannot express (which origin, which unit) — exactly the obscurity a comment should remove. The other two restate what's already obvious and will only rot.
