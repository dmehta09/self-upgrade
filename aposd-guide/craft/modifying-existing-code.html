Everyday craft

Modifying existing code.

Most design doesn't happen on green fields — it happens inside systems that already exist. Every change you make either improves the design or erodes it; there is no neutral edit. Chapter 16 is about making sure it's the former.

01 Stay strategic when changing code

The ideal: after each change, the system looks as if it had been designed that way from the start. If you're not making the design better, you're probably making it worse.

In plain English analogy

Home repairs. A leaky pipe joint can be wrapped in tape in two minutes, or the joint can be fixed properly in an hour. One taped joint is fine; ten taped joints later, nobody dares touch the plumbing — every repair now starts with “careful, don't disturb the tape.”

The trap is the smallest possible change mindset: “the safest edit is the tiniest one.” Each quick patch adds a special case, a dependency, or a flag — and because changes compound, a system maintained this way drifts into tactical mush one harmless edit at a time. The strategic move: ask “is the current design still the best one, given this change?” — and if not, redesign the part you're touching.

See also complexity

This is the maintenance-time face of the investment mindset — the same 10–20% premium, paid on every change. See Strategic vs tactical.

02 The quick-patch trap

Three bug tickets, three “minimal” fixes — and notify_user is now a museum of special cases. The strategic version redesigns just the touched function, so the third fix becomes data, not another branch.

Before · patched
def notify_user(user, msg, channel):
    if channel == "sms":
        if user.country == "IN":   # fix #3812
            msg = msg[:140]
        send_sms(user.phone, msg)
    elif channel == "email":
        if user.plan == "free":    # fix #4101
            msg += AD_FOOTER
        send_email(user.email, msg)
    elif channel == "push":
        if not user.push_token:    # fix #4216
            send_email(user.email, msg)
        else:
            send_push(user.push_token, msg)
After · redesigned
CHANNELS = {
    "sms":   Channel(send_sms, lambda u: u.phone,
                     prep=clip_to_country_limit),
    "email": Channel(send_email, lambda u: u.email,
                     prep=footer_for_free_plan),
    "push":  Channel(send_push, lambda u: u.push_token,
                     fallback="email"),
}

def notify_user(user, msg, channel):
    ch = CHANNELS[channel]
    if not ch.addr(user) and ch.fallback:
        ch = CHANNELS[ch.fallback]
    ch.send(ch.addr(user), ch.prep(msg, user))

Why it's better: each fix is now one row in a table instead of one more branch in a minefield — the next channel quirk is data, and notify_user reads as if it were designed for per-channel rules from day one.

03 Comments live with the code

Documentation belongs as close as possible to the code it describes. The further away a comment lives, the faster it rots — and the less likely the next reader ever sees it.

The gradient is real: a comment on the line it explains almost always gets updated with it; a docstring usually does; a design doc sometimes; a commit message never. So when you change code, updating its comments is part of the change — not optional cleanup, not a follow-up ticket.

Buried in the commit log

git commit -m "must flush before reorder, else replay corrupts" — a subtle invariant, recorded exactly where the next reader will never look.

Next to the code

# flush BEFORE reordering: replay assumes on-disk order — the same invariant, one line above the call it protects.

Red flag — the commit-message trap gotcha

Explaining a subtle invariant only in the commit message (or the PR description, or a chat thread). Developers read code, not logs — if the information matters for using or changing the code, it belongs in the code. Commit messages are for the change; comments are for the code.

04 Keep it honest

Before pushing, review your own diff and ask two questions: “does the design read as intended-from-the-start, or as patched?” and “did I update every comment my change invalidated?” A stale comment you left behind is a landmine with your name on it.

One more smell: duplicated comments. If the same explanation appears in three places, two of them will rot. Keep one canonical copy where it's most natural, and have the other sites reference it — “see the comment on flush()” beats a drifting photocopy.

05 Check yourself

You're fixing a bug in a gnarly function. The “smallest possible change” is one more if. What does chapter 16 say?

Redesign the touched part. The smallest-change mindset adds a special case per fix, and patches compound into tactical mush. “Later” never comes — and if you're not making the design better, you're probably making it worse.
