Deep modules · the core move

Deep modules.

This is the central idea of the whole book. A module is any unit with an interface and an implementation — a function, a class, a service. The best modules are deep: a simple interface hiding a lot of power. Get this one habit and most other rules follow.

01 Interface vs implementation

A module's interface is everything a user must know to use it. Its implementation is how it actually works. A good abstraction hides the second behind a small first.

In plain English analogy

A deep module is a microwave: one button (“+30s”) commands a magnetron, timer, and turntable you never think about. A shallow module is a light switch wired to another light switch — an extra thing to flip that adds no power of its own.

02 Deep vs shallow

Picture a module as a rectangle. The top edge is the interface (its cost — what you must learn); the area is the functionality (its benefit). You want much more area than edge.

Cost = interface · Benefit = functionality
Deep: a small interface over deep functionality — high benefit, low cost. Shallow: the interface is nearly as big as what's behind it — you pay to learn it and gain little.

The classic deep module is Unix file I/O: just open, read, write, close, lseek — five calls hiding disk layout, buffering, permissions, and scheduling. The classic shallow one is a class that makes you stack three objects just to read a file with a buffer.

03 Make a shallow class deep

Getters and setters are the purest shallow interface: they expose the implementation one field at a time and push the rules onto every caller. A deep method swallows the rule.

Before · shallow
class Cursor:
    def get_line(self): return self._line
    def set_line(self, n): self._line = n
    def get_col(self): return self._col
    def set_col(self, n): self._col = n

# every caller must know the rule
# "a new line resets the column":
cur.set_line(cur.get_line() + 1)
cur.set_col(0)
After · deep
class Cursor:
    def move_to_next_line(self):
        self._line += 1
        self._col = 0      # the rule lives here, once

# callers just say what they mean
cur.move_to_next_line()

Why it's better: the shallow class leaks the “new line resets column” rule to every caller — miss it once and you have a bug. The deep method hides the rule behind a name that says intent. Smaller interface, more power.

04 Beware classitis

Red flag — classitis gotcha

The belief that classes/methods should be small, taken to an extreme, breeds lots of tiny shallow classes. Each adds interface to learn and glue code to write, while hiding almost nothing. “More, smaller units” is not automatically simpler — depth is the goal, not size.

Splitting one deep class into five shallow ones moves complexity from inside the class (where it was hidden) out into the connections between classes (where everyone sees it). Only split when each piece is independently deeper than the whole.

05 Check yourself

Which interface is deeper?

The Unix calls. Depth is benefit-over-cost: a tiny interface commanding enormous machinery. Sixteen getters/setters are almost pure interface with no hiding, and “more methods” usually means a shallower, not richer, module.
