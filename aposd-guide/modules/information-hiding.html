Deep modules · the core move

Information hiding & leakage.

Depth comes from hiding. Each module should bury a design decision — a piece of knowledge — behind its interface, so the rest of the system never has to know it. When the same knowledge shows up in two modules, you have a leak, and a dependency that will bite.

01 Hide a design decision

A well-designed module encapsulates one piece of knowledge — a format, an algorithm, a policy — so changing that decision touches only that module.

In plain English analogy

A vending machine hides its whole mechanism behind two buttons. You don't know — or care — how it routes coins or drops cans. The maker can swap the entire insides and your “interface” (press B4) never changes. That freedom is information hiding.

02 Information leakage

Leakage is when one design decision is reflected in multiple modules, coupling them.

The tell: you change one module and a “separate” one must change in lockstep. If two classes both know the on-disk layout of a file, the format has leaked across both — they're secretly one decision wearing two hats. Leakage is the single most common source of unnecessary dependencies.

Red flag — temporal decomposition gotcha

Designing modules around the order things happen (“first read, then process, then write”) instead of around knowledge. It feels natural but it scatters the same decision across the read step and the write step — guaranteed leakage. Organise by what a module knows, not when it runs.

03 Plug the leak

Splitting by execution order gives a reader and a writer that both hard-code the format. Splitting by knowledge gives one module that owns it.

Before · leaky
# format knowledge duplicated in BOTH classes
class ConfigReader:
    def load(self, path):
        cfg = {}
        for line in open(path):
            key, val = line.split("=", 1)   # format!
            cfg[key.strip()] = val.strip()
        return cfg

class ConfigWriter:
    def save(self, path, cfg):
        with open(path, "w") as f:
            for key, val in cfg.items():
                f.write(f"{key}={val}\n")    # format again!
# change "=" to ":" → must edit two classes in sync
After · hidden
# one module OWNS the format; nobody else knows it
class Config:
    SEP = "="                       # the one decision

    @classmethod
    def load(cls, path):
        cfg = {}
        for line in open(path):
            key, val = line.split(cls.SEP, 1)
            cfg[key.strip()] = val.strip()
        return cfg

    @classmethod
    def save(cls, path, cfg):
        with open(path, "w") as f:
            for key, val in cfg.items():
                f.write(f"{key}{cls.SEP}{val}\n")

Why it's better: the format now lives in exactly one place. Changing the separator is a one-line edit, and no other module even knows a separator exists. The leak — and its lockstep dependency — is gone.

04 What to hide

Good things to bury behind an interface: file/wire formats, choice of data structure, an algorithm, units and encodings, the existence of a cache, retry/backoff policy. The test: could I change this decision later without any other module noticing? If not, the knowledge has leaked.

See also lld guide

Information hiding is the soul of encapsulation. For the OOP framing, see the four pillars in the LLD guide.

05 Check yourself

You change a date format in one module and three others break. What happened?

Leakage. One design decision (the date format) lives in four places, so they're coupled even though they look independent. The fix is to hide the format behind a single module the others call.
