Deep modules · the core move

Pull complexity down · together or apart.

Two closely-related judgment calls. First: when complexity is unavoidable, who absorbs it — the module or its users? Pull it down, into the module. Second: should two pieces of code live together or apart? A few clear tests decide.

01 Pull complexity downward

A simple interface matters more than a simple implementation. When in doubt, let the module's author suffer the complexity so its many users don't have to.

In plain English analogy

A great restaurant hides the chaos of the kitchen. You say “the salmon,” not “sear at 200°C for four minutes, rest two.” One author handles the hard part once; thousands of diners get a one-word interface. Pushing the recipe onto every diner would be absurd — yet config-heavy APIs do exactly that.

02 The configuration-parameter trap

Config parameters are often complexity pushed upward: instead of solving a problem, the module hands it to the caller — who usually has less context to choose well. Prefer to compute a sensible default inside, and let callers override only when they truly need to.

Before · pushed up
def make_client(host, port, timeout, retries,
                backoff, pool_size, keepalive):
    ...

# every caller must choose seven values
# they don't understand and can't get right
client = make_client("api", 443, 30, 5,
                     2.0, 20, True)
After · pulled down
def make_client(host, port=443, **overrides):
    cfg = dict(timeout=30, retries=5, backoff=2.0,
               pool_size=20, keepalive=True)  # good defaults
    cfg.update(overrides)                     # escape hatch
    ...

# the common case is trivial; expertise lives
# in the module, where it belongs
client = make_client("api")

Why it's better: the author chooses defaults once, with the most context. Callers get a one-argument interface and can still override in the rare case they know better. Complexity moved down, where it's cheapest.

Red flag gotcha

A pile of required knobs each caller must tune is complexity dumped on the people with the least context. Don't pull complexity down so far it disappears into a single magic blob, though — pull it to the level that can handle it best.

03 Better together or better apart?

When deciding whether two chunks belong in one module or two, Ousterhout's tests are concrete:

Bring together if…
they share information; they're (nearly) always used together; combining simplifies the interface; or it removes duplication.
Keep apart if…
doing so separates general-purpose code from special-purpose code — the general part can then be reused and stay clean.
Repetition → together
The same snippet copied in several places is a sign it wants to be one module. Duplication is leaked knowledge.
Conjoined methods → together
If you can't understand method A without also reading method B (and vice-versa), the split is fake — it added an interface without adding independence.

04 Check yourself

Your API requires callers to pass timeout, retries, and backoff on every call. What's the better design?

Defaults inside, override optional. Most callers have less context than the module author, so required knobs push complexity to the worst place to handle it. Pull it down: sensible defaults, with an escape hatch.
