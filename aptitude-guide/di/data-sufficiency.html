Data Interpretation · data sufficiency

Data sufficiency.

A weird-looking format that's actually a gift: you don't have to find the answer, only decide whether the clues are enough to find it. Judge, don't solve.

01 The idea

You get a question plus two statements, (1) and (2). Your job is to decide if they're SUFFICIENT to pin down a unique answer — not to compute the value.

The five answer choices are always the same: (1) alone, (2) alone, both together, either alone, or neither. Test each statement on its own first, then together only if needed.

In plain English analogy

It's a detective asking "do I have enough evidence to convict?" — not "who did it?" You don't run the whole trial; the moment the clues point to one unique answer, you stop. Knowing it's solvable is the win.

02 The five-way logic & decision path

Always check (1) alone, then (2) alone, then (combine only if both failed). The branch you land on names the answer.

Decision tree — test alone, then together
Five outcomes: (1) only · (2) only · either alone · both needed · neither. Stop at the first branch that decides it.
(1) alone
Statement 1 fixes a unique answer; statement 2 does not.
(2) alone
Statement 2 fixes it; statement 1 does not.
Both together
Neither alone works, but combined they pin it down.
Either alone
Each one independently is enough.
Neither
Even together they leave more than one answer.
Common trap gotcha

Never fully solve — the moment a statement gives one unique answer, mark it sufficient and stop computing. For a yes/no question like "is x positive?", you only need the sign, not the value: "x = 5" and "x² = 9 with x > 0" are both sufficient. And the two statements never contradict each other — if your work makes them clash, you've misread one.

03 A clean approach

Hide statement (2), judge (1); hide (1), judge (2). Combine only if both alone failed. "Could the answer be two different values?" → insufficient.

Slow / wrong

Grind both statements into the full numeric answer, then second-guess which choice to pick — burning a minute you don't have.

Fast / right

Ask only "does this force one answer?" Mark sufficient/insufficient and move on. Decidability, not arithmetic.

"Is n even?" — Statement (1): n = 2k for some integer k. Statement (1) alone is:

Sufficient. The question is yes/no, not "what is n". "n = 2k for integer k" guarantees n is even — a definite "yes" every time — so it's sufficient even though n's value is unknown.

04 Solve it fast

In data sufficiency, what are you actually deciding?warm-up
Solve it

Whether the statements are sufficient to answer — not the final numeric value itself.

The fast way shortcut

Reframe every DS question as "can I answer?", never "what is the answer?". That single switch saves the most time.

Value of integer x? (1) x > 5 (2) x < 7. Using both statements, x = ?core
Solve it

Alone, each leaves many values. Together: 5 < x < 7 with x an integer → only x = 6. Both statements are needed.

The fast way shortcut

The word integer is doing the work: it squeezes the open range 5 < x < 7 down to a single point. Drop "integer" and it would be insufficient.

When have you done enough work on a DS item?stretch
Solve it

The instant you know it's answerable (or that it isn't). Computing the full value past that point is wasted time.

The fast way shortcut

Try to break it: can you find two different valid answers under the statement? One counter-example proves it insufficient — stop instantly.
