Part II · Distributed Data · Chapter 7

Transactions.

A transaction groups several reads and writes into one all-or-nothing unit. Its job is to be a safety blanket: it lets the application pretend there are no concurrent users and no partial failures. The whole chapter is about how strong that blanket really is — and what it costs to make it stronger.

01 What ACID actually promises

A transaction either happens completely or not at all, and runs as if it had the database to itself. That illusion is built from four guarantees — but the word ACID hides as much as it reveals.

In plain English analogy

A bank transfer is two steps: debit one account, credit the other. If the power dies between them, money must not vanish — so the bank treats the pair as a single sealed envelope: either both entries land, or neither does. And while the teller works, no one else may see the half-finished state. That sealed-envelope, no-peeking promise is a transaction.

Atomicity

All or nothing
If any write in the transaction fails, the whole thing aborts and rolls back. Nothing partial survives. (Not about concurrency — about abortability.)

Consistency

The app's invariants hold
The odd one out: this is your job, not the database's. The DB only provides A, I, and D so your code can keep its invariants true.

Isolation

As if alone
Concurrent transactions don't step on each other — each runs as though it were the only one. The hard part, and the rest of this chapter.

Durability

Once committed, it stays
After commit, data survives a crash — written to disk, and usually replicated. (Even this is a spectrum, not an absolute.)

02 The race conditions isolation must stop

Weak isolation lets concurrent transactions interfere in specific, named ways. Knowing the anomalies is how you pick a level:

Dirty read / dirty write

Reading another transaction's uncommitted write (dirty read), or overwriting it (dirty write). The floor most databases prevent — that's read committed.

Read skew (non-repeatable read)

You read row A, someone commits, you read row B — and the two are now inconsistent (e.g. money in flight between accounts). Fixed by snapshot isolation: read from one consistent point in time.

Lost update

Two read-modify-write cycles race; one clobbers the other (counter increments, wiki edits). Fixed with atomic ops, explicit locks (SELECT … FOR UPDATE), or automatic detection.

Write skew & phantoms

Each transaction reads, checks a condition, and writes — individually fine, but together they break an invariant (both on-call doctors sign off at once). The subtle one that only serializable truly prevents.

03 Isolation levels — the dial

Isolation is a dial from “fast and loose” to “correct and costly.” Most databases default to a weak level for performance, so you must know which anomalies your data can't tolerate.

04 Three ways to be serializable

If serializable is so safe, why isn't it the default? Because every implementation pays for it differently:

Actual serial execution

Just run one transaction at a time on a single thread (VoltDB, Redis). Trivially correct — viable now that RAM is large and transactions are short. No parallelism, so it needs stored procedures and partitioning.

Two-phase locking (2PL)

The classic: readers and writers block each other with shared/exclusive locks. Correct but pessimistic — contention, latency, and deadlocks that must be detected and aborted.

Serializable Snapshot Isolation (SSI)

The modern winner (PostgreSQL's SERIALIZABLE): optimistic. Let transactions run on a snapshot without blocking, track their read/write sets, and at commit time check whether they actually conflicted — if so, abort and retry. Full serializability with far less contention, as long as conflicts are rare.

Two doctors are on call. Each runs a transaction that checks “at least one other doctor is on call” and then takes themselves off. Run concurrently under snapshot isolation, both checks pass and both go off call — now nobody is on call. What is this?

Right: this is the canonical write skew. Each transaction's read was still true when it read, but their writes together violate the invariant. Snapshot isolation can't see it — only serializable isolation (or an explicit lock on the rows they read) prevents it.
