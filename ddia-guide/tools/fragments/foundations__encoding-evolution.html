Part I · Foundations · Chapter 4

Encoding & evolution.

Data in memory is pointers and objects; data on disk or a wire is just bytes. Turning one into the other is encoding. Get it right and old and new versions of your code can keep talking to each other through a deploy — get it wrong and a rollout becomes an outage.

01 Why encoding exists

In-memory objects can't leave the process. To store or send them you encode (serialize) to bytes; to use them again you decode. The format you choose decides size, speed, and — crucially — how gracefully your schema can change.

In plain English analogy

You can't mail a thought — you write it as letters, post it, and the reader reconstructs the thought. Encoding is the same: collapse a rich in-memory object into a flat stream of bytes for travel, then rebuild it on the other side. Both sides must agree on the alphabet.

02 Textual vs binary-with-schema

Textual · JSON / XML / CSV

Human-readable and universal. But verbose, ambiguous about numbers (is it an int? how big?), and the field names ship in every record. Great for APIs and config; wasteful at scale.

Binary with a schema · Protobuf / Thrift / Avro

A schema declares the fields once; records carry compact field tags, not names. Far smaller and faster, and the schema doubles as documentation and a compatibility contract.

The trick that makes binary formats compact and evolvable is the numeric tag on each field:

message Person {              // a Protobuf-style schema
  string name      = 1;       // field tag 1 — its identity forever
  int32  birth_year = 2;
  string city      = 3;       // NEW field added later (see below)
}

On the wire a record says “tag 1 = Bill, tag 2 = 1955” — never the word name. The tag is the contract; the human name can change freely.

03 Schema evolution — the whole point

During a rolling deploy, old and new code run at the same time, reading each other's data. So a schema change must keep working in both directions:

Backward compatible

New code reads old data. Easy — new code knows the old fields. (A new reader just handles a missing new field.)

Forward compatible

Old code reads new data. Harder — old code must ignore fields it doesn't recognise rather than choke on them.

The two unbreakable rules

1. Only add fields as optional (or with a default) — a required new field breaks old writers. 2. Never reuse or renumber a tag — the tag is the identity; reusing tag 3 for something new makes old data decode as garbage. Follow both and you can evolve a schema for years without coordinated downtime.

04 Where encoded data flows

Compatibility matters because encoded data crosses boundaries between code versions in three ways:

Through databases
The writer may be newer than the reader (or vice-versa). Data outlives code — a row written years ago must still decode. Beware: old code that reads + rewrites a row can silently drop new fields it didn't understand.
Through services (REST / RPC)
Clients and servers deploy independently, so a server must accept old requests and clients must accept old responses. API versioning is schema evolution by another name.
Through async messages (queues)
A producer encodes; a consumer — possibly an older or newer build — decodes later. The broker just moves bytes, so the schema is the only contract.

You add a new field to a message schema and deploy gradually. What keeps the rollout from breaking?

Right: optional + a fresh tag keeps it backward-compatible (new readers cope with old data) and forward-compatible (old readers ignore the unknown field). Required fields and reused tags are exactly what break rolling deploys.
