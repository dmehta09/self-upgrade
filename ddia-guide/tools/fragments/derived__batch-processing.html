Part III · Derived Data · Chapter 10

Batch processing.

Everything so far served live requests. Batch processing is the opposite shape: take a large, fixed input, grind through all of it, and produce a derived output — no user waiting on the other end. It's how search indexes, recommendation models, and reports get built, and its ideas quietly underpin the whole derived-data world.

01 The batch mindset

Batch jobs read immutable input and write fresh output, touching nothing in place. That single property is a superpower: a job that fails can just be re-run, the same input always gives the same output, and you can experiment fearlessly because the source data is never harmed.

In plain English analogy

Online services are like a restaurant kitchen — orders arrive nonstop and you cook each to order, fast. Batch processing is like a cannery: once a day a giant fixed pile of tomatoes comes in, the line runs end to end, and out comes a pallet of cans. Nobody's waiting at the counter, so you optimise for throughput, not latency — and if a machine jams, you just run the batch again.

The intellectual ancestor is the Unix philosophy: small tools that each do one thing, share a uniform interface (a stream of bytes / lines), and compose with pipes — cat log | grep ERROR | sort | uniq -c. MapReduce is essentially that idea, scaled across thousands of machines.

02 MapReduce — map, shuffle, reduce

MapReduce runs a job over a distributed filesystem (HDFS) in three movements. Map transforms each input record into key-value pairs. The framework's shuffle sorts and groups every pair by key. Reduce then sees all values for one key together and aggregates them. Watch one record flow through:

The shuffle is where joins happen: emit both sides of the join with the same join key, and the reducer sees them side by side (a reduce-side join). Skew — one hot key with far more values than the rest — is the classic batch performance problem.

03 Beyond MapReduce — dataflow engines

MapReduce writes every intermediate result to disk, and a multi-stage job becomes a chain of separate MapReduce jobs — slow. Modern dataflow engines (Spark, Flink, Tez) model the whole job as one graph of operators and keep intermediate data in memory, recomputing lost pieces from lineage instead of always materialising.

04 The real point: building derived data

A batch job's output is derived data — a search index, a recommendation model, a daily report. Because the input is immutable and the transformation is deterministic, the output is a pure function of the input: lose it and you rebuild it; change the code and you reprocess from scratch. This is the seed of Part III's big idea — keep one source of truth, and treat everything else as a view you can always regenerate.

Why can a MapReduce task that crashes halfway simply be re-run, with no risk of corrupting results?

Right: batch processing never mutates its input. A task reads immutable data and writes new output, so a failed task is just retried on the same input — no locks, no transactions, no partial-update hazards. That retry-safety is exactly why immutability is so powerful.
