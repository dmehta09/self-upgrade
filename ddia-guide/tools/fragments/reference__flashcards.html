01 The deck

0/0 known

  • Fault vs failure

    A fault is one component deviating from spec; a failure is the whole system stopping. The goal of reliability is to stop faults becoming failures.

  • The three concerns of a data system

    Reliability (tolerate faults), scalability (handle growth), maintainability (operability, simplicity, evolvability).

  • Why report percentiles, not the mean?

    The average hides the tail. Users feel the slowest few percent — report p50/p95/p99 and write SLAs on p99 / p99.9.

  • Tail-latency amplification

    When one request waits on several backends, it's only as fast as the slowest — so its effective high-percentile latency climbs as fan-out grows.

  • Load parameter

    A number that describes load (QPS, followers/user, fan-out). “Is it scalable?” is meaningless until you name what grows.

  • Fan-out: on write vs on read

    On write = precompute each follower's timeline (fast reads, costly celebrity writes). On read = assemble at query time (cheap writes, heavy reads). Twitter shipped a hybrid.

  • Scale up vs scale out

    Up = a bigger machine (simple, but capped). Out = more machines (unbounded, but you take on distributed-systems hardness).

  • Accidental vs essential complexity

    Essential is inherent to the problem; accidental comes from our implementation. Maintainability = killing accidental complexity with good abstractions.

  • The impedance mismatch

    The awkward translation between relational tables and the nested objects in application code. The document model reduces it for tree-shaped data.

  • When does the document model win?

    Self-contained, one-to-many data read as a unit — a résumé, an order, a product. One read, great locality, no joins needed.

  • When do relational / graph win?

    many-to-one and many-to-many data. Relational lets the DB do joins; graph excels at dense, variable-depth connections (social, fraud, recs).

  • Schema-on-read vs schema-on-write

    On-read = structure interpreted when reading (flexible, no migration to add a field). On-write = enforced when writing (guaranteed shape, needs a migration).

  • Locality (data model)

    Keeping data that's accessed together physically together, so one read fetches it all. A core strength of the document model.

  • Declarative vs imperative queries

    Declarative (SQL/Cypher) says what you want; the engine picks how and can parallelise. Imperative spells out the steps, pinning the execution order.

  • Property graph

    A model of vertices and edges where both can carry properties. Built for many-to-many, variable relationships; queried declaratively with Cypher.

  • LSM-tree vs B-tree

    LSM = append to a sorted memtable → immutable SSTables → compaction (write-optimised). B-tree = fixed pages updated in place + WAL (read-optimised; the relational default).

  • SSTable & compaction

    An SSTable is an immutable file of key-sorted entries. Compaction merges several in the background and drops overwritten/deleted keys, keeping reads fast and space tight.

  • An index is never free

    Every index speeds reads but slows writes (it must be kept up to date). Add indexes deliberately — the core trade-off of all storage engines.

  • OLTP vs OLAP (row vs column)

    OLTP = small key-based reads/writes → row-oriented. OLAP = scan few columns over many rows → column-oriented (compresses well), in a separate data warehouse.

  • Backward vs forward compatibility

    Backward = new code reads old data (easy). Forward = old code reads new data (must ignore unknown fields). Rolling deploys need both, since versions coexist.

  • Field tags (Protobuf/Thrift/Avro)

    Binary formats carry a numeric tag per field, not its name. To evolve safely: add fields as optional with a new tag, and never reuse or renumber an existing tag.

  • Why replicate data?

    Three wins: availability (survive a node failure), latency (a copy near each user), and read throughput (spread reads across replicas). The cost is keeping copies consistent.

  • Single-leader replication

    One replica (the leader) takes all writes and streams a replication log to followers, which replay it in order. Reads can hit any replica. Simple and the common default.

  • Synchronous vs asynchronous replication

    Sync: leader waits for the follower's ack — guaranteed fresh, but a slow follower blocks writes. Async: leader acks at once — fast and resilient, but a crash can lose un-replicated writes.

  • Replication lag

    The window where an async follower is behind the leader. It's eventually consistent — but “eventually” can be long, and reads in that window see stale data.

  • Read-your-writes

    A user must always see their own recent writes. Fix the “I edited it but it's gone” bug by routing a user's reads to the leader or a fresh-enough replica.

  • Monotonic reads

    Time must not appear to go backwards: once you've seen data, you won't see an older state on a later read. Fix by pinning a user to one replica.

  • Consistent prefix reads

    If writes happen in an order, anyone reading them sees them in that order — no seeing the answer before the question. Matters across partitions.

  • Failover & split brain

    Promote a follower when the leader dies — but an async-promoted leader may miss recent writes, and if the old leader returns you get two leaders (split brain). Automatic failover trades availability pain for correctness risk.

  • Quorum: w + r > n

    Leaderless rule: with n replicas, if writes touch w and reads consult r, then w + r > n forces the read and write sets to overlap — so a read sees the latest write.

  • Replication vs partitioning

    Replication copies the whole dataset to many nodes — for availability. Partitioning splits it across nodes — for scale. Real systems do both: each partition is also replicated.

  • Partition by range vs by hash

    Range keeps keys sorted → fast range scans, but risks hot spots on sequential keys. Hash scatters keys → even load, no hot spot, but range scans hit every partition.

  • Skew & hot spot

    Skew = a partition with disproportionate data/traffic; a hot spot is the extreme case. It caps the whole system at one node's speed — the thing partitioning exists to avoid.

  • Consistent hashing

    Place keys and nodes on a ring; a key belongs to the first node clockwise. Adding/removing a node remaps only one arc (~1/N of keys) instead of everything — unlike hash % N.
