02 The decisions, so far

Choosing a data model

Self-contained, read together?
One-to-many tree (a résumé, order, product) → document. One read, great locality.
Interconnected, many ways in?
many-to-one / many-to-many → relational. Let the DB do the joins.
Densely connected, variable links?
Social graph, recommendations, fraud → graph. Traversals beat join piles.
Don't emulate joins in app code
If you're hand-joining documents, you probably wanted relational/graph.

Schema & queries

Heterogeneous / evolving data?
Schema-on-read — flexible, no migration to add a field.
Want the DB to guarantee shape?
Schema-on-write — enforced on write; changes need a migration.
How to ask for data
Prefer declarative (SQL/Cypher): the engine optimises & parallelises. Imperative loops pin the “how.”

Describing load & performance

Name the load parameter
“Scalable?” is meaningless until you say what grows (QPS, fan-out, data size).
Report percentiles, not the mean
Use p50 / p95 / p99. The average hides the tail users actually feel.
Tail-latency amplification
A request waiting on N backends is as slow as the slowest → its p99 climbs with N.
Scale up vs out
Up (bigger box) is simple but capped; out (more boxes) is the only path past one machine.

Reliability

Fault vs failure
A fault is one part misbehaving; a failure is the whole system stopping. Stop faults becoming failures.
Hardware faults
Expect them → redundancy (replicas, RAID, dual power).
Human faults (the #1 cause)
Good interfaces, sandboxes, fast rollback, telemetry.
Trust by breaking
Trigger faults on purpose (chaos) so you know tolerance works.

Maintainability

Operability
Make ops easy — monitoring, predictability, sane defaults.
Simplicity
Kill accidental complexity with good abstractions. (See APOSD.)
Evolvability
Make change cheap — requirements always move.

Storage engines

Write-heavy / ingestion?
LSM-tree — sequential appends + compaction; high write throughput, tight compression.
Read-heavy / predictable?
B-tree — in-place pages; strong O(log n) reads, one place per key (good for transactions).
An index is never free
It speeds reads and slows writes — add them deliberately.
Analytics (OLAP)?
Column-oriented storage in a separate warehouse; keep heavy scans off the OLTP box.

Encoding & evolution

At scale, over the wire?
Binary + schema (Protobuf/Avro/Thrift) — compact and a compatibility contract. JSON for APIs/config.
Adding a field
Make it optional / defaulted with a new tag — never required.
Never
Reuse or renumber a field tag — old data would decode as garbage.
Rolling deploys
Old + new code coexist → stay both backward (new reads old) and forward (old ignores unknown) compatible.

Replication

Default topology
Single-leader — simplest; all writes to the leader, reads from any replica.
Multi-region or offline writes?
Multi-leader — but you must resolve write conflicts.
Sync vs async
Async is fast + available but can lose recent writes on failover; make one follower synchronous for durability.
Lag anomalies
Provide the guarantee you need: read-your-writes, monotonic reads, consistent prefix.
Leaderless quorum
Pick w + r > n so read and write sets overlap (Dynamo-style).

Partitioning

Need efficient range scans?
By key range — keys stay sorted. Watch for hot spots on sequential keys.
Need even load?
By hash of key — scatters writes, kills hot spots; range scans then hit every partition.
Rebalancing
Never hash % N (remaps everything). Use consistent hashing or a fixed partition count.
Secondary indexes
Local (by document): cheap writes, scatter/gather reads. Global (by term): cheap reads, multi-partition writes.
Pairs with replication
Each partition is also replicated — partitioning is for scale, replication for availability.

Transactions & isolation

Default isolation
Usually read committed — knows nothing of read skew, lost updates, or write skew.
Reading consistent data?
Snapshot isolation (MVCC) — one consistent point in time; kills read skew.
Concurrent read-modify-write?
Guard lost updates: atomic ops, SELECT … FOR UPDATE, or detection.
Invariant across rows?
Only serializable stops write skew. Modern default impl: SSI (optimistic).
“Consistency” in ACID
Is your app's job — the DB supplies A, I, D.

Consistency & consensus

Need recency / one truth?
Linearizable — for locks, uniqueness, leader election. It's slow; don't reach for it by default.
During a partition
CAP forces a choice: CP (refuse, stay correct) or AP (answer, maybe stale). No choice the rest of the time.
Cheapest safe ordering
Causal order — survives partitions; use logical clocks, not wall clocks.
Need everyone to agree?
Consensus = total order broadcast. Don't build it — rent ZooKeeper/etcd.
Cluster size
Odd (3, 5): any two majorities overlap, so split decisions can't both win.
