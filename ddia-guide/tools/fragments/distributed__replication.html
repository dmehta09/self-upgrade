Part II · Distributed Data · Chapter 5

Replication.

Keep a copy of the same data on more than one machine. Do it well and you get lower latency, higher availability, and more read throughput — almost for free. The whole difficulty is one word: change. When the data is updated, how do all the copies stay in step?

01 Why keep copies at all

Replication buys you three things: availability (a node dies, others carry on), latency (a copy near each user), and read throughput (spread reads over many machines). The price you pay is keeping the copies consistent.

In plain English analogy

One master ledger in head office is risky — lose the building, lose the books, and everyone queues at one desk. So you photocopy it to every branch: reads happen locally and instantly, and if one branch burns down the others still have the numbers. The hard part isn't the copies — it's that the moment head office writes a new line, every photocopy is briefly out of date.

If the data never changed, replication would be trivial: copy once, done. It changes constantly, so every strategy below is really an answer to “how do writes propagate to the copies, and what does a reader see in the meantime?”

02 The leader-based model

The most common scheme by far. One replica is the leader (primary/master); the rest are followers (replicas/secondaries). All writes go to the leader. The leader applies the change, then streams it — as a replication log — to every follower, which replays it in the same order. Reads can be served by any replica.

The single decision that defines the system's character: does the leader wait for followers before telling the client “done”?

03 Replication lag and the guarantees that hide it

Asynchronous followers are eventually consistent — given no new writes, they catch up. But “eventually” can be milliseconds or minutes, and in that window users hit confusing anomalies. Three guarantees paper over the three classic ones:

Read-your-writes

You post a comment, reload, and it's gone — your read hit a lagging follower. Fix: read your own recent writes from the leader (or a fresh-enough replica), so you always see your own edits.

Monotonic reads

You refresh and see a comment, refresh again and it vanishes — two reads hit followers at different lag. Fix: pin each user to one replica, so time never appears to move backwards.

Consistent prefix

You see the answer before the question — writes arrive out of order across partitions. Fix: guarantee that anyone reading a sequence of writes sees them in the order they happened.

The trap

“Eventual consistency” sounds harmless until lag spikes. Don't assume it's small — name the guarantee your app actually needs, and provide it explicitly.

Failover isn't free

If the leader dies, a follower is promoted. But an async-promoted leader may be missing the dead leader's last writes — and if the old leader returns, you have two leaders (split brain). Automatic failover trades a hard availability problem for a subtle correctness one; many teams keep a human in the loop.

04 One leader, many leaders, or none

Single-leader is simple but funnels every write through one node — bad across datacenters or offline clients. Two alternatives relax that:

Multi-leader

A leader per datacenter (or per device). Each accepts writes locally and replicates to the others. Great for multi-region and offline editing — but two leaders can edit the same record at once, so you must resolve write conflicts (last-write-wins, merge, or app logic).

Leaderless (Dynamo-style)

No leader: clients write to several replicas directly and read from several too. Used by Cassandra, Riak, DynamoDB. Consistency comes from quorums plus read-repair and anti-entropy, not from a single ordering point.

The leaderless trick is a counting rule. With n replicas, if every write lands on w of them and every read consults r of them, then as long as w + r > n the read and write sets must overlap — so a read is guaranteed to see at least one copy of the latest write:

n = 3            # replicas per key
w = 2            # replicas that must ack a write
r = 2            # replicas consulted on a read

def is_quorum(n, w, r):
    # overlap guaranteed when the write set and read set must intersect
    return w + r > n

assert is_quorum(n, w, r)        # 2 + 2 = 4 > 3  -> a read sees the latest write
assert not is_quorum(3, 1, 1)   # 1 + 1 = 2  !> 3 -> reads may miss recent writes
