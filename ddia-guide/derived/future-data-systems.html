Part III · Derived Data · Chapter 12

The future of data systems.

No single database does everything well, so real systems are stitched together from many specialised stores. This closing chapter argues that the way to keep them all correct and in sync is dataflow: pick one source of truth, and derive everything else from its stream of changes.

01 One source of truth, many views

Stop asking one database to be transactional store, search index, cache, and warehouse at once. Instead: keep a single system of record, and treat every other store as a derived view kept up to date from its changelog. Truth lives in one place; everything else is rebuildable.

In plain English analogy

A serious kitchen doesn't own one machine that boils, bakes, and blends badly. It has specialised appliances — but they all start from the same prepped ingredients. Data systems are heading the same way: one pantry (the source of truth) feeds many appliances (index, cache, warehouse, ML features), each fed by the same stream so nothing drifts out of step.

02 Unbundling the database

A database already does several jobs internally — a write triggers index updates, replication, and materialized-view maintenance. Kleppmann's idea is to unbundle those into separate tools, composed by a stream that carries every change. Dataflow becomes the integration glue — replacing fragile distributed transactions across heterogeneous systems:

Because each view is a pure function of the log, you can add a new index, fix a bug, or change a schema by reprocessing the stream into a fresh view and swapping it in — no risky in-place migration.

04 Correctness, and doing right by data

Spreading data across many derived stores raises the obvious worry: how do you stay correct without distributed transactions? The answer is the end-to-end argument — build correctness from deterministic derivation plus idempotence and dedup (e.g. a unique request ID carried through), so retries and reprocessing are safe. Exactly-once effects emerge without locking everything together.

The book's last word: data has consequences

Kleppmann closes not on technology but on responsibility — privacy, consent, bias, and surveillance. The power to collect and derive data is also the power to harm with it. Build systems that treat data as something held in trust, not merely owned. A fitting end to a book about getting data systems right.

In the dataflow / unbundling approach, why can a search index, a cache, and a warehouse never permanently disagree with each other?

Right: there is exactly one source of truth (the log). Every other store is a pure, rebuildable function of that log, so any temporary lag resolves as each catches up — no view is authoritative, and there's no second truth to conflict with. That's the whole appeal of dataflow over distributed transactions.
