Stream processing.

Batch processing assumes the input is complete. But data never stops arriving — so stream processing takes batch's ideas and runs them continuously on unbounded input: process each event soon after it happens, forever. It's how derived data stays fresh instead of being a day old.

01 Events and streams

An event is a small, immutable record that something happened at a point in time. A stream is an unbounded sequence of them. Stream processing is batch processing without the assumption that the input ever ends.

In plain English analogy

Batch is the cannery processing a fixed pile once a day. Streaming is a conveyor belt that never stops — items keep arriving and you handle each as it passes. You can't wait for "all the input" because there is no all; you keep a little state, update it per item, and emit results continuously. Same recipes as batch, just run forever on a moving belt.

02 Getting events around: two kinds of broker

Producers and consumers are decoupled by a message broker, and there are two very different designs — the distinction matters more than any other in streaming:

Traditional queue (AMQP/JMS)

The broker hands each message to one consumer and deletes it after acknowledgement. Great for distributing tasks (a job queue), but the event is gone once processed — no replay, no second reader.

Log-based (Kafka)

An append-only, partitioned log. Messages are kept (not deleted on read); each consumer tracks its own offset. Many independent consumers, full replay of history, ordering per partition. The backbone of modern streaming.

03 Where streams come from, and how you reason about time

A powerful source of events is the database itself. Change Data Capture (CDC) turns every write to a system of record into a stream other systems can follow; event sourcing goes further and makes the log of events the source of truth, with current state derived by replaying it. Both reveal the stream–table duality: a table is a snapshot of a stream, a stream is the changelog of a table.

Unbounded input forces you to confront time. You compute over windows (tumbling, hopping, sliding), and you must choose between event time (when it happened) and processing time (when you saw it) — they diverge whenever events are delayed, so a window must decide how long to wait for stragglers before it declares itself complete.

Fault tolerance: exactly-once, honestly

Streams achieve "exactly-once" results not by magic but by microbatching / checkpoints plus idempotent writes: replay after a crash is safe because applying the same event twice has no extra effect. The processing may happen more than once; the observable effect happens once.

04 Keeping derived data fresh

The pay-off: a stream processor maintains materialized views that are always up to date. A search index, a cache, a running aggregate, a join of two streams — each is kept current by consuming the event log, so derived data is seconds behind the source instead of a full batch cycle behind.

See also sysdesign-guide

For the operational side of brokers — queues vs pub/sub, delivery guarantees, back-pressure, and dead-letter queues — see Messaging & queues in the System Design Field Guide.

You need several independent systems (a search indexer, an analytics job, an audit trail) to all consume the same event stream, and you want a new consumer to be able to replay history from the beginning. Which broker style fits?

Right: a traditional queue deletes a message once it's acknowledged, so it can't feed multiple independent consumers or replay the past. A log-based broker retains messages and lets each consumer read at its own offset — exactly what fan-out plus replay needs.
