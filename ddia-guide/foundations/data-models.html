Part I · Foundations · Chapter 2

Data models & query languages.

The data model is the most important choice you make — it shapes not just how you store data, but how you think about the problem. Three families dominate: relational (tables), document (self-contained trees), and graph (everything connected). None is “best”; each fits a shape of data.

01 One profile, three models

Pick the model that matches the shape of your relationships: one-to-many → document, many-to-one / many-to-many → relational, densely connected → graph.

In plain English analogy

It's how you organise a library. Relational = shelves by subject with a card catalogue that cross-references everything. Document = each book is a self-contained folder you grab in one go. Graph = a web of “see also” strings connecting every book to every related one. Same knowledge, three very different ways to find it.

02 Relational vs document

The old debate, settled pragmatically: it depends on your data's relationships. The friction that pushed people to document stores is the impedance mismatch — the awkward translation layer between relational tables and the nested objects in application code. A document (JSON) maps straight onto an object tree, so for self-contained, one-to-many data (a résumé, a product, an order), the document model wins on locality: it's all there in one read.

But data loves to connect. The moment you need many-to-one (many people in one city) or many-to-many (people ↔ companies), the relational model's joins — and the graph model — pull ahead. Documents force you to either duplicate data or emulate joins in application code.

03 Schema-on-read vs schema-on-write

“Schemaless” is misleading — there's always a schema; the question is when it's enforced.

Schema-on-read · document

Structure is interpreted when you read. Like a dynamically-typed language — flexible, forgiving of heterogeneous or evolving data. Adding a field is free: new writes just include it.

Schema-on-write · relational

Structure is enforced when you write. Like static typing — the database guarantees shape, catching mistakes early. Changing it means a migration (ALTER TABLE).

Concretely, adding a “middle name” field:

# Schema-on-read (document): no migration — old docs simply lack the field
if "middle_name" in user:          # app handles both shapes
    show(user["middle_name"])

# Schema-on-write (relational): change the schema first, then backfill
# ALTER TABLE users ADD COLUMN middle_name TEXT;
# UPDATE users SET middle_name = split_name(full_name);

Neither is “better.” Schema-on-read shines when records are heterogeneous or the structure is decided by an external system; schema-on-write shines when you want the database to guarantee a consistent shape.

04 Declarative vs imperative queries

How you ask for data matters as much as how you store it.

Declarative (SQL, Cypher, CSS)
You say what you want — “all active users in Seattle” — not how to get it. The engine chooses the execution plan, uses indexes, and can parallelise across cores and machines. You get out of the optimiser's way.
Imperative (a loop in code)
You spell out how: step through records, test each, accumulate. Readable in the small, but it pins down an order, so the engine can't reorder or parallelise it freely.
Why declarative scales

Because you didn't dictate the how, the same query can run faster next year on a smarter engine — or be spread across a cluster — with zero code change. (This is exactly why MapReduce and SQL beat hand-written loops at scale.) Graph data has its own declarative languages: Cypher, SPARQL, Datalog — “find friends-of-friends” is one short pattern, not a nested loop.
