Part II · Distributed Data · Chapter 6

Partitioning.

Replication copies the whole dataset to every node. But when the data is too big — or too busy — for any single machine, you must split it: each partition (shard) lives on a different node. The art is deciding which record goes where, so that load spreads evenly and growing the cluster doesn't reshuffle everything.

01 Why split the data

Replication is for availability; partitioning is for scale. Each partition is a little database of its own — spread them across nodes and both storage and throughput scale with the cluster. Partitioning and replication almost always travel together: each partition is also replicated for safety.

In plain English analogy

One library can't hold every book in the country, so you open branches and decide how to divide the collection. By title's first letter (A–F here, G–M there)? Then everyone researching “Smith” floods one branch — a hot spot. By a shuffled call-number instead? Load spreads evenly, but “give me every author from A–C” now means visiting every branch. That single choice — by range or by hash — is the whole chapter.

The goal is to avoid skew: a partition with disproportionate data or traffic. A maximally skewed partition is a hot spot, and it caps your whole system at the speed of one node — defeating the point of partitioning.

02 Two ways to assign keys

By key range

Contiguous ranges of the key, kept sorted (like an encyclopedia's volumes). Range scans are efficient — “all events in March” reads one partition. Risk: an uneven or sequential key (a timestamp) sends all new writes to one partition — a hot spot.

By hash of key

Hash the key, partition by the hash. Spreads load evenly and tames hot spots. Cost: you destroy ordering, so a range scan must hit every partition. The pragmatic middle ground is a compound key — hash one part, range the rest.

03 The ring — and why rebalancing is the real problem

Hashing fixes skew, but raises a new question: how many partitions, and on which node? The naïve answer node = hash(key) % N is a trap — change N (add or remove a node) and almost every key remaps, moving the entire dataset over the network. Consistent hashing places both keys and nodes on a ring; a key belongs to the first node clockwise. Add a node and only the keys in one arc move.

In practice: a fixed number of partitions

Many systems skip the literal ring and instead create a large fixed number of partitions up front (say 1,000), then hand whole partitions to nodes. Adding a node just steals a few partitions from each existing node — entire partitions move, never individual keys, and the partition count never changes. Same property (move a fraction, not everything), simpler bookkeeping.

04 Finding the data again

Once data is scattered, a client asking for key k needs to reach the right partition — this is request routing, an instance of service discovery. Three designs: let any node forward the request, put a routing tier in front, or make clients partition-aware. A coordination service (ZooKeeper) or a gossip protocol keeps the partition-to-node map current.

Secondary indexes don't partition as cleanly as primary keys, and you pick your poison:

Local index (by document)

Each partition indexes only its own data. Writes are cheap (one partition), but a query on the index must scatter/gather across all partitions. The common default.

Global index (by term)

The index itself is partitioned by term, independent of the data. Reads are cheap (one partition), but a single write may have to update index entries on several partitions, so it's often asynchronous.

You shard a time-series table by an auto-incrementing timestamp, using key-range partitioning. What goes wrong?

Right: a monotonically increasing key sends every new write to the single newest range, so one partition absorbs the entire write load. Fix it by prefixing the key with something that scatters writes (e.g. a hashed or per-source prefix), trading some range-scan locality for even load.
